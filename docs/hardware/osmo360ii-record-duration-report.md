# OSMO 360 II 的 10 秒录像为什么会变长

已修复主机额外等待 STOP 的调度缺口。独立安装包的新原片为自动曝光 **11.277933 秒**、手动曝光 **11.544867 秒**，均录满 10 秒，但尚未达到此前希望的 10～11 秒范围。原来约 15 秒的条件没有复现，不能据此宣称已消除所有设备条件下的偏差。

## 已经查清的部分

**没有发现先等待文件、忘记及时发送 STOP 的错误。** 出问题的那次录像，在 START 完整返回后约 11.05 秒就发出了 STOP；随后才开始等待文件写完。文件等待发生在停止之后，不会被框架加进录像计时。

这里的“10 秒”目前按“保证至少录够 10 秒”执行。程序先等 START 命令完整返回，再留 1 秒启动余量，然后等待目标 10 秒，最后发送 STOP。它不知道相机第一帧究竟何时产生，也不能把 STOP 调用耗时全部解释为仍在录像。因此，这套保守规则可以避免主机主动少录，却不能保证原片恰好为 10 秒。

修复前，程序没有专门在录像截止时唤醒，而是依靠下一轮调度检查。默认轮询间隔为 0.5 秒。配置中的轮询间隔此前没有接入生产会话，进程内唤醒通知器也未装配。这些缺口会额外推迟 STOP，但不足以单独解释多出的约 5 秒。

相机开始产生画面、START 工具完整返回、相机停止采集和 STOP 工具完整返回，是不同的时点。原来那轮的 STOP 调用本身耗时 2.306071 秒；相机实际首帧与末帧没有留存时间依据，不能把它们当成工具返回时点。可确定的是程序采用了保守的返回后计时，并存在额外调度等待；具体设备阶段贡献了多少仍未知。

新采集没有复现约 15 秒，而且自动曝光这次比手动曝光更短。**现有证据不能证明自动曝光就是原因，也不能直接扣除一个固定的 5 秒。** 本次五轮各自只有一次 START 和一次 STOP，原片保留；最终相机状态回调为空闲。

修复前的三轮在可靠 START 返回后 11.365595～11.563733 秒保存 STOP 意图；修复后两轮分别为 11.075766 秒、11.079842 秒，接近原定的 11 秒截止。停止调用分别耗时 0.654041 秒、1.101071 秒。主机调度延迟已减少，设备生效时点仍不能由调用耗时直接推定。

手动曝光轮的文件核实遇到一次元数据查询超时和一次可选预览目录查询超时。原有限核实流程最终以成功状态登记 OSV，CLI 返回 0；本轮没有登记 LRF 预览。这个结果不表示所有 ADB 查询均成功，也不把停止后的文件核实耗时计入录像。

## 还需要分清的事情

相机状态日志中“正在录像”的回调早于 START 工具的完整返回，但这个回调不是首帧时间。它只能证明相机已报告相应状态，不能据此计算应提前多少秒停止。

原来 15.382033 秒样本中，从 START 完整返回到 STOP 完整返回只有 13.354311 秒，相差约 2.03 秒。**如果**沿用当前驱动“STOP 确认表示采集已经停止”的假设，并把普通录像的媒体时间轴视为近似实时采集时间，则约 2 秒内容在 START 完整返回前就已存在。这是带前提的区间推算，不是实际首帧观察，也不能证明预录制。它说明返回后再计时可能把前面已经录下的画面也包含进原片，不能仅靠返回后的等待长度精确决定成片长度。

另一项需要排除的设备设置是“预录制”。[DJI 官方说明](https://repair.dji.com/help/content?customId=01700008789&lang=zh-CN&paperDocType=ARTICLE&re=CN&spaceId=17)指出，开启后会把触发前的缓存一并保存，Osmo 360 系列支持 5 秒等档位。新采集的相机日志显示未开启预录制；原来约 15 秒的两次记录没有保存这项状态，因此不能把它认定为原因。

### 现有日志和媒体时间标签的只读复核

已检查五轮日志中的界面录像计数。每轮最后都显示到 12 秒后归零，但对应原片为 11.277933～12.045367 秒；界面秒数不能直接等同于文件时长。安装包自动曝光轮在界面归零后还出现了编码启动日志，配置是 736×736、2048×896 等低分辨率，无法关联为双路 3840×3840 原片的首帧。

两份安装包原片的首视频包时间戳均为 0，视频轨道也从 0 开始。这能确定片内相对时间，不能确定主机时钟上的实际首帧。`creation_time` 标签记录的是 2000 年；另有 `timecode` 标签和时间码轨道，但没有现场依据说明它与主机 UTC、实际首帧的映射。相机私有数据轨尚未解码，因此这里只说明已核对的可见标签不足以建立新锚点，不声称文件内部绝对没有其他时间信息。

这些观察均不足以支持缩短启动余量，或把界面回调替换为可靠首帧确认；当前仍保留原停止计时规则。

## 已实施的修复与验收标准

用户要求最终时长尽量接近目标，允许少量偏差，并优先保证录满目标。修复让普通录像按原截止唤醒调度，并在背景调用完成时通知重新检查。正式 CLI 同时接入轮询配置和进程内通知器。正常 STOP 仍使用可靠 START 返回加 1 秒启动余量及目标时长；取消不等待正常截止，保存延迟不刷新原确认点，重启恢复继续沿原动作处理。

启用通知器后，回归还复现了“通知和外部取消同时到达时，等待者吞掉取消”的问题。等待实现已改用 Python 3.11 的超时接口，保留外部取消。5958 项单元测试与 429 项相关集成测试通过；软件范围见[验证记录](../camctl/verification.md#普通录像截止唤醒的软件验证2026-10-19)。

设备侧的开始、停止和文件时长差异仍需以实际调用与原片对照核验。若需要改变计时锚点或相机设置，先取得对应依据并更新契约；相机没有提供的设置命令继续保持接口缺口。

每项调整均以“目标 10 秒的真实原片”为最终检查对象，分别记录主机 STOP 时序和媒体时长。软件测试用于证明计时、取消和恢复逻辑，不能代替实际原片测量。

## 尚需确定的验收对象

当前规则优先保证至少录满，保留 1 秒启动余量；[正常录像规格](../architecture/camera-recording.md#正常轻微多录)不要求为了卡秒裁剪全部录像。若验收允许原片约 1～2 秒的偏差，可保留这一规则继续观察。若交付文件必须稳定落在 10～11 秒，需要另行确定是否生成按目标裁剪的 MP4 并保留原 OSV；若原始 OSV 本身必须满足该范围，则仍需官方提供实际起止时刻或定长录像的可靠接口。该选择待用户确定。
