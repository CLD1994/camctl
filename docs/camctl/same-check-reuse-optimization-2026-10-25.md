# 单次检查中的重复读取、解析与构造分析

记录日期：2026-10-25。状态：调查及外部原型对照已完成，正式生产实现尚未修改。本文承接[固定批量写入成本分析](integration-test-batch-write-cost-2026-10-25.md)，聚焦同一次函数调用内部的重复工作。

## 结论和实测效果

可以减少重复工作。优先处理两类情况：程序刚在当前函数中取得的数据，随后又查询或构造一次；程序已经完整检查全部候选文件，发现没有合格预览，却仍为预览再扫描全部成员。

在独立源码副本中，通过运行时替换三个函数完成可行性对照。输入固定为 200 份原片、0 份合格预览，默认范围含 14 份成员，候选批量为 4；原发现页仍按实际 128 份上限划分。每档开始前关闭数据库连接，将同一冻结数据库恢复到相同物理路径，核对文件摘要和完整数据库逻辑摘要。每档都使用原容量测试的 SQL 计数包装，没有开启函数剖析。

| 运行方式 | 写入 | 再次核对已保存结果 | 两者合计 | SQL 调用总数 |
| --- | ---: | ---: | ---: | ---: |
| 原实现，对照前 | 8.143 秒 | 0.839 秒 | 8.982 秒 | 72,227 |
| 仅复用本次页检查的局部数据 | 7.525 秒 | 0.817 秒 | 8.343 秒 | 72,227 |
| 仅省去刚解码事件的第二次结构检查 | 7.875 秒 | 0.980 秒 | 8.855 秒 | 72,227 |
| 仅减少重复成员读取和无预览扫描 | 7.538 秒 | 0.621 秒 | 8.159 秒 | 64,011 |
| 合并三组候选改动 | 6.458 秒 | 0.620 秒 | 7.078 秒 | 64,011 |
| 原实现，对照后 | 8.345 秒 | 0.850 秒 | 9.195 秒 | 72,227 |
| 原实现，开启内存跟踪 | 32.343 秒 | 4.137 秒 | 36.480 秒 | 72,227 |
| 合并候选，开启内存跟踪 | 27.906 秒 | 2.597 秒 | 30.502 秒 | 64,011 |

合并候选相对前后两个普通对照约减少 21%—23% 的操作耗时；内存跟踪样本约减少 16%。SQL 调用少 8,216 次，约减少 11.4%。这些是固定输入下的可行性样本，每档仅一次，原实现前后各一次；没有清空操作系统缓存，不构成稳定性能承诺，不能换算成全量回归节省多少分钟。

八档返回结果相同，保存后的完整数据库逻辑摘要也相同。最大单次取行均为 128，完成组整体计数均为 1。内存跟踪下，写入峰值从 2,194,778 字节变为 2,217,797 字节，核对峰值从 1,926,813 字节变为 1,940,746 字节。该结果表明没有通过扩大常驻缓存换取提速，但单个规模不能证明完整增长边界，仍须运行原容量测试。

## 原页检查：把已经取得的数据留在本次函数里

程序检查一页文件时，必须确认实际文件、首次发现事件、发现页和文件登记事件完整对应。责任入口是 [result_pages.py](../../apps/camctl/src/camctl/persistence/repositories/result_pages.py) 的 `_verify_page_relations`。

| 重复工作 | 建议的处理方式 | 必须保留的检查 |
| --- | --- | --- |
| 每处理一条首次发现事件，都重新执行 `dict(file_ids)`。一页可能包含 128 个身份映射。 | 在函数开始时建立一次身份到文件 ID 的字典，后续循环直接查找。 | 实际文件 ID、完整设备身份和页内身份仍须逐条相符。 |
| 第一遍已经读取各文件的创建事件 ID，后续循环又调用 `row_facts` 取相同字段。 | 只在本次调用中保存文件 ID 到创建事件 ID 的标量映射；比较后随函数返回释放。 | 创建事件必须处于正确事务边界，并与实际首次发现事件精确对应。 |
| 为取得首次发现顺序，对每个页成员再遍历全部首次发现成员。 | 在第一次有序遍历中直接记录需创建的成员和顺序；避免嵌套搜索以及不必要的列表、元组副本。 | 实际创建集合和顺序都须与页内实际差集一致，不能只比较集合。 |

这些局部映射最多跟随当前一页的 128 份文件，不跨调用、连接或事务保留。正式实现建议在首遍直接保留原二元组的引用，避免原型中投影列表新建二元组的额外分配。

本次单独对照中 SQL 次数没有下降。原因是第二次 `row_facts` 已可能命中现有读取缓存，仍需执行缓存入口、键处理和深复制。局部复用省掉的是这些 Python 工作，不能将减少的函数调用直接换算成减少的 SQL。

## 事件解释：同一份刚解码的数据只做一次结构检查

`_verify_page_relations` 从数据库原行调用 `decode_event_row`，后者已经检查事件结构。当前函数随后又分别对首次发现事件和文件登记事件调用 `validate_event_structure`。

建议省去这两处紧邻的第二次结构检查，同时保留所有业务对应比较。适用前提是：对象确实来自刚完成结构检查的解码入口，从解码到使用之间没有修改事件字段、嵌套字典或行集合，也没有写入数据库。这里只使用当前函数的局部值；不能仅凭外层数据类声明不可变，就认定其内部字典也不可变。

该单独样本改善很小，优先级低于成员扫描和页内重复构造。其他事件解释入口同时接收未校验输入，仍须按实际输入来源处理，不能全局移除结构检查。

## 成员检查：复用刚读出的成员，避免没有用途的第二遍扫描

责任入口是 [segment_transactions.py](../../apps/camctl/src/camctl/persistence/repositories/segment_transactions.py) 的 `_verify_scope_members` 和 `_canonical_events`。

检查默认范围时，`read_segment_members` 已经返回经过核验的成员。原路径再按成员 ID 调用 `segment_output_candidate`，重新加载并构造相同成员。建议在当前检查中取得一次对应结果集，直接把刚读取的成员交给既有资格判断函数 `_output_candidate`。不新增另一份资格判定规则；默认范围未知或为空时，仍不读取非空范围才需要的依据。

生成预期事件时，程序先完整扫描候选，产生原片事件；随后重新扫描全部候选，产生预览事件。第一次扫描实际上已经检查所有候选的资格，包括预览。建议在该完整扫描中记录是否出现过合格预览。没有合格预览时，第二遍可以直接结束；出现过时，仍执行完整预览扫描。

| 第一次完整扫描的实际情况 | 后续行为 |
| --- | --- |
| 没有合格预览，且全部实际成员检查成功 | 省去只为产生预览事件而做的第二遍扫描，仍核对最终计数与结束标记。 |
| 至少有一份合格预览 | 保留第二遍，维持全部原片在前、预览在后的事件顺序及来源对应。 |
| 扫描发现成员、配对或原文件事实不一致 | 传播原有错误，按既定规则拒绝；不能解释成“没有预览”。 |

是否执行第二遍由实际扫描结果决定，不能读取申请头的 `preview_count` 来代替检查。生产事件生成、独立重新生成并核对事件、原键恢复核实各自新建自己的扫描和局部标记；任何一方都不继承另一方的结论。

按当前全原片样本的调用路径推导，写入可少构造 `2N + 3R = 442` 次成员，再次核对少 `N + R = 214` 次；N=200，R=14。R 指默认范围游标区间内实际需要判断资格的成员数量，一般情况下不保证等于最终合格原片数量。这里没有为原型另加成员调用计数；SQL 降幅以实测记录为准，不能把这些构造次数直接当成查询次数。

## 复用范围和回归要求

现有[单次事务读取复用](persistence-runtime.md#单次完整事务的读取复用)及[结果页校验范围](persistence-runtime.md#结果页证明的事务与校验阶段范围)继续作为行为依据。每个独立检查仍重新读取实际保存事实；事件生成后、独立检查开始前的清空规则、写入代变化后的失效、三份原始页记录的上限均保持。上述建议只减少一次具体检查内部的重复工作。

正式落地时需要覆盖下列输入与可观察结果。文件和函数拆分是实现建议，验收针对行为。

| 场景 | 应观察到的结果 |
| --- | --- |
| 全原片；真实预览；预览与原片跨页；前若干候选页没有合格成员、后页才出现预览 | 正式事件、来源和默认范围与原实现一致，不能漏掉后页预览。 |
| 申请头将实际预览数量谎报为零或非零 | 根据完整实际候选核对后拒绝，不能借跳过扫描通过。 |
| 默认范围未知、为空、非空；范围缺成员或身份错误 | 合法三态保留区别；缺失或身份错误仍拒绝。 |
| 文件创建关系缺失或改变；新旧文件混合；发现页无新增文件 | 逐条文件关系、实际差集、创建顺序及登记关系继续精确成立或明确拒绝。 |
| 提案形成后依据改变；跨批事件、预览来源或结束标记被篡改 | 有限和有界入口均由独立检查拒绝，整个事务回滚。 |
| 提交结果未知；用原操作键重开核实；后续文件观察改变当前状态 | 按原范围核对已保存结果，不重复分配，不把后续观察当成原保存依据。 |
| 候选批量 4，真实输入 20、200、400 份 | 原容量测试的内存增长、最大取行、整体计数及索引访问门槛全部保持。 |

在同一隔离源码副本中，通过外部 pytest 插件替换相同三个函数，运行了 23 个测试节点展开的 91 个参数实例：全部通过，0 失败、0 错误、0 跳过，退出码 0，pytest 报告总耗时 188.61 秒。实际导入路径、替换后的函数身份及签名均已核对；源码、测试、项目配置和锁文件共 1,139 份，与源码基线逐字节相同，运行前后也没有变化。

该范围包含真实预览和跨页来源、有限与有界入口的事件篡改、独立检查拒绝、晚失败整体回滚、默认范围三态及身份错误、原保存范围完整性、混合新旧文件、创建关系损坏、零差集和 APPEND／INDEX 顺序。原 20／200／400、批量 4 的容量测试也通过，原有取行、计数、索引访问和四个内存增长断言均执行；该节点 call 约 150.84 秒。通过用例的标准输出未被该次 pytest 配置保存，因此不声称取得了三档具体峰值。该耗时不是严格前后对照，也不据此宣称容量用例已稳定提速。

## 建议实施顺序

1. 先提交页内身份字典、创建事件标量和顺序复用。验证混合新旧文件、创建关系损坏、差集与顺序，同时审计相同函数内其他临时列表复制。
2. 再提交范围成员复用和实际无预览时省略第二遍扫描。沿有限、有界、独立核对及恢复入口逐项核实上述状态分类，并补足缺少的反例。
3. 依据单独收益和可读性决定是否整理两处紧邻的重复结构检查。对仍接收未校验对象的入口保留其原责任。
4. 在正式源码上运行相关持久化回归和原 20／200／400 容量用例；以同输入、同测量开关再次对照。原型替换通过不代替正式实现验收，也不代替全量集成测试。

成员枚举值的二次解码也有重复，但上轮剖析中累计仅约 0.063 秒，作为低优先级整理，不计入主要收益。完整解码页长期驻留、跨独立检查传递证明、对含可变子对象的缓存统一改成浅复制，都涉及不同的隔离或资源边界，不属于本方案。
