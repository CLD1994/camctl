# 日志投递、线程与多进程适配

[设计入口](README.md) · [实现总览](implementation.md) · [实施准备](implementation-readiness.md)

本页完整定义日志入口、队列接纳、取消与退出，并说明标准库、Janus 和文件处理器的适配方式。日志配置、通道故障及日志副本的业务规则见[运行日志](../architecture/logging.md)。先读组件分工和投递规则，再核对水位判定与实现适配。

## 普通日志执行与多进程轮换

普通日志复用标准库 `logging` 的日志级别、`LogRecord`、处理器和格式化机制，协程通过可等待的日志入口投递。各个需要写文件日志的 Python 进程独立创建日志入口适配、`QueueHandler`、`janus` 有界队列、`QueueListener` 和 `ConcurrentRotatingFileHandler`；文件处理器来自第三方库 `concurrent-log-handler`。组件职责如下：

| 组件 | 职责与执行位置 |
| --- | --- |
| 异步日志入口与接纳适配 | 在业务协程中检查级别、准备记录并应用分级接纳规则，需要等待空位时通过 `janus.async_q` 异步等待 |
| `QueueHandler` 与同步接纳适配 | 在同步日志调用所在的线程中准备记录，经 `janus.sync_q` 提交并应用共用分级策略，不等待队列空位；接纳自身低于 `ERROR` 的日志及第三方日志 |
| `janus` 有界队列 | 同一进程内以 `async_q` 和 `sync_q` 两个接口共享记录与容量，负责协程和线程间的等待及唤醒 |
| `QueueListener` | 使用本进程的专用日志工作线程从 `janus.sync_q` 取出记录，并调用文件处理器 |
| `ConcurrentRotatingFileHandler` | 在日志线程中协调跨进程文件锁，检查轮换并追加日志 |

`run` 与独立 `submit` 各自持有上述组件，共用同一日志路径及轮换配置。队列是进程内交接通道，进程间通过文件处理器的锁协调；各进程可独立启动、写入及退出。报告子进程需要写入同一文件日志时，也在自身初始化组件。日志处理器、队列及锁对象不跨进程传递，配置从本次 CLI 生效值取得；子进程使用主进程传入的相应配置。

轮换参数从[运行日志配置](../architecture/logging.md#配置与默认值)转换：`session.log_max_size` 换算为字节后提供给 `maxBytes`，`session.log_file_count` 包含正在写入的文件，因此 `backupCount` 为该值减 1。同一路径的各写入进程采用一致的参数与锁位置，配置更新遵守既有停止相关 CLI 后再更新的部署规则。文件锁等待、文件追加和轮换发生在日志线程中；业务线程承担记录准备和入队成本。

日志线程独立于普通文件任务使用的默认线程池，直接消费队列并顺序执行文件处理器。协程与同步入口共享记录准备和接纳规则，路由、原子水位适配及通知见[日志适配](#日志适配与写入完成通知)；跨线程等待与唤醒复用 `janus`。该队列只连接本进程的一个事件循环与同步线程，进程间写入协调仍由文件处理器负责。

| 进程阶段 | 日志组件处理 |
| --- | --- |
| 初始化文件日志 | 在本进程创建组件并启动监听线程；配置或文件初始化失败分别遵守原错误分类 |
| 正常运行 | 协程通过异步入口、同步代码通过同步入口提交记录，本地监听线程调用文件处理器 |
| 文件处理器报告轮换、追加或协调故障 | 按[日志通道故障](../architecture/logging.md#日志通道故障)分类，保留轮换失败但仍可追加与必须禁用文件日志的区别 |
| 正常退出 | 按重要日志取消与退出规则完成必要收场及待投递记录交接，结束日志生产，处理已接纳记录或按日志通道故障规则结束处理，由日志线程按丢弃汇总规则处理一次摘要，再停止监听线程、关闭本进程文件处理器并完成 `janus` 队列及通知任务的关闭 |
| 进程突然终止 | 不保证队列中尚未写出的日志保留；业务恢复继续依据状态数据库 |

复用库的文件锁和轮换能力，项目适配集中于日志入口、按水位接纳、丢弃汇总、配置转换、故障分类及生命周期组织。取消保护、停止标记和通道禁用通知的具体接入方式，以及调小保留数量后的归档清理仍需细化；这些实现必须满足规定的取消、退出及故障契约，库默认行为不能代替它们。正常关闭须在处理已接纳记录后关闭队列，不能把关闭队列等同于记录已写完。依赖版本与目标主机兼容性在实施时锁定和验证。

报告首次失败时，按[日志副本交付规则](../architecture/log-delivery.md#准备与交接)复制当前普通日志文件。业务协程通过正常日志入口记录错误；日志副本交付流程另行确认该错误实际写入并刷新，随后协调共享文件的追加、轮换与复制，保证固定副本包含该错误且日志记录完整。副本保留当前日志的全部原始字节，完整保存后才移入 `ready`；原日志继续留在配置路径供各进程使用。

上述写入完成通知与复制协调遵守[包含触发错误的日志副本](#包含触发错误的日志副本)：副本要求在触发记录入队前绑定，在同一共享锁内完成追加和复制。`QueueListener` 与 `ConcurrentRotatingFileHandler` 通过该项目适配共同提供所需接口。实施时核验库的锁接口及调用顺序，复用现有跨进程锁，并将锁等待和文件操作放在工作线程中；主事件循环异步等待。普通 `await logger.error(...)` 仍以入队完成为返回条件，不为每条普通日志增加文件写入确认，也不等待其他进程的日志队列全部排空。

日志级别遵守[运行日志的部署约定](../architecture/logging.md#配置与默认值)，接纳 `ERROR` 及以上记录。

验收组合真实独立进程与文件处理器，覆盖并发追加和轮换、`submit` 单独运行、一个进程退出而其他进程继续写入、保留数量为 1、调整保留数量及日志通道故障。使用进程内队列的集成测试验证正常退出处理已接纳记录、日志线程执行文件操作，以及普通业务错误与日志错误保持各自分类。

接口依据见 [QueueHandler 与 QueueListener](https://docs.python.org/3.11/library/logging.handlers.html#queuehandler)和 [concurrent-log-handler 使用说明](https://github.com/Preston-Landers/concurrent-log-handler)。

### 日志异步投递入口与有界队列

协程使用 `await logger.error(...)` 形式投递，异步 Logger 的 `debug`、`info`、`warning`、`error`、`critical`、`exception` 方法统一采用可等待接口，保留标准日志常用的消息参数、`extra` 和异常信息语义。日志来源须指向业务调用处，异常信息在等待前捕获。级别检查沿用本次进程生效配置，被配置级别过滤的记录不进入队列。

camctl 自身的 `ERROR` / `CRITICAL` 日志只允许由主事件循环中的协程通过异步入口投递，`exception()` 按 `ERROR` 处理。数据库、文件、报告通信等工作线程通过已有结果或异常通道报告错误，由所属流程的协程统一处理并记录；这些线程可以通过同步入口记录低于 `ERROR` 的日志。主事件循环直接调用的同步函数或回调同样通过结果、异常或既有监督通道报告错误，由所属协程记录。报告子进程的同步工作通过既有任务结果与控制通信报告失败，由主进程所属协程处理和记录。

错误结果的交付不等待日志接纳。数据库线程先按事务实际结果完成必要处理并交付结果，日志不能延迟事务结果交付，也不能成为停止普通执行、录像应急停止等必要故障处理的前置条件。工作线程与所属协程不重复记录同一次重要错误；日志线程自身故障继续遵守[日志通道故障规则](../architecture/logging.md#日志通道故障)。这些调用位置约定适用于 camctl 自身代码，第三方代码仍由同步日志适配接入。

下面定义合法调用入口、日志通道正常可用时的行为分区；通道故障遵守前述故障分类，取消及关闭过程中尚未入队记录的归属遵守[重要日志取消与退出规则](#重要日志等待期间的取消与退出)。

| 调用环境与记录状态 | 处理 |
| --- | --- |
| 任意来源，记录被配置级别过滤 | 直接完成，不入队 |
| 任意来源，记录按共用接纳规则保留且可立即入队 | 完成入队后返回，不等待文件写入 |
| camctl 自身主事件循环中的协程入口，`ERROR` / `CRITICAL` 经共用接纳规则处理后仍无法取得位置 | 异步等待接纳，不因队列满载主动丢弃；等待只暂停调用协程，事件循环可继续处理其他工作 |
| 第三方来源，`ERROR` / `CRITICAL` 经共用接纳规则处理后仍无法取得位置 | 丢弃本条新记录并返回，不等待空位；适用于主事件循环线程和普通工作线程 |
| 任意来源，`WARNING` 遇到过载 | 不采样、不等待空位，队列未满时接纳，满时丢弃本条；通过下述水位规则限制低级别日志，为警告和错误保留接纳空间 |
| 任意来源，`INFO` 遇到过载 | 按下述水位规则独立随机采样或丢弃，不等待空位；概率采用本次进程生效配置 |
| 任意来源，`DEBUG` 遇到过载 | 达到第一水位后丢弃新记录，不等待空位 |

camctl 自身与第三方日志共用一套按级别与水位接纳的策略；`WARNING` / `INFO` / `DEBUG` 均不等待队列空位。来源造成的唯一接纳策略差异是 `ERROR` / `CRITICAL` 满载时的保障：camctl 自身不允许因过载主动丢弃，只通过上述协程入口异步等待，第三方允许丢弃本条。同步与异步入口共用策略实现和队列容量，不各自维护一套采样或水位规则。

按水位接纳及顺序消费遵守[下述规则](#日志按水位接纳并顺序消费)，容量、水位与采样概率由[运行日志配置](../architecture/logging.md#配置与默认值)统一定义，双方来源使用相同配置；因接纳限制丢弃的记录按[计数与退出汇总规则](#日志丢弃计数与退出汇总)处理。文件轮换保留规则、日志通道故障及进程突然终止的边界继续有效。

第三方标准日志经配置的 Handler 接入，先应用共用的级别与接纳策略；需要立即尝试入队时，以 `janus.sync_q.put_nowait()` 的实际结果判断接纳或满载，不采用先检查空位再保证入队的方式。按策略丢弃属于正常接纳分支，不向调用方抛出满载异常、不转为同步文件写入，也不为本条记录创建后台投递任务或反复输出 stderr 错误；后续新记录继续按共用策略处理。队列满载不禁用日志通道，不改变第三方调用本身的业务结果，其他日志错误仍按各自故障规则处理。来源由日志接入配置明确区分，不以当前线程或日志级别推断；具体 Logger 路由在实施时确定，并检查第三方传播设置及重复处理器。

异步入口直接在调用协程中等待接纳，不为每条待投递记录另建后台任务。低级别日志采用可等待的调用形式不表示会等待队列空位；这类记录在同步入口及异步入口均按上述规则立即完成接纳或丢弃判定。队列容量只限制已入队的等待记录，不包含消费者正在处理的记录及等待入队协程持有的记录，不能据此宣称日志总内存已受到固定上限约束。入队成功也不等于文件写入成功。

集成验证须组合真实 `janus` 队列与 `QueueListener`：队列满时 camctl 自身异步入口的重要日志等待，其他业务协程仍能推进，消费释放位置后等待者能够完成接纳；同步和异步入口共用容量，日志线程执行文件处理，普通文件线程池繁忙不占用日志专用执行线程。在接纳条件相同的场景对照双方来源，验证 `WARNING` / `INFO` / `DEBUG` 遵守相同规则且不等待空位，来源只改变重要日志满载时的等待或丢弃分支。第三方重要日志覆盖主事件循环线程和普通工作线程、过滤、入队成功、满载丢弃及腾出位置后再次接纳，确认丢弃分支返回、无后台补投及重复 stderr 错误，并验证来源路由正确。

队列保持满载时，验证数据库操作的实际结果及工作线程错误仍能交付，必要故障处理不以日志接纳为前置条件，由所属协程记录重要错误且不重复投递；审查自身重要日志实际调用入口及执行上下文，覆盖主循环同步辅助函数、工作线程和报告子进程结果处理。还须覆盖多个等待者、异常上下文与调用位置，以及正常退出处理已接纳记录并关闭队列通知资源。取消与正常退出按下述状态分类补充验收。队列能力依据见 [janus 项目说明](https://github.com/aio-libs/janus)。

### 重要日志等待期间的取消与退出

camctl 自身的重要日志已经开始投递、正在等待队列空位时，取消请求不丢弃该记录。记录仍由所属协程持有，直到确认入队，或日志通道实际失效并按既有规则禁用后结束本次投递；再传播待处理的协程取消或完成原有收场，不把取消吞掉并恢复普通业务。重复取消不产生记录副本，也不提前结束这项交接责任。已入队记录归日志消费侧处理，不因调用协程随后取消而撤回。

日志等待保护只延后所属协程的最终结束，不延后必要的业务取消和设备停止。收到取消或会话收场请求时，取消事实保存、停止新增普通动作、录像停止、源读取停止及适用清理，继续按各自契约推进。流程必须在日志等待前完成必要的责任安排，或通过已有取消与监督路径保证这些操作可以在日志等待期间推进；若必要停止只能由当前等待协程执行，须调整该流程的调用顺序或责任分工。仅用取消屏蔽让整个业务流程停在日志等待中，不满足此契约。

下表的“通道可用”也包含轮换失败但仍能可靠追加的情况；单纯队列满载不属于通道失效。

| 本条记录与日志通道状态 | 取消或收场处理 |
| --- | --- |
| 尚未开始本次投递 | 继续按所属业务的取消与错误处理规则决定工作，不因保护机制额外生成记录 |
| 正在等待入队，通道可用，尚无取消请求 | 所属协程异步等待接纳 |
| 正在等待入队，通道可用，收到取消或会话收场请求 | 保留本条及其所有权，必要业务停止继续推进；确认入队后才允许所属协程最终结束 |
| 已确认入队，随后收到取消 | 不撤回、不重新投递；日志线程继续处理，所属协程按原取消或收场规则结束，不必等该条写入文件 |
| 通道实际失效并被禁用，本条尚未入队 | 通知并结束全部受影响的等待，本条按日志通道故障结束，不能宣称入队或写入成功；所属协程继续取消或收场 |
| 通道实际失效并被禁用，本条已经入队或正在处理 | 按已有日志通道故障规则结束处理，不为本条补投，不改变原业务结果 |
| 取消与入队、通道禁用发生竞争 | 以实际接纳阶段确认唯一结果，同一记录最多入队一次；不能因取消通知先到就丢掉已入队记录，也不能因结果竞争再次入队 |
| 进程被强制终止或突然退出 | 不保证内存中待投递、已入队记录和丢弃计数保留 |

通道禁用须传递到接纳侧，唤醒正在等待空位的协程并使后续投递遵守禁用规则；不能只让消费线程停止，再把生产者留在等待中。因通道故障未写出的记录不计入水位、采样或满载丢弃摘要。具体通知和结果表示由日志适配实现，保持日志故障不掩盖业务故障的契约。

正常退出按下列顺序组织：停止新增普通工作，推进必要业务收场及其日志投递；保持日志消费可用，等待现有生产者及其待投递记录完成交接，或按通道故障规则结束投递；确认生产已经结束后，处理完已接纳记录，按既有规则尝试写出一次丢弃摘要；最后停止监听线程并关闭文件处理器、队列及其通知资源。不能提前停止消费者或关闭队列来让尚未完成的重要日志交接看似结束。

日志积压可以延长正常取消收场中的协程结束和正常进程退出，不另设超时后丢弃重要日志的规则，也不承诺固定完成时间。底层系统持续不返回的处置继续遵守第一版已有故障范围。所有待投递记录保持在既有所属流程内，不为规避取消等待另建逐条后台补投任务；接纳侧保护不改变业务责任、状态数据库事实或设备实际结果。

验收覆盖等待前取消、等待中取消、重复取消、入队后取消、取消与接纳竞争、等待期间通道禁用，以及正常收场时队列仍满。使用受控消费者证明：队列暂不释放空位时记录仍被持有，必要设备停止及数据库结果交付仍可推进；释放位置后本条只接纳一次且取消继续生效；禁用通道时所有受影响等待者结束，不宣称日志保存成功、不计为满载丢弃。集成验证先完成生产与投递交接，再处理已接纳记录、退出摘要及组件关闭；重复收场不重复投递或汇总。

### 日志按水位接纳并顺序消费

第一版通过提前限制低级别日志接纳，为 `WARNING`、`ERROR` 和 `CRITICAL` 留出队列空间。每个进程使用一个有界先进先出队列，已接纳记录按实际入队顺序交给文件处理器；不因新日志级别更高而删除、替换或重排已有记录。先入队顺序不等于不同线程中日志调用开始时间的顺序。

设队列总容量为 `C`，第一水位为 `L`，第二水位为 `H`，均按记录条目计量，满足 `0 < L < H < C`。`q` 为接纳判定时已在队列中等待的记录数量，不包含日志线程已取出的记录或尚未入队的等待者。日志先经过配置级别过滤，再按下表处理；表中的丢弃均针对本条新记录。

| 队列状态 | `DEBUG`，任意来源 | `INFO`，任意来源 | `WARNING`，任意来源 | camctl 自身 `ERROR` / `CRITICAL` | 第三方 `ERROR` / `CRITICAL` |
| --- | --- | --- | --- | --- | --- |
| `0 ≤ q < L` | 接纳 | 接纳 | 接纳 | 接纳 | 接纳 |
| `L ≤ q < H` | 丢弃 | 采样选中才接纳，未选中则丢弃 | 接纳 | 接纳 | 接纳 |
| `H ≤ q < C` | 丢弃 | 丢弃 | 接纳 | 接纳 | 接纳 |
| `q = C` | 丢弃 | 丢弃 | 丢弃 | 所属协程异步等待接纳 | 丢弃 |

判定随队列积压变化：下降到第二水位以下后恢复 `INFO` 的采样接纳，下降到第一水位以下后恢复普通接纳；丢弃的记录不补投。水位及容量约束在同步与异步生产者之间共同成立，容量判定与实际接纳须协调为一致结果，不能用未受协调的 `qsize()` 检查宣称满足水位边界。等待重要日志入队时，不持有消费者或其他生产者取得位置所需的锁。并发适配的具体方式在实施时验证，复用 `janus` 的等待与唤醒机制。

`WARNING` 不采样、不等待空位。第二水位以上的空间由警告和错误共同使用，不为单个级别或来源独占；警告和错误自身持续积压仍可填满队列。默认日志级别为 `WARNING` 时，低级别记录已在入口过滤，水位抑制主要用于启用更详细日志的部署。已入队的重要记录仍需等待前面的记录被处理，本规则不提供优先写出或固定等待时限。日志通道故障、进程突然终止及文件轮换保留继续遵守各自规则。

`C`、`L`、`H` 分别取自 `session.log_queue_capacity`、`session.log_queue_low_watermark`、`session.log_queue_high_watermark`。默认值、合法类型、组合关系及部署生效规则由[运行日志配置](../architecture/logging.md#配置与默认值)定义。

`INFO` 在 `L ≤ q < H` 时采用独立随机采样，选中概率为本次进程的 `session.log_info_sample_probability`，记为 `p`。每条符合采样条件的新记录独立进行一次判定，取均匀随机值 `u ∈ [0, 1)`，当且仅当 `u < p` 时选中；未选中即丢弃。概率为 0 时全部省略，为 1 时全部选中。低于第一水位的 `INFO` 不采样，达到第二水位后直接丢弃；配置级别已过滤的记录不参与采样。采样选中不等于已接纳，仍须与水位检查及实际入队协调；并发状态变化需要重新判断水位时，同一条记录不反复抽样以争取入队。

双方来源使用同一概率与算法，不保证每固定数量的记录恰好选中固定条数，允许连续选中或连续省略。随机采样只影响普通诊断日志，不改变业务结果、历史或报告内容。复用标准库随机数能力，随机源允许在测试中替换；不按历史事件回放采样结果。采样省略计入下述丢弃汇总。

验收按表覆盖各级别、双方来源、采样选中与未选中，以及 `L - 1`、`L`、`H - 1`、`H`、`C - 1`、`C` 的边界。配置覆盖默认值、合法覆盖、非法类型和非有限概率、概率端点、水位相等或倒置、容量不足以及部分字段覆盖后组合不合法；验证进程内配置固定、后续进程采用新值、各进程队列容量独立。单元验证通过可控随机源覆盖 `u < p`、`u = p`、`u > p`、概率端点及非采样区间，不以真实随机运行恰好产生固定条数作为通过条件。

组合真实同步与异步生产者和日志线程，验证并发接纳不突破容量及相应水位限制，消费者取出后后续记录恢复适用规则，同一记录不因竞争而重复抽样，已接纳记录不被新记录淘汰且按入队顺序处理。覆盖队列仅由警告和错误填满的情况，验证第三方错误和新警告丢弃、自身错误异步等待。

### 日志丢弃计数与退出汇总

每个进程在内存中按日志级别累计因接纳策略丢弃的记录数量，包含自身和第三方来源，同一条记录只计一次。只保留计数，不保存丢弃的消息内容，不为每条丢弃生成新日志；运行中不定时或按水位恢复输出摘要。计数不写入状态库、不跨进程合并、不跨启动累计，进程突然终止时不保证保留。

| 记录处理结果 | 是否计入相应级别的丢弃数量 |
| --- | --- |
| 被配置日志级别过滤，未进入接纳判定 | 否 |
| 因水位限制直接丢弃 | 是 |
| `INFO` 采样未选中 | 是 |
| 本条按策略需尝试接纳，但最终因满载被丢弃 | 是；不得再按其他接纳原因重复计数 |
| 自身重要日志仍在等待接纳，或记录已经入队 | 否 |
| 日志文件通道故障导致无法写出，或通道已禁用而跳过 | 否；该故障继续由日志通道故障规则诊断，不能混称为队列接纳限制 |
| 退出摘要被级别过滤，或摘要本身写入失败 | 否；不生成新的丢弃摘要 |

正常退出时先结束本进程日志生产并处理完已接纳记录，再由日志线程检查最终计数，最多尝试写出一条 `WARNING` 摘要，随后关闭日志组件。这里的正常退出指能够完成有序关闭的路径，也适用于业务失败后正常完成进程收场，不表示业务成功。摘要携带本进程身份及各非零级别的丢弃数量，表明这些记录因日志接纳限制被省略；`ERROR` / `CRITICAL` 的此类丢弃只来自第三方。不同进程各自汇总，同一共享文件中出现多条不同进程的摘要不属于重复。

| 退出时状态 | 摘要处理 |
| --- | --- |
| 所有丢弃计数均为零 | 不生成摘要 |
| 存在丢弃，但当前日志级别不允许 `WARNING` | 不写摘要，不提升摘要级别或转写其他通道 |
| 存在丢弃，允许 `WARNING`，文件日志通道可用 | 日志线程直接交给原文件处理器一次，遵守已有文件锁、追加和轮换规则 |
| 存在丢弃，允许 `WARNING`，文件日志通道已禁用 | 跳过摘要，不为汇总重新打开或启用通道 |
| 摘要写入或轮换过程中发生故障 | 按已有日志通道故障分类处理，以实际追加结果判断摘要是否写入；轮换失败但追加成功仍算写入，不递归记录或重试投递摘要 |
| 进程突然终止，无法执行正常关闭 | 不保证有摘要，也不由下次进程补造 |

摘要不重新进入业务日志队列，不参与水位或采样判定。同步与异步生产者更新计数须正确协调；停止生产后读取最终计数，避免漏计或重复汇总。组件关闭被重复调用时，也不能再次生成同一进程的摘要。摘要失败不改变业务或 CLI 的原结果，日志故障的 stderr 提示继续遵守原故障规则。

单元验证覆盖计数分类、同一记录只计一次、混合级别和来源、全部为零、摘要级别过滤、通道禁用及摘要失败，断言级别与数量事实，不逐字比较文案。集成验证组合真实同步与异步生产者、队列和日志线程，验证并发计数、先处理已接纳记录再写摘要、摘要由日志线程直接写出且不入队、重复关闭不重复汇总，以及多个独立进程分别汇总；真实写入失败按既有故障契约处理。验证采样省略会计数而配置级别过滤不会计数，进程重启不继承前次计数。

## 日志适配与写入完成通知

### 路由与分级接纳

`camctl` 命名空间使用自身入口，不向 root 重复传播；第三方 Logger 经 root 的同步 `QueueHandler` 接入。接入配置核对第三方自带处理器及传播设置，避免重复写入。异步入口与同步入口共用记录准备和策略；来源由路由确定，不按线程或级别猜测。

普通 `await logger.error(...)` 的成功条件仍是入队。自身同步入口只用于低于 `ERROR` 的日志；数据库及文件线程通过结果通道返回错误。线程内部发出的第三方日志仍使用第三方策略。

Janus 负责队列容量、FIFO、等待与唤醒。为原子执行水位策略，建议用一个很小的 Janus 子类，在已持有队列内部锁的 `_put` 扩展点检查水位和一次性采样结果，再调用原插入方法。正常策略拒绝须在插入和未完成计数增加之前返回到适配层；该拒绝不向日志调用者抛出业务异常。满队列的同步投递按级别计入丢弃，自身重要日志由 `async_q.put()` 等待。

这是依赖内部扩展点的版本绑定适配，必须隔离在日志接纳模块并锁定经过验证的 Janus 版本。不能到处访问队列私有锁，也不能持有外部锁跨 `await`。升级验证覆盖同步与异步生产者同时达到 L、H、C、水位下降、一次采样、拒绝后计数一致、关闭唤醒及 FIFO；验证依据见[队列核验](integration-readiness.md#队列与监听线程核验)。

### 包含触发错误的日志副本

只等待错误写入完成，再另行取得文件锁复制，存在其他进程在两步之间轮换日志的空隙。因此，日志副本需求必须在触发记录入队前绑定到该记录；不能在记录已经处理后补挂一个复制要求。

建议给这类记录附加内部交付凭据，包含已保存的故障身份、副本身份、准备文件归属及完成通知。普通日志调用仍以入队为返回条件；副本流程另行等待凭据结果。故障标记未可靠保存时只记录普通错误，不附加复制要求。

日志线程按以下顺序处理带凭据的记录：

1. 按普通方式格式化，取得 CLH 使用的同一跨进程文件锁。
2. 执行适用轮换，追加触发错误并刷新缓冲。
3. 在释放同一文件锁前，将正在使用的日志文件完整复制到指定准备文件；此时其他写入进程不能追加或轮换。
4. 复制取得固定字节后释放共享锁；完成副本刷新、文件同步和关闭，再通知副本流程。
5. 副本流程将完整文件移入 `ready`、同步目录，并保存实际日志交接进度。

CLH 适配在其持锁调用 `do_write()` 的范围内追加复制动作，复用库的轮换和加锁过程。日志线程执行阻塞复制，不在事件循环持有文件锁。副本流程不等待其他进程的队列排空。

| 实际失败步骤 | 日志通道 | 副本与业务处理 |
| --- | --- | --- |
| 轮换失败，但协调有效且追加、刷新成功 | 按既有规则继续写入 | 可以复制包含触发记录的日志；提示一次轮换错误 |
| 追加、刷新或共享锁失败 | 禁用本进程文件日志 | 完成凭据的失败通知，终止本次副本流程；业务按原错误处理 |
| 触发记录写入成功，副本读取、写入或同步失败 | 不因副本失败禁用仍可用的日志追加 | 返回副本失败，释放锁并按日志专题清理，不重写触发记录 |
| 完整副本已保存，移动到 `ready` 或目录同步失败 | 不改变普通日志通道 | 由日志副本流程处理实际位置与清理，不递归触发复制 |
| 首次故障标记已可靠创建，仅后续标记进度更新失败 | 不改变仍可用的普通日志通道 | 记录保存错误，副本本身符合条件时继续本次交付；保持原身份，不重启复制或补投 |

`handleError()` 和轮换故障通知须适配成结构化结果，不能从库函数没有抛异常推断写入成功。CLH 有些轮换错误只调用内部诊断入口后返回，适配须覆盖这些路径；不能解析人类错误字符串决定业务分支。完成通知通过 `loop.call_soon_threadsafe` 回到事件循环，日志线程不直接修改 asyncio Future。

### 正常退出与通道故障

正常退出先结束生产并完成重要日志交接，异步等待 Janus 的已接纳任务处理完毕，再由日志线程处理一次适用丢弃摘要。确认生产者和摘要工作结束后，停止标记才入队；线程 `join` 由工作线程执行，最后关闭处理器并 `await queue.aclose()`。不能在事件循环调用会等待线程结束的 `QueueListener.stop()`。

日志通道禁用时使用 Janus 的非立即关闭 `shutdown(immediate=False)` 停止新接纳并唤醒等待空位的协程；它们收到通道失效结果而不是入队成功。监听适配识别 Janus 的关闭结果：消费者对已取出的任务仍完成记账，对剩余记录和副本凭据按通道故障完成处理，队列排空后结束监听；这些损失不计入采样或满载丢弃数。只要消费者仍在正常处理，就不能关闭队列或插入越过既有记录的停止标记。
