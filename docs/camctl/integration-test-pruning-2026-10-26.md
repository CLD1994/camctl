## 验证结果

运行环境为 Linux x86_64 开发容器、CPython 3.11.17。在测试删除前后的源码上，分别按 16 个组件目录及根目录收集，进程之间顺序执行；没有执行被收集的业务场景。

| Python 测试函数比较 | 3879 → 3861，删除 18 个函数，没有新增函数。保留函数只有三处预定变化：两处合并原断言，一处移除重复参数。 |
| 全范围节点收集 | 10566 → 10548，集合差恰好是预定的 18 个节点，没有新增节点或其他遗漏。两轮均只有旧缓存文件收集失败。 |
| 合并后的单元承接组合 | 138 项通过，退出 0。 |
| 合并后的组件集成组合 | 151 项通过、7 项失败；各目录独立执行，合计命令墙钟 14.50 秒包含单元组合。 |
| 独立静态评审 | 七组改动均已核对，未发现确定的覆盖缺口。评审者没有另行运行测试。 |

函数数与收集节点数采用不同口径：一个被删旧缓存函数原本就无法收集，另一个保留函数减少了一个参数组合。因此，删除 18 个函数及 1 个参数组合，实际收集节点减少 18 个；无法收集的四个旧缓存参数组合不计入这项减少。

7 项组件集成失败来自报告冻结和发布拒绝用例。它们均在准备时向异步受理接口传入旧 `OwnedConnection`，因缺少 `write` 失败，尚未执行冻结或发布。本次删除没有修改这些准备调用，原完整回归也已记录报告目录的同类接口失配；本次没有把这些失败算作修复。保留的拍摄时长矩阵还存在旧 `CaptureRuntime(owned=...)` 准备错误，原关闭竞争测试也有旧连接工厂替身问题，分别保留在各组证据中。

收集只证明本次读取到了哪些节点。上述定向运行没有覆盖剩余全部节点，也没有执行容量、严格无交换、真实设备或目标主机验收；14.50 秒不能与旧完整回归耗时比较，也不作为整套提速结论。

## 后续重构重点

先为保留的业务目标确定所属模块的公开入口，并集中维护合法环境和共享调用。输入从哪里提交、哪些真实模块参与、最终核对什么结果，应在测试支持中清楚表达；单纯恢复旧内部参数会继续扩大维护负担。

优先处理启动、拍摄及取回目录中反复出现的旧运行对象、旧异步数据库调用和私有状态拼装。报告与会话中的同类问题随后按共同入口处理。旧缓存文件的五项目标需要逐项迁移，不能仅删除导入来取消检查。

真实事务、取消、保存结果未知后的恢复、文件归属、分页和容量目标继续保留。此前确认的清理 `closing` 导入及 Hasselblad 独立只读核查问题仍按[完整回归报告](integration-regression-2026-10-26.md#生产问题与未决契约)追踪。
