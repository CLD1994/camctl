检查日期：2026-09-22。范围是 camctl 第一版的行为规格及其与客户端、主程序、设备驱动之间的接口；检查结论仅评价规格完整性，不代表生产实现或设备验收结果。

## 行为分区与验收要求

### B1：普通交付文件已经离开交接目录，但发布结果还未保存

**场景。** camctl 已在 `staging` 准备好视频副本 D，然后把 D 移入 `ready`。主程序立即将 D 移到 `processing`，发送后删除。camctl 尚未保存发布结果，主机就断电了。下次启动时，数据库可能仍记着正在发布，而三个位置都没有 D。

**依据与不变量。** [普通产物不自动重传](../architecture/outputs.md#普通产物传输失败与重新取回)、文件缺失不证明客户端收到，以及[准备完成后允许清理源产物](../architecture/output-cleanup.md#准备完成与断电恢复)同时成立。不能直接套用状态报告的 ACK 补投规则，也不能假定源文件总能重新拷贝。

根因是文件移动、主程序处理和数据库提交属于不同步骤。恢复必须区分可靠完成事实、实际文件证据与证据不足，避免重复交付、虚构发布成功或长期停留在 `publishing`。

**规则。** 保存顺序及恢复决策表以[普通交付的保存顺序与中断恢复](../architecture/file-handoff.md#普通交付的保存顺序与中断恢复)为准。尚未结束且未取消的交付，在没有可靠完成事实、三个位置均无副本并且交接结果无法确认时，结束为 `failed`，明确保留结果未知的原因，不自动重新投放。该结果不证明主程序未发送或客户端未收到；其他交付继续处理，取回按逐项结果汇总。公共错误由根目录 `protocol` 定义，事件字段及事务接口仍须在实施设计中落实，取消与撤回遵守各自的状态规则。

**影响与验收。** 涉及普通交付、文件交接、取回汇总、撤回和报告。用受控步骤覆盖移动前后、同步前后、提交前后断电，以及主程序提前领取并删除、源产物已清理、取消与领取竞争。先验证规则函数的各个分区，再组合真实 SQLite、目录和领取模块验证。修订时一并审计正常发布、重启恢复和已终态取回的撤回入口。实际断电持久性须在目标存储上确认。

### B2：等待来源结束后的取回与清理资格授予顺序

**场景。** 录像 A 尚未结束。10:00 的取回 B 和 10:01 的清理 C 都已等待 A。A 结束并登记产物后，需要按业务顺序决定资格，不能让 C 因为先醒来或先保存选择而抢先登记删除限制。

**依据与不变量。** 等待不提前取得未知产物的读取资格，动作处于运行状态也不证明它已持有所有产物的资格。已经取得的资格、有效删除限制和最终结果保持原效力；来源完成后符合条件的候选须统一调度，正常运行与重启恢复使用同一规则。

**规则。** 判定表以[逐产物资格授予顺序](../architecture/outputs.md#延后执行时的取回与清理顺序)为准。当前具备条件的候选按计划时间处理，同时间取回优先，包含此前已进入等待的动作。候选依据可靠业务事实确定，不能把某个协程先保存选择当成优先依据。条件未满足者不提前占位；已取得资格但仍在等待相机拷贝的取回继续受保护。来源完成等状态变化唤醒调度，不为本规则增加轮询。

**影响与验收。** 涉及动作、组和计划来源的取回与清理、自动预览、精确 ID 判定及重启调度。来源固定、逐来源选择、资格和限制的具体事务接口仍须落实。验收覆盖计划时间两种先后及同时间，交换协程唤醒、选择保存与查询返回顺序；在产物登记、选择保存及资格事务前后中断，确认已提交事实不丢失，尚未授予的资格按同一业务规则恢复。覆盖多个候选、条件未满足、既有资格和限制、相机拷贝排队、组内来源分别结束，以及取消、终态和提交结果未知。修订与实现须一并审计普通取回、自动预览、范围及精确 ID 清理的资格入口。

### B3：取消动作自身被取消后的责任与等待范围

**场景。** C1 已可靠保存“取消录像 A”，正在等待 A 停止。此时 C2 取消 C1，或取消包含 C1 的计划；需要分别确定 C1 的结束条件、A 的必要停止责任，以及 C2 是否应等待 A。

**依据与不变量。** 取消生效、目标实际停止与取消动作完成是不同事实。已生效取消不撤销，必要设备与文件收场不能依赖发起者继续等待；后一个取消动作不能递归扩大自己的目标范围，多个入口不能重复创建收场流程或重置预算。

**规则。** 阶段与等待范围以[取消动作自身被取消](../architecture/task-cancellation.md#取消动作自身被取消)为准。C1 停止尚未生效的工作及目标结果等待，完成自身必要收场后以取消结束；已受影响目标继续自己的停止与清理。C2 只按自己的目标范围等待，直接包含 A 时复用 A 已有流程，否则不通过 C1 间接等待 A。已有终态保持不变，提交结果未知先核实。完整目标集合包含本次取消动作自身时，按[自身目标检查](../architecture/task-cancellation.md#目标集合不得包含取消动作自身)在任何目标取消生效前失败。

**影响与验收。** 涉及动作、组、计划和请求 ID 取消入口，自动预览扩展及受限会话中的合法取消。单元验证完整集合、取消阶段和等待范围；集成组合真实 SQLite、调度及设备和文件协作者，在各提交边界中断，验证已生效责任继续、未生效工作停止、终态保持、预算不重置。既覆盖 C2 只选 C1，也覆盖同时选中 A；自身目标检查验证集合中其他动作同样不受影响。审计录像停止、取回读写结束、交付撤回和清理取消，不能只保留设备效果而遗漏文件责任。报告机器表示由根目录 `protocol` 定义，具体事件与事务仍须在实施设计中落实。

### B4：取消后完整交付副本的清理

**场景。** 组取回已在 staging 准备好 A 的完整交付副本，仍等待 B 录像结束。用户取消取回后，A 的副本不再交付，也不供新请求接管，需要按本次取回的归属释放存储。

**依据与不变量。** 完整交付副本与正式源产物具有不同生命周期。取消可靠保存、归属明确且相关操作确认结束后，才允许删除本次工作副本；已进入交接目录的文件继续遵守撤回和主程序所有权。清理结果与取回取消、取消动作结果及会话结果分别表达。

**规则。** 判定表及后续处理以[取回工作副本的保留与清理](../architecture/obtaining-outputs.md#取回工作副本的保留与清理)为准。取消后的完整副本与半成品共用清理机制，满足条件时自动删除；删除失败保存原因和未完成责任，后续正常 run 再有限尝试，不增加轮询或独立重试会话。有效取回仍待交付的副本继续保留，位置或操作结果未知时先核实。源文件此前已合法清理不阻止删除已取消副本，也不保证以后仍能重新取回。

**影响与验收。** 涉及取回、文件交接、工作副本清理报告及会话工作判定。验证组内完整副本等待期间取消、相关操作尚未停止、进入 ready 或 processing，以及取消、删除、结果提交前后中断。删除失败后验证有限处理、取消动作如实报告本次失败、其他职责正常时会话可以正常结束、后续正常运行继续清理且已有终态不改写。覆盖源文件存在或已合法清理、其他请求副本并存，审计单文件、组、计划及自动预览取回入口。具体尝试次数、有限工作量及持久化接口仍属实施设计。

## 实施前必须形成的具体设计

这些事项不能用现有测试通过来代替，也不需要重新选择已经批准的总体方案。

### I1：各组件接入公共机器协议

**问题与场景。** 自动预览、按计划取回、来源范围清理及 B1～B4 的行为需要客户端与主机共同理解字段、关联和错误含义。只分别修改组件内部类型，可能使客户端生成的合法意图被主机拒绝，或让报告丢失业务事实。

**协议依据。** [公共协议入口](../../protocol/README.md#协议定义与校验入口)提供计划与能力说明 Schema、报告扩展、错误登记及共享样例。输入采用分阶段校验，区分整份结构错误、单动作失败与独立 ACK；报告表达固定来源、逐来源选择、自动关联、预览原文件关系和取消效果。各组件必须遵守这些字段及其业务语义。

**验证与接入边界。** `node scripts/check-protocol.mjs` 校验 Schema、全部报告样例及原始字节摘要、计划与能力说明、结构正反例和已登记错误详情。它不代替生产受理、冻结历史生成、客户端语义合并及真实设备联调。客户端能力参数类型的外层字段白名单尚未包含预览声明；取回失败项的去重还需包含请求 ID。接入实现必须覆盖能力导出、客户端计划生成、camctl 的 run / submit 入口、报告生成与客户端导入，消费同一批公共样例，不另建机器字段清单。

### I2：驱动必须给出可验证的录像与文件归属证据

**问题与场景。** 启动成功但源文件关联尚未保存就断电；或者停止响应丢失后恢复。框架不能仅凭一个新文件名证明它属于这次录像，也不能凭文件存在证明写入完成。[驱动接入契约](../architecture/camera-recording.md#第一版驱动接入契约)及[源文件关联](../architecture/camera-recording.md#源文件命名与录像关联)已经要求提供证据，具体映射仍待核实。

**处理。** 先核对真实设备资料并完成受控联调，明确启动意图与设备任务关联、完成文件的身份及固定长度、按偏移读取、摘要与删除结果、原文件和预览的配对。普通成功路径已确认的能力继续有效；恢复分支缺少证据时明确报告未确认，不能让替身编造设备保证。只有实际能力不满足现有契约，才提交保证范围或产品行为的取舍。

**影响与验证。** 涉及拍摄、异常核验与修复、取回续传、预览及清理。用真实驱动完成正常路径和关键中断点验证；驱动替身与真实适配器遵守同一结果类型和证据条件。主机杀进程不能代替相机断电或存储持久性验证。未知的多预览、多修复候选先核实是否实际存在，不为假设新增选择策略。

### I3：内部录像工作文件需要独立的生命周期设计

**问题与场景。** camctl 为异常录像拷贝原片并完成检查，或者使用该副本完成修复后，主机仍可能保存输入副本和处理输出。[内部检查](../architecture/camera-recovery.md#计时证据不足时的原片检查)规定检查与修复复用同一输入，[修复文件处理](../architecture/camera-recovery.md#修复内容与文件处理)规定成品登记，但尚未给出这些工作文件在成功、失败、取消及重启后的完整清理表。普通取回半成品规则明确不适用于这类文件；文件留在 `staging` 本身也不表示可删除。

**处理建议。** 由录像处理流程保存工作文件归属与后续用途：仍需续传、检查或修复时保留输入；全部用途结束且实际操作停止后释放工作副本；已经登记的修复成品继续长期保留。尚未登记的输出按原处理记录恢复，先判断是否仍有登记或修复责任。另行写清删除失败是否可延后及怎样报告；不能直接复制普通取回的错误结果，更不能以临时清理改变已经成立的录像成功依据。

**影响与验证。** 涉及原片检查、内部修复、录像取消、终态登记与正常启动恢复。按输入仍被使用、用途已结束、输出待登记、正式成品已登记及归属未知分别验证；在修复完成和登记提交之间中断，确认可恢复成品未被清理。结合真实文件系统测量连续异常录像后工作文件是否按生命周期释放。该项须先形成生命周期设计；影响业务结果的清理失败语义尚未确定，须在实现前明确。

## 文档一致性核对

各项规则须直接引用其权威章节：

- 三种拍摄动作都有启动窗口，报告 Schema 的相机动作分类与之对应。
- 文件传输按 `copy.segment_size` 分段保存进度，默认 `"128 MiB"`；普通取回的分段取消已有完整阶段表。
- 文件任务使用默认线程池，第一版没有应用层统一提交上限；数据库和日志队列分别有界。
- 规格规定了报告分批读取、分阶段时限、父进程结束保护和失败后触发，待落实的是接口、部分取消收场及部署数值。
- 历史快照按四类对象分别累计变化，统一默认阈值 64，创建计一次，跨会话保留；只由正常运行中的提交与对象发现唤醒，不单独延长会话。

B1～B4 的恢复、资格授予、取消责任及完整副本清理规则以对应专题为权威来源。

## 收口顺序与交接条件

1. 依据 B1、B2 的规则，落实交付恢复及资格授予的事件、候选查询和事务接口。
2. 落实 B3、B4 的独立收场、统一工作副本清理和报告接口；结合实际流程完成内部录像工作文件设计。
3. 依据公共协议安排各组件的协议接入；形成设备证据清单并核实真实能力。
4. 据上述结果形成数据库、内部接口、线程与进程生命周期及配置设计，再沿同一业务链复核失败和恢复。
5. 完整规格获审阅后编写实施计划，明确依赖、逐步测试、真实组合门禁及最终验收，之后再进入生产实现。

上述工作涉及持久化、并发、状态机及跨组件交接，属于复杂工作。**不直接向执行者交接为“自行补齐”的代码任务。** 行为尚未确认时只能交接设计问题；确认后，实施计划必须包含相应决策表、事务边界、入口、先失败测试后实现的步骤及阶段验收。若设备事实或实际代码与计划不一致，停止相关任务并报告证据。
