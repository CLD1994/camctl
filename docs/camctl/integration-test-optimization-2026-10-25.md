## 结果页重复证明的生产成本

同一个原结果页会被分类、成员读取、文件完成及配对等消费者反复读取，每次都重新核验整页关系。native 单例中仅一个页事件就发生 8,909 次完整核验；history 增长目标的主要成本同样发生于构造真实世界，测量主体开始之前已经付出大部分成本。

最终实现按[事务与校验阶段边界](persistence-runtime.md#结果页证明的事务与校验阶段范围)复用最多三份紧凑的原 SQL 历史行和完整事务范围。命中后重新解码，不长期持有 `SavedResultPage`、事件及字典对象图；未命中时先释放超窗旧记录，再查询、解码及完整核验。`row_facts` 直接使用原列描述解码，省去重复的列名元组。

普通提案返回后，以及有限／有界入口每条上下文形成后，先清空记录，再由独立守卫从实际数据库重新建立证明。候选页不进入已提交缓存，动态资格和当前引用仍实际核对；事务结束命令发出前停用记录。原 12 项 after-proposal 矩阵与缓存生命周期反例共同约束该边界。

## 跨组件夹具与失败等待

OSMO 单原片清理链的任务包装器已透传真实工厂的 `result_mode` 参数，继续显式保存原单原片结果策略。正常新请求和在途取消恢复两个代表通过，原 STOP 后真实等待及清理断言保持。修正前九项在提交前失败；修正会让它们实际执行后续链条，因此不能把修正后的额外运行时间解释为性能回退。

`HostDemo.watch_failures` 在操作前取得日志游标。等待在成功谓词之外，只检查此后本 host 的明确 run 错误、自动重试耗尽、host 本身退出，以及指定 request_id 下指定动作的不相容终态；合法自动重试和正常 run 退出保持。失败诊断每 50 毫秒最多检查一次，原成功预算不变。

真实 host／SQLite 的 12 个观察器分区通过。C 六动作链仍在当前请求的动作过期后失败，call 从 184.70 秒降到 6.89 秒，原成功断言没有放宽。Action6 的原基线副本清理失败在候选轮次通过，前后业务结果不同，不能把约 180 秒差当作严格性能收益，也不能据此声明原生产问题已修复。命令、失败事实及各次组合范围见[回执](verification-data/2026-10-25-integration-optimization/root-wait.json)。
