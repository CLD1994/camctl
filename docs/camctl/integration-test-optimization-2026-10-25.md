活跃读者从 frozen 切到 running 时，先采实际单调读数再读取新状态，可能把旧采样与较新的锚点组合而报负差。共享测试时钟改为先读状态、再取实际时间；确定性交错反例证明旧顺序失败、新顺序正常，显式无效读数仍拒绝。暂停推进只在执行已停止或原故障门确已进入的同步点进行；没有增加任意并发回退的保障。

## 遗留生产维护问题

以下两项已完成实际交付后，在既有生产维护路径失败，相关责任源码在优化前后相同。它们与 START 前过期的夹具问题分开处理，数据库事实、原错误及合同依据见[诊断记录](verification-data/2026-10-25-integration-optimization/action6-maintenance-diagnostics.json)。

`unknown-prefix` 的来源先终态，等待者约六秒后才全部终态。来源检查副本在首次发现时尚不具备释放资格；等待者结束后，发现逻辑只处理等待者自身文件，没有重新发现来源检查副本。原轮因 host 偶然再起一次正常 run 而清理，本轮没有该额外 run，三份副本保持原保留状态并等待超时。应在等待者终态时，沿既有依赖和冻结 H 关联发现来源副本的新清理资格，或保留有限的首次责任；不得以增加历史扫描、重复处理已完成文件或测试主动补起 run 代替修复。回归须用确定门闩分开来源终态与等待者终态，验证同次运行及时发现并实际清理，每份文件仍遵守既定首次处理约束。

原生场景的合法 inspection READ End 已登记，副本为 `inspection_id` 非空、`processing_id` 为空；读取结束恢复却只通过 `recording_processing` 关联动作，于是明确报“原内部读取结束缺少处理、源观察者与动作归属”。应为 inspection 责任沿原 ticket、动作和源观察者核对归属，同时保留错误责任的拒绝；不能忽略该 READ End 或删去失败观察。回归应在真实读取结束提交之后中断，再由新会话恢复合法原责任，并覆盖错误 inspection／动作／观察者关系。现有诊断未给出具体触发的副本 ID，不能在三份候选中进一步指认。

## 后续测试设计的依据

1. 先说明真实协作者和失败分区，再决定测试层级。局部值域的等价单元覆盖可以承接重复断言；实际导入、资源登记和安装物仍需要集成见证。
2. 分开记录准备、操作和结果核对。测试体中的建库仍属于准备成本，调用栈中的热点也须确认发生于哪一段。
3. 共享只读来源时，为改变状态的消费者保留独立身份。拒绝矩阵只有在每次完整回滚、事务结束和相关事实不变得到核对后，才适合同库复用。
4. 缓存已证明内容仍须限定真实事务、候选上界与独立守卫范围。条目数上限不能替代字节峰值测量；严格三页消费者不能由不进入该分支的大夹具冒充。
5. 尽量在准备完成后选择执行时间，用确定同步点安排故障。成功等待同时观察本请求明确失败，保留原成功预算和完整成功断言。
6. 并发前逐项隔离源码生成、构建、工具缓存和数据库。排序要识别历史失败造成的成本下界，不把早期失败误认为短任务。
7. 采集工具本身也要验证故障边界。清单覆盖、阶段完整性、嵌套子检查和退出码共同决定结果是否有效，墙钟变短不能掩盖未执行的测试。

这些原则的通用要求由[共享测试规则](../../.agents/rules/testing.md#控制集成测试成本)维护，本记录只保存本次发现和证据。
