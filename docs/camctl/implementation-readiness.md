## 驱动绑定的处理边界与字段衔接

**行为契约。** 合法拍摄动作保存首次选定的 `actions.driver_id`。成功加载配置后发现所需设备配置缺失或驱动绑定不一致时，不发起相关设备操作，将无法执行的动作或处理项按所属规则判为失败；其他设备、本地处理和报告维护继续推进。已有终态、取消和过期优先，设备收场无法执行时保存失败及残留或未知设备事实，不重新解释实际设备状态。失败结果、适用收场和必要报告处理完成，且无其他责任时，会话正常结束；配置修正与请求重送不重开已失败任务。字段及判定分类见[拍摄动作的驱动绑定](database/plans-actions.md#拍摄动作的驱动绑定)，完整行为遵守[设备绑定异常的影响范围](../architecture/configuration.md#设备绑定异常的影响范围)。

**错误登记与验证衔接。** 将设备配置缺失、驱动绑定不一致对应的错误码、唯一阶段、详情与固定整数编号纳入[动作错误登记任务](database-boundary-review.md#动作错误码与阶段核对)。诊断随所属动作、明细或处理结果保存，报告通过相应失败结构表达；机器标识、阶段及整数编号使用 [device_binding_unavailable](database/action-errors.md) 的公共登记。验证需覆盖拍摄、跨设备取回、清理、取消及独立收场；绑定检查前未发起设备调用不增加尝试次数，未知设备效果保持未知。以真实持久化、调度和报告组件组合验证失败结果与历史共同保存、其他设备继续、正常收尾、配置修正后终态不变；设备接口使用受契约约束的测试替身。

**字段衔接。** 设备文件通过 `device_files.observer_action_id`、活动通过 `device_activities.action_id` 取得原设备及驱动绑定。核对内部录像处理、跨设备取回、清理和取消的调用路径，保证来源动作终态后仍能取得原绑定。具体字段及历史归属分别见[文件字段](database/file-fields.md)和[操作字段](database/operation-fields.md)。

## 检查范围与已有依据

**数据库字段依据。** [数据库设计入口](database-schema.md)按职责提供表目录。[来源成员字段](database/sources-obtaining.md#取回与范围清理的来源成员)定义 `action_dependencies` 的身份、两端关联、唯一约束及原子保存；[动作执行定义](database/execution-definitions.md)定义受理结果与 JSON 空值组合，并分别规定录像、延时摄影及取回的字段、固定编号和组合约束。字段清单与取值只在对应专题维护。

**数据库结构与事务。** [字段与结构覆盖](database-boundary-review.md#字段与结构设计覆盖)按职责组织目标规格；SQL、协议和检查脚本的覆盖范围及生产工作见[同步清单](#数据库规格同步清单)。[事务接口](database/transactions.md)定义各流程的共同提交及恢复边界，[历史格式](database/history-formats.md)定义事件、目录和快照。实施计划按这些契约组织生产实现、事件应用和真实 SQLite 集成验证。

**延时摄影完成核实。** 设备自行结束的定时任务遵守[等待与完成核实](../architecture/camera-capture.md#设备自行结束时的等待与完成核实)。状态查询为可选能力；采用[时间与产物判定](../architecture/camera-capture.md#按时间与产物判定完成)的任务，在声明的等待条件满足后直接核实产物，不创建状态查询流程或预算。[返回含义与计时](../architecture/camera-capture.md#命令返回含义与等待起点)规定发送成功时立即取得锚点、数据库和日志不推迟锚点；原生调用在任务完成后返回时，不再等待完整目标时长。首次结果核实前不周期查询拍摄状态；取消和重启可以提前触发相应处理。[等待余量](../architecture/camera-capture.md#驱动必要余量与部署额外等待)由首次固定的驱动必要余量与本次运行的部署额外等待相加，部署额外等待默认 0；驱动必要余量使用 [result_wait_margin_ms](database/execution-definitions.md#延时摄影执行定义的结果等待余量)，保存非负整数毫秒；适用但无需余量时为 0，不适用时省略。部署额外等待使用 [capture.extra_wait_ms](../architecture/configuration.md#拍摄结果核实的额外等待)，实际等待依据由设备活动保存。随后按实际采用的返回及结果取得方式确定调用期限、核实间隔、预算及耗尽语义。[无状态查询任务的重启等待恢复](../architecture/camera-capture.md#无状态查询任务的重启等待恢复)按原发送成功日期时间及预计检查时间计算剩余等待，本次运行内使用单调钟；部署保证跨重启日期时间可靠，重启保留原任务及输出范围的占用。[取消资格](../architecture/task-cancellation.md#设备任务的取消资格)规定未启动任务可取消，已启动或可能启动且无停止能力的任务拒绝取消并继续原流程；取消明细保存失败与未生效事实，批量结果和自动预览联动按各自规则处理。发送结果未知及失败后占用遵守[恢复分类](database/operation-fields.md#等待未知结果和占用恢复)。设备具体设置及文件规则按接入资料和联调核验；基于运行假设的成功判定保证范围由专题定义。

**延时摄影产物检查。** [文件完成依据与产物检查](../architecture/camera-capture.md#文件完成依据与产物检查)区分归属、单份文件写完和集合齐备。文件完成采用驱动明确保证或声明的等待假设；检查只执行任务声明的必要文件规则，不默认全面验证媒体内容。接口与持久化设计须保留所用依据及具体检查结果；实际产物类别、数量约束和结束处理耗时由接入驱动明确，不能用框架统一的文件数量或大小稳定规则代替。

## 关键协作场景与验收

### 本地执行配置与历史报告的衔接

**行为契约。** 用户要求、设备身份、驱动选择及生效拍摄参数随动作保存。本地执行配置由每次运行加载，未完成工作的新操作使用本次值；累计次数、确定结果、已保存决定和终态保持原事实。上限降低后，历史次数可以超过新上限；已登记且可恢复的尝试或轮次沿用原身份，不因配置变化重复计数。具体分类见[本地配置变化与未完成工作](../architecture/configuration.md#本地配置变化与未完成工作)。

**待实现的组件适配。** 客户端的报告类型、导入校验、历史合并和展示须按[正式字段契约](../architecture/report-format.md)及公共 Schema 适配，具体任务和验收见[客户端适配计划](../superpowers/plans/2026-09-30-report-client-adaptation.md)。客户端只验证已经公开且能够取得证据的业务事实；内部配置、尝试及恢复校验继续由 camctl 负责。

**实施与验证。** 先用新格式报告建立失败用例，再落实类型、校验、合并、展示和真实导入。验证新旧历史边界、设备执行提示解除、部分结果、客户端文件核验与 ACK；camctl 的历史生成继续保持原报告字节。协议文件更新不代表客户端或跨组件验收已经完成。

### 普通交付文件已被取走，结果尚未保存

**场景。** camctl 已在 `staging` 准备好视频副本 D，然后把 D 移入 `ready`。主程序立即将 D 移到 `processing`，发送后删除。camctl 尚未保存发布结果，主机就断电了。下次启动时，数据库可能仍记着正在发布，而三个位置都没有 D。

**依据与不变量。** [普通产物不自动重传](../architecture/outputs.md#普通产物传输失败与重新取回)、文件缺失不证明客户端收到，以及[准备完成后允许清理源产物](../architecture/output-cleanup.md#准备完成与断电恢复)同时成立。不能直接套用状态报告的 ACK 补投规则，也不能假定源文件总能重新拷贝。

根因是文件移动、主程序处理和数据库提交属于不同步骤。恢复必须区分可靠完成事实、实际文件证据与证据不足，避免重复交付、虚构发布成功或长期停留在 `publishing`。

**规则。** 保存顺序及恢复决策表以[普通交付的保存顺序与中断恢复](../architecture/file-handoff.md#普通交付的保存顺序与中断恢复)为准。尚未结束且未取消的交付，在没有可靠完成事实、三个位置均无副本并且交接结果无法确认时，结束为 `failed`，明确保留结果未知的原因，不自动重新投放。该结果不证明主程序未发送或客户端未收到；其他交付继续处理，取回按逐项结果汇总。公共错误由根目录 `protocol` 定义，事件字段及事务接口仍须在实施设计中落实，取消与撤回遵守各自的状态规则。

**影响与验收。** 涉及普通交付、文件交接、取回汇总、撤回和报告。用受控步骤覆盖移动前后、同步前后、提交前后断电，以及主程序提前领取并删除、源产物已清理、取消与领取竞争。先验证规则函数的各个分区，再组合真实 SQLite、目录和领取模块验证。实施时一并审计正常发布、重启恢复和已终态取回的撤回入口。实际断电持久性须在目标存储上确认。

### 来源结束后的取回与清理顺序

**场景。** 录像 A 尚未结束。10:00 的取回 B 和 10:01 的清理 C 都已等待 A。A 结束并登记产物后，需要按业务顺序决定资格，不能让 C 因为先醒来或先保存选择而抢先登记删除限制。

**依据与不变量。** 等待不提前取得未知产物的读取资格，动作处于运行状态也不证明它已持有所有产物的资格。已经取得的资格、有效删除限制和最终结果保持原效力；来源完成后符合条件的候选须统一调度，正常运行与重启恢复使用同一规则。

**规则。** 判定表以[逐产物资格授予顺序](../architecture/outputs.md#延后执行时的取回与清理顺序)为准。当前具备条件的候选按计划时间处理，同时间取回优先，包含此前已进入等待的动作。候选依据可靠业务事实确定，不能把某个协程先保存选择当成优先依据。条件未满足者不提前占位；已取得资格但仍在等待相机拷贝的取回继续受保护。来源完成等状态变化唤醒调度，不为本规则增加轮询。

**影响与验收。** 涉及动作、组和计划来源的取回与清理、自动预览、精确 ID 判定及重启调度。来源固定、逐来源选择、资格和限制的具体事务接口仍须落实。验收覆盖计划时间两种先后及同时间，交换协程唤醒、选择保存与查询返回顺序；在产物登记、选择保存及资格事务前后中断，确认已提交事实不丢失，尚未授予的资格按同一业务规则恢复。覆盖多个候选、条件未满足、既有资格和限制、相机拷贝排队、组内来源分别结束，以及取消、终态和提交结果未知。实现须一并审计普通取回、自动预览、范围及精确 ID 清理的资格入口。

### 取消动作自身被取消

**场景。** C1 已可靠保存“取消录像 A”，正在等待 A 停止。此时 C2 取消 C1，或取消包含 C1 的计划；需要分别确定 C1 的结束条件、A 的必要停止责任，以及 C2 是否应等待 A。

**依据与不变量。** 取消生效、目标实际停止与取消动作完成是不同事实。已生效取消不撤销，必要设备与文件收场不能依赖发起者继续等待；后一个取消动作不能递归扩大自己的目标范围，多个入口不能重复创建收场流程或重置预算。

**规则。** 阶段与等待范围以[取消动作自身被取消](../architecture/task-cancellation.md#取消动作自身被取消)为准。C1 停止尚未生效的工作及目标结果等待，完成自身必要收场后以取消结束；已受影响目标继续自己的停止与清理。C2 只按自己的目标范围等待，直接包含 A 时复用 A 已有流程，否则不通过 C1 间接等待 A。已有终态保持不变，提交结果未知先核实。完整目标集合包含本次取消动作自身时，按[自身目标检查](../architecture/task-cancellation.md#目标集合不得包含取消动作自身)在任何目标取消生效前失败。

**影响与验收。** 涉及动作、组、计划和请求 ID 取消入口，自动预览扩展及受限会话中的合法取消。单元验证完整集合、取消阶段和等待范围；集成组合真实 SQLite、调度及设备和文件协作者，在各提交边界中断，验证已生效责任继续、未生效工作停止、终态保持、预算不重置。既覆盖 C2 只选 C1，也覆盖同时选中 A；自身目标检查验证集合中其他动作同样不受影响。审计录像停止、取回读写结束、交付撤回和清理取消，不能只保留设备活动的停止责任而遗漏文件责任。报告机器表示由根目录 `protocol` 定义，具体事件与事务仍须在实施设计中落实。

### 取消后的完整副本清理

**场景。** 组取回已在 staging 准备好 A 的完整交付副本，仍等待 B 录像结束。用户取消取回后，A 的副本不再交付，也不供新请求接管，需要按本次取回的归属释放存储。

**依据与不变量。** 完整交付副本与正式源产物具有不同生命周期。取消可靠保存、归属明确且相关操作确认结束后，才允许删除本次中间文件；已进入交接目录的文件继续遵守撤回和主程序所有权。清理结果与取回取消、取消动作结果及会话结果分别表达。

**规则。** 判定表及后续处理以[取回中间文件的保留与清理](../architecture/obtaining-outputs.md#取回中间文件的保留与清理)为准。取消后的完整副本与半成品共用清理机制，满足条件时自动删除；删除失败保存原因和未完成责任，后续正常 run 再有限尝试，不增加轮询或独立重试会话。有效取回仍待交付的副本继续保留，位置或操作结果未知时先核实。源文件此前已合法清理不阻止删除已取消副本，也不保证以后仍能重新取回。

**影响与验收。** 涉及取回、文件交接、中间文件维护、取消结果报告及会话工作判定。验证组内完整副本等待期间取消、相关操作尚未停止、进入 ready 或 processing，以及取消、删除、结果提交前后中断。删除失败后验证有限处理、取消动作如实报告本次失败、其他职责正常时会话可以正常结束、后续正常运行继续清理且已有终态不改写；仅内部文件维护事实变化不单独触发报告。覆盖源文件存在或已合法清理、其他请求副本并存，审计单文件、组、计划及自动预览取回入口。尝试次数和有限工作量遵守[中间文件清理的运行预算](../architecture/file-handoff.md#中间文件清理的运行预算)，持久化及续查接口仍需实现。

## 实施计划与接入验证需要落实的事项

以下事项区分组件实现和真实设备证据。执行计划须落实软件接口与测试步骤；设备证据按单独联调任务核实。既有行为契约继续有效。

### 各组件接入公共机器协议

**场景与责任。** 自动预览、按计划取回、来源范围清理以及交付恢复、资格授予和取消清理行为需要客户端与主机共同理解字段、关联和错误含义。只分别修改组件内部类型，可能使客户端生成的合法意图被主机拒绝，或让报告丢失业务事实。

**协议依据。** [公共协议入口](../../protocol/README.md#协议定义与校验入口)提供计划与能力说明 Schema、报告格式、错误登记及共享样例。输入采用分阶段校验，区分整份结构错误、单动作失败与独立 ACK。固定来源和逐来源选择保存在内部历史中；报告保留原请求，通过产物、交付和逐项最终失败表达选择结果，并提供自动预览展示关系、预览原文件关系、取消结果及适用的设备执行提示。各组件必须遵守这些字段及其业务语义。

**对象 ID 接入。** 数据库对象 ID 在公共 JSON 中统一使用规范十进制字符串。客户端实现须同步生成类型、报告文件名校验、报告导入、实体保存、ACK 选择与导出、同步起点和错误详情；ID 的大小比较必须精确，水位与计数仍按数值处理。现有客户端的报告 ID 数字处理尚需适配。接入验证覆盖大于 JavaScript 安全整数的合法 ID、最大合法值、越界、前导零、数字类型被拒绝，以及导入、保存、重新读取和导出后身份不变。

**请求身份、计划顺序与时间接入。** `request_id` 是调用方提供的正整数，公共 JSON 使用规范十进制字符串，范围为 1～9223372036854775807。客户端的 UUID 请求生成、草稿验证占位值、请求校验、原请求保存、取消寻址和报告匹配须适配该契约；原请求重送保持身份，新的执行意图取得新身份。整数请求 ID 的生成方案须保证请求身份不误复用，具体分配方式在客户端接入设计中确定。主机计划 ID 同时表达受理顺序，报告和客户端按 `plan_instance_id` 的精确整数值排序；生成类型和报告合并以计划身份字段表达受理顺序。公共时间固定为 UTC 的 `YYYY-MM-DD HH:mm:ss`，输入校验拒绝小数秒，客户端编辑、导出及报告读取采用同一格式。验证须覆盖大整数请求从导出到受理、重送、取消及报告关联的完整路径，以及计划顺序、时间格式和错误原值的保存。

**验证与接入边界。** `node scripts/check-protocol.mjs` 校验 Schema、全部报告样例及原始字节摘要、计划与能力说明、结构正反例和已登记错误详情。它不代替生产受理、冻结历史生成、客户端语义合并及真实设备联调。客户端能力参数类型的外层字段白名单尚未包含预览声明；取回失败项的去重还需包含请求 ID。接入实现必须覆盖能力导出、客户端计划生成、camctl 的 run / submit 入口、报告生成与客户端导入，消费同一批公共样例，不另建机器字段清单。

### 驱动提供录像与文件归属证据

**场景与责任。** 启动成功但源文件关联尚未保存就断电；或者停止响应丢失后恢复。框架不能仅凭一个新文件名证明它属于这次录像，也不能凭文件存在证明写入完成。[驱动接入契约](../architecture/camera-recording.md#第一版驱动接入契约)及[源文件关联](../architecture/camera-recording.md#源文件命名与录像关联)已经要求提供证据，具体命令与响应的映射属于设备联调证据。

**处理。** 接入证据和联调场景以[设备联调表](integration-readiness.md#设备证据与联调输入)为依据。核对真实设备资料并完成受控联调，明确启动意图与设备任务关联、完成文件的身份及固定长度、按偏移读取、摘要与删除结果、原文件和预览的配对。普通成功路径已确认的能力继续有效；恢复分支缺少证据时明确报告未确认，不能让替身编造设备保证。只有实际能力不满足现有契约，才提交保证范围或产品行为的取舍。

**影响与验证。** 涉及拍摄、异常核验与修复、取回续传、预览及清理。软件集成测试用设备通信替身组合真实适配代码及其他软件组件，验证正常路径和关键中断点；替身与真实设备接入遵守同一结果类型和证据条件。真实设备响应和目标存储持久性另行联调，不作为软件集成测试门槛，也不以主机杀进程代替物理断电验证。未知的多预览、多修复候选留待设备证据核实，不为假设新增选择策略。

### 内部录像中间文件的生命周期接入

**场景与依据。** 原片检查和内部修复在主机留下输入副本、处理临时文件及未登记输出。[内部中间文件的保留与清理](../architecture/camera-recovery.md#内部中间文件的保留与清理)定义成功、失败、取消及中断后的保留和自动清理规则；普通取回中间文件与正式产物继续遵守各自规则。

**实施要求。** 录像处理流程须保存文件归属、后续用途和清理结果。先可靠保存处理结果或取消决定，确认相关操作实际结束后，再删除无用中间文件。尚有续传、核验、修复或登记责任时保留所需文件；归属或结果未知时先核实。清理失败保留后续正常运行中的有限处理责任，不改变录像结果、不反复延长会话；数据库及其他必要职责失败仍按各自规则处理。运行预算遵守[共用清理规则](../architecture/file-handoff.md#中间文件清理的运行预算)，具体事件、查询及续查接口仍需落实。

**影响与验证。** 涉及原片检查、内部修复、录像取消、终态登记与正常启动恢复。按专题决策表覆盖文件身份、处理记录、后续用途和操作状态；在修复完成、成品登记及删除结果保存前后中断，验证待恢复文件和正式产物得到保留，删除失败可延后，后续清理不改变已有终态。结合真实文件系统测量连续异常录像后中间文件是否按生命周期释放。

### 日志接入与副本交付

落实规定的日志队列、分级接纳、取消与退出规则，以及多进程写入和归档清理。

日志副本采用当前普通日志文件的全部原始字节；按[日志适配](logging-runtime.md#日志适配与写入完成通知)实现错误写入完成通知和持锁复制，并验证完整生命周期。

日志副本交付使用[独立故障标记文件](../architecture/log-failure-marker.md#跨-run-的独立状态文件)，[标记创建未可靠成功](../architecture/log-failure-marker.md#故障标记创建失败)时停止本次交付流程。

流程失败后，camctl 按[失败清理规则](../architecture/log-delivery.md#日志副本的失败清理)删除仍归本次流程所有的准备文件，保留故障标记，不自动重试或补投。

每次 `run` 取得会话锁后，camctl 安排一次[旧日志副本清理](../architecture/log-delivery.md#run-启动时清理遗留日志副本)。

故障标记删除按第一版正常运行假设处理；再检查按[故障标记异常后的再检查](../architecture/log-failure-marker.md#故障标记异常后的再检查)实现；临时文件按[标记保存流程](../architecture/log-failure-marker.md#故障标记的临时文件)清理，首次标记可靠创建后按[进度更新失败规则](../architecture/log-failure-marker.md#故障标记的进度更新失败)继续本次适用交付；落实日志副本及标记临时文件的命名。

## 文档一致性核对

各项规则须直接引用其权威章节：

- 三种拍摄动作都有启动窗口，报告 Schema 的相机动作分类与之对应。
- 文件传输按 `copy.segment_size` 分段保存进度，默认 `"128 MiB"`；普通取回的分段取消已有完整阶段表。
- 文件任务使用默认线程池，第一版没有应用层统一提交上限；数据库和日志队列分别有界。
- 规格规定了报告分批读取、分阶段时限、父进程结束保护和失败后触发，报告继续与停止条件由专题规定，待落实的是接口、通信收场及部署数值。
- 历史快照按六类对象分别累计变化，统一默认阈值 64，创建计一次，跨会话保留；只由正常运行中的提交与对象发现唤醒，不单独延长会话。

恢复、资格授予、取消责任及完整副本清理规则以对应专题为权威来源。

## 计划编写与交接条件

客户端与 C 接入模块已有实现；真实 camctl 与两端的全流程验证须在 camctl 实现后完成。接入模块已有验证范围见[验证记录](../host-demo/verification.md)。关键行为和设计由负责该工作的执行者掌握，实施任务按已批准的阶段与依赖组织。

1. 依据普通交付恢复及来源结束后的取回、清理顺序，落实交付恢复及资格授予的事件、候选查询和事务接口。
2. 落实取消责任的独立收场、统一中间文件清理和报告接口；依据录像中间文件生命周期规则落实归属、清理及恢复接口。
3. 依据公共协议安排各组件的协议接入；软件集成测试使用设备替身，设备证据清单用于单独安排真实联调。
4. 据上述结果形成数据库、内部接口、线程与进程生命周期及配置设计，再沿同一业务链复核失败和恢复。
5. 将上述设计纳入实施计划，明确依赖、逐步测试、真实软件组件组合的验证门禁及最终验收；计划审阅完成后进入生产实现。

上述工作涉及持久化、并发、状态机及跨组件交接，属于复杂工作。**不直接向执行者交接为“自行补齐”的代码任务。** 行为尚未确认时只能交接设计问题；确认后，实施计划必须包含相应决策表、事务边界、入口、先失败测试后实现的步骤及阶段验收。若设备事实或实际代码与计划不一致，停止相关任务并报告证据。

数据库实施计划须沿事件保存、当前投影、对象关联、目录与快照、同一 H 查询、报告生成和客户端导入安排任务依赖。整数编号及历史引用规则是事件与恢复共同使用的依据；应急补记、设备占用、目录切换和运行库入口检查须接入各自的事务与失败路径。各模块分别通过检查后，仍须验证完整链路在回滚、提交未知、重试及重启恢复后的可观察结果，并独立核对实现与验证证据。

检查遵守第一版的 MVP 范围和正常运行假设。扩大故障保障范围须有新的需求或运行证据，不能由实施工作自行引入。

### 历史与报告的实施准备

历史归属、快照范围、变化计数与同一 H 查询由[文件独立历史](database/outputs-files.md#文件独立历史与关联查询)、[历史查询](historical-state-query.md)和[报告变化目录](database/report-changes.md)定义。历史对象、[字段依赖](database/report-dependencies.md#检查与实施边界)及[事件转换](database/event-transitions.md)已有机器可读的规则和设计检查；报告依赖所需 SQL 与事件类型范围已同步。以下列出生产实现与集成验收任务。

- **接入统一历史对象登记。** [内部登记](database/enum-registry.json)已提供对象编号、主表、报告及快照资格，SQL 约束与快照排序从该登记生成。后续目录引用校验、快照维护和恢复读取同一登记；不得因文件具有独立历史就新增公共报告文件集合。
- **实现分批查找旧文件记录。** [接口、候选查询和继续规则](historical-state-query.md#按历史边界分批查找关联文件)已定义。使用已同步的文件历史元数据和关系约束，按逐表归属生成快照；验证零有效结果页、固定上界、来源从未知补齐、独立文件恢复及读取失败。执行 H-01—H-06，不使用当前关系或当前清理状态替代 H 的结果。
- **实现事件规则的生产消费者。** 读取[事件转换规则](database/event-transitions.json)中的事件类型、版本、分支、列权限、状态模型及具名业务校验；事件报告影响判断与字段生成读取[字段依赖说明](database/report-dependencies.json)，不另写完整映射。报告依赖、事件列分类与 SQL 已同步。生产代码执行条件、关联、证据与共同提交校验，再应用可逆变化。历史引用按同一文件的业务引用、派生计算及基础表规则处理；事件范围、完整边界与具体引用值按 J-01—J-06 验证。重建目录时使用原事件版本与事件发生时的关系，核验既有业务序号，不使用最新关系重新解释旧事件。
- **验证实际分页查询。** 采用[对象选择的 SQL 与容量规则](database/report-changes.md#报告对象选择的索引与分页)，落实有界预查询与大范围按对象 ID 续读，不按报告名称或全范围计数选择路径。在有代表性数据并执行 `ANALYZE` 的数据库中检查查询计划和实际读取量，验证去重、排序和续读成本；分页期间的新提交不得混入固定范围。[开发环境实验](../superpowers/notes/2026-09-30-report-pagination-experiment.md)保留样本、测量方法及结果范围，不代替目标主机性能或生产查询与报告的组合验证。按[独立历史与报告重建验收](database/consistency-verification.md#独立历史与报告重建)比较正向恢复、逆向恢复和从初始状态回放的结果，验证同一报告重建字节不变。

### 驱动与主机的实施准备

正式行为以本表引用的章节为准。以下工作需要在执行计划和实施中落实，不作为新增业务规则；结果记录只保存执行、恢复及结果解释所需的数据，沿用第一版运行假设和故障范围。

- **实现结果保存与校验。** 按尝试规格定义的类型和版本校验结果正文，落实 SQL 空值约束、完整结果事件及正反向历史恢复。具体设备和文件适配器按操作含义定义必要业务观察及其格式，把这些定义作为程序、检查脚本和测试共同使用的来源；已有尝试关联、错误和退出信息不重复保存。公共报告按[字段契约](../architecture/report-format.md)选择业务结果。
- **写清进程退出检查步骤。** 按[启动与回收约定](../host-demo/design.md#受管工具的启动与主程序回收约定)建立原进程组并保留 camctl 退出记录。[本地核验](../superpowers/notes/2026-09-28-adb-call-cleanup-experiments.md#linux-本地进程收场核验)支持 `waitid(..., WNOWAIT)` 与终止后读取 `/proc` 的方法；执行计划须写清怎样分批找出原组的进程、检查存活线程，并区分读取期间进程退出、读取被拒绝、信息不完整和解析失败。结合现有工作线程安排检查，不长时间阻塞其他调用的输出和退出处理。
- **按原保证验证组合行为。** 将启动、退出观察、原组终止、停止确认、最终回收和下一次调用放行一起实施，验证 R-01—R-14。软件集成测试使用真实本地进程和受操作契约约束的设备替身；实际主程序的信号和回收行为、工具及包装程序是否保持组归属、查询与终止权限，以及固定 ADB 版本的启动行为，另列目标主机联调。现有接入代码和数据库检查通过不代表这些工作已经实现。

进程收场与结果持久化的修改涉及恢复和跨组件协作，实施前须形成包含失败分类、任务依赖及验收门禁的执行计划。若实际主程序或工具不能满足正式约定，应带具体证据重新讨论保证范围。
