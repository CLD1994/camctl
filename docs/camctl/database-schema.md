# 数据库结构与字段归属

[设计入口](README.md) · [数据库执行与事务](persistence-runtime.md) · [历史存储](history-storage.md)

本页定义状态库的物理组织原则。业务事实、历史边界、快照和文件生命周期分别遵守对应专题；物理上拆分记录不改变业务对象的身份、事务边界或恢复责任。

## 按职责组织业务投影

当前投影按业务职责分表。每张表集中表达一种实体、关系或处理责任；相关业务通过明确的持久化接口读取和更新，不直接修改其他模块的内部状态。

历史事件使用统一的 `history_events` 表，公共信息使用固定列，各类事件的业务事实与必要恢复信息使用有明确格式的 JSON 正文。`history_transactions` 保存事件的完整提交分组。当前投影、历史查询目录和快照均遵守其从权威历史派生的规则。

## 主键与身份引用

所有表统一使用名为 `id` 的单列整数主键，采用 SQLite 的 `INTEGER PRIMARY KEY`。该类型支持 64 位有符号整数，最大值为 `9223372036854775807`（`2⁶³ − 1`），见 [SQLite 整数主键](https://www.sqlite.org/lang_createtable.html#rowid)。各表按自身业务契约确定合法值与分配规则；主键的存储类型不代替字段的业务范围约束。

业务对象的身份就是所属表的 `id`。规格和公共协议中的身份名称用于说明所引用的对象，不要求主表使用同名字段，也不另行建立一套业务身份与主键之间的映射。

| 语义名称 | 数据库中的身份 |
| --- | --- |
| `plan_instance_id` | `plans.id` |
| `action_instance_id` | `actions.id` |
| `output_id` | `outputs.id` |
| `delivery_id` | `deliveries.id` |
| `diagnostic_id` | `plan_file_diagnostics.id` |
| `report_id` | `reports.id` |
| 历史事件位置 `event_seq` | `history_events.id` |
| 历史事务标识 `transaction_id` | `history_transactions.id`，在事务表内从 1 独立递增 |

表之间通过整数值引用目标表的 `id`，引用字段的名称表达所属关系或目标角色。主键在所属表内唯一；跨对象类型的历史关联同时保存对象类型和对象 ID，不能仅凭整数相等判断两个对象相同。业务对象在重启恢复和历史重建中沿用原身份。

关联表、明细表、快照表和单份状态表同样具有 `id` 主键。具有业务唯一性的字段组合另设唯一约束。例如，来源成员关系仍须保证同一所属动作与同一来源动作不重复；对象事件关联仍须保证同一对象与同一事件只关联一次。单份状态表还须保证只有一条规定的记录，其固定主键值由表定义确定。

历史事件以 `id` 保存事件序号，历史事务以独立递增的 `id` 标识分组，并以 `first_event_id`、`last_event_id` 引用首尾事件；`plans.id` 同时承担计划身份与受理顺序，分配和读取遵守[新计划受理序列](../architecture/protocol-session.md#新计划受理序列)；`change_seq` 表达业务报告覆盖范围。数据库对象身份在公共 JSON 中使用同一整数的规范十进制字符串，范围为 1～9223372036854775807；计划、动作、产物、交付、诊断和报告及其引用均遵守这一表示。字符串编码规则由[对象 ID](../architecture/plan-input.md#对象-id)定义。对象按 ID 排序时使用其精确整数值；报告实体集合、相应分页和快照候选的 ID 比较遵守同一规则。水位、计数及独立序号遵守各自数值契约。

## 日期时间的存储

用于保存日期时间的数据库普通列统一使用 SQLite `INTEGER`，值为自 `1970-01-01 00:00:00 UTC` 起经过的整数微秒数。起点之前使用负数，起点本身为 0；每个时间字段的定义明确标注 UTC 和微秒单位。存储使用 64 位有符号整数，合法日期及业务范围继续由所属字段契约决定。

| 内部 UTC 时间示意 | 数据库整数值 | 含义 |
| --- | --- | --- |
| `1969-12-31 23:59:59.999999` | `-1` | 起点之前一微秒 |
| `1970-01-01 00:00:00` | `0` | 时间戳起点，是一个确定的时间 |
| `1970-01-01 00:00:01.250000` | `1250000` | 起点之后一秒又二十五万微秒 |

输入解析、数据库写入、读取、历史恢复及输出转换保持整数微秒的精确值，不经过浮点秒数，不将不合法的日期或超出允许精度的输入舍入为合法时间。公开时间字段继续遵守[UTC 时间字面量](../architecture/plan-input.md#时间字面量)，包括年份范围和固定到秒的格式；其全部合法时间均可用此整数表示。

合法公共时间采用唯一的秒级格式，在数据库中保存为对应整数微秒；报告和原计划重建从整数值还原相同字符串。字段省略、显式空值和非法输入继续按原始输入规则区分保存；错误输入不生成虚构的有效时间。实际运行观测的时间仍可以具有微秒精度，不能因为公共计划时间固定到秒而截断内部事实。事件和快照 JSON 中各项内容的表示由其格式契约定义，恢复到时间列后须得到相同整数微秒值。

0 和负数具有真实时间含义，不能用作尚未发生、未知或不适用的占位值；具体可空性及状态组合由各表字段定义。日期时间值与其可信性分别表达，保存了整数时间不表示启动墙钟检查已经通过。历史顺序仍由事件 ID 确定，不以时间戳代替。

本节适用于日期时间，不改变时长、超时和重试间隔各自的单位。会话内经过时长继续使用单调钟；单调钟读数不是 UTC 日期时间，不能写入这些时间列或用于跨会话相减。精确转换与验证要求见[日期时间的精确适配](data-types.md#日期时间的精确适配)。

## 空值与状态组合

数据库字段没有具体值时使用 SQL `NULL`。每个可空字段必须定义空值的准确含义；没有值的原因由该字段的固定语义或记录中的明确状态解释。不同原因会导致不同处理时，读取和写入同时判断状态与字段值，不能仅凭 `NULL` 选择业务分支。

优先复用记录已有的业务状态。只有实际存在需要区分的情况、且已有字段不足以表达时，才增加专门的状态字段。例如，尚未取得文件摘要与已经确认无法取得摘要，都没有摘要值，但后续处理不同，需要由相应处理状态区分；取得成功时必须保存完整合法摘要。具体状态值及原因字段由所属业务契约确定。

各表按有效业务状态，将每个字段划分为必须有值、可以没有值或必须没有值，并定义合法组合：

| 记录状态对字段的要求 | 字段实际内容 | 处理 |
| --- | --- | --- |
| 必须有值 | 满足类型、范围及业务约束的具体值 | 组合合法，按该值处理 |
| 必须有值 | `NULL` | 组合非法，不能将状态解释为尚未完成来绕过错误 |
| 可以没有值 | 合法具体值或 `NULL` | 按该字段分别定义的有值与空值含义处理 |
| 必须没有值 | `NULL` | 组合合法，按该状态规定的不适用或未形成事实处理 |
| 必须没有值 | 任意具体值 | 组合非法，不保留与状态矛盾的值 |
| 必须或可以有值 | 不符合该字段约束的具体值 | 组合非法，不转换为 `NULL` 或默认值 |

状态和值的变化按所属业务事务一起保存。数据库约束与事务写入流程共同保证合法组合；各表明确哪些不变量由数据库约束检查、哪些由业务写入流程检查。读取到矛盾组合、无法解释的业务状态或无效记录时，按状态库错误处理，不能自行补值或猜测业务结果。

0、空字符串及虚构时间不能替代缺失值；字段允许这些值时，它们表达自身的实际含义。例如，文件大小为 0 表示已取得大小为零的事实，时间值为 0 表示 UTC 时间戳起点。初始化或其他业务默认值只能用于契约明确规定的创建场景，不能掩盖后续记录缺失、非法或读取失败。

查询可靠确认记录不存在、记录存在但字段为 `NULL`、记录无效和数据库查询失败，分别按所属接口的结果或错误契约表达。查询失败不能返回 `NULL` 或空集合，使调用方误判为数据尚未形成；必要单份状态记录不存在时继续按状态库错误处理。

原始 JSON 中字段省略、显式 `null` 和具体值保持原有区别，不能直接合并到一个可空列中而丢失输入事实。事件与快照按各自格式保存重建所需的存在性、状态和值；历史回放恢复原组合，不采用本次运行的默认值补齐。具体 JSON 适配见[输入类型与精确编码](data-types.md)。

## 状态与类型的整数枚举

状态、动作类型、事件类型、对象类型及其他取值有限的内部业务标识，在数据库普通列中使用 `INTEGER` 保存，程序使用 Python 标准库 `IntEnum` 表达对应含义。持久化层在枚举成员与整数值之间转换，业务逻辑使用所属枚举类型。现有能力见 [Python IntEnum](https://docs.python.org/3.11/library/enum.html#enum.IntEnum)，转换适配见[整数枚举与协议边界](data-types.md#整数枚举与协议边界)。

每种枚举在其责任模块中集中定义明确、固定且不重复的整数值。写入过持久化数据的数值与含义保持稳定，不按成员声明顺序、列表位置或自动编号推导存储值；增加成员不改变已有编号，不将已有编号重新用于其他含义。各枚举的具体成员及编号在相应表和事件契约中定义，编号的大小不自动表示业务阶段或执行优先级。

公共协议的字段类型和字面量由根 `protocol` 维护。公共状态和类型的文本表示与内部整数枚举通过明确对应关系转换；公共合法值从协议读取或生成，内部整数编号在一处维护，并核对两者覆盖关系。数据库约束所需的合法编号集合从该定义生成或校验，不在 SQL、业务代码和测试中各自维护完整清单。内部专属枚举由其责任模块定义。

动作最终错误的 `actions.error_code` 使用可空 `INTEGER` 列，程序使用具有固定编号的整数枚举。没有最终错误时为 `NULL`；公共报告通过对应关系输出协议错误码。具体成员、编号及与动作状态的组合在错误字段契约中定义。

每个动作最终错误码的定义同时确定唯一的业务阶段。报告生成通过错误码定义取得 `error.stage`，动作投影保存错误码及相应详情；阶段不由写入调用方自由填写。编号、公共错误码和阶段的对应关系保持稳定，历史恢复及旧报告重建使用相同含义。动作错误码进入持久化契约前，须补齐这一对应关系；已有错误及驱动适配的核对范围见[动作错误码与阶段核对](database-boundary-review.md#动作错误码与阶段核对)。本规则适用于动作最终错误，不自动扩展到操作尝试、文件诊断或会话错误。

| 保存或读取情况 | 处理规则 |
| --- | --- |
| 写入合法枚举成员 | 保存该枚举成员固定的整数值，同时保证状态与其他字段的组合合法 |
| 读取所属枚举已定义的整数 | 转换为对应枚举成员，由业务逻辑解释 |
| 读取未定义整数、错误存储类型或无法解释的内部业务标识 | 按状态库错误处理，不替换为初始状态、未知状态或 `NULL` |
| 字段允许 `NULL`，且与记录状态组合合法 | 按字段空值契约处理，不将 `NULL` 隐式转换为某个枚举成员 |
| 读取原始输入或协议明确允许开放值的内容 | 按该内容的协议保留合法值或错误证据，不强制纳入封闭枚举 |

该规则不改变原始输入和公共 JSON 的表示。原始输入、驱动参数及开放的外部错误码继续按各自契约保存；有限枚举不能成为丢弃外部未知值或改写非法输入的理由。事件和快照中的枚举表示按其格式契约定义，重建时恢复同一含义与稳定编号。

## 主要业务对象与主表边界

计划、动作、正式产物、普通交付、输入文件诊断和状态报告分别建立主表。产物之间的来源关联由 `output_origins` 表保存，自动预览取回与来源拍摄的关联由 `auto_preview_links` 表保存，取回和范围清理的来源成员由 `action_output_sources` 表保存。取回的逐来源选择与逐目标处理分别由 `obtain_source_selections`、`obtain_items` 保存，清理的逐目标处理由 `cleanup_items` 保存。公共操作流程及其尝试分别由 `operation_runs`、`operation_attempts` 保存，文件拷贝专属状态由 `file_copies` 保存。

设备文件的身份、定位信息、业务归属及可靠取得的文件事实由 `device_files` 保存；主机中间文件的归属、用途及清理状态由 `intermediate_files` 保存。取消动作的逐目标处理由 `cancel_items` 保存，针对目标取回中各份交付的处理由 `cancel_delivery_items` 保存。录像内部检查与修复的决定、进度和结果由 `recording_processing` 保存，动作在设备上启动的持续活动及其已知状态由 `device_activities` 保存。

显式状态同步的固定起点、开始依据和责任结束情况由 `state_syncs` 保存，客户端累计确认位置、可信历史时间下界及中间文件清理继续位置由 `runtime_state` 保存。业务投影由二十三张表组成：六张主表、三张关联表、两张取回明细表、一张清理明细表、两张取消明细表、两张公共操作表，以及设备文件、文件拷贝、中间文件、录像处理、设备活动、状态同步和全局运行状态各一张表。

历史事实及提交分组分别由 `history_events`、`history_transactions` 保存，对象与事件的关联由 `entity_event_links` 保存。对象快照及其维护进度分别由 `entity_snapshots`、`entity_snapshot_progress` 保存，数据库元信息由 `database_metadata` 保存，与业务投影共同构成二十九张表。表清单的覆盖范围与跨流程职责见[数据库表职责核对](database-boundary-review.md)，字段、约束和索引由后续表定义细化。

| 主表 | 一条记录表示什么 | 归属与生命周期 |
| --- | --- | --- |
| `plans` | 一个成功受理的计划实例 | 保存首次成功受理的请求关联和计划自身状态；动作分别存储。计划结束后仍可被后续请求引用 |
| `actions` | 一个已受理计划中的动作实例 | 每个动作属于一个计划；各动作类型共用身份与公共执行状态，专属处理记录按各自职责组织 |
| `outputs` | 一份已登记的正式产物，对应一份文件 | 属于产生它的动作；原文件、预览和修复成品分别有自己的产物记录。文件清理改变可用性，记录永久保留 |
| `deliveries` | 一个取回动作针对一份正式产物创建的普通交付 | 同时关联取回动作和实际产物；同一产物可被不同取回交付，跨会话恢复沿用原交付 |
| `plan_file_diagnostics` | 一次输入处理中形成的完整文件诊断 | 不要求已有计划或合法请求身份；提交后内容固定。另一次输入再次失败时形成新的诊断，历史重建复用原记录 |
| `reports` | 一份已登记的逻辑状态报告 | 保存固定身份和生成依据，并关联后续文件处理事实；可以覆盖多个计划及输入诊断，不属于某个单独计划 |

这些主表保存可直接查询的业务记录，权威业务事实仍由不可变历史保存。历史与相关主表、子表和查询目录按同一业务事务更新；输入诊断等内容固定的记录也遵守这一原子保存规则。

### 请求身份与成功受理关联

`plans.request_id` 使用 `INTEGER NOT NULL`，范围为 1～9223372036854775807，并具有唯一约束。公共 JSON 中的请求身份使用规范十进制字符串，主机通过精确整数转换保存和查询。请求 ID 由调用方提供，计划 ID 由 camctl 分配；二者分别表达逻辑请求与已受理计划，不要求数值相同。

`plans` 直接保存请求身份与计划实例的一对一关联，承担按请求查找首次成功受理结果的职责。该关联与计划、全部动作及对应历史一起提交，并在计划结束后永久保留。请求身份作为计划的受理依据保存，不建立独立请求表。

首次受理、幂等复用和拒绝的判定遵守[请求身份规则](../architecture/plan-acceptance.md#request_id)。同一请求此前被拒绝时，失败事实保存在输入文件诊断中；后续成功受理建立计划及关联，原诊断继续保留。诊断中的请求身份只表示本次输入可靠取得的身份，不能作为成功受理凭据。

同一请求重送时复用原计划，新的有效 ACK 仍按[独立处理规则](../architecture/plan-acceptance.md#计划正文与-ack-独立处理)保存其实际影响。累计确认和输入诊断分别由所属记录承担，不通过改写原计划内容表达。

### 计划与动作

首次受理成功时，计划和全部动作一起登记；动作可以因为自身参数错误而初始失败。整份输入被拒绝时不登记本次计划和动作，按输入诊断规则保存问题。同一请求重送复用原计划，不新建动作。

动作主表统一表示拍摄、取回、清理、取消和显式报告等已支持动作。各类动作的专属状态、逐项结果、执行尝试及恢复责任不因共用主表而合并为同一种流程，其物理组织按相应生命周期确定。

计划状态由动作事实派生，与引起变化的动作事实共同提交。计划完成不表示产物已删除、设备活动已结束、文件已传输或客户端已确认；这些后续责任由所属记录表达。

### 计划与动作的输入存储

计划的固定公共字段使用普通列保存。动作按独立记录保存，字段和值的存在性、精确数值及原数组位置共同支持原计划重建。下表定义身份与输入部分；运行状态见[计划与动作的运行状态](#计划与动作的运行状态)，其他字段继续由相应表契约细化。

| 表与字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `plans.id` | `INTEGER PRIMARY KEY`，正整数 | 计划身份及首次成功受理顺序；按受理写事务分配 |
| `plans.request_id` | `INTEGER NOT NULL UNIQUE`，正整数 | 调用方提供的请求身份，范围与转换遵守上一节 |
| `plans.name` | `TEXT NOT NULL` | 已通过公共结构校验的计划名称，不要求跨计划唯一 |
| `plans.created_at` | `INTEGER NOT NULL` | 客户端创建计划的 UTC 时间，单位为微秒；合法输入固定到秒，值为整秒对应的微秒数，不证明主机时间可信 |
| `actions.id` | `INTEGER PRIMARY KEY`，正整数 | 动作身份 |
| `actions.plan_id` | `INTEGER NOT NULL`，引用 `plans.id` | 所属计划 |
| `actions.input_index` | `INTEGER NOT NULL`，非负整数 | 动作在首次受理的输入数组中的位置，从 0 开始 |
| `actions.name` | `TEXT NOT NULL` | 已通过公共结构校验的动作名称，在所属计划内精确唯一 |
| `actions.type` | `INTEGER NOT NULL` | 已支持的动作类型，使用固定整数枚举，与公共类型字面量一一对应 |
| `actions.device_id` | 可空 `TEXT` | 通过该字段校验的部署设备标识，例如 `cam0`；设备由动作类型决定是否必填 |
| `actions.scheduled_at` | 可空 `INTEGER` | 调用方指定的计划开始处理时间，保存为 UTC 整数微秒；合法输入固定到秒 |
| `actions.group_name` | 可空 `TEXT` | 动作在所属计划中的有效组名；公共输入和报告使用字段名 `group` |
| `actions.input_fields_json` | `TEXT NOT NULL`，精确 JSON 对象 | 普通列不能完整表达的原始输入，包括可变参数、策略、非法值和额外字段；没有这些内容时为 `{}` |

`actions` 分别对 `(plan_id, input_index)` 和 `(plan_id, name)` 设置唯一约束。名称比较保持输入的大小写与 Unicode 字符，不做归一化。首次受理时，输入位置覆盖从 0 到动作总数减 1 的全部位置；失败动作也占有原位置。原计划重建按该位置组装全部动作，报告实体集合继续按各自 ID 排序，二者不相互替代。

`device_id` 引用部署配置中的设备标识，使用原标识字符串，不是数据库对象的整数主键。拍摄动作必须指定符合契约的设备；取回、清理、取消和报告动作的该列为 SQL `NULL`，其实际设备或文件位置按来源、产物或目标确定。首次受理后更新部署配置不改写已保存的设备标识。

`scheduled_at` 的必填性由动作类型决定：拍摄、取回和清理必须提供；取消和报告可以省略。允许省略且动作通过受理校验时，该列为 SQL `NULL`，执行会话取得资格后立即处理，不填入受理时间作为替代。合法值为整秒对应的 UTC 微秒数，实际日期及格式遵守[时间字面量](../architecture/plan-input.md#时间字面量)。时间已过只影响执行时的调度判断，不使其成为静态非法输入。

`group_name` 按输入原字符保存，不改变大小写或进行 Unicode 归一化。同一个组由 `(plan_id, group_name)` 确定，多个动作可以具有相同的组归属；这不是动作表的唯一约束。未提供组名或组字段非法时为 SQL `NULL`。有效组归属和其他输入字段分别校验，其他参数失败不抹去合法组归属。

三个普通列同时满足查询及原输入重建要求。原始输入按以下互斥分区保存；同一个原始字段只从指定来源重建。

| 输入分类 | 保存与重建规则 |
| --- | --- |
| 必须合法才能受理的动作名称和类型 | 保存为普通列；类型通过固定枚举与协议字面量的对应关系重建 |
| 提供了设备、时间或组字段，且通过该字段适用的校验 | 保存为有效普通列；字符串保持原字符，时间从整数值按固定秒级格式还原；其他参数错误不抹去合法组归属 |
| 上述字段未提供，且对应动作允许省略或要求省略 | 普通列为 SQL `NULL`，`input_fields_json` 中没有该字段；重建时省略 |
| 上述字段未提供，但对应动作要求必填 | 普通列为 SQL `NULL`，`input_fields_json` 中没有该字段；动作在受理时失败，错误保留字段缺失的原因，重建时仍省略 |
| 提供了上述字段，但其类型、值或适用性非法，包括显式 `null` | 原始字段及其值保存在 `input_fields_json`，有效列不产生虚构值；重建时保留原字段和 JSON 类型 |
| 提供了 `params`、`policy` 或额外字段 | 在 `input_fields_json` 中保留原键和值，包括空对象、数组、精确数值及非法类型；省略的键仍省略 |

读取时校验字段归属、存在性和状态组合；设备、时间或组字段同时出现在普通列的有效表示与原始例外表示中，或者缺少契约要求的依据，按状态库错误处理，不选择其中一份猜测。合法时间不需要额外的原字符串列。输入 JSON 的空白、缩进和数值字面量写法不属于原计划重建契约；结构化值和字段存在性须保持。

调度不能仅凭 `scheduled_at IS NULL` 判定立即执行，必须先确认动作通过受理校验、类型允许省略时间，并满足相应执行资格。受理失败动作的空列不产生执行资格；提供非法值时，原值与失败原因共同解释空列的含义。某一字段非法不清除其他已经通过自身校验的普通列值。

三个字段在首次受理时与动作、原始输入例外及历史共同保存。请求重送、重启和后续配置变化均不改写原值；历史回放还原原列值与原始字段的存在性。数据库约束检查存储类型及适用的范围、状态组合；业务写入和读取流程核对字段适用性、原始输入归属及受理结果。验证覆盖合法值、合法省略、必填缺失、显式 `null`、非法类型或值、动作不允许该字段、其他参数失败但本字段合法，以及原计划重建与恢复的一致性。

生效拍摄参数和用户业务策略按[生效拍摄参数与启动延迟](#生效拍摄参数与启动延迟)保存，原始 `params` 和 `policy` 表达调用方实际提交的内容；拍摄默认值不能反向覆盖原输入。本地执行配置由每次运行加载，后续操作按[本地配置变化与未完成工作](../architecture/configuration.md#本地配置变化与未完成工作)处理。运行状态、尝试消耗、固定来源及逐项结果由所属普通列、关联表和明细表保存，实际判断采用的必要配置值随对应事实保存。

计划与全部动作的普通列、必要 JSON、有效关联和对应历史在同一受理事务中形成。历史创建事实提供重建这些列和值的依据；当前投影仍可从历史恢复。原计划由计划自身字段和按原位置读取的动作组装，独立 ACK 继续按其确认事实处理。

### 生效拍摄参数与启动延迟

调用方省略驱动允许缺省的拍摄字段时，原始 `params` 保持省略，完整生效参数保存驱动补齐的默认值。执行与恢复使用首次受理保存的生效参数；原计划重建使用原始输入。二者分别表达调用方输入与动作通过受理后确定的拍摄要求。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.effective_params_json` | 可空 `TEXT`，非空时为精确 JSON 对象 | 通过全部受理校验的拍摄动作的完整生效参数，包含 `type` 及按驱动契约补齐的默认值 |
| `actions.max_delay_ms` | 可空 `INTEGER`，非空时为非负整数 | 从通过该动作业务策略校验的 `policy.max_delay_ms` 提取的启动延迟，单位为毫秒 |

生效参数只适用于 `camera_take_photo`、`camera_record` 和 `camera_timelapse`。参数结构由已选驱动及参数类型定义，不拆成各驱动专用列，也不另建参数表。SQL `NULL` 表示没有生效参数；JSON `null`、数组、标量以及缺少必要字段的对象均不能替代完整参数对象。驱动定义无法可靠取得等内部故障按既有会话错误处理，不能登记为调用方参数错误。

`max_delay_ms` 是调度使用的派生列，原始 `policy` 仍完整保存在 `input_fields_json`。原计划与报告的 `policy` 均从原始输入重建，不用普通列补造省略的字段或替换非法输入。只有拍摄动作的整个业务策略通过校验时才提取该值；即使其中的 `max_delay_ms` 本身合法，存在不支持的策略字段等错误时，该列仍为 SQL `NULL`。其他字段导致动作受理失败，不抹去独立通过校验的业务策略值。`0` 表示不允许延迟启动；SQL `NULL` 不代表 `0`，也不提供执行资格。

下表中的受理结果是首次受理时的完整判定，不按动作后续的运行状态重新计算。

| 条件 | `effective_params_json` | `max_delay_ms` |
| --- | --- | --- |
| 整份计划被拒绝 | 不创建动作记录 | 不创建动作记录 |
| 拍摄动作通过全部受理校验 | 保存完整生效参数 | 保存通过校验的值 |
| 拍摄动作的业务策略合法，但其他受理条件不满足 | SQL `NULL`，即使拍摄参数本身合法也不保存生效参数 | 保存通过校验的值 |
| 拍摄动作的业务策略缺失或非法，不论其他字段是否通过校验 | SQL `NULL` | SQL `NULL`；原始输入保持原样 |
| 已支持的非拍摄动作，不论是否通过自身受理校验 | SQL `NULL` | SQL `NULL`；不适用的策略输入按既有规则使动作初始失败 |

合法受理的拍摄动作后来过期、取消或执行失败时，两个字段保持首次保存的值。受理失败动作保留原始输入和错误，报告不提供 `effective_params`；不能因某个拍摄参数局部合法而保存可执行参数。两个字段是否为空须结合动作类型、受理结果和原始业务策略解释，不能仅凭 `status = failed` 判断。

两个字段、原始输入、动作受理结果及对应历史在同一受理事务中保存。`max_delay_ms` 必须与原始合法策略中的值精确一致，二者不能分别修改；它不是第二份可独立调整的业务要求。生效参数与原始参数可以因默认值补齐而不同。请求重送、重试、重启及配置变化不改写这些值；历史回放按创建事实恢复，不调用驱动按新的默认值重新计算。

数据库约束检查类型、范围及适用的空值组合，业务读写核对受理分类与原始策略的一致性。不符合契约的记录按状态库错误处理，不从配置补值或在两个策略值中任选其一。调度计算启动窗口时使用 `actions.max_delay_ms`，先确认动作具有执行资格，再按时间字段单位精确换算。

验证覆盖上述全部分区，以及驱动默认值补齐但原输入不变、其他字段非法但业务策略合法、合法延迟与非法额外策略字段并存、缺失策略、显式 `null`、错误类型、负数和零延迟。还须验证受理后过期、执行前取消、执行后失败、请求重送、默认值变化、重启与历史回放均保持原值；派生列与原始策略不一致、缺少必要生效参数及不适用对象出现生效参数时按状态库错误处理。报告验证覆盖生效参数解码为对象、受理失败省略该字段，以及原始 `policy` 的存在性和值保持不变。

### 拍摄动作的驱动绑定

拍摄动作通过受理校验时，camctl 从目标设备的本地配置中选择驱动，使用该驱动的参数契约确定生效参数。动作同时保存设备标识、驱动标识和生效参数，以便后续执行能够使用原来选定的驱动解释这些参数。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.driver_id` | 可空 `TEXT`，非空时为非空字符串 | 拍摄动作首次通过全部受理校验时选定的驱动标识，与能力说明的 `driver_id` 使用同一标识 |

驱动标识按字符串精确匹配，不是数据库对象的整数主键，也不引用驱动表。标识由驱动注册契约定义，保持稳定，不使用随代码重构变化的 Python 类路径。动作保存驱动选择，不保存整份驱动配置。

| 首次受理结果 | `driver_id` 的保存规则 |
| --- | --- |
| 整份计划被拒绝 | 不创建动作记录 |
| 拍摄动作通过全部受理校验 | 保存实际用于校验和确定生效参数的驱动标识 |
| 拍摄动作在受理时失败，包括已经找到驱动但其他字段非法 | SQL `NULL`；原始输入与受理错误仍按各自契约保存 |
| 已支持的非拍摄动作，不论是否通过自身受理校验 | SQL `NULL`；所需设备及驱动依据从实际来源或目标取得 |

`driver_id` 与 `effective_params_json` 在拍摄动作通过全部受理校验时共同形成，其他动作记录的这两个字段均为 SQL `NULL`。驱动标识、设备标识、生效参数、受理结果及对应历史在同一受理事务中保存。合法受理后的过期、取消、执行失败、请求重送、重试和重启均不改变原驱动标识。读取空字符串、错误类型或不符合受理分类的组合时，按状态库错误处理，不从本地配置补造首次驱动选择。

取回动作可以涉及多台设备，其自身不选择一个统一驱动。设备文件的读取、核实与删除沿实际文件的来源取得原设备及驱动依据；取消涉及的设备操作沿目标动作或所属设备活动取得依据。来源拍摄动作已经终态，不清除后续设备活动、取回及清理仍需使用的绑定事实。具体关联由设备文件和设备活动的字段设计落实。

后续运行在发起设备操作前核对原绑定与本次设备配置。判定按下表处理；“继续”仍以所属业务的执行资格与恢复规则成立为前提。

| 处理对象与本次配置 | 绑定处理规则 |
| --- | --- |
| 只回放历史、读取已保存事实或重建报告 | 使用历史中的原标识与参数，不调用旧驱动；这些状态重建过程不要求旧驱动仍安装 |
| 需要设备操作，所需设备配置可用，且绑定驱动与原记录一致 | 使用原生效参数，后续操作采用本次运行的本地执行配置 |
| 需要设备操作，但所需设备配置缺失 | 不发起相关设备操作，明确报告配置问题 |
| 需要设备操作，设备配置存在，但绑定驱动与原记录不同 | 不发起相关设备操作，明确报告绑定不一致；不把原参数交给新驱动，也不改写原驱动标识 |

上述设备配置缺失或驱动绑定不一致使无法执行的动作、处理项或设备收场流程按所属规则失败，不使 `run` 立即结束；其他设备、本地处理和报告维护继续推进。已有终态、取消和过期规则优先，流程失败不证明设备已经停止或文件已经删除。绑定失败原因、业务结果和原设备事实按所属事务共同保存，配置修正或重送不重开已失败任务。完整状态分类、执行标记与退出规则遵守[设备绑定异常的影响范围](../architecture/configuration.md#设备绑定异常的影响范围)。

驱动标识表达驱动选择，不证明物理相机未被替换，也不记录完整软件版本。部署负责保持设备身份和同一驱动标识下对已有动作的兼容性。第一版不增加驱动版本管理或物理设备替换检测机制。驱动定义或配置本身无法可靠加载的情况，继续遵守既有配置加载错误规则。

验证覆盖首次受理的全部分类、事务提交前后中断、终态后保留、重送与重启不重选驱动，以及历史回放和报告重建不调用驱动。设备操作验证覆盖绑定一致、仅本地通信参数改变、设备配置缺失和驱动绑定不一致；后两者不能产生相关设备操作。跨设备取回、文件清理及取消须逐来源或目标取得绑定，不能使用发起动作的单一驱动代替。

### 计划与动作的运行状态

计划 A 中一个动作已经执行结束，另一个动作仍等待未来时间时，A 仍处于运行阶段。录像动作 B 已经接受取消要求、但停止操作尚未结束时，B 仍在运行，其普通执行资格已经终止。状态、是否曾执行及取消是否生效分别保存，以便重启后恢复这些不同事实。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `plans.status` | `INTEGER NOT NULL`，计划状态枚举 | 由全部所属动作事实派生的计划执行阶段 |
| `actions.status` | `INTEGER NOT NULL`，动作状态枚举 | 动作的执行阶段或最终结果 |
| `actions.execution_started` | `INTEGER NOT NULL`，只允许 0 或 1 | 是否曾可靠保存首次进入 `running` 的事实 |
| `actions.cancel_requested` | `INTEGER NOT NULL`，只允许 0 或 1 | 针对该动作自身执行的取消要求是否已经生效 |

状态字段在程序中使用各自的整数枚举，两个标记使用 `bool`。创建动作时两个标记均为 0；状态由受理校验结果确定。标记一旦成为 1，后续执行、重试及重启均保持为 1。读取非法状态、非 0/1 标记或缺失值按状态库错误处理，不补初始值。

计划状态采用以下固定编号，公共报告使用表中的协议值：

| 整数编号 | 枚举成员 | 公共协议值 | 含义 |
| --- | --- | --- | --- |
| 1 | `PENDING` | `pending` | 尚无动作开始执行，且仍有动作未结束 |
| 2 | `RUNNING` | `running` | 曾有动作开始执行，且仍有动作未结束 |
| 3 | `COMPLETED` | `completed` | 全部动作已进入终态 |

计划状态依据同一完整历史边界处的全部所属动作判定，不能只检查报告中的动作子集合或本次进程持有的协程：

| 全部动作已终态 | 是否存在 `execution_started = 1` 的动作 | `plans.status` |
| --- | --- | --- |
| 否 | 否 | `PENDING` |
| 否 | 是 | `RUNNING` |
| 是 | 否或是 | `COMPLETED` |

计划允许保持原状态，或发生 `PENDING → RUNNING`、`PENDING → COMPLETED`、`RUNNING → COMPLETED`。至少一个动作开始执行后，计划不会因暂时没有运行中动作而退回 `PENDING`。全部动作在受理时失败，或全部在执行前取消、过期时，计划也进入 `COMPLETED`。具体成功、失败、过期和取消结果由各动作表达，计划完成后保持终态。

动作状态采用以下固定编号；编号大小不表达执行优先级或允许的转换顺序：

| 整数编号 | 枚举成员 | 公共协议值 | 含义 |
| --- | --- | --- | --- |
| 1 | `PENDING` | `pending` | 已受理，尚未开始执行 |
| 2 | `RUNNING` | `running` | 已开始执行，包括等待条件和必要收场 |
| 3 | `SUCCEEDED` | `succeeded` | 动作成功结束 |
| 4 | `FAILED` | `failed` | 受理校验失败或执行失败 |
| 5 | `EXPIRED` | `expired` | 拍摄动作未能在允许窗口内成功启动 |
| 6 | `CANCELED` | `canceled` | 动作已按取消规则结束 |

`execution_started` 表示 camctl 开始执行该动作，不证明设备命令已经发出或设备已成功开始工作。首次从 `PENDING` 进入 `RUNNING` 时，状态与标记在同一事务中保存；后续报告的 `execution.started` 由该标记转换为布尔值。`cancel_requested` 只在目标取消事实可靠提交后生效，取消目标明细已经创建或协程已收到取消信号均不能替代它。

下表列出动作状态与两个标记的全部合法组合；未列出的组合不允许保存。错误详情、过期原因、动作类型资格及关联记录还须满足各自业务契约。

| `actions.status` | `execution_started` | `cancel_requested` | 对应事实 |
| --- | --- | --- | --- |
| `PENDING` | 0 | 0 | 尚未开始执行，没有生效的取消要求 |
| `RUNNING` | 1 | 0 | 正常处理或等待执行条件 |
| `RUNNING` | 1 | 1 | 取消已生效，必要收场尚未结束 |
| `SUCCEEDED` | 1 | 0 | 执行成功结束 |
| `FAILED` | 0 | 0 | 首次受理时动作校验失败，失败阶段为 `admission` |
| `FAILED` | 1 | 0 | 开始执行后失败，保留实际错误阶段与原因 |
| `EXPIRED` | 0 或 1 | 0 | 按实际历史保留是否执行过，并保存规定的过期原因 |
| `CANCELED` | 0 或 1 | 1 | 按取消规则结束，保留是否执行过 |

取消 `PENDING` 动作时，在同一事务中将状态改为 `CANCELED`、取消标记改为 1，执行标记保持 0。取消 `RUNNING` 动作时，先将取消标记保存为 1，状态保持 `RUNNING`，停止新的普通执行和普通重试；本次规定的有限收场完成后进入 `CANCELED`。取消生效后，迟到的普通执行结果仍须如实登记设备或文件事实，但不能把动作改判为成功、失败或过期。并发取消与动作结束按写事务内的可靠状态判断，已有终态保持不变。

已终态动作后续受到取消寻址时，保持其状态及两个标记。成功取回仍有交付可以撤回时，由取消明细和交付记录保存处理结果，不将原动作改为执行被取消。目标动作的标记、取消明细中的生效进度和对应历史共同提交；多个取消入口复用目标已有事实和必要收场流程，发起取消动作自身结束不撤销目标的取消标记。完整处理边界见[取消动作](../architecture/task-cancellation.md)。

状态字段和标记的范围及本表组合由数据库约束保证；状态转换、标记只增不减、计划聚合结果及相关记录的一致性由事务写入流程保证。动作变化、受影响的计划状态和对应历史在同一事务中提交，回滚不留下部分状态。提交结果未知时先核实可靠事实，再按原状态继续；历史回放和快照恢复还原相同的状态与标记，不执行外部操作。

验证覆盖上述合法组合与其余非法组合、状态转换、初始校验失败、执行前取消、运行中取消及终态后的交付撤回。计划聚合覆盖已执行动作全部结束但仍有未来动作、全部未经执行就终态、部分动作终态和完整报告中的动作子集合。事务与恢复验证覆盖状态及标记共同提交、回滚、提交结果未知、取消与结束竞争、迟到结果和发起取消动作自身被取消；新成员不改变既有枚举编号。

### 动作最终错误字段

动作最终错误使用错误码和结构化详情共同表达。例如，启动尝试耗尽时，错误码说明动作结束的原因，详情按该错误的定义说明涉及的设备、尝试次数及相关尝试记录。不同错误需要的详情不同，详情对象的结构由对应错误契约确定。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.error_code` | 可空 `INTEGER`，动作最终错误的固定整数枚举 | camctl 根据业务结束条件确定的最终错误；没有最终错误时为 SQL `NULL` |
| `actions.error_details_json` | 可空 `TEXT`；非空时必须是合法 JSON 对象文本 | 最终错误的说明及关联依据；没有最终错误时为 SQL `NULL` |

两个字段的合法组合如下；有错误时，详情对象还须满足该错误规定的字段、类型和取值要求。

| 最终错误情况 | `error_code` | `error_details_json` |
| --- | --- | --- |
| 没有最终错误 | SQL `NULL` | SQL `NULL` |
| 有最终错误，其契约不要求额外详情，且没有额外详情 | 合法整数错误码 | JSON 对象文本 `{}` |
| 有最终错误，包含具体详情 | 合法整数错误码 | 符合该错误契约的 JSON 对象文本 |

只填写其中一个字段、保存未定义的动作整数错误码，或将详情保存为空字符串、JSON `null`、数组及其他非对象值，均为非法组合。SQL `NULL` 表示没有最终错误，`{}` 表示存在最终错误但没有额外详情，两者不能互换。有必填详情的错误不能用 `{}` 代替缺失的信息。

数据库约束检查错误码的合法范围、两个字段是否同时为空，以及非空详情是否为合法 JSON 对象；业务写入流程检查详情是否满足对应错误契约，并检查与动作状态及关联事实是否一致。错误码、详情、动作结果及对应历史在同一业务事务中提交。历史回放和快照恢复还原相同的错误码及结构化详情，不根据后续尝试结果改写动作终态时的错误。

报告生成从固定错误定义取得公共 `error.code` 和唯一的 `error.stage`，解析详情对象后输出为 `error.details`，不将 JSON 文本作为字符串再次嵌入报告。没有最终错误时，按报告契约省略动作的 `error`。用于查询和调度的业务状态保存在所属普通列或专属记录中；错误详情按契约解释结果和引用依据，不另行维护可独立修改的业务状态副本。驱动原始错误的保存遵守[动作最终错误与驱动错误](#动作最终错误与驱动错误)。

验证覆盖三个合法分区、仅一个字段为空、非法错误码、无效 JSON、非对象 JSON、必填详情缺失，以及报告生成和历史恢复前后的结构化值一致性。具体错误码、详情成员及其与动作状态的完整对应关系按[错误码与阶段核对](database-boundary-review.md#动作错误码与阶段核对)逐项落实。

### 启动窗口观察与过期原因

camctl 在拍摄动作的允许启动窗口内检查到该动作时，先可靠保存观察时间，再检查设备条件和调度资格。如果设备一直被占用，动作最终可能过期，但仍保留曾在窗口内检查到它的事实。若第一次有效检查时窗口已经结束，且没有此前可靠保存的窗口内观察，则保留未观察到的事实。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.first_window_observed_at` | 可空 `INTEGER`，UTC 整数微秒 | 首次可靠保存的窗口内观察时间；SQL `NULL` 表示没有这项持久化观察事实 |
| `actions.expiration_reason` | 可空 `INTEGER`，过期原因整数枚举 | 动作以 `EXPIRED` 结束的原因；其他动作状态为 SQL `NULL` |

过期原因采用以下固定编号，程序使用整数枚举，公共报告使用对应文本值：

| 整数编号 | 枚举成员 | 公共协议值 |
| --- | --- | --- |
| 1 | `WINDOW_MISSED` | `window_missed` |
| 2 | `WINDOW_EXHAUSTED` | `window_exhausted` |

启动窗口只适用于 `camera_take_photo`、`camera_record` 和 `camera_timelapse`。窗口内观察须满足 `scheduled_at <= trusted_wall_now <= window_end`，其中 `window_end = scheduled_at + max_delay_ms`；比较前按字段单位精确换算。提前加载未来动作不形成观察记录，设备是否空闲也不影响窗口内观察成立。

下表定义字段与动作类型、状态及持久化观察事实的合法组合；其他组合均不允许。有效观察时间必须位于该动作的启动窗口内。

| 动作类别及状态 | `first_window_observed_at` | `expiration_reason` |
| --- | --- | --- |
| 不采用启动窗口的动作，处于其允许的非过期状态 | SQL `NULL` | SQL `NULL` |
| 拍摄动作在受理校验时失败 | SQL `NULL` | SQL `NULL` |
| 合法受理的拍摄动作，尚未过期且没有持久化窗口内观察 | SQL `NULL` | SQL `NULL` |
| 合法受理的拍摄动作，尚未过期且已有持久化窗口内观察 | 原观察时间 | SQL `NULL` |
| 拍摄动作以 `EXPIRED` 结束，没有持久化窗口内观察 | SQL `NULL` | `WINDOW_MISSED` |
| 拍摄动作以 `EXPIRED` 结束，已有持久化窗口内观察 | 原观察时间 | `WINDOW_EXHAUSTED` |

表中的非过期组合仍须满足动作状态机及实际执行事实：成功启动前必须保存窗口内观察，因此成功的拍摄动作具有观察时间；失败或取消的拍摄动作按实际经历保留有值或空值。观察时间不证明已经发出设备命令，也不要求 `execution_started` 必须为 1；`WINDOW_EXHAUSTED` 可以没有任何设备尝试。不采用启动窗口的动作不能进入 `EXPIRED`。

创建动作时观察时间为 SQL `NULL`。首次有效观察与对应历史共同提交后，才能进入后续设备条件检查和执行流程；后续观察不覆盖首次时间。动作成功、失败、取消或过期均不清除已经保存的观察时间。重启继续使用原记录；若断电发生在内存观察之后、提交之前，恢复不能依据已经丢失的内存事实补造观察时间。

过期状态与原因在同一业务事务中保存，原因依据该事务所见的可靠观察记录确定。数据库约束检查整数类型、原因合法编号及表中的状态、类型和空值组合；业务写入流程检查时间可信性、窗口边界、首次观察只写一次和允许的状态转换。提交结果未知时按状态库规则核实，不猜测观察是否已经保存。历史回放及快照恢复还原原时间与原因，不根据恢复时的墙钟重新分类。

报告按整数枚举对应关系输出 `expiration_reason`，非过期动作省略该字段。观察时间用于内部调度、恢复和诊断，公共报告继续遵守[计划与动作的报告规则](../architecture/report-format.md#计划与动作)。过期判定与已经成功启动的动作后续处理遵守[公共过期规则](../architecture/scheduling-execution.md#过期原因)。

验证覆盖全部合法组合和其余非法组合、窗口起点及终点、提前加载、设备被占用但已观察、没有设备尝试就耗尽窗口、成功或取消后保留观察时间，以及首次观察提交前后中断和重启后的分类一致性。

### 动作组归属

动作的有效组归属直接保存在 `actions.group_name` 中。组由 `actions.plan_id` 和 `actions.group_name` 共同确定，成员通过动作记录查询；组作为计划内的组织名称管理，其存储由动作主表承担。公共 JSON 中仍使用 `group`，省略时数据库列为 SQL `NULL`。

组归属与首次受理的动作一起保存，判定遵守[动作组规则](../architecture/plan-acceptance.md#group)。原始输入与有效归属分别表达：非法组值保留在输入和诊断中，不产生有效归属；合法组归属不因动作的其他参数错误而消失。取回动作的来源组引用属于其操作参数，不是该动作的所属组。

按组取回、取消和报告组织分别应用各自的成员选择规则。已固定的执行来源集合及逐项处理结果由所属流程保存，不能仅凭动作上的组归属替代这些执行记录。

### 自动预览取回关联

`auto_preview_links` 保存自动预览取回动作与来源拍摄动作之间的明确关联，以及受理时可靠取得的自动用途和设备能力依据。两个动作仍分别保存在 `actions` 中；关联表回答哪个取回动作负责自动获取哪个拍摄动作的预览，`output_origins` 则回答某份预览或修复成品对应哪份原文件。

关联及能力依据与计划、动作和对应历史在同一受理事务中保存。重启和同一请求重送沿用原受理结果，不依据后续设备能力重新计算。关联属于取回动作自身状态，历史恢复和对象快照包含这些信息；保存关联本身不增加来源拍摄动作的历史变化次数。

关联按[自动取回的责任](../architecture/preview-obtaining.md#自动取回的责任)区分有效关系与失败时保留的依据：

| 受理结果 | 保存与使用规则 |
| --- | --- |
| 自动预览取回通过校验 | 保存同一计划内的来源拍摄关联及能力依据；同一来源至多有一个有效的自动预览取回 |
| 多个自动预览取回可靠地声明同一来源 | 所有冲突取回均初始失败；分别保留可靠关联、原输入和完整冲突原因，不能通过只保存其中一条关联消除冲突 |
| 自动预览取回存在其他参数错误 | 保存可靠取得的自动用途、来源及能力依据；无法确认的信息不补造，原输入和错误由动作保存 |
| 普通手动取回 | 按普通取回规则保存来源，不建立自动预览关联 |

关联记录的存在不表示动作已通过校验或具备执行资格。报告中的 `action.automation` 按[预览与范围选择的报告契约](../architecture/report-format.md#预览与范围选择的报告契约)生成；取消流程根据已保存的自动用途和来源关联，按[取消联动](../architecture/preview-obtaining.md#取消联动)处理相关取回及交付。

### 取回与范围清理的来源成员

`action_output_sources` 由取回和范围清理共用。每条记录表示一个取回或清理动作以某个拍摄动作为产物来源；同一所属动作的来源成员不重复。来源成员描述要处理哪些拍摄动作的产物，文件选择则描述最终要处理哪些正式产物，两者分别保存。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY`，正整数 | 本条来源关联的身份 |
| `action_id` | 非空 `INTEGER`，正整数，外键引用 `actions.id` | 使用该来源产物的取回或范围清理动作 |
| `source_action_id` | 非空 `INTEGER`，正整数，外键引用 `actions.id` | 产生正式产物的来源拍摄动作 |

三个字段均遵守[主键与身份引用](#主键与身份引用)的 64 位整数范围；关联自身的主键按该表分配，两个引用沿用所指动作的身份。表设置 `UNIQUE (action_id, source_action_id)`，禁止同一所属动作重复关联同一来源，允许不同取回或清理动作引用相同来源。两个外键保证引用真实动作，业务写入流程同时核对所属动作和来源动作的类型、输入范围及适用的自动预览关联。来源是否成功不决定关联能否成立，失败或取消的拍摄仍可能留下正式产物。

动作、组及计划来源均保存为具体来源动作的成员关系。取回支持组来源，范围清理仅支持动作或计划来源；计划中的取回、清理和报告等非产物来源动作不加入集合。原始计划、组或动作描述保留在所属动作参数中，本表不重复保存计划 ID、组名、选择方式、文件列表或选择进度。

来源成员按[取回来源规则](../architecture/obtaining-outputs.md#校验与失败处理)和[清理参数规则](../architecture/output-cleanup.md#清理参数)在适用时点解析。需要在首次受理时解析的本计划引用，与计划和动作一起保存；需要在执行时核实的实例引用，在取得相应执行资格后解析。完整来源集合、所属动作的来源解析状态及对应历史在同一事务中保存。集合固定后，重试和重启恢复沿用原成员，不重新扩大范围。

所属动作的处理状态区分尚未确定来源、来源集合已可靠固定和来源解析已失败。成员记录的数量不能替代这些状态；来源不存在、类型不适用和数据库查询失败分别按所属流程处理，不能统一解释为来源集合为空。精确 ID 清理直接处理指定产物，不建立范围来源成员。

| 来源成员的使用场景 | 成员记录与后续流程的边界 |
| --- | --- |
| 普通取回 | 每个来源完成拍摄及适用的产物处理后，可以分别固定文件选择和准备副本；全部来源及条目满足取回条件后，才将成功准备的文件移入 `ready` |
| 自动预览取回 | 来源成员从已保存的 `auto_preview_links` 关联派生，不能独立修改来源；关联存在仍不替代动作的执行资格判定 |
| 范围清理 | 等待全部来源及其产物处理结束后，固定完整的清理文件集合，再按清理规则逐项处理 |

`action_output_sources` 只承担来源成员关系。逐来源的选择进度、选中的文件和处理结果分别由取回或清理流程保存，不因为共用关系表而共用状态机。来源成员属于引用它们的取回或清理动作自身状态，随该动作进行历史恢复和快照保存；仅建立来源引用不增加被引用拍摄动作的历史变化次数。

事务未提交时，来源集合不能作为已经固定的执行依据；提交结果未知时先按状态库规则核实，不重新解析或重复创建关系。正常恢复沿用原关联身份，历史恢复使用目标历史边界处的成员，不用之后的来源或选择结果解释过去。业务执行不删除已经固定的来源成员。

验证字段非空、正整数范围、两端外键及组合唯一性；同一关联重复写入受到约束，不同所属动作引用同一来源合法。业务验证覆盖动作、组和计划来源展开、非产物来源排除、自动预览来源一致、精确 ID 清理不创建成员，以及失败或取消的拍摄仍可作为来源。组合真实数据库、受理和执行解析流程验证完整集合与状态及历史原子保存，回滚不残留部分成员，提交未知先核实，重送与重启保持成员及身份。无成员时仍按所属动作的来源解析状态判断，不能据行数推断解析成功、失败或尚未完成。

### 取回的来源选择与目标明细

取回动作使用两张明细表保存文件选择和逐项处理。一个来源尚未结束、一个来源已结束但没有产物，以及一个已选文件尚未创建交付，分别需要保留不同的处理状态，不能仅凭交付记录是否存在判断。

| 明细表 | 一条记录的职责 | 与其他表的边界 |
| --- | --- | --- |
| `obtain_source_selections` | 保存一个取回动作对一个固定来源的文件选择进度，以及适用的来源级选择结果 | 来源成员由 `action_output_sources` 确定；具体文件和显式请求目标由 `obtain_items` 保存 |
| `obtain_items` | 保存一个取回动作的一个具体目标、读取资格及依赖状态，包括实际选中的产物，或显式指定但尚待判定、判定无效的请求目标 | 可靠确认产物存在且属于指定来源时才建立产物关联；实际交付创建后关联 `deliveries` |

取回进入执行且来源集合已固定后，每个固定来源恰有一条来源选择记录。选择状态及报告含义遵守[预览与范围选择的报告契约](../architecture/report-format.md#预览与范围选择的报告契约)：尚未完成选择时为 `pending`；完整选择可靠保存后为 `fixed`，其中实际选中的产物可以为空。来源选择状态与完整选择结果在同一事务中保存；重试和恢复不重新选择或扩大已固定集合。

| 来源或目标的情况 | 保存位置与结果 |
| --- | --- |
| 来源整体尚未可靠确定 | 由所属动作保存来源解析状态和实际错误，不虚构来源选择记录或无产物结果 |
| 来源已固定，但该来源的文件选择尚未完成 | 来源选择记录保持 `pending`，不以没有目标记录表示选择已完成 |
| 来源选择已完成，可靠确认存在选中产物 | 来源选择记录为 `fixed`；每个选中产物在 `obtain_items` 中保存身份和选择依据 |
| 来源选择已完成，没有选中产物 | 来源选择记录为 `fixed`；是否构成来源级失败按取回规则判断并保存，空选择本身不决定成功或失败 |
| 显式请求目标尚待判定 | 目标明细保留请求值和未完成状态；尚未可靠取得的产物或交付身份不补造 |
| 显式请求目标可靠确认不存在或不属于指定来源 | 目标明细保存请求值及具体失败原因，不把该请求值当成选中产物关联，不创建交付 |
| 实际选中的产物在创建交付前最终失败 | 目标明细保存实际产物关联及最终错误，不为表达失败创建交付 |
| 目标已有交付记录 | 目标明细关联交付；交付阶段的进度与最终结果由交付事实提供，不在两处独立维护结论 |

实际选中产物的选择依据包括适用的原文件关联、预览关联及比较时保存的完整大小，具体内容遵守报告契约。显式请求中的多个无效 ID 分别保留目标明细，不能因为缺少实际产物关联而合并。来源级无产物失败由来源选择记录表达，不创建虚假的文件目标。

报告中的选择数组只包含实际选中的产物；逐项最终失败按[取回失败项的报告表达](../architecture/obtaining-outputs.md#取回失败项的报告表达)从来源选择、目标明细及已关联交付的历史事实生成。同一最终失败只报告一次，临时等待和单次尝试失败不自动成为最终失败。

两张明细表属于取回动作自身状态，其历史恢复和对象快照包含相应记录；已关联交付仍按交付对象自身的历史与快照规则管理。明细、受影响的动作状态及对应历史按业务事务共同保存，同一请求重送或重启恢复沿用原记录和已确定结果。

### 取回的读取资格与依赖

`obtain_items` 直接保存本次取回目标的读取资格，以及是否仍依赖正式源产物。资格授予、保持和依赖解除属于该目标的处理状态，与明细及其历史一起保存。尚未确认实际产物的请求目标不能取得读取资格，取回受理或动作开始等待来源本身也不授予资格。

同一产物被多个取回引用时，每个取回明细分别保存自己的资格和依赖。清理流程通过产物关联查询仍需保护的取回明细，不以某个副本已经准备完成代替所有取回均已完成，也不需要加载整个计划才能判断该产物的读取依赖。

| 本次取回目标的事实 | 读取保护与后续处理 |
| --- | --- |
| 尚未取得读取资格 | 尚未建立本项保护；按执行顺序、产物可用性及删除限制判定能否授予 |
| 已取得资格，仍在等待拷贝、读取、校验或适用重试 | 保持本项读取依赖，后来的删除限制不撤销已有资格，清理必须等待 |
| 副本已经可靠准备完成，准备完成事务已成功提交 | 解除本项读取依赖，后续使用独立副本，不等待其他产物、交接或客户端接收 |
| 本项最终失败或取消，实际读取和重试尚未确认停止 | 保持本项读取依赖；取消标记或最终失败本身不能证明源文件已无人读取 |
| 本项最终失败或取消，实际读取和重试已确认停止 | 可靠保存相应事实并解除本项读取依赖 |
| 资格、依赖或准备完成事实无法可靠确认 | 核实实际记录或按持久化错误处理，不据此放行源文件删除 |

授予资格时，在同一事务中检查有效删除限制并保存资格或本项失败，顺序遵守[逐产物资格授予规则](../architecture/outputs.md#延后执行时的取回与清理顺序)。已经保存的最终失败不因清理后来取消而恢复；已有资格和依赖解除事实不因重启重新分配。

副本准备完成时，在同一事务中保存交付副本的身份、位置、大小、摘要及准备完成事实，并更新 `obtain_items` 的依赖状态和相关历史。文件已经写完但事务未提交，仍保持读取依赖；提交结果未知时先核实，不能猜测依赖已经解除。恢复与已确认交付的处理遵守[逐产物解除读取依赖](../architecture/output-cleanup.md#逐产物解除读取依赖)及[准备完成与断电恢复](../architecture/output-cleanup.md#准备完成与断电恢复)。

录像内部检查和修复的输入读取由原录像处理流程管理。正式产物清理按既有规则等待来源及适用产物处理结束，不为内部处理创建虚假的取回明细。读取依赖的解除只表示本次取回不再需要源文件，实际删除仍须满足清理自身的资格、完整目标记录及其他取回的保护要求。

### 清理目标明细

`cleanup_items` 的每条记录表示一个清理动作对一个目标产物的处理，保存本次请求的目标、处理状态、逐项结果，以及本项删除限制的状态和建立、解除依据。`outputs` 保存产物自身的可用性和清理事实，清理明细保存某次清理请求的实际处理；同一产物可以被不同清理动作引用，各次请求的结果分别保留。

范围清理通过 `action_output_sources` 保存来源成员，由清理动作自身保存目标集合尚未确定或已经确定的状态。全部来源及其产物处理结束后，完整目标集合、清理明细、集合确定状态及对应历史在同一事务中保存。精确 ID 清理按原请求的目标及顺序保存明细，目标存在性在执行时核实；格式非法的受理失败不生成可执行的清理明细。

下表说明目标明细的存储责任，具体执行资格、取消及恢复仍遵守[清理正式产物](../architecture/output-cleanup.md)：

| 目标情况 | 明细与产物记录的处理 |
| --- | --- |
| 范围清理尚未确定完整目标集合 | 动作保存尚未确定的状态，不把暂时没有清理明细解释为无需清理 |
| 范围清理已可靠确定目标集合为空 | 动作保存集合已确定和无需清理的结果，不创建占位清理明细 |
| 显式目标尚待核实 | 明细保留请求中的 ID 和未完成状态，尚未确认的产物关联不补造 |
| 数据库可靠确认显式目标不存在 | 明细保存本项失败及原请求 ID，不创建虚假产物；其他合法目标继续按各自规则处理 |
| 目标产物存在，尚需等待已有取回或继续删除、核实结果 | 明细关联实际产物并保存处理进度；等待、删除已发出及结果未知分别表达 |
| 本次确认目标产物此前已完整清理 | 明细保存本次确认成功的结果，沿用产物既有清理完成事实，不新增虚构的删除调用 |
| 本次已可靠完成目标产物清理 | 明细保存本项成功，与受影响产物的清理完成事实及历史共同提交 |
| 本项最终失败或取消 | 明细保留实际结果、错误及已发生的删除或未知事实，不因动作整体结束而抹去副作用 |

目标查询失败或记录无法解释时，按状态库错误处理，不能将其保存为目标不存在。清理动作按逐项结果汇总自身状态；不同目标的结果相互独立，一项失败不撤销另一项已经完成的删除。物理文件删除与存在性查询的尝试记录按各自调用事实组织，不以目标最终状态代替尝试历史。

清理明细属于清理动作自身状态，随该动作进行历史恢复和快照保存；产物自身状态仍遵守产物的历史与快照规则。同一请求重送和重启恢复沿用原明细及已确定结果，新的清理动作建立自己的明细。已有最终结果、继续执行及取消收场的边界遵守[批量清理结果](../architecture/output-cleanup.md#批量清理结果)和[删除中断后的恢复](../architecture/output-cleanup.md#删除中断后的恢复)。

### 逐请求的删除限制

`cleanup_items` 保存本清理请求针对目标产物建立的删除限制。同一产物可以关联多个清理项，每项分别保存自己的限制状态及建立、解除依据；记录存在或目标集合已固定，不表示限制已经生效。尚未可靠确认实际产物的请求目标不能建立有效限制。

限制建立遵守[逐产物资格授予顺序](../architecture/outputs.md#延后执行时的取回与清理顺序)，与清理项状态、受影响的产物投影及对应历史在同一事务中保存。限制可以在等待已有取回结束读取时生效，此时尚无物理删除调用；物理删除意图、尝试与预算继续由公共操作记录保存，不能用是否存在删除尝试代替限制状态。

新取回的资格检查同时读取该产物全部相关清理项的有效限制，以及产物已删除或无法排除删除的事实。检查结果与 `obtain_items` 中的资格授予或逐项失败共同提交；已有取回的资格和读取依赖按原规则保持。为查询维护的产物限制摘要必须从这些事实严格派生，不独立修改。

取消生效后，按下表顺序判断每份产物；删除调用的派发与取消继续遵守所属操作契约：

| 产物及相关清理项的可靠事实 | 限制与后续取回 |
| --- | --- |
| 产物文件已确认清理完成 | 保持已清理、不可取回，取消不撤销清理事实 |
| 尚未确认清理完成，但已发出可能删除文件的调用、已发生删除或无法排除删除发生 | 保持取回限制，保存实际结果与未知依据，不因取消开放尚存文件 |
| 可靠确认本请求未发出删除，其他清理项仍有有效限制 | 仅解除本项可撤销的限制，保留其他清理项的限制 |
| 可靠确认本请求未发出删除，且没有其他限制或可能删除事实 | 解除本项限制，后续取回按实际可用性申请资格 |
| 必要记录或上述事实无法可靠读取和判断 | 按状态库错误及恢复规则处理，不猜测限制已解除或产物可取回 |

例如 C1 和 C2 都对产物 O 建立限制，尚未发出删除。取消 C1 时，只更新 C1 对应清理项的限制与结果；C2 的限制继续有效。限制解除不重新激活已经因限制而失败的取回项，新的取回仍须具有独立请求及执行资格。

限制解除与本项取消处理、受影响投影及历史共同提交；确认回滚时均不生效，提交结果未知时先核实整个事务。重启沿用原清理项、限制依据和已知文件事实，不从动作终态或内存任务是否存在推断限制已消失。限制是清理项自身状态的一部分，由所属清理动作的历史和快照保存；其对产物状态的实际影响按产物历史规则共同记录。

### 取消目标明细

`cancel_items` 的每条记录表示一个取消动作对一个实际目标动作的处理，保存固定的目标关联、取消是否生效、本次处理或等待的进度，以及逐项目标的结果。其处理状态属于本次取消，不能复制目标动作状态来代替：目标已收到取消要求时，必要停止仍可能尚未完成；目标取回已成功时，本次取消仍可能需要撤回尚在 `ready` 的交付文件。

取消执行时按[取消目标寻址](../architecture/task-cancellation.md#取消目标寻址)解析直接目标及自动预览候选关联，去重后在施加取消或执行停止、撤回之前检查是否包含取消动作自身。检查通过后，按取消资格和联动规则固定实际处理集合，保存目标是直接寻址还是联动选中的依据。拒绝取消的直接目标保留失败明细，不仅因预览存在关联就取消它。集合及其固定事实可靠保存后，逐目标继续处理；同一取消动作针对同一目标只有一条明细，重启和请求重送沿用原集合及已保存进度。目标不存在、集合包含自身和查询结果无法确认，分别按取消契约处理，不创建虚假的目标关联或取消成功结果。

| 本次取消与目标的情况 | 明细及责任归属 |
| --- | --- |
| 目标未终态，取消尚未生效 | 明细保留待处理事实，不以记录存在表示目标已经取消 |
| 目标任务已启动或可能启动，缺少停止能力而拒绝取消 | 明细保存失败、取消未生效及判定依据；不修改目标取消标记，不创建停止流程，不等待原任务结束 |
| 目标取消已生效，必要停止、读取结束或适用清理尚未完成 | 明细保存取消已生效和本次等待进度；目标所属流程独立承担必要处理 |
| 目标已有终态，但仍有适用的撤回等责任 | 保留目标原终态，明细跟踪本次适用处理；没有适用责任时按可靠确认结果结束本项 |
| 本次适用处理已结束 | 明细保存实际成功、失败或未确认原因，取消动作按各项结果汇总；不因一项失败撤销其他目标已生效的取消 |
| 发起取消的动作自身被取消，部分目标已受影响 | 分别保留已生效和未生效事实，停止新增目标取消及适用等待；已生效目标继续必要收场，已有逐项最终结果保持 |
| 发起取消的动作已有终态，目标后续处理取得新结果 | 保留取消动作及其明细的已确定结果，由目标所属记录表达后续进度，不改写原取消结果 |

施加目标取消前先按[设备任务的取消资格](../architecture/task-cancellation.md#设备任务的取消资格)判断，不能无条件修改目标。拒绝时保存明细结果及历史，目标继续原流程。允许取消时，目标取消事实、相应明细进度和历史按同一业务事务保存；数据库操作结果未知时先核实，不把结束协程等待解释成取消未生效。具体完成条件、取消自身的收场及等待范围遵守[取消动作的完成时机](../architecture/task-cancellation.md#取消动作的完成时机)和[取消动作自身被取消](../architecture/task-cancellation.md#取消动作自身被取消)。

多个取消入口触达同一目标时，复用目标已有的操作流程和剩余预算，不为每条取消明细另建一套停止流程。取回目标的逐交付处理由 `cancel_delivery_items` 保存，交付自身事实由交付记录维护。`cancel_items` 属于发起取消动作自身状态，随该动作进行历史恢复和快照保存；目标的必要收场不依赖发起取消动作继续存在于活动调度或继续等待。

### 取消动作的交付处理明细

`cancel_delivery_items` 是 `cancel_items` 的子表，每条记录表示本次取消处理某个取回目标时，对一份实际交付取得的处理进度和结果。记录关联所属取消目标明细与真实交付，交付必须属于该明细指定的取回动作。同一取消目标明细下，同一交付只保存一条处理记录。

一个取回可以包含多份交付，各份文件的位置和撤回结果分别判断。逐项结果按[取消报告契约](../architecture/report-format.md#取消)生成 `withdrawals`，不能用目标动作的汇总结果代替：

| 本次逐交付处理的可靠事实 | 明细表达与边界 |
| --- | --- |
| 适用的撤回或核实尚未结束 | 保存待处理状态，不提前表达成功或已经不可撤回 |
| 已可靠确认交付撤回完成 | 保存已撤回结果，并关联交付自身的实际撤回事实 |
| 已可靠确认文件进入 `processing` 或已由主程序处理，超出 CLI 撤回权限 | 保存不可撤回结果，不等待主程序，不将其表达为撤回成功或客户端已收到 |
| 撤回明确失败，或有限核实结束后仍无法确认位置或结果 | 保存本项失败和实际原因，不把未知解释为已越过撤回边界 |

文件位于 `ready` 只表示可以按交接规则尝试撤回，不证明撤回已经成功。文件仍在 `staging` 时，适用的取消清理由中间文件生命周期处理，不以撤回记录代替中间文件清理记录。真实文件操作的意图、结果和中断恢复继续遵守交付及取消规则。

`deliveries` 保存交付自身的事实，`cancel_delivery_items` 保存某次取消对该交付的处理结果；两者引用相同的实际撤回依据，不独立维护相互矛盾的事实。多个取消动作涉及同一交付时，各自保存明细，但复用交付已有结果或正在履行的撤回责任，不因增加明细而重复发起文件删除。一次实际结果同时影响交付和本次取消明细时，相关投影与历史按同一业务事务保存。

明细属于发起取消动作自身状态，随该动作进行历史恢复和快照保存。重启及同一请求重送沿用原记录；取消动作自身被取消后，已生效的目标责任继续由目标负责，后续交付变化不改写已经结束的取消处理结果。该表保存业务处理明细，不以每次文件系统调用新增一条记录，也不增加撤回重试预算。

### 正式产物与普通交付

正式产物与交付分别管理。拍摄动作可以登记多份正式产物；一个取回动作可以为多个选中产物创建交付。交付关联的取回动作与产物的来源动作可以属于不同计划。

`deliveries` 保存本次副本准备完成、发布意图、本地交付完成及适用的撤回事实，并关联其稳定文件名、可读名称及完整性依据。准备完成与读取依赖解除一起提交，发布意图在移动前提交，本地交付完成事实在移动及必要目录同步成功后保存，分别遵守[普通交付保存与恢复](../architecture/file-handoff.md#普通交付的保存顺序与中断恢复)。文件已被主程序取走而结果无法确认时，按原交付身份保存规定的未知原因与最终结果。

交付文件被主程序取走、删除或被 camctl 撤回，不等于正式源产物被清理。正式源产物已经合法清理，也不抹去已形成交付的身份和处理事实。另一个取回动作沿用产物身份并创建属于该动作的交付，同一次取回的恢复继续使用原交付。

正式产物主表只登记满足相应业务条件的产物。修复临时文件、尚未登记的成品和内部原片副本按中间文件规则保存归属与进度，不因存在文件就建立正式产物。取回失败可能发生在创建交付之前，失败项须能够独立于交付记录表达。

### 产物来源关系

`outputs` 统一保存正式业务文件的共同信息。文件内容类型描述视频、图片、文档等内容，产物角色描述原文件、预览和修复成品等业务含义，两者分别表达。各种文件内容类型使用同一产物主表；具体可登记的产物继续由第一版已接入动作及其结果契约决定。

`output_origins` 保存一份正式产物与其来源原产物之间的关联。每条记录表达一项实际存在的来源关系，两个端点均为正式产物。原产物的所属拍摄动作与这里的文件来源关系分别保存：前者回答产物由哪个动作产生，后者回答预览或修复成品对应哪份原文件。

第一版采用[正式产物契约](../architecture/report-format.md#正式产物)中的三种角色，按下表组织关系：

| 引用来源的产物角色 | 来源关系 | 完整性要求 |
| --- | --- | --- |
| 原文件 `original` | 没有以自身为引用方的来源记录 | 自身可以被预览或修复成品引用 |
| 预览 `preview` | 恰好一条记录，指向对应原文件 | 两端属于同一来源动作；关系由可靠的预览配对事实确定 |
| 修复成品 `repaired` | 恰好一条记录，指向被修复的原文件 | 两端属于同一来源动作；关系由实际修复及成品登记事实确定 |

关系含义由引用方的产物角色解释。查询一份原文件的预览或修复成品时，通过来源关系定位相应产物，再取得其自身状态。两端身份、角色及归属必须一致；预览或修复成品的关系缺失、重复、非法或读取失败，按状态库错误处理，不能解释成该产物无需来源。

预览或修复成品登记时，其产物记录、来源关系及对应历史在同一事务中保存。来源关系是所属产物自身状态的一部分；历史恢复和对象快照包含这项关系。仅引用原文件不表示原文件自身发生状态变化，不因新增引用而增加原文件的历史变化次数。

清理任何一端的实际文件，只按所属规则更新文件可用性和处理结果，产物记录及来源关系永久保留。预览与修复成品各自管理文件生命周期，来源关系不授予对其他产物的清理权限。

其他业务对象通过稳定的产物身份引用产物。类别专属信息、来源关系和共同信息分别由其所属结构维护；公共报告按既定字段契约从这些记录的冻结历史状态生成。

### 输入诊断与状态报告

输入文件诊断独立于计划保存。无法读取或解析输入时仍可形成诊断；合法计划与无效 ACK 同时出现时，可以在同次事务中保存计划及诊断。动作自身参数错误保存在动作中，不因此创建重复的文件诊断。

状态报告与普通交付分别保存。报告按照固定历史边界和覆盖范围恢复内容，重建或补投沿用原报告身份和确定字节。普通交付遵守产物取回、文件交接和撤回规则，不能直接套用报告的补投规则。

`reports` 保存报告身份、固定生成依据和相应处理状态。完整报告正文由不可变历史及这些依据生成，写入供主程序传输的 JSON 文件；重建遵守[从历史重建报告](../architecture/status-reports.md#从历史重建报告)的确定字节规则。输入文件诊断作为状态报告中的内容发送，其数据库记录不要求生成独立的诊断文件。

报告的每次成功发布及恢复观察保存在 `history_events`，并同步更新 `reports` 的查询投影；首次发布与后续补投分别保留实际事实，不能用最后一次结果覆盖历史。已登记报告、曾经成功发布、文件仍在交接目录和客户端已确认分别判断，遵守[报告发布与补投](../architecture/report-publication.md)。

报告可以由自动维护生成，也可以用于完成显式报告动作的本地处理责任；二者不存在必然的一对一关系。显式同步责任由 `state_syncs` 保存，客户端累计确认位置由 `runtime_state` 保存，不能仅由报告动作是否完成推断同步已结束或客户端已确认。

### 客户端累计确认状态

`runtime_state` 的累计确认字段为第一版的一个逻辑客户端保存当前确认位置，供报告维护和输入处理直接读取。该位置表示客户端已经可靠保存到哪个业务水位，不能用收到的最大报告编号代替。确认位置的变化及其依据保存在统一的不可变历史中，并与当前投影共同提交。

累计确认位置按[全局运行状态](#全局运行状态)的初始化与读取规则管理，初始值为 0。ACK 处理只修改累计确认相关字段，不改变同一记录中的可信历史时间下界。

输入中的 `last_report_id` 用于查询 `reports`，累计位置使用所引用报告的 `to_wm`。设已有位置为 A、引用的报告为 R，ACK 处理遵守[报告确认规则](../architecture/status-reports.md#ack-引用的报告记录)：

| ACK 及查询结果 | 累计确认位置 | 对同步责任的处理 |
| --- | --- | --- |
| 未提供 ACK | 保持原位置 | 不因本次输入缺少 ACK 而确认同步结束 |
| ACK 合法，报告记录可靠有效，`R.to_wm > A` | 推进到 `R.to_wm` | 检查并结束该报告满足的全部未结束责任 |
| ACK 合法，报告记录可靠有效，`R.to_wm <= A` | 保持 A | 仍检查并结束该报告满足的全部未结束责任，不能因为位置未推进而跳过 |
| ACK 字段非法，或查询成功并确认报告不存在 | 保持原位置，保存 ACK 诊断 | 不由该 ACK 改变同步责任 |
| 报告或确认状态无法可靠读取、写入失败，或者提交结果未知 | 按状态库错误及提交核实规则处理，不宣称更新成功 | 不宣称责任已确认结束，也不猜测事务已经回滚 |

以上同步确认按[状态同步记录](#状态同步记录)中的范围和历史边界条件逐项判断。累计位置更新、适用同步的结束事实及对应权威历史在同一次输入事务中保存；需要恢复时核实实际提交结果，不允许确认位置与同步结束只保存一部分。ACK 与计划正文按[独立处理规则](../architecture/plan-acceptance.md#计划正文与-ack-独立处理)执行，计划被拒绝或同一请求重送不阻止处理有效 ACK。

累计确认位置只前进、不后退。客户端从旧备份恢复后要求重新补齐的范围由 `state_syncs` 保存，不回退累计位置；报告生成在同一一致历史边界内读取累计位置及有效同步责任，确定本份报告的冻结范围。后续 ACK 不修改已经登记报告的内容。

有效 ACK 引起的累计确认及同步管理变化不增加 `change_seq`，不产生用于确认 ACK 的新报告责任；无效 ACK 的诊断及同次输入中的其他业务变化按各自规则报告。累计确认状态按自身历史恢复，不进入历史快照维护范围。

### 状态同步记录

`state_syncs` 的每条记录表示一个 `report_status` 动作实际开始执行后建立的同步责任，关联发起动作，保存原同步要求、确定后的固定起点、同步开始的完整历史边界，以及是否已经结束、结束原因和对应的 ACK 或取消依据。同一动作至多建立一条同步记录；重试、重启及同一请求重送沿用原记录，不重算起点或开始边界。不同动作即使要求相同起点，也分别保存责任。

动作取得执行资格后，按[同步开始规则](../architecture/status-sync.md#camctl-何时开始同步)确定起点。动作进入运行、起点确定及同步责任建立在同一事务中保存；局部同步对起点报告的查询也在该事务中完成。参数受理失败、执行前取消，或执行时可靠确认起点报告不存在时，不建立同步责任；查询或提交无法确认时按状态库错误处理，不假定责任尚未建立。

`actions` 保存报告动作的本地执行状态和结果，`reports` 保存各份报告的固定生成依据和文件处理事实，`state_syncs` 保存仍需履行的同步责任。一份报告可以满足多个同步；同一同步也可以由先后生成的不同报告覆盖，不将同步责任绑定为某一份报告文件的生命周期。

| 已建立同步责任的后续情况 | 同步记录与相关处理 |
| --- | --- |
| 本地报告工作尚未完成，或会话出错、断电、报告生成及文件交接未完成 | 保留同步要求与实际进度，恢复原责任，不以文件缺失或操作失败结束同步 |
| 报告动作已完成本地工作并成功，尚无合格 ACK | 同步责任继续保留；后续报告机会仍须覆盖其固定起点，`run` 不为等待远端确认持续运行 |
| 同步尚未结束，发起动作在进入终态前被取消 | 在取消事务中结束该动作的同步责任并保存依据；其他同步继续按自身状态处理 |
| 报告动作已经成功，随后收到针对该动作或计划的取消 | 保持动作结果；尚未确认的同步责任继续等待合格 ACK |
| 收到满足该责任的有效 ACK | 保存确认结束及对应依据，并与累计确认处理在同一输入事务中提交 |
| 同步责任已经结束 | 永久保留结束事实；同一动作的恢复、重送或后续报告生成不重新建立责任，也不改写原结束原因 |

报告范围根据全部尚未结束的同步及累计确认位置共同确定，遵守[报告范围规则](../architecture/status-sync.md#报告范围)。停止等待某项责任，不修改已经登记报告的冻结依据，也不直接终止已经开始的共享报告生成任务。

对于尚未结束的同步，设固定起点为 S、开始事务的完整历史边界为 B。ACK 引用的报告 R 已可靠存在且生成依据有效时，按下表判断；B 属于完整历史顺序，不能与业务水位混用。

| R 的冻结历史已包含 B | `R.from_wm <= S` | 对该同步责任的处理 |
| --- | --- | --- |
| 否 | 否 | 保留责任，报告既早于本次同步，也未覆盖所需起点 |
| 否 | 是 | 保留责任，报告范围足够，但采用的状态早于本次同步 |
| 是 | 否 | 保留责任，报告起点过晚 |
| 是 | 是 | 确认责任结束，保存与本次 ACK 的关联 |

每份有效 ACK 都检查它满足的全部未结束责任，即使累计确认位置没有推进也执行该检查；累计位置按 `max(A, R.to_wm)` 处理，并与适用同步的结束事实共同提交。ACK 非法或可靠确认报告不存在时，保存 ACK 诊断，不由该 ACK 改变确认位置或同步责任；状态库读取、写入或提交结果无法确认时按对应错误处理。

同步管理历史和投影在同一事务中保存，管理变化自身不增加 `change_seq`；发起动作的注册、开始和结果变化仍按业务规则计数。`state_syncs` 按[同步持久化规则](../architecture/status-sync.md#数据库需要保存哪些信息)从自身历史恢复，不进入历史快照维护范围；`report_status` 动作自身继续按动作对象维护快照。历史回放不新建同步、不调用设备，也不重新交付报告文件。

## 数据库元信息

`database_metadata` 保存唯一一条数据库元信息记录，以固定字段表达 camctl 数据库标识、数据库实例身份和整体格式版本。各入口在解释业务数据之前读取并校验这些信息，再按支持的格式检查必要结构、读取业务投影。元信息的有效性不能仅由文件名或 SQLite 能否打开文件判断。

| 信息 | 职责 | 建立与更新规则 |
| --- | --- | --- |
| camctl 数据库标识 | 表明数据库属于 camctl，配合必要结构检查识别状态库 | 首次初始化时保存，日常运行不修改 |
| 数据库实例身份 | 将报告生成任务、查询结果和缓存绑定到相应状态库 | 首次初始化时生成；不同的首次初始化分别建立不同实例身份，重启和重复 `init` 沿用已有身份 |
| 整体格式版本 `format_version` | 确定表结构、允许的事件及其他持久化表示如何解释 | 第一版初始化为 1，日常调用不修改；后续格式变化遵守显式升级规则 |

数据库标识表达数据库类型，实例身份区分具体状态库。报告任务与查询缓存使用数据库身份时，以该实例身份为依据；具体字段名、标识形式、类型和约束由字段设计细化。

首次显式初始化时，元信息记录与完整结构、初始运行状态一起建立；只有完整有效的初始化结果才能供日常入口使用。`runtime_state` 保存累计 ACK 和可信历史时间下界等业务投影，由对应历史推进和重建；`database_metadata` 提供识别数据库和解释持久化数据的基础信息，由初始化与显式格式维护负责。历史回放不改变数据库身份或整体格式。

| 读取或初始化情况 | 处理 |
| --- | --- |
| 首次初始化，目标状态库可靠确认不存在 | 按初始化规则建立唯一元信息记录及完整初始状态，可靠保存后提供正式数据库 |
| 已有唯一有效记录，格式受支持且必要结构有效 | 使用该实例身份和格式继续执行；重复 `init` 保留原记录和业务数据 |
| 元信息有效，但格式不受支持 | 按格式不受支持处理，在使用业务状态之前停止 |
| 记录缺失、存在多条、标识或版本非法，或必要结构与声明不符 | 按状态库校验错误处理，不补建元信息或解释为初始状态 |
| 无法可靠读取或确认元信息 | 按状态库错误处理，保留读取失败与记录不存在的区别 |

初始化及重复验证遵守[目录与状态库](../architecture/initialization.md#目录与状态库)，格式解释和显式升级遵守[数据库整体格式检查](persistence-runtime.md#数据库整体格式检查与显式升级)。第一版实现格式 1 的读写与检查，后续格式的实际迁移步骤随相应需求定义。

## 全局运行状态

`runtime_state` 保存唯一一条全局运行状态记录，以具有明确类型和约束的固定字段分别表达客户端累计确认位置、可信历史时间下界、中间文件清理继续位置及其必要依据。每组字段由所属业务的专用读写接口维护，更新只修改该业务负责的字段，不将先前读取的整行内容重新写回。共用一行不合并各类状态的判定、更新资格或历史含义。

| 状态分组 | 用途与更新责任 | 初始状态 |
| --- | --- | --- |
| 客户端累计确认 | 输入处理根据有效 ACK 引用的报告推进确认位置，报告维护据此确定普通未确认范围 | 累计确认位置为 0 |
| 可信历史时间下界 | `run` 使用已有下界检查启动墙钟，通过后以本次检查读数建立或推进下界 | 尚无可信历史时间依据 |
| 中间文件清理继续位置 | 正常 `run` 的历史清理维护保存可靠检查后的继续位置，供后续会话接续 | 尚未检查历史清理记录，从适用候选范围的起点开始 |

首次显式初始化状态库时，与完整初始结构一起建立该记录，遵守[初始化边界](../architecture/initialization.md#目录与状态库)，不为初始值插入虚构历史事件，也不将初始化时未经校验的墙钟读数保存为可信依据。重复初始化保留已有状态；日常读取发现记录缺失、存在多条记录、内容无效或无法可靠读取时，按状态库错误处理，不补建记录或返回初始值。合法的“尚无可信历史时间依据”与记录缺失分别表达。

累计确认字段遵守[客户端累计确认状态](#客户端累计确认状态)。确认位置更新、适用的同步责任结束及对应历史仍在同一次输入事务中提交；该操作不授予输入处理中未经校验的时间推进可信下界的资格。

可信历史时间下界只在 `run` 启动墙钟检查通过后更新，每次会话至多一次，遵守[下界更新规则](../architecture/clock-recovery.md#可信历史时间下界的更新)。检查使用原有下界，更新使用实际通过检查的读数；已有下界只前进、不后退。需要变更时，在进入普通执行前共同提交权威历史与投影；保存失败或提交结果未知时按状态库错误处理。

下界变化不增加 `change_seq`，也不单独产生报告责任。它保存历史依据，不表示后续会话已经通过时间检查。正常运行及退出阶段、`submit` 和时钟异常会话不更新下界；这些阶段的事件仍按各自事实及时间可信性保存。单次会话中的命令超时、重试间隔等经过时长仍使用单调钟，不使用历史下界计算跨重启经过的时间，也不将不同会话的单调钟读数相减。

各类状态分别按所属规则形成不可变历史，并与受影响投影原子保存。历史恢复使用当时保存的变更，不用本次墙钟、其他事件中的更晚时间或后续 ACK 改写旧状态。全局运行状态不进入历史快照维护范围；具有独立身份和生命周期的状态同步责任由 `state_syncs` 保存。

### 中间文件清理进度

`runtime_state` 使用独立字段组保存历史中间文件清理的跨会话继续位置，由清理维护接口更新。位置采用中间文件清理记录的稳定登记顺序及必要身份，不依赖该记录仍在待清理集合中。首次初始化表达为尚无已检查位置，与记录缺失或内容无效分别判断；具体字段表示在表定义中确定。

继续位置从相应检查历史派生，与本次检查结果、适用的 `intermediate_files` 状态及对应历史在同一事务中保存。文件检查与删除在事务外执行，只有结果及位置可靠提交后，才能越过相应记录。位置变化本身不增加 `change_seq`；实际文件清理结果按所属对象的报告规则处理。

| 检查、保存或恢复情况 | 继续位置与后续处理 |
| --- | --- |
| 检查结果与继续位置已可靠提交 | 从该稳定顺序位置之后继续；本项暂不能删除或删除失败，不阻止后面的记录获得机会 |
| 检查或删除已经发生，保存事务确认回滚 | 数据库位置不推进；后续按实际文件事实重新核实，不推测旧调用结果 |
| 保存结果未知，或位置无法可靠读取和解释 | 按状态库错误规则核实，不猜测位置已经推进或恢复为起点 |
| 位置对应的记录已经清理完成或不再是候选 | 仍从其顺序位置之后继续，不要求该记录重新进入候选集合 |
| 首次初始化后的合法起点 | 从本次适用候选范围的起点开始，遵守数量限制 |
| 后续正常 `run` 开始 | 沿用已保存位置，重新建立本次历史范围上界、额度及已检查状态；到范围末尾后的处理遵守清理预算规则 |

固定范围、循环到起点、每次运行最多检查一轮及新增文件首次清理的协调遵守[中间文件清理的运行预算](../architecture/file-handoff.md#中间文件清理的运行预算)。范围上界、本次已检查数及防止同一文件重复处理的会话状态，不作为跨会话继续位置使用；重启不继承上一会话已消耗的运行额度。位置更新只修改清理字段，不回写先前读到的 ACK 或可信时间。

## 操作流程与尝试的公共模型

操作流程与业务尝试分别组织，并复用公共记录结构。一个操作流程表示所属业务针对明确目标承担的一项具体操作责任；一次尝试表示该流程按业务规则开始的一次执行。流程保存归属、目标、适用的预算及整体处理状态，尝试保存自身身份、执行进度和实际结果。哪些情况开始新流程、开始新尝试或继续已有尝试，由所属业务契约决定。

| 公共表 | 一条记录的职责 | 归属与生命周期 |
| --- | --- | --- |
| `operation_runs` | 一个具体操作流程，保存其业务归属、操作责任、目标、适用预算和整体处理状态 | 流程身份由所属业务确定，可以跨多次 `camctl run` 存续；表名中的 `runs` 不表示 CLI 会话 |
| `operation_attempts` | 一个操作流程下的一次业务尝试，保存尝试身份、执行进度和实际结果 | 每条尝试只属于一个流程；恢复已有尝试与开始新尝试按业务规则区分，单次底层调用不自动产生新尝试 |

公共记录负责可靠保存身份、预算消耗和执行事实；业务流程负责判断执行资格、成功条件、安全重试和恢复方式。文件可靠进度、整片重拷轮次、持续设备活动、文件选择依据及删除限制等专属状态，继续由各自业务记录管理。公共模型不根据统一的成功或失败标签自行调度重试，也不替代设备或文件状态核实。

操作流程跨运行保留累计次数，新增尝试使用本次运行的上限。流程或尝试保存的上限、超时等值表达实际采用的历史依据；后续运行的资格判断从本次配置取得值，不将旧依据作为不可修改的执行配置。降低上限后，累计次数允许大于新上限，数据库不能以二者大小关系判定历史记录无效。尝试登记、额度判断依据、结果和对应历史按各自业务事务共同保存，已提交的旧事实不改写。完整分类见[本地配置变化与未完成工作](../architecture/configuration.md#本地配置变化与未完成工作)。

以下操作使用两张公共表保存流程与尝试。流程身份同时区分业务归属、操作责任和实际目标。相同设备上的相同命令可以属于不同流程；正常执行、取消和恢复也可以共同继续同一个流程。

| 已有业务流程 | 流程与尝试的身份边界 | 必须保留的业务规则 |
| --- | --- | --- |
| 拍摄启动 | 录像、单张拍摄和延时摄影各自保存所属动作的启动流程及尝试 | 重试受启动窗口、设备条件、本次上限、累计次数及安全重复规则约束 |
| 单张拍摄或延时摄影的适用停止 | 按所属动作与设备能力保存实际停止流程及尝试 | 使用对应拍摄契约和有限预算，不伪造未执行的停止结果 |
| 录像普通停止 | 同一录像的正常停止、取消停止和断电恢复停止共用原停止流程 | 切换入口不创建新预算；普通停止与启动分别计数 |
| 后续动作停止历史残留录像 | 同一触发动作针对同一历史录像建立一个独立收场流程 | 不消耗触发录像自身的启动或停止预算，不重置历史录像原停止预算 |
| 文件读取 | 每个所属处理中的每份文件有自己的读取流程；一次读取尝试可跨数据段和重启继续 | 只有符合读取重试规则时才新增尝试；摘要不一致的重拷轮次和预算分别保存 |
| 正式产物清理中的文件删除及存在性查询 | 同一清理责任中的每份目标文件分别保存删除与查询流程及其尝试 | 两种调用分别消耗预算；查询成功与文件已删除分别表达 |
| 会话应急停止 | 同一会话对同一录像只建立一个应急流程 | 使用独立应急限额；数据库不可写时仍按应急规则有限停止，不能以保存公共记录为执行前提 |

同一来源文件被不同取回或内部处理使用时，读取流程归属于各自的具体处理，不仅凭源文件身份合并。文件读取流程的预算与尝试由公共表保存，可靠字节进度、重拷轮次及校验依据由拷贝专属记录保存。正式产物的每份目标文件分别关联删除和查询流程，两者继续归属于原清理责任。

上述身份与预算规则分别遵守[录像启动与停止](../architecture/camera-recording.md#启动与停止的尝试上限)、[残留录像收场](../architecture/camera-recovery.md#后续动作触发的残留收场)、[文件读取](../architecture/file-copy.md#按文件累计读取尝试)、[正式产物清理](../architecture/output-cleanup.md#删除与查询的独立尝试预算)及[会话应急停止](../architecture/session-errors.md#正在录像时的应急停止)。

需要先保存意图和额度再派发的普通业务，在同一事务中保存本次尝试、预算占用、相关业务状态及权威历史，提交成功后才执行外部操作。登记意图不证明调用已经发出，调用结束不证明业务目标已经达成。应急停止按其独立记录边界保存实际事实，无法保存的结果不补造为数据库历史。

报告再次处理由[报告维护的触发规则](../architecture/report-maintenance.md#报告处理失败后何时再尝试)决定，中间文件清理由[每次运行的清理预算](../architecture/file-handoff.md#中间文件清理的运行预算)决定。公共记录的使用不改变这些触发条件，也不为原流程增加定时重试或跨会话预算。日志副本交付继续遵守独立于状态库的运行边界。

流程及尝试记录具有明确的业务归属和合法引用，不能仅靠一个无法校验所属对象的通用 ID 表达关系。预算、实际结果与必要查询表示保持单一事实来源，业务专属记录不得另行维护可独立修改的副本。物理拆表不自动增加历史快照对象；记录由所属业务对象的历史恢复，跨对象影响仍在同一业务事务中保存，回放不派发外部操作。

### 动作最终错误与驱动错误

camctl 根据业务规则确定动作的最终错误，驱动负责返回本次操作的原始错误和实际观察。驱动返回错误时，所属流程先保存对应尝试或处理记录，再根据操作结果、剩余预算、执行资格及动作状态决定后续处理。一次调用返回错误不直接证明动作失败，也不证明设备没有执行命令。

`actions.error_code` 使用 camctl 定义的固定整数枚举，其公共错误码和唯一阶段遵守[整数枚举规则](#状态与类型的整数枚举)。驱动原始错误保存在对应的操作尝试或业务处理记录中，保留原始标识、发生步骤、详情及可靠取得的操作结果。未识别的驱动错误也保留原值；不能将其直接写入动作整数错误码，或仅凭错误名称推断设备效果。

动作最终错误的详情按所属错误契约提供必要说明，并关联导致该结果的尝试或逐项处理事实。动作错误表达业务结束的原因，原始错误表达具体操作遇到的问题；历史恢复和报告生成保留这两层含义。具体错误码的整数编号、触发条件、详情结构和关联字段由错误登记及相应字段定义确定。

下表先区分是否已有动作终态或取消要求，再判断普通执行的结果和继续资格。数据库无法可靠保存事实时，适用状态库错误规则，不以此表推定动作结果。

| 动作状态与操作结果 | 错误记录及后续处理 |
| --- | --- |
| 动作已有终态，之后收到操作结果 | 将可靠结果保存在所属尝试、设备活动或文件处理记录中；保持动作原有终态及最终错误 |
| 动作尚未结束，取消要求已经生效 | 保存操作错误及已知结果，按取消规则继续必要收场；普通操作失败不能覆盖取消要求，也不能重新启动普通业务重试 |
| 动作尚未结束且未被取消，尚未满足业务终态条件，操作的实际效果仍无法确认 | 保存错误和未确认事实，按所属业务规则核实；不能将未知当作没有执行，也不能据此直接重复可能产生副作用的操作 |
| 动作尚未结束且未被取消，尚未满足业务终态条件，操作结果已经明确，仍满足业务继续或安全重试条件 | 保留本次错误，按所属流程继续；动作不因这一次错误直接结束为失败 |
| 动作尚未结束且未被取消，业务已经满足最终失败条件 | camctl 根据实际失败分支确定动作整数错误码及详情，并与相应业务事实和历史共同提交；不将驱动原始错误码直接作为动作最终错误码 |
| 动作尚未结束且未被取消，后续尝试成功，且动作满足成功条件 | 保留此前尝试的错误，按成功规则结束动作；曾经发生过操作错误不要求动作最终失败 |
| 动作尚未结束且未被取消，按启动窗口等规则满足其他终态条件 | 按所属业务规则保存过期等结果，并保留操作错误；不能仅因曾有驱动错误而将这些结果改为动作失败 |

最终失败条件包括所属业务规定的预算耗尽、有限核实结束后仍不能确认结果等情况；各条件的优先级和动作终态继续由业务契约决定。公共错误记录不增加重试预算，也不改变过期、取消或恢复规则。状态库读取、写入或提交结果无法确认时，遵守[会话错误规则](../architecture/session-errors.md)，不能为了保存一个动作错误而绕过状态库故障处理。

## 设备活动记录

`device_activities` 的每条记录表示一个动作在某台设备上启动的一次持续活动，例如一段录像或一次延时采集。记录保存所属动作、设备、活动类型及可靠取得的状态和观察依据；启动结果尚未确认时，保留未确认事实，记录存在不证明活动已经启动。同一活动的重试、取消和重启恢复沿用原身份，查询取得新观察时更新该活动的投影并追加历史，不为每次查询创建新活动。

动作结果、设备活动状态和控制操作结果分别保存。原动作已经失败或取消时，设备仍可能继续执行；停止流程已经结束时，其结果也可能是未能确认停止。后续取得新观察可以更新活动的已知状态，但不能改写已经结束的动作或原操作流程的结果。

| 信息或责任 | 保存位置与边界 |
| --- | --- |
| 动作的执行资格、公共状态及最终结果 | 由 `actions` 保存，设备活动后续变化不重开已结束的动作 |
| 一次设备活动的归属、是否仍在执行及可靠观察依据 | 由 `device_activities` 保存；未知与已确认结束分别表达 |
| 启动、普通停止、应急停止及后续动作触发的有限停止 | 由 `operation_runs`、`operation_attempts` 保存适用流程、尝试和预算，并关联目标活动；活动记录不另行维护同一预算或流程结果 |
| 录像原片检查、修复和文件处理 | 分别由 `recording_processing`、文件拷贝及中间文件记录保存，设备活动结束不表示这些处理已经完成 |

设备活动按[设备活动登记与停止处理](../architecture/scheduling-execution.md#设备活动登记与停止处理)保存和恢复。执行前按所属设备契约核实状态，不能仅凭历史记录认定设备仍在执行，也不能仅凭没有活动记录认定设备空闲或取得停止未知活动的权限。

| 可靠取得的活动事实 | 状态保存与后续处理 |
| --- | --- |
| 已确认活动仍在执行，所属动作尚未结束 | 保存观察，按原动作的执行或取消流程处理 |
| 已确认活动仍在执行，所属动作已结束 | 保存残留活动事实；录像按后续有效动作触发的规则处理，不重置原停止预算或启动周期性收场 |
| 已确认活动结束 | 保存结束依据，保持已有动作终态和已结束操作流程的结果；尚未结束的相关业务按各自规则继续 |
| 活动是否启动、是否仍在执行或是否结束无法确认 | 保存实际未知状态和错误，按适用的有限核实与恢复规则处理，不推断停止成功 |
| 所需记录无法可靠读取或保存，或者提交结果未知 | 按状态库错误与提交核实规则处理，不把缺少可靠记录解释为没有设备活动 |

多个取消入口涉及同一活动时，共用原停止流程及剩余预算。[后续动作停止历史残留录像](../architecture/camera-recovery.md#后续动作触发的残留收场)使用触发动作自己的独立流程，关联原录像活动；停止成功保存新观察和本次流程结果，原录像终态与原停止结果保持不变。应急停止继续遵守数据库不可写时仍可有限执行的规则，不以成功保存活动记录为前提。

活动记录属于发起它的动作自身状态，历史恢复及快照包含相应信息，不成为独立的历史快照对象。一次结果影响历史动作的活动状态和另一触发动作的处理状态时，相关历史与投影在同一业务事务中保存。已经结束的活动及其历史永久保留；历史回放只重建记录，不调用设备。

## 录像内部检查与修复记录

`recording_processing` 保存一个录像动作在提交终态前的内部原片检查和修复处理。同一录像动作至多有一条记录，保存适用的检查决定、修复判定及其依据，以及检查和修复各自的进度、结果与错误。动作自身的执行状态与最终结果由 `actions` 保存；检查失败、修复失败和录像失败分别表达。

处理记录关联已可靠确定的源文件、输入拷贝和适用的中间文件。检查与修复使用同一有效输入副本时，继续引用同一份文件及拷贝记录。需要逐份管理的文件由相应文件记录保存，不在处理记录的 JSON 中另外维护可增长的文件清单。

| 信息或处理责任 | 保存位置与使用规则 |
| --- | --- |
| 是否需要检查或修复、采用的门槛和可靠依据 | 由 `recording_processing` 保存判定及当时依据；已保存的决定跨重启沿用，尚未决定的事项使用本次运行配置 |
| 检查取得的视频时长、判定及实际错误 | 由 `recording_processing` 保存；未取得可靠时长与已确认时长不足分别表达，工具错误不直接表示原片损坏 |
| 修复尚待判定、不需要修复、处理未完成或已取得最终结果 | 由 `recording_processing` 分别表达；未执行不表示成功，修复结果不单独决定录像结果 |
| 输入文件拷贝、读取尝试和预算 | 分别引用 `file_copies`、`operation_runs` 和 `operation_attempts`，不在处理记录中独立维护同一进度或预算 |
| 输入、工具临时文件及尚未登记的修复成品的保留与清理 | 由 `intermediate_files` 保存，处理记录提供实际用途及处理结果依据 |
| 录像最终结果与正式产物登记 | 按录像结束规则共同提交，分别由 `actions` 和 `outputs` 保存；内部文件及处理结果的存在不表示产物已登记 |

检查与修复的判定遵守[修复门槛](../architecture/camera-recovery.md#自动修复的多录门槛)、[原片检查](../architecture/camera-recovery.md#计时证据不足时的原片检查)及[修复与动作成功分离](../architecture/camera-recovery.md#修复与动作成功分离)的规则。判定未知、处理未完成和已取得最终结果分别保存；所需历史、配置或提交结果无法可靠确认时，按对应错误处理，不补造判定。

适用处理尚未结束时，保存内部进度，按[录像动作的结束时点](../architecture/camera-recording.md#录像动作的结束时点)继续处理或恢复。取消与过期仍按各自规则执行，记录未执行或停止后续处理的原因。录像终态提交后，不重新启动该录像的内部检查和修复；后续取回或检查发现的媒体问题由正式产物的质量事实表达，不改写原录像终态。

处理记录及其变化属于录像动作自身状态，由该动作的历史恢复和快照包含，不成为独立的历史快照对象。处理结果与相关文件、动作及正式产物的状态按所属业务事务共同保存，文件删除不删除处理记录和历史。

## 设备文件记录

`device_files` 的每条记录表示 camctl 业务涉及的一份设备文件，保存稳定的内部文件身份、所属设备、驱动可解释的定位信息、业务归属及可靠取得的文件事实。记录范围由拍摄、内部处理、取回和清理的实际需要确定，不要求扫描并登记设备存储中的全部文件。尚未可靠确认的归属、写入完成情况、完整大小或摘要保持未确认，不以记录存在代替这些结论。

设备文件可以先于正式产物登记。录像原片已经生成但仍需检查或修复时，内部处理和拷贝引用相应设备文件记录；正式产物登记后，`outputs` 关联原记录，沿用同一文件身份。重启恢复、后续取回及清理继续定位同一份文件，不因新增处理流程而重建文件身份。内部文件身份与设备定位信息分别表达，不能仅凭文件名判断两次观察必然属于同一份文件。

采用[拍摄前后比较](../architecture/camera-capture.md#本次任务的文件归属)时，启动前的实际目录或编号基准属于动作执行记录，在发送命令前可靠保存；它不属于首次受理的只读执行定义，也不要求将基准中的历史文件全部登记到 `device_files`。实际识别出的本次文件再按本节建立内部身份和关联，重启沿用原基准与已保存事实。

延时摄影的文件完成事实遵守[文件完成依据与产物检查](../architecture/camera-capture.md#文件完成依据与产物检查)。执行记录须能区分设备完成保证与声明等待假设，并保存实际采用的依据和必要检查结果。单份 `device_files` 记录存在或某份文件已经写完，不代替动作层面的产物集合检查，也不表示媒体内容已经全面验证。

| 记录或处理 | 与设备文件的关系 |
| --- | --- |
| 拍摄动作及录像内部处理 | 保存已经可靠取得的文件归属及关联，在正式产物登记前也能恢复原片检查和修复 |
| `file_copies` | 源文件位于设备时引用 `device_files`，目标主机文件引用 `intermediate_files`；同一设备文件可以被不同处理分别拷贝 |
| `outputs` | 正式登记设备产物时关联既有设备文件；正式产物身份及业务可用性由产物记录表达 |
| 公共读取、删除及存在性查询流程 | 引用实际目标文件，各自保存所属业务的尝试与预算；共用文件身份不合并不同处理的预算 |
| 主机中间文件及主机派生成品 | 继续由相应主机文件与产物记录管理，不作为设备文件重复登记 |

文件记录、正式产物登记和操作资格分别判断：

| 文件事实与登记阶段 | 保存与使用规则 |
| --- | --- |
| 文件身份或归属尚未可靠确认 | 保留已取得的信息和未确认原因；不建立猜测的可靠归属，不据此读取、登记产物或删除未知文件 |
| 身份和归属已确认，但尚未确认写入完成 | 保存已有文件关联及实际写入状态；依赖完整文件的拷贝和产物登记继续等待或按所属有限处理规则结束 |
| 已确认写完，但正式产物尚未登记 | 保存完整文件依据；具备内部处理资格时可以检查或修复，普通取回仍须等待正式产物登记 |
| 正式产物已登记，文件尚未确认清理完成 | 取回和清理通过产物定位设备文件，分别检查读取资格、删除限制及操作进度；关联存在不单独授予操作权限 |
| 按所属规则已确认文件删除 | 保存实际删除事实和相关业务结果，永久保留文件记录及历史，不据此删除产物或处理记录 |
| 必要记录无法可靠读取或保存，或者提交结果未知 | 按状态库错误与提交核实规则处理，不解释为文件不存在、已写完或已删除 |

文件读取沿用[固定源文件与续传规则](../architecture/file-copy.md#相机视频的断点续传)。同一份固定内容已可靠取得的源端摘要可以按[校验规则](../architecture/file-copy.md#读取正确性与文件校验)复用；各次拷贝的主机端摘要及比较结果仍由相应拷贝记录保存。文件事实及必要派生表示保持单一来源，不在动作、拷贝和产物中独立维护相互矛盾的副本。

设备文件登记不改变[拍摄结束与产物登记](../architecture/camera-recording.md#录像动作的结束时点)的事务边界，也不产生额外删除权限。未登记文件按所属拍摄的取消、保留及清理规则处理；正式产物按显式清理规则处理。文件事实影响相关动作、产物或处理结果时，权威历史与相应投影在同一业务事务中保存。

设备文件不成为独立的历史快照对象。相关文件事实按业务归属参与历史恢复；恢复动作、产物或交付时，使用目标历史边界处的文件事实，不以之后取得的大小、摘要或删除结果解释过去的状态。

## 文件拷贝记录

`file_copies` 的每条记录表示所属业务中的一次具体文件拷贝，保存业务归属、源文件与目标中间文件的关联、最新可靠字节进度、重拷轮次及预算、完整性校验状态和依据。普通取回、录像内部原片检查及修复输入拷贝共用这张表，分别遵守所属业务的执行资格和后续处理规则。

| 拷贝用途 | 归属与身份 |
| --- | --- |
| 普通取回的独立副本 | 关联本次取回目标及实际交付；不同请求创建独立副本时，各有自己的拷贝记录 |
| 录像内部原片检查或修复输入 | 归属于原录像的内部处理，不创建普通交付；同一内部副本按规则继续用于检查或修复时沿用原拷贝记录 |

每条拷贝记录关联其读取流程，读取尝试预算和尝试事实由 `operation_runs`、`operation_attempts` 保存。读取重试、分段推进和同一任务的重启恢复沿用原拷贝身份。摘要不一致时按[有限重拷规则](../architecture/file-copy.md#摘要不一致后的有限重拷)增加轮次并从头拷贝，不建立新拷贝记录来重置预算，也不把重拷轮次当成读取尝试次数。

最新可靠进度保存在 `file_copies`，历次进度和轮次变化保存在不可变历史中。分段保存遵守[先保存文件，再记录进度](../architecture/file-copy.md#先保存文件再记录进度)：文件及必要目录同步成功后，在同一事务中记录进度历史并更新投影。分段不建立独立业务表，重启从可靠进度及原轮次恢复，不根据中间文件长度直接推进数据库进度。

读取完成、完整性校验完成和交付完成分别表达。`file_copies` 保存拷贝及校验事实；普通交付的准备完成和文件交接由 `deliveries` 保存，并引用同一套拷贝依据。内部拷贝的成功不自动表示录像成功或修复完成，结果继续由所属处理按其契约判断。公共报告中的交付 `copy` 和录像 `source_copy` 按[公共拷贝字段](../architecture/report-format.md#公共拷贝字段)从对应历史状态生成。

拷贝记录不成为独立的历史快照对象。普通取回的拷贝状态归属相应交付，录像内部拷贝状态归属录像动作；历史恢复和快照按所属对象包含相应信息。实际中间文件的保留、删除及交接权限继续遵守各自生命周期，删除中间文件不删除拷贝记录或历史，也不改写已经确定的业务结果。

## 中间文件记录

`intermediate_files` 的每条记录表示 camctl 为取回、原片检查或内部修复在主机上管理的一份中间文件，保存稳定的文件身份、所属处理、用途、位置关联、保留需要及清理状态。中间文件可以是未完成的副本、完整输入、处理临时文件或等待登记及交接的完整输出；“中间”描述业务阶段，不表示内容不完整或允许随时删除。

`file_copies` 保存复制过程，`intermediate_files` 保存文件的归属与生命周期。拷贝记录关联目标中间文件，修复工具直接生成的中间文件也有自己的文件记录，不要求存在拷贝记录。同一文件的清理状态在中间文件记录中维护，相关报告和业务详情根据其历史状态生成，不另行维护可独立修改的清理结论。

| 文件与所属处理的情况 | 中间文件记录与后续管理 |
| --- | --- |
| 文件仍用于续传、检查、修复，或尚有登记及交接责任 | 保存用途与归属并保留文件；完整文件也可能仍处于这一阶段 |
| 文件已无用途，处理结果或取消决定已可靠保存，相关操作已确认结束 | 按所属业务规则清理，并保存实际结果；查询或删除失败时保留未完成责任 |
| 归属、用途、登记结果或相关操作是否结束无法可靠确认 | 保留文件并核实，不能根据目录、文件年龄或大小判定可以删除 |
| 修复输出已可靠登记为正式产物 | 保留中间文件记录及其与正式产物的关联，结束适用的中间文件清理资格，实际文件由正式产物规则管理 |
| 取回副本已移入 `ready` 或 `processing` | 保留原文件关联和历史，按实际交接位置及所有权处理；不继续按 `staging` 中间文件规则删除 |
| 文件已确认清理完成 | 永久保留数据库记录与历史，不再作为待清理候选，不改写所属业务已有结果 |

中间文件的保留和删除资格分别遵守[取回中间文件](../architecture/obtaining-outputs.md#取回中间文件的保留与清理)及[录像内部中间文件](../architecture/camera-recovery.md#内部中间文件的保留与清理)。清理维护从已保存责任中分批查询候选，并遵守[中间文件清理的运行预算](../architecture/file-handoff.md#中间文件清理的运行预算)，不能通过扫描目录将所有文件作为清理目标。产物登记、交接及清理涉及的状态按各自事务与恢复规则保存，不能以一次路径变更推断责任已经转移。

状态报告的临时文件、日志副本及故障标记分别由所属机制管理，不纳入这张表的清理范围。中间文件记录不成为独立的历史快照对象，其事实按所属录像动作或交付的历史与快照规则保存。

## 历史事件与事务分组

`history_events` 统一保存业务与内部管理的权威历史事实，`history_transactions` 保存这些事件共同提交的分组。两张表分别回答发生了什么、哪些变化必须作为一次完整提交解释；动作、产物或报告的生命周期不作为历史事务的分组边界。

| 历史基础表 | 一条记录的职责 | 保存边界 |
| --- | --- | --- |
| `history_events` | 保存一项具有明确含义的事件，包括全局顺序、所属历史事务、类型与格式，以及重建相关状态需要的事实 | 公共信息使用固定列，正文使用按事件类型定义的 JSON；正文保存一次，查询目录按事件身份引用 |
| `history_transactions` | 保存一组共同提交的历史事件，使用独立递增的 `id`，以 `first_event_id`、`last_event_id` 保存本组首尾事件 ID | 保存完整提交分组，不复制事件正文；组内事件连续，不与其他历史事务交错或重叠 |

事件由[事件契约](persistence-runtime.md#事件契约的定义方式)定义。修改事实保存实际变化所需的前后值及字段存在性，创建事实保存足以重建对象的完整初始信息；一次事件影响多个对象时，分别建立实际需要的查询关联，不复制多份正文，也不因仅引用某个对象就认定该对象发生变化。

追加权威历史时，事件、历史事务记录、相关查询目录及受影响的业务投影在同一个 SQLite 写事务中保存。计划受理、录像结束、有效 ACK、报告管理及可信时间下界更新等分别遵守自身业务边界；跨表组织不拆开必须共同提交的事实。序号与事务标识遵守[全局事件序号与显式事务边界](history-storage.md#全局事件序号与显式事务边界)及其分配规则。

例如，录像结束的一次事务可以同时保存录像最终结果、正式产物创建及计划完成事实。若本次分配的事务 ID 为 101，事件 ID 为 301、302、303，则三条事件的 `transaction_id` 均为 101；事务记录保存 `id = 101`、`first_event_id = 301`、`last_event_id = 303`。这个例子说明提交分组，不固定录像结束必须拆成三个事件；具体粒度由事件契约决定。

| 写入或读取情况 | 两张历史表与相关状态的处理 |
| --- | --- |
| 一次写事务追加一条或多条权威事件 | 建立一条完整历史事务记录，全部事件及相关目录、投影一起提交 |
| 一次写事务只维护快照等派生数据，没有新增权威事件 | 不新增历史事件或历史事务记录 |
| 显式初始化状态库 | 以历史位置 0 表示初始边界，不创建虚构事件或事务记录 |
| 写事务提交成功 | 整组历史及相关业务状态共同生效，历史事务记录的结束位置成为完整历史边界 |
| 写事务确认回滚 | 本次新增历史及投影变化均不生效，不留下部分分组 |
| 提交结果无法确认 | 按状态库错误及恢复规则核实整次提交，不能根据调用报错猜测已经回滚 |
| 分批读取停在事务内非末尾事件 | 可以作为读取游标，不能作为报告、快照或完整历史状态的截止边界 |

报告冻结及对象快照使用完整已提交事务边界。事务 101 的事件范围为 301～303 时，历史截止位置使用末条事件 ID 303；事件 ID 301 和 302 可用于事件分页，但不能作为该事务的完整状态交付；选择更早状态时使用此前的完整边界。边界不存在、分组矛盾或必要记录不可可靠读取时，按历史状态错误处理，不取相邻位置代替。

已提交事件及事务分组永久保留。对象终态、文件删除和快照生成均不删除权威历史；历史回放只重建状态，不执行设备命令、文件生成或交接操作。字段布局、约束、索引及各事件的具体正文遵守后续表定义与事件契约，不由本节示例推定。

## 对象与事件关联

`entity_event_links` 保存对象与改变其状态的历史事件之间的关联。一条记录表示一条事件对一个对象产生了需要恢复的状态变化，并保存该对象截至本事件的累计变化次数。事件正文由 `history_events` 保存，对象的当前状态由所属业务投影保存；关联表只保存定位和计数所需的信息，可以根据权威历史与事件规则重建。

同一对象与同一事件只建立一条关联。对象身份由类型与 ID 共同确定，按各业务的状态归属解释；将对象的数据拆到多张物理表，不因此增加独立历史对象或扩大快照范围。创建、单事件多字段、同事务多事件及多对象的累计计数规则见[实体历史关联与累计变化计数](history-storage.md#实体历史关联与累计变化计数)。

每条关联还表达该对象变化是否属于应报告的业务变化。属于时保存对应的 `change_seq`；不属于时不保存业务变化序号，其含义是该变化不进入报告业务覆盖区间，而非尚未分配或结果未知。

| 事件对对象的实际影响 | 关联的处理 | 报告对象选择 |
| --- | --- | --- |
| 对象状态发生变化，且该变化应报告 | 保存一条关联，增加该对象的累计变化次数，并保存对应业务变化序号 | 业务变化序号落在报告覆盖区间时，该对象参与选择 |
| 对象状态发生变化，但该变化属于不应报告的内部管理事实 | 保存一条关联并增加该对象的累计变化次数，不保存业务变化序号 | 该关联仅用于历史恢复，不据此选入报告 |
| 事件仅引用对象身份，没有改变该对象状态 | 不为该对象建立关联，也不增加其累计变化次数 | 不因引用而选入报告 |
| 报告为提供上下文补齐父对象，父对象本身未发生变化 | 不因补齐操作建立关联或增加计数 | 按报告父对象补齐规则读取其冻结状态 |

父对象自身的派生状态发生变化时，按表中对象状态变化的规则处理。一条事件改变多个对象时，分别判断每个对象的状态变化与报告资格，为实际改变的对象各保存一条关联。

历史恢复与报告对象选择共用这张表，通过不同的索引支持各自的查询。历史恢复按对象类型、ID 和事件位置查找关联，再读取事件正文；报告生成按业务变化区间查找关联，在数据库中对对象去重并分页。每次应报告的变化都保留关联，不能只保存对象最近一次业务变化的位置。具体查询路径见[历史、目录与查询](persistence-runtime.md#历史目录与查询)。

新增关联与对应事件、历史事务记录、受影响的当前投影及适用的快照维护进度在同一写事务中保存。提交后的关联保持不变，读取与历史回放不重复增加计数；确认回滚与提交结果未知分别遵守数据库事务规则。关联字段的具体列名、类型和索引布局由表定义细化。

## 对象快照与维护进度

`entity_snapshots` 保存对象在指定完整历史边界处的状态，供历史查询复用；`entity_snapshot_progress` 保存各对象尚未被最近已提交快照包含的变化次数，供维护协程发现候选。两张表按对象类型与 ID 统一组织，其对象范围遵守[历史快照的对象范围](history-snapshots.md#历史快照的对象范围)。

| 表 | 一条记录的职责 | 生命周期与查询 |
| --- | --- | --- |
| `entity_snapshots` | 保存一个对象在完整历史边界 S 处的状态、该边界处的累计变化次数及保存格式版本 | 同一对象可以保留多个历史边界的快照；已提交内容固定并永久保留。历史查询按对象查找不晚于目标边界 H 的最近快照 |
| `entity_snapshot_progress` | 保存一个对象尚未被最近已提交快照包含的变化次数 Δ | 维护范围内每个对象只有一条进度记录，从对象创建时建立，随对象变化与快照提交更新。维护协程通过索引分批查询达到阈值的对象 |

快照内容包含所属对象自身状态及按业务归属纳入的明细，父子对象分别遵守自身快照规则。其身份、边界、计数、格式与完整内容一起保存，准备期间的新变化不能混入已有边界。快照的编码和字段布局按保存格式契约细化。

维护进度遵守 Δ＝A－B：A 为对象当前累计变化次数，B 为最近已提交快照包含的累计变化次数；确认没有快照时 B＝0。进度由权威历史与已提交快照派生，可以重建。对象尚未达到阈值、已有快照包含全部变化或维护暂停时，进度记录仍保留实际值；它表示对象的维护依据，不表示已经创建了生成任务。

| 操作或状态 | 两张表与相关记录的处理 |
| --- | --- |
| 创建维护范围内的对象 | 在创建事件、关联和投影的同一事务中建立进度，创建计为第一次变化；是否生成首份快照按阈值判断 |
| 对象发生后续变化 | 与事件、关联和投影一起更新维护进度，已有快照保持不变 |
| 快照正在准备，尚未提交 | 已提交快照及进度基准保持不变，业务变化继续累计 |
| 保存完整快照 | 新增对应边界的快照，并在同一事务中按提交时的 A 和保存后的最近快照计数更新 Δ；只维护派生数据，不新增权威历史事件 |
| 事务确认回滚 | 本次快照或业务变化及相应进度更新均不生效 |
| 提交结果未知 | 按既有事务规则核实实际保存结果，不按内存结果重复扣减 Δ |

例如，在 S 处读取对象累计第 64 次变化后的状态，准备期间对象又发生 6 次变化。保存这份快照时，快照计数仍为 64，提交时 A 为 70，因此进度更新为 Δ＝6。已有历史快照继续保留，后续查询仍可使用各自边界处的内容。

统一阈值、候选排序、批量限制、提交与对象发现驱动的唤醒及会话退出遵守[历史快照维护](history-snapshots.md)。进度记录缺失或与可信依据矛盾时，按该专题的状态库错误规则处理。具体字段与索引按历史快照查询和维护候选查询的实际访问路径细化。

## 普通列、子表与 JSON 的分工

先根据数据的用途和生命周期确定存储位置，再选择字段表示。多个条件同时成立时，以独立查询、逐项更新及关系约束的需要决定是否建立子表；该记录内部的复杂内容仍可使用 JSON。

| 数据用途与变化方式 | 保存方式 | 设计要求 |
| --- | --- | --- |
| 用于身份定位、所属关系、状态判断、排序或候选查询 | 普通列，并按实际查询设置约束和索引 | 直接表达查询条件与关系，明确空值和合法范围 |
| 同一对象包含可增长的记录集合，且需要独立定位、逐项更新或分页查询 | 具有明确父对象关联的子表 | 为成员确定稳定身份；有业务顺序时明确保存或计算顺序的依据 |
| 动作首次受理时确定、之后只读的小型专属执行定义，按动作整体读取，不承担公共查询条件 | 动作的专属执行定义 JSON | 按动作类型定义明确结构；由所属动作处理模块解释，与受理事实共同保存 |
| 内容形状随动作或事件类型变化，通常随所属记录整体解释 | 有明确格式的 JSON 字段 | 定义字段、类型、存在性及解释规则；保存和读取均遵守精确数字契约 |
| 同时包含查询条件和复杂内容 | 普通列与 JSON 配合 | 明确每项信息的来源；额外查询表示只能按规定派生，不能独立修改 |

动作所属计划、设备、执行时间及状态使用适合查询的列。拍摄参数采用有明确类型的 JSON。启动尝试、来源成员、逐产物选择、取消目标及中间文件责任，按各自的身份和生命周期设计关联记录。

JSON 内部同样有字段契约。字段不存在、显式空值、未知和未完成分别按所属业务规则表达；解析成功不等于内容有效。序列化、校验和读取遵守[精确数字与类型适配](data-types.md)。

### 动作专属执行定义

录像动作的驱动从生效参数及拍摄任务定义取得目标时长，录像处理模块据此计时、恢复和判断完成。这个时长属于首次受理时确定的专属执行定义，保存在动作的有明确结构的 JSON 中；其解释由录像处理模块负责。公共调度管理动作资格、计划时间、启动窗口和状态，不需要理解每种设备的全部专属执行字段。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.execution_spec_json` | 可空 `TEXT`，非空时为精确 JSON 对象 | 动作首次通过全部受理校验时确定的执行定义，供所属动作处理模块执行及恢复使用 |

动作执行定义使用 `actions.type` 对应的数据类型。JSON 对象直接保存该类型的执行定义字段，不增加动作类型名称的外层包装，也不重复保存动作类型。每种结构明确字段含义、类型、单位、必填性及适用条件；输入转换、保存、读取和历史回放使用同源定义。字段缺失、内容非法或类型不适用时，按所属错误契约处理，不能用字典缺省值猜测执行含义。

下表先按首次受理结果区分，再按对应动作是否需要专属执行依据区分。是否通过受理由可靠受理事实判断，不能根据动作后来是否 `failed` 推断。

| 受理结果及定义要求 | `execution_spec_json` 的保存规则 |
| --- | --- |
| 整份计划被拒绝 | 不创建动作记录 |
| 动作在受理时失败，不论是否已经计算出局部执行依据 | SQL `NULL`，表示没有形成有效执行定义；原输入和错误按各自规则保存 |
| 动作通过全部校验，所属类型需要专属执行依据 | 保存符合该类型契约的完整对象，必需字段不能缺失 |
| 动作通过全部校验，所属类型没有额外执行定义字段 | 保存 `{}`，表示有效定义没有额外字段 |

合法录像必须保存其所需目标时长，不能使用 `{}` 代替完整执行定义。JSON `null`、数组、字符串及其他标量不是合法执行定义；SQL `NULL` 与有效空对象的含义不同，不能互相转换。合法受理后发生过期、取消或执行失败时，保留首次保存的对象。

| 信息 | 内容及负责解释的边界 |
| --- | --- |
| 原始输入 | 调用方提交的结构化值及字段存在性，由原计划重建和诊断流程使用 |
| 生效驱动参数 | 首次受理确定的完整驱动参数，由原选定驱动解释；拍摄动作使用 `effective_params_json` |
| 动作执行定义 `execution_spec_json` | 对应动作处理模块需要的固定执行依据；录像目标时长从生效参数及任务定义取得 |
| 本地执行配置 | 本次运行采用的通信、重试及处理配置，由配置规则管理；实际判断的必要依据随对应执行事实保存 |
| 操作尝试、逐项结果与检查修复进度 | 按独立身份、关联和生命周期保存到所属列或记录，由相应业务流程推进 |

原始输入、生效参数和专属执行定义分别表达输入与受理结果，不各自成为可独立修改的要求。首次受理按驱动及动作契约建立派生关系，与动作、绑定及对应历史在同一事务中保存。后续执行、重送、重启和历史回放使用已保存的执行定义，不重新读取新的驱动默认值推算旧定义。运行进度和操作结果另行保存，不改写首次执行定义。

受理流程由对应动作模块形成并校验执行定义，再与全部受理结果共同提交；驱动提供拍摄任务所需的依据，动作模块负责转换为自身明确的执行结构。定义只保存该模块确实需要的固定依据，不复制完整原输入、生效驱动参数或本地配置。读取时按动作类型及受理事实核对 JSON 结构和空值组合；无效的持久化定义按状态库错误处理，不以空对象或新计算结果修补。公共报告按其既有字段和出现条件读取所需依据，不将整份内部执行定义直接输出。

普通列的选择依据是公共管理、查询、排序和关系约束的需要，不要求每种动作都有值。设备及驱动标识、计划时间和适用的启动延迟仍按各自列契约保存。数据只读不自动意味着适合 JSON；只读的身份、关联和需要分页查询的大型集合仍按前表组织。小型专属定义使用 JSON，可增长或需要独立更新的记录使用子表。

验证须覆盖上述受理与空值分区、不同动作采用各自结构、错误类型或不适用字段被拒绝、合法录像缺少必需字段、JSON `null` 与 SQL `NULL` 不混用，以及受理提交与回滚。核对固定定义与原输入的派生关系，验证受理后过期、取消、执行失败、重送、重启、历史回放和驱动默认值变化均保持原定义；结构或空值组合错误按状态库错误处理。公共调度通过既定公共接口取得需要的信息，动作模块负责解释专属定义；新增动作时按实际数据用途选择列、JSON 或专属记录。

### 各类动作的执行定义分工

动作执行定义保存所属处理模块需要的固定派生依据和受理时确定的默认含义。原输入已经完整表达的要求、已有的实例关联，以及执行时才能取得的目标和结果，分别使用各自的保存位置。下表适用于通过全部受理校验的动作；受理失败仍保存 SQL `NULL`。

| 动作类型 | `execution_spec_json` 的内容 | 其他信息的保存位置 |
| --- | --- | --- |
| `camera_take_photo` | `{}`；动作类型已经确定执行一次拍摄 | 生效参数由 `effective_params_json` 保存；实际采集、设备活动和文件事实按各自记录保存 |
| `camera_record` | 录像目标时长 `target_duration_ms` | 启动、停止、实际计时、检查和修复进度按各自执行记录保存 |
| `camera_timelapse` | 从生效参数和任务契约取得处理模块需要的固定执行依据；按持续时间采集时，两种结束方式都保存 `target_duration_ms` | 完整设备要求由 `effective_params_json` 保存；设备任务关联、实际采集进度、尝试和文件事实另行保存 |
| `obtain_action_outputs` | 首次受理确定的 [selection_mode](#取回执行定义的选择方式)，区分默认取回、预览取回和精确 ID 取回 | 原输入保留来源描述及显式 ID；来源关联、实际文件选择和处理结果由来源表及取回明细保存；自动预览用途、关联和能力依据由 `auto_preview_links` 保存 |
| `delete_action_outputs` | `{}`；来源范围或精确 ID 已由输入明确指定 | 原输入保留选择条件；范围来源由 `action_output_sources` 保存；实际目标和处理结果由 `cleanup_items` 保存 |
| `cancel_task` | `{}`；原输入已经完整表达取消目标描述 | 执行时解析并固定的实际目标和处理结果由取消明细保存 |
| `report_status` | `{}`；原输入已经明确指定完整或局部同步要求 | 执行时确定的固定起点、开始依据和同步责任由 `state_syncs` 保存 |

单张拍摄的次数不等于产物文件数。一次拍摄可以产生多种格式的文件；完成判定使用驱动提供的采集完成、文件归属和写入完成依据，不使用固定文件数量代替这些事实。

延时摄影的生效参数保存设备契约接受的完整拍摄要求，包括适用的采集间隔、持续时间和输出设置。动作执行定义只提取处理模块需要理解的固定依据，不复制整份驱动参数，也不由时长除以间隔生成强制目标次数或实际进度。处理模块和驱动按[职责分工](../architecture/camera-capture.md#延时摄影处理模块与驱动的职责)落实计时、停止和完成判断。采用时间与产物判定时，保存声明的执行依据以及实际发送、等待和产物核实事实，不补造设备状态观察。设备自动结束和主机控制结束使用各自明确的任务契约，执行与重启恢复沿用首次确定的要求。

取回的选择方式与最终选中的文件分别保存。例如，输入同时省略 `filter` 和 `output_ids` 时，受理流程保存默认取回的解释结果，但保留原输入中的字段缺省；后续文件选择按照该方式处理。实际文件尚未产生、来源尚未结束或来源尚待执行时解析，不妨碍保存合法的选择方式，也不授权提前固定目标文件集合。显式请求 ID 与实际产物关联仍分别遵守取回明细规则。

清理、取消和报告的处理模块从已保存的合法输入读取明确要求，并转换为相应程序类型。读取不重新受理计划、不吸收重送正文，也不重算已经固定的来源、目标或同步起点。需要运行时查询的引用继续在所属契约规定的时点解析；已保存的关联和执行结果用于后续恢复。合法空执行定义不表示动作没有参数、没有目标或已经执行完成。

验证按动作类型和受理结果覆盖完整对象、有效空对象与 SQL `NULL` 的适用条件；单张拍摄覆盖一次采集生成多份文件，取回覆盖省略筛选参数与显式选择，清理、取消及报告覆盖仅受理尚未解析运行时引用。重送、重启和历史恢复保持首次选择方式及已固定的实际集合，不通过重新解释输入扩大处理范围。

### 录像执行定义的目标时长

`camera_record` 的 `execution_spec_json` 使用 `target_duration_ms` 保存录像目标时长。该值表示从可靠确认本次录像已经开始的计时锚点起，正常控制流程要求至少继续录制的时长；取消和异常收场仍按各自规则处理。

| JSON 字段 | 类型与范围 | 保存规则 |
| --- | --- | --- |
| `target_duration_ms` | JSON 整数，1～9223372036854775807，单位为毫秒 | 合法受理的录像执行定义必填；从生效参数和驱动任务定义精确取得，首次保存后保持不变 |

例如，目标为 60 秒的录像保存以下执行定义：

```json
{"target_duration_ms": 60000}
```

表示范围不等于设备支持范围；实际目标时长还须符合对应驱动的参数契约。公共计划时间固定到秒表达开始时间，目标时长可以具有毫秒粒度，两者分别校验。客户端及驱动输入可以使用其契约规定的单位，内部转换不要求调用方改用毫秒。

| 待转换或读取的值 | 处理 |
| --- | --- |
| 可精确表示为范围内的正整数毫秒，且符合驱动业务约束 | 保存整数毫秒；例如 1.5 秒保存为 `1500` |
| 零或负时长 | 非法，不表示无限录像或立即停止 |
| 精确换算后存在不足一毫秒的余量，例如 1.0005 秒 | 不受该执行定义支持，不舍入、不截断 |
| 换算后的整数超出表示范围，或超出驱动允许范围 | 非法，不裁剪为边界值 |
| 目标时长缺失、为字符串、布尔值、`null` 或其他非数值类型 | 不能形成合法录像执行定义，不隐式转换或补值 |

JSON 整数按数学值判断，沿用[精确数字规则](data-types.md#精确数字与统一输出方向)；合法输入的精确转换和持久化不得先经过二进制浮点数。受理失败时整列仍按执行定义规则保存 SQL `NULL`，不保存缺少目标时长的局部对象。

用户输入违反有效驱动规则所声明的范围或精度时，按动作参数错误处理。用户输入符合已声明规则，但驱动任务定义或转换结果无法形成合法目标时长时，属于驱动定义或内部转换错误，按所属会话错误处理，不将规则或实现错误归咎于用户。已保存的目标时长缺失或非法时，按状态库错误处理。

执行、恢复和修复判断使用同一已保存目标，按参与计算的单位精确换算；实际媒体时长与目标分别保留。不能先将实测媒体时长舍入到毫秒，再判定是否达到目标。毫秒存储精度不承诺设备能在毫秒边界停止，也不改变启动确认、单调钟及异常恢复的既有规则。

验证覆盖 1 毫秒、零、负数、最大表示值及越界值、驱动范围两侧、可精确换算的小数秒、不足一毫秒的余量、错误 JSON 类型，以及固定任务和用户指定时长两种来源。区分用户输入错误、驱动定义或转换错误、持久化记录错误；验证重送及历史恢复保持精确值。以低于目标但舍入后会相等的实测时长作为反例，确认完成判定不通过舍入制造达标结果。

### 延时摄影执行定义的目标时长

对于按持续时间采集的 `camera_timelapse`，`execution_spec_json.target_duration_ms` 保存首次受理确定的目标采集时长。该字段为正整数毫秒，沿用[录像目标时长](#录像执行定义的目标时长)的数值范围、精确转换和错误归属规则，且须符合对应延时摄影驱动的参数契约。数值表示相同不意味着两种动作采用相同的停止、媒体检查或修复流程。

| 受理结果与结束方式 | 保存规则与用途 |
| --- | --- |
| 合法受理，设备按目标持续时间自行结束 | 必须保存 `target_duration_ms`；命令返回后任务仍在执行时，按声明安排等待；返回已证明采集完成时，直接继续尚需进行的产物核实 |
| 合法受理，主机按目标持续时间发出停止命令 | 必须保存 `target_duration_ms`，处理模块据此安排停止操作 |
| 动作受理失败 | 整列保存 SQL `NULL`，不保存局部执行定义 |

采集间隔与输出设置由生效驱动参数保存，不通过时长除以间隔生成实际采集次数。目标时长与运行时的计时锚点、剩余时间及设备观察分别保存；首次定义保持不变，重启根据原任务的可靠事实和声明的恢复方式继续，不能把某次运行的单调钟截止值作为跨会话时间使用。[等待与完成核实](../architecture/camera-capture.md#设备自行结束时的等待与完成核实)规定适用的状态或产物核实、取消和重启行为。

验证覆盖两种结束方式都必须保存合法目标时长、首次受理失败仍为 SQL `NULL`、重送和恢复不改写目标，以及目标时长到达只触发相应操作而不直接形成成功结果。已有记录缺少必要目标时长或数值非法时，按状态库错误处理，不从新的驱动默认值补造。

返回后等待所用的单调钟锚点遵守[命令返回含义与等待起点](../architecture/camera-capture.md#命令返回含义与等待起点)，不使用数据库保存完成时点替代实际取得成功结果的时点。持久记录区分命令发送、启动观察、等待完成和任务完成响应；保存目标时长不意味着每次调用返回后都重新等待该时长。

[无状态查询任务的重启等待恢复](../architecture/camera-capture.md#无状态查询任务的重启等待恢复)保存发送成功时取得的 UTC 日期时间、预计检查时间及采用的等待依据。日期时间沿用数据库整数微秒规则，单调钟截止值不作为跨会话依据。预计检查时间由原发送时间、固定目标及余量和实际部署额外等待派生，不成为可独立修改的第二套时长要求。各次安排及等待完成事实属于执行记录，具体字段归属随执行记录结构细化；动作的只读执行定义不保存这些运行结果。

采用发送成功后等待的任务，将[驱动必要余量](../architecture/camera-capture.md#驱动必要余量与部署额外等待)与目标时长分别保存到只读动作执行定义；必要余量由驱动按首次生效参数形成，重送和重启不按新的驱动默认值重算。部署额外等待默认 0，是本地运行配置，实际采用的值随执行事实保存，不作为首次受理的固定字段。等待完成事实及其实际依据共同保存，历史恢复不使用新的配置改写原结论。

### 延时摄影执行定义的结束控制

`camera_timelapse` 的 `execution_spec_json.end_control` 表示正常执行时由谁结束采集。驱动根据任务契约和生效参数，在动作首次通过全部受理校验时确定该字段；处理模块按保存值选择正常结束流程。字段保存在专属执行定义 JSON 中，不作为 `actions` 的独立列。

| JSON 整数值 | 程序枚举成员 | 正常结束责任 |
| --- | --- | --- |
| `1` | `DEVICE` | 设备按本次任务参数自行结束采集，camctl 等待并核实结果 |
| `2` | `HOST_TIMER` | camctl 计量目标采集时长，到时通过驱动发出停止命令 |

程序使用具有上述固定整数值的枚举，JSON 使用对应整数，遵守[整数枚举规则](#状态与类型的整数枚举)及[精确数字规则](data-types.md#精确数字与统一输出方向)。不接受字符串、布尔值、JSON `null`、非整数数值或未定义编号，不通过缺省值猜测结束方式。

| 受理结果及任务契约 | 保存与处理 |
| --- | --- |
| 合法延时摄影任务由设备自行结束 | 必须保存 `end_control: 1`；按持续时间采集时，同时保存合法 `target_duration_ms` |
| 合法延时摄影任务由主机按时停止 | 必须保存 `end_control: 2` 和合法 `target_duration_ms`；驱动契约必须具备相应停止能力及明确计时依据 |
| 动作受理失败 | 整个 `execution_spec_json` 保存 SQL `NULL`，不保存局部结束控制字段 |
| 驱动任务定义无法明确结束责任，或声明由主机停止却没有对应能力 | 不能形成可用执行契约，按驱动定义错误处理，不将其解释为用户参数错误或自动改用设备结束 |

`end_control` 不表示命令返回时机。命令发送成功即返回和任务完成后才返回，都可以对应 `DEVICE`；是否还需等待由原返回契约及实际结果判断。该字段也不代替停止能力声明：`DEVICE` 任务可以支持提前停止，不能仅凭该值拒绝取消；`HOST_TIMER` 必须支持正常结束所需的停止操作，取消仍按[取消资格](../architecture/task-cancellation.md#设备任务的取消资格)判断。

合法受理后，该值保持不变。重送、重启、配置变化和历史回放不重新选取结束方式；实际启动、等待、停止和结果另行保存。读取到必需字段缺失、编号非法或持久化定义自相矛盾时，按状态库错误处理，不根据新的驱动默认值补齐。

验证覆盖两种结束方式的必填字段及能力约束、非法类型和编号、受理失败的整列空值，以及重送、恢复和回放保持原值。组合 `DEVICE` 与两种命令返回时机、支持和不支持提前停止的任务，确认不会从结束控制推断返回时机或取消能力。

### 延时摄影执行定义的停止能力

`camera_timelapse` 的 `execution_spec_json.stop_supported` 保存驱动是否支持停止本次设备任务。该字段为必填 JSON 布尔值，由驱动根据本次任务契约及生效参数在首次受理时确定，合法受理后保持不变。它只保存本任务所需的停止能力，不复制整个设备能力目录，也不作为 `actions` 的独立列。

| 字段值 | 含义 |
| --- | --- |
| `true` | 驱动支持停止本次设备任务；是否可以向实际活动发出停止操作及是否成功，仍按归属、执行阶段和调用结果判断 |
| `false` | 驱动不支持停止本次设备任务；已启动或可能启动且尚未终态时，拒绝取消，原任务继续处理 |

程序使用布尔值，JSON 保存 `true` 或 `false`，不接受整数 `0`、`1`、字符串、JSON `null` 或字段缺失。驱动定义必须明确提供能力，不能用缺省 `false` 掩盖未定义的任务契约。动作受理失败时，整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部停止能力字段。

正常结束责任与停止能力按以下完整组合校验：

| `end_control` | `stop_supported` | 合法性与行为 |
| --- | --- | --- |
| `1`（`DEVICE`） | `true` | 合法；设备正常自行结束，必要时可按取消规则提前停止 |
| `1`（`DEVICE`） | `false` | 合法；设备正常自行结束，已启动或可能启动时拒绝取消 |
| `2`（`HOST_TIMER`） | `true` | 合法；camctl 到时通过驱动停止，取消仍遵守所属规则 |
| `2`（`HOST_TIMER`） | `false` | 非法；主机负责结束任务却没有停止能力，不能形成可用执行契约 |

驱动提供的类型或组合非法时，按驱动定义错误处理，不当作用户参数错误。读取到已保存定义缺失、类型非法或组合矛盾时，按状态库错误处理，不重新查询设备能力补齐或改写原定义。重送、重启、配置变化和历史回放均保留首次值。

该字段不表示已经发出停止命令、停止成功或停止操作可以安全重复，也不代替设备活动归属证明。实际停止意图、尝试和结果由执行记录保存。`false` 不阻止可靠确认尚未启动的任务被取消；终态、已有取消事实及启动结果未知的处理遵守[设备任务的取消资格](../architecture/task-cancellation.md#设备任务的取消资格)。实际驱动或设备不可用时，按对应执行错误处理，不将本字段改成 `false`。

验证四种结束控制与停止能力组合、非法类型和字段缺失、受理失败的整列空值，以及重送和恢复保持原定义。组合任务未启动、已启动、启动结果未知和已有终态，验证取消资格；验证能力为 `true` 但实际停止失败时，保留失败结果且不修改能力声明。

### 延时摄影执行定义的启动返回含义

`camera_timelapse` 的 `execution_spec_json.start_return_meaning` 保存启动任务的调用成功返回时，驱动保证的事实。该字段由驱动根据任务契约及生效参数在首次受理时确定，合法受理后只读；它不是某次调用的结果，也不作为 `actions` 的独立列。

| JSON 整数值 | 程序枚举成员 | 成功返回保证及处理 |
| --- | --- | --- |
| `1` | `SENT` | 只确认命令发送成功，不直接确认设备已经开始采集；需要等待的任务按声明的发送成功锚点计时 |
| `2` | `STARTED` | 确认设备已经开始采集，处理模块按驱动声明的可靠计时依据继续管理任务 |
| `3` | `COMPLETED` | 确认采集任务已经完成，继续尚需进行的文件检查，不重新等待完整采集时长 |

程序使用固定整数枚举，JSON 保存对应整数，遵守[整数枚举规则](#状态与类型的整数枚举)和[精确数字规则](data-types.md#精确数字与统一输出方向)。合法受理的延时摄影必须提供该字段，不接受缺省值、字符串、布尔值、JSON `null`、非整数数值及未定义编号。受理失败时，整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部返回定义。驱动无法给出明确返回含义时，按驱动定义错误处理；持久化定义缺失或非法时，按状态库错误处理，不用新的驱动默认值补齐。

固定定义与实际调用结果共同决定后续处理，已有终态、生效取消及状态库错误仍优先适用各自规则：

| 本次调用的实际证据 | 处理 |
| --- | --- |
| 取得契约规定的成功响应 | 按保存的 `start_return_meaning` 记录相应事实，并执行上表对应的后续处理 |
| 调用失败、超时或中断，且没有可靠的成功事实 | 保存实际结果及未知情况，按原异常或恢复规则处理；不能从定义值推导发送、启动或采集已经成功 |
| 已取得可靠事实，随后调用发生异常 | 分别保存已取得的事实与调用异常，按所属执行规则处理；不抹去事实，也不将异常伪装为正常返回 |

采集完成不自动证明文件写完，`COMPLETED` 不代替文件归属、写入完成和产物集合检查。`end_control` 表示正常结束责任，与本字段分别判断；`DEVICE` 可与三种返回含义分别组合，具体任务仍须提供与所选方式一致的等待及完成契约。仅凭返回含义也不能判断是否支持提前停止。主机负责计时停止的任务仍须具备及时安排停止所需的计时依据，不能等采集完成才开始计算停止时间。

调用尝试及实际结果由执行记录保存，不写回本字段。重送、重启和历史回放使用首次确定的含义，不因驱动默认值变化重新解释原响应。验证三种成功含义、各类非成功结果及先取得事实后发生异常；组合完成响应与文件仍未写完，确认不会提前登记产物，声明为 `COMPLETED` 但调用超时时也不会产生虚构完成事实。

### 延时摄影执行定义的结果等待余量

`camera_timelapse` 的 `execution_spec_json.result_wait_margin_ms` 保存驱动要求的必要等待余量，适用于发送成功后等待目标采集时长、再检查结果的任务。该值覆盖目标时长之外的启动准备和最终文件处理时间，由驱动根据任务契约及首次生效参数确定；合法受理后保持不变。

| 字段 | 类型与范围 | 含义 |
| --- | --- | --- |
| `result_wait_margin_ms` | JSON 非负整数，范围为 `0` 至 `9223372036854775807`，单位为毫秒 | 在目标采集时长之外，驱动要求检查结果前额外等待的时长 |

该字段的存在性由任务的等待契约决定，不能仅根据 `end_control` 推断。按以下分类保存：

| 受理结果与等待契约 | 保存规则 |
| --- | --- |
| 合法受理，采用发送成功后等待目标时长的方式，需要额外余量 | 必须保存驱动确定的正整数毫秒值，并保存该方式要求的合法目标时长 |
| 合法受理，采用该等待方式，但驱动明确不需要额外余量 | 必须保存 `0`，不能省略字段 |
| 合法受理，不采用该等待方式 | 省略字段，不能用 `0` 或 JSON `null` 表示不适用 |
| 动作在受理时失败 | 整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部余量定义 |

数值遵守[精确数字规则](data-types.md#精确数字与统一输出方向)，不得先经二进制浮点数换算后舍入或截断。字符串、布尔值、JSON `null`、负数、非整数毫秒及越界值均不合法。驱动定义无法形成合法余量时，按驱动定义或内部转换错误处理，不将其归咎于用户输入；读取到持久化值非法、适用时缺失或不适用时仍有值，按状态库错误处理，不补默认值。

例如，设备自行执行 20 分钟的任务，发送成功后还需等待 5 秒的必要余量，则有关字段为 `target_duration_ms: 1200000`、`end_control: 1` 和 `result_wait_margin_ms: 5000`。本地部署额外增加的等待时间按[等待余量规则](../architecture/camera-capture.md#驱动必要余量与部署额外等待)另行保存到执行记录，不累加写回本字段。命令返回已经证明任务完成时，不因设备自行结束或存在原等待定义而重新等待完整采集时长；实际已取得的事实按返回契约解释。

验证适用时的零值、正值和上界，不适用时字段省略，以及受理失败的整列空值。覆盖非法类型、数值越界、适用时缺失和不适用时提供字段；验证重送、配置变化、恢复和历史回放保持首次余量，本地额外等待不修改该值。

### 延时摄影执行定义的完成判定方式

`camera_timelapse` 的 `execution_spec_json.completion_mode` 保存处理模块判定采集完成时允许使用的依据。字段由驱动根据本次任务契约及生效参数在首次受理时确定，合法受理后只读，不作为 `actions` 的独立列。两种方式均须完成必要的文件归属、写入完成及产物集合检查，才能登记动作成功。

| JSON 整数值 | 程序枚举成员 | 完成判定要求 |
| --- | --- | --- |
| `1` | `DEVICE_EVIDENCE` | 必须取得驱动认可、能够关联原任务的设备完成依据，再完成必要的产物检查 |
| `2` | `TIME_AND_OUTPUTS` | 允许按明确的设备运行假设，在声明的等待条件满足且产物检查通过后判定完成 |

程序使用固定整数枚举，JSON 保存对应整数，遵守[整数枚举规则](#状态与类型的整数枚举)及[精确数字规则](data-types.md#精确数字与统一输出方向)。合法受理的延时摄影必须保存该字段，不接受缺省值、字符串、布尔值、JSON `null`、非整数数值及未定义编号。受理失败时，整个 `execution_spec_json` 保存 SQL `NULL`。

设备完成依据可以来自任务完成后返回的成功响应、任务状态查询、设备保存的完成记录，或符合任务契约的停止结果及必要计时依据。`DEVICE_EVIDENCE` 不统一要求状态查询接口；具体证据的含义和取得方式由驱动声明。`start_return_meaning` 只解释启动调用的成功响应，不代替本字段对后续完成判定的约束。

结束控制与完成方式按下表校验，停止能力继续遵守其自身组合约束：

| `end_control` | `completion_mode` | 契约要求 |
| --- | --- | --- |
| `1`（`DEVICE`） | `1`（`DEVICE_EVIDENCE`） | 驱动须提供原任务的可靠完成依据及必要文件检查规则 |
| `1`（`DEVICE`） | `2`（`TIME_AND_OUTPUTS`） | 驱动须声明有限时长、自行结束、可靠等待及文件完成规则；采用发送成功后等待目标时长时，保存合法目标时长及 `result_wait_margin_ms` |
| `2`（`HOST_TIMER`） | `1`（`DEVICE_EVIDENCE`） | camctl 按原契约计时并执行停止，结合停止及必要计时依据判断，随后核实产物 |
| `2`（`HOST_TIMER`） | `2`（`TIME_AND_OUTPUTS`） | 非法；需要主机停止的任务不能仅凭时间到达及文件存在认定设备已经结束 |

运行时先处理已有终态、生效取消、明确失败证据及状态库错误。其余情况按下表依次判断；实际取得的依据及检查结果由执行记录保存，不写回固定定义：

| 实际取得的事实 | `DEVICE_EVIDENCE` | `TIME_AND_OUTPUTS` |
| --- | --- | --- |
| 已取得原任务的可靠完成依据 | 使用该依据，继续尚需进行的文件检查 | 使用该依据，不重复等待已经证明完成的阶段；未被依据覆盖的文件处理仍按原契约核实 |
| 尚无完成依据，但声明的发送及等待条件已经满足 | 仍不能判定采集完成，继续适用的有限核实 | 按声明的文件完成与产物规则核实，全部要求满足后登记成功 |
| 尚无完成依据，声明的发送或等待条件也未满足 | 继续原执行或恢复流程，不根据文件存在推断完成 | 继续原发送处理、等待或恢复流程，不提前登记成功 |

任何方式下，产物缺失、归属或写入完成尚未确认时均不登记成功，按所属有限核实及文件保留规则处理。时间与产物判定不产生设备直接报告完成的观察，也不补造实际采集次数或时长。明确的失败或提前中断证据不能被等待到期或表面齐备的产物覆盖。

执行时不因状态查询失败或预算耗尽，将 `DEVICE_EVIDENCE` 改为 `TIME_AND_OUTPUTS`。重送、重启及历史回放沿用首次方式；实际完成依据可以增加，但不能重写过去的处理结果。驱动定义的模式、能力或等待规则不一致时，按驱动定义错误处理；持久化字段缺失、非法或组合矛盾时按状态库错误处理，不补默认值或切换方式。

验证全部结束控制与完成方式组合，以及非法类型、编号、必填字段缺失和受理失败的整列空值。按运行判定表覆盖取得可靠完成依据、只有等待完成、等待未完成及文件检查不通过；验证查询失败不切换方式、可靠依据只免除其已经证明完成的阶段、已知失败优先，以及报告不会混淆直接设备观察与等待推导结论。

### 取回执行定义的选择方式

`obtain_action_outputs` 的 `execution_spec_json.selection_mode` 保存本次取回选择文件的规则。该字段在首次通过全部受理校验时由合法输入确定，之后保持不变，不作为 `actions` 的独立列。实际来源和选中文件按各自执行时点确定，不因选择方式已保存而提前固定。

| JSON 整数值 | 程序枚举成员 | 选择规则 |
| --- | --- | --- |
| `1` | `DEFAULT` | 默认取回排除预览；每份原文件有已登记的对应修复成品时选择修复成品，否则选择原文件 |
| `2` | `PREVIEW` | 按预览取回契约选择，包括存在有效预览且对应修复成品满足完整大小比较条件时，选择修复成品 |
| `3` | `EXPLICIT_IDS` | 仅处理用户明确指定的产物 ID，不自动替换或扩大选择范围 |

程序使用固定整数枚举，JSON 保存对应整数，遵守[整数枚举规则](#状态与类型的整数枚举)及[精确数字规则](data-types.md#精确数字与统一输出方向)。合法取回必须提供该字段，`DEFAULT` 是显式保存的规则，不是读取缺失字段时的兜底值。字段缺失、字符串、布尔值、JSON `null`、非整数数值或未定义编号均不合法。

输入映射遵守[取回参数组合](../architecture/plan-input.md#取回来源筛选与预览)。下表中的合法条件包含来源、用途及其组合限制；仅能识别筛选方式不代表动作已经通过全部受理校验。

| 首次受理的输入及结果 | 保存规则 |
| --- | --- |
| 全部校验通过，未提供 `output_ids`，`filter` 省略或为 `default` | 保存 `selection_mode: 1` |
| 全部校验通过，未提供 `output_ids`，`filter` 为 `preview` | 保存 `selection_mode: 2`；手动与自动预览使用相同选择方式 |
| 全部校验通过，动作级来源提供合法的非空、无重复 `output_ids`，且未提供 `filter` | 保存 `selection_mode: 3` |
| 动作受理失败，包括空 ID 列表、非法 ID、同时提供 `output_ids` 与 `filter`、不允许的来源或用途组合 | 整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部选择方式 |

合法预览取回的执行定义为 `{"selection_mode":2}`。自动用途、来源关联及能力依据继续由 `auto_preview_links` 保存，不另设自动预览选择枚举，也不在执行定义中重复保存用途。原参数保留调用方实际填写的来源、ID 列表及字段存在性；实际来源成员由 `action_output_sources` 保存，逐来源选择进度由 `obtain_source_selections` 保存，实际产物或显式请求目标由 `obtain_items` 保存，交付结果使用相应交付记录。

选择规则沿用[默认及精确取回](../architecture/obtaining-outputs.md#产物选择)和[预览产物选择](../architecture/preview-obtaining.md#产物选择与失败)。预览不存在时，不因有修复成品而自动选择该成品；有效预览与修复成品比较完整大小，相等时选修复成品。默认选择的修复成品不可用时不退回原片，精确 ID 可以指定原片、预览或修复成品。选择结果可靠保存后，重试及恢复不因文件不可用而改选其他文件。

重送、配置变化、重启及历史回放沿用首次选择方式和已经固定的实际选择。读取到必需字段缺失、值非法或与保存的原输入及关联矛盾时，按状态库错误处理，不重新解释缺省参数补齐。合法输入的内部转换无法形成一致定义时，按内部错误处理，不将转换故障归咎于用户。

验证三种方式的全部合法输入映射、显式默认与省略默认具有相同方式但保留不同原输入，以及各种非法组合的整列空值。验证手动与自动预览共享选择方式、来源或文件尚未产生时仍可保存合法定义，以及默认替代、预览大小比较和精确 ID 不替代的区别。覆盖字段缺失、非法类型和编号、重送及恢复保持原选择；实际无效 ID 仍分别保存明细，不创建虚假产物关联或交付。

## 数据归属与原子更新

物理子表不自动成为独立的历史快照对象。例如，动作的尝试记录可以使用子表，但仍属于动作自身状态；动作的历史恢复与快照须包含相应尝试信息。计划、动作、正式产物和普通交付的快照范围遵守[对象范围](history-snapshots.md#历史快照的对象范围)。

同一字段的权威历史、当前投影和必要查询表示具有明确的派生关系。事务写入流程统一形成事件并更新受影响投影和目录；其他模块不能分别修改这些表示。历史回放使用同一事实解释规则重建投影，不执行外部操作。

跨表原子性由业务契约决定。例如，录像终态与正式产物登记由同一个业务操作提交；动作与产物分别存表时，这些记录仍在同一 SQLite 事务中保存。分模块和分表不拆分必须共同提交的事实。

数据库表示与公共报告表示分别承担执行恢复和客户端同步职责。报告根据冻结历史和公共协议生成；数据库记录还包含执行意图、尝试预算、可靠进度等内部依据，不能直接将整份投影作为报告输出。

## 表设计的交付要求

每张表的定义包括：

- 记录表达的事实或派生状态、所属业务对象及生命周期。
- 字段名、存储类型、可空性、合法范围，以及缺省或空值的准确含义。
- 枚举字段的成员含义、固定整数编号、权威定义及适用的公共协议对应关系；遵守[状态与类型的整数枚举](#状态与类型的整数枚举)。
- 各有效业务状态下，字段必须有值、可以没有值或必须没有值的组合，以及非法组合的写入与读取处理；遵守[空值与状态组合](#空值与状态组合)。
- 主键、外键、唯一约束和必要索引。
- 创建与更新入口、共同提交的记录，以及提交失败或结果未知时的处理依据。
- 正常查询、重启恢复和历史读取所需的查询方式。
- 由数据库约束保证的不变量，以及必须由事务写入流程保证的不变量。

索引由实际查询推导，通过 SQL 执行计划和软件集成测试验证。表结构验证须同时检查初始化、完整提交、回滚、并发写入和历史重建；仅能成功建表不代表业务契约已经闭合。
