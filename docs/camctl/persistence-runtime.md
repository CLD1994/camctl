# 数据库执行、事务与缓存

[设计入口](README.md) · [实现总览](implementation.md) · [实施准备](implementation-readiness.md)

本页定义数据库线程的操作接纳、事务完成与取消语义，并说明格式检查、物理结构和缓存的实现方向。历史位置 H 表示要恢复的完整事务边界，C 表示读取当前投影时绑定的边界，S 表示已保存快照的边界；概念与算法见[历史状态查询](historical-state-query.md)。表名及职责遵守[数据库结构与字段归属](database-schema.md)。未被规格固定的接口名、SQL 组织和索引方案属于实现建议，输入输出、不变量与失败分类属于必须保持的契约。

## 数据库整体格式检查与显式升级

`database_metadata` 的唯一记录保存 camctl 数据库标识、数据库实例身份和整体格式版本，职责见[数据库元信息](database-schema.md#数据库元信息)。其中 `format_version` 定义数据库采用的持久化契约，包括表结构、允许存在的事件类型及版本、当前投影和历史快照等表示。程序发布版本、数据库整体格式版本、各事件类型的 `event_version` 分别管理，不要求编号相同。修改日志文案等不改变持久化契约的程序更新不增加数据库格式版本。

程序具备读取某种新事件的能力，不会自动改变已有数据库的格式。数据库正式允许写入新事件格式时，必须先完成相应整体格式升级；仍标记为旧格式的库只能按旧格式契约读写。程序支持的数据库格式及每个格式允许的事件、持久化结构应由单一权威定义管理，不能只凭版本数字大小认定兼容。

所有使用状态库的入口先检查数据库身份、整体格式及必要结构。`run`、`submit` 在业务受理、使用投影作决策及产生设备或报告发布副作用之前完成检查；报告子进程在查询业务状态和生成报告之前独立检查。`init` 验证已有库时也检查格式，`describe` 的既有无状态库依赖保持不变。

| 数据库与程序能力 | 处理规则 |
| --- | --- |
| 数据库标识、格式与必要结构有效，程序明确支持该格式 | 按该格式契约使用；具体事件仍按类型和版本校验 |
| 程序支持新旧格式，打开的是旧格式库 | 继续遵守旧格式写入范围；需要新格式的功能要求先显式升级 |
| 数据库格式有效，但程序不支持 | 在使用业务状态之前明确报格式不受支持，不尝试部分执行或自动降级 |
| 格式标识缺失、非法，或内容与声明格式矛盾 | 按状态库校验错误处理，不猜测为版本 1 或其他可用版本 |
| 状态库缺失或读取结果无法确认 | 继续遵守既有不存在与错误分类，不自动建立空库 |

通过元信息判定整体格式兼容性，不为识别版本而扫描全部历史；这不代替必要结构检查及实际读取时的数据校验。版本或内容错误遵守各入口既有错误输出契约，保留不依赖状态库可用的诊断。

格式升级由部署人员显式执行，日常 `run`、`submit`、报告生成及重复 `init` 不自动升级。升级前暂停日常调用，并确认相关 `run`、`submit`、报告子进程及状态库维护操作已经结束；升级期间阻止新的日常操作进入。不能在旧程序仍使用业务状态时，由另一入口启用新格式。实际维护入口、锁协调、升级原子性及中断恢复在确有后续格式时另行定义。

升级后，旧程序只要不支持目标格式，即使库中尚未出现新版本事件，也拒绝使用。新程序保留旧历史读取能力；数据库升级后不承诺旧程序接管，不通过修改版本数字或改写历史实现软件降级。

采用[当前投影与历史快照的保存格式](history-storage.md#当前投影与历史快照的保存格式)：当前投影跟随数据库当前格式，结构变化时在维护阶段转换或重建并验证；历史快照保留原内容及生成时的 `format_version`，读取时按自身格式解释和适配。每份快照的历史边界 S 与保存格式分别记录，不增加独立快照版本编号。程序支持某个数据库格式时，须支持该格式允许保留的旧快照。

第一版显式初始化创建格式 1，仅实现格式 1 的读写、兼容性检查及不支持格式的诊断，不实现假想后续格式的迁移步骤。验收覆盖各状态库入口的支持、未知、缺失与非法格式分支，保证拒绝时不受理输入、不执行设备动作、不发布报告、不自动建库或升级；报告子进程的格式错误继续按状态库错误交付主进程。后续新增格式时再验收升级隔离、中断恢复及新旧程序读写范围。

## 持久化接口契约

| 接口类别 | 输入 | 输出 |
| --- | --- | --- |
| 状态查询 | 查询条件、当前状态或指定历史边界 | 明确的数据对象；不存在与读取失败分别表达 |
| 原子业务操作 | 本次操作输入，例如计划受理数据、设备观察结果 | 已提交的业务结果，或明确的失败状态 |
| 历史回放与投影重建 | 完整已提交的历史边界 | 重建结果，或明确的历史解释错误 |

原子业务操作包含依赖数据库现状的判断。例如，受理请求须在取得写事务资格后查询 `request_id`，再决定复用已有计划或注册新计划，完成 ACK 处理和历史、投影保存后提交。不能先在事务外认定新请求，再把该判断直接作为数据库写入前提。

具体业务判断由所属业务模块提供，持久化执行层管理连接与事务。事务内仅进行必要计算、数据库操作，以及规格规定的非阻塞锁操作；不等待设备、文件生成或其他长任务。数据库连接在所属线程内创建、使用和关闭。报告读取在独立进程中按批次完成短读事务，具体连接与结果所有权见[数据库连接与完整事务](#数据库连接与完整事务)。

同一 `run` 内的数据库操作采用[业务优先、快照维护等待空闲机会](history-snapshots.md#业务操作优先使用数据库线程)：每次选择下一项操作时，先处理等待中的业务查询与事务，再处理快照候选查询、依据读取或保存。已开始的操作跟踪至实际结束，不因后来到达的业务被打断；快照读取与保存分别排队，事务外准备内容不占用数据库线程。持续业务可以推迟快照维护，进度按原规则保留。此顺序只适用于本进程，独立 `submit` 及报告进程的数据库锁竞争另按所属规则处理。

数据库执行完成状态与业务结果是两个维度：

| 执行状态 | 数据库事实 | 后续处理 |
| --- | --- | --- |
| 未开始且确认不会执行 | 没有本次写入 | 根据原业务资格决定是否另行安排；不发送依赖本次写入的命令 |
| 提交成功 | 操作结果、事件、目录和投影整体存在 | 使用返回结果继续；业务结果可能是接纳，也可能是可靠拒绝 |
| 提交前失败且回滚成功 | 本次候选变更全部撤销 | 交付实际错误；不更新缓存，不产生后续外部副作用 |
| 提交或回滚结果未知 | 不能确认本次操作是否保存 | 停止依赖操作，按稳定业务身份核实；不能生成新身份后盲目重做 |

操作身份用于定位一次具体保存责任，例如启动尝试、交付进度段或报告发布结果。身份在入队前确定，并随相应事件或业务记录保存；它不代替请求幂等、实体身份或历史事务标识。恢复查询须核对身份对应的输入及阶段，不能只看某个事务编号是否出现。

取消调用协程不改变上述事实分类。已经开始的数据库操作仍由持久化执行层跟踪到实际结果；连接复用、排队取消及退出处理遵守[数据库线程状态表](#数据库连接与完整事务)。

正常写入与历史回放共用“根据历史事实更新投影”的规则。以同一批历史验证正常写入结果和回放重建结果一致；回放不发送命令、发布或删除文件。

### 数据库等待队列容量

数据库线程的等待队列按完整操作的条目数量限制容量。一项可以是一次状态查询或一个完整事务，不以 SQL 条数、动作数量或本批快照对象数量计数；同一事务的多条语句仍属于同一操作。业务操作与快照操作共用该等待容量，选择下一项时仍遵守业务优先规则。

本节定义主机本地配置的默认值及合法范围：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `database.queue_capacity` | `64` | 正整数；本进程数据库线程等待队列允许的最大操作条目数 |

按[本地配置的加载与更新](../architecture/configuration.md#本地配置的加载与更新)取得生效值。省略时采用默认值；显式提供 0、负数、浮点数、布尔值或字符串等非法值时，按配置错误处理。配置在本次 CLI 启动时读取，进程运行期间保持不变，部署调整在后续调用生效。容量属于进程内运行配置，不固化到动作，不作为跨进程共享额度。

| 操作状态或转换 | 对等待队列容量的影响 |
| --- | --- |
| 尚未入队，正在等待空位 | 不占用队列条目，遵守入队等待时限 |
| 成功入队、等待执行 | 占用一个条目；所有优先级的等待条目合计不超过生效容量 |
| 从等待队列取出并交由数据库线程执行 | 释放一个等待条目，执行中的操作另由数据库线程持有并跟踪实际结果 |
| 已入队但尚未开始，确认取消且不会执行 | 释放所占条目，不将其转交执行 |
| 入队前超时或确认取消 | 未取得条目，无需释放；不得迟到入队或执行 |

队列满载时按入队等待规则处理，不覆盖或丢弃已有条目。取出操作腾出空位不代表该操作已完成或已提交，容量释放与结果确认分别处理；取消与取出发生竞争时按实际阶段处理，不能重复释放条目或让已确认取消的操作执行。

容量不限制队列外等待者总数，也不保证固定内存占用或数据库处理速度。默认值用于容纳短时突发，属于尚待负载测量的初始工程值。调整容量不改变事务边界、优先顺序、入队时限及超时分类，不改变计划、历史或报告内容。

验收覆盖配置省略、合法覆盖、非法类型和数值，以及会话内固定、后续调用使用新值；容量取 1 及较大值，覆盖空队列、未满、恰好满载、并发入队、执行取出及排队取消。业务与快照合计遵守同一上限，多语句事务仍只占一项；执行中的操作和等待入队者不计入等待条目，入队前超时、取消与取出竞争均不导致条目计数错误。负载测试分别测量已入队数量、等待入队者数量、排队延迟和实际资源消耗。

### 数据库队列入队等待时限

数据库任务队列达到容量上限时，调用协程异步等待空位，入队等待上限为 9 秒，使用单调钟计量。该时限只约束本次提交取得队列位置的等待，不包含入队后的排队、数据库锁等待、执行及提交时间。入队不表示操作已执行或保存成功，调用方仍须取得实际操作结果。

| 本次提交状态 | 处理 |
| --- | --- |
| 有可用位置，立即完成入队 | 等待操作的实际结果 |
| 尚未入队，等待未满 9 秒 | 异步等待空位，事件循环可继续处理其他工作 |
| 在截止时间前完成入队 | 结束本次入队计时，按已排队操作跟踪；迟到的入队超时通知不改变结果 |
| 到达截止时间仍未入队 | 返回明确的入队超时错误，并保证该次提交以后也不会执行 |

空位取得与超时判定必须形成唯一结果：只有截止时间前确认入队的操作才进入执行队列，不能先向调用方报告超时，再让同一操作进入队列。超时只证明本次数据库操作未执行，不撤销已经发生的设备效果或先前已提交的事实；不得把待保存结果解释为已经可靠保存。

队列满载本身不丢弃操作或直接判定业务失败；达到 9 秒上限后明确报错。正常 `run` 中，必要业务数据库操作入队超时归为 `state_db_error`，按[无法继续执行时的退出](../architecture/session-errors.md#无法继续执行时的退出)进入会话错误收场。必要操作包括执行资格所需的状态查询、执行依据与设备结果保存、文件可靠进度保存以及报告责任登记和推进。不能只把对应动作改成失败并继续普通执行，也不能重新提交同一操作来无限延长本次等待。

`run` 停止启动新的普通动作并退出普通接纳阶段，已有活动按既定有限收场规则处理；满足可靠归属和安全停止条件的录像执行既有应急停止。错误诊断交付不依赖该次数据库操作成功，超时本身不证明数据库损坏。此前已提交状态保持不变，尚未保存的结果不得宣称已经可靠保存；后续正常 `run` 根据已提交历史与实际设备或文件证据恢复，沿用原身份及已消耗预算。

快照维护的入队超时采用[本会话停用规则](history-snapshots.md#快照入队超时后的会话内停用)：向维护调用方报错并记录诊断，停止本次 `run` 的快照维护，普通业务继续；后续提交或空位出现不重新启用，下一次正常 `run` 从持久化进度接续。此超时自身不形成会话错误。进入收尾时可确认取消尚未入队的快照操作，无须等满时限。已入队或已开始操作的取消与实际结果继续遵守持久化接口契约，实际数据库错误及提交未知不适用上述停用规则。

验收覆盖立即入队、等待后入队、持续满载、截止边界、空位与超时竞争，以及超时后禁止迟到执行；分别对必要查询、设备结果、文件进度及报告登记注入入队超时，验证会话错误、停止新增普通工作、保留已提交事实、按资格收场及后续恢复。

### 入队后的排队与取消

数据库操作成功入队后，第一版不另设等待开始执行的排队超时。操作按既定优先顺序等待数据库线程派发；入队等待的计时已经结束，不能把入队后的等待时间计入此前的 9 秒上限。容量限制和入队时限均不保证整个数据库调用的完成时间。

所属流程允许取消，或会话收尾需要撤回该项操作时，按实际状态处理：

| 实际状态 | 处理 |
| --- | --- |
| 已入队、尚未开始，未要求取消 | 保留操作并等待派发，不因排队时间较长报超时或重新提交副本 |
| 已入队、尚未开始，已确认取消且不会执行 | 移出等待队列并释放条目，返回未执行结果 |
| 已提出取消，但尚未确认能否阻止执行 | 继续协调取消与派发，不能先宣称未执行或关闭连接 |
| 操作已经开始，包括取消与开始执行发生竞争的情况 | 跟踪至实际结果，按完成、回滚或结果未知处理；调用协程停止等待不代表实际操作结束 |

会话收尾仍按各类责任判断哪些操作可以取消，不以取消必要保存来宣称业务完成。快照维护已入队但尚未开始的操作，继续遵守规定的维护退出规则。已开始操作的数据库锁等待遵守[SQLite 内置忙等待规则](history-storage.md#sqlite-内置忙等待与失败处理)，错误处理及连接关闭继续跟踪实际结果，不将执行阶段的等待参数解释为排队时限。

验收使用可控时钟及同步点，让操作在成功入队后等待超过入队时限，验证不触发入队或排队超时；随后释放执行机会，确认操作只执行一次。覆盖排队取消、取消与派发竞争、迟到的入队超时通知，以及已开始操作在等待者取消后仍被跟踪，确认容量释放、未执行结果和实际提交结果分别正确。

## 数据库连接与完整事务

Python 3.11 连接建议使用 `isolation_level=None`，由持久化层显式执行事务边界。日常写连接使用 SQLite URI 的 `mode=rw`，报告连接使用 `mode=ro`；动态拼接路径须正确进行 URI 编码。连接创建、使用、回滚和关闭均由所属线程完成，不通过关闭线程检查共享连接。

各写连接设置并核验 `synchronous=FULL`、规定的忙等待和自动检查点参数。日常入口检查已有 WAL 模式，不通过隐式建库或修复模式掩盖无效状态库。报告连接不得使用 `immutable=1`，因为业务进程仍会写入该数据库。相关库行为见[Python SQLite](https://docs.python.org/3.11/library/sqlite3.html#transaction-control)。

一次业务写入的顺序为：

1. 取得写事务资格，建议使用 `BEGIN IMMEDIATE`。
2. 读取请求、实体及原阶段，在事务内完成资格、幂等和状态判断。
3. 形成具有业务含义的事件，读取旧值并计算相应投影变化。
4. 分配连续的事件序号，保存事务分组、事件、历史关联、业务变化关联及投影。
5. 提交；只有确认提交成功后，才向调用方返回可执行后续操作的结果。

事件序号从事务内最后已提交序号之后分配，不使用会在回滚后留下独立进度的分配器。写锁竞争交给 SQLite 的规定忙等待处理，不在业务层增加一轮循环重试来延长上限。忙等待失败、磁盘错误和约束失败保留实际原因，按所属入口映射错误。

| 数据库线程情况 | 连接处理 | 等待者与退出处理 |
| --- | --- | --- |
| 操作排队，取消先于派发取得确认 | 不开始事务 | 移除操作，释放一次队列容量，返回未执行 |
| 派发已开始，随后取消等待 | 继续完成实际操作 | 保存最终结果并通知责任拥有者；不提前释放操作占用或关闭连接 |
| 提交成功，连接处于无活动事务状态 | 可以执行下一项 | 一次性完成结果通知 |
| 执行失败，回滚成功，连接仍有效 | 连接具备复用条件；是否继续业务由会话错误规则决定 | 返回明确失败；不能因为连接还能用就忽略 `state_db_error` |
| 事务结束结果未知、回滚失败或连接失效 | 停用并在所属线程关闭该连接 | 保留未知分类；不在失效连接上继续普通任务 |
| 进入关闭阶段 | 停止新接纳，按责任撤回未开始操作，跟踪已开始操作 | 实际工作结束后关闭连接、结束线程；事件循环异步等待 |

队列的派发和取消在同一短临界区决定，不能让两个路径都完成同一个操作。队列容量在取出或确认撤回时释放；完成结果在操作实际结束时产生，两者分别计量。数据库线程不打印自身 `ERROR` 日志，通过结果通道交给主事件循环记录。

## 历史、目录与查询

物理组织遵守[数据库结构与字段归属](database-schema.md)。下表描述访问关系，不复制全部业务事件或字段清单。

| 结构 | 保存内容 | 约束与查询 |
| --- | --- | --- |
| 历史事务 `history_transactions` | 首条事件序号作为事务身份、末条事件序号 | 整体提交；历史状态只使用完整事务结束位置 |
| 历史事件 `history_events` | `event_seq`、事务身份、事件类型与格式、JSON 正文 | 主键定位事件；正文保存业务事实及必要前后值 |
| 对象与事件关联 `entity_event_links` | 对象类型、ID、事件序号、累计变化次数，以及应报告变化对应的 `change_seq` | 同一对象与同一事件只有一条关联；分别通过索引支持 H 处末条关联、正反向分页及业务区间内的对象选择 |
| 当前投影 | 实体自身状态、父子身份、创建位置、累计次数 | 按所属父对象和 ID 分批读子实体；索引父子关系，不组装整棵树 |
| 对象快照 `entity_snapshots` | 实体身份、S、S 处累计次数、数据库格式与内容 | 唯一键绑定实体和 S；支持查找 `S ≤ H` 的最近快照，已提交快照保持不变 |
| 对象快照维护进度 `entity_snapshot_progress` | 对象累计次数与最近快照计数之差 Δ | 每个维护范围内的对象一条记录；索引采用维护专题规定的候选排序，不另设业务变化计数 |
| 报告及同步投影 | 冻结依据、发布事实、ACK 与同步责任 | 从对应历史派生；报告冻结不读取生成时的新配置 |

`entity_event_links` 可以用以下查询形状定位 H 处计数：限定实体类型和 ID，再限定 `event_seq ≤ H`，按事件序号倒序取一条。事件正文仅按入选的事件序号分批读取；不同实体共享同一事件时只读取一份正文，但分别应用该事件对各实体的影响。

报告对象选择查询同一张关联表中业务变化序号落在固定区间内的记录。每次应报告的变化都保留关联，不能只保留实体最近一次变化。业务区间中同一实体可能出现多次，查询层在固定区间内完成去重并按协议 ID 顺序分页；跨批次不能把去重集合无限保存在 Python 内存中。SQLite 使用临时排序结构不等于 Python 已加载全部对象，实际查询仍须通过执行计划和负载验证。

### 事件契约的定义方式

事件按业务事实定义，不能把通用 JSON 字段差异作为全部历史语义。每个事件契约至少包含：适用实体与前置状态、必要证据、变化字段的前后存在性和值、父对象派生变化、是否产生应报告变化，以及正向和逆向应用规则。字段不存在用独立标记表示，不与 JSON `null` 合并。

| 操作族 | 必须一起保存的事实 | 允许外部副作用的边界 |
| --- | --- | --- |
| 首次受理、重送与 ACK | 新受理的计划及全部动作初始结果，或原请求关联；独立 ACK 结果及必要诊断 | 本次输入处理提交后才使用新执行资格；重送不重新生成动作 |
| 启动、停止及读取尝试 | 尝试身份、原额度、消耗后额度和操作意图 | 意图与额度提交后才调用外部操作；结果未知不退还额度 |
| 设备结果与录像结束 | 本次尝试结果、可靠设备证据；终态成立时同时登记正式产物和父计划变化 | 回放只恢复事实，不重新发令；终态与产物不得分两次提交 |
| 固定来源与取得文件资格 | 按来源规则固定的集合、逐项选择、读取资格或删除限制 | 在同一产物的候选排序中判定并提交，之后才读文件或发出删除 |
| 分段拷贝与准备完成 | 同步成功的可靠进度；最终长度、摘要及准备完成事实，适用时解除源读取依赖 | 下一段从已提交进度开始；工作线程完成不代替数据库提交 |
| 文件交接 | 交接意图、实际移动及目录同步证据、最终结果 | 严格遵守普通交付与报告各自恢复表，不能共用缺失文件的结论 |
| 删除及文件存在性查询尝试 | 原清理动作、目标文件、本次尝试身份、对应额度占用及操作意图 | 分别遵守[删除与查询预算](../architecture/output-cleanup.md#删除与查询的独立尝试预算)，提交后才派发；结果未知不退还额度 |
| 取消与清理 | 取消目标和生效事实、目标独立收场责任、每项实际结果 | 目标继续履行已生效收场；取消发起者不撤销这些责任 |
| 报告登记、发布与 ACK | 报告身份、H、覆盖范围、生成依据及各次后续事实 | 登记后生成；移动并同步后保存发布事实；ACK 不改写冻结内容 |

具体事件类型在生产事件定义处集中登记；持久化解码、正反向应用与测试读取同一登记。事件类型未知或恢复字段缺失是状态库错误，不跳过事件。完整的业务状态仍引用责任专题，不在此另建状态清单。

### 初始化与维护

显式 `init` 在正式数据库所在文件系统准备独立的新库。准备阶段完成结构与初始事实、提交、收拢自身 WAL 并关闭全部准备连接，确认主文件可独立验证后，再将其放到正式路径。建议使用 `os.link` 实现目标存在即失败的原子创建，然后同步正式目录；准备文件的清理不得移除正式路径。

| 放置结果 | 处理 |
| --- | --- |
| 目标原先不存在且创建成功 | 同步目录后报告初始化成功；准备文件可按归属清理 |
| 目标已经存在 | 打开并按已有库规则校验，不覆盖；有效则保留，非法则失败 |
| 放置或目录同步报错，结果无法确认 | 报告失败并保留实际信息；下次显式 `init` 按正式路径实际状态判断 |

硬链接适用于同一文件系统；不支持时明确初始化失败，不能退回覆盖式重命名。上述方式是实现建议，其他方式须证明同样的“不覆盖、完整可用及目录持久化”契约。格式升级和派生结构整体重建要求日常进程停止；不设计在线切换或自动修复空库。

## 当前投影与按范围逆向恢复

采用“当前投影＋包含必要旧值的业务事件＋按范围逆向恢复”。每次保存业务事件时，在同一事务中保存必要恢复依据并更新受影响的当前投影；调度与普通业务查询直接使用可靠的已提交投影。不可变历史继续作为权威来源，正向回放用于投影重建与一致性验证。

报告冻结边界记为 H，整份报告保持不变。报告进程在短读事务中一起取得本批当前投影、对应的完整已提交边界 C 及当前累计变化计数，且 `C ≥ H`，取回数据后结束查询和事务。再通过范围索引，以多个短读事务分批读取这些实体及必要依赖在固定 `(H, C]` 内的相关事件，在事务外按事务与事务内事件的逆序恢复到 H。相关状态没有变化时，直接使用该投影。不同对象可以使用不同的 C，各自恢复范围始终与所取投影绑定，最终均表达同一 H 的状态。

业务事件必须保存报告相关状态逆向恢复所需的旧值或等价事实，覆盖字段存在性、集合、关系及实体创建边界。事件仍表达独立业务事实，不能仅以通用字段补丁代替业务含义。读取失败、投影失效、冻结依据无法确认或历史缺少必要恢复信息时，按状态库错误及投影恢复规则处理。完整状态分类见[历史状态查询与报告重建](historical-state-query.md#状态分类)。

每种事件按业务含义明确被改变的字段或集合成员，保存必要的前后值。父对象派生状态发生变化时，也直接保存其前后值，与触发变化的子对象事实同事务提交，使报告恢复父对象自身状态时无需读取全部子对象。旧值取自事务内该事件发生前的实际状态；同事务连续变化保留内部顺序。原始计划和固定生效参数由创建事实永久保存，后续事件通过身份关联。详细分类见[事件恢复依据](history-storage.md#事件恢复依据)。

逆向恢复只修改本次报告的数据副本，不将数据库当前投影改回旧状态，不执行外部副作用。报告仍按业务变化区间选择实体，所有入选实体及补齐的父对象都使用同一冻结边界；报告首次生成与后续重建采用相同的字节生成规则。

事件正文保存一次，由 `entity_event_links` 统一保存可重建的对象与事件关联，通过不同的查询路径支持报告对象选择和历史状态恢复。关联与事件及相关投影同事务提交；仅引用对象不视为改变它，批量查到同一事件时复用正文，分别保留各对象需要恢复的影响，避免遗漏或重复应用。采用[统一事件表与按类型定义的 JSON 正文](history-storage.md#统一事件表与按类型定义的-json-正文)，公共信息使用固定列，正文由持久化边界与有明确类型的事件对象相互转换。

采用[事件格式版本与读取兼容性](history-storage.md#事件格式版本与读取兼容性)：固定列 `event_version` 按事件类型独立演进，新程序保留旧版读取能力，适配仅改变内存表示，历史保持原样；不支持的格式明确报错。第一版仅实现事件版本 1 及识别、分派接口，整体兼容性遵守[数据库格式检查](#数据库整体格式检查与显式升级)，具体字段、列布局、索引和检查接口仍需细化。

采用 SQLite WAL 模式，所有状态库写连接显式设置并核验 `synchronous=FULL`，第一版不提供降低同步等级的配置；提交失败及结果未知继续按各自契约处理，详见[FULL 同步](history-storage.md#所有状态库写连接使用-full-同步)。

采用[自动 PASSIVE 检查点与可配置阈值](history-storage.md#自动-passive-检查点与可配置阈值)，各写连接显式设置并核验本次生效的 `database.wal_autocheckpoint_pages`，默认值及合法范围由该专题定义；不新增专用检查点线程；部分推进与数据库故障分别处理，阈值不代表 WAL 大小上限。

采用[SQLite 内置忙等待与失败处理](history-storage.md#sqlite-内置忙等待与失败处理)。各状态库连接显式设置并核验本次会话的 `database.busy_timeout_ms`，默认值和合法范围由该专题定义；报告进程取得主进程传入的生效值，重新创建时保持相同配置。最终锁忙错误不在应用层循环重发，按实际事务状态清理并交付状态库错误；该参数与入队等待分别计量，不构成事务总时限。

报告进程在自己的只读连接上使用分批短读事务。对象选择依据固定业务区间与 H 处历史关联，投影及计数绑定各自的 C；已选快照绑定 S，历史分页固定为 `(H, C]` 或 `(S, H]`。已提交历史及既有查询关联不改写或删除，快照内容不变，因此后续短读事务仍能取得这些固定范围的数据。每批读取完成后释放查询和事务，再恢复状态、编码和写文件。批次之间暂时让出资源时可保留本次任务的有界处理进度；任务失败或进程结束后仍按报告规则从头生成。缓存须明确对应不可变事实或实体在 C／H 的状态。完整分类与例子见[WAL 与分批短读事务](historical-state-query.md#wal-与分批短读事务)。

部署核验 Python 实际链接的 SQLite 运行库，并选用包含已知 WAL 并发缺陷修复的版本；具体部署版本仍待锁定。报告计算与文件生成在读写事务外进行。验收须覆盖正向与逆向结果一致、跨事务并发变化、固定范围分页、恢复旧状态不改变当前投影、报告字节一致性，以及恢复和写文件期间实际释放数据库读取。持续计划提交、慢存储和大规模报告组合下，联合测量 WAL 积压、计划接纳延迟、设备调度延迟与完整报告的业务滞后，不将某款设备或固定内存额度作为运行保障前提；这些测量用于了解第一版的适用负载，不要求实现后置的积压协调机制。

范围查询的读取量应取决于所需实体和相关历史区间，不能先加载全库历史再过滤。很早的边界若对应大量后续变化，仍可能需要较多计算；长期存储增长和各类报告负载的验收预算尚待确定。

同时采用[按对象累计变化次数触发的历史快照](history-snapshots.md#按对象累计变化次数触发历史快照)。各对象独立保存自身状态、身份、完整历史边界、对应累计计数及格式版本，父对象的子实体分别保存快照。维护范围内的对象共用正整数配置 `history.snapshot_change_threshold`，默认值与校验规则由该专题定义，各自独立计数和判断。当前投影持续更新；对象当前累计计数减去其最近已提交快照包含的计数，达到统一阈值时安排维护。没有快照时基准为 0，创建计为第一次变化，首次也按阈值触发；计数跨会话保留，正常 `run` 重新发现已达标对象，无须等待新变化。

配置每次会话启动时读取，会话内保持不变，后续会话按当次阈值重新判断，调整不重置计数或改变已有快照、业务事实及报告内容。可从不晚于目标边界的可靠快照正向恢复，与当前投影的逆向路径共存。

上述快照及其维护进度、候选查询和唤醒统一遵守[历史快照对象范围](history-snapshots.md#历史快照的对象范围)。第一版覆盖计划、动作、正式产物与普通交付，`report_status` 属于动作。输入诊断复用原创建事实，报告内部管理记录、累计 ACK 和同步责任使用各自历史与当前投影；这些记录不进入快照维护，阈值为 1 时也保持相同范围。既有报告的冻结依据和重建字节保持不变。

采用[持久化派生维护进度与候选索引查询](history-snapshots.md#持久化快照维护进度与候选查询)：数据库为维护范围内的对象保存尚未被最近快照包含的变化次数，`run` 与 `submit` 等入口随事件、关联和当前投影在同一事务内更新；保存快照时，在同一写事务内依据当前累计计数及该快照实际包含的次数推进维护进度，保留准备期间新增的变化。正常 `run` 按本次阈值通过索引分批发现候选，按未包含变化次数降序、对象类型标识和完整 ID 字典序升序选取。每批结束后依据最新已提交进度重新选取下一批，本批准备期间不因后来变化重排已选对象；该顺序不保证候选在固定时间内获得快照。

重启和配置变化不要求新事件或全量历史回放。维护进度可从历史及已提交快照重建，异常按状态库错误处理；实际表和索引仍需细化。

维护采用[提交与对象发现驱动](history-snapshots.md#提交与对象发现驱动快照维护)：进入正常 `run` 时查询一次遗留候选；本进程对象变化提交成功后，维护范围内的受影响对象达标即发布维护唤醒；通过既有流程发现外部提交的新对象时检查其维护资格，覆盖阈值为 1 的情况。本次会话维护启用期间，维护协程逐批处理，查空后等待通知；因入队超时停用后不再响应维护唤醒。通知可以合并，但须覆盖维护期间及空查询到进入等待之间到达的通知；数据库始终是候选的依据。

查询[按对象选择恢复路径](historical-state-query.md#按对象选择恢复路径)：无后续变化直接用当前投影，恰好命中目标边界的可靠快照时直接使用快照；其余情况在两条回放路径都有依据时比较相关事件数，正向更少时选正向，逆向更少或相同时选逆向；没有不晚于目标边界的快照时使用逆向路径。采用[实体历史关联与累计变化计数](history-storage.md#实体历史关联与累计变化计数)：每条关联保存实体类型、ID、事件序号及累计计数，一条事件改变一个实体需要恢复的状态计一次，同一实体与事件只建立一条关联。

计数由历史派生，并随事件和投影保存，快照保留对应计数；通过索引和差值取得范围内变化数，快照触发也采用同一计数单位。不同对象可采用不同路径，但都恢复到同一冻结边界并产生相同报告字节。具体索引仍需细化。

快照在业务可靠提交后，由 `run` 的维护协程分批生成，数据库读写仍使用已有数据库线程。每批对象数量受 `history.snapshot_batch_size` 限制，默认值与规则见[快照维护批量限制](history-snapshots.md#快照维护批量限制)；每批完成后释放临时数据，让出执行机会并重新检查会话状态。每批从一致视图取得对象状态和历史边界 S，结束读事务后准备内容，再通过短写事务整体保存快照与 S。生成期间出现的新变化不改变该快照的含义；维护进度只确认到 S，不遗漏之后的变化。报告不等待新快照生成，数据库错误仍按既有规则处理。

完整状态分类见[快照生成流程](history-snapshots.md#业务提交后分批生成快照)。

快照维护不单独阻止 `run` 结束，也不单独产生 `needs_run: true`。正常收尾停止新增维护：未开始的候选留给后续会话，尚在准备的临时内容可以丢弃，排队数据库操作须确认取消且不会执行，已开始的操作跟踪至实际结果后再关闭连接。下一次正常 `run` 通过维护进度索引重新发现候选。详见[快照维护与会话退出](history-snapshots.md#快照维护与会话退出)；具体取消机制及等待预算仍需细化。

## 缓存范围与数据库访问优化方向

采用 SQLite 页缓存、有容量限制的不可变内容缓存、活动任务缓存和单次报告内部数据复用；原子业务操作在提交成功后直接返回已保存结果，减少紧接着的重复查询。缓存复用已提交数据，写入继续保持既定可靠保存边界。容量及跨进程刷新机制仍需细化；拷贝进度按下文规定的分段规则保存，跨报告的历史计算结果缓存仍待评估。衡量时区分 SQL 调用次数、读取和解码的数据量、存储设备实际读写量以及可靠提交次数。

### 缓存范围与候选扩展

| 对象 | 采用方式或待评估内容 | 主要收益与边界 |
| --- | --- | --- |
| SQLite 数据页 | 为各连接配置适当的页缓存容量 | 减少重复读取存储设备；仍有 SQL 执行和结果转换成本 |
| 原始计划、固化参数、不可变事件及报告冻结依据 | 按稳定身份缓存已经提交并验证的内容，随数据库使用范围结束而清空 | 减少反复查询和解码；身份必须限定到同一状态数据库，未提交数据不能进入已提交缓存 |
| 当前活动任务的状态 | 沿用既有内存调度缓存，提交成功后以原子操作返回的结果更新受影响对象 | 省去提交后立即重复读取；独立 `submit` 的提交仍须按持久化序列发现，跨对象状态不得混合不一致版本 |
| 一次报告读取的对象与关联 | 在本次一致读取范围内复用，例如多个交付共用同一父动作时只加载一次 | 减少重复查询；分批处理时释放不再需要的内容 |
| 指定历史边界的计算结果 | 可评估按数据库身份、对象身份、历史边界及所需解释规则缓存，限定容量 | 旧状态不会因后续提交改变；命中率未知，不将其收益计入第一版性能承诺 |

SQLite 自带页缓存，容量设置是按连接所打开的数据库配置，默认实现按需分配；它不是 Python 业务对象缓存，见[SQLite 页缓存说明](https://www.sqlite.org/pragma.html#pragma_cache_size)。选择页缓存容量时，测试与联调须覆盖主进程与报告进程同时打开连接的情况，评估整体资源消耗。

### 已提交结果与当前状态的边界

原子业务操作在提交成功后返回本次已保存的结果及必要版本依据，调用方直接更新其负责的内存状态，不额外查询同一结果。结果只证明本次提交的事实，不保证之后没有其他事务提交；不能仅凭本次提交位置跳过尚未吸收的其他提交。

| 情况 | 缓存使用规则 |
| --- | --- |
| 已确认提交成功，结果及所属版本完整 | 更新对应已提交缓存；查询时仍遵守其版本范围 |
| 已确认回滚 | 丢弃本次候选结果，不把它作为已提交状态 |
| 提交结果未知 | 不发布候选缓存，停止依赖该结果的处理，按持久化规则确认实际结果 |
| 缓存缺失或被淘汰 | 从可靠数据库查询或重新计算 |
| 当前状态版本无法确认，或已知有尚未吸收的相关提交 | 先读取或刷新所需状态，再作依赖该状态的判断 |
| 数据库已知失效 | 按状态库错误处理，缓存不能提供继续普通执行的授权 |

新计划发现继续遵守[调度缓存](../architecture/scheduling-execution.md#新计划发现与内存调度缓存)：周期性轻量读取 `latest_plan_seq`，变化时增量加载；不能因缓存而延长现有感知目标。报告责任和 ACK 等状态按各自范围检查，不能仅凭 `plan_seq` 未变就认为数据库没有其他变化。幂等受理、旧值取得、依赖当前状态的写入判断，以及会话最终退出检查继续在规定事务内进行。

报告缓存中的“D 在 H 的状态”与“D 的当前状态”具有不同含义。前者仅复用于相同历史边界；后者进入报告恢复前，必须证明对应所绑定的 C，后续事件分页始终限定在 `(H, C]`。缓存登记事实不证明文件当前仍在 `ready` 或 `processing`，实际发布与恢复继续按文件交接规则检查。

SQLite 的 `PRAGMA data_version` 可提示同一连接两次检查之间发生了其他连接的提交，但不能直接作为跨连接的统一历史位置，也不跟踪本连接自己的提交，见[官方说明](https://www.sqlite.org/pragma.html#pragma_data_version)。是否使用这一提示尚未决定，它不替代事务内判断和一致读取设计。

### 减少写入的方式

保留业务规定的持久化边界，优先减少重复工作：同一原子业务操作的历史、目录和相关投影一次提交；仅更新受影响的投影部分；相同观察在没有新增状态、恢复依据或报告事实时，按既有事件粒度规则不追加历史。相同状态值仍可能携带新的恢复证据，不能只按字段相等去重。

拷贝进度保存频率采用[进度保存的分段大小](../architecture/file-copy.md#进度保存的分段大小)：使用本次会话的 `copy.segment_size`，默认值与合法范围由文件拷贝专题定义，取回、异常原片检查及修复输入共用。容量按[统一语法](../architecture/configuration.md#容量配置的表示)书写，加载时精确换算为整数个字节。采用[按段提交的流式传输任务](file-runtime.md#按段提交的流式传输任务)，线程内按较小块持续读取和写文件，段尾同步完成后由主协程组织进度提交，确认成功后继续下一段。

源文件最后不足一段也正常保存，提前结束但未达到已知源长度按读取失败处理。后续会话改变段大小仍从原可靠字节位置继续，不改变身份和预算。具体类型和签名仍需细化；任务提交遵守[默认线程池规则](file-runtime.md#本地文件执行使用默认线程池)。

缓存只复用已提交数据；操作意图、尝试预算、正式产物登记等继续在其规定位置可靠保存。

### 容量与验收

缓存设置条目数量上限，并在缓存满时淘汰可重新取得的内容。活动流程确实仍需持有的状态按实际生命周期保留，不能假定都可淘汰；流程完成后及时释放引用。数据按需读取，缓存只保留适合复用的部分，遵守[资源处理约束](implementation.md#通过处理流程控制资源使用)。负载验收同时覆盖条目数量和单条数据大小的变化，并测量数据库缓存、对象转换、报告与文件缓冲以及受管理工具进程共同工作时的实际消耗。

验收对比关闭与启用缓存时的业务结果和报告字节，覆盖独立 `submit` 提交、数据库回滚、提交未知、缓存淘汰、进程重启和读取期间发生新提交。分别统计缓存命中、SQL 次数、查询与解码量、实际读写、提交耗时和峰值内存。缓存关闭或全部丢失后仍满足相同业务契约。

### 已完成计划逐步退出常驻内存

冷热作为内存保留与查询加载策略，根据当前工作需要、近期访问和容量选择保留内容；业务状态仍采用既定计划、动作、产物及交付状态。已完成计划退出执行调度，无当前流程持有的详情可暂留近期缓存；缓存条目达到上限时，优先淘汰最久未使用且可重新取得的内容。具体容量、数据结构和查询索引仍需细化。

计划 `completed` 表示其动作均已进入终态。历史产物仍可能被新计划取回或清理；报告同步责任、残留设备事实及允许延后的清理也有各自生命周期。内存保留应按对象和责任判断，避免把计划完成解释为所有关联数据永远不变。

| 使用情况 | 内存与读取策略 |
| --- | --- |
| 当前执行、必要收场或恢复流程仍需要的数据 | 保留流程所需的最小状态；已结束且无关的计划详情可以释放 |
| 计划已经完成，无当前流程持有详情，近期可能再次读取 | 进入有条目数量限制的近期缓存；达到上限时允许立即淘汰 |
| 已完成且近期未使用的数据 | 释放可重新读取的内容，数据库保留历史、投影和身份关联 |
| 新计划引用旧产物或动作 | 按引用和实际选择范围加载所需对象，沿用原身份和终态，不重启旧计划 |
| 报告补投、同步或待确认责任需要旧数据 | 按冻结范围或责任标识查询；无需为等待远端确认而常驻整份旧计划 |
| 是否仍有责任或数据是否可靠无法确认 | 按既有未知与状态库错误规则处理，不能以冷数据分类代替责任判断 |

启动和日常检查按未完成动作、适用本地责任及设备关联索引查询，避免先加载全部历史计划再筛选。冷热变化本身不产生业务事件，不要求新增持久化冷却标记；责任的产生、变更和完成仍按原规则保存。收益主要是减少重复查询、解码和常驻内存，数据库永久历史的存储增长继续单独评估。

验收覆盖计划完成后被淘汰、新计划按范围引用旧产物、等待 ACK 时释放计划详情，以及计划终态后仍有独立收场责任的情况；缓存淘汰和重新加载不得改变原身份、终态、剩余预算或报告责任。增加已完成历史计划数量时，启动和正常调度不应因此加载全部计划详情。
