## 生产阻塞的修复前证据与处理要求

以下记录描述 `70149be6` 上的保存竞争和退出交接问题。前期窄复现证明机制，原场景证明阻塞位置；日志不足以直接确认的因果关系分别说明。当前修复状态见上节。

### 同一笔保存被正常流程和恢复流程同时处理

原流程登记待保存申请后等待数据库结果；下一轮恢复流程能取得同一申请并再次提交。数据库执行器按操作键只保存一个等待句柄，后一次提交覆盖前一次；完成通知也按同一键取走句柄。可控复现中，第一名调用者始终未收到结果，第二名调用者却取得第一笔操作的结果。位置为 `persistence/executor.py:252` 的 `_submit` 和 `:400` 的 `_finish`。

分段层还有结果消费的竞争：`capture/segment_completion.py:54` 的恢复入口与 `:86` 的原保存入口都能提交同一申请，随后都删除同一待处理项。用真实的两个入口、仅延迟数据库响应的窄复现，得到两次同键提交和一次 `KeyError(1)`。因此只让两名调用者都收到数据库结果，仍不足以修复完整流程。

OSMO 原超时现场已保存全部结果页；重启后完成第一个文件的登记，再为第二个文件保存“在场”事实。同一键出现普通和恢复两次保存，恢复阶段结束而原阶段没有结束，与上述回执丢失机制吻合。原现场没有记录等待句柄身份，尚不能把这一机制表述为该次超时的直接运行时证明。一次带观察的正常链可以完整通过，说明这是交错相关问题，不能据单次通过排除。

前期还在 Action6 的目录基准保存发现相同接手窗口，涉及当时的 `capture/baseline.py:144` 和 `capture/baseline_reads.py:41`；两处在等待后分别消费并应用原申请。`capture/result_pages.py:83` 的页保存、普通文件事实保存也需审查。Action6 上一轮现场在目录基准固定后未开始拍摄；重复基准保存是当时线索，不作为最新拍摄启动后停滞的直接证据。

最新 Action6 已开始拍摄并进入文件登记，同一 `_FileCompleteCommand` 键出现两次提交：第一次产生一个事件，第二次幂等返回；恢复路径记录保存结束，原路径没有相应结束记录。这些早期记录在运行中提取到 `live-log-summary.json`；原日志随后轮换，最终归档的压缩日志只保留后续空事务。最新 OSMO 已保存检查结果和分段集合，同一 `release_occupancy` 键的普通、恢复事务均记录完成，随后没有完成来源拍摄。它们支持继续核对同一申请的重复接手；本次未直接记录等待句柄身份，不能声称已经在两次现场逐一证明句柄覆盖是超时的唯一原因。OSMO 此次停在占用释放后的收尾，不能沿用上一轮普通文件在场保存的具体位置。

修复应让同一申请的“提交、取得结果、消费申请、更新内存状态”作为一个完整阶段由明确的拥有者推进。恢复入口协调或接手该阶段，保留原输入和原键；已结束后的真实新申请仍能继续。数据库层应保留每笔已接纳操作的正确结果交付，避免覆盖。不能只把删除改成忽略缺项，也不能只共享数据库结果而留下两次消费。回归覆盖并发普通与恢复入口、未知结果后原键核实、等待者取消、只应用一次以及后续申请不被旧阶段误删；最后验证原 Action6 与 OSMO 参数组。

## 首轮分段结果保存失败的归因

Action6 和 OSMO 的原代表用例均在真实 CLI 保存集合成员时回滚，错误为“分段保存只接受固定大小模型”。两项均在客户端复用接入前发生。

`0522159e` 的目标是让普通消费者读取已经保存的文件事实，避免重复执行旧 START／WAIT 和原保存核实；其[实施计划](../superpowers/plans/2026-10-26-transaction-facts-refactor.md)明确保持业务身份、事件表示和操作键语义。这一优化有设计依据，但没有要求所有调用方统一持有 `ObjectId` 对象。

具体类型变化发生在 `result_file_proofs._completion_page()`：旧实现已经用 `ObjectId(...)` 检查编号范围，最后返回 `int(page_id)`；重写后保留校验，却直接返回 `page_id`。这会把 `ObjectId` 对象放进 `SegmentMemberInput.page_event_id`。后续生产保存代码仍调用原有 `segment_storage.document()`，该编码器只接收普通标量，于是拒绝这个整数子类。读取端、模型和编码器在同一生产流程中没有衔接完整。

未发现提交说明或设计文档解释为何必须去掉最后的整数转换，不能据此推断作者主观意图。现有证据支持它是在重写核验路径时遗失了原适配；不是已经完成并被测试误解的新业务规则。`page_event_id: int` 注解本身并不排除整数子类，最终判断依据是设计目标、未改变的生产消费者，以及真实 CLI 的组合失败。

近期单元用例只比较编号数值，`ObjectId(872) == 872` 会通过；其他用例从已经保存的成员开始，未验证“读取新成员输入→编码保存申请”的接缝。真实失败库的 8 项成员中，原片和预览均出现此类型；仅对内存副本转换编号后，原编码器全部接受。这个只读诊断不等于保存事务或交付流程已经通过。

生产端在实现分支的 `f3b8f1c3` 恢复了读取适配末尾的普通整数返回，保留范围与来源检查，并补上 Action6／OSMO 的真实返回模型编码单元检查；该修复已同步。测试没有在真实 CLI 外替换此返回值、绕过成员保存或放宽成功预期。本轮未另行修改生产实现。

## 恢复检查与历史准备的调整

OSMO `native-tail` 已改为在重启后、首批新字节流出前保持读取门闩关闭。测试核对同一副本、交付身份、已提交偏移，以及设备读取命令的来源路径、块大小和跳过块数，然后放行读取，继续原最终字节及业务断言。这样可以发现从头重拷后最终内容仍正确的错误恢复。原 8 个场景、输入数据和成功预算保留。

历史报告准备改为生成 4 个真实照片产物，保留前后各 3 个动作、中间 4200 个动作、全部分页续读与资源释放检查。新增只包含前一计划产物变化的窗口：前一计划的产物为 `[1, 2, 3, 4]`，后一计划的产物和动作均为空；产物 4 与后一计划的动作 4 使用相同整数编号，缺少种类或父对象过滤就会失败。相同文件仍保留五类目标、父对象过滤及合法空页的独立检查。这个节点不再额外验证 128 张普通照片的完整发布规模，未声称该额外规模已由其他节点等价承接；256／2048 成员容量测试保持原规模。

Action6 与 OSMO 已让同一世界的计划导出、报告导入及媒体上传共用真实客户端；跨世界和专门验证重开的步骤继续隔离。接入采用原 Application／Files 路径、原完整参数、独立回执和原 120 秒命令预算。该改造以功能、恢复和资源生命周期验证为完成范围；首轮被生产问题阻塞的失败耗时不用于计算成功路径收益，也不据此发布整组提速比例。

公共辅助已经接通原 `export`、`import`、`import-media` 函数。独立真实客户端验证完成连续导出、报告导入、媒体上传和 ACK，记录为一个 Node、一个 Application、一个 Files，HTTP 服务和浏览器启动数均为零；既有 Hasselblad 浏览器签名与上下文切换验证通过。严格 TypeScript 检查、客户端构建、原独立命令、错误存储目录和未知命令的拒绝、0.5 秒启动／调用／关闭超时收场均通过。该窄验证不代表相机业务世界通过。

## 环境与证据

解释器为 CPython 3.11.17，SQLite 为 3.53.1。各任务使用独立工作区和临时根；history 与 bootstrap 按目录分进程执行。同一工作区没有并发构建、资源同步或集成测试。需要实际 CLI 的代表用例由既有启动器配置 2GiB 内存与交换空间合计预算，失败不记作业务验收通过。严格无交换能力单独验证。

准备、目标操作、pytest 总时间和入口墙钟按各自口径说明，不将各进程相加当作整轮墙钟。
