# 录像启动流程与机会归属

[操作字段](operation-fields.md) · [启动事务](waiting.md#首次启动机会与尝试的共同提交) · [一致性验收](consistency-verification.md)

录像 A 的启动流程负责让本次录像可靠开始。一次流程可以包含多次启动尝试；单次尝试失败不直接结束流程。本文定义 `camera_record` 的 `START` 流程，其他拍摄类型的启动完成条件由各自驱动与任务契约确定。

启动结果需要状态查询时，使用[启动核实责任](operation-fields.md#启动核实与停止核实)的独立查询次数；启动命令重试不刷新该计数，后来的停止核实另行计数。已有可靠启动响应时，不为建立查询记录追加无必要的调用。

## 流程状态与合法组合

流程沿用 `operation_runs` 的身份、状态、累计次数和重试间隔标记。动作保存取消与终态，设备活动保存真实观察及占用，尝试保存调用意图和结果。各字段共同表达一次启动责任，不将动作开始执行当作设备已经开始录像。

| 流程状态 | 含义 | `attempts_used` | `retry_wait_required` |
| --- | --- | --- | --- |
| `PENDING` | 已建立启动责任，尚未登记启动尝试 | 0 | 0 |
| `ACTIVE` | 已登记至少一次尝试，普通启动责任仍在处理，包括允许的重试及有限核实 | 大于 0 | 按实际间隔责任为 0 或 1 |
| `SUCCEEDED` | 在普通启动责任结束前取得并保存了可靠启动确认 | 大于 0 | 0 |
| `FAILED` | 普通启动责任因确定的失败条件结束 | 大于或等于 0 | 0 |
| `CANCELED` | 普通启动责任因动作取消生效而结束 | 大于或等于 0 | 0 |
| `EXPIRED` | 普通启动责任随动作的可靠过期判定结束 | 大于或等于 0 | 0 |
| `UNCONFIRMED` | 有限核实已经结束，启动效果仍不能确认 | 大于 0 | 0 |

`PENDING`、`ACTIVE` 仅用于尚未终态且取消未生效的动作；`ACTIVE` 所属动作必须为 `RUNNING`。动作取消生效、过期或其他最终结果结束普通启动责任时，与尚未结束的启动流程及间隔责任共同保存相应变化。已经结束的流程保持原结果，例如启动已成功后取消录像，不把原启动流程改为取消。

`FAILED`、`UNCONFIRMED` 按公共字段契约保存错误及依据；取消与过期沿用动作自身的原因及实际操作记录。次数必须与已有尝试一致，流程结束不清零次数。允许首次登记尝试时直接建立 `ACTIVE` 流程；没有建立过流程的动作在首次尝试前结束时，不为补齐状态路径而创建流程。

## 转换与共同提交

写入前先核对记录及原事务是否可靠；不可读、矛盾或提交未知进入状态库错误或原事务核实，不能转为业务成功或无效果失败。以下转换使用已经按动作契约判断的取消、过期和启动结果，不用当前墙钟重新推定历史结果。

| 当前流程与业务事实 | 流程及相关事实的变化 |
| --- | --- |
| 尚无流程，需要提前建立准备责任 | 可以建立 `PENDING`，次数为 0，尚未取得录像启动机会；准备占用按自身规则保存 |
| 尚无流程或为 `PENDING`，首次启动条件与候选顺序全部满足 | 建立或转为 `ACTIVE`，与首次尝试、额度和可能效果共同提交，再派发 |
| `PENDING`，准备或执行条件尚未满足且未达到结束条件 | 保持 `PENDING`，不登记启动尝试 |
| `ACTIVE`，调用尚未取得结束结果，包括实际收场 | 保持流程及原尝试责任；独立取得的取消或可靠启动事实按对应分支保存 |
| `ACTIVE`，尝试明确失败、确认未启动且仍允许重试 | 保存实际尝试结果及适用间隔责任，流程保持 `ACTIVE` |
| `ACTIVE`，间隔完成但其他条件仍受阻 | 清除已完成的间隔标记，流程仍为 `ACTIVE`，不增加次数 |
| `ACTIVE`，安全重试、间隔、窗口、预算及设备条件全部满足 | 沿原流程和活动登记新尝试并增加次数，状态保持 `ACTIVE`；提交后派发 |
| `ACTIVE`，启动效果未知且仍在允许的有限核实中 | 保持 `ACTIVE`，核实沿原任务进行，不能仅凭剩余启动次数重发 |
| `ACTIVE`，普通启动资格仍有效且可靠确认录像启动 | 转为 `SUCCEEDED`，清除间隔责任，与启动确认及适用活动事实共同提交 |
| `PENDING` 或 `ACTIVE`，取消已经生效 | 转为 `CANCELED`，清除间隔责任，与动作取消共同提交；实际调用和活动收场独立继续 |
| `PENDING` 或 `ACTIVE`，动作已按业务规则判定过期 | 转为 `EXPIRED`，清除间隔责任，与动作过期共同提交；可能效果及占用不因此消失 |
| `PENDING` 或 `ACTIVE`，已满足确定的最终失败条件 | 转为 `FAILED`，保存原因、清除间隔责任，与适用动作结果共同提交；不把未知效果冒充明确未启动 |
| `ACTIVE`，有限核实已结束且启动效果仍未知 | 转为 `UNCONFIRMED`，保存错误、清除间隔责任，并保存适用动作结果；未知活动及占用继续保留 |
| 流程已为结束状态，后来收到调用结果、设备观察、取消或配置变化 | 流程结果保持；保存新取得的尝试或活动事实，继续必要收场，不重开普通启动 |

已有终态及生效取消按动作契约优先处理。`SUCCEEDED` 表示可靠启动确认，不是命令发送成功；只取得发送确认时，仍按实际保证核实。最后一次允许的启动尝试尚在处理或仍需有限核实时，可以保持 `ACTIVE`，即使累计次数已经达到上限。仅禁止追加启动尝试，不凭次数判定设备没有启动。

录像确认启动后，源文件关联、录制时长、停止及产物处理由各自责任继续，不能让启动流程等待整段录像结束。启动流程的所有结束状态均不可返回 `PENDING` 或 `ACTIVE`；提高预算或迟到的启动确认不复活已结束流程。

## 窗口结束后的流程处理

动作结果遵守[窗口结束与在途启动](../../architecture/scheduling-execution.md#窗口结束与在途启动)。窗口只限制发起调用；原尝试尚待结果或仍在有限核实中时，动作保持未终态，`START` 保持 `ACTIVE`。此时不允许新的启动调用，但原启动责任和机会归属仍然存在，不因当前时间或次数已到上限而从持有者查询中排除。

| 窗口结束后取得的结论 | 动作与启动流程 |
| --- | --- |
| 可靠确认原尝试已经启动，且没有取消或已有终态 | 共同保存确认及 `START → SUCCEEDED`；动作继续拍摄，不直接变为 `SUCCEEDED` |
| 可靠确认没有启动效果，也没有其他待核实启动责任 | 共同保存动作 `EXPIRED`、过期原因、适用 `START → EXPIRED` 及间隔责任结束 |
| 有限核实结束仍不能确定是否启动 | 保存实际未知依据，`START → UNCONFIRMED`，动作 `FAILED` 及 `capture_result_unconfirmed`；活动占用及必要收场独立保留 |
| 取消已经生效或已有终态 | 按原取消或终态处理；新取得的尝试及设备观察不重开启动流程 |

意图提交后可靠确认尚未派发，且派发前检查发现窗口已结束时，保存实际未派发事实及过期结果，不退还已提交次数。恢复只有意图、无法确认发送或效果时，先核实原责任，不将缺少结果当作未派发，也不在窗口外补发。没有既存启动流程时不为保存过期而新建流程。

窗口结束、调用结束与业务结果保存分别处理；单独经过窗口截止不要求写入额外流程状态。相关事实的共同提交、原事务核实及三种历史恢复路径沿用本文规则，历史查询不使用当前时间改变已保存的结果。

## 启动机会的推导与唯一性

首次启动机会与首次尝试共同提交，因此已保存的尝试证明曾取得机会。当前持有者从同一完整状态边界的动作与启动流程共同取得，须同时满足：

- 动作类型为 `camera_record`，`actions.status = RUNNING` 且 `cancel_requested = 0`。
- 该动作的唯一 `START` 流程为 `ACTIVE`，且 `attempts_used > 0`。
- 相关记录满足上文合法组合，设备从动作原 `device_id` 取得。

推导不依赖重试间隔是否结束，也不将剩余额度或当前墙钟作为归属筛选条件。间隔、预算和时间影响后续发令或结束判断；判断形成可靠事实时保存相应状态变化。历史查询在同一 H 恢复动作与流程后应用相同条件，不用本次配置重算历史权利。

同一设备至多有一个这样的持有者。授予入口在同一 `BEGIN IMMEDIATE` 写事务内查询完整的现有归属、设备活动、兼容性和候选顺序，再登记首次尝试。初次派发、重试、恢复及新提交触发的调度均沿用这项检查；已有持有者先恢复，新候选不能因缓存或分页边界遗漏它。发现多个持有者或非法组合按一致性错误处理，不按排序挑一个后继续。

动作、流程及按设备的查询需要索引支持，限定设备和未完成责任，不扫描全部永久历史。跨表的唯一性由事务入口及完整性校验保证；仅有流程责任键唯一，不能证明同一设备没有其他动作持有机会。

## 流程结束、调用收场与设备占用

流程保存普通启动责任的结果，尝试保存调用实际结束情况。可靠设备观察已经证明启动，而原调用仍在收场时，可以共同保存启动确认及流程 `SUCCEEDED`，原尝试继续保持 `RUNNING`。调用结束后保存真实结果；后来的调用错误不覆盖已经成立的启动事实，也不把原尝试伪装成没有错误。

取消或过期结束启动流程时，同样不能提前结束尚在执行的尝试。调度和恢复除未结束流程外，还必须发现已结束流程下未结束的尝试及独立设备活动，沿原身份完成适用收场。流程结束后继续的是原调用或活动处理，不创建新的普通启动尝试。

启动流程不再为 `ACTIVE` 后，普通启动机会随之结束，但相机不一定空闲。是否允许下一动作执行，仍取决于实际调用、设备活动、准备范围占用及兼容性；活动释放必须有所属契约要求的可靠依据。

流程、尝试和活动分别归所属录像动作的历史，相关共同提交使用完整事务边界。首次登记、重试、取消、成功、过期和未知结束均保存实际发生变化的记录；回放只重建状态，不发令、不重新计时、不重新选择候选。提交未知先核实原事务，重启不退还次数。
