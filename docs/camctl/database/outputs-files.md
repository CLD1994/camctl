# 产物、交付与文件记录

[数据库设计入口](../database-schema.md) · [CLI 资料入口](../README.md)

本页定义正式产物、普通交付、产物来源、设备文件、拷贝及主机中间文件的存储职责。文件生命周期的业务规则由架构专题定义，本页规定这些事实如何关联、共同保存及参与历史恢复。

## 正式产物与普通交付

正式产物与交付分别管理。拍摄动作可以登记多份正式产物；一个取回动作可以为多个选中产物创建交付。交付关联的取回动作与产物的来源动作可以属于不同计划。

`deliveries` 保存本次副本准备完成、发布意图、本地交付完成及适用的撤回事实，并关联其稳定文件名、可读名称及完整性依据。准备完成与读取依赖解除一起提交，发布意图在移动前提交，本地交付完成事实在移动及必要目录同步成功后保存，分别遵守[普通交付保存与恢复](../../architecture/file-handoff.md#普通交付的保存顺序与中断恢复)。文件已被主程序取走而结果无法确认时，按原交付身份保存规定的未知原因与最终结果。

交付文件被主程序取走、删除或被 camctl 撤回，不等于正式源产物被清理。正式源产物已经合法清理，也不抹去已形成交付的身份和处理事实。另一个取回动作沿用产物身份并创建属于该动作的交付，同一次取回的恢复继续使用原交付。

正式产物主表只登记满足相应业务条件的产物。修复临时文件、尚未登记的成品和内部原片副本按中间文件规则保存归属与进度，不因存在文件就建立正式产物。取回失败可能发生在创建交付之前，失败项须能够独立于交付记录表达。

## 产物来源关系

`outputs` 统一保存正式业务文件的共同信息。文件内容类型描述视频、图片、文档等内容，产物角色描述原文件、预览和修复成品等业务含义，两者分别表达。各种文件内容类型使用同一产物主表；具体可登记的产物继续由第一版已接入动作及其结果契约决定。

`output_origins` 保存一份正式产物与其来源原产物之间的关联。每条记录表达一项实际存在的来源关系，两个端点均为正式产物。原产物的所属拍摄动作与这里的文件来源关系分别保存：前者回答产物由哪个动作产生，后者回答预览或修复成品对应哪份原文件。

第一版采用[正式产物契约](../../architecture/report-format.md#正式产物)中的三种角色，按下表组织关系：

| 引用来源的产物角色 | 来源关系 | 完整性要求 |
| --- | --- | --- |
| 原文件 `original` | 没有以自身为引用方的来源记录 | 自身可以被预览或修复成品引用 |
| 预览 `preview` | 恰好一条记录，指向对应原文件 | 两端属于同一来源动作；关系由可靠的预览配对事实确定 |
| 修复成品 `repaired` | 恰好一条记录，指向被修复的原文件 | 两端属于同一来源动作；关系由实际修复及成品登记事实确定 |

关系含义由引用方的产物角色解释。查询一份原文件的预览或修复成品时，通过来源关系定位相应产物，再取得其自身状态。两端身份、角色及归属必须一致；预览或修复成品的关系缺失、重复、非法或读取失败，按状态库错误处理，不能解释成该产物无需来源。

预览或修复成品登记时，其产物记录、来源关系及对应历史在同一事务中保存。来源关系是所属产物自身状态的一部分；历史恢复和对象快照包含这项关系。仅引用原文件不表示原文件自身发生状态变化，不因新增引用而增加原文件的历史变化次数。

清理任何一端的实际文件，只按所属规则更新文件可用性和处理结果，产物记录及来源关系永久保留。预览与修复成品各自管理文件生命周期，来源关系不授予对其他产物的清理权限。

其他业务对象通过稳定的产物身份引用产物。类别专属信息、来源关系和共同信息分别由其所属结构维护；公共报告按既定字段契约从这些记录的冻结历史状态生成。

## 设备文件记录

`device_files` 的每条记录表示 camctl 业务涉及的一份设备文件，保存稳定的内部文件身份、所属设备、驱动可解释的定位信息、业务归属及可靠取得的文件事实。记录范围由拍摄、内部处理、取回和清理的实际需要确定，不要求扫描并登记设备存储中的全部文件。尚未可靠确认的归属、写入完成情况、完整大小或摘要保持未确认，不以记录存在代替这些结论。

设备文件可以先于正式产物登记。录像原片已经生成但仍需检查或修复时，内部处理和拷贝引用相应设备文件记录；正式产物登记后，`outputs` 关联原记录，沿用同一文件身份。重启恢复、后续取回及清理继续定位同一份文件，不因新增处理流程而重建文件身份。内部文件身份与设备定位信息分别表达，不能仅凭文件名判断两次观察必然属于同一份文件。

采用[拍摄前后比较](../../architecture/camera-capture.md#本次任务的文件归属)时，启动前的实际目录或编号基准属于动作执行记录，在发送命令前可靠保存；它不属于首次受理的只读执行定义，也不要求将基准中的历史文件全部登记到 `device_files`。实际识别出的本次文件再按本节建立内部身份和关联，重启沿用原基准与已保存事实。

延时摄影的文件完成事实遵守[文件完成依据与产物检查](../../architecture/camera-capture.md#文件完成依据与产物检查)。执行记录须能区分设备完成保证与声明等待假设，并保存实际采用的依据和必要检查结果。单份 `device_files` 记录存在或某份文件已经写完，不代替动作层面的产物集合检查，也不表示媒体内容已经全面验证。

| 记录或处理 | 与设备文件的关系 |
| --- | --- |
| 拍摄动作及录像内部处理 | 保存已经可靠取得的文件归属及关联，在正式产物登记前也能恢复原片检查和修复 |
| `file_copies` | 源文件位于设备时引用 `device_files`，目标主机文件引用 `intermediate_files`；同一设备文件可以被不同处理分别拷贝 |
| `outputs` | 正式登记设备产物时关联既有设备文件；正式产物身份及业务可用性由产物记录表达 |
| 公共读取、删除及存在性查询流程 | 引用实际目标文件，各自保存所属业务的尝试与预算；共用文件身份不合并不同处理的预算 |
| 主机中间文件及主机派生成品 | 继续由相应主机文件与产物记录管理，不作为设备文件重复登记 |

文件记录、正式产物登记和操作资格分别判断：

| 文件事实与登记阶段 | 保存与使用规则 |
| --- | --- |
| 文件身份或归属尚未可靠确认 | 保留已取得的信息和未确认原因；不建立猜测的可靠归属，不据此读取、登记产物或删除未知文件 |
| 身份和归属已确认，但尚未确认写入完成 | 保存已有文件关联及实际写入状态；依赖完整文件的拷贝和产物登记继续等待或按所属有限处理规则结束 |
| 已确认写完，但正式产物尚未登记 | 保存完整文件依据；具备内部处理资格时可以检查或修复，普通取回仍须等待正式产物登记 |
| 正式产物已登记，文件尚未确认清理完成 | 取回和清理通过产物定位设备文件，分别检查读取资格、删除限制及操作进度；关联存在不单独授予操作权限 |
| 按所属规则已确认文件删除 | 保存实际删除事实和相关业务结果，永久保留文件记录及历史，不据此删除产物或处理记录 |
| 必要记录无法可靠读取或保存，或者提交结果未知 | 按状态库错误与提交核实规则处理，不解释为文件不存在、已写完或已删除 |

文件读取沿用[固定源文件与续传规则](../../architecture/file-copy.md#相机视频的断点续传)。同一份固定内容已可靠取得的源端摘要可以按[校验规则](../../architecture/file-copy.md#读取正确性与文件校验)复用；各次拷贝的主机端摘要及比较结果仍由相应拷贝记录保存。文件事实及必要派生表示保持单一来源，不在动作、拷贝和产物中独立维护相互矛盾的副本。

设备文件登记不改变[拍摄结束与产物登记](../../architecture/camera-recording.md#录像动作的结束时点)的事务边界，也不产生额外删除权限。未登记文件按所属拍摄的取消、保留及清理规则处理；正式产物按显式清理规则处理。文件事实影响相关动作、产物或处理结果时，权威历史与相应投影在同一业务事务中保存。

设备文件不成为独立的历史快照对象。相关文件事实按业务归属参与历史恢复；恢复动作、产物或交付时，使用目标历史边界处的文件事实，不以之后取得的大小、摘要或删除结果解释过去的状态。

## 文件拷贝记录

`file_copies` 的每条记录表示所属业务中的一次具体文件拷贝，保存业务归属、源文件与目标中间文件的关联、最新可靠字节进度、重拷轮次及预算、完整性校验状态和依据。普通取回、录像内部原片检查及修复输入拷贝共用这张表，分别遵守所属业务的执行资格和后续处理规则。

| 拷贝用途 | 归属与身份 |
| --- | --- |
| 普通取回的独立副本 | 关联本次取回目标及实际交付；不同请求创建独立副本时，各有自己的拷贝记录 |
| 录像内部原片检查或修复输入 | 归属于原录像的内部处理，不创建普通交付；同一内部副本按规则继续用于检查或修复时沿用原拷贝记录 |

每条拷贝记录关联其读取流程，读取尝试预算和尝试事实由 `operation_runs`、`operation_attempts` 保存。读取重试、分段推进和同一任务的重启恢复沿用原拷贝身份。摘要不一致时按[有限重拷规则](../../architecture/file-copy.md#摘要不一致后的有限重拷)增加轮次并从头拷贝，不建立新拷贝记录来重置预算，也不把重拷轮次当成读取尝试次数。

最新可靠进度保存在 `file_copies`，历次进度和轮次变化保存在不可变历史中。分段保存遵守[先保存文件，再记录进度](../../architecture/file-copy.md#先保存文件再记录进度)：文件及必要目录同步成功后，在同一事务中记录进度历史并更新投影。分段不建立独立业务表，重启从可靠进度及原轮次恢复，不根据中间文件长度直接推进数据库进度。

读取完成、完整性校验完成和交付完成分别表达。`file_copies` 保存拷贝及校验事实；普通交付的准备完成和文件交接由 `deliveries` 保存，并引用同一套拷贝依据。内部拷贝的成功不自动表示录像成功或修复完成，结果继续由所属处理按其契约判断。公共报告中的交付 `copy` 和录像 `source_copy` 按[公共拷贝字段](../../architecture/report-format.md#公共拷贝字段)从对应历史状态生成。

拷贝记录不成为独立的历史快照对象。普通取回的拷贝状态归属相应交付，录像内部拷贝状态归属录像动作；历史恢复和快照按所属对象包含相应信息。实际中间文件的保留、删除及交接权限继续遵守各自生命周期，删除中间文件不删除拷贝记录或历史，也不改写已经确定的业务结果。

## 中间文件记录

`intermediate_files` 的每条记录表示 camctl 为取回、原片检查或内部修复在主机上管理的一份中间文件，保存稳定的文件身份、所属处理、用途、位置关联、保留需要及清理状态。中间文件可以是未完成的副本、完整输入、处理临时文件或等待登记及交接的完整输出；“中间”描述业务阶段，不表示内容不完整或允许随时删除。

`file_copies` 保存复制过程，`intermediate_files` 保存文件的归属与生命周期。拷贝记录关联目标中间文件，修复工具直接生成的中间文件也有自己的文件记录，不要求存在拷贝记录。同一文件的清理状态在中间文件记录中维护，相关报告和业务详情根据其历史状态生成，不另行维护可独立修改的清理结论。

| 文件与所属处理的情况 | 中间文件记录与后续管理 |
| --- | --- |
| 文件仍用于续传、检查、修复，或尚有登记及交接责任 | 保存用途与归属并保留文件；完整文件也可能仍处于这一阶段 |
| 文件已无用途，处理结果或取消决定已可靠保存，相关操作已确认结束 | 按所属业务规则清理，并保存实际结果；查询或删除失败时保留未完成责任 |
| 归属、用途、登记结果或相关操作是否结束无法可靠确认 | 保留文件并核实，不能根据目录、文件年龄或大小判定可以删除 |
| 修复输出已可靠登记为正式产物 | 保留中间文件记录及其与正式产物的关联，结束适用的中间文件清理资格，实际文件由正式产物规则管理 |
| 取回副本已移入 `ready` 或 `processing` | 保留原文件关联和历史，按实际交接位置及所有权处理；不继续按 `staging` 中间文件规则删除 |
| 文件已确认清理完成 | 永久保留数据库记录与历史，不再作为待清理候选，不改写所属业务已有结果 |

中间文件的保留和删除资格分别遵守[取回中间文件](../../architecture/obtaining-outputs.md#取回中间文件的保留与清理)及[录像内部中间文件](../../architecture/camera-recovery.md#内部中间文件的保留与清理)。清理维护从已保存责任中分批查询候选，并遵守[中间文件清理的运行预算](../../architecture/file-handoff.md#中间文件清理的运行预算)，不能通过扫描目录将所有文件作为清理目标。产物登记、交接及清理涉及的状态按各自事务与恢复规则保存，不能以一次路径变更推断责任已经转移。

状态报告的临时文件、日志副本及故障标记分别由所属机制管理，不纳入这张表的清理范围。中间文件记录不成为独立的历史快照对象，其事实按所属录像动作或交付的历史与快照规则保存。
