# 计划与动作字段

[数据库设计入口](../database-schema.md) · [CLI 资料入口](../README.md)

本页定义 `plans` 与 `actions` 的公共字段、输入保存、受理依据和运行状态。动作的只读专属结构见[动作执行定义](execution-definitions.md)，执行中形成的来源、明细及设备事实分别由对应专题定义。

完整列、可空性及行内约束见 [core.sql](schema/core.sql)。两表的历史元数据遵守[公共定义](common.md#对象历史元数据)。`plans` 除下文的身份、输入、状态和三项历史元数据外没有其他列；动作结果从专属记录生成，不再保存一份可以独立修改的完整 `result` JSON。

电机通知的动作编号、SQL 约束及历史记录接入进度见[实施路线图](../../superpowers/plans/2026-09-30-camctl-implementation-roadmap.md#电机控制与主程序通知接入)。下文定义其字段目标语义，运行版本是否已支持该动作以接入和验证记录为准。

整数编号由[统一定义](enum-registry.json)提供，[编号一览](enum-values.md)从该定义生成。本页使用成员名称说明字段含义和处理规则。

## 请求身份与成功受理关联

`plans.request_id` 使用 `INTEGER NOT NULL`，范围为 1～9223372036854775807，并具有唯一约束。公共 JSON 中的请求身份使用规范十进制字符串，主机通过精确整数转换保存和查询。请求 ID 由调用方提供，计划 ID 由 camctl 分配；二者分别表达逻辑请求与已受理计划，不要求数值相同。

`plans` 直接保存请求身份与计划实例的一对一关联，承担按请求查找首次成功受理结果的职责。该关联与计划、全部动作及对应历史一起提交，并在计划结束后永久保留。请求身份作为计划的受理依据保存，不建立独立请求表。

首次受理、幂等复用和拒绝的判定遵守[请求身份规则](../../architecture/plan-acceptance.md#request_id)。同一请求此前被拒绝时，失败事实保存在输入文件诊断中；后续成功受理建立计划及关联，原诊断继续保留。诊断中的请求身份只表示本次输入可靠取得的身份，不能作为成功受理凭据。

同一请求重送时复用原计划，新的有效 ACK 仍按[独立处理规则](../../architecture/plan-acceptance.md#计划正文与-ack-独立处理)保存其实际影响。累计确认和输入诊断分别由所属记录承担，不通过改写原计划内容表达。

## 计划与动作

首次受理成功时，计划和全部动作一起登记；动作可以因为自身参数错误而初始失败。整份输入被拒绝时不登记本次计划和动作，按输入诊断规则保存问题。同一请求重送复用原计划，不新建动作。

动作主表统一表示拍摄、取回、清理、取消、显式报告和电机控制等已支持动作。各类动作的专属状态、逐项结果、执行尝试及恢复责任不因共用主表而合并为同一种流程，其物理组织按相应生命周期确定。

计划状态由动作事实派生，与引起变化的动作事实共同提交。计划完成不表示产物已删除、设备活动已结束、文件已传输或客户端已确认；这些后续责任由所属记录表达。

## 计划与动作的输入存储

计划的固定公共字段使用普通列保存。动作按独立记录保存，字段和值的存在性、精确数值及原数组位置共同支持原计划重建。下表定义身份与输入部分；运行状态见[计划与动作的运行状态](#计划与动作的运行状态)。

| 表与字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `plans.id` | `INTEGER PRIMARY KEY`，正整数 | 计划身份及首次成功受理顺序；按受理写事务分配 |
| `plans.request_id` | `INTEGER NOT NULL UNIQUE`，正整数 | 调用方提供的请求身份，范围与转换遵守[请求身份与成功受理关联](#请求身份与成功受理关联) |
| `plans.name` | `TEXT NOT NULL` | 已通过公共结构校验的计划名称，不要求跨计划唯一 |
| `plans.created_at` | `INTEGER NOT NULL` | 客户端创建计划的 UTC 时间，单位为微秒；合法输入固定到秒，值为整秒对应的微秒数，不证明主机时间可信 |
| `actions.id` | `INTEGER PRIMARY KEY`，正整数 | 动作身份 |
| `actions.plan_id` | `INTEGER NOT NULL`，引用 `plans.id` | 所属计划 |
| `actions.input_index` | `INTEGER NOT NULL`，非负整数 | 动作在首次受理的输入数组中的位置，从 0 开始 |
| `actions.name` | `TEXT NOT NULL` | 已通过公共结构校验的动作名称，在所属计划内精确唯一 |
| `actions.type` | `INTEGER NOT NULL` | 已支持的动作类型，使用固定整数枚举，与公共类型字面量一一对应 |
| `actions.device_id` | 可空 `TEXT` | 通过该字段校验的部署设备标识，例如 `cam0`；设备由动作类型决定是否必填 |
| `actions.scheduled_at` | 可空 `INTEGER` | 调用方指定的计划开始处理时间，保存为 UTC 整数微秒；合法输入固定到秒 |
| `actions.group_name` | 可空 `TEXT` | 动作在所属计划中的有效组名；公共输入和报告使用字段名 `group` |
| `actions.input_fields_json` | `TEXT NOT NULL`，精确 JSON 对象 | 普通列不能完整表达的原始输入，包括可变参数、策略、非法值和额外字段；没有这些内容时为 `{}` |

`actions` 分别对 `(plan_id, input_index)` 和 `(plan_id, name)` 设置唯一约束。名称比较保持输入的大小写与 Unicode 字符，不做归一化。首次受理时，输入位置覆盖从 0 到动作总数减 1 的全部位置；失败动作也占有原位置。原计划重建按该位置组装全部动作，报告实体集合继续按各自 ID 排序，二者不相互替代。

`device_id` 引用部署配置中的设备标识，使用原标识字符串，不是数据库对象的整数主键。拍摄动作必须指定符合契约的设备；取回、清理、取消和报告动作的该列为 SQL `NULL`，其实际设备或文件位置按来源、产物或目标确定。首次受理后更新部署配置不改写已保存的设备标识。

`scheduled_at` 的必填性由动作类型决定：拍摄、取回和清理必须提供；取消和报告可以省略。允许省略且动作通过受理校验时，该列为 SQL `NULL`，执行会话取得资格后立即处理，不填入受理时间作为替代。合法值为整秒对应的 UTC 微秒数，实际日期及格式遵守[时间字面量](../../architecture/plan-input.md#时间字面量)。时间已过只影响执行时的调度判断，不使其成为静态非法输入。

`group_name` 按输入原字符保存，不改变大小写或进行 Unicode 归一化。同一个组由 `(plan_id, group_name)` 确定，多个动作可以具有相同的组归属；这不是动作表的唯一约束。未提供组名或组字段非法时为 SQL `NULL`。有效组归属和其他输入字段分别校验，其他参数失败不抹去合法组归属。

三个普通列同时满足查询及原输入重建要求。原始输入按以下互斥分区保存；同一个原始字段只从指定来源重建。

| 输入分类 | 保存与重建规则 |
| --- | --- |
| 必须合法才能受理的动作名称和类型 | 保存为普通列；类型通过固定枚举与协议字面量的对应关系重建 |
| 提供了设备、时间或组字段，且通过该字段适用的校验 | 保存为有效普通列；字符串保持原字符，时间从整数值按固定秒级格式还原；其他参数错误不抹去合法组归属 |
| 上述字段未提供，且对应动作允许省略或要求省略 | 普通列为 SQL `NULL`，`input_fields_json` 中没有该字段；重建时省略 |
| 上述字段未提供，但对应动作要求必填 | 普通列为 SQL `NULL`，`input_fields_json` 中没有该字段；动作在受理时失败，错误保留字段缺失的原因，重建时仍省略 |
| 提供了上述字段，但其类型、值或适用性非法，包括显式 `null` | 原始字段及其值保存在 `input_fields_json`，有效列不产生虚构值；重建时保留原字段和 JSON 类型 |
| 提供了 `params`、`policy` 或额外字段 | 在 `input_fields_json` 中保留原键和值，包括空对象、数组、精确数值及非法类型；省略的键仍省略 |

读取时校验字段归属、存在性和状态组合；设备、时间或组字段同时出现在普通列的有效表示与原始例外表示中，或者缺少契约要求的依据，按状态库错误处理，不选择其中一份猜测。合法时间不需要额外的原字符串列。输入 JSON 的空白、缩进和数值字面量写法不属于原计划重建契约；结构化值和字段存在性须保持。

调度不能仅凭 `scheduled_at IS NULL` 判定立即执行，必须先确认动作通过受理校验、类型允许省略时间，并满足相应执行资格。受理失败动作的空列不产生执行资格；提供非法值时，原值与失败原因共同解释空列的含义。某一字段非法不清除其他已经通过自身校验的普通列值。

三个字段在首次受理时与动作、原始输入例外及历史共同保存。请求重送、重启和后续配置变化均不改写原值；历史回放还原原列值与原始字段的存在性。数据库约束检查存储类型及适用的范围、状态组合；业务写入和读取流程核对字段适用性、原始输入归属及受理结果。验证覆盖合法值、合法省略、必填缺失、显式 `null`、非法类型或值、动作不允许该字段、其他参数失败但本字段合法，以及原计划重建与恢复的一致性。

生效拍摄参数和用户业务策略按[生效拍摄参数与启动延迟](#生效拍摄参数与启动延迟)保存，原始 `params` 和 `policy` 表达调用方实际提交的内容；拍摄默认值不能反向覆盖原输入。本地执行配置由每次运行加载，后续操作按[本地配置变化与未完成工作](../../architecture/configuration.md#本地配置变化与未完成工作)处理。运行状态、尝试消耗、固定来源及逐项结果由所属普通列、关联表和明细表保存，实际判断采用的必要配置值随对应事实保存。

计划与全部动作的普通列、必要 JSON、有效关联和对应历史在同一受理事务中形成。历史创建事实提供重建这些列和值的依据；当前投影仍可从历史恢复。原计划由计划自身字段和按原位置读取的动作组装，独立 ACK 继续按其确认事实处理。

## 生效拍摄参数与启动延迟

调用方省略驱动允许缺省的拍摄字段时，原始 `params` 保持省略，完整生效参数保存驱动补齐的默认值。执行与恢复使用首次受理保存的生效参数；原计划重建使用原始输入。二者分别表达调用方输入与动作通过受理后确定的拍摄要求。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.effective_params_json` | 可空 `TEXT`，非空时为精确 JSON 对象 | 通过全部受理校验的拍摄动作的完整生效参数，包含 `type` 及按驱动契约补齐的默认值 |
| `actions.max_delay_ms` | 可空 `INTEGER`，非空时为非负整数 | 从通过该动作业务策略校验的 `policy.max_delay_ms` 提取的启动延迟，单位为毫秒 |

生效参数只适用于 `camera_take_photo`、`camera_record` 和 `camera_timelapse`。参数结构由已选驱动及参数类型定义，不拆成各驱动专用列，也不另建参数表。SQL `NULL` 表示没有生效参数；JSON `null`、数组、标量以及缺少必要字段的对象均不能替代完整参数对象。驱动定义无法可靠取得等内部故障按既有会话错误处理，不能登记为调用方参数错误。

`max_delay_ms` 是调度使用的派生列，原始 `policy` 仍完整保存在 `input_fields_json`。原计划与报告的 `policy` 均从原始输入重建，不用普通列补造省略的字段或替换非法输入。只有拍摄或电机动作的整个业务策略通过校验时才提取该值；即使其中的 `max_delay_ms` 本身合法，存在不支持的策略字段等错误时，该列仍为 SQL `NULL`。其他字段导致动作受理失败，不抹去独立通过校验的业务策略值。`0` 表示不允许延迟启动；SQL `NULL` 不代表 `0`，也不提供执行资格。

下表中的受理结果是首次受理时的完整判定，不按动作后续的运行状态重新计算。

| 条件 | `effective_params_json` | `max_delay_ms` |
| --- | --- | --- |
| 整份计划被拒绝 | 不创建动作记录 | 不创建动作记录 |
| 拍摄动作通过全部受理校验 | 保存完整生效参数 | 保存通过校验的值 |
| 拍摄动作的业务策略合法，但其他受理条件不满足 | SQL `NULL`，即使拍摄参数本身合法也不保存生效参数 | 保存通过校验的值 |
| 拍摄动作的业务策略缺失或非法，不论其他字段是否通过校验 | SQL `NULL` | SQL `NULL`；原始输入保持原样 |
| 电机动作的业务策略合法，不论其他字段是否通过校验 | SQL `NULL` | 保存通过校验的值 |
| 电机动作的业务策略缺失或非法 | SQL `NULL` | SQL `NULL`；原始输入保持原样 |
| 其他已支持的非拍摄动作，不论是否通过自身受理校验 | SQL `NULL` | SQL `NULL`；不适用的策略输入按既有规则使动作初始失败 |

合法受理的拍摄动作后来过期、取消或执行失败时，两个字段保持首次保存的值。受理失败动作保留原始输入和错误，报告不提供 `effective_params`；不能因某个拍摄参数局部合法而保存可执行参数。两个字段是否为空须结合动作类型、受理结果和原始业务策略解释，不能仅凭 `status = failed` 判断。

两个字段、原始输入、动作受理结果及对应历史在同一受理事务中保存。`max_delay_ms` 必须与原始合法策略中的值精确一致，二者不能分别修改；它不是第二份可独立调整的业务要求。生效参数与原始参数可以因默认值补齐而不同。请求重送、重试、重启及配置变化不改写这些值；历史回放按创建事实恢复，不调用驱动按新的默认值重新计算。

数据库约束检查类型、范围及适用的空值组合，业务读写核对受理分类与原始策略的一致性。不符合契约的记录按状态库错误处理，不从配置补值或在两个策略值中任选其一。调度计算启动窗口时使用 `actions.max_delay_ms`，先确认动作具有执行资格，再按时间字段单位精确换算。

验证覆盖上述全部分区，以及驱动默认值补齐但原输入不变、其他字段非法但业务策略合法、合法延迟与非法额外策略字段并存、缺失策略、显式 `null`、错误类型、负数和零延迟。还须验证受理后过期、执行前取消、执行后失败、请求重送、默认值变化、重启与历史回放均保持原值；派生列与原始策略不一致、缺少必要生效参数及不适用对象出现生效参数时按状态库错误处理。报告验证覆盖生效参数解码为对象、受理失败省略该字段，以及原始 `policy` 的存在性和值保持不变。

## 拍摄动作的驱动绑定

拍摄动作通过受理校验时，camctl 从目标设备的本地配置中选择驱动，使用该驱动的参数契约确定生效参数。动作同时保存设备标识、驱动标识和生效参数，以便后续执行能够使用原来选定的驱动解释这些参数。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.driver_id` | 可空 `TEXT`，非空时为非空字符串 | 拍摄动作首次通过全部受理校验时选定的驱动标识，与能力说明的 `driver_id` 使用同一标识 |

驱动标识按字符串精确匹配，不是数据库对象的整数主键，也不引用驱动表。标识由驱动注册契约定义，保持稳定，不使用随代码重构变化的 Python 类路径。动作保存驱动选择，不保存整份驱动配置。

| 首次受理结果 | `driver_id` 的保存规则 |
| --- | --- |
| 整份计划被拒绝 | 不创建动作记录 |
| 拍摄动作通过全部受理校验 | 保存实际用于校验和确定生效参数的驱动标识 |
| 拍摄动作在受理时失败，包括已经找到驱动但其他字段非法 | SQL `NULL`；原始输入与受理错误仍按各自契约保存 |
| 已支持的非拍摄动作，不论是否通过自身受理校验 | SQL `NULL`；所需设备及驱动依据从实际来源或目标取得 |

`driver_id` 与 `effective_params_json` 在拍摄动作通过全部受理校验时共同形成，其他动作记录的这两个字段均为 SQL `NULL`。驱动标识、设备标识、生效参数、受理结果及对应历史在同一受理事务中保存。合法受理后的过期、取消、执行失败、请求重送、重试和重启均不改变原驱动标识。读取空字符串、错误类型或不符合受理分类的组合时，按状态库错误处理，不从本地配置补造首次驱动选择。

取回动作可以涉及多台设备，其自身不选择一个统一驱动。设备文件的读取、核实与删除沿实际文件的来源取得原设备及驱动依据；取消涉及的设备操作沿目标动作或所属设备活动取得依据。来源拍摄动作已经终态，不清除后续设备活动、取回及清理仍需使用的绑定事实。

后续运行在发起设备操作前核对原绑定与本次设备配置。判定按下表处理；“继续”仍以所属业务的执行资格与恢复规则成立为前提。

| 处理对象与本次配置 | 绑定处理规则 |
| --- | --- |
| 只回放历史、读取已保存事实或重建报告 | 使用历史中的原标识与参数，不调用旧驱动；这些状态重建过程不要求旧驱动仍安装 |
| 需要设备操作，所需设备配置可用，且绑定驱动与原记录一致 | 使用原生效参数，后续操作采用本次运行的本地执行配置 |
| 需要设备操作，但所需设备配置缺失 | 不发起相关设备操作，明确报告配置问题 |
| 需要设备操作，设备配置存在，但绑定驱动与原记录不同 | 不发起相关设备操作，明确报告绑定不一致；不把原参数交给新驱动，也不改写原驱动标识 |

上述设备配置缺失或驱动绑定不一致使无法执行的动作、处理项或设备收场流程按所属规则失败，不使 `run` 立即结束；其他设备、本地处理和报告维护继续推进。已有终态、取消和过期规则优先，流程失败不证明设备已经停止或文件已经删除。绑定失败原因、业务结果和原设备事实按所属事务共同保存，配置修正或重送不重开已失败任务。完整状态分类、执行标记与退出规则遵守[设备绑定异常的影响范围](../../architecture/configuration.md#设备绑定异常的影响范围)。

驱动标识表达驱动选择，不证明物理相机未被替换，也不记录完整软件版本。部署负责保持设备身份和同一驱动标识下对已有动作的兼容性。第一版不增加驱动版本管理或物理设备替换检测机制。驱动定义或配置本身无法可靠加载的情况，继续遵守既有配置加载错误规则。

验证覆盖首次受理的全部分类、事务提交前后中断、终态后保留、重送与重启不重选驱动，以及历史回放和报告重建不调用驱动。设备操作验证覆盖绑定一致、仅本地通信参数改变、设备配置缺失和驱动绑定不一致；后两者不能产生相关设备操作。跨设备取回、文件清理及取消须逐来源或目标取得绑定，不能使用发起动作的单一驱动代替。

## 计划与动作的运行状态

计划 A 中一个动作已经执行结束，另一个动作仍等待未来时间时，A 仍处于运行阶段。录像动作 B 已经接受取消要求、但停止操作尚未结束时，B 仍在运行，其普通执行资格已经终止。状态、是否曾执行及取消是否生效分别保存，以便重启后恢复这些不同事实。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `plans.status` | `INTEGER NOT NULL`，计划状态枚举 | 由全部所属动作事实派生的计划执行阶段 |
| `actions.status` | `INTEGER NOT NULL`，动作状态枚举 | 动作的执行阶段或最终结果 |
| `actions.execution_started` | `INTEGER NOT NULL`，只允许 0 或 1 | 是否曾可靠保存首次进入 `running` 的事实 |
| `actions.cancel_requested` | `INTEGER NOT NULL`，只允许 0 或 1 | 针对该动作自身执行的取消要求是否已经生效 |

状态字段在程序中使用各自的整数枚举，两个标记使用 `bool`。创建动作时两个标记均为 0；状态由受理校验结果确定。标记一旦成为 1，后续执行、重试及重启均保持为 1。读取非法状态、非 0/1 标记或缺失值按状态库错误处理，不补初始值。

计划状态及其公共表示如下；固定编号见[编号一览](enum-values.md)：

| 枚举成员 | 公共协议值 | 含义 |
| --- | --- | --- |
| `PENDING` | `pending` | 尚无动作开始执行，且仍有动作未结束 |
| `RUNNING` | `running` | 曾有动作开始执行，且仍有动作未结束 |
| `COMPLETED` | `completed` | 全部动作已进入终态 |

计划状态依据同一完整历史边界处的全部所属动作判定，不能只检查报告中的动作子集合或本次进程持有的协程：

| 全部动作已终态 | 是否存在 `execution_started = 1` 的动作 | `plans.status` |
| --- | --- | --- |
| 否 | 否 | `PENDING` |
| 否 | 是 | `RUNNING` |
| 是 | 否或是 | `COMPLETED` |

计划允许保持原状态，或发生 `PENDING → RUNNING`、`PENDING → COMPLETED`、`RUNNING → COMPLETED`。至少一个动作开始执行后，计划不会因暂时没有运行中动作而退回 `PENDING`。全部动作在受理时失败，或全部在执行前取消、过期时，计划也进入 `COMPLETED`。具体成功、失败、过期和取消结果由各动作表达，计划完成后保持终态。

动作状态及其公共表示如下；执行优先级和允许的转换由业务规则决定：

| 枚举成员 | 公共协议值 | 含义 |
| --- | --- | --- |
| `PENDING` | `pending` | 已受理，尚未开始执行 |
| `RUNNING` | `running` | 已开始执行，包括等待条件和必要收场 |
| `SUCCEEDED` | `succeeded` | 动作成功结束 |
| `FAILED` | `failed` | 受理校验失败或执行失败 |
| `EXPIRED` | `expired` | 启动窗口已结束，尚未成功启动，且已可靠排除待核实的启动效果 |
| `CANCELED` | `canceled` | 动作已按取消规则结束 |

`execution_started` 表示 camctl 开始执行该动作，不证明设备命令已经发出或设备已成功开始工作。首次从 `PENDING` 进入 `RUNNING` 时，状态与标记在同一事务中保存，供内部执行、取消和恢复判断使用；公共报告按[字段契约](../../architecture/report-format.md)表达动作状态、错误和结果。`cancel_requested` 只在目标取消事实可靠提交后生效，取消目标明细已经创建或协程已收到取消信号均不能替代它。

下表列出动作状态与两个标记的全部合法组合；未列出的组合不允许保存。错误详情、过期原因、动作类型资格及关联记录还须满足各自业务契约。

| `actions.status` | `execution_started` | `cancel_requested` | 对应事实 |
| --- | --- | --- | --- |
| `PENDING` | 0 | 0 | 尚未开始执行，没有生效的取消要求 |
| `RUNNING` | 1 | 0 | 正常处理或等待执行条件 |
| `RUNNING` | 1 | 1 | 取消已生效，必要收场尚未结束 |
| `SUCCEEDED` | 1 | 0 | 执行成功结束 |
| `FAILED` | 0 | 0 | 首次受理时动作校验失败，失败阶段为 `admission` |
| `FAILED` | 1 | 0 | 开始执行后失败，保留实际错误阶段与原因 |
| `EXPIRED` | 0 或 1 | 0 | 按实际历史保留是否执行过，并保存规定的过期原因 |
| `CANCELED` | 0 或 1 | 1 | 按取消规则结束，保留是否执行过 |

取消 `PENDING` 动作时，在同一事务中将状态改为 `CANCELED`、取消标记改为 1，执行标记保持 0。取消 `RUNNING` 动作时，先将取消标记保存为 1，状态保持 `RUNNING`，停止新的普通执行和普通重试；本次规定的有限收场完成后进入 `CANCELED`。取消生效后，迟到的普通执行结果仍须如实登记设备或文件事实，但不能把动作改判为成功、失败或过期。并发取消与动作结束按写事务内的可靠状态判断，已有终态保持不变。

已终态动作后续受到取消寻址时，保持其状态及两个标记。成功取回仍有交付可以撤回时，由取消明细和交付记录保存处理结果，不将原动作改为执行被取消。目标动作的标记、取消明细中的生效进度和对应历史共同提交；多个取消入口复用目标已有事实和必要收场流程，发起取消动作自身结束不撤销目标的取消标记。完整处理边界见[取消动作](../../architecture/task-cancellation.md)。

状态字段和标记的范围及本表组合由数据库约束保证；状态转换、标记只增不减、计划聚合结果及相关记录的一致性由事务写入流程保证。动作变化、受影响的计划状态和对应历史在同一事务中提交，回滚不留下部分状态。提交结果未知时先核实可靠事实，再按原状态继续；历史回放和快照恢复还原相同的状态与标记，不执行外部操作。

验证覆盖上述合法组合与其余非法组合、状态转换、初始校验失败、执行前取消、运行中取消及终态后的交付撤回。计划聚合覆盖已执行动作全部结束但仍有未来动作、全部未经执行就终态、部分动作终态和完整报告中的动作子集合。事务与恢复验证覆盖状态及标记共同提交、回滚、提交结果未知、取消与结束竞争、迟到结果和发起取消动作自身被取消；新成员不改变既有枚举编号。

## 动作最终错误字段

动作最终错误使用错误码和结构化详情共同表达。例如，启动尝试耗尽时，错误码说明动作结束的原因，详情按该错误的定义说明涉及的设备、尝试次数及相关尝试记录。不同错误需要的详情不同，详情对象的结构由对应错误契约确定。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.error_code` | 可空 `INTEGER`，动作最终错误的固定整数枚举 | camctl 根据业务结束条件确定的最终错误；没有最终错误时为 SQL `NULL` |
| `actions.error_details_json` | 可空 `TEXT`；非空时必须是合法 JSON 对象文本 | 最终错误的说明及关联依据；没有最终错误时为 SQL `NULL` |

两个字段的合法组合如下；有错误时，详情对象还须满足该错误规定的字段、类型和取值要求。

| 最终错误情况 | `error_code` | `error_details_json` |
| --- | --- | --- |
| 没有最终错误 | SQL `NULL` | SQL `NULL` |
| 有最终错误，其契约不要求额外详情，且没有额外详情 | 合法整数错误码 | JSON 对象文本 `{}` |
| 有最终错误，包含具体详情 | 合法整数错误码 | 符合该错误契约的 JSON 对象文本 |

只填写其中一个字段、保存未定义的动作整数错误码，或将详情保存为空字符串、JSON `null`、数组及其他非对象值，均为非法组合。SQL `NULL` 表示没有最终错误，`{}` 表示存在最终错误但没有额外详情，两者不能互换。有必填详情的错误不能用 `{}` 代替缺失的信息。

数据库约束检查错误码的合法范围、两个字段是否同时为空，以及非空详情是否为合法 JSON 对象；业务写入流程检查详情是否满足对应错误契约，并检查与动作状态及关联事实是否一致。错误码、详情、动作结果及对应历史在同一业务事务中提交。历史回放和快照恢复还原相同的错误码及结构化详情，不根据后续尝试结果改写动作终态时的错误。

报告生成从固定错误定义取得公共 `error.code` 和唯一的 `error.stage`，解析详情对象后输出为 `error.details`，不将 JSON 文本作为字符串再次嵌入报告。没有最终错误时，按报告契约省略动作的 `error`。用于查询和调度的业务状态保存在所属普通列或专属记录中；错误详情按契约解释结果和引用依据，不另行维护可独立修改的业务状态副本。驱动原始错误的保存遵守[动作最终错误与驱动错误](operations-devices.md#动作最终错误与驱动错误)。

验证覆盖三个合法分区、仅一个字段为空、非法错误码、无效 JSON、非对象 JSON、必填详情缺失，以及报告生成和历史恢复前后的结构化值一致性。具体错误码、详情成员及其与动作状态的完整对应关系按[动作错误分支](action-errors.md)逐项落实。

## 启动窗口观察与过期原因

camctl 在拍摄动作的允许启动窗口内检查到该动作时，先可靠保存观察时间，再检查设备条件和调度资格。如果设备一直被占用，动作最终可能过期，但仍保留曾在窗口内检查到它的事实。若第一次有效检查时窗口已经结束，且没有此前可靠保存的窗口内观察，则保留未观察到的事实。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.first_window_observed_at` | 可空 `INTEGER`，UTC 整数微秒 | 首次可靠保存的窗口内观察时间；SQL `NULL` 表示没有这项持久化观察事实 |
| `actions.expiration_reason` | 可空 `INTEGER`，过期原因整数枚举 | 动作以 `EXPIRED` 结束的原因；其他动作状态为 SQL `NULL` |

过期原因使用以下成员，公共报告使用对应文本值：

| 枚举成员 | 公共协议值 |
| --- | --- |
| `WINDOW_MISSED` | `window_missed` |
| `WINDOW_EXHAUSTED` | `window_exhausted` |

启动窗口适用于 `camera_take_photo`、`camera_record`、`camera_timelapse` 和 `motor_control`。窗口内观察须满足 `scheduled_at <= trusted_wall_now <= window_end`，其中 `window_end = scheduled_at + max_delay_ms`；比较前按字段单位精确换算。提前加载未来动作不形成观察记录，设备是否空闲也不影响窗口内观察成立。

下表定义字段与动作类型、状态及持久化观察事实的合法组合；其他组合均不允许。有效观察时间必须位于该动作的启动窗口内。

| 动作类别及状态 | `first_window_observed_at` | `expiration_reason` |
| --- | --- | --- |
| 不采用启动窗口的动作，处于其允许的非过期状态 | SQL `NULL` | SQL `NULL` |
| 拍摄动作在受理校验时失败 | SQL `NULL` | SQL `NULL` |
| 合法受理的拍摄动作，尚未过期且没有持久化窗口内观察 | SQL `NULL` | SQL `NULL` |
| 合法受理的拍摄动作，尚未过期且已有持久化窗口内观察 | 原观察时间 | SQL `NULL` |
| 拍摄动作以 `EXPIRED` 结束，没有持久化窗口内观察 | SQL `NULL` | `WINDOW_MISSED` |
| 拍摄动作以 `EXPIRED` 结束，已有持久化窗口内观察 | 原观察时间 | `WINDOW_EXHAUSTED` |

电机动作的上述字段按相同的受理、观察及终态分区保存，其中“启动”表示开始发送通知。发送结果不确定时不进入 `EXPIRED`；具体终态及恢复规则见[电机状态判断](../../architecture/motor-control.md#状态判断与恢复)。

表中的非过期组合仍须满足动作状态机及实际执行事实：成功启动前必须保存窗口内观察，因此成功的拍摄动作具有观察时间；失败或取消的拍摄动作按实际经历保留有值或空值。观察时间不证明已经发出设备命令，也不要求 `execution_started` 必须为 1；`WINDOW_EXHAUSTED` 可以没有任何设备尝试。不采用启动窗口的动作不能进入 `EXPIRED`。窗口内发出的尝试可以在窗口结束后确认成功；调用尚待结果或启动效果尚在有限核实中时，不仅凭当前时间写入过期原因。具体分类见[窗口结束与在途启动](../../architecture/scheduling-execution.md#窗口结束与在途启动)。

创建动作时观察时间为 SQL `NULL`。首次有效观察与对应历史共同提交后，才能进入后续设备条件检查和执行流程；后续观察不覆盖首次时间。动作成功、失败、取消或过期均不清除已经保存的观察时间。重启继续使用原记录；若断电发生在内存观察之后、提交之前，恢复不能依据已经丢失的内存事实补造观察时间。

过期状态与原因在同一业务事务中保存，原因依据该事务所见的可靠观察记录确定。数据库约束检查整数类型、原因合法编号及表中的状态、类型和空值组合；业务写入流程检查时间可信性、窗口边界、首次观察只写一次和允许的状态转换。提交结果未知时按状态库规则核实，不猜测观察是否已经保存。历史回放及快照恢复还原原时间与原因，不根据恢复时的墙钟重新分类。

报告按整数枚举对应关系输出 `expiration_reason`，非过期动作省略该字段。观察时间用于内部调度、恢复和诊断，公共报告继续遵守[计划与动作的报告规则](../../architecture/report-format.md#计划与动作)。过期判定与已经成功启动的动作后续处理遵守[公共过期规则](../../architecture/scheduling-execution.md#过期原因)。

验证覆盖全部合法组合和其余非法组合、窗口起点及终点、提前加载、设备被占用但已观察、没有设备尝试就耗尽窗口、成功或取消后保留观察时间，以及首次观察提交前后中断和重启后的分类一致性。

## 动作组归属

动作的有效组归属直接保存在 `actions.group_name` 中。组由 `actions.plan_id` 和 `actions.group_name` 共同确定，成员通过动作记录查询；组作为计划内的组织名称管理，其存储由动作主表承担。公共 JSON 中仍使用 `group`，省略时数据库列为 SQL `NULL`。

组归属与首次受理的动作一起保存，判定遵守[动作组规则](../../architecture/plan-acceptance.md#group)。原始输入与有效归属分别表达：非法组值保留在输入和诊断中，不产生有效归属；合法组归属不因动作的其他参数错误而消失。取回动作的来源组引用属于其操作参数，不是该动作的所属组。

按组取回、取消和报告组织分别应用各自的成员选择规则。已固定的执行来源集合及逐项处理结果由所属流程保存，不能仅凭动作上的组归属替代这些执行记录。

## 动作类型与受理分类

`actions.type` 的整数成员及编号见[编号一览](enum-values.md)，与公共动作类型的对应关系由[报告字段依赖](report-dependencies.json)中的动作类型映射定义。类型不表达执行顺序；未知类型在计划首次受理时按公共规则拒绝整份输入。

`execution_spec_json IS NULL` 唯一表示受理失败，必须同时满足 `status = FAILED`、`execution_started = 0` 和最终错误阶段为 `admission`。合法受理的动作始终保留非空执行定义，即使其后来失败、取消或过期。业务接口据此检查受理分类，不新增冗余的受理状态列。

## 来源解析与目标集合

`source_resolution_state` 表示取回或范围清理的产物来源动作是否已确定。`resolved_source_plan_id` 保存成功解析出的来源计划，即使该计划内没有任何符合条件的拍摄来源，也保留这个真实计划身份。原始引用仍由输入字段保存，不能用来源计划 ID 改写请求。

| 动作分类及事实 | `source_resolution_state` | `resolved_source_plan_id` |
| --- | --- | --- |
| 受理失败、精确 ID 清理或不使用产物来源的动作 | SQL `NULL` | SQL `NULL` |
| 合法取回或范围清理，尚未到解析时点 | `PENDING` | SQL `NULL` |
| 完整来源成员已可靠固定，包括有效空集合 | `FIXED` | 已确认的来源计划 ID，必须有值 |
| 执行时确认来源引用无效，动作以对应错误失败 | `FAILED` | SQL `NULL` |

只允许 `PENDING → FIXED` 或 `PENDING → FAILED`。受理时解析的合法本计划引用直接创建为 `FIXED`；其他字段导致受理失败时不建立执行来源集合。`FIXED` 与完整 `action_dependencies` 集合共同提交，之后保持不变。查询错误不进入 `FAILED`，而是状态库错误；不能将部分查询结果保存为完整集合。公共报告中 `PENDING`、`FAILED` 均表示 `source.status = unresolved`，`FAILED` 的实际失败由动作错误表达，不扩展公共枚举。

`target_selection_state` 表示清理或取消的完整目标集合是否已经固定，使用 `PENDING`、`FIXED`、`FAILED`，但与产物来源解析是独立阶段。

| 动作分类及事实 | `target_selection_state` | 成员及结果 |
| --- | --- | --- |
| 受理失败或不是清理、取消动作 | SQL `NULL` | 不创建目标处理项 |
| 已受理，尚未取得完整目标或仍在等待来源结束 | `PENDING` | 不允许根据部分集合执行删除或目标取消 |
| 完整目标已保存 | `FIXED` | 与全部 `cleanup_items` 或 `cancel_items` 一起提交；有效空集合按业务规则结束 |
| 完整解析确认失败，或取消集合包含自身 | `FAILED` | 保存动作失败，未向任何候选目标施加取消或删除 |

精确 ID 清理在执行开始时将输入 ID 固定为请求明细，后续逐项核实真实产物；因此某项不存在不把集合状态改为 `FAILED`。范围清理须先固定来源，再等待全部来源及产物处理结束，最后固定文件集合。取消先解析直接目标及自动预览候选并检查自身目标，再固定适用集合；逐目标拒绝、失败或被取消不重选集合。取消动作在集合固定前被另一个取消动作取消时，保留 `PENDING`，终态解释为什么没有继续解析。

## 等待原因的保存与报告

各类条件的事实归属、状态转换、事务和恢复规则统一见[等待条件与执行责任](waiting.md#等待条件的事实归属)。动作表保存公共执行资格、取消与终态；来源选择、资源归属和重试责任由各自业务记录承担。

报告选择需要的业务事实时，所有关联对象均恢复到同一完整历史边界 H；不能读取当前来源、读取者或设备占用补算过去，也不能补造当时没有保存的调度观察。公开内容与字段含义由[报告契约](../../architecture/report-format.md)定义，历史生成验证见[历史与报告验收](consistency-verification.md#独立历史与报告重建)，客户端接入见[适配计划](../../superpowers/plans/2026-09-30-report-client-adaptation.md)。SQL、事件与检查脚本的同步进度见[结构与检查边界](schema/README.md#结构同步状态)。

## 写入与查询接口

首次受理入口在一个写事务中查重请求、分配计划及动作 ID、登记所有初始事实和可确定的关系、处理 ACK 与输入诊断。动作状态更新入口检查原状态、取消标记、事件身份和完整专属结果，派生计划状态并一起提交。来源及目标集合接口接受完整的解析结果，在事务中再次核对所属动作资格；回滚不能留下部分成员。

`latest_plan_id` 使用 `coalesce(max(id), 0)`，增量读取使用 `id > :last_id ORDER BY id LIMIT :limit`。计划的成员及组成员分别使用 `actions_plan_members`、`actions_group_members`；待执行查询使用 `actions_schedule`，单设备候选使用 `actions_device_active`。立即执行的合法取消、报告与定时动作分两路查询后按调度规则合并，不能把非法动作的空时间当成立即执行。

原数组位置连续性、枚举与公共协议覆盖、受理错误阶段、JSON 内部结构、首次观察所在窗口、来源成员类型、集合完整性、等待详情及计划聚合由业务写入和读取校验保证。SQLite 负责 SQL 中能够表达的范围、引用、唯一性和行内组合。时间窗口乘加先检查整数范围，不能让 SQLite 溢出后转成浮点数参与调度。
