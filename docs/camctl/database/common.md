# 公共存储规则

[数据库设计入口](../database-schema.md) · [CLI 资料入口](../README.md)

本页定义各表共用的身份、时间、空值、枚举、存储分工和事务原则。具体表在这些公共规则之上定义字段与约束；字段设计的完整性按文末的交付要求检查。

## 结构定义与校验边界

格式 1 的目标语义、字段责任、状态转换及跨记录不变量由所属专题定义，SQL 应完整落实其类型、空值、外键、唯一性和索引要求。结构文件和检查脚本的完成状态见[结构与检查边界](schema/README.md#结构同步状态)。目标契约尚未同步到 SQL 的部分不得按旧结构实施，结构检查也不代替生产持久化层验证。

表采用 `STRICT` 模式。每个连接在事务开始前启用并核验 `PRAGMA foreign_keys = ON`；外键使用 `NO ACTION` 和 `DEFERRABLE INITIALLY DEFERRED`，允许历史、投影及相互引用的处理记录在一个事务内按方便的顺序插入，提交时必须全部存在。日常业务不删除数据库记录，不使用级联删除。结构初始化不使用 `IF NOT EXISTS` 掩盖残缺结构。

SQLite 会对能够无损转换的输入进行类型转换，因此 `STRICT` 不能替代 Python 入口的精确类型校验。写入前拒绝布尔值冒充整数、非法枚举、超范围整数及不合法 JSON；JSON 内的精确数值由应用校验，SQL 中的 JSON 检查只检查语法和外层形状。`CHECK` 遇到 SQL `NULL` 不一定失败，必须用显式 `IS NULL` / `IS NOT NULL` 表达必填组合。依据见 [STRICT 表](https://www.sqlite.org/stricttables.html)、[外键](https://www.sqlite.org/foreignkeys.html)和 [CHECK 约束](https://www.sqlite.org/lang_createtable.html#check_constraints)。

普通 ID 在持有写事务时由所属表的最大 ID 加 1 分配；空表从 1 开始。调用方不得省略主键、写入 `NULL` 或依赖 SQLite 在整数耗尽后的分配行为。所有计数、序号和乘加运算先用 Python 整数检查上限，再绑定参数；整批所需编号不足时整次事务失败，不写入部分结果。文件记录 ID 同时表达稳定登记顺序，不复用已提交编号。

所有未声明 `DEFAULT` 的列由创建契约显式赋值。可空引用表示尚未建立或不适用；必须结合所属状态表解释。没有对应事实时不能预先创建一条看似成功的处理记录。查询接口分别返回存在、可靠不存在或错误，不用空集合吞掉数据库错误。

## 对象历史元数据

`plans`、`actions`、`outputs`、`deliveries`、`device_files`、`intermediate_files` 统一保存三个非空字段：`created_event_id` 引用创建事件，`last_event_id` 引用最后改变自身状态的事件，`change_count` 保存累计变化次数。创建计 1；一条事件改变同一对象多个字段或多个所属子表记录，仍只计 1。仅引用对象、补齐报告父对象或改变其独立子实体，不增加父对象计数。

这些列与 `entity_event_links`、`entity_snapshot_progress` 均由同一事件处理器派生，不能作为独立业务输入。创建事件的正文不递归包含自身的元数据；回放根据事件位置及归属恢复这些列。其他表是否需要创建或结果事件引用按各自职责确定，不机械增加三列。

报告的创建及最近变化事件、输入诊断的创建事件也从各自历史派生；业务上的调用结果、交接意图、同步开始及结束引用则直接保存前后值。完整分类、逐字段目标及逆向恢复规则见[事件引用与事务边界的编码](history-formats.md#事件引用与事务边界的编码)，不能仅按列名判断是否省略正文。

## 结构化事实与错误

名称以 `_json` 结尾的列存 UTF-8 JSON 文本。原输入和生效参数保留精确结构；驱动定位、观察和工具结果采用相应驱动或工具适配器声明的结构。业务写入接口先将外部结果转换成具有明确保证范围的记录，再保存。JSON 不是绕过字段契约的任意字典。

`error_json`、`last_error_json`、`withdrawal_error_json`、`verification_error_json`、`repair_error_json` 和 `discard_error_json` 使用公共报告的 `error` 结构：`code`、`stage`、`details` 必填。它们保存单次操作或专属处理的错误，允许驱动原始标识保持开放；没有错误时为 SQL `NULL`。动作最终错误及取回、清理、取消的封闭业务分类使用各自整数枚举，不能将开放驱动标识强行转换为某个未知整数。

单份观察可能包含多个媒体问题，采用公共 `media` 结构保存；完整性、实测时长及实际问题遵守公共 Schema。观察是一次完整结果，更新时在事件中保存前后值，不在其中积累尝试、文件或变化历史。可增长的集合仍由关系表或不可变事件分页表达。

## 按职责组织业务投影

当前投影按业务职责分表。每张表集中表达一种实体、关系或处理责任；相关业务通过明确的持久化接口读取和更新，不直接修改其他模块的内部状态。

历史事件使用统一的 `history_events` 表，公共信息使用固定列，各类事件的业务事实与必要恢复信息使用有明确格式的 JSON 正文。`history_transactions` 保存事件的完整提交分组。当前投影、历史查询目录和快照均遵守其从权威历史派生的规则。

## 主键与身份引用

所有表统一使用名为 `id` 的单列整数主键，采用 SQLite 的 `INTEGER PRIMARY KEY`。该类型支持 64 位有符号整数，最大值为 `9223372036854775807`（`2⁶³ − 1`），见 [SQLite 整数主键](https://www.sqlite.org/lang_createtable.html#rowid)。各表按自身业务契约确定合法值与分配规则；主键的存储类型不代替字段的业务范围约束。

业务对象的身份就是所属表的 `id`。规格和公共协议中的身份名称用于说明所引用的对象，不要求主表使用同名字段，也不另行建立一套业务身份与主键之间的映射。

| 语义名称 | 数据库中的身份 |
| --- | --- |
| `plan_instance_id` | `plans.id` |
| `action_instance_id` | `actions.id` |
| `output_id` | `outputs.id` |
| `delivery_id` | `deliveries.id` |
| `diagnostic_id` | `plan_file_diagnostics.id` |
| `report_id` | `reports.id` |
| 历史事件位置 `event_seq` | `history_events.id` |
| 历史事务标识 `transaction_id` | `history_transactions.id`，在事务表内从 1 独立递增 |

表之间通过整数值引用目标表的 `id`，引用字段的名称表达所属关系或目标角色。主键在所属表内唯一；跨对象类型的历史关联同时保存对象类型和对象 ID，不能仅凭整数相等判断两个对象相同。业务对象在重启恢复和历史重建中沿用原身份。

关联表、明细表、快照表和单份状态表同样具有 `id` 主键。具有业务唯一性的字段组合另设唯一约束。例如，来源成员关系仍须保证同一所属动作与同一来源动作不重复；对象事件关联仍须保证同一对象与同一事件只关联一次。单份状态表还须保证只有一条规定的记录，其固定主键值由表定义确定。

历史事件以 `id` 保存事件序号，历史事务以独立递增的 `id` 标识分组，并以 `first_event_id`、`last_event_id` 引用首尾事件；`plans.id` 同时承担计划身份与受理顺序，分配和读取遵守[新计划受理序列](../../architecture/protocol-session.md#新计划受理序列)；`change_seq` 表达业务报告覆盖范围。数据库对象身份在公共 JSON 中使用同一整数的规范十进制字符串，范围为 1～9223372036854775807；计划、动作、产物、交付、诊断和报告及其引用均遵守这一表示。字符串编码规则由[对象 ID](../../architecture/plan-input.md#对象-id)定义。对象按 ID 排序时使用其精确整数值；报告实体集合、相应分页和快照候选的 ID 比较遵守同一规则。水位、计数及独立序号遵守各自数值契约。

## 日期时间的存储

用于保存日期时间的数据库普通列统一使用 SQLite `INTEGER`，值为自 `1970-01-01 00:00:00 UTC` 起经过的整数微秒数。起点之前使用负数，起点本身为 0；每个时间字段的定义明确标注 UTC 和微秒单位。存储使用 64 位有符号整数，合法日期及业务范围继续由所属字段契约决定。

| 内部 UTC 时间示意 | 数据库整数值 | 含义 |
| --- | --- | --- |
| `1969-12-31 23:59:59.999999` | `-1` | 起点之前一微秒 |
| `1970-01-01 00:00:00` | `0` | 时间戳起点，是一个确定的时间 |
| `1970-01-01 00:00:01.250000` | `1250000` | 起点之后一秒又二十五万微秒 |

输入解析、数据库写入、读取、历史恢复及输出转换保持整数微秒的精确值，不经过浮点秒数，不将不合法的日期或超出允许精度的输入舍入为合法时间。公开时间字段继续遵守[UTC 时间字面量](../../architecture/plan-input.md#时间字面量)，包括年份范围和固定到秒的格式；其全部合法时间均可用此整数表示。

合法公共时间采用唯一的秒级格式，在数据库中保存为对应整数微秒；报告和原计划重建从整数值还原相同字符串。字段省略、显式空值和非法输入继续按原始输入规则区分保存；错误输入不生成虚构的有效时间。实际运行观测的时间仍可以具有微秒精度，不能因为公共计划时间固定到秒而截断内部事实。事件和快照 JSON 中各项内容的表示由其格式契约定义，恢复到时间列后须得到相同整数微秒值。

0 和负数具有真实时间含义，不能用作尚未发生、未知或不适用的占位值；具体可空性及状态组合由各表字段定义。日期时间值与其可信性分别表达，保存了整数时间不表示启动墙钟检查已经通过。历史顺序仍由事件 ID 确定，不以时间戳代替。

本节适用于日期时间，不改变时长、超时和重试间隔各自的单位。会话内经过时长继续使用单调钟；单调钟读数不是 UTC 日期时间，不能写入这些时间列或用于跨会话相减。精确转换与验证要求见[日期时间的精确适配](../data-types.md#日期时间的精确适配)。

## 空值与状态组合

数据库字段没有具体值时使用 SQL `NULL`。每个可空字段必须定义空值的准确含义；没有值的原因由该字段的固定语义或记录中的明确状态解释。不同原因会导致不同处理时，读取和写入同时判断状态与字段值，不能仅凭 `NULL` 选择业务分支。

优先复用记录已有的业务状态。只有实际存在需要区分的情况、且已有字段不足以表达时，才增加专门的状态字段。例如，尚未取得文件摘要与已经确认无法取得摘要，都没有摘要值，但后续处理不同，需要由相应处理状态区分；取得成功时必须保存完整合法摘要。具体状态值及原因字段由所属业务契约确定。

各表按有效业务状态，将每个字段划分为必须有值、可以没有值或必须没有值，并定义合法组合：

| 记录状态对字段的要求 | 字段实际内容 | 处理 |
| --- | --- | --- |
| 必须有值 | 满足类型、范围及业务约束的具体值 | 组合合法，按该值处理 |
| 必须有值 | `NULL` | 组合非法，不能将状态解释为尚未完成来绕过错误 |
| 可以没有值 | 合法具体值或 `NULL` | 按该字段分别定义的有值与空值含义处理 |
| 必须没有值 | `NULL` | 组合合法，按该状态规定的不适用或未形成事实处理 |
| 必须没有值 | 任意具体值 | 组合非法，不保留与状态矛盾的值 |
| 必须或可以有值 | 不符合该字段约束的具体值 | 组合非法，不转换为 `NULL` 或默认值 |

状态和值的变化按所属业务事务一起保存。数据库约束与事务写入流程共同保证合法组合；各表明确哪些不变量由数据库约束检查、哪些由业务写入流程检查。读取到矛盾组合、无法解释的业务状态或无效记录时，按状态库错误处理，不能自行补值或猜测业务结果。

0、空字符串及虚构时间不能替代缺失值；字段允许这些值时，它们表达自身的实际含义。例如，文件大小为 0 表示已取得大小为零的事实，时间值为 0 表示 UTC 时间戳起点。初始化或其他业务默认值只能用于契约明确规定的创建场景，不能掩盖后续记录缺失、非法或读取失败。

查询可靠确认记录不存在、记录存在但字段为 `NULL`、记录无效和数据库查询失败，分别按所属接口的结果或错误契约表达。查询失败不能返回 `NULL` 或空集合，使调用方误判为数据尚未形成；必要单份状态记录不存在时继续按状态库错误处理。

原始 JSON 中字段省略、显式 `null` 和具体值保持原有区别，不能直接合并到一个可空列中而丢失输入事实。事件与快照按各自格式保存重建所需的存在性、状态和值；历史回放恢复原组合，不采用本次运行的默认值补齐。具体 JSON 适配见[输入类型与精确编码](../data-types.md)。

## 状态与类型的整数枚举

状态、动作类型、事件类型、对象类型及其他取值有限的内部业务标识，在数据库普通列中使用 `INTEGER` 保存，程序使用 Python 标准库 `IntEnum` 表达对应含义。持久化层在枚举成员与整数值之间转换，业务逻辑使用所属枚举类型。现有能力见 [Python IntEnum](https://docs.python.org/3.11/library/enum.html#enum.IntEnum)，转换适配见[整数枚举与协议边界](../data-types.md#整数枚举与协议边界)。

内部状态及类型的固定编号以[整数编号定义](enum-registry.json)为机器可读来源。这份 JSON 文件逐项列出字段、成员名称及固定编号；“登记”表示将这些对应关系集中写入该文件，供其他部分读取和检查。所属表和事件契约解释各成员的行为，[编号一览](enum-values.md)从权威文件生成，便于阅读和核对。责任模块从定义生成或加载对应 `IntEnum`，不独立分配另一套编号。写入过持久化数据的数值与含义保持稳定，不按成员声明顺序、列表位置或自动编号推导存储值；增加成员不改变已有编号，不将已有编号重新用于其他含义。编号的大小不自动表示业务阶段或执行优先级。

公共协议的字段类型和字面量由根 `protocol` 维护。公共状态和类型的文本表示与内部整数枚举通过明确对应关系转换；公共合法值从协议读取或生成，内部整数编号在一处维护，并核对两者覆盖关系。数据库约束所需的合法编号集合从该定义生成或校验，不在 SQL、业务代码和测试中各自维护完整清单。内部专属枚举同样遵守集中登记规则；普通布尔列仍按其 0/1 契约处理。

登记采用以下结构，字段名称和合法组合属于格式契约：

| 登记位置 | 结构及含义 |
| --- | --- |
| 根对象 | `format_version` 为 1，`description` 为说明文本；其余成员按下列分类组织，不允许未定义成员。此格式版本不代替数据库或事件版本 |
| `enums` 的每个键 | 使用 `表名.列名` 定位普通整数列；值包含 `contract` 和 `members`，前者指向解释行为的正式章节 |
| `json_enums` 的每个键 | 使用 `表名.JSON列名.成员名` 定位框架定义的 JSON 整数分类；值同样包含 `contract` 和 `members`。JSON 中保存对应整数，成员名称只用于程序和文档表达含义；驱动自行定义的观察正文不在此分配编号 |
| `members` | 将唯一的大写成员名称映射到固定正整数；同一组编号不重复，不同组可使用相同整数；JSON 数值必须是整数，布尔值不是编号 |
| `boolean_columns` | 列出普通布尔列，0 表示否、1 表示是；它们不建立业务状态枚举。可空布尔列仍按所属契约区分未知或不适用 |
| `sources` | 以相对本文件的路径指定 `public_errors` 和 `events` 的权威文件，不复制其编号 |
| `external_columns` | 以 `表名.列名` 指定编号来源。`public_errors` 按 `key` 读取动作或明细错误编号；`events`、`event_versions` 分别读取事件类型和版本；`history_objects` 读取本文件的对象定义，可用 `qualification` 限定为 `report_target` 或 `snapshot` |
| `history_objects` | 按[历史对象规则](history-formats.md#对象目录与归属)定义标识、编号、主表及报告和快照资格；不同目录使用各自的资格子集 |
| `fixed_columns` | 以 `表名.列名` 指定固定的 `value` 和说明其含义的 `contract`，用于单份记录身份及格式版本；不作为可转换的业务状态。事件版本仍从事件定义取得 |
| 字段可空、状态转换和跨表约束 | 由所属正式字段及事件契约定义；空值不登记为枚举成员，编号大小不表达转换顺序 |
| 公共错误登记的 `action_error_id` | 定义该公共错误在 `actions.error_code` 中的固定编号 |
| 公共错误登记的 `item_error_ids` | 以明细表名为键、该表 `error_code` 的固定正整数为值；同一表的编号唯一。同一公共错误可以在不同明细表中具有不同编号 |

动作与逐项业务错误的编号、公共码、阶段及详情共用[公共错误登记](../../../protocol/errors/workflow-codes.json)，不在内部枚举登记复制错误成员。逐项错误的内部成员名称为公共码的大写形式，阶段及详情直接使用同一公共条目；未包含某明细表键的错误不属于该表的合法错误集合。操作尝试的开放驱动错误继续使用原结构，不加入这套封闭编号。

表、列和成员须与所属正式规格对应；同一普通列只能属于一种编号分类。读取 JSON 文件时拒绝重复键，不能让后一个同名成员覆盖前一个。新增有限值整数列时，必须同时声明其编号来源；既有编号定义指向不存在的表或列也属于错误。业务章节使用成员名称解释行为，完整编号表从权威定义生成；不能按正文排列顺序推导编号。事件分支的前后值、状态转换两端及报告映射只能引用所属字段的合法值，不能因编号恰好相等而跨字段解释。

SQL 合法编号集合、程序枚举与定义进行完整双向核对，既不能缺项，也不能额外接受未定义值。检查分为两层：先核对每列允许的编号及空值，再用真实表的完整记录验证字段组合；一个编号合法不表示带有该编号的任意记录都合法。框架 JSON 中的整数分类由应用校验，SQL 的 JSON 外层检查不能证明内部成员正确。协议字段只有在明确需要公开时才建立转换，不因内部增加成员而自动扩大公开字段。

设计检查使用[现有结构检查脚本](../../../scripts/check-database-spec.py)：读取实际建表定义中的列约束，在 SQLite 中逐值验证其接受集合，并继续执行完整表的状态组合样本。每个有限值整数列都须有对应分类；新增或遗漏分类、编号不一致及生成的编号一览不一致均使检查失败。程序枚举、输入类型校验、完整 JSON 校验和持久化往返属于生产验证，按[整数编号与字段约束验收](consistency-verification.md#整数编号与字段约束)检查；进度由[模块计划](../../superpowers/plans/2026-09-30-camctl-implementation-roadmap.md#模块计划与任务入口)跟踪。

动作最终错误的 `actions.error_code` 使用可空 `INTEGER` 列，程序使用具有固定编号的整数枚举。没有最终错误时为 `NULL`；公共报告通过对应关系输出协议错误码。具体成员、编号及与动作状态的组合在错误字段契约中定义。

每个动作最终错误码的定义同时确定唯一的业务阶段。报告生成通过错误码定义取得 `error.stage`，动作投影保存错误码及相应详情；阶段不由写入调用方自由填写。编号、公共错误码和阶段的对应关系保持稳定，历史恢复及旧报告重建使用相同含义。这一对应关系由[公共错误登记](../../../protocol/errors/workflow-codes.json)的 `action_error_id` 定义；错误及驱动适配的核对范围见[动作错误分支](action-errors.md)。本规则适用于动作最终错误，不自动扩展到操作尝试、文件诊断或会话错误。

| 保存或读取情况 | 处理规则 |
| --- | --- |
| 写入合法枚举成员 | 保存该枚举成员固定的整数值，同时保证状态与其他字段的组合合法 |
| 读取所属枚举已定义的整数 | 转换为对应枚举成员，由业务逻辑解释 |
| 读取未定义整数、错误存储类型或无法解释的内部业务标识 | 按状态库错误处理，不替换为初始状态、未知状态或 `NULL` |
| 字段允许 `NULL`，且与记录状态组合合法 | 按字段空值契约处理，不将 `NULL` 隐式转换为某个枚举成员 |
| 读取原始输入或协议明确允许开放值的内容 | 按该内容的协议保留合法值或错误证据，不强制纳入封闭枚举 |

该规则不改变原始输入和公共 JSON 的表示。原始输入、驱动参数及开放的外部错误码继续按各自契约保存；有限枚举不能成为丢弃外部未知值或改写非法输入的理由。事件和快照中的枚举表示按其格式契约定义，重建时恢复同一含义与稳定编号。

## 普通列、子表与 JSON 的分工

先根据数据的用途和生命周期确定存储位置，再选择字段表示。多个条件同时成立时，以独立查询、逐项更新及关系约束的需要决定是否建立子表；该记录内部的复杂内容仍可使用 JSON。

| 数据用途与变化方式 | 保存方式 | 设计要求 |
| --- | --- | --- |
| 用于身份定位、所属关系、状态判断、排序或候选查询 | 普通列，并按实际查询设置约束和索引 | 直接表达查询条件与关系，明确空值和合法范围 |
| 同一对象包含可增长的记录集合，且需要独立定位、逐项更新或分页查询 | 具有明确父对象关联的子表 | 为成员确定稳定身份；有业务顺序时明确保存或计算顺序的依据 |
| 动作首次受理时确定、之后只读的小型专属执行定义，按动作整体读取，不承担公共查询条件 | 动作的专属执行定义 JSON | 按动作类型定义明确结构；由所属动作处理模块解释，与受理事实共同保存 |
| 内容形状随动作或事件类型变化，通常随所属记录整体解释 | 有明确格式的 JSON 字段 | 定义字段、类型、存在性及解释规则；保存和读取均遵守精确数字契约 |
| 同时包含查询条件和复杂内容 | 普通列与 JSON 配合 | 明确每项信息的来源；额外查询表示只能按规定派生，不能独立修改 |

动作所属计划、设备、执行时间及状态使用适合查询的列。拍摄参数采用有明确类型的 JSON。启动尝试、来源成员、逐产物选择、取消目标及中间文件责任，按各自的身份和生命周期设计关联记录。

JSON 内部同样有字段契约。字段不存在、显式空值、未知和未完成分别按所属业务规则表达；解析成功不等于内容有效。序列化、校验和读取遵守[精确数字与类型适配](../data-types.md)。

## 数据归属与原子更新

物理子表不自动成为独立的历史快照对象。例如，动作的尝试记录可以使用子表，但仍属于动作自身状态；动作的历史恢复与快照须包含相应尝试信息。计划、动作、正式产物和普通交付的快照范围遵守[对象范围](../history-snapshots.md#历史快照的对象范围)。

同一字段的权威历史、当前投影和必要查询表示具有明确的派生关系。事务写入流程统一形成事件并更新受影响投影和目录；其他模块不能分别修改这些表示。历史回放使用同一事实解释规则重建投影，不执行外部操作。

跨表原子性由业务契约决定。例如，录像终态与正式产物登记由同一个业务操作提交；动作与产物分别存表时，这些记录仍在同一 SQLite 事务中保存。分模块和分表不拆分必须共同提交的事实。

数据库表示与公共报告表示分别承担执行恢复和客户端同步职责。报告根据冻结历史和公共协议生成；数据库记录还包含执行意图、尝试预算、可靠进度等内部依据，不能直接将整份投影作为报告输出。

## 表设计的交付要求

每张表的定义包括：

- 记录表达的事实或派生状态、所属业务对象及生命周期。
- 字段名、存储类型、可空性、合法范围，以及缺省或空值的准确含义。
- 枚举字段的成员含义、固定整数编号、权威定义及适用的公共协议对应关系；遵守[状态与类型的整数枚举](#状态与类型的整数枚举)。
- 各有效业务状态下，字段必须有值、可以没有值或必须没有值的组合，以及非法组合的写入与读取处理；遵守[空值与状态组合](#空值与状态组合)。
- 主键、外键、唯一约束和必要索引。
- 创建与更新入口、共同提交的记录，以及提交失败或结果未知时的处理依据。
- 正常查询、重启恢复和历史读取所需的查询方式。
- 由数据库约束保证的不变量，以及必须由事务写入流程保证的不变量。

索引由实际查询推导，通过 SQL 执行计划和软件集成测试验证。表结构验证须同时检查初始化、完整提交、回滚、并发写入和历史重建；仅能成功建表不代表业务契约已经闭合。
