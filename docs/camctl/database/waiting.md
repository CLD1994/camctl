# 等待条件、执行责任与事务

[数据库入口](../database-schema.md) · [一致性验收](consistency-verification.md)

## 数据库设计原则

数据库处于设计阶段，表及字段可以按业务语义和责任边界增加、删除或重组。结构设计以已确定的行为契约和不变量为依据，已有表名、字段及划分不构成必须保留的约束。

数据库首先按业务对象、工作职责和生命周期确定事实的保存责任、关联、状态转换及一致性边界，支持内部执行、失败处理和恢复。状态报告基于这些业务事实生成，报告中的字段位置不直接决定数据库中的事实归属。既定报告需求用于检验事实及历史是否完整；需要派生摘要或共享历史记录时，明确其来源和一致性规则，保持业务事实的责任归属。

逐类确定具体工作、等待条件、状态转换、修改责任、事务边界和历史恢复依据，再选择保存位置。优先由承担该项工作的业务记录表达等待事实；业务记录不能完整表达时，评估补充业务状态或独立记录。统一查询与报告汇总不要求将同一事实重复持久化。

例如，取回 R 等待录像 A 结束时，数据库保存 R 的来源成员与选择进度、A 的拍摄及产物处理事实。调度器据此判断 R 能否继续；A 结束并不要求给 R 另写一条“等待已解除”的记录。重试间隔则不同：间隔尚未完成与间隔已完成但设备仍受阻会导致不同的恢复行为，因此由操作流程保存这项责任。

稳定责任、已授予权利、外部效果、预算和完成依据由所属业务记录保存。候选条件根据当前可靠事实重新判断；过去没有保存的调度观察不能在历史查询时补造。取消后的实际读写、删除及进程收场仍须取得各自的结束依据，取消标记或协程退出不代替实际调用结束。

## 等待条件的事实归属

下表用于定位各类条件的权威记录和详细契约，不另定义一套等待状态。各工作仍须结合取消、终态、时间资格及所属流程的合法组合判断能否继续。

| 条件或责任 | 保存依据与详细契约 |
| --- | --- |
| 尚未到计划时间或启动窗口结束 | 动作时间意图、执行与取消状态；[窗口观察及过期原因](plans-actions.md#启动窗口观察与过期原因)保存首次有效观察，[启动窗口](../../architecture/scheduling-execution.md#窗口结束与在途启动)定义在途结果分类。时间等待从这些事实判断 |
| 被设备活动阻挡 | 设备绑定、活动身份、状态与占用，以及核实或收场责任；见[设备活动与候选](#设备活动启动保留与未完成责任) |
| 等待录像启动机会 | 动作资格、启动流程与尝试；归属及状态组合见[录像启动流程](recording-start.md)，首次授予见[共同提交](#首次启动机会与尝试的共同提交) |
| 等待相机读取机会 | 拷贝的 `slot_device_id`、所属交付或录像处理进度、源依赖及读取流程；见[读取机会](#相机读取机会与未完成责任) |
| 等待来源结束 | 固定的 `action_dependencies`、来源完成事实及依赖方选择进度；见[来源转换](#来源等待的记录与转换) |
| 清理等待既有读取结束 | 源依赖、逐请求删除限制、清理责任及处理归属；见[清理协调](cleanup-coordination.md#清理读取等待与待删除状态) |
| 等待重试间隔 | 原流程的实际失败、预算、配置和 `retry_wait_required`；见[重试转换](#重试责任的完整转换) |
| 等待拍摄完成及结果检查 | 设备活动的 `expected_check_at`、`wait_completed_event_id` 及适用完成依据；见[等待与完成核实](operation-fields.md#等待未知结果和占用恢复) |
| 因时间不可信暂停执行 | 本会话时间检查、可信历史下界与各项未完成责任；见[时钟恢复](../../architecture/clock-recovery.md)。后续会话重新检查时间资格，再从业务责任恢复工作 |
| 等待报告本地处理 | `report_status` 执行结果、`state_syncs` 责任及 `reports` 冻结与发布事实；见[同步记录](reports-runtime.md#状态同步记录)。本地处理成功和客户端 ACK 分别判断 |

计划时间、设备条件、来源状态和报告处理进度均从表中所属记录判断。调度与恢复按范围查询未完成责任；查询须有对应索引并分批处理，资源消耗通过实现与联调测量。

## 动作依赖关系

`action_dependencies` 保存取回或范围清理动作对拍摄动作产物结果的依赖，中文名称为“动作依赖关系”。每条记录具有以下字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 本条依赖关系的稳定编号 |
| `action_id` | 使用其他动作产物结果的取回或范围清理动作 |
| `depends_on_action_id` | 被依赖的拍摄动作 |

例如，记录 `(101, C, A)` 表示 C 依赖 A 的产物结果。业务代码核对两个动作存在、类型及输入范围符合要求，且同一动作对同一拍摄动作只有一条依赖关系。完整成员集合与固定状态共同提交，固定后沿用原成员及身份；精确 ID 清理直接处理指定产物。

依赖关系在拍摄动作结束后继续保留。拍摄成功、失败或取消与是否留下正式产物分别判断；依赖方按自身业务规则处理最终产物。设备活动及启动保留等待按下文所属规则表达，相机读取机会由持有者及未完成责任表达。依赖关系属于 `action_id` 指定动作的历史状态，并进入其快照。

来源关系给出成员身份；来源是否满足选择条件，由来源拍摄及适用的产物处理事实决定；依赖方是否仍需选择文件，由自身执行资格和选择进度决定。三者结合使用，具体分类见[来源等待的记录与转换](#来源等待的记录与转换)。

## 内部等待、报告数据与界面展示

一个动作可以包含多项分别推进的工作。需要持久化的等待事实均须能定位所属动作、具体工作、等待条件，以及适用的来源、文件或占用责任。同一动作的两个读取流程分别保存重试责任和实际采用的配置，分别计时；其中一个流程解除等待，不改变另一个流程的等待事实。

内部逐项保存服务于正确执行、恢复和必要诊断。状态报告表达什么、详细到什么程度，以及客户端展示哪些内容，均由用户需求决定，公共报告契约据此定义。内部状态以逻辑完整和一致性所需的信息为准，对外详情按需求选择；内部存在一条等待记录，不自动要求报告增加字段或界面显示该记录。

已确定的对外契约继续提供相应历史重建依据。新增内部状态时，分别判断其执行与恢复用途，以及是否影响已有报告内容；只有对外需求要求表达的信息才进入报告，不为预想中的详尽展示额外扩充数据库模型。

执行资格由设备活动、文件读取保护、操作预算、取消和时间资格等所属记录共同决定。没有额外等待标记不表示可以执行；条件满足也不证明后续工作已经开始或成功。

## 相机读取机会与未完成责任

拷贝 A 持有相机读取机会，B、C 已建立副本准备责任且仍需读取。数据库用 A 的 `file_copies.slot_device_id` 保存机会归属，用各份拷贝及其交付或录像处理、读取流程保存未完成责任。调度器结合这些事实判断当前候选，候选顺序遵守[文件拷贝规则](../../architecture/file-copy.md#多个候选文件的选择顺序)。

下表按顺序判断；普通工作结束不自动结束实际调用、源保护和独立收场责任。

| 可靠状态 | 处理 |
| --- | --- |
| 所需记录缺失、矛盾、不可读或提交结果未知 | 按状态库错误或原事务核实规则处理，不能解释为空闲或无工作 |
| 普通拷贝责任已结束或取消生效 | 不授予新的普通读取机会；原调用、源保护和收场继续按所属责任处理 |
| 拷贝只需主机校验、发布或清理，或源文件位于主机 | 不申请相机机会；完整字节本身不证明设备读取已经结束 |
| 本拷贝已持有机会 | 恢复原责任，分别检查重试间隔、累计额度、调用和取消，不重新竞争 |
| 其他拷贝持有机会，包括等待重试期间保留 | 保持本拷贝的未完成责任，不开始读取尝试，不消耗次数 |
| 无持有者，但本拷贝尚未满足其他执行条件 | 按实际阶段等待条件变化或截止时间；应当结束的失败按对应错误规则结束 |
| 本拷贝合格，但有排序更早的合格候选 | 选择较早候选，本拷贝继续保留未完成责任 |
| 本拷贝合格且应被选中 | 在写事务内核对当前占用、资格及排序，保存机会归属；派发前仍须保存适用尝试意图与额度 |

机会授予和释放与各自历史共同提交。A 满足释放条件时保存 A 的归属变化；B、C 仅因当前持有者变化而无需写入记录。各对象实际发生的取消、准备完成、源依赖解除等变化仍遵守自身共同提交契约。读取机会与源保护分别判断，分段间隙和允许的读取重试保留均不释放机会。

机会释放与下一候选授予可以分别提交，也可以在完整核对条件后共同提交。通知只请求重新判断；授予后取消按原持有者的收场规则处理。A 后来重新取得机会时，迟到的旧通知不修改新归属；实际释放核对原操作身份及当前阶段，不能仅凭拷贝 ID 无条件清空机会。

| 保存结果或中断位置 | 后续行为 |
| --- | --- |
| 未提交或确认回滚 | 本次归属变化未生效，按原可靠责任核实外部工作 |
| 提交结果未知 | 沿原操作身份核实，确认前不重复授予或派发 |
| 提交成功，进程继续运行 | 负责流程按[读取工作触发规则](../../architecture/file-copy.md#读取工作的发现与唤醒)请求重新调度 |
| 提交成功，通知前进程退出 | 下一次实际启动从未完成责任恢复；先处理已有归属，再选择其他候选 |
| 下一候选已取得机会后重启 | 沿已保存身份恢复该候选，不重新分配已有机会 |

机会事实归普通交付或录像内部处理所属动作的历史，按[事件归属](history-formats.md)保存。历史查询在同一完整边界恢复归属、进度及结果，不重做调度选择或设备调用，不把当时未保存的调度观察当成历史事实。适用报告变化按[报告目录](report-changes.md)登记。

## 设备活动、启动保留与未完成责任

录像 A 已开始，录像 B、C 已到计划时间时，数据库保存 A 的设备活动及占用，保存 B、C 的执行资格与未完成责任。调度器结合设备绑定、兼容性、时间和既定顺序判断候选。A 的设备活动由 `device_activities` 保存；动作终态、调用结果和活动状态分别表达，动作失败或取消不单独证明设备已经空闲。

录像 A 启动明确失败、确认没有开始且仍允许重试时，数据库通过 A 的动作资格和 `ACTIVE` 启动流程表达其下一次录像启动机会，具体状态及推导见[录像启动流程](recording-start.md)。相机可以没有正在执行的录像，但下一次录像启动机会仍属于 A。保留遵守[录像启动规则](../../architecture/camera-recording.md#等待重试时保留相机)，与其兼容的文件操作仍按各自资格执行。

### 启动保留与活动占用的分类

先处理所需事实不可读、矛盾或提交结果未知的状态；这些情况进入状态库错误或原事务核实，不解释为空闲。下表区分正常候选、重试保留和外部活动。每个动作仍按自身窗口、取消和既有终态判断资格。

| 已可靠保存的事实 | 启动机会及活动的处理 |
| --- | --- |
| 动作尚未取得启动机会 | 保持候选责任，按资格与既定顺序选择 |
| 原启动明确失败、确认未开始，且仍允许重试 | 与该结果共同保存原动作的启动保留；同一相机至多有一个有效的录像启动保留者 |
| 重试间隔尚未完成 | 保持原启动保留，按该流程的间隔责任计时 |
| 重试间隔已经完成，但其他启动条件尚未满足 | 保持原启动保留，按实际条件等待或结束；已完成间隔不重新计量 |
| 原动作再次尝试启动，结果尚未确认 | 跟踪原尝试及可能产生的活动；不能将启动机会交给其他录像 |
| 原动作已经确认开始录像 | 与启动确认共同结束重试保留，由设备活动表达占用，按已开始录像优先规则继续 |
| 原动作取消、最终失败或过期 | 与对应结果共同结束启动保留；此前可能产生的设备活动及必要收场继续独立处理 |

`retry_wait_required` 只保存重试间隔责任。标记为 0 时，原动作仍可能持有启动保留；间隔完成不解除保留。普通启动资格结束也不解除尚未核实的设备活动占用。活动释放条件遵守[设备活动恢复](operation-fields.md#等待未知结果和占用恢复)，不能把撤销再次启动权利当作设备停止证据。

### 首次启动机会与尝试的共同提交

录像 A 已完成必要准备、现在可以登记并派发启动调用时，调度器在写事务内再次核对设备占用、已有启动保留、动作取消与终态、可信时间及启动窗口、剩余额度、必要准备和候选顺序。条件成立后，在同一事务将 A 的启动流程建立或转为 `ACTIVE`，保存原设备活动身份、本次启动尝试及意图、增加后的累计次数、实际采用的参数与配置，以及相关历史。动作与流程的完整组合表达首次机会归属。事务提交成功后才允许发出本次启动调用；派发前再次核对窗口及执行资格。已超过窗口而可靠未派发时，保存未派发事实和适用过期结果，不退还已提交次数；已有调用或效果未知按[窗口结束与在途启动](../../architecture/scheduling-execution.md#窗口结束与在途启动)核实。

首次选择但尚未提交，仅表示程序当前的候选判断。已经提交的首次机会必然关联本次启动尝试及额度；等待重试时的保留则关联原失败尝试，不要求提前登记下一次尝试。意图使用 `dispatch_state = MAY_HAVE_DISPATCHED` 表达恢复时的可能效果，不证明命令已经发出或录像已经启动；仅据意图建立的活动保持未知。

下表按顺序判断登记新启动尝试的资格。失败、取消或过期结果仍按所属业务规则保存，不能为了授予机会绕过已有责任。

| 事务内条件 | 保存及执行结果 |
| --- | --- |
| 所需事实不可读、矛盾，或原提交结果未知 | 按状态库错误或原事务核实处理，不授予、不重复登记、不派发 |
| 普通启动资格已经结束，包括取消生效或已有终态 | 不登记新启动尝试，处理已有保留及适用独立收场 |
| 当前时间、窗口、预算或必要准备不允许登记 | 按对应等待、失败或过期规则处理，不新增尝试次数 |
| 存在未核实的原启动尝试或冲突活动 | 核实原责任或按活动规则处理，不用剩余额度授权重发 |
| 其他录像持有启动保留，或设备条件不允许启动 | 保持本动作未完成责任，按条件变化继续处理 |
| 尚无本动作的保留，存在排序更早的合格候选 | 选择合格的较早候选，本动作不取得机会 |
| 首次候选应被选中且全部条件满足 | 共同保存首次归属、尝试意图、次数及可能效果；提交后派发 |
| 本动作已有有效保留，安全重试条件及间隔均满足 | 沿原流程、活动身份和归属登记下一次尝试并增加累计次数，提交后派发 |

再次启动前，间隔完成与安全重试资格分别核对。明确失败、确认没有开始且仍可重试时，失败结果、启动保留及间隔责任共同提交；可靠确认启动时，启动事实、适用活动占用和保留结束共同提交。启动效果未知时保留原责任，按驱动契约核实。调用结果的结束记录仍须满足[调用收场条件](operation-fields.md#尝试字段与结果)。

依赖拍摄前目录基准的任务，须先按[输出范围与基准规则](../../architecture/camera-capture.md#本次任务的文件归属)取得准备所需占用，完成并可靠保存基准，再登记启动尝试。前置准备可能跨越多个事务，不能放在启动事务内等待设备，也不因仅取得准备占用就消耗启动次数。已经存在的活动身份和准备依据在启动事务中沿用。

| 启动事务或调用的中断位置 | 恢复要求 |
| --- | --- |
| 首次启动事务未提交或确认回滚 | 本次归属、尝试及额度未生效；已有准备责任仍按其原记录处理 |
| 启动事务提交结果未知 | 核实原事务，确认前不发命令，也不另建尝试 |
| 意图已提交，但没有可靠调用结果 | 恢复原尝试并核实实际效果；不能仅凭缺少结果判定没有启动，也不能退还已占用次数 |
| 可靠确认没有派发 | 保存实际依据；按原累计次数、窗口、取消和安全条件决定后续工作 |
| 失败结果和重试保留已提交 | 沿原归属、累计次数和间隔责任恢复，不重新选择持有者 |
| 启动确认已提交 | 沿原活动继续执行或对账，不重复启动 |

提交后发生取消时，按是否已经派发、是否可靠确认未派发及实际活动处理原责任，不将已提交额度清零。对已结束的动作，迟到结果只补充真实操作及活动事实并推进必要收场，不重新授予普通启动资格。

### 事实保存与候选检查

设备活动和各项未完成工作分别保存，录像启动机会由[动作与启动流程](recording-start.md#启动机会的推导与唯一性)共同推导。候选是否被其他活动或启动保留阻挡，由这些事实和兼容性重新判断。A 的占用或保留变化时保存 A 的实际变化及历史；B、C 仅因阻挡条件变化而不需要写入记录。B、C 自身发生取消、过期或取得机会时，仍保存各自变化。

授予和释放在写事务内核对当前可靠责任、资格及适用顺序，与相关事实和历史共同提交。释放与下一候选授予可以分别提交；释放本身不授予机会，不消耗新尝试次数，不派发调用。普通调用遵守意图及额度提交后派发的契约。

活动占用按[释放条件](operation-fields.md#设备活动占用的释放条件)核对设备结束或适用完成依据及剩余文件归属限制。`ENDED` 不直接等于 `RELEASED`，`RELEASED` 也不结束尚在收场的独立调用；候选查询必须结合这些记录及驱动兼容性判断冲突。

例如 A 结束保留后，B 已过期而 C 仍合格，调度器先按业务规则保存 B 的过期结果，再按资格选择 C。不能因为 B 曾经排在 A 后面，就让 B 越过自己的启动窗口。

提交后按受影响设备触发候选检查。触发入口包括新工作接纳、计划时间或窗口截止、重试间隔完成、启动结果、设备活动观察及占用释放、保留结束、取消和设备操作兼容条件变化。候选查询按设备和未完成责任分批进行，覆盖未缓存及后续页的工作；已有保留和活动先于新候选恢复。运行期间的通知交接遵守[调度交接](../implementation.md#调度通知与待处理工作的交接)，时间条件由截止时间唤醒。

通知只请求重新检查。重复或迟到通知不能修改机会归属；实际释放必须核对原责任及当前阶段，不能仅凭动作 ID 清除后来取得的机会。候选取消先提交时不再授予其普通机会；授予先提交时沿原责任处理取消及适用收场。

### 提交、恢复与历史

| 保存结果或中断位置 | 后续行为 |
| --- | --- |
| 未提交或确认回滚 | 保持原可靠事实，不把回滚解释为外部命令没有发生 |
| 提交结果未知 | 核实原事务；确认前不按假定结果重新授予或派发 |
| 提交成功，进程继续运行 | 负责流程接手结果并触发相关设备的候选检查 |
| 提交成功，通知前进程退出 | 下一次启动从活动、启动保留及未完成责任恢复，先处理既有归属 |
| 后续候选已取得机会后重启 | 沿已保存归属恢复，不重新竞争已经授予的机会 |

表达启动保留的动作、流程与尝试归所属录像动作的历史；设备活动继续归发起动作。历史在同一完整边界恢复活动、归属、资格与工作进度，不重做调度选择，不补造当时未保存的检查观察。对象自身没有变化时不增加自身历史计数；影响已定义公开字段时按[报告目录](report-changes.md)登记。报告详情由报告需求确定。

## 重试间隔的计时与历史

数据库保存操作流程的重试责任及实际采用的配置，不保存倒计时剩余值，也不因时间流逝周期性写入等待历史。对外表达由[报告契约](../../architecture/report-format.md#错误)定义，不在本页另行维护公共字段。

同次运行由各流程使用单调钟计量重试间隔；间隔结束后，业务代码重新检查取消、累计次数及其他执行资格，再保存相应变化。重启时依据可靠保存的重试责任和本次配置重新计量完整间隔，沿用原流程身份及累计次数。历史回放只恢复等待事实，不启动计时；报告按冻结边界处已保存的动作、产物和交付结果生成。

等待所属工作、引用身份、允许的状态转换及跨记录一致性由业务代码在写入前校验。依赖已有状态的判断在同一写事务中读取可靠事实，并结合本次拟保存的完整变化检查；不能在事务外检查后直接沿用旧判断，也不能将数据库是否接受写入作为业务合法性的判定方式。历史应用核对事件前后值，事务级完整性在完整事务边界检查，不把事务内部尚未应用完的记录当成已提交状态。

## 来源等待的记录与转换

取回 R 依赖拍摄 A。A 尚未完成拍摄及适用产物处理时，R 对 A 的选择为 `PENDING`；A 满足条件后，该选择仍为 `PENDING`，表示已经可以选择但尚未保存结果。选择结果与 `FIXED` 共同提交后，后续执行沿用该结果。

来源成员由 `action_dependencies` 保存，成员集合与 `actions.source_resolution_state` 共同固定。取回逐来源使用 `obtain_source_selections.status` 保存选择进度；范围清理使用 `actions.target_selection_state` 保存完整目标集合的固定进度。来源自身保存拍摄、产物处理和正式产物登记事实。这些记录分别承担成员、进度和完成依据的职责。

取回进入执行且来源已固定时，为每条依赖共同建立唯一的 `PENDING` 来源选择记录；执行后才固定来源时，在固定成员的同一事务建立这些记录。范围清理不创建取回选择记录。应有的选择行缺失属于一致性错误，不能解释为尚未开始；合法空来源集合由已固定的解析状态与所属业务规则解释，不能由零行推断解析结果。

取回的来源选择只允许 `PENDING → FIXED`，与完整选择项及适用来源错误共同提交。范围清理的目标集合固定遵守[目标集合状态](plans-actions.md#来源解析与目标集合)。取消或已有终态可以使尚未完成的选择保持 `PENDING`；动作资格说明为何不再继续，已保存选择结果保持。通知不重新开启已结束的工作。

## 来源处理的状态分类

以下按顺序判断。满足来源条件指拍摄及适用产物处理已结束、正式产物登记完整；来源成功、失败或取消与是否留下产物分别判断。来源条件尚未满足与事实无法可靠确认是不同情况。

| 可靠事实 | 取回或范围清理的处理 |
| --- | --- |
| 必要记录缺失、矛盾、不可读或提交未知 | 按状态库错误或原事务核实处理，不保存空集合或推测来源已结束 |
| 依赖动作已有终态或取消已经阻止普通选择 | 保持成员及选择进度，不继续普通选择；交付和文件收场按独立责任处理 |
| 尚未取得时间、会话或执行资格 | 保留原状态，等待适用的时间或资格；成员已存在不表示可以执行 |
| 来源解析仍为 `PENDING` | 在规定的解析时点固定完整成员或保存可靠的来源错误，不使用部分集合 |
| 来源解析为 `FAILED` | 保持原失败；与动作结果矛盾时按一致性错误处理 |
| 来源集合可靠固定且合法为空 | 按取回或范围清理的空来源规则取得结果，不无限等待不存在的成员 |
| 选择或目标集合已经 `FIXED` | 沿用成员和结果，进入逐项处理，不重新选择；其他不合法状态组合按一致性错误处理 |
| 取回的某个来源选择为 `PENDING`，该来源尚未满足条件 | 保留选择责任，等待来源变化；其他已满足条件的来源可以独立推进 |
| 取回的某个来源选择为 `PENDING`，该来源已满足条件 | 按选择方式固定完整结果；无选中文件时保存适用来源结果，不创建虚构目标 |
| 范围清理目标为 `PENDING`，仍有来源未满足条件 | 保留整项集合固定责任，不根据部分来源执行删除 |
| 范围清理目标为 `PENDING`，全部来源已满足条件 | 固定完整清理集合，与全部清理项共同提交，再按逐项规则处理 |

选择保存前在写事务内核对取消、现有结果、成员及来源完成依据，完整集合与状态共同提交。分批读取须保持固定范围与完整性，不能将第一批当成完整选择。取回可以逐来源准备副本，但发布仍须满足全部来源与条目的既定条件。范围清理固定目标不自动取得删除资格，仍须尊重源保护与取回排序。

## 重试责任的完整转换

已有 `operation_runs.retry_wait_required` 足以保存逐流程的重试间隔责任。每次失败后的重试复用原流程，不为每次间隔新增一条等待记录。间隔时长取自该流程实际使用的配置，累计次数保持原事实。

| 可靠事实或触发点 | 保存和执行 |
| --- | --- |
| 尝试尚未结束，包括调用仍在收场 | 不提前进入本次失败后的重试等待；调用边界见[普通尝试结束结果](operation-fields.md#普通尝试结束结果的保存边界) |
| 尝试已结束，仍有执行资格、预算且需要等待再次尝试 | 尝试结果与 `retry_wait_required = 1` 共同保存；启动所属流程的单调钟计时 |
| 间隔未结束，其他流程的条件变化 | 保持本流程的等待和配置，不借用其他流程的计时 |
| 间隔结束，资格复查通过，可以派发 | 清除标记，与新尝试意图和额度共同提交，再派发 |
| 间隔结束，但仍受其他独立条件阻挡 | 清除已经完成的间隔责任，依据其他条件所属记录保留未完成工作；不派发，不消耗次数 |
| 取消、预算不足或其他事实结束了该流程的重试责任 | 与相应责任变化共同清除标记；取消普通重试不阻止按原契约继续必要收场 |
| 后续一次尝试再次需要重试 | 同一流程再次置 1，保存新的实际配置和历史；不重置累计次数 |
| 重启时标记为 1，仍承担重试责任 | 按本次实际使用的配置重新计量完整间隔；先核对资格，不用墙钟差抵扣 |
| 重启时标记为 0，但流程尚未结束 | 按其可靠阶段恢复；不能因未结束就补造重试间隔，也不能跳过其他执行条件 |

普通交付读取流程归交付历史，录像内部读取及其他动作自身流程归相应动作历史。生成取回报告时，沿 H 时的交付关联恢复所需的交付事实；交付公开结果变化通过[报告目录与父对象补齐](../historical-state-query.md#交付变化与取回报告更新)更新所属取回。动作快照不复制交付流程，重试等待按其内部归属恢复；仅等待记录变化而公开结果未变时，不产生报告变化。动作终态后，设备执行情况、产物及交付继续按各自公开契约更新。

## 来源结束的共同提交

来源拍摄 A 结束时，在写事务内核对结束资格、取消及已有结果，共同保存所属契约要求的动作终态、正式产物与关联、内部文件提升、父计划状态和相应历史。A 自身的阶段与最终产物必须完整；依赖方 R 的选择由 R 的事务保存。

A 的结束仅改变 A 及本次实际变化对象的事实，稳定的来源成员关系继续保留。对象历史计数依据自身记录的实际变化，报告变化目录依据公开字段映射；两者分别遵守[历史关联与报告目录](report-changes.md)。

提交成功后沿固定来源关系定位仍承担普通处理责任的取回和范围清理，分批安排重新检查。来源产物处理完成、依赖关系建立、动作首次执行和适用时间到达，也须触发检查：来源先结束时由依赖方初始化后的检查发现，关系先建立时由来源结果通知推进。通知合并、检查与等待交接及原协程取消后的结果接手遵守[调度通知契约](../implementation.md#调度通知与待处理工作的交接)。

重新调度按当前可靠事实处理全部合格候选，不按通知先后抢占资格。取回与清理继续遵守[逐产物顺序](../../architecture/outputs.md#延后执行时的取回与清理顺序)。缓存中没有某个依赖方不代表它不存在；按来源反向查询关系，再结合动作资格及选择进度，分批继续处理未完成责任。

## 失败与恢复

| 保存阶段或结果 | 处理 |
| --- | --- |
| 来源结果未提交或确认回滚 | 依据原事实核实设备及产物，不因回滚推断外部操作未发生，不提前选择 |
| 来源结果提交成功，进程继续运行 | 负责流程通知依赖方重新判断，后续选择在自身事务保存 |
| 来源结果提交后、通知前退出 | 下一次实际启动从未完成取回和范围清理恢复，结合固定成员及来源事实继续 |
| 选择结果提交前中断或确认回滚 | 沿原选择责任重新核对，完整结果未提交前保持未完成 |
| 来源结果或选择提交未知 | 沿原操作身份核实，不新建身份盲目重做 |
| 选择结果已提交，后续处理前退出 | 沿用完整选择及原身份，不重选文件，不扩大集合 |
| 取消与来源结束或选择保存交错 | 写事务内核对最新资格；取消先提交则不继续普通选择，选择先提交则保留结果并处理取消 |
| 报告生成或发布失败 | 业务事实保持，报告责任独立继续；不阻止仍有资格的执行工作 |

启动恢复同时检查来源解析、逐来源选择、完整目标集合及后续条目责任。选择保持 `PENDING` 与来源已结束可以合法并存，恢复必须发现这种可继续工作。独立交付与收场不因所属动作已终态而消失；已结束的普通来源选择不因后续通知重新开始。

## 历史与报告重建

依赖动作的快照保存自身成员关系、选择记录、处理明细及稳定引用。来源完成事实归来源自身的历史。查询过去完整边界 H 时，在同一 H 分别恢复依赖方和被引用来源的事实，依据该时刻的资格与选择进度解释状态，不读取最新来源补算过去。

各业务记录的实际变化保存可逆前后值，与自身历史关联和适用报告目录共同提交。来源变化影响已定义公开字段时，按公开依赖映射登记报告目录；不要求依赖方通过虚构自身变化取得历史计数。公共报告内容与详细程度由报告契约确定。

历史可以还原当时的来源条件和处理进度，不将它们解释为调度器当时已经执行过某次检查。历史回放只重建已保存事实，不选择文件、不发出设备命令，也不重发正常调度通知。同一报告使用固定边界和确定的排列规则，后续来源结束、选择或取消不改变原报告字节。
