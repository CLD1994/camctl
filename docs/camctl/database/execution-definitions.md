## 动作专属执行定义

录像动作的驱动从生效参数及拍摄任务定义取得目标时长，录像处理模块据此计时、恢复和判断完成。这个时长属于首次受理时确定的专属执行定义，保存在动作的有明确结构的 JSON 中；其解释由录像处理模块负责。公共调度管理动作资格、计划时间、启动窗口和状态，不需要理解每种设备的全部专属执行字段。

| 字段 | 存储类型与约束 | 含义 |
| --- | --- | --- |
| `actions.execution_spec_json` | 可空 `TEXT`，非空时为精确 JSON 对象 | 动作首次通过全部受理校验时确定的执行定义，供所属动作处理模块执行及恢复使用 |

动作执行定义使用 `actions.type` 对应的数据类型。JSON 对象直接保存该类型的执行定义字段，不增加动作类型名称的外层包装，也不重复保存动作类型。每种结构明确字段含义、类型、单位、必填性及适用条件；输入转换、保存、读取和历史回放使用同源定义。字段缺失、内容非法或类型不适用时，按所属错误契约处理，不能用字典缺省值猜测执行含义。

下表先按首次受理结果区分，再按对应动作是否需要专属执行依据区分。是否通过受理由可靠受理事实判断，不能根据动作后来是否 `failed` 推断。

| 受理结果及定义要求 | `execution_spec_json` 的保存规则 |
| --- | --- |
| 整份计划被拒绝 | 不创建动作记录 |
| 动作在受理时失败，不论是否已经计算出局部执行依据 | SQL `NULL`，表示没有形成有效执行定义；原输入和错误按各自规则保存 |
| 动作通过全部校验，所属类型需要专属执行依据 | 保存符合该类型契约的完整对象，必需字段不能缺失 |
| 动作通过全部校验，所属类型没有额外执行定义字段 | 保存 `{}`，表示有效定义没有额外字段 |

合法录像必须保存其所需目标时长，不能使用 `{}` 代替完整执行定义。JSON `null`、数组、字符串及其他标量不是合法执行定义；SQL `NULL` 与有效空对象的含义不同，不能互相转换。合法受理后发生过期、取消或执行失败时，保留首次保存的对象。

| 信息 | 内容及负责解释的边界 |
| --- | --- |
| 原始输入 | 调用方提交的结构化值及字段存在性，由原计划重建和诊断流程使用 |
| 生效驱动参数 | 首次受理确定的完整驱动参数，由原选定驱动解释；拍摄动作使用 `effective_params_json` |
| 动作执行定义 `execution_spec_json` | 对应动作处理模块需要的固定执行依据；录像目标时长从生效参数及任务定义取得 |
| 本地执行配置 | 本次运行采用的通信、重试及处理配置，由配置规则管理；实际判断的必要依据随对应执行事实保存 |
| 操作尝试、逐项结果与检查修复进度 | 按独立身份、关联和生命周期保存到所属列或记录，由相应业务流程推进 |

原始输入、生效参数和专属执行定义分别表达输入与受理结果，不各自成为可独立修改的要求。首次受理按驱动及动作契约建立派生关系，与动作、绑定及对应历史在同一事务中保存。后续执行、重送、重启和历史回放使用已保存的执行定义，不重新读取新的驱动默认值推算旧定义。运行进度和操作结果另行保存，不改写首次执行定义。

受理流程由对应动作模块形成并校验执行定义，再与全部受理结果共同提交；驱动提供拍摄任务所需的依据，动作模块负责转换为自身明确的执行结构。定义只保存该模块确实需要的固定依据，不复制完整原输入、生效驱动参数或本地配置。读取时按动作类型及受理事实核对 JSON 结构和空值组合；无效的持久化定义按状态库错误处理，不以空对象或新计算结果修补。公共报告按其既有字段和出现条件读取所需依据，不将整份内部执行定义直接输出。

读取已受理动作时，普通列与原始例外必须能够重建符合第一版公共动作结构的原输入，采用时间窗口的动作策略中的 `max_delay_ms` 必须与对应普通列相同；拍摄动作的原 `params.type` 必须与生效参数类型相同。首次受理失败的动作保留实际缺省或非法原值，不要求其原输入符合合法动作结构。合法受理后进入终态的动作继续保持上述依据；读取不调用当前驱动规则、默认值或任务工厂，也不重新查询输入中引用的目标。

普通列的选择依据是公共管理、查询、排序和关系约束的需要，不要求每种动作都有值。设备及驱动标识、计划时间和适用的启动延迟仍按各自列契约保存。数据只读不自动意味着适合 JSON；只读的身份、关联和需要分页查询的大型集合仍按[公共存储分工](common.md#普通列子表与-json-的分工)组织。小型专属定义使用 JSON，可增长或需要独立更新的记录使用子表。

验证须覆盖上述受理与空值分区、不同动作采用各自结构、错误类型或不适用字段被拒绝、合法录像缺少必需字段、JSON `null` 与 SQL `NULL` 不混用，以及受理提交与回滚。核对固定定义与原输入的派生关系，验证受理后过期、取消、执行失败、重送、重启、历史回放和驱动默认值变化均保持原定义；结构或空值组合错误按状态库错误处理。公共调度通过既定公共接口取得需要的信息，动作模块负责解释专属定义；新增动作时按实际数据用途选择列、JSON 或专属记录。

## 各类动作的执行定义分工

动作执行定义保存所属处理模块需要的固定派生依据和受理时确定的默认含义。原输入已经完整表达的要求、已有的实例关联，以及执行时才能取得的目标和结果，分别使用各自的保存位置。下表适用于通过全部受理校验的动作；受理失败仍保存 SQL `NULL`。

| 动作类型 | `execution_spec_json` 的内容 | 其他信息的保存位置 |
| --- | --- | --- |
| `motor_control` | `{}`；位置由原始参数完整表达，没有额外派生的设备执行定义 | 原始参数随动作保存，窗口策略使用公共列；发送意图及结果按[电机持久化规则](../../architecture/motor-control.md#持久化与报告)保存为专属记录 |
| `camera_take_photo` | `{}`；动作类型已经确定执行一次拍摄 | 生效参数由 `effective_params_json` 保存；实际采集、设备活动和文件事实按各自记录保存 |
| `camera_record` | 录像目标时长 `target_duration_ms`，以及适用的[文件归属声明](#拍摄执行定义的文件归属声明) | 启动、停止、实际计时、检查和修复进度按各自执行记录保存 |
| `camera_timelapse` | 从生效参数和任务契约取得处理模块需要的固定执行依据；按持续时间采集时，两种结束方式都保存 `target_duration_ms` | 完整设备要求由 `effective_params_json` 保存；设备任务关联、实际采集进度、尝试和文件事实另行保存 |
| `obtain_action_outputs` | 首次受理确定的 [selection_mode](#取回执行定义的选择方式)，区分默认取回、预览取回和精确 ID 取回 | 原输入保留来源描述及显式 ID；来源关联、实际文件选择和处理结果由来源表及取回明细保存；自动预览用途、关联和能力依据由 `auto_preview_links` 保存 |
| `delete_action_outputs` | `{}`；来源范围或精确 ID 已由输入明确指定 | 原输入保留选择条件；范围来源由 `action_dependencies` 保存；实际目标和处理结果由 `cleanup_items` 保存 |
| `cancel_task` | `{}`；原输入已经完整表达取消目标描述 | 执行时解析并固定的实际目标和处理结果由取消明细保存 |
| `report_status` | `{}`；原输入已经明确指定完整或局部同步要求 | 执行时确定的固定起点、开始依据和同步责任由 `state_syncs` 保存 |

单张拍摄的次数不等于产物文件数。一次拍摄可以产生多种格式的文件；完成判定使用驱动提供的采集完成、文件归属和写入完成依据，不使用固定文件数量代替这些事实。

延时摄影的生效参数保存设备契约接受的完整拍摄要求，包括适用的采集间隔、持续时间和输出设置。动作执行定义只提取处理模块需要理解的固定依据，不复制整份驱动参数，也不由时长除以间隔生成强制目标次数或实际进度。处理模块和驱动按[职责分工](../../architecture/camera-capture.md#延时摄影处理模块与驱动的职责)落实计时、停止和完成判断。采用时间与产物判定时，保存声明的执行依据以及实际发送、等待和产物核实事实，不补造设备状态观察。设备自动结束和主机控制结束使用各自明确的任务契约，执行与重启恢复沿用首次确定的要求。

取回的选择方式与最终选中的文件分别保存。例如，输入同时省略 `filter` 和 `output_ids` 时，受理流程保存默认取回的解释结果，但保留原输入中的字段缺省；后续文件选择按照该方式处理。实际文件尚未产生、来源尚未结束或来源尚待执行时解析，不妨碍保存合法的选择方式，也不授权提前固定目标文件集合。显式请求 ID 与实际产物关联仍分别遵守取回明细规则。

清理、取消和报告的处理模块从已保存的合法输入读取明确要求，并转换为相应程序类型。读取不重新受理计划、不吸收重送正文，也不重算已经固定的来源、目标或同步起点。需要运行时查询的引用继续在所属契约规定的时点解析；已保存的关联和执行结果用于后续恢复。合法空执行定义不表示动作没有参数、没有目标或已经执行完成。

验证按动作类型和受理结果覆盖完整对象、有效空对象与 SQL `NULL` 的适用条件；单张拍摄覆盖一次采集生成多份文件，取回覆盖省略筛选参数与显式选择，清理、取消及报告覆盖仅受理尚未解析运行时引用。重送、重启和历史恢复保持首次选择方式及已固定的实际集合，不通过重新解释输入扩大处理范围。

## 拍摄执行定义的文件归属声明

录像或延时摄影驱动在任务定义中声明文件归属方式与输出范围时，处理模块将两者共同保存到首次执行定义。设备活动直接消费该声明；实际目录读取结果和基准首尾引用保存在执行历史与活动记录中，不写入只读定义。

| JSON 字段 | 类型与含义 |
| --- | --- |
| `ownership_mode` | JSON 整数，使用[设备活动字段](operation-fields.md#设备活动字段)登记的 `TASK_SCOPE` 或 `BASELINE_COMPARISON` 值 |
| `output_scope` | 非空精确 JSON 对象，表达驱动定义的目录、前缀或任务范围；具体定位结构由对应驱动解释 |

| 字段组合 | 校验结果 |
| --- | --- |
| 两字段均省略 | 定义未携带文件归属声明，不能据此推断基准已经固定或输出范围已可靠确定 |
| 只提供其中一个字段 | 定义无效，归属方式和范围必须共同声明 |
| 两字段均存在，但方式未登记、范围为空或不是 JSON 对象 | 定义无效，不用空范围代替未知范围 |
| 两字段均合法 | 保存完整声明，后续重送、恢复和活动建立使用原值 |
| 定义包含实际基准、运行游标等未登记字段 | 定义无效；这些事实由运行记录保存 |

两款 ADB 相机使用 `BASELINE_COMPARISON`，其范围包含驱动声明的完整目录列表。范围本身不证明本次任务的文件归属、文件写完或集合确定；启动准备及完成判定仍遵守[文件归属规则](../../architecture/camera-capture.md#本次任务的文件归属)。驱动声明的内容保存后不随本次运行配置变化而替换；读取时验证字段组合与精确 JSON 类型。

## 拍摄执行定义的必要产物规则

录像和延时摄影任务可以声明 `product_rules`，处理模块在首次受理时将完整规则保存为 JSON 数组。规则只使用首次固定定义，后续配置和驱动默认值不改变原要求。未声明时沿用对应动作的必要类别；声明空数组表示没有附加规则，不免除动作本身的必要类别。

每条规则恰好包含以下成员，不接受额外成员。格式标识由驱动的任务和文件解释契约共同定义，不根据照片类别将 RAW 解释为 JPEG。

| 成员 | 含义与约束 |
| --- | --- |
| `kind` | 文件类别 `photo`、`video` 或 `other` |
| `format_id` | 非空格式标识；JSON `null` 表示不限制具体格式 |
| `min_count` | 非负 JSON 整数，表示符合本规则的最低文件数量 |
| `exact_count` | 不低于 `min_count` 的 JSON 整数；JSON `null` 表示不要求精确数量 |
| `require_pairing` | JSON 布尔值，只在 `true` 时要求符合本规则的文件具有已确认配对 |

检查按以下优先顺序处理。扫描结束、集合确定、文件写完和归属分别判断，文件数量不由目标时长或采集间隔推算。

| 条件 | 规则结果 |
| --- | --- |
| 集合未确定，或必要文件读取错误、归属未确定、文件未写完 | `UNKNOWN`，不能判定明确缺失或不合格 |
| 上述事实均充分，但所需格式或适用配对仍未知 | 对应规则为 `UNKNOWN`；已知规则结果保留，整体仍不能作出成功或明确不合格结论 |
| 所需事实均充分，最低或精确数量不符，或明确缺少要求的配对 | `FAILED` |
| 所需事实均充分且本规则全部要求满足 | `PASSED` |

评估按单次迭代聚合精确数量和规则结果，不累计完整文件集合。内部未完成、归属未知和读取错误的文件身份分别只保留前 128 项诊断样本，同时保留完整计数；详细事实仍从原文件和页历史分页读取。

## 录像执行定义的目标时长

`camera_record` 的 `execution_spec_json` 使用 `target_duration_ms` 保存录像目标时长。该值表示从可靠确认本次录像已经开始的计时锚点起，正常控制流程要求至少继续录制的时长；取消和异常收场仍按各自规则处理。

| JSON 字段 | 类型与范围 | 保存规则 |
| --- | --- | --- |
| `target_duration_ms` | JSON 整数，1～9223372036854775807，单位为毫秒 | 合法受理的录像执行定义必填；从生效参数和驱动任务定义精确取得，首次保存后保持不变 |

例如，目标为 60 秒的录像保存以下执行定义：

```json
{"target_duration_ms": 60000}
```

表示范围不等于设备支持范围；实际目标时长还须符合对应驱动的参数契约。公共计划时间固定到秒表达开始时间，目标时长可以具有毫秒粒度，两者分别校验。客户端及驱动输入可以使用其契约规定的单位，内部转换不要求调用方改用毫秒。

| 待转换或读取的值 | 处理 |
| --- | --- |
| 可精确表示为范围内的正整数毫秒，且符合驱动业务约束 | 保存整数毫秒；例如 1.5 秒保存为 `1500` |
| 零或负时长 | 非法，不表示无限录像或立即停止 |
| 精确换算后存在不足一毫秒的余量，例如 1.0005 秒 | 不受该执行定义支持，不舍入、不截断 |
| 换算后的整数超出表示范围，或超出驱动允许范围 | 非法，不裁剪为边界值 |
| 目标时长缺失、为字符串、布尔值、`null` 或其他非数值类型 | 不能形成合法录像执行定义，不隐式转换或补值 |

JSON 整数按数学值判断，沿用[精确数字规则](../data-types.md#精确数字与统一输出方向)；合法输入的精确转换和持久化不得先经过二进制浮点数。受理失败时整列仍按执行定义规则保存 SQL `NULL`，不保存缺少目标时长的局部对象。

用户输入违反有效驱动规则所声明的范围或精度时，按动作参数错误处理。用户输入符合已声明规则，但驱动任务定义或转换结果无法形成合法目标时长时，属于驱动定义或内部转换错误，按所属会话错误处理，不将规则或实现错误归咎于用户。已保存的目标时长缺失或非法时，按状态库错误处理。

执行、恢复和修复判断使用同一已保存目标，按参与计算的单位精确换算；实际媒体时长与目标分别保留。不能先将实测媒体时长舍入到毫秒，再判定是否达到目标。毫秒存储精度不承诺设备能在毫秒边界停止，也不改变启动确认、单调钟及异常恢复的既有规则。

验证覆盖 1 毫秒、零、负数、最大表示值及越界值、驱动范围两侧、可精确换算的小数秒、不足一毫秒的余量、错误 JSON 类型，以及固定任务和用户指定时长两种来源。区分用户输入错误、驱动定义或转换错误、持久化记录错误；验证重送及历史恢复保持精确值。以低于目标但舍入后会相等的实测时长作为反例，确认完成判定不通过舍入制造达标结果。

## 延时摄影执行定义的目标时长

合法延时摄影定义必须保存两个 JSON 布尔字段：`duration_based` 表示本任务是否按持续时间采集，`wait_after_send` 表示本任务是否采用发送成功后等待目标时长再检查结果的方式。这两个字段由驱动任务契约在首次受理时确定，之后只读；读取时不查询新的驱动配置来推断适用性。

| 固定条件 | 目标时长与等待余量的保存规则 |
| --- | --- |
| `duration_based: false`、`wait_after_send: false` | 省略 `target_duration_ms` 和 `result_wait_margin_ms`；任务须由设备结束，并使用设备完成依据 |
| `duration_based: true`、`wait_after_send: false` | 必须保存 `target_duration_ms`，省略 `result_wait_margin_ms` |
| `duration_based: true`、`wait_after_send: true` | 必须保存 `target_duration_ms` 和 `result_wait_margin_ms`；任务由设备结束，启动返回含义为 `SENT` |
| `duration_based: false`、`wait_after_send: true` | 非法；发送后等待目标时长的任务必须具有固定目标时长 |

两个布尔字段缺失、使用其他 JSON 类型，或者条件字段与保存的固定条件不一致时，按状态库错误处理。由主机按时停止的任务必须 `duration_based: true`，且不能在启动返回已经声明 `COMPLETED` 后才安排停止；使用 `TIME_AND_OUTPUTS` 时必须按有限持续时间采集。其他结束、停止、返回及完成方式组合继续遵守本页各自规则。

对于按持续时间采集的 `camera_timelapse`，`execution_spec_json.target_duration_ms` 保存首次受理确定的目标采集时长。该字段为正整数毫秒，沿用[录像目标时长](#录像执行定义的目标时长)的数值范围、精确转换和错误归属规则，且须符合对应延时摄影驱动的参数契约。数值表示相同不意味着两种动作采用相同的停止、媒体检查或修复流程。

| 受理结果与结束方式 | 保存规则与用途 |
| --- | --- |
| 合法受理，设备按目标持续时间自行结束 | 必须保存 `target_duration_ms`；命令返回后任务仍在执行时，按声明安排等待；返回已证明采集完成时，直接继续尚需进行的产物核实 |
| 合法受理，主机按目标持续时间发出停止命令 | 必须保存 `target_duration_ms`，处理模块据此安排停止操作 |
| 动作受理失败 | 整列保存 SQL `NULL`，不保存局部执行定义 |

采集间隔与输出设置由生效驱动参数保存，不通过时长除以间隔生成实际采集次数。目标时长与运行时的计时锚点、剩余时间及设备观察分别保存；首次定义保持不变，重启根据原任务的可靠事实和声明的恢复方式继续，不能把某次运行的单调钟截止值作为跨会话时间使用。[等待与完成核实](../../architecture/camera-capture.md#设备自行结束时的等待与完成核实)规定适用的状态或产物核实、取消和重启行为。

验证覆盖两种结束方式都必须保存合法目标时长、首次受理失败仍为 SQL `NULL`、重送和恢复不改写目标，以及目标时长到达只触发相应操作而不直接形成成功结果。已有记录缺少必要目标时长或数值非法时，按状态库错误处理，不从新的驱动默认值补造。

返回后等待所用的单调钟锚点遵守[命令返回含义与等待起点](../../architecture/camera-capture.md#命令返回含义与等待起点)，不使用数据库保存完成时点替代实际取得成功结果的时点。持久记录区分命令发送、启动观察、等待完成和任务完成响应；保存目标时长不意味着每次调用返回后都重新等待该时长。

[无状态查询任务的重启等待恢复](../../architecture/camera-capture.md#无状态查询任务的重启等待恢复)保存发送成功时取得的 UTC 日期时间、预计检查时间及采用的等待依据。日期时间沿用数据库整数微秒规则，单调钟截止值不作为跨会话依据。预计检查时间由原发送时间、固定目标及余量和实际部署额外等待派生，不成为可独立修改的第二套时长要求。各次安排及等待完成事实属于执行记录，动作的只读执行定义不保存这些运行结果。

采用发送成功后等待的任务，将[驱动必要余量](../../architecture/camera-capture.md#驱动必要余量与部署额外等待)与目标时长分别保存到只读动作执行定义；必要余量由驱动按首次生效参数形成，重送和重启不按新的驱动默认值重算。部署额外等待默认 0，是本地运行配置，实际采用的值随执行事实保存，不作为首次受理的固定字段。等待完成事实及其实际依据共同保存，历史恢复不使用新的配置改写原结论。

## 延时摄影执行定义的结束控制

`camera_timelapse` 的 `execution_spec_json.end_control` 表示正常执行时由谁结束采集。驱动根据任务契约和生效参数，在动作首次通过全部受理校验时确定该字段；处理模块按保存值选择正常结束流程。字段保存在专属执行定义 JSON 中，不作为 `actions` 的独立列。

| JSON 整数值 | 程序枚举成员 | 正常结束责任 |
| --- | --- | --- |
| `1` | `DEVICE` | 设备按本次任务参数自行结束采集，camctl 等待并核实结果 |
| `2` | `HOST_TIMER` | camctl 计量目标采集时长，到时通过驱动发出停止命令 |

程序使用具有上述固定整数值的枚举，JSON 使用对应整数，遵守[整数枚举规则](common.md#状态与类型的整数枚举)及[精确数字规则](../data-types.md#精确数字与统一输出方向)。不接受字符串、布尔值、JSON `null`、非整数数值或未定义编号，不通过缺省值猜测结束方式。

| 受理结果及任务契约 | 保存与处理 |
| --- | --- |
| 合法延时摄影任务由设备自行结束 | 必须保存 `end_control: 1`；按持续时间采集时，同时保存合法 `target_duration_ms` |
| 合法延时摄影任务由主机按时停止 | 必须保存 `end_control: 2` 和合法 `target_duration_ms`；驱动契约必须具备相应停止能力及明确计时依据 |
| 动作受理失败 | 整个 `execution_spec_json` 保存 SQL `NULL`，不保存局部结束控制字段 |
| 驱动任务定义无法明确结束责任，或声明由主机停止却没有对应能力 | 不能形成可用执行契约，按驱动定义错误处理，不将其解释为用户参数错误或自动改用设备结束 |

`end_control` 不表示命令返回时机。命令发送成功即返回和任务完成后才返回，都可以对应 `DEVICE`；是否还需等待由原返回契约及实际结果判断。该字段也不代替停止能力声明：`DEVICE` 任务可以支持提前停止，不能仅凭该值拒绝取消；`HOST_TIMER` 必须支持正常结束所需的停止操作，取消仍按[取消资格](../../architecture/task-cancellation.md#设备任务的取消资格)判断。

合法受理后，该值保持不变。重送、重启、配置变化和历史回放不重新选取结束方式；实际启动、等待、停止和结果另行保存。读取到必需字段缺失、编号非法或持久化定义自相矛盾时，按状态库错误处理，不根据新的驱动默认值补齐。

验证覆盖两种结束方式的必填字段及能力约束、非法类型和编号、受理失败的整列空值，以及重送、恢复和回放保持原值。组合 `DEVICE` 与两种命令返回时机、支持和不支持提前停止的任务，确认不会从结束控制推断返回时机或取消能力。

## 延时摄影执行定义的停止能力

`camera_timelapse` 的 `execution_spec_json.stop_supported` 保存驱动是否支持停止本次设备任务。该字段为必填 JSON 布尔值，由驱动根据本次任务契约及生效参数在首次受理时确定，合法受理后保持不变。它只保存本任务所需的停止能力，不复制整个设备能力目录，也不作为 `actions` 的独立列。

| 字段值 | 含义 |
| --- | --- |
| `true` | 驱动支持停止本次设备任务；是否可以向实际活动发出停止操作及是否成功，仍按归属、执行阶段和调用结果判断 |
| `false` | 驱动不支持停止本次设备任务；已启动或可能启动且尚未终态时，拒绝取消，原任务继续处理 |

程序使用布尔值，JSON 保存 `true` 或 `false`，不接受整数 `0`、`1`、字符串、JSON `null` 或字段缺失。驱动定义必须明确提供能力，不能用缺省 `false` 掩盖未定义的任务契约。动作受理失败时，整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部停止能力字段。

正常结束责任与停止能力按以下完整组合校验：

| `end_control` | `stop_supported` | 合法性与行为 |
| --- | --- | --- |
| `1`（`DEVICE`） | `true` | 合法；设备正常自行结束，必要时可按取消规则提前停止 |
| `1`（`DEVICE`） | `false` | 合法；设备正常自行结束，已启动或可能启动时拒绝取消 |
| `2`（`HOST_TIMER`） | `true` | 合法；camctl 到时通过驱动停止，取消仍遵守所属规则 |
| `2`（`HOST_TIMER`） | `false` | 非法；主机负责结束任务却没有停止能力，不能形成可用执行契约 |

驱动提供的类型或组合非法时，按驱动定义错误处理，不当作用户参数错误。读取到已保存定义缺失、类型非法或组合矛盾时，按状态库错误处理，不重新查询设备能力补齐或改写原定义。重送、重启、配置变化和历史回放均保留首次值。

该字段不表示已经发出停止命令、停止成功或停止操作可以安全重复，也不代替设备活动归属证明。实际停止意图、尝试和结果由执行记录保存。`false` 不阻止可靠确认尚未启动的任务被取消；终态、已有取消事实及启动结果未知的处理遵守[设备任务的取消资格](../../architecture/task-cancellation.md#设备任务的取消资格)。实际驱动或设备不可用时，按对应执行错误处理，不将本字段改成 `false`。

验证四种结束控制与停止能力组合、非法类型和字段缺失、受理失败的整列空值，以及重送和恢复保持原定义。组合任务未启动、已启动、启动结果未知和已有终态，验证取消资格；验证能力为 `true` 但实际停止失败时，保留失败结果且不修改能力声明。

## 延时摄影执行定义的启动返回含义

`camera_timelapse` 的 `execution_spec_json.start_return_meaning` 保存启动任务的调用成功返回时，驱动保证的事实。该字段由驱动根据任务契约及生效参数在首次受理时确定，合法受理后只读；它不是某次调用的结果，也不作为 `actions` 的独立列。

| JSON 整数值 | 程序枚举成员 | 成功返回保证及处理 |
| --- | --- | --- |
| `1` | `SENT` | 只确认命令发送成功，不直接确认设备已经开始采集；需要等待的任务按声明的发送成功锚点计时 |
| `2` | `STARTED` | 确认设备已经开始采集，处理模块按驱动声明的可靠计时依据继续管理任务 |
| `3` | `COMPLETED` | 确认采集任务已经完成，继续尚需进行的文件检查，不重新等待完整采集时长 |

程序使用固定整数枚举，JSON 保存对应整数，遵守[整数枚举规则](common.md#状态与类型的整数枚举)和[精确数字规则](../data-types.md#精确数字与统一输出方向)。合法受理的延时摄影必须提供该字段，不接受缺省值、字符串、布尔值、JSON `null`、非整数数值及未定义编号。受理失败时，整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部返回定义。驱动无法给出明确返回含义时，按驱动定义错误处理；持久化定义缺失或非法时，按状态库错误处理，不用新的驱动默认值补齐。

固定定义与实际调用结果共同决定后续处理，已有终态、生效取消及状态库错误仍优先适用各自规则：

| 本次调用的实际证据 | 处理 |
| --- | --- |
| 取得契约规定的成功响应 | 按保存的 `start_return_meaning` 记录相应事实，并执行上表对应的后续处理 |
| 调用失败、超时或中断，且没有可靠的成功事实 | 保存实际结果及未知情况，按原异常或恢复规则处理；不能从定义值推导发送、启动或采集已经成功 |
| 已取得可靠事实，随后调用发生异常 | 分别保存已取得的事实与调用异常，按所属执行规则处理；不抹去事实，也不将异常伪装为正常返回 |

采集完成不自动证明文件写完，`COMPLETED` 不代替文件归属、写入完成和产物集合检查。`end_control` 表示正常结束责任，与本字段分别判断；`DEVICE` 可与三种返回含义分别组合，具体任务仍须提供与所选方式一致的等待及完成契约。仅凭返回含义也不能判断是否支持提前停止。主机负责计时停止的任务仍须具备及时安排停止所需的计时依据，不能等采集完成才开始计算停止时间。

调用尝试及实际结果由执行记录保存，不写回本字段。重送、重启和历史回放使用首次确定的含义，不因驱动默认值变化重新解释原响应。验证三种成功含义、各类非成功结果及先取得事实后发生异常；组合完成响应与文件仍未写完，确认不会提前登记产物，声明为 `COMPLETED` 但调用超时时也不会产生虚构完成事实。

## 延时摄影执行定义的完整启动调用期限

`camera_timelapse` 的 `execution_spec_json.start_call_timeout_s` 保存驱动按生效参数声明的完整启动调用期限，单位为秒。该字段只适用于固定 `start_return_meaning = COMPLETED`，用于覆盖原生采集及最终处理。首次受理保存后只读，启动授予和实际调用使用同一值；它不是部署重试配置，也不增加客户端计划字段。

| 固定返回含义或受理结果 | 保存规则 |
| --- | --- |
| `COMPLETED` 且动作受理成功 | 必须保存有限、正的精确 JSON 数字秒数；程序使用 `Decimal`，不能采用短控制调用默认值 |
| `SENT` 或 `STARTED` 且动作受理成功 | 省略该字段，继续适用短控制调用期限 |
| 动作受理失败 | 整个执行定义保存 SQL `NULL`，不保留局部期限 |
| 期限缺失、为空、非正、非有限，或类型是布尔、字符串、浮点数 | 定义非法；受理按驱动定义错误处理，已保存定义按状态库错误处理 |

驱动声明对整项任务期限负责，具体设备的处理余量在真机验证确认。框架不从目标时长、发送后的等待余量或本次驱动默认值推导替代期限；重送、重启和历史回放沿原精确值。

## 延时摄影执行定义的结果等待余量

`camera_timelapse` 的 `execution_spec_json.result_wait_margin_ms` 保存驱动要求的必要等待余量，适用于发送成功后等待目标采集时长、再检查结果的任务。该值覆盖目标时长之外的启动准备和最终文件处理时间，由驱动根据任务契约及首次生效参数确定；合法受理后保持不变。

| 字段 | 类型与范围 | 含义 |
| --- | --- | --- |
| `result_wait_margin_ms` | JSON 非负整数，范围为 `0` 至 `9223372036854775807`，单位为毫秒 | 在目标采集时长之外，驱动要求检查结果前额外等待的时长 |

该字段的存在性由任务的等待契约决定，不能仅根据 `end_control` 推断。按以下分类保存：

| 受理结果与等待契约 | 保存规则 |
| --- | --- |
| 合法受理，采用发送成功后等待目标时长的方式，需要额外余量 | 必须保存驱动确定的正整数毫秒值，并保存该方式要求的合法目标时长 |
| 合法受理，采用该等待方式，但驱动明确不需要额外余量 | 必须保存 `0`，不能省略字段 |
| 合法受理，不采用该等待方式 | 省略字段，不能用 `0` 或 JSON `null` 表示不适用 |
| 动作在受理时失败 | 整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部余量定义 |

数值遵守[精确数字规则](../data-types.md#精确数字与统一输出方向)，不得先经二进制浮点数换算后舍入或截断。字符串、布尔值、JSON `null`、负数、非整数毫秒及越界值均不合法。驱动定义无法形成合法余量时，按驱动定义或内部转换错误处理，不将其归咎于用户输入；读取到持久化值非法、适用时缺失或不适用时仍有值，按状态库错误处理，不补默认值。

例如，设备自行执行 20 分钟的任务，发送成功后还需等待 5 秒的必要余量，则有关字段为 `target_duration_ms: 1200000`、`end_control: 1` 和 `result_wait_margin_ms: 5000`。本地部署额外增加的等待时间按[等待余量规则](../../architecture/camera-capture.md#驱动必要余量与部署额外等待)另行保存到执行记录，不累加写回本字段。命令返回已经证明任务完成时，不因设备自行结束或存在原等待定义而重新等待完整采集时长；实际已取得的事实按返回契约解释。

验证适用时的零值、正值和上界，不适用时字段省略，以及受理失败的整列空值。覆盖非法类型、数值越界、适用时缺失和不适用时提供字段；验证重送、配置变化、恢复和历史回放保持首次余量，本地额外等待不修改该值。

## 延时摄影执行定义的完成判定方式

`camera_timelapse` 的 `execution_spec_json.completion_mode` 保存处理模块判定采集完成时允许使用的依据。字段由驱动根据本次任务契约及生效参数在首次受理时确定，合法受理后只读，不作为 `actions` 的独立列。两种方式均须完成必要的文件归属、写入完成及产物集合检查，才能登记动作成功。

| JSON 整数值 | 程序枚举成员 | 完成判定要求 |
| --- | --- | --- |
| `1` | `DEVICE_EVIDENCE` | 必须取得驱动认可、能够关联原任务的设备完成依据，再完成必要的产物检查 |
| `2` | `TIME_AND_OUTPUTS` | 允许按明确的设备运行假设，在声明的等待条件满足且产物检查通过后判定完成 |

程序使用固定整数枚举，JSON 保存对应整数，遵守[整数枚举规则](common.md#状态与类型的整数枚举)及[精确数字规则](../data-types.md#精确数字与统一输出方向)。合法受理的延时摄影必须保存该字段，不接受缺省值、字符串、布尔值、JSON `null`、非整数数值及未定义编号。受理失败时，整个 `execution_spec_json` 保存 SQL `NULL`。

设备完成依据可以来自任务完成后返回的成功响应、任务状态查询、设备保存的完成记录，或符合任务契约的停止结果及必要计时依据。`DEVICE_EVIDENCE` 不统一要求状态查询接口；具体证据的含义和取得方式由驱动声明。`start_return_meaning` 只解释启动调用的成功响应，不代替本字段对后续完成判定的约束。

结束控制与完成方式按下表校验，停止能力继续遵守其自身组合约束：

| `end_control` | `completion_mode` | 契约要求 |
| --- | --- | --- |
| `1`（`DEVICE`） | `1`（`DEVICE_EVIDENCE`） | 驱动须提供原任务的可靠完成依据及必要文件检查规则 |
| `1`（`DEVICE`） | `2`（`TIME_AND_OUTPUTS`） | 驱动须声明有限时长、自行结束、可靠等待及文件完成规则；采用发送成功后等待目标时长时，保存合法目标时长及 `result_wait_margin_ms` |
| `2`（`HOST_TIMER`） | `1`（`DEVICE_EVIDENCE`） | camctl 按原契约计时并执行停止，结合停止及必要计时依据判断，随后核实产物 |
| `2`（`HOST_TIMER`） | `2`（`TIME_AND_OUTPUTS`） | 非法；需要主机停止的任务不能仅凭时间到达及文件存在认定设备已经结束 |

运行时先处理已有终态、生效取消、明确失败证据及状态库错误。其余情况按下表依次判断；实际取得的依据及检查结果由执行记录保存，不写回固定定义：

| 实际取得的事实 | `DEVICE_EVIDENCE` | `TIME_AND_OUTPUTS` |
| --- | --- | --- |
| 已取得原任务的可靠完成依据 | 使用该依据，继续尚需进行的文件检查 | 使用该依据，不重复等待已经证明完成的阶段；未被依据覆盖的文件处理仍按原契约核实 |
| 尚无完成依据，但声明的发送及等待条件已经满足 | 仍不能判定采集完成，继续适用的有限核实 | 按声明的文件完成与产物规则核实，全部要求满足后登记成功 |
| 尚无完成依据，声明的发送或等待条件也未满足 | 继续原执行或恢复流程，不根据文件存在推断完成 | 继续原发送处理、等待或恢复流程，不提前登记成功 |

任何方式下，产物缺失、归属或写入完成尚未确认时均不登记成功，按所属有限核实及文件保留规则处理。时间与产物判定不产生设备直接报告完成的观察，也不补造实际采集次数或时长。明确的失败或提前中断证据不能被等待到期或表面齐备的产物覆盖。

执行时不因状态查询失败或预算耗尽，将 `DEVICE_EVIDENCE` 改为 `TIME_AND_OUTPUTS`。重送、重启及历史回放沿用首次方式；实际完成依据可以增加，但不能重写过去的处理结果。驱动定义的模式、能力或等待规则不一致时，按驱动定义错误处理；持久化字段缺失、非法或组合矛盾时按状态库错误处理，不补默认值或切换方式。

验证全部结束控制与完成方式组合，以及非法类型、编号、必填字段缺失和受理失败的整列空值。按运行判定表覆盖取得可靠完成依据、只有等待完成、等待未完成及文件检查不通过；验证查询失败不切换方式、可靠依据只免除其已经证明完成的阶段、已知失败优先，以及报告不会混淆直接设备观察与等待推导结论。

## 取回执行定义的选择方式

`obtain_action_outputs` 的 `execution_spec_json.selection_mode` 保存本次取回选择文件的规则。该字段在首次通过全部受理校验时由合法输入确定，之后保持不变，不作为 `actions` 的独立列。实际来源和选中文件按各自执行时点确定，不因选择方式已保存而提前固定。

| JSON 整数值 | 程序枚举成员 | 选择规则 |
| --- | --- | --- |
| `1` | `DEFAULT` | 默认取回排除预览；每份原文件有已登记的对应修复成品时选择修复成品，否则选择原文件 |
| `2` | `PREVIEW` | 按预览取回契约选择，包括存在有效预览且对应修复成品满足完整大小比较条件时，选择修复成品 |
| `3` | `EXPLICIT_IDS` | 仅处理用户明确指定的产物 ID，不自动替换或扩大选择范围 |

程序使用固定整数枚举，JSON 保存对应整数，遵守[整数枚举规则](common.md#状态与类型的整数枚举)及[精确数字规则](../data-types.md#精确数字与统一输出方向)。合法取回必须提供该字段，`DEFAULT` 是显式保存的规则，不是读取缺失字段时的兜底值。字段缺失、字符串、布尔值、JSON `null`、非整数数值或未定义编号均不合法。

输入映射遵守[取回参数组合](../../architecture/plan-input.md#取回来源筛选与预览)。下表中的合法条件包含来源、用途及其组合限制；仅能识别筛选方式不代表动作已经通过全部受理校验。

| 首次受理的输入及结果 | 保存规则 |
| --- | --- |
| 全部校验通过，未提供 `output_ids`，`filter` 省略或为 `default` | 保存 `selection_mode: 1` |
| 全部校验通过，未提供 `output_ids`，`filter` 为 `preview` | 保存 `selection_mode: 2`；手动与自动预览使用相同选择方式 |
| 全部校验通过，动作级来源提供合法的非空、无重复 `output_ids`，且未提供 `filter` | 保存 `selection_mode: 3` |
| 动作受理失败，包括空 ID 列表、非法 ID、同时提供 `output_ids` 与 `filter`、不允许的来源或用途组合 | 整个 `execution_spec_json` 保存 SQL `NULL`，不保留局部选择方式 |

合法预览取回的执行定义为 `{"selection_mode":2}`。自动用途、来源关联及能力依据继续由 `auto_preview_links` 保存，不另设自动预览选择枚举，也不在执行定义中重复保存用途。原参数保留调用方实际填写的来源、ID 列表及字段存在性；实际来源成员由 `action_dependencies` 保存，逐来源选择进度由 `obtain_source_selections` 保存，实际产物或显式请求目标由 `obtain_items` 保存，交付结果使用相应交付记录。

选择规则沿用[默认及精确取回](../../architecture/obtaining-outputs.md#产物选择)和[预览产物选择](../../architecture/preview-obtaining.md#产物选择与失败)。预览不存在时，不因有修复成品而自动选择该成品；有效预览与修复成品比较完整大小，相等时选修复成品。默认选择的修复成品不可用时不退回原片，精确 ID 可以指定原片、预览或修复成品。选择结果可靠保存后，重试及恢复不因文件不可用而改选其他文件。

重送、配置变化、重启及历史回放沿用首次选择方式和已经固定的实际选择。读取到必需字段缺失、值非法或与保存的原输入及关联矛盾时，按状态库错误处理，不重新解释缺省参数补齐。合法输入的内部转换无法形成一致定义时，按内部错误处理，不将转换故障归咎于用户。

验证三种方式的全部合法输入映射、显式默认与省略默认具有相同方式但保留不同原输入，以及各种非法组合的整列空值。验证手动与自动预览共享选择方式、来源或文件尚未产生时仍可保存合法定义，以及默认替代、预览大小比较和精确 ID 不替代的区别。覆盖字段缺失、非法类型和编号、重送及恢复保持原选择；实际无效 ID 仍分别保存明细，不创建虚假产物关联或交付。
