本页定义清理请求和取消请求的逐项记录、删除限制及交付处理关系。来源成员见[来源关联与取回明细](sources-obtaining.md)；实际文件及交付状态见[产物、交付与文件记录](outputs-files.md)。

## 清理目标明细

读取等待与待删除、单项处理归属、独立预算和接手排序由[清理协调](cleanup-coordination.md)定义；最终结果事件及取消错误由[清理汇总与错误来源](output-cleanup-state.md)定义。

`cleanup_items` 的每条记录表示一个清理动作对一个目标产物的处理，保存本次请求的目标、处理状态、逐项结果，以及本项删除限制的状态和建立、解除依据。`outputs` 保存产物自身的可用性和清理事实，清理明细保存某次清理请求的实际处理；同一产物可以被不同清理动作引用，各次请求的结果分别保留。

范围清理通过 `action_dependencies` 保存来源成员，由清理动作自身保存目标集合尚未确定或已经确定的状态。全部来源及其产物处理结束后，完整目标集合、清理明细、集合确定状态及对应历史在同一事务中保存。精确 ID 清理按原请求的目标及顺序保存明细，目标存在性在执行时核实；格式非法的受理失败不生成可执行的清理明细。

下表说明目标明细的存储责任，具体执行资格、取消及恢复仍遵守[清理正式产物](../../architecture/output-cleanup.md)：

| 目标情况 | 明细与产物记录的处理 |
| --- | --- |
| 范围清理尚未确定完整目标集合 | 动作保存尚未确定的状态，不把暂时没有清理明细解释为无需清理 |
| 范围清理已可靠确定目标集合为空 | 动作保存集合已确定和无需清理的结果，不创建占位清理明细 |
| 显式目标尚待核实 | 明细保留请求中的 ID 和未完成状态，尚未确认的产物关联不补造 |
| 数据库可靠确认显式目标不存在 | 明细保存本项失败及原请求 ID，不创建虚假产物；其他合法目标继续按各自规则处理 |
| 目标产物存在，尚需等待已有取回或继续删除、核实结果 | 明细关联实际产物并保存处理进度；等待、删除已发出及结果未知分别表达 |
| 本次确认目标产物此前已完整清理 | 明细保存本次确认成功的结果，沿用产物既有清理完成事实，不新增虚构的删除调用 |
| 本次已可靠完成目标产物清理 | 明细保存本项成功，与受影响产物的清理完成事实及历史共同提交 |
| 本项最终失败或取消 | 明细保留实际结果、错误及已发生的删除或未知事实，不因动作整体结束而抹去副作用 |

目标查询失败或记录无法解释时，按状态库错误处理，不能将其保存为目标不存在。清理动作按逐项结果汇总自身状态；不同目标的结果相互独立，一项失败不撤销另一项已经完成的删除。物理文件删除与存在性查询的尝试记录按各自调用事实组织，不以目标最终状态代替尝试历史。

清理明细属于清理动作自身状态，随该动作进行历史恢复和快照保存；产物自身状态仍遵守产物的历史与快照规则。同一请求重送和重启恢复沿用原明细及已确定结果，新的清理动作建立自己的明细。已有最终结果、继续执行及取消收场的边界遵守[批量清理结果](../../architecture/output-cleanup.md#批量清理结果)和[删除中断后的恢复](../../architecture/output-cleanup.md#删除中断后的恢复)。

## 逐请求的删除限制

`cleanup_items` 保存本清理请求针对目标产物建立的删除限制。同一产物可以关联多个清理项，每项分别保存自己的限制状态及建立、解除依据；记录存在或目标集合已固定，不表示限制已经生效。尚未可靠确认实际产物的请求目标不能建立有效限制。

限制建立遵守[逐产物资格授予顺序](../../architecture/outputs.md#延后执行时的取回与清理顺序)，与清理项状态、受影响的产物投影及对应历史在同一事务中保存。限制可以在等待已有取回结束读取时生效，此时尚无物理删除调用；物理删除意图、尝试与预算继续由公共操作记录保存，不能用是否存在删除尝试代替限制状态。

新取回的资格检查同时读取该产物全部相关清理项的有效限制，以及产物已删除或无法排除删除的事实。检查结果与 `obtain_items` 中的资格授予或逐项失败共同提交；已有取回的资格和读取依赖按原规则保持。为查询维护的产物限制摘要必须从这些事实严格派生，不独立修改。

取消生效后，按下表顺序判断每份产物；删除调用的派发与取消继续遵守所属操作契约：

| 产物及相关清理项的可靠事实 | 限制与后续取回 |
| --- | --- |
| 产物文件已确认清理完成 | 保持已清理、不可取回，取消不撤销清理事实 |
| 尚未确认清理完成，但已发出可能删除文件的调用、已发生删除或无法排除删除发生 | 保持取回限制，保存实际结果与未知依据，不因取消开放尚存文件 |
| 可靠确认本请求未发出删除，其他清理项仍有有效限制 | 仅解除本项可撤销的限制，保留其他清理项的限制 |
| 可靠确认本请求未发出删除，且没有其他限制或可能删除事实 | 解除本项限制，后续取回按实际可用性申请资格 |
| 必要记录或上述事实无法可靠读取和判断 | 按状态库错误及恢复规则处理，不猜测限制已解除或产物可取回 |

例如 C1 和 C2 都对产物 O 建立限制，尚未发出删除。取消 C1 时，只更新 C1 对应清理项的限制与结果；C2 的限制继续有效。限制解除不重新激活已经因限制而失败的取回项，新的取回仍须具有独立请求及执行资格。

限制解除与本项取消处理、受影响投影及历史共同提交；确认回滚时均不生效，提交结果未知时先核实整个事务。重启沿用原清理项、限制依据和已知文件事实，不从动作终态或内存任务是否存在推断限制已消失。限制是清理项自身状态的一部分，由所属清理动作的历史和快照保存；其对产物状态的实际影响按产物历史规则共同记录。

## 取消目标明细

`cancel_items` 的每条记录表示一个取消动作对一个实际目标动作的处理，保存固定的目标关联、取消是否生效、本次处理或等待的进度，以及逐项目标的结果。其处理状态属于本次取消，不能复制目标动作状态来代替：目标已收到取消要求时，必要停止仍可能尚未完成；目标取回已成功时，本次取消仍可能需要撤回尚在 `ready` 的交付文件。

取消执行时按[取消目标寻址](../../architecture/task-cancellation.md#取消目标寻址)解析直接目标及自动预览候选关联，去重后在施加取消或执行停止、撤回之前检查是否包含取消动作自身。检查通过后，按取消资格和联动规则固定实际处理集合，保存目标是直接寻址还是联动选中的依据。拒绝取消的直接目标保留失败明细，不仅因预览存在关联就取消它。集合及其固定事实可靠保存后，逐目标继续处理；同一取消动作针对同一目标只有一条明细，重启和请求重送沿用原集合及已保存进度。目标不存在、集合包含自身和查询结果无法确认，分别按取消契约处理，不创建虚假的目标关联或取消成功结果。

| 本次取消与目标的情况 | 明细及责任归属 |
| --- | --- |
| 目标未终态，取消尚未生效 | 明细保留待处理事实，不以记录存在表示目标已经取消 |
| 目标任务已启动或可能启动，缺少停止能力而拒绝取消 | 明细保存失败、取消未生效及判定依据；不修改目标取消标记，不创建停止流程，不等待原任务结束 |
| 目标取消已生效，必要停止、读取结束或适用清理尚未完成 | 明细保存取消已生效和本次等待进度；目标所属流程独立承担必要处理 |
| 目标已有终态，但仍有适用的撤回等责任 | 保留目标原终态，明细跟踪本次适用处理；没有适用责任时按可靠确认结果结束本项 |
| 本次适用处理已结束 | 明细保存实际成功、失败或未确认原因，取消动作按各项结果汇总；不因一项失败撤销其他目标已生效的取消 |
| 发起取消的动作自身被取消，部分目标已受影响 | 分别保留已生效和未生效事实，停止新增目标取消及适用等待；已生效目标继续必要收场，已有逐项最终结果保持 |
| 发起取消的动作已有终态，目标后续处理取得新结果 | 保留取消动作及其明细的已确定结果，由目标所属记录表达后续进度，不改写原取消结果 |

施加目标取消前先按[设备任务的取消资格](../../architecture/task-cancellation.md#设备任务的取消资格)判断，不能无条件修改目标。拒绝时保存明细结果及历史，目标继续原流程。允许取消时，目标取消事实、相应明细进度和历史按同一业务事务保存；数据库操作结果未知时先核实，不把结束协程等待解释成取消未生效。具体完成条件、取消自身的收场及等待范围遵守[取消动作的完成时机](../../architecture/task-cancellation.md#取消动作的完成时机)和[取消动作自身被取消](../../architecture/task-cancellation.md#取消动作自身被取消)。

多个取消入口触达同一目标时，复用目标已有的操作流程和剩余预算，不为每条取消明细另建一套停止流程。取回目标的逐交付处理由 `cancel_delivery_items` 保存，交付自身事实由交付记录维护。`cancel_items` 属于发起取消动作自身状态，随该动作进行历史恢复和快照保存；目标的必要收场不依赖发起取消动作继续存在于活动调度或继续等待。

## 取消动作的交付处理明细

`cancel_delivery_items` 是 `cancel_items` 的子表，每条记录表示本次取消处理某个取回目标时，对一份实际交付取得的处理进度和结果。记录关联所属取消目标明细与真实交付，交付必须属于该明细指定的取回动作。同一取消目标明细下，同一交付只保存一条处理记录。

一个取回可以包含多份交付，各份文件的位置和撤回结果分别判断。逐项结果按[取消报告契约](../../architecture/report-format.md#取消)生成 `withdrawals`，不能用目标动作的汇总结果代替：

| 本次逐交付处理的可靠事实 | 明细表达与边界 |
| --- | --- |
| 适用的撤回或核实尚未结束 | 保存待处理状态，不提前表达成功或已经不可撤回 |
| 已可靠确认交付撤回完成 | 保存已撤回结果，并关联交付自身的实际撤回事实 |
| 已可靠确认文件进入 `processing` 或已由主程序处理，超出 CLI 撤回权限 | 保存不可撤回结果，不等待主程序，不将其表达为撤回成功或客户端已收到 |
| 撤回明确失败，或有限核实结束后仍无法确认位置或结果 | 保存本项失败和实际原因，不把未知解释为已越过撤回边界 |

文件位于 `ready` 只表示可以按交接规则尝试撤回，不证明撤回已经成功。文件仍在 `staging` 时，适用的取消清理由中间文件生命周期处理，不以撤回记录代替中间文件清理记录。真实文件操作的意图、结果和中断恢复继续遵守交付及取消规则。

`deliveries` 保存交付自身的事实，`cancel_delivery_items` 保存某次取消对该交付的处理结果；两者引用相同的实际撤回依据，不独立维护相互矛盾的事实。多个取消动作涉及同一交付时，各自保存明细，但复用交付已有结果或正在履行的撤回责任，不因增加明细而重复发起文件删除。一次实际结果同时影响交付和本次取消明细时，相关投影与历史按同一业务事务保存。

明细属于发起取消动作自身状态，随该动作进行历史恢复和快照保存。重启及同一请求重送沿用原记录；取消动作自身被取消后，已生效的目标责任继续由目标负责，后续交付变化不改写已经结束的取消处理结果。该表保存业务处理明细，不以每次文件系统调用新增一条记录，也不增加撤回重试预算。
