# 清理读取等待与逐请求协调

[数据库入口](../database-schema.md) · [一致性验收](consistency-verification.md)

## 清理的五维状态与推进顺序

清理动作或成员的业务状态不能独自决定是否还有工作。一个 DELETE 已返回、尝试结果已保存、成员结果尚未保存时，既没有新调用资格，也不能释放原保存责任。清理流程同时判断以下五个维度；本节维护其内部协作含义，业务预算及取消结果分别由[清理正式产物](../../architecture/output-cleanup.md)维护。

| 维度 | 必须区分的事实 | 决策责任 |
| --- | --- | --- |
| 业务资格 | 普通推进、取消收场、成员终态、动作终态；来源、依赖、处理归属、原绑定及对应预算是否满足 | 只决定当前可否新增调用或保存哪类业务结果；已有终态不重开。 |
| 意图事务 | 原申请待提交、确认回滚、提交未知、可靠票据、可靠拒绝且没有尝试 | 不可靠时只处理原申请，不派发、不另扣额度；可靠拒绝不构造票据。 |
| 物理调用 | 本会话可靠未派发、在途或收场中、实际已返回、重启后派发未知 | 只有可靠未派发且对应资格仍成立时可沿原票据派发一次；重启后的意图不授予补发许可。 |
| 本地保存 | 原返回已持有、验证诊断已固定、尝试结束申请待存、结果已存、成员申请待存、伴随流程申请待存、交接完成 | 每阶段持有唯一原申请、key、时刻和来源证据；等待者取消不消灭责任。 |
| 文件事实 | 可靠缺席、最新有效在场、删除效果未知 | 调用错误与可靠观察可以并存；后续可能 DELETE 使旧在场观察失效。 |

每轮先核实数据库身份、原申请及事务可靠性，再接回原在途调用和处理尚未交接的实际结果；原结果可靠保存后，消费文件事实及适用成员、伴随流程保存。完成这些步骤后，才按业务取消、既有终态、当前资格和文件事实判断新调用。普通推进使用[预算决策表](../../architecture/output-cleanup.md#删除与查询的独立尝试预算)，取消只使用[有限核实规则](../../architecture/output-cleanup.md#文件查询与取消的有限核实)。重试间隔届满、工厂重建或缓存缺项都不授予调用资格。

## 原申请与结果保存责任

会话在第一次调用保存接口前接管完整申请和稳定 `operation_key`。已有成员时，责任至少绑定 `database_id`、`item_id`、原票据或尝试、消费用途、完整原申请、原 key、原 `occurred_at` 及原证据；尚无成员的动作开始、集合固定等申请绑定原动作和选择范围。消费用途区分删除结果、删除前核实、删除后核实及取消核实，创建后不随重入重新选择。返回时的单调钟读数需要用于本会话等待时一并持有，不跨进程解释。

同一会话的新 runtime 或 factory 接手同一集合，使用新连接保存或核实原申请；集合不保存旧数据库连接、旧运行时回调或重新执行外部调用的闭包。真实返回在任何解析、验证、状态读取、日志等待及首次写入前进入拥有者。验证失败固定原返回及原诊断，不在重入时重新解释为成功或空观察。进程终止后丢失的内存返回不能重构，只能从可靠历史恢复已保存事实，或按旧尝试恢复资格保存未知。

| 保存阶段或实际回执 | 拥有者的下一步及释放条件 |
| --- | --- |
| 动作开始、目标固定、限制建立等前置申请待存 | 持有完整原申请、key 和时刻；只有可靠回执才能推进依赖该事实的步骤。 |
| 尝试意图原申请待存或提交未知 | 沿原 key 保存或核实完整事务；未知时不派发，也不创建第二个申请增加次数。 |
| 原意图确认回滚 | 资格仍成立时重送原申请及 key；资格已失效时取得原申请可靠未生效或拒绝的处置，取消其派发可能，不创建调用许可或虚构尝试结果。 |
| 可靠拒绝且确认没有尝试 | 交付原拒绝，按业务结果处理；不派发、不保存不存在尝试的结束结果。 |
| 已取得可靠票据，本会话可靠未派发 | 再检查取消和对应调用资格。允许时派发一次；否则阻止迟到派发，沿原票据保存真实 `not_dispatched`，已用次数保留。 |
| 调用在途或收场中，等待者取消或成员状态变化 | 原拥有者继续接回实际结果并完成保存；保持处理归属，不发出同目标冲突调用。 |
| 实际返回已持有，验证未完成或失败 | 先固定完整返回、原时刻及证据，再验证；失败保留原诊断并阻止后续依赖步骤，不丢失返回或重新调用。 |
| 尝试结束申请待存、保存失败、确认回滚或回执未知 | 原申请、key、时刻和完整结果保持；失败按状态库规则处理，回滚重送原申请，未知先核实，均不重复物理调用。DELETE 的不可撤销事实与尝试结果按原边界共同提交。 |
| 尝试结果可靠保存，尚未消费 | 交给原用途消费者；保存尝试结果本身不释放成员、限制、文件事实及伴随流程责任。 |
| 成员成功、失败、取消或额度耗尽申请待存 | 固定唯一原申请、key、时刻及依据；同键核实或重送直至可靠处置。已有成员终态保持，不能用原拟写入值覆盖合法已提交结果。 |
| 成员结果可靠保存，DELETE 或 QUERY 伴随流程仍待结束 | 按实际已提交成员结果形成唯一原伴随申请；沿原 key 核实或重送，清除适用重试等待，已结束流程保持原结果。 |
| 动作汇总、取消结算或后续通知尚未交接 | 持有对应原保存申请及必要通知责任；全部可靠完成后才释放这一阶段。 |

固定原申请不要求无限重试已经失去业务适用性的分支。原保存调用已经结束、原 key 的完整事务已可靠确认不存在（包括确认回滚后的核实），并且后来生效的取消使原申请的取消分支不再适用时，拥有者先可靠结束该申请继续保存的可能，再按当前取消事实形成下一阶段唯一的新申请、key 和形成时刻。旧申请对象保持不变；原 DELETE／QUERY 返回、票据、次数与处理归属继续由原拥有者持有，直到后续合法交接结束。这一处置不授予新的物理调用机会。

原 key 已可靠保存时，先沿原申请核实完整事务并按真实成员终态交接，晚到取消不改写它。原提交仍未知、原 key 暂时无法可靠核实或原保存调用仍可能提交时，继续持有原申请，不形成替代申请。普通输入输出错误、SQLite 错误或保存失败本身不表示业务拒绝，不能作为替换原申请的依据。

上述责任覆盖保存接口抛错、可靠回滚、提交未知、回执验证失败及等待取消。持久化错误不是文件业务结论，不能降格为未删除或结果未知的成员终态。事务完整性和同键输入核对遵守[公共事务契约](transactions.md#公共完成与失败契约)。无法可靠核实原申请时，保留责任并进入状态库错误处理，不通过更换 key、时刻、消费用途或新外部调用取得替代结果。

## 持久化发现与原结果消费

清理发现分别从会话本地保存集合和持久化责任分批读取候选，并按数据库及原成员身份去重。持久化查询采用[限定范围、稳定游标及批量上限](transactions.md#查询接口与分页)，只持有当前批次和续读位置，不一次缓存全部历史动作、成员或尝试；查询错误不能返回空批作为扫描结束。持久化发现至少覆盖未结束清理成员、任何流程终态下仍为 `RUNNING` 的 DELETE／QUERY 尝试、已保存结果但成员尚未交接的尝试，以及成员终态后仍未结束的伴随流程。动作或成员已终态不排除这些残留候选；发现不能只依赖运行中动作、当前驱动目录或进程内缓存。

| 发现的责任 | 允许处理及边界 |
| --- | --- |
| 同一会话仍持有原申请、返回或实际调用 | 先接手原拥有者，不以持久化缺少结果覆盖它，也不启动旧尝试恢复。 |
| 原 DELETE 或 QUERY 已可靠保存结果，成员尚未完成交接 | 恢复原结果及完整事务后消费，先完成必要本地保存，再判断新调用。 |
| 成员已经终态，仍有原结果待交接或伴随流程未结束 | 保存合法迟到事实、核实原成员终态并结束伴随责任；不改写成员或动作原终态，不授予新的普通调用。 |
| 旧尝试仍为 `RUNNING` | 按[恢复资格](#旧-running-尝试的恢复资格)结束原尝试，或保留具体诊断；不能因所属流程终态而遗漏或直接删掉。 |
| 终态成员关联的尝试没有适用收场依据，或同产物存在多个处理者 | 保留原记录，报告一致性错误；不能靠重开成员或选择其他处理者绕过。 |
| 必要本地和持久化交接均完成，仅剩永久保存的终态历史 | 不构成新的执行责任，不重新消费以产生尝试、报告变化或计数。 |

DELETE 与 QUERY 都具有从原历史恢复结果的入口。消费者核对原流程种类、责任键、动作、成员及目标关联，读取原尝试的状态、效果、错误、完整 `result_json`、结果事件和所属完整事务，核对历史前后值与投影相符。原结果的类型、版本及结构由对应历史解释规则读取，不用当前驱动注册表重新验证；无法解释时保留诊断并按状态库错误处理，不跳过结果改做新查询。当前设备缺失、绑定变化或能力关闭不阻止这一步，新的设备调用仍独立检查这些条件。

原 DELETE 返回的缺席及错误可共同消费，不为确认已经可靠保存的缺席追加查询。原 QUERY 的观察只在没有更新的可能 DELETE 时作为当前文件事实；新查询仍在途时不跳过它复用更早结果。原保存时刻及证据保持，后来才进行的成员或伴随保存使用各自真实形成的时刻，一旦申请形成即固定。完成事实、限制和产物汇总按各自共同提交边界保存；已有成员终态不因迟到观察而重开，后续可靠文件事实仍可更新产物自身。

### 终态成员的可靠缺席交接

删除尝试已经可靠保存文件缺席，成员成功尚未保存时退出，历史流程可能随后因设备绑定异常保存成员失败。该成员、流程和动作即使都已终态，原结果中的文件事实仍须交接。下列记录分别处理，不能把成员终态当作文件事实已经保存的证明。

| 原成员、尝试及结果的可靠事实 | 处理 |
| --- | --- |
| 成员已终态，原物理尝试仍为 `RUNNING` 或没有适用结束依据 | 报告一致性错误；不补造缺席或恢复结果来消除矛盾。 |
| 原尝试已保存未知，后来返回缺席，但结束申请取得 `ALREADY_ENDED` | 消费原已保存结果，保留差异诊断；未进入原可靠结果的迟到返回不授予缺席交接。 |
| 原 DELETE 或 QUERY 的完整结果已保存可靠缺席，但承载文件及产物尚未共同保存清理完成 | 独立交接原缺席事实，保留成员、动作及流程原终态，不新增物理调用或尝试。 |
| 文件已具有可靠缺席事实，产物尚未保存清理完成 | 核实原清理结果来源后，只保存实际变化的产物完成观察，不生成空文件事件。 |
| 产物已为 `CLEANED/COMPLETED`，承载文件却不符合完成事实 | 报告一致性错误，不单独补文件事件来掩盖已有投影矛盾。 |
| 承载文件及产物已经共同保存可靠清理完成 | 只读完成交接，不产生重复历史、报告变化或次数。 |

缺席交接申请绑定原数据库、成员、完整票据、结果事件及其完整事务、产物和唯一承载文件。写事务重新读取原历史并核对这些关联及观察类型、版本和目标，不接受调用者独立传入的缺席布尔值、仅有的效果状态、当前路径检查或当前驱动声明。原调用错误与可靠缺席可以并存，错误继续保留在原尝试中。原结果事件唯一确定原结果事务及其操作键；新交接通过[历史来源引用](history-formats.md#事件正文版本-1)关联该事件，不重复存储可从原事件还原的票据及目标清单。

交接在同一事务保存设备文件 `ABSENT` 或主机正式源文件清理 `COMPLETED`，以及对应产物的 `availability=CLEANED`、`cleanup_status=COMPLETED` 和清理汇总错误清除，并保存适用报告变化。该事务不修改成员的状态、完成依据、终态事件、错误及限制，也不修改动作、流程、尝试、次数或配置；伴随流程另按原实际成员终态结束。清理完成事实按[汇总优先级](output-cleanup-state.md#总体状态的判定)持续优先，后续限制或失败事务不能将它退回未完成。普通文件缺失不独自构成清理完成，仍须具有原清理结果的可靠依据。

会话首次保存前持有唯一完整交接申请、操作键和真实形成时刻，沿前述原申请规则处理回滚、提交未知、取消及 runtime 重建。来源结果及其发生时刻保持，新文件事实使用新交接事件的时刻，不回写历史边界之前的投影。交接保存命令严格限定完整事件组，拒绝只保存文件或产生空事件；携带来源的产物观察守卫核对原结果关联和本事件之前已经成立的文件完成事实，原键核实再检查原完整事务。普通文件观察继续按自身契约独立保存，不因没有清理来源引用而被解释成清理交接。独立发现覆盖所有动作、成员和流程均终态的未交接缺席；可靠完成后不再作为候选，不能仅因关闭伴随流程而遗漏它。

## 旧 RUNNING 尝试的恢复资格

启动恢复固定一次完整已提交历史上界 H，并沿用会话调用方提供的旧本地执行收场边界。H 在本会话开始普通执行前取得，之后不随新事务推进；恢复比较原尝试 `intent_event_id <= H`。同一进程重建 runtime 或 factory 不重新授予边界，也不把当前会话新尝试纳入旧尝试集合。

| 旧尝试及恢复前提 | 处理 |
| --- | --- |
| 原意图、尝试、目标、结果引用或完整事务不可靠 | 按状态库错误或原 key 核实规则处理，先停止依赖步骤。 |
| 已有可靠结果，或本会话拥有者可接回实际结果 | 保存或消费原结果，不用恢复 UNKNOWN 覆盖。 |
| 无可靠结束结果，旧本地执行已确认停止，原意图不晚于 H，且原操作明确登记适用恢复证据及版本 | 沿原尝试、原目标及原次数保存 UNKNOWN 恢复结果，记录本次恢复依据；可靠保存并消费后，才按当前普通或取消资格和剩余预算核实。 |
| 缺少旧本地收场保证、H、原操作恢复支持，或意图晚于 H | 保留 `RUNNING` 和具体诊断，阻止依赖该收场的调用；不生成未派发或成功结果，不使用新票据绕过。 |

正式会话发现旧尝试无法取得上述恢复资格，且没有本会话拥有者可接回实际结果时，无法完成必要的历史解释及收场职责，按一致性错误进入[状态库错误退出](../../architecture/session-errors.md#错误标识)。原尝试、成员、动作及诊断保持，不循环等待不会自行改变的恢复前提，不保存业务失败或取消终态来替代调用收场。当前会话仍在途、可靠未派发或已经持有结果的调用先由原拥有者处理，不因其意图晚于 H 而套用旧尝试恢复错误；当前设备绑定异常仍按[设备绑定异常的影响范围](../../architecture/configuration.md#设备绑定异常的影响范围)单独判断。

ADB 原操作使用[ADB 恢复记录](operation-fields.md#第一版-adb-未完成调用的恢复记录)；主机正式源使用[主机文件恢复记录](operation-fields.md#主机正式源未完成调用的恢复记录)。两种恢复都不重放旧票据、不退还次数、不补造原返回、退出码、超时、宽限或丢失的原发生时刻。旧本地工作结束不证明文件效果，原恢复结果与后来文件观察分别保存。共享恢复边界及诊断可以放在通用操作层，不能要求清理依赖拍摄任务运行时。

## 清理读取等待与待删除状态

清理项 C 已核实产物 O 并建立本项删除限制，但尚未取得清理处理归属时，保存 `PENDING_DELETE`。这个状态表达待处理责任。程序按 O 查询 `obtain_items.source_dependency = 1` 的取回项，判断当前是否仍须保留源文件；查询结果用于执行检查。

### 建立删除限制与待处理责任

清理流程在同一写事务内核对目标、执行资格及逐产物排序，保存本项限制、处理阶段及适用产物汇总。按以下顺序分类：

| 事务内的可靠事实 | 保存和处理 |
| --- | --- |
| 必要记录不可读、矛盾或提交未知 | 按状态库错误或原事务核实规则处理，不推断没有读取者 |
| 本项已有最终结果，或取消已经生效 | 保留结果，或按取消规则完成必要收场，不建立新的普通处理责任 |
| 尚未到时间、来源或目标尚未满足条件 | 继续所属阶段，不提前建立限制 |
| 目标此前已可靠清理完成 | 按既有规则保存本项成功，不补造删除调用 |
| 本项具备建立限制的资格，目标可靠且仍需清理 | 共同保存本项有效限制和 `PENDING_DELETE`，不论当前有零个、一个或多个源依赖 |

`PENDING_DELETE` 要求真实产物及本项有效删除限制；已有源依赖合法地与它并存。有效限制阻止新的取回取得资格，已经授予的资格和源保护保持原效力。建立限制不消耗调用次数、不预留实际处理归属，也不证明文件删除已经开始。

取得处理归属前，流程重新检查取消、源依赖、目标事实、同产物处理者、设备条件、排序和所需调用预算。当前持有者由 `DELETING` 表达，具体分类见[下一清理项的选择](#下一清理项的选择)。所需条件在同一写事务内核对，不能在事务外查到无依赖后直接保存删除意图。`DELETING` 与有效源依赖同时存在属于一致性错误，不能继续派发删除。

### 源依赖解除与重新调度

取回 R1、R2 都保护 O，清理 C1、C2 已建立限制时，C1、C2 均为 `PENDING_DELETE`。R1 解除依赖后，R2 仍保护 O，清理不能取得处理归属；R2 也解除依赖后，清理流程才可按其他条件和顺序选择处理者。C1、C2 自身事实没有变化时保持原记录。

解除源依赖的事务共同保存副本可靠准备完成，或失败、取消后的实际读取及重试停止依据，并把对应取回项的 `source_dependency` 置为 0，保存自身历史及适用目录。取回仅收到取消而读取尚未停止时，依赖继续保留。一次解除多项依赖时，以本次拟提交的完整事实为准。

提交成功后按受影响产物安排清理重新检查。检查发现仍有源依赖则继续等待，发现没有源依赖则按候选规则推进；通知本身不授予处理归属。实现可以合并同一产物的检查请求，必须覆盖全部相关未完成责任。通知与等待交接、原协程取消后的结果接手遵守[调度通知契约](../implementation.md#调度通知与待处理工作的交接)。

限制与取回资格的竞争遵守[逐产物资格顺序](../../architecture/outputs.md#延后执行时的取回与清理顺序)：取回资格先成立则保留保护，删除限制先成立则阻止新的资格。限制生效后，已经解除的源依赖不重新开启。

### 取消与依赖解除的交错

清理项尚未取得处理归属、可靠确认本项没有已派发或可能迟到派发的删除且无其他收场责任时，取消事务保存本项取消、最终结果事件和可撤销限制的解除，并共同更新适用产物汇总。取消不要求等待取回结束。

| 事务顺序或已有阶段 | 清理项及限制的处理 |
| --- | --- |
| 清理取消先提交，源依赖随后解除 | 保持取消结果；依赖解除通知不重新开启该项 |
| 源依赖先解除，清理随后取消，尚未取得处理归属 | 保持待处理责任直到取消事务保存结果；满足条件时解除本项可撤销限制 |
| 本项已进入 `DELETING`，随后取消 | 按原尝试意图、实际派发及收场事实处理，不能仅因收到取消就释放处理归属 |
| 已有成功、失败或取消结果 | 保持原结果，其他取回或清理请求变化不重新开启 |
| C1 取消但 C2 的限制仍有效 | 只解除 C1 可以撤销的限制，O 继续受 C2 限制 |
| 本项已经或可能发出删除 | 按不可撤销限制及结果核实规则处理，不从协程结束推断删除未发生 |

### 历史、汇总与恢复

清理项、限制和最终结果属于所属清理动作的历史。取回项的源依赖变化属于取回自身事实；仅源依赖变化而清理项没有变化时，不为清理动作追加虚构状态变化。需要按历史边界判断源保护时，在同一 H 查询相关对象的事实，不读取最新取回状态解释过去。

产物总体阶段继续由 `outputs.cleanup_status` 保存。有效待处理项对应 `pending`；所选项进入 `DELETING` 时按[产物汇总](output-cleanup-state.md)共同保存 `running` 及相关事实。当前项结束而仍有有效待处理项时，总体阶段回到 `pending`；可靠清理完成事实按原优先级处理。源依赖解除本身不改变待处理阶段，汇总及其他产物事实未变时不重复写入产物历史。

| 保存结果或恢复时的记录 | 处理 |
| --- | --- |
| 源依赖解除未提交或确认回滚 | 原依赖继续有效，核实原副本及调用责任，不开放删除 |
| 源依赖解除已提交，进程继续运行 | 负责流程触发受影响产物的清理检查 |
| 源依赖解除提交后、通知前退出 | 下一次实际启动发现 `PENDING_DELETE` 责任，重新检查依赖和已有处理归属 |
| 限制、归属或结果的提交未知 | 核实原事务，确认前不创建替代责任或派发调用 |
| 必需限制、目标、归属或结果记录矛盾 | 按一致性错误处理；待处理项有源依赖本身是合法状态 |

查询与恢复按产物及未完成责任分批进行，缓存不包含某个请求不代表该请求不存在。已保存的处理者优先恢复；其余请求按可靠排序重新选择。历史回放只恢复记录，不启动删除；旧报告直接恢复已保存的产物汇总及所需同边界事实。

## 同一产物的清理协调与结果复用

同一产物的保留文件在同一时刻由一个清理项连续推进删除、结果核实和有限重试。各清理项保留自己的删除限制、删除流程、存在性查询流程、累计次数及最终结果；文件实际状态和可靠清理完成事实可供其他请求使用。该规则适用于设备正式源与主机正式源，具体调用仍遵守各自的驱动或本地文件契约。

当前处理归属由 `cleanup_items.status = DELETING` 表达。同一 `output_id` 在完整已提交边界最多有一个清理项处于该状态，且该项必须关联真实产物。该归属约束同一目标的操作，不授予超出清理请求的权限；源依赖、取消、设备条件和各类预算继续独立检查。

### 处理状态与归属

`DELETING` 表示本项已经负责该产物的清理处理，且尚未完成本项责任及必要收场。该阶段覆盖删除、存在性查询、重试等待和取消收场；具体调用是否已经派发、采用何种收场依据及产生何种效果，由流程、尝试和相应依据表达。调用收场可以依据实际结束证据，或符合适用条件的驱动运行假设；第一版 ADB 普通前台命令遵守[驱动运行假设](../../architecture/adb-execution.md#第一版普通前台命令的运行假设)，本地文件操作继续等待实际返回。

| 清理项的阶段或已取得事实 | 状态与处理归属 |
| --- | --- |
| 尚未核实目标、等待读取或等待其他清理项处理 | 保持所属未处理阶段；`PENDING_DELETE` 等状态不持有处理归属 |
| 具备处理资格并取得该产物的清理责任 | 进入 `DELETING`，持有处理归属；状态本身不证明物理删除已经发生 |
| 正在删除、查询，或仍有资格等待有限重试 | 保持 `DELETING`，连续处理同一目标 |
| 调用超时或发生错误，尚未完成收场 | 尝试保持 `RUNNING`，清理项保持 `DELETING`；执行流程继续收场 |
| 已保存动作取消事实，当前调用或其他收场责任尚未结束 | 保持 `DELETING`；取消阻止新增普通调用，原调用及收场继续跟踪 |
| 调用已具备适用收场依据或确认不会再执行，但仍需本项核实、重试或保存必要结果 | 保持 `DELETING`，继续所属责任，不提前让其他请求接手 |
| 本项责任和必要收场完成，结果及相关事实可靠保存 | 进入适用终态，处理归属随该状态变化释放 |

进入 `DELETING` 时，在写事务中核对本项执行资格、源依赖和同一产物当前处理者；已有其他处理者时继续等待。首次取得处理归属、创建所需操作流程及登记第一次尝试共同提交，具体规则见下文。退出该阶段只进入适用终态，重试、查询及取消收场均在该阶段内推进。终态事务共同保存本项结果及必要收场事实；事务结果未确认前，其他请求不能据猜测接手。

尝试结果、动作取消事实和清理项终态具有不同含义。取消事实按其生效规则及时保存；普通尝试的结束结果在其调用收场后保存。保存尝试结束结果时，本项仍有核实、重试或其他必要责任的，清理项继续处于 `DELETING`。取消生效后，调度依据取消事实停止新增普通调用；当前调用取得适用收场依据后，清理项按实际结果及取消契约结束。清理项已经终态时，其相关调用必须具有适用收场依据或确认不会再执行，必要结果必须已可靠保存。

调用具备适用收场依据而删除效果仍未知时，仍具备核实资格的项按有限核实规则处理，取消已生效的项按取消收场规则处理。适用责任已经结束后，可以保存带实际未知原因的最终结果并退出 `DELETING`。处理归属释放不要求文件效果一定已知；删除限制是否解除仍按逐请求限制及实际文件事实判断。已结束的流程、尝试及其历史继续保留，当前处理者按清理项状态确定。

查询或恢复发现同一产物有多个 `DELETING` 项，或者清理项已终态但相关调用仍缺少适用收场依据时，按一致性错误处理，不任取一个处理者或直接开放后续操作。

### 连续处理与接手条件

清理项 C1 取得产物 O 的处理归属后，在删除调用、存在性核实及适用重试间隔期间保持归属。其他已满足读取保护条件、尚未开始处理的清理项保持 `PENDING_DELETE`，不替 C1 发出删除或查询，也不因排队消耗次数。

后续清理项接手前，C1 必须已经满足上述清理项终态条件并可靠保存终态，当前产物没有其他 `DELETING` 项；后续项仍须满足自身执行资格。取消标记、协程结束、调用超时或单个操作流程终态均不代替清理项的完成判定。

| C1 的责任与实际操作情况 | 对 O 的处理归属及后续请求 |
| --- | --- |
| 归属、目标、调用或结果记录缺失、矛盾或不可读 | 按状态库错误处理，不通过选择另一请求绕过 |
| C1 仍有执行资格，正在删除、核实或等待允许的重试 | 保持 C1 的归属，其他请求继续等待 |
| C1 已收到取消，调用尚无适用收场依据 | 阻止 C1 后续普通调用，跟踪现有调用；其他请求不接手操作 |
| C1 已取得结束依据，但必要结果尚未可靠保存，或终态事务结果未知 | 未提交时保持 `DELETING`，提交未知时核实原事务；其他请求不据此接手 |
| C1 已满足收场条件并可靠保存清理项终态，文件结论为已清理或仍存在 | 其他仍有效请求可按自身资格接手或使用清理完成事实 |
| C1 已满足收场条件并可靠保存清理项终态，文件结论是删除效果未知 | 保留未知及删除限制；其他仍有效请求可接手，但须先按自己的查询预算核实 |

上述接手允许由此前已经排队的有效请求承担。C1 最终失败后，C2 使用自己的授权与预算继续，不要求 C2 必须在 C1 失败后才提交。C1 的失败或取消保持原结果；同一请求重送不新建清理责任或补充预算。

### 下一清理项的选择

产物 O 由 C1 处理，C2 和 C3 都在等待时，C1 在删除、查询、重试等待及取消收场期间保持处理归属。C1 可靠保存终态后，若 O 仍需操作，则从当时具备条件的清理项中选择下一项。例如 C2 的计划时间为 10:05，C3 为 10:03，两者均具备条件时由 C3 接手；若 C1 已可靠保存清理完成事实，则仍有效且满足结果确认条件的 C2、C3 分别保存 `already_cleaned`，无需排队取得操作归属。

对同一产物，调度器先按下表自上而下分类。表中的执行条件按当前所需步骤判断：读取数据库中已保存的完成事实，不要求具有外部删除或查询的调用额度。

| 当前可靠事实 | 调度处理 |
| --- | --- |
| 判定所需的记录或排序依据缺失、矛盾、不可读，或相关事务提交结果未知 | 先按状态库错误或原事务核实规则处理，不通过跳过该候选来绕过错误 |
| 本项已有最终结果，或取消已经生效 | 保留原结果，或按取消规则结束等待及完成必要收场；不参与普通接手排序 |
| 本项尚未到计划时间，或来源、目标集合等前置条件尚未满足 | 继续相应等待，不提前取得处理归属；其他具备条件的项可以推进 |
| 已有可靠清理完成事实，本项满足结果确认条件且没有未完成收场责任 | 保存本项成功；尚未开始处理的项保存 `already_cleaned`，不创建调用，不参加操作接手排序 |
| 本项已可靠确认存在应当结束责任的执行错误或所需预算耗尽，且没有未完成收场责任 | 按所属错误规则保存最终结果，不无限保留为待接手候选 |
| 本项已经处于 `DELETING` | 沿原处理归属、流程及预算继续执行或收场，不重新竞争 |
| 本项尚未开始处理，产物仍有有效源依赖 | 保持 `PENDING_DELETE`，不参加操作接手排序 |
| 本项尚未开始处理，其他清理项仍处于 `DELETING` | 保持 `PENDING_DELETE`，不代替当前处理者发出查询或删除，不消耗次数 |
| 没有当前处理者，但本项所需步骤仍有其他适用等待条件 | 继续所属等待，不提前预留处理归属 |
| 没有当前处理者，本项满足执行条件且仍需查询或删除 | 参加下述排序；被选中后按共同建档规则取得处理归属 |

操作候选必须已具备建立删除限制的资格，关联可靠目标，满足源依赖保护条件，且处于 `PENDING_DELETE`。候选发现依据可靠业务事实，不以某个协程是否已经保存自己的选择结果作为唯一门槛；相关来源及选择条件已经满足时，统一调度须纳入相应请求并按业务顺序完成必要选择和状态保存，再授予操作归属。[逐产物资格授予顺序](../../architecture/outputs.md#延后执行时的取回与清理顺序)继续决定取回资格和删除限制，接手排序不撤销这些既有事实。

当前合格候选按以下持久化依据依次升序比较：

1. 所属清理动作的 `scheduled_at`。
2. 所属计划的 `plans.id`，表示首次成功受理顺序。
3. 所属动作的 `actions.input_index`，表示原动作数组位置。

同一动作对同一产物只有一条清理明细，因此上述依据足以确定同一产物候选之间的顺序。不同产物分别选择处理者，本规则不建立跨产物的全局串行队列；实际调用仍须满足设备及本地文件操作约束。计划受理顺序和原数组位置的含义沿用[计划与动作字段](plans-actions.md)，不以墙钟受理时间、明细创建顺序、查询返回顺序或协程唤醒顺序代替。

排队项尚未取得处理归属。后来受理但计划时间更早的请求，在具备条件后可以排在原等待项之前；任何后来候选都不能打断已经可靠进入 `DELETING` 的项。正常调度和重启恢复采用同一规则，重送请求不重新分配排序依据。

### 接手事务与调度恢复

前一项保存终态与下一项取得处理归属可以使用两个事务。前一事务共同保存前一项结果及必要事实，并通过进入终态释放归属；后一事务重新核对候选资格、排序、取消、目标事实及当前处理者，按下文规则共同保存所选项的 `DELETING`、所需流程、首次尝试、配置及额度，成功提交后派发调用。

| 中断或事务情况 | 后续处理 |
| --- | --- |
| 前一项终态事务尚未提交或明确回滚 | 保持原处理归属，下一项不接手 |
| 前一项终态已提交，下一项尚未建档或建档明确回滚 | 当前没有处理者，从届时具备条件的候选重新选择；内存中曾选中的项不享有预留资格 |
| 下一项建档已提交 | 沿该项已经保存的处理归属、身份和额度恢复，不因另有更早候选而换人 |
| 任一相关事务提交结果未知 | 先核实原事务，再按已确认的完整状态处理，不重复建档或提前调用 |

清理限制建立、源依赖解除、当前项终态、取消生效、设备条件变化及适用截止时间分别触发重新调度。新请求沿现有计划发现机制进入执行；启动恢复依据持久化状态检查待处理项，覆盖提交后通知前退出。运行期间的通知交接遵守上述调度契约。排队顺序从上述依据计算，不另存接班者关联或持久化排队序号。历史回放恢复当时实际保存的状态与处理归属，不按后来的候选重新决定历史处理者，也不执行外部操作。

### 独立流程与尝试预算

每个清理项分别拥有删除和存在性查询责任。一次尝试只归属实际承担该调用的流程；删除与查询分别累计，重试、重启和配置变化不清零。新的调用继续按原契约先保存尝试身份、意图及额度，再派发；失败、超时、未知及派发前中断均不退还已经可靠占用的额度。

排队、查询数据库中的资格及读取已保存的清理完成事实，不构成外部文件查询，不消耗删除或查询次数。C1 删除一次、查询两次后成功，C2 使用该完成事实时不复制 C1 的尝试，不消耗 C2 的调用额度，也不把两者累计次数合并。

### 流程关联与按需创建

删除和存在性查询流程通过 `operation_runs.cleanup_item_id` 单向引用所属清理项。每个清理项的每种流程最多一个；删除流程的类型为 `DELETE_FILE`，责任键为 `delete/<cleanup_item_id>`，查询流程的类型为 `CHECK_FILE_EXISTS`，责任键为 `exists/<cleanup_item_id>`。流程的 `action_id` 必须与清理项的所属动作一致，目标必须是该项关联的真实产物。清理项通过自身编号及流程种类查找关联流程；尝试通过 `operation_attempts.run_id` 归属流程。

每种流程在首次需要且允许执行该种调用时，与第一次尝试共同创建。清理项 C1 首次删除就取得可靠成功时，只建立删除流程；后来 C2 使用该产物已有的清理完成事实时，可以直接保存 `already_cleaned`，没有删除或查询流程。先核实此前删除效果的清理项先建立查询流程，确认仍存在且允许删除时再建立删除流程。

首次进入处理阶段时，在同一写事务中核对执行资格、取消、源依赖、处理归属、目标依据及调用预算，将清理项从 `PENDING_DELETE` 改为 `DELETING`，创建本次所需流程，登记第一次尝试、调用意图、实际采用配置及已占用额度，并共同保存历史、投影和适用报告变化关联。完整已提交状态中，首次取得处理归属的清理项已具有对应流程及第一次尝试；实际调用在提交成功后派发。

判断依次检查记录可靠性、已有终态及取消事实，再判断执行资格、处理归属、文件事实及预算。状态库错误不进入普通业务分支；下表中的调用分支均要求相应执行前提满足。

| 当前事实与所需操作 | 保存和执行行为 |
| --- | --- |
| 必需记录缺失、矛盾或不可读，或者前一相关事务结果未知 | 按状态库错误或原事务核实规则处理，不创建替代流程 |
| 清理项已有终态，或取消已经生效 | 保持已有结果，或按取消收场处理；不新建普通调用流程或尝试 |
| 其他必要执行条件不满足 | 按对应等待或错误规则处理，不以创建流程代替资格判断 |
| 已有可靠清理完成事实，本项没有未收场的调用，也没有其他未完成收场责任 | 保存本项成功及相应结果；尚未开始处理的项直接保存 `already_cleaned`，无需取得处理归属或创建流程 |
| 尚有源依赖，或其他清理项持有该产物的处理归属 | 保持对应等待状态，不创建流程、不消耗调用次数 |
| 尚未进入处理阶段，需要先核实可能发生的删除，且查询预算允许 | 共同取得处理归属、创建查询流程及第一次查询尝试，删除流程仍未建立 |
| 尚未进入处理阶段，具备直接删除依据，且删除预算允许 | 共同取得处理归属、创建删除流程及第一次删除尝试，查询流程仍未建立 |
| 已在处理阶段，首次需要另一种操作且允许调用 | 保持 `DELETING`，共同创建该种流程及第一次尝试 |
| 已有对应流程，仍具备继续尝试资格且适用重试间隔已结束 | 复用原流程，登记新尝试并递增累计次数，提交后派发 |
| 已有对应流程，尚在适用重试间隔内 | 保持原流程及 `DELETING`，继续等待，不提前占用下一次额度 |
| 所需操作的预算已耗尽，或所属责任已经结束 | 按有限处理及清理项收场规则保存结果，不新建流程延长责任或重置次数 |

查询成功只结束本次尝试。查询确认文件仍存在时，查询流程保持 `ACTIVE`；后续删除若仍需核实，继续使用该查询流程和累计次数。清理目标结束或明确放弃核实时，流程按所属责任结束；后续可靠文件事实不重开已结束流程。流程及尝试创建、后续结果和累计次数均属于所属清理动作的历史及快照。

流程存在表示曾经建立对应操作责任，当前处理者仍由清理项的 `DELETING` 状态确定。某种流程从未建立，表示该项尚未登记该种调用的尝试；已有尝试、创建历史或其他可靠事实要求该流程存在时，流程缺失属于一致性错误。类型、责任键、目标或动作归属不一致，以及同一项同一种流程重复，也按一致性错误处理。

### 流程创建的失败与恢复

| 首次处理事务或后续首次创建流程的结果 | 恢复规则 |
| --- | --- |
| 尚未提交，或确认整体回滚 | 本次新增流程和尝试未生效，不派发依赖本次提交的调用；首次取得处理归属也未生效，原有已提交责任保持 |
| 提交成功，实际调用尚未派发 | 沿原清理项、流程和尝试继续，已占用次数保留；派发前仍检查取消及适用执行条件 |
| 提交成功，但无法可靠确认调用是否已经派发或产生效果 | 按原尝试的派发及效果核实规则恢复，不因流程存在就重发删除，也不因缺少成功结果就断言没有执行 |
| 提交结果未知 | 沿原稳定事务身份核实完整提交结果，确认前不另建流程或派发依赖步骤 |
| 已有责任要求流程存在，但流程缺失、重复或归属不一致 | 按状态库错误处理，不补建替代流程、不重置预算、不任取一条记录 |

历史恢复在同一完整事务边界还原清理项、流程和尝试。首次提交之前没有本次归属、流程及尝试，首次提交之后三者共同存在；后来首次使用另一种操作时，其流程和第一次尝试同样共同出现。历史回放恢复身份、状态、依据和次数，不派发外部调用。

### 接手时的文件事实与后续操作

后续请求先核对自身取消、终态、执行资格及前述接手条件。已有终态保持，已取消请求按自身收场规则处理；记录错误优先按状态库错误处理。对仍有资格的 C2，按下表顺序使用可靠文件事实；恢复要求核实时，不能仅凭旧的存在记录进入直接删除分支。

| 目标文件的可靠事实 | C2 的预算条件 | C2 的处理 |
| --- | --- | --- |
| 已可靠保存清理完成 | 不需要额外调用额度 | 保存本项成功及 `already_cleaned`，不创建虚假的删除或查询尝试 |
| 前一次删除可能发生但效果仍未知，或按恢复契约需要核实实际状态 | 查询额度有余 | 使用 C2 的查询流程核实，不直接重新删除 |
| 同上 | 查询额度耗尽 | 保存 C2 本项最终失败并保留未知，不以删除代替核实 |
| 尚未发生删除且具备直接删除依据，或最新有效观察确认文件仍存在且不存在尚待核实的删除效果 | 删除额度有余 | 使用 C2 的删除流程占用一次额度，按调用契约删除 |
| 同上 | 删除额度耗尽 | 保存 C2 本项最终失败，不派发删除 |

查询取得可靠不存在证据时，保存实际观察及清理完成事实，按 `absence_confirmed` 表达本项成功。查询确认仍存在后，按 C2 自己的剩余删除预算和适用间隔继续。查询失败或响应无法解释时保留未知，依 C2 剩余查询预算决定有限重试或最终失败；不能用另一个请求的未用额度延长 C2 的责任。

文件观察的有效性取决于观察之后的实际操作。先查询到文件存在、随后又有一次可能执行但结果未知的删除时，旧存在记录不能作为直接再次删除的依据。历史保留原观察，但当前判定必须包含后续可能改变文件状态的操作。外部操作实际结束与其效果是否已知分别保存和解释。

### 请求结果、历史与恢复

C1 已失败或取消，后来 C2 清理成功时，更新产物及文件的可靠清理事实，保存 C2 自己的结果；C1 的原终态、尝试、错误和限制历史继续保留。后续成功不将早先失败或取消改成成功。

C1 成功后，尚未结束且未被取消的 C2 可使用可靠完成事实保存 `already_cleaned`。该确认是 C2 自己的新事实，进入 C2 的历史与快照。恢复 C2 在历史边界 H 的状态时，只采用 H 之前已经保存的本项结果；不能凭产物后来的完成状态，把 C2 当时的待处理状态改成成功。实际文件事实按[独立文件历史](outputs-files.md#文件独立历史与关联查询)恢复到同一 H。

重启从 `DELETING` 清理项恢复当前处理归属，沿用原流程、尝试及累计次数，按实际调用和文件效果的恢复规则继续。重试等待仍属于原清理项，不因重启换用排队请求的预算。进入处理阶段、结果保存或进入终态的提交结果未知时，先核实原事务，不同时让两个请求推进同一文件。状态变化属于清理动作自身历史及快照；历史回放恢复相应边界的状态和处理归属，不派发删除或查询。
