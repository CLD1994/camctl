# 操作尝试与设备执行记录

[数据库设计入口](../database-schema.md) · [CLI 资料入口](../README.md)

本页定义公共操作流程与尝试、设备持续活动以及录像内部处理的存储职责。公共操作模型也服务于文件读取和清理；各流程的执行资格、预算及恢复条件由所属业务契约决定。

## 操作流程与尝试的公共模型

操作流程与业务尝试分别组织，并复用公共记录结构。一个操作流程表示所属业务针对明确目标承担的一项具体操作责任；一次尝试表示该流程按业务规则开始的一次执行。流程保存归属、目标、适用的预算及整体处理状态，尝试保存自身身份、执行进度和实际结果。哪些情况开始新流程、开始新尝试或继续已有尝试，由所属业务契约决定。

| 公共表 | 一条记录的职责 | 归属与生命周期 |
| --- | --- | --- |
| `operation_runs` | 一个具体操作流程，保存其业务归属、操作责任、目标、适用预算和整体处理状态 | 流程身份由所属业务确定，可以跨多次 `camctl run` 存续；表名中的 `runs` 不表示 CLI 会话 |
| `operation_attempts` | 一个操作流程下的一次业务尝试，保存尝试身份、执行进度和实际结果 | 每条尝试只属于一个流程；恢复已有尝试与开始新尝试按业务规则区分，单次底层调用不自动产生新尝试 |

公共记录负责可靠保存身份、预算消耗和执行事实；业务流程负责判断执行资格、成功条件、安全重试和恢复方式。文件可靠进度、整片重拷轮次、持续设备活动、文件选择依据及删除限制等专属状态，继续由各自业务记录管理。公共模型不根据统一的成功或失败标签自行调度重试，也不替代设备或文件状态核实。

操作流程跨运行保留累计次数，新增尝试使用本次运行的上限。流程或尝试保存的上限、超时等值表达实际采用的历史依据；后续运行的资格判断从本次配置取得值，不将旧依据作为不可修改的执行配置。降低上限后，累计次数允许大于新上限，数据库不能以二者大小关系判定历史记录无效。尝试登记、额度判断依据、结果和对应历史按各自业务事务共同保存，已提交的旧事实不改写。完整分类见[本地配置变化与未完成工作](../../architecture/configuration.md#本地配置变化与未完成工作)。

以下操作使用两张公共表保存流程与尝试。流程身份同时区分业务归属、操作责任和实际目标。相同设备上的相同命令可以属于不同流程；正常执行、取消和恢复也可以共同继续同一个流程。

| 已有业务流程 | 流程与尝试的身份边界 | 必须保留的业务规则 |
| --- | --- | --- |
| 拍摄启动 | 录像、单张拍摄和延时摄影各自保存所属动作的启动流程及尝试 | 重试受启动窗口、设备条件、本次上限、累计次数及安全重复规则约束 |
| 单张拍摄或延时摄影的适用停止 | 按所属动作与设备能力保存实际停止流程及尝试 | 使用对应拍摄契约和有限预算，不伪造未执行的停止结果 |
| 录像普通停止 | 同一录像的正常停止、取消停止和断电恢复停止共用原停止流程 | 切换入口不创建新预算；普通停止与启动分别计数 |
| 后续动作停止历史残留录像 | 同一触发动作针对同一历史录像建立一个独立收场流程 | 不消耗触发录像自身的启动或停止预算，不重置历史录像原停止预算 |
| 文件读取 | 每个所属处理中的每份文件有自己的读取流程；一次读取尝试可跨数据段和重启继续 | 只有符合读取重试规则时才新增尝试；摘要不一致的重拷轮次和预算分别保存 |
| 正式产物清理中的文件删除及存在性查询 | 同一清理责任中的每份目标文件分别保存删除与查询流程及其尝试 | 两种调用分别消耗预算；查询成功与文件已删除分别表达 |
| 会话应急停止 | 同一会话对同一录像只建立一个应急流程 | 使用独立应急限额；数据库不可写时仍按应急规则有限停止，不能以保存公共记录为执行前提 |

同一来源文件被不同取回或内部处理使用时，读取流程归属于各自的具体处理，不仅凭源文件身份合并。文件读取流程的预算与尝试由公共表保存，可靠字节进度、重拷轮次及校验依据由拷贝专属记录保存。正式产物的每份目标文件分别关联删除和查询流程，两者继续归属于原清理责任。

上述身份与预算规则分别遵守[录像启动与停止](../../architecture/camera-recording.md#启动与停止的尝试上限)、[残留录像收场](../../architecture/camera-recovery.md#后续动作触发的残留收场)、[文件读取](../../architecture/file-copy.md#按文件累计读取尝试)、[正式产物清理](../../architecture/output-cleanup.md#删除与查询的独立尝试预算)及[会话应急停止](../../architecture/session-errors.md#正在录像时的应急停止)。

需要先保存意图和额度再派发的普通业务，在同一事务中保存本次尝试、预算占用、相关业务状态及权威历史，提交成功后才执行外部操作。登记意图不证明调用已经发出，调用结束不证明业务目标已经达成。应急停止按其独立记录边界保存实际事实，无法保存的结果不补造为数据库历史。

报告再次处理由[报告维护的触发规则](../../architecture/report-maintenance.md#报告处理失败后何时再尝试)决定，中间文件清理由[每次运行的清理预算](../../architecture/file-handoff.md#中间文件清理的运行预算)决定。公共记录的使用不改变这些触发条件，也不为原流程增加定时重试或跨会话预算。日志副本交付继续遵守独立于状态库的运行边界。

流程及尝试记录具有明确的业务归属和合法引用，不能仅靠一个无法校验所属对象的通用 ID 表达关系。预算、实际结果与必要查询表示保持单一事实来源，业务专属记录不得另行维护可独立修改的副本。物理拆表不自动增加历史快照对象；记录由所属业务对象的历史恢复，跨对象影响仍在同一业务事务中保存，回放不派发外部操作。

## 动作最终错误与驱动错误

camctl 根据业务规则确定动作的最终错误，驱动负责返回本次操作的原始错误和实际观察。驱动返回错误时，所属流程先保存对应尝试或处理记录，再根据操作结果、剩余预算、执行资格及动作状态决定后续处理。一次调用返回错误不直接证明动作失败，也不证明设备没有执行命令。

`actions.error_code` 使用 camctl 定义的固定整数枚举，其公共错误码和唯一阶段遵守[整数枚举规则](common.md#状态与类型的整数枚举)。驱动原始错误保存在对应的操作尝试或业务处理记录中，保留原始标识、发生步骤、详情及可靠取得的操作结果。未识别的驱动错误也保留原值；不能将其直接写入动作整数错误码，或仅凭错误名称推断设备效果。

动作最终错误的详情按所属错误契约提供必要说明，并关联导致该结果的尝试或逐项处理事实。动作错误表达业务结束的原因，原始错误表达具体操作遇到的问题；历史恢复和报告生成保留这两层含义。具体错误码的整数编号、触发条件、详情结构和关联字段由错误登记及相应字段定义确定。

下表先区分是否已有动作终态或取消要求，再判断普通执行的结果和继续资格。数据库无法可靠保存事实时，适用状态库错误规则，不以此表推定动作结果。

| 动作状态与操作结果 | 错误记录及后续处理 |
| --- | --- |
| 动作已有终态，之后收到操作结果 | 将可靠结果保存在所属尝试、设备活动或文件处理记录中；保持动作原有终态及最终错误 |
| 动作尚未结束，取消要求已经生效 | 保存操作错误及已知结果，按取消规则继续必要收场；普通操作失败不能覆盖取消要求，也不能重新启动普通业务重试 |
| 动作尚未结束且未被取消，尚未满足业务终态条件，操作的实际效果仍无法确认 | 保存错误和未确认事实，按所属业务规则核实；不能将未知当作没有执行，也不能据此直接重复可能产生副作用的操作 |
| 动作尚未结束且未被取消，尚未满足业务终态条件，操作结果已经明确，仍满足业务继续或安全重试条件 | 保留本次错误，按所属流程继续；动作不因这一次错误直接结束为失败 |
| 动作尚未结束且未被取消，业务已经满足最终失败条件 | camctl 根据实际失败分支确定动作整数错误码及详情，并与相应业务事实和历史共同提交；不将驱动原始错误码直接作为动作最终错误码 |
| 动作尚未结束且未被取消，后续尝试成功，且动作满足成功条件 | 保留此前尝试的错误，按成功规则结束动作；曾经发生过操作错误不要求动作最终失败 |
| 动作尚未结束且未被取消，按启动窗口等规则满足其他终态条件 | 按所属业务规则保存过期等结果，并保留操作错误；不能仅因曾有驱动错误而将这些结果改为动作失败 |

最终失败条件包括所属业务规定的预算耗尽、有限核实结束后仍不能确认结果等情况；各条件的优先级和动作终态继续由业务契约决定。公共错误记录不增加重试预算，也不改变过期、取消或恢复规则。状态库读取、写入或提交结果无法确认时，遵守[会话错误规则](../../architecture/session-errors.md)，不能为了保存一个动作错误而绕过状态库故障处理。

## 设备活动记录

`device_activities` 的每条记录表示一个动作在某台设备上启动的一次持续活动，例如一段录像或一次延时采集。记录保存所属动作、设备、活动类型及可靠取得的状态和观察依据；启动结果尚未确认时，保留未确认事实，记录存在不证明活动已经启动。同一活动的重试、取消和重启恢复沿用原身份，查询取得新观察时更新该活动的投影并追加历史，不为每次查询创建新活动。

动作结果、设备活动状态和控制操作结果分别保存。原动作已经失败或取消时，设备仍可能继续执行；停止流程已经结束时，其结果也可能是未能确认停止。后续取得新观察可以更新活动的已知状态，但不能改写已经结束的动作或原操作流程的结果。

| 信息或责任 | 保存位置与边界 |
| --- | --- |
| 动作的执行资格、公共状态及最终结果 | 由 `actions` 保存，设备活动后续变化不重开已结束的动作 |
| 一次设备活动的归属、是否仍在执行及可靠观察依据 | 由 `device_activities` 保存；未知与已确认结束分别表达 |
| 启动、普通停止、应急停止及后续动作触发的有限停止 | 由 `operation_runs`、`operation_attempts` 保存适用流程、尝试和预算，并关联目标活动；活动记录不另行维护同一预算或流程结果 |
| 录像原片检查、修复和文件处理 | 分别由 `recording_processing`、文件拷贝及中间文件记录保存，设备活动结束不表示这些处理已经完成 |

设备活动按[设备活动登记与停止处理](../../architecture/scheduling-execution.md#设备活动登记与停止处理)保存和恢复。执行前按所属设备契约核实状态，不能仅凭历史记录认定设备仍在执行，也不能仅凭没有活动记录认定设备空闲或取得停止未知活动的权限。

| 可靠取得的活动事实 | 状态保存与后续处理 |
| --- | --- |
| 已确认活动仍在执行，所属动作尚未结束 | 保存观察，按原动作的执行或取消流程处理 |
| 已确认活动仍在执行，所属动作已结束 | 保存残留活动事实；录像按后续有效动作触发的规则处理，不重置原停止预算或启动周期性收场 |
| 已确认活动结束 | 保存结束依据，保持已有动作终态和已结束操作流程的结果；尚未结束的相关业务按各自规则继续 |
| 活动是否启动、是否仍在执行或是否结束无法确认 | 保存实际未知状态和错误，按适用的有限核实与恢复规则处理，不推断停止成功 |
| 所需记录无法可靠读取或保存，或者提交结果未知 | 按状态库错误与提交核实规则处理，不把缺少可靠记录解释为没有设备活动 |

多个取消入口涉及同一活动时，共用原停止流程及剩余预算。[后续动作停止历史残留录像](../../architecture/camera-recovery.md#后续动作触发的残留收场)使用触发动作自己的独立流程，关联原录像活动；停止成功保存新观察和本次流程结果，原录像终态与原停止结果保持不变。应急停止继续遵守数据库不可写时仍可有限执行的规则，不以成功保存活动记录为前提。

活动记录属于发起它的动作自身状态，历史恢复及快照包含相应信息，不成为独立的历史快照对象。一次结果影响历史动作的活动状态和另一触发动作的处理状态时，相关历史与投影在同一业务事务中保存。已经结束的活动及其历史永久保留；历史回放只重建记录，不调用设备。

## 录像内部检查与修复记录

`recording_processing` 保存一个录像动作在提交终态前的内部原片检查和修复处理。同一录像动作至多有一条记录，保存适用的检查决定、修复判定及其依据，以及检查和修复各自的进度、结果与错误。动作自身的执行状态与最终结果由 `actions` 保存；检查失败、修复失败和录像失败分别表达。

处理记录关联已可靠确定的源文件、输入拷贝和适用的中间文件。检查与修复使用同一有效输入副本时，继续引用同一份文件及拷贝记录。需要逐份管理的文件由相应文件记录保存，不在处理记录的 JSON 中另外维护可增长的文件清单。

| 信息或处理责任 | 保存位置与使用规则 |
| --- | --- |
| 是否需要检查或修复、采用的门槛和可靠依据 | 由 `recording_processing` 保存判定及当时依据；已保存的决定跨重启沿用，尚未决定的事项使用本次运行配置 |
| 检查取得的视频时长、判定及实际错误 | 由 `recording_processing` 保存；未取得可靠时长与已确认时长不足分别表达，工具错误不直接表示原片损坏 |
| 修复尚待判定、不需要修复、处理未完成或已取得最终结果 | 由 `recording_processing` 分别表达；未执行不表示成功，修复结果不单独决定录像结果 |
| 输入文件拷贝、读取尝试和预算 | 分别引用 `file_copies`、`operation_runs` 和 `operation_attempts`，不在处理记录中独立维护同一进度或预算 |
| 输入、工具临时文件及尚未登记的修复成品的保留与清理 | 由 `intermediate_files` 保存，处理记录提供实际用途及处理结果依据 |
| 录像最终结果与正式产物登记 | 按录像结束规则共同提交，分别由 `actions` 和 `outputs` 保存；内部文件及处理结果的存在不表示产物已登记 |

检查与修复的判定遵守[修复门槛](../../architecture/camera-recovery.md#自动修复的多录门槛)、[原片检查](../../architecture/camera-recovery.md#计时证据不足时的原片检查)及[修复与动作成功分离](../../architecture/camera-recovery.md#修复与动作成功分离)的规则。判定未知、处理未完成和已取得最终结果分别保存；所需历史、配置或提交结果无法可靠确认时，按对应错误处理，不补造判定。

适用处理尚未结束时，保存内部进度，按[录像动作的结束时点](../../architecture/camera-recording.md#录像动作的结束时点)继续处理或恢复。取消与过期仍按各自规则执行，记录未执行或停止后续处理的原因。录像终态提交后，不重新启动该录像的内部检查和修复；后续取回或检查发现的媒体问题由正式产物的质量事实表达，不改写原录像终态。

处理记录及其变化属于录像动作自身状态，由该动作的历史恢复和快照包含，不成为独立的历史快照对象。处理结果与相关文件、动作及正式产物的状态按所属业务事务共同保存，文件删除不删除处理记录和历史。
