# 报告、运行状态与数据库元信息

[数据库设计入口](../database-schema.md) · [CLI 资料入口](../README.md)

本页定义输入诊断、报告、状态同步、全局运行状态和数据库元信息的存储职责。报告正文按冻结历史生成；同步责任、累计确认、可信时间和数据库身份分别遵守各自生命周期。

完整列、类型和约束见 [reports.sql](schema/reports.sql)。本页字段定义中的时间均遵守公共整数时间契约，事件引用均引用同一次状态变化的可靠历史。

整数编号由[统一定义](enum-registry.json)提供，[编号一览](enum-values.md)从该定义生成。本页使用成员名称说明字段含义和处理规则。

## 输入诊断与状态报告

输入文件诊断独立于计划保存。无法读取或解析输入时仍可形成诊断；合法计划与无效 ACK 同时出现时，可以在同次事务中保存计划及诊断。动作自身参数错误保存在动作中，不因此创建重复的文件诊断。

状态报告与普通交付分别保存。报告按照固定历史边界和覆盖范围恢复内容，重建或补投沿用原报告身份和确定字节。普通交付遵守产物取回、文件交接和撤回规则，不能直接套用报告的补投规则。

`reports` 保存报告身份、固定生成依据和相应处理状态。完整报告正文由不可变历史及这些依据生成，写入供主程序传输的 JSON 文件；重建遵守[从历史重建报告](../../architecture/status-reports.md#从历史重建报告)的确定字节规则。输入文件诊断作为状态报告中的内容发送，其数据库记录不要求生成独立的诊断文件。

报告的每次成功发布及恢复观察保存在 `history_events`，并同步更新 `reports` 的查询投影；首次发布与后续补投分别保留实际事实，不能用最后一次结果覆盖历史。已登记报告、曾经成功发布、文件仍在交接目录和客户端已确认分别判断，遵守[报告发布与补投](../../architecture/report-publication.md)。

报告可以由自动维护生成，也可以用于完成显式报告动作的本地处理责任；二者不存在必然的一对一关系。显式同步责任由 `state_syncs` 保存，客户端累计确认位置由 `runtime_state` 保存，不能仅由报告动作是否完成推断同步已结束或客户端已确认。

## 客户端累计确认状态

`runtime_state` 的累计确认字段为第一版的一个逻辑客户端保存当前确认位置，供报告维护和输入处理直接读取。该位置表示客户端已经可靠保存到哪个业务水位，不能用收到的最大报告编号代替。确认位置的变化及其依据保存在统一的不可变历史中，并与当前投影共同提交。

累计确认位置按[全局运行状态](#全局运行状态)的初始化与读取规则管理，初始值为 0。ACK 处理只修改累计确认相关字段，不改变同一记录中的可信历史时间下界。

输入中的 `last_report_id` 用于查询 `reports`，累计位置使用所引用报告的 `to_wm`。设已有位置为 A、引用的报告为 R，ACK 处理遵守[报告确认规则](../../architecture/status-reports.md#ack-引用的报告记录)：

| ACK 及查询结果 | 累计确认位置 | 对同步责任的处理 |
| --- | --- | --- |
| 未提供 ACK | 保持原位置 | 不因本次输入缺少 ACK 而确认同步结束 |
| ACK 合法，报告记录可靠有效，`R.to_wm > A` | 推进到 `R.to_wm` | 检查并结束该报告满足的全部未结束责任 |
| ACK 合法，报告记录可靠有效，`R.to_wm <= A` | 保持 A | 仍检查并结束该报告满足的全部未结束责任，不能因为位置未推进而跳过 |
| ACK 字段非法，或查询成功并确认报告不存在 | 保持原位置，保存 ACK 诊断 | 不由该 ACK 改变同步责任 |
| 报告或确认状态无法可靠读取、写入失败，或者提交结果未知 | 按状态库错误及提交核实规则处理，不宣称更新成功 | 不宣称责任已确认结束，也不猜测事务已经回滚 |

以上同步确认按[状态同步记录](#状态同步记录)中的范围和历史边界条件逐项判断。累计位置更新、适用同步的结束事实及对应权威历史在同一次输入事务中保存；需要恢复时核实实际提交结果，不允许确认位置与同步结束只保存一部分。ACK 与计划正文按[独立处理规则](../../architecture/plan-acceptance.md#计划正文与-ack-独立处理)执行，计划被拒绝或同一请求重送不阻止处理有效 ACK。

累计确认位置只前进、不后退。客户端从旧备份恢复后要求重新补齐的范围由 `state_syncs` 保存，不回退累计位置；报告生成在同一一致历史边界内读取累计位置及有效同步责任，确定本份报告的冻结范围。后续 ACK 不修改已经登记报告的内容。

有效 ACK 引起的累计确认及同步管理变化不增加 `change_seq`，不产生用于确认 ACK 的新报告责任；无效 ACK 的诊断及同次输入中的其他业务变化按各自规则报告。累计确认状态按自身历史恢复，不进入历史快照维护范围。

## 状态同步记录

`state_syncs` 的每条记录表示一个 `report_status` 动作实际开始执行后建立的同步责任，关联发起动作，保存原同步要求、确定后的固定起点、同步开始的完整历史边界，以及是否已经结束、结束原因和对应的 ACK 或取消依据。同一动作至多建立一条同步记录；重试、重启及同一请求重送沿用原记录，不重算起点或开始边界。不同动作即使要求相同起点，也分别保存责任。

动作取得执行资格后，按[同步开始规则](../../architecture/status-sync.md#camctl-何时开始同步)确定起点。动作进入运行、起点确定及同步责任建立在同一事务中保存；局部同步对起点报告的查询也在该事务中完成。参数受理失败、执行前取消，或执行时可靠确认起点报告不存在时，不建立同步责任；查询或提交无法确认时按状态库错误处理，不假定责任尚未建立。

`actions` 保存报告动作的本地执行状态和结果，`reports` 保存各份报告的固定生成依据和文件处理事实，`state_syncs` 保存仍需履行的同步责任。一份报告可以满足多个同步；同一同步也可以由先后生成的不同报告覆盖，不将同步责任绑定为某一份报告文件的生命周期。

| 已建立同步责任的后续情况 | 同步记录与相关处理 |
| --- | --- |
| 本地报告工作尚未完成，或会话出错、断电、报告生成及文件交接未完成 | 保留同步要求与实际进度，恢复原责任，不以文件缺失或操作失败结束同步 |
| 报告动作已完成本地工作并成功，尚无合格 ACK | 同步责任继续保留；后续报告机会仍须覆盖其固定起点，`run` 不为等待远端确认持续运行 |
| 同步尚未结束，发起动作在进入终态前被取消 | 在取消事务中结束该动作的同步责任并保存依据；其他同步继续按自身状态处理 |
| 报告动作已经成功，随后收到针对该动作或计划的取消 | 保持动作结果；尚未确认的同步责任继续等待合格 ACK |
| 收到满足该责任的有效 ACK | 保存确认结束及对应依据，并与累计确认处理在同一输入事务中提交 |
| 同步责任已经结束 | 永久保留结束事实；同一动作的恢复、重送或后续报告生成不重新建立责任，也不改写原结束原因 |

报告范围根据全部尚未结束的同步及累计确认位置共同确定，遵守[报告范围规则](../../architecture/status-sync.md#报告范围)。停止等待某项责任，不修改已经登记报告的冻结依据，也不直接终止已经开始的共享报告生成任务。

对于尚未结束的同步，设固定起点为 S、开始事务的完整历史边界为 B。ACK 引用的报告 R 已可靠存在且生成依据有效时，按下表判断；B 属于完整历史顺序，不能与业务水位混用。

| R 的冻结历史已包含 B | `R.from_wm <= S` | 对该同步责任的处理 |
| --- | --- | --- |
| 否 | 否 | 保留责任，报告既早于本次同步，也未覆盖所需起点 |
| 否 | 是 | 保留责任，报告范围足够，但采用的状态早于本次同步 |
| 是 | 否 | 保留责任，报告起点过晚 |
| 是 | 是 | 确认责任结束，保存与本次 ACK 的关联 |

每份有效 ACK 都检查它满足的全部未结束责任，即使累计确认位置没有推进也执行该检查；累计位置按 `max(A, R.to_wm)` 处理，并与适用同步的结束事实共同提交。ACK 非法或可靠确认报告不存在时，保存 ACK 诊断，不由该 ACK 改变确认位置或同步责任；状态库读取、写入或提交结果无法确认时按对应错误处理。

同步管理历史和投影在同一事务中保存，管理变化自身不增加 `change_seq`；发起动作的注册、开始和结果变化仍按业务规则计数。`state_syncs` 按[同步持久化规则](../../architecture/status-sync.md#数据库需要保存哪些信息)从自身历史恢复，不进入历史快照维护范围；`report_status` 动作自身继续按动作对象维护快照。历史回放不新建同步、不调用设备，也不重新交付报告文件。

## 全局运行状态

`runtime_state` 保存唯一一条全局运行状态记录，以具有明确类型和约束的固定字段分别表达客户端累计确认位置、可信历史时间下界、中间文件清理继续位置及其必要依据。每组字段由所属业务的专用读写接口维护，更新只修改该业务负责的字段，不将先前读取的整行内容重新写回。共用一行不合并各类状态的判定、更新资格或历史含义。

| 状态分组 | 用途与更新责任 | 初始状态 |
| --- | --- | --- |
| 客户端累计确认 | 输入处理根据有效 ACK 引用的报告推进确认位置，报告维护据此确定普通未确认范围 | 累计确认位置为 0 |
| 可信历史时间下界 | `run` 使用已有下界检查启动墙钟，通过后以本次检查读数建立或推进下界 | 尚无可信历史时间依据 |
| 中间文件清理继续位置 | 正常 `run` 的历史清理维护保存可靠检查后的继续位置，供后续会话接续 | 尚未检查历史清理记录，从适用候选范围的起点开始 |

首次显式初始化状态库时，与完整初始结构一起建立该记录，遵守[初始化边界](../../architecture/initialization.md#目录与状态库)，不为初始值插入虚构历史事件，也不将初始化时未经校验的墙钟读数保存为可信依据。重复初始化保留已有状态；日常读取发现记录缺失、存在多条记录、内容无效或无法可靠读取时，按状态库错误处理，不补建记录或返回初始值。合法的“尚无可信历史时间依据”与记录缺失分别表达。

累计确认字段遵守[客户端累计确认状态](#客户端累计确认状态)。确认位置更新、适用的同步责任结束及对应历史仍在同一次输入事务中提交；该操作不授予输入处理中未经校验的时间推进可信下界的资格。

可信历史时间下界只在 `run` 启动墙钟检查通过后更新，每次会话至多一次，遵守[下界更新规则](../../architecture/clock-recovery.md#可信历史时间下界的更新)。检查使用原有下界，更新使用实际通过检查的读数；已有下界只前进、不后退。需要变更时，在进入普通执行前共同提交权威历史与投影；保存失败或提交结果未知时按状态库错误处理。

下界变化不增加 `change_seq`，也不单独产生报告责任。它保存历史依据，不表示后续会话已经通过时间检查。正常运行及退出阶段、`submit` 和时钟异常会话不更新下界；这些阶段的事件仍按各自事实及时间可信性保存。单次会话中的命令超时、重试间隔等经过时长仍使用单调钟，不使用历史下界计算跨重启经过的时间，也不将不同会话的单调钟读数相减。

各类状态分别按所属规则形成不可变历史，并与受影响投影原子保存。历史恢复使用当时保存的变更，不用本次墙钟、其他事件中的更晚时间或后续 ACK 改写旧状态。全局运行状态不进入历史快照维护范围；具有独立身份和生命周期的状态同步责任由 `state_syncs` 保存。

## 中间文件清理进度

`runtime_state` 使用独立字段组保存历史中间文件清理的跨会话继续位置，由清理维护接口更新。位置采用中间文件清理记录的稳定登记顺序及必要身份，不依赖该记录仍在待清理集合中。首次初始化表达为尚无已检查位置，与记录缺失或内容无效分别判断。

继续位置从相应检查历史派生，与本次检查结果、适用的 `intermediate_files` 状态及对应历史在同一事务中保存。文件检查与删除在事务外执行，只有结果及位置可靠提交后，才能越过相应记录。位置变化本身不增加 `change_seq`；实际文件清理结果按所属对象的报告规则处理。

| 检查、保存或恢复情况 | 继续位置与后续处理 |
| --- | --- |
| 检查结果与继续位置已可靠提交 | 从该稳定顺序位置之后继续；本项暂不能删除或删除失败，不阻止后面的记录获得机会 |
| 检查或删除已经发生，保存事务确认回滚 | 数据库位置不推进；后续按实际文件事实重新核实，不推测旧调用结果 |
| 保存结果未知，或位置无法可靠读取和解释 | 按状态库错误规则核实，不猜测位置已经推进或恢复为起点 |
| 位置对应的记录已经清理完成或不再是候选 | 仍从其顺序位置之后继续，不要求该记录重新进入候选集合 |
| 首次初始化后的合法起点 | 从本次适用候选范围的起点开始，遵守数量限制 |
| 后续正常 `run` 开始 | 沿用已保存位置，重新建立本次历史范围上界、额度及已检查状态；到范围末尾后的处理遵守清理预算规则 |

固定范围、循环到起点、每次运行最多检查一轮及新增文件首次清理的协调遵守[中间文件清理的运行预算](../../architecture/file-handoff.md#中间文件清理的运行预算)。范围上界、本次已检查数及防止同一文件重复处理的会话状态，不作为跨会话继续位置使用；重启不继承上一会话已消耗的运行额度。位置更新只修改清理字段，不回写先前读到的 ACK 或可信时间。

## 数据库元信息

`database_metadata` 保存唯一一条数据库元信息记录，以专用字段表达 camctl 数据库标识、数据库实例身份、整体格式版本和当前部署的文件目录绑定。各入口在解释业务数据之前读取并校验这些信息，再按支持的格式检查必要结构、读取业务投影。元信息的有效性不能仅由文件名或 SQLite 能否打开文件判断。

| 信息 | 职责 | 建立与更新规则 |
| --- | --- | --- |
| camctl 数据库标识 | 表明数据库属于 camctl，配合必要结构检查识别状态库 | 首次初始化时保存，日常运行不修改 |
| 数据库实例身份 | 将报告生成任务、查询结果和缓存绑定到相应状态库 | 首次初始化时生成；不同的首次初始化分别建立不同实例身份，重启和重复 `init` 沿用已有身份 |
| 整体格式版本 `format_version` | 确定表结构、允许的事件及其他持久化表示如何解释 | 第一版初始化为 1，日常调用不修改；后续格式变化遵守显式升级规则 |
| `staging_path`、`ready_path`、`processing_path` | 保存该状态库当前使用的三处文件目录，供各入口与本次配置比较 | 首次初始化共同保存，非空且两两不同；按[目录绑定与变更](../../architecture/configuration.md#文件目录的绑定与变更)保存规范绝对路径，只有满足切换条件的显式 `init` 可以共同更新 |

数据库标识表达数据库类型，实例身份区分具体状态库。报告任务与查询缓存使用数据库身份时，以该实例身份为依据。

首次显式初始化时，元信息记录与完整结构、初始运行状态一起建立；只有完整有效的初始化结果才能供日常入口使用。`runtime_state` 保存累计 ACK 和可信历史时间下界等业务投影，由对应历史推进和重建；`database_metadata` 提供识别数据库、解释持久化数据及核对部署位置的基础信息，由初始化、合格的目录切换与显式格式维护负责。历史回放不改变数据库身份、整体格式或目录绑定。

目录绑定保存普通文本，不进入业务事件的 `row_changes` 或对象快照，也不影响报告业务水位。SQL 检查绝对路径的基本形状、非空、NUL 及两两不同；路径规范化、目录包含关系、实际目录别名、文件保留责任和切换资格由部署入口验证。其他普通配置仍按每次运行加载，不随元信息保存。

| 读取或初始化情况 | 处理 |
| --- | --- |
| 首次初始化，目标状态库可靠确认不存在 | 按初始化规则建立唯一元信息记录及完整初始状态，可靠保存后提供正式数据库 |
| 已有唯一有效记录，格式受支持且必要结构有效 | 使用该实例身份和格式，并按入口核对目录绑定；重复 `init` 保留身份与业务数据，路径变化须独立满足切换条件 |
| 元信息有效，但格式不受支持 | 按格式不受支持处理，在使用业务状态之前停止 |
| 记录缺失、存在多条、标识或版本非法，或必要结构与声明不符 | 按状态库校验错误处理，不补建元信息或解释为初始状态 |
| 无法可靠读取或确认元信息 | 按状态库错误处理，保留读取失败与记录不存在的区别 |

初始化及重复验证遵守[目录与状态库](../../architecture/initialization.md#目录与状态库)，格式解释和显式升级遵守[数据库整体格式检查](../persistence-runtime.md#数据库整体格式检查与显式升级)。第一版实现格式 1 的读写与检查，后续格式的实际迁移步骤随相应需求定义。

## 字段与状态组合

### 输入诊断字段

`plan_file_diagnostics` 包含 `id`、`input_path`、可空 `request_id`、可空 `plan_id`、`errors_json` 和 `created_event_id`。`input_path` 保存本次 CLI 收到的输入路径，公共 `file_name` 由它的最后一个路径分量取得；路径不是输入身份。只有完整解析并确认合法的请求 ID 才能填入 `request_id`；`plan_id` 只在本次输入实际受理或复用了计划时填写，因此 ACK 错误可以关联已有计划，整份拒绝和读取、解析失败均为空。

`errors_json` 是非空公共 `error` 数组，一次输入的全部文件级、整份受理及 ACK 错误放在同一诊断中。阶段只允许 `input_read`、`input_parse`、`admission`、`ack`，详情按[错误登记](../../../protocol/errors/workflow-codes.json)及原始输入契约保存。驱动或 OS 原始原因可以位于详情，不能凭其名称更改所属阶段。诊断创建后不可修改；动作自身错误不重复加入数组。`created_event_id` 指向本次诊断创建事件。

### 报告字段

| 字段 | 含义及空值规则 |
| --- | --- |
| `id` | 报告身份，写事务中按最大已提交 ID 加 1 分配 |
| `frozen_event_id` | 冻结事务之前的最近完整已提交边界；没有已提交事件时为 0。登记时固定，必须早于该事务首条事件 |
| `from_wm`、`to_wm` | 冻结业务覆盖区间的左右端点，均非负；右端不小于左端 |
| `format_version` | 报告生成所使用的数据库及编码契约，格式 1 为 1 |
| `status` | 下表的文件处理阶段，不表达客户端确认 |
| `size_bytes`、`sha256` | 首次完整生成且同步成功的确定字节依据；尚未形成时同时为空，形成后保持不变 |
| `publication_count` | 已可靠保存的成功发布次数，初始为 0；每次实际补投成功再增加 1 |
| `last_published_event_id` | 最近一次成功发布事件；次数为 0 时为空，否则必填 |
| `last_error_json` | 最近一次文件生成、交接或恢复观察错误；无错误或后续完整成功时为空，旧错误仍由历史保留 |
| `created_event_id`、`last_event_id` | 报告登记及最后一次管理事实的事件，非空；按报告自身历史派生，不作为事件的业务前后值 |

| `status` | 必须有的依据 | 恢复与转换 |
| --- | --- | --- |
| `REGISTERED` | 冻结范围，完整文件依据可以尚无 | 生成原范围内容；不改报告 ID |
| `PREPARED` | 完整长度与摘要 | 保存移动意图后进入 `PUBLISHING` |
| `PUBLISHING` | 原字节依据与移动意图历史 | 根据实际文件位置、目录同步及历史核实，不能猜测文件从未交出 |
| `PUBLISHED` | 至少一次成功发布记录 | 文件被领取不倒退成功事实；未确认补投按报告规则使用同一字节 |
| `FAILED` | 本次文件处理错误 | 保留原冻结依据和已有字节；只在规定的新机会恢复，可重新进入 `REGISTERED`、`PREPARED` 或 `PUBLISHING` |

尚未得到可靠完整字节时不能进入 `PREPARED`、`PUBLISHING` 或 `PUBLISHED`。补投可以从 `PUBLISHED` 进入 `PUBLISHING`；如果本次补投失败，状态可以为 `FAILED`，但 `publication_count` 与原成功发布事件仍保留。文件名由报告 ID 和确定摘要按公共命名规则生成，不再保存一份可独立修改的文件名。生成过程中尚未完成的子进程、临时文件及分页位置不作为数据库报告阶段。

### 同步字段

`state_syncs.action_id` 唯一引用发起报告动作。`mode` 为 `FULL` 或 `INCREMENTAL`：完整同步的 `after_report_id` 为空、`from_wm = 0`；局部同步保存实际存在的起点报告及其 `to_wm`。`started_boundary_event_id` 引用建立责任的完整事务末位，不能仅取事务内开始事件。

`status` 为 `OUTSTANDING`、`ACKNOWLEDGED`、`CANCELED`。`OUTSTANDING` 的 `ack_report_id`、`ended_event_id` 均为空；`ACKNOWLEDGED` 两者必填；`CANCELED` 仅 `ended_event_id` 必填。结束后不转换到其他状态。`local_report_id` 在尚无报告可靠满足本地责任时为空；有值时永久指向首次满足的报告，并与动作成功共同提交。动作被取消时可以保持为空；不能因 ACK 先结束责任而补造本地发布成功。

局部起点不存在时，不创建这条记录，动作直接保存执行失败。开始边界、起点及模式创建后只读。局部同步的起点、ACK 的覆盖资格和本地报告资格由事务接口核对，单纯存在外键不能证明范围合格。

### 单份状态字段

`runtime_state.id = 1`。显式初始化写入 `acknowledged_wm = 0`，其余四个字段全部 SQL `NULL`，不生成历史。`acknowledged_report_id` 保存最近一次使累计水位严格提高的报告；同水位 ACK 可以结束同步，但不覆盖该字段。值为空时累计水位必须为 0。

`trusted_time_lower_bound` 与 `trusted_time_event_id` 同时为空或同时有值；后者引用建立或推进下界的事件。通过检查但没有推进下界时无需写重复事件。`cleanup_cursor_file_id` 为空表示合法初始位置；有值时引用最近一次可靠保存检查结果的中间文件 ID，即使该文件已完成清理也保留该位置。循环到本次范围起点时不先清空游标，只有下一项检查结果可靠保存后才改为实际检查到的 ID。

`database_metadata.id = 1`，`application_id` 固定为 `camctl`，`instance_id` 在首次初始化生成 UUID4 的小写 32 位十六进制形式，`format_version = 1`。它不保存未经校验的创建时间，不参与业务历史回放。初始化 SQL 和两条记录在同一事务提交；日常入口发现任一单份记录缺失均报状态库错误。

## 查询与事务接口

输入处理在同一事务中登记诊断、查重或受理计划、吸收有效 ACK 并结束所有合格同步。请求诊断查询使用 `diagnostics_request`；报告选择通过对象历史目录按业务区间读取，不能按诊断的请求 ID 代替报告选择条件。

报告冻结在写事务内读取本事务之前的完整已提交历史末位 H，以及该边界的业务水位、累计确认和未结束同步的最小起点，再分配报告 ID。冻结不包含本事务尚未提交的部分变化，事件及边界的区别见[历史引用规则](history-formats.md#事件引用与事务边界的编码)。`reports_coverage` 用于按覆盖水位查找报告；ACK 和重建按报告主键定位。`syncs_outstanding` 支持固定起点和责任查询，合格性还必须比较报告冻结历史与同步开始边界。跨事务查询使用固定报告记录，不把后来推进的水位混入原报告。

报告准备、每次成功发布、同步结束、可信时间推进和清理游标分别使用专用更新接口。每个接口只更新所属字段，保存事件及受影响投影，并用稳定的事务操作身份处理提交未知。重建报告使用原冻结边界、范围和格式；实际生成字节与已有摘要不一致时报告错误，不更新原摘要接受新字节。
