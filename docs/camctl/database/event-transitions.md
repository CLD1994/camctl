# 事件保存与状态转换规则

[历史记录的格式](history-formats.md) · [共同提交的事务规则](transactions.md) · [事件转换规则的 JSON 文件](event-transitions.json) · [报告字段的来源与生成规则](report-dependencies.md)

取回动作开始执行时，camctl 需要把动作状态从 `PENDING`（待执行）改为 `RUNNING`（执行中）。如果该动作的来源已经确定，camctl 还需要为每个来源建立一条记录，用来保存后续选择哪些产物。这些修改必须在同一事务中提交，也就是一起保存成功，或者一起回滚。

数据库用“事件”保存这类已经确认的事实。事件包含修改前后的字段值，当前状态表则保存应用这些修改后的结果。例如，`ACTION_STARTED` 表示动作开始执行；保存该事件时，程序只能进行开始动作所需的修改，不能顺便改写用户的原输入。历史恢复程序读取这些已保存的事件来还原状态，不重新选择来源或调用设备。

本页说明每类事件允许修改哪些数据、保存前必须检查什么，以及这些变化怎样进入对象历史和状态报告。[事件转换规则的 JSON 文件](event-transitions.json)用程序可以读取的结构列出相应规则。

## JSON 文件记录什么

设计者把允许的事件类型、各类事件的具体分支、可以修改的字段和必须满足的条件，逐项写入同一份清单。这个维护设计清单的过程称为“登记”。`event-transitions.json` 就是这样一份机器可读的事件转换规则说明；运行时发生的每一次事件则另行保存在数据库的 `history_events` 表中。

同一类事件可以包含不同分支，用来区分该类事实的具体情况。例如，`ACTION_FINISHED` 用于保存动作结束的事实，成功和失败分别使用不同分支，各自规定要保存的结果及必须满足的条件。每个分支都有自己的编号。

这份 JSON 文件涉及两个不同的版本字段，读取时分别解释：

| 字段位置 | 含义 |
| --- | --- |
| 文件顶层的 `format_version: 1` | 表示 `event-transitions.json` 自身采用第 1 版文件格式。读取规则文件的程序按这个版本解释文件中的成员及其结构。 |
| `events` 中每类事件的 `version: 1` | 表示该类事件采用第 1 版事件正文，保存到数据库后对应 `history_events.event_version`。正文的具体结构见[事件正文版本 1](history-formats.md#事件正文版本-1)。 |

事件类型、分支及其修改规则以这份 JSON 文件为统一依据。检查脚本和后续事件处理程序读取同一份说明，不各自维护一套完整清单。其他规则分别从以下文件取得：

- [report-dependencies.json](report-dependencies.json)说明每个报告字段来自哪些数据、何时出现，以及怎样生成字段值。
- [enum-registry.json](enum-registry.json)列出数据库内部使用的类型、状态编号及其含义。
- [公共错误定义](../../../protocol/errors/workflow-codes.json)列出错误编号及其对外使用的错误码。

## 数据库字段可以怎样修改

每张保存当前业务状态的表，都必须为全部列注明修改方式。这里的“列”就是数据库表中的字段。JSON 文件在 `tables` 下按表列出这些分类：

| 分类 | 保存事件时的规则 |
| --- | --- |
| `immutable` | 只在创建记录时写入，记录创建后不得修改。例如，动作最初保存的用户输入不能被后续执行事件改写。 |
| `mutable` | 可以修改，但必须由具体事件分支明确允许；列在这一分类中并不表示任何事件都能修改它。 |
| `derived` | 不放入事件正文的字段前后值中。主键由事件中的行 ID 单独表达；其余列必须同时列在 `derived_history` 中，按对象自身历史计算。 |

两项补充规则进一步限制可变字段：`write_once` 列出的字段只允许从空值变为有可靠依据的值；`state_columns` 列出的字段必须遵守明确列出的状态转换。例如，动作可以按开始分支从“待执行”变为“执行中”，但已经结束的动作不能重新进入“执行中”。

字段是否影响报告，由 `report-dependencies.json` 中的数据来源、关联关系、生成条件和完整性检查共同决定。未被这些规则使用的业务字段只用于内部执行和恢复。某个字段参与报告检查，也不一定要展示给用户；例如，可靠保存的字节数用于核对文件是否已准备完整，但报告不因此增加复制进度。

有些字段只在特定条件下影响报告。程序必须保留并执行这些条件，不能把它们简化为“这个字段一变就生成报告”。

检查器逐列核对上述分类与实际 SQL，新增未分类列、遗漏实际列或引用不存在的列均使检查失败。等待、查询责任、应急停止和设备占用释放等生产实现进度见[数据库规格同步清单](../implementation-readiness.md#数据库规格同步清单)。

## 校验的输入与输出

保存事件前，负责写入数据库的程序需要取得事件类型、事件正文版本、具体分支、可靠的完整旧记录、拟保存的修改前后值，以及设备或工具提供的必要证据。它还需要知道本次事务预先分配的事件 ID 范围，以便核对字段中的事件引用。

同一事务共同创建读取流程和拷贝时，两者的固定关联按完整事务提案核对，允许任一方先出现在事件顺序中。历史归属同样可以沿固定身份列解析后来创建的关联对象。状态、执行资格、旧值和报告影响仍按各事件之前的事实及本事件变化判断，不能用后续事件的状态提前证明资格。

| 关联事实的提供方式 | 固定关系的核对依据 |
| --- | --- |
| 提供完整事务提案 | 使用完整提案中的固定身份、目标、父对象及唯一流程；必要关系缺失或矛盾时拒绝整笔事务。 |
| 独立校验未提供完整提案 | 将事件之前的事实与当前事件的修改后行合并核对，不修改原事实，也不假定未来事件创建了目标。 |
| 明确提供空提案 | 按空图核对，不能退回已有状态来补齐必需关联。 |

检查通过后，程序得到可以保存的数据变化，并确定这些变化分别属于哪个对象的历史。原记录无法读取，或者事件类型、正文版本、分支不在规则允许的范围内时，程序必须报出状态库一致性错误并拒绝保存。必要证据缺失、修改了不允许修改的字段、旧值不符或关联关系矛盾时，也按同样方式处理。程序不能跳过有问题的记录后继续提交。

只检查字段和状态仍然不够。例如，开始取回动作时，还需要确认每个固定来源都已经建立了对应的选择记录。JSON 文件中的 `guards` 为这类业务校验逐项命名，并给出判定规则和正式规格的链接。事件处理程序必须执行适用的校验；规则文件中列出了校验名称，并不表示运行时已经检查通过。

保存过程按以下阶段核对：

| 阶段 | 程序必须检查或完成的内容 |
| --- | --- |
| 读取原状态 | 确认记录身份、关联和旧值可靠。如果此前一次提交的结果未知，先用原操作身份核实它是否已经提交。 |
| 形成事件正文 | 每条拟修改记录都必须符合当前分支的一条规则。创建记录时保存全部业务字段；更新记录时只保存实际变化的字段，并为同一组字段同时保存旧值和新值。 |
| 检查每条记录 | 核对允许修改的字段、修改前后状态、只允许首次赋值的字段，以及只能按规定方向变化的字段。同一记录中的各字段还必须满足所属表的组合约束。 |
| 检查整笔事务 | 确认应当一起保存的记录齐全，包括固定集合的成员、共同建立的关联记录、操作次数和尝试记录，以及汇总结果和终态所需的依据。事务内尚未完成的中间状态不能对外提供。 |
| 保存历史和查询目录 | 根据实际修改的记录确定历史归属，比较事件发生前后的报告字段，并将事件、当前状态、查询目录和计数一起提交。 |
| 处理提交结果 | 只有确认提交成功后，才能执行依赖这些新事实的外部操作或发送通知。明确回滚时不保留部分修改；提交结果未知时核实原事务，不通过重新执行设备操作来补记录。 |

如果同一保存请求已经完成，程序复用原有记录并返回原结果，不重复创建记录或事件。字段值没有实际改变时，也不能把相同值再次写成新事实。一个事件中，同一条数据库记录只能出现一次；涉及多个字段的修改必须放在一起校验。

## 事件分支怎样约束状态变化

JSON 文件中的每个分支通过 `rows` 说明它可以在哪些表中创建或更新记录。对于更新记录，`before` 和 `after` 列出该记录在修改前、修改后必须满足的字段条件。例如，动作开始分支要求旧状态为“待执行”，新状态为“执行中”。规则中的条件用于判断一条完整记录是否合法，实际事件正文则保存此次变化的具体旧值和新值。

`columns` 列出该分支允许修改的全部字段，实际修改可以只涉及其中一部分，但至少要有一个字段改变。`required` 列出的字段每次使用该规则时都必须改变。没有列入条件的其他字段，仍然要遵守所属表的约束和业务规则。新建记录没有旧值，其初始状态必须同时符合创建分支和所属表的规定。

`state_models` 集中列出状态字段允许从哪个值变为哪个值。一次有方向的变化称为一条“状态转换”，在 JSON 中保存在 `edges` 数组里。例如，“待执行→执行中”和“执行中→成功”是两条不同的转换。没有列出的转换不得使用；迟到结果、程序恢复或配置变化均不能重新打开已经结束的动作。

每条转换都有稳定标识。分支通过 `transitions` 引用允许使用的转换，转换通过 `by` 列出哪些分支可以使用它。检查脚本从两侧核对引用是否一致，并检查转换的起点、终点是否符合分支的前后条件。多个字段能否一起改变，还必须经过所属表的组合约束和业务校验。

如果状态字段没有改变，该字段无需发生状态转换，但同一记录必须有其他真实变化。文件的新观察结果、报告补投和独立撤回分别遵守各自的状态规则，不能直接套用动作的终态规则。

### 来源和目标在何时确定

取回动作需要先确定从哪些拍摄动作取得产物，再确定每个来源中的具体产物；清理和取消动作则需要确定各自要处理的目标。把某个集合的全部成员确定并保存下来，称为“固定集合”。来源集合、每个来源的产物选择集合，以及清理或取消目标集合是不同的集合，分别保存固定状态。

来源可以在受理动作时确定，也可以在动作执行期间解析。取回动作开始执行时，如果来源已经固定，程序必须为每个来源建立待选择记录；如果执行期间才固定来源，就在固定来源的同一事务中建立这些记录。合法的空集合仍须明确保存“已固定”，查询出错不能解释为空集合。取消已经提交后，不再继续普通产物选择。

解析来源或目标失败时，程序在同一次行修改中保存解析失败状态、动作的 `FAILED`（失败）状态和完整错误。每条记录应用修改后就必须满足自身的字段约束；需要多条记录共同满足的完整性和汇总约束，则在整笔事务完成时核对。

创建记录可以直接表达已有可靠依据的状态。例如，首次尝试发生时，可以共同创建 `ACTIVE`（正在执行）的操作流程并保存尝试次数 1；如果已有 `PENDING`（待执行）的流程，就更新原记录。同样，固定清理目标时，某项已经具备完整的完成依据，可以直接创建为终态，不需要补写并未发生的中间过程。

开始核实拍摄结果时，程序使用对应的开始分支，把结果集合状态改为 `CHECKING`（核实中）。分批观察文件不代表多次开始核实，也不按文件批次增加尝试次数。核实结束时，程序分别保存“完整且符合要求”“完整但不符合要求”或“无法确认”的结果；无法确认时保留已经知道的文件，不补造完整集合。集合判定、所属核实尝试的结果和相应业务结果必须一起提交。

### 业务校验在什么阶段执行

首次固定集合与推进已有成员发生在不同阶段。例如，创建完整清理集合时，程序要检查此前尚未固定成员；处理其中一个已有清理项时，集合已经固定，此时应核对该项的执行资格和结果。两者不能使用相同的阶段前提。

每项业务校验的 `scope` 说明它适用于什么对象。值为 `transaction` 时，程序检查整笔事务；值为一组表名和行操作条件时，程序只对匹配的创建或更新记录执行该项校验。检查脚本会拒绝这样一种错误引用：分支列出的所有行操作都不适用，却仍要求执行该校验。只要适用条件成立，运行时就必须执行它，其他应执行的校验也不能省略。

| 保存阶段 | 必须核对的集合及执行条件 |
| --- | --- |
| 首次固定完整目标集合 | 集合原状态为 `PENDING`（尚未固定），且满足普通执行条件。全部成员与 `FIXED`（已固定）状态共同保存。 |
| 创建清理项时直接保存最终结果 | 该项属于本次固定的完整集合。程序核对原请求、成员完整性和最终结果依据。 |
| 推进或结束已有清理项 | 集合已经固定，原成员身份保持。程序根据该项状态、读取保护、实际调用及结果依据判断允许的修改。 |
| 取消后完成必要的清理收场 | 取消事实继续保留。程序根据实际结果保存逐项成功或取消，不恢复普通执行资格。 |
| 首次固定某个来源的全部产物选择 | 该来源的选择状态从 `PENDING` 变为 `FIXED`，全部成员及来源处理结果共同保存。 |
| 核实已选中的显式目标，或在建立交付记录前保存失败 | 原选择保持 `FIXED`。程序只更新原取回项，不重新选择产物或增加成员。 |

### 拍摄前的目录基准如何重新收集

某些驱动需要在拍摄前保存设备已有文件的目录，用来区分本次拍摄产生的新文件，这份目录称为“基准”。基准按批次保存在历史事件中，设备活动记录保存本次基准的首条和末条事件 ID。

如果收集过程被中断，且基准尚未固定、拍摄命令尚未派发，程序重新读取目录。重新读取的结果可能与旧结果不同，必须分别处理：

| 原状态与重新读取的结果 | 保存规则 |
| --- | --- |
| 基准仍为 `COLLECTING`（收集中），拍摄命令尚未派发；新目录非空 | 新批次建立新的首尾事件范围。固定基准时，程序使用这个新范围并核对批次和目录项数量。 |
| 基准仍为 `COLLECTING`，拍摄命令尚未派发；新目录为空 | 程序固定零批、零项的基准，并把首尾事件引用一起置空。即使旧收集已经保存过批次，也按此规则处理，不追加空批次。 |
| 基准已经 `FIXED`（固定），或者拍摄命令已经派发 | 不允许替换或清空基准范围。 |

清空旧范围时，事件正文仍保留首尾引用的旧值，历史恢复程序可以据此还原当时的收集状态。旧批次事件永久保留。

### 录像处理何时关联原片

录像处理可能先确定“不需要检查原片”，稍后才取得原片的可靠身份。因此，首次保存原片关联是一项独立事实，不以开始检查或运行处理工具为前提。

只要录像仍在处理、尚未关联原片，并且文件身份及其属于这次录像的依据可靠，程序就可以保存首次关联。检查决定尚未确定、不需要检查、需要检查这三种情况均适用。此次保存保持检查决定、检查状态和判定依据不变，也不启动处理工具。

已经关联的原片不能被替换或清空。再次确认相同关联时，不产生新事件；缺少归属依据时，程序拒绝保存关联。

## 变化属于谁的历史，何时需要更新报告

一条记录发生变化后，程序要确定它属于哪个对象的历史。例如，普通交付所用的拷贝记录、操作流程和尝试记录都属于该交付；设备文件和主机中间文件则分别保存自己的历史。各表的具体归属按[自身记录与快照成员](history-formats.md#自身记录与快照成员)确定。

程序沿事件发生时的关联关系查找唯一所属对象。同一事务中新建的关联可以用于查找，后来新增的关系不能用来解释旧事件。状态查询流程属于发起查询的动作；如果查询同时更新了其他动作留下的设备活动，该活动的变化仍属于原动作。一个事件修改同一对象的多条记录时，该对象的历史变化次数只增加一次；涉及多个对象时，各自增加一次。

历史变化还要另行判断是否影响状态报告。数据库用 `change_seq` 保存需要报告的业务变化序号：只有报告字段的值或是否出现发生变化时，才为事件分配该序号。保存可靠拷贝段、采用配置、等待重试或收集基准通常只改变内部事实；取得文件摘要或观察到设备结束，则可能改变已有报告对象的内容。

判断时，程序读取 `report-dependencies.json`，找出可能受影响的报告对象，并比较同一事件发生前后的公开结果。具体处理如下：

| 比较结果或关联情况 | 业务序号与报告目录的处理 |
| --- | --- |
| 没有报告字段的值或出现情况改变 | 事件的 `change_seq` 为空；照常保存内部历史并增加所属对象的历史变化次数。 |
| 一个或多个报告对象的公开结果改变 | 为本事件分配一个连续业务序号。将每个实际受影响的对象各写入报告变化目录一次，它们共用本事件的序号。 |
| 交付结果改变，报告还需要包含所属取回动作 | 按交付的实际变化写入目录。为组织报告而补齐取回动作，不额外分配序号，也不把取回动作记成自身发生了变化。 |
| 同一事务中的另一个事件改变了公开结果 | 对另一个事件独立判断和分配序号，不把整笔事务中的所有事件一律视为需要报告的变化。 |

报告管理、状态同步管理、ACK（累计确认）、可信时间和清理游标自身的变化不产生业务序号。同一事务中如果还包含业务动作开始、结束或清理结果，仍须分别判断这些事件是否影响报告。重建查询目录时，程序使用原事件正文版本核验原有序号，不重新分配旧序号。

## 怎样从事件恢复历史状态

正向恢复是从较早状态开始，按事件顺序应用已保存的变化。遇到创建记录，程序先确认该 ID 的记录尚不存在；遇到更新记录，先逐字段核对当前值与事件保存的旧值一致，再写入新值。

逆向恢复是从较新状态开始，按事件及事件内记录的相反顺序撤回变化。遇到更新记录，程序先确认当前值等于事件保存的新值，再还原旧值；遇到创建记录，则在用于历史查询的状态副本中移除该记录，表示它在目标时刻尚不存在。这个过程不删除永久状态库中的历史或业务数据。

两个方向使用相同的字段分类、JSON 结构、精确整数和事件正文版本。恢复只采用当时保存的事实，不用当前配置、时间、设备观察或调度结果重新判断旧状态。同一事务中创建的记录可以互相引用；恢复程序必须处理完整笔事务，才向查询方提供结果。

有些业务字段本身引用事件。例如，尝试结果需要引用保存该结果的事件，状态同步需要引用完整事务的结束位置。这些引用也是要恢复的业务值，必须保存在事件的字段前后值中。引用本事件时使用预先分配的本事件 ID；引用本事务结束位置时使用本事务最后一条事件的 ID。其他引用按 `history_references` 中逐字段列出的目标处理，已有引用不能在回放时被替换成正在处理的事件 ID。

业务引用、可以重算的历史信息，以及历史基础表中的引用分别由下列规则说明。`history_contract` 指向[逐字段编码及恢复规则](history-formats.md#事件引用与事务边界的编码)，其中定义首次赋值、后续替换、空值、初始化边界和校验时点。

| JSON 成员 | 记录什么 | 怎样解释 |
| --- | --- | --- |
| `history_references` | 业务列引用哪个事件或完整边界 | `creating_event` 是创建该行的事件；`assigning_event` 是保存本次对应事实的事件；`creating_transaction_end` 是创建该行的事务末位；`prior_complete_boundary` 是冻结事务之前的最近完整边界；`baseline_first_chunk`、`baseline_last_chunk` 是本次基准收集的首尾批次事件。业务前后值保留精确引用 |
| `derived_history` | 哪些列可以从对象自身历史计算，以及采用哪种计算方式 | `first_own_event` 取创建事件，`last_own_event` 取目标位置之前或等于该位置的最近自身事件，`own_event_count` 统计不同自身事件。不能改用其他对象的事件，也不能把业务引用改成这一分类 |
| `structural_history_references` | 历史事务、对象关联和快照中的引用 | `target` 是实际外键目标，`rule` 说明额外需要核对的对象、事务范围、业务序号或快照依据。这些表不作为业务事件的行修改目标 |

例如，报告自身的创建和最近管理事件属于派生历史信息；报告的冻结边界及最近成功发布事件属于业务值，需要保存原值。保存一条失败的发布记录时，报告的最近管理事件会前进，最近成功发布事件仍保持原值。逆向恢复分别按两类规则处理，不能一起替换成同一个编号。

## 设计检查工具与后续实现

现有检查工具用于核对规则文件、SQL 表结构和报告字段来源是否一致。在仓库根目录运行：

```sh
node --disable-warning=ExperimentalWarning scripts/check-event-transitions.mjs
node --disable-warning=ExperimentalWarning --test tests/integration/event-transitions.test.mjs
```

修改 JSON 规则文件后，使用检查脚本的 `--write` 参数，更新历史格式文档中的事件清单和 `history.sql` 中允许的事件类型编号，再运行默认检查。工具只更新指定的生成区段，不创建实际状态库。

检查脚本读取 SQL、事件转换规则、内部状态编号和报告字段来源，查找未分类字段、不存在的表列、冲突的分支编号、没有对应事件分支的状态转换、超出允许范围的修改、错误历史归属，以及没有定义的业务校验名称。测试通过合法和非法样例验证这些检查，也覆盖终态被重新打开、固定成员被改变、首次赋值被覆盖和报告所需字段遗漏等情况。

历史字段检查结合实际外键核对引用是否完整分类、规则目标与 SQL 是否一致，以及派生列的计算方式和对象归属。设计检查不执行运行时的引用值校验；例如，外键能证明一个事件存在，却不能证明它确实保存了该尝试的结果。完整事务范围、具体分支和对象身份仍由生产程序按正式契约核对。

辅助函数 `validateRowChange` 只判断一条修改是否符合允许字段、前后条件和状态转换规则，并通过 `pendingGuards` 返回仍需执行的业务校验。函数返回成功只表示这些局部条件成立。负责正式写入数据库的程序还必须核对外部证据、执行全部适用的业务校验，并检查整笔事务，才能保存历史和查询目录。

生产事件处理、设备调用、完整历史恢复和报告生成仍须在实现阶段完成。后续按[数据库一致性验收](consistency-verification.md)验证真实组件共同运行的结果，包括正向恢复、逆向恢复、从初始状态回放的一致性，以及同一份报告重建后字节不变。
