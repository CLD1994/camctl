## 历史事务与事件字段

`history_transactions.id` 按已提交最大值加 1 分配；`first_event_id`、`last_event_id` 指向该组连续事件的首尾。`operation_key` 是调用方在数据库任务入队前生成的 UUID4 小写 32 位十六进制值，用于核实提交结果，不是事件序号或业务流程 ID。同一次保存责任的重查使用同一值。发现该值已经存在时，逐项核对事件类型、目标和输入事实后返回原结果；不生成第二组事件。确认原事务回滚后允许使用原值重试。实际重新提交的输入文件是新的处理责任，取得新值，计划请求幂等仍由 `request_id` 保证。

`history_events` 的列含义如下；类型、可空性和 SQL 约束由结构定义给出。

| 字段 | 含义及空值规则 |
| --- | --- |
| `id`、`transaction_id` | 全局事件位置及所属历史事务；正整数，不能为空 |
| `event_type`、`event_version` | 下文事件种类和正文版本；格式 1 只写版本 1 |
| `occurred_at` | 记录该事实时取得的 UTC 整数微秒，不用作提交顺序 |
| `clock_status` | `UNCHECKED`、`TRUSTED`、`INVALID`；分别表示所在入口未检查、正常会话检查已通过、时钟异常会话。提交输入可以使用 `UNCHECKED`，不因此失去事实效力；编号见[整数编号一览](enum-values.md) |
| `change_seq` | 本事件引起应报告业务变化时分配的独立连续序号；内部管理事件为 SQL `NULL` |
| `body_json` | 版本 1 的事件正文；精确 JSON 对象，格式见下文 |

在同一个 `BEGIN IMMEDIATE` 事务内读取三条最大已提交序列：历史事务 ID、事件 ID、非空 `change_seq`。空序列的基准都是 0。先检查整个事务的编号容量，再一次分配所需范围；`change_seq` 每条应报告事件增加 1，事件影响多个对象时仍只分配一个。没有新增事实的幂等读不创建空历史事务。报告编号由 `reports.id` 自身分配，计划编号由 `plans.id` 自身分配，不增加通用序列表。

事务提交前核对：事件数等于 `last_event_id - first_event_id + 1`，全部事件归属本事务，首尾没有与其他事务重叠，前一个事务的末位与本组首位相接。完整历史边界是 0 或 `history_transactions.last_event_id` 的实际值；0 表示初始化状态，不伪造一条编号为 0 的事件。

## 对象目录与归属

恢复目录与报告目录的列、唯一性和序号规则由[两类目录的结构与职责](report-changes.md#两类目录的结构与职责)定义。历史对象的整数编号、类型标识、主表及报告和快照资格统一由[内部登记](enum-registry.json)的 `history_objects` 提供。对象标识是该节的键，`id` 是持久化编号，`table` 是主表，`report_target` 和 `snapshot` 分别表示两种资格；未登记的类型为错误。目录引用校验和历史恢复读取同一登记，不另建完整类型清单。

SQL 的历史、报告和快照类型范围由[生成工具](../../../scripts/sync-history-object-sql.py)从该登记生成。快照进度中的 `entity_type_name` 是由类型编号生成的虚拟列；候选按 `pending_changes DESC, entity_type_name COLLATE BINARY, entity_id` 排序。类型编号不表示优先级，生成的标识保持大小写，ID 按精确整数比较。生成方式和检查入口见[结构说明](schema/README.md#历史对象登记与生成)。

多态对象目录不能用一个 SQLite 外键引用全部对象表。事件处理器按固定类型分派并核对目标存在、身份与归属；不得把不存在的对象写入目录。`runtime_state` 的对象 ID 固定为 1。初始化状态不产生事件关联，首次实际改变全局状态时计数从 1 开始。

### 自身记录与快照成员

录像 A 的内部拷贝属于 A，源设备文件 F 和目标主机文件 G 则分别是独立历史对象。A 的快照包含拷贝行及其中的 F、G 身份；F、G 的字段从各自历史恢复。一次事件同时更新拷贝和 G 时，分别关联 A 和 G，不把 G 的行复制进 A 的快照。

下表列全业务投影行的历史归属。所属对象的快照包含该对象在快照边界已经存在的全部自身行，包含终态、取消、失效及已完成清理的记录；不按“仍在执行”等当前条件删减。只有下表指定的历史归属决定行是否进入快照，外键引用、业务观察者和报告嵌套位置均不扩大范围。

| 投影表或分支 | 唯一所属历史对象及查找规则 |
| --- | --- |
| `plans` | `id` 指定的计划；不包含其独立动作、产物或交付 |
| `actions` | `id` 指定的动作 |
| `auto_preview_links` | `obtain_action_id` 指定的取回动作 |
| `action_dependencies` | `action_id` 指定的依赖动作，不是 `depends_on_action_id` 指定的来源 |
| `obtain_source_selections` | 沿 `dependency_id` 找到依赖关系，再取其 `action_id` |
| `obtain_items` | 沿 `selection_id` 找到来源选择，再按上一行找到所属取回动作；关联交付独立恢复 |
| `cleanup_items`、`cancel_items` | 各行的 `action_id`；被清理产物和被取消动作独立恢复 |
| `cancel_delivery_items` | 沿 `cancel_item_id` 找到取消项，再取其 `action_id` |
| `device_activities`、`recording_processing` | 各行的 `action_id` |
| `outputs` | `id` 指定的产物 |
| `output_origins` | `output_id` 指定的引用方产物，不是 `original_output_id` 指定的原产物 |
| `deliveries` | `id` 指定的交付 |
| `file_copies`，普通交付分支 | `delivery_id` 指定的交付 |
| `file_copies`，录像内部分支 | 沿 `processing_id` 找到录像处理，再取其 `action_id` |
| `operation_runs`，`READ_FILE` | 沿 `copy_id` 找到拷贝，使用该拷贝的历史归属；流程中重复保存的动作、交付关联须与此一致 |
| `operation_runs`，`STOP_RESIDUAL` 或 `EMERGENCY_STOP` | 沿 `activity_id` 找到设备活动，再取其 `action_id`；后续残留收场的触发者不取得这条流程的历史归属 |
| `operation_runs`，其余类型，包括全部 `QUERY_ACTIVITY` 用途 | 该行的 `action_id`；查询保存的新活动观察另行更新活动所属动作，不能将查询预算一并转给被观察动作 |
| `operation_attempts` | 沿 `run_id` 找到流程，使用该流程的历史归属 |
| `device_files`、`intermediate_files` | 各表的 `id` 指定的文件自身；每个文件快照只包含该文件行 |
| `plan_file_diagnostics`、`reports`、`state_syncs`、`runtime_state` | 各行自身的目录对象；保存可逆历史，但不参加对象快照维护 |

`database_metadata` 属于数据库身份、格式及部署目录管理，不是可由业务事件修改的投影。历史事务、事件、两类查询目录、快照及维护进度不属于上述业务行集合，也不递归进入对象快照。设备基准内容由不可变事件分块保存，动作快照只保留读取这些分块所需的范围引用。

决定历史归属的行身份、父记录身份及流程类型在创建后保持；晚到的结果仍记入原责任。共同建档时允许在同一事务创建整条归属链，但完整提交边界上必须能找到唯一的已有所属对象。未知表或分支、归属链缺失、出现多个所属对象、重复关联矛盾均为状态库一致性错误，不能省略该行或随意选一个所属对象。

事件内同一对象的多条自身行变化合计一次。只修改所属子表时，也必须推进主对象的派生历史元数据、恢复目录和快照维护计数。单对象回放只应用归属于该对象的行变化；事件中的其他对象分别恢复，不能因为共享同一事件正文就把它们混入当前快照。快照读取时校验主行、归属链和重复行；构建时须读完全部自身成员，完整性验收须与同边界的独立回放结果比较，不能仅凭快照中每一行都合法就认定没有漏行。

后续收场流程的建立、实际采用额度及尝试结果按上表归入原设备活动所属动作的历史。即使设备活动列没有变化，所属流程或尝试行的实际变化也须保存原动作的恢复关联并增加自身历史计数。报告目录和业务序号另按[公开字段的依赖登记](report-changes.md#公开字段的依赖登记)判断：只有 `device_execution` 等公开字段的值或出现条件改变时，才登记相应报告目标；仅有内部过程变化时不产生报告变化。

例如，动作 A 已失败，动作 B 随后触发停止 A 留下的设备工作。仅登记停止尝试而 A 的公开结果未变时，只增加 A 的历史记录和计数；可靠确认设备结束后，新报告清除 A 的设备执行提示，A 的失败终态保持。仅引用 B 不增加 B 的历史计数，也不因此选中 B；B 自身状态或结果变化时，按其自身事实另行处理。

文件独立恢复与同边界关联规则见[文件独立历史](outputs-files.md#文件独立历史与关联查询)；其对其他对象报告字段的影响按[字段依赖表](report-changes.md#文件到报告字段的依赖)登记，不将引用关系当作恢复归属。拷贝保存的固定源长度和校验依据仍属于拷贝，不因源文件后来删除而改写。

对象发生内部变化时仍增加自身历史计数。事件有应报告对象时分配业务序号并保存报告目录，否则 `history_events.change_seq` 为空。报告登记、报告文件发布、有效 ACK、同步管理、可信时间和清理游标自身均不产生业务序号；同一事务中的动作开始、结束或清理结果可以另有应报告事件。

## 事件正文版本 1

正文采用以下精确结构，顶层不接受额外字段：

```json
{
  "reason": 1,
  "evidence": {},
  "rows": [
    {
      "table": "actions",
      "id": 8,
      "before": {"exists": true, "values": {"status": 1, "execution_started": 0}},
      "after": {"exists": true, "values": {"status": 2, "execution_started": 1}}
    }
  ]
}
```

`reason` 是下表中该事件类型自己的固定整数分支；编号不跨类型解释。`rows` 是非空数组，按事件内实际应用顺序排列，同一物理行在一个事件中至多出现一次。`table` 只允许格式 1 的业务投影表，不能修改历史、目录、快照、维护进度或元信息。`id` 为精确正整数。创建使用 `before = {"exists": false}`，`after.values` 包含该行全部业务列；初始化后的业务不删除记录，`after.exists` 始终为 true。

更新时两侧 `values` 含有完全相同的列集合，只列出本次发生变化的业务列。列值为 SQL `NULL` 时编码为 JSON `null`；JSON 列先解码为其结构化值，不二次包装字符串。JSON 对象中字段省略与显式 `null` 的区别由对象本身保留。主键、派生历史元数据及生成列不进入 `values`。空更新、未知列、缺少旧值、旧值与前置状态不一致、非法枚举或 JSON 结构均为历史错误。

`evidence` 只保存不能由行变更完整表达的依据。公共成员为 `attempt_id`（正整数，实际操作结果的尝试身份）、`observation`（驱动或工具返回的结构化保证与数据）和 `input_key`（本次输入处理的 32 位十六进制身份）；各分支允许的公共成员及专属成员统一在 [事件转换规则的 JSON 文件](event-transitions.json)登记。未登记的成员不能写入。缺少必要证据时不能写入对应事实；没有额外依据时使用 `{}`。依据仅引用某个对象，不使该对象自动成为变化对象。

由结果页取得的设备结束事实使用 `DEVICE_OBSERVED.OBSERVE` 的公共 `observation` 成员。其结构为 `{result_page_event_id, completion_evidence}`：前者指向原 RESULTS 尝试可靠页范围中的实际页，后者保存该页原 `{type, version, data}` 完成观察。设备观察事件的事实时刻沿用该页实际返回时刻，集合结论继续使用其自身原时刻。写入及原键重送核对原页、原活动、完整观察和原时刻；恢复读取已保存的依据，不访问设备补齐或用本次配置重新解释。

可靠未派发的基准准备已经解除时，`ACTION_FINISHED.FAIL/EXPIRE/CANCEL` 与适用的 `DEVICE_OBSERVED.RELEASE` 可以保存 `preparation_resolved: true`。拥有者必须先确认实际目录调用完成收场，且原页保存申请已经可靠解决；尚未调用目录时，须确认不存在在途准备调用和原保存申请。该事实允许取消、过期或目录读取失败后的 `COLLECTING` 活动释放占用，不说明设备已经结束，不补造空基准或结果集合。省略成员表示没有这项额外依据；不保存 `false`。原键重送核对成员有无及取值，不把当前基准状态反推为原输入。

准备收场时已有动作终态，实际目录错误通过 `DEVICE_OBSERVED.OBSERVE` 保存到原活动的 `last_error_json`，与适用释放共同提交。释放分支携带错误时，登记 `preparation_error: {code, stage, details}`，并须同时携带 `preparation_resolved: true`。该成员保存原完整错误输入，使原键核实不依赖当前活动错误；原错误已经相同则省略重复观察，仍保留释放输入。省略成员表示原释放申请没有错误输入，不等同于事后省略错误。

非电机目标的 `CANCEL_CHANGED.APPLY` 使用专属成员 `cancel_request` 保存原取消申请，结构恰好为 `{"item_id": 正整数, "mode": 字符串, "occurred_at": UTC 微秒整数}`。`mode` 为 `pre_start`、`with_stop`、`terminal` 或 `already`；成员身份、模式及时间须与本事件实际处理的目标和分支一致。原操作键重送逐字段核对这项输入，不通过后续投影或行变化反推原申请。电机目标沿用该分支已登记的 `motor_request` 和适用的 `motor_permit`，不同时保存两份申请身份。该证据不改变动作、同步或成员状态转换，也不进入对外报告。

`INTERMEDIATE_FILE_CHANGED.CLEANUP_RESULT` 必须使用专属成员 `cleanup_request` 保存原清理结果申请中的游标输入，结构恰好为 `{"advance_cursor": 布尔值}`。原文件身份、结果、错误和时刻由同一结果事件表达。自动历史清理保存 `true`，单文件首次清理和显式主机清理保存 `false`。原游标已经指向目标文件时不产生重复位置变化，结果事件仍保存原布尔输入；原操作键重送逐项核对该输入和完整事件组，不能把 `true` 与 `false` 相互替代。该输入不改变文件清理或游标的状态转换，也不进入对外报告。

同一事务可以组合多类事件。复杂集合按成员分批形成事件，最后一条记录集合固定事实，但整个固定操作只提交一次；这样既能逐事件读取，又不会公开半个集合。事件处理器验证该类型允许的表和状态变化，再应用前后值，不能提供一个允许调用者任意写表的通用补丁入口。

`EMERGENCY_RECORDED` 的创建行完整保存应急配置及结果，包括 `intent_event_id = null` 和等于本事件 ID 的 `result_event_id`；它们属于需恢复的列值，不作为可省略的派生元数据。停止证据保存在实际尝试结果或本事件的可靠 `observation` 中，活动变化须有相应依据；事件记录的是补记时保存的事实，不把事件时间冒充设备停止时间。逆向恢复移除本次创建的流程及全部尝试，并恢复活动旧值；只在完整事务边界交付状态。

每个应急补记事件对应一条目标活动及其唯一会话责任，尝试行数必须与流程中的实际次数一致。零尝试但已确认停止时，不能引用不存在的尝试，须在 `evidence.observation` 中保存可靠停止依据；具体字段组合和跨表校验见[应急记录约束](operation-fields.md#应急记录的结构约束与事务校验)。不同录像分别形成补记事务，各自完成后即可提交。

## 事件引用与事务边界的编码

一个事务依次保存动作开始、同步责任创建和计划开始三条事件，事件 ID 分别为 101、102、103。同步记录在事件 102 中创建，但 `started_boundary_event_id` 必须保存 103，因为它表示整笔事务完成后的状态。另一个尝试在事件 104 中保存结果时，`result_event_id` 则保存 104，因为它表示保存该结果的具体事件。这两种引用不能互换。

设正在解释的事件为 E，所属事务的首尾事件为 F、L，事务前最近的完整已提交边界为 P。事件引用保存精确的正整数；只有字段明确允许时才保存 SQL `NULL`，报告冻结还允许初始化边界 0。事件正文的业务列值直接保存对应整数或 JSON `null`，不保存执行时才替换的占位符。事务 ID、事件 ID、业务序号分别解释，不能因数值相同而混用。

### 需要保存前后值的业务引用

下表列出业务投影中的全部事件及边界引用。具体列及目标同时列在[事件规则文件](event-transitions.json)的 `history_references` 中；表内“首次赋值”包括创建时直接保存已有可靠依据的最终结果。创建记录时保存全部业务列，更新时只保存实际变化列的前后值。字段未改变时沿用原值，不能在处理另一个事件时自动改写为 E。

| 字段 | 非空值的目标 | 首次保存、后续修改及空值规则 |
| --- | --- | --- |
| `operation_attempts.intent_event_id` | 创建该普通尝试的事件 E | 普通尝试创建时必填且以后不变。应急尝试创建时为空，之后也不补写普通调用意图 |
| `operation_attempts.result_event_id` | 保存该尝试结束结果的事件 E | 普通尝试未结束时为空，结果与引用一起首次保存后不变；应急尝试在补记创建时填写 E |
| `device_activities.wait_completed_event_id` | 保存本活动等待完成事实的事件 E | 未完成时为空；首次完成后保持。配置改变、重启及后续产物观察不替换该引用 |
| `cleanup_items.final_event_id` | 首次保存该项最终结果的事件 E | 未结束时为空；首次终态及直接创建终态时必填，此后不变。复用已有清理成功依据时，仍引用保存本项成功的事件，不引用其他清理项的结束事件 |
| `deliveries.publication_intent_event_id` | 保存本交付移动意图的事件 E | 意图保存前为空，首次赋值后不变 |
| `deliveries.published_event_id` | 首次保存本交付可靠交接完成的事件 E | 未确认完成时为空，首次赋值后不变；后来撤回不清除已有交接事实 |
| `reports.last_published_event_id` | 保存本报告这一次可靠发布的事件 E | 尚无成功发布时为空；每次成功发布与 `publication_count` 增加共同替换，失败和其他管理变化保持原值 |
| `state_syncs.ended_event_id` | 保存本同步 ACK 完成或取消的事件 E | 未结束时为空；首次结束时必填，此后不变。不使用所引用报告的事件或所在事务末位代替 |
| `runtime_state.trusted_time_event_id` | 首次建立或推进可信时间下界的事件 E | 初始化为空；仅随下界实际推进而首次填写或替换，检查通过但下界未变时不改写 |
| `state_syncs.started_boundary_event_id` | 创建本同步责任的事务末位 L | 创建时必填且以后不变；即使 E 小于 L，也保存 L |
| `reports.frozen_event_id` | 冻结时所见的完整已提交边界 P | 创建时固定，P 必须小于 F；没有已提交事件时为 0。不能包含本次冻结事务中的部分业务变化，补投及重建保持原值 |
| `device_activities.baseline_first_event_id` | 本次基准收集的第一条 `BASELINE_CHUNK.APPEND` 事件 | 新收集首批设为 E，后续批次保持；尚无批次时为空，固定空基准时与末条引用共同置空 |
| `device_activities.baseline_last_event_id` | 本次基准收集的最后一条 `BASELINE_CHUNK.APPEND` 事件 | 每次追加设为 E；首批与首条引用相等，固定非空基准时保持；固定空基准时共同置空 |

基准首尾必须属于同一活动和同一次收集，首条的 `chunk_no` 为 1，后续批号连续。事件范围内可以夹有其他活动或其他类型事件，读取时仍须按活动及分支筛选。中断后重收非空基准时，新首批同时替换两个引用；重收为空时按空基准分支清空。前后值保留被替换的旧范围，以便恢复重收前的状态。

JSON 中的业务依据引用同样保留原整数。例如，文件及活动完成依据中的 `wait_completed_event_id` 引用该活动实际保存的等待完成事件，核对活动身份、事件分支和证据；它不因当前正在保存文件观察而改成 E。此类 JSON 作为所属业务列的完整前后值保存，不能在恢复时仅按成员名称递归替换引用。

### 从对象自身历史计算的元数据

`plans`、`actions`、`outputs`、`deliveries`、`device_files`、`intermediate_files` 的 `created_event_id`、`last_event_id`、`change_count`，以及 `reports.created_event_id`、`reports.last_event_id`、`plan_file_diagnostics.created_event_id`，由对象自身历史计算。这些列不放入事件的 `before.values` 或 `after.values`；主键另由行 ID 表达。它们的计算规则集中列在事件规则文件的 `derived_history` 中。

| 派生列 | 在给定历史位置的值 | 逆向越过一次自身变化时的处理 |
| --- | --- | --- |
| `created_event_id` | 创建该对象的事件；也是该对象第一条自身历史关联 | 对象仍存在时保持；越过创建事件时从查询副本移除该对象 |
| `last_event_id` | 不晚于目标位置的最后一条自身历史关联 | 恢复为该对象此前一条自身关联的事件 ID，不使用 E−1 或数据库其他对象的最新事件 |
| `change_count` | 从创建起、不晚于目标位置的不同自身事件数 | 每撤回一条自身事件减一；同一事件修改多行或多列仍只减一次 |

报告有自己的管理历史，因此其创建和最近变化事件按报告自身关联计算；输入诊断创建后不变，只需计算创建事件。这些字段名称相似，但不能据此将上表中的调用结果、交接或同步引用也归为派生列。只有 `derived_history` 明确列出的列使用本节规则。

正向计算可以利用已经验证的前置计数和本次实际归属增量推进，逆向计算可以使用可信的自身关联定位前一条事件；目录重建时从权威事件恢复这些关联。对象本应存在但找不到创建依据、前条关联缺失或计数矛盾时，按历史错误处理，不借用其他对象的关联。快照保存完整投影行，因此仍包含这些派生值，并核对它们与快照边界一致。

### 历史基础表中的引用

历史事务、事件目录及快照属于历史保存结构，不作为业务事件的行修改目标。其引用按下表保存，规则同时列在事件文件的 `structural_history_references` 中：

| 字段 | 目标及共同校验 |
| --- | --- |
| `history_transactions.first_event_id`、`last_event_id` | 本事务的 F、L；全部事件连续且确实属于该事务，不能引用另一事务的首尾 |
| `history_events.transaction_id` | 该事件所属事务的 ID；该事务的范围必须包含 E |
| `entity_event_links.event_id` | 实际改变该对象自身记录的事件；对象归属及去重计数同时正确 |
| `report_entity_changes.event_id`、`change_seq` | 使该对象公开结果改变的同一事件及其非空业务序号；两列必须成对匹配 |
| `entity_snapshots.boundary_event_id` | 快照实际表达的完整已提交边界 S；对象已存在，正文头、内容和计数共同属于 S |
| `entity_snapshot_progress.latest_snapshot_id` | 该对象维护规则选定的最近快照；对象身份、边界及基准计数一致，尚无快照时为空 |

### 引用的校验时点与恢复

引用首先要有合法类型及对应目标含义，再按下面的时点分类检查。所有事件及引用共同提交；事件查询可以分批读取，但不能在一笔事务尚未解释完整时向调用方提供状态。

| 引用与当前事件的关系 | 保存及恢复时的判定 |
| --- | --- |
| 引用本事件 E | 核对当前分支确实保存该行对应的意图、结果或其他事实；仅有编号相等不够 |
| 引用此前的事件或完整边界 | 目标必须可靠存在，类型、对象及原事实符合字段契约；不可读取属于错误，不能解释为空值 |
| 按字段规则引用本事务末位 L，且 E 小于 L | 按预先确定的事务范围校验，允许目标行稍后写入；提交前核对完整分组。L 未成为完整提交边界前，不对外提供依赖它的状态 |
| 字段不允许指向后续事件，却保存了大于 E 的值；或引用超出本事务范围的未来事件 | 拒绝保存；历史读取遇到同样情况则报错，不等待未来事件补齐 |
| 字段允许为空、为 0 或从旧值替换 | 只按该字段及所属业务状态的规则处理；不能用空值、0 或 E 代替缺失依据 |

逆向恢复业务引用时，先核对查询副本等于事件保存的新值，再恢复原旧值；创建记录则恢复为不存在。解释旧事件时使用它原来所属事务的 F、L，不使用恢复程序当前事务的边界。派生元数据按上一节分别恢复。引用及其目标在分批读取中尚未凑齐时，只保留内部处理位置，读取错误或缺失记录必须使整次历史查询失败。

## 拍摄基准的分批记录

需要完整目录基准时，`BASELINE_CHUNK.APPEND`（`reason = 1`）的 `evidence` 使用 `activity_id`、`chunk_no`、`entries`，前两项是正整数；`entries` 为本批驱动稳定文件身份的数组，成员采用驱动已声明的定位结构，不登记为设备业务文件。每批为 1—128 项，按驱动稳定身份排序并去重，应用层流式形成批次；单项很大时仍按其精确 JSON 编码处理。

`BASELINE_CHUNK.FIX`（`reason = 2`）只固定非空基准，`evidence` 使用 `activity_id` 及正整数计数 `chunk_count`、`entry_count`。`BASELINE_CHUNK.FIX_EMPTY`（`reason = 3`）固定空基准，保存零批、零项，并将基准首尾事件引用共同置空；尚未派发且基准仍在收集时，即使旧收集已有批次，新收集为空也按此分支保存，不追加空批次。

目录基准可以跨多个事务追加，但 `baseline_state` 保持收集中，设备和输出范围占用持续有效。最终固定事务检查分块连续及计数后才允许启动。中断后未固定的基准不能直接用于差集；尚未派发时重新读取基准，新的收集使用新的首尾事件范围，旧事件保留。固定后首尾范围不变。恢复从该范围内属于该活动及本次基准的事件分页读取，不将其他事件或旧基准混入。紧凑编号基准按同一结构保存为一个驱动定义的基准项。

## 结果页的分批记录

`RESULT_PAGE.APPEND` 保存同一 RESULTS 尝试的一批实际返回。页中的完整文件观察与 `operation_attempts.result_first_page_event_id`、`result_last_page_event_id` 同事务保存；实际差集中的首次发现同时使用 `DEVICE_FILE_OBSERVED.CREATE` 保存设备文件。归属、在场、完成及配对仍沿已有独立文件事实责任可靠保存，原页已经保存不能使未完成子责任消失。全部页和适用文件事实可靠后才允许集合结论、产物或终态成立。

该分支恰好使用 `attempt_id` 和 `result_page` 两个 evidence 成员。`attempt_id` 是物理尝试 ID；`result_page` 恰好包含 `run_id`、`attempt_no`、`activity_id`、`page_no`、`cursor`、`outcome`、`baseline_position`、`last_identity`、`file_ids`。前三项是原票据的正整数身份，`page_no` 从 1 连续递增。`cursor` 是本次原请求游标。`outcome` 恰好包含 `status`、`effect_state`、`error`、`result`：前两项使用尝试行的整数枚举；后两项保持完整实际错误和格式 1 的实际调用结果，不能只保留最后一页的退出信息。

`baseline_position` 为 JSON `null` 或 `{event_id, entry_index}`，表示原固定基准中尚未比较的下一项；空基准和已比较完的基准为 `null`，不把新的目录事实写回基准。`last_identity` 是本轮已取得的最后稳定身份或 JSON `null`，空中间页保留此前身份。`file_ids` 是本页新文件的 `[驱动文件身份, 设备文件 ID]` 数组，只包含原任务的实际差集或任务范围文件，不登记历史基准文件。该引用与已保存的原页输入共同用于独立文件事实恢复，不能由后来投影替代原输入。

首次页将首末引用共同设为本页事件 E，后续页只推进末引用。范围内允许夹有其他事件；读取按原物理尝试及页分支筛选，核对页号和游标连续。无后续游标或实际调用错误的页不允许继续追加。页保存保持尝试 `RUNNING`，不增加尝试次数，也不虚构整轮的一次本地或远端退出。页或文件发现提交未知时沿原完整申请、key 和时刻核实，可靠回执前不读下一页。

## 正向、逆向与快照格式

正向回放先验证 `before`，再应用 `after`；逆向按事件和行的相反顺序验证 `after` 并恢复 `before`。逆向遇到创建事实只从查询副本移除该行，不删除真实数据库记录。事件结束后按实际变化对象派生目录及历史元数据；事务尚未读完时不交付中间状态。未知类型、版本、缺失旧值或矛盾状态均报历史错误，不跳过。

`entity_snapshots` 保存对象类型、ID、完整边界 `boundary_event_id`、该边界的 `change_count`、`format_version` 和二进制列 `content`。内容是 UTF-8 JSON Lines（每行一个 JSON 值，以 LF 结束），首行固定为 `{"format_version":1,"entity_type":1,"entity_id":8,"boundary_event_id":120,"change_count":64}` 这样的头记录；后续每行使用 `{"table":"actions","row":{...}}` 保存一个完整投影行。表按表名的固定字典序、行按 ID 升序排列；JSON 行使用项目的精确确定编码，不包含派生目录和快照表。`row` 包含主键及该行完整投影列，包括主对象的历史元数据；JSON 列解码为结构化值，SQL 空值编码为 `null`。读取时核对头信息、对象归属和行结构，不把快照内容当成无需校验的任意 SQL。

快照包含主对象及上文归属表定义的自身记录及稳定引用；各文件快照保存文件自身行，不递归包含引用的独立对象。设备基准保留指向不可变事件分块的范围，不复制旧设备目录。保存时先在事务外流式编码临时文件，取得长度后在维护事务内插入 `zeroblob`，使用标准库 `sqlite3.Connection.blobopen` 分块写入；默认缓冲为 64 KiB，不先把整个对象拼成一个 Python 字符串。快照和进度必须一起提交；未完成的 BLOB 写入回滚，不向读取者公开部分内容。

`entity_snapshot_progress` 保存对象身份、`current_change_count`、`snapshot_change_count` 和 `latest_snapshot_id`；`pending_changes` 是两项计数之差的存储生成列。无快照时后两项为 0 和 SQL `NULL`。新快照的对象、边界、计数必须匹配实际历史；保存时按写事务最新累计次数计算差值，旧边界的迟到结果不能降低最近快照基准。同一对象与边界重复保存时核对已有内容并复用，不重复扣减次数。

## 查询形状与索引

对象在 H 的末条关联使用 `entity_type = ? AND entity_id = ? AND event_id <= ? ORDER BY event_id DESC LIMIT 1`；正反向回放使用相同唯一索引按 `event_id` 翻页。报告对象选择从 `report_entity_changes` 限定类型和 `(from_wm, to_wm]`，在数据库内按整数 ID 去重和游标分页。候选预查询、容量判断与大范围续读采用[报告对象选择的具体 SQL](report-changes.md#报告对象选择的索引与分页)，不在每页重新扫描整个业务区间。父对象补齐通过业务外键读取，不改变目录。

快照使用对象及边界唯一索引，按 `boundary_event_id <= H ORDER BY boundary_event_id DESC LIMIT 1` 选择。维护使用 `pending_changes >= :threshold ORDER BY pending_changes DESC, entity_type_name COLLATE BINARY, entity_id LIMIT :batch`，对应 `snapshot_candidates`。获取事件正文时限定已选 ID 和完整读取上界，不能扫描全部历史再在 Python 中筛选。初始化边界 0 的查询直接返回定义的初始状态。
