## 基准目录调用

`baseline_read_calls` 保存完整目录基准的一次实际读取责任，属于 `action_id` 指定的动作历史。它保存调用前的原始输入及实际返回身份，不登记目录中的业务文件，也不替代操作流程的尝试编号。目录页内容仍只由原 `BASELINE_CHUNK.APPEND` 保存。

| 字段 | 类型、空值与含义 |
| --- | --- |
| `id`、`created_event_id` | 正整数主键及创建意图的实际历史事件外键；创建后固定。 |
| `action_id`、`activity_id` | 必填动作及原准备活动外键；活动必须属于该动作，历史归属为动作。 |
| `call_key`、`result_save_key` | 必填、各自唯一的32位小写操作键；调用前分别生成且互不相同。两列之间也不得复用其他调用的键。INTEND使用call_key，实际结果使用原result_save_key。 |
| `device_id`、`driver_id` | 必填原动作绑定，创建后固定。 |
| `directories_json`、`cursor_json`、`timeout_s_json` | 规范完整目录数组、可空原输入游标和精确正超时数字。游标为空表示首次读取，其余游标必须绑定相同设备及完整目录；输入均固定。 |
| `baseline_first_event_id`、`baseline_last_event_id` | 可空原基准前缀首末事件外键；空前缀共同为空，非空前缀共同有值且首不晚于末。 |
| `chunk_count`、`entry_count`、`read_no` | 必填非负前缀批数和条数、正整数调用序号。前缀为空时两计数为零，否则条数不小于批数；同一活动的read_no唯一连续，空页也消耗调用序号。 |
| `state` | 必填INTENDED、RETURNED或UNCONFIRMED；只从INTENDED进入一种结果，不重开。 |
| `returned_at`、`result_event_id` | 可空UTC整数微秒实际返回时刻和结果事件外键。INTENDED时共同为空；RETURNED时共同有值；UNCONFIRMED只保存结果事件，不补造返回时刻。 |
| `error_json`、`next_cursor_json`、`chunk_event_id` | 可空实际错误、成功页下一游标和原基准批次事件外键。INTENDED及UNCONFIRMED时均为空；错误返回不带下一游标或批次。成功非空页引用同组前序APPEND，成功空页不建批次，是否结束由下一游标判断。 |

意图创建必须核对原动作的准备资格：沿原执行路径时要求 `RUNNING + execution_started=1`；首次独立提前准备时要求 `PENDING + execution_started=0`；原动作已开始、但原 `START` 均有可靠无效果依据且仍可重试时，保留 `RUNNING + execution_started=1`。独立准备路径均须持有当前会话已经可靠保存的设置准备结果。两者均要求活动为 `COLLECTING/NOT_DISPATCHED/HELD`，绑定、目录、实际前缀及连续调用关系完整。首调用从空前缀和空游标开始；后续调用只沿前一成功RETURNED的非空下一游标继续，前一调用未结束、出错、返回未知或已到末页时不创建下一调用。

INTEND独立提交。非空成功页的APPEND与RETURN按此顺序在同一事务保存；空页、实际错误或返回未知各只保存一个结果事件。结果列首次赋值后固定。意图不表示已经派发，调用结果不自行结束动作、固定基准或释放活动。实际返回未知的拥有者及后续收场规则见[核实结束与终态提交](../../superpowers/specs/2026-10-20-osmo360ii-record-segmentation-design.md#核实结束与终态提交)；接入进度由[分段实施计划](../../superpowers/plans/2026-10-21-osmo360ii-record-segmentation.md#p4把分段规则接入正常录像异常恢复和空尾分类)跟踪。

本会话新建意图的拥有者可靠确认实际读取尚未开始时，原意图保存恢复成功后继续使用同一拥有者、序号及双键，不创建替代调用。取消或启动窗口结束后不再发起读取，先按原结果键保存 UNCONFIRMED，再提交动作终态及解除占用；没有实际返回时不填写 `returned_at` 或 `error_json`。冷恢复读取到 INTENDED 不能单凭没有本地 Task 推断原调用未派发，仍须按既定恢复边界收场。实际读取仍在执行时，其他流程保留等待；只有已有保存申请未可靠完成才按状态保存错误处理。

SQL约束主外键、两键各自唯一、同活动序号唯一、状态与空值组合。业务守卫独立核对原设备/目录/前缀、跨列键唯一性、连续调用和实际批次来源。动作恢复及快照包含调用行；按 `(action_id,id)` 分页发现原调用，历史读取使用固定完整边界，不从当前状态改写原始输入。

## 操作流程的身份与参数

`RESOLVE_OUTPUT_SCOPE` 要求整体格式 V6，拥有者为原拍摄动作，目标为其原活动。原活动必须已经 `ENDED`、占用仍为 `HELD` 且基准为 `FIXED`，输出范围尚未确定；原动作可以已经终态。该责任使用 `operation=result`，按原设备本次 `result_check` 配置独立累计有限次数、超时和间隔，不修改原 `CHECK_CAPTURE_RESULTS` 流程、尝试、动作终态或错误。新拍摄在有效提前准备期间触发范围收尾，调度重扫和重启复用同一责任。

范围页沿用 `result_files_listed/v2` 的可靠分页结构，只枚举文件身份，不读取元数据。成功末页的 `set_finalized=true` 与原固定基准差集的完整归属共同支持 `OUTPUTS_FINALIZED`，文件大小未知、文件完整性未确认不阻止范围成立。适用的结束后等待仍沿原可靠停止来源核对；范围事实可靠保存后，沿统一占用释放入口解除原占用。

`operation_runs.id` 表示一项操作责任；普通未完成责任可以跨会话继续，应急责任限于其所属会话。`action_id` 必填，表示承担该流程的动作；普通交付读取还填写 `delivery_id`，此时其历史归属交付；后续残留收场归属原设备活动动作的历史，`action_id` 另表示触发者。该流程实际改变原动作的公开字段时，报告更新原动作。`responsibility_key` 按下表格式确定，全库唯一，里面的 ID 使用无前导零十进制表示。

| `kind` | 责任键 | 必填目标引用 |
| --- | --- | --- |
| `START` | `start/<action_id>` | `activity_id` |
| `STOP` | `stop/<action_id>` | `activity_id`；正常、取消和恢复共用 |
| `READ_FILE` | `read/<copy_id>` | `copy_id` |
| `DELETE_FILE` | `delete/<cleanup_item_id>` | `cleanup_item_id` |
| `CHECK_FILE_EXISTS`（清理） | `exists/<cleanup_item_id>` | `cleanup_item_id` |
| `CHECK_FILE_EXISTS`（显式取回源检查） | `obtain-exists/<obtain_item_id>` | `obtain_item_id` |
| `QUERY_ACTIVITY` | 按[活动查询的责任范围](#活动查询的责任范围)唯一确定 | 执行前检查指向 `action_id` 保存的设备绑定；其余用途必填目标 `activity_id` |
| `CHECK_DEVICE_AVAILABILITY` | 由稳定检查 ID 唯一确定，见[检查记录](../hasselblad-availability-recovery.md#数据与事件模型) | 独立检查及其固定目标集合；流程归触发动作，不冒充单一活动查询或 READ |
| `CHECK_CAPTURE_RESULTS` | `results/<activity_id>` | `activity_id` |
| `RESOLVE_OUTPUT_SCOPE` | `scope/<activity_id>` | 原拍摄动作的 `activity_id` |
| `STOP_RESIDUAL` | `followup/<action_id>/<activity_id>` | 原历史 `activity_id`；动作是新的触发者 |
| `EMERGENCY_STOP` | `emergency/<session_key>/<activity_id>` | `activity_id` 和 `session_key` |
| `PREPARE_CAPTURE` | `prepare/<activity_id>/<session_key>` | 原动作的 `activity_id` 和当前 `session_key` |

`activity_id`、`copy_id`、`cleanup_item_id`、`obtain_item_id` 按表中责任填写，互不混用。CHECK 恰好选择 cleanup 或 obtain 一种 owner；DELETE 只接受 cleanup。执行前状态检查的四个目标列均为空，目标相机由发起动作已经保存的设备绑定确定；观察到的活动按实际证据关联，不改变该查询责任的身份。其余流程填写对应的目标列，其余目标列为空。`session_key` 是本次 CLI 进程取得的 UUID4 小写 32 位十六进制身份，应急和独立准备流程必须填写，其他流程必须为空；它区分同一会话的唯一责任，不新增会话表。除执行前检查和下述独立可用性检查外，设备绑定从活动原动作、拷贝实际源文件或清理目标文件取得，不从触发动作猜测。

`CHECK_DEVICE_AVAILABILITY` 使用[独立检查关系](../hasselblad-availability-recovery.md#数据与事件模型)保存目标，原有 activity、copy、cleanup、obtain 目标列保持不适用；检查通过明确的专属关联定位。流程复用公共状态、尝试和原结果保存，终结与取消分区由[可用性恢复](../hasselblad-availability-recovery.md#检查责任共享与有限预算)定义。

录像和延时的 `PREPARE_CAPTURE` 要求整体格式 V4，照片要求 V5。取得准备资格时，原动作保持 `PENDING + execution_started=0`，通过 `DEVICE_OBSERVED.CREATE` 建立唯一活动及占用；到计划时间开始执行时复用该活动。录像和延时的原动作已经开始且原 `START` 均可靠无效果时，新会话设置准备复用原活动和固定基准，保留执行标记及累计 `START` 次数；照片存在任一 START 责任时沿原收场或恢复路径处理。每个会话对同一活动只允许一次设置组合，流程及尝试的 `max_attempts_used=1`，`timeout_s_json` 保存本次设置准备的整体预算，包含适用的独立设备配置预算及普通控制预算，`retry_interval_s_json` 为空，`retry_wait_required=0`。准备尝试按普通意图和结果事件可靠保存，允许流程因取消或窗口结束进入 `CANCELED` 或 `EXPIRED`；已开始的调用仍须独立收场。设置成功不消耗 `START` 次数，也不替代驱动当前会话凭据和适用的固定完整基准。详细资格与恢复规则见[拍摄提前准备规格](../../superpowers/specs/2026-10-25-capture-preparation-design.md)。

显式取回源检查的固定归属沿 `obtain_items.selection_id → obtain_source_selections.dependency_id → action_dependencies.action_id` 核对原获取动作；以 `requested_output_id` 定位产物，再以唯一 `device_file_id` 或 `intermediate_file_id` 载体确定设备或主机配置。未选择条目的 `output_id` 可以为空。这项身份核对不判定产物可用性、文件存在性或取回资格。主机 CHECK 的流程和每次尝试保存空 timeout/interval；开放原责任的后续票据还要求上一票已有完整结果与结果事件，沿用累计次数。设备 CHECK 保存正 timeout 和非负 interval，间隔为零仍要求已有重试等待责任。原键重送核对原 owner、采用配置和时刻，返回原票据及历史；终态或预算耗尽不建立新尝试。

有限和有界写入入口按实际流程及创建行自动绑定同连接的取回检查读取端口，不能通过省略读取范围或自报上下文关闭核验。一次尝试意图涉及的每个取回检查流程必须各自创建恰好一张新票；同事件中其他流程的新票不能代替它，也不能只增加累计次数。守卫从实际固定关系核配置分区，并定点读取紧邻前票、原意图和原结果事件；完整结果事务必须早于本次 F。结果事件只保存实际变更列，未变列从原意图创建行恢复，重建后的状态、效果、正文、错误和结果引用须与前票相同。读取错误、引用损坏或未完成前票均拒绝新票，不消费未来提案作为依据。其他操作仍遵守自身的保存规则。

普通流程的 `attempts_used` 从 0 开始，每登记一次新的尝试增加 1，无尝试时为 0，否则必须等于该流程已有尝试的最大 `attempt_no`。应急流程按[最终补记](#应急停止的最终补记)一次保存实际次数及配置，未尝试时允许保留未知配置。`max_attempts_used` 保存最后一次实际资格判断使用的上限，`timeout_s_json`、`retry_interval_s_json` 保存其实际超时和重试间隔，有值时都是精确 JSON 数字文本。主机文件操作没有应用层调用时限，超时列为空；不适用定时重试时，间隔列为空。普通流程的配置空值表示不适用；应急零尝试记录还允许用空值表达未能可靠取得的配置，含义按[补记字段组合](#应急记录的结构约束与事务校验)区分。不能把零当成无限超时。超时为有限正秒数，间隔为有限非负秒数；使用数字文本避免把允许的小数秒截断成整数微秒。读取时按精确数值适配，不能把字符串直接输出到公共秒数字段。

`retry_wait_required` 为 0 或 1，保存本流程的重试间隔责任。进入、清除、其他条件阻挡、取消、预算变化与恢复按[重试责任转换](waiting.md#重试责任的完整转换)处理。实际使用新配置时保存依据；只加载配置不写库。普通流程采用降低后的上限时，上限可以小于累计已用次数；应急限额在本会话内固定，实际次数不得超过该限额。

读取流程的最近尝试已可靠保存 `UNKNOWN/result_not_saved`，不能继续原票据且没有可直接完成的可靠副本时，若已用次数达到本次上限，按[读取尝试预算](../../architecture/file-copy.md#按文件累计读取尝试)将流程结束为 `FAILED/read_attempts_exhausted`。事务独立核对原尝试、完整结果与收场、当前拷贝和所属工作资格，保存实际采用的上限并清除重试等待；不修改原尝试、追加读取或授予机会。原键重送核实原完整事务；所属交付或内部处理沿原失败及取消规则继续收场。

`status` 为 `PENDING`、`ACTIVE`、`SUCCEEDED`、`FAILED`、`CANCELED`、`UNCONFIRMED`、`EXPIRED`。`EXPIRED` 用于启动、独立准备或可用性检查责任随动作过期结束，以及尚未尝试的后续残留收场因触发动作过期结束；前三类流程保留已有尝试和累计次数，后续残留收场仍要求尚未尝试。`SUCCEEDED`、`FAILED`、`CANCELED`、`EXPIRED` 表示该操作责任的最终结果；`UNCONFIRMED` 表示有限处理结束但其外部效果尚未确认，原普通责任不自动重开。后续可靠观察更新设备或文件事实，而非把原失败流程改判成功。`FAILED`、`UNCONFIRMED` 必须有 `error_json`；单次尝试失败但仍在重试时可为 `ACTIVE`，不直接结束动作。可用性检查与取消、过期同时发生时，先消费原调用结果，再按其专属终结分区判断。

录像 `START` 的合法字段组合、转换、结束条件及当前机会推导由[录像启动流程](recording-start.md)定义。首次尝试共同建立 `ACTIVE` 责任；结束状态不重新激活。流程的业务结果与尚未收场的尝试分别保存，恢复不能仅查询未结束流程。

一次查询响应成功表示该次尝试取得了可靠响应，查询流程是否完成还取决于所属责任。启动核实取得符合启动契约的可靠证据时可以完成；停止核实发现目标活动仍在执行时，若仍有继续资格则保持 `ACTIVE`，后续检查继续使用同一流程和累计次数。存在性查询发现文件仍在时，继续按清理责任处理。查询、结果核实的每次实际检查均占一次额度，包括正常返回但条件尚未满足的检查。责任目标达成、所属处理结束或明确放弃核实时，流程才随所属责任结束；不能仅因响应成功就结束尚未完成的查询责任，再为后续查询建立新预算。结果核实一次尝试可以分页读取同一检查轮次的文件集合，不按页数或文件数增加尝试。

本地主机文件操作记录实际尝试，不套用设备调用时限或设备重试间隔。普通本地读取的首次操作上限为 1，失败后按所属文件规则结束；正式产物清理的 DELETE 与 CHECK_FILE_EXISTS 则统一采用[独立清理预算](../../architecture/output-cleanup.md#删除与查询的独立尝试预算)，涵盖主机 original、preview、repaired，不受普通本地读取上限约束。主机清理的 `timeout_s_json`、`retry_interval_s_json` 均为空，没有隐含的定时重试或新增主机配置。设备参数使用本次加载的对应操作配置，有限次数和间隔不从动作时长推算。

`QUERY_ACTIVITY` 和独立的 `CHECK_DEVICE_AVAILABILITY` 从本次目标设备的 `query` 配置取得次数、间隔及调用时限，各自责任分别计数，`CHECK_CAPTURE_RESULTS` 从 `result_check` 配置取得；字段与默认值统一见[查询与核实配置](../../architecture/configuration.md#状态查询与产物核实的配置)。流程及尝试分别将实际值保存到 `max_attempts_used`、`retry_interval_s_json`、`timeout_s_json`。结果核实的 `timeout_s_json` 表示该轮每次适用设备查询的时限，不是整轮总时限；批次不增加尝试次数，轮内设备查询失败后不隐式重试。

### 显式分段来源的文件核实

普通分段来源的显式取回项已确认产物归属、但文件可用性尚未确认时，使用该项唯一的 `obtain-exists/<obtain_item_id>` 责任核实原文件。设备调用采用当前查询预算及设备文件查询的超时、间隔配置；未知返回继续原累计次数，耗尽后保存 `source_file_unconfirmed`，不解释为文件缺失。原调用及其保存未决时，先接手原票据和原完整结果，不派发替代查询。

ADB 文件端口对这类责任保存 `file_presence/v2`，正文为 `obtain_item_id` 和布尔 `present`；清理仍使用原 `file_presence/v1` 与 `cleanup_item_id`。可靠结果先绑定原 `ATTEMPT_RESULT`，再保存文件存在性、产物观察及原取回项的解析或失败。产物观察和具有可靠在场／缺席依据的项结算使用 `obtain_check_source: {item_id, result_event_id}`，写守卫从原实际结果独立核对目标和观察。失败项保留已经确认的正式产物关联；重送核对原完整事件和时刻。后续清理限制仍按当前资格执行，不以已查询在场绕过清理。

## 活动查询的责任范围

录像 A 停止失败后，录像 B 为判断自己能否启动而查询绑定相机的状态，并从可靠响应中确认 A 仍在运行。后来录像 C 也需要查询这台相机时，C 的查询属于 C 自己的处理责任。两者可以观察到同一条设备活动，但分别保存查询流程及累计次数；B 用完次数不消耗 C 的额度。相机没有已登记活动时，执行前检查仍可按驱动契约进行，不能为满足查询关联而创建虚构活动。

查询流程按下表中的发起责任、用途和目标唯一确定。五种用途的责任规则见[查询用途、责任键和目标字段](#查询用途责任键和目标字段)，不由调用函数、调度次数、尝试编号或会话身份临时命名。各用途分别累计次数；未实际需要查询的用途不消耗额度。产物结果核实另用 `CHECK_CAPTURE_RESULTS`，其范围见[产物结果核实](#产物结果核实的责任与轮次)。

| 查询用途 | 发起责任与固定目标 | 继续和结束的边界 |
| --- | --- | --- |
| 执行前检查 | 发起动作对自身绑定相机的执行准备责任 | 取得空闲等观察后仍按实际占用和调度资格执行；尚未执行且仍需再次检查时沿用原次数，执行准备结束后不重开。观察到不同活动不刷新预算 |
| 启动核实 | 同一 `START` 责任及其目标活动 | 按下节核实本次启动；多次启动尝试共用该查询预算 |
| 活动核实 | 原拍摄动作管理同一已启动活动的责任 | 按需确认运行状态、源文件关联或自行完成情况；重启对账沿用原次数。仍需管理活动时，一次正常观察不结束整项查询责任；转入停止处理或活动管理结束时结束该责任 |
| 停止核实 | 同一 `STOP` 责任及其目标活动 | 按下节核实停止结果；正常、取消及恢复沿用原次数 |
| 残留收场核实 | 同一 `STOP_RESIDUAL` 责任及其目标历史活动 | 核实该次残留停止的结果，与触发动作的执行前检查、原录像的停止核实及触发动作自身的停止核实分别计数；随原残留收场结束 |

执行前检查发现其他动作正常占用设备时，按已有占用和窗口规则等待，不为等待新增周期查询。残留停止已经可靠证明设备空闲时，可以使用该证据继续判断执行资格，不为完成执行前查询的形式而追加调用。活动核实的存在也不新增拍摄期间的周期检查；查询时机继续遵守驱动、拍摄及恢复契约。

| 查询责任与运行情况 | 流程身份与次数 |
| --- | --- |
| 同一触发动作继续同一项查询责任，包括调度重入、通信重试或原请求重送 | 复用原查询流程及累计次数，不因进入查询函数而另建流程 |
| camctl 重启后继续上述未完成责任 | 恢复原流程、尝试及已用次数；新增尝试按本次配置判断资格，不按会话刷新额度 |
| 不同触发动作分别查询同一活动 | 使用各自的查询流程与次数，目标活动身份保持不变 |
| 原查询流程已经结束 | 保持原结果，不为同一责任换身份重新取得次数；后续可靠观察按设备事实保存 |
| 旧查询调用尚未完成适用收场，新的责任准备执行 | 保留并跟踪旧尝试；独立额度不解除设备占用或相关调用的执行限制，不能借新流程绕过收场 |

查询流程的 `action_id` 指向发起该责任的动作，目标与设备绑定按用途确定。查询尝试及预算属于发起动作的历史；查询改变已知活动事实时，同时保存该活动所属动作的实际变化与历史。查询的独立计数不改变旧录像的终态，也不授予新动作启动或停止设备的权限。

恢复先根据已保存事实确定仍需处理的责任：启动结果未确认时继续启动核实；已启动且尚未进入停止处理时继续活动核实；停止结果未确认时继续对应停止核实；设备阶段已经完成时继续尚未完成的产物处理。重启不单独产生查询用途，也不重开已经结束的启动或停止核实。已有可靠结果可以满足当前判断时直接使用；仍需取得新的设备观察时，在对应原责任内登记新的查询尝试，保留此前已用次数。

取消或过期结束普通执行资格时，不再新增普通执行前检查或活动核实；已开始的调用仍须完成适用收场并保存实际结果。必要停止及已经开始的残留收场按各自契约继续，其查询次数保持原值。查询额度耗尽而仍需新观察时，按所属责任的有限处理失败或未确认规则结束，不换用途取得额度，也不将未知状态解释为设备空闲。会话应急停止继续遵守独立应急契约。

### 查询用途、责任键和目标字段

同一个动作可能先检查设备是否空闲，再核实启动是否成功，最后核实设备是否停止。为了让恢复程序明确区分这些工作，`operation_runs.query_purpose` 保存查询用途。该字段与发起动作、目标和责任键一起在创建流程时确定，此后保持不变。整数编号及名称集中列在[内部类型与状态说明](enum-registry.json)的 `operation_runs.query_purpose` 中。

| `query_purpose` | 查询目的 | `responsibility_key` | `activity_id` 及关联要求 |
| --- | --- | --- | --- |
| `BEFORE_EXECUTION` | 检查发起动作所绑定的设备是否满足执行条件 | `query/preflight/<action_id>` | 必须为空。设备从发起动作已保存的绑定取得；后来观察到哪条活动，都不改变这个查询流程。 |
| `START_CONFIRMATION` | 核实原启动流程的结果 | `query/start/<action_id>/<activity_id>` | 必填，指向该动作的活动。必须能找到同一动作、同一活动的 `START` 流程；多次启动尝试沿用此查询流程。 |
| `ACTIVITY_OBSERVATION` | 在原动作仍管理活动时，按需确认状态、文件关联或自行完成情况 | `query/activity/<action_id>/<activity_id>` | 必填，指向该动作已经启动的活动。进入停止处理后，不再通过本用途取得新的查询次数。 |
| `STOP_CONFIRMATION` | 核实原普通停止流程的结果 | `query/stop/<action_id>/<activity_id>` | 必填，指向该动作的活动。必须能找到同一动作、同一活动的 `STOP` 流程；正常、取消及恢复使用同一查询流程。 |
| `RESIDUAL_STOP_CONFIRMATION` | 核实本次后续收场是否停止了历史残留活动 | `query/residual/<action_id>/<activity_id>` | 必填，指向待收场的历史活动。必须能找到相同触发动作、相同目标活动的 `STOP_RESIDUAL` 流程；触发动作与活动所属动作分别保留。 |

只有 `kind = 6 QUERY_ACTIVITY` 必须填写 `query_purpose`，其他操作该字段必须为空。查询流程的 `delivery_id`、`copy_id`、`cleanup_item_id`、`obtain_item_id` 和 `session_key` 均为空。启动核实、活动核实及普通停止核实的 `action_id` 必须等于目标活动的 `action_id`；残留收场核实则使用原收场流程的触发动作。

表中的责任键是确定的字符串格式，ID 使用无前导零十进制表示。SQL 检查键值与用途、动作和活动字段是否一致，再用全库唯一约束拒绝重复责任。已经结束的流程仍保留原键；更换调用入口、重启或提高上限都不能为同一责任创建第二条记录。结果核实同样检查 `results/<activity_id>`，每条活动至多有一个结果核实流程。

SQL 负责列值、空值组合、责任键格式及唯一性。保存事件的程序还必须检查设备绑定、动作类型、活动归属，以及上表要求的原启动、停止或残留收场流程确实存在并且关系一致。这些跨表检查在同一写事务中完成，不能仅凭字符串格式正确就认定查询合法。

### 一次查询结束与整项核实结束

一次查询正常返回，只说明本次尝试取得了响应。例如，停止核实查到设备仍在录制时，本次查询尝试可以成功，但停止核实流程仍未完成。执行前检查曾取得空闲观察，也不表示后续一定能启动；如果该动作仍需再次检查，继续使用同一流程及已用次数。

以下分类适用于状态查询和产物结果核实。先判断原流程是否已经结束，再判断该用途是否仍承担必要工作，最后按可靠结果和继续条件处理。触发动作被取消或过期，不自动结束仍须继续的普通停止或已开始的残留收场核实。

| 保存时的情况 | 流程状态及后续处理 |
| --- | --- |
| 流程已有最终结果，包括 `UNCONFIRMED` | 保持原流程状态、错误及配置依据。迟到结果只结束尚未结束的尝试，并保存实际设备或文件观察。 |
| 该用途因取消、过期或明确放弃而不再承担核实责任 | 流程保存 `CANCELED`，清除重试等待要求。已开始的尝试仍完成适用收场并保存结果，已用次数不退还。查询流程不使用 `EXPIRED`；动作自身的取消或过期结果分别保留。 |
| 该用途需要确认的目标已有可靠依据，且该项责任可以结束 | 流程保存 `SUCCEEDED`。来源可以是本次查询，也可以是其他操作已保存、足以满足当前判断的可靠证据；不为形式完整追加查询。 |
| 责任目标已明确未达到，且按所属规则不再继续 | 流程保存 `FAILED` 和具体原因。例如，产物结果已经明确不符合要求，不能把它改解释为暂时未知继续检查。 |
| 仍需新的观察才能确定结果，但次数已经耗尽且不能继续 | 流程保存 `UNCONFIRMED` 和具体原因，保留已有观察与未知部分，不更换用途或身份取得次数。 |
| 责任尚未结束，仍需继续且具备相应资格和次数 | 已有尝试时保持 `ACTIVE`；尚未开始首次尝试时保持 `PENDING`。按原业务时机、重试间隔及调用收场条件继续，等待本身不消耗次数。 |

结束流程时，`retry_wait_required` 共同清零。尝试的调用结果、流程的整体结果、设备活动的实际状态和动作结果分别保存；其中一项成功不自动把其他项改为成功。不能先把查询流程结束，再为了继续相同工作新建流程。

### 启动核实与停止核实

同一录像的启动命令和停止命令分别可能需要状态查询。启动核实负责判断本次启动的实际结果，停止核实负责判断本次停止的实际结果，两者分别保存查询流程和累计次数。启动阶段消耗的查询次数不减少停止核实额度；发送启动或停止命令的次数与相应查询次数也分别累计。

| 所属操作责任与查询目的 | 流程与预算规则 |
| --- | --- |
| 核实同一 `START` 流程的启动结果 | 使用该启动责任的查询流程；后续启动尝试仍需查询时沿用累计次数，不按启动尝试逐次建立新查询预算 |
| 核实同一 `STOP` 流程的停止结果 | 使用该停止责任的查询流程，与启动核实分别计数；后续停止尝试仍需查询时沿用累计次数 |
| 正常停止转入取消停止，或重启后继续原停止责任 | 沿用原停止核实流程和次数；入口变化不产生新的停止核实责任 |
| 启动或停止的核实跨会话继续 | 恢复对应责任及历史次数，不以重启次数或当前调用位置划分新责任 |
| 直接响应已满足所属操作的结果确认要求，无需额外状态查询 | 使用可靠响应继续处理，不为补齐流程形式执行查询或消耗查询次数 |

查询观察按所属操作的完成条件解释。可靠确认本次录像已经启动，可以完成启动核实；同一条“仍在录制”的观察用于停止核实时，则表示尚未确认停止。查询成功不自动结束录像动作，也不改变取消、过期及动作终态的既定规则。核实责任终态保持，后续查询取得的新观察不能重开原流程。

## 产物结果核实的责任与轮次

分段结果建立固定集合后，同一 RESULTS run 不再取得新实际尝试。命令预检与原写连接的独立意图守卫共同核对已保存集合，原意图键重放仍恢复原票据；不能通过新键刷新固定来源。集合身份、原H0和当前扫描的区别见[分段集合](segments.md)。

`CHECK_CAPTURE_RESULTS` 属于原拍摄动作对本次活动结果的核实责任，使用 `results/<activity_id>`，`action_id` 必须等于活动所属动作。该流程检查驱动契约要求的文件归属、结果集合及必要的写入完成事实，与设备状态查询、后续取回和拷贝校验分别累计次数。

一轮核实是对本次拍摄结果进行的一次检查，按一个尝试保存。例如，100 个文件分五批读取仍是一轮；文件数和批次数不增加尝试次数。集合、文件及已取得证据可以分批保存，但不能用某一批读取成功代替整轮检查完成。

| 检查事实或运行情况 | 结果与次数处理 |
| --- | --- |
| 正在读取同一轮的后续批次 | 继续原尝试，不增加次数；保留尚未完成的检查责任 |
| 已可靠确认全部适用结果要求满足 | 保存实际依据并结束核实，按原拍摄契约继续产物登记及动作处理 |
| 已可靠确认结果明确不满足要求 | 保存明确不满足的结果，按所属失败及文件保留规则处理，不将其当成暂时未知反复核实 |
| 文件暂未齐备、写入完成尚不能确认，或本轮查询失败 | 保存本轮实际结果及已知事实；仍有资格与额度时，后续重新检查作为新轮次，增加一次尝试 |
| 中断后已有可靠完整结果 | 使用原结果继续，不因重启重新开始已完成核实 |
| 中断后缺少完整结果，需要重新从设备取得观察 | 按尝试恢复规则保存原未完成调用的实际已知结果，保留已用次数；需要重新开始检查时登记新轮次，不因部分批次已保存而把整轮判为完成 |
| 取消、已有终态或预算耗尽使普通核实不再允许继续 | 按所属拍摄及收场规则结束普通核实，保留真实文件与未知事实，不刷新额度或补造完整集合 |

可靠读取数据库中已保存的检查事实不构成新的设备检查轮次。整轮结果、设备活动的集合核实状态及适用业务结果按原事务规则共同保存；提交未知先核实原事务，不为补写结果重新执行检查。历史恢复保留当时的次数、配置依据与结果，不访问设备重新判定。

分页核实中断后，程序分别读取原尝试结束结果和原可靠页。页中的实际返回与发生时刻保持原事实；它不要求与恢复时保存的整轮未知结果相同。原尝试仍为 RUNNING 且没有当前调用拥有者时，程序先核实原意图位于恢复历史边界内、旧本地执行已收场，以及原驱动声明该操作适用恢复。恢复按下表处理。

| 原可靠页与调用事实 | 恢复行为 |
| --- | --- |
| 当前拥有者仍在执行原页调用，或旧调用缺少适用恢复资格 | 当前拥有者继续等待实际返回；旧调用缺少资格时保留 RUNNING 和诊断，均不开始新设备检查 |
| 末页没有后续游标，或末页保存了实际调用错误 | 复用末页的完整实际结果及原时刻，继续原消费者保存；不把错误或扫描结束解释为集合已确定 |
| 没有可靠页，或末页有后续游标且没有调用错误，原调用缺少完整返回 | 按普通前台恢复规则保存原尝试为 UNKNOWN；已有各页仍保存自己的实际结果及原时刻，扫描和集合保持未确定 |
| 部分页包含实际设备完成观察 | 原设备结束与原尝试结束共同保存，设备结束采用原观察时刻；集合是否确定另行判定 |
| 部分页发现的文件尚未保存独立归属、完成或配对事实 | 先消费原可靠页，保存有充分依据的文件事实；预览原片尚未读到时，保留原预览输入和未确定配对，不补造关联 |
| 新轮首批尚未可靠返回，前轮已有可靠文件页 | 前轮页只用于恢复原文件子责任，保留当前尝试的原结果和时刻；不以跨轮文件补造当前轮的完整扫描或集合保证 |
| 原尝试结束已提交，原页文件子责任尚未保存 | 从原可靠页继续保存有充分依据的文件事实，可靠完成这些保存后才允许新设备检查；不重新执行已结束的原调用 |
| 原尝试已收场且需要新检查 | 沿同一结果核实流程的累计次数、重试等待及普通资格开始新轮次，新游标从本轮起点开始 |

原可靠末页和完成观察由原驱动的证据登记解释，当前设备绑定缺失或不匹配不改变原结果。绑定失败先保存原调用及适用实际结束，再按所属业务规则失败并保留合格文件。原保存申请回执未知时保持原 key、完整输入、时刻与页引用，先核实该申请。

## 查询和结果核实怎样保存配置与历史

创建查询或结果核实流程时，程序保存该责任实际采用的次数上限、间隔和调用时限。执行前检查从发起动作所绑定的设备取得配置；其余查询和结果核实从目标活动原动作所绑定的设备取得配置。后续收场的触发者不改变目标设备的配置来源。

| 保存字段 | `QUERY_ACTIVITY` 的配置来源 | `CHECK_CAPTURE_RESULTS` 的配置来源 |
| --- | --- | --- |
| `max_attempts_used` | `devices.<id>.query.max_attempts` | `devices.<id>.result_check.max_attempts` |
| `retry_interval_s_json` | `devices.<id>.query.retry_interval_s` | `devices.<id>.result_check.retry_interval_s` |
| `timeout_s_json` | `devices.<id>.query.timeout_s` | `devices.<id>.result_check.call_timeout_s`，表示该轮每次适用设备查询的时限 |

两类操作都适用这三项配置，流程和新建尝试均须保存实际值。次数为正整数，调用时限为有限正秒数，间隔为有限非负秒数；合法性和默认值按[本地配置](../../architecture/configuration.md#状态查询与产物核实的配置)校验。数据库中的 JSON 数字文本用于精确保留这些值，SQL 的基本数字类型检查不能代替配置数值范围检查。

开始一次新查询或新一轮结果核实时，写事务先确认原流程未结束、相关调用已完成适用收场、执行资格仍成立，并且 `attempts_used` 小于本次上限。随后共同保存新的尝试意图、连续的尝试编号、增加后的累计次数及采用配置；提交成功后才调用设备。已有预建流程时更新原记录，没有预建流程时可以与首次尝试一起建立。

后续运行实际采用新配置时，只更新仍未结束的流程，并保存变更历史。原累计次数保持；降低上限后可以出现已用次数大于新上限，此时不能新增尝试。已经结束的尝试保留当时配置；一次设备查询或结果核实轮次中断后若需重新检查，按原恢复规则开始新尝试，不能通过修改旧尝试的参数退还次数。

事件保存分别使用已有的操作流程、尝试意图、尝试结果、重试等待、设备观察和结果集合事件。一次结果同时影响流程、尝试、活动或动作时，按[事务规则](transactions.md)共同提交。查询用途和配置属于内部事实，按原流程的历史归属恢复；报告仍按实际公开字段是否改变判断，不向用户增加查询次数或配置字段。

## 尝试字段与结果

`operation_attempts.run_id` 唯一归属一个流程；`attempt_no` 在该流程内从 1 连续递增，`(run_id, attempt_no)` 唯一。读取尝试必须保存意图登记时的 `copy_round`；其他操作该列为空。跨段及按契约恢复同一未结束读取尝试保持原身份；摘要不一致后的合法重拷由拷贝轮次历史关联，不改写原意图的起始轮次。

读取尝试为 `RUNNING` 时，可以已有[当前拷贝轮次的完整读取结束依据](file-fields.md#当前轮次的完整读取结束依据)，而尚待本地校验或有限重拷。该事实不占用本尝试的最终 `result_event_id`，也不新增尝试或重试等待；设备互斥须结合当前轮次、实际收场及后续是否仍需设备调用判断，不能只凭 `RUNNING` 推断相机仍被读取。最终结果保存时核对实际采用的原票据及适用轮次，不把旧轮结束引用用于证明后续重拷已经结束。

普通尝试的 `intent_event_id` 必填，指向派发前意图及额度提交的事件；应急尝试该列为空，按[最终补记](#应急停止的最终补记)保存。`result_event_id` 在没有可靠结束结果时为空，有结果后指向保存该结束结果的事件，结束后保持。每条尝试保存实际执行时使用的 `max_attempts_used`、`timeout_s_json`、`retry_interval_s_json`。恢复原读取尝试时后续调用可以采用新配置，应用层将新依据写入该尝试并保留变更历史，不能改动已结束尝试的依据。

`CHECK_CAPTURE_RESULTS` 的 `result_first_page_event_id`、`result_last_page_event_id` 指向本次尝试已可靠保存的首末结果页。没有页时两列共同为空；首次页共同建立范围，后续页保持首引用并推进末引用。范围中每页保留完整实际结果，尝试仍可为 `RUNNING`；页读取、原游标和基准比较位置遵守[结果页的分批记录](history-formats.md#结果页的分批记录)。其他操作两列为空，不将多次实际页调用合成为一次本地或远端退出。

| `status` | 结果与错误 | `effect_state` 的含义 |
| --- | --- | --- |
| `RUNNING` | `result_event_id`、`result_json`、`error_json` 均为空，可能只有已保存意图 | `UNKNOWN`，不能证明命令已经发出或没有发出 |
| `SUCCEEDED` | 结果事件和 `result_json` 必填，错误为空 | 按驱动保证使用 `UNKNOWN`、`NO_EFFECT` 或 `CONFIRMED`；仅保证命令发送成功可以仍为 `UNKNOWN`，成功响应不自动证明整个任务完成 |
| `FAILED` | `result_event_id`、`result_json`、`error_json` 必填；结果包含结束依据和实际观察 | 可以是 `UNKNOWN`、`NO_EFFECT` 或 `CONFIRMED`，通信失败不等于没有效果 |
| `UNKNOWN` | `result_event_id`、`result_json`、`error_json` 必填；结果包含结束依据及能够确认的部分 | 可以是 `UNKNOWN`、`NO_EFFECT` 或 `CONFIRMED`，按操作保证分别表达；尝试结果未知不抹去已可靠确认的部分，也不推断完整操作成功 |

`result_json` 使用[统一外层结构](#结束结果的统一结构)和操作专属证据。开放原始错误使用公共 `error` 对象的结构原样保留；结构复用不使该尝试成为公开报告内容。尝试状态供内部执行和历史恢复使用。只登记意图后发生中断时不重新发出可能重复执行的启动命令；先按驱动契约核实。

## 应急停止的最终补记

录像 A 的第一次应急停止超时，第二次确认停止时，camctl 先在内存中保留两次尝试及采用的参数。A 的应急处理结束、相关调用完成适用收场后，再用一个事务共同创建一条 `operation_runs`、两条 `operation_attempts` 及对应历史，并同步可靠的设备活动变化。保存动作不派发设备命令，不等待其他录像或整个会话结束。

执行资格及有限预算由[会话应急停止](../../architecture/session-errors.md#正在录像时的应急停止)定义。数据库使用现有两张操作表，按以下规则保存最终事实：

| 记录 | 身份、字段与不变量 |
| --- | --- |
| 应急流程 | `kind = 9`，责任键为 `emergency/<session_key>/<activity_id>`；`action_id` 是目标活动所属动作，`delivery_id`、`copy_id`、`cleanup_item_id` 为空。同一会话对同一活动至多一条，创建时已经结束；不保存 `PENDING` 或 `ACTIVE`，不重新激活 |
| 累计次数及配置 | `attempts_used` 是实际已开始的应急尝试数，等于本次共同保存的尝试行数；编号从 1 连续递增。上限在本会话内固定，已知时为正整数且次数不超过上限；未知上限仅在零尝试时允许为空。超时及间隔保存实际可靠取得的配置，未知时为空，已有尝试不能缺少执行所需配置 |
| 应急尝试 | `run_id` 引用本次流程，`copy_round` 为空；保存实际采用的配置、调用状态、错误、已知效果及结束依据，不保存 `RUNNING`。`intent_event_id` 为空，`result_event_id` 指向本次补记事件；补记事件不能冒充派发前的意图提交 |
| 尝试结果 | 沿用[结果结构](#结束结果的统一结构)及驱动的收场保证。调用超时与停止效果分别表达，不能用本地进程退出证明录像停止；没有实际尝试时不创建尝试行 |
| 流程结束信息 | `retry_wait_required = 0`；结束原因、次数、配置及尝试结果一次保存后保持不变。后续会话取得的新观察保存为新事实，不修改旧应急结果 |

记录方式由所属流程的 `kind` 确定，不另设一套可独立变化的登记方式。普通流程的尝试仍必须具有派发前提交的 `intent_event_id`；普通事件不得创建应急尝试，应急补记不得创建其他种类的流程或尝试。

先按执行契约判断是否需要应急处理：已有可靠停止确认时不重复发令，也不为形式完整而创建应急尝试。对实际进入应急处理或因执行条件不足而未能尝试的可靠目标，最终组合如下：

| 最终事实 | 流程状态与错误 | 次数与依据 |
| --- | --- | --- |
| 取得驱动认可的停止确认 | `SUCCEEDED`，流程错误为空；先前失败尝试仍保留各自错误 | 保存实际次数与已知上限，必须具有可靠停止证据；确认发生在首次发令前时可以为零次，不创建虚假尝试 |
| 已开始尝试，有限处理结束后仍未确认停止 | `UNCONFIRMED`，保存 `emergency_stop_unconfirmed` | 次数大于 0，上限及所需配置必须已知，保留各次实际结果，不推断设备已经停止 |
| 尚未开始尝试，执行条件已经不成立或未知 | `FAILED`，保存 `emergency_not_attempted` | 次数为 0；上限已知就保存，未知则为空。对应 `not_attempted`，不凭当前配置补填历史 |

这两个框架错误的阶段及详情由[公共错误登记](../../../protocol/errors/workflow-codes.json)定义。阶段为 `emergency`，详情的 `activity_id` 指向本次实际目标活动，`reason` 保存生产者提供的非空实际诊断字符串。保存端不根据当前配置、尝试次数或最后一次驱动错误补造原因；各次调用的原错误与观察独立保留。成功记录不携带失败原因。流程及活动表达同一错误时使用相同完整值，即使活动错误没有变化而省略活动行，事务仍须核验流程错误与最终结果及活动身份一致。

应急处理结束只表示本会话不会再为该目标新增应急尝试。它不表示录像已经停止，也不表示录像动作成功。可靠停止事实与补记共同保存时，按设备活动的证据和占用规则处理；既有动作终态、普通停止流程和普通预算保持原事实。

### 应急记录的结构约束与事务校验

一次应急补记可能包含零条尝试。例如，camctl 已确认需要处理的录像，但未能可靠取得停止配置，因此没有发令；也可能在准备首次发令时取得了可靠停止确认。这两种情况都没有尝试记录，但流程结果分别是 `FAILED` 和 `SUCCEEDED`，不能只根据次数为零决定成败。

| 所属操作及实际次数 | 流程上限与配置 | 尝试的意图及结果引用 |
| --- | --- | --- |
| 普通操作，任意次数 | `max_attempts_used` 必须为正整数；超时和间隔按各操作的适用规则保存。 | 每条尝试的 `intent_event_id` 必填，引用派发前保存意图的事件；结果引用按尝试是否结束填写。 |
| 应急停止，零次尝试 | 上限、超时和间隔分别保存可靠取得的值，未取得的值为空；有上限时必须为正整数。 | 不创建尝试行。成功结果必须具有首次发令前取得的可靠停止证据。 |
| 应急停止，已有尝试 | 上限、超时和间隔必须完整；次数不得超过本会话固定上限。 | 每条尝试的 `intent_event_id` 必须为空，`result_event_id` 必须指向共同补记事件；尝试已结束且保存完整结果，`copy_round` 为空。 |

SQL 检查应急责任键与 `session_key`、`activity_id` 一致，并通过全库唯一约束限制同一会话对同一活动至多一条记录。它还检查上限的空值范围、已用次数、最终状态、错误及配置的行内组合。应急流程只允许前述结果分类中的 `SUCCEEDED`、`FAILED`、`UNCONFIRMED`，不保存进行中、取消或过期状态。

尝试所属的操作种类保存在父流程中，因此 `operation_attempts.intent_event_id` 在 SQL 中允许为空，但空值只接受已结束、配置和结果齐全、没有拷贝轮次的记录。保存事件的程序必须在同一写事务中沿 `run_id` 检查父流程：普通尝试必须有意图引用，应急尝试必须没有意图引用。不能仅凭空值或尝试已经结束就认定它属于应急停止，也不另加一份可能与父流程矛盾的操作种类。

`EMERGENCY_RECORDED.FINAL` 共同创建一个目标的最终流程及全部实际尝试。事务校验核对原动作与录像活动的归属、规范责任键、尝试从 1 开始连续编号、尝试行数与 `attempts_used` 一致，以及每条尝试采用的配置与本会话固定配置一致。全部结果引用本次事件；普通事件不能追加应急尝试或改写已补记结果。配置数值是否合法、结果证据是否符合原驱动保证，也由事务校验负责，SQL 的外层 JSON 检查不能代替这些判断。

可靠停止证据优先保存在实际尝试的 `result_json.observations` 中。首次发令前已经确认停止，或依据来自尝试结果之外的可靠观察时，在补记事件的 `evidence.observation` 中保存该依据，并核对它确实指向目标活动。流程成功与适用的活动结束事实共同保存；已有可靠设备事实不重复改写。只保存调用成功、进程退出或流程 `SUCCEEDED`，都不能代替停止证据。

### 补记失败与后续恢复

补记沿用稳定的 `operation_key` 及事务核实规则；责任键同时防止同一会话对同一目标建立第二条流程。保存接口不依赖重新执行停止命令来取得相同输入。

| 数据库及进程情况 | 保存与恢复处理 |
| --- | --- |
| 补记可靠提交 | 流程、全部尝试、适用设备事实和历史整体可见；保存诊断为 `recorded` |
| 已知不能可靠写入，未发起补记，或已确认补记回滚 | 没有本次补记事实，保存诊断为 `not_recorded`；不以等待数据库恢复延长有限退出，不重新发送停止命令来补记录 |
| 提交结果未知 | 保存诊断为 `unknown`；数据库可可靠访问时，先核实同一事务和责任身份。原事务可靠存在则复用；可靠不存在且不可能迟到提交时，仅在原完整内存事实仍可用且退出条件允许时重试同一补记，不重做设备操作 |
| 补记前或补记期间进程中断 | 后续 camctl 先恢复对状态库的可靠访问，再读取实际已提交历史。存在完整补记则使用；不存在时不创建旧会话应急流程，也不从缺少记录推断没有发令 |
| 后续取得设备的新观察 | 按新观察更新设备活动及适用业务事实，不补造旧尝试次数、超时、停止结果或当时配置；已保存的旧应急记录保持不变 |

stderr、日志及最终错误消息只用于诊断。主程序不据此接手设备控制或数据库恢复；后续 camctl 也不通过解析这些消息补写丢失的应急事实。没有可靠设备证据时保留未知状态，不能将未保存解释为停止失败或停止成功。

历史归属是原设备活动的动作。补记前的完整历史边界不包含本次应急流程；补记后的边界包含完整最终记录，不出现只有流程或部分尝试的中间状态。历史查询只依赖该边界内已提交的记录，不额外判断所属进程是否退出。恢复和回放不执行补发命令，也不把后来观察写入旧边界。

### 应急补记怎样影响状态报告

录像已经可靠停止，但补记尚未提交时，状态报告仍使用其冻结边界 H 内的已保存事实。例如，原动作已经失败、H 时尚未确认设备停止，报告继续按[设备执行情况](../../architecture/report-format.md#动作结束后设备是否仍在执行)保留相应提示。错误消息中的 `stopped` 及进程内的停止观察不能直接加入这份报告。

补记提交后，如果可靠设备事实使公开字段发生变化，事务同时记录原动作的报告变化。之后冻结的新报告可以清除已经不适用的设备执行提示，原动作的失败、取消或过期结果保持。只增加内部应急流程和尝试、没有改变任何公开字段时，不产生新的报告变化。原动作尚未结束时，是否提供设备执行提示仍按公共字段的适用条件判断。

应急流程、次数、配置和逐次调用结果属于内部历史；会话错误消息中的 `emergency_stops` 属于退出诊断。状态报告不增加应急明细，也不依赖进程退出后才能生成。同一 H 的报告在补记、其他录像收场和后续新观察发生后，重建结果保持不变。

## Action6 分段普通录像的正常停止事实

Action6 分段普通录像的原 STOP 实际成功时，框架在该尝试的 `ATTEMPT_RESULT.evidence.normal_recording_stop` 保存正常到时的来源依据。该成员属于主机控制流程的事实，不加入驱动观察数组，不改变原 STOP 责任、意图、次数或结果状态。它只用于 `camera_record` 且冻结策略为 `action6_video_segments_v1` 的动作；其他任务继续自己的完成合同。

该对象恰好包含以下两个成员。字段结构仅在本节定义，历史格式及消费者通过引用使用。

| 成员 | 类型与含义 |
| --- | --- |
| `start_result_event_id` | 正整数，引用同一动作、同一活动的原 START 可靠成功结果事件。原调用错误为空，确认符合动作冻结的 START 返回语义，并提供本会话实际持有的正常计时锚点；查询恢复后建立的确认不能代替原调用确认。 |
| `elapsed_before_stop_ns` | 可持久表示的非负整数纳秒，表示从上述确认响应的原单调钟锚点到派发本次 STOP 前的实际经过时间。布尔值、小数及未知值均不合法。 |

正常拥有者在派发 STOP 前固定这两项输入。此时动作尚未取消，拥有者仍持有同一会话的原确认锚点，按原冻结 `startup_margin_ms = S` 与 `target_duration_ms = D` 满足 `elapsed_before_stop_ns >= (S + D) × 1_000_000`；`S`、`D` 只从原执行定义读取，不在该对象另存一份。拥有者正按正常到时路径停止本次录像，没有已经确认的采集异常、原 STOP 错误或结果未知后的恢复责任。调度迟到不改变这个来源。跨会话墙钟差、STOP 返回后的时长以及新进程的单调钟不能用来生成该输入。

原调用取得真实成功、错误为空、停止效果已确认且调用实际收场后，才能随原完整结果保存该成员；效果已确认但调用同时报错时保留原错误，不形成正常停止事实。原 STOP 此前已有实际错误或未知结果并进入恢复时，后续成功仍属于异常处理。取消、恢复或保守停止不形成正常来源。正常上下文形成后才生效的业务取消不抹去原实际成功及其来源，所属动作继续按取消规则处理。

结果事务及独立守卫核对冻结动作类型与策略、同动作活动的原 STOP 流程和票据、该尝试的 `intent_event_id`、原完整成功结果及实际停止观察，再核对 START 结果引用、原调用成功且错误为空、原返回语义要求及冻结 `S/D` 的精确比较。START 结果必须早于本次 STOP 意图并与原确认一致；本成员与本次结果事件只能属于该原尝试。真实同会话计时由拥有者在正常派发入口取得，持久化层校验其结构、关联和目标要求，不从历史墙钟重新推算。正常停止事实与原 STOP 结果及适用活动结束共同提交，不另建全局状态或独立停止责任。

原完整结果申请一旦形成，保存回滚或回执未知时保持原票据、来源对象、结果、事实时刻及操作键。原键核实检查完整事务和本成员的有无、引用及精确整数，不能按重送时的会话、配置或取消状态重新生成。普通消费通过原活动所属 STOP 的尝试与 `result_event_id` 定点读取这项事实，核对直接身份和可靠结果，不重演已保存的单调钟观察；按原键核实仍执行该保存接口的完整事务检查。

| 中断或恢复位置 | 处理 |
| --- | --- |
| STOP 意图已保存，原结果尚在执行或保存未决 | 沿原调用及票据收场，已有完整结果申请先按原键核实；意图本身不提供正常完成资格。 |
| 完整正常 STOP 结果已可靠保存，仅文件核实或来源发布未完成 | 使用原结果的来源事实继续正常处理；不重复 STOP，不重新建立计时锚点。 |
| 新进程已按既定边界接手，但原 STOP 真实结果没有可靠保存 | 按原异常恢复规则保存未知与收场事实，后续采用异常内容检查；不重建派发前的正常来源。 |
| 原结果可靠保存但没有正常来源，或者已有明确采集／停止异常 | 保持原实际结果，按 Action6 异常分区继续；不因 STOP 成功而补写正常成员。 |
| 已有分段检查责任或覆盖决定 | 优先恢复原检查与决定；正常来源也不能撤销尚未完成的输入读取或检查。 |

正常停止来源不证明文件已经写完、媒体内容达到目标或来源可以立即发布。文件核实、原 READ 结果、适用检查及来源共同提交仍遵守各自依赖；依据缺失、读取失败和内容矛盾分别处理，不能从 `control_elapsed_ns`、`clock_status` 或 STOP 成功状态补造正常来源。

## 尝试结束结果的编码

### 结束结果的统一结构

一次删除调用超时后，本地调用已经收场，驱动仍不知道文件是否删除。该尝试保存 `FAILED` 和超时错误，`effect_state` 为 `UNKNOWN`，`result_json` 保存采用运行假设结束本次命令责任的依据。另一调用已经取得可靠删除成功证据，随后通信异常时，仍保存调用错误，同时在结果中保留成功观察并使用适用的 `CONFIRMED`；清理流程按可靠文件事实判断结果，不仅根据尝试是否失败决定重试。

尝试的 `result_json` 为以下对象，不重复保存所在行的状态、错误和效果分类。它是一次结束结果的组成部分，不独立推进收场状态；应急尝试按最终补记边界保存同一结构。

| 成员 | 类型及必填规则 | 含义 |
| --- | --- | --- |
| `format_version` | 必填整数，格式为 1 | 确定结果外层的解释规则，不代替历史事件版本 |
| `settlement` | 必填对象，包含 `basis` 和 `evidence` | 说明本次调用为何已经满足结束条件；不代表业务效果成功 |
| `settlement.basis` | 必填，取 `observed`、`assumed` 或 `not_dispatched` | 分别表示实际结束依据、适用运行假设、可靠确认未派发且不会执行 |
| `settlement.evidence` | 必填的类型化对象，至少包含 `type`、`version`、`data` | `type` 是适配器或恢复契约登记的证据类型，`version` 是该类型的正整数版本，`data` 是符合该版本结构的证据对象 |
| `observations` | 必填数组，每项为具有 `type`、`version`、`data` 的类型化对象 | 保存实际取得的操作事实及依据；没有可靠业务观察时使用空数组，不伪造“无效果”观察 |
| `call_info` | 可选对象，仅包含下表定义的已知调用信息；没有信息时省略 | 区分本地退出信息与远端退出结果，不由其中一项自动填出另一项 |
| `diagnostics` | 可选的独立内部诊断对象，结构见[受管工具的内部诊断](#受管工具的内部诊断)；不适用时省略 | 按所属调用契约保留有界原始双流，与结构化结果共同保存，不属于观察或收场证据 |

`type` 使用所属结果契约中固定的非空标识，`version` 必须为正整数；二者共同定位 `data` 的结构和保证范围。业务层按操作类型、原设备驱动或文件适配器检查适用性，不接受任意类型的证据。外层及类型化对象不接受未定义成员。具体证据类型只保存影响执行、恢复或结果解释的必要数据；目标身份、调用结果及配置依据已有保存位置时，沿原关联读取。固定的运行条件由驱动规格定义，实现和测试保证；证据正文保存本次调用需要保留的差异。类型登记及各操作适配不通过重新解释日志或当前驱动配置补齐旧证据。

观察数组保存本次结果需要的结构化事实，按适配器契约限制成员和数量；原始输出不作为无限增长的观察列表保存。文件流、逐字节内容和整份设备输出不进入该数组。驱动提取必要证据；调用契约要求随结果保留的有界原始双流进入独立 `diagnostics`，运行日志承载其余适用诊断。诊断原文和日志都不是恢复依据。

| `call_info` 成员 | 合法内容与限制 |
| --- | --- |
| `local_exit` | 对象，恰好包含整数 `exit_code` 或正整数 `signal` 之一；分别表示实际取得的本地正常退出码或终止信号。发出信号但未确认退出时不填写终止结果 |
| `remote_exit_code` | 仅在确实取得可信远端退出结果时填写整数；ADB shell 协议的值为 0～255。采用运行假设或只知道本地退出码时省略 |

本地 ADB 退出码不单独证明取得远端退出结果。尤其是 `255`，可以来自未收到远端退出消息的默认路径，也可以是远端退出值，不能直接复制成 `remote_exit_code`。具体取证能力由 ADB 适配器声明；没有该证据时仍可按既定运行假设收场，业务效果继续保持实际已知范围。公开实现依据见[ADB 实验记录](../../superpowers/notes/2026-09-28-adb-call-cleanup-experiments.md#公开实现依据与结论范围)。

本次实际使用[本地 ADB 终止宽限](../../architecture/configuration.md#本地-adb-客户端的终止宽限)时，所属 `settlement.evidence.data` 包含 `terminate_grace_s`，保存本次采用的精确 JSON 秒数。该成员只适用于声明了本地终止处理的证据类型；其他证据类型不因主机配置存在就填写它。恢复未取得原终止处理记录时，不用当前配置补造原值；实际终止信号及退出结果分别按已知事实保存。

### 受管工具的内部诊断

Hasselblad 单张 START 在返回实际结果时，使用独立 `diagnostics` 保存本次工具调用实际取得的 stdout 和 stderr。原尝试行已经确定动作、活动、运行和责任身份，诊断只按步骤关联，不再复制这些身份、命令参数、原错误、退出、效果或收场事实。实时返回尚未执行工具时保存空 `calls`；原结果无法取得或操作不适用诊断时省略整个成员，不能补造旧调用的空输出。

| 成员 | 类型及约束 |
| --- | --- |
| `diagnostics.version` | 必填整数，当前为 `1`。 |
| `diagnostics.call_limit` | 必填正整数，保存本次经所属调用登记核验的工具调用数量上限。 |
| `diagnostics.calls` | 必填数组，长度不超过 `call_limit`；按实际工具调用顺序保存，不包含工作目录准备等非工具步骤。 |
| `calls[].step_index` | 必填正整数，从 `1` 连续递增，与实际工具步骤逐项对应。 |
| `calls[].step_name` | 必填非空字符串，与所属结构化步骤的名称相同。 |
| `calls[].stdout`、`calls[].stderr` | 必填对象，各自恰含 `state` 和 `hex`。两条流分别表达，不能拼接。 |
| `state` | 取 `complete`、`unconfirmed` 或 `unavailable`，分别表示取得完整字节、已取得字节但完整性未确认、没有取得字节。 |
| `hex` | `unavailable` 时为 JSON `null`；其他状态为实际取得字节的小写连续十六进制字符串。空字符串表示已取得空字节，不表示缺失。 |

上述对象均不接受未定义成员或版本；整数不接受布尔值。每流上限沿用[受管工具输出限制](../file-runtime.md)，实现只从 `operations/process.py::OUTPUT_LIMIT_BYTES` 取得，不另存一份上限常量。解码在分配字节前核对字符数量、偶数长度和合法字符，解码后再核对字节长度；不接受空白或其他编码变体。

工具调用数量上限由同一份有限命令槽目录派生，通过现有调用契约登记核验。新结果校验要求 `call_limit` 与该登记相等，并核对诊断是实际执行步骤的合法前缀。历史解码及结果事件守卫核对原冻结上限、连续序号、结构和字节约束，不导入当前驱动，也不按当前参数重新规划原调用。诊断格式校验由同一生产入口提供，实时、保存和恢复不各写一份规则。

只有两流均已取得且原受管结果没有 `output_failure`，才把两流标为 `complete`。任一流未取得或存在输出错误时，缺失流标为 `unavailable`，已取得流标为 `unconfirmed`，保留实际字节或前缀。受管结果只有汇总错误时，不解析错误文案猜测逐流完整性。超限后保留的前缀不能被声明为完整输出；非零退出或超时与输出是否完整分别表达，原实际调用错误仍优先处理。

原始字节使用可逆编码，与结构化结果在同一原结果事务和历史事件中保存。原文编码或状态保存失败时，原拥有者保留完整结果、原字节、票据、事实时刻和操作键，沿既有保存及核实责任处理；不裁掉诊断另存结果，也不重复设备调用。回执未知先核实原完整申请；同键重送改变任一字节、空缺状态、完整性或步骤关联时拒绝。

诊断不用于重解析成功文本、补齐定位或判断是否进入 START。原结构化结果缺失时，即使诊断中存在成功文本，也不能补造成功观察。公共报告继续只消费适用业务字段和通用失败摘要，不输出诊断或整组内部步骤。

### 结果文件观察的分页格式

`result_files_listed/v1` 只包含原活动的规范十进制字符串 `activity_id` 和 `entries` 数组，不证明扫描结束或集合确定。`result_files_listed/v2` 恰好包含下表成员；一次调用最多返回 128 个条目。每批保持独立的实际 `CallOutcome`、错误、收场和调用信息，核实轮次沿同一个 RESULTS 尝试计数。

| 成员 | 含义与约束 |
| --- | --- |
| `activity_id` | 原活动的规范十进制字符串，与原 RESULTS 票据目标精确相同 |
| `entries` | 本次实际取得的文件数组；合法空页可以仍有后续页 |
| `cursor` | 本次请求的原游标；首批为 JSON `null` |
| `next_cursor` | 下一批游标；JSON `null` 明确表示本次扫描没有后续页，不证明集合已经确定 |
| `set_finalized` | JSON 布尔值，表示驱动按任务契约取得的集合确定保证；有后续页时必须为 `false` |
| `completion_evidence` | JSON `null` 或恰好包含 `type`、`version`、`data` 的实际设备完成观察；身份须关联原活动，含义由原驱动登记校验，等待假设不写入该成员 |

目录游标恰好包含 `device_id`、`driver_id`、`directories`、`directory_index`、`after_path`，保持原绑定和完整目录范围，目录索引及路径遵守目录分页端口。后续游标须推进，不能返回同一游标。文件条目保留稳定身份、定位、写完状态、大小、类别及适用元数据；`format_id` 是驱动声明的非空格式标识或 JSON `null`，不由 PHOTO 类别推定具体格式。

没有文件观察的错误保存真实空观察，不能解释为成功读取空目录。扫描中断或读取错误时，已经取得的文件和保证仍保留，但这次扫描不提供完整扫描依据；新轮次不拼接旧扫描形成完整集合。扫描完整、集合确定、设备完成、文件归属和单个文件写完分别核对。实时解释与原历史恢复使用同一格式登记和编解码器。

### 第一版 ADB 运行假设的结果记录

删除调用超时，本地 ADB 客户端已经退出并完成资源清理，但没有可靠删除结果时，尝试保存 `FAILED`、超时错误和 `UNKNOWN` 效果。`result_json.settlement.basis` 为 `assumed`，`settlement.evidence.type` 为 `adb_foreground_assumption`，`version` 为 `1`。该类型及版本对应[第一版普通前台命令运行假设](../../architecture/adb-execution.md#第一版普通前台命令的运行假设)，适用于本次运行中完成本地收场的调用；运行假设的适用条件由驱动规格、实现及测试保证。

该版本的 `data` 只包含本次实际采用的 `terminate_grace_s`；未使用终止宽限时为 `{}`。其必填条件及精确数值规则沿用上节。实际取得的本地退出结果保存于 `call_info.local_exit`，实际业务观察保存于 `observations`；没有可靠观察时为空数组。尚未完成本地收场时，仍按原规则保留 `RUNNING`，不能提前保存结束结果。

| 本次调用的实际情况 | 结果记录 |
| --- | --- |
| 客户端自行退出，适用运行假设且没有使用终止宽限 | 使用上述类型及版本，`data` 为 `{}`；调用结果和效果按实际证据保存 |
| 超时或取消后使用终止宽限，随后确认客户端退出并完成本地清理 | 使用上述类型及版本，`data` 保存实际采用的宽限；实际退出结果单独保存，不根据发出的信号推断终止结果 |
| 重启后缺少原调用的结束结果 | 按[恢复记录](#第一版-adb-未完成调用的恢复记录)保存新会话实际采用的依据，不冒充在原调用中完成了退出观察或取得了原配置值 |

例如，本次超时后实际使用 3 秒宽限，最终取得客户端被 `SIGKILL` 终止的结果，且没有可靠业务观察时，`result_json` 为：

```json
{
  "format_version": 1,
  "settlement": {
    "basis": "assumed",
    "evidence": {
      "type": "adb_foreground_assumption",
      "version": 1,
      "data": {"terminate_grace_s": 3}
    }
  },
  "observations": [],
  "call_info": {"local_exit": {"signal": 9}}
}
```

这条结果与所在行的失败状态、超时错误、未知效果及结果事件引用共同提交。后来查询确认文件已删除时，新查询保存取得的文件事实，原尝试保留当时的结果。驱动和恢复方式后续调整时，历史仍按所保存的类型及版本解释，未完成责任与累计次数保持原事实。

### 收场依据与结果组合

先确认调用及其本地资源已满足所属契约的收场条件，再按下表选择依据；尚未满足条件时不生成已结束的尝试结果。

| `settlement.basis` | 必需依据 | 不由此推出的业务事实 |
| --- | --- | --- |
| `observed` | 操作契约认可的实际结束证据；适配器必须说明证据覆盖的是本次命令、文件调用还是发令责任 | 发令责任结束不表示独立拍摄活动结束；命令结束不自动表示文件已删除 |
| `assumed` | 以证据类型及版本标明采用的运行假设，保存必要的当次数据；ADB 本次运行的结果与重启恢复分别使用本章规定的记录，本地收场是提交结束结果的前提 | 不填写虚构的远端退出响应、退出时间或业务成功观察 |
| `not_dispatched` | 可靠确认该尝试的调用未派发，且已阻止迟到执行；保留具体判定依据 | 已保存意图、进程退出或本地启动报错本身不覆盖全部派发可能性；不能仅据这些事实选用本分支 |

`assumed` 的类型及版本固定记录当时采用的规则；历史解释使用该版本的含义。驱动在适用范围内执行，并在本地实际完成收场后返回结果。已有可靠证据与假设矛盾时，不选择该分支，不依赖假设放行后续冲突操作。`not_dispatched` 只证明本次调用没有发出，不撤销同一流程此前尝试的效果或累计次数。

`status` 表达本次尝试的调用结果，`effect_state` 按操作契约表达已知效果，二者分别校验。明确取得调用失败原因时，`FAILED` 可以与效果未知或效果已确认并存；中断后无法取得原调用结果时，按恢复契约处理，不补造原超时或退出错误。`SUCCEEDED` 必须有该接口定义的成功依据，不能仅凭本地收场或采用运行假设填入成功。用户取消事实按所属动作保存，原尝试仍保留实际调用结果。

Hasselblad 复合 START 的 `effect_state` 描述本次照片采集，设置和镜头副作用由同一尝试的步骤事实另行表达，不能用采集无效果推断相机完全没有变化。完整分类及其与整次未派发的区别由[尝试结果、采集效果与步骤事实](../../superpowers/specs/2026-10-20-hasselblad-photo-parameters-design.md#尝试结果采集效果与步骤事实)定义；步骤保存在内部历史，不因此新增公共报告字段。

### 明确返回和可靠未派发的结果记录

删除调用返回后，驱动根据操作契约确认目标文件已经不存在，尝试保存成功和相应文件观察。拍摄发令返回只确认发送成功时，尝试保存发令成功，设备活动继续按自身契约判断。取得返回与业务成功分别解释；错误响应也可以证明命令已经结束，但不一定证明没有产生效果。

| 调用已经完成本地收场后取得的结果 | 尝试结果与效果 |
| --- | --- |
| 操作契约确认成功，并能证明业务效果 | 保存 `SUCCEEDED` 和相应已确认效果，保留实际观察 |
| 操作契约只确认命令发送成功 | 保存 `SUCCEEDED`；设备实际执行效果按已有证据表达，缺少依据时仍为 `UNKNOWN` |
| 明确失败，且可靠确认没有效果 | 保存 `FAILED`、实际错误和 `NO_EFFECT` |
| 明确失败，但没有足够证据判断效果 | 保存 `FAILED`、实际错误和 `UNKNOWN` 效果 |
| 已取得可靠业务效果，随后发生调用错误 | 同时保存 `FAILED`、实际错误及已确认效果，不丢弃先前观察 |
| 只有本地客户端退出，缺少可靠设备结果 | 按适用运行假设或恢复规则处理，不根据本地退出直接生成业务成功 |

操作契约认可的实际返回能够证明本次命令、文件调用或发令责任已经结束时，`settlement.basis = observed`，`settlement.evidence.type = operation_returned`，`version = 1`。业务事实放在 `observations`，实际取得的退出信息放在 `call_info`；`data` 为 `{}`，实际使用了上文规定的 ADB 终止宽限时，仅增加相应 `terminate_grace_s`。固定的返回含义由驱动或文件适配器按所属操作定义，实现与测试保证。调用只是返回部分进度、或实际执行工作尚未结束时，不生成这种结束结果。

可靠未派发指本次尝试的调用没有交给执行方，并且执行流程已经阻止后续派发。例如，意图与额度已提交，执行流程尚未启动 ADB 客户端就发现取消已经生效，随后停止这次派发。此时保存 `status = FAILED`、`effect_state = NO_EFFECT`，`error_json` 保存未能执行的实际原因；`settlement.basis = not_dispatched`，`settlement.evidence.type = dispatch_prevented`，`version = 1`，`data = {}`。没有可靠业务观察时 `observations` 为空，没有实际退出信息时省略 `call_info`。

| 派发与尝试登记的实际情况 | 处理 |
| --- | --- |
| 尝试尚未登记，执行资格已被取消或过期等规则结束 | 不创建尝试，不占用次数，按所属动作或流程保存结果 |
| 尝试已登记，可靠确认本次尝试没有执行，且后续派发已经被阻止 | 保存上述未派发结果；已提交次数保留，动作和流程仍分别表达取消、过期或其他结果 |
| 设备已经收到命令并明确拒绝 | 保存实际拒绝结果；有可靠无效果依据时使用 `NO_EFFECT`，不使用未派发类型 |
| 只有意图、没有结果，无法确认是否发出 | 按未完成尝试恢复，不将缺少结果解释为未派发 |
| 同一读取尝试此前已经执行部分工作，仅后续某次底层调用尚未发出 | 按原读取的继续或结束规则处理，不把整个尝试记为未派发 |

`NO_EFFECT` 只描述本次尝试，不撤销同一流程此前尝试可能产生的效果。保存未派发结果不退还次数，也不自动授予新的执行资格。上述两类结果沿用原尝试身份，与错误、效果及结果事件引用共同提交；提交情况未知时先核实原事务。

### 正常返回、恢复与历史保存

驱动或文件适配器提供实际结果，业务流程核对尝试身份、结果类型及所属责任后保存。正常完成和预期调用错误都保留已取得证据；不能只抛出超时错误而丢掉此前可靠观察。未知结果类型、结构错误或相互矛盾的证据进入所属诊断与错误处理，不将其改成空观察或成功结果继续执行。

| 取得或保存结果的阶段 | 处理 |
| --- | --- |
| 正常等待超时，本地调用仍在收场 | 尝试保持 `RUNNING`；超时及已知证据由原执行流程持有，继续跟踪收场 |
| 本次调用完成适用收场，结果尚未提交 | 共同提交状态、效果分类、错误、完整 `result_json` 和结果事件引用；提交前不提前推进依赖结果的操作 |
| 结果事务回滚或提交未知 | 回滚后沿原尝试保存同一实际结果；提交未知先核实原事务，不新建尝试或重新派发命令 |
| 重启后没有结束结果，旧本地执行责任已按启动边界结束 | 恢复流程保存本次实际使用的启动边界及适用假设依据；原调用结果仍按已知范围表达，不补填丢失的退出码、超时或观察时刻 |
| 未结束读取尝试符合恢复续传条件 | 沿原身份继续，不仅因为旧本地连接已结束就先保存尝试终态；整体读取尝试结束时再保存最终结果 |
| 已有可靠结束结果，后来查询取得新观察 | 原结果及证据保持；新查询按自己的责任保存文件或设备事实，不替换旧尝试的证据 |

恢复依据可以来自接入模块保证的旧执行进程收场边界，或主机重新上电后旧本地进程已停止的运行前提；其保证范围仍按[主机收场契约](../../host-demo/design.md#接入模块的本地进程收场责任)解释。适用 ADB 普通前台命令时，按下节保存恢复结果。

Hasselblad 下载属于本地前台读取。原读取无法继续且驱动明确支持本地读取恢复时，使用 `settlement.basis = assumed`、`settlement.evidence.type = local_read_recovery`、`version = 1`、`data = {}` 保存原尝试的未知结果。恢复同样要求旧本地执行已经停止，且原读取意图不晚于本次启动固定的历史边界；普通重新启动或发现下载目录均不能单独满足该条件。已保存的实际读取结果保持原证据，不能由恢复记录覆盖。

Hasselblad 单张实际进入驱动 `control` 时生成 `hasselblad_start_entered/v1` 观察，正文只含原 `activity_id`，随原调用结果保存。即使首条工具命令尚未执行，该观察也表示整次调用已进入；`NO_EFFECT` 仅描述照片采集效果。框架可靠封住整次未进入调用时，沿原票据使用 `start_call_prevented/v1` 空正文、`not_dispatched` 和空观察保存阻止结果；没有原意图时不创建尝试。缺少这两种独立入口依据时保持入口未知，通用 `dispatch_prevented`、工具步骤或诊断均不能补造未进入事实。

Hasselblad 单张的原 `control` 尝试只有在驱动声明本地控制恢复能力、提供 `local_control_recovery/v1` 空正文契约，且旧本地执行已按上述启动边界停止时，才可沿原票据保存 `UNKNOWN` 结果。原调用意图必须位于本次启动固定的历史边界以内；本会话仍在执行原调用时不能使用该恢复。恢复使用 `settlement.basis = assumed`、`settlement.evidence.type = local_control_recovery`、`version = 1`、`data = {}`，保留原尝试身份，不补填退出信息或入口观察。该依据只说明旧本地控制责任停止，不能证明整次调用未进入、相机效果、设备活动结束或占用释放，也不允许重放 START、设置、调焦或拍摄。缺少声明、契约、启动边界或固定历史边界时，原尝试继续等待核实。

历史事件包含 `result_json` 的完整前后值，快照包含其完整结构；尝试结果及适用业务派生事实共同提交。三种历史恢复路径按原类型及版本还原，不加载当前配置重算依据、不查询设备、不执行收场。内部证据不因保存而自动成为公共报告字段；报告继续按其既定范围生成。

### 第一版 ADB 未完成调用的恢复记录

camctl A 发出删除命令后中断，数据库只留下调用意图。接入模块完成旧本地执行进程的收场，再启动 camctl B。B 无法取得 A 的原调用结果时，原尝试以 `UNKNOWN` 结束，错误说明原调用结果未可靠保存；没有可靠效果证据时，`effect_state` 仍为 `UNKNOWN`。B 随后查询确认文件不存在，新查询保存自己的观察，清理项按既定规则完成，原删除尝试的未知结果保持不变。

这类普通前台调用使用 `settlement.basis = assumed`，`settlement.evidence.type = adb_foreground_recovery`，`version = 1`，`data = {}`。该类型及版本表示恢复依靠[主机收场契约](../../host-demo/design.md#接入模块的本地进程收场责任)保证旧本地执行工作已停止，再按[普通前台命令运行假设](../../architecture/adb-execution.md#第一版普通前台命令的运行假设)继续处理。接入模块收场后启动和主机重新上电均可满足这一保证；仅有程序重新启动这一事实不构成依据。

没有原调用的可靠退出信息时省略 `call_info`，没有可靠业务观察时使用空的 `observations`。该恢复类型的正文为空，本次恢复不填原调用的退出码、超时、终止宽限或发生时间；后续文件查询的结果保存在新查询及对应文件记录中。恢复沿用原尝试身份、累计次数和已有业务责任，不创建独立的进程收场记录。

下表在原事务提交情况已经查清后使用；取消和所属责任终态仍按既定规则优先处理。

| 已保存事实与恢复条件 | 处理 |
| --- | --- |
| 原尝试已有可靠结束结果 | 保留原结果，按所属流程继续，不生成恢复结果覆盖它 |
| 原读取尝试尚未结束，且符合原续传资格 | 沿原尝试继续读取，不仅因旧本地连接结束就保存尝试终态 |
| 原调用没有结束结果，旧本地执行工作已按主机契约停止，调用适用普通前台命令运行假设，且不属于上述续传分支 | 保存本节的未知调用结果和恢复依据；效果按已有可靠证据表达，后续核实另记 |
| 无法依靠主机契约确认旧本地执行工作已经停止 | 保留未完成责任和诊断，不保存本节结果或放行可能冲突的调用 |
| 原调用不适用普通前台命令运行假设 | 按该操作自身的恢复规则处理，不套用本节结果 |

适用异步拍摄发令时，本节只结束原发令责任；设备活动仍按自己的启动、停止和结果核实规则恢复。恢复结果、错误、效果分类及结果事件引用共同提交，提交结果未知先核实原事务。后续查询成功不改写此前冻结边界中的原尝试状态。

### 主机正式源未完成调用的恢复记录

主机正式源的 DELETE_FILE 与 CHECK_FILE_EXISTS 使用 `local_file_recovery/v1`，不使用 ADB 恢复类型，也不借用仅用于读取的 `local_read_recovery/v1`。其 `settlement.basis = assumed`、`settlement.evidence.data = {}`，外层沿用版本 1 的统一结构。该类型只确认旧本地主机文件执行责任已停止，不能证明原调用成功、未派发或文件缺席。

本地文件适配器负责登记这一类型对 DELETE 与 FILE_QUERY 的适用性和空正文校验，每次按原票据操作绑定恢复登记，不在同一集合中重复登记同一类型及版本；会话恢复层提供旧执行收场保证及启动固定历史上界，清理流程核对[旧 RUNNING 资格](cleanup-coordination.md#旧-running-尝试的恢复资格)，沿原尝试保存结果，写事务再次核对原目标、操作及意图范围。主机重新上电，或接入模块按[本地进程收场责任](../../host-demo/design.md#接入模块的本地进程收场责任)确认旧执行进程及线程均已停止，可以提供本地边界；普通工厂重建、连接重开或只观察到 CLI 主线程退出不能提供该保证。

| 原主机尝试的事实 | 恢复记录与后续处理 |
| --- | --- |
| 已有实际结果或当前会话结果拥有者 | 优先保存、核实并消费原实际结果；不生成恢复结果覆盖它。 |
| 只有旧意图，无实际返回可接回，且全部恢复资格成立 | 保存 `status = UNKNOWN`、原结果未可靠保存的实际诊断；没有可靠效果时 `effect_state = UNKNOWN`、`observations = []`，省略 `call_info`。不虚构原错误、原完成时刻、退出信息或超时。 |
| 本地边界、启动历史上界或原适用登记不足 | 保留 `RUNNING` 及具体诊断，阻止依赖本次收场的调用；不从文件路径不存在推断旧调用已经结束。 |
| 原尝试已按本节结束，业务仍需核实文件 | 原票据不补发；按所属取消或普通资格和剩余 QUERY 预算登记新查询，保存恢复时实际取得的观察。 |

恢复申请的 `occurred_at` 是本次实际形成恢复结论的时刻，不能冒充丢失的原调用时刻；同一恢复申请重送仍固定原 key、输入及该时刻。恢复结果、错误、效果及引用共同提交，原预算不退还。类型及版本的历史解释独立于当前设备配置；共享恢复边界和诊断类型可以由通用操作模块提供，不要求依赖拍摄模块。

## 设备活动字段

`device_activities.action_id` 唯一引用发起拍摄动作，原设备及驱动通过该动作取得；`task_key` 在首次派发前生成 UUID4 小写十六进制身份。驱动支持传入任务标识时使用该值；不支持时它只用于本地关联，不能据此声称设备支持幂等命令。`task_locator_json` 保存驱动实际返回或可以提前可靠确定的任务定位结构，尚无依据时为空。

| 字段 | 固定含义或空值规则 |
| --- | --- |
| `expected_identity_json`、`resource_key` | Hasselblad 活动在首次预留前固定预期 serial 和产品标识，以及由驱动和精确 serial 规范编码的资源键；两列同时为空或同时有值。其他驱动不使用该身份。固定身份表示操作目标，不是实际设备观察。 |
| `state_query_supported`、`stop_supported`、`safe_repeat_stop` | 第一次建立活动时实际使用的能力，均为 0/1；可安全重复停止必然要求支持停止 |
| `start_return_meaning` | `SENT`、`STARTED`、`COMPLETED`，声明成功返回保证的范围；与动作首次冻结的执行定义保持一致。`SENT` 只表达驱动契约规定的可靠发送成功返回，不表示设备已经开始采集。 |
| `completion_mode` | `DEVICE_EVIDENCE`、`TIME_AND_OUTPUTS`；与固定任务契约一致，不在查询失败后改为另一种 |
| `ownership_mode`、`output_scope_json` | `TASK_SCOPE` 表示任务独立输出范围，`BASELINE_COMPARISON` 表示拍摄前基准比较；对象内保存驱动定义的目录、前缀或任务归属范围，不能为空 |
| `baseline_state` | `NOT_REQUIRED`、`COLLECTING`、`FIXED`；独立范围只能为 `NOT_REQUIRED`，基准方式只能为 `COLLECTING` 或 `FIXED` |
| `baseline_first_event_id`、`baseline_last_event_id` | 当前基准分块的事件范围，同时为空或同时有值；已固定的空基准以 `FIXED` 和空范围表示 |
| `dispatch_state` | `NOT_DISPATCHED`、`MAY_HAVE_DISPATCHED`、`SUCCESS_RETURNED`、`REJECTED_WITHOUT_EFFECT`；`MAY_HAVE_DISPATCHED` 在提交启动意图时设置 |
| `activity_state` | `UNKNOWN`、`ACTIVE`、`ENDED`，仅描述实际设备活动，不复制动作状态 |
| `occupancy_state` | `HELD`、`RELEASED`；包括设备和所属输出范围的冲突限制，不表示持有跨进程锁 |
| `sent_at`、`started_at` | 分别保存实际可靠取得的 UTC 发送成功响应时刻与实际开始观察时刻；尚未取得时为空，不由余量或重启时间补齐。新 `SENT` 普通录像只凭命令返回保存 `sent_at`，`started_at` 仍为空，除非另有独立开始观察。 |
| `result_wait_margin_ms`、`extra_wait_ms_used`、`expected_check_at` | 分别保存执行定义冻结的自然结束余量、本次采用的部署额外等待和预计检查时间；前者与 `startup_margin_ms` 独立，后者可以在等待未完成时随新配置调整。不采用对应等待方式时为空。 |
| `wait_completed_event_id` | 原自然等待的完整预计时点已满足且真实完成事件时刻不早于该时点时，引用可靠保存的完成事件，否则为空；配置变化不清除已有完成事实 |
| `capture_json` | 单张拍摄与延时摄影的内部采集结果，结构见下文；进入采集处理前为空，录像为空。它保存采集阶段结果，不从动作终态或文件数量直接猜测 |
| `control_elapsed_ns` | 原始控制经过时间，以非负整数纳秒表示；需有本次连续单调钟或充分连续性的依据，不能证明时为空。它不是录制内容时长；按冻结启动余量派生的可保证录制时长下界不写入此列或媒体实测字段。 |
| `completion_basis` | 单张拍摄与延时摄影的采集判定：`UNDETERMINED`、`DEVICE_EVIDENCE`、`TIME_AND_OUTPUTS`、`KNOWN_FAILURE`；录像不适用，使用 SQL `NULL`，其停止和成功依据分别由活动、操作及录像处理记录保存 |
| `completion_evidence_json` | `completion_basis` 为 `DEVICE_EVIDENCE`、`TIME_AND_OUTPUTS` 或 `KNOWN_FAILURE` 时必填，为 `UNDETERMINED` 或不适用时为空；保存 `method`、`observation` 及适用的 `attempt_id`、`wait_completed_event_id`，不能填理论张数作为实际观察 |
| `result_set_state` | `UNEXAMINED`、`CHECKING`、`COMPLETE`、`UNCONFIRMED` |
| `result_check_json` | 结果集合为 `COMPLETE` 或 `UNCONFIRMED` 时必填，结构为 `contract`（驱动结果规则标识）、`outcome`（`SATISFIED` 表示满足，`NOT_SATISFIED` 表示明确不满足，`UNCONFIRMED` 表示无法确认）、`observation`（驱动结构化依据）；不放可增长的文件清单 |
| `output_set_finalized_event_id` | 本次文件范围已经确定时引用独立的 `RESULT_SET_CONFIRMED.OUTPUTS_FINALIZED` 事件；尚未保存该事实时为空，首次确定后保持原引用。它不表达采集目标是否满足 |
| `last_error_json` | 目前设备或结果核实的错误，无错误时为空；动作最终错误另行保存 |

新普通录像的 `SENT` 只确认设备接受了本次命令，不证明设备已开始录制。`sent_at` 保存驱动取得该可靠响应的实际时刻，`started_at` 保持未知，直到另有独立设备开始观察。启动余量从动作的冻结 `execution_spec_json` 读取，不复制为活动列；旧定义继续按自身原确认事实读取。完整规则见[相机启动余量设计](../../superpowers/specs/2026-10-18-camera-startup-margin-design.md)。

能力列保存实际执行依据，不把设备调用本身伪造成受理操作。延时摄影受理时已固定的相同能力必须精确一致；其他任务以驱动接入契约和部署兼容性要求解释。文件集合通过 `device_files.source_action_id` 分页读取，基准通过不可变事件分块读取。任务可能有多份原文件和预览，不能仅发现一个视频就固定集合。

普通录像和主机计时任务共同保存原 STOP 结果、实际结束和原始连续控制时长；普通录像遵守[录像恢复规则](../../architecture/camera-recovery.md)，主机计时延时遵守[停止与恢复规则](../../architecture/camera-capture.md#主机计时任务的停止与恢复)。实际结束事件使用原 STOP 返回时刻及[结果引用格式](history-formats.md)，与 STOP 尝试结果共同提交；文件归属或集合尚未确定时仍保持占用。适用启动余量时，控制耗时包含余量及停止调用的控制开销；按原冻结余量派生的录制时长下界只用于证明目标或判断修复门槛，不是实际媒体时长。跨运行缺少连续计时依据时，`control_elapsed_ns` 保持 SQL `NULL`，结束观察显式保存未知输入，不在原 STOP 已保存后补写时长。控制时长不能证明目标时，不以该字段提供控制完成依据；相应动作继续按其其他可靠完成依据或未确认分区处理。停止未确认则保留实际未知活动。原完成保证和原完整保存申请先于新执行资格恢复。

可靠 STOP 后声明的 `file_completion_wait_ms` 只从原停止事实安排文件等待。该等待与普通录像或原生延时使用的启动余量、以及自然结束的 `result_wait_margin_ms` 分开；不把 `startup_margin_ms` 叠加到 STOP 后文件等待。

`capture_json` 是内部 JSON 对象，只包含必填的 `status`、可选的实际 `captured_count`、`elapsed_s` 及适用的 `error`。`captured_count` 是 0～9007199254740991 的整数，`elapsed_s` 是有限非负秒数；只填驱动可靠提供的次数和时长，未知成员省略，不能用 `null` 代替。状态与错误按下表保存，错误使用公共 `error` 对象的结构。

| 已保存的采集事实 | `status` | `error` |
| --- | --- | --- |
| 采集处理尚未结束 | `running` | 省略 |
| 采集完成契约已满足 | `completed` | 省略 |
| 采集已明确失败 | `failed` | 必填，说明实际失败 |
| 生效取消后的采集处理已结束 | `canceled` | 省略；具体调用错误由所属尝试保存 |
| 有限核实结束后仍无法确认采集结果 | `unconfirmed` | 必填，说明无法确认的原因 |

产物登记、修复或交付尚未结束时，采集阶段可以已经完成；因此不能直接复制动作状态。结果检查的完整集合仍可能不满足任务要求，此时 `result_set_state = COMPLETE`、`result_check_json.outcome` 为 `NOT_SATISFIED`，采集失败；集合不能确认时，这两个字段分别采用各自枚举中的 `UNCONFIRMED`。报告按[拍摄结果字段](../../architecture/report-format.md#单张拍摄与延时摄影结果)表达动作状态及实际保留产物。

动作终态后，`device_execution` 从同一历史边界的原设备活动事实及适用完成依据生成，状态、观察错误与出现条件统一见[设备执行情况](../../architecture/report-format.md#动作结束后设备是否仍在执行)。后续可靠确认设备结束时清除该提示；原动作终态和原停止失败结果保持。设备活动已结束但输出范围限制尚未解除时，按已结束的设备事实生成报告。

后续收场已经发出停止命令后，即使触发者取消或过期，也继续按原预算保存收场成功或失败，不能把已有尝试的流程改成 `CANCELED` 或 `EXPIRED`。应急流程及全部实际尝试按[最终补记组合](#应急停止的最终补记)保存。流程、尝试及配置属于内部历史，是否产生报告变化由[字段依赖规则](report-changes.md#公开字段的依赖登记)确定。

## 等待、未知结果和占用恢复

取得原活动的可靠发送成功返回后，处理模块立即取得单调钟锚点和 UTC 时间，再保存 `sent_at` 与等待安排。对自然延时，启动余量从原动作执行定义中的 `startup_margin_ms` 读取，自然结束余量来自冻结的 `result_wait_margin_ms`，部署额外等待采用本次实际值；启动余量不并入另两项。预计检查时间的完整计算与新旧定义兼容由[相机启动余量设计](../../superpowers/specs/2026-10-18-camera-startup-margin-design.md)维护，本页不另列公式。正常会话使用单调钟等待；恢复时在约定的可靠墙钟及设备独立运行前提下计算剩余时间，转换成本次单调钟等待。已有完成凭据仅跳过其能够证明的阶段。

部署额外等待采用[本地配置](../../architecture/configuration.md#拍摄结果核实的额外等待)定义的 `devices.<id>.capture.extra_wait_ms`。未完成等待采用新值时，保持原 `sent_at` 及冻结的启动、自然结束余量，保存新的 `extra_wait_ms_used` 和 `expected_check_at`；不得从当前时刻重建发送锚点。已保存等待完成后沿用原完成事实，不因新配置重开等待。

等待完成和结果页保留各自的真实发生时刻。自然完成的结果页不得早于原等待完成，新的文件事实不得早于其引用页；不合格实际页仍保留原调用和输入，后续校时不改变其完成资格。当前真实时间不足以承载原来源时，延后新读取或新文件事实；原合格申请沿原键和原时刻恢复。启动余量与原来源规则见[相机启动余量设计](../../superpowers/specs/2026-10-18-camera-startup-margin-design.md)，会话时钟边界见[时钟与恢复](../../architecture/clock-recovery.md)。

| 恢复时的事实 | 持久化处理与执行边界 |
| --- | --- |
| 意图已保存，可靠确认没有实际派发 | 保存未派发依据，按原额度和窗口决定是否允许继续；已占用的尝试不退还 |
| 可能派发，驱动能核实原任务 | 沿原 `task_key`、驱动定位或基准核实，不重新创建任务 |
| 可能派发，既无可靠发送时间，也无法核实原任务 | 原动作保存结果无法确认并失败；设备活动与占用保持未知，不补造时间或重复启动 |
| 有可靠发送时间，采用无状态查询的有限自主任务 | 按原等待恢复及结果检查规则推进，不创建不存在的状态查询流程 |
| 取得设备结束证据，或满足声明的时间与全部产物结束条件 | 保存适用依据，按[释放条件](#设备活动占用的释放条件)检查剩余输出范围限制；条件全部满足后释放，动作仍按自身完成要求结束 |
| 动作已经失败，但活动仍可能存在 | 保留独立占用记录，结束原普通处理；其他设备继续。适用驱动按独立恢复契约处理后续工作，不支持恢复或有限恢复仍未解决时保存对应失败，不让会话无限等待 |

无查询、无可靠锚点且无可恢复完成证据的任务，其结果不能由框架补推。受支持的相机按[无人值守的软件重启恢复](../../architecture/camera-recovery.md#无人值守的软件重启恢复)或 [Hasselblad 可用性恢复](../hasselblad-availability-recovery.md)建立独立、有界的责任，分别使用所属契约的依据，不覆盖原动作或控制结果。支持安全停止的历史录像仍使用后续动作收场规则。没有适用恢复或合格释放依据时，继续保持原限制。

释放占用按下节区分设备活动事实、采集判定与剩余冲突限制。取消要求、协程结束或动作终态本身均不构成放行证据。

### 有限设备任务的取消后自然收场

原执行定义声明 `cancel_completion_policy=finite_device_end` 时，已经生效的取消、原活动以及第一次实际 STOP 的 `FAILED` 流程共同表达必要收场责任。STOP 的实际失败或未知结果与流程失败在同一事务保存，清除重试等待，不再使用剩余额度发出 STOP。目标动作在收场期间保持执行中，因此既有会话工作量查询继续发现它；该责任不新增数据库列，也不重开失败的 STOP。

有同一活动的可靠 SENT 返回及原 `sent_at` 时，处理模块复用原目标、执行定义冻结的 `startup_margin_ms` 与 `result_wait_margin_ms`，以及本次实际采用的部署额外等待，沿原发送锚点完成自然等待后再按原有限结果预算核实；完整等待时点只由[相机启动余量设计](../../superpowers/specs/2026-10-18-camera-startup-margin-design.md)定义。未完成等待采用新部署配置时，按原锚点和冻结余量保存新预计检查时间；已完成等待继续复用，不因配置变化重开。原必要文件规则满足、归属可靠且完整结果集合已经固定时，`DEVICE_OBSERVED.FINITE_CANCEL_END` 单独将活动置为 `ENDED`。事件的 `cancel_completion` 依据引用原 SENT、原失败 STOP、等待完成事件及原结果末页，并保存原策略和实际等待规则；原定义有 `startup_margin_ms` 时，依据保存同名原值，缺字段的旧定义不补入。原结果的完整输入仍由各引用事件保存。处理器的结束资格、保存命令和事件守卫共同通过原活动、原尝试及末页上界限定的读取端口，逐页复核当前完整扫描和原必要产物规则，不一次缓存完整目录。跨轮已知文件只决定保留，不能补足当前扫描的空集合、缺件或未知事实；当前文件未完成或集合未确定时继续原有限核实。该事件不设置采集完成判定，不写入 `capture.status=completed`，也不保存设备直接完成观察。占用随后沿统一释放条件处理。

当前扫描的必要文件必须明确完成，当前长度还须满足原规则，并与已保存的可靠完整长度相同。旧完整文件事实不能补足当前长度未知、零长度或长度矛盾。格式和配对角色明确、且原固定规则没有要求其数量的可选 LRF，可以只保留发现事实；它不阻止合格 OSV 的结束资格或完整集合范围确定，也不能补足必要原片。集合保存命令、复用与事件守卫均按同一有界扫描核对归属；必要预览缺配对仍按原归属规则拒绝。

缺少同一活动的可靠 SENT、原 `sent_at` 或其他必要历史依据时，不从当前时刻或执行定义补造发送锚点或等待完成事实；有限结果核实后仍缺少充分文件与集合依据时，目标动作按取消收场，活动和必要占用保持未知残留。取消项消费原 STOP 的失败结论，发起取消动作最终失败。结果为空、缺件、零长度或调用错误本身均不成为活动结束依据。未声明该策略的旧任务及普通录像继续使用各自原取消契约。

## 设备活动占用的释放条件

录像 A 原定录制十分钟，两分钟时取消并可靠停止。`activity_state` 保存 `ENDED`，动作按取消规则处理，不需要证明已经录够十分钟。如果 A 的文件依赖拍摄前后目录比较，而文件归属仍未确定，`occupancy_state` 继续保存 `HELD`，阻止会混淆该目录结果的新拍摄。归属限制解除后再保存 `RELEASED`；主机上的媒体检查或修复尚未完成，本身不要求继续占用相机。

`activity_state` 表达实际设备活动，`completion_basis` 表达适用采集阶段的判定，`occupancy_state` 表达设备及输出范围的冲突限制。三者分别保存，不从动作终态、停止流程是否存在或本地调用是否退出推导设备已经停止。录像的采集判定列不适用，不为释放占用填写虚构完成依据。

### 释放依据与状态组合

首先核对所需历史、身份及事务结果可靠，排除下表中的矛盾组合，再检查是否有释放依据。表中的“可以继续检查释放条件”尚不表示可以直接放行新动作。

| 发送、活动及采集判定的事实 | 合法组合与处理 |
| --- | --- |
| `dispatch_state` 为 `NOT_DISPATCHED` 或 `REJECTED_WITHOUT_EFFECT`，可靠确认本活动没有启动效果 | `activity_state` 不得为 `ACTIVE` 或 `ENDED`，采集判定不得为设备完成或时间与产物完成。可以继续检查准备及输出范围限制；单次尝试无效果不撤销此前尝试可能产生的活动 |
| 启动可能或已经生效，已取得原活动的可靠结束证据 | 保存 `activity_state = ENDED`，可以继续检查释放条件。录像的采集判定为空；其他拍摄的采集判定可以仍待定、已完成或明确失败，不因释放而改判成功 |
| 没有设备结束观察，满足预先声明的时间与全部产物完成契约 | 保存 `completion_basis = TIME_AND_OUTPUTS`，没有设备状态观察时保留 `activity_state = UNKNOWN`。必须具有可靠发送、适用等待完成及完整产物依据，且没有相矛盾的实际观察，才可以继续检查释放条件；采用 `SENT` 自然等待时，还须核对同一活动的原发送结果、`sent_at` 和执行定义中冻结的启动余量。旧定义缺少启动余量时沿用原规则，不补默认值。 |
| Hasselblad 原失败单张活动为 `UNKNOWN`，满足[可用性释放契约](../hasselblad-availability-recovery.md#活动与释放依据的合法组合) | 保存独立检查引用并解除调度限制；活动、采集完成字段、原动作及文件保持原事实。 |
| 启动可能或已经生效，设备仍在执行或是否结束未知，且没有上述完成契约或适用可用性释放依据 | 保持 `HELD`；采集明确失败、动作已取消或已失败均不代替释放依据 |
| `completion_basis = DEVICE_EVIDENCE`，但 `activity_state` 不是 `ENDED` | 属于矛盾组合，拒绝保存；不能用完成依据绕过活动状态 |
| `completion_basis = TIME_AND_OUTPUTS`，但完成方式不适用、必要事实缺失，或仍有可靠的活动进行中证据 | 属于不成立的完成判定，拒绝保存，不以时间或文件存在覆盖实际观察 |

时间与产物分支仅用于采用该固定契约的任务，不在查询失败后启用。它要求 `completion_mode = TIME_AND_OUTPUTS`、`dispatch_state = SUCCESS_RETURNED`、按原执行定义核验的等待完成事实、结果集合及产物要求均满足；采用 `SENT` 自然等待时，等待事实还须关联同一活动的原可靠发送结果和 `sent_at`，并使用原冻结的启动余量、自然结束余量及实际采用的部署等待。不能仅凭经过目标时长释放；精确时点见[相机启动余量设计](../../superpowers/specs/2026-10-18-camera-startup-margin-design.md)。完成后另取得可靠设备结束观察时，可以保存 `ENDED`，不改写历史完成依据。

行内约束要求 RELEASED 具有可靠未启动、活动结束、适用的时间与全部产物完成，或独立 Hasselblad 可用性释放依据。可空字段须显式处理 SQL NULL，不能以空值绕过必要条件。`completion_basis = DEVICE_EVIDENCE` 仍要求 `activity_state = ENDED`；可用性检查不写入采集完成字段。

[可用性检查的数据与事件模型](../hasselblad-availability-recovery.md#数据与事件模型)定义新增引用、目标关系、合法组合和共同提交。只有原实际检查成功、关联和剩余资源条件都成立时，独立守卫才允许该路径下的 `UNKNOWN + RELEASED`；不能仅检查外键非空。已有 `ENDED` 不强制立即释放占用。

### 字段适用范围与保存校验

录像的停止结果保存在设备活动和停止流程中，录像内容是否满足要求由录像处理记录保存。因此，录像的 `capture_json`、`completion_basis` 和 `completion_evidence_json` 均为空。单张拍摄和延时摄影必须具有采集判定：创建活动时为 `UNDETERMINED`，有可靠依据后才变为设备完成、时间与产物完成或明确失败。动作类型在 `actions` 中保存，写入程序沿 `action_id` 核对这些字段的适用范围；不能仅凭采集判定为空就认定该活动属于录像。

| 字段组合或实际情况 | SQL 检查 | 写入事务还须核对的事实 |
| --- | --- | --- |
| 采集判定不适用或尚未确定 | `completion_basis` 为空或为 `UNDETERMINED` 时，完成依据必须为空；判定为空时，`capture_json` 也必须为空。 | 只有录像可以使用空判定；单张拍摄和延时摄影必须从 `UNDETERMINED` 开始，采集结果按实际阶段保存。 |
| 已有确定的采集判定 | 判定为 `DEVICE_EVIDENCE`、`TIME_AND_OUTPUTS` 或 `KNOWN_FAILURE` 时，完成依据必须有值。 | 依据的类型、目标及含义与原驱动契约一致，不能用空对象或本地进程退出代替可靠证据。 |
| 可靠未派发或启动被明确拒绝且没有效果 | 活动状态只能为 `UNKNOWN`；采集判定不能是设备完成或时间与产物完成。 | 必须排除该活动此前尝试仍可能生效的情况，单次调用没有效果不足以解除整个活动的占用。 |
| 按设备证据判定采集完成 | 判定为 `DEVICE_EVIDENCE` 时，活动状态必须为 `ENDED`。 | 证据确实说明原活动结束；动作结果、文件检查及剩余限制分别判断。 |
| 按时间与全部产物判定完成 | 判定为 `TIME_AND_OUTPUTS` 时，固定完成方式必须为 `TIME_AND_OUTPUTS`，发送状态必须为 `SUCCESS_RETURNED`；发送时间、预计检查时间和等待完成事件引用齐全，结果集合为 `COMPLETE`，活动状态只能为 `UNKNOWN` 或 `ENDED`。 | 等待事件确属本活动且满足原等待要求，完整集合的 `outcome` 为 `SATISFIED`，全部必要产物要求已有可靠依据；没有相矛盾的设备观察。预计检查时间的计算及配置依据也须一致。 |
| 按 Hasselblad 可用性规则释放 | 活动仍为 `UNKNOWN`，独立释放引用与占用变化共同建立；采集完成字段保持原值。 | 逐项核对固定目标、原机身、真实检查及原调用收场，遵守[原子保存](../hasselblad-availability-recovery.md#原子保存与历史归属)。 |
| 准备释放占用 | 必须满足前述释放必要条件，空采集判定不能绕过检查。 | 原活动的准备清理和输出范围限制已经解除；无法读取这些事实或原事务结果未知时，不放行冲突操作。 |

SQL 对每次行修改即时检查这些组合。一个事件同时确定设备结束与设备完成依据时，须在同一条活动修改中保存；如果使用结果集合事件填写设备完成依据，原活动的 `ENDED` 必须已由同一事务中先应用的设备观察事件或更早的可靠历史保存。时间与产物完成依据同样只能与齐备的等待、完整结果共同成立，不能先写完成标记再补必要事实。

结果列举的任一可靠页可以提供驱动认可、指向原活动的完成观察。处理模块通过 `DEVICE_OBSERVED.OBSERVE` 保存该活动的实际结束，与原 RESULTS 调用结果共同提交；适用的集合结论在同一事务中随后保存。末页不必重复提供前页的完成观察，后续核实轮次也可以沿用已经可靠保存的原设备结束依据。目录读取错误、集合尚未确定或文件要求尚未确认，不抹去独立取得的设备完成观察，也不据此判定产物满足要求。文件要求明确失败时保存失败的采集与动作结果；实际设备结束仍按原事实保留，释放占用另行核对剩余限制。

固定返回含义为 `COMPLETED` 的延时 START 取得可靠成功返回时，同事务保存原尝试结果和实际 `ENDED`，依据按[历史格式](history-formats.md#事件正文版本-1)引用原结果事件。发送和开始时间仍只保存实际已取得的时间，完成返回时刻不作为这两个时间的替代。采集判定保持待定，直到独立的文件、集合及必要产物要求得到核实；失败返回本身不产生这项完成事实。

报告生成检查设备完成依据时，也从同一历史边界读取发送时间、等待安排、等待完成引用及结果事实。这些输入由[报告字段依赖说明](report-dependencies.json)的 `device_completion_consistency` 集中列出，用于核对设备执行提示的依据，不增加公开字段。设备已经结束而仍保留占用时，报告不把内部的文件归属限制解释成设备仍在运行。

### 剩余限制与下一动作

取消收尾或目标时长无法确认时，文件范围仍可以已经确定。`RESULT_SET_CONFIRMED.OUTPUTS_FINALIZED` 只保存这项独立事实，不修改 `capture_json`、`completion_basis`、`result_set_state` 或动作状态。原 RESULTS 尚未保存结果时，结果与该事实共同提交；原结果已经保存时，沿原可靠页范围补齐该事实，不重开尝试。事务沿原票据核对全部连续可靠页、成功且无错误的末页、没有后续游标、驱动明确提供的 `set_finalized=true`，以及全部新增成员的可靠归属。历史目录成员由原固定基准排除，不混入本次文件范围；事件引用及原键核实遵守[历史格式](history-formats.md#结果页的分批记录)。

| 真实活动与输出范围 | 保存与释放行为 |
| --- | --- |
| 活动可靠结束，基准固定，原集合结论为 `COMPLETE` 或独立文件范围事实已经保存，全部调用已收场 | 可以释放；取消和时长无法确认分别保持原 `CANCELED` 和 `capture_result_unconfirmed/duration_unknown` 结果 |
| 活动可靠结束，基准固定，但集合或新增成员归属仍未知 | 保持 `HELD`；保留已确认的完整文件，不补造集合确定事实 |
| 文件范围已经确定，但活动是否结束仍未知且没有其他适用释放依据 | 保持 `HELD`；目录扫描结束不表示相机停止 |

这项事实没有新增公开字段。原完整保存申请、原末页引用、key 和实际时刻在回执未知时继续保持；改变或省略原末页的原键重送必须拒绝。

取得上述释放依据后，事件处理器按下表核对剩余责任。不新增一套占用状态，沿用 `HELD` 与 `RELEASED`，通过已有任务归属、基准、文件记录及处理进度判断具体限制。

| 剩余事实 | 保存及调度行为 |
| --- | --- |
| 必要准备清理或输出范围归属仍未解决，冲突操作可能改变原任务的识别依据 | 保存已知活动结果，继续保持 `HELD`；兼容操作及其他设备按原资格推进 |
| 原设备活动和准备、输出范围限制均已满足释放条件 | 将 `occupancy_state` 保存为 `RELEASED`；存在尚未完成的主机后处理不单独阻止释放 |
| 剩余限制所需记录不可读、矛盾，或保存结果未知 | 按状态库错误或原事务核实处理，不猜测限制已经解除 |
| 占用已可靠释放，但原调用仍未完成适用收场或驱动不允许新操作并行 | 保留并处理独立调用责任，继续阻止冲突调用；不因活动占用释放而伪造尝试结束结果 |
| 占用已释放，独立调用及驱动兼容条件允许 | 触发候选重新检查；下一动作仍须满足自身取消、终态、窗口、预算、启动保留和排序条件，不自动取得机会 |

仅凭 `HELD` 不能报告录像仍在进行：`ENDED` 与 `HELD` 可以同时成立，表示活动结束但输出范围等限制尚在。`device_execution` 使用同历史边界的活动事实及适用完成依据，遵守[字段出现条件](../../architecture/report-format.md#动作结束后设备是否仍在执行)。

### 共同提交与全部释放入口

正常完成、普通停止、取消停止、启动可靠未派发或无效果拒绝、恢复对账、后续残留收场和应急补记都采用同一释放判定。保存实际结束或完成依据、适用的文件归属进度、占用变化以及原动作历史时，使用同一事务；若剩余文件限制稍后才解除，则由后一次事务保存其事实及占用释放。应急停止遵守最终补记时点；没有可靠提交前，不据内存结果推进依赖该释放的新业务。

| 保存入口 | 事件与共同提交要求 |
| --- | --- |
| 正常完成、普通或取消停止、可靠未派发、无效果拒绝、恢复观察及后续残留收场 | 通过 `DEVICE_OBSERVED.OBSERVE` 保存真实发送或活动状态，通过适用的尝试结果事件保存调用结果；释放条件齐备时，在同一事务中使用 `DEVICE_OBSERVED.RELEASE` 释放该活动。 |
| 核实产物后确定采集结果 | 使用 `RESULT_SET_CONFIRMED` 的对应分支保存集合及采集判定，设备观察按实际证据保存；该事务若同时释放占用，仍使用 `DEVICE_OBSERVED.RELEASE` 并检查剩余限制。 |
| Hasselblad 设备可用性检查 | 按[原子保存规则](../hasselblad-availability-recovery.md#原子保存与历史归属)共同保存真实检查结果、固定目标的释放及检查终结；释放事件引用专属依据，不产生旧活动结束观察。 |
| 活动已经结束，后来才确定文件归属或完成准备清理 | 保存原活动相关的文件或清理事实，并在同一事务中使用 `DEVICE_OBSERVED.RELEASE`；不重新执行停止，也不重开原动作。 |
| 会话错误后的应急补记 | `EMERGENCY_RECORDED.FINAL` 共同保存最终流程、全部尝试及适用设备变化；只有同一释放判定成立时才同时保存 `RELEASED`，否则保留 `HELD`。 |

释放与授予下一动作可以分别提交，释放后按[候选检查](waiting.md#事实保存与候选检查)通知调度；提交后通知前中断由启动恢复发现。回滚保留原状态，提交未知核实原事务，不重新执行停止命令以补记录。迟到观察只改变原活动及其真实关联事实，不清除下一动作的占用；旧动作终态及旧停止失败结果保持不变。

从初始状态回放、快照正向恢复和当前投影逆向恢复，在同一完整边界必须取得相同活动状态、占用、适用完成依据及剩余文件责任。回放不查询设备、不重做停止、不使用当前时间或配置重算旧依据。

## 录像内部处理

本节的单原片输入、主机媒体检查和裁剪字段适用于声明采用单原片媒体处理的录像任务。OSMO 360 II 普通录像的完成依据、默认分段范围及恢复由[分段产物设计规格](../../superpowers/specs/2026-10-20-osmo360ii-record-segmentation-design.md#完成归属与结果判定)维护，集合及范围的[历史归属与有界处理](../../superpowers/specs/2026-10-20-osmo360ii-record-segmentation-design.md#有界处理与历史重建)按该规格衔接；不得将本节的计时不足分支套用于分段时长下界。

`recording_processing.action_id` 唯一关联录像动作，`source_device_file_id` 在可靠取得原片前为空。内部输入拷贝通过 `file_copies.processing_id` 唯一反查；工具产生的文件按中间文件责任和用途查询，不在本表保存文件数组。

`check_decision` 为 `UNDETERMINED`、`NOT_NEEDED`、`REQUIRED`；为 `NOT_NEEDED` 或 `REQUIRED` 时，`check_basis_json` 必填。对象使用 `reason`（`CONTINUOUS_CONTROL_COMPLETE` 表示连续控制完成，`INSUFFICIENT_TIMING` 表示计时不足需媒体证据，`EXCESS_DURATION_CHECK` 表示异常多录检查）、`target_duration_ms`，以及实际用于判定的原始 `control_elapsed_ns`、`continuity_evidence` 等已知成员；未知的依据省略，不能默认为零。启动余量适用时，程序从原冻结定义推导可保证的录制时长下界；该派生下界不覆盖原始控制时长，也不作为媒体实测保存。

`check_state` 为 `NOT_PERFORMED`、`RUNNING`、`COMPLETED`、`FAILED`、`UNCONFIRMED`，`media_json` 使用公共媒体结构并保持检查阶段一致。工具未取得时长与实测时长不足分别表达。

检查取得的实际容器与逐流事实保存在原动作的 `RECORDING_PROCESSED` 历史依据中，不扩展公共 `media_json`。检查结果以 `source_probe` 保存实际输入探测；未执行检查而直接修复时，首次登记修复输出的同一事务保存该输入事实。修复成功以 `output_probe` 保存实际成品探测，恢复和正式产物的格式信息读取原已保存的事实。原键重送同时核对这些探测事实；结果提交未知时先核实原完整申请，不重新探测替换。旧事件未含这些成员时保持原规则；需要 OSV 双流验证的恢复缺少原输入事实时，不猜测或发布修复成品。成员的适用分支由[事件登记](event-transitions.json)维护。

逐流探测事实保存精确 `duration_s`、实际读取的整数 `frame_count`、解析后的 `fps` 和 `attached_pic`，未知字段保持空值。实际帧数只在检查帧数目标时按需计数，普通时长检查和单文件处理不增加整段帧计数。分段检查排除附加图片，只从唯一可识别的主视频流取得所需指标；容器时长缺失与主视频指标未知分别表达，可靠逐流事实不会因容器时长缺失而丢失。逐段检查的事实归属见[分段存储](segments.md)，公共覆盖只在来源结果发布后出现。

原输入与修复输出的问题按下列矩阵解释。原输入问题从同一处理身份的实际 OSV 输入副本和原 `source_probe` 派生；录像处理器、终态申请和写事务守卫共同消费这一依据。守卫在原 `PlanReadScope` 内核对动作归属，再有界读取唯一处理及其原探测历史。

事实|原片与录像结果|修复处理
-|-|-
原探测缺失、工具失败，或必要字段未知，且没有已确认的原输入错误|保持无法核实，不将未知改成损坏，也不撤销独立可靠的控制完成依据|无法完成必要双流验证时保存修复失败，不发布成品
原探测已可靠确认必要主视频缺失，或必要视频／音频流不足目标|保留具体流问题；任何检查决定和阶段都不能用控制完成覆盖已知原输入失败|保留原探测，停止修复派发并沿实际阶段收场；未执行检查不改写为检查完成
原输入合格，但修复输出缺流、时长不足、编码／尺寸变化或工具失败|只说明修复失败，不据此推断原片损坏|保留原片，保存实际修复失败，不发布不合格成品


`repair_state` 为 `UNDETERMINED`、`NOT_NEEDED`、`PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELED`。除 `UNDETERMINED` 外均必填 `repair_basis_json`，保存 `reason`（`BELOW_THRESHOLD` 表示未达到多录门槛，`THRESHOLD_REACHED` 表示达到门槛，`NO_USABLE_INPUT` 表示没有可用输入，`CANCELED` 表示取消停止处理）、`target_duration_ms`、实际比较门槛时使用的 `threshold_s`（原因为 `BELOW_THRESHOLD` 或 `THRESHOLD_REACHED` 时必填，其他原因不适用时省略），以及实际已知的 `actual_duration_s` 或原始 `control_elapsed_ns`；秒数采用精确 JSON 数值。原始控制耗时、按原冻结启动余量派生的录制时长下界和实际媒体时长分别表达；下界不是 `actual_duration_s`，该字段只保存媒体探测取得的实际时长，原始控制耗时也不能复制到其中。控制时间证据不能确定是否达到异常多录门槛时，检查决定采用 `INSUFFICIENT_TIMING`，等待实际媒体检查。已经决定后不因本地门槛变化重算。`SUCCEEDED` 必填 `repair_output_file_id`，`FAILED` 必填 `repair_error_json`，不需要修复时不能用成功修复冒充。

`discard_state` 是取消或过期后处理产生文件的收场进度：`NOT_NEEDED`、`PENDING`、`RUNNING`、`COMPLETED`、`FAILED`、`UNKNOWN`。`FAILED`、`UNKNOWN` 必填 `discard_error_json`。它跟踪所属录像的处理结果；实际中间文件逐份保留和删除由文件表负责。原片检查、修复及取消后处理不在动作终态后重新启动；剩余文件清理责任仍可独立推进。

## 查询与事务不变量

流程按责任唯一键恢复，尝试通过 `(run_id, attempt_no)` 分页，设备活动通过动作唯一键取得。`operations_activity` 定位同一活动的正常停止、后续收场及应急事实；`operations_delivery` 取得交付自身的读取历史。未释放占用使用 `activities_occupancy` 结合原动作的设备绑定查询，不能只查询非终态动作。录像启动机会按[当前归属条件](recording-start.md#启动机会的推导与唯一性)查询；独立查询尚为 `RUNNING` 的尝试并关联其流程，即使流程已经结束也须完成适用收场。

业务接口保证：流程引用目标与所属动作、交付一致；新尝试编号连续且额度同时增加；读取轮次与拷贝一致；能力及固定任务定义一致；等待依据完整；释放占用有实际证据；媒体、修复和正式登记遵守各自阶段。SQL 负责引用、唯一性、范围和可表达的行内组合。外部调用在意图提交之后、结果事务之前进行，不能在 SQLite 事务内等待设备或工具。

## 普通尝试结束结果的保存边界

清理项 C1 删除产物 O 时，先可靠提交尝试身份、调用意图和额度，再派发删除。正常等待超时后，执行流程保留超时及已取得的证据，记录运行诊断并继续收场；数据库中的尝试保持 `RUNNING`，C1 保持 `DELETING`。调用完成适用收场后，业务层共同保存尝试结束结果、实际已知效果及收场依据，再按取消、执行资格和预算决定后续核实或结束。

普通操作尝试的成功、失败或结果未知等结束结果，只在该尝试负责的调用完成适用收场后提交。结束结果已可靠保存，表示本次调用已经满足收场条件；业务效果仍按操作契约单独解释。`RUNNING` 表示该尝试尚未保存结束结果，覆盖已提交意图、实际调用、超时后收场以及收场完成但结果尚未提交等阶段，不证明设备仍在执行或正常等待期限尚未到达。

本次调用的收场由运行中的执行流程管理。camctl 已退出时，接入模块按[接入模块的收场规则](../../host-demo/design.md#接入模块的本地进程收场责任)结束遗留本地执行进程，再允许新会话恢复。尝试结果按[统一结构](#结束结果的统一结构)保存实际结束证据、适用运行假设或确认不会执行的必要依据。普通尝试不另设可独立推进的持久化收场状态。

不同事实遵守各自保存边界：

| 事实 | 保存时点与责任 |
| --- | --- |
| 尝试身份、调用意图和额度 | 派发之前共同提交；收场及恢复不退还已占用额度 |
| 用户取消已经生效 | 按取消规则及时保存并阻止后续普通调用，不等待当前调用收场 |
| 文件已可靠落盘的分段进度 | 按段保存；一段完成不结束整个读取尝试 |
| 独立设备活动的可靠观察 | 按设备活动契约保存，只表达实际取得的保证，不以发令调用结束代替拍摄结束 |
| 普通尝试的结束结果 | 调用完成适用收场后，与已知效果及必要依据共同提交；只有确认提交结果后才推进依赖该结果的操作 |
| 应急停止的事后补记 | 遵守应急收场专属契约，不将普通尝试的意图和结果保存流程直接套用于状态库不可用时的应急操作 |

超时收场期间，执行流程持续处理必要收场，其他动作、取消事实保存和报告生成按各自规则继续推进。运行诊断可以先记录超时，但日志不作为业务历史的恢复来源。调用异常与可靠业务证据共同保留；取得成功事实后发生的调用异常不能抹去该事实，调用收场也不能将未知效果改成成功或无效果。

下表按已有记录及事务可靠性优先判定。恢复继续使用原业务身份和累计预算；新会话开始业务恢复之前，原本地执行进程必须已经满足接入模块的收场边界，或因主机断电而停止。

| 已保存事实与中断位置 | 恢复处理 |
| --- | --- |
| 记录不可读、矛盾，或结果事务提交情况未知 | 按状态库错误或原事务核实规则处理，不猜测有无结束结果 |
| 超时或调用错误已在运行中发生，但结束结果未提交 | 按原未完成尝试恢复，不补造尚未保存的超时、失败或具体发生时刻 |
| 调用已经收场，但结束结果未提交 | 同样按原未完成尝试恢复，不根据进程退出猜测成功、失败或无效果 |
| 没有结束结果的删除或启动尝试 | 按原可能已执行的分区核实，不能仅凭剩余额度重新派发 |
| 没有明确失败结果的读取尝试，仍符合续传资格 | 核实源身份及可靠进度后继续原尝试，不因恢复连接增加次数 |
| 结束结果已可靠提交 | 保留原结果、依据和累计次数，按所属责任继续，不重开已结束尝试 |
| 取消已可靠保存，尝试结束结果尚未保存 | 恢复必要收场并保存实际结果，不恢复普通删除或读取重试 |

恢复先检查取消和所属责任的终态，普通重试或续传以相应执行资格仍然成立为前提；原调用收场及独立设备活动核实按其自身责任继续，不能因普通流程已结束而遗漏。读取超时已经发生但失败结果尚未保存时中断，恢复可以按未完成读取尝试继续；已经保存的读取失败则保持原结果，新增尝试按原累计次数和本次上限判断。

报告只采用冻结边界前已提交的事实。冻结时尝试仍为 `RUNNING`，即使进程内已经观察到超时，内部历史恢复仍取得未结束的尝试；报告使用该边界已保存的动作、产物和交付结果，不把内存中的超时补成公开失败。后来保存结束结果不改写旧报告。结果及其必要依据具有相同的事务可见边界，三种历史恢复路径均恢复该边界的尝试状态、已知效果和其他已提交事实，历史回放不执行调用或收场。

## 无人值守的软件重启责任

格式 V3 的 `software_recoveries` 独立保存已经失败或取消、仍占用相机的原活动恢复责任。`action_id` 引用原动作，`activity_id` 唯一引用原设备活动；后续触发动作在责任正文中另行保存。它不属于原 START、STOP 或 RESULTS，不消耗或重置这些流程的预算，也不改写其结果。

`phase` 使用普通整数枚举列承担候选发现及状态判断，编号和转换由[枚举登记](enum-registry.json)及[事件状态模型](event-transitions.json)统一维护；`state_json` 不重复保存阶段。`state_json` 使用版本 1，其完整身份及可变进度如下；秒数字段使用有限十进制文本，时间使用 UTC 整数微秒。物理列及唯一性约束见[operations.sql](schema/operations.sql)。内存 `RecoveryPhase` 从同一枚举成员名派生文本，不维护第二份成员清单。

| 正文成员 | 保存及推进规则 |
| --- | --- |
| `version`、`origin_trigger_id`、`device_id`、`driver_id`、`serial`、`fingerprint` | 首次固定。`serial` 是部署明确指定的 ADB transport 选择器；`fingerprint` 是已经完成该固件重启合同核实、带资料来源类型的精确指纹，其编码见[恢复配置](../configuration-reference.md#相机软件重启恢复)。重启前后沿同一类型和规则比较，不另存重复身份。 |
| `trigger_id` | 当前授权触发动作。原触发动作结束且尚未派发时保存 `abandoned`；新的有效触发动作可沿同一责任接续，累计预算及原期限保持。已经派发后不因触发动作结束改变原目标。 |
| `created_at`、`deadline_at`、`timeout_s`、`retry_interval_s`、`max_reboots`、`max_checks`、`max_pages` | 首次固定。后续请求、配置变化和 run 不重算整体期限或预算。 |
| `reboots`、`checks`、`pages`、`next_check_at` | 派发和核实前先可靠增加相应累计次数；次数不回退，每次最多增加一次，不能超过首次上限。等待时刻持久化。 |
| `boot_before`、`boot_after`、`reported_serial` | 原 boot 在首次可靠意图前确定，boot 字段一经保存不改写。`ro.serialno` 可以为空，只是额外身份观察；前后都有值而不同则停止恢复。它不代替明确的 ADB 选择器及原绑定。 |
| `prepared`、`scope_finalized` | 检查、意图、确认、准备、目录、就绪分别推进。新 boot 与已验证的固件合同只建立旧活动 ENDED；设置及存储可用和范围事实分别建立。失败或到期保存 `isolated`；未派发且触发者结束保存 `abandoned`。 |
| `baseline_first`、`baseline_last`、`cursor` | 原基准首末引用首次固定；目录页始终保持原绑定、完整目录及连续游标。恢复不重拍、不删除原片、不重开终态 RESULTS。 |
| `scope_pages`、`scope_members`、`scope_first_event_id`、`scope_last_event_id` | 保存已经可靠提交的差集页数、新成员累计数及首末页事件。事件页逐批保存当前目录身份及与原完整基准计算的 `new_entries`。空差集同样需要完整扫描和可靠末页。 |
| `last_identity`、`last_identity_check`、`last_preparation`、`last_directory_error`、`last_directory_return`、`reason` | 保存实际工具结果、错误、对应核实次数及隔离或未派发结束原因；不把调用退出或目录结束解释为采集完成。 |

`DEVICE_OBSERVED.SOFTWARE_RECOVERY` 保存独立责任的创建或更新；确认新 boot 时可共同保存原活动 `activity_state = ENDED`。`evidence.recovery.request` 保存完整原申请，原键重送必须逐项相同。原始核实及设置调用保存在 `identity_call`、`call` 或 `preparation`；可靠目录页的 `directory` 保存 `activity_id`、`page_no`、`previous_event_id`、原输入与后续游标、完整本页 `entries` 及 `new_entries`。差集只排除原固定基准中的身份；原基准按连续历史批次有界读取并核对首末、总批数、总成员数和排序。恢复页链必须从首页开始，逐页引用上一可靠页，并覆盖所有原目录到无后续游标的末页。

事件守卫核对原终态动作、设备绑定、保留占用、不可改写的启动代次、阶段前后关系、累计预算和目录游标；目录保存及释放使用独立的原事务读取端口重新核对基准和差集。释放前逐页核实全部已保存差集、累计成员及可靠末引用，不能只凭 `scope_finalized` 或新 boot 释放。基准缺失、差集未定、目录错误或预算耗尽时仍保留 HELD，保存隔离原因，其他设备继续。

恢复明确结束后的占用释放仍通过 `DEVICE_OBSERVED.RELEASE`，原 `result_set_state`、`capture_json`、采集完成依据、动作终态和 STOP 结果不因恢复范围确定而改写。差集记录只证明文件身份归属范围，不证明文件写完、媒体有效、目标满足或交付成功。
