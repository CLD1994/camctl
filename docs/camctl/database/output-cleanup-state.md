# 产物清理汇总与错误来源

[数据库入口](../database-schema.md) · [一致性验收](consistency-verification.md)

## 产物清理汇总

清理请求 C1 和 C2 都处理视频 O，C1 已失败而 C2 正在处理时，两条 `cleanup_items` 分别保留各自结果，O 在 `outputs` 中保存总体状态 `running`。C2 可靠确认清理完成后，C2 的成功与 O 的 `completed` 共同保存，C1 的失败保持不变。

| 保存位置 | 表达的事实 |
| --- | --- |
| 数据库 `cleanup_items.status` | 某一次清理请求对某份产物的处理状态 |
| 数据库 `outputs.cleanup_status` | 该产物的总体清理状态，是相关清理责任和可靠文件事实的派生投影 |
| 数据库 `outputs.cleanup_error_json` | 该产物清理汇总使用的完整结构化错误，与产物可用性错误 `outputs.error_json` 分开保存 |
| 报告 `cleanup.status`、`cleanup.error` | 从冻结边界处的上述产物字段生成的清理状态及适用错误 |

### 总体状态的判定

事务先验证所需记录可靠、状态组合符合约束，再按下表自上而下选择首个适用分区。记录不可读、矛盾或相关事务结果未知时，按状态库错误及事务核实规则处理，不能用默认汇总掩盖错误。

| 产物及相关清理项的可靠事实 | `outputs.cleanup_status` 对应的报告值 | `outputs.availability` 的约束 |
| --- | --- | --- |
| 已可靠保存该产物清理完成事实 | `completed` | 必须为 `cleaned`，二者同时成立 |
| 尚未清理完成，有清理项处于 `DELETING`，包括查询、重试等待或取消收场 | `running` | 保持 `restricted` |
| 没有处理中项，但仍有有效的 `PENDING_DELETE` 项 | `pending` | 保持 `restricted` |
| 没有尚待处理的清理责任，但仍有删除限制或无法排除删除发生 | `incomplete` | 保持 `restricted`，清理汇总必须附错误原因 |
| 曾建立有效删除意图，相关请求均在允许解除限制的阶段取消，且不存在其他限制或可能删除事实 | `canceled` | 根据可靠文件事实判断，不凭取消推断文件仍存在 |
| 从未建立有效删除意图 | `not_requested` | 根据可靠文件事实判断 |

未知产物 ID 的失败不影响任何真实产物的汇总；尚未满足来源及目标条件的请求不构成已生效的删除意图。已建立限制但尚未取得处理归属的责任由[清理项的 `PENDING_DELETE`](cleanup-coordination.md#清理读取等待与待删除状态)表达；源依赖是否仍存在按执行时的可靠事实检查，取消、限制及汇总变化遵守各自共同提交规则。产物处于 `canceled` 或 `not_requested` 时，文件事实分别决定 `available`、`missing` 或 `unknown`，缺失或未知仍须保留对应可用性错误。

C1 最终失败并完成收场、C2 尚在待删除时，产物可从 `running` 变为 `pending`；C2 接手后再变为 `running`。这是当前总体阶段的变化，不撤销 C1 的失败。所有待处理请求均结束且限制仍在时，产物进入 `incomplete`。取消已生效但当前清理项仍在收场时，该项保持 `DELETING`，产物继续为 `running`；已经可靠清理完成时，完成事实优先。

### 汇总字段的合法组合

`cleanup_status` 必填，整数编号见[内部枚举登记](enum-registry.json)，`cleanup_error_json` 仅在 `incomplete` 时有值。两列与 `availability` 在同一事务中满足下表；表中状态使用对应枚举的公共含义，不将未知文件状态解释为可用。

| `cleanup_status` | `cleanup_error_json` | 允许的 `availability` |
| --- | --- | --- |
| `not_requested` | SQL `NULL` | `available`、`missing` 或 `unknown`，由可靠文件事实决定 |
| `pending` | SQL `NULL` | `restricted` |
| `running` | SQL `NULL` | `restricted` |
| `completed` | SQL `NULL` | `cleaned` |
| `incomplete` | 必填，采用下述错误选择规则得到的完整结构化错误 | `restricted` |
| `canceled` | SQL `NULL` | `available`、`missing` 或 `unknown`，由可靠文件事实决定 |

`cleanup_status = completed` 与 `availability = cleaned` 同时成立。其他非法组合按一致性错误处理；`incomplete` 缺少合格错误来源时，不能补造通用错误。产物可用性错误 `outputs.error_json` 继续遵守其独立字段契约，不受本表的清理错误空值规则替代。

清理项的 `CANCELED` 与产物汇总的 `canceled` 含义不同。前者可以保留不可撤销限制及实际错误，此时产物可能为 `incomplete`；后者要求相关限制已按规则解除，不能携带上一次清理错误。产物后来清理完成，只清空产物当前汇总错误，不删除各请求的原始结果或历史。

### 等待或处理期间的错误显示

视频 O 曾因 C1 未能完成清理而处于 `incomplete`，并保存 C1 的结束原因。新的有效请求 C2 使 O 进入 `pending` 或 `running` 时，O 只报告当前等待或处理阶段，不继续显示 C1 的旧清理错误。C1 自己的错误和历史保持不变。

| 产物总体阶段及变化 | 产物记录与报告的处理 |
| --- | --- |
| 总体状态为 `pending` 或 `running` | `outputs.cleanup_error_json` 为 SQL `NULL`，报告省略该产物的 `cleanup.error`；各请求及尝试仍保存自己的实际错误 |
| 从 `incomplete` 进入 `pending` 或 `running` | 在引起阶段变化的同一事务中更新 `outputs.cleanup_status` 并清空当前汇总错误，事件保留错误的旧值 |
| 所有待处理责任结束后再次进入 `incomplete` | 按下节规则重新选择仍留下限制的已结束项，并保存其结束原因，不能因之前清空汇总错误而丢失依据 |

仅受理 C2，或 C2 尚未满足建立有效清理责任的条件，不自动清除 O 的错误；清除与产物实际进入 `pending` 或 `running` 同步。若 C2 在删除前取消并解除自己的限制，而 C1 的限制仍在，O 可重新进入 `incomplete` 并使用 C1 原有错误。

清空的是产物当前汇总字段，不删除原清理项的错误或任何历史。报告冻结在旧 `incomplete` 边界时仍恢复原错误，冻结在后续 `pending` 或 `running` 边界时省略清理错误；任何后续变化均不改变同一报告的内容。产物可用性错误 `outputs.error_json` 按其独立规则处理，不因清理汇总错误清空而一并清除。

### 清理未完成时的错误选择

视频 O 的清理请求 C1 在历史事件 100 保存删除失败，C2 在事件 120 保存查询次数耗尽，两项均已结束且仍留下删除限制。O 的总体状态为 `incomplete` 时，使用 C2 的结束原因作为产物清理错误。C3 后来在事件 135 保存删除前取消并完整解除本项限制，不替换 O 的错误；C1、C2、C3 各自的结果仍分别保留。

仅在总体状态已经判定为 `incomplete` 后，按下表筛选同一产物的错误来源。总体状态判定优先，不能用某项旧失败覆盖仍在推进的清理责任或已经可靠保存的清理完成事实。

| 清理项在判定边界的事实 | 是否参与错误选择 |
| --- | --- |
| 没有建立过有效删除限制，包括未知目标或建立限制前的失败 | 不参与 |
| 已在允许解除的阶段取消，且本项限制已完整解除 | 不参与，不因结束较晚而替换旧错误 |
| 尚未结束 | 不作为最终错误来源；其仍需承担的责任必须先纳入总体状态判定 |
| 已结束且仍留下有效或不可撤销的删除限制 | 参与，使用本项可靠保存的结束原因 |
| 候选的结束结果、限制或所需历史依据不可读、缺失或矛盾 | 按状态库一致性错误处理，不跳过该项选择较旧错误 |

在合格候选中，先按 `cleanup_items.final_event_id` 降序比较，编号相同时再按 `cleanup_items.id` 降序比较，选择第一项。`final_event_id` 引用保存本项最终结果的 `history_events.id`，表示数据库历史中的保存顺序，不表示设备操作实际发生的时刻；计划时间、墙钟时间及记录最后修改事件不替代最终结果事件。清理项 ID 仅在最终结果事件相同的候选之间固定选择，不表示结束时间先后或错误严重程度。后续无关修改不改变排序依据，重送及重启不重新分配已保存结果的顺序。

例如，同一产物的清理项 601、702 都在事件 200 保存最终结果，且均仍留下删除限制，则选择 702 的结束原因。如果 601 的最终结果事件是 201，则选择 601，不受清理项 ID 较小影响。先筛选有效候选再排序；不符合候选条件的项不能因编号更大而被选中。

最终结果与其历史事件共同提交。事务回滚的事实不参加比较；提交结果未知时先核实原事务。同一事务内的判定使用拟提交的完整状态及已分配事件编号，不能遗漏本事务刚保存的结束结果。

所选结束原因生成的完整结构化错误保存在 `outputs.cleanup_error_json` 中，并与产物汇总共同提交。报告生成和历史报告重建读取产物自身已保存的错误，不再次查询各请求的当前结果。各请求的原错误、尝试和预算保留，不因产物只显示一个错误而合并或改写。

### 清理项的最终结果事件

`cleanup_items.final_event_id` 是可空的正整数外键，引用 `history_events.id`，定位首次保存本项最终结果的事件。例如清理项 601 尚在处理时该字段为空；事件 120 保存本项最终失败时，状态、错误及 `final_event_id = 120` 共同保存。该字段属于清理项的派生投影，由最终结果事件确定，不独立生成或修改。

| 清理项阶段或保存行为 | `final_event_id` 的规则 |
| --- | --- |
| 尚未结束，包括未核实、待删除及处理中 | 必须为 SQL `NULL`；单次尝试结束或动作收到取消不填写本字段 |
| 首次保存 `SUCCEEDED`、`FAILED` 或 `CANCELED` | 必填，引用保存该最终结果的本事件编号 |
| 创建清理项时直接保存最终结果 | 必填，引用共同保存创建与最终结果的事件 |
| 已有最终结果，发生重送、重启或其他后续事实变化 | 保持原结果及原编号，不将其改为最近一次修改事件 |

最终结果事务先按历史编号规则分配事件 ID，再将该 ID 写入清理项及对应事件正文；相关投影、历史、对象关联和适用产物汇总共同提交。确认回滚时本次结果和引用均不生效；提交未知时沿原事务身份核实，不另建结束事件替代原结果。

符合事件契约的一条事件可以保存多个清理项的最终结果，各项的 `final_event_id` 可以相同，不对该字段施加全表唯一约束。共同提交不要求共用同一事件；一个事务中使用不同事件保存的结果仍按各自事件编号排序。产物错误选择采用上述并列规则，不为消除并列而强制拆分业务事件。

事件正文包含该字段的前后值，更新时从 JSON `null` 变为本事件编号，创建时在完整后值中保存编号。它不是从事件正文排除的通用派生历史元数据。清理动作快照包含清理项完整行及该字段；正向回放、逆向恢复和快照恢复保持终态与引用一致。恢复到终态之前的边界时，已有清理项的该字段为空；若尚未创建，保持记录不存在。

外键只校验事件存在。事件处理及历史校验还须确认被引用事件确实保存了同一清理项的首次终态，事件中的目标、最终状态和实际结果一致。指向其他清理项、普通进度或单次尝试结果的事件，以及终态缺少引用、非终态带有引用、已保存引用被替换等，均按一致性错误处理。正常错误排序直接使用本字段，不通过解析所属动作的全部历史重新查找终态事件。

### 取消后删除结果与错误的保存

清理项 C1 已向设备发出删除视频 O 的命令，随后收到取消。程序停止新增普通调用并完成已有调用的适用收场，仍未取得删除结果时，C1 保存 `CANCELED`，同时通过自身的 `error_code` 和 `error_details_json` 保存 `DELETE_UNCONFIRMED` 及目标 `output_id`。取消状态表达本请求不再继续处理，错误表达此前删除可能留下的未知效果，二者同时成立。公共错误使用已有的 `delete_unconfirmed`，不因取消而补造查询次数耗尽或文件仍存在的结论。

若收场后已有可靠依据确认删除失败且文件仍存在，C1 保存 `CANCELED` 和 `FILE_DELETE_FAILED`，详情保存目标 `output_id`，公共错误使用已有的 `file_delete_failed`。原操作尝试保留驱动返回的具体失败原因、已知效果及依据。单独的超时、非零退出码或通信错误不能证明文件仍在；没有可靠效果结论时仍按结果未知分支处理。

先保留已有终态，并按状态库规则处理不可读、矛盾或提交未知的记录。对于取消已生效、尚无逐项终态的清理项，按下表判断；表中“未发出”要求本项此前没有任何可能删除文件的操作，不能只检查最后一次尝试。

| 调用及文件结果 | 本项保存和处理 |
| --- | --- |
| 已有或可能派发的工作尚未取得适用收场依据，也未可靠确认不会执行 | 继续原项收场，不提前保存取消终态；已在 `DELETING` 的项继续持有处理归属 |
| 可靠确认本项从未发出删除，尚未派发的工作也不会再执行，且没有其他未完成责任 | 保存 `CANCELED`，按规则解除本项可撤销限制，不生成 `DELETE_UNCONFIRMED` |
| 已完成必要收场，取得该产物清理完成的可靠依据 | 本项保存成功及实际完成依据，所属动作保留已生效的取消；产物保存 `completed` |
| 已完成必要收场，删除已经或可能发生，删除结果仍未知 | 本项保存 `CANCELED` 和 `DELETE_UNCONFIRMED`，保留本项不可撤销限制 |
| 已完成必要收场，可靠确认删除失败且文件仍存在 | 保存 `CANCELED` 和 `FILE_DELETE_FAILED`，详情包含目标产物；本项已发出删除所形成的不可撤销限制继续保留 |

取消项的删除失败或结果未知错误及目标属于该清理项自身事实，进入所属清理动作的历史和快照。操作尝试继续保存实际错误、已知效果及适用收场依据；终态保存不清除这些事实，也不重新分配次数。字段及 SQL 组合必须允许取消项携带实际错误，不能将取消项的错误一律置空。

取消项终态、错误、限制及受影响产物汇总共同提交。若没有其他请求继续处理且限制仍在，产物按汇总规则为 `incomplete`；该取消项按最终结果事件顺序被选为错误来源时，将其实际保存的 `file_delete_failed` 或 `delete_unconfirmed` 错误保存到 `outputs.cleanup_error_json`。其他请求仍在等待或处理时，产物继续按总体优先级判断，不仅因本项取消而强制改为 `incomplete`。其他请求后来清理成功，不改写本项的取消结果或原错误，旧报告仍恢复原事实。

### 汇总与相关事实共同保存

`outputs.cleanup_status` 和 `outputs.cleanup_error_json` 由业务事务根据相关事实维护，不接受独立于事实的任意修改。保存清理限制的建立或解除、清理项待处理或处理阶段变化、终态及可靠文件事实时，事务重新判定受影响产物的汇总；汇总或可用性实际变化时，与引起变化的记录共同保存历史和投影。读取资格检查继续遵守原资格及限制规则，汇总字段不成为额外的授权来源。

例如，清理项从 `PENDING_DELETE` 进入 `DELETING` 时，所需流程、首次尝试和额度按原建档边界保存，产物同时从 `pending` 变为 `running`。该事件包含实际变化行的前后值，并关联清理动作和产物；即使 `availability` 仍为 `restricted`，产物清理状态变化也必须取得适用业务序号，使增量报告选中该产物。

若另一请求加入等待，但产物汇总及其他自身报告字段均未变化，则不单凭新增清理项为产物生成报告变化。清理动作继续保存自身变化。错误内容变化同样属于产物报告变化，不能只比较状态；同一事务需要共同保存的事实不得拆成先提交清理项、后补产物汇总的两个事务。

### 汇总的历史与报告恢复

产物快照包含完整的 `outputs` 行及这两个汇总字段；产物相关事件保存它们的实际前后值。恢复报告边界 H 时，直接恢复 O 在 H 的汇总，不读取清理项的最新状态重新计算，也不为生成该汇总将全部清理项复制进产物快照。清理项自身历史仍归所属清理动作。

报告冻结时 O 为 `pending`，后来清理开始或完成，再重建原报告仍为 `pending`。从初始状态回放、从快照正向恢复、从当前投影逆向恢复，均须取得同一汇总及错误。实际执行恢复根据可靠当前事实继续推进；历史回放只应用已保存事实，不触发查询、删除或新调度决定。
