# 设备驱动与文件执行

[设计入口](README.md) · [实现总览](implementation.md) · [实施准备](implementation-readiness.md)

本页说明设备驱动怎样返回证据，以及协程怎样组织线程中的文件操作。取回、清理、取消和文件交接的业务规则仍由[产物专题](../architecture/outputs.md)及其细则定义；这里规定执行位置、接口完成含义与资源所有权。

## 设备驱动接口契约

| 接口部分 | 能力 |
| --- | --- |
| 静态定义 | 拍摄能力、参数 Schema、默认值、完成条件和操作兼容性，不连接设备 |
| 设备控制 | 准备通信、发送拍摄命令，以及设备明确支持的状态查询和停止操作 |
| 设备文件访问 | 按任务和文件处理契约声明可用的文件信息、读取、摘要及删除能力 |

不同拍摄能力按实际设备提供接口，不要求录像、照片和延时摄影采用相同的启动、停止及完成方式。ADB 命令、厂商响应格式及证据解释留在具体驱动内部；业务层消费明确事实。驱动不自行写业务数据库、改变动作状态或生成状态报告。

框架根据声明选择执行及恢复路径，不因没有拍摄状态查询接口而把设备判为查询失败。延时摄影可以采用[时间与产物判定](../architecture/camera-capture.md#按时间与产物判定完成)，由明确的运行假设、等待完成事实和产物核实共同形成动作结果。通过设备内置应用或脚本发令时，执行返回若只表示发送成功，驱动必须保留这一含义，不将其包装为设备已经启动、停止或完成的直接观察。

延时摄影按[处理模块与驱动的职责](../architecture/camera-capture.md#延时摄影处理模块与驱动的职责)组织。驱动定义并执行设备操作、解释设备证据；处理模块组织持久化、有限尝试、取消和恢复。设备原生任务自行控制周期采集；需要主机控制结束时，业务计时和停止决定由处理模块负责。驱动对上层提供需要持久化和恢复的操作阶段，不自行隐藏业务计时、停止或重试。设备原生调用可以持续到任务完成才返回，框架按[返回含义](../architecture/camera-capture.md#命令返回含义与等待起点)异步等待和解释结果，期限按相应任务契约确定。

业务层通过[设备文件记录](database/outputs-files.md#设备文件记录)保存设备文件的内部身份、驱动定位信息、业务归属及可靠取得的文件事实。正式产物登记前的内部处理与登记后的取回、清理引用同一文件记录；驱动解释定位信息并返回实际证据，文件是否已登记为正式产物及是否具备操作资格由业务层判断。

延时摄影的[文件完成依据与产物检查](../architecture/camera-capture.md#文件完成依据与产物检查)由任务契约明确。驱动分别说明文件归属、写完及集合齐备的依据，并定义必要产物类别、数量和文件检查规则。处理模块保存采用的完成保证或等待假设及实际检查结果，不把等待推导出的完成结论包装为设备直接观察，也不默认执行全面媒体内容验证。

[无状态查询任务的重启等待恢复](../architecture/camera-capture.md#无状态查询任务的重启等待恢复)使用发送成功时取得并保存的 UTC 日期时间和预计检查时间。日期时间用于跨重启计算剩余等待，本次运行内仍使用单调钟。驱动提供原任务的可靠完成凭据时按其保证范围使用；框架不将主机经过时长包装为设备实际采集时长，也不因重启自动解除原设备活动的执行限制。

调用结束情况与设备事实分别表达。普通尝试的结束结果采用[统一结构](database/operation-fields.md#结束结果的统一结构)，驱动或文件适配器声明各操作证据的类型、版本、字段及保证范围，业务层核对后共同保存；预期调用错误不能丢弃此前取得的可靠观察。读取分段结果仍按分段接口返回，不将每一段都当作尝试结束。以下是已有设备契约的代表性分区：

| 已取得证据 | 驱动表达 |
| --- | --- |
| 按设备契约，命令执行返回只确认发送成功 | 命令发送已确认，设备实际执行状态仍按已知事实表达 |
| 可靠识别启动成功响应 | 启动已确认，携带确认时的计时依据 |
| 原生调用在任务执行完成后返回，成功响应按契约证明采集完成 | 采集完成已确认；文件完成事实按返回保证分别表达 |
| 设备明确拒绝本次操作 | 拒绝结果及原因；其他设备状态仍只表达已知事实 |
| 调用超时，效果无法确认 | 调用超时、设备结果未知 |
| 已取得可靠成功证据，调用随后异常 | 同时保留成功事实与调用异常 |

上层执行流程管理业务尝试预算、重试间隔和恢复决策；驱动执行本次明确要求的调用，不自行增加业务尝试或重置预算。录像的计时与证据要求见[相机拍摄](../architecture/camera-recording.md)，其他任务按各自声明解释返回和计时含义，不统一套用录像控制语义。

文件读取接口须支持：

- 向分段传输工作线程提供指定偏移起的连续文件数据，由该执行方按小块读取并及时观察实际数据到达，用于无数据超时判定。文件内容在驱动读取端与传输线程之间流动；主事件循环处理段结果、控制和异常通知。
- 底层源读取返回不超过请求长度的 `bytes`，只有空字节串表示暂时没有数据。会话在推进位置前校验类型与长度；非法返回按读取错误关闭源，不截断超长数据，也不把非法空值解释为无数据超时。
- 请求停止并确认实际读取结束；确认前保留设备拷贝占用。
- 拷贝期间必要的录像停止命令仍能执行；不独占整个设备直到文件读完。

读取会话的 `request_stop()` 只发送停止信号并建立独立结束责任，不在事件循环中等待读取或关闭。读取返回部分数据后，即使消费者不再调用下一次读取，结束责任仍在工作线程等待原读取退出并关闭资源。重复停止请求复用同一责任；源端停止信号与关闭串行，关闭期间不再发送信号。

停止信号发送失败由 `request_stop()` 报告，实际关闭结果由 `wait_stopped()` 报告；关闭失败不能返回停止成功。读取失败后仍执行关闭，并向读取调用方保留原异常；读取和关闭都失败时保留两者。取消一个等待者不取消实际关闭或共享结果，其他及后来的等待者仍能取得实际结果。所属流程在退出事件循环前须跟踪会话结束，不能以取消等待代替源端收场。

同一相机的单文件拷贝限制由统一设备协调负责，取回、异常原片检查和修复共用。分段、重试与重启均沿用既有身份和预算，见[文件拷贝规格](../architecture/file-copy.md)。

读取和分段接口在执行数据操作前校验数值参数。字节计数与轮次必须是整数，布尔值、浮点数和数字字符串不能隐式转换为整数。非法会话构造参数不接管源端；非法单次读取长度不读取或关闭已有会话，原会话仍可供合法调用使用。

| 参数 | 有效范围 |
| --- | --- |
| 固定源长度 | 大于或等于零的整数。 |
| 初始读取偏移 | 从零到固定源长度，包含两端。直接构造会话与工厂函数使用同一校验。 |
| 单次读取长度 | 正整数。实际请求还须限制在源剩余长度内。 |
| 分段范围和轮次 | 起点及轮次为非负整数，终点为大于起点的整数。 |
| 小块大小 | 从 1 到 4194304 字节的整数，包含两端。 |
| 无数据超时 | 有限正 `Decimal` 秒数；保留原阈值，不能因浮点转换将其变为零、无限或另一个边界。 |

## 文件处理接口契约

| 部分 | 责任 |
| --- | --- |
| 取回流程 | 确定来源及产物集合，创建交付身份，判断发布资格，汇总逐项结果 |
| 可恢复拷贝流程 | 组合设备读取与本地文件接口，管理读取尝试、可靠进度、续传和完整性校验 |
| 本地文件接口 | 检查、写入、同步、截断、原子移动和删除，返回实际操作结果 |

可恢复拷贝由取回、异常原片检查和录像修复共用，接收已经确定的来源、中间文件与所属处理身份。是否创建 `delivery` 由发起流程决定。

每段拷贝按“读取并写入 → 文件与必要目录同步成功 → 数据库保存可靠进度 → 提交成功后继续下一段”推进。文件操作只提供事实，数据库进度由拷贝流程保存。恢复时按固定源长度、可靠进度和实际文件状态判定，遵守[续传决策表](../architecture/file-copy.md#重启后选择续传位置)。

发布接口保留实际操作阶段：

| 操作结果 | 可以确认的事实 |
| --- | --- |
| 确认移动尚未发生 | 本次操作尚未把文件交给 `ready` |
| 移动成功，必要目录同步失败或未确认 | 文件已对主程序可见，持久性未确认，不能当作从未发布 |
| 移动及必要目录同步成功 | camctl 的文件发布步骤完成，可继续保存所属流程要求的记录 |
| 移动结果无法确认 | 保留未知，结合历史与实际文件证据核实 |

文件可以在数据库记录保存前被主程序领取。当前进程依据自己已经可靠确认的移动与同步结果保存事实，不要求文件仍留在 `ready`。普通交付、业务状态报告和日志副本分别遵守自身的交接及恢复规则；文件接口不自行分配业务身份或要求先写业务数据库，因此日志副本交付可以在数据库不可用时工作。

普通交付流程按[保存顺序与中断恢复](../architecture/file-handoff.md#普通交付的保存顺序与中断恢复)组织发布意图、文件移动、目录同步和完成事务。重启后没有可靠完成事实、三个位置均无副本且无法确定结果时，交付结束为 `failed`，保留本地交接结果未知的原因，不自动重新投放。该判断属于业务恢复流程，不能由通用文件接口或目录缺失的默认值代替；其他交付继续按取回汇总规则推进。

取消和恢复由所属流程组织。取回半成品与取消后的完整副本共用[中间文件清理机制](../architecture/obtaining-outputs.md#取回中间文件的保留与清理)，先保存适用的失败或取消，确认文件归属及相关操作已结束，再删除本次仍在 `staging` 的副本；清理失败保留记录，后续正常 `run` 再作有限尝试，不单独触发会话。

普通取回遵守[拷贝取消与文件操作收场](../architecture/obtaining-outputs.md#拷贝期间的取消与文件操作收场)：同一文件按段提交任务，线程内部顺序处理小块并检查停止请求；取消后停止新增普通操作，排队任务确认撤回，已开始的文件调用跟踪实际结果。源读取、本地读写和重试分别确认停止后，才能按取回归属清理。已开始的进度事务仍按数据库规则确认结果，不因取消抹去已提交历史。文件接口不凭文件残留自行决定清理资格。主程序领取与传输边界见[文件交接](../architecture/file-handoff.md)。

### 本地文件执行使用默认线程池

第一版本地文件任务通过 `asyncio.to_thread()` 使用当前事件循环的默认线程池。分段传输与其他本地文件操作共享该池；线程按需创建并复用，任务完成后线程可执行下一项任务，在线程池关闭时统一收场。

线程数量沿用所选 Python 运行库的默认上限；具体行为见 [Python 3.11 线程池](https://docs.python.org/3.11/library/concurrent.futures.html#concurrent.futures.ThreadPoolExecutor)及 [`to_thread()` 实现](https://github.com/python/cpython/blob/3.11/Lib/asyncio/threads.py)。

| 执行情况 | 处理 |
| --- | --- |
| 有空闲线程，或默认上限内可以创建线程 | 由默认线程池调度任务，调用协程异步等待实际结果 |
| 工作线程全部占用且达到上限 | 任务等待执行位置，调用协程保持异步等待 |
| 任务实际结束 | 向所属流程交付成功、失败或停止结果，线程可复用于后续任务 |
| 所属流程请求取消 | 沿用排队撤回、段内停止检查及实际结果跟踪规则；文件资源按实际执行状态释放 |

业务流程按需提交工作，动作执行协程遵守[创建时机规则](implementation.md#动作执行协程的创建时机)，相机文件读取遵守[同一相机的拷贝并发限制](../architecture/file-copy.md#同一相机的拷贝并发限制)。同一文件最多有一个未完成分段任务，可靠进度提交成功后才安排下一段。文件与源读取句柄归所属流程或读取尝试管理，连续分段可以由不同工作线程执行，仍须保持顺序与明确的所有权。取消后保留已开始任务的结果跟踪，直至满足既有资源关闭和清理条件。

文件任务的提交与等待共用一个中断处理边界：执行体尚未开始时，在执行器锁内撤回并释放文件修改资格；执行体已开始时，将尚未交付的实际结果登记给监督器拥有者。即使操作已经完成，等待协程随后取消也不能丢弃其结果。提交失败或执行包装器报错同样按实际开始情况处理，原等待者取得原异常。句柄通过共享完成事实提供结果，取消某个等待不影响其他观察；正常返回 `None` 仍表示执行成功。具体状态分区见[文件任务结果与等待中断](../superpowers/plans/2026-10-03-camctl-file-task-results.md#行为契约)。

文件修改资格随实际结束释放，任务身份保留到结果交付给原等待者或接手句柄的等待者；保留期间，同名任务不能提交，异名的同文件后继可以按业务资格执行。结果交付后允许复用任务身份，旧句柄的重复观察不影响新任务。执行体自身抛出 `asyncio.CancelledError` 时，先保存实际失败和释放文件资格，再传播取消；已登记或随后登记的接手者均可取得该结束结果。

媒体任务与同步文件任务共用上述占用登记。检查任务占用输入文件，修复任务同时占用不同身份的输入和输出文件；任一文件冲突即整项拒绝。工具退出及后续文件结果采集属于同一任务，阶段之间不释放文件。等待者取消时，监督器接手实际任务；停止通过执行器或接手句柄请求，不取消内部受管协程。工具输出读取失败或信号发送失败时仍须完成实际退出及输出收场，错误分别保存。文件结果采集在线程池排队或执行期间收到停止请求后，仍完成必要的输出观察；已经开始的摘要或同步保留实际结果，尚未开始的后续阶段不再执行。状态分类与验证见[媒体任务责任](../superpowers/plans/2026-10-03-camctl-media-results-review.md#m3b-的任务责任与实施顺序)。

第一版本地文件任务不设置应用层统一提交上限。符合业务资格的任务通过 `asyncio.to_thread()` 直接提交，默认线程池的工作线程全部占用时，由线程池排队，调用协程异步等待。默认线程池限制执行线程数量，其内部等待队列没有有界容量；现有按需创建、逐段提交和设备并发规则减少提前积压，但不提供所有未完成文件任务的固定数量上限。数据库、日志和报告通信继续使用各自专用执行资源，报告生成子进程自行完成其文件写入和同步。

验收覆盖共享池中传输与其他文件任务交错执行、任务排队、跨段顺序及取消后结果跟踪。联调测量实际吞吐、文件任务积压、文件操作等待和主事件循环调度延迟，以运行证据评估资源安排。若发现某个流程集中提交大量任务，优先检查并调整该流程的任务创建和提交方式。

### 按段提交的流式传输任务

取回、异常原片检查和修复输入共用分段传输方式。主协程根据可靠进度、源长度及生效段大小确定本段范围，通过 `asyncio.to_thread()` 提交一个默认线程池任务并异步等待结果。任务在所属读取尝试内，从驱动取得源数据，在同一执行流程中按小块顺序写入目标文件，复用有容量限制的缓冲；到达本段目标后完成文件及必要目录同步，返回实际结果。源数据读取和本地写入均在传输执行方推进，主事件循环只协调阶段转换和必要控制。

同一文件同一时刻最多有一个分段任务，期间对该文件的修改由任务独占。任务内前一小块处理完成后再推进下一小块，缓冲容量独立于段大小。主协程收到段成功结果后，仍须检查所属流程资格，再通过专用数据库线程保存可靠进度；提交成功后才安排下一段。段成功只证明对应范围的文件处理完成，可靠进度以数据库实际提交为准。

| 当前阶段与结果 | 后续处理 |
| --- | --- |
| 分段任务尚未开始，收到取消 | 确认撤回且不会执行后结束该任务 |
| 分段任务已经开始，收到取消 | 主协程通过线程安全的停止请求通知任务；线程在小块之间及开始段尾同步前检查，停止新增普通读写和同步，跟踪已经开始的调用并返回实际停止结果 |
| 正在等待源数据，收到停止请求或达到无数据超时 | 驱动按既有规则推进读取停止并确认实际结束；停止控制须能在段完成前传达，不能以主协程取消等待代替读取结束 |
| 段写入和必要同步成功，所属流程仍有执行资格 | 返回段范围与同步结果，由主协程组织可靠进度保存 |
| 段结果返回时所属流程已经取消 | 按所属取消和文件保留规则收场，普通取回不为待清理副本新增进度保存 |
| 源读取、目标写入或同步失败 | 返回失败阶段、已知效果及读取停止情况，按所属流程处理；不因已收到或写入部分数据推进可靠进度 |
| 进度事务已经开始 | 跟踪实际提交、回滚或结果未知，按既有数据库规则处理；提交确认前不安排下一段 |

工作线程的停止检查覆盖整个分段任务生命周期，主协程持续响应取消和设备控制。段边界不构成新的设备读取尝试，不重置读取预算或无数据计时规则。数据到达由读取执行方及时观察；等待源数据时使用单调钟，目标写入、同步和进度提交阶段不计入源无数据等待。读取接口、控制通道和数据流的所有权应支持这一分工，具体句柄与通知接口仍需细化。

目标写入接口返回实际写入字节数。短写后，线程在检查停止通知后继续写入同块剩余内容；返回零表示写入没有进展，应结束为写入失败。源读取返回后、每次目标写入前和同步前均检查停止通知。已经开始的调用仍返回实际结果，不因随后收到停止而抹去其效果。

`SegmentResult.processed_end` 表示已确认写入的连续范围末尾，不是数据库可靠进度。写入抛出异常或返回非法计数时，`write_extent_known` 为假，该偏移只是下界，当前调用可能产生其他未确认效果。机器错误分类由 `error` 提供，原异常由 `failure` 保留。源读取异常也返回这一结构，因此此前写入范围不会随异常丢失；读取与关闭双重错误共同保留。

源结束状态独立取自 `ReadSession.poll_stopped()` 的非阻塞观察。关闭成功时，段结果的 `source_end` 保留实际读取字节数和结束原因；关闭失败时，`source_close_error` 保留异常；两者都为空表示尚未取得关闭结果。目标写入或同步失败不改变已取得的源结束事实。未结束的会话由所属流程继续通过 `wait_stopped()` 跟踪，分段函数不自行释放相机机会或增加业务尝试。完整状态分类见[分段结果契约](../superpowers/plans/2026-10-03-camctl-segment-results.md#行为契约与范围)。

正常传输按段交换结果，文件内容使用有界缓冲在传输执行方处理；取消、失败和设备控制按实际发生时通知。数据库事务、业务重试预算与设备协调继续由原业务流程管理。按默认分段配置，每 GiB 的正常分段任务提交为 8 次，创建、最终校验及异常收场等操作另计。

验收分别改变内部小块和分段大小，验证文件字节、可靠进度、取消和恢复结果；检查线程任务提交随段数变化，主事件循环不逐块中转文件内容。覆盖段内取消、等待源数据时取消、同步前后取消、进度提交期间取消和各阶段失败。目标主机联调按分段任务粒度测量吞吐、主事件循环调度延迟、任务交互次数、等待积压及缓冲占用。

### 本地文件操作的完成与故障边界

第一版以本地文件系统调用最终返回成功或错误为正常运行前提。工作线程执行的读写、同步、截断、查询、移动及删除一旦开始，调用方异步等待实际结果；单次本地文件操作及其取消收场不另设应用层完成时限。有限收场限制适用工作和尝试次数，不承诺底层存储持续失去响应时仍能限时正常退出。

| 本地文件操作状态 | 处理 |
| --- | --- |
| 已开始，尚未返回，包括所属流程已取消 | 继续跟踪并等待结果，保持相关文件与操作占用；取消后停止新增普通操作 |
| 返回成功 | 使用已确认的实际效果，按所属流程继续或收场 |
| 返回错误 | 保留错误和已知效果，按所属业务失败、报告失败或恢复规则处理；同步失败不推进可靠进度 |
| 底层持续不返回 | 超出第一版应用内恢复范围，由部署侧处置；不宣称操作结束或正常退出，后续启动按既有持久化状态和文件证据恢复 |

该边界适用于本地文件调用。设备通信、源读取无数据等待、数据库入队与锁等待、报告子进程整次任务的时限继续遵守各自契约；报告任务的总时限仍覆盖其文件处理阶段。

验收使用可控协作者覆盖取消后操作仍未完成、随后成功或报错，以及完成前禁止冲突操作和资源释放。集成测试覆盖真实文件写入、同步、空间不足等错误与中断恢复，联调测量实际负载下的操作延迟。

## 主机文件的定位与路径检查

普通交付、录像输入、处理临时文件和修复目标统一按[中间文件路径契约](database/file-fields.md#中间文件的路径与用途目录)取得工作位置。调用方提供已保存的文件身份、用途、责任及相对路径，文件执行方核对所属目录和实际对象类型后才操作；不能将设备定位信息或用户名称直接当成本地主机路径。

目录无法访问、目标文件不存在、目标类型不符以及读取或删除失败分别返回明确结果。所属流程依据结果及已保存阶段决定续传、恢复、失败或清理完成；文件接口不把这些不同结果折叠成“不存在”。普通交付移动后采用交付文件名及交接目录定位，原中间文件路径仍保留用于解释历史。

## 读取会话与文件所有权

文件流程持有读取会话和唯一文件修改资格，线程池中的各段任务可以由不同线程执行，但不能同时使用同一会话。源数据句柄由分段线程读取；控制子进程及取消由事件循环组织，跨边界只发送停止通知和结果。文件线程实际结束前不关闭其仍在使用的文件，也不发布或删除其准备文件。日志副本不共用普通 delivery 状态机。
