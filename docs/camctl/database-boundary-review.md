# 数据库表职责核对

[设计入口](README.md) · [数据库结构与字段归属](database-schema.md) · [实施准备](implementation-readiness.md)

本页核对第一版业务流程与数据库表的对应关系，说明存储职责、跨表协作边界以及字段设计任务。检查范围是规格，不包括生产代码、真实设备或硬件性能验证。正式表职责以数据库设计及各业务专题为准。

## 核对结论

第一版状态库按二十九张表组织，覆盖主要业务对象、操作尝试、文件处理、历史恢复、报告同步和数据库元信息。中间文件清理的跨会话继续位置由 `runtime_state` 保存，逐清理请求的删除限制由 `cleanup_items` 保存。

表数量与职责边界构成后续字段设计的依据。所有表的整数 `id` 主键遵守[主键与身份引用](database-schema.md#主键与身份引用)。其余字段类型、状态表示、约束、索引和事务接口仍需细化；表职责覆盖不代表完整数据库结构已经定义或实现。

## 业务流程与已有存储职责

各流程均以权威历史与投影共同提交为前提。文件、设备和进程操作发生在数据库事务之外，操作意图、已确认结果及未知事实分别记录；历史回放只恢复状态。

| 业务流程 | 已有表与职责 | 必须保留的协作边界 |
| --- | --- | --- |
| 输入、受理、幂等重送与诊断 | `plans` 保存成功受理关联和计划；`actions` 保存动作及固化参数；`plan_file_diagnostics` 保存独立输入诊断 | 计划、动作、有效关联、适用 ACK 及诊断共同提交；输入失败不创建虚假计划，同一请求重送不重复创建动作 |
| 自动预览与范围来源 | `auto_preview_links` 保存自动用途及来源依据；`action_output_sources` 保存固定来源成员 | 自动用途不代替执行资格；成员集合固定后，重启不扩大范围 |
| 设备拍摄与录像内部处理 | `device_activities` 保存持续活动及观察；`device_files` 保存设备文件身份与事实；`recording_processing` 保存录像检查与修复状态 | 动作终态、设备是否仍在执行、文件是否完整以及修复是否成功分别判断；终态与正式产物登记共同提交 |
| 外部操作及有限重试 | `operation_runs` 保存具体流程与预算；`operation_attempts` 保存各次尝试 | 普通操作派发前提交意图及额度；启动、停止、读取、删除和查询按自身契约计数，恢复不补满预算 |
| 取回选择与读取保护 | `obtain_source_selections` 保存逐来源选择进度；`obtain_items` 保存逐目标选择、失败及读取依赖 | 未选择与已选择为空分别表达；副本可靠准备完成与依赖解除共同提交，取消不等于实际读取已停止 |
| 正式产物及来源关系 | `outputs` 保存每份正式文件的身份、位置关联、质量与可用性；`output_origins` 保存派生产物与原产物的关联 | 一份产物对应一份文件，一个动作可有多份产物；清理文件不删除身份或历史，来源关系不授予级联删除权限 |
| 拷贝、普通交付与中间文件 | `file_copies` 保存可靠字节进度及校验；`deliveries` 保存独立交付与交接事实；`intermediate_files` 保存主机中间文件的用途与生命周期 | 文件先同步，再提交可靠进度；准备完成、移入 `ready`、主程序领取和远端接收分别判断；清理正式源文件不影响已可靠准备的交付副本 |
| 中间文件历史清理 | `runtime_state` 保存全局继续位置，`intermediate_files` 保存逐文件责任和结果 | 检查结果与位置共同提交；重启沿用位置，本次处理额度重新计量 |
| 正式产物清理 | `cleanup_items` 保存请求对每份产物的处理、结果和删除限制，结合产物事实和公共操作记录恢复 | 逐项失败不抹去其他项结果；删除与查询分别限额，取消本项只解除本项可撤销的限制 |
| 取消与撤回 | `cancel_items` 保存固定目标和逐目标处理；`cancel_delivery_items` 保存逐交付处理 | 取消事实与目标变化共同提交；取消动作自身结束后，已生效的必要收场仍由目标负责；已被主程序领取的文件不撤回 |
| 报告、同步、ACK 与启动时间检查 | `reports` 保存冻结依据及管理投影；`state_syncs` 保存显式同步责任；`runtime_state` 保存累计 ACK 和可信历史时间下界 | 一份报告可满足多项同步；ACK 与适用同步结束共同提交；报告发布事实不能代替 ACK，可信时间只在启动检查通过后按规则推进 |
| 历史与对象查询 | `history_events` 保存事件正文；`history_transactions` 保存完整提交分组；`entity_event_links` 保存实际变化对象的关联、计数及适用业务序号 | 事件、关联和受影响投影共同提交；引用对象不增加其变化计数，报告对象选择与历史恢复使用各自查询路径 |
| 历史快照 | `entity_snapshots` 保存不可变对象快照；`entity_snapshot_progress` 保存未包含变化次数 | 快照与维护进度共同提交；准备期间新增变化仍保留；未完成维护不单独延长会话 |
| 数据库识别与初始化 | `database_metadata` 保存数据库标识、实例身份和整体格式 | 完整结构与初始状态一起建立；日常入口不补建缺失数据库或元信息 |

## 数据库之外的状态

| 状态或数据 | 保存与恢复依据 |
| --- | --- |
| 普通日志、日志副本和跨会话故障轮次 | 普通日志及[独立故障标记文件](../architecture/log-failure-marker.md#跨-run-的独立状态文件)；状态库不可用时仍须保留相应诊断与交付能力 |
| 会话接纳资格、报告工作资格 | 内核锁及实际进程状态；数据库记录不能代替持锁事实 |
| 调度缓存、已吸收计划序号、单调钟计时及本次队列等待 | 会话内存；重启根据可靠业务记录重新建立，不能回放旧会话的锁、协程或单调钟值 |
| 报告生成任务、分页位置与本次尝试观察边界 | 活跃任务与会话处理状态；重启通过冻结报告、业务变化、同步责任和实际文件恢复，新会话按规则重新取得处理机会 |
| 设备绑定、驱动能力及部署配置 | 本地配置与驱动定义；用户要求、设备身份、驱动选择及生效拍摄参数随动作保存，本地执行配置在每次运行加载，实际判断依据随对应历史事实保存 |
| 输入计划文件、正式文件、交付文件和报告 JSON | 文件系统及各自所有权规则；数据库保存身份、事实和恢复依据，完整报告 JSON 按冻结依据重建 |

这些边界分别见[会话协议](../architecture/protocol-session.md)、[报告维护](../architecture/report-maintenance.md)、[报告进程](report-runtime.md)及[文件交接](../architecture/file-handoff.md)。报告的每次成功发布仍属于持久化历史，不能与生成进程的临时状态混为一谈。

## 中间文件清理的继续位置

跨会话继续位置由 `runtime_state` 的独立字段组保存，与检查结果、适用的中间文件状态及对应历史共同提交，具体状态分类见[中间文件清理进度](database-schema.md#中间文件清理进度)。每次运行固定的历史范围、额度和重复检查控制遵守[清理预算](../architecture/file-handoff.md#中间文件清理的运行预算)。

软件集成测试使用超过单次额度的记录，并让前面的文件持续无法删除，验证后面的记录仍获得机会。在检查结果与继续位置提交前后中断，验证二者不会部分生效；位置对应记录已经完成时仍能继续，合法初始位置与记录错误分别处理。需要核对历史清理、业务首次清理及退出检查的协作，防止同一文件在一次运行中被重复处理。

## 多个清理请求的删除限制

`cleanup_items` 保存每个请求对目标产物的限制状态及建立、解除依据。新取回结合全部相关清理项及实际文件事实判断资格；取消一个清理项不撤销其他项的限制。完整状态分类、事务与恢复规则见[逐请求的删除限制](database-schema.md#逐请求的删除限制)及[清理取消后的取回限制](../architecture/output-cleanup.md#取消后的取回限制)。

软件集成测试组合两个清理请求与已有、新增取回，在限制建立、取消解除及删除意图保存前后中断，验证单个请求不能撤销另一请求的限制，已失败取回不被重新激活。检查正常资格授予、来源结束后的唤醒、清理取消和重启恢复，并核对 `cleanup_items`、`outputs`、`obtain_items` 及公共删除流程之间的事务接口。

## 动作错误码与阶段核对

核对范围包括工作流程错误登记、动作专题及公共报告样例中的动作最终错误。下表列出已有依据的对应关系，用于检查字段设计；它不是完整错误登记，也不分配数据库整数编号。公共机器定义仍由根 `protocol` 维护，后续登记须将已有专题约定与样例纳入同一来源。

| 动作最终错误码 | 已定义阶段 | 依据 |
| --- | --- | --- |
| `duplicate_auto_preview` | `admission` | [工作流程错误登记](../../protocol/errors/workflow-codes.json) |
| `preview_not_supported` | `admission` | [工作流程错误登记](../../protocol/errors/workflow-codes.json) |
| `source_action_not_found` | `admission` | [客户端样例的错误表达](../architecture/client-protocol-examples.md#错误表达) |
| `start_attempts_exhausted` | `device_start` | [客户端样例的错误表达](../architecture/client-protocol-examples.md#错误表达) |
| `obtain_items_failed` | `execution` | [取回失败项](../architecture/obtaining-outputs.md#取回失败项的报告表达) |
| `cancel_items_failed` | `execution` | [取消动作的完成时机](../architecture/task-cancellation.md#取消动作的完成时机) |
| `cancel_self_target` | `execution` | [工作流程错误登记](../../protocol/errors/workflow-codes.json) |
| `sync_report_not_found` | `execution` | [同步起点解析](../architecture/status-sync.md#camctl-何时开始同步) |
| `device_start_failed` | `execution` | [工作流程报告目录](../../protocol/examples/workflows/reports.json)中 `empty` 场景的动作错误；完整触发条件与详情结构尚需登记 |

上述错误没有同一码对应多个阶段的冲突。`start_attempts_exhausted` 与 `device_start_failed` 是不同错误码，阶段分别沿用各自定义；不能因为文字都涉及启动而擅自合并。操作尝试中的 `camera_start_rejected`、`device_rejected` 等错误不属于动作最终错误，原始错误及其发生步骤需要按所属记录保存。

动作最终错误采用“错误码定义唯一确定阶段”的规则。代码和报告适配从登记取得阶段；写入接口不接受可以独立覆盖该阶段的参数。第一版错误字段定稿还须完成以下覆盖，不能以已有样例没有冲突代替完整性检查：

| 尚需完成的部分 | 必须明确的内容 |
| --- | --- |
| 全部动作受理校验 | 缺失字段、非法类型或组合、设备和参数类型不适用、引用与自动关联错误分别对应哪个最终错误码；保留多个错误的实际字段和值 |
| 执行及结果汇总 | 每个可能结束为 `FAILED` 的业务分支对应的错误码、唯一阶段、详情和所引用的逐项结果；区分实际操作失败、预算耗尽和结果无法确认；登记设备任务不支持取消的逐项错误，区分取消未生效与停止操作失败，整体继续使用 `cancel_items_failed` |
| 驱动结果对应的业务失败分支 | 遵守[动作最终错误与驱动错误](database-schema.md#动作最终错误与驱动错误)的职责划分，逐项确定业务最终失败条件、动作整数错误码及其引用的尝试或处理事实；驱动原始错误由所属记录保存，不要求每个驱动错误都一对一对应动作错误 |
| 权威登记与固定编号 | 公共错误码、阶段和详情契约归入根 `protocol`；内部固定整数编号按单一来源维护，并完整关联公共定义，不能根据清单位置自动编号 |

验证须覆盖每个动作整数错误码均有且只有一个公共错误码和阶段，生成报告与历史恢复使用相同定义。开放的驱动原始错误、操作尝试错误、文件诊断和会话错误继续遵守各自范围，不能因动作省去重复的阶段列而丢失其他责任边界掌握的阶段事实。

## 字段设计与实施交接

数据库对象的整数身份在公共 JSON 中统一使用规范十进制字符串，具体格式与边界遵守[对象 ID](../architecture/plan-input.md#对象-id)。组件适配须覆盖输入、报告、ACK、同步起点、文件名、错误详情和客户端保存，保持同一身份；独立序号与水位继续使用各自的数值类型。

字段设计须按表职责逐表给出身份、状态分类、可空语义、关联、唯一约束和实际查询，并沿以下事务继续核对：输入与 ACK、拍摄终态与产物登记、读取资格授予、副本准备与依赖解除、交付完成与撤回、清理及取消、报告登记与发布、同步确认、快照与进度。

日期时间列统一采用 [UTC 整数微秒](database-schema.md#日期时间的存储)，公共 JSON 使用既有 UTC 时间字符串。逐表设计须区分实际时间、时间可信性及字段缺省含义，并明确原始输入与查询时间列的派生关系。

可空字段遵守[空值与状态组合](database-schema.md#空值与状态组合)。逐表定义须覆盖状态和值的合法组合，优先复用已有状态区分没有值的原因；验证记录不存在、字段为 NULL、记录无效和读取失败不会被混为同一种结果。

状态与类型字段采用[整数枚举](database-schema.md#状态与类型的整数枚举)。逐表定义须落实固定编号、合法组合、公共协议转换及历史恢复，避免编号随声明顺序变化；开放的外部值与原始错误输入继续按各自协议保存。

计划和动作的核心字段遵守[运行状态定义](database-schema.md#计划与动作的运行状态)。状态编号、执行标记、取消标记及合法组合直接用于表约束与事务契约；核验计划聚合、动作结束、取消生效、迟到结果和终态后的交付撤回，保证动作、计划、取消明细与历史共同提交，恢复不重置标记或重开终态。

历史事务 ID 与事件 ID 的独立分配、首尾范围及共同提交遵守[独立事务身份与事件范围](history-storage.md#独立事务身份与事件范围)。计划身份与受理顺序共用 `plans.id`，分配、空库和最新位置读取遵守[受理规则](../architecture/protocol-session.md#新计划受理序列)。`change_seq`、`report_id` 的分配与最新位置查询仍需细化原子性、初始值及上限。对应计划、事件关联和报告记录已提供归属；是否使用派生计数列及具体查询属于字段与 SQL 设计，不预先新增一张通用序列表。文件候选的稳定登记顺序、驱动定位信息及各事件正文也在字段设计时落实。

清理进度与逐请求删除限制涉及跨入口、事务和重启恢复，不能只给实施者一个表名后让其自行补全语义。须将各责任专题的状态分类及业务规则纳入持久化阶段实施计划，按先失败测试、再实现的步骤安排，并在交接前检查同类入口。软件验证使用真实 SQLite 与文件系统及受接口约束的设备替身，不连接真实相机，也不替代硬件性能或物理断电验证。
