# 历史快照维护

[返回 CLI 资料入口](README.md) · [历史存储与事件](history-storage.md) · [历史查询与报告重建](historical-state-query.md)

普通业务读取当前投影；重建较早状态时，可以复用某个历史边界处的对象快照，再正向应用后续事件。历史快照由权威历史派生，保存对象自身状态，用于减少恢复所需的历史计算量；业务事实和报告责任继续遵守各自的持久化规则。快照尚未生成时，历史查询仍按[恢复路径规则](historical-state-query.md#按对象选择恢复路径)使用已有可靠依据。

本页依次定义维护对象、变化次数阈值、持久化候选、唤醒和调度，再说明生成、错误与会话退出。H 表示报告冻结的目标边界，C 表示读取当前投影时的一致边界，S 表示一份快照所表达的完整已提交历史边界；累计变化次数由[实体历史关联](history-storage.md#实体历史关联与累计变化计数)派生；投影与快照的格式见[保存格式规则](history-storage.md#当前投影与历史快照的保存格式)。维护遵守[第一版 MVP 范围](implementation.md#第一版实现范围)，性能优化不扩大业务执行条件。

## 历史快照的对象范围

第一版历史快照维护对象限定为下表四类。快照资格、派生维护进度、候选索引查询、排序及提交后唤醒均使用同一范围；类型范围由统一对象类型定义提供。

| 对象 | 身份 | 快照保存的内容 |
| --- | --- | --- |
| 计划 | `plan_instance_id` | 指定历史边界处的计划自身状态与字段 |
| 动作 | `action_instance_id` | 指定历史边界处的动作自身状态与字段，包括参数、结果及尝试记录等 |
| 正式产物 | `output_id` | 指定历史边界处的产物自身状态与字段，包括可用性及清理结果等 |
| 普通交付 | `delivery_id` | 指定历史边界处的交付自身状态与字段，包括拷贝进度、发布及撤回状态等 |

`report_status` 按动作对象维护快照。对象之间的父子关联继续遵守报告与历史查询规则，父对象保存自身字段，子实体独立处理。

计划文件诊断按诊断创建事实保存完整内容，报告在固定覆盖范围和历史边界内选择并复用原记录。报告生成、发布及补投等管理记录、累计 ACK 和同步责任继续保存各自的历史及当前投影，需要历史状态时依据相应历史恢复。这些记录的保存与恢复沿用所属专题，不建立快照维护进度或进入快照候选查询；阈值为 1 时也保持这一范围。

对象范围只限定历史查询的快照优化。全部权威历史的永久保存、当前投影的事务一致性及报告责任保持各自契约。重建已有报告仍采用它已登记的覆盖范围、冻结边界和固定元数据，不用后来的累计 ACK 或同步责任改写报告内容。

## 按对象累计变化次数触发历史快照

客户端取得的是入选对象在报告冻结边界处的状态快照，事件历史用于主机内部恢复和状态计算。当前投影已经持久化，并随每次状态变更的事务更新；普通当前状态查询直接使用它。

### 对象快照内容与次数触发

按对象在 `entity_snapshots` 中保存历史状态快照，记录某个完整已提交边界处的对象自身状态，供旧报告或其他历史查询复用。每份快照保存对象类型与身份、完整历史边界 S、该边界处的累计变化次数、保存格式版本及状态内容。同一对象可以有多份不同历史边界的快照，已提交内容固定并永久保留。父对象快照保存自身字段，子实体分别保存自己的快照；普通参数或结果中的数组、对象仍属于所属对象的自身字段。

各对象独立累计变化、判断阈值和保存快照。一次维护可以批量处理多个对象，它们仍各自拥有独立快照，不同对象的最近快照可以对应不同历史边界。生成报告时，各对象分别恢复到同一个冻结边界 H，再按报告结构组织。当前投影继续在每次状态变化时更新。

例如，报告冻结在 H＝1005，当前读取位置已到 C＝2000，若存在对象在 S＝1000 的完整快照，则可从该快照正向应用 `(1000, 1005]` 中的相关事件，取得 H 的状态。从当前投影逆向恢复的路径适用于目标之后变化较少的情况，两条路径按[对象相关变化次数](historical-state-query.md#按对象选择恢复路径)选择。

历史快照仅按累计变化次数阈值触发。维护范围内的对象共用一个可配置的正整数阈值 N，各对象分别累计和判断自身尚未包含的变化次数。对已存在且持久化依据有效的对象，设当前累计变化次数为 A，最近已提交快照包含的累计变化次数为 B；没有快照时 B＝0。尚未包含的变化次数为 Δ＝A－B。变化次数采用[实体累计变化计数](history-storage.md#实体历史关联与累计变化计数)的单位，创建计为第一次变化，首次快照也按同一阈值触发。

| 对象状态 | 处理 |
| --- | --- |
| Δ＝0 | 已有快照包含全部变化，不安排重复快照 |
| 0＜Δ＜N | 暂不安排快照 |
| Δ≥N | 安排快照维护 |

上述判断以可靠计数为前提。对象应已存在但计数或关联缺失、A 与 B 矛盾、快照无效或读取失败时，遵守既有状态库错误规则；只有确认没有快照时才使用基准 0。

累计计数与已提交快照跨会话保留，重启不清零。正常 `run` 根据持久化记录重新发现达到阈值的对象，不要求对象在本次会话再发生变化。快照提交成功后，基准只推进到该快照实际包含的计数；读取快照依据后新增的变化继续计入后续判断。确认回滚不推进基准，提交结果未知时按既有规则核实实际持久化状态。

例如，阈值为 64 时，没有快照的对象在重启前累计变化 40 次，重启后再变化 24 次即可成为维护候选；若重启前已经达到阈值但尚未保存快照，后续正常 `run` 仍能发现它。假设保存的快照包含累计第 64 次变化，而准备期间对象又变化了 5 次，保存成功后 Δ＝5。

阈值使用主机本地 TOML 配置，本节定义其默认值与合法范围：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `history.snapshot_change_threshold` | `64` | 正整数；每个对象尚未被最近快照包含的变化次数达到此值时，安排快照维护 |

省略配置项时使用默认值；显式提供 0、负数、浮点数、布尔值或字符串等非法值时，按[本地配置的加载与更新](../architecture/configuration.md#本地配置的加载与更新)报告配置错误。阈值属于本次会话的维护配置，按[统一配置加载规则](../architecture/configuration.md#本地配置的加载与更新)取得，在每次运行内固定，各对象沿用累计变化次数与已保存快照。

配置在会话启动时读取，本次会话内保持不变。后续会话使用当次统一阈值重新判断各对象的持久化计数差；调整阈值不重置累计计数或快照基准，不改变已有业务事实、快照内容、报告冻结依据或输出字节。每批工作量遵守下文的[快照维护批量限制](#快照维护批量限制)。

阈值用于安排快照维护，不是阻止设备操作的条件；维护可能晚于阈值到达时刻，不能据此宣称历史恢复量具有固定上限。维护继续遵守[会话退出规则](#快照维护与会话退出)。

累计变化始终未达阈值的对象可以一直没有历史快照。它停止变化后的状态可直接使用当前投影，较早状态按恢复路径规则查询。若目标 H 早于该对象首份快照，且 H 之后持续发生大量变化，现有路径需从当前投影逆向恢复，成本可能较高。次数也不等同于字节量或实际耗时，相关负载须纳入性能验收。

快照是可由权威历史重建的派生数据，须标明对象身份和对应的完整历史边界，不能混入生成期间较晚的状态。它减少历史计算量，但新增快照写入和永久存储；其收益应与实际部署的存储容量及共享负载一起评估。大范围同步若需要输出大量对象，快照不能消除这些对象自身的读取和编码成本，报告继续按规定的分批处理方式生成。

## 持久化快照维护进度与候选查询

`entity_snapshot_progress` 为快照维护范围内的每个对象保存一条维护进度，记录尚未被最近已提交快照包含的变化次数 Δ，并为候选查询建立索引。该值遵守 Δ＝A－B：A 为对象当前累计变化次数，B 为其最近已提交快照在快照边界处的累计变化次数，没有快照时 B＝0。对象类型与身份共同确定进度所属对象；对象创建时建立记录，尚未达到阈值时也保存实际进度。两张表的职责见[对象快照与维护进度](database/history.md#对象快照与维护进度)，具体列名和索引结构由表定义细化。

维护进度是从不可变历史及已提交快照派生的查询数据，可以重建。各对象的 Δ 无论是否达标都按实际次数保存，阈值只用于查询条件。同一事务结束后，事件、历史关联、当前投影、累计计数及维护进度必须表达一致的已提交状态。`run` 与 `submit` 等保存对象变化的入口共用该规则，历史快照仍由正常 `run` 维护。

| 持久化操作或状态 | 维护进度的处理 |
| --- | --- |
| 创建对象 | 与创建事件和投影一起保存初始 Δ＝1；同一事务中后续变化继续按计数规则累计 |
| 已有对象发生需要计数的变化 | 在保存事件、关联与投影的同一事务内更新 A 及 Δ；B 保持不变 |
| 事件仅引用对象，没有改变其需要恢复的状态 | 该对象的 A 与 Δ 均不增加 |
| 已取得边界 S 的状态，快照尚未提交 | 已提交维护进度仍采用原 B；准备中的快照不推进基准 |
| 保存快照 | 在保存完整快照的同一写事务内，按提交时对象当前累计计数及保存后的最近快照计数更新 Δ；维护基准只确认已提交快照实际包含的变化 |
| 事务确认回滚 | 本次事件或快照及对应维护进度更新均不生效 |
| 提交结果未知 | 按既有提交结果未知规则确认整个事务，不依据内存中的候选进度宣称成功或再次扣减 |
| 对象应有维护进度但记录缺失、计数为负或与可信依据矛盾，或读取失败 | 按状态库错误处理；不默认成 0，也不将查询失败解释为没有候选 |

保存快照时使用该写事务中最新的 A，不能把读取 S 时的 A 带回去覆盖。假设对象当前累计计数已经从 S 处的 64 增至 70，本次保存的快照只包含 64 次变化，则提交后 Δ＝6。快照记录与这次进度更新整体提交，历史快照维护不新增权威业务事件，A 保持不变。再次确认同一已提交结果也不会重复减少 Δ，最近快照基准按已提交记录确定并保持不倒退。

正常 `run` 使用本次生效阈值查询 Δ≥N 的对象，通过索引分批返回候选，每批最多采用 `history.snapshot_batch_size` 个对象。启动后可以直接发现上次会话留下的候选；`submit` 已提交的对象变化也通过同一持久化进度进入可查询范围。候选发现以数据库为依据，进程内通知只能用于安排检查时机。

候选按本批查询的一致读取视图排序，优先处理 Δ 较大的对象；Δ 相同时先按对象类型标识的字典序升序排列；对象类型也相同时，再按对象 ID 的整数值升序排列。对象类型比较保留大小写，ID 使用精确整数比较；同一类型与 ID 唯一确定一个对象。具体类型标识由对象类型定义统一提供，排序不另行维护一套类型优先级清单。

| 候选比较情况 | 顺序 |
| --- | --- |
| 对象 Δ＜N | 不进入本批候选范围 |
| 两个候选的 Δ 不同 | Δ 较大的优先 |
| Δ 相同，对象类型不同 | 对象类型标识字典序较小的优先 |
| Δ 与对象类型相同，ID 不同 | 对象 ID 的整数值较小的优先 |

每批从当前候选排序的开头选取至多配置数量的对象。已选批次准备期间的新变化不重排本批对象，按已取得的状态与 S 完成保存；本批结束后让出执行机会，再依据最新已提交进度重新选取下一批。前一批保存快照会改变相应对象的 Δ，新增业务变化也可能改变候选集合与顺序，因此候选查询每批重新排序取前若干项，不沿用上一批可变 Δ 的分页位置。

持续频繁变化的对象可能在后续批次再次排在前面；该顺序不保证每个候选在固定时间内获得快照。未入选对象的维护进度保持真实值，继续参与后续查询。候选顺序只决定维护先后，不改变历史、当前投影或报告内容；快照维护继续遵守会话退出规则。

后续会话调整 N 时使用新的查询条件，已保存的 Δ 保持原含义。例如 Δ＝50 时，将 N 从 64 调为 32，后续正常 `run` 即可查到该对象；无需等待新事件，也无需改写所有对象的维护进度。未达标对象及已有快照覆盖全部变化的对象保留各自的实际计数。

查询只加载本批需要的候选及状态，不反复遍历全部对象或读取历史事件正文来判断是否达标。验收须检查实际 SQL 执行计划与读取量：保持达标对象及本批数量不变，增加未达标对象和无关历史，确认候选定位使用索引限定范围，并利用索引支持上述排序及数量限制。检查时机遵守下文的提交与发现驱动规则，实际索引方案仍需细化。

### 提交与对象发现驱动快照维护

快照维护由正常 `run` 内的提交结果与对象发现事件唤醒。数据库写操作在更新对象计数和派生维护进度时，判断本次受影响的快照对象是否已有 Δ≥N；确认提交成功后，通过本进程的完成处理路径发布维护唤醒。通知只表达需要检查候选，实际对象及顺序仍以数据库索引查询为准。普通业务处理只等待自身事务结果，快照生成由维护协程异步推进。

正常运行且快照维护启用时按下表处理；本次会话因[入队超时停止维护](#快照入队超时后的会话内停用)后，后续通知不再启动维护。进入会话收尾后，优先遵守已有维护退出规则。

| 场景 | 处理 |
| --- | --- |
| 进入正常 `run` | 通过维护进度索引查询一次，发现前次会话遗留或本次阈值下已达标的对象 |
| 本进程对象变化确认提交成功，至少一个受影响快照对象的 Δ≥N | 唤醒维护协程 |
| 本进程对象变化确认提交成功，受影响快照对象均未达标 | 本次变化不产生维护唤醒 |
| 对象变化事务确认回滚 | 本次变化不产生维护唤醒，已提交候选保持原状态 |
| 对象变化提交结果未知 | 按既有提交结果未知规则处理，不根据候选结果推断已提交 |
| `run` 通过既有流程发现外部提交的新对象 | 检查本次发现对象的已提交维护进度，存在达标快照对象时唤醒维护 |
| 收到维护唤醒 | 按索引、阈值和排序查询并处理本批候选 |
| 一批维护完成 | 释放临时数据并让出执行机会，仍处于正常运行时查询下一批 |
| 候选查询成功且为空 | 等待后续提交或对象发现产生的唤醒 |
| 进入会话收尾 | 停止安排新维护，准备、排队及已开始操作按实际阶段收尾 |

多个通知可以合并为一次待处理唤醒。维护期间发生的唤醒须保留到后续候选检查，空查询与进入等待之间到达的通知也须能够启动后续检查；不能在进入等待时覆盖尚未消费的通知。通知与提交结果的发布遵守数据库操作的实际完成状态，调用协程取消等待不等于实际操作回滚或结束。进程结束后由后续正常 `run` 的启动查询接续持久化候选。

新计划由 `submit` 原子受理后，`run` 在[已有新计划发现流程](../architecture/scheduling-execution.md#新计划发现与内存调度缓存)中检查新发现对象的维护资格。创建按对象分别计数：一个计划包含多个动作，每个对象仍按自身事件累计；子对象数量不累计为父对象变化次数。阈值 N＝1 时，创建即可达标，既有发现流程须覆盖这一合法配置。幂等重送复用对象，不因再次发现而增加计数。

`submit` 同时承担输入诊断及 ACK 的独立处理；有效 ACK 可以改变累计确认位置并结束同步责任。这些记录按[对象范围](#历史快照的对象范围)保存历史和相应投影，其变化自身不产生快照维护唤醒。同一事务同时创建计划或动作时，快照维护资格按本次受影响的范围内对象单独判断；受理拒绝及 ACK 错误产生的业务报告责任继续遵守所属专题。

### 快照维护批量限制

每批维护按对象数量上限组织，遵守[资源处理约束](implementation.md#通过处理流程控制资源使用)。数量上限使用本地配置：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `history.snapshot_batch_size` | `16` | 正整数；每批最多处理的对象数量 |

省略时采用默认值，非法值按本地配置错误处理；合法值与错误分类沿用快照变化次数阈值的正整数规则。配置在会话启动时读取，本次会话内保持不变。该值是批次上限，候选不足时可以处理较小批次。

维护只保留当前批次需要的对象状态与快照内容，减少读取、转换和编码过程中的重复副本，已完成且不再使用的临时数据及时释放。超过本批数量上限的候选留给后续批次，仍按其持久化计数与快照判断资格；未保存快照的对象基准保持不变。

| 会话及批次状态 | 处理 |
| --- | --- |
| 已进入会话收尾 | 停止安排新批次，进行中的操作按会话退出规则处理 |
| 正常运行，本批已达数量上限 | 停止向本批加入对象，按生成流程处理本批 |
| 正常运行，本批未达数量上限且还有候选 | 可继续向本批加入对象 |
| 正常运行，本批未达数量上限且当前候选范围已读完 | 处理本批已有对象；本批为空时不执行快照保存 |

每批完成后释放不再需要的临时数据，让出执行机会，再检查会话状态及后续候选，决定是否安排下一批。批次上限不保证固定的内存占用或数据库耗时，也不要求本次会话清空全部维护候选。测试与联调覆盖不同对象大小和候选数量，测量快照维护与业务并行时的实际资源消耗及延迟。

## 业务操作优先使用数据库线程

同一个正常 `run` 内，数据库线程在选择下一项操作时优先处理等待中的业务操作；只有没有业务操作等待时，才开始快照维护的数据库操作。此处业务操作包括正常执行所需的状态查询及事务保存，快照维护包括候选查询、快照依据读取及快照保存。报告责任的登记与推进仍属于正常业务处理。

下表适用于允许继续派发数据库操作的正常运行阶段。“有等待操作”指已进入本进程排队、尚未开始且仍有效的操作；已确认取消的操作不参与选择。

| 数据库线程状态 | 有业务操作等待 | 有快照操作等待 | 处理 |
| --- | --- | --- | --- |
| 已有操作开始 | 任意 | 任意 | 跟踪当前操作至实际结束，按既有结果与错误规则处理；允许继续时再选择下一项 |
| 空闲 | 是 | 是 | 先执行业务操作，快照操作继续等待 |
| 空闲 | 是 | 否 | 执行业务操作 |
| 空闲 | 否 | 是 | 执行一次快照数据库操作 |
| 空闲 | 否 | 否 | 等待新操作 |

每次从等待状态转为开始执行时按上述规则选择。业务操作在快照尚未开始时进入排队，应先获得执行机会；快照操作已经开始后才到达的业务操作，等待当前操作实际结束。优先顺序不打断已开始的读取或事务，不改变提交、回滚及结果未知的处理规则。

成功入队后按[排队与取消规则](persistence-runtime.md#入队后的排队与取消)等待派发，第一版不另设排队超时。快照长期等待派发不等于入队超时，不因此触发本会话维护停用；进入收尾时仍按实际阶段取消或跟踪。

快照读取与保存分别参与排队，读取完成不为后续保存保留数据库线程。事务外准备快照内容时，数据库线程可处理业务操作；准备完成后的保存重新按表中规则等待。批次结束后的让出执行机会仍按批量限制执行。持续有业务操作等待时，快照可以长期推迟；对象维护进度继续保留，不保证快照完成时间。已开始的快照操作仍可能使后来到达的业务等待，其耗时需要通过短事务和实际负载测量控制。

本规则只决定同一 `run` 内的操作派发顺序。独立 `submit` 进程及报告子进程使用各自连接，它们与 `run` 的数据库锁竞争遵守对应连接与事务规则，本进程排队不提供跨进程优先级。进入收尾后按[快照维护与会话退出](#快照维护与会话退出)停止新增维护并处理已排队及已开始的操作。

### 快照入队超时后的会话内停用

快照候选查询、依据读取及保存均遵守[数据库队列入队等待时限](persistence-runtime.md#数据库队列入队等待时限)。等待达到该上限且确认本次操作未入队、以后也不会执行时，向维护调用方返回明确的入队超时错误，通过既有日志通道记录诊断，并停止本次 `run` 的后续快照维护。此故障自身不形成会话 `state_db_error`，不阻止普通业务，也不改变会话成功条件。

维护是否启用属于本次会话的内存状态；对象的累计计数、快照基准及派生维护进度仍以数据库为准。维护状态按下表转换，进入收尾优先于安排新维护：

| 会话与维护状态 | 事件 | 处理及后续状态 |
| --- | --- | --- |
| 新会话进入正常 `run` | 正常运行启动 | 启用维护，按本次阈值查询持久化候选 |
| 正常运行、维护启用 | 某次快照数据库操作确认入队超时 | 返回错误并记录诊断，停止本次维护并释放可重新生成的临时内容，转为本会话停用 |
| 正常运行、本会话停用 | 新业务提交、外部对象发现、已发出的维护通知、队列空位出现或时间经过 | 保持停用，不查询新候选、不安排读取或保存；正常业务仍按原事务规则更新计数与维护进度 |
| 进入会话收尾 | 尚在等待快照操作入队 | 确认取消且以后不会入队或执行后退出等待，无须等满入队时限 |
| 进入会话收尾 | 快照操作已入队或已经开始 | 按实际阶段遵守维护退出规则，确认取消或跟踪至实际结果 |

本次超时不推进快照基准或减少未包含的变化次数，已提交快照保持有效。已发出但尚未处理的维护通知不能重新启用维护，也无需累计待下次消费的通知；后续正常 `run` 从持久化进度重新发现候选。未生成快照的对象仍按既有历史恢复规则参与查询，快照积压不单独延长会话或产生 `needs_run: true`。

已经入队的操作不再适用入队超时，迟到的入队计时通知不能将其当作未执行。实际数据库查询、读取或保存失败及提交结果未知仍遵守状态库错误规则，不能解释为本节的可延后优化失败。必要业务入队超时或其他会话错误也仍按自身规则处理，本次停用快照维护不改变这些错误的影响。

## 业务提交后分批生成快照

业务先按既定规则可靠提交。由 `run` 中的维护协程分批处理达到生成条件的对象，实际数据库读写交给已有数据库线程，遵守[业务操作优先顺序](#业务操作优先使用数据库线程)；报告子进程继续只读数据库。每批按以下顺序处理：

1. 通过维护进度索引，按本次阈值与批量限制找出本批需要生成快照的对象。
2. 在一致的读取视图内取得这些对象的状态、完整历史边界 S、S 处各对象的累计变化次数及生成所用的格式版本，保留不可变的数据副本。
3. 结束读取事务，在事务外准备快照内容。
4. 用短写事务保存各对象的完整快照、对象身份、边界 S、对应累计变化次数及格式标记，并在同一事务中更新派生维护进度；只有提交成功后，快照及相应进度才可用于后续查询。升级与运行隔离保证本次维护期间不会启用另一数据库格式。

例如，在位置 100 读到 D 的进度为 40%，准备期间业务推进到位置 110，D 变成 70%；随后保存的快照仍标记为“D 在位置 100 时为 40%”。不能用保存时的最新历史位置替换 S，也不因对象后来变化而反复丢弃可靠的旧状态。

| 生成与保存情况 | 处理 |
| --- | --- |
| 已取得 S 的完整状态，期间对象继续变化 | 保存对应 S 的快照；S 之后的变化仍属于后续快照触发的判断范围 |
| 尚未生成快照，或正在准备、尚未提交 | 报告使用已有可靠快照或当前投影与历史，不等待本次维护完成 |
| 快照事务提交成功 | 完整快照可查询；维护进度仅确认到该快照实际包含的边界 |
| 保存失败且确认回滚 | 本批没有新增已提交快照；数据库错误按既有状态库错误规则处理 |
| 保存结果未知 | 不宣称快照已保存或未保存；按既有提交结果未知规则确认实际状态 |
| 生成期间进程终止或主机断电 | 恢复时以完整已提交记录为准，未完成内容不能作为有效快照 |

快照保存到数据库；报告生成进程使用这些快照恢复状态后，按[分批读取与分段生成报告](historical-state-query.md#分批读取与分段生成报告)的规则写出文件。

## 快照维护与会话退出

快照维护属于性能优化，不单独阻止 `run` 结束，也不单独使 `submit` 返回 `needs_run: true`。已有业务及本地报告责任仍按[待处理工作的判定](../architecture/protocol-session.md#待处理工作的判定)检查；快照维护不能改变它们的完成条件。

正常收尾时停止安排新的快照维护，并按操作实际阶段处理：

| 维护阶段 | 退出行为 |
| --- | --- |
| 尚未达到生成阈值 | 不等待阈值到达，按其他责任正常收尾 |
| 已达到阈值，尚未开始维护 | 留给后续正常 `run`，不要求本次清空积压 |
| 已取得对象状态，正在准备快照内容，尚未提交保存操作 | 可以取消，丢弃可重新生成的临时结果 |
| 数据库操作正在等待入队 | 确认取消且以后不会入队或执行后继续退出，无须等满入队时限 |
| 数据库操作已排队，尚未执行 | 确认取消且不会执行后，继续退出 |
| 数据库操作已经开始，包括取消请求与开始执行发生竞争的情况 | 跟踪至实际结束；按读取结果或提交、回滚、结果未知分类处理，再关闭连接 |

后续正常 `run` 通过派生维护进度索引重新发现达到本次阈值的候选，不依赖上次会话尚未保存的内存队列。报告仍可使用已有可靠快照或当前投影与历史恢复，不等待新快照生成。

数据库错误继续按既有状态库错误规则处理；快照属于优化不改变提交结果未知的处理要求。排队取消与连接收场见[数据库线程状态表](persistence-runtime.md#数据库连接与完整事务)，已开始操作沿用数据库忙等待和实际完成规则，不新增通用执行时限。

## 待细化事项与验收

在 `entity_snapshots`、`entity_snapshot_progress` 的职责，以及本页规定的对象范围、统一阈值、按对象计数、派生维护进度、候选排序、批量限制、提交与发现驱动机制及退出规则基础上，细化字段、索引、查询接口和退出预算。恢复路径继续由[历史状态查询](historical-state-query.md#按对象选择恢复路径)定义；快照及事件的查询成本须结合实际负载验证。

各节验收要求与下列矩阵共同适用。候选查询须检查实际 SQL 执行计划与读取量，不能只搜索源码判断实现是否满足要求。

| 验证目标 | 场景与预期 |
| --- | --- |
| 快照触发 | 有无已有快照分别覆盖 Δ＝0、0＜Δ＜N、Δ＝N 与 Δ＞N 的有效分区；创建计为 1，首次基准为 0，N＝1 时创建即可达标；计数矛盾或查询失败不解释为无快照 |
| 快照对象范围 | 四类对象分别覆盖创建、更新及达标，`report_status` 按动作处理；计划文件诊断、报告管理记录、累计 ACK 与同步责任保留各自历史及投影，N＝1 时也不产生维护进度、候选或自身的维护唤醒；同一事务混合范围内外变化时，仅按范围内对象判断快照资格 |
| 范围外记录恢复 | 输入诊断按覆盖范围和 H 复用原事实；ACK 与同步责任按既有规则原子保存；后续 ACK 推进、同步责任结束及报告管理变化不改变已有报告重建字节，内部状态的历史恢复得到独立预期 |
| 快照阈值配置 | 省略配置项采用本节默认值，合法正整数覆盖默认值；0、负数、浮点数、布尔值及字符串按配置错误处理；会话内值固定，后续会话按新配置判断已有对象 |
| 快照跨会话判断 | 未达阈值时重启后继续累计；达标未保存时重启后无需新变化即可发现候选；后续会话提高或降低阈值时按原计数差重新判断；对象无新变化且已有快照覆盖全部变化时不重复生成 |
| 快照维护进度 | 创建、同事务多次变化、多对象变化及仅引用分别得到正确 Δ；`run` 与独立 `submit` 均随事件和投影原子更新；准备快照后新增变化仍保留，快照与进度同事务提交，确认回滚及提交未知按实际结果处理，重复核验已提交结果不重复扣减 |
| 候选查询与异常 | 以独立历史和快照预期核对 Δ 及达标集合；配置变化直接改变查询条件；进度缺失、计数矛盾和查询失败进入状态库错误；保持候选规模不变并增加未达标对象与无关历史，核验实际索引、排序及限量查询的读取成本 |
| 候选维护顺序 | 覆盖 Δ 不同、Δ 相同但类型不同、同类型且 Δ 相同但 ID 不同，以及跨过批量上限的情况；按 Δ 降序、对象类型标识字典序升序、ID 整数值升序选取；对象类型覆盖大小写，ID 覆盖 2、10、100、超过 JavaScript 安全整数的相邻值和最大合法值 |
| 候选批间变化 | 本批准备期间其他对象变化不重排已选批次；提交快照后 Δ 减少、业务变化使其他对象达标或提高 Δ，下一批按最新排序重新选取；重启后按持久化进度和相同规则选择，未入选对象进度不变 |
| 维护唤醒 | 维护启用期间，启动查询发现遗留候选；本进程对象变化达标后仅在提交成功时唤醒，回滚不唤醒，提交未知按原错误规则处理；多次通知合并、维护期间通知以及空查询到等待之间的通知均能得到后续检查 |
| 外部对象发现 | 独立 `submit` 创建计划及动作后，`run` 通过既有流程发现并检查对象；N＝1 时创建即可唤醒，默认阈值下单次创建未达标；子对象数量不增加父对象计数，幂等重送不增加计数 |
| 对象快照独立 | 同类型及不同类型的多个对象使用同一阈值，分别达标或未达标时仅安排达标对象；多个对象的计数差合计达标而各自未达标时均不安排；父对象保存自身字段，子实体独立保存；批量维护后各快照身份、边界及计数正确，不同快照边界仍可恢复到同一报告 H |
| 快照批量限制 | 数量上限的默认与合法覆盖、非法配置，候选为空、少于、等于及超过上限；未纳入对象仍保留资格且基准不变；本批对象数始终不超过配置上限 |
| 快照资源使用 | 增加候选总数时仍分批查询与处理，不保留全部候选的状态；本批结束后释放无后续用途的临时数据；组合不同对象大小及并行业务，测量实际峰值内存、读写量和业务延迟 |
| 快照批间调度 | 每批完成后让出执行机会并重新检查会话状态；进入收尾时不再安排下一批，候选不足时不等待凑满批次；批次大小变化不改变快照内容与其实际边界的对应关系 |
| 数据库操作优先顺序 | 覆盖线程已占用及空闲时两类等待操作的全部组合；快照先排队但尚未开始时业务可优先执行，快照开始后到达的业务等待其实际结束；候选查询、依据读取和快照保存均遵守相同优先级 |
| 快照读写之间的调度 | 读取后暂停准备，业务仍可使用数据库线程；保存重新排队时已有业务先执行；持续业务使快照推迟时维护进度不丢失，维护仍启用且业务队列清空后快照可获得执行机会；收尾仍按阶段取消或跟踪，操作结果未知不能因让出线程而被忽略 |
| 快照入队超时 | 候选查询、依据读取与保存分别覆盖入队超时，确认本次操作不会迟到执行、维护转为本会话停用且普通业务继续；已提交快照、基准和进度不因超时改变，业务新增变化仍正常累计；后续提交、对象发现、已发通知、空位出现与时间经过均不重新启动维护 |
| 快照停用后的恢复与错误边界 | 后续正常 `run` 重新启用并查询持久化候选；收尾可取消等待入队而不等满时限；截止前已入队的操作不受迟到超时通知影响，实际查询或保存失败、提交未知及必要业务超时仍按自身错误规则处理；仅快照入队超时不改变会话成功条件 |
| 快照生成与保存 | 读取 S 后提交新业务变化，保存内容仍对应 S；S 之后的变化不被误记为已覆盖；提交前后中断、回滚及提交未知分别按实际持久化状态处理 |
| 快照维护退出 | 覆盖未达阈值、已达阈值未开始、准备中、数据库操作排队中与已开始各阶段；单独维护积压不触发 `needs_run`，不等待将来达标，取消与开始竞争不能提前关闭连接；重启后仍能发现应维护对象 |
