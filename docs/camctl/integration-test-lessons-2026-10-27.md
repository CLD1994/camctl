# 集成测试重构复盘与编写示例

## 这次重构要解决什么

集成测试应回答：用户或调用方提交一个合法输入后，几个真实模块能否共同完成工作；中途失败或取消后，原结果是否保存，文件、任务和连接是否妥善收场。

此前的大面积失败包含大量测试准备与当前接口不匹配的情况。许多用例尚未执行目标操作，就因旧构造参数、同步调用异步接口或内部对象变化而失败。这些失败既拖慢维护，也使真正的功能问题难以辨认。重构的目标是让测试重新围绕可观察的功能建立证据，并减少重复准备。实施进度和实际结果由[重构记录](integration-test-refactor-2026-10-26.md)维护；测试规则统一见[共享测试规则](../../.agents/rules/testing.md)。

## 从代码中看到的形成原因

### 测试跟随内部实现拆分，逐渐失去功能边界

部分测试直接创建 `CaptureRuntime`，给它补入待保存集合，再调用私有推进方法。这样容易快速触达某个分支，却跳过了真实工厂、数据库线程和任务接手。内部对象重构后，即使正式调用方仍可正常工作，这些用例也会同时失效。

更深的问题是：测试准备可以制造正式入口根本不会产生的状态。例如，旧会话观察测试中有 24 项要求同一内部等待对象被额外观察者取消，或在已经交付后再次取结果；正式 `run_session` 没有这条调用路径。另一些 START 查询测试假定新活动具备查询能力，但当前正式受理保存的能力值并不支持该分支。维护时必须重新核对目标是否属于有效契约，不能只补回旧字段。

### 测试把内部标记当作完成证据

“待保存集合为空”“某个辅助方法执行了一次”只能说明局部变化。它们不能独立证明设备返回已完整保存、同一请求不会重复执行，或者旧数据库线程已经退出。

这次通过真实取消和结果恢复发现了一种具体缺口：文件事实已经保存，动作已经取消，但对应的原结果调用仍是运行中，结果字段仍为空。如果只检查动作终态或文件存在，就会漏掉这类问题。有效断言需要沿原请求核对结果、历史身份和必要收场。

### 替身绕过了需要验证的协作

有些故障测试直接返回 `UNKNOWN`，没有执行真实提交；有些“恢复”测试只重开观察连接，原 worker 仍在；还有些消费者通过替换私有守卫建立前置状态。这些准备让测试名称看起来覆盖了提交未知或冷恢复，实际证据却不足。

替身适合控制驱动、时钟、工具和明确的存储端口。跨线程、真实提交、取消接手和文件生命周期本身就是目标时，测试必须保留对应协作者。故障点还要证明实际命中，否则一次通过可能只是没有走到故障分支。

### 参数数量增长快于独立行为数量

同一套昂贵的拍摄、建库或客户端启动被重复用于许多局部拒绝条件；相同错误又在多个层级逐字比较。参数展开产生了大量节点，却没有同步记录每个维度要证伪什么。

这会带来两个后果：准备成本淹没目标操作成本；一处共用准备错误被展开成数百个失败，看起来像数百项功能故障。整理时应先找共享首因，再分别统计受影响实例与独立缺陷。

### 验收与评审没有及时识别证据缺口

之前的检查过于依赖节点数量、局部通过和执行者的完成声明，未逐项核对真实入口、故障命中、原结果及关闭责任。此次重构中也再次出现了这种问题：把内部持有对象的检查搬到单元目录，或把“查询后耗尽”改成“不发查询”，都曾被当作完成迁移。复核已经将这些交付退回，要求恢复原行为目标或明确说明该目标为何不属于现行接口。

迁往单元层的具体错误，是继续拼装内部对象、断言私有集合和对象身份，却没有证明独立函数契约、资源隔离或原业务目标承接。有独立语义契约并正确隔离协作者的局部分支仍适合单元测试。查询案例最终也区分了目标：当前新 START 查询业务不可达，原两个共同存储及恢复目标由三个公开仓储见证承接，其中一个新增投影回滚反例；它们不计作原业务持有者的验收。

这也是统筹者需要承担的改进：分派任务时交代行为和证据，集成前独立检查差异与运行收据；不能让子代理通过搬动目录、集中包装或更名完成表面迁移。

## 本次已经怎样调整

| 问题 | 当前做法与已有证据 |
| --- | --- |
| 大量用例各自装配内部对象 | 集中真实数据库、正式会话工厂及关闭支持。受理经 `accept_input`，完整会话经 `build_runtime`、`execute_command`、`close_runtime`，专项事务使用公开仓储命令。 |
| 故障依赖 SQL 拼写 | 在真实 SQLite 表操作、返回游标、COMMIT 或外部工具端口安排故障，并核对命中次数、原异常、回滚及实际提交。 |
| 恢复只更换观察连接 | 冷恢复先关闭旧 worker 和实际文件任务，再创建新协作者；同会话原申请恢复则保留原正式工厂，分别验证两种语义。 |
| 只检查内部等待对象 | 用户同意删除不可由公开会话触发的 24 项；其余九项目标合并到公开会话的取消、错误顺序和实际收场验证。 |
| 私有缓存和调用图断言 | 来源存储与产物存储改为核对当前事实范围、事务隔离、完整回滚、分页及公开结果。分别移除两项无效预填和四项矛盾缓存输入，并保留逐项审计。 |
| 跨组件反复启动与重复准备 | 复用同一世界的真实客户端会话；从完整只读来源恢复独立消费者，同时保留实际重启、数据库模式、路径、文件和资源收场见证。 |
| 计量范围混淆 | 准备、目标执行、核对与关闭分别计时；程序预算由独立资源组计量主进程和后代，开发环境验证内存与交换空间合计 2GiB。 |
| 失败归因过早 | 先核对正式契约和实际执行路径。已撤回由非法输入或错误准备引出的生产判断；确认的功能缺口保留失败和完整证据。 |

这些调整仍在推进，不能据此宣称全部保留用例已经迁移、完整回归已经通过，或给出统一提速比例。具体源码身份、范围、耗时和未决问题以重构记录及其证据为准。

## 后续怎样写一项测试

### 先写清一个具体问题

在写环境准备前，用完整句子说明输入、真实协作者和观察结果。例如：

> 文件读取尚未完成时，执行器收到停止请求。测试实际等待读取线程结束，核对已经可靠保存的进度，再按停止原因检查原调用的后续处置。

这里至少分开三种情况：

| 停止时的实际事实 | 应观察的结果 |
| --- | --- |
| 没有可靠业务取消，内容尚未完整，也没有实际读写或关闭错误 | 保留原未结束尝试及进度，不记录读取失败，后续可以沿原身份继续。 |
| 业务取消已经可靠生效 | 等待实际读取收场，再依该业务取消的契约结束原责任，保留已经可靠取得的事实。 |
| 停止同时出现真实写入或关闭错误 | 保留原异常及适用的失败结果；停止本身不能抹去真实错误。 |

随后列明正常、取消、保存回滚、提交结果未知以及再次恢复中哪些分区属于这项测试。每个参数必须改变一个有意义的条件或结果。纯字段合法性由较窄的契约测试承担；需要真实线程接手的取消验证继续放在集成层。

### 选择与目标相称的公开入口

| 要证明的事情 | 合适的入口与结果 |
| --- | --- |
| 一次完整业务能运行 | 提交正式输入，由真实会话消费，观察报告、文件和持久化结果。 |
| 某个模块与协作者组合正确 | 使用文档约定的工厂、上下文和模块入口；驱动或工具通过其正式端口提供输入。 |
| 保存原子性、键重送或历史格式 | 使用公开仓储命令、事务协议或明确的存储格式；核对提交、回滚和同键结果。 |
| 静态历史事件是否满足约束 | 使用 H1 的 `validate_event`、明确的 `EventContext` 和 `ReadCoverage`；只声明静态校验的结论。 |
| 独立函数的局部分支 | 隔离协作者后验证函数契约；同时检查导入时是否读取真实资源，确定测试归属。 |

函数能被导入并不足以证明它是公开入口。选择依据应能定位到接口文档、行为契约或正式调用约定。把私有方法放进共用辅助函数，也不会改变测试边界。

### 让失败和恢复真正发生

提交未知场景应区分 COMMIT 之前失败和 COMMIT 已完成但回执丢失。测试保存原请求、键、实际提交次数及完整结果；恢复时核对沿用原身份，且不会重复设备副作用。场景声称冷恢复时，须证明旧 worker 与原任务已经结束。

取消场景应在明确的在途同步点发出实际停止，再等待线程或进程收场。原始返回、错误及停止事实均须保留。只取消外层等待任务，不能自动证明底层工作已经停止。

### 先减少重复准备，再调整验证安排

同一只读来源可以供多个独立消费者使用。拒绝条件可以共享一份合法准备，但每次必须确认只读或完整回滚。会改变状态的成功、取消和恢复场景使用独立状态；真实重启和文件所有权变化仍须逐项验证。

每项昂贵测试都记录准备与目标执行的时间。保留跨分页边界、原容量规模及计量窗口。单个解释器的分配增长与整个程序的 2GiB 预算分别报告，不能互相替代。运行方式见[测试指南](../../apps/camctl/tests/AGENTS.md)，预算范围见[内存预算测试](memory-budget-testing.md)。

### 交付可独立核对的结果

新增或迁移测试应交付：原目标到新入口和观察结果的映射、实际故障命中与恢复证据、源码身份、完整选中范围、结果、耗时及资源收场。没有执行的范围明确保留；准备阶段失败单独归因。

评审者尤其应核对三个容易遗漏的地方：场景是否真的可由该入口产生；测试是否跳过了原本要验证的接手或保存步骤；最终结果是否只是一份内部标记。发现测试目标已经失效时，记录契约依据与剩余覆盖，再决定删除或迁移。

## 持续记录方式

单元测试的资源边界按用途区分。随代码版本固定的状态编号、事件登记和错误码定义可以在加载模块时只读初始化；这类局部逻辑测试不应被描述为完全没有文件访问。用户数据、部署目录、真实数据库、网络、工作线程和子进程仍按真实协作边界分类。验证资源定位、文件缺失、发布内容或内容一致性本身属于集成；不能把这些目标借“固定定义”名义放入单元层。此边界已经用户确认，并由共享测试规则统一维护。

故障注入要证明实际命中。恢复诊断中的九个读取失败测试依赖旧 SQL 的列格式或探针前缀，生产查询改变后没有抛出预期异常，测试却仍把成功返回视为生产拒绝错误。改造后按实际游标字段及原数据身份识别目标，断言命中次数、原异常、回滚后的完整状态与事务结束；不依赖 SQL 空格或列顺序。模拟注入的 SQLite 异常与数据库自身发生故障分别记录。

同一个错误图和传输消息也有不同的边界。报告 worker 的完整异常图可以超过控制消息容量；正式实现会把完整图写到 stderr，并交付受限的回退消息。测试分别验证完整消息超限被拒、回退消息可以编码和解码，以及 stderr 仍有完整原图；不能把整份展开图误当成已交付控制消息，再随意扩大数值上限。

原内部视图的某个字段没有公开可观察效果时，不能通过各读一次当前值和历史值就声称验证了二者的合并。保留有效的身份、历史来源及产物目标；需要证明类型回退或大小冲突时，用只有该输入不同的正反场景，观察实际资格和产物。纯内部对象形态单独记录退役依据，不给生产增加测试接口，也不在测试辅助函数中复制合并算法。

协调者还出现过把提醒发送给已结束的子代理，却误以为工作已经开始的失误。任务安排应区分已经分配、实际执行和已经结束，结束后的新工作须重新触发；进度以执行回执和真实进程为依据，不能只凭消息已经发出。此类调度失误属于重构成本，不能归因于被测程序耗时。

恢复开发容器后，还要核对解释器实际导入的源码路径。共享虚拟环境的可编辑安装可能指向另一个工作区；只记录当前 Git 提交不能证明运行了该提交。测试命令应显式设置所属源码路径，并记录实际模块位置。并行工作区也应分别指定唯一的 pytest 临时根；默认临时目录的轮转会删除其他组已经结束的数据库。源码、临时文件和证据保留是三个分别核对的边界。

本轮重构自身暴露了三个需要继续纠正的问题。第一，两组新测试把原重试间隔改成零，下载清理组还改变了原票据超时；取消组又将原一秒或 1.25 秒的结果读取超时统一改为十秒。测试虽然通过，验证的场景已经改变。核对共享支持时，应实际比较新旧数据库中的次数、超时、间隔、目标和时间依据，不能只看节点数量与结果。第二，执行器登记前取消和登记后、执行前取消验证的责任不同；后者还要证明已登记任务撤回及身份释放，不能因名称都含“排队”就视为等价。第三，协调者一度把阶段交给原作者作独立评审，作者指出后重新分配；分配前必须核对作者身份，自查与独立评审分别记录。

每批重构完成后，同时更新[阶段记录](integration-test-refactor-2026-10-26.md)中的目标承接、耗时和失败归因。出现新的重复问题时，补充本页对应原因与具体做法。通用约束继续维护在共享测试规则，执行命令与隔离范围继续维护在组件测试指南，避免形成多份相互漂移的规则清单。
