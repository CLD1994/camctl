# 集成测试重构复盘与编写示例

## 这次重构要解决什么

集成测试应回答：用户或调用方提交一个合法输入后，几个真实模块能否共同完成工作；中途失败或取消后，原结果是否保存，文件、任务和连接是否妥善收场。

此前的大面积失败包含大量测试准备与当前接口不匹配的情况。许多用例尚未执行目标操作，就因旧构造参数、同步调用异步接口或内部对象变化而失败。这些失败既拖慢维护，也使真正的功能问题难以辨认。重构的目标是让测试重新围绕可观察的功能建立证据，并减少重复准备。实施进度和实际结果由[重构记录](integration-test-refactor-2026-10-26.md)维护；测试规则统一见[共享测试规则](../../.agents/rules/testing.md)。

本页记录优化过程中发现的测试质量问题，也记录重构自身引入的问题。出现新的可复用经验时，按[持续记录方式](#持续记录方式)补充；已有经验只补新结论，不随每批运行重复更新。

## 从代码中看到的形成原因

### 测试跟随内部实现拆分，逐渐失去功能边界

部分测试直接创建 `CaptureRuntime`，给它补入待保存集合，再调用私有推进方法。这样容易快速触达某个分支，却跳过了真实工厂、数据库线程和任务接手。内部对象重构后，即使正式调用方仍可正常工作，这些用例也会同时失效。

更深的问题是：测试准备可以制造正式入口根本不会产生的状态。例如，旧会话观察测试中有 24 项要求同一内部等待对象被额外观察者取消，或在已经交付后再次取结果；正式 `run_session` 没有这条调用路径。另一些 START 查询测试假定新活动具备查询能力，但当前正式受理保存的能力值并不支持该分支。维护时必须重新核对目标是否属于有效契约，不能只补回旧字段。

后续停止测试也出现同类不一致：活动历史已经保存支持停止，测试工厂却因漏传端口登记为不支持，再通过后置赋值让处理器能够停止。测试通过并不能证明正式装配正确。核对场景实际验证停止预算和取消范围后，准备改为从工厂提供原停止端口，并明确登记值的修正；不能把这项修正称作原输入完全相同，或误称它验证了驱动丢失能力。

测试支持还可能覆盖本来已经正确的生产装配。共享工厂原本负责录像状态和列举缓存，测试辅助函数又保留未使用的状态参数，并在五处重新写入空缓存。确认没有相应调用者及默认缓存的真实所有权后，移除这些覆盖，原功能断言和时间预算保持。以后增加测试参数前，先核对正式工厂已经提供什么；共享、重开和继续推进的差异用实际所有权解释，避免持续补回旧对象字段。

### 测试把内部标记当作完成证据

“待保存集合为空”“某个辅助方法执行了一次”只能说明局部变化。它们不能独立证明设备返回已完整保存、同一请求不会重复执行，或者旧数据库线程已经退出。

这次通过真实取消和结果恢复发现了一种具体缺口：文件事实已经保存，动作已经取消，但对应的原结果调用仍是运行中，结果字段仍为空。如果只检查动作终态或文件存在，就会漏掉这类问题。有效断言需要沿原请求核对结果、历史身份和必要收场。

排查时，共享准备漏传扫描集合也曾被列为候选原因。补齐该参数后，代表用例仍在同一断言失败；进一步观察发现它使用非分页返回，原结果始终留在原拥有者手里，处理器在动作终态处分支返回而未交付。以后先用最小代表检验准备缺口是否真是首因，再沿原结果的实际持有与交付追踪。保存一次返回、扫描结束和集合确定是不同事实，应分别按协议核对。

### 生产缺陷与测试判据问题同时存在

照片提交回执丢失后的核实要求独立只读连接。旧测试用 `PRAGMA query_only == 1` 判断只读，但以 URI `mode=ro` 打开的连接也可以返回零；旧组件测试还与观察连接比较身份，并用父线程访问连接时报 `ProgrammingError` 证明关闭，而该错误也可能仅表示线程不匹配。这些观察不能独立证明目标事实。

修正后，在真实保存回调记录原写连接，仅在原生 `close()` 成功后留存关闭事实，再用可回滚的主库建表尝试核对核实连接的写权限。诊断覆盖 URI 只读、可写连接启用仅查询、普通可写三种情况；非只读错误继续传播。探针限定无活动事务的核实入口，不扩称对任意已有读事务的锁状态透明。组件与安装版共用一份标准库测试资产。修正后的四个业务用例仍发现核实连接可写，原生产问题继续保留；测试判据校正与生产修复分别交付。[证据与范围](verification-data/2026-10-26-integration-refactor/stage-23/manifest.json)

### 替身绕过了需要验证的协作

有些故障测试直接返回 `UNKNOWN`，没有执行真实提交；有些“恢复”测试只重开观察连接，原 worker 仍在；还有些消费者通过替换私有守卫建立前置状态。这些准备让测试名称看起来覆盖了提交未知或冷恢复，实际证据却不足。

替身适合控制驱动、时钟、工具和明确的存储端口。跨线程、真实提交、取消接手和文件生命周期本身就是目标时，测试必须保留对应协作者。故障点还要证明实际命中，否则一次通过可能只是没有走到故障分支。

共享准备还曾覆盖协作者原有的错误。工具在真实保存后用一个异常暂停处理器，却只按异常类型识别自己创建的暂停；当原回执已经带有同类型的另一个错误时，工具把它捕获，再用自己的断言失败覆盖。独立评审通过这一条件指出缺口，局部探针复现后改为记录并核对本次创建的异常对象，只消费自己拥有的暂停。以后验证这类工具时，同时保留原错误的类型、对象和传播结果；测试自造的中断与协作者原错误须有明确归属。假回执探针只证明工具的局部行为，真实保存及停止点继续由真实数据库用例验证。

机内照片改为按需读取后，旧替身仍交付早期版本的拍摄观察，旧测试也要求拍摄后立即得到设备文件的大小和摘要。按当前契约，拍摄时先保存固定机身、双角色和来源身份，首次实际读取后才形成适用的大小与摘要。共享替身现通过真实驱动的公开控制入口和受约束的工具响应形成当前观察及双流。测试应在各阶段精确核对当时应知的事实：读取前要求未知，读取后验证可靠字节和摘要；不能用宽松接受新旧值的断言掩盖契约差异。完整来源、恢复和取回矩阵的迁移仍由工作记录跟踪，部分代表通过不代替整个矩阵完成。

### 参数数量增长快于独立行为数量

同一套昂贵的拍摄、建库或客户端启动被重复用于许多局部拒绝条件；相同错误又在多个层级逐字比较。参数展开产生了大量节点，却没有同步记录每个维度要证伪什么。

这会带来两个后果：准备成本淹没目标操作成本；一处共用准备错误被展开成数百个失败，看起来像数百项功能故障。整理时应先找共享首因，再分别统计受影响实例与独立缺陷。

### 验收与评审没有及时识别证据缺口

之前的检查过于依赖节点数量、局部通过和执行者的完成声明，未逐项核对真实入口、故障命中、原结果及关闭责任。此次重构中也再次出现了这种问题：把内部持有对象的检查搬到单元目录，或把“查询后耗尽”改成“不发查询”，都曾被当作完成迁移。复核已经将这些交付退回，要求恢复原行为目标或明确说明该目标为何不属于现行接口。

迁往单元层的具体错误，是继续拼装内部对象、断言私有集合和对象身份，却没有证明独立函数契约、资源隔离或原业务目标承接。有独立语义契约并正确隔离协作者的局部分支仍适合单元测试。查询案例最终也区分了目标：当前新 START 查询业务不可达，原两个共同存储及恢复目标由三个公开仓储见证承接，其中一个新增投影回滚反例；它们不计作原业务持有者的验收。

这也是统筹者需要承担的改进：分派任务时交代行为和证据，集成前独立检查差异与运行收据；不能让子代理通过搬动目录、集中包装或更名完成表面迁移。

同步生产改进时，语法检查和静态评审都漏掉了一处自动合并错误：一边在保存闭包开头读取外层的原调用身份，另一边在闭包后面的分支给同名变量赋值，组合后 Python 将前面的读取解释为尚未赋值的局部变量。两边单独没有这个错误，真实读取用例却在合并后报错。修正只区分两种变量的名称，保持原票据和保存责任。合并评审应沿自动合并后的实际函数检查变量作用域及新增分支，并运行真实协作路径；仅检查冲突标记和语法不足以确认组合正确。

### 使用公开入口之前，没有先评估模块接口

公开入口本身不能保证测试边界合理。如果为了验证一个模块的保存或恢复行为，必须依次经过受理、调度、拍摄及完整会话等多层准备，测试就会依赖很多无关步骤。一处变化可能让大量用例同时失败；把这条长链放进公共辅助函数，只是隐藏了耦合，没有消除它。

以后先确定最小而有意义的真实模块协作，再判断模块接口是否能独立接收必要输入、执行操作并交付结果。若只能通过内部对象或更高层长链表达目标，记录具体设计缺口、受影响测试与改进建议，等待后续接口改进。不能把“还能找到更高一层公开入口”当作必须继续迁移的理由，也不能为了测试而将私有实现补成所谓公开契约。现有明确契约支持的独立工作继续推进。

### 把常规重构做成了过重的审计

上一批十八个文件的实际测试入口耗时约两分钟，但推进过程还承担了多轮环境核查、源码指纹、数据库逐字段对照、基线与组合验证及串行归档。这些工作有各自用途，却被过多地安排成每批必经步骤，增加了等待和协调成本。

常规流程应先按业务预期写好测试，再运行受影响范围，失败后定位具体原因。环境就绪后直接复用；受测提交、准确命令和运行结果提供基本记录。只有出现导入位置、输入漂移、性能对照或发布来源等具体问题时，才做相应专项调查；没有新改动或疑点，不重复已经通过的范围。改动按完整行为分组，组合验证与必要归档在集成点安排，不让记录工作阻塞独立实施。

为了回答剩余数量，又建立了逐文件哈希和状态大表，但多数条目只是尚未关联评审，并不能给出准确的剩余用例总数。计划、状态摘要、接口问题和阶段说明随之反复同步。现将当前信息合并到一份工作记录，历史索引只保留为证据；复盘只在有新经验时更新，不再另建平行进度文档。

分组数字必须能追溯到具体目标和参数实例。清理恢复的一组历史数量没有逐项身份，复核时只能确认范围，不能继续用该数字计算剩余总数。源码扫描只负责找出待判断的依赖；命中内部字段既不证明目标无效，也不直接构成剩余用例数。

全量后的分类脚本又曾假定 pytest 失败标题至少有四个下划线，漏掉长用例名称的标题，将三十九个失败节点误记为三十二个。协调者按实际主节点逐一关联全部一百二十个失败段后校正。异常文本次数、失败段和用例身份应分别核对；无法完整关联时先报告缺项，不能把未经独立核定的中间计数作为结论。完整基线、收集阻断、小批补测和最终组合分别记录，避免把不同源码的通过数拼成全量结果。

清理取消的设备 DELETE 用例还被误记为独立超时。等待辅助函数虽然有两秒超时保护，原日志却表明它发现会话已因缺少 `closing` 导入而结束，立即抛出了断言。原取消标记已经保存，设备返回和结果保存仍未完成。归因时须核对本次实际抛出的异常、会话主错误及尚未完成的步骤；不能从等待函数的名称或外层超时保护推断失败原因。

随后一批结果查询与录像媒体测试在原有工厂前提供协作者，保留原来的真实读取和保存链，没有为避开内部字段增加上层业务步骤。录像媒体中任意指定的未来时刻改为同一可控时钟，内部待保存字典检查改为驱动没有重复控制操作的事实；原预算、失败与原身份重送继续由业务断言验证。合并后直接运行受影响范围，实际结果见[本批记录](integration-test-refactor-2026-10-26.md#最近验证结果)。需要等待接口改进的目标另行登记，不与这些已有合理入口的改动混为一组。

另一个过严判断是把旧夹具中的任意时刻也当成必须逐字保留的需求。媒体测试曾让检查流程固定使用一个未来时刻，而拍摄流程使用另一套时钟；正式工厂采用同一时钟。应先判断这种差异是否承担有效的窗口、超时或恢复语义，而不是因无法复制两个旧时间值就宣告缺少接口。偶然准备值可以修正，有效预算、错误、恢复身份和必要顺序仍须由测试证明。

进度记录也必须区分“运行过”“某个接口依赖已移除”和“整项重构已验收”。此前按批次保存结果，却没有持续汇总去重后的剩余目标，导致无法直接回答还有多少用例未处理。补查出的字段修改还包含没有调用方的旧辅助函数；不能把所在文件的全部参数实例列为待重写。清单应分别登记有效目标、部分迁移、待判断的候选和用户暂缓的范围，再引用原运行与评审证据。

建立文件索引时还曾按 `fixtures` 文件名将一个真实媒体自检测试计成零，生成器和自检又沿用了同一角色判断，未发现漏计。协调者按每份源码的语法结构独立重算后发现差异。共享支持文件也可能包含自己的真实测试；文件角色与可收集定义必须分别判断，验证不能从生成器的分类结果反推实际定义数。

统计 Python 测试方法还要识别 `unittest.TestCase`：两个未以 `Test` 开头的类仍会被 pytest 收集，索引曾漏计其二十七个方法。静态定义、参数展开后的实例和实际运行结果分别记录；机械重算要采用独立的定义识别逻辑，并保留动态收集尚未执行的限制。

就绪文件的只读接口调查没有修改源码，却仍按“基线、最终”各运行了一次完整文件。第二次通过没有新增迁移证据，还消耗了三十余秒。分派任务时应将最终回归明确限定在存在实际改动、失败或新的待验证疑点时；没有改动的调查复用已有完整基线，并以新的接口事实交付结果。

近期复核再次发现，生产目录的聚合摘要不能证明实际执行的测试源码。测试文件尚未提交时，如果只保存生产源码摘要，后来提交的版本不能反向证明当时的测试字节。常规记录应明确受测提交或当时实际差异；只有需要定位来源疑点时，再记录相关文件摘要，不要求每轮生成全库清单。缺失的旧快照如实保留，不补造历史执行事实。

## 后续怎样写一项测试

### 先写清一个具体问题

在写环境准备前，用完整句子说明输入、真实协作者和观察结果。例如：

> 文件读取尚未完成时，执行器收到停止请求。测试实际等待读取线程结束，核对已经可靠保存的进度，再按停止原因检查原调用的后续处置。

这里至少分开三种情况：

| 停止时的实际事实 | 应观察的结果 |
| --- | --- |
| 没有可靠业务取消，内容尚未完整，也没有实际读写或关闭错误 | 保留原未结束尝试及进度，不记录读取失败，后续可以沿原身份继续。 |
| 业务取消已经可靠生效 | 等待实际读取收场，再依该业务取消的契约结束原责任，保留已经可靠取得的事实。 |
| 停止同时出现真实写入或关闭错误 | 保留原异常及适用的失败结果；停止本身不能抹去真实错误。 |

随后列明正常、取消、保存回滚、提交结果未知以及再次恢复中哪些分区属于这项测试。每个参数必须改变一个有意义的条件或结果。纯字段合法性由较窄的契约测试承担；需要真实线程接手的取消验证继续放在集成层。

### 选择与目标相称的公开入口

具体边界、测试层级与接口缺口的处理统一遵守[测试规则](../../.agents/rules/testing.md#集成测试的接口边界)。本页保留实际案例及避免方法，当前接口问题和迁移进度只在[工作记录](integration-test-refactor-2026-10-26.md)维护。

底层写入专项还要区分行为要求与调用约定。P3 要求事件、当前状态和历史目录共同提交，任一步失败都整笔撤销；具体仓储的内部命令实现不因此成为公开接口。本次先明确[仓储与事务写入模块的协作约定](persistence-runtime.md#仓储与事务写入模块的协作约定)，再让配对、结果页、结果集合、结论和基准读取专项从公开仓储的交付边界取得不透明命令。真实事务开始后才执行其计划，保留反例和整笔回滚，解除对具体仓储命令类的依赖。

讨论这类测试的取舍时，先说明此前已经保存什么、本次故意改坏什么，以及本次失败后哪些数据必须不变。再明确是否已有可依赖的模块协作约定、需要维护哪些输入与失败语义。静态校验不能独立证明真实事务回滚；业务功能继续通过公开仓储和正式会话验证。

审计还确认两类合法准备应当保留：测试自建的核心事务命令，以及公开仓储在完整独立 SQLite 副本中实际提交后取得的历史事件格式。后者仅作为反例输入来源，原库仍重新分配本次编号、读取自身当前事实并执行守卫；副本提交不赋予原库资格。有限事件序列与生产业务采用的有界命令分别验证事务协议，不能因名字含 `Command` 或生产业务主要走有界路径就删去有限专项。共享存储支持已经符合这一边界时，记录审计与原运行，不为制造修改而改名或重复执行同一昂贵范围。

### 共用准备带入额外能力和不同时间

选择共享场景支持前，逐项比较其声明能力、停止和目录端口、UTC 与单调钟、预算、工厂与数据库线程的所有权。一批结果消费者直接换用 `ResultCase` 后，测试仍通过，但照片和延时摄影新增了停止端口，恢复工厂也新增停止与目录端口；录像和取消恢复时的单调钟由原五秒变成六十五秒。后续改为保留原准备流程，在工厂前提供测试拥有的结果脚本、控制驱动和时钟，并单独保留恢复工厂的原五秒单调钟及端口范围。数据库结果相同不能证明这些未持久化输入相同。

Action6 受限媒体场景后来又出现相反的漂移：重建工厂时遗漏原 STOP 和目录能力，测试仍然通过。修正后复用测试持有的首次装配输入，只改变媒体开关。同时去掉了为模拟接续而共享的十六个集合：该点的读取已经结束，部分进度和错误结果已可靠保存，应验证持久状态恢复，不能用共享空集合证明接手了在途任务或未保存结果。运行对象是否相同，应依据当时仍由谁持有什么责任判断。

媒体事件的时间回调也要逐调用点核对。有的场景原先捕获固定读数，有的原先跟随可变时钟；不能把某一场景的修正推广为所有媒体都固定或都随主时钟推进。本批又有一次十五项全绿但三十九条事件时间变化的尝试，实际数据库对照发现后恢复原回调。原始不等价记录保留，验收只使用恢复原关系后的源码。

## 具体问题与避免方法

### 测试只清理了相互关联的一半登记状态

两个会话辅助入口结束时清空运行驱动登记，却遗留了对应静态定义。后续测试再走默认装配，程序正确拒绝了不一致的内置相机身份；单独跑其中一个文件时则未必遇到先前残留。修正只在原清理位置同时使用两个公开重置入口，并分别验证正常结束和异常结束后的下一次真实装配，保留身份校验。测试资源的隔离需要覆盖相互关联的状态，不能只清理最容易看到的一份字典。

### 把错误的展示形式当作错误是否交付的依据

一项日志副本测试仍寻找旧的整句文案，实际文件已按 JSONL 保存原异常。另一项把可读附注和完整异常图拼接后数关键词，将同一事实的两种表示误判为重复交付。现在分别核对错误类型、原消息、异常图、副本内容、标记抑制，以及两种表示各自的数量。重构时又曾按 JSON 首字段识别完整诊断，复核后改为解析内容，不依赖字段顺序或空格。错误是否重复应依据对应结果与诊断记录判断，不能仅按整段输出里某个词出现几次判断。

### 准备状态没有经过合法业务前态

一些清理测试直接创建“查询此前删除结果”的责任，却没有先发生过结果未知的删除。仓储接受了测试写入，不代表正常调用能形成这一状态。恢复资格、原票据和不重复派发的目标仍然有效，不能连同错误准备一起删除。

相机来源的准备现先经清理模块实际产生未知的删除和查询结果，耗尽预算并可靠结束前一清理项，再由后一清理项取得自己的查询票据。由此也暴露出原来的下一轮立即调用假设不成立；测试显式推进原有三秒间隔，并检查间隔内没有调用。以后先证明状态怎样由所属模块形成，再检查失败与恢复；尚未证明可达的组合单独保留待判断。修改和首次失败证据见[工作记录](integration-test-refactor-2026-10-26.md#最近验证结果)。

以下记录更新至 2026-10-31。它们总结测试设计、实现和验证中的经验；各项测试的最新通过数、耗时及生产问题仍以重构记录为准。

### 测试分类没有区分固定定义与真实运行资源

单元测试的资源边界按用途区分。随代码版本固定的状态编号、事件登记和错误码定义可以在加载模块时只读初始化；这类局部逻辑测试不应被描述为完全没有文件访问。用户数据、部署目录、真实数据库、网络、工作线程和子进程仍按真实协作边界分类。验证资源定位、文件缺失、发布内容或内容一致性本身属于集成；不能把这些目标借“固定定义”名义放入单元层。此边界已经用户确认，并由共享测试规则统一维护。

以后分类时，同时检查首次导入和测试执行两个阶段，并说明资源的实际用途。不能仅凭测试函数体没有文件操作就判定隔离成立，也不能仅凭加载过一份固定编号文件就判定整项属于集成。

### 故障替身没有真正命中目标操作

故障注入要证明实际命中。恢复诊断中的九个读取失败测试依赖旧 SQL 的列格式或探针前缀，生产查询改变后没有抛出预期异常。调用实际返回成功，测试仍期待回滚，因此断言失败；当时尚不能据此认定生产未处理读取错误。改造后按实际游标字段及原数据身份识别目标，断言命中次数、原异常、回滚后的完整状态与事务结束；不依赖 SQL 空格或列顺序。模拟注入的 SQLite 异常与数据库自身发生故障分别记录。

以后先证明原故障确实发生，再核对消费者怎样处理它。缺少这一证据时，先修测试准备，不把预期失败没有发生直接归为生产缺陷。

查询观察器也有同类问题：只把私有连接方法替换为 `sqlite3.connect`，仍可能依赖 URI 的固定拼写、`BEGIN` 字面量和 SQL 别名。后续改为解析只读文件身份、观察 SQLite 事务状态及实际读取的表列，并保留原分页和资源断言。数据库替换也改为真正替换同一路径的完整文件，先证明原游标有效，再核对跨实例后拒读与关闭；不再靠修改仓储对象的路径字段模拟替换。该阶段的限制和原始结果见[历史读取证据](verification-data/2026-10-26-integration-refactor/stage-11/README.md)。

故障范围也要限定。已发布文件的撤回测试曾对所有删除操作报错，连报告文件都被影响，结果出现与原交付无关的报告失败。修正时只拦截目标文件；以后按原文件或业务身份限定故障，并核对最终诊断来自预期操作。

媒体诊断还暴露了故障先后误读：最初期待“检查工具完成后，保存回执丢失”，实际却先发生文件任务冲突，工具尚未启动；只有退出收场形成的失败观察才命中保存故障。仅有一次故障命中和 `state_db_error` 不足以证明目标过程。复核按原键对齐日志和数据库，明确工具调用、实际保存阶段及主次错误；再统一所有时钟入口、撤掉保存故障，独立观察到后续修复阶段的同类文件冲突。两个发生窗口分别报告。

以后故障条件须限定目标阶段及原输入，保存实际命中的申请；先证明工具确实执行并形成目标结果，再声明结果保存的故障覆盖。临时诊断中未到达的断言也须审查：本次还发现一项不适用于普通 MP4 的额外输出检查预期，已经明确不作验收依据。前置真实失败可作为相应问题证据，但整条诊断不能因此算作正确且完整的回归用例。

机内照片改为拍摄时登记来源、实际取回时再确认字节后，旧测试仍在拍摄结束时要求完整摘要，并向已经不再调用的保存方法注入故障。这些失败首先说明测试停留在旧契约，不能直接证明拍摄或恢复有错。重构先区分相机上的原文件、拍摄工具顺带传回的缓存和用户最终取回的文件，再分别验证各自的保存、恢复与清理。参数只有在改变实际阶段或失败结果时才保留；文件归档没有数据库提交前后之分，相应重复参数应合并。

非法事件专项还需要一个成功对照：先证明公开仓储产生的完整提案能在同样的正式事务入口提交，再只删除一个角色或改坏配对，核对真实拒绝原因及整笔回滚。否则，一个本来就不合法的准备也会被拒绝，看似通过却没有验证目标守卫。

### 共享故障工具改变了真实仓储的配置

测试支持本身也需要独立反例。集中仓储故障注入时，首版工具在替身实例上执行原方法，会丢失实际仓储实例的读取批量等配置；按整个仓储类屏蔽再次进入，又会漏掉同类另一个方法的故障。独立评审发现后，转调保留实际实例、配置和状态，每个方法分别匹配。相同的 17 项局部测试在原工具上有 8 项失败，修订后全部通过；反例包含两个不同配置的仓储实例、跨方法调用、嵌套作用域和原异常。只验证替身收到调用，无法证明真实操作保持等价；支持工具的通过也不能代替其调用场景的组合验证。

以后引入共用支持时，检查它是否保留原对象、输入、配置、异常和资源责任。共享范围越大，越需要在批量接入前安排独立评审。原实现和修订后的同组反例见[第六批证据](verification-data/2026-10-26-integration-refactor/stage-6/README.md)。

### 重送断言没有证明真的发生了第二次保存

设备照片登记测试曾用 `all(call == first for call in calls)` 检查原申请复用。只有一次调用时，这个断言也会通过，无法证明恢复时真的重送了原申请。改造后分别记录失败轮与恢复轮：核对第一次事务是否已经提交，要求恢复轮新增至少一次保存，并比较完整申请、键与时刻，最终只有一份已提交结果。

同一次会话保留原申请，与关闭并重建数据库线程，是两种不同目标。原测试只要求同会话恢复时，不机械增加重启；声称冷恢复的场景则实际关闭旧线程并打开新线程。照片归档中断发生在文件已经归档之后，还要检查恢复没有替换文件；它不是一项数据库保存回执未知测试。具体见[设备照片测试](../../apps/camctl/tests/integration/capture/test_device_photo_flow.py)。

取消与工作文件测试还暴露了另一种差别：旧测试在保存错误后手动再次调用同一内部流程，而完整会话遇到必要数据库错误会进入收场并退出。后续新会话只能依据实际留下的持久事实恢复，不能据此声称同一内存拥有者重送了未保存的完整返回。此组覆盖仍在核对；原矩阵保留，先分别确定实际会话退出、同会话原结果责任和下一次运行的恢复目标。

### 选错入口，把下一步操作的错误当成原结果保存错误

清理恢复测试要求当前设备已经移除时，程序仍能保存此前 DELETE 的实际返回。直接调用单项删除入口后，原返回已经保存，但入口随后继续检查新 QUERY 的当前协作者并报错。若只看最后异常，就会误以为原结果保存依赖当前设备，甚至据此修改生产代码。

正式清理轮次先交接原结果，再判断是否允许新调用。测试改从这一入口进入，保留原申请、键、超时和间隔，并核对没有新设备调用。以后遇到失败，先说明此前已经完成哪些操作，再定位出错的具体步骤；分别核对原结果消费和新副作用的契约。该次错误入口记录保留为测试诊断，没有列为生产问题。

### 修改辅助函数时漏掉其他目录的调用者

工作文件清理重构曾删除 `_seed_repaired_artifact`，但另外四处测试仍使用它，其中两个模块在导入时就依赖它。修改者自己的两个文件通过，也不能阻止其他目录收集失败。修正时恢复原签名和返回格式，并明确该辅助函数只准备存储格式；完整业务场景通过真实录像停止、修复和产物登记产生来源。

以后修改共享准备前，查找全部实际导入与调用方，交代哪些继续兼容、哪些一起迁移。独立评审检查调用图，集成后验证完整被改文件及受影响调用者，不能只运行作者直接修改的文件。

公开接口新增必需输入时，也要同步核对所有实际调用者。本轮按导入绑定清点取消流程，发现多处测试仍未提供与原数据库匹配的临时文件目录。集中修正同类准备，能够避免下一轮逐文件重复遇到同一个缺参错误；静态调用点只用于定位，不等同于已经执行的失败用例。

### 等待任务结束，却丢掉了任务的错误

工作文件测试改用共享执行器后，只等待 `supervisor.drain_required()`，没有检查它返回的失败记录。等待结束不表示全部任务成功，原文件错误可能因此被测试吞掉。修正后提取并交付原异常；会话本身也有错误时，两份事实都保留，并增加真实任务接手、等待和失败的见证。

以后审查关闭代码时，分别确认任务已经结束、返回结果已经消费、原错误已经呈现。不能用“已经 await”代替这三项检查，也不能只检查没有剩余任务。相关例子见[清理会话测试](../../apps/camctl/tests/integration/bootstrap/test_cleanup_flow.py)。

测试自身的收场和证据写入也可能覆盖首异常：会话已经因生产代码缺少名称而退出，诊断 JSON 又因无法序列化该异常报错，最终只显示后一个错误。诊断产物应使用已有异常图保留类型、消息、堆栈及因果关系；已有首异常时，额外收场错误作为附注交付，没有首异常时则正常抛出。不能通过忽略收场错误或把所有对象转成字符串来掩盖问题。

### 把一次推进、历史分支或能力声明当成完整行为

OSMO 结果恢复测试曾要求一次处理调用既恢复旧票据又派发新一轮。正式处理允许分轮交接，测试现从相同公开入口等待实际新调用；原时钟、累计次数、重试间隔、旧页和最终动作结果保持。同步条件应说明业务操作实际发生了什么，不能固定内部推进轮数。

另一项读取测试把机会释放绑定到单独的历史分支，还要求 READ 尝试结果先保存。当前契约允许完整读取结束、源摘要核对后，在尝试结果尚待保存时释放设备。重构现核对完整结束引用、原票据、源和目标、轮次、实际字节、匹配摘要及后继授予顺序；尝试结果仍须真实成功，但不再照抄旧事件顺序。

判断并行能力时还要检查完整申请链，并区分操作先后。取回正在重试时已经持有相机批次，普通录像不能插入；录像先开始时，能否读取另一份完成文件由驱动声明决定。后一个分区仍被生产批次检查阻挡，因为该检查没有区分兼容录像与独占操作，已列入生产问题交接。

此次诊断曾只凭“拍摄占用时等待”就判为规格冲突，没有连读调度专题中“录像运行不等于独占设备”的明确解释，过早要求用户重新选择业务规则。以后先核对术语所指的实际状态、操作先后和驱动兼容声明，再判断是否矛盾；实现统一阻止了某类操作，不能反过来证明规格要求如此。有效测试揭示生产缺陷时保留失败和原行为目标，其他不依赖该缺陷的重构继续。

### 外层等待结束，却没有确认真实线程任务结束

日志扫描专项曾只观察会话协程或异步等待对象；它们结束或收到取消，不能独立证明线程池中排队或正在执行的目录扫描已经结束。后续观察改为在正式日志调用入口识别对应的真实线程池任务，等待该任务实际完成或可靠撤回后，再检查文件、锁和收场结果。[日志扫描测试](../../apps/camctl/tests/integration/bootstrap/test_startup_log_sweep.py)保留了这项见证。

取消的同步点也曾选错：测试等候日志收场入口，但数据库打开失败后的关闭仍被已满线程池阻挡，程序根本没有到达该入口。改为独立观察数据库工作线程已经退出后请求取消，才能区分“取消尚未送达”与“日志模块没有撤回”。这次发现的生产缺口由[工作记录](integration-test-refactor-2026-10-26.md#生产问题交接)维护；不能通过释放占池任务或改用空闲池使失败消失。

以后每个同步条件都说明它证明哪个实际阶段，并允许同一契约的合法实现提前完成；不要要求未来正确实现仍卡在当前错误步骤。跨线程用例分别核对外层等待、实际执行、结果交付和资源释放。

### 混淆调用失败与副作用未知

主机文件已经被删除，随后返回错误；紧接着检查文件是否仍存在时，也遇到错误。这说明本次调用失败，删除效果暂时不能可靠确认，不表示调用状态本身也必须是未知。测试一度混用这两个维度，给出了错误预期。

现在分别核对调用失败、效果未知、两个原始错误及后续独立查询取得的缺席事实。后续确认缺席不改写此前的失败。以后从实际发生的过程推导每个字段的含义，不用一个“失败”或“未知”概括整组状态。

### 误把完整异常图当成受限控制消息

同一个错误图和传输消息也有不同的边界。报告 worker 的完整异常图可以超过控制消息容量；正式实现会把完整图写到 stderr，并交付受限的回退消息。测试分别验证完整消息超限被拒、回退消息可以编码和解码，以及 stderr 仍有完整原图；不能把整份展开图误当成已交付控制消息，再随意扩大数值上限。

### 没有公开效果的内部字段被当作验收目标

原内部视图的某个字段没有公开可观察效果时，不能通过各读一次当前值和历史值就声称验证了二者的合并。保留有效的身份、历史来源及产物目标；需要证明类型回退或大小冲突时，用只有该输入不同的正反场景，观察实际资格和产物。纯内部对象形态单独记录退役依据，不给生产增加测试接口，也不在测试辅助函数中复制合并算法。

同样，直接填入内部等待结果，再制造所属动作未结束的组合，不能证明正常流程会进入该分支。当前仍有这类清理测试未完成迁移。处理前须说明原目标、合法路径与承接范围；不能仅因测试难改就删除，也不能为保留节点制造无效状态。

审查也不能反过来只靠关键词判断。`LocalWorkPort.required_settlements` 有正式会话调用契约；看到属性访问或名称含 `Runtime`，不足以判定违规。源码结构扫描用于找候选，最终按所属模块的契约和真实调用方判断。

### 迁移时悄悄改变时间和预算

两组新测试把原重试间隔改成零，下载清理组还改变了原票据超时；取消组又将原一秒或 1.25 秒的结果读取超时统一改为十秒。另有测试沿用共享工厂的默认时钟，导致实际保存时刻改变。测试虽然通过，经历的条件已经不同。

修正时恢复原次数、超时、间隔及时间依据，并检查实际请求和持久化事件。通过正式入口新增准备操作时，计划时间必须与测试时钟相容；不能只把旧数字塞回一个尚未到期的动作。以后逐项比较业务输入及实际数据库记录，区分必要准备变化和目标条件变化，不以节点数量相同代替等价性。

另一次时钟迁移让 39 条媒体事件由原固定时刻变成推进后的主时钟，完整节点仍然通过。原辅助函数捕获旧回调的行为没有被重构者识别。最终把主流程时间和媒体原发生时间分别由测试显式持有，保留原事实；不能看到两个对象都有“时钟”就统一成一个可变回调。跨次并发分派的自增编号先后也可能不同，对照应同时保留原始差异，并按真实业务责任核对预算、事件和结果，避免把身份顺序差异抹掉后宣称逐字段相同。

执行器登记前取消和登记后、执行前取消也有不同责任。后者还要证明已登记任务撤回及身份释放，不能因名称都含“排队”就合并。

### 装配字段被误当作最终保存的预算

共享时钟诊断曾根据运行对象的通用 START 配置，直接期待照片和延时摄影的开始调用也有三次机会。真实窄测有两项因此失败。对照原基线和保存的操作记录才确认，本批样本由正式入口冻结为一次、三十秒及空重试间隔；装配字段不能直接代表最终授予的预算。原诊断断言已经更正，原始失败按测试假设错误保留，没有登记为生产问题。

以后迁移准备时，同时核对配置输入、正式入口的适用规则和实际已保存的尝试。比较同一组场景的前后事实，分别保留每类消费者的次数、超时、间隔、票据和时刻；不能把新源码的观测值直接当作原行为，也不能从装配字段推断全部分区。其他长调用及录像的空间隔语义仍按各自契约判断。证据和适用范围见[共享时钟复核](integration-test-refactor-2026-10-26.md#已完成的主要改动)。

### 验证收据不能唯一对应实际源码

一批修正是在未提交状态下运行，收据只保存了此前的 HEAD，没有保存当时差异或源码摘要。日志能证明运行过新增节点，却不能证明最终提交与受测内容逐字相同。记录实际受测提交或当时差异，遇到这一明确的来源疑点时再安排必要验证和相关文件摘要；不能把纠正该缺项的专项办法变成每批常规测试的全量取证要求。

常规运行记录命令、工作目录、受测提交或实际差异和退出码，在已确认解释器与源码位置的环境中复用既有设置。出现错误导入、受测内容来源不清等具体疑点时，再增加实际模块路径或相关文件摘要核验。提交身份不能反向证明未记录的历史运行内容，也不因此要求每次测试都做全量取证。

分段历史阶段还发现，启动器把预期的工作区路径拼成 `import_path` 字段，并没有向解释器取得实际 `__file__`。原回执保留这一限制，补充检查单独记录；协调分支的新运行在预检解释器中实际导入模块并核对路径，同时明确预检不等于 pytest 内部观测。记录字段本身必须对应真实采集动作，不能把预期值写成测量值。

归档也会出现内容与说明不对应的问题。一个临时探针从两分区改成三分区后，早期运行只剩两项通过的收据，保存的源码却已是后续三分区版本；同一批归档还实际含有后续修正载荷，范围说明没有写清。摘要核验只能证明载荷字节保存完整，仍须逐组匹配执行源码和说明。本次补齐来源说明、标出早期源码缺失，并在下一批引用已有载荷，保留原始日志和压缩字节；以后每次运行就冻结诊断脚本，归档结束同时核对实际文件与清单语义。

静态调用调查曾在执行树推进后继续使用旧行位点，留下未核定候选；XML 又没有 `file` 属性，按该属性推断的文件计数为零，说明文字却写成已覆盖。后续改为从固定 Git 对象解析源码，并将 XML 的 `classname` 映射到真实模块路径，才核定 105 文件的保守组合清单。调查脚本自己的字段和结论也要相互核对，候选、命令所选文件与实际执行节点分别识别。

### 环境准备发生得太晚，或并行任务共享了临时目录

新工作区的部分测试在加载目录 `conftest.py` 时，就经导入链读取固定定义；资源同步的 `pytest_configure` 此时尚未执行，因此收集前已经报资源未登记。权威同步应在这一导入之前完成，隔离运行入口已经执行该准备。直接运行的新工作区也要先核对资源就绪；这类失败不算业务操作失败。

旧取消用例还直接调用了已经改成异步的初始化方法，却没有等待其完成，随后在进入目标断言前失败。迁移时先核对真实初始化顺序与异步返回，逐步确认目标操作已经执行；不能把这类准备错误统计为功能故障，或用内联执行替代真实数据库线程。

后续组合又发现历史回放测试的两处媒体准备漏掉 `await`，协程被当作媒体上下文，报告和回放尚未执行便报错。同一用例还创建了从未传给消费者的配置对象，无法据此证明配置变化的影响。修正等待后，删除未被消费的对象，并核对实际绑定检查、源文件打开和媒体工具没有重新执行；报告字节与原读取尝试断言保留，测试说明和名称改为这项实际目标。以后共享工厂变为异步时核对全部调用者，同时沿参数追踪所谓配置变化是否真正进入被测入口。

恢复开发容器后，还要核对解释器实际导入的源码路径。共享虚拟环境的可编辑安装可能指向另一个工作区；只记录当前 Git 提交不能证明运行了该提交。并行工作区也分别指定唯一的 pytest 临时根；默认临时目录的轮转曾删除其他组已经结束的数据库。源码、临时文件和证据保留分别核对，具体运行方式以[测试指南](../../apps/camctl/tests/AGENTS.md)为准。

本轮共享准备的持久化验证直接调用 pytest，容量节点因无法创建专属资源组而失败，被测容量业务尚未执行。随后改用既有 sudo 专属委派启动器，相同源码及原 513 项输入通过了真实合计预算核验。这里需要修正的是执行入口；原权限失败仍保留为环境记录。以后安排含容量节点的验证，启动前先核对所用入口是否提供了正式委派，不以无约束运行代替预算验收。委派父目录与实际业务叶组的限额也分别读取，避免把父目录的不限额误认为业务没有受限。

### 计时和内存观察混进了业务成本

有的历史增长测试同时启用 Python 分配追踪，以及每条 SQLite 指令都进入 Python 的计数回调；有的报告测试先经真实受理生成 4200 项来源。这些操作属于测试成本。当前整项耗时尚未将准备、目标执行和观察开销分开，不能直接据此判断瓶颈在 SQL 或生产算法。

以后保持原输入规模，分别测量准备、正式操作、核对及关闭；诊断工具的附加开销另行说明。Python 分配追踪只反映其计量范围，不代替整个程序及后代的预算验收。

来源测试额外要求 600 条输入比 20 条输入的 Python 内存峰值增加不到两百万字节，这个具体差值缺少需求依据。但原测试还有有效目标：同一份代码在批量参数固定时，不应因总数据量增加而持续积累内存。此次移除差值断言时只保留了分页和原键核实，连同有效的增长验证一起撤掉，判断不完整。整组预算仍由独立容量专项核验，来源路径的增长验证尚待合理重构；不能把分页检查通过当作内存增长目标已经完成。

时间汇总也要分清口径。例如同一次单元运行的 JUnit 套件时间为 150.120 秒，用例时间相加为 134.227 秒，进程墙钟为 153.088 秒；它们衡量不同范围，不能互相替代。多进程时间相加也不等于并行入口墙钟。原始口径见[第六批证据](verification-data/2026-10-26-integration-refactor/stage-6/README.md)。

后续对两个慢节点保留原规模和观察工具，实际拆出准备、目标、核对和关闭：4200 个动作的报告选择准备约 47.22 秒、选择读取约 0.51 秒；2048 个成员的历史准备约 72.81 秒、读取与快照准备约 12.07 秒。原先只看整项时间，会把昂贵来源准备错误归给被测查询。这里三次受理分别包含 3、4200、3 个动作；动作数、受理调用数、历史事务数和 SQL 调用数不能互相替代。计时补丁和原始输出已归档，明细及边界见[阶段记录](integration-test-refactor-2026-10-26.md#耗时与容量)。

完整只读样本原型证明，可以很快执行同一规模的历史读取；它同时移除了该节点实时生成上游数据的工作。消费者输入完整，不等于生产者仍在本次运行中受测。用户选择保留生成覆盖后，主测试将真实来源生成和固定样本读取分别验证：生成仍走原受理、调度和拍摄，读取使用独立完整样本。读取节点准备显著缩短，完整回归仍承担真实生成成本；最终收益按两类测试的总耗时比较。样本中的精确事务、事件数量用于核对该资产，实时生成验证依据业务结果和完整历史，避免把一次观测值变成长期业务合同。

### 只在核心大数据场景验证内存增长

内存增长测试用于核心、且已经明确预计会处理大量数据的场景，例如持续累积的历史读取或大量成员的来源解析。先说明预计增长的数据是什么、由哪个核心处理环节消费，以及随总量积累内存会造成什么影响，再选择少量代表场景验证。普通有限输入的功能检查，以及使用同一批量处理路径的等价参数分支，不重复铺设大规模增长矩阵，避免测试准备、测量和维护成本超过其发现问题的价值。

总量预算与增长趋势回答不同问题。整个程序及后代共享可配置的 2GiB 预算，用于限制实际运行的总内存；增长验证用于发现数据规模扩大后，程序是否仍把全部数据逐渐堆进内存。某个规模没有超过预算，不能证明内存不会线性增长；较窄的分页检查也不能代替实际内存观察。

选定场景后，保持同一份代码、单条数据的结构和大小以及每批处理量，逐步扩大总数据量，跨过相关分页或缓存边界，同时核对全部业务结果。数据准备和断言与被测处理分开计量，诊断工具的额外开销单独说明。判定依据应来自固定工作集、批量边界及整体预算等实际设计，不能任意增加每个模块的局部字节门槛，也不能仅凭两次采样就宣称已经证明任意规模有界。具体运行和计量范围遵守[内存预算测试](memory-budget-testing.md)。

### 调度和评审安排本身造成返工

协调者还出现过把提醒发送给已结束的子代理，却误以为工作已经开始的失误。任务安排应区分已经分配、实际执行和已经结束，结束后的新工作须重新触发；进度以执行回执和真实进程为依据，不能只凭消息已经发出。此类调度失误属于重构成本，不能归因于被测程序耗时。

报告替换的后续补强再次暴露了这一调度失误：普通消息已送达，已结束的子代理仍未执行；核对状态并重新触发后才完成。另一处协调失误是完整文件已经开跑，协调者才补查同节点的路径字段修改。保留首轮后，只对新增变化的独立节点补测，分别记录源码，最终再在集成点完整验证；没有为这个局部输入变化立即重复昂贵的 4200 动作准备。以后先核对任务状态及完整数据流，再交付一次可执行的任务范围。

协调者也曾把独立评审交给原作者。分配前须核对作者身份，自查与独立评审分别记录。分派实现任务时，明确原目标、失败与恢复分区及交付证据；发现同类问题反复出现时，补齐具体分类和反例，而不是重复发送原则。

一次归档校验器没有处理可为空的解析状态，报错后协调者仍继续了后面的归档集成。这违反了依赖顺序。修正校验器后已补核全部载荷、交叉引用和 Git 源码，原始证据没有改变；后续执行链须在前置校验非零退出时停止依赖动作，不能只因工具调用被放在同一脚本中就视为已建立成功条件。

一次首次清理评审中，协调者转述证据目录时漏写 `work-files-` 前缀，评审者因路径不存在而无法核验。修正绝对路径后原证据仍在；这属于交接错误，不能判断为测试失败或证据丢失。以后交付路径须实际读取，连同源码摘要和运行收据一起提供。

### 工具接口变化被误当成环境能力缺失

根目录 TypeScript 静态调查最初发现，当时使用的本地 AST（抽象语法树）接口未导出熟悉的 `createSourceFile`。进一步读取实际包的导出后，使用其现有项目与语法树接口完成六个 TS／MJS 文件解析；不能只因熟悉的函数缺失就改回文本搜索，或宣称没有解析器。C 文件另用编译器语法检查，其结果不冒充 C 语法树审查或真实执行。冻结来源及静态判定见[第八批证据](verification-data/2026-10-26-integration-refactor/stage-8/README.md#根非-python-边界静态审查)。

以后先核对本机安装版本和实际可调用接口，再选择工具；工具调查与业务测试结果分别报告。

## 持续记录方式

有新的可复用问题时，说明发生了什么、原因依据、怎样处理及如何避免。已有条目只补充新结论；没有新经验时不为重复运行另写复盘。未经核实的推测保留为待查。

多个实例同一首因合并说明，新的责任边界分别记录。复盘同时包含旧测试的问题与本次重构的失误，不能只归因于历史代码或生产程序。

[阶段记录](integration-test-refactor-2026-10-26.md)维护当前目标承接、运行结果、耗时与生产问题；本页维护原因和后续写法；[共享测试规则](../../.agents/rules/testing.md)维护通用要求；[测试指南](../../apps/camctl/tests/AGENTS.md)维护执行命令及隔离范围。新增经验需要成为长期要求时，修改对应权威文档，本页引用它，不另存一套规则清单。
