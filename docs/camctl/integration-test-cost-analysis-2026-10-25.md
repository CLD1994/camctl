# 集成测试耗时分析（2026-10-25）

当前最值得继续优化的是少数完整业务流程中重复启动客户端，以及部分测试自身的检查开销。最近一次完整回归仍是旧源码上的四路约 47 分钟；修复后源码还没有完整计时，不能把 47 分钟当作当前全量耗时。

本轮读取并重算已有逐项记录，并在 `fc3104424fd8ce64152cbdd6f1b4899d38e011e1` 的三个独立源码副本中各测一个现有用例。三项均通过。本轮只新增分析文档和测量材料，生产代码、现有测试及运行配置均未修改。

## 有哪些可用的耗时记录

“入口耗时”指从测试运行入口开始到结束，人实际等待的时间。“阶段累计”指多个测试各自的准备、执行和收场时间相加；这些测试可以同时运行，因此累计值不能直接当作人的等待时间。

| Hasselblad 照片专项，四路 | `8164851c` | 390.592 秒 | 29 项全部通过；已包含客户端会话复用及网页流程分组。 |

完整回归中另有 342 个嵌套子检查，它们已经包含在父测试耗时内，不再加时。44 个失败实例合计占 pytest 阶段时间的 10.01%，且只运行到失败处；修复后完成全部流程的成本可能不同。

## 完整回归的时间集中在哪里

旧全量的 camctl 组件集成有 9951 个实例，pytest 阶段累计 3898.999 秒；根目录跨组件集成只有 270 个实例，却累计 6865.820 秒，占全部 pytest 阶段的 63.78%。优化重点应由实际流程成本决定，不能只看用例数量。

下表四个文件共 56 个实例，占旧全量 pytest 阶段累计时间的 **45.49%**。它们都包含安装版命令、真实数据库、客户端或媒体交接等完整协作流程。

| 完整业务流程 | 实例数 | 阶段累计时间 | 占全部 pytest 阶段 |
| --- | ---: | ---: | ---: |
| Hasselblad 照片拍摄、取回及恢复 | 29 | 2118.073 秒 | 19.68% |
| OSMO 分段录像及交付 | 8 | 1018.498 秒 | 9.46% |
| 源文件清理及消费者隔离 | 11 | 1001.869 秒 | 9.31% |
| Action6 分段恢复及取回 | 8 | 758.159 秒 | 7.04% |

前 50 个单例占 52.83%，前 100 个占 67.00%。另外四项容量测试合计 587.958 秒，占 5.46%，涉及缓存溢出、磁盘缓存容量及固定批量下的内存增长。这些规模对应明确的验收边界，不能靠减少数据量消除耗时。

上述排名用于寻找责任流程。Hasselblad 和清理专项后来已经优化，不能继续把旧文件总时间当作当前成本或未来可节省量。

## 当前代码的三个分阶段样本

三个样本均使用独立的 `git archive` 源码副本、独立临时目录和 Python 字节码缓存，显式将 `PYTHONPATH` 绑定到副本。解释器为 Python 3.11.17，SQLite 3.53.1。不同样本存在同期负载，且外部计时包装有开销；本轮不把它们与旧全量作稳定提速对照，也不把三个入口耗时相加作为一批回归的耗时。

### 文件候选分页：测试强制回收内存占了一半时间

对象是 `outputs/test_read_discovery.py::test_candidate_capacity_tracks_batch_not_total`。测试逐页读取候选文件，删除本页后用弱引用检查这些对象是否已经释放，以证明读取不会一直保留旧页。

| 测量对象 | 次数 | 耗时 |
| --- | ---: | ---: |
| 整个入口 | 1 | 23.156 秒 |
| pytest 测试体 | 1 | 19.442 秒 |
| 测试主动执行完整内存回收 `gc.collect()` | 179 | 10.391 秒，占测试体 53.44% |
| 实际候选分页读取 | 179 | 0.196 秒 |
| 为新消费者建立真实文件领取记录 | 120 | 6.775 秒 |

这项测试的主要已知成本是每页都强制执行完整内存回收，而候选读取本身很短。三轮扫描已经共享按 12→120 递增建立的来源，不能再把同一来源共享列成新优化。

可以研究减少完整回收的次数，并继续逐页检查弱引用是否失效。实施时必须保留 120 个新消费者、批量上限 1 和 3、全部候选数量、游标数量、查询计划及扫描前后数据库不变的断言。是否能够完全取消逐页回收，仍需由改造后的原断言验证；本轮尚未实施。


### Action6：一次业务流程启动客户端 11 次

对象是 `test_installed_action6_native_required_photo_failure_keeps_reached_video_scope_and_waiters`。它验证照片检查失败后，已经找到的视频仍能交付给两个独立取回请求，并完成客户端导入和确认。

入口耗时 61.366 秒，pytest 准备阶段 16.980 秒，测试体 42.426 秒。测试体中调用真实客户端命令 11 次，每次均启动 Node 并打开客户端应用：

| 客户端操作 | 次数 | 完整命令耗时 |
| --- | ---: | ---: |
| 导出计划或确认 | 4 | 7.839 秒 |
| 导入报告 | 1 | 2.048 秒 |
| 逐份导入媒体 | 6 | 12.058 秒 |
| 合计 | 11 | 21.945 秒，占测试体 51.73% |

这些时间包含实际导入、导出及持久化，不能全部算作启动成本或可节省量。释放业务时钟后，等待来源和两个取回报告的区间为 10.941 秒；真实测试媒体生成仅为 0.561 秒。单就这个样本，没有证据把媒体编码列为首要瓶颈。

当前逐份媒体检查验证交付身份、文件字节、大小、摘要及上传后的验证状态，没有逐份验证客户端重启恢复。可以参考已经落地的 Hasselblad 方式，让同一业务场景复用真实客户端会话，同时保留六份独立上传、两份取回身份、报告导入与确认顺序。若要收敛已有的跨进程持久化见证，可以在全部媒体导入后实际关闭、重开一次，再核对媒体记录及关联并导出确认。具体覆盖映射与效果需要另行验证。

OSMO 的相似装配方式也值得检查；本轮只测了 Action6 这一个实例，不把同一比例推广到 OSMO 或其他 Action6 参数。


### 固定批量写入：主要成本在完成事务及其测量窗口

对象是 `persistence/test_segment_transaction_batches.py::test_fixed_batch_write_and_verification_have_bounded_residency`。测试分别准备 20、200、400 个真实文件，以固定批量 4 完成写入并再次核实，检查内存、读取批量和索引边界。

入口耗时 206.428 秒，测试体 202.709 秒。各规模记录如下：

| 文件数 | 准备完整数据 | 完成写入 | 再次核实 | 两个操作合计的 SQL 调用数 |
| --- | ---: | ---: | ---: | ---: |
| 20 | 1.434 秒 | 2.095 秒 | 0.290 秒 | 3880 |
| 200 | 8.962 秒 | 51.197 秒 | 5.966 秒 | 72227 |
| 400 | 13.572 秒 | 107.034 秒 | 11.676 秒 | 151958 |
| 合计 | 23.967 秒 | 160.326 秒 | 17.932 秒 | 228065 |

准备占测试体的 11.82%，完成写入占 79.09%，再次核实占 8.85%。准备内部的来源文件构造累计 6.819 秒，已经包含在 23.967 秒中；不能重复相加。

这项测试不能仅靠合并准备解决主要成本。两个目标操作同时处在 `tracemalloc`（内存分配跟踪）窗口内，还使用测试连接包装计数 SQL 和读取行；因此表中耗时是业务操作与这些测量工具共同作用的结果，不能直接称为正常生产延迟，也尚不能判断其中有多少可由测试侧消除。

后续已完成同一冻结 200 份输入的开关对照：不开内存跟踪时写入与核对约 9～10 秒，开启后约 38～48 秒；另一个仅开启现有阶段计量的样本确认，9.292 秒写入主要用于事件生成、校验依据构造及独立检查，SQL 写入阶段约 0.052 秒。原页重复解释及测量边界见[固定批量写入深入分析](integration-test-batch-write-cost-2026-10-25.md)。三个规模、真实完整事务、固定批量、原结果核实及内存增长断言仍须保留；本轮没有改动该实现。


## 为什么增加并行数不一定解决问题

旧完整回归的 84 个任务墙钟合计 11036.698 秒，四个任务槽的占用率为 **97.84%**。这里统计的是任务槽是否有工作，不是 CPU 利用率；任务等待子进程或设备替身时也占用槽位。

假定所有任务耗时保持不变，四路理想下界为 2759.174 秒，比实际入口只少 **60.986 秒**。因此仅重新排序，无法把这轮 47 分钟缩短很多。

已有同一源码 `8164851c` 的 Hasselblad 并行专项：

| 并行数 | 入口耗时 | 结果 |
| --- | ---: | --- |
| 4 | 390.592 秒 | 29 项通过 |
| 6 | 527.968 秒 | 28 项通过、1 项失败 |
| 8 | 542.515 秒 | 24 项通过、5 项失败 |

每档只有一次，分片数量、安装和客户端构建份数也随并行数变化。现有证据支持继续使用默认四路，不能据此宣称固定的硬件最优值，也不能把失败和变慢直接归因于 CPU 或磁盘饱和。

排程仍有独立的小问题：运行器继续读取最早的逐项 CSV，其中提前失败的测试被估得很短。例如修复定向组合最后一个 Hasselblad 参数任务估计 4.019 秒，实际 113.802 秒，导致其他任务槽最后空闲。该组合占用率为 89.38%，按实际耗时重排的离线模拟约有一分钟空间。更新排程输入有价值，但不会替代减少任务本身的重复工作。

## 准备成本还有哪些不确定性

旧全量的 pytest 任务墙钟合计，比 pytest 各阶段合计多 262.179 秒，约为可比任务总成本的 2.38%。这个差额包含源码及环境副本、解释器启动、收集、观察记录和进程收场等，不能全部称为安装。明确独立记录的资源同步和客户端构建合计仅 30.793 秒。另一方面，测试体内部的建库、拍摄和客户端启动会计入执行阶段，因此也不能据此断言所有准备都很便宜。

运行器为每个任务复制完整冻结源码；本轮开始时追踪文件约 77.56 MB，其中验证数据约 47.90 MB，占 61.76%。重复复制历史证据确有可查的工作量，但这是静态体积，不是实测 I/O 或耗时。应先分别记录快照、任务副本、缓存副本、资源同步和收集，再判断是否值得调整副本范围。调整前必须核对测试对文档和资源的实际依赖，并保持源码身份和隔离保证。

组件内部还保留以下待测边界：

| 对象 | 已确认执行的工作 | 当前缺少的测量 |
| --- | --- | --- |
| 历史选择的 4096 候选容量测试 | 真实受理 4206 个动作并生成 128 个无关产物，然后才安装查询探针 | 受理、产物准备、首次选择与后续分页各自的耗时 |
| 256／2048 文件的大历史测试 | 真实保存 18 页结果及 4608 次文件归属、完成事实 | 当前源码下的来源构造、历史读取和快照准备占比 |
| bootstrap 产品矩阵 | 静态核对为 14 个库、42 次 CLI 调用；wheel 在模块级准备 | 安装、各次命令及业务等待的分别耗时；目录总时间不能全部归为打包 |
| capture 与 outputs 的慢完整流程 | 包含真实事务、发布、等待和取回；部分来源已经共享 | 当前每次准备与目标操作的分别耗时，不能沿用优化前比例 |

五个空来源消费者仍有从五次准备归并为两类来源的静态候选，但旧记录总共只有 2.132 秒。它的收益有限，不应先为此增加复杂的备份恢复机制。

## 下一步顺序

1. 优先研究 Action6／OSMO 真实客户端按业务场景复用。先从已测的 Action6 单例建立逐份交付与持久化覆盖映射，再测相同实例的启动次数及阶段耗时。
2. 调整候选分页测试中的完整内存回收频率，保留原逐页释放及容量断言。这是本轮最明确、范围最小的测试自身开销。
3. 补测容量测试中的测量工具成本，并拆分历史容量用例的准备与实际查询。保留规模与真实提交；依据数据决定测试侧还能减少哪些工作。
4. 更新排程使用的成功耗时，并补齐运行器准备阶段计时。执行上述测试侧改造后，再用同一冻结源码、默认四路进行完整计时，记录全部结果；最终以该轮入口耗时判断总体效果。

Hasselblad 会话复用及网页代表分组、清理只读来源共享、取消矩阵合并、outputs 六次来源拍摄减少为三次、220 成员历史世界合并、协议解析复用和安装命令共享等均已落地。本轮不把它们再次计入未来收益。当前没有足够证据把其他用例直接删除，也不把未执行的容量覆盖算作优化后的通过。

## 计时边界

全量与修复组合的 UTC 起止跨度和原单调计时分别相差 16.270 秒、33.705 秒，原因尚未查明。本文入口耗时、累计耗时和槽位占用计算均使用原单调值；不把 UTC 差额解释为已知的环境故障或额外执行成本。
