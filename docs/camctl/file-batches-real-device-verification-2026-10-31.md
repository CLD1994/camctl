## 权限与连接

连接时 `/dev/bus/usb/001/004` 为 `root:root`、权限 `0664`。仅将此实际哈苏节点的组归属改为 `plugdev`，保留权限位；运行账户属于该组。普通账户的 `hb_cli --pid 0x000a list` 和 `info` 随后均退出 0，确认唯一机身及预期序列号。该调整作用于本次节点；USB 重新枚举后的权限须重新核对。

前两张在取回开始前完成，因此其设备读取不能依赖固定等待者缓存；第三张供已等待的两个取回复用同步副本。该安排同时见证真实下载与纯本地读取。

三次精确路径 DELETE 均退出 1，工具返回 `camErrDbusCallFailure`。后续九次 `images` 均退出 0，包含 3FR、JPEG 及多空格对齐的真实响应通过格式解析；没有再出现原列表格式拒绝。查询仍不能确认原捕获路径的文件状态，保存 `file_presence_unconfirmed`，随后耗尽各自有限预算。

六个原图、预览清理项最终均失败，报告为 `cleanup_items_failed`，逐项保留 `file_query_attempts_exhausted`。本次确认清理等待、调用互斥及失败收场，未确认物理删除成功；不将 `/SSD/...` 与捕获返回路径中的同名文件视为同一定位。

## 下载取消发现的既有缺陷

取消验证先使用独立 RAW 来源 S4。设置均正常返回，但 `capture` 退出 1，返回 `camErrDbusCallFailure`；来源保存为未确认失败，没有重放该 START，也没有产生可用于取消验证的正式产物。

另一个独立 JPEG 来源 S5 成功。其执行前，可用性检查成功核对并释放了此前未知活动；这不改变 S4 的原失败结果。S5 完成后，新请求 Ocancel 沿设备来源实际下载。下载开始后，通过正式 `cancel_task` 请求 Xcancel 取消 Ocancel。

该场景未通过。下载正常返回，取消在段保存前生效，可靠段保存被跳过。copy 7 的 `source_size=2240512`、`committed_bytes=0`；原 READ run 24、尝试 1 仍未取得结束结果。代码将“源会话位置已到末尾”当作“可靠副本进度完整”，申请的 `READ_END` 声明完整进度，被现有守卫以“读取结束与当前轮次、来源或可靠进度不一致”拒绝。会话随后以 `state_db_error` 结束；取消动作和原取回仍为运行中，批次 4 保留取得事件 540，没有释放。

与 `a3fc8c24` 比较，该结束判据、可靠进度守卫及取消续接函数均未在批次提交中修改，属于既有缺陷。后续修复须分别处理“源已结束但可靠进度未满且动作取消”与“可靠副本已经完整”：保存原实际结束和原票据，沿取消流程结束原尝试；只有可靠进度完整时才能建立完整副本的 `READ_END`。不得补造进度、放宽守卫或直接清除批次。仅修改完整标志不足以接通 EOF 且无读取错误的取消分支；还须核对部分停止、完整提交后取消、保存未知及重启接续。

本次只定位并记录该缺陷，没有修改生产代码。取消后的独立取回没有执行。
