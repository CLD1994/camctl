# 合计内存预算测试结果

当前开发环境已完成真实合计预算验收：513 项固定批量持久化用例在 2GiB 限额下通过，内存与交换空间合计峰值为 **36,081,664 字节，约 34.41MiB**，没有内存不足或触限事件。严格无交换运行能力另行验证。本轮只改测试、开发脚本及文档，没有修改生产代码、生产配置、协议或依赖，也没有执行全量集成回归。

目标、参数和计量口径由[内存预算测试说明](memory-budget-testing.md)维护，进度见[实施计划](../superpowers/plans/2026-10-25-memory-budget-testing.md)。

## 环境与执行边界

实测使用 Linux WSL2 5.15.167.4、Python 3.11.17、SQLite 3.53.1 和 memory v1 控制器，宿主启用了 4GiB 交换空间。启动器通过 sudo 创建本次独占委派目录，pytest、CLI、host 和容量工作进程继续以普通用户运行；记录的调用 UID 为 1002。宿主交换设置与已有资源组没有调整。

每次被测运行独立设置内存限额和内存加交换空间合计限额，两者均回读确认。合计峰值读取内核的同一累计计数器。pytest、输入准备和最终断言在组外；原生产入口及其全部后代在专属叶组内。组外准备对共享文件缓存归属的影响仍遵守测试说明的计量边界。

直接组件 pytest、根跨组件 pytest 及隔离运行器使用同一插件和配置。正常终止信号仍由被测程序处理；测试被中断时，pytest 会话结束阶段也会恢复待完成收据。所有真实运行的叶组与本次委派目录均已删除，清理收据没有错误。

## 513 项容量结果与耗时

父测试准备 513 项输入，跨过五个原结果页，关闭数据库连接后启动独立业务进程。业务进程以批量 4 执行真实完成写入、原操作核实、同键重试，再分别新增三条文件摘要记录并核实原操作。父测试重开数据库核对全部产物字段、范围绑定和历史记录；最终 513 项原片产物完整，重试没有重复写入，后续记录没有改变原操作结果。

| 阶段 | 实测耗时 |
| --- | ---: |
| 资源预检 | 0.001 秒 |
| 输入与数据库准备 | 13.35 秒 |
| 受限业务进程，包含启动和资源收场 | 37.04 秒 |
| 父测试核对完整结果 | 2.98 秒 |
| pytest 整轮 | 53.94 秒 |
| 包含 sudo 委派与清理的入口墙钟 | 54.51 秒 |

受限业务进程中的分项如下。各分项不包含全部导入、连接和退出开销，不能直接当作进程总时间。

| 业务操作 | 实测耗时 |
| --- | ---: |
| 首次完成写入 | 23.02 秒 |
| 首次核实原操作 | 2.68 秒 |
| 同键重试 | 2.69 秒 |

当前样本中，首次写入占业务进程时间约 62%；原操作的核实与重试也有可见开销。这个分阶段计时没有细分 SQL、解析或对象构造，不能据此将全部时间归因给数据库调用。容量用例已移出逐次对象分配追踪，但本轮没有同规模、同环境的改造前对照，因此不计算提速比例。


## 定向验证结果

| 检查范围 | 结果 | pytest 耗时 |
| --- | --- | ---: |
| 执行器、共享入口、sudo 委派、收据恢复及组件插件加载 | 127 项通过，另有 8 个子检查通过；两个真实专项在下行独立执行。 | 3.62 秒 |
| 隔离集成运行器 | 13 项通过，另有 2 个子检查通过。 | 17.90 秒 |
| 小规模独立业务、预检优先及业务结果不完整的拒绝检查 | 7 项通过。 | 3.68 秒 |
| 129 项跨页读取及索引边界 | 1 项通过。 | 11.35 秒 |
| 64MiB 真实进程树与合计超限专项 | 2 项通过。 | 0.35 秒 |
| 513 项真实容量 | 1 项通过。 | 53.94 秒 |
| 真实 CLI 初始化、运行及 C host 发布与领取 | 5 项通过。 | 36.66 秒 |

以上去重后为 **156 项定向检查及 10 个子检查通过**。表内子检查属于对应主用例，不另算 pytest 节点。仅收集测试的入口检查不计入通过数；早期执行器复核与最终组合重复的用例也不重复计算。

64MiB 专项先分别验证 24MiB 和 48MiB 分配能够单独完成，再让父进程保留 24MiB、子进程申请 48MiB。子进程被内核终止后，父进程故意返回 0；执行器仍从累计内存不足事件发现失败并保存证据，合计峰值为 64MiB。该预期失败被测试正确捕获，专项通过。另一个专项确认父、子、孙三个进程正常收场。

真实 CLI／host 的五项检查共保存 15 份进程预算收据，最高合计峰值为 93,224,960 字节，约 88.91MiB，均无内存不足事件，全部叶组已删除。host 持有的 PID、进程组、标准流、默认部署路径和原等待窗口保持原测试语义；由外层读取的待完成收据也完成了恢复与清理。

运行中发现的组件 pytest 参数加载缺口已修复：组件根配置按实际注册状态加载共享插件。实际容量节点已重新通过不显式加载插件的参数解析与收集；从仓库根、组件目录、混合目标及递归入口的协作检查均通过。这处修复没有改变已完成容量运行的后端或业务路径，实际容量验收使用的是同一插件。

独立只读评审已核对控制器、sudo 委派、CLI／host 接缝、容量断言及中断恢复，当前没有未解决的实质发现。源码审计确认相对本轮基线的生产目录、生产配置、协议和依赖差异为空。

## 证据与验收边界

实际两个限额均为 2,147,483,648 字节，合计峰值 36,081,664 字节，内存不足及两个触限计数均为 0；进程退出 0，叶组已删除。

两次运行未进入负载：一次测试文件名错误，一次组件插件未加载。前者由正确目标验证替代，后者已修复并核验；它们不计为已执行容量失败，也不计入通过数。此前环境受限的历史记录保持原样，本页当前结论以本轮真实资源证据为准。

本轮只证明已运行负载符合合计预算。513 项与同库三条后续记录覆盖分页、缓存及历史增长的明确边界，不能证明任意数据量、多次新动作或长期完整会话均符合预算。严格无交换业务运行、更大规模与长期负载、目标 ARM64 环境仍须分别验证；不能从本轮结果推导这些结论。
