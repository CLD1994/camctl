# Hasselblad 未知活动后的无人值守恢复

[Hasselblad 驱动](hasselblad-driver.md) · [相机恢复](../architecture/camera-recovery.md) · [操作与设备字段](database/operation-fields.md) · [软件验证依据](hasselblad-availability-preconditions-2026-10-28.md)

## 目标与责任范围

Hasselblad 拍摄调用异常结束后，camctl 可能已经把原动作记为失败，却仍然不知道相机是否结束了那次拍摄。原活动因此保存为 `UNKNOWN`，并以 `HELD` 阻止同机后续工作。无人值守部署需要在相机重新可通信后继续处理有效计划，同时准确保留旧拍摄的未知结果。

本专题定义独立的设备可用性检查，以及检查成功后解除旧调度限制的规则。后续拍摄和 DEVICE 正式源的读取共用这条路径；HOST 正式源的本地处理继续独立推进。原动作、原调用、原工作文件和正式产物各自保持原生命周期。

| 本专题完整定义的内容 | 沿用的共同契约 |
| --- | --- |
| 检查适用条件、固定机身身份、检查责任、多个旧活动、释放依据、触发工作与检查的共同处理 | [动作调度与时间](../architecture/scheduling-execution.md)、[拍摄提前准备](../superpowers/specs/2026-10-25-capture-preparation-design.md) |
| 新事实的存储关系、原子释放、重启恢复及独立守卫 | [公共存储规则](database/common.md)、[事务与回放](../architecture/system-foundations.md#事务投影与回放)、[操作尝试](database/operation-fields.md) |
| 两种正式源如何接入恢复、失败如何交付给原工作 | [Hasselblad 文件契约](hasselblad-driver.md)、[取回](../architecture/obtaining-outputs.md)、[文件拷贝](../architecture/file-copy.md) |
| 此能力的联合验收和部署边界 | [软件验证](verification.md)、[显式初始化](../architecture/initialization.md)、[设备执行报告](../architecture/report-format.md#动作结束后设备是否仍在执行) |

设备检查不会执行供电操作。供电周期由部署侧管理；camctl 在有效业务需要设备时尝试检查，并按有限预算处理失败。当前开发结构可以直接演进，本能力不以旧程序读写、旧格式适配或旧库迁移为实现前提。既有现场数据的保留与部署选择见[现场环境](#现场环境与待执行计划)。

## 运行假设与事实边界

Hasselblad 在满足下列全部条件时，允许后续工作重新使用机身：原本地设备调用已经完成适用收场；当前产品标识下恰有一台匹配相机；实际读取的 serial 与原固定机身身份相符；新的 `doctor` 调用完整、正常地返回 `doctor: PASS`；本专题规定的其余资源条件成立。

这是一项可用性运行假设。[工具契约](../hardware/hasselblad/hb_cli.md#首次运行)中的 PASS 表示 USB、相机联机握手和基础参数通信正常，不证明发生过断电或重启，也不证明旧拍摄已经结束、成功或形成完整文件。物理机身在检查后仍可能失去通信；后续真实调用继续按自己的结果和有限处理规则执行。

| 对象 | 保存的事实及检查后的含义 |
| --- | --- |
| 原动作 | 保留原失败终态及错误，不再次执行原拍摄。 |
| 原 START 尝试 | 保留原实际结果，或者依据原收场边界保存的未知结果。新的检查结果不替换它。 |
| 原活动 `activity_state` | 保持 `UNKNOWN`；检查不产生 `ENDED` 或采集完成依据。 |
| 原活动 `occupancy_state` | 表示 camctl 对冲突工作施加的调度限制。满足本专题的释放条件后，从 `HELD` 变为 `RELEASED`。 |
| 新检查 | 保存当前身份、每条实际工具调用、完整结果、采用的运行假设及释放关联。 |
| 原文件 | 原工作文件继续保留；已登记正式产物保持原身份、内容依据和独立取回资格。 |
| 原动作报告 | 仍提供 `device_execution.status: end_unconfirmed`。新检查不清除原采集错误。 |

一次成功检查只处理该责任固定的旧限制。已经解除的限制是持久化的调度事实，不是一个永久有效的“设备在线”缓存。后来新拍摄再次留下未知活动时，新的活动重新持有限制，并使用新的检查责任。没有未解决限制时，普通拍摄和读取不额外周期运行 doctor。

本路径只适用于 Hasselblad 单张拍摄的任务独占归属方式 `TASK_SCOPE`。其他设备的停止、活动查询、软件重启、时间与产物完成及公共目录范围责任继续遵守各自契约。

## 原机身身份的固定与核对

逻辑绑定继续使用原 `device_id` 和 `driver_id`。首次建立 Hasselblad 活动并预留设备、或者建立尚无新活动的恢复检查时，在调用意图之前保存本次采用的 serial 和产品标识。它们表达准备操作的目标机身，属于预期身份；不能因为已经写入数据库就称为实际观察。

实际 `list`、`info` 返回形成另一项观察事实。只有真实响应满足驱动契约时才能记录已核对身份。旧 START 结果遗失时可以仍然没有旧身份观察；恢复检查使用调用前已经固定的预期身份，并保存自己取得的新观察，不要求补造旧响应。

设备资源身份由驱动标识和固定 serial 确定，产品标识用于核对工具选择范围。用于查询的资源键按驱动确定的规范编码派生，与固定身份共同验证，不独立修改。当前配置中的同一物理机身不能同时绑定多个逻辑设备；设备资源检查还须识别与未完成原责任相同的物理身份，不能通过改用另一个逻辑设备名绕过原限制。

| 身份情况 | 处理 |
| --- | --- |
| 原逻辑绑定仍存在，当前 serial、产品标识与原固定身份一致 | 可以继续核对实际设备及其他资格。工具可执行文件路径使用本次运行配置。 |
| 原逻辑设备缺失、驱动改变，或当前 serial、产品标识与原固定身份不一致 | 保存对应的绑定失败，不运行针对替代机身的检查，不解除原限制。 |
| 另一逻辑设备指向仍有原未完成责任的同一物理机身 | 按绑定冲突处理，不取得第二份设备执行资格。 |
| `list` 可靠返回零台或多台匹配相机 | 保存本次实际结果，检查不通过；不按列表顺序选择一台。 |
| `info` 的实际 serial 与原固定值不一致 | 保存身份不符，检查不通过；不继续 doctor 或下载。 |
| 必需固定身份缺失、历史关系矛盾或读取失败 | 按状态库错误处理，不从当前配置补齐原事实。 |

Hasselblad DEVICE 正式源在登记时，把已由可靠拍摄结果核对的机身身份固定到驱动文件身份和定位信息。后续读取同时检查原逻辑绑定、原机身、原图名称或路径、读取种类、大小及 SHA-256。重新配置相机不能把旧照片解释为新机身上的同名文件。

HOST 正式源已经是主机文件，其归档、读取、报告及适用清理不需要当前相机配置或在线身份。

## 触发工作与检查目标

检查由尚有资格的实际工作触发。新拍摄在[提前准备区间](../superpowers/specs/2026-10-25-capture-preparation-design.md#提前量和设备资格)内，可以在创建自己的准备活动之前触发检查；检查不使动作提前进入 `running`，不消耗 START 次数，也不提前创建照片文件责任。真正 START 仍须位于原启动窗口内。

DEVICE 读取在来源已确定、确实还需要设备字节、所属工作允许读取时触发检查。调度器必须在授予 READ 机会之前发现这项需要，不能让旧 `HELD` 把读取候选永久挡在检查入口之外。相机源读取的资格与完成情况仍由原拷贝责任决定。

以下表按从上到下的顺序分类；较早分区成立时不进入后续分区。

| 当前事实 | 调度结果 |
| --- | --- |
| 所需历史不可读、矛盾或原保存结果未知 | 先核实原状态或结束依赖该状态的会话处理，不创建检查。 |
| 触发工作已终态、取消生效、尚未到自己的允许时间，或拍摄窗口已结束 | 按原工作规则等待或结束，不创建新检查。 |
| 存在尚未交付的原调用结果、活动中的本地设备调用、未结束的读取会话或冲突文件操作 | 先完成原拥有者的结果交付与实际收场，不运行 doctor。 |
| 已有正常准备、START、可靠 `ACTIVE` 活动、其他设备操作或不适用本路径的输出范围限制 | 按对应持有者和冲突规则处理，不使用本检查解除它们。 |
| 本触发动作针对目标已有检查责任 | 复用原责任、目标和次数；按其实际阶段等待、推进或采用已保存结论，不换检查身份。 |
| 同一设备有其他触发动作的检查责任，但没有尚待收场的尝试或保存 | 按[检查之间的调度](#检查等待与拍摄优先级)选择工作；排队中的检查不自动占有设备执行资格。 |
| 没有阻挡该工作的旧限制 | 直接回到普通准备或读取调度，不为形式运行 doctor。 |
| 全部阻挡活动均为原动作已经失败、可能产生过启动效果的 Hasselblad `UNKNOWN + HELD`，原身份一致，任务工作目录相互隔离，且前述条件均已满足 | 固定检查目标并创建或复用有限检查责任。 |

旧动作尚未完成普通处理时，先沿原责任完成结果保存、有限核实及终态判断。检查不能把“未完成的原责任”转换成“已失败的可恢复旧活动”。原成功结果已保存、仅归档或登记未完成时，继续原文件流程，不进入新的恢复拍摄。

一次检查固定同一设备当前全部合格的阻挡活动。目标以独立关联记录保存，逐项关联原活动，不把清单放入不断增长的 JSON。目标集合创建后不增删；新活动不能被后来加入已经取得 PASS 的集合。读取完整目标集合和当前冲突事实时使用有界分页，不能只检查一条记录或将多个旧未知活动误判为多个正常准备持有者。

## 检查责任、共享与有限预算

检查的业务拥有者是触发动作。一次检查可以为该动作对同一设备的多份读取工作解除同一批限制，因此 original、preview 和同设备其他候选共享已经建立的检查，不分别复制预算。检查记录保存首次触发的工作关联；每个依赖者仍按自己的当前来源和资格决定是否执行。

同一触发动作针对同一旧活动只能把它纳入一项检查责任。调度重入、候选分页、文件顺序变化、原请求重送和进程重启都复用这项关联。某检查已经耗尽而其目标仍持有限制时，后来发现的同动作读取项使用该失败结论，不通过缩小目标集合或更换检查 ID 获得新次数。

新的触发动作拥有自己的有限检查责任。某动作先前的检查已经成功解除旧限制，随后另一次拍摄产生了新的未知活动时，该动作仍有资格的后续读取也可以针对新活动建立新责任；新责任不能再次纳入已经检查过的原活动来刷新预算。已经失败的动作或读取项不会因此重新打开。

读取检查等待重试时，合格拍摄可以按共同调度建立自己的检查。两项责任可以关联同一旧活动，分别保存所属动作和累计次数；它们不合并、转移预算，也不同时取得实际执行资格。新的责任只在其触发工作被正常调度选中时建立，不能为所有排队动作预先建立检查以轮流绕过间隔。原读取检查对其他读取候选的先后关系继续保持。

检查沿公共操作状态推进，终态不重新打开。单次工具调用的成功与整项责任完成分别判断：取得 PASS 但没有满足事务内释放条件，不等于责任成功。

| 检查责任阶段 | operation_runs 的状态及结论 |
| --- | --- |
| 已固定目标，尚未登记第一次尝试 | `PENDING`；只有仍具资格时才能登记意图。 |
| 尝试正在执行、原结果正在交付，或允许在有限间隔后重试 | `ACTIVE`；失败的单次尝试不自动结束整项责任。 |
| 固定目标均已按本次可用性检查或其他可靠依据解除限制 | `SUCCEEDED`；历史分别说明实际释放依据，没有额外调用时不补造 PASS。 |
| 有限处理结束，实际失败或释放前提不成立 | `FAILED`；保存原因，不释放尚未解决的目标。 |
| 有限处理结束，最后所需调用或检查结果仍无法确认 | `UNCONFIRMED`；保留真实未知及必要独立收场。 |
| 触发工作取消，原结果已处理且没有足以完成本责任的合格结果 | `CANCELED`；实际尝试中的错误继续保留。 |
| 触发拍摄过期，原结果已处理且没有足以完成本责任的合格结果 | `EXPIRED`；允许保留已用次数，不退还已提交的尝试。 |

触发动作可以先进入自己的终态，但检查的结果选择须消费已经开始的原调用。合格结果在取消或过期后仍能完成原批释放时，检查记录其自身的成功，触发动作的终态保持；不能先把检查随动作强制终结，再用迟到结果改写检查终态。

次数、重试间隔及单次期限统一来自原目标设备的[query 配置](../architecture/configuration.md#状态查询与产物核实的配置)。它们只是执行参数来源；检查使用独立操作种类 `CHECK_DEVICE_AVAILABILITY`，拥有自己的累计次数，不属于 `QUERY_ACTIVITY` 的五种用途，也不改变 Hasselblad 的活动查询能力。

| 事件或条件 | 次数与后续处理 |
| --- | --- |
| 新尝试意图可靠提交 | 累计次数增加一次，保存本次实际上限、间隔和期限；三条工具命令共用这一次尝试。 |
| 只是在排队、等待其他资源、等待重试间隔或重复收到唤醒 | 不增加次数，不产生虚构调用结果。 |
| 已提交意图后可靠确认未派发 | 保存未派发事实，已经登记的次数不退还。 |
| 任一步失败、超时、输出不完整、身份不符或中断后结果未知 | 本次次数已经消耗；先收场，再按剩余额度及触发资格判断是否重试。 |
| 重启时存在开放责任 | 继续原累计次数；没有可靠原结果的尝试不能再获得完整正常等待期限。 |
| 后续会话改变 query 配置 | 新增尝试采用当次值并保存依据；原次数和事实保持，提高上限不重开终态责任。 |
| 次数耗尽且没有可接受的释放结果 | 结束本检查，并使仍依赖该限制的触发工作按[失败规则](#失败结果与诊断)结束。 |

重试沿[原间隔责任](database/waiting.md#重试责任的完整转换)使用单调钟。会话重启不能把原单调钟数值当作连续时间；按既有规则重新承担尚未完成的间隔，不退还次数。间隔不提供设备执行资格。

有合格触发工作时，正常会话推进该有限责任及必要等待。没有触发者、触发者已经结束且没有在途调用或保存时，不为旧活动启动后台健康轮询，不为了下一次可能的供电持续保持会话。部署人员依据实际上电时间调整现有检查参数和拍摄提前量；默认参数不保证覆盖任意供电周期。

## 单次检查的驱动契约

每次尝试按 `list → info → doctor` 顺序执行。所有工具经现有受管进程入口启动，使用已保存的目标产品标识。每一步必须取得实际退出及完整双流事实；后一条命令只在前一条通过其完整分类后派发。驱动内部不重试，也不运行设置、对焦、拍摄、下载或关机命令。

整次尝试共用一个单调钟期限。每条工具调用只获得剩余时间；输出片段不刷新期限。正常结果等待结束后，必要的进程终止、双流收集及结果交付继续按受管进程契约收场，不能把超过正常等待期限解释为本地执行已经结束。

| 实际返回 | 检查结论 |
| --- | --- |
| 唯一匹配相机、serial 相符，doctor 按工具契约明确返回 PASS；各步骤正常退出且输出完整 | 得到本次可用性观察，可以进入事务内释放判定。 |
| PASS 文本伴随非零退出、信号退出、超时、输出丢失或截断 | 检查不通过，保留真实调用事实。 |
| 输出不能可靠解析、只有相似文本、出现矛盾的 PASS/FAIL、明确 FAIL | 检查不通过，不推测相机空闲。 |
| 工具未能启动 | 保存实际启动异常，不补造退出状态或空双流。 |
| 调用取消且受管进程已经收场 | 保存真实取消及已取得的输出，检查未完成；原拥有者继续处理取消交付。 |
| 尚不能确认工具或输出读取任务已经结束 | 保留未完成调用责任，不开始下一条命令、下一次尝试或冲突设备工作。 |

本次观察应完整关联预期身份、实际身份、调用步骤及实际返回时刻。驱动只报告事实和可用性结论，不直接修改数据库、释放活动或替调度器承诺后续拍摄成功。

## 资源互斥与共同调度

同一机身一次只允许一个检查尝试持有实际执行资格。资格随尝试意图共同保存，保持到该尝试的调用、输出读取、原结果保存及必要收场全部完成；在此期间，其他检查、准备、START、设备查询、停止及 DEVICE 读取不能与它交错。`list → info → doctor` 是一次完整尝试，命令之间的空隙不提供交接机会。HOST 本地读取、报告以及其他设备工作继续按原规则执行。

开放的检查责任与正在执行的检查尝试分别判断。一次尝试结束后的重试间隔保留原责任、目标、次数和等待事实，不保留实际设备执行资格。同机可以有等待中的读取检查和拍摄检查，守卫不能仅凭另一项流程为 `PENDING` 或 `ACTIVE` 就认定相机仍有在途调用。

新的检查不得抢占正在收场的 READ。已经开始的一次读取或检查只因到时拍摄出现而不主动中止，先按自身期限、取消及收场规则保存完整结果，再重新选择工作。尚未开始的读取重试按[拍摄协调](../architecture/file-copy.md#自动预览读取与拍摄协调)让位；原文件对其他文件的拷贝顺序保留，与实际调用的执行资格分别处理，不能用清除原保留或重建拷贝实现让路。

### 检查等待与拍摄优先级

拍摄在启动窗口内，或者虽未到计划时间但除待解决旧限制外已经满足[普通提前准备资格](../superpowers/specs/2026-10-25-capture-preparation-design.md#提前量和设备资格)时，按原拍摄选择顺序参与调度。进入提前区间本身不授予抢占权；已有拍摄、准备及正常规则要求尊重的保留仍优先。可用性检查尚未授予 READ 机会，不因此替读取创造一份新的普通拷贝保留。

下表在核实状态库和原事务可靠后按顺序判断。拍摄的取消、原窗口和其他资源条件同时适用，不能因为读取已让位就省略。

| 当前阶段与竞争条件 | 必须执行的处理 |
| --- | --- |
| 原检查的工具已经派发，组合尚未完成，或原 READ、输出任务、结果保存仍在收场 | 原拥有者继续完成本次尝试；其他工作等待。到时拍摄不能插入剩余工具之间，也不能取得第二份执行资格。 |
| 原检查意图已提交，工具可靠尚未派发，派发前复查发现已有按正常规则优先的拍摄 | 保存可靠未派发及让位原因，先完成原尝试保存和资格解除，再选择拍摄。已提交次数不退还；让位不补造工具失败，也不把原责任写为取消。保存后已经无剩余次数且目标仍未解决时，按原有限失败规则结束。 |
| 原尝试已完成并可靠保存合格释放结果 | 消费该结果并完成目标释放；重新比较当前拍摄和读取候选。读取触发的检查成功不保证读取先于到时拍摄。 |
| 已有正常拍摄、准备持有者或其他必须优先完成的设备责任 | 继续原持有者；等待中的检查保留自身事实，不派发新的尝试。 |
| 读取检查正在等待或准备重试，拍摄已按既有准备或到时规则被选中 | 暂缓读取检查。拍摄复用自己的检查；尚无检查时按固定目标创建，沿自己的次数和间隔推进。不能把读取检查尚未届满的间隔当作拍摄自己的间隔，也不能缩短原读取间隔。 |
| 拍摄仅进入提前区间，但尚不满足正常准备条件或被已有保留阻挡 | 不凭提前时间抢占。原读取检查仍按自身条件判断；实际读取保留与准备资格沿原规则处理。 |
| 没有可优先推进的拍摄，原读取检查仍有资格，原间隔已完成且有剩余次数 | 沿原检查身份登记下一次尝试；其他读取不能通过新建检查越过它。 |
| 原读取检查的间隔未完成，或者其他独立资源条件仍未满足 | 保留实际等待，不派发、不增加次数；相机没有在途检查不等于读取已取得执行资格。 |

让位期间，原重试计时按[既有等待转换](database/waiting.md#重试责任的完整转换)继续。间隔已经完成时，即使拍摄尚未结束，也可靠清除已经完成的间隔责任；读取之后因拍摄占用等待，不再重复计满一段间隔。重启时标记仍为 1 的责任按既有规则重新承担间隔，标记为 0 时不补造等待；累计次数始终保持。

调度器同时发现原检查的重试时点、拍摄准备时间、计划时间、窗口结束、取消及资源变化。不能让一个等待重试的协程独占设备，或者只在其间隔到达后才发现到时拍摄。控制候选的发现须包含因旧未知限制而尚未建立新活动的拍摄，不能只查询已经拥有新活动的动作。

### 交接后的结果与责任

| 后续可靠事实 | 原读取检查和读取工作的处理 |
| --- | --- |
| 拍摄检查或其他可靠路径已解除原读取检查的全部固定目标，原读取检查仍开放 | 沿真实释放引用将原检查结束为 `SUCCEEDED`，不新增检查尝试，不补造其自己的 PASS；清除不再需要的重试等待。然后按当前拍摄、来源和读取资格重新调度。 |
| 只解决部分固定目标 | 逐项复用已解决事实，保留原完整目标和次数；其余目标仍须满足本路径，不能因另一项检查成功就整体放行。 |
| 拍摄检查失败、耗尽、取消或过期，旧目标仍未解除 | 拍摄及其检查按自身规则结束。原读取检查不继承该失败，也不刷新预算；其他阻挡消失后，沿自身尚未完成的间隔和剩余次数继续。 |
| 原读取工作在让位期间取消或终态 | 处理其原尝试及保存后结束自身检查，不影响拍摄检查的拥有者、次数和结果；不再为原读取追加尝试。 |
| 原读取检查或读取项已经失败、取消或过期，后来旧目标才被解除 | 保留原终态，不改判成功或重新打开已结束项。其他仍具资格的工作按当前真实资源事实继续。 |
| 拍摄解除旧目标后又产生新的未知活动 | 原读取检查只解释自己的旧目标；真正读取仍受新活动阻挡，按新目标建立适用责任，不复用旧 PASS。 |
| 任何交接、释放或终结的提交结果未知 | 先按原键核实事务；旧执行资格未可靠解除前，不向另一责任派发工具。 |

多个检查关联同一活动时，释放只发生一次。每次尝试登记和派发前，以及消费结果时，独立守卫都重新读取完整目标、实际在途拥有者、当前优先候选、取消和时间资格。优先级约束下一次派发；后来出现更优先候选，不拒绝保存已经开始的原调用结果，也不撤销其合格释放依据。另一检查已解决目标时，尚未登记意图的责任直接按事实完成；已有意图而可靠未派发的责任先保存未派发事实，不再调用工具。已经派发的原尝试仍完整收场，不丢弃真实结果。重送、迟到通知和并发唤醒沿原操作键核实，不重复计数、释放或运行相同尝试。

同一设备的检查尝试执行资格、准备或启动持有者、实际读取调用按相互冲突关系核对；等待中的检查、读取顺序保留和旧未知活动可以有各自多项记录。实现不得把这些未完成责任都解释为正在执行，也不能因没有实际调用就忽略正常候选顺序和保留。

以下入口必须从同一完整数据库边界取得资源事实，并分别独立判断提案是否合格：

- 检查责任创建、检查尝试意图及实际工具派发。
- 拍摄准备预留、PREPARE_CAPTURE、START 意图及实际驱动派发。
- DEVICE 读取候选规划、读取机会授予、READ 意图及实际打开读取。
- 原调用结果消费、检查终结及占用释放。

守卫可以共享内核拥有的事实读取，但不能直接采信调度器传入的“允许执行”。检查释放的目标必须在保存结果时再次核对；迟到通知只唤醒检查，不得清除新活动或新读取的归属。设备锁定和唤醒从持久责任及实际拥有者推导，不依赖不可恢复的“已经 doctor 过”内存标记。

部署继续采用一台主机、同一机身由一个受控执行环境管理的边界。数据库内的限制和进程内资格不能协调另一个独立状态库、其他相机软件或人工工具的同时操作；切换验证环境前须完成原环境的实际进程收场。

## 数据与事件模型

现有 `device_activities` 继续保存原活动及占用。为可用性释放增加独立依据引用；采集完成字段只表达原拍摄的完成事实。以下表名和新增内部字段名是实现建议，身份关系、保存时点及合法状态是必须满足的契约。

| 记录 | 必须保存的内容及关系 |
| --- | --- |
| 原活动的固定机身信息 | 逻辑绑定从原动作取得；调用前固定预期 serial、产品标识及规范资源键。驱动专属小型身份正文可以使用有明确格式的 JSON；用于身份查询的资源键使用普通列，严格从该正文派生。实际观察保存在对应调用结果。 |
| `device_availability_checks` | 稳定检查 ID、触发动作、首次触发工作关联、固定原设备身份、采用的可用性规则及版本、目标固定时的历史边界，以及唯一操作流程关联。身份字段创建后固定。流程状态和计数由 operation_runs 保存，不再复制一套。 |
| `device_availability_targets` | 检查与每项原活动的固定关联。目标同属一台原机身；同一触发动作与原活动的组合唯一。关联创建后固定，可以有多行，不能用第一项代表全部。 |
| `operation_runs` | 新增 `CHECK_DEVICE_AVAILABILITY`，指向唯一检查记录；`action_id` 是触发动作。责任键由检查 ID 确定，例如 `availability/<check_id>`。其他操作目标列不用于冒充旧活动查询或 READ。 |
| `operation_attempts` | 复用意图、累计尝试序号、实际配置、结果、错误、收场证据及原结果事件引用。新检查证据使用独立类型；调用返回不被标成旧采集效果。 |
| 原活动的释放引用 | 例如 `availability_release_attempt_id`，初始为空；按本路径释放时填写本次可靠成功检查尝试。只能与 `HELD → RELEASED` 共同建立，随后保持；后续真实结束观察不删除这项历史来源。 |

新的操作种类、内部枚举、结构约束和事件分支在[统一登记](database/enum-registry.json)及[事件登记](database/event-transitions.json)中维护；SQL、运行代码和检查器从这些权威定义取得编号。不为本功能分配另一套独立编号，也不以可空 JSON 绕过必要关系。

### 活动与释放依据的合法组合

| 状态与依据 | 合法性与意义 |
| --- | --- |
| `UNKNOWN + HELD`，释放引用为空 | 仍有未解决的调度限制；不说明相机实际仍在拍摄。 |
| `UNKNOWN + RELEASED`，引用适用成功检查 | 原活动结束未知，但已按可用性策略解除限制。 |
| `UNKNOWN + RELEASED`，没有上述引用 | 必须满足原有可靠未派发、无效果或时间与全部产物完成规则；不能任意接受。 |
| `ACTIVE + HELD` | 保持原活动执行事实，本路径不适用。 |
| `ACTIVE + RELEASED`，试图用 doctor 作为依据 | 拒绝。doctor 不覆盖可靠进行中的活动观察。 |
| `ENDED + HELD` | 允许；原输出范围等限制尚未解除时继续保持。 |
| `ENDED + RELEASED` | 按正常释放依据或已保存的可用性释放历史解释；后来确认结束不改写过去的释放原因。 |

行内约束防止无必要依据的 RELEASED，并显式处理 SQL NULL；外键保证引用存在。跨表守卫还须确认：尝试确属该检查、该活动在固定目标中、原绑定和规则适用、实际观察合格、原调用与保存已收场、没有其他冲突、输出范围允许解除。具有合法编号或非空外键本身不能证明这些条件。

Hasselblad 的旧工作目录仍属于旧活动。检查不删除目录、不建立空的正式产物集合，不把临时文件登记为成功结果。采用公共目录基准比较的活动继续受原范围契约限制，本检查不给它们提供范围完成事实。

### 原子保存与历史归属

检查创建事务共同保存检查记录、完整目标关联和原操作流程。首次尝试事务共同保存意图、实际参数、增加后的次数及执行资格。事务提交前不得派发依赖该意图的命令。

取得完整可接受结果后，在一个业务事务中保存原尝试结果、检查终结和所有仍需解除的目标限制。释放事件引用同一成功尝试及可用性规则，只改变 occupancy 和对应依据引用；活动状态、采集判定、动作终态、原错误和文件记录保持原值。

保存时重新读取全部固定目标和当前资源事实。已按其他可靠依据释放的目标不再修改；全部目标已经解决时，可以结束检查且不增加设备调用。若某项仍有阻挡事实且不满足本路径，实际 PASS 仍保存为本次观察，但不生成本批释放事件；检查以适用的失败或未确认结论结束，等待或执行原责任不能被改造成新的许可。不能只释放一部分后将整批标成已解决。

检查创建、尝试及终结归触发动作的自身历史；检查和目标关系随该动作的历史、快照恢复，不因新增物理表而另建历史快照对象。每项旧活动的占用及依据变化归其原动作。一次事务可以包含多个事件，但所有事件在完整事务边界共同可见。相同活动状态下取得新的恢复依据，由检查结果事件表达，不依靠没有行变化的伪造活动观察。

占用变化属于内部管理事实。它没有改变原动作的公开设备执行情况，因此不单独推进该动作的公开变化水位；触发动作或读取项失败则按实际公开影响登记报告变化。完整回放、快照恢复和当前投影逆向恢复必须还原相同检查、次数、目标关联与释放引用，不调用设备、不读取当前配置或时钟重判旧结论。

## 中断、原结果与重启恢复

检查通过现有原调用拥有者交付结果。每个实际返回及其完整保存申请只有一个拥有者；主循环恢复与原协程同时推进时，共同等待同一保存任务。某个等待者取消不能丢弃原错误、双流或已经开始的保存。

| 中断位置或恢复事实 | 必须执行的处理 |
| --- | --- |
| 创建或意图事务尚未提交且已确认回滚 | 没有新责任或新次数，未派发工具；以后按实际资格重新判断。 |
| 意图已提交，可靠证据确认工具未开始 | 保存未派发结果，保留已用次数。 |
| 原工具仍在运行、输出读取未结束或保存仍未交付 | 沿原拥有者完成收场，不开始新检查或冲突工作。 |
| 原结果已经由拥有者持有，保存失败或回执未知 | 保留完整输入及操作键；先核实原保存，不再次调用 doctor。 |
| 重启后只有意图、没有可靠结果 | 先取得适用的本地执行收场边界和原历史范围；成立后把原尝试记为结果未知，次数不退还。不从日志中的 PASS 文本补写可用性成功。 |
| 已有可靠检查结果及释放事务 | 复用整项已提交结果，不重放检查，不重复释放。 |
| 实际 PASS 尚未与释放共同提交就失去进程 | 保持旧限制；缺少持久结果时按上一未确认分区恢复，后续尝试取得新的完整观察。 |
| 释放提交成功、通知丢失或尚未授予后续工作 | 启动恢复和正常候选发现读取已提交状态，继续普通调度。 |
| 数据库提交或回滚结果未知 | 先按原稳定身份核实完整事务，停止依赖该结果的新设备调用；不能另建检查或直接修改投影。 |

本地收场证明只涉及主机上的原执行。`HOST_LOCAL_SETTLED` 等适用边界不能被解释为相机已经重启；本检查也不使用软件重启责任中的 `boot_id` 变化来构造不存在的证据。

终态检查仍可能有未交付的实际调用或保存，恢复发现不能只查询开放流程。必要收场结束后才释放检查自身的执行资格；旧活动是否释放则取决于已经可靠保存的业务结果。

## 取消、窗口与结果竞争

| 触发工作发生变化的时点 | 检查与后续工作 |
| --- | --- |
| 尚未创建责任或派发新尝试，取消生效或拍摄过期 | 不开始新尝试；按原动作或读取取消规则结束。 |
| 意图已经提交，实际派发前资格失效 | 保存可靠未派发事实，保留次数，不派发工具。 |
| 某条工具已经执行，取消生效 | 通过受管入口停止适用本地调用，完成实际退出及双流交付；不派发剩余工具或后续尝试。 |
| 检查已经执行，拍摄窗口届满 | 不增加新尝试；已开始调用完成有界收场及结果保存。没有 START 或待核实启动效果时，触发拍摄按实际窗口事实过期。 |
| 完整合格结果已经取得，随后触发工作取消、过期或结束 | 可以保存本次真实结果，并在其余释放条件成立时完成原批限制解除；触发工作保持自身终态，不执行后续拍摄或读取。 |
| 本次结果尚不完整，触发工作结束 | 保存已有事实和终结结论，保持旧限制，不追加尝试。 |

检查不改变 Hasselblad 的拍摄取消边界。真正 START 已经开始或可能开始后，按原单张契约处理，不因还有 doctor 功能就允许重发或强行取消原拍摄。动作、操作流程和本地调用的结束可以发生在不同时点，必须分别保存。

## HOST 与 DEVICE 正式源的完整路径

### HOST 正式源

可靠拍摄结果已保存时，主机文件的归档、正式登记、取回和报告沿原文件身份继续，相机离线不阻止这些本地工作。未知拍摄的工作文件继续保留；文件存在、大小稳定或后来 doctor 成功均不能补成原拍摄成功。

本地拷贝不申请相机读取机会，也不触发可用性检查。需要同机执行的新拍摄仍须处理实际旧限制。两条路径可以在各自资源允许的范围内独立推进。

### DEVICE 正式源

1. 取回按原来源规则选择已经登记的正式产物，并建立自己的 delivery 和拷贝责任。恢复检查不会从未知工作目录生成新产物。
2. 读取候选发现设备受旧未知活动阻挡时，进入共同检查入口。新检查不提前授予 READ 机会，不增加 READ 次数；同动作对同一批目标共享检查。
3. 限制可靠解除后，重新核对原来源、取消、清理保护、读取机会和普通拍摄优先级，沿原 `copy_id` 创建或恢复 READ。
4. 驱动每次打开读取时核对固定原机身，下载指定原图或缩略图，以拍摄时固定的完整大小和 SHA-256 核验。新的下载内容不能重新定义原摘要。
5. 核验通过后，按原可靠进度提供指定偏移起的字节；主机交付沿既有分段持久化和重拷规则继续。工具需要重新下载整片，不改变已经提交的交付进度。
6. 成功、失败、超时及取消都先完成实际下载进程、文件句柄和原结果交付，再按原 READ 责任回收临时副本。不能以清除下载目录代替调用收场。

检查不通过时，本次尚未发生的读取保持零新增 READ 尝试。检查预算耗尽后，受影响的当前读取项明确失败，其他设备和 HOST 项继续，取回动作按原部分成功规则汇总。源文件不被写成缺席、损坏或已删除；未来新的独立取回仍有自己的机会。

若 READ 原来已经派发且结果或下载目录尚未收场，先恢复这个 READ，不能用 doctor 为它重新分配票据或重置读取预算。读取途中后来产生新的设备限制时，先按普通资源交接完成原读取收场，再处理新的检查需要。

## 失败结果与诊断

绑定错误、检查未能确认可用、原拍摄结果未知、读取内容不符、数据库故障和正常取消分别表达。检查没有发送 START 时，新拍摄不能报告 `capture_result_unconfirmed`；这项错误仍只说明原拍摄自己的未知结果。

本能力新增 `device_availability_unconfirmed`，用于拍摄准备未能确认设备可用，stage 为 `execution`；新增 `source_device_unavailable`，用于 DEVICE 来源读取未能取得设备可用性，stage 为 `source_read`。两者的详情保存 `device_id`、`operation_run_id`、`attempts_used` 和 `max_attempts`，表达具体设备、检查及实际有限处理依据。前者可以用于合法受理但尚未开始的拍摄失败，后者用于对应的逐项读取或交付失败，取回动作仍按既有部分失败规则汇总。

完整机器定义由 [workflow-codes.json](../../protocol/errors/workflow-codes.json)维护，实施时与动作状态约束、逐项失败及报告消费共同接入；数字编号、详情类型和必填约束在该权威登记中分配，不在代码中临时拼装未登记错误。检查未取得可接受依据这一结论不等于相机已损坏或源文件不存在。

| 失败位置 | 对外业务结果与内部保留 |
| --- | --- |
| 拍摄前检查有限结束仍不可用 | 动作失败，保留尚未开始的执行标记；没有 START 尝试和照片文件责任。保存检查身份及有限次数，原活动继续 HELD。 |
| DEVICE 读取前检查有限结束仍不可用 | 本次相关交付或取回项失败，保留原产物身份及源文件事实；不伪称 READ 次数耗尽。 |
| 当前配置不能满足原固定身份 | 按[设备绑定失败契约](../architecture/configuration.md#设备绑定异常的影响范围)处理；尚未开始的单张拍摄在准备阶段直接保存绑定失败，执行标记保持 0，不为该失败创建新活动或发起调用。已有活动及在途调用继续按原责任处理，不调用替代机身。 |
| 检查开始后发生工具或解析错误 | 检查尝试保存原原因和已完成前序；是否重试由剩余次数与资格决定。 |
| 后续下载内容不符或下载失败 | 沿 READ 自己的错误和预算处理，已经完成的可用性释放不被改写为失败。 |
| 原状态不可读、事务失败或提交未知 | 按状态库或会话故障处理，不转换为普通设备不可用并继续派发。 |

已有终态和生效取消优先；尚未 START 的拍摄已经超过窗口时按实际过期原因结束。准备期间允许“合法受理、尚未开始、执行准备失败”的状态，不能为了获得写入资格把动作提前标成 running。公共报告只提供稳定业务错误和必要关联，不输出工具路径、原始双流或内部调用清单。

每个实际错误按[全局诊断责任](../architecture/logging.md#全局错误诊断责任)交给结果消费者一次。诊断保留设备、触发动作、检查、尝试、目标活动及适用文件关联，保留实际阶段、原异常图、退出、超时、输出完整性及双流。重复保存、恢复和多个等待者共用原诊断状态；新的实际失败产生新的诊断。必要停止和原结果交付不等待日志队列空位，日志错误不覆盖原设备错误。

## 现场环境与待执行计划

新环境通过正常 `init` 创建当前完整结构，当前结构、枚举、事件和快照资格共同登记。程序在使用已有状态库之前核对格式及结构；不支持的库明确拒绝，不隐式改表、修改格式标志或重建空库。本能力不增加旧格式运行模式，也不要求为了开发验收维护一套旧事件适配机制。

现有现场数据库、日志、工作文件、正式产物、交付、客户端状态和待执行计划分别保留。代码的兼容性整理不授予删除、改写或重新执行这些对象的权限。全仓既有兼容代码的整理是独立工作，不属于本能力的实施范围。

| 部署方式 | 必须满足的条件与验收含义 |
| --- | --- |
| 保留旧环境，使用独立目录和新状态库验收 | 原环境及其文件保持，原设备进程已收场；新旧环境不能同时控制同一机身。新请求具有新身份，新库不继承旧计划和确认水位。验收证明新环境中的流程，不声称已恢复原现场动作。 |
| 要求新程序继续原实例、原计划、原文件关系及原确认进度 | 单独制定并执行一次离线状态转换，包含备份、原历史解释、身份与文件核对、完整性检查及失败恢复；在完成该工作前不能宣称原实例已经接续。它不要求在日常程序中永久保留旧格式分支。 |

新库不会自动接续旧待执行计划。重新安排工作之前，部署人员须逐项核对原动作是否已经执行、是否存在未知效果、窗口是否仍有效、来源产物和客户端状态怎样关联。已过期计划不通过延长原时间或重用原请求身份获得新拍摄机会；需要新的业务工作时创建新的明确请求。旧环境在新环境接管设备后保持停止，避免之后再次执行同一业务。

新环境的未知活动验收必须通过受控的真实软件入口和工具替身形成。真机联调采用另行明确的操作步骤；不通过直接修改数据库标志制造“恢复成功”，也不为验证删除现场原文件。实际断电、相机恢复所需时间、真实 doctor 与拍摄或下载的行为属于设备验收。

## 实施责任与联合验收

以下模块划分是依据现有代码的实现建议。实现可以调整内部组织，但必须一次贯通拍摄与 DEVICE 读取，并保留共同的资源和事务边界。

| 责任 | 主要实现边界 |
| --- | --- |
| 身份与独立检查 | Hasselblad 驱动、准备凭据、正式源文件身份、设备注册和装配。 |
| 有限检查及原结果拥有者 | operations 的种类、目标、尝试、结果、重试及本地恢复；共享设备恢复协调入口。 |
| 调度与互斥 | scheduling/resources、拍摄准备及 START、outputs/dispatch、读取候选和机会授予、实际派发再检查。 |
| 持久化与历史 | operations/capture/outputs 仓储、检查与目标关系、SQL、统一枚举、事件守卫、历史对象和快照范围。 |
| 业务失败及报告 | 公共错误登记、动作和逐项状态组合、公开报告映射及固定边界重建。 |
| 交付 | 当前结构的新环境初始化、包资源同步、配置说明和既有真机环境部署脚本的适用核对。 |

软件测试通过公开函数、对象、仓储事务、CLI 或文件契约执行。真实 SQLite、文件、受管进程及组件组合属于集成测试；设备侧使用受实际工具接口约束的替身。不得用直接 UPDATE 活动状态代替业务链验收，也不得通过恢复被删除的私有装配接口使旧测试表面通过。

| 编号 | 必须取得的可观察结果 |
| --- | --- |
| HA-01 原责任先收场 | START 结果遗失后，沿真实执行收场边界恢复原尝试；原身份、工作文件和未知结果保持，旧拍摄不重放。原调用仍活跃、原保存未确认或边界缺失时，doctor 和后续拍摄均为零次。 |
| HA-02 完整检查分类 | 唯一设备与匹配 serial 后才执行 doctor；零台、多台、身份变化、解析失败、FAIL、含 PASS 的非零退出、输出不完整和超时均不释放。总期限覆盖完整检查；原始双流和实际退出保留。 |
| HA-03 原子释放与报告 | 检查成功与所有目标释放共同提交，旧活动保持 UNKNOWN、旧动作和文件保持；真实报告仍为 end_unconfirmed。任一目标不合格、错误引用和伪造结论不能部分放行。 |
| HA-04 多活动与共享预算 | 多个旧活动一次固定；同动作多个文件共享检查；重复发现、不同候选顺序和重启不刷新次数。耗尽后的同目标不换身份，新业务及新的未知活动按各自规则处理。 |
| HA-05 并发与其他设备 | 按下述交错矩阵覆盖检查等待、拍摄资格、尝试派发和结果保存，证明同机互斥、读取让位及原责任继续；独立事务守卫拒绝越过实际持有者或正常优先候选。其他机身与 HOST 工作继续，其他驱动的停止和公共范围限制保持。 |
| HA-06 取消与窗口 | 在创建、意图提交、工具派发、完整返回和释放提交的两侧取消或推进时间；保存原结果、次数和实际退出，后续不发 START 或 READ。合格迟到结果可释放旧限制，但不重开触发工作。 |
| HA-07 故障与历史 | 每个事务边界覆盖回滚、提交未知、进程中断和通知丢失；原键重送不再运行设备。完整回放、快照正向恢复和投影逆向恢复一致；固定历史报告字节保持，回放零设备调用。 |
| HA-08 HOST 路径 | 原结果未知的工作文件保持；原成功结果的归档、登记和独立取回在相机离线时完成，不申请相机机会。 |
| HA-09 DEVICE 路径 | RAW/JPEG 的 original/preview 经检查解除阻挡后实际下载、验证原摘要、续传并发布；两次独立取回保持源身份。下载错误、内容不符、无设备、多设备和身份改变保留实际失败。 |
| HA-10 DEVICE 失败与取消 | 检查耗尽不消耗未发生的 READ、不改写源存在性；其他项继续。真实下载超时或取消先终止工具、关闭文件、保存原结果，再清理临时目录；跨运行沿原票据和预算恢复。 |
| HA-11 诊断与关闭 | 每个实际错误交付一次，重送不重复；队列满载、取消和保存失败下，必要收场仍能推进。工具忽略 SIGTERM 时，核对既有升级终止与实际退出路径；仍不能确认收场时保留责任且不派发冲突调用。终态后的未完成调用被发现并结束，有限失败不会使会话永久轮询。 |
| HA-12 当前结构与环境隔离 | 新库包含完整结构和事件约束，不支持的现场库保持原内容并明确拒绝。新旧环境不同时操作设备；验收记录分别陈述软件、安装版和真机范围。 |

HA-05 使用可控时间和明确的派发、返回、保存同步点，通过公开调度与事务入口验证以下交错；不能只验证纯选择函数的返回值。

| 交错场景 | 必须观察到的结果 |
| --- | --- |
| 读取检查失败并进入间隔；拍摄先进入提前区间，随后到达计划时间 | 分别核对提前准备尚不合格、提前准备已合格和到时拍摄三种分区。只有正常选中的拍摄推进自己的检查；原读取 ID、目标、次数及拷贝顺序保持，原间隔不重置或缩短，没有新增 READ。 |
| 拍摄被选中与读取重试计时结束同时发生，或任意次序唤醒两个拥有者 | 事务与派发守卫选择同一个合格执行者；没有两项工具重叠。只等待的责任零新增次数，已提交但可靠未派发的次数保留且无工具调用。 |
| 拍摄到时分别发生在读取检查的 list、info、doctor 内及命令间隙 | 原完整检查先完成实际收场与保存，拍摄不插入、不主动取消它；随后按真实结果和当前窗口选择。窗口不延长。 |
| 两项检查关联同一批旧活动，拍摄检查取得 PASS 并提交释放 | 活动仅释放一次，旧状态仍为 UNKNOWN；等待的读取检查无额外 doctor、无新增次数而按真实引用完成。再交错两边通知、结果重送及进程重启，结果仍相同。 |
| 拍摄检查失败耗尽、取消或窗口结束；另行覆盖原读取检查取消或已经耗尽 | 各责任保留各自终态、次数和原错误；未终态读取按自己的剩余预算恢复，已终态读取不重开。取消一方不停止另一方已经开始的调用。 |
| 拍摄占用跨过原读取间隔，分别在间隔清除和交接提交两侧中断 | 恢复保持原责任和实际已用次数，按真实等待标记处理；提交未知先核实，未确认原收场时零新派发。 |
| 拍摄释放旧目标后形成新的未知活动，或仅部分旧目标由其他路径解决 | 不重复检查已解决的旧批次，不用旧 PASS 放行当前读取；保留未解决目标，新的活动沿自己的责任检查。 |

前置软件实验只证明其实际覆盖的底层能力和现有行为，记录见[设计前验证](hasselblad-availability-preconditions-2026-10-28.md)。尤其 HA-01 的安装版缺失 START 恢复在前置实验中没有进入目标恢复，必须通过公开入口重新建立并取得实际证据；其完成是本能力联合验收的一部分。设备检查 PASS 也不代替该项原责任恢复证明。
