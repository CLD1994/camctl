# 历史存储、事件与事务边界

[返回 CLI 资料入口](README.md) · [历史查询与报告重建](historical-state-query.md) · [历史快照维护](history-snapshots.md)

camctl 以不可变历史保存已经发生的事实，并在同一事务中更新当前投影。本页说明事件如何排序、怎样划定完整提交边界，以及事件、查询目录、投影和快照采用什么保存格式；最后说明 SQLite 连接的同步、忙等待和检查点规则。业务契约以[共同原则与状态持久化](../architecture/system-foundations.md)和[状态报告](../architecture/status-reports.md)为准。

先通过取回文件的例子区分历史位置与业务水位，再阅读事务和保存规则。[历史状态查询](historical-state-query.md)使用这些记录恢复指定边界处的状态，[快照维护](history-snapshots.md)负责保存可复用的历史状态。三个专题均遵守[第一版 MVP 范围](implementation.md#第一版实现范围)，具体事件字段、表和索引等未决实现事项列在各页末尾。

历史查询使用三个边界记号。它们都表示完整已提交事务结束处的历史位置，初始化起点 0 的特殊规则见下文。

| 记号 | 表示什么 |
| --- | --- |
| H | 报告登记时冻结的历史边界，同一报告始终使用这一位置 |
| C | 读取某份当前投影时，同一短读事务视图中的完整已提交边界；作为恢复起点时要求 C≥H |
| S | 某份历史快照所表达的完整历史边界；用于恢复 H 时要求 S≤H |

## 先理解事件、历史位置与业务变化序号

本节通过取回文件的例子解释三个概念。表中的名称和编号用于说明含义，不规定最终数据库字段、事件拆分方式或序列分配算法。

### 事件记录保存什么

事件记录是数据库对一件已经发生的事情的记载。例如，camctl 保存了一次拷贝进度变化：

| 记录内容 | 示例 |
| --- | --- |
| 发生了什么 | 已保存的拷贝进度增加 |
| 涉及哪个对象 | 交付 D |
| 原来是什么 | 已可靠保存 40 MB |
| 现在是什么 | 已可靠保存 70 MB |
| 在历史中的位置 | 历史位置 110 |
| 属于哪次数据库事务 | 事务 T |

这里保存旧值，是为了将来能够从 70 MB 恢复出当时的 40 MB。实际进度按[可恢复拷贝](../architecture/file-copy.md)规定的可靠保存顺序记录；本例的 MB 只是便于阅读的表示。

不同事件保存的事实不同。例如，计划受理事件保存计划身份、原始输入和确定的生效参数等；报告登记事件保存报告身份、覆盖范围和冻结依据；报告发布成功事件保存哪份报告已经成功放入 `ready`。

事件所需的信息由它表达的事实决定：读者需要知道发生了什么，程序需要据此准确重建相关状态。修改事件保存必要的变化信息；创建事件保存对应对象的完整初始事实。

### 两种顺序分别解决什么问题

**历史位置给全部权威历史记录排序，业务变化序号 `change_seq` 只跟踪需要向客户端报告的业务变化。** 同一条事件可以同时具有历史位置和业务变化序号；报告内部管理事件仍有历史位置，但不产生新的业务变化序号。

业务水位表示已经推进到的业务变化序号。例如，“水位为 22”表示业务变化已经推进到 22。它与客户端已经确认到哪个水位是不同的信息。

假设计划 P 中的取回动作 A 正在取回文件，创建了交付 D。客户端此前已经确认到业务水位 20。下面展示后续的一段历史，用百分比表达 D 的拷贝进度。每行代表一个完整提交位置，事务内可能包含多条事件；数字是示意，省略了无关记录。

| 历史位置 | 保存的事情 | 是否产生新的业务变化 | 提交后的业务水位 |
| --- | --- | --- | --- |
| 90 | 创建交付 D | 是 | 21 |
| 100 | D 的拷贝进度达到 40% | 是 | 22 |
| 101 | 登记报告 R，内容截止到历史位置 100 | 否 | 仍为 22 |
| 102 | 报告 R 已成功放入 `ready` | 否 | 仍为 22 |
| 103 | 收到并保存客户端对 R 的有效确认 | 否 | 仍为 22 |
| 110 | D 的拷贝进度达到 70% | 是 | 23 |

登记报告、发布报告、保存有效确认都必须留下历史，否则断电后无法确定报告处理到了哪一步。这些内部处理本身不产生新的业务报告责任，所以历史继续推进，业务水位保持不变。确认处理中的其他业务变化或无效 ACK 诊断仍遵守[报告与累计确认](../architecture/status-reports.md)的分类。

### 为什么业务变化序号不能代替历史位置

仅知道“业务水位为 22”，无法区分下面四种情况：

| 历史位置 | 当时已经保存的状态 |
| --- | --- |
| 100 | 业务进度已经保存，报告 R 尚未登记 |
| 101 | R 已登记，尚未保存发布成功事实 |
| 102 | R 已保存发布成功事实，尚未保存客户端确认 |
| 103 | 已保存客户端对 R 的确认 |

这四种情况对应不同的恢复依据。历史位置能够准确指定查询哪一个完整提交后的状态，业务水位只说明业务变化推进到了哪里。数据库尚未保存发布事实时，文件也可能已经发布；实际恢复还须按[文件交接](../architecture/file-handoff.md)核实文件位置，不能仅凭记录缺席推断外部操作未发生。

历史位置是数据库内部确定的先后顺序，不是时钟时间。同一事务中的事件整体提交，历史状态查询只接受完整事务边界；具体表示采用下文的[全局事件序号与显式事务边界](#全局事件序号与显式事务边界)。

### 一份报告怎样同时使用两种边界

例子中的报告 R 登记时保存两项不同的范围依据：

- **业务覆盖范围 `(20, 22]`**：选择业务变化序号大于 20、小于等于 22 的变化对象。本例选中交付 D，并按报告结构补齐它的父动作 A 和父计划 P。
- **历史冻结边界 100**：这些对象的自身字段都取数据库在历史位置 100 时已经知道的值，因此 D 的进度为 40%。

业务覆盖范围决定报告包含哪些变化对象，历史冻结边界决定这些对象采用什么状态。补齐父对象不意味着把其他子对象全部加入报告。

报告子进程读取时，当前投影中的 D 可能已经达到 70%。只要报告 R 的冻结边界仍为 100，就需要使用位置 110 的事件所保存的旧值，在查询副本中恢复出 40%。数据库当前投影及实际拷贝不受影响。

同一报告后续重建仍使用原覆盖范围和冻结边界。后来的业务进展和客户端确认不会改变它原来的内容。业务变化序号保持独立，也使报告登记、发布及有效确认本身不会不断触发下一份报告。

## 全局事件序号与显式事务边界

每条权威历史事件使用一个全局事件序号 `event_seq`，并保存所属历史事务的标识。同一状态数据库中，已提交事件的序号唯一、严格递增，不依赖墙钟。第一版按下文的[序号分配规则](#序号分配范围与初始化边界)连续分配全局事件序号；筛选后的事件位置可以不连续。一次历史事务中的事件按实际发生顺序排列，不与其他事务的事件交错。

每组一起提交的历史事件对应一份历史事务记录，以该组首条事件的 `event_seq` 作为事务标识，并保存本事务最后一个事件的序号。该记录描述这些事件的提交分组，不另存一份业务事实。事件、事务记录、本次派生的查询目录和受影响的当前投影在同一个 SQLite 写事务中保存；事务结束位置必须确实指向该组最后一条事件。

| 信息 | 用途 |
| --- | --- |
| 事件的 `event_seq` | 确定正向或逆向恢复顺序，唯一定位分页已经读到的事件 |
| 事件所属事务及事务结束位置 | 确定哪些历史位置代表完整提交后的状态 |
| 请求、计划与事件的业务关联 | 追溯事实属于哪个业务对象或请求；一个计划可经历多次事务提交 |
| `change_seq` 与 `plan_seq` | 继续分别遵守业务报告覆盖和新计划受理顺序的既有规则 |

历史事务记录适用于写入权威历史的事务。只维护历史快照等派生数据的事务不因此新增历史事件或历史事务记录。报告登记、发布与有效确认等内部历史仍分配 `event_seq`，是否推进 `change_seq` 则按对应业务规则判定。

例如，某次事务依次保存“输出文件已确认”“动作已完成”“计划已完成”，事件序号为 201、202、203，事务记录的结束位置为 203。恢复程序一批读到 202 后，可以从该位置继续读 203；该批处理结果尚不能作为完整状态交付。报告冻结位置只能选择 203 或此前某次完整提交的结束位置。

| 位置或保存状态 | 处理规则 |
| --- | --- |
| 目标位置为 0，且数据库已经可靠确认完整有效 | 表示初始化后的历史起点，不对应事件或历史事务记录 |
| 目标位置是当前一致读取视图内的已提交事务结束位置 | 可作为历史状态查询边界；报告 H、读取依据 C 和快照 S 继续满足各自范围约束 |
| 目标位置是事务内的非末尾事件 | 可作为事件分页位置，不接受为完整状态查询或报告冻结边界 |
| 目标位置不存在或超出当前读取视图 | 不接受为该视图内的历史状态边界，不自动取邻近位置替代 |
| 写事务已经确认回滚 | 本次事件、事务记录及投影变化均不成为可用历史；继续以此前已提交状态为准 |
| 写事务提交结果未知 | 按既有状态库错误及恢复规则确认整个事务结果，不从内存中的序号推断成功或失败 |
| 已保存的冻结依据、事务记录或事件分组相互矛盾 | 按历史不可可靠解释的状态库错误处理，不截断、补齐或猜测边界 |

除初始化起点 0 外，H、C、S 均使用完整事务结束处的 `event_seq` 表示，不以请求结束、计划完成或业务水位代替。C 与对应的当前投影在同一次短读事务的一致视图内取得；该投影副本用于恢复期间，C 保持不变。不同批次取得的投影可以对应不同的 C，所有对象最终恢复到同一个 H。位置 0 的存在不创建业务实体或报告责任，报告及快照的生成资格仍按各自规则判断。分页游标可以位于事务内部，恢复到 H 的结果只能在所需影响全部处理完毕后使用。

验收覆盖单事件和多事件事务、同事务多次修改同一对象、事务内跨批分页、筛选结果的序号间隔、并发提交、确认回滚与提交结果未知，以及无效边界被拒绝、保存的边界矛盾被诊断。单元测试验证边界分类和恢复顺序，集成测试验证事件、事务记录、目录与投影一起提交或回滚。

具体表名和列布局、数据库约束和查询接口仍需细化。

### 以首条事件序号标识历史事务

历史事务的 `transaction_id` 等于该组首条事件的 `event_seq`，使用相同的正整数范围，不另设事务编号计数器。组内所有事件保存这个事务标识；事务记录以该标识定位起点，并保存结束序号，不另存一份重复的起始编号。

| 本次新增事件 | 事务标识及记录 |
| --- | --- |
| 只有序号 201 的事件 | `transaction_id = 201`，结束序号为 201 |
| 序号 201、202、203 的三个事件 | 三条事件均属于事务 201，事务结束序号为 203 |
| 前一事务结束于 203，下一事务从 204 开始 | 下一事务标识为 204，结束序号由该组最后一条事件确定 |
| 没有新增历史事件 | 不创建历史事务记录，包括只维护派生快照的写事务 |

产生本次首条事件时确定事务标识，完成该组事件写入后确定结束序号。提交时，事务记录必须完整，起止事件都存在并属于本组，组内事件连续且不与其他事务范围重叠。事件及事务记录一起提交或一起回滚，不暴露只有起点、缺少结束位置的已提交分组。事务内部的暂存表示和数据库约束实现仍需细化。

事务标识仅定位同一状态数据库中一组已提交历史。请求身份、计划身份与事务标识分别保存，一个计划可以经历多次事务。确认回滚后，相同起始序号可以用于下一次实际提交；因此，提交结果未知时，不能仅凭该事务标识或某个事件序号存在就认定原调用成功，仍须结合业务身份和保存的事实核验整个操作结果。

验收覆盖单事件与多事件分组、相邻事务、无事件写事务、确认回滚后的标识重新使用，以及组内归属错误、范围重叠、首尾事件缺失和未完成分组不得提交。提交结果核验须覆盖某序号已由其他操作使用的情形，不将历史位置当作请求幂等凭据。

### 序号分配范围与初始化边界

`event_seq` 使用 SQLite 的 64 位有符号整数保存，真实事件范围为 `1` 至 `9223372036854775807`，对应 `2⁶³ − 1` 的上限，见 [SQLite 整数表示](https://www.sqlite.org/datatype3.html)。0 专门表示完整有效数据库初始化后的历史起点，不插入序号为 0 的事件或虚构事务记录。数据库不存在、损坏、历史与其他状态矛盾或读取失败时，不能用 0 代替错误。

新增历史时，先成功取得 `BEGIN IMMEDIATE` 写事务资格，再通过序号索引读取最后一个已提交事件的序号；可靠确认尚无事件时以 0 为起点。本次事件按顺序逐条加一，连同事务记录、目录及投影一起提交。分配依据直接来自已有历史，不另设永久递增计数器，也不依赖进程启动时读取的旧序号。其他写入者在取得写事务资格后重新读取依据；写事务互斥规则见 [SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)。

| 分配与保存情况 | 处理规则 |
| --- | --- |
| 当前最后序号为 L，本次 N 条事件全部提交成功，N＞0 | 本次使用 L＋1 至 L＋N；下次从 L＋N＋1 开始 |
| 本次没有新增历史事件 | 不分配事件序号，不创建空的历史事务分组 |
| 本次已分配序号，但整个事务确认回滚 | 分配结果没有成为历史；下次仍从数据库实际最后序号之后开始 |
| 提交结果未知 | 先按恢复规则确认完整事务结果，不从内存分配记录决定重用或跳号 |
| 剩余序号不足以保存本次全部事件 | 整个写事务失败并确认回滚，不提交部分事件或投影 |

分配时检查数值范围，不回绕、不改用浮点数，也不重复使用已提交的序号。本次事务内部可以引用已经分配的序号；提交确认前，不据此发布已提交缓存、确认报告冻结完成或启动依赖这些事实的外部操作。序号耗尽按既有状态库错误规则处理，停止启动依赖新持久化事实的普通设备动作，保留已有数据和诊断。第一版不实现序号扩容；将来需要扩大表示范围时须通过显式数据库格式升级设计。

第一版正常提交的全局序列连续，事务回滚不留下空缺。按对象或事件类型筛选后，结果可能只包含 201、204 等位置，因为其他事件属于别的对象或类型；分页按实际序号大小继续，不能将序号差当成筛选结果的事件数量。完整历史出现空缺时须调查并诊断，不归因于正常回滚，也不为消除空缺改写历史。此要求不意味着每次局部查询都扫描全库检查连续性，具体完整性检查方式随持久化接口细化。

验收覆盖初始边界 0、首次分配、多事件事务、确认回滚后的重新分配、并发写入按实际提交结果续号、提交结果未知，以及上限恰好够用和不足的分区。上限测试验证整批原子性，筛选查询测试验证位置有间隔时无遗漏或重复；缺失或无效数据库不得被当作空历史继续分配。

## 事件恢复依据

每种业务事件明确规定它改变哪些状态，并保存这些变化所需的前后值。恢复信息按有业务含义的字段或成员组织；例如，更新一次录像启动尝试时，保存该次尝试被改变的部分。事件类型、成立条件、正向更新规则和逆向恢复规则共同构成该事件的契约。

| 状态变化 | 必须能够表达的恢复信息 |
| --- | --- |
| 覆盖字段 | 变化前的值及其类型；新值用于正向更新与一致性检查 |
| 新增或移除可选字段 | 明确区分字段不存在与显式空值 |
| 新建实体 | 身份、所属关系、完整初始事实及创建位置；逆向跨过创建位置时恢复成不存在 |
| 改变逻辑有效性或状态 | 变化前后的明确状态；不能从名称推测原值 |
| 增加集合成员 | 成员身份、内容和必要顺序；逆向时先恢复该成员后来的变化，再撤销加入 |
| 修改集合成员 | 成员身份及被修改部分的前后值；保留其他成员 |
| 移除或替换集合成员、改变关系 | 被移除或替换的成员及关系的前后事实；有语义顺序时还需恢复顺序 |
| 更新派生父对象 | 直接保存父对象被改变状态的前后值，与触发变化的子对象事实同事务提交 |
| 清理产物或撤回交付 | 原状态、新状态及实际处理事实；逆向只恢复查询副本中的状态，数据库永久保留实体与历史 |
| 同一事务改变多个实体 | 保留事务分组与内部顺序；状态查询只暴露完整事务边界 |

旧值在写事务内依据该事件发生前的实际状态取得。同一事务多次修改同一字段时，后一个事件的旧值对应前一个事件生效后的值；逆向按相反顺序处理。

例如，最后一个未结束动作完成，使计划由 `running` 变为 `completed`，同一事务保存动作完成及计划状态变化的恢复信息；本次还登记正式产物时，一并保存产物创建事实。恢复父计划自身的旧状态直接使用这些信息，无需为计算计划阶段读取全部子动作。具体拆成几个事件及字段名称仍需在事件契约中确定。

逆向跨过事务时，应处理它对本次查询对象及必要依赖的全部影响。只恢复动作的 `status`，却保留后来的产物、诊断或父计划状态，不能得到合法的旧状态。

原始计划及受理时固定的生效参数由创建事实永久保存，后续事件通过稳定身份关联。其他大型不可变结果的复用方式仍需细化。引用必须能够定位永久保存的事实，不能读取当前配置、重新应用默认值或访问已经可能删除的输入文件。

## 事件正文与两类查询目录

事件正文保存一次，另维护两类轻量查询目录。目录保存定位事件和对象所需的关联，内容由事件及确定的规则派生，能够从历史重建。表和索引的实现建议见[历史、目录与查询](persistence-runtime.md#历史目录与查询)，实际 SQL 须验证执行计划和负载。

| 目录 | 回答的问题 | 索引组织方向 |
| --- | --- | --- |
| 业务变化与实体的关联 | 业务覆盖区间内哪些实体发生了应报告的变化 | 按业务变化序号定位区间，再取得实体类型与身份 |
| 实体与历史事件的关联 | 指定实体在冻结之后发生了哪些状态变化 | 按实体类型、身份及历史位置定位相关事件 |

例如，交付 D 在业务变化 21、22 和 23 分别创建、推进到 40% 和 70%，业务目录保留这三次关联。覆盖 `(20, 22]` 的报告仍能选中 D，不能只保存其最后变化序号 23。若报告冻结在历史位置 100，当前读取位置为 110，历史目录直接定位 D 在 `(100, 110]` 的事件，取得旧值并恢复查询副本。

事件正文、两类目录中本次新增的关联及受影响的当前投影在同一事务中保存。只追加本次关联，不遍历全部历史。一次事件改变多个实体时，为各受影响实体建立关联；批量读取正文按事件身份去重，保留每个实体需要应用的影响。恢复按各实体选定路径的顺序进行，每个实体对同一事件的影响只应用一次。

关联按实际影响分类：改变对象状态时建立恢复查询关联；产生应报告的业务变化时建立业务变化关联。仅引用另一个对象的身份，不表示该对象发生变化。补齐报告父对象也不因此产生业务变化。

两者都需要适当索引，不能先读取整库历史再在 Python 中过滤。复合索引可以支持限定条件和顺序读取，具体列顺序及查询方式应由实际 SQL 和执行计划决定，见[SQLite 查询规划](https://www.sqlite.org/queryplanner.html)。

### 实体历史关联与累计变化计数

实体历史目录中，每条关联保存实体类型、实体 ID、`event_seq` 和该实体截至本事件的累计变化计数。同一实体与同一事件只保存一条关联，按“实体类型、实体 ID、事件序号”定位；不同实体各自计数，不使用全局事件序号或 `change_seq` 代替累计变化计数。

计数单位是一条事件对一个实体产生需要恢复的状态变化。按各事件实际发生的变化计算，不把整个事务的净结果当作一次变化；事件正文仍只保存一次。

| 事件影响 | 关联与计数规则 |
| --- | --- |
| 创建实体 | 保存创建关联，该实体累计计数从 1 开始 |
| 一条事件改变同一实体的一个或多个字段 | 保存一条关联，计数加 1 |
| 同一事务内 N 条事件分别改变同一实体，N＞0 | 按事件顺序保存 N 条关联，累计计数依次增加 |
| 一条事件同时改变多个实体 | 为每个受影响实体分别保存一条关联，各自计数加 1 |
| 事件只引用实体身份，没有改变其需要恢复的状态 | 不为该实体建立恢复关联，也不增加其计数 |
| 重复取得同一实体与事件的关联 | 不重复保存或增加计数；读取复用不改变持久化计数 |
| 保存事务回滚或提交结果未知 | 与事件、目录和投影保持同一事务结果，沿用确认回滚及结果未知的分类 |

累计计数由不可变历史及各事件的状态变化规则派生，可以重建。事件正文、关联、计数及相关当前投影一起提交；计数不是另一份独立业务事实。生成快照时保存边界 S 处的计数，后续变化不修改旧快照中的计数，快照维护也不重置实体的累计计数。

对在目标边界 H 已存在的实体，通过索引定位该实体在 `event_seq ≤ H` 范围内的最后一条关联，取得 H 处的累计计数。即使 H 处最后一条全局事件属于其他对象，也能取得正确计数。对象在 H 尚未创建时遵守不存在分支；对象应已存在但关联缺失、计数矛盾或查询失败时，按状态库错误处理，不默认计数为 0。

计数分别绑定其历史位置：C 处计数与对应当前投影在同一短读事务内取得，S 处计数随已选快照保存，H 处计数按不可变历史关联查询。分别用 H 与 S 的计数差估计正向恢复的事件数量，用 C 与 H 的计数差估计逆向恢复的事件数量。例如，S、H、C 处计数分别为 20、23、100，正向需要 3 条相关事件，逆向需要 77 条。无需为比较路径读取事件正文或逐条统计整段关联；索引与查询计划须验证能够定位对应实体的范围及末条关联。

快照触发中的“变化次数”使用相同单位。以当前累计计数减去该对象最近已提交快照在其边界处的计数，判断尚未包含的相关变化数；没有快照时基准为 0，创建计为第一次变化。首次及后续快照统一遵守[按对象累计变化次数触发](history-snapshots.md#按对象累计变化次数触发历史快照)的规则。每条关联增加一个累计计数字段，以额外存储换取范围计数查询，相关读写量纳入性能验收。

对[历史快照维护范围](history-snapshots.md#历史快照的对象范围)内的对象，用于发现候选的计数差按[派生维护进度](history-snapshots.md#持久化快照维护进度与候选查询)持久化，并与本次事件和投影保持同一事务结果。累计历史计数仍按上述规则永久递增，快照保存只更新相应的维护进度。

验收覆盖创建、单事件多字段、多事件同实体、单事件多实体、仅引用、重复关联、事务回滚与提交未知；验证同事务内多次覆盖乃至最终回到原值时仍按相关事件数量计数。查询覆盖 H 恰好位于对象变化处、位于两次对象变化之间、对象尚未创建及关联异常；快照生成后继续变化、正反向路径比较与维护触发使用同一计数含义。

### 统一事件表与按类型定义的 JSON 正文

事件使用统一事件表保存。`event_seq`、所属事务和事件类型等公共信息使用固定列；各类事件表达的事实及必要恢复信息使用 JSON 正文保存。正文只保存一次，查询目录引用对应事件；相关实体和历史范围的定位使用目录及索引，不通过逐条解析整库 JSON 完成。

JSON 是持久化表示。每种事件仍须有明确的字段、合法值、成立条件、正向更新及逆向恢复契约；Python 内部使用有明确类型的事件对象。持久化边界负责校验并在事件对象与 JSON 之间转换，未知事件类型、无效正文或缺失必要恢复依据按状态库错误处理。保存与读取遵守规定的精确数字、字符串及字段存在性规则。

| 处理阶段 | 责任 |
| --- | --- |
| 形成事件 | 根据事务内实际状态构造已定义类型的事件，包含真实的新旧值 |
| 保存事件 | 校验并编码正文，与公共信息、事务记录、目录及投影一起提交 |
| 查找历史 | 通过实体、业务区间或历史区间定位事件，再分批取得所需正文 |
| 读取事件 | 校验并解码为对应事件类型，再按既定方向恢复；不把解析成功等同于事件有效 |

事件字段演进遵守下文的[事件格式版本与读取兼容性](#事件格式版本与读取兼容性)。不可变历史继续保留原始事实，后续程序不能用当前默认值、配置或设备状态猜测旧记录缺失的信息。

验收覆盖不同事件类型的读写往返、缺失与空值、精确数值及 Unicode 字符、非法正文、未知事件类型，以及读取后的正向和逆向恢复结果。

### 事件格式版本与读取兼容性

统一事件表增加固定列 `event_version`，与 `event_type` 一起确定正文的字段及解释规则。各事件类型独立演进，第一版从版本 1 开始；事件格式版本不表示程序发布版本，也不代替数据库整体兼容性标识。

已发布的事件版本保持原有契约。新增、删除或改名字段，以及字段类型或含义变化，均使用新的事件格式版本。表达另一种独立业务事实时，使用新的事件类型。更新某类事件不要求其他事件类型同步增加版本。

新程序保留对旧版有效事件的读取能力。持久化边界根据事件类型和版本选择对应的校验与解释规则，在内存中转换为语义明确的事件对象；可以保持原意的结构差异由适配处理。数据库中的已有事件正文、类型、版本、序号及事务归属保持不变，不为适配新程序重写不可变历史。

例如，旧版以 `old_bytes`、`new_bytes` 表达可靠拷贝进度，新版将它们组织为 `before.bytes`、`after.bytes`，可以在读取时转换为相同含义。若新版新增分段校验和，旧事件未保存该事实，则保留“旧记录未提供”的明确含义或继续按旧版规则解释；不能使用当前文件、设备状态、默认值或空字符串补造当时的事实。

| 读取情况 | 处理规则 |
| --- | --- |
| 事件类型及版本受支持，正文满足该版契约 | 按该版本解释，再执行相应正向更新或逆向恢复 |
| 新程序读取受支持的旧版事件 | 保留原有事实和语义，仅在内存中适配表示 |
| 受支持版本的正文损坏或缺少该版必需字段 | 按状态库错误处理，不能当作正常旧格式补默认值 |
| 事件类型或格式版本不受支持 | 明确诊断格式不受支持，停止依赖该状态的业务处理，不忽略事件或试用邻近版本 |
| 新字段对应的事实未在旧记录中保存 | 按旧版契约保留信息边界；不把未记录解释为已知结果 |
| 事件格式升级后需要重建既有报告 | 继续使用原报告冻结依据及确定生成规则，保持原有字节、文件名和摘要 |

兼容性方向是新程序能够读取旧历史；不承诺旧程序可以处理新程序写入的新格式。对不支持格式的诊断与对损坏记录的诊断分别保留原因，均遵守既有状态库错误边界。

第一版只实现版本 1、版本识别和分派接口。正式增加后续版本时，同步提供旧版读取适配及回归用例，不提前实现假想的第二版。事件类型、版本与解释器的对应关系应有单一权威定义，校验和分派据此确定。

第一版验收覆盖支持版本的正确分派、不支持类型或版本、缺失或非法版本标识，以及合法正文与损坏正文的区分。新增版本时，再以固定旧记录验证新旧格式解释、正向及逆向恢复、历史记录保持原样和既有报告字节不变。

数据库采用[整体格式检查与显式升级](persistence-runtime.md#数据库整体格式检查与显式升级)。正式允许新事件格式前先升级整体 `format_version`；程序在使用业务状态前检查兼容性，不等到恢复某条新事件时才发现格式不受支持。投影与快照遵守下文的[保存格式规则](#当前投影与历史快照的保存格式)，后续实际升级流程及并发准入机制仍需细化。

## 当前投影与历史快照的保存格式

当前投影使用状态库当前 `format_version` 对应的结构。将来显式升级确实改变投影表示时，在维护阶段转换，或根据权威历史重建；验证完成后才恢复日常使用。投影表示没有变化时，不因整体格式编号增加而要求无意义地重写投影。转换与重建仍不执行设备或文件交接副作用，也不改写历史事实。

历史快照保持原有内容，每份快照保存生成时采用的数据库格式版本，不增加独立的快照版本编号。快照的格式标记、对象身份、完整历史边界 S、对应计数及内容一起提交。读取时按该快照自身的格式标记解释，不以数据库当前格式替换旧快照的标记。

| 信息 | 含义 |
| --- | --- |
| 数据库元信息中的 `format_version` | 当前状态库采用的持久化契约及当前投影表示 |
| 快照记录中的 `format_version` | 生成这份快照时采用的保存格式 |
| 快照边界 S | 快照表达哪个完整历史边界处的对象状态 |

例如，格式 2 的数据库可以按其契约保留一份“边界 100、保存格式 1”的旧快照，同时新增“边界 200、保存格式 2”的快照。程序先确认支持该数据库格式，再分别按快照记录的格式校验和解码；旧快照需要的表示适配在内存中完成。S 不因解码或适配而改变。

| 情况 | 处理规则 |
| --- | --- |
| 快照采用当前格式且内容有效 | 校验后用于相应边界的恢复 |
| 快照采用当前数据库契约允许保留的旧格式，内容有效 | 按旧格式校验并解释，需要时在内存中适配；不重写原快照 |
| 快照格式标记缺失、非法、不受支持或不属于当前数据库允许的格式 | 明确按状态库错误处理，不按当前格式猜测，也不作为普通缓存未命中跳过 |
| 快照内容损坏或不能可靠解释 | 继续遵守历史状态查询的错误规则，不补造状态 |
| 新格式需要的信息未在旧快照及相应旧事实中记录 | 保留旧契约的信息边界，不用当前默认值或设备状态补齐 |

程序声明支持某个数据库格式时，必须支持该格式允许保留的旧快照表示。增加数据库格式时明确其当前投影结构、新快照保存结构和可读取的旧快照结构；共用相同表示的格式可以复用解释器。格式及解释器的对应关系遵守单一权威定义要求。

第一版只生成和读取格式 1 的快照，并实现格式标记校验。后续实际格式变化时再实现转换和适配，验收旧快照内容与边界保持不变、新旧快照解释得到独立预期、正向恢复结果正确及既有报告字节不变。投影转换、重建的维护步骤和中断恢复随实际升级方案定义。

## 所有状态库写连接使用 FULL 同步

SQLite WAL（预写日志）模式允许读取与写入并行。报告通过[分批短读事务](historical-state-query.md#wal-与分批短读事务)释放读取视图，数据库连接则按本节及后续两节设置同步等级、忙等待参数和自动检查点阈值。三项设置分别控制持久化、锁竞争与内部维护。

状态库统一采用 `journal_mode=WAL`、`synchronous=FULL`。每个状态库写连接在执行写事务之前显式设置并核验同步等级，确认 WAL 模式符合要求；不能仅依赖初始化连接或另一个进程的连接设置。适用范围包括初始化、`run`、`submit`、快照等派生数据维护，以及后续明确设计的写入入口。第一版不提供降低同步等级的配置。

WAL 模式下，`FULL` 在每次事务提交时增加 WAL 同步，用于保证已经提交事务的断电持久性。它同步事务所需日志，不要求每次重写整个数据库；可靠性以操作系统和存储设备正确履行同步请求为前提，见 [SQLite 同步等级](https://www.sqlite.org/pragma.html#pragma_synchronous)。部署联调需验证目标主机的实际存储行为。

持久化完成仍先于依赖这些事实的外部副作用。例如，录像启动意图可靠提交后才允许发送相应设备命令；不能让命令已经生效，而意图记录因降低同步等级在断电后丢失。文件内容及目录同步继续由文件处理契约保证，数据库同步不代替文件交接的持久化步骤。

| 写连接或提交情况 | 处理规则 |
| --- | --- |
| WAL 与 FULL 设置已经核验，事务提交确认成功 | 才能返回已提交结果，并允许依赖该事实的后续处理 |
| 设置失败、核验结果不符或无法确认 | 不以该连接继续写入，按所属入口的状态库错误契约处理，不静默降级 |
| 提交失败且确认回滚 | 不发布本次已提交结果，不执行依赖它的外部副作用 |
| 提交或回滚结果无法确认 | 保留结果未知，按既有恢复规则核实；设置 FULL 不消除提交结果未知的分支 |

降低存储开销通过合理组织事务、控制可恢复进度的保存粒度和快照维护批次实现，不延后协议要求的可靠保存位置。数据库操作继续在专用数据库线程执行；同步造成的提交等待仍计入业务时延，不能以使用协程为由忽略。

单元测试覆盖连接核验失败与提交各结果下的后续行为。集成测试使用各实际写入口打开的连接检查生效设置，并验证同步或提交错误不会被解释为成功；目标主机联调另测提交延迟、设备调度延迟和断电恢复。进程终止测试不代替真实断电场景的验证。锁等待与检查点按下文安排，磁盘故障的具体处理仍需细化。

## SQLite 内置忙等待与失败处理

第一版使用 SQLite 内置忙等待机制处理适用的锁冲突，通过连接的 `busy_timeout` 参数设置等待量。SQLite 最终返回锁忙错误后，应用层结束本次操作并按实际事务状态清理、交付错误，不再循环重发同一语句或重开同一事务来延长等待。该规则不阻止后续合法启动的会话按既有恢复协议核实状态。

本节集中定义主机本地配置：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `database.busy_timeout_ms` | `9000` | 1～2147483647 的整数，单位为毫秒；传给 SQLite 内置忙等待机制的参数 |

省略配置项时使用默认值；0、负数、超出范围的整数、浮点数、布尔值、字符串等按配置错误处理，不以截断或溢出后的值建立连接。参数采用 SQLite 接口可表达的有符号 32 位正整数范围。配置按[本地配置加载规则](../architecture/configuration.md#本地配置的加载与更新)在 CLI 启动时取得，会话内固定，部署调整在后续调用生效，不固化到动作。

每个访问状态库的连接在执行查询或事务前，显式设置并读取核验 `PRAGMA busy_timeout`；适用范围包括初始化、`run`、`submit`、快照维护及报告只读连接。新建或重新创建连接时沿用所属会话的生效值，不依赖另一个连接的设置。主进程将本次值传给报告子进程，故障后重新创建的报告进程仍沿用同一值。设置或核验失败时，不使用该连接继续工作，按所属入口的状态库错误协议处理。只读连接仅设置自身运行参数，保持只读权限。参数按连接生效，见 [SQLite 忙等待配置](https://www.sqlite.org/pragma.html#pragma_busy_timeout)。

SQLite 按自身忙处理规则在适用的锁冲突期间等待；为避免死锁等原因，也可能直接返回 `SQLITE_BUSY`。因此既不要求每次锁忙都等满配置值，也不将它作为事务或数据库调用的总耗时上限。数据库执行、提交同步、其他锁冲突及系统调度仍可能增加耗时。该参数与进程内的入队等待分别计量，已入队等待派发继续遵守不另设排队超时的规则。机制边界见 [SQLite 内置忙等待](https://www.sqlite.org/c3ref/busy_timeout.html)及[忙处理回调的适用条件](https://www.sqlite.org/c3ref/busy_handler.html)。

先按本次操作结果处理；失败后需要回滚时，再按回滚结果分类：

| 锁等待或事务结果 | 处理 |
| --- | --- |
| 锁冲突消除，SQLite 继续执行 | 继续本次操作，最终按实际查询或事务结果返回 |
| `BEGIN IMMEDIATE` 返回锁忙，确认尚未取得本次写事务资格 | 本次事务未开始，交付状态库错误；不进入业务判断或执行依赖它的外部副作用 |
| 读取、事务内语句或提交返回锁忙，包括未等满参数值即返回 | 结束本次操作，按实际事务状态释放读取或执行必要回滚，不在外层重发；交付状态库错误 |
| 失败后已确认回滚 | 本次变更未提交，保留其他已提交事实并交付错误 |
| 提交或回滚结果无法确认 | 保留结果未知，按既有恢复规则核实；不能仅凭锁忙错误宣称整个事务未保存 |

`run` 与 `submit` 按 `state_db_error` 处理最终锁忙错误；报告进程保留状态库错误分类交给主进程，初始化沿用自身错误输出契约。快照操作已进入数据库执行后的锁忙失败也遵守此规则，不适用尚未入队超时的会话内停用策略。等待期间取消调用协程不证明数据库操作结束，仍须跟踪实际结果后处理连接。自动 PASSIVE 检查点未完整推进继续按其专门规则处理，不因本参数而要求检查点等待其他事务结束。

验收覆盖配置缺省、合法边界及覆盖、非法类型及越界值；逐个检查各入口、报告只读连接和重新创建连接的生效值。单元测试控制锁忙、提前返回、明确回滚和结果未知，验证不额外重发及错误分类。集成测试通过真实连接竞争验证锁释放后继续与持续竞争后失败，检查失败事务的实际状态，不以精确等于参数值的墙钟耗时作为断言。另测锁等待期间的队列积压及设备调度延迟；报告进程重建仍使用所属会话的配置，超时与退出继续遵守报告生命周期契约。

## 自动 PASSIVE 检查点与可配置阈值

第一版保留 SQLite 自动检查点，通过 `wal_autocheckpoint` 设置可配置的页数阈值。本节集中定义本地配置：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `database.wal_autocheckpoint_pages` | `1000` | 1～2147483647 的整数；事务提交后 WAL 达到该页记录数量时，由 SQLite 自动尝试 PASSIVE 检查点 |

省略时使用默认值；0、负数、超出范围的整数、浮点数、布尔值或字符串等按配置错误处理。采用 SQLite 接口可表达的有符号 32 位正整数范围，保持自动检查点启用。配置按[本地配置加载规则](../architecture/configuration.md#本地配置的加载与更新)在 CLI 启动时取得，进程运行期间固定，部署调整在后续调用生效；不固化到动作，不改写业务事实或报告内容。

所有状态库写连接在执行写事务前显式设置并读取核验 `PRAGMA wal_autocheckpoint`，包括初始化、`run`、`submit` 及快照等派生数据维护；重新创建连接时沿用所属会话的生效值。不能依赖 SQLite 构建时的默认设置或其他连接已经设置。设置失败、结果不符或无法核验时，按所属入口的状态库错误协议处理，不以该连接继续写入。报告进程保持只读，不承担写入触发的自动检查点职责。

阈值计量 WAL 中的页记录数量，不是不同数据库页面的数量，也不是业务事件或快照对象数量。实际页面大小由数据库决定；例如每页 4 KiB 时，默认阈值约对应 3.9 MiB 的页面数据，不包含 WAL 格式开销，也不代表文件大小上限。该默认值采用 SQLite 通常使用的初始阈值，实际负载下的提交开销与 WAL 增长仍需联调测量，见 [SQLite 自动检查点配置](https://www.sqlite.org/c3ref/wal_autocheckpoint.html)。

检查点将 WAL 中的数据库页面合并回主数据库，并为日志空间复用创造条件。它是数据库内部维护，不生成业务历史，不推进事件序号或业务水位。已可靠提交的事务不以整个 WAL 合并完成作为有效条件；WAL 本身是数据库持久状态的一部分，由 SQLite 管理，不能作为普通临时文件清理。

SQLite 自动检查点采用 `PASSIVE` 模式，尽量推进而不等待其他读写事务结束来强求完整完成。自动检查点会在触发提交的线程中执行实际读写，因此仍可能增加该次提交的返回耗时，不能将“不等待其他事务结束”解释为“不耗时”或“不产生存储竞争”。第一版继续由已有数据库线程承载这些操作，不新增专用检查点线程，见 [SQLite 自动检查点](https://www.sqlite.org/wal.html#automatic_checkpoint)及[检查点模式](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html)。

| 运行情况 | 处理规则 |
| --- | --- |
| 事务提交后 WAL 页记录数量达到或超过本连接的阈值 | 由 SQLite 自动尝试 PASSIVE 检查点 |
| 检查点可以完成本次页面合并 | 由 SQLite 按其规则维护和复用 WAL 空间，不要求文件立即缩小 |
| 存在并发读写或检查点争用，本次不能完整推进 | 保留尚需处理的日志，后续再推进；单纯维护未完成不改判已提交业务或报告为失败 |
| 获得实际数据库读写故障证据 | 按状态库错误处理，不能归入普通维护未完成；提交结果仍按实际证据分类 |

日常运行中的检查点选择遵守 PASSIVE 策略，不主动使用要求更强等待的检查点模式来强制清空 WAL。检查点模式与 `synchronous=FULL` 是两项不同设置，采用 PASSIVE 不降低规定的提交同步等级。

自动检查点阈值是触发条件，不是 WAL 文件大小上限。慢查询及交叠的读事务可能阻碍页面合并或日志复用，文件已有空间也可能留作复用；不能仅凭文件未缩小认定检查点失败。第一版依靠自动 PASSIVE 检查点及报告逐批释放读取；实际数据库故障继续按已有错误规则处理。

验收覆盖配置缺省、合法覆盖与边界、非法类型及越界值，以及会话内固定、后续调用采用新值。逐个核验写入口及重新创建连接的实际设置，覆盖设置失败和核验不符。使用可控写入验证未达、恰好达到及超过阈值的行为，按实际 WAL 页记录计量，不以事件数代替。另覆盖报告持有读事务时部分推进、读事务结束后后续写入能够继续推进，以及维护争用与实际数据库错误的区分。目标主机测量触发检查点时的提交延迟、设备调度延迟和 WAL 增长；是否需要调整执行安排由实际负载证据决定。

## 后续设计提醒：WAL 积压时的读取协调

**本节不属于第一版实现或验收范围。** 若后续联调或运行发现自动检查点与分批短读事务仍不足以应对持续积压，可评估按压力协调读取与检查点的机制。第一版不为该提醒增加运行时积压监测、暂停通信、协调状态机或专用配置。

候选流程为：发现需要干预的积压后，报告完成当前批次并释放读取，暂缓下一批；主进程暂缓新增快照维护读取，通过已有数据库线程安排一次 PASSIVE 检查点；本次返回后报告继续已有任务，不以 WAL 清空作为继续条件。恢复副本、冻结范围、分页位置和文件生成进度保留，普通计划接纳与必要业务保存继续进行。

正式启用前仍须定义压力判据、监测方式、协调频率、等待预算、与报告总生成时限的关系，以及通信失败和实际数据库故障的处理。PASSIVE 自身的磁盘读写可能耗时，不能把它视为固定时长操作；检查点部分推进也不等于数据库故障。设计需要同时验证 WAL 能够继续维护和报告能够持续完成，避免反复停读或重新生成导致状态迟迟无法交付。
