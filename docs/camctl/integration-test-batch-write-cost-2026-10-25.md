# 固定批量写入耗时的深入分析（2026-10-25）

这项测试慢，主要有两个原因叠加：程序反复读取、解释并核对同一批文件的来源和历史；测试又追踪了这些处理过程中每次 Python 内存分配，进一步放大对象密集处理的成本。固定批量限制一次保留的数据量，不会自动减少这些检查的总次数。

本轮使用 `98d3b28da5751e1e8c733f2712180cd5e0e119aa` 的独立源码副本。它与上次 `fc310442` 样本的生产及测试源码相同。只运行诊断脚本，没有修改生产代码、现有测试或配置，也没有重新运行全量回归。记录、脚本和源码摘要见[本轮证据目录](verification-data/2026-10-25-integration-batch-write-analysis/)。

## 测试实际上做了什么

目标用例是 [`test_fixed_batch_write_and_verification_have_bounded_residency`](../../apps/camctl/tests/integration/persistence/test_segment_transaction_batches.py)。它分别准备 20、200、400 份文件事实，将它们登记为正式产物，再根据原操作身份重新核对已保存的完整结果。测试检查文件数量增加后，内存峰值、单次读取量和查找成本仍符合边界。

这里保存的是文件名称、定位、大小、归属、完成事实和产物登记等数据库信息。测试来源中的文件大小事实为 10 字节，不涉及传输或写入 400 段实际视频。

`batch_size=4` 表示每次分批读取候选、生成范围关联；全部结果仍在**一次完整事务**中提交。每份正式产物仍各有一条历史事件。例如本轮 200 份原片中，14 份属于默认取回范围，最终形成 208 条历史事件、218 项业务行变化：200 条产物事件、4 条范围关联事件，以及来源终态、处理责任结束、计划完成和最终发布各一条。

写入最后只有一次 COMMIT；后续重新核对结果使用单独的只读事务。因此数万次 SQL 调用不能解释为数万次磁盘提交，也不能解释为每四份文件提交一次。

## 内存跟踪把同一操作放大了多少

本轮先用原测试的真实准备入口建立 200 份文件的数据，关闭连接后冻结完整数据库。每一档都在同一物理路径恢复同一份数据库，使用相同请求、操作身份和批量参数，再核对数据库模式、元信息、返回结果及全部逻辑内容摘要。四档的最终结果和数据库逻辑摘要完全一致。

SQL 计数包装直接从原测试的局部类定义读取，没有重新实现一份替代逻辑。分别开关该包装和 `tracemalloc`（Python 内存分配跟踪）后，观察到：

| 测量方式 | 完成写入 | 再次核对结果 | 两项合计 |
| --- | ---: | ---: | ---: |
| 两种工具都不开启 | 9.566 秒 | 0.860 秒 | 10.426 秒 |
| 只开启原测试的 SQL 计数 | 8.589 秒 | 0.880 秒 | 9.469 秒 |
| 只开启内存跟踪 | 42.273 秒 | 5.439 秒 | 47.712 秒 |
| 同时开启两种工具，与原测试相同 | 34.366 秒 | 3.755 秒 | 38.121 秒 |

本次开启内存跟踪后，写入和核对的合计时间约为相应关闭档的 4.0～4.6 倍。程序需要构造并释放大量临时字典、事件、文件成员和缓存副本；即使它们很快被释放，内存跟踪仍要记录这些分配。

每档只有一次顺序测量，没有重置操作系统缓存。SQL 计数档略快于普通档，同时开启两种工具也快于只开启内存跟踪，说明单次计时存在波动；不能把四档耗时直接相减，分摊出两个工具各自稳定的成本百分比。可以确认的是，内存跟踪开关对本次路径的耗时影响很大；当前没有证据把 SQL 计数单独认定为主要瓶颈。

本轮只对 200 份输入做了开关对照，不能把倍数直接套用到上轮 400 份输入的 107 秒写入时间，也不能据此推算整个容量测试或全量回归的提速。

证据：[四档结果](verification-data/2026-10-25-integration-batch-write-analysis/factor-results.json)、[对照汇总](verification-data/2026-10-25-integration-batch-write-analysis/factor-summary.json)、[冻结输入及模式](verification-data/2026-10-25-integration-batch-write-analysis/metadata.json)、[执行记录](verification-data/2026-10-25-integration-batch-write-analysis/execution.json)。

## 不开内存跟踪时，时间花在哪里

为定位正常操作中的成本，本轮另外恢复相同输入，只开启项目现有的事务阶段和 SQL 计量。这个样本没有开启内存跟踪、原测试的连接包装或 `cProfile`（函数调用剖析器）。写入总计 9.292 秒，再次核对结果另用 0.824 秒。

以下主阶段使用独占计时，可以相加；表中省略的小阶段合计约 0.040 秒。

| 主阶段 | 程序实际做什么 | 写入中的耗时 |
| --- | --- | ---: |
| 构造校验依据 | 为当前事件读取实际状态、形成检查上下文，并对生成的事件流独立核对 | 3.341 秒 |
| 生成事件 | 根据冻结文件重新生成本次应保存的正式事件 | 3.090 秒 |
| 逐条校验事件 | 根据实际保存事实检查每条事件是否成立 | 2.022 秒 |
| 规划 | 判断哪些文件合格、默认范围是否完整及本次需生成哪些结果 | 0.742 秒 |
| 插入和更新数据库 | 保存历史、业务投影和相关索引记录 | 0.052 秒 |
| 最后提交 | 执行唯一一次 COMMIT | 0.0048 秒 |

本次写入有 59718 次 SQL 调用，交回 84894 行；SQL 执行与取数计量合计 0.692 秒，已包含在上述主阶段内。大部分时间发生在读取之后的 Python 对象构造、解释和核对。这里的 0.052 秒是写入阶段耗时，不能当作全部数据库访问耗时；0.692 秒也不能再与主阶段相加。

再次核对结果在原测试计数包装下另有 12509 次 SQL，写入与核对合计 72227 次，与上轮相同规模的记录一致。它会根据原申请重新生成预期事件，并逐项比较已保存完整组，因此也有自己的读取和解释成本。

证据：[现有阶段计量结果](verification-data/2026-10-25-integration-batch-write-analysis/write-stages-no-profile.json)。该观察本身仍有开销，不能视为目标主机的性能验收。

## 为什么同一批数据会被处理这么多次

程序要分别完成以下责任：先判断能否发布，生成应保存的事件，由另一条检查路径核对事件，最后检查所有正式产物与原来源是否双向对应。各责任不能直接把上一阶段的判断当作自己的授权。

带函数剖析的独立诊断样本记录了下列调用次数。该样本的耗时受到额外观察影响，主要用于确认调用关系和次数；不拿它替换上一节的阶段耗时。

| 对象或动作 | 写入阶段的实测次数 | 实际含义 |
| --- | ---: | --- |
| 重新构造文件成员信息 | 3442 | 从成员记录、原发现页和固定文件事实重新形成可判断的成员 |
| 读取原发现页 | 578 | 同样两页数据反复用于多个成员和多个独立检查阶段 |
| 完整核对原发现页关系 | 113 | 重读原事务，检查发现页、实际文件及文件登记之间的完整对应 |
| 命中原行缓存后重新解释发现页 | 465 | 省去部分 SQL 和关系核对，但仍解析原行并构造完整页对象 |
| 解码历史事件 | 12875 | 包含反复核对原发现事务及固定文件历史时的事件解释 |

发现页最多包含 128 份文件。为了确认某个成员确实来自那一页，程序会读取和解释整页内容；完整关系核对还会读取原事务里的文件创建事件，并再次核对各文件身份。于是 200 份正式产物会触发远多于 200 次的对象处理。

成员构造次数取决于全部候选和默认范围的数量。令 N 为全部候选文件数量、S 为默认范围中的数量，当前这条路径的写入成员构造次数为 `17N + 3S`。本轮 N=200、S=14，因此恰为 3442 次：

| 责任步骤 | 成员构造次数 |
| --- | ---: |
| 规划本次结果 | `4N + S`，814 次 |
| 检查完成申请头及实际依据 | `4N + S`，814 次 |
| 生成正式事件，分别处理原片和预览 | `2N`，400 次；本例无预览仍会扫描该分支 |
| 独立生成预期事件并核对 | `2N`，400 次 |
| 最后发布，正向和反向核对成员、范围及实际产物 | `5N + S`，1014 次 |

固定文件读取入口另被调用 3842 次，其中真正加载 3742 次；从该入口看，只有 100 次被复用。`device_files` 全行查询总计 15289 次。它们分布在多个阶段，不能据此认定这些检查都可以删除。

代码入口包括[分段完成事务](../../apps/camctl/src/camctl/persistence/repositories/segment_transactions.py)、[成员读取](../../apps/camctl/src/camctl/persistence/repositories/segments.py)、[原发现页的完整关系核对](../../apps/camctl/src/camctl/persistence/repositories/result_pages.py)及[命中后仍重新解码的路径](../../apps/camctl/src/camctl/persistence/repositories/result_pages.py)。逐阶段推导和调用方数据见[路径分析](verification-data/2026-10-25-integration-batch-write-analysis/path-analysis.json)、[函数计数](verification-data/2026-10-25-integration-batch-write-analysis/selected-function-counts.json)及[按阶段汇总的 SQL](verification-data/2026-10-25-integration-batch-write-analysis/write-sql-groups.json)。

## 已有缓存为什么没有消除这些成本

当前设计同时限制驻留内存，并要求独立检查重新取得实际保存依据，见[单次完整事务读取复用](persistence-runtime.md#单次完整事务的读取复用)和[结果页证明范围](persistence-runtime.md#结果页证明的事务与校验阶段范围)。

具体而言：

- 每条事件形成校验上下文后，内核清空此前的页记录和通用读取依据，使独立检查不能直接沿用生成方的判断；本连接写入后，通用读取结果也会失效。
- 原页窗口保存紧凑的 SQLite 原行，不保留完整解码对象图。命中可以减少查询和完整关系核对，但仍须重新解码并检查页结构。
- 通用读取缓存有条目数和字节数上限。满 128 份文件的一页，再加动作、历史事务和其他事实，不能保证第二次遍历时所有文件都仍在缓存中。本轮没有逐项记录淘汰原因，因此不把全部重读都归因于缓存容量。
- 缓存保存、命中时还会复制可变值并估算保留字节数，这些工作也会分配对象，并受内存跟踪影响。

因此，“峰值内存保持在约 2.2 MB”和“累计处理工作很少”是不同结论。大量临时对象可以及时释放，使峰值受控，同时仍消耗较多 CPU 和内存跟踪时间。

## 哪些解释已经可以排除

上轮测试的六次主动完整内存回收合计只有 0.317 秒；索引查询计划和逐虚拟机指令回调在写入、核对和内存测量结束后执行，不能解释两个主要慢段。详见[测量窗口审计](verification-data/2026-10-25-integration-batch-write-analysis/measurement-window-audit.json)。

当前完整完成组的首尾和数量核对，在写入阶段计数为 0、再次核对结果时为 1。诊断中另有数千次针对既有小历史事务的范围检查，不能把它们说成反复扫描当前完整完成组。固定文件已使用自身最后历史边界，产物查找也已使用唯一索引；这些既有优化仍在生效。

该输入未进入严格文件差集证明的实质工作；对应入口虽然被调用 3442 次，但带函数剖析时累计只有 0.022 秒。单次产物索引查找的 23 个虚拟机步骤，以及约 2.2 MB 的峰值，也不足以证明全表扫描、内存泄漏或平方级增长。

## 后续怎样推进

当前证据支持继续区分两件事：容量测试为了记录峰值而增加的耗时，以及生产路径本来就执行的重复解释和核对。

内存跟踪是这项容量验收的组成部分，不能简单关闭后仍声称原验收通过。本轮开关实验只是诊断，不替代原 20／200／400 三档测试。SQL 计数包装没有表现出稳定的大额成本，也没有证据表明仅把两类测量拆开就能提速。

若继续减少实际操作的工作量，优先核对同一次独立检查内部的重复成员构造、原页解释和文件事实读取，并记录缓存命中及清空原因。跨规划与独立检查直接共享授权、删除反向核对、扩大缓存或长期保留完整解码页，都涉及当前正确性及内存边界，不能直接作为现成修复。生产实现的优化需单独确定范围，并保留提案后事实变化、损坏历史、真实完整提交及原键恢复等回归。

本轮已确认主要成本和重复路径；尚未测得每一种复用方案的净收益，也没有选择删除哪条检查。
