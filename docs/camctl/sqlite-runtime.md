# SQLite 运行库与部署要求

[初始化](../architecture/initialization.md) · [连接与事务](persistence-runtime.md#数据库连接与完整事务) · [结构检查](database/schema/README.md#初始化与验证)

camctl 使用 Python 标准库 `sqlite3` 访问主机状态库。部署是否合格，取决于该 Python 进程实际链接的 SQLite、所需功能和目标文件系统；安装了新版 `sqlite3` 命令行工具，并不表示 Python 已使用同一运行库。本页定义 camctl 状态库的统一要求，客户端使用的 Node.js 数据库另按客户端部署规则管理。

## 允许的版本

[版本条件文件](sqlite-runtime.json)是版本门槛与回移修复例外的唯一维护来源。它用整数数组表示版本分量；`sqlite_mainline_minimum` 是主线最低版本，`sqlite_fixed_backports` 逐项列出允许的旧分支修复版，`python_minimum` 表示接口所需的最低 Python 版本。以下表格由现有规格检查脚本从该文件生成，其他文档引用本页。

<!-- SQLite 版本条件生成开始 -->

| 条件 | 允许范围 |
| --- | --- |
| Python 接口 | 3.11 及后续版本 |
| SQLite 主线 | 3.51.3 及后续版本 |
| SQLite 旧分支例外 | 3.44.6、3.50.7；仅精确匹配这些版本 |
| 其他 SQLite 版本 | 不允许 |

<!-- SQLite 版本条件生成结束 -->

版本按整数分量比较，不按字符串字典序比较。达到主线门槛，或者精确匹配回移修复清单，才通过版本条件；不能将最小回移版本变成全局下限，也不能自动放行未列出的旧分支版本。版本信息缺失、类型非法或不能可靠取得时，检查失败。

SQLite 官方说明，WAL-reset 缺陷可能在多个连接交叠写入和执行检查点时损坏数据库；官方同时列出主线修复版本及两个旧分支的回移修复。采用以上条件是为了满足本项目已确定的 WAL 并发使用方式，修复依据见[官方 WAL 说明](https://www.sqlite.org/wal.html#walreset)和[主线修复发布记录](https://www.sqlite.org/releaselog/3_51_3.html)。

官方将 `STRICT` 表的特性门槛定义为 SQLite 3.37.0，但这一数字仅表示能够识别该表结构，不是本项目的部署基线，见[STRICT 表说明](https://www.sqlite.org/stricttables.html)。功能可用也不证明某个并发缺陷已经修复，版本条件与功能检查必须同时满足。

## 取得哪个运行库的信息

生产入口和部署检查均读取当前进程的 `sqlite3.sqlite_version_info`，诊断同时记录 `sqlite3.sqlite_version`、Python 版本和实际解释器路径。SQL `sqlite_version()` 应与该运行库一致；`sqlite_source_id()` 用于记录构建身份，不用它替代版本和功能检查。Python 对这些运行库属性的定义见[标准库说明](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.sqlite_version)。

生产部署仍以项目既定的 Python 3.11 与 ARM64 主机为目标。开发环境使用更高 Python 版本通过检查，只证明这个开发环境具备相应能力。系统包版本、Python 包装模块的版本和 Node.js 内嵌 SQLite 的版本都不能代替目标 camctl 进程的检查结果。

构建来源也须能够确认：不得仅修改版本字符串来声明修复完成。低于主线门槛且未列入例外的发行商补丁包，不能自动获得准入；若部署确需采用，应先核实其补丁与能力，再更新统一版本条件。版本准入不是自动升级许可，部署发行物仍须固定具体解释器、SQLite 构建及依赖，并记录检查结果；更换运行库后重新验证。

## 必需能力与检查时点

版本条件通过后，仍须实际执行本项目需要的操作，不能只检查方法名存在或库能打开文件。

| 检查对象 | 必须取得的结果 |
| --- | --- |
| 规格 SQL | 真实结构能够建立，`STRICT` 类型约束、外键、索引及生成列按[结构检查](database/schema/README.md#初始化与验证)通过验证 |
| JSON 函数 | `json_valid`、`json_type`、`json_extract` 能按规格处理对象及字段；具体编译能力以实际调用为准，见[SQLite JSON 函数](https://www.sqlite.org/json1.html) |
| 增量 BLOB 接口 | 使用 `zeroblob` 分配内容，实际通过 `Connection.blobopen` 分段写入并读回相同字节；接口规则见[Python BLOB 说明](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.Connection.blobopen) |
| 文件数据库的 WAL 与 FULL | 新建隔离的检查库，确认设置结果确实为 WAL、写连接同步等级为 FULL；已有业务库继续按[连接规则](history-storage.md#所有状态库写连接使用-full-同步)逐连接核对 |
| 多连接与线程支持 | 运行库不是单线程编译模式；不同连接能按既定线程归属独立使用。多连接读视图与提交须通过软件集成验证，不以短小检查证明所有并发场景 |

显式部署检查可在临时文件数据库中验证这些能力；它不打开、创建或修改业务状态库。内存数据库不能证明目标文件系统支持 WAL，开发容器的临时库也不能证明目标 eMMC 的同步和断电行为。

`init`、`run`、`submit` 及报告子进程在打开业务状态库之前，检查实际运行库的版本和接口能力；进程内检查结果可以复用，不逐次数据库操作重复探测。日常检查可使用隔离的内存库验证 SQL、JSON 和 BLOB 基本能力，不为此在业务库写入探针数据或新建磁盘状态库。实际连接打开后再核对该连接的 WAL、同步及外键配置。`describe` 仍只读取配置与驱动定义，不增加状态库或 SQLite 部署资格前提。

| 版本、能力与连接条件 | 处理 |
| --- | --- |
| 版本准入且能力、连接条件全部成立 | 按正常数据库入口执行；业务格式和目录绑定仍须分别检查 |
| 版本不在允许范围，或 Python 接口、SQL 功能、线程支持不满足要求 | 按运行环境配置不兼容拒绝使用状态库，诊断记录具体缺项；不靠取消 WAL、降低同步或忽略约束继续执行 |
| 版本或能力检查无法可靠完成 | 保留检查步骤及底层原因并停止，不解释为能力可用 |
| 运行库合格，但实际状态库无法打开、结构无效或连接设置失败 | 按原状态库错误处理；不将数据库错误改写为版本不兼容，也不重建空库 |

`run`、`submit` 在入口检查发现运行库不兼容时采用 `configuration_error`；`init` 按初始化失败输出。这些入口不受理业务、不执行设备或文件发布操作，也不把未执行的动作改成失败。错误诊断保留实际运行库和缺少的能力，见[会话错误分类](../architecture/session-errors.md#错误标识)。

报告子进程在发送就绪通知之前完成运行库检查；不兼容时报告启动失败及具体原因，不打开业务库或开始生成。若主进程自己的运行库、状态库及执行条件仍可靠，按[报告启动失败](report-runtime.md#报告生成使用独立进程)保留报告责任，普通设备执行继续；退出时责任仍未完成则采用 `report_error`。子进程随后打开状态库遇到的数据库错误仍按 `state_db_error` 处理。普通日志及独立日志副本继续遵守不依赖状态库的规则。

## 设计检查与生产验收边界

在仓库根使用所需 Python 解释器运行现有脚本：

```sh
~/.venv/bin/python -B scripts/check-database-spec.py --runtime-only
~/.venv/bin/python -B scripts/check-database-spec.py
```

前者核对统一版本条件和当前解释器，并使用临时库验证必要能力；后者还执行完整规格 SQL 与结构样本。修改版本条件后，运行同一脚本的 `--write-runtime-doc` 更新本页版本表，再执行默认检查。脚本是设计与部署核验辅助工具，尚未接入生产入口，不安装或升级运行库。

验收见[V-01—V-04](database/consistency-verification.md#sqlite-运行库与部署版本)。版本边界样例只验证准入逻辑，不表示本机实际运行过所有允许版本；短小 WAL 检查也不复现或证明底层并发缺陷修复。目标构建须另外完成真实 WAL 多连接、历史恢复、报告生成及既有性能检查；物理断电与硬件性能按目标主机联调安排。
