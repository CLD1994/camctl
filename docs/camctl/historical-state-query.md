# 历史状态查询与报告重建

[返回 CLI 资料入口](README.md) · [历史存储与事件](history-storage.md) · [历史快照维护](history-snapshots.md)

报告需要重建冻结边界处的对象状态，而数据库中的当前投影仍会随业务推进。本页规定如何从当前投影逆向恢复，或从历史快照正向恢复，再分批写出确定不变的报告文件。恢复只处理查询副本，不修改真实业务状态，也不执行设备或文件交接操作。

阅读前先了解[事件、历史位置与业务变化序号](history-storage.md#先理解事件历史位置与业务变化序号)。H 表示报告已经登记的冻结历史边界；C 表示读取某份当前投影时，同一短读事务视图中的完整已提交边界，要求 C≥H；S 表示不晚于 H 的历史快照边界。不同对象可以采用不同的 C 或 S，但都须恢复到同一 H。

本页先说明查询目标和恢复路径，再说明一致读取、分页和逐层写出，最后列出性能边界与验收。事件恢复依据、序号、查询目录及数据库连接设置见[历史存储](history-storage.md)，快照的生成和调度见[历史快照维护](history-snapshots.md)。第一版范围见[实现规格](implementation.md#第一版实现范围)；具体接口、容器容量及清理方式的待细化事项列在页末。

## 查询目标

数据库永久保存不可变历史，并在每次写入历史的同一事务中更新当前投影。普通业务查询使用可靠的当前投影。

报告需要取得冻结边界处的实体状态。同一报告在首次生成、断电恢复和补投时，必须使用同一组冻结依据并生成相同字节。当前投影继续变化，因此需要能够取得旧状态的查询方法。

全量读取历史、回放事件、组织报告及编码文件是不同成本。即使不再回放全部历史，如果仍把全部事件载入内存，每份报告仍会支付随历史增长的读取和对象构造成本。分批读取只能限制部分内存占用，独立进程只改变执行位置，二者都不能减少必须处理的事件数量。

## 从当前投影逆向恢复

事件保留恢复旧状态所需的变更前后值，查询从当前投影的副本出发，按逆序恢复目标边界之后的变化。

例如，下表仅用于说明状态恢复，不定义新的动作状态协议：

| 历史位置 | 已保存事实 | 状态恢复所需信息 |
| --- | --- | --- |
| H100 | 动作 A 正在执行 | 当时的实体状态 |
| H110 | 更新了一项诊断 | 该字段原先是否存在、原值及新值 |
| H120 | 确认动作 A 完成 | 被改变字段的原值与新值，包括状态和完成结果 |

如果当前投影位于 H120，而报告冻结在 H100，查询先恢复 H120 改变的字段，再恢复 H110 改变的字段，得到 H100 的状态。这里只改变本次查询的数据副本，不改变真实动作、数据库当前投影或已有历史。

事件继续表达有独立含义的业务事实，并携带必要恢复依据。事件的业务含义、正向更新规则和逆向恢复规则必须一起定义，不能只保存字段变化而丢失事实的含义。

所有影响报告重建的状态变化都必须具有完整恢复依据。事件与受影响的当前投影在同一事务中保存，正向回放继续用于投影重建和一致性验证。旧值必须对应本次事务中实际发生的变化，不能使用事务外读取、可能已经过时的状态。

## 状态分类

| 情况 | 处理规则 |
| --- | --- |
| 投影与相关历史可靠，在 `(H, C]` 中没有报告所需状态的变化 | 直接使用 C 的相关投影；报告实体选择与元数据仍取自冻结依据 |
| 上述前提成立，存在需要恢复的相关变化 | 按恢复路径选择规则，在副本上使用快照正向恢复或当前投影逆向恢复到 H |
| 对象在 H 之后创建 | 在 H 的结果中为不存在，不混入冻结报告 |
| 当前投影缺失、落后或不一致 | 按现有投影恢复规则重建并验证，不把坏投影用作逆向起点 |
| 事件缺失必要恢复依据、数据不一致、未知事件无法解释或数据库读取失败 | 明确按状态库错误处理，不以默认值补齐，也不把损坏静默解释为普通性能降级 |

报告正常生成与重建都使用这套分类。不能仅凭报告是首次生成就认定当前投影可用，也不能仅凭报告较旧就认定所有实体都发生过变化。

### 按对象选择恢复路径

先按上述规则处理数据库错误、投影失效及对象在 H 尚不存在的情况。对在 H 存在、所用依据可靠的对象，按下表顺序选择路径。S 表示不晚于 H 的最近可用历史快照位置。

| 条件 | 处理方式 |
| --- | --- |
| `(H, C]` 内对象没有相关状态变化 | 直接使用当前投影 |
| 对象在 H 之后有变化，存在 S＝H 的快照 | 直接使用该快照 |
| 对象在 H 之后有变化，没有不晚于 H 的快照 | 从当前投影逆向处理 `(H, C]` 的相关事件 |
| 对象在 H 之后有变化，存在 S＜H 的快照，正向所需事件更少 | 从快照正向处理 `(S, H]` 的相关事件 |
| 上述两条路径都有依据，逆向所需事件更少 | 从当前投影逆向恢复 |
| 上述两条路径所需事件数相同 | 从当前投影逆向恢复，复用已经取得的投影副本 |

比较对象自身的相关变化次数，不以全库历史位置的数值距离估计。采用[实体历史关联与累计变化计数](history-storage.md#实体历史关联与累计变化计数)，一条事件改变一个实体需要恢复的状态计一次；计数与事件、目录和投影同事务更新，快照保存对应计数。通过索引取得 H 处的计数后，以计数差计算两段范围的相关变化数，避免为选择路径而读取两段完整事件正文。具体列名和索引实现仍需细化。

例如，S 处累计变化 20 次，H 处 28 次，C 处 328 次，正向处理 8 次，逆向处理 300 次，选择快照路径。事件数量是第一版的成本估计，不保证实际耗时始终最小；单条事件大小、读取与解码成本仍纳入性能验收。

若 S、H、C 处累计计数分别为 20、28、36，正向与逆向均需处理 8 条相关事件，则从当前投影逆向恢复。无需回放或恰好命中快照的情况先按表中前置分支处理，再对需要回放的两条可用路径比较事件数。

同一报告可对不同对象选择不同路径，所有对象最终都恢复到同一 H。事件正文可复用读取和解码结果，实际状态恢复按各对象所需的事件区间与方向进行；事件涉及多个对象时，必须分别处理本次需要恢复的对象影响，每个对象对同一事件的影响只应用一次。对象之间的关联及父对象完整状态均遵守同一边界，不执行外部副作用。

缺少可选历史快照时可按表使用逆向路径；检测到计数、快照或所需历史损坏、无法解释时按状态库错误处理，不能把数据错误当作普通缓存未命中。

## 读取流程与边界

每份当前投影副本都绑定读取时取得的 C，且满足 `C ≥ H`。不同批次可以有不同的 C；本节未带下标的 C 均指正在恢复的投影副本对应的位置。主进程与报告进程按以下顺序配合：

1. 主进程登记报告身份、H、覆盖水位及固定生成元数据。
2. 报告进程使用自己的只读连接核验状态库及报告冻结依据，按固定业务区间和历史关联分批选择实体，补齐 H 处的必要父对象与关联。
3. 在短读事务内一起取得本批当前投影、对应的 C 及当前累计变化计数，将所需数据复制到本批内存，结束查询和读事务。父对象自身状态与子实体分别处理，读取不要求组装整棵对象树。
4. 按[对象恢复路径规则](#按对象选择恢复路径)，选定该投影副本或不晚于 H 的可靠历史快照。H 处的历史计数和已有快照可以在另一次短读事务中取得；它们必须明确对应所需历史位置。选定快照后固定其身份、S、格式、计数与内容。
5. 通过索引分批读取固定范围内的历史：逆向使用 `(H, C]`，正向使用 `(S, H]`。每批读完均结束查询和读事务，再在独立副本上应用本批事件；一个对象有大量历史时也按此方式分批。
6. 对象恢复至 H 后，在事务外按固定顺序编码并写入同一份 `staging` 报告。释放不再需要的数据，继续后续对象。已写父对象与后来恢复的子对象均表达 H 处的状态。
7. 全部内容写出后完成摘要及文件同步，再交由主进程组织发布与保存发布事实。

当前投影副本与它的恢复范围始终绑定：即使后来读取历史时数据库已推进到 C2，原先在 C1 取得的副本也只处理 `(H, C1]`。后续提交不会改变这个已提交历史区间的内容。

### WAL 与分批短读事务

状态库采用 SQLite WAL（预写日志）模式，连接的同步、忙等待和自动检查点设置见[状态库连接规则](history-storage.md#所有状态库写连接使用-full-同步)。每次需要一起取得可变数据及其版本位置时，显式开启短读事务，通过首次读取建立一致视图；例如，当前投影与对应 C 必须来自同一视图，见[SQLite 隔离说明](https://www.sqlite.org/isolation.html)。报告的一致性由固定 H 和各份恢复依据的明确范围保证。

跨事务读取成立的前提是：已提交历史、历史事务分组及查询目录中的既有关联不被改写或删除；新事件及关联只能追加到新的历史位置。已提交的历史快照内容不变。整个任务使用同一状态库，数据库格式升级及派生结构重建遵守维护与日常运行隔离的规则；具体协调机制仍需细化。

| 所读数据 | 每次查询必须保持的依据 | 后续提交后的处理 |
| --- | --- | --- |
| 报告登记信息 | 同一报告身份、H、覆盖水位及生成元数据 | 不用较新的 ACK 或同步责任改写本份报告范围 |
| 入选实体及父子关系 | 冻结业务区间、H 和历史关联 | 新对象及关系变化不改变 H 处的入选集合和所属关系 |
| 当前投影及当前计数 | 在同一短读事务内取得投影、计数与 C | 保留副本及 C，恢复期间不替换为较新的当前值 |
| H 处的历史计数 | 对应实体在不晚于 H 的末条历史关联 | 可另开短读事务查询，结果仍对应 H |
| 历史快照 | 已选快照身份、S、格式、计数与内容，且 S≤H | 本对象恢复期间保留已选依据；后来新增快照不改变它 |
| 逆向事件分页 | 对应实体、固定 `(H, C]`、方向和最后已读位置 | 后来的事件查询仍以上述 C 为上限 |
| 正向事件分页 | 对应实体、固定 `(S, H]`、方向和最后已读位置 | 后来的事件查询仍以上述 H 为上限 |

例如，报告冻结在 H＝100，交付 D 当时为 `preparing`。短读事务在 C＝120 取得 D 的 `prepared` 投影及 C，复制后结束读取。业务随后推进到 150，D 已发布；报告分多个短读事务读取 D 在 `(100, 120]` 的事件，每批结束读取后逆向恢复，最终仍得到 `preparing`。下一个对象可以从 C＝160 的投影出发，但也恢复到 H＝100。不同对象的 C、批次大小及实际读取时刻不改变最终报告字节。

每批数据取回后，先结束相关查询、释放未完成游标并结束显式读事务，再恢复状态、编码或写文件。仅调用一次事务结束命令，不足以代替对未完成查询的清理，见 [SQLite 查询与事务生命周期](https://www.sqlite.org/lang_transaction.html#implicit_versus_explicit_transactions)。批次之间可以复用连接；复用的是连接，不是上一次读取视图。必要的数据取回和复制仍发生在读事务内，其耗时计入单次读取预算。

同一次生成在批次之间暂时让出资源时，保留当前处理所需的恢复副本、固定范围、分页位置与编码进度，恢复后继续本次任务。这里没有发生生成失败，不构成新的报告尝试。若任务已经失败、取消或进程结束，则结束实际读取，保留未完成报告责任，半成品不发布；后续合法触发仍按既有规则从头生成。第一版按已有生成时限及异常生命周期处理，不增加按 WAL 积压触发的暂停协议。

缓存必须明确对应数据库身份和不可变事实，或对应实体在 C／H 的状态。使用当前状态缓存作为恢复起点时，必须证明它与绑定的 C 一致；父对象恢复到 H 后可按相同 H 复用。

WAL 支持读写并行，但慢查询及多个读取者交叠仍可能阻碍检查点推进和日志复用，见[WAL 工作方式](https://www.sqlite.org/wal.html)。短事务使报告能在批次之间释放读取，不能单凭批次数量或 `LIMIT` 宣称耗时有上限。联调测量查询计划、实际读取时长、WAL 积压、计划接纳延迟和完整报告的新鲜程度，用于确定适用负载及后续优化需要；第一版不承诺持续资源压力下的固定时延，不要求实现积压协调机制。

部署及各状态库入口按统一的[SQLite 运行库与部署要求](sqlite-runtime.md)核验 Python 实际链接的运行库。版本须满足 WAL 并发缺陷的修复条件，并通过所需能力检查；目标部署固定具体构建后，继续验证本节规定的读视图、短事务与并发行为。

Python SQLite 的连接上下文管理器不能单独证明已建立覆盖多次查询的读事务，实现须明确开启和结束事务，见[Python 事务说明](https://docs.python.org/3.11/library/sqlite3.html#transaction-control)。

## 存储接口与分批查询

当前状态查询、历史范围查询和原子写入应有分别明确的接口。写入只追加本次事实并更新受影响的投影；一次局部变化不应重新遍历、序列化或尝试插入全部已有历史。

批量生成报告时，应避免对每个对象重复扫描整段全局历史。分页必须保持冻结边界、入选条件或恢复范围及排序依据一致；每页使用短读事务，新提交不进入已经固定的范围。

批次返回结构及结束判定遵守[分页结果契约](module-contracts.md#分页结果契约)。以下规则定义历史查询的范围、排序和候选筛选，不能由通用批次结构代替。

### 按最后一个排序值续读

报告查询采用游标分页，即每批返回后记住最后一个排序值，下一批从该值之后继续读取。实体在各自所属集合内按 ID 的整数值升序读取，历史事件按恢复所需的历史顺序读取。分页位置必须完整表达排序依据并能唯一定位一项；事件使用 `event_seq` 区分同一事务内的不同事件。

| 读取情况 | 下一批的范围 |
| --- | --- |
| 某个集合或事件范围首次读取 | 从该范围在规定方向上的第一项开始 |
| 实体集合已返回一批 | 在同一集合及入选条件下，读取 ID 的整数值严格大于本批最后一个 ID 的实体 |
| 正向恢复已返回一批事件 | 在同一对象和恢复区间内，读取位置严格大于本批最后一个事件位置的事件 |
| 逆向恢复已返回一批事件 | 在同一对象和恢复区间内，读取位置严格小于本批最后一个事件位置的事件 |
| 查询成功且该范围无剩余项 | 结束该范围的读取 |
| 查询失败或取消 | 按相应失败或取消规则处理，不将缺失结果当作范围读完 |

每个集合分别维护分页位置。例如，动作 A 的产物读取完毕后，动作 B 的产物从 B 的集合开头读取。实体分页位置绑定数据库身份、H、固定入选条件、父对象和实体类型；事件分页位置另外绑定对应对象、恢复方向及固定的 `(H, C]` 或 `(S, H]`。每页取回数据后结束查询和读事务，在事务外处理，下一页重新开启短读事务。分页位置是本次生成的临时状态，批次之间暂时让出资源时保留；任务失败或进程结束后按报告恢复规则重新生成。

实体选择先按身份合并，再按实体排序和分页返回；同一实体在业务区间内多次变化也只返回一次。合并是查询结果契约，不要求先在 Python 中保存全部入选实体。查询接口、索引及执行计划需保证有序续读，不反复扫描已处理前缀；同时验收实体选择、去重和排序的读取量及资源开销，不能仅凭采用游标分页就认定查询高效。相关索引能力见 [SQLite 连续分页说明](https://www.sqlite.org/rowvalue.html#scrolling_window_queries)。

报告变化目录的具体索引、候选容量和 SQL 由[报告对象选择](database/report-changes.md#报告对象选择的索引与分页)统一定义。每个冻结范围和对象类型先进行一次有上限的候选预查询：完整候选能容纳时，在有界整数集合中去重排序后分批交付；否则释放候选，按对象 ID 从索引续读。路径在交付第一批前确定，不对每一页重复执行范围预查询；两条路径均遵守本节的冻结范围、短读事务和分页位置规则。

例如，每批读取两个入选产物，按整数顺序依次返回 ID 为 1、4 的产物，再从 ID 大于 4 的位置返回 7、12，之后确认没有剩余项。ID 无需连续，批次大小变化不改变入选实体、排序或报告字节。批次数量由下文的独立配置控制，具体接口类型和完成标记仍需细化。

### 实体与事件读取批次分别配置

报告生成及重建使用两个独立的主机本地 TOML 配置项，部署时可以分别调整：

| 配置项 | 默认值 | 单位与适用范围 |
| --- | --- | --- |
| `history.entity_batch_size` | `32` | 对象数；读取一个实体集合时，每页最多返回的入选实体数量，各类实体集合共用此值 |
| `history.event_batch_size` | `256` | 事件数；恢复一个对象时，在其已选历史范围内每页最多返回的相关事件数量，正向与逆向共用此值 |

实体批次读取对象自身状态，父对象与子实体集合按既定层次分别处理。事件批次控制该对象的历史分页，一个对象可以需要多个事件批次；无需恢复的对象直接使用已确定的状态。两项参数各自控制所属查询的返回数量，不规定并发任务数量。快照维护使用其独立的 `history.snapshot_batch_size`。

两项配置均为正整数，0、负数、浮点数、布尔值和字符串等非法值按[本地配置的加载与更新](../architecture/configuration.md#本地配置的加载与更新)报告配置错误。各项省略时使用本节定义的对应默认值。主进程在会话启动时加载并校验配置，将生效的读取批次参数传给报告进程；报告进程在本次会话内沿用这些值，包含故障后重新创建的报告进程。

| 配置情况 | 处理 |
| --- | --- |
| 两项均省略 | 分别使用各自内置默认值 |
| 只提供实体批次的合法值 | 实体读取使用该值，事件读取使用其默认值 |
| 只提供事件批次的合法值 | 事件读取使用该值，实体读取使用其默认值 |
| 两项均提供合法值 | 各类读取分别使用对应值 |
| 任一项非法 | 按配置错误结束调用，不开始报告读取 |

本次会话内值固定，部署调整后由后续会话加载。已有报告重建可以采用后续会话的批次设置，报告身份、冻结依据、入选对象、恢复结果及最终字节保持不变。各页仍使用短读事务，读完后释放查询和事务，再恢复状态或写出；候选不足一页时处理实际取得的数据，不等待凑满。

实现须避免为一批实体同时预载各自的完整历史。批次影响查询次数、单次读取工作量和临时数据数量，实际资源消耗及延迟由测试与联调验证。

默认值是第一版的初始工程取值，尚无实测性能依据。实体批次保持较小，控制同时保留的完整对象状态数量；事件批次采用较大的数量，减少长历史恢复中的分页次数。事件本身也可能较大，数量上限不保证固定的字节量或处理时长。联调分别覆盖大实体、长历史及较大的事件正文，按查询次数、读取量、实际峰值和业务延迟独立调整这两项参数。

### 分批读取与分段生成报告

camctl 与第三方主程序及其他软件共享主机内存。报告采用分批读取、恢复状态并逐步编码写出的方式，以适应超过可用内存的整体报告规模。内存中保留当前处理所需数据和有容量限制的缓存，已处理且不再需要的内容及时释放。

报告从新的 `staging` 文件开始生成。编码器维护对象、数组、分隔符及当前写入位置，依次写入 JSON 片段，无需读取或重新解析已经写出的部分。最终只形成一份完整报告，客户端按既有协议读取。任务失败、取消或进程结束后的 `staging` 文件按报告恢复规则从头生成；同一次生成在批次之间暂时让出资源时保留已有进度。

| 约束 | 要求 |
| --- | --- |
| 输出内容 | 仅包含本份报告选中的对象状态及必要父对象，不向客户端输出恢复事件历史 |
| 数据一致性 | 所有批次使用同一冻结依据；每份投影绑定自己的 C，历史查询限定在对应恢复区间，每个对象恢复到同一 H |
| 确定性 | 批次大小、缓存命中、正反向恢复路径不改变对象排列、JSON 编码及最终字节 |
| 处理范围 | 限制每批实体与事件数量，保留当前处理所需的父对象、恢复状态和续读位置；缓存、去重记录及编码缓冲有容量上限，已处理内容及时释放 |
| 第一版数据范围 | 按单个字段能在目标部署环境中正常处理来设计和验收；累计实体、子集合和相关历史数量增加时仍须分批处理 |
| 发布条件 | 全部入选对象和所需事件处理完成，完整内容、摘要和所需同步均成功后才交由主进程发布；容量限制不改变输出内容 |
| 读事务时长 | 每批取回数据后结束查询和事务，再恢复状态及写文件；联合评估单次读取时长、检查点推进、WAL 积压和主进程业务延迟 |

报告遵守[通过处理流程控制资源使用](implementation.md#通过处理流程控制资源使用)的规则。实体与事件读取批次分别按上述配置控制，缓存条目数、队列容量与满载处理、读写缓冲大小及分页查询接口仍需确定。实际资源消耗由测试与联调测量，覆盖 camctl 主进程、报告子进程及其管理的工具进程共同运行的情况，部署参考条件见[运行环境](implementation.md#目标环境与部署分工)。

### 逐层分批写出与实体排序

生成器按计划、动作及其产物或交付的所属关系逐层读取和写出。先写当前父对象的自身字段，再打开需要输出的子集合，分批恢复和写出入选子实体；当前子集合完成后关闭它，再继续后续集合或对象。顶层计划文件诊断也分批生成。数据库读取使用分批短读事务，恢复与写出在事务外进行，所有状态均恢复至同一 H。

查询接口按[报告格式中的实体排序规则](../architecture/report-format.md)返回入选实体，并保证跨批次不遗漏、不重复。父对象因自身变化和多个子实体变化同时入选时，也只输出一次。应用不先收集全部实体再排序或维护随报告总量增长的去重集合；采用上述游标分页，具体 SQL、索引、位置的字段表示及数据库查询的资源占用仍需细化和验证。

例如，计划 P 的动作 A 有一万个入选产物，可以先写 P 和 A 的自身字段，再每批处理 100 个产物，完成后继续 P 的下一个入选动作。100 仅为批次数量示例，改为 50 或 200 不改变输出字节。内存保留当前父对象、当前批次及有容量限制的缓冲，不组装整棵计划或动作子树。

| 场景 | 处理要求 |
| --- | --- |
| 仅父对象自身变化，无入选子实体 | 输出父对象自身字段；子集合表达遵守固定生成规则 |
| 一个或多个子实体入选 | 补齐所属父对象的完整自身字段，仅输出入选子实体 |
| 父对象自身和子实体均入选 | 合并为一次父对象输出，不重复对象或子集合成员 |
| 子集合跨多个批次 | 保持同一个 JSON 数组的写入位置和顺序，写完一批不关闭该数组 |
| 跨计划引用 | 按各实体实际所属关系输出，引用不扩大入选范围或复制被引用实体 |

对象自身字段、实体子集合的输出次序、紧凑排版及可选空实体集合的省略方式遵守[第一版生成器的结构与排版](../architecture/report-encoding.md#第一版生成器的结构与排版)。数字输出遵守[精确数值与统一写法](../architecture/report-encoding.md#精确数值与统一写法)，字符编码遵守[字符串与转义](../architecture/report-encoding.md#字符串与转义)。参数或结果中的普通数组保留原有顺序，不按实体排序规则重排。

## 收益与性能边界

假设数据库已有一百万条历史，新报告冻结后又提交十条相关变化。具备完整恢复依据及范围索引时，逆向方法需要读取本份报告的对象状态并处理这十条变化，无需计算之前的一百万条历史。这是算法示例，不是实测性能数据。

若目标边界很早，且相关实体在其后仍变化了几十万次，逆向方法依然昂贵。它将回放量从“目标之前的相关历史”换成“目标之后的相关历史”，并未使任意历史查询都具有固定成本。已长期稳定的实体则可能直接使用当前状态，即使全库增长了很多无关历史。

完整同步可能需要输出大量实体。无论采用哪种状态恢复方式，读取并编码这些输出本身都有成本。

事件中增加旧值会增大永久历史存储。内存、可用存储、CPU 与存储带宽均按实际部署及共享负载评估，运行保障不依赖某款设备或某个固定内存额度。报告生成时间、计划接纳延迟、主进程调度延迟、客户端可取得报告的冻结位置距当前业务的滞后、读取量、峰值内存与新增存储需要分别测量。持续负载超过实际存储能力时，短读事务不能保证固定时限内交付。

## 待细化事项与验收

实施前还须细化有序分页接口、可变状态读取粒度、缓存适用性及条目上限、队列容量与满载处理、读写缓冲大小和取消清理，并验证实际表、索引及查询计划。正常新报告、断电后补投、较旧报告和完整同步四类负载的规模与验收预算也须明确。

本页沿用[历史存储契约](history-storage.md)规定的事件序号、分配范围、初始化边界、事务分组、WAL 和同步规则，并使用[历史快照维护](history-snapshots.md)提供的可靠快照。各专题分别保留存储和维护的验收要求；查询、恢复和输出至少覆盖下表。

| 验证目标 | 场景与预期 |
| --- | --- |
| 恢复准确 | 多次覆盖同一字段、字段不存在与显式空值、创建边界、集合成员加入与后续修改、终态及父子关系变化，得到独立定义的旧状态 |
| 父状态恢复 | 最后一个未结束动作完成并改变计划状态，逆向恢复动作和父计划；补齐父计划自身字段无需读取全部子动作 |
| 并发一致 | 取得投影与 C 后结束事务，再提交新变化；历史分页仍限定原 C，多对象采用不同 C 后均恢复至同一 H |
| 入选集合稳定 | 分页之间新增对象、修改入选对象或改变关系，按冻结区间和 H 查询仍无遗漏、重复或未来对象混入；H 处父子关系正确 |
| 读取依据稳定 | 当前计数与投影一起取得，H 的计数及已选快照跨事务读取仍对应固定位置；分页中出现新快照不替换本对象的恢复依据 |
| 事务释放 | 在历史恢复、编码及文件写入处暂停，验证该任务没有保留活动数据库查询或读事务；同一对象的大量事件也逐批释放 |
| 负载与持续推进 | 持续提交计划并产生业务变化，组合慢存储、CPU 竞争、完整同步及长历史，测量 WAL 积压、计划接纳延迟与完整报告产出；不以单次报告总耗时或物理 WAL 文件大小代替这些指标 |
| 回放无副作用 | 正向与逆向路径只生成查询结果，不改变当前投影，不执行外部操作 |
| 报告不可变 | 后续业务变化、配置变化、进程重启及重新生成后，原报告字节相同 |
| 分批编码 | 改变批次大小及缓存容量，包含跨批父子关系、特殊字符和空集合，输出仍为相同完整 JSON；中断不发布半成品 |
| 结构与排版 | 改变自身字段的构造顺序，含嵌套参数对象和中文，输出顺序与字节不变；验证 UTF-8、无 BOM、紧凑分隔符和唯一结尾 LF；空实体集合省略，参数中的空数组、空对象及 null 保留 |
| 字符串编码 | 字段名和字符串值覆盖中文、表情、引号、反斜杠、全部 U+0000～U+001F 控制字符及正斜杠；等值合法转义生成同一字节，异常输入诊断中的转义文本可编码且准确保留 |
| 数字格式 | 覆盖正负零、非零正负数、尾随零、指数写法、绝对值在 `0.000001` 与 `10²¹` 两个分界的两侧及恰好等于分界；保留全部有效数字，保存与历史恢复后输出字节一致 |
| 有序嵌套 | 覆盖仅父对象、仅子实体、父子均变化、跨计划引用和同实体多次变化；跨批次无遗漏或重复，父对象只输出一次，不加入未入选兄弟实体 |
| 排序边界 | 实体 ID 覆盖 2、10、100、超过 JavaScript 安全整数的相邻值及最大合法值，按精确整数值升序排列；参数和逐项结果等普通数组保持原有顺序 |
| 分页边界 | 覆盖空集合、单项、恰好一批、多批、ID 不连续、切换父对象和同实体多次变化；批次大小变化不遗漏或重复实体，查询失败不判为读完 |
| 历史分页 | 正反向恢复均覆盖同一事务内多事件跨批次，以及区间上下界；每个对象所需事件影响恰好应用一次，后续并发提交不混入读取 |
| 读取批次配置 | 两项均省略、仅覆盖其中一项、分别覆盖两项和非法值；只改变一项时另一项生效值不变；每个实体页及事件页分别遵守所属上限，覆盖空页、不满页、恰好一页和多页，正反向事件读取采用同一事件批次值 |
| 读取配置传递与重建 | 报告进程取得本次会话生效参数，故障后重新创建仍沿用相同值；后续会话分别调整实体与事件批次重建同一报告，所得对象、状态及报告字节均与独立预期一致 |
| 续读成本与中断 | 增加已处理前缀长度，核验后续分页不重复扫描该前缀；批次间暂时让出资源后按原范围续读；任务失败或进程结束后的重新生成不复用半份 JSON，仍为相同字节 |
| 报告内存 | 在第一版数据范围内，增加总对象数、单个父对象的子实体数和相关事件数，验证不保留全量对象、事件或去重集合；验收峰值须包含数据库缓存及对象转换开销 |
| 错误明确 | 投影不可靠、恢复依据缺失和读取中断均进入明确错误或恢复分支 |
| 局部查询成本 | 保持目标之后相关变化数不变，增加无关历史与历史前缀，检查查询计划、读取量及处理量 |
| 旧边界成本 | 增大目标之后的相关变化数量，测量逆向路径成本及是否满足预算 |
| 快照恢复 | 从可靠快照正向恢复，与从当前投影逆向恢复及独立预期得到相同结果；同一报告字节不因所选路径改变 |
| 路径选择 | 覆盖无后续变化、恰好命中快照、无较早快照，以及两条回放路径事件数的比较：正向更少时选正向，逆向更少或相同时选逆向；验证前置分支的处理顺序及多对象分别选择路径；选择时不加载两段完整事件正文 |
| 多对象事件复用 | 同一事件涉及多个入选对象，不因正文去重漏掉其他对象，也不对同一对象重复应用；不同快照起点及正反向路径均得到同一 H 的独立预期 |

正向与逆向结果比较必须配合独立预期，避免两条路径共享同一错误。源码搜索不能代替对实际查询计划、读取量和行为的验证。

历史存储、查询和快照维护共同约束事件格式、持久化原子边界、查询接口及报告恢复。实施前需要补齐事件与状态分类，并编写包含失败、恢复和性能门禁的实施计划。

## 按历史边界分批查找关联文件

录像 A 在 H 时已有文件 F，但尚未确认另一个文件 G 的来源。后来才确认 G 也来自 A。查询“A 在 H 时已确认的来源文件”必须返回 F，不能因为 G 今天已关联 A 就把 G 算进去。另一方面，F 后来已从设备删除，数据库仍保留它，旧查询必须能找到并恢复 F。

### 输入、返回与读取范围

查询接收状态库身份、完整已提交边界 H、查询种类、所属动作或交付身份、继续位置及批次上限。单批上限使用 `history.entity_batch_size`。继续位置绑定同一状态库、H、查询种类和所属对象，不在不同集合间复用。参数按精确整数及已登记种类校验；未知种类、错误身份或不完整历史边界返回错误，不改查当前状态。

| 查询需要 | 身份从哪里取得 | 恢复到 H 后核对什么 |
| --- | --- | --- |
| 产物引用的设备文件或主机文件 | 已恢复到 H 的 `outputs` 文件引用 | 引用组合、文件在 H 存在、固定身份及业务归属一致 |
| 拷贝引用的源文件与目标文件 | 已恢复到 H 的 `file_copies` 文件引用 | 原源文件身份和目标责任一致；查询固定源长度或已采用摘要时直接使用拷贝事实 |
| 录像处理引用的原片或修复输出 | 已恢复到 H 的 `recording_processing` 文件引用 | 该阶段允许无引用，或所需文件确实存在且归属一致 |
| 某动作最初观察的全部设备文件 | 按不变的 `device_files.observer_action_id` 查找候选 | 文件在 H 已登记，观察者一致；不把观察者解释为已确认来源 |
| 已确认属于某来源动作的全部设备文件 | 按 `device_files.source_action_id` 查找候选 | 文件在 H 已登记，且 H 时的来源确为该动作 |
| 某动作或交付创建的全部主机文件 | 按不变的 `intermediate_files.owner_action_id` 或 `owner_delivery_id` 查找候选 | 文件在 H 已登记且原责任一致；不按今天的用途、保留或清理状态预先排除 |

前三种查询先恢复引用方，再按当时实际存在的引用分批取文件；不能先按最新引用读取文件，再尝试补算过去的关系。一个被引用对象恢复到 H 后，只继续查询本次结果确实需要的关联，不递归展开所有外键。来源等待需要来源动作事实时，同样沿 H 时的 `action_dependencies` 查询来源动作；本接口不把来源的文件集合当成来源已结束的证明。

后三种查询通过[分页结果契约](module-contracts.md#分页结果契约)返回一页已经恢复到 H 的文件记录及下一继续位置，调用方从继续位置推导是否读完。返回记录按本文件类型的整数 ID 升序；不同文件类型分别分页，身份始终带类型。每页返回数可以小于批次上限，也可以为零；调用方只有在结果表明已读完时才结束，不能把空的有效结果页当作集合结束。

### 候选分页与同边界筛选

文件 ID 按登记顺序增加且不复用，行永久保留。最初观察者与主机文件原责任不变；设备文件的来源允许从未知补为确认值，确认后保持，具体规则见[文件字段](database/file-fields.md)。这些条件保证：在 H 属于查询集合的文件，在以后仍能由相同条件找到；后来才登记或确认的候选则需要排除。

第一次查询在短读事务中取得该文件表的最大 ID，作为本次扫描的固定上界 `upper_id`，并取得完整读取边界 C，要求 C≥H。空表上界为 0。后续页面的起点为上一页最后检查的候选 ID，首次为 0。以来源设备文件为例，候选查询为：

```sql
SELECT id
FROM device_files
WHERE source_action_id = :source_action_id
  AND id > :after_id
  AND id <= :upper_id
  AND created_event_id <= :boundary_h
ORDER BY id
LIMIT :page_limit;
```

其他集合分别使用表中指定的固定关系列，按 `(关系列, id)` 的索引续读。`created_event_id <= H` 只排除后来创建的文件，不证明归属在 H 已确认。历史查询不使用只覆盖未清理文件的部分索引来限定成员，也不添加当前状态、错误或用途作为成员过滤条件。状态过滤必须在恢复 H 之后进行。

取得一页候选身份后结束读取事务，再按普通对象恢复规则分批取得文件状态；每份当前文件投影仍须与自己的 C 和计数一起读取，不能把候选查询的 C 当作后来取得投影的版本。文件恢复到 H 后核对上述关系及所需条件，返回符合条件的记录。所需主对象本身在 H 不存在时，查询结果明确表达主对象不存在，与存在但集合为空分别处理。

| 本页检查结果 | 返回及继续规则 |
| --- | --- |
| 候选查询成功且没有记录 | 返回已读完；此前已返回的结果保持 |
| 候选在 H 尚未确认属于该来源，或不满足在 H 上应用的查询条件 | 本页不返回该文件，但继续位置仍越过已检查的候选 ID |
| 候选在 H 属于集合，所需事实可靠 | 返回恢复后的文件行，包含当时的实际空值和状态 |
| H 时保存的必需直接引用指向不存在或归属不符的文件 | 返回状态库一致性错误；不能作为候选不匹配而跳过 |
| 候选行与创建元数据、固定归属或历史互相矛盾，或任何必要读取失败 | 返回状态库错误，不把损坏解释为尚未登记、空集合或读完 |
| 任务取消、失败或进程退出 | 释放游标、事务和临时状态；半成品不发布，下一次按原冻结依据重新开始 |

本页最后检查的候选 ID 用作继续位置，不能使用最后一个返回文件的 ID。原始候选数小于批次上限，或者已经达到固定上界时可以返回已读完；原始候选满一页且未到上界时继续查询，即使这一页在 H 的有效结果为空。不得为了填满一页有效结果而在一次调用中无界扫描候选。

例如候选页包含 G、J，两者都是 H 之后才确认来源的文件，该页可以返回零个文件和“尚未读完”。下一页仍可能有 H 之前已确认的 K；使用最后一个候选 J 的位置才能继续找到 K，既不漏掉 K，也不反复检查 G、J。

同一扫描期间后来确认来源的旧文件可能进入尚未经过的候选区间；恢复到 H 后它不符合当时的来源条件，不进入结果。它也可能位于已越过的游标之前，此时无需回头读取，因为它在 H 同样不是成员。后来新建文件不会进入固定上界和创建边界限定的集合。已确认成员不能改归其他动作，是上述候选算法完整性的必要条件；若引入允许转移成员的业务关系，必须同时设计能够查到旧关系的历史索引，不能直接复用此查询。

接口每次只保留一批候选和正在恢复的文件，缓存按状态库、文件类型、ID、H 及查询结果范围区分。运行中的关系查询与历史集合查询分别使用各自条件，不能互换。该接口用于取得查询依赖，不自动把所有返回文件变成报告公开对象，也不产生业务序号、调度通知或外部文件操作。

## 取回与交付的同一边界历史查询

取回 R 的取回项 601 在历史位置 100 已关联交付 D，D 当时正在准备副本。D 在 120 保存准备完成，在 150 保存发布最终失败。查询 R 在 100 的结果时，601 的关联和 D 的状态均取自 100，结果表达已经建立交付、仍在准备；查询 150 时才取得 D 的发布失败及错误。

查询以取回动作身份和完整已提交历史边界 H 为输入。先恢复该动作在 H 的自身记录，包括来源选择、取回项及交付关联，再沿这些关联分别恢复交付在 H 的状态。查询依据同一 H 的来源、目标和交付事实组织结果；具体错误继续由产生错误的业务责任保存。

| 在 H 恢复出的事实 | 查询处理 |
| --- | --- |
| 取回动作在 H 尚不存在 | 返回该动作在 H 不存在，不引入后来创建的记录 |
| 取回项在 H 尚未建立交付 | 使用该项自身的目标处理事实，不引入 H 之后建立的交付 |
| 取回项在 H 已关联交付 D，D 存在且归属一致 | 恢复 D 在同一 H 的状态，核对其所属取回及产物，再组合查询结果 |
| 取回项在 H 已关联 D，但 D 在 H 不存在或归属矛盾 | 按状态库一致性错误处理，不解释为尚未完成或尚未建档 |
| 查询所需历史、快照或投影存在损坏、缺失或无法解释的内容 | 按状态库错误处理，不用当前交付状态或默认结果替代 |

取回动作的快照包含自身记录及取回项的交付关联；交付快照包含交付自身记录。取回快照不递归包含关联交付。两类快照可以位于不同的历史边界，各对象按历史查询规则独立选择快照正向恢复或当前投影逆向恢复，最终均取得 H 的状态。每份当前投影副本与同一短读事务取得的读取边界 C 绑定，恢复范围固定；查询期间的新提交不改变已选依据。

取回项在 H 之后没有变化，只能证明该项的相应字段无需恢复，不能证明关联交付没有变化。每个被依赖的交付仍须独立核对和恢复。共同建档及其他跨对象事务只在完整提交边界提供结果，回放不执行外部副作用。

计算取回的完整失败列表时，检查该动作在 H 的全部相关来源、取回项及关联交付，不能将检查范围缩小为本次增量报告选中的交付。读取所需交付与向报告输出交付是不同的范围：查询依赖本身不扩大报告的交付输出集合。关联和交付可以分批读取、恢复和使用，不要求同时载入全部交付及其完整历史；批次大小、快照位置和恢复方向不改变结果及报告字节。

## 交付变化与取回报告更新

取回 R 的交付 D1 发布最终失败，另一交付 D2 仍在准备时，R 可以继续执行，其取回项也保持原状态和关联。D1 保存失败状态及错误，事件建立 D1 的历史关联并分配应报告的业务变化序号。报告按覆盖区间选中 D1 后，按所属关系补齐 R 和所属计划，并取得它们在冻结边界 H 的完整自身字段。R 的完整失败列表按同一边界历史查询规则生成，包含 D1 及其他在 H 已确定的相关最终失败。

对象的历史关联、`last_event_id` 和 `change_count` 跟随该对象自身记录的实际变化。对象自身记录包括按归属规则属于它的子表记录；被引用的独立交付由交付自身历史恢复。报告补齐父对象只决定输出范围，不增加父对象的历史关联、累计变化计数或业务序号。

| 实际保存的变化 | 历史关联与计数 | 报告选择 |
| --- | --- | --- |
| 只有交付记录变化，影响交付自身或所属取回的应报告内容 | 为交付保存事件关联，按事件增加交付计数；取回自身记录未变，不增加取回计数 | 报告变化目录登记交付，交付入选后补齐所属取回和计划 |
| 交付变化，同时取回项的源依赖等自身记录变化 | 各事件分别关联其实际改变的对象；同一事件对同一对象只计一次 | 各对象是否登记到报告变化目录按其报告影响确定；交付入选仍补齐父对象 |
| 取回自身保存动作终态、来源选择或建档前逐项结果等变化 | 为取回保存实际变化的历史关联并增加计数 | 应报告的变化登记到报告变化目录，可以直接选中取回 |
| 只有交付内部记录变化，交付及所属取回的应报告内容均未受影响 | 为交付保存内部变化的历史关联并增加计数 | 该变化不产生业务序号，不单独触发报告更新 |

交付的最终失败及其他会影响所属取回报告结果的交付变化必须具有应报告的业务序号，不能归为纯内部变化。业务序号属于事件；同一事件涉及多个应报告对象时，报告变化目录中的各项使用该事件的同一序号。事件正文、适用业务序号、历史关联、报告变化目录、计数及投影在同一事务保存，提交成功后的报告选择不依赖内存通知。

交付入选时，所属取回必须携带 H 时的完整自身字段，包括完整失败列表；仅输出取回身份不能完成更新。报告按对象身份去重，多个交付入选或取回同时直接入选时，取回只输出一次。普通增量报告、完整同步及按历史起点同步均遵守相同的父对象补齐和同边界查询规则。

`change_count` 表示对象自身记录的累计变化次数，不表示包含其他对象事实的完整查询结果版本。取回计数不变时，其关联交付仍可能变化。缓存完整取回查询结果须明确绑定同一状态库、取回身份和 H；不能仅凭取回的计数未变跨边界复用旧失败列表。快照维护继续按各对象自身计数推进，补齐父对象不产生额外快照变化。
