# 历史状态查询与报告重建

[返回 CLI 资料入口](README.md) · [实现规格](implementation.md)

camctl 持续维护当前投影，在业务事件中保存必要旧值，支持按范围逆向恢复；同时按对象保存历史快照，支持从快照正向恢复。使用 SQLite WAL 模式、`synchronous=FULL` 和自动 PASSIVE 检查点。报告固定历史边界 H，通过分批短读事务取得数据，在事务外恢复状态和写出文件。第一版遵守[较为乐观的 MVP 范围](implementation.md#第一版实现范围)。本文记录正确性条件、性能边界及待细化事项，不是实施计划。具体事件字段、索引与查询接口、快照维护和容器容量，以及 SQLite 连接清理仍需细化；WAL 积压协调仅保留为后续设计提醒。业务契约以[持久化规则](../architecture/system-foundations.md)和[状态报告](../architecture/status-reports.md)为准。

## 先理解事件、历史位置与业务变化序号

本节通过取回文件的例子解释三个概念。表中的名称和编号用于说明含义，不规定最终数据库字段、事件拆分方式或序列分配算法。

### 事件记录保存什么

事件记录是数据库对一件已经发生的事情的记载。例如，camctl 保存了一次拷贝进度变化：

| 记录内容 | 示例 |
| --- | --- |
| 发生了什么 | 已保存的拷贝进度增加 |
| 涉及哪个对象 | 交付 D |
| 原来是什么 | 已可靠保存 40 MB |
| 现在是什么 | 已可靠保存 70 MB |
| 在历史中的位置 | 历史位置 110 |
| 属于哪次数据库事务 | 事务 T |

这里保存旧值，是为了将来能够从 70 MB 恢复出当时的 40 MB。实际进度按[可恢复拷贝](../architecture/file-copy.md)规定的可靠保存顺序记录；本例的 MB 只是便于阅读的表示。

不同事件保存的事实不同。例如，计划受理事件保存计划身份、原始输入和确定的生效参数等；报告登记事件保存报告身份、覆盖范围和冻结依据；报告发布成功事件保存哪份报告已经成功放入 `ready`。

事件所需的信息由它表达的事实决定：读者需要知道发生了什么，程序需要据此准确重建相关状态。修改事件保存必要的变化信息；创建事件保存对应对象的完整初始事实。

### 两种顺序分别解决什么问题

**历史位置给全部权威历史记录排序，业务变化序号 `change_seq` 只跟踪需要向客户端报告的业务变化。** 同一条事件可以同时具有历史位置和业务变化序号；报告内部管理事件仍有历史位置，但不产生新的业务变化序号。

业务水位表示已经推进到的业务变化序号。例如，“水位为 22”表示业务变化已经推进到 22。它与客户端已经确认到哪个水位是不同的信息。

假设计划 P 中的取回动作 A 正在取回文件，创建了交付 D。客户端此前已经确认到业务水位 20。下面展示后续的一段历史，用百分比表达 D 的拷贝进度。每行代表一个完整提交位置，事务内可能包含多条事件；数字是示意，省略了无关记录。

| 历史位置 | 保存的事情 | 是否产生新的业务变化 | 提交后的业务水位 |
| --- | --- | --- | --- |
| 90 | 创建交付 D | 是 | 21 |
| 100 | D 的拷贝进度达到 40% | 是 | 22 |
| 101 | 登记报告 R，内容截止到历史位置 100 | 否 | 仍为 22 |
| 102 | 报告 R 已成功放入 `ready` | 否 | 仍为 22 |
| 103 | 收到并保存客户端对 R 的有效确认 | 否 | 仍为 22 |
| 110 | D 的拷贝进度达到 70% | 是 | 23 |

登记报告、发布报告、保存有效确认都必须留下历史，否则断电后无法确定报告处理到了哪一步。这些内部处理本身不产生新的业务报告责任，所以历史继续推进，业务水位保持不变。确认处理中的其他业务变化或无效 ACK 诊断仍遵守[报告与累计确认](../architecture/status-reports.md)的分类。

### 为什么业务变化序号不能代替历史位置

仅知道“业务水位为 22”，无法区分下面四种情况：

| 历史位置 | 当时已经保存的状态 |
| --- | --- |
| 100 | 业务进度已经保存，报告 R 尚未登记 |
| 101 | R 已登记，尚未保存发布成功事实 |
| 102 | R 已保存发布成功事实，尚未保存客户端确认 |
| 103 | 已保存客户端对 R 的确认 |

这四种情况对应不同的恢复依据。历史位置能够准确指定查询哪一个完整提交后的状态，业务水位只说明业务变化推进到了哪里。数据库尚未保存发布事实时，文件也可能已经发布；实际恢复还须按[文件交接](../architecture/file-handoff.md)核实文件位置，不能仅凭记录缺席推断外部操作未发生。

历史位置是数据库内部确定的先后顺序，不是时钟时间。同一事务中的事件整体提交，历史状态查询只接受完整事务边界；具体表示采用下文的[全局事件序号与显式事务边界](#全局事件序号与显式事务边界)。

### 一份报告怎样同时使用两种边界

例子中的报告 R 登记时保存两项不同的范围依据：

- **业务覆盖范围 `(20, 22]`**：选择业务变化序号大于 20、小于等于 22 的变化对象。本例选中交付 D，并按报告结构补齐它的父动作 A 和父计划 P。
- **历史冻结边界 100**：这些对象的自身字段都取数据库在历史位置 100 时已经知道的值，因此 D 的进度为 40%。

业务覆盖范围决定报告包含哪些变化对象，历史冻结边界决定这些对象采用什么状态。补齐父对象不意味着把其他子对象全部加入报告。

报告子进程读取时，当前投影中的 D 可能已经达到 70%。只要报告 R 的冻结边界仍为 100，就需要使用位置 110 的事件所保存的旧值，在查询副本中恢复出 40%。数据库当前投影及实际拷贝不受影响。

同一报告后续重建仍使用原覆盖范围和冻结边界。后来的业务进展和客户端确认不会改变它原来的内容。业务变化序号保持独立，也使报告登记、发布及有效确认本身不会不断触发下一份报告。

## 全局事件序号与显式事务边界

每条权威历史事件使用一个全局事件序号 `event_seq`，并保存所属历史事务的标识。同一状态数据库中，已提交事件的序号唯一、严格递增，不依赖墙钟。第一版按下文的[序号分配规则](#序号分配范围与初始化边界)连续分配全局事件序号；筛选后的事件位置可以不连续。一次历史事务中的事件按实际发生顺序排列，不与其他事务的事件交错。

每组一起提交的历史事件对应一份历史事务记录，以该组首条事件的 `event_seq` 作为事务标识，并保存本事务最后一个事件的序号。该记录描述这些事件的提交分组，不另存一份业务事实。事件、事务记录、本次派生的查询目录和受影响的当前投影在同一个 SQLite 写事务中保存；事务结束位置必须确实指向该组最后一条事件。

| 信息 | 用途 |
| --- | --- |
| 事件的 `event_seq` | 确定正向或逆向恢复顺序，唯一定位分页已经读到的事件 |
| 事件所属事务及事务结束位置 | 确定哪些历史位置代表完整提交后的状态 |
| 请求、计划与事件的业务关联 | 追溯事实属于哪个业务对象或请求；一个计划可经历多次事务提交 |
| `change_seq` 与 `plan_seq` | 继续分别遵守业务报告覆盖和新计划受理顺序的既有规则 |

历史事务记录适用于写入权威历史的事务。只维护历史快照等派生数据的事务不因此新增历史事件或历史事务记录。报告登记、发布与有效确认等内部历史仍分配 `event_seq`，是否推进 `change_seq` 则按对应业务规则判定。

例如，某次事务依次保存“输出文件已确认”“动作已完成”“计划已完成”，事件序号为 201、202、203，事务记录的结束位置为 203。恢复程序一批读到 202 后，可以从该位置继续读 203；该批处理结果尚不能作为完整状态交付。报告冻结位置只能选择 203 或此前某次完整提交的结束位置。

| 位置或保存状态 | 处理规则 |
| --- | --- |
| 目标位置为 0，且数据库已经可靠确认完整有效 | 表示初始化后的历史起点，不对应事件或历史事务记录 |
| 目标位置是当前一致读取视图内的已提交事务结束位置 | 可作为历史状态查询边界；报告 H、读取依据 C 和快照 S 继续满足各自范围约束 |
| 目标位置是事务内的非末尾事件 | 可作为事件分页位置，不接受为完整状态查询或报告冻结边界 |
| 目标位置不存在或超出当前读取视图 | 不接受为该视图内的历史状态边界，不自动取邻近位置替代 |
| 写事务已经确认回滚 | 本次事件、事务记录及投影变化均不成为可用历史；继续以此前已提交状态为准 |
| 写事务提交结果未知 | 按既有状态库错误及恢复规则确认整个事务结果，不从内存中的序号推断成功或失败 |
| 已保存的冻结依据、事务记录或事件分组相互矛盾 | 按历史不可可靠解释的状态库错误处理，不截断、补齐或猜测边界 |

除初始化起点 0 外，H、C、S 均使用完整事务结束处的 `event_seq` 表示，不以请求结束、计划完成或业务水位代替。C 与对应的当前投影在同一次短读事务的一致视图内取得；该投影副本用于恢复期间，C 保持不变。不同批次取得的投影可以对应不同的 C，所有对象最终恢复到同一个 H。位置 0 的存在不创建业务实体或报告责任，报告及快照的生成资格仍按各自规则判断。分页游标可以位于事务内部，恢复到 H 的结果只能在所需影响全部处理完毕后使用。

验收覆盖单事件和多事件事务、同事务多次修改同一对象、事务内跨批分页、筛选结果的序号间隔、并发提交、确认回滚与提交结果未知，以及无效边界被拒绝、保存的边界矛盾被诊断。单元测试验证边界分类和恢复顺序，集成测试验证事件、事务记录、目录与投影一起提交或回滚。

具体表名和列布局、数据库约束和查询接口仍需细化。

### 以首条事件序号标识历史事务

历史事务的 `transaction_id` 等于该组首条事件的 `event_seq`，使用相同的正整数范围，不另设事务编号计数器。组内所有事件保存这个事务标识；事务记录以该标识定位起点，并保存结束序号，不另存一份重复的起始编号。

| 本次新增事件 | 事务标识及记录 |
| --- | --- |
| 只有序号 201 的事件 | `transaction_id = 201`，结束序号为 201 |
| 序号 201、202、203 的三个事件 | 三条事件均属于事务 201，事务结束序号为 203 |
| 前一事务结束于 203，下一事务从 204 开始 | 下一事务标识为 204，结束序号由该组最后一条事件确定 |
| 没有新增历史事件 | 不创建历史事务记录，包括只维护派生快照的写事务 |

产生本次首条事件时确定事务标识，完成该组事件写入后确定结束序号。提交时，事务记录必须完整，起止事件都存在并属于本组，组内事件连续且不与其他事务范围重叠。事件及事务记录一起提交或一起回滚，不暴露只有起点、缺少结束位置的已提交分组。事务内部的暂存表示和数据库约束实现仍需细化。

事务标识仅定位同一状态数据库中一组已提交历史。请求身份、计划身份与事务标识分别保存，一个计划可以经历多次事务。确认回滚后，相同起始序号可以用于下一次实际提交；因此，提交结果未知时，不能仅凭该事务标识或某个事件序号存在就认定原调用成功，仍须结合业务身份和保存的事实核验整个操作结果。

验收覆盖单事件与多事件分组、相邻事务、无事件写事务、确认回滚后的标识重新使用，以及组内归属错误、范围重叠、首尾事件缺失和未完成分组不得提交。提交结果核验须覆盖某序号已由其他操作使用的情形，不将历史位置当作请求幂等凭据。

### 序号分配范围与初始化边界

`event_seq` 使用 SQLite 的 64 位有符号整数保存，真实事件范围为 `1` 至 `9223372036854775807`，对应 `2⁶³ − 1` 的上限，见 [SQLite 整数表示](https://www.sqlite.org/datatype3.html)。0 专门表示完整有效数据库初始化后的历史起点，不插入序号为 0 的事件或虚构事务记录。数据库不存在、损坏、历史与其他状态矛盾或读取失败时，不能用 0 代替错误。

新增历史时，先成功取得 `BEGIN IMMEDIATE` 写事务资格，再通过序号索引读取最后一个已提交事件的序号；可靠确认尚无事件时以 0 为起点。本次事件按顺序逐条加一，连同事务记录、目录及投影一起提交。分配依据直接来自已有历史，不另设永久递增计数器，也不依赖进程启动时读取的旧序号。其他写入者在取得写事务资格后重新读取依据；写事务互斥规则见 [SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)。

| 分配与保存情况 | 处理规则 |
| --- | --- |
| 当前最后序号为 L，本次 N 条事件全部提交成功，N＞0 | 本次使用 L＋1 至 L＋N；下次从 L＋N＋1 开始 |
| 本次没有新增历史事件 | 不分配事件序号，不创建空的历史事务分组 |
| 本次已分配序号，但整个事务确认回滚 | 分配结果没有成为历史；下次仍从数据库实际最后序号之后开始 |
| 提交结果未知 | 先按恢复规则确认完整事务结果，不从内存分配记录决定重用或跳号 |
| 剩余序号不足以保存本次全部事件 | 整个写事务失败并确认回滚，不提交部分事件或投影 |

分配时检查数值范围，不回绕、不改用浮点数，也不重复使用已提交的序号。本次事务内部可以引用已经分配的序号；提交确认前，不据此发布已提交缓存、确认报告冻结完成或启动依赖这些事实的外部操作。序号耗尽按既有状态库错误规则处理，停止启动依赖新持久化事实的普通设备动作，保留已有数据和诊断。第一版不实现序号扩容；将来需要扩大表示范围时须通过显式数据库格式升级设计。

第一版正常提交的全局序列连续，事务回滚不留下空缺。按对象或事件类型筛选后，结果可能只包含 201、204 等位置，因为其他事件属于别的对象或类型；分页按实际序号大小继续，不能将序号差当成筛选结果的事件数量。完整历史出现空缺时须调查并诊断，不归因于正常回滚，也不为消除空缺改写历史。此要求不意味着每次局部查询都扫描全库检查连续性，具体完整性检查方式随持久化接口细化。

验收覆盖初始边界 0、首次分配、多事件事务、确认回滚后的重新分配、并发写入按实际提交结果续号、提交结果未知，以及上限恰好够用和不足的分区。上限测试验证整批原子性，筛选查询测试验证位置有间隔时无遗漏或重复；缺失或无效数据库不得被当作空历史继续分配。

## 查询目标

数据库永久保存不可变历史，并在每次写入历史的同一事务中更新当前投影。普通业务查询使用可靠的当前投影。

报告需要取得冻结边界处的实体状态。同一报告在首次生成、断电恢复和补投时，必须使用同一组冻结依据并生成相同字节。当前投影继续变化，因此需要能够取得旧状态的查询方法。

全量读取历史、回放事件、组织报告及编码文件是不同成本。即使不再回放全部历史，如果仍把全部事件载入内存，每份报告仍会支付随历史增长的读取和对象构造成本。分批读取只能限制部分内存占用，独立进程只改变执行位置，二者都不能减少必须处理的事件数量。

## 从当前投影逆向恢复

事件保留恢复旧状态所需的变更前后值，查询从当前投影的副本出发，按逆序恢复目标边界之后的变化。

例如，下表仅用于说明状态恢复，不定义新的动作状态协议：

| 历史位置 | 已保存事实 | 状态恢复所需信息 |
| --- | --- | --- |
| H100 | 动作 A 正在执行 | 当时的实体状态 |
| H110 | 更新了一项诊断 | 该字段原先是否存在、原值及新值 |
| H120 | 确认动作 A 完成 | 被改变字段的原值与新值，包括状态和完成结果 |

如果当前投影位于 H120，而报告冻结在 H100，查询先恢复 H120 改变的字段，再恢复 H110 改变的字段，得到 H100 的状态。这里只改变本次查询的数据副本，不改变真实动作、数据库当前投影或已有历史。

事件继续表达有独立含义的业务事实，并携带必要恢复依据。事件的业务含义、正向更新规则和逆向恢复规则必须一起定义，不能只保存字段变化而丢失事实的含义。

所有影响报告重建的状态变化都必须具有完整恢复依据。事件与受影响的当前投影在同一事务中保存，正向回放继续用于投影重建和一致性验证。旧值必须对应本次事务中实际发生的变化，不能使用事务外读取、可能已经过时的状态。

## 读取流程与边界

H 表示报告已经登记的冻结历史边界，整份报告保持不变。C 表示取得某份当前投影时，该短读事务视图中的完整已提交边界，要求 `C ≥ H`。不同批次可以有不同的 C；下文未带下标的 C 均指正在恢复的投影副本对应的位置。

1. 主进程登记报告身份、H、覆盖水位及固定生成元数据。
2. 报告进程使用自己的只读连接核验状态库及报告冻结依据，按固定业务区间和历史关联分批选择实体，补齐 H 处的必要父对象与关联。
3. 在短读事务内一起取得本批当前投影、对应的 C 及当前累计变化计数，将所需数据复制到本批内存，结束查询和读事务。父对象自身状态与子实体分别处理，读取不要求组装整棵对象树。
4. 按下文的恢复路径规则，选定该投影副本或不晚于 H 的可靠历史快照。H 处的历史计数和已有快照可以在另一次短读事务中取得；它们必须明确对应所需历史位置。选定快照后固定其身份、S、格式、计数与内容。
5. 通过索引分批读取固定范围内的历史：逆向使用 `(H, C]`，正向使用 `(S, H]`。每批读完均结束查询和读事务，再在独立副本上应用本批事件；一个对象有大量历史时也按此方式分批。
6. 对象恢复至 H 后，在事务外按固定顺序编码并写入同一份 `staging` 报告。释放不再需要的数据，继续后续对象。已写父对象与后来恢复的子对象均表达 H 处的状态。
7. 全部内容写出后完成摘要及文件同步，再交由主进程组织发布与保存发布事实。

当前投影副本与它的恢复范围始终绑定：即使后来读取历史时数据库已推进到 C2，原先在 C1 取得的副本也只处理 `(H, C1]`。后续提交不会改变这个已提交历史区间的内容。

### WAL 与分批短读事务

采用 SQLite WAL（预写日志）模式。每次需要一起取得可变数据及其版本位置时，显式开启短读事务，通过首次读取建立一致视图；例如，当前投影与对应 C 必须来自同一视图，见[SQLite 隔离说明](https://www.sqlite.org/isolation.html)。报告的一致性由固定 H 和各份恢复依据的明确范围保证。

跨事务读取成立的前提是：已提交历史、历史事务分组及查询目录中的既有关联不被改写或删除；新事件及关联只能追加到新的历史位置。已提交的历史快照内容不变。整个任务使用同一状态库，数据库格式升级及派生结构重建遵守维护与日常运行隔离的规则；具体协调机制仍需细化。

| 所读数据 | 每次查询必须保持的依据 | 后续提交后的处理 |
| --- | --- | --- |
| 报告登记信息 | 同一报告身份、H、覆盖水位及生成元数据 | 不用较新的 ACK 或同步责任改写本份报告范围 |
| 入选实体及父子关系 | 冻结业务区间、H 和历史关联 | 新对象及关系变化不改变 H 处的入选集合和所属关系 |
| 当前投影及当前计数 | 在同一短读事务内取得投影、计数与 C | 保留副本及 C，恢复期间不替换为较新的当前值 |
| H 处的历史计数 | 对应实体在不晚于 H 的末条历史关联 | 可另开短读事务查询，结果仍对应 H |
| 历史快照 | 已选快照身份、S、格式、计数与内容，且 S≤H | 本对象恢复期间保留已选依据；后来新增快照不改变它 |
| 逆向事件分页 | 对应实体、固定 `(H, C]`、方向和最后已读位置 | 后来的事件查询仍以上述 C 为上限 |
| 正向事件分页 | 对应实体、固定 `(S, H]`、方向和最后已读位置 | 后来的事件查询仍以上述 H 为上限 |

例如，报告冻结在 H＝100，交付 D 当时的进度为 40%。短读事务在 C＝120 取得 D 的 70% 投影及 C，复制后结束读取。业务随后推进到 150，D 已完成；报告分多个短读事务读取 D 在 `(100, 120]` 的事件，每批结束读取后逆向恢复，最终仍得到 40%。下一个对象可以从 C＝160 的投影出发，但也恢复到 H＝100。不同对象的 C、批次大小及实际读取时刻不改变最终报告字节。

每批数据取回后，先结束相关查询、释放未完成游标并结束显式读事务，再恢复状态、编码或写文件。仅调用一次事务结束命令，不足以代替对未完成查询的清理，见 [SQLite 查询与事务生命周期](https://www.sqlite.org/lang_transaction.html#implicit_versus_explicit_transactions)。批次之间可以复用连接；复用的是连接，不是上一次读取视图。必要的数据取回和复制仍发生在读事务内，其耗时计入单次读取预算。

同一次生成在批次之间暂时让出资源时，保留当前处理所需的恢复副本、固定范围、分页位置与编码进度，恢复后继续本次任务。这里没有发生生成失败，不构成新的报告尝试。若任务已经失败、取消或进程结束，则结束实际读取，保留未完成报告责任，半成品不发布；后续合法触发仍按既有规则从头生成。第一版按已有生成时限及异常生命周期处理，不增加按 WAL 积压触发的暂停协议。

缓存必须明确对应数据库身份和不可变事实，或对应实体在 C／H 的状态。使用当前状态缓存作为恢复起点时，必须证明它与绑定的 C 一致；父对象恢复到 H 后可按相同 H 复用。

WAL 支持读写并行，但慢查询及多个读取者交叠仍可能阻碍检查点推进和日志复用，见[WAL 工作方式](https://www.sqlite.org/wal.html)。短事务使报告能在批次之间释放读取，不能单凭批次数量或 `LIMIT` 宣称耗时有上限。联调测量查询计划、实际读取时长、WAL 积压、计划接纳延迟和完整报告的新鲜程度，用于确定适用负载及后续优化需要；第一版不承诺持续资源压力下的固定时延，不要求实现积压协调机制。

部署须核验 Python 实际链接的 SQLite 运行库，并采用包含已知 WAL 并发缺陷修复的版本。官方列出的修复版本包括 3.51.3 及后续版本，以及 3.44.6、3.50.7 的回移修复；具体部署版本仍待锁定，见[WAL 并发缺陷与修复版本](https://www.sqlite.org/wal.html#walreset)。

Python SQLite 的连接上下文管理器不能单独证明已建立覆盖多次查询的读事务，实现须明确开启和结束事务，见[Python 事务说明](https://docs.python.org/3.11/library/sqlite3.html#transaction-control)。

### 所有状态库写连接使用 FULL 同步

状态库统一采用 `journal_mode=WAL`、`synchronous=FULL`。每个状态库写连接在执行写事务之前显式设置并核验同步等级，确认 WAL 模式符合要求；不能仅依赖初始化连接或另一个进程的连接设置。适用范围包括初始化、`run`、`submit`、快照等派生数据维护，以及后续明确设计的写入入口。第一版不提供降低同步等级的配置。

WAL 模式下，`FULL` 在每次事务提交时增加 WAL 同步，用于保证已经提交事务的断电持久性。它同步事务所需日志，不要求每次重写整个数据库；可靠性以操作系统和存储设备正确履行同步请求为前提，见 [SQLite 同步等级](https://www.sqlite.org/pragma.html#pragma_synchronous)。部署联调需验证目标主机的实际存储行为。

持久化完成仍先于依赖这些事实的外部副作用。例如，录像启动意图可靠提交后才允许发送相应设备命令；不能让命令已经生效，而意图记录因降低同步等级在断电后丢失。文件内容及目录同步继续由文件处理契约保证，数据库同步不代替文件交接的持久化步骤。

| 写连接或提交情况 | 处理规则 |
| --- | --- |
| WAL 与 FULL 设置已经核验，事务提交确认成功 | 才能返回已提交结果，并允许依赖该事实的后续处理 |
| 设置失败、核验结果不符或无法确认 | 不以该连接继续写入，按所属入口的状态库错误契约处理，不静默降级 |
| 提交失败且确认回滚 | 不发布本次已提交结果，不执行依赖它的外部副作用 |
| 提交或回滚结果无法确认 | 保留结果未知，按既有恢复规则核实；设置 FULL 不消除提交结果未知的分支 |

降低存储开销通过合理组织事务、控制可恢复进度的保存粒度和快照维护批次实现，不延后协议要求的可靠保存位置。数据库操作继续在专用数据库线程执行；同步造成的提交等待仍计入业务时延，不能以使用协程为由忽略。

单元测试覆盖连接核验失败与提交各结果下的后续行为。集成测试使用各实际写入口打开的连接检查生效设置，并验证同步或提交错误不会被解释为成功；目标主机联调另测提交延迟、设备调度延迟和断电恢复。进程终止测试不代替真实断电场景的验证。锁等待与检查点按下文安排，磁盘故障的具体处理仍需细化。

### SQLite 内置忙等待与失败处理

第一版使用 SQLite 内置忙等待机制处理适用的锁冲突，通过连接的 `busy_timeout` 参数设置等待量。SQLite 最终返回锁忙错误后，应用层结束本次操作并按实际事务状态清理、交付错误，不再循环重发同一语句或重开同一事务来延长等待。该规则不阻止后续合法启动的会话按既有恢复协议核实状态。

本节集中定义主机本地配置：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `database.busy_timeout_ms` | `9000` | 1～2147483647 的整数，单位为毫秒；传给 SQLite 内置忙等待机制的参数 |

省略配置项时使用默认值；0、负数、超出范围的整数、浮点数、布尔值、字符串等按配置错误处理，不以截断或溢出后的值建立连接。参数采用 SQLite 接口可表达的有符号 32 位正整数范围。配置按[本地配置加载规则](../architecture/configuration.md#本地配置的加载与更新)在 CLI 启动时取得，会话内固定，部署调整在后续调用生效，不固化到动作。

每个访问状态库的连接在执行查询或事务前，显式设置并读取核验 `PRAGMA busy_timeout`；适用范围包括初始化、`run`、`submit`、快照维护及报告只读连接。新建或重新创建连接时沿用所属会话的生效值，不依赖另一个连接的设置。主进程将本次值传给报告子进程，故障后重新创建的报告进程仍沿用同一值。设置或核验失败时，不使用该连接继续工作，按所属入口的状态库错误协议处理。只读连接仅设置自身运行参数，保持只读权限。参数按连接生效，见 [SQLite 忙等待配置](https://www.sqlite.org/pragma.html#pragma_busy_timeout)。

SQLite 按自身忙处理规则在适用的锁冲突期间等待；为避免死锁等原因，也可能直接返回 `SQLITE_BUSY`。因此既不要求每次锁忙都等满配置值，也不将它作为事务或数据库调用的总耗时上限。数据库执行、提交同步、其他锁冲突及系统调度仍可能增加耗时。该参数与进程内的入队等待分别计量，已入队等待派发继续遵守不另设排队超时的规则。机制边界见 [SQLite 内置忙等待](https://www.sqlite.org/c3ref/busy_timeout.html)及[忙处理回调的适用条件](https://www.sqlite.org/c3ref/busy_handler.html)。

先按本次操作结果处理；失败后需要回滚时，再按回滚结果分类：

| 锁等待或事务结果 | 处理 |
| --- | --- |
| 锁冲突消除，SQLite 继续执行 | 继续本次操作，最终按实际查询或事务结果返回 |
| `BEGIN IMMEDIATE` 返回锁忙，确认尚未取得本次写事务资格 | 本次事务未开始，交付状态库错误；不进入业务判断或执行依赖它的外部副作用 |
| 读取、事务内语句或提交返回锁忙，包括未等满参数值即返回 | 结束本次操作，按实际事务状态释放读取或执行必要回滚，不在外层重发；交付状态库错误 |
| 失败后已确认回滚 | 本次变更未提交，保留其他已提交事实并交付错误 |
| 提交或回滚结果无法确认 | 保留结果未知，按既有恢复规则核实；不能仅凭锁忙错误宣称整个事务未保存 |

`run` 与 `submit` 按 `state_db_error` 处理最终锁忙错误；报告进程保留状态库错误分类交给主进程，初始化沿用自身错误输出契约。快照操作已进入数据库执行后的锁忙失败也遵守此规则，不适用尚未入队超时的会话内停用策略。等待期间取消调用协程不证明数据库操作结束，仍须跟踪实际结果后处理连接。自动 PASSIVE 检查点未完整推进继续按其专门规则处理，不因本参数而要求检查点等待其他事务结束。

验收覆盖配置缺省、合法边界及覆盖、非法类型及越界值；逐个检查各入口、报告只读连接和重新创建连接的生效值。单元测试控制锁忙、提前返回、明确回滚和结果未知，验证不额外重发及错误分类。集成测试通过真实连接竞争验证锁释放后继续与持续竞争后失败，检查失败事务的实际状态，不以精确等于参数值的墙钟耗时作为断言。另测锁等待期间的队列积压及设备调度延迟；报告进程重建仍使用所属会话的配置，超时与退出继续遵守报告生命周期契约。

### 自动 PASSIVE 检查点与可配置阈值

第一版保留 SQLite 自动检查点，通过 `wal_autocheckpoint` 设置可配置的页数阈值。本节集中定义本地配置：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `database.wal_autocheckpoint_pages` | `1000` | 1～2147483647 的整数；事务提交后 WAL 达到该页记录数量时，由 SQLite 自动尝试 PASSIVE 检查点 |

省略时使用默认值；0、负数、超出范围的整数、浮点数、布尔值或字符串等按配置错误处理。采用 SQLite 接口可表达的有符号 32 位正整数范围，保持自动检查点启用。配置按[本地配置加载规则](../architecture/configuration.md#本地配置的加载与更新)在 CLI 启动时取得，进程运行期间固定，部署调整在后续调用生效；不固化到动作，不改写业务事实或报告内容。

所有状态库写连接在执行写事务前显式设置并读取核验 `PRAGMA wal_autocheckpoint`，包括初始化、`run`、`submit` 及快照等派生数据维护；重新创建连接时沿用所属会话的生效值。不能依赖 SQLite 构建时的默认设置或其他连接已经设置。设置失败、结果不符或无法核验时，按所属入口的状态库错误协议处理，不以该连接继续写入。报告进程保持只读，不承担写入触发的自动检查点职责。

阈值计量 WAL 中的页记录数量，不是不同数据库页面的数量，也不是业务事件或快照对象数量。实际页面大小由数据库决定；例如每页 4 KiB 时，默认阈值约对应 3.9 MiB 的页面数据，不包含 WAL 格式开销，也不代表文件大小上限。该默认值采用 SQLite 通常使用的初始阈值，实际负载下的提交开销与 WAL 增长仍需联调测量，见 [SQLite 自动检查点配置](https://www.sqlite.org/c3ref/wal_autocheckpoint.html)。

检查点将 WAL 中的数据库页面合并回主数据库，并为日志空间复用创造条件。它是数据库内部维护，不生成业务历史，不推进事件序号或业务水位。已可靠提交的事务不以整个 WAL 合并完成作为有效条件；WAL 本身是数据库持久状态的一部分，由 SQLite 管理，不能作为普通临时文件清理。

SQLite 自动检查点采用 `PASSIVE` 模式，尽量推进而不等待其他读写事务结束来强求完整完成。自动检查点会在触发提交的线程中执行实际读写，因此仍可能增加该次提交的返回耗时，不能将“不等待其他事务结束”解释为“不耗时”或“不产生存储竞争”。第一版继续由已有数据库线程承载这些操作，不新增专用检查点线程，见 [SQLite 自动检查点](https://www.sqlite.org/wal.html#automatic_checkpoint)及[检查点模式](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html)。

| 运行情况 | 处理规则 |
| --- | --- |
| 事务提交后 WAL 页记录数量达到或超过本连接的阈值 | 由 SQLite 自动尝试 PASSIVE 检查点 |
| 检查点可以完成本次页面合并 | 由 SQLite 按其规则维护和复用 WAL 空间，不要求文件立即缩小 |
| 存在并发读写或检查点争用，本次不能完整推进 | 保留尚需处理的日志，后续再推进；单纯维护未完成不改判已提交业务或报告为失败 |
| 获得实际数据库读写故障证据 | 按状态库错误处理，不能归入普通维护未完成；提交结果仍按实际证据分类 |

日常运行中的检查点选择遵守 PASSIVE 策略，不主动使用要求更强等待的检查点模式来强制清空 WAL。检查点模式与 `synchronous=FULL` 是两项不同设置，采用 PASSIVE 不降低规定的提交同步等级。

自动检查点阈值是触发条件，不是 WAL 文件大小上限。慢查询及交叠的读事务可能阻碍页面合并或日志复用，文件已有空间也可能留作复用；不能仅凭文件未缩小认定检查点失败。第一版依靠自动 PASSIVE 检查点及报告逐批释放读取；实际数据库故障继续按已有错误规则处理。

验收覆盖配置缺省、合法覆盖与边界、非法类型及越界值，以及会话内固定、后续调用采用新值。逐个核验写入口及重新创建连接的实际设置，覆盖设置失败和核验不符。使用可控写入验证未达、恰好达到及超过阈值的行为，按实际 WAL 页记录计量，不以事件数代替。另覆盖报告持有读事务时部分推进、读事务结束后后续写入能够继续推进，以及维护争用与实际数据库错误的区分。目标主机测量触发检查点时的提交延迟、设备调度延迟和 WAL 增长；是否需要调整执行安排由实际负载证据决定。

### 后续设计提醒：WAL 积压时的读取协调

**本节不属于第一版实现或验收范围。** 若后续联调或运行发现自动检查点与分批短读事务仍不足以应对持续积压，可评估按压力协调读取与检查点的机制。第一版不为该提醒增加运行时积压监测、暂停通信、协调状态机或专用配置。

候选流程为：发现需要干预的积压后，报告完成当前批次并释放读取，暂缓下一批；主进程暂缓新增快照维护读取，通过已有数据库线程安排一次 PASSIVE 检查点；本次返回后报告继续已有任务，不以 WAL 清空作为继续条件。恢复副本、冻结范围、分页位置和文件生成进度保留，普通计划接纳与必要业务保存继续进行。

正式启用前仍须定义压力判据、监测方式、协调频率、等待预算、与报告总生成时限的关系，以及通信失败和实际数据库故障的处理。PASSIVE 自身的磁盘读写可能耗时，不能把它视为固定时长操作；检查点部分推进也不等于数据库故障。设计需要同时验证 WAL 能够继续维护和报告能够持续完成，避免反复停读或重新生成导致状态迟迟无法交付。

## 状态分类

| 情况 | 处理规则 |
| --- | --- |
| 投影与相关历史可靠，在 `(H, C]` 中没有报告所需状态的变化 | 直接使用 C 的相关投影；报告实体选择与元数据仍取自冻结依据 |
| 上述前提成立，存在需要恢复的相关变化 | 按恢复路径选择规则，在副本上使用快照正向恢复或当前投影逆向恢复到 H |
| 对象在 H 之后创建 | 在 H 的结果中为不存在，不混入冻结报告 |
| 当前投影缺失、落后或不一致 | 按现有投影恢复规则重建并验证，不把坏投影用作逆向起点 |
| 事件缺失必要恢复依据、数据不一致、未知事件无法解释或数据库读取失败 | 明确按状态库错误处理，不以默认值补齐，也不把损坏静默解释为普通性能降级 |

报告正常生成与重建都使用这套分类。不能仅凭报告是首次生成就认定当前投影可用，也不能仅凭报告较旧就认定所有实体都发生过变化。

### 按对象选择恢复路径

先按上述规则处理数据库错误、投影失效及对象在 H 尚不存在的情况。对在 H 存在、所用依据可靠的对象，按下表顺序选择路径。S 表示不晚于 H 的最近可用历史快照位置。

| 条件 | 处理方式 |
| --- | --- |
| `(H, C]` 内对象没有相关状态变化 | 直接使用当前投影 |
| 对象在 H 之后有变化，存在 S＝H 的快照 | 直接使用该快照 |
| 对象在 H 之后有变化，没有不晚于 H 的快照 | 从当前投影逆向处理 `(H, C]` 的相关事件 |
| 对象在 H 之后有变化，存在 S＜H 的快照，正向所需事件更少 | 从快照正向处理 `(S, H]` 的相关事件 |
| 上述两条路径都有依据，逆向所需事件更少 | 从当前投影逆向恢复 |
| 上述两条路径所需事件数相同 | 从当前投影逆向恢复，复用已经取得的投影副本 |

比较对象自身的相关变化次数，不以全库历史位置的数值距离估计。采用下文的[实体历史关联与累计变化计数](#实体历史关联与累计变化计数)，一条事件改变一个实体需要恢复的状态计一次；计数与事件、目录和投影同事务更新，快照保存对应计数。通过索引取得 H 处的计数后，以计数差计算两段范围的相关变化数，避免为选择路径而读取两段完整事件正文。具体列名和索引实现仍需细化。

例如，S 处累计变化 20 次，H 处 28 次，C 处 328 次，正向处理 8 次，逆向处理 300 次，选择快照路径。事件数量是第一版的成本估计，不保证实际耗时始终最小；单条事件大小、读取与解码成本仍纳入性能验收。

若 S、H、C 处累计计数分别为 20、28、36，正向与逆向均需处理 8 条相关事件，则从当前投影逆向恢复。无需回放或恰好命中快照的情况先按表中前置分支处理，再对需要回放的两条可用路径比较事件数。

同一报告可对不同对象选择不同路径，所有对象最终都恢复到同一 H。事件正文可复用读取和解码结果，实际状态恢复按各对象所需的事件区间与方向进行；事件涉及多个对象时，必须分别处理本次需要恢复的对象影响，每个对象对同一事件的影响只应用一次。对象之间的关联及父对象完整状态均遵守同一边界，不执行外部副作用。

缺少可选历史快照时可按表使用逆向路径；检测到计数、快照或所需历史损坏、无法解释时按状态库错误处理，不能把数据错误当作普通缓存未命中。

## 事件恢复依据

每种业务事件明确规定它改变哪些状态，并保存这些变化所需的前后值。恢复信息按有业务含义的字段或成员组织；例如，更新一次录像启动尝试时，保存该次尝试被改变的部分。事件类型、成立条件、正向更新规则和逆向恢复规则共同构成该事件的契约。

| 状态变化 | 必须能够表达的恢复信息 |
| --- | --- |
| 覆盖字段 | 变化前的值及其类型；新值用于正向更新与一致性检查 |
| 新增或移除可选字段 | 明确区分字段不存在与显式空值 |
| 新建实体 | 身份、所属关系、完整初始事实及创建位置；逆向跨过创建位置时恢复成不存在 |
| 改变逻辑有效性或状态 | 变化前后的明确状态；不能从名称推测原值 |
| 增加集合成员 | 成员身份、内容和必要顺序；逆向时先恢复该成员后来的变化，再撤销加入 |
| 修改集合成员 | 成员身份及被修改部分的前后值；保留其他成员 |
| 移除或替换集合成员、改变关系 | 被移除或替换的成员及关系的前后事实；有语义顺序时还需恢复顺序 |
| 更新派生父对象 | 直接保存父对象被改变状态的前后值，与触发变化的子对象事实同事务提交 |
| 清理产物或撤回交付 | 原状态、新状态及实际处理事实；逆向只恢复查询副本中的状态，数据库永久保留实体与历史 |
| 同一事务改变多个实体 | 保留事务分组与内部顺序；状态查询只暴露完整事务边界 |

旧值在写事务内依据该事件发生前的实际状态取得。同一事务多次修改同一字段时，后一个事件的旧值对应前一个事件生效后的值；逆向按相反顺序处理。

例如，最后一个未结束动作完成，使计划由 `running` 变为 `completed`，同一事务保存动作完成及计划状态变化的恢复信息；本次还登记正式产物时，一并保存产物创建事实。恢复父计划自身的旧状态直接使用这些信息，无需为计算计划阶段读取全部子动作。具体拆成几个事件及字段名称仍需在事件契约中确定。

逆向跨过事务时，应处理它对本次查询对象及必要依赖的全部影响。只恢复动作的 `status`，却保留后来的产物、诊断或父计划状态，不能得到合法的旧状态。

原始计划及受理时固定的生效参数由创建事实永久保存，后续事件通过稳定身份关联。其他大型不可变结果的复用方式仍需细化。引用必须能够定位永久保存的事实，不能读取当前配置、重新应用默认值或访问已经可能删除的输入文件。

## 事件正文与两类查询目录

事件正文保存一次，另维护两类轻量查询目录。目录保存定位事件和对象所需的关联，内容由事件及确定的规则派生，能够从历史重建。具体表划分、列名和索引组合仍需结合 SQL 细化。

| 目录 | 回答的问题 | 索引组织方向 |
| --- | --- | --- |
| 业务变化与实体的关联 | 业务覆盖区间内哪些实体发生了应报告的变化 | 按业务变化序号定位区间，再取得实体类型与身份 |
| 实体与历史事件的关联 | 指定实体在冻结之后发生了哪些状态变化 | 按实体类型、身份及历史位置定位相关事件 |

例如，交付 D 在业务变化 21、22 和 23 分别创建、推进到 40% 和 70%，业务目录保留这三次关联。覆盖 `(20, 22]` 的报告仍能选中 D，不能只保存其最后变化序号 23。若报告冻结在历史位置 100，当前读取位置为 110，历史目录直接定位 D 在 `(100, 110]` 的事件，取得旧值并恢复查询副本。

事件正文、两类目录中本次新增的关联及受影响的当前投影在同一事务中保存。只追加本次关联，不遍历全部历史。一次事件改变多个实体时，为各受影响实体建立关联；批量读取正文按事件身份去重，保留每个实体需要应用的影响。恢复按各实体选定路径的顺序进行，每个实体对同一事件的影响只应用一次。

关联按实际影响分类：改变对象状态时建立恢复查询关联；产生应报告的业务变化时建立业务变化关联。仅引用另一个对象的身份，不表示该对象发生变化。补齐报告父对象也不因此产生业务变化。

两者都需要适当索引，不能先读取整库历史再在 Python 中过滤。复合索引可以支持限定条件和顺序读取，具体列顺序及查询方式应由实际 SQL 和执行计划决定，见[SQLite 查询规划](https://www.sqlite.org/queryplanner.html)。

### 实体历史关联与累计变化计数

实体历史目录中，每条关联保存实体类型、实体 ID、`event_seq` 和该实体截至本事件的累计变化计数。同一实体与同一事件只保存一条关联，按“实体类型、实体 ID、事件序号”定位；不同实体各自计数，不使用全局事件序号或 `change_seq` 代替累计变化计数。

计数单位是一条事件对一个实体产生需要恢复的状态变化。按各事件实际发生的变化计算，不把整个事务的净结果当作一次变化；事件正文仍只保存一次。

| 事件影响 | 关联与计数规则 |
| --- | --- |
| 创建实体 | 保存创建关联，该实体累计计数从 1 开始 |
| 一条事件改变同一实体的一个或多个字段 | 保存一条关联，计数加 1 |
| 同一事务内 N 条事件分别改变同一实体，N＞0 | 按事件顺序保存 N 条关联，累计计数依次增加 |
| 一条事件同时改变多个实体 | 为每个受影响实体分别保存一条关联，各自计数加 1 |
| 事件只引用实体身份，没有改变其需要恢复的状态 | 不为该实体建立恢复关联，也不增加其计数 |
| 重复取得同一实体与事件的关联 | 不重复保存或增加计数；读取复用不改变持久化计数 |
| 保存事务回滚或提交结果未知 | 与事件、目录和投影保持同一事务结果，沿用确认回滚及结果未知的分类 |

累计计数由不可变历史及各事件的状态变化规则派生，可以重建。事件正文、关联、计数及相关当前投影一起提交；计数不是另一份独立业务事实。生成快照时保存边界 S 处的计数，后续变化不修改旧快照中的计数，快照维护也不重置实体的累计计数。

对在目标边界 H 已存在的实体，通过索引定位该实体在 `event_seq ≤ H` 范围内的最后一条关联，取得 H 处的累计计数。即使 H 处最后一条全局事件属于其他对象，也能取得正确计数。对象在 H 尚未创建时遵守不存在分支；对象应已存在但关联缺失、计数矛盾或查询失败时，按状态库错误处理，不默认计数为 0。

计数分别绑定其历史位置：C 处计数与对应当前投影在同一短读事务内取得，S 处计数随已选快照保存，H 处计数按不可变历史关联查询。分别用 H 与 S 的计数差估计正向恢复的事件数量，用 C 与 H 的计数差估计逆向恢复的事件数量。例如，S、H、C 处计数分别为 20、23、100，正向需要 3 条相关事件，逆向需要 77 条。无需为比较路径读取事件正文或逐条统计整段关联；索引与查询计划须验证能够定位对应实体的范围及末条关联。

快照触发中的“变化次数”使用相同单位。以当前累计计数减去该对象最近已提交快照在其边界处的计数，判断尚未包含的相关变化数；没有快照时基准为 0，创建计为第一次变化。首次及后续快照统一遵守[按对象累计变化次数触发](#按对象累计变化次数触发历史快照)的规则。每条关联增加一个累计计数字段，以额外存储换取范围计数查询，相关读写量纳入性能验收。

对[历史快照维护范围](#历史快照的对象范围)内的对象，用于发现候选的计数差按[派生维护进度](#持久化快照维护进度与候选查询)持久化，并与本次事件和投影保持同一事务结果。累计历史计数仍按上述规则永久递增，快照保存只更新相应的维护进度。

验收覆盖创建、单事件多字段、多事件同实体、单事件多实体、仅引用、重复关联、事务回滚与提交未知；验证同事务内多次覆盖乃至最终回到原值时仍按相关事件数量计数。查询覆盖 H 恰好位于对象变化处、位于两次对象变化之间、对象尚未创建及关联异常；快照生成后继续变化、正反向路径比较与维护触发使用同一计数含义。

### 统一事件表与按类型定义的 JSON 正文

事件使用统一事件表保存。`event_seq`、所属事务和事件类型等公共信息使用固定列；各类事件表达的事实及必要恢复信息使用 JSON 正文保存。正文只保存一次，查询目录引用对应事件；相关实体和历史范围的定位使用目录及索引，不通过逐条解析整库 JSON 完成。

JSON 是持久化表示。每种事件仍须有明确的字段、合法值、成立条件、正向更新及逆向恢复契约；Python 内部使用有明确类型的事件对象。持久化边界负责校验并在事件对象与 JSON 之间转换，未知事件类型、无效正文或缺失必要恢复依据按状态库错误处理。保存与读取遵守规定的精确数字、字符串及字段存在性规则。

| 处理阶段 | 责任 |
| --- | --- |
| 形成事件 | 根据事务内实际状态构造已定义类型的事件，包含真实的新旧值 |
| 保存事件 | 校验并编码正文，与公共信息、事务记录、目录及投影一起提交 |
| 查找历史 | 通过实体、业务区间或历史区间定位事件，再分批取得所需正文 |
| 读取事件 | 校验并解码为对应事件类型，再按既定方向恢复；不把解析成功等同于事件有效 |

事件字段演进遵守下文的[事件格式版本与读取兼容性](#事件格式版本与读取兼容性)。不可变历史继续保留原始事实，后续程序不能用当前默认值、配置或设备状态猜测旧记录缺失的信息。

验收覆盖不同事件类型的读写往返、缺失与空值、精确数值及 Unicode 字符、非法正文、未知事件类型，以及读取后的正向和逆向恢复结果。

### 事件格式版本与读取兼容性

统一事件表增加固定列 `event_version`，与 `event_type` 一起确定正文的字段及解释规则。各事件类型独立演进，第一版从版本 1 开始；事件格式版本不表示程序发布版本，也不代替数据库整体兼容性标识。

已发布的事件版本保持原有契约。新增、删除或改名字段，以及字段类型或含义变化，均使用新的事件格式版本。表达另一种独立业务事实时，使用新的事件类型。更新某类事件不要求其他事件类型同步增加版本。

新程序保留对旧版有效事件的读取能力。持久化边界根据事件类型和版本选择对应的校验与解释规则，在内存中转换为语义明确的事件对象；可以保持原意的结构差异由适配处理。数据库中的已有事件正文、类型、版本、序号及事务归属保持不变，不为适配新程序重写不可变历史。

例如，旧版以 `old_bytes`、`new_bytes` 表达可靠拷贝进度，新版将它们组织为 `before.bytes`、`after.bytes`，可以在读取时转换为相同含义。若新版新增分段校验和，旧事件未保存该事实，则保留“旧记录未提供”的明确含义或继续按旧版规则解释；不能使用当前文件、设备状态、默认值或空字符串补造当时的事实。

| 读取情况 | 处理规则 |
| --- | --- |
| 事件类型及版本受支持，正文满足该版契约 | 按该版本解释，再执行相应正向更新或逆向恢复 |
| 新程序读取受支持的旧版事件 | 保留原有事实和语义，仅在内存中适配表示 |
| 受支持版本的正文损坏或缺少该版必需字段 | 按状态库错误处理，不能当作正常旧格式补默认值 |
| 事件类型或格式版本不受支持 | 明确诊断格式不受支持，停止依赖该状态的业务处理，不忽略事件或试用邻近版本 |
| 新字段对应的事实未在旧记录中保存 | 按旧版契约保留信息边界；不把未记录解释为已知结果 |
| 事件格式升级后需要重建既有报告 | 继续使用原报告冻结依据及确定生成规则，保持原有字节、文件名和摘要 |

兼容性方向是新程序能够读取旧历史；不承诺旧程序可以处理新程序写入的新格式。对不支持格式的诊断与对损坏记录的诊断分别保留原因，均遵守既有状态库错误边界。

第一版只实现版本 1、版本识别和分派接口。正式增加后续版本时，同步提供旧版读取适配及回归用例，不提前实现假想的第二版。事件类型、版本与解释器的对应关系应有单一权威定义，校验和分派据此确定。

第一版验收覆盖支持版本的正确分派、不支持类型或版本、缺失或非法版本标识，以及合法正文与损坏正文的区分。新增版本时，再以固定旧记录验证新旧格式解释、正向及逆向恢复、历史记录保持原样和既有报告字节不变。

数据库采用[整体格式检查与显式升级](implementation.md#数据库整体格式检查与显式升级)。正式允许新事件格式前先升级整体 `format_version`；程序在使用业务状态前检查兼容性，不等到恢复某条新事件时才发现格式不受支持。投影与快照遵守下文的[保存格式规则](#当前投影与历史快照的保存格式)，后续实际升级流程及并发准入机制仍需细化。

### 存储接口与分批查询

当前状态查询、历史范围查询和原子写入应有分别明确的接口。写入只追加本次事实并更新受影响的投影；一次局部变化不应重新遍历、序列化或尝试插入全部已有历史。

批量生成报告时，应避免对每个对象重复扫描整段全局历史。分页必须保持冻结边界、入选条件或恢复范围及排序依据一致；每页使用短读事务，新提交不进入已经固定的范围。

### 按最后一个排序值续读

报告查询采用游标分页，即每批返回后记住最后一个排序值，下一批从该值之后继续读取。实体在各自所属集合内按完整 ID 的 ASCII 字典序升序读取，历史事件按恢复所需的历史顺序读取。分页位置必须完整表达排序依据并能唯一定位一项；事件使用 `event_seq` 区分同一事务内的不同事件。

| 读取情况 | 下一批的范围 |
| --- | --- |
| 某个集合或事件范围首次读取 | 从该范围在规定方向上的第一项开始 |
| 实体集合已返回一批 | 在同一集合及入选条件下，读取 ID 严格大于本批最后一个 ID 的实体 |
| 正向恢复已返回一批事件 | 在同一对象和恢复区间内，读取位置严格大于本批最后一个事件位置的事件 |
| 逆向恢复已返回一批事件 | 在同一对象和恢复区间内，读取位置严格小于本批最后一个事件位置的事件 |
| 查询成功且该范围无剩余项 | 结束该范围的读取 |
| 查询失败或取消 | 按相应失败或取消规则处理，不将缺失结果当作范围读完 |

每个集合分别维护分页位置。例如，动作 A 的产物读取完毕后，动作 B 的产物从 B 的集合开头读取。实体分页位置绑定数据库身份、H、固定入选条件、父对象和实体类型；事件分页位置另外绑定对应对象、恢复方向及固定的 `(H, C]` 或 `(S, H]`。每页取回数据后结束查询和读事务，在事务外处理，下一页重新开启短读事务。分页位置是本次生成的临时状态，批次之间暂时让出资源时保留；任务失败或进程结束后按报告恢复规则重新生成。

实体选择先按身份合并，再按实体排序和分页返回；同一实体在业务区间内多次变化也只返回一次。合并是查询结果契约，不要求先在 Python 中保存全部入选实体。查询接口、索引及执行计划需保证有序续读，不反复扫描已处理前缀；同时验收实体选择、去重和排序的读取量及资源开销，不能仅凭采用游标分页就认定查询高效。相关索引能力见 [SQLite 连续分页说明](https://www.sqlite.org/rowvalue.html#scrolling_window_queries)。

例如，每批读取两个入选产物，依次返回 `O001`、`O004`，再从大于 `O004` 的位置返回 `O007`、`O012`，之后确认没有剩余项。ID 无需连续，批次大小变化不改变入选实体、排序或报告字节。批次数量由下文的独立配置控制，具体接口类型和完成标记仍需细化。

### 实体与事件读取批次分别配置

报告生成及重建使用两个独立的主机本地 TOML 配置项，部署时可以分别调整：

| 配置项 | 默认值 | 单位与适用范围 |
| --- | --- | --- |
| `history.entity_batch_size` | `32` | 对象数；读取一个实体集合时，每页最多返回的入选实体数量，各类实体集合共用此值 |
| `history.event_batch_size` | `256` | 事件数；恢复一个对象时，在其已选历史范围内每页最多返回的相关事件数量，正向与逆向共用此值 |

实体批次读取对象自身状态，父对象与子实体集合按既定层次分别处理。事件批次控制该对象的历史分页，一个对象可以需要多个事件批次；无需恢复的对象直接使用已确定的状态。两项参数各自控制所属查询的返回数量，不规定并发任务数量。快照维护使用其独立的 `history.snapshot_batch_size`。

两项配置均为正整数，0、负数、浮点数、布尔值和字符串等非法值按[本地配置的加载与更新](../architecture/configuration.md#本地配置的加载与更新)报告配置错误。各项省略时使用本节定义的对应默认值。主进程在会话启动时加载并校验配置，将生效的读取批次参数传给报告进程；报告进程在本次会话内沿用这些值，包含故障后重新创建的报告进程。

| 配置情况 | 处理 |
| --- | --- |
| 两项均省略 | 分别使用各自内置默认值 |
| 只提供实体批次的合法值 | 实体读取使用该值，事件读取使用其默认值 |
| 只提供事件批次的合法值 | 事件读取使用该值，实体读取使用其默认值 |
| 两项均提供合法值 | 各类读取分别使用对应值 |
| 任一项非法 | 按配置错误结束调用，不开始报告读取 |

本次会话内值固定，部署调整后由后续会话加载。已有报告重建可以采用后续会话的批次设置，报告身份、冻结依据、入选对象、恢复结果及最终字节保持不变。各页仍使用短读事务，读完后释放查询和事务，再恢复状态或写出；候选不足一页时处理实际取得的数据，不等待凑满。

实现须避免为一批实体同时预载各自的完整历史。批次影响查询次数、单次读取工作量和临时数据数量，实际资源消耗及延迟由测试与联调验证。

默认值是第一版的初始工程取值，尚无实测性能依据。实体批次保持较小，控制同时保留的完整对象状态数量；事件批次采用较大的数量，减少长历史恢复中的分页次数。事件本身也可能较大，数量上限不保证固定的字节量或处理时长。联调分别覆盖大实体、长历史及较大的事件正文，按查询次数、读取量、实际峰值和业务延迟独立调整这两项参数。

### 分批读取与分段生成报告

camctl 与第三方主程序及其他软件共享主机内存。报告采用分批读取、恢复状态并逐步编码写出的方式，以适应超过可用内存的整体报告规模。内存中保留当前处理所需数据和有容量限制的缓存，已处理且不再需要的内容及时释放。

报告从新的 `staging` 文件开始生成。编码器维护对象、数组、分隔符及当前写入位置，依次写入 JSON 片段，无需读取或重新解析已经写出的部分。最终只形成一份完整报告，客户端按既有协议读取。任务失败、取消或进程结束后的 `staging` 文件按报告恢复规则从头生成；同一次生成在批次之间暂时让出资源时保留已有进度。

| 约束 | 要求 |
| --- | --- |
| 输出内容 | 仅包含本份报告选中的对象状态及必要父对象，不向客户端输出恢复事件历史 |
| 数据一致性 | 所有批次使用同一冻结依据；每份投影绑定自己的 C，历史查询限定在对应恢复区间，每个对象恢复到同一 H |
| 确定性 | 批次大小、缓存命中、正反向恢复路径不改变对象排列、JSON 编码及最终字节 |
| 处理范围 | 限制每批实体与事件数量，保留当前处理所需的父对象、恢复状态和续读位置；缓存、去重记录及编码缓冲有容量上限，已处理内容及时释放 |
| 第一版数据范围 | 按单个字段能在目标部署环境中正常处理来设计和验收；累计实体、子集合和相关历史数量增加时仍须分批处理 |
| 发布条件 | 全部入选对象和所需事件处理完成，完整内容、摘要和所需同步均成功后才交由主进程发布；容量限制不改变输出内容 |
| 读事务时长 | 每批取回数据后结束查询和事务，再恢复状态及写文件；联合评估单次读取时长、检查点推进、WAL 积压和主进程业务延迟 |

报告遵守[通过处理流程控制资源使用](implementation.md#通过处理流程控制资源使用)的规则。实体与事件读取批次分别按上述配置控制，缓存条目数、队列容量与满载处理、读写缓冲大小及分页查询接口仍需确定。实际资源消耗由测试与联调测量，覆盖 camctl 主进程、报告子进程及其管理的工具进程共同运行的情况，部署参考条件见[运行环境](implementation.md#目标环境与部署分工)。

### 逐层分批写出与实体排序

生成器按计划、动作及其产物或交付的所属关系逐层读取和写出。先写当前父对象的自身字段，再打开需要输出的子集合，分批恢复和写出入选子实体；当前子集合完成后关闭它，再继续后续集合或对象。顶层计划文件诊断也分批生成。数据库读取使用分批短读事务，恢复与写出在事务外进行，所有状态均恢复至同一 H。

查询接口按[报告格式中的实体排序规则](../architecture/report-format.md)返回入选实体，并保证跨批次不遗漏、不重复。父对象因自身变化和多个子实体变化同时入选时，也只输出一次。应用不先收集全部实体再排序或维护随报告总量增长的去重集合；采用上述游标分页，具体 SQL、索引、位置的字段表示及数据库查询的资源占用仍需细化和验证。

例如，计划 P 的动作 A 有一万个入选产物，可以先写 P 和 A 的自身字段，再每批处理 100 个产物，完成后继续 P 的下一个入选动作。100 仅为批次数量示例，改为 50 或 200 不改变输出字节。内存保留当前父对象、当前批次及有容量限制的缓冲，不组装整棵计划或动作子树。

| 场景 | 处理要求 |
| --- | --- |
| 仅父对象自身变化，无入选子实体 | 输出父对象自身字段；子集合表达遵守固定生成规则 |
| 一个或多个子实体入选 | 补齐所属父对象的完整自身字段，仅输出入选子实体 |
| 父对象自身和子实体均入选 | 合并为一次父对象输出，不重复对象或子集合成员 |
| 子集合跨多个批次 | 保持同一个 JSON 数组的写入位置和顺序，写完一批不关闭该数组 |
| 跨计划引用 | 按各实体实际所属关系输出，引用不扩大入选范围或复制被引用实体 |

对象自身字段、实体子集合的输出次序、紧凑排版及可选空实体集合的省略方式遵守[第一版生成器的结构与排版](../architecture/report-format.md#第一版生成器的结构与排版)。数字输出遵守[精确数值与统一写法](../architecture/report-format.md#精确数值与统一写法)，字符编码遵守[字符串与转义](../architecture/report-format.md#字符串与转义)。参数或结果中的普通数组保留原有顺序，不按实体排序规则重排。

## 收益与性能边界

假设数据库已有一百万条历史，新报告冻结后又提交十条相关变化。具备完整恢复依据及范围索引时，逆向方法需要读取本份报告的对象状态并处理这十条变化，无需计算之前的一百万条历史。这是算法示例，不是实测性能数据。

若目标边界很早，且相关实体在其后仍变化了几十万次，逆向方法依然昂贵。它将回放量从“目标之前的相关历史”换成“目标之后的相关历史”，并未使任意历史查询都具有固定成本。已长期稳定的实体则可能直接使用当前状态，即使全库增长了很多无关历史。

完整同步可能需要输出大量实体。无论采用哪种状态恢复方式，读取并编码这些输出本身都有成本。

事件中增加旧值会增大永久历史存储。内存、可用存储、CPU 与存储带宽均按实际部署及共享负载评估，运行保障不依赖某款设备或某个固定内存额度。报告生成时间、计划接纳延迟、主进程调度延迟、客户端可取得报告的冻结位置距当前业务的滞后、读取量、峰值内存与新增存储需要分别测量。持续负载超过实际存储能力时，短读事务不能保证固定时限内交付。

## 按对象累计变化次数触发历史快照

客户端取得的是入选对象在报告冻结边界处的状态快照，事件历史用于主机内部恢复和状态计算。当前投影已经持久化，并随每次状态变更的事务更新；普通当前状态查询直接使用它。

### 历史快照的对象范围

第一版历史快照维护对象限定为下表四类。快照资格、派生维护进度、候选索引查询、排序及提交后唤醒均使用同一范围；类型范围由统一对象类型定义提供。

| 对象 | 身份 | 快照保存的内容 |
| --- | --- | --- |
| 计划 | `plan_instance_id` | 指定历史边界处的计划自身状态与字段 |
| 动作 | `action_instance_id` | 指定历史边界处的动作自身状态与字段，包括参数、结果及尝试记录等 |
| 正式产物 | `output_id` | 指定历史边界处的产物自身状态与字段，包括可用性及清理结果等 |
| 普通交付 | `delivery_id` | 指定历史边界处的交付自身状态与字段，包括拷贝进度、发布及撤回状态等 |

`report_status` 按动作对象维护快照。对象之间的父子关联继续遵守报告与历史查询规则，父对象保存自身字段，子实体独立处理。

计划文件诊断按诊断创建事实保存完整内容，报告在固定覆盖范围和历史边界内选择并复用原记录。报告生成、发布及补投等管理记录、累计 ACK 和同步责任继续保存各自的历史及当前投影，需要历史状态时依据相应历史恢复。这些记录的保存与恢复沿用所属专题，不建立快照维护进度或进入快照候选查询；阈值为 1 时也保持这一范围。

对象范围只限定历史查询的快照优化。全部权威历史的永久保存、当前投影的事务一致性及报告责任保持各自契约。重建已有报告仍采用它已登记的覆盖范围、冻结边界和固定元数据，不用后来的累计 ACK 或同步责任改写报告内容。

### 对象快照内容与次数触发

按对象额外保存历史状态快照，记录某个完整已提交边界处的对象自身状态，供旧报告或其他历史查询复用。每份快照保存对象类型与身份、完整历史边界 S、该边界处的累计变化次数、保存格式版本及状态内容。父对象快照保存自身字段，子实体分别保存自己的快照；普通参数或结果中的数组、对象仍属于所属对象的自身字段。

各对象独立累计变化、判断阈值和保存快照。一次维护可以批量处理多个对象，它们仍各自拥有独立快照，不同对象的最近快照可以对应不同历史边界。生成报告时，各对象分别恢复到同一个冻结边界 H，再按报告结构组织。当前投影继续在每次状态变化时更新。

例如，报告冻结在 H＝1005，当前读取位置已到 C＝2000，若存在对象在 S＝1000 的完整快照，则可从该快照正向应用 `(1000, 1005]` 中的相关事件，取得 H 的状态。从当前投影逆向恢复的路径适用于目标之后变化较少的情况，按上文的相关变化次数选择。

历史快照仅按累计变化次数阈值触发。维护范围内的对象共用一个可配置的正整数阈值 N，各对象分别累计和判断自身尚未包含的变化次数。对已存在且持久化依据有效的对象，设当前累计变化次数为 A，最近已提交快照包含的累计变化次数为 B；没有快照时 B＝0。尚未包含的变化次数为 Δ＝A－B。变化次数采用[实体累计变化计数](#实体历史关联与累计变化计数)的单位，创建计为第一次变化，首次快照也按同一阈值触发。

| 对象状态 | 处理 |
| --- | --- |
| Δ＝0 | 已有快照包含全部变化，不安排重复快照 |
| 0＜Δ＜N | 暂不安排快照 |
| Δ≥N | 安排快照维护 |

上述判断以可靠计数为前提。对象应已存在但计数或关联缺失、A 与 B 矛盾、快照无效或读取失败时，遵守既有状态库错误规则；只有确认没有快照时才使用基准 0。

累计计数与已提交快照跨会话保留，重启不清零。正常 `run` 根据持久化记录重新发现达到阈值的对象，不要求对象在本次会话再发生变化。快照提交成功后，基准只推进到该快照实际包含的计数；读取快照依据后新增的变化继续计入后续判断。确认回滚不推进基准，提交结果未知时按既有规则核实实际持久化状态。

例如，阈值为 64 时，没有快照的对象在重启前累计变化 40 次，重启后再变化 24 次即可成为维护候选；若重启前已经达到阈值但尚未保存快照，后续正常 `run` 仍能发现它。假设保存的快照包含累计第 64 次变化，而准备期间对象又变化了 5 次，保存成功后 Δ＝5。

阈值使用主机本地 TOML 配置，本节定义其默认值与合法范围：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `history.snapshot_change_threshold` | `64` | 正整数；每个对象尚未被最近快照包含的变化次数达到此值时，安排快照维护 |

省略配置项时使用默认值；显式提供 0、负数、浮点数、布尔值或字符串等非法值时，按[本地配置的加载与更新](../architecture/configuration.md#本地配置的加载与更新)报告配置错误。阈值属于本次会话的维护配置，按[统一配置加载规则](../architecture/configuration.md#本地配置的加载与更新)取得，不属于动作受理时固化的设备配置。

配置在会话启动时读取，本次会话内保持不变。后续会话使用当次统一阈值重新判断各对象的持久化计数差；调整阈值不重置累计计数或快照基准，不改变已有业务事实、快照内容、报告冻结依据或输出字节。每批工作量遵守下文的[快照维护批量限制](#快照维护批量限制)。

阈值用于安排快照维护，不是阻止设备操作的条件；维护可能晚于阈值到达时刻，不能据此宣称历史恢复量具有固定上限。维护继续遵守[会话退出规则](#快照维护与会话退出)。

累计变化始终未达阈值的对象可以一直没有历史快照。它停止变化后的状态可直接使用当前投影，较早状态按恢复路径规则查询。若目标 H 早于该对象首份快照，且 H 之后持续发生大量变化，现有路径需从当前投影逆向恢复，成本可能较高。次数也不等同于字节量或实际耗时，相关负载须纳入性能验收。

快照是可由权威历史重建的派生数据，须标明对象身份和对应的完整历史边界，不能混入生成期间较晚的状态。它减少历史计算量，但新增快照写入和永久存储；其收益应与实际部署的存储容量及共享负载一起评估。大范围同步若需要输出大量对象，快照不能消除这些对象自身的读取和编码成本，报告继续按规定的分批处理方式生成。

### 持久化快照维护进度与候选查询

数据库为快照维护范围内的每个对象保存尚未被最近已提交快照包含的变化次数 Δ，并为候选查询建立索引。该值遵守 Δ＝A－B：A 为对象当前累计变化次数，B 为其最近已提交快照在快照边界处的累计变化次数，没有快照时 B＝0。对象类型与身份共同确定进度所属对象；具体表、列名和索引结构在数据库设计时确定。

维护进度是从不可变历史及已提交快照派生的查询数据，可以重建。各对象的 Δ 无论是否达标都按实际次数保存，阈值只用于查询条件。同一事务结束后，事件、历史关联、当前投影、累计计数及维护进度必须表达一致的已提交状态。`run` 与 `submit` 等保存对象变化的入口共用该规则，历史快照仍由正常 `run` 维护。

| 持久化操作或状态 | 维护进度的处理 |
| --- | --- |
| 创建对象 | 与创建事件和投影一起保存初始 Δ＝1；同一事务中后续变化继续按计数规则累计 |
| 已有对象发生需要计数的变化 | 在保存事件、关联与投影的同一事务内更新 A 及 Δ；B 保持不变 |
| 事件仅引用对象，没有改变其需要恢复的状态 | 该对象的 A 与 Δ 均不增加 |
| 已取得边界 S 的状态，快照尚未提交 | 已提交维护进度仍采用原 B；准备中的快照不推进基准 |
| 保存快照 | 在保存完整快照的同一写事务内，按提交时对象当前累计计数及保存后的最近快照计数更新 Δ；维护基准只确认已提交快照实际包含的变化 |
| 事务确认回滚 | 本次事件或快照及对应维护进度更新均不生效 |
| 提交结果未知 | 按既有提交结果未知规则确认整个事务，不依据内存中的候选进度宣称成功或再次扣减 |
| 对象应有维护进度但记录缺失、计数为负或与可信依据矛盾，或读取失败 | 按状态库错误处理；不默认成 0，也不将查询失败解释为没有候选 |

保存快照时使用该写事务中最新的 A，不能把读取 S 时的 A 带回去覆盖。假设对象当前累计计数已经从 S 处的 64 增至 70，本次保存的快照只包含 64 次变化，则提交后 Δ＝6。快照记录与这次进度更新整体提交，历史快照维护不新增权威业务事件，A 保持不变。再次确认同一已提交结果也不会重复减少 Δ，最近快照基准按已提交记录确定并保持不倒退。

正常 `run` 使用本次生效阈值查询 Δ≥N 的对象，通过索引分批返回候选，每批最多采用 `history.snapshot_batch_size` 个对象。启动后可以直接发现上次会话留下的候选；`submit` 已提交的对象变化也通过同一持久化进度进入可查询范围。候选发现以数据库为依据，进程内通知只能用于安排检查时机。

候选按本批查询的一致读取视图排序，优先处理 Δ 较大的对象；Δ 相同时依次按对象类型标识、完整对象 ID 的字典序升序排列。字符串比较保留大小写，数字片段按原字符串比较；同一类型与 ID 唯一确定一个对象。具体类型标识由对象类型定义统一提供，排序不另行维护一套类型优先级清单。

| 候选比较情况 | 顺序 |
| --- | --- |
| 对象 Δ＜N | 不进入本批候选范围 |
| 两个候选的 Δ 不同 | Δ 较大的优先 |
| Δ 相同，对象类型不同 | 对象类型标识字典序较小的优先 |
| Δ 与对象类型相同，ID 不同 | 完整对象 ID 字典序较小的优先 |

每批从当前候选排序的开头选取至多配置数量的对象。已选批次准备期间的新变化不重排本批对象，按已取得的状态与 S 完成保存；本批结束后让出执行机会，再依据最新已提交进度重新选取下一批。前一批保存快照会改变相应对象的 Δ，新增业务变化也可能改变候选集合与顺序，因此候选查询每批重新排序取前若干项，不沿用上一批可变 Δ 的分页位置。

持续频繁变化的对象可能在后续批次再次排在前面；该顺序不保证每个候选在固定时间内获得快照。未入选对象的维护进度保持真实值，继续参与后续查询。候选顺序只决定维护先后，不改变历史、当前投影或报告内容；快照维护继续遵守会话退出规则。

后续会话调整 N 时使用新的查询条件，已保存的 Δ 保持原含义。例如 Δ＝50 时，将 N 从 64 调为 32，后续正常 `run` 即可查到该对象；无需等待新事件，也无需改写所有对象的维护进度。未达标对象及已有快照覆盖全部变化的对象保留各自的实际计数。

查询只加载本批需要的候选及状态，不反复遍历全部对象或读取历史事件正文来判断是否达标。验收须检查实际 SQL 执行计划与读取量：保持达标对象及本批数量不变，增加未达标对象和无关历史，确认候选定位使用索引限定范围，并利用索引支持上述排序及数量限制。检查时机遵守下文的提交与发现驱动规则，实际索引方案仍需细化。

### 提交与对象发现驱动快照维护

快照维护由正常 `run` 内的提交结果与对象发现事件唤醒。数据库写操作在更新对象计数和派生维护进度时，判断本次受影响的快照对象是否已有 Δ≥N；确认提交成功后，通过本进程的完成处理路径发布维护唤醒。通知只表达需要检查候选，实际对象及顺序仍以数据库索引查询为准。普通业务处理只等待自身事务结果，快照生成由维护协程异步推进。

正常运行且快照维护启用时按下表处理；本次会话因[入队超时停止维护](#快照入队超时后的会话内停用)后，后续通知不再启动维护。进入会话收尾后，优先遵守已有维护退出规则。

| 场景 | 处理 |
| --- | --- |
| 进入正常 `run` | 通过维护进度索引查询一次，发现前次会话遗留或本次阈值下已达标的对象 |
| 本进程对象变化确认提交成功，至少一个受影响快照对象的 Δ≥N | 唤醒维护协程 |
| 本进程对象变化确认提交成功，受影响快照对象均未达标 | 本次变化不产生维护唤醒 |
| 对象变化事务确认回滚 | 本次变化不产生维护唤醒，已提交候选保持原状态 |
| 对象变化提交结果未知 | 按既有提交结果未知规则处理，不根据候选结果推断已提交 |
| `run` 通过既有流程发现外部提交的新对象 | 检查本次发现对象的已提交维护进度，存在达标快照对象时唤醒维护 |
| 收到维护唤醒 | 按索引、阈值和排序查询并处理本批候选 |
| 一批维护完成 | 释放临时数据并让出执行机会，仍处于正常运行时查询下一批 |
| 候选查询成功且为空 | 等待后续提交或对象发现产生的唤醒 |
| 进入会话收尾 | 停止安排新维护，准备、排队及已开始操作按实际阶段收尾 |

多个通知可以合并为一次待处理唤醒。维护期间发生的唤醒须保留到后续候选检查，空查询与进入等待之间到达的通知也须能够启动后续检查；不能在进入等待时覆盖尚未消费的通知。通知与提交结果的发布遵守数据库操作的实际完成状态，调用协程取消等待不等于实际操作回滚或结束。进程结束后由后续正常 `run` 的启动查询接续持久化候选。

新计划由 `submit` 原子受理后，`run` 在[已有新计划发现流程](../architecture/scheduling-execution.md#新计划发现与内存调度缓存)中检查新发现对象的维护资格。创建按对象分别计数：一个计划包含多个动作，每个对象仍按自身事件累计；子对象数量不累计为父对象变化次数。阈值 N＝1 时，创建即可达标，既有发现流程须覆盖这一合法配置。幂等重送复用对象，不因再次发现而增加计数。

`submit` 同时承担输入诊断及 ACK 的独立处理；有效 ACK 可以改变累计确认位置并结束同步责任。这些记录按[对象范围](#历史快照的对象范围)保存历史和相应投影，其变化自身不产生快照维护唤醒。同一事务同时创建计划或动作时，快照维护资格按本次受影响的范围内对象单独判断；受理拒绝及 ACK 错误产生的业务报告责任继续遵守所属专题。

### 当前投影与历史快照的保存格式

当前投影使用状态库当前 `format_version` 对应的结构。将来显式升级确实改变投影表示时，在维护阶段转换，或根据权威历史重建；验证完成后才恢复日常使用。投影表示没有变化时，不因整体格式编号增加而要求无意义地重写投影。转换与重建仍不执行设备或文件交接副作用，也不改写历史事实。

历史快照保持原有内容，每份快照保存生成时采用的数据库格式版本，不增加独立的快照版本编号。快照的格式标记、对象身份、完整历史边界 S、对应计数及内容一起提交。读取时按该快照自身的格式标记解释，不以数据库当前格式替换旧快照的标记。

| 信息 | 含义 |
| --- | --- |
| 数据库元信息中的 `format_version` | 当前状态库采用的持久化契约及当前投影表示 |
| 快照记录中的 `format_version` | 生成这份快照时采用的保存格式 |
| 快照边界 S | 快照表达哪个完整历史边界处的对象状态 |

例如，格式 2 的数据库可以按其契约保留一份“边界 100、保存格式 1”的旧快照，同时新增“边界 200、保存格式 2”的快照。程序先确认支持该数据库格式，再分别按快照记录的格式校验和解码；旧快照需要的表示适配在内存中完成。S 不因解码或适配而改变。

| 情况 | 处理规则 |
| --- | --- |
| 快照采用当前格式且内容有效 | 校验后用于相应边界的恢复 |
| 快照采用当前数据库契约允许保留的旧格式，内容有效 | 按旧格式校验并解释，需要时在内存中适配；不重写原快照 |
| 快照格式标记缺失、非法、不受支持或不属于当前数据库允许的格式 | 明确按状态库错误处理，不按当前格式猜测，也不作为普通缓存未命中跳过 |
| 快照内容损坏或不能可靠解释 | 继续遵守历史状态查询的错误规则，不补造状态 |
| 新格式需要的信息未在旧快照及相应旧事实中记录 | 保留旧契约的信息边界，不用当前默认值或设备状态补齐 |

程序声明支持某个数据库格式时，必须支持该格式允许保留的旧快照表示。增加数据库格式时明确其当前投影结构、新快照保存结构和可读取的旧快照结构；共用相同表示的格式可以复用解释器。格式及解释器的对应关系遵守单一权威定义要求。

第一版只生成和读取格式 1 的快照，并实现格式标记校验。后续实际格式变化时再实现转换和适配，验收旧快照内容与边界保持不变、新旧快照解释得到独立预期、正向恢复结果正确及既有报告字节不变。投影转换、重建的维护步骤和中断恢复随实际升级方案定义。

### 快照维护批量限制

每批维护按对象数量上限组织，遵守[资源处理约束](implementation.md#通过处理流程控制资源使用)。数量上限使用本地配置：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `history.snapshot_batch_size` | `16` | 正整数；每批最多处理的对象数量 |

省略时采用默认值，非法值按本地配置错误处理；合法值与错误分类沿用快照变化次数阈值的正整数规则。配置在会话启动时读取，本次会话内保持不变。该值是批次上限，候选不足时可以处理较小批次。

维护只保留当前批次需要的对象状态与快照内容，减少读取、转换和编码过程中的重复副本，已完成且不再使用的临时数据及时释放。超过本批数量上限的候选留给后续批次，仍按其持久化计数与快照判断资格；未保存快照的对象基准保持不变。

| 会话及批次状态 | 处理 |
| --- | --- |
| 已进入会话收尾 | 停止安排新批次，进行中的操作按会话退出规则处理 |
| 正常运行，本批已达数量上限 | 停止向本批加入对象，按生成流程处理本批 |
| 正常运行，本批未达数量上限且还有候选 | 可继续向本批加入对象 |
| 正常运行，本批未达数量上限且当前候选范围已读完 | 处理本批已有对象；本批为空时不执行快照保存 |

每批完成后释放不再需要的临时数据，让出执行机会，再检查会话状态及后续候选，决定是否安排下一批。批次上限不保证固定的内存占用或数据库耗时，也不要求本次会话清空全部维护候选。测试与联调覆盖不同对象大小和候选数量，测量快照维护与业务并行时的实际资源消耗及延迟。

### 业务操作优先使用数据库线程

同一个正常 `run` 内，数据库线程在选择下一项操作时优先处理等待中的业务操作；只有没有业务操作等待时，才开始快照维护的数据库操作。此处业务操作包括正常执行所需的状态查询及事务保存，快照维护包括候选查询、快照依据读取及快照保存。报告责任的登记与推进仍属于正常业务处理。

下表适用于允许继续派发数据库操作的正常运行阶段。“有等待操作”指已进入本进程排队、尚未开始且仍有效的操作；已确认取消的操作不参与选择。

| 数据库线程状态 | 有业务操作等待 | 有快照操作等待 | 处理 |
| --- | --- | --- | --- |
| 已有操作开始 | 任意 | 任意 | 跟踪当前操作至实际结束，按既有结果与错误规则处理；允许继续时再选择下一项 |
| 空闲 | 是 | 是 | 先执行业务操作，快照操作继续等待 |
| 空闲 | 是 | 否 | 执行业务操作 |
| 空闲 | 否 | 是 | 执行一次快照数据库操作 |
| 空闲 | 否 | 否 | 等待新操作 |

每次从等待状态转为开始执行时按上述规则选择。业务操作在快照尚未开始时进入排队，应先获得执行机会；快照操作已经开始后才到达的业务操作，等待当前操作实际结束。优先顺序不打断已开始的读取或事务，不改变提交、回滚及结果未知的处理规则。

成功入队后按[排队与取消规则](implementation.md#入队后的排队与取消)等待派发，第一版不另设排队超时。快照长期等待派发不等于入队超时，不因此触发本会话维护停用；进入收尾时仍按实际阶段取消或跟踪。

快照读取与保存分别参与排队，读取完成不为后续保存保留数据库线程。事务外准备快照内容时，数据库线程可处理业务操作；准备完成后的保存重新按表中规则等待。批次结束后的让出执行机会仍按批量限制执行。持续有业务操作等待时，快照可以长期推迟；对象维护进度继续保留，不保证快照完成时间。已开始的快照操作仍可能使后来到达的业务等待，其耗时需要通过短事务和实际负载测量控制。

本规则只决定同一 `run` 内的操作派发顺序。独立 `submit` 进程及报告子进程使用各自连接，它们与 `run` 的数据库锁竞争遵守对应连接与事务规则，本进程排队不提供跨进程优先级。进入收尾后按[快照维护与会话退出](#快照维护与会话退出)停止新增维护并处理已排队及已开始的操作。

### 快照入队超时后的会话内停用

快照候选查询、依据读取及保存均遵守[数据库队列入队等待时限](implementation.md#数据库队列入队等待时限)。等待达到该上限且确认本次操作未入队、以后也不会执行时，向维护调用方返回明确的入队超时错误，通过既有日志通道记录诊断，并停止本次 `run` 的后续快照维护。此故障自身不形成会话 `state_db_error`，不阻止普通业务，也不改变会话成功条件。

维护是否启用属于本次会话的内存状态；对象的累计计数、快照基准及派生维护进度仍以数据库为准。维护状态按下表转换，进入收尾优先于安排新维护：

| 会话与维护状态 | 事件 | 处理及后续状态 |
| --- | --- | --- |
| 新会话进入正常 `run` | 正常运行启动 | 启用维护，按本次阈值查询持久化候选 |
| 正常运行、维护启用 | 某次快照数据库操作确认入队超时 | 返回错误并记录诊断，停止本次维护并释放可重新生成的临时内容，转为本会话停用 |
| 正常运行、本会话停用 | 新业务提交、外部对象发现、已发出的维护通知、队列空位出现或时间经过 | 保持停用，不查询新候选、不安排读取或保存；正常业务仍按原事务规则更新计数与维护进度 |
| 进入会话收尾 | 尚在等待快照操作入队 | 确认取消且以后不会入队或执行后退出等待，无须等满入队时限 |
| 进入会话收尾 | 快照操作已入队或已经开始 | 按实际阶段遵守维护退出规则，确认取消或跟踪至实际结果 |

本次超时不推进快照基准或减少未包含的变化次数，已提交快照保持有效。已发出但尚未处理的维护通知不能重新启用维护，也无需累计待下次消费的通知；后续正常 `run` 从持久化进度重新发现候选。未生成快照的对象仍按既有历史恢复规则参与查询，快照积压不单独延长会话或产生 `needs_run: true`。

已经入队的操作不再适用入队超时，迟到的入队计时通知不能将其当作未执行。实际数据库查询、读取或保存失败及提交结果未知仍遵守状态库错误规则，不能解释为本节的可延后优化失败。必要业务入队超时或其他会话错误也仍按自身规则处理，本次停用快照维护不改变这些错误的影响。

### 业务提交后分批生成快照

业务先按既定规则可靠提交。由 `run` 中的维护协程分批处理达到生成条件的对象，实际数据库读写交给已有数据库线程，遵守[业务操作优先顺序](#业务操作优先使用数据库线程)；报告子进程继续只读数据库。每批按以下顺序处理：

1. 通过维护进度索引，按本次阈值与批量限制找出本批需要生成快照的对象。
2. 在一致的读取视图内取得这些对象的状态、完整历史边界 S、S 处各对象的累计变化次数及生成所用的格式版本，保留不可变的数据副本。
3. 结束读取事务，在事务外准备快照内容。
4. 用短写事务保存各对象的完整快照、对象身份、边界 S、对应累计变化次数及格式标记，并在同一事务中更新派生维护进度；只有提交成功后，快照及相应进度才可用于后续查询。升级与运行隔离保证本次维护期间不会启用另一数据库格式。

例如，在位置 100 读到 D 的进度为 40%，准备期间业务推进到位置 110，D 变成 70%；随后保存的快照仍标记为“D 在位置 100 时为 40%”。不能用保存时的最新历史位置替换 S，也不因对象后来变化而反复丢弃可靠的旧状态。

| 生成与保存情况 | 处理 |
| --- | --- |
| 已取得 S 的完整状态，期间对象继续变化 | 保存对应 S 的快照；S 之后的变化仍属于后续快照触发的判断范围 |
| 尚未生成快照，或正在准备、尚未提交 | 报告使用已有可靠快照或当前投影与历史，不等待本次维护完成 |
| 快照事务提交成功 | 完整快照可查询；维护进度仅确认到该快照实际包含的边界 |
| 保存失败且确认回滚 | 本批没有新增已提交快照；数据库错误按既有状态库错误规则处理 |
| 保存结果未知 | 不宣称快照已保存或未保存；按既有提交结果未知规则确认实际状态 |
| 生成期间进程终止或主机断电 | 恢复时以完整已提交记录为准，未完成内容不能作为有效快照 |

快照生成与报告分批生成是不同流程，本节不确定报告的编码与文件写入方式。

### 快照维护与会话退出

快照维护属于性能优化，不单独阻止 `run` 结束，也不单独使 `submit` 返回 `needs_run: true`。已有业务及本地报告责任仍按[待处理工作的判定](../architecture/protocol-session.md#待处理工作的判定)检查；快照维护不能改变它们的完成条件。

正常收尾时停止安排新的快照维护，并按操作实际阶段处理：

| 维护阶段 | 退出行为 |
| --- | --- |
| 尚未达到生成阈值 | 不等待阈值到达，按其他责任正常收尾 |
| 已达到阈值，尚未开始维护 | 留给后续正常 `run`，不要求本次清空积压 |
| 已取得对象状态，正在准备快照内容，尚未提交保存操作 | 可以取消，丢弃可重新生成的临时结果 |
| 数据库操作正在等待入队 | 确认取消且以后不会入队或执行后继续退出，无须等满入队时限 |
| 数据库操作已排队，尚未执行 | 确认取消且不会执行后，继续退出 |
| 数据库操作已经开始，包括取消请求与开始执行发生竞争的情况 | 跟踪至实际结束；按读取结果或提交、回滚、结果未知分类处理，再关闭连接 |

后续正常 `run` 通过派生维护进度索引重新发现达到本次阈值的候选，不依赖上次会话尚未保存的内存队列。报告仍可使用已有可靠快照或当前投影与历史恢复，不等待新快照生成。

数据库错误继续按既有状态库错误规则处理；快照属于优化不改变提交结果未知的处理要求。排队取消的具体机制及已开始操作的等待预算仍需细化。

## 待细化事项与验收

1. 按规定的恢复信息分类，逐类定义业务事件的字段、成立条件及事务内的校验和保存方式。
2. 将各类事件的正向、逆向规则落实为接口契约，覆盖字段存在性、集合及关联变化、派生父状态和事务内部顺序。
3. 在已选全局事件序号及分配规则、初始化边界、事务标识及边界、WAL、分批短读事务、独立读取批次配置与逐层分批输出方式基础上，细化表与索引、有序分页接口、可变状态读取粒度、缓存适用性与条目上限、队列与缓冲容量及取消清理。积压触发的检查点协调及暂停协议属于后续设计提醒，不作为第一版待办。
4. 在规定的快照对象范围、统一阈值配置、按对象计数触发、派生维护进度、候选排序与索引查询、批次数量上限、提交与对象发现驱动及路径选择规则基础上，细化退出预算，以及快照和事件的实际索引与接口。
5. 正常新报告、断电后补投、较旧报告和完整同步四类负载的规模与验收预算。

验证矩阵至少包括：

| 验证目标 | 场景与预期 |
| --- | --- |
| 恢复准确 | 多次覆盖同一字段、字段不存在与显式空值、创建边界、集合成员加入与后续修改、终态及父子关系变化，得到独立定义的旧状态 |
| 父状态恢复 | 最后一个未结束动作完成并改变计划状态，逆向恢复动作和父计划；补齐父计划自身字段无需读取全部子动作 |
| 实体历史计数 | 一事件多字段只计一次，多实体各自计数，同事务多事件分别计数；边界间计数差与独立枚举的相关事件数量一致，回滚不推进计数，关联缺失不解释为 0 |
| 事务完整 | 同事务多个事件、多个实体，在事务前后分别查询，不出现部分提交状态 |
| 并发一致 | 取得投影与 C 后结束事务，再提交新变化；历史分页仍限定原 C，多对象采用不同 C 后均恢复至同一 H |
| 入选集合稳定 | 分页之间新增对象、修改入选对象或改变关系，按冻结区间和 H 查询仍无遗漏、重复或未来对象混入；H 处父子关系正确 |
| 读取依据稳定 | 当前计数与投影一起取得，H 的计数及已选快照跨事务读取仍对应固定位置；分页中出现新快照不替换本对象的恢复依据 |
| 事务释放 | 在历史恢复、编码及文件写入处暂停，验证该任务没有保留活动数据库查询或读事务；同一对象的大量事件也逐批释放 |
| 负载与持续推进 | 持续提交计划并产生业务变化，组合慢存储、CPU 竞争、完整同步及长历史，测量 WAL 积压、计划接纳延迟与完整报告产出；不以单次报告总耗时或物理 WAL 文件大小代替这些指标 |
| 回放无副作用 | 正向与逆向路径只生成查询结果，不改变当前投影，不执行外部操作 |
| 报告不可变 | 后续业务变化、配置变化、进程重启及重新生成后，原报告字节相同 |
| 分批编码 | 改变批次大小及缓存容量，包含跨批父子关系、特殊字符和空集合，输出仍为相同完整 JSON；中断不发布半成品 |
| 结构与排版 | 改变自身字段的构造顺序，含嵌套参数对象和中文，输出顺序与字节不变；验证 UTF-8、无 BOM、紧凑分隔符和唯一结尾 LF；空实体集合省略，参数中的空数组、空对象及 null 保留 |
| 字符串编码 | 字段名和字符串值覆盖中文、表情、引号、反斜杠、全部 U+0000～U+001F 控制字符及正斜杠；等值合法转义生成同一字节，异常输入诊断中的转义文本可编码且准确保留 |
| 数字格式 | 覆盖正负零、非零正负数、尾随零、指数写法、绝对值在 `0.000001` 与 `10²¹` 两个分界的两侧及恰好等于分界；保留全部有效数字，保存与历史恢复后输出字节一致 |
| 有序嵌套 | 覆盖仅父对象、仅子实体、父子均变化、跨计划引用和同实体多次变化；跨批次无遗漏或重复，父对象只输出一次，不加入未入选兄弟实体 |
| 排序边界 | 实体 ID 覆盖大小写、共同前缀和数字片段，按完整 ASCII 字典序排列；参数和逐项结果等普通数组保持原有顺序 |
| 分页边界 | 覆盖空集合、单项、恰好一批、多批、ID 不连续、切换父对象和同实体多次变化；批次大小变化不遗漏或重复实体，查询失败不判为读完 |
| 历史分页 | 正反向恢复均覆盖同一事务内多事件跨批次，以及区间上下界；每个对象所需事件影响恰好应用一次，后续并发提交不混入读取 |
| 读取批次配置 | 两项均省略、仅覆盖其中一项、分别覆盖两项和非法值；只改变一项时另一项生效值不变；每个实体页及事件页分别遵守所属上限，覆盖空页、不满页、恰好一页和多页，正反向事件读取采用同一事件批次值 |
| 读取配置传递与重建 | 报告进程取得本次会话生效参数，故障后重新创建仍沿用相同值；后续会话分别调整实体与事件批次重建同一报告，所得对象、状态及报告字节均与独立预期一致 |
| 续读成本与中断 | 增加已处理前缀长度，核验后续分页不重复扫描该前缀；批次间暂时让出资源后按原范围续读；任务失败或进程结束后的重新生成不复用半份 JSON，仍为相同字节 |
| 报告内存 | 在第一版数据范围内，增加总对象数、单个父对象的子实体数和相关事件数，验证不保留全量对象、事件或去重集合；验收峰值须包含数据库缓存及对象转换开销 |
| 错误明确 | 投影不可靠、恢复依据缺失和读取中断均进入明确错误或恢复分支 |
| 局部查询成本 | 保持目标之后相关变化数不变，增加无关历史与历史前缀，检查查询计划、读取量及处理量 |
| 写入成本 | 保持本次事件与受影响实体数不变，增加已有历史，局部写入不遍历全部历史 |
| 旧边界成本 | 增大目标之后的相关变化数量，测量逆向路径成本及是否满足预算 |
| 快照恢复 | 从可靠快照正向恢复，与从当前投影逆向恢复及独立预期得到相同结果；同一报告字节不因所选路径改变 |
| 路径选择 | 覆盖无后续变化、恰好命中快照、无较早快照，以及两条回放路径事件数的比较：正向更少时选正向，逆向更少或相同时选逆向；验证前置分支的处理顺序及多对象分别选择路径；选择时不加载两段完整事件正文 |
| 多对象事件复用 | 同一事件涉及多个入选对象，不因正文去重漏掉其他对象，也不对同一对象重复应用；不同快照起点及正反向路径均得到同一 H 的独立预期 |
| 快照触发 | 有无已有快照分别覆盖 Δ＝0、0＜Δ＜N、Δ＝N 与 Δ＞N 的有效分区；创建计为 1，首次基准为 0，N＝1 时创建即可达标；计数矛盾或查询失败不解释为无快照 |
| 快照对象范围 | 四类对象分别覆盖创建、更新及达标，`report_status` 按动作处理；计划文件诊断、报告管理记录、累计 ACK 与同步责任保留各自历史及投影，N＝1 时也不产生维护进度、候选或自身的维护唤醒；同一事务混合范围内外变化时，仅按范围内对象判断快照资格 |
| 范围外记录恢复 | 输入诊断按覆盖范围和 H 复用原事实；ACK 与同步责任按既有规则原子保存；后续 ACK 推进、同步责任结束及报告管理变化不改变已有报告重建字节，内部状态的历史恢复得到独立预期 |
| 快照阈值配置 | 省略配置项采用本节默认值，合法正整数覆盖默认值；0、负数、浮点数、布尔值及字符串按配置错误处理；会话内值固定，后续会话按新配置判断已有对象 |
| 快照跨会话判断 | 未达阈值时重启后继续累计；达标未保存时重启后无需新变化即可发现候选；后续会话提高或降低阈值时按原计数差重新判断；对象无新变化且已有快照覆盖全部变化时不重复生成 |
| 快照维护进度 | 创建、同事务多次变化、多对象变化及仅引用分别得到正确 Δ；`run` 与独立 `submit` 均随事件和投影原子更新；准备快照后新增变化仍保留，快照与进度同事务提交，确认回滚及提交未知按实际结果处理，重复核验已提交结果不重复扣减 |
| 候选查询与异常 | 以独立历史和快照预期核对 Δ 及达标集合；配置变化直接改变查询条件；进度缺失、计数矛盾和查询失败进入状态库错误；保持候选规模不变并增加未达标对象与无关历史，核验实际索引、排序及限量查询的读取成本 |
| 候选维护顺序 | 覆盖 Δ 不同、Δ 相同但类型不同、同类型且 Δ 相同但 ID 不同，以及跨过批量上限的情况；按 Δ 降序、类型与 ID 字典序升序选取；ID 覆盖大小写与数字片段 |
| 候选批间变化 | 本批准备期间其他对象变化不重排已选批次；提交快照后 Δ 减少、业务变化使其他对象达标或提高 Δ，下一批按最新排序重新选取；重启后按持久化进度和相同规则选择，未入选对象进度不变 |
| 维护唤醒 | 维护启用期间，启动查询发现遗留候选；本进程对象变化达标后仅在提交成功时唤醒，回滚不唤醒，提交未知按原错误规则处理；多次通知合并、维护期间通知以及空查询到等待之间的通知均能得到后续检查 |
| 外部对象发现 | 独立 `submit` 创建计划及动作后，`run` 通过既有流程发现并检查对象；N＝1 时创建即可唤醒，默认阈值下单次创建未达标；子对象数量不增加父对象计数，幂等重送不增加计数 |
| 对象快照独立 | 同类型及不同类型的多个对象使用同一阈值，分别达标或未达标时仅安排达标对象；多个对象的计数差合计达标而各自未达标时均不安排；父对象保存自身字段，子实体独立保存；批量维护后各快照身份、边界及计数正确，不同快照边界仍可恢复到同一报告 H |
| 快照批量限制 | 数量上限的默认与合法覆盖、非法配置，候选为空、少于、等于及超过上限；未纳入对象仍保留资格且基准不变；本批对象数始终不超过配置上限 |
| 快照资源使用 | 增加候选总数时仍分批查询与处理，不保留全部候选的状态；本批结束后释放无后续用途的临时数据；组合不同对象大小及并行业务，测量实际峰值内存、读写量和业务延迟 |
| 快照批间调度 | 每批完成后让出执行机会并重新检查会话状态；进入收尾时不再安排下一批，候选不足时不等待凑满批次；批次大小变化不改变快照内容与其实际边界的对应关系 |
| 数据库操作优先顺序 | 覆盖线程已占用及空闲时两类等待操作的全部组合；快照先排队但尚未开始时业务可优先执行，快照开始后到达的业务等待其实际结束；候选查询、依据读取和快照保存均遵守相同优先级 |
| 快照读写之间的调度 | 读取后暂停准备，业务仍可使用数据库线程；保存重新排队时已有业务先执行；持续业务使快照推迟时维护进度不丢失，维护仍启用且业务队列清空后快照可获得执行机会；收尾仍按阶段取消或跟踪，操作结果未知不能因让出线程而被忽略 |
| 快照入队超时 | 候选查询、依据读取与保存分别覆盖入队超时，确认本次操作不会迟到执行、维护转为本会话停用且普通业务继续；已提交快照、基准和进度不因超时改变，业务新增变化仍正常累计；后续提交、对象发现、已发通知、空位出现与时间经过均不重新启动维护 |
| 快照停用后的恢复与错误边界 | 后续正常 `run` 重新启用并查询持久化候选；收尾可取消等待入队而不等满时限；截止前已入队的操作不受迟到超时通知影响，实际查询或保存失败、提交未知及必要业务超时仍按自身错误规则处理；仅快照入队超时不改变会话成功条件 |
| 快照生成与保存 | 读取 S 后提交新业务变化，保存内容仍对应 S；S 之后的变化不被误记为已覆盖；提交前后中断、回滚及提交未知分别按实际持久化状态处理 |
| 快照维护退出 | 覆盖未达阈值、已达阈值未开始、准备中、数据库操作排队中与已开始各阶段；单独维护积压不触发 `needs_run`，不等待将来达标，取消与开始竞争不能提前关闭连接；重启后仍能发现应维护对象 |

正向与逆向结果比较必须配合独立预期，避免两条路径共享同一错误。源码搜索不能代替对实际查询计划、读取量和行为的验证。

该方案影响事件格式、持久化原子边界、查询接口及报告恢复。形成可实施方案前，需要补齐事件与状态分类，再编写包含失败、恢复和性能门禁的实施计划。
