# camctl 实现规格

[返回 CLI 资料入口](README.md) · [全局行为规格](../architecture/README.md)

本文规定 camctl 第一版的技术选型、职责划分和接口契约。未完成的设计事项集中列于[尚需细化的事项](#尚需细化的事项)及[规格收口检查](specification-closure-review.md)，这些事项须在对应功能实施前形成具体契约。生产代码与全流程验收尚未完成。

客户端与 C 接入模块已有实现；真实 camctl 与两端的全流程验证仍待 camctl 实现后进行，现有接入模块的验证范围见[验证记录](../host-demo/verification.md)。设计与实现由负责该工作的执行者直接推进，不使用 subagent。

## 文档范围与使用方式

接口契约规定输入、输出、责任和失败语义。具体 Python 类型、函数签名、数据库结构和代码文件划分属于实施设计；尚未确定的方案须与规范要求明确区分。

持久化采用[当前投影与按范围逆向恢复](#当前投影与按范围逆向恢复)、按业务事件保存必要旧值和父对象派生状态变化、[事件正文与两类查询目录](historical-state-query.md#事件正文与两类查询目录)、缓存范围与已完成计划的内存淘汰，以及 [WAL 与分批短读事务](historical-state-query.md#wal-与分批短读事务)。[报告生成使用独立进程](#报告生成使用独立进程)的正常生命周期、主子进程分工、任务与结果的数据范围及 `spawn` 启动方式由本文规定。实施设计须明确第一版必需的事件与索引、内部接口、内存批次和失败处理，完成[尚需细化的事项](#尚需细化的事项)，形成完整设计后编写分步实施计划。

### 第一版实现范围

camctl 以较为乐观的 MVP（最小可行产品）为目标，优先打通计划接纳、设备执行、可靠保存及报告交付的业务闭环。实现须满足一致性、持久化、分批处理和失败语义；复杂的持续资源压力协调机制先作为后续设计提醒，根据联调和运行证据再决定是否实现，不作为第一版开工或验收的前提。

第一版按规定的正常运行假设和故障范围展开设计、实现及验收。日志副本交付明确假设[故障标记文件能够正常删除](../architecture/logging.md#跨-run-的独立状态文件)：业务状态报告可靠恢复后，camctl 正常删除故障标记文件并结束本次故障。

本地文件操作采用工作线程，正常完成和返回错误按业务契约处理；持续不返回的底层故障由部署侧处置，具体范围见[本地文件操作的完成与故障边界](#本地文件操作的完成与故障边界)。联调优先验证空间不足、实际读写和同步延迟、取消及中断恢复。

第一版报告按固定 H 使用分批短读事务，恢复与文件写出在事务外完成，WAL 维护依靠已配置的 SQLite 自动 PASSIVE 检查点。按积压监测触发的停读、快照维护让行、主动检查点及恢复调度统一保留为[后续设计提醒](historical-state-query.md#后续设计提醒wal-积压时的读取协调)，第一版不实现该协调机制。

全局行为和公共机器协议继续以 `docs/architecture`、根目录 `protocol` 为依据。本文记录实现选择及关键接口衔接，不另行建立一套业务状态、错误码或协议字段清单。存在影响业务结果的未定义分支时，先明确契约，再实现。

历史位置采用[全局事件序号与显式事务边界](historical-state-query.md#全局事件序号与显式事务边界)：每条事件有唯一递增的 `event_seq` 和所属事务，一份历史事务记录保存该组事件的结束位置，并与事件、目录及投影一起提交。事务以[首条事件序号作为标识](historical-state-query.md#以首条事件序号标识历史事务)，不另设编号计数器。事件分页可停在事务内部；历史状态、报告冻结和快照依据使用初始化起点 0 或完整事务边界。按[序号分配规则](historical-state-query.md#序号分配范围与初始化边界)，写事务内从最后已提交序号之后连续分配 64 位正整数，不另设永久计数器；确认回滚不留下空缺，上限不足时整个事务失败。请求及计划关联另按业务语义保存，事务标识不作为提交结果核验的唯一依据。

### 通过处理流程控制资源使用

第一版通过按需加载、分批处理和明确的容器容量控制资源需求。在满足行为契约与必要性能的前提下，减少重复读取、解析、编码和临时副本；已处理且不再需要的数据及时释放。可配置的批次与容量参数在会话启动时读取，本次会话内保持不变。

| 用途 | 处理约束 |
| --- | --- |
| 设备控制与工具进程 | 保留当前执行、停止及异常处理所需状态，任务结束后释放相应资源；按各自生命周期限制并发和输出缓冲 |
| 报告生成 | 实体和历史事件分批读取，逐步恢复和编码写出；保留当前处理所需的父对象、批次及续读位置 |
| 数据缓存 | 设置条目数量上限，满后淘汰可重新取得的内容；数据库页缓存配置适当容量 |
| 历史快照维护 | 按对象数量上限分批生成，减少状态副本和编码副本的重叠保留，批次结束后及时释放临时数据 |
| 队列与读写缓冲 | 数据库和日志队列按各自容量规则处理；读写缓冲限制字节容量，按批次或数据块推进。本地文件任务使用下文规定的默认线程池及业务并发限制，不增加统一提交上限 |

批次、缓存条目和缓冲容量限制具体处理的数据范围，实际内存占用还取决于对象大小、数据库缓存和转换过程。测试与联调使用不同规模和数据大小的负载，测量主进程、报告子进程及受管理工具进程的合计峰值内存、CPU、读写量与业务延迟，再调整处理方式及参数。历史总量增加时，检查局部操作是否仍只加载相关数据，避免无关历史带来重复扫描或常驻数据增长。

具体缓存条目数、其他队列的容量与满载处理、缓冲大小及其配置有效性规则仍需细化；数据库等待队列遵守规定的[容量配置](#数据库等待队列容量)和[入队等待时限](#数据库队列入队等待时限)。报告实体与事件读取批次已分别配置，默认值及生效规则见[读取批次配置](historical-state-query.md#实体与事件读取批次分别配置)。实际查询、编码、文件写入或进程运行失败时，继续按所属流程的失败与恢复契约处理；容量限制不改变数据完整性、事务边界或报告内容。

## 基础技术选型

技术选型优先复用标准库和成熟第三方开源库。先根据规定的行为契约核实候选能力，再结合维护状况、目标主机兼容性及总体维护成本选择；能降低实现和维护成本的第三方依赖可以引入。通用机制需要自行实现时，说明现有方案无法覆盖的具体契约，自有代码集中于业务规则和必要适配。技术选型如下表所示，其他尚未确定的工具沿用这一原则评估。

| 用途 | 选择 | 约束 |
| --- | --- | --- |
| 异步协调 | 标准库 `asyncio` | 主事件循环组织等待、调度及执行流程 |
| 数据库访问 | 标准库 `sqlite3`，配合专用线程 | 对调度协程提供异步接口；完整事务在所属数据库线程内执行 |
| 普通运行日志 | 标准库 `logging`、`QueueHandler`、`QueueListener`，配合 `janus` 有界队列和 `concurrent-log-handler` 的 `ConcurrentRotatingFileHandler` | 协程使用可等待的日志入口，同步来源使用同步入口；各进程独立持有队列与专用日志线程，通过文件锁协调共享文件 |
| JSON 解析 | 标准库 `json` | 按输入契约拒绝重复成员名和非 JSON 数值常量，保留原始结构化输入 |
| 精确数字 | 标准库 `int`、`decimal.Decimal` | 整数字面量使用 `int`，带小数点或指数的字面量直接从原文构造 `Decimal`；校验、保存与报告恢复保持数值精确 |
| 拍摄参数校验 | `jsonschema` | 显式采用 Draft 2020-12，使用本地提供的规则及引用定义 |
| 内部数据类型 | 标准库 `dataclasses`、`Enum` | 表达内部对象、状态和操作结果；数据类本身不承担自动校验 |
| 测试执行与组织 | `pytest` | 参数化用例、断言及测试资源管理 |
| 异步测试 | `pytest-asyncio` | 管理测试事件循环，执行异步测试 |
| 测试替身 | `pytest-mock`，配合手写 fake | 使用 `mocker` 管理替换与清理，替身受真实接口约束 |

Python 第三方包的确切版本尚未锁定。生产依赖与测试依赖分别管理；测试工具只用于开发和验收环境。源码、依赖和发布物的目录边界遵守[仓库结构](../architecture/repository-layout.md)，组件入口约定使用 `pyproject.toml`、`uv.lock`、`src/camctl` 及分类测试。

### 输入校验与内部类型

按[输入校验顺序](../architecture/plan-input.md#校验顺序与错误优先级)分阶段处理，不能先要求整个输入转换成一份完全合法的执行模型：

- 完整读取并无歧义解析后，才取得请求身份及 ACK；解析包含全部字段名和字符串值的 Unicode 完整性检查。未配对代理码点按整份解析失败处理，诊断使用可编码的转义文本；不从失败的读取或解析结果提取身份。
- 已受理的 `request_id` 重送时复用原计划，跳过本次正文校验，独立处理本次 ACK。
- 新计划的公共结构错误与单个动作自身错误分别处理，保持整份拒绝的优先级。
- 原始结构化输入保持原样；合法动作的生效参数按驱动定义补齐后单独保存。
- Schema 无效、必要引用缺失或规则不可解释属于规则处理错误，不能当成用户参数错误。

驱动直接维护拍摄参数 Schema，同一份规则用于 camctl 校验及能力说明导出，客户端使用导出的规则。参数默认值与说明保持同源；公共字段、引用和业务资格由对应业务规则判断。完整契约见[拍摄参数的 JSON Schema](../architecture/camera-capabilities.md#拍摄参数的-json-schema)。

### 精确数字与统一输出方向

数值在输入校验、数据库保存、历史恢复和报告输出之间保持精确。标准库 `json` 将整数字面量解析为 `int`，将带小数点或指数的数字原文直接交给 `Decimal`，不先转为 `float`。原始结构化输入保留精确数值，不要求保留数字的尾随零或指数写法；报告按[精确数值与统一写法](../architecture/report-format.md#精确数值与统一写法)输出 JSON 数字。

| 输入分类 | 整数字段的类型判断 |
| --- | --- |
| 整数字面量，例如 `1` | 按整数判断，再检查字段范围 |
| 带小数点或指数且数学值为整数，例如 `1.0`、`1e0` | 按整数判断，再检查字段范围 |
| 数学值不是整数，例如 `1.0000000000000001` | 不满足整数字段要求，不先舍入或截断 |
| 字符串、布尔值、null 或其他 JSON 类型 | 不满足整数字段要求，不隐式转换 |

原始输入的保存不因字段校验失败而舍入或修改该值。整数身份、范围及安全整数边界按字段契约判断，不能以 Python 对象是否属于 `int` 作为完整校验规则。非 JSON 数值常量继续按输入解析规则拒绝。

相机 Schema 中的数值约束采用相同的精确表示；为 `jsonschema` 适配精确数字类型和相关数值判断。适配须覆盖整数识别、范围、倍数、数值相等及其参与的组合规则，不能只替换类型判断而遗漏其他数值操作。数据库存储、派生投影、快照和跨模块传递均须保持同一数值；具体存储表示与适配接口仍需细化。

`Decimal` 的文本构造可以保留输入值，算术操作仍受计算精度和舍入规则影响。数字格式遵守[精确数值与统一写法](../architecture/report-format.md#精确数值与统一写法)，格式选择和去除多余尾随零也必须保持精确。计算精度、设备接口所需转换及编码器适配方式仍需明确；不因选用了 `Decimal` 就假定所有后续运算自动精确。相关能力见 [Python JSON 解析](https://docs.python.org/3.11/library/json.html)和 [Decimal](https://docs.python.org/3.11/library/decimal.html)。

验收覆盖上述类型分区、字段范围边界、带小数或指数的等值数字、精确 Schema 数值约束，以及输入保存后经当前投影、历史快照和正反向恢复再输出的数值一致性。报告数字不得被编码为字符串，也不得通过浮点转换改变原始数值。

## 执行位置与异步接口

“异步”表示调用方如何等待，“线程或进程”表示操作实际在哪里执行。设计和接口文档应直接写明执行位置，避免只用“后台处理”概括。

| 工作 | 执行方式 |
| --- | --- |
| 调度、执行流程及取消、重试的组织 | `asyncio` 主事件循环中的协程 |
| 普通业务规则判断 | 同步函数，输入明确状态与证据，不直接访问外部资源 |
| 定时、子进程控制结果及结束的等待 | 协程异步等待，让事件循环处理其他工作；相机文件内容由下述分段传输任务读取 |
| SQLite 操作 | 专用数据库线程，调用协程等待其结果 |
| 相机文件内容传输 | 主协程按进度段通过 `asyncio.to_thread()` 提交默认线程池；线程内以小块连续读取、写入并完成段尾同步 |
| 其他普通文件读写、截断和同步 | 通过 `asyncio.to_thread()` 使用同一默认线程池，调用协程等待结果 |
| 外部设备及媒体工具 | 异步启动和管理 `adb`、`ffmpeg`、`ffprobe` 子进程 |
| 普通日志追加与轮换 | 各进程的专用 `QueueListener` 日志线程按入队顺序消费 `janus` 有界队列并调用 `ConcurrentRotatingFileHandler`；按水位限制低级别日志接纳并对中间区间的 `INFO` 独立随机采样 |
| 报告状态读取、按范围逆向恢复和 JSON 编码 | 独立报告生成进程；主进程通过协程异步等待结果 |
| 报告进程通信 | 主进程中的专用通信线程执行可能阻塞的管道收发；调度协程通过异步接口等待结果，并监测子进程退出 |

数据库专用线程用于隔离同步查询、数据库锁等待和提交落盘等待，避免直接阻塞事件循环。它不会消除 SQLite 的写事务竞争或共享磁盘竞争。相关动作仍须等待自己的事务提交成功，才能产生设备副作用。

本地文件执行使用[默认线程池](#本地文件执行使用默认线程池)。数据库、日志和报告通信使用各自规定的专用线程，报告内容生成在独立进程中执行。本地文件任务按业务资格直接提交，由默认线程池排队执行；其他尚未确定的队列容量及退出清理接口继续在相应专题细化。

统一约束：调用协程取消等待，不证明线程任务、子进程或远端操作已结束。操作的实际结果与占用仍须跟踪，满足原恢复与安全重试条件后才能继续。

## 模块组织与依赖方向

按业务职责划分模块，将业务判断与外部操作分开。跨模块工作由对应业务流程组织；流程本身也按用例拆分，不集中到一个总控制器中。

| 部分 | 责任 |
| --- | --- |
| 命令入口 | 解析命令、加载配置、启动对应流程、输出最终结果 |
| 业务流程 | 组织受理、调度、设备恢复、产物处理和报告维护的步骤 |
| 业务规则 | 根据输入、状态及证据，判断允许的操作和状态变化 |
| 外部接口实现 | SQLite、设备通信、本地文件、时钟和日志的实际操作 |

建议以以下业务模块细化接口；职责及协作方向为规范要求，具体包名和文件划分仍可按数据流调整：

| 模块 | 集中负责的规则 |
| --- | --- |
| 计划受理 | 输入校验、请求幂等、动作初始状态，以及 ACK 处理的组织 |
| 会话管理 | 会话锁、接纳资格、`needs_run`、启动与收尾 |
| 调度 | 时间窗口、工作顺序、唤醒、执行资格和资源占用 |
| 采集执行与恢复 | 拍摄、有限尝试、停止、取消及设备对账 |
| 产物与交付 | 正式产物、取回、清理、可恢复拷贝和文件交接 |
| 状态报告 | 冻结范围、内容生成、发布、累计确认与同步责任 |
| 持久化 | 历史与投影的原子保存、状态查询及历史回放 |
| 设备驱动 | 静态能力、设备命令和响应证据解释 |

依赖组织如下：

```text
命令入口
    ↓
按业务用例拆分的流程
    ├── 调用业务规则，取得判断与待保存事实
    ├── 通过持久化接口提交完整变更
    └── 通过设备、文件、时钟等接口执行外部操作
```

业务规则不直接访问数据库、设备和文件系统。具体协作者通过创建对象时传入，测试可以传入替身；业务模块不自行创建数据库连接或寻找全局设备对象。模块不直接操纵其他模块的内部状态，也不以私有数据库表或内部调用顺序作为协作接口。

### 模块边界与事务边界

模块可以分别实现，但一项业务要求的原子提交必须保持完整：

| 场景 | 协作方式 | 不变量 |
| --- | --- | --- |
| 采集完成并登记产物 | 采集模块提供完成证据与文件事实，产物模块确定登记内容，采集完成流程统一提交 | 动作终态与正式产物同事务保存 |
| 取消正在录像或取回的动作 | 取消流程固定并保存目标，交给对应执行模块收场，再汇总结果 | 取消标记不等于处理完成；复用已有进度与剩余预算 |
| 同一输入携带计划和 ACK | 受理流程分别调用计划及报告确认规则，再统一提交 | 两者独立判断，本次结果一起保存 |

历史回放共用已记录事实的投影更新规则，不重新执行业务决策，不调用设备或文件接口，不重新分配业务身份。具体历史粒度和事务语义继续遵守[持久化规则](../architecture/system-foundations.md)。

## 接口设计与可测试性标准

接口先确定行为契约，再细化函数签名。每个接口需说明：

1. 输入、输出、数据所有权与生命周期。
2. 是否异步，以及实际执行的线程或进程。
3. 成功返回表示已接收、已提交数据库，还是已确认外部操作。
4. 明确失败、结果未知和取消的表达方式。
5. 重试资格，以及重复调用可能产生的副作用。
6. 谁保存结果、谁在重启后恢复、什么证据允许结束责任。

可测试性的验收标准：

- 给定状态、时间和证据，可以独立验证规则及状态转换。
- 数据库失败、设备结果未知和文件操作中断，可以通过稳定的协作者接口主动构造。
- 替身受真实接口约束；适用的协作者契约用于验证替身和真实实现，另以集成测试验证双方配合。
- 内部实现变化但契约不变时，不应引起大量测试修改。
- 只有操作顺序本身属于协议或副作用契约时，才断言交互顺序，例如意图保存失败后不能发送录像指令。

## 数据库整体格式检查与显式升级

状态库元信息保存整体格式版本 `format_version`。它定义数据库采用的持久化契约，包括表结构、允许存在的事件类型及版本、当前投影和历史快照等表示。程序发布版本、数据库整体格式版本、各事件类型的 `event_version` 分别管理，不要求编号相同。修改日志文案等不改变持久化契约的程序更新不增加数据库格式版本。

程序具备读取某种新事件的能力，不会自动改变已有数据库的格式。数据库正式允许写入新事件格式时，必须先完成相应整体格式升级；仍标记为旧格式的库只能按旧格式契约读写。程序支持的数据库格式及每个格式允许的事件、持久化结构应由单一权威定义管理，不能只凭版本数字大小认定兼容。

所有使用状态库的入口先检查数据库身份、整体格式及必要结构。`run`、`submit` 在业务受理、使用投影作决策及产生设备或报告发布副作用之前完成检查；报告子进程在查询业务状态和生成报告之前独立检查。`init` 验证已有库时也检查格式，`describe` 的既有无状态库依赖保持不变。

| 数据库与程序能力 | 处理规则 |
| --- | --- |
| 数据库标识、格式与必要结构有效，程序明确支持该格式 | 按该格式契约使用；具体事件仍按类型和版本校验 |
| 程序支持新旧格式，打开的是旧格式库 | 继续遵守旧格式写入范围；需要新格式的功能要求先显式升级 |
| 数据库格式有效，但程序不支持 | 在使用业务状态之前明确报格式不受支持，不尝试部分执行或自动降级 |
| 格式标识缺失、非法，或内容与声明格式矛盾 | 按状态库校验错误处理，不猜测为版本 1 或其他可用版本 |
| 状态库缺失或读取结果无法确认 | 继续遵守既有不存在与错误分类，不自动建立空库 |

通过元信息判定整体格式兼容性，不为识别版本而扫描全部历史；这不代替必要结构检查及实际读取时的数据校验。版本或内容错误遵守各入口既有错误输出契约，保留不依赖状态库可用的诊断。

格式升级由部署人员显式执行，日常 `run`、`submit`、报告生成及重复 `init` 不自动升级。升级前暂停日常调用，并确认相关 `run`、`submit`、报告子进程及状态库维护操作已经结束；升级期间阻止新的日常操作进入。不能在旧程序仍使用业务状态时，由另一入口启用新格式。实际维护入口、锁协调、升级原子性及中断恢复在确有后续格式时另行定义。

升级后，旧程序只要不支持目标格式，即使库中尚未出现新版本事件，也拒绝使用。新程序保留旧历史读取能力；数据库升级后不承诺旧程序接管，不通过修改版本数字或改写历史实现软件降级。

采用[当前投影与历史快照的保存格式](historical-state-query.md#当前投影与历史快照的保存格式)：当前投影跟随数据库当前格式，结构变化时在维护阶段转换或重建并验证；历史快照保留原内容及生成时的 `format_version`，读取时按自身格式解释和适配。每份快照的历史边界 S 与保存格式分别记录，不增加独立快照版本编号。程序支持某个数据库格式时，须支持该格式允许保留的旧快照。

第一版显式初始化创建格式 1，仅实现格式 1 的读写、兼容性检查及不支持格式的诊断，不实现假想后续格式的迁移步骤。验收覆盖各状态库入口的支持、未知、缺失与非法格式分支，保证拒绝时不受理输入、不执行设备动作、不发布报告、不自动建库或升级；报告子进程的格式错误继续按状态库错误交付主进程。后续新增格式时再验收升级隔离、中断恢复及新旧程序读写范围。

## 持久化接口契约

| 接口类别 | 输入 | 输出 |
| --- | --- | --- |
| 状态查询 | 查询条件、当前状态或指定历史边界 | 明确的数据对象；不存在与读取失败分别表达 |
| 原子业务操作 | 本次操作输入，例如计划受理数据、设备观察结果 | 已提交的业务结果，或明确的失败状态 |
| 历史回放与投影重建 | 完整已提交的历史边界 | 重建结果，或明确的历史解释错误 |

原子业务操作包含依赖数据库现状的判断。例如，受理请求须在取得写事务资格后查询 `request_id`，再决定复用已有计划或注册新计划，完成 ACK 处理和历史、投影保存后提交。不能先在事务外认定新请求，再把该判断直接作为数据库写入前提。

具体业务判断由所属业务模块提供，持久化执行层管理连接与事务。事务内仅进行必要计算、数据库操作，以及规格规定的非阻塞锁操作；不等待设备、文件生成或其他长任务。数据库连接在所属线程内创建、使用和关闭。报告长查询如何与短事务分开安排仍须细化。

同一 `run` 内的数据库操作采用[业务优先、快照维护等待空闲机会](historical-state-query.md#业务操作优先使用数据库线程)：每次选择下一项操作时，先处理等待中的业务查询与事务，再处理快照候选查询、依据读取或保存。已开始的操作跟踪至实际结束，不因后来到达的业务被打断；快照读取与保存分别排队，事务外准备内容不占用数据库线程。持续业务可以推迟快照维护，进度按原规则保留。此顺序只适用于本进程，独立 `submit` 及报告进程的数据库锁竞争另按所属规则处理。

操作结果按实际执行状态分类：

| 实际状态 | 返回语义及后续行为 |
| --- | --- |
| 尚未开始，且确认不会执行 | 未执行，没有本次数据库变更 |
| 事务提交成功 | 返回已提交结果；业务拒绝也可以可靠提交 |
| 操作失败，已确认回滚 | 明确失败，本次变更未保存 |
| 无法确认提交或回滚结果 | 结果未确认；停止依赖该结果的后续操作，按恢复规则核实 |

取消调用协程不改变上述事实分类。已经开始的数据库操作仍由持久化执行层跟踪到实际结果；连接何时允许复用、排队期间取消及退出清理的具体机制还需形成完整状态表。

正常写入与历史回放共用“根据历史事实更新投影”的规则。以同一批历史验证正常写入结果和回放重建结果一致；回放不发送命令、发布或删除文件。

### 数据库等待队列容量

数据库线程的等待队列按完整操作的条目数量限制容量。一项可以是一次状态查询或一个完整事务，不以 SQL 条数、动作数量或本批快照对象数量计数；同一事务的多条语句仍属于同一操作。业务操作与快照操作共用该等待容量，选择下一项时仍遵守业务优先规则。

本节定义主机本地配置的默认值及合法范围：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `database.queue_capacity` | `64` | 正整数；本进程数据库线程等待队列允许的最大操作条目数 |

按[本地配置的加载与更新](../architecture/configuration.md#本地配置的加载与更新)取得生效值。省略时采用默认值；显式提供 0、负数、浮点数、布尔值或字符串等非法值时，按配置错误处理。配置在本次 CLI 启动时读取，进程运行期间保持不变，部署调整在后续调用生效。容量属于进程内运行配置，不固化到动作，不作为跨进程共享额度。

| 操作状态或转换 | 对等待队列容量的影响 |
| --- | --- |
| 尚未入队，正在等待空位 | 不占用队列条目，遵守入队等待时限 |
| 成功入队、等待执行 | 占用一个条目；所有优先级的等待条目合计不超过生效容量 |
| 从等待队列取出并交由数据库线程执行 | 释放一个等待条目，执行中的操作另由数据库线程持有并跟踪实际结果 |
| 已入队但尚未开始，确认取消且不会执行 | 释放所占条目，不将其转交执行 |
| 入队前超时或确认取消 | 未取得条目，无需释放；不得迟到入队或执行 |

队列满载时按入队等待规则处理，不覆盖或丢弃已有条目。取出操作腾出空位不代表该操作已完成或已提交，容量释放与结果确认分别处理；取消与取出发生竞争时按实际阶段处理，不能重复释放条目或让已确认取消的操作执行。

容量不限制队列外等待者总数，也不保证固定内存占用或数据库处理速度。默认值用于容纳短时突发，属于尚待负载测量的初始工程值。调整容量不改变事务边界、优先顺序、入队时限及超时分类，不改变计划、历史或报告内容。

验收覆盖配置省略、合法覆盖、非法类型和数值，以及会话内固定、后续调用使用新值；容量取 1 及较大值，覆盖空队列、未满、恰好满载、并发入队、执行取出及排队取消。业务与快照合计遵守同一上限，多语句事务仍只占一项；执行中的操作和等待入队者不计入等待条目，入队前超时、取消与取出竞争均不导致条目计数错误。负载测试分别测量已入队数量、等待入队者数量、排队延迟和实际资源消耗。

### 数据库队列入队等待时限

数据库任务队列达到容量上限时，调用协程异步等待空位，入队等待上限为 9 秒，使用单调钟计量。该时限只约束本次提交取得队列位置的等待，不包含入队后的排队、数据库锁等待、执行及提交时间。入队不表示操作已执行或保存成功，调用方仍须取得实际操作结果。

| 本次提交状态 | 处理 |
| --- | --- |
| 有可用位置，立即完成入队 | 等待操作的实际结果 |
| 尚未入队，等待未满 9 秒 | 异步等待空位，事件循环可继续处理其他工作 |
| 在截止时间前完成入队 | 结束本次入队计时，按已排队操作跟踪；迟到的入队超时通知不改变结果 |
| 到达截止时间仍未入队 | 返回明确的入队超时错误，并保证该次提交以后也不会执行 |

空位取得与超时判定必须形成唯一结果：只有截止时间前确认入队的操作才进入执行队列，不能先向调用方报告超时，再让同一操作进入队列。超时只证明本次数据库操作未执行，不撤销已经发生的设备效果或先前已提交的事实；不得把待保存结果解释为已经可靠保存。

队列满载本身不丢弃操作或直接判定业务失败；达到 9 秒上限后明确报错。正常 `run` 中，必要业务数据库操作入队超时归为 `state_db_error`，按[无法继续执行时的退出](../architecture/session-errors.md#无法继续执行时的退出)进入会话错误收场。必要操作包括执行资格所需的状态查询、执行依据与设备结果保存、文件可靠进度保存以及报告责任登记和推进。不能只把对应动作改成失败并继续普通执行，也不能重新提交同一操作来无限延长本次等待。

`run` 停止启动新的普通动作并退出普通接纳阶段，已有活动按既定有限收场规则处理；满足可靠归属和安全停止条件的录像执行既有应急停止。错误诊断交付不依赖该次数据库操作成功，超时本身不证明数据库损坏。此前已提交状态保持不变，尚未保存的结果不得宣称已经可靠保存；后续正常 `run` 根据已提交历史与实际设备或文件证据恢复，沿用原身份及已消耗预算。

快照维护的入队超时采用[本会话停用规则](historical-state-query.md#快照入队超时后的会话内停用)：向维护调用方报错并记录诊断，停止本次 `run` 的快照维护，普通业务继续；后续提交或空位出现不重新启用，下一次正常 `run` 从持久化进度接续。此超时自身不形成会话错误。进入收尾时可确认取消尚未入队的快照操作，无须等满时限。已入队或已开始操作的取消与实际结果继续遵守持久化接口契约，实际数据库错误及提交未知不适用上述停用规则。验收覆盖立即入队、等待后入队、持续满载、截止边界、空位与超时竞争，以及超时后禁止迟到执行；分别对必要查询、设备结果、文件进度及报告登记注入入队超时，验证会话错误、停止新增普通工作、保留已提交事实、按资格收场及后续恢复。

### 入队后的排队与取消

数据库操作成功入队后，第一版不另设等待开始执行的排队超时。操作按既定优先顺序等待数据库线程派发；入队等待的计时已经结束，不能把入队后的等待时间计入此前的 9 秒上限。容量限制和入队时限均不保证整个数据库调用的完成时间。

所属流程允许取消，或会话收尾需要撤回该项操作时，按实际状态处理：

| 实际状态 | 处理 |
| --- | --- |
| 已入队、尚未开始，未要求取消 | 保留操作并等待派发，不因排队时间较长报超时或重新提交副本 |
| 已入队、尚未开始，已确认取消且不会执行 | 移出等待队列并释放条目，返回未执行结果 |
| 已提出取消，但尚未确认能否阻止执行 | 继续协调取消与派发，不能先宣称未执行或关闭连接 |
| 操作已经开始，包括取消与开始执行发生竞争的情况 | 跟踪至实际结果，按完成、回滚或结果未知处理；调用协程停止等待不代表实际操作结束 |

会话收尾仍按各类责任判断哪些操作可以取消，不以取消必要保存来宣称业务完成。快照维护已入队但尚未开始的操作，继续遵守规定的维护退出规则。已开始操作的数据库锁等待遵守[SQLite 内置忙等待规则](historical-state-query.md#sqlite-内置忙等待与失败处理)，错误处理及连接关闭继续跟踪实际结果，不将执行阶段的等待参数解释为排队时限。

验收使用可控时钟及同步点，让操作在成功入队后等待超过入队时限，验证不触发入队或排队超时；随后释放执行机会，确认操作只执行一次。覆盖排队取消、取消与派发竞争、迟到的入队超时通知，以及已开始操作在等待者取消后仍被跟踪，确认容量释放、未执行结果和实际提交结果分别正确。

## 当前投影与按范围逆向恢复

采用“当前投影＋包含必要旧值的业务事件＋按范围逆向恢复”。每次保存业务事件时，在同一事务中保存必要恢复依据并更新受影响的当前投影；调度与普通业务查询直接使用可靠的已提交投影。不可变历史继续作为权威来源，正向回放用于投影重建与一致性验证。

报告冻结边界记为 H，整份报告保持不变。报告进程在短读事务中一起取得本批当前投影、对应的完整已提交边界 C 及当前累计变化计数，且 `C ≥ H`，取回数据后结束查询和事务。再通过范围索引，以多个短读事务分批读取这些实体及必要依赖在固定 `(H, C]` 内的相关事件，在事务外按事务与事务内事件的逆序恢复到 H。相关状态没有变化时，直接使用该投影。不同对象可以使用不同的 C，各自恢复范围始终与所取投影绑定，最终均表达同一 H 的状态。

业务事件必须保存报告相关状态逆向恢复所需的旧值或等价事实，覆盖字段存在性、集合、关系及实体创建边界。事件仍表达独立业务事实，不能仅以通用字段补丁代替业务含义。读取失败、投影失效、冻结依据无法确认或历史缺少必要恢复信息时，按状态库错误及投影恢复规则处理。完整状态分类见[历史状态查询与报告重建](historical-state-query.md#状态分类)。

每种事件按业务含义明确被改变的字段或集合成员，保存必要的前后值。父对象派生状态发生变化时，也直接保存其前后值，与触发变化的子对象事实同事务提交，使报告恢复父对象自身状态时无需读取全部子对象。旧值取自事务内该事件发生前的实际状态；同事务连续变化保留内部顺序。原始计划和固定生效参数由创建事实永久保存，后续事件通过身份关联。详细分类见[事件恢复依据](historical-state-query.md#事件恢复依据)。

逆向恢复只修改本次报告的数据副本，不将数据库当前投影改回旧状态，不执行外部副作用。报告仍按业务变化区间选择实体，所有入选实体及补齐的父对象都使用同一冻结边界；报告首次生成与后续重建采用相同的字节生成规则。

事件正文保存一次，维护业务变化与实体、实体与历史事件两类可重建的查询目录，分别支持报告对象选择和历史状态恢复。目录与事件及相关投影同事务提交；仅引用对象不视为改变它，批量查到同一事件时复用正文，分别保留各对象需要恢复的影响，避免遗漏或重复应用。采用[统一事件表与按类型定义的 JSON 正文](historical-state-query.md#统一事件表与按类型定义的-json-正文)，公共信息使用固定列，正文由持久化边界与有明确类型的事件对象相互转换。采用[事件格式版本与读取兼容性](historical-state-query.md#事件格式版本与读取兼容性)：固定列 `event_version` 按事件类型独立演进，新程序保留旧版读取能力，适配仅改变内存表示，历史保持原样；不支持的格式明确报错。第一版仅实现事件版本 1 及识别、分派接口，整体兼容性遵守[数据库格式检查](#数据库整体格式检查与显式升级)，具体字段、列布局、索引和检查接口仍需细化。

采用 SQLite WAL 模式，所有状态库写连接显式设置并核验 `synchronous=FULL`，第一版不提供降低同步等级的配置；提交失败及结果未知继续按各自契约处理，详见[FULL 同步](historical-state-query.md#所有状态库写连接使用-full-同步)。采用[自动 PASSIVE 检查点与可配置阈值](historical-state-query.md#自动-passive-检查点与可配置阈值)，各写连接显式设置并核验本次生效的 `database.wal_autocheckpoint_pages`，默认值及合法范围由该专题定义；不新增专用检查点线程；部分推进与数据库故障分别处理，阈值不代表 WAL 大小上限。

采用[SQLite 内置忙等待与失败处理](historical-state-query.md#sqlite-内置忙等待与失败处理)。各状态库连接显式设置并核验本次会话的 `database.busy_timeout_ms`，默认值和合法范围由该专题定义；报告进程取得主进程传入的生效值，重新创建时保持相同配置。最终锁忙错误不在应用层循环重发，按实际事务状态清理并交付状态库错误；该参数与入队等待分别计量，不构成事务总时限。

报告进程在自己的只读连接上使用分批短读事务。对象选择依据固定业务区间与 H 处历史关联，投影及计数绑定各自的 C；已选快照绑定 S，历史分页固定为 `(H, C]` 或 `(S, H]`。已提交历史及既有查询关联不改写或删除，快照内容不变，因此后续短读事务仍能取得这些固定范围的数据。每批读取完成后释放查询和事务，再恢复状态、编码和写文件。批次之间暂时让出资源时可保留本次任务的有界处理进度；任务失败或进程结束后仍按报告规则从头生成。缓存须明确对应不可变事实或实体在 C／H 的状态。完整分类与例子见[WAL 与分批短读事务](historical-state-query.md#wal-与分批短读事务)。

部署核验 Python 实际链接的 SQLite 运行库，并选用包含已知 WAL 并发缺陷修复的版本；具体部署版本仍待锁定。报告计算与文件生成在读写事务外进行。验收须覆盖正向与逆向结果一致、跨事务并发变化、固定范围分页、恢复旧状态不改变当前投影、报告字节一致性，以及恢复和写文件期间实际释放数据库读取。持续计划提交、慢存储和大规模报告组合下，联合测量 WAL 积压、计划接纳延迟、设备调度延迟与完整报告的业务滞后，不将某款设备或固定内存额度作为运行保障前提；这些测量用于了解第一版的适用负载，不要求实现后置的积压协调机制。

范围查询的读取量应取决于所需实体和相关历史区间，不能先加载全库历史再过滤。很早的边界若对应大量后续变化，仍可能需要较多计算；长期存储增长和各类报告负载的验收预算尚待确定。

同时采用[按对象累计变化次数触发的历史快照](historical-state-query.md#按对象累计变化次数触发历史快照)。各对象独立保存自身状态、身份、完整历史边界、对应累计计数及格式版本，父对象的子实体分别保存快照。维护范围内的对象共用正整数配置 `history.snapshot_change_threshold`，默认值与校验规则由该专题定义，各自独立计数和判断。当前投影持续更新；对象当前累计计数减去其最近已提交快照包含的计数，达到统一阈值时安排维护。没有快照时基准为 0，创建计为第一次变化，首次也按阈值触发；计数跨会话保留，正常 `run` 重新发现已达标对象，无须等待新变化。配置每次会话启动时读取，会话内保持不变，后续会话按当次阈值重新判断，调整不重置计数或改变已有快照、业务事实及报告内容。可从不晚于目标边界的可靠快照正向恢复，与当前投影的逆向路径共存。

上述快照及其维护进度、候选查询和唤醒统一遵守[历史快照对象范围](historical-state-query.md#历史快照的对象范围)。第一版覆盖计划、动作、正式产物与普通交付，`report_status` 属于动作。输入诊断复用原创建事实，报告内部管理记录、累计 ACK 和同步责任使用各自历史与当前投影；这些记录不进入快照维护，阈值为 1 时也保持相同范围。既有报告的冻结依据和重建字节保持不变。

采用[持久化派生维护进度与候选索引查询](historical-state-query.md#持久化快照维护进度与候选查询)：数据库为维护范围内的对象保存尚未被最近快照包含的变化次数，`run` 与 `submit` 等入口随事件、关联和当前投影在同一事务内更新；保存快照时，在同一写事务内依据当前累计计数及该快照实际包含的次数推进维护进度，保留准备期间新增的变化。正常 `run` 按本次阈值通过索引分批发现候选，按未包含变化次数降序、对象类型标识和完整 ID 字典序升序选取。每批结束后依据最新已提交进度重新选取下一批，本批准备期间不因后来变化重排已选对象；该顺序不保证候选在固定时间内获得快照。重启和配置变化不要求新事件或全量历史回放。维护进度可从历史及已提交快照重建，异常按状态库错误处理；实际表和索引仍需细化。

维护采用[提交与对象发现驱动](historical-state-query.md#提交与对象发现驱动快照维护)：进入正常 `run` 时查询一次遗留候选；本进程对象变化提交成功后，维护范围内的受影响对象达标即发布维护唤醒；通过既有流程发现外部提交的新对象时检查其维护资格，覆盖阈值为 1 的情况。本次会话维护启用期间，维护协程逐批处理，查空后等待通知；因入队超时停用后不再响应维护唤醒。通知可以合并，但须覆盖维护期间及空查询到进入等待之间到达的通知；数据库始终是候选的依据。

查询[按对象选择恢复路径](historical-state-query.md#按对象选择恢复路径)：无后续变化直接用当前投影，恰好命中目标边界的可靠快照时直接使用快照；其余情况在两条回放路径都有依据时比较相关事件数，正向更少时选正向，逆向更少或相同时选逆向；没有不晚于目标边界的快照时使用逆向路径。采用[实体历史关联与累计变化计数](historical-state-query.md#实体历史关联与累计变化计数)：每条关联保存实体类型、ID、事件序号及累计计数，一条事件改变一个实体需要恢复的状态计一次，同一实体与事件只建立一条关联。计数由历史派生，并随事件和投影保存，快照保留对应计数；通过索引和差值取得范围内变化数，快照触发也采用同一计数单位。不同对象可采用不同路径，但都恢复到同一冻结边界并产生相同报告字节。具体索引仍需细化。

快照在业务可靠提交后，由 `run` 的维护协程分批生成，数据库读写仍使用已有数据库线程。每批对象数量受 `history.snapshot_batch_size` 限制，默认值与规则见[快照维护批量限制](historical-state-query.md#快照维护批量限制)；每批完成后释放临时数据，让出执行机会并重新检查会话状态。每批从一致视图取得对象状态和历史边界 S，结束读事务后准备内容，再通过短写事务整体保存快照与 S。生成期间出现的新变化不改变该快照的含义；维护进度只确认到 S，不遗漏之后的变化。报告不等待新快照生成，数据库错误仍按既有规则处理。完整状态分类见[快照生成流程](historical-state-query.md#业务提交后分批生成快照)。

快照维护不单独阻止 `run` 结束，也不单独产生 `needs_run: true`。正常收尾停止新增维护：未开始的候选留给后续会话，尚在准备的临时内容可以丢弃，排队数据库操作须确认取消且不会执行，已开始的操作跟踪至实际结果后再关闭连接。下一次正常 `run` 通过维护进度索引重新发现候选。详见[快照维护与会话退出](historical-state-query.md#快照维护与会话退出)；具体取消机制及等待预算仍需细化。

## 缓存范围与数据库访问优化方向

采用 SQLite 页缓存、有容量限制的不可变内容缓存、活动任务缓存和单次报告内部数据复用；原子业务操作在提交成功后直接返回已保存结果，减少紧接着的重复查询。缓存复用已提交数据，写入继续保持既定可靠保存边界。容量及跨进程刷新机制仍需细化；拷贝进度按下文规定的分段规则保存，跨报告的历史计算结果缓存仍待评估。衡量时区分 SQL 调用次数、读取和解码的数据量、存储设备实际读写量以及可靠提交次数。

### 缓存范围与候选扩展

| 对象 | 采用方式或待评估内容 | 主要收益与边界 |
| --- | --- | --- |
| SQLite 数据页 | 为各连接配置适当的页缓存容量 | 减少重复读取存储设备；仍有 SQL 执行和结果转换成本 |
| 原始计划、固化参数、不可变事件及报告冻结依据 | 按稳定身份缓存已经提交并验证的内容，随数据库使用范围结束而清空 | 减少反复查询和解码；身份必须限定到同一状态数据库，未提交数据不能进入已提交缓存 |
| 当前活动任务的状态 | 沿用既有内存调度缓存，提交成功后以原子操作返回的结果更新受影响对象 | 省去提交后立即重复读取；独立 `submit` 的提交仍须按持久化序列发现，跨对象状态不得混合不一致版本 |
| 一次报告读取的对象与关联 | 在本次一致读取范围内复用，例如多个交付共用同一父动作时只加载一次 | 减少重复查询；分批处理时释放不再需要的内容 |
| 指定历史边界的计算结果 | 可评估按数据库身份、对象身份、历史边界及所需解释规则缓存，限定容量 | 旧状态不会因后续提交改变；命中率未知，不将其收益计入第一版性能承诺 |

SQLite 自带页缓存，容量设置是按连接所打开的数据库配置，默认实现按需分配；它不是 Python 业务对象缓存，见[SQLite 页缓存说明](https://www.sqlite.org/pragma.html#pragma_cache_size)。选择页缓存容量时，测试与联调须覆盖主进程与报告进程同时打开连接的情况，评估整体资源消耗。

### 已提交结果与当前状态的边界

原子业务操作在提交成功后返回本次已保存的结果及必要版本依据，调用方直接更新其负责的内存状态，不额外查询同一结果。结果只证明本次提交的事实，不保证之后没有其他事务提交；不能仅凭本次提交位置跳过尚未吸收的其他提交。

| 情况 | 缓存使用规则 |
| --- | --- |
| 已确认提交成功，结果及所属版本完整 | 更新对应已提交缓存；查询时仍遵守其版本范围 |
| 已确认回滚 | 丢弃本次候选结果，不把它作为已提交状态 |
| 提交结果未知 | 不发布候选缓存，停止依赖该结果的处理，按持久化规则确认实际结果 |
| 缓存缺失或被淘汰 | 从可靠数据库查询或重新计算 |
| 当前状态版本无法确认，或已知有尚未吸收的相关提交 | 先读取或刷新所需状态，再作依赖该状态的判断 |
| 数据库已知失效 | 按状态库错误处理，缓存不能提供继续普通执行的授权 |

新计划发现继续遵守[调度缓存](../architecture/scheduling-execution.md#新计划发现与内存调度缓存)：周期性轻量读取 `latest_plan_seq`，变化时增量加载；不能因缓存而延长现有感知目标。报告责任和 ACK 等状态按各自范围检查，不能仅凭 `plan_seq` 未变就认为数据库没有其他变化。幂等受理、旧值取得、依赖当前状态的写入判断，以及会话最终退出检查继续在规定事务内进行。

报告缓存中的“D 在 H 的状态”与“D 的当前状态”具有不同含义。前者仅复用于相同历史边界；后者进入报告恢复前，必须证明对应所绑定的 C，后续事件分页始终限定在 `(H, C]`。缓存登记事实不证明文件当前仍在 `ready` 或 `processing`，实际发布与恢复继续按文件交接规则检查。

SQLite 的 `PRAGMA data_version` 可提示同一连接两次检查之间发生了其他连接的提交，但不能直接作为跨连接的统一历史位置，也不跟踪本连接自己的提交，见[官方说明](https://www.sqlite.org/pragma.html#pragma_data_version)。是否使用这一提示尚未决定，它不替代事务内判断和一致读取设计。

### 减少写入的方式

保留业务规定的持久化边界，优先减少重复工作：同一原子业务操作的历史、目录和相关投影一次提交；仅更新受影响的投影部分；相同观察在没有新增状态、恢复依据或报告事实时，按既有事件粒度规则不追加历史。相同状态值仍可能携带新的恢复证据，不能只按字段相等去重。

拷贝进度保存频率采用[进度保存的分段大小](../architecture/file-copy.md#进度保存的分段大小)：使用本次会话的 `copy.segment_size`，默认值与合法范围由文件拷贝专题定义，取回、异常原片检查及修复输入共用。容量按[统一语法](../architecture/configuration.md#容量配置的表示)书写，加载时精确换算为整数个字节。采用[按段提交的流式传输任务](#按段提交的流式传输任务)，线程内按较小块持续读取和写文件，段尾同步完成后由主协程组织进度提交，确认成功后继续下一段。源文件最后不足一段也正常保存，提前结束但未达到已知源长度按读取失败处理。后续会话改变段大小仍从原可靠字节位置继续，不改变身份和预算。具体类型和签名仍需细化；任务提交遵守[默认线程池规则](#本地文件执行使用默认线程池)。

缓存只复用已提交数据；操作意图、尝试预算、正式产物登记等继续在其规定位置可靠保存。

### 容量与验收

缓存设置条目数量上限，并在缓存满时淘汰可重新取得的内容。活动流程确实仍需持有的状态按实际生命周期保留，不能假定都可淘汰；流程完成后及时释放引用。数据按需读取，缓存只保留适合复用的部分，遵守[资源处理约束](#通过处理流程控制资源使用)。负载验收同时覆盖条目数量和单条数据大小的变化，并测量数据库缓存、对象转换、报告与文件缓冲以及受管理工具进程共同工作时的实际消耗。

验收对比关闭与启用缓存时的业务结果和报告字节，覆盖独立 `submit` 提交、数据库回滚、提交未知、缓存淘汰、进程重启和读取期间发生新提交。分别统计缓存命中、SQL 次数、查询与解码量、实际读写、提交耗时和峰值内存。缓存关闭或全部丢失后仍满足相同业务契约。

### 已完成计划逐步退出常驻内存

冷热作为内存保留与查询加载策略，根据当前工作需要、近期访问和容量选择保留内容；业务状态仍采用既定计划、动作、产物及交付状态。已完成计划退出执行调度，无当前流程持有的详情可暂留近期缓存；缓存条目达到上限时，优先淘汰最久未使用且可重新取得的内容。具体容量、数据结构和查询索引仍需细化。

计划 `completed` 表示其动作均已进入终态。历史产物仍可能被新计划取回或清理；报告同步责任、残留设备事实及允许延后的清理也有各自生命周期。内存保留应按对象和责任判断，避免把计划完成解释为所有关联数据永远不变。

| 使用情况 | 内存与读取策略 |
| --- | --- |
| 当前执行、必要收场或恢复流程仍需要的数据 | 保留流程所需的最小状态；已结束且无关的计划详情可以释放 |
| 计划已经完成，无当前流程持有详情，近期可能再次读取 | 进入有条目数量限制的近期缓存；达到上限时允许立即淘汰 |
| 已完成且近期未使用的数据 | 释放可重新读取的内容，数据库保留历史、投影和身份关联 |
| 新计划引用旧产物或动作 | 按引用和实际选择范围加载所需对象，沿用原身份和终态，不重启旧计划 |
| 报告补投、同步或待确认责任需要旧数据 | 按冻结范围或责任标识查询；无需为等待远端确认而常驻整份旧计划 |
| 是否仍有责任或数据是否可靠无法确认 | 按既有未知与状态库错误规则处理，不能以冷数据分类代替责任判断 |

启动和日常检查按未完成动作、适用本地责任及设备关联索引查询，避免先加载全部历史计划再筛选。冷热变化本身不产生业务事件，不要求新增持久化冷却标记；责任的产生、变更和完成仍按原规则保存。收益主要是减少重复查询、解码和常驻内存，数据库永久历史的存储增长继续单独评估。

验收覆盖计划完成后被淘汰、新计划按范围引用旧产物、等待 ACK 时释放计划详情，以及计划终态后仍有独立收场责任的情况；缓存淘汰和重新加载不得改变原身份、终态、剩余预算或报告责任。增加已完成历史计划数量时，启动和正常调度不应因此加载全部计划详情。

## 设备驱动接口契约

| 接口部分 | 能力 |
| --- | --- |
| 静态定义 | 拍摄能力、参数 Schema、默认值、完成条件和操作兼容性，不连接设备 |
| 设备控制 | 准备通信、启动拍摄、查询状态，以及设备支持的停止操作 |
| 设备文件访问 | 查询文件信息、按偏移读取、取得源端摘要、删除指定文件 |

不同拍摄能力按实际设备提供接口，不要求录像、照片和延时摄影采用相同的启动、停止及完成方式。ADB 命令、厂商响应格式及证据解释留在具体驱动内部；业务层消费明确事实。驱动不自行写业务数据库、改变动作状态或生成状态报告。

调用结束情况与设备事实分别表达；以下是已有设备契约的代表性分区，实际结果类型还需按操作细化：

| 已取得证据 | 驱动表达 |
| --- | --- |
| 可靠识别启动成功响应 | 启动已确认，携带确认时的计时依据 |
| 设备明确拒绝本次操作 | 拒绝结果及原因；其他设备状态仍只表达已知事实 |
| 调用超时，效果无法确认 | 调用超时、设备结果未知 |
| 已取得可靠成功证据，调用随后异常 | 同时保留成功事实与调用异常 |

上层执行流程管理业务尝试预算、重试间隔和恢复决策；驱动执行本次明确要求的调用，不自行增加业务尝试或重置预算。计时与证据要求见[相机拍摄](../architecture/camera-recording.md)，单次调用结束不代表设备任务结束。

文件读取接口须支持：

- 向分段传输工作线程提供指定偏移起的连续文件数据，由该执行方按小块读取并及时观察实际数据到达，用于无数据超时判定。文件内容在驱动读取端与传输线程之间流动；主事件循环处理段结果、控制和异常通知。
- 请求停止并确认实际读取结束；确认前保留设备拷贝占用。
- 拷贝期间必要的录像停止命令仍能执行；不独占整个设备直到文件读完。

同一相机的单文件拷贝限制由统一设备协调负责，取回、异常原片检查和修复共用。分段、重试与重启均沿用既有身份和预算，见[文件拷贝规格](../architecture/file-copy.md)。

## 文件处理接口契约

| 部分 | 责任 |
| --- | --- |
| 取回流程 | 确定来源及产物集合，创建交付身份，判断发布资格，汇总逐项结果 |
| 可恢复拷贝流程 | 组合设备读取与本地文件接口，管理读取尝试、可靠进度、续传和完整性校验 |
| 本地文件接口 | 检查、写入、同步、截断、原子移动和删除，返回实际操作结果 |

可恢复拷贝由取回、异常原片检查和录像修复共用，接收已经确定的来源、工作文件与所属处理身份。是否创建 `delivery` 由发起流程决定。

每段拷贝按“读取并写入 → 文件与必要目录同步成功 → 数据库保存可靠进度 → 提交成功后继续下一段”推进。文件操作只提供事实，数据库进度由拷贝流程保存。恢复时按固定源长度、可靠进度和实际文件状态判定，遵守[续传决策表](../architecture/file-copy.md#重启后选择续传位置)。

发布接口保留实际操作阶段：

| 操作结果 | 可以确认的事实 |
| --- | --- |
| 确认移动尚未发生 | 本次操作尚未把文件交给 `ready` |
| 移动成功，必要目录同步失败或未确认 | 文件已对主程序可见，持久性未确认，不能当作从未发布 |
| 移动及必要目录同步成功 | camctl 的文件发布步骤完成，可继续保存所属流程要求的记录 |
| 移动结果无法确认 | 保留未知，结合历史与实际文件证据核实 |

文件可以在数据库记录保存前被主程序领取。当前进程依据自己已经可靠确认的移动与同步结果保存事实，不要求文件仍留在 `ready`。普通交付、业务状态报告和日志副本分别遵守自身的交接及恢复规则；文件接口不自行分配业务身份或要求先写业务数据库，因此日志副本交付可以在数据库不可用时工作。

普通交付流程按[保存顺序与中断恢复](../architecture/file-handoff.md#普通交付的保存顺序与中断恢复)组织发布意图、文件移动、目录同步和完成事务。重启后没有可靠完成事实、三个位置均无副本且无法确定结果时，交付结束为 `failed`，保留本地交接结果未知的原因，不自动重新投放。该判断属于业务恢复流程，不能由通用文件接口或目录缺失的默认值代替；其他交付继续按取回汇总规则推进。

取消和恢复由所属流程组织。取回半成品与取消后的完整副本共用[工作副本清理机制](../architecture/obtaining-outputs.md#取回工作副本的保留与清理)，先保存适用的失败或取消，确认文件归属及相关操作已结束，再删除本次仍在 `staging` 的副本；清理失败保留记录，后续正常 `run` 再作有限尝试，不单独触发会话。普通取回遵守[拷贝取消与文件操作收场](../architecture/obtaining-outputs.md#拷贝期间的取消与文件操作收场)：同一文件按段提交任务，线程内部顺序处理小块并检查停止请求；取消后停止新增普通操作，排队任务确认撤回，已开始的文件调用跟踪实际结果。源读取、本地读写和重试分别确认停止后，才能按取回归属清理。已开始的进度事务仍按数据库规则确认结果，不因取消抹去已提交历史。文件接口不凭文件残留自行决定清理资格。主程序领取与传输边界见[文件交接](../architecture/file-handoff.md)。

### 本地文件执行使用默认线程池

第一版本地文件任务通过 `asyncio.to_thread()` 使用当前事件循环的默认线程池。分段传输与其他本地文件操作共享该池；线程按需创建并复用，任务完成后线程可执行下一项任务，在线程池关闭时统一收场。线程数量沿用所选 Python 运行库的默认上限；具体行为见 [Python 3.11 线程池](https://docs.python.org/3.11/library/concurrent.futures.html#concurrent.futures.ThreadPoolExecutor)及 [`to_thread()` 实现](https://github.com/python/cpython/blob/3.11/Lib/asyncio/threads.py)。

| 执行情况 | 处理 |
| --- | --- |
| 有空闲线程，或默认上限内可以创建线程 | 由默认线程池调度任务，调用协程异步等待实际结果 |
| 工作线程全部占用且达到上限 | 任务等待执行位置，调用协程保持异步等待 |
| 任务实际结束 | 向所属流程交付成功、失败或停止结果，线程可复用于后续任务 |
| 所属流程请求取消 | 沿用排队撤回、段内停止检查及实际结果跟踪规则；文件资源按实际执行状态释放 |

业务流程按需提交工作，动作执行协程遵守[创建时机规则](#动作执行协程的创建时机)，相机文件读取遵守[同一相机的拷贝并发限制](../architecture/file-copy.md#同一相机的拷贝并发限制)。同一文件最多有一个未完成分段任务，可靠进度提交成功后才安排下一段。文件与源读取句柄归所属流程或读取尝试管理，连续分段可以由不同工作线程执行，仍须保持顺序与明确的所有权。取消后保留已开始任务的结果跟踪，直至满足既有资源关闭和清理条件。

第一版本地文件任务不设置应用层统一提交上限。符合业务资格的任务通过 `asyncio.to_thread()` 直接提交，默认线程池的工作线程全部占用时，由线程池排队，调用协程异步等待。默认线程池限制执行线程数量，其内部等待队列没有有界容量；现有按需创建、逐段提交和设备并发规则减少提前积压，但不提供所有未完成文件任务的固定数量上限。数据库、日志和报告通信继续使用各自专用执行资源，报告生成子进程自行完成其文件写入和同步。

验收覆盖共享池中传输与其他文件任务交错执行、任务排队、跨段顺序及取消后结果跟踪。联调测量实际吞吐、文件任务积压、文件操作等待和主事件循环调度延迟，以运行证据评估资源安排。若发现某个流程集中提交大量任务，优先检查并调整该流程的任务创建和提交方式。

### 按段提交的流式传输任务

取回、异常原片检查和修复输入共用分段传输方式。主协程根据可靠进度、源长度及生效段大小确定本段范围，通过 `asyncio.to_thread()` 提交一个默认线程池任务并异步等待结果。任务在所属读取尝试内，从驱动取得源数据，在同一执行流程中按小块顺序写入目标文件，复用有容量限制的缓冲；到达本段目标后完成文件及必要目录同步，返回实际结果。源数据读取和本地写入均在传输执行方推进，主事件循环只协调阶段转换和必要控制。

同一文件同一时刻最多有一个分段任务，期间对该文件的修改由任务独占。任务内前一小块处理完成后再推进下一小块，缓冲容量独立于段大小。主协程收到段成功结果后，仍须检查所属流程资格，再通过专用数据库线程保存可靠进度；提交成功后才安排下一段。段成功只证明对应范围的文件处理完成，可靠进度以数据库实际提交为准。

| 当前阶段与结果 | 后续处理 |
| --- | --- |
| 分段任务尚未开始，收到取消 | 确认撤回且不会执行后结束该任务 |
| 分段任务已经开始，收到取消 | 主协程通过线程安全的停止请求通知任务；线程在小块之间及开始段尾同步前检查，停止新增普通读写和同步，跟踪已经开始的调用并返回实际停止结果 |
| 正在等待源数据，收到停止请求或达到无数据超时 | 驱动按既有规则推进读取停止并确认实际结束；停止控制须能在段完成前传达，不能以主协程取消等待代替读取结束 |
| 段写入和必要同步成功，所属流程仍有执行资格 | 返回段范围与同步结果，由主协程组织可靠进度保存 |
| 段结果返回时所属流程已经取消 | 按所属取消和文件保留规则收场，普通取回不为待清理副本新增进度保存 |
| 源读取、目标写入或同步失败 | 返回失败阶段、已知效果及读取停止情况，按所属流程处理；不因已收到或写入部分数据推进可靠进度 |
| 进度事务已经开始 | 跟踪实际提交、回滚或结果未知，按既有数据库规则处理；提交确认前不安排下一段 |

工作线程的停止检查覆盖整个分段任务生命周期，主协程持续响应取消和设备控制。段边界不构成新的设备读取尝试，不重置读取预算或无数据计时规则。数据到达由读取执行方及时观察；等待源数据时使用单调钟，目标写入、同步和进度提交阶段不计入源无数据等待。读取接口、控制通道和数据流的所有权应支持这一分工，具体句柄与通知接口仍需细化。

正常传输按段交换结果，文件内容使用有界缓冲在传输执行方处理；取消、失败和设备控制按实际发生时通知。数据库事务、业务重试预算与设备协调继续由原业务流程管理。按默认分段配置，每 GiB 的正常分段任务提交为 8 次，创建、最终校验及异常收场等操作另计。

验收分别改变内部小块和分段大小，验证文件字节、可靠进度、取消和恢复结果；检查线程任务提交随段数变化，主事件循环不逐块中转文件内容。覆盖段内取消、等待源数据时取消、同步前后取消、进度提交期间取消和各阶段失败。目标主机联调按分段任务粒度测量吞吐、主事件循环调度延迟、任务交互次数、等待积压及缓冲占用。

### 本地文件操作的完成与故障边界

第一版以本地文件系统调用最终返回成功或错误为正常运行前提。工作线程执行的读写、同步、截断、查询、移动及删除一旦开始，调用方异步等待实际结果；单次本地文件操作及其取消收场不另设应用层完成时限。有限收场限制适用工作和尝试次数，不承诺底层存储持续失去响应时仍能限时正常退出。

| 本地文件操作状态 | 处理 |
| --- | --- |
| 已开始，尚未返回，包括所属流程已取消 | 继续跟踪并等待结果，保持相关文件与操作占用；取消后停止新增普通操作 |
| 返回成功 | 使用已确认的实际效果，按所属流程继续或收场 |
| 返回错误 | 保留错误和已知效果，按所属业务失败、报告失败或恢复规则处理；同步失败不推进可靠进度 |
| 底层持续不返回 | 超出第一版应用内恢复范围，由部署侧处置；不宣称操作结束或正常退出，后续启动按既有持久化状态和文件证据恢复 |

该边界适用于本地文件调用。设备通信、源读取无数据等待、数据库入队与锁等待、报告子进程整次任务的时限继续遵守各自契约；报告任务的总时限仍覆盖其文件处理阶段。

验收使用可控协作者覆盖取消后操作仍未完成、随后成功或报错，以及完成前禁止冲突操作和资源释放。集成测试覆盖真实文件写入、同步、空间不足等错误与中断恢复，联调测量实际负载下的操作延迟。

## 普通日志执行与多进程轮换

普通日志复用标准库 `logging` 的日志级别、`LogRecord`、处理器和格式化机制，协程通过可等待的日志入口投递。各个需要写文件日志的 Python 进程独立创建日志入口适配、`QueueHandler`、`janus` 有界队列、`QueueListener` 和 `ConcurrentRotatingFileHandler`；文件处理器来自第三方库 `concurrent-log-handler`。组件职责如下：

| 组件 | 职责与执行位置 |
| --- | --- |
| 异步日志入口与接纳适配 | 在业务协程中检查级别、准备记录并应用分级接纳规则，需要等待空位时通过 `janus.async_q` 异步等待 |
| `QueueHandler` 与同步接纳适配 | 在同步日志调用所在的线程中准备记录，经 `janus.sync_q` 提交并应用共用分级策略，不等待队列空位；接纳自身低于 `ERROR` 的日志及第三方日志 |
| `janus` 有界队列 | 同一进程内以 `async_q` 和 `sync_q` 两个接口共享记录与容量，负责协程和线程间的等待及唤醒 |
| `QueueListener` | 使用本进程的专用日志工作线程从 `janus.sync_q` 取出记录，并调用文件处理器 |
| `ConcurrentRotatingFileHandler` | 在日志线程中协调跨进程文件锁，检查轮换并追加日志 |

`run` 与独立 `submit` 各自持有上述组件，共用同一日志路径及轮换配置。队列是进程内交接通道，进程间通过文件处理器的锁协调；各进程可独立启动、写入及退出。报告子进程需要写入同一文件日志时，也在自身初始化组件。日志处理器、队列及锁对象不跨进程传递，配置从本次 CLI 生效值取得；子进程使用主进程传入的相应配置。

轮换参数从[运行日志配置](../architecture/logging.md#配置与默认值)转换：`session.log_max_size` 换算为字节后提供给 `maxBytes`，`session.log_file_count` 包含正在写入的文件，因此 `backupCount` 为该值减 1。同一路径的各写入进程采用一致的参数与锁位置，配置更新遵守既有停止相关 CLI 后再更新的部署规则。文件锁等待、文件追加和轮换发生在日志线程中；业务线程承担记录准备和入队成本。

日志线程独立于普通文件任务使用的默认线程池，直接消费队列并顺序执行文件处理器。协程与同步入口共享记录准备和接纳规则，异步接口的具体封装方式在实施时确定；跨线程等待与唤醒复用 `janus`。该队列只连接本进程的一个事件循环与同步线程，进程间写入协调仍由文件处理器负责。

| 进程阶段 | 日志组件处理 |
| --- | --- |
| 初始化文件日志 | 在本进程创建组件并启动监听线程；配置或文件初始化失败分别遵守原错误分类 |
| 正常运行 | 协程通过异步入口、同步代码通过同步入口提交记录，本地监听线程调用文件处理器 |
| 文件处理器报告轮换、追加或协调故障 | 按[日志通道故障](../architecture/logging.md#日志通道故障)分类，保留轮换失败但仍可追加与必须禁用文件日志的区别 |
| 正常退出 | 按重要日志取消与退出规则完成必要收场及待投递记录交接，结束日志生产，处理已接纳记录或按日志通道故障规则结束处理，由日志线程按丢弃汇总规则处理一次摘要，再停止监听线程、关闭本进程文件处理器并完成 `janus` 队列及通知任务的关闭 |
| 进程突然终止 | 不保证队列中尚未写出的日志保留；业务恢复继续依据状态数据库 |

复用库的文件锁和轮换能力，项目适配集中于日志入口、按水位接纳、丢弃汇总、配置转换、故障分类及生命周期组织。取消保护、停止标记和通道禁用通知的具体接入方式，以及调小保留数量后的归档清理仍需细化；这些实现必须满足规定的取消、退出及故障契约，库默认行为不能代替它们。正常关闭须在处理已接纳记录后关闭队列，不能把关闭队列等同于记录已写完。依赖版本与目标主机兼容性在实施时锁定和验证。

报告首次失败时，按[日志副本交付规则](../architecture/logging.md#准备与交接)复制当前普通日志文件。业务协程通过正常日志入口记录错误；日志副本交付流程另行确认该错误实际写入并刷新，随后协调共享文件的追加、轮换与复制，保证固定副本包含该错误且日志记录完整。副本保留当前日志的全部原始字节，完整保存后才移入 `ready`；原日志继续留在配置路径供各进程使用。

上述写入完成通知与复制协调属于项目适配，不能假定 `QueueListener` 或 `ConcurrentRotatingFileHandler` 已提供完整的日志副本接口。实施时核验库的锁接口及调用顺序，复用现有跨进程锁，并将锁等待和文件操作放在工作线程中；主事件循环异步等待。普通 `await logger.error(...)` 仍以入队完成为返回条件，不为每条普通日志增加文件写入确认，也不等待其他进程的日志队列全部排空。日志级别遵守[运行日志的部署约定](../architecture/logging.md#配置与默认值)，接纳 `ERROR` 及以上记录。

验收组合真实独立进程与文件处理器，覆盖并发追加和轮换、`submit` 单独运行、一个进程退出而其他进程继续写入、保留数量为 1、调整保留数量及日志通道故障。使用进程内队列的集成测试验证正常退出处理已接纳记录、日志线程执行文件操作，以及普通业务错误与日志错误保持各自分类。接口依据见 [QueueHandler 与 QueueListener](https://docs.python.org/3.11/library/logging.handlers.html#queuehandler)和 [concurrent-log-handler 使用说明](https://github.com/Preston-Landers/concurrent-log-handler)。

### 日志异步投递入口与有界队列

协程使用 `await logger.error(...)` 形式投递，异步 Logger 的 `debug`、`info`、`warning`、`error`、`critical`、`exception` 方法统一采用可等待接口，保留标准日志常用的消息参数、`extra` 和异常信息语义。日志来源须指向业务调用处，异常信息在等待前捕获。级别检查沿用本次进程生效配置，被配置级别过滤的记录不进入队列。

camctl 自身的 `ERROR` / `CRITICAL` 日志只允许由主事件循环中的协程通过异步入口投递，`exception()` 按 `ERROR` 处理。数据库、文件、报告通信等工作线程通过已有结果或异常通道报告错误，由所属流程的协程统一处理并记录；这些线程可以通过同步入口记录低于 `ERROR` 的日志。主事件循环直接调用的同步函数或回调同样通过结果、异常或既有监督通道报告错误，由所属协程记录。报告子进程的同步工作通过既有任务结果与控制通信报告失败，由主进程所属协程处理和记录。

错误结果的交付不等待日志接纳。数据库线程先按事务实际结果完成必要处理并交付结果，日志不能延迟事务结果交付，也不能成为停止普通执行、录像应急停止等必要故障处理的前置条件。工作线程与所属协程不重复记录同一次重要错误；日志线程自身故障继续遵守[日志通道故障规则](../architecture/logging.md#日志通道故障)。这些调用位置约定适用于 camctl 自身代码，第三方代码仍由同步日志适配接入。

下面定义合法调用入口、日志通道正常可用时的行为分区；通道故障遵守前述故障分类，取消及关闭过程中尚未入队记录的归属遵守[重要日志取消与退出规则](#重要日志等待期间的取消与退出)。

| 调用环境与记录状态 | 处理 |
| --- | --- |
| 任意来源，记录被配置级别过滤 | 直接完成，不入队 |
| 任意来源，记录按共用接纳规则保留且可立即入队 | 完成入队后返回，不等待文件写入 |
| camctl 自身主事件循环中的协程入口，`ERROR` / `CRITICAL` 经共用接纳规则处理后仍无法取得位置 | 异步等待接纳，不因队列满载主动丢弃；等待只暂停调用协程，事件循环可继续处理其他工作 |
| 第三方来源，`ERROR` / `CRITICAL` 经共用接纳规则处理后仍无法取得位置 | 丢弃本条新记录并返回，不等待空位；适用于主事件循环线程和普通工作线程 |
| 任意来源，`WARNING` 遇到过载 | 不采样、不等待空位，队列未满时接纳，满时丢弃本条；通过下述水位规则限制低级别日志，为警告和错误保留接纳空间 |
| 任意来源，`INFO` 遇到过载 | 按下述水位规则独立随机采样或丢弃，不等待空位；概率采用本次进程生效配置 |
| 任意来源，`DEBUG` 遇到过载 | 达到第一水位后丢弃新记录，不等待空位 |

camctl 自身与第三方日志共用一套按级别与水位接纳的策略；`WARNING` / `INFO` / `DEBUG` 均不等待队列空位。来源造成的唯一接纳策略差异是 `ERROR` / `CRITICAL` 满载时的保障：camctl 自身不允许因过载主动丢弃，只通过上述协程入口异步等待，第三方允许丢弃本条。同步与异步入口共用策略实现和队列容量，不各自维护一套采样或水位规则。

按水位接纳及顺序消费遵守[下述规则](#日志按水位接纳并顺序消费)，容量、水位与采样概率由[运行日志配置](../architecture/logging.md#配置与默认值)统一定义，双方来源使用相同配置；因接纳限制丢弃的记录按[计数与退出汇总规则](#日志丢弃计数与退出汇总)处理。文件轮换保留规则、日志通道故障及进程突然终止的边界继续有效。

第三方标准日志经配置的 Handler 接入，先应用共用的级别与接纳策略；需要立即尝试入队时，以 `janus.sync_q.put_nowait()` 的实际结果判断接纳或满载，不采用先检查空位再保证入队的方式。按策略丢弃属于正常接纳分支，不向调用方抛出满载异常、不转为同步文件写入，也不为本条记录创建后台投递任务或反复输出 stderr 错误；后续新记录继续按共用策略处理。队列满载不禁用日志通道，不改变第三方调用本身的业务结果，其他日志错误仍按各自故障规则处理。来源由日志接入配置明确区分，不以当前线程或日志级别推断；具体 Logger 路由在实施时确定，并检查第三方传播设置及重复处理器。

异步入口直接在调用协程中等待接纳，不为每条待投递记录另建后台任务。低级别日志采用可等待的调用形式不表示会等待队列空位；这类记录在同步入口及异步入口均按上述规则立即完成接纳或丢弃判定。队列容量只限制已入队的等待记录，不包含消费者正在处理的记录及等待入队协程持有的记录，不能据此宣称日志总内存已受到固定上限约束。入队成功也不等于文件写入成功。

集成验证须组合真实 `janus` 队列与 `QueueListener`：队列满时 camctl 自身异步入口的重要日志等待，其他业务协程仍能推进，消费释放位置后等待者能够完成接纳；同步和异步入口共用容量，日志线程执行文件处理，普通文件线程池繁忙不占用日志专用执行线程。在接纳条件相同的场景对照双方来源，验证 `WARNING` / `INFO` / `DEBUG` 遵守相同规则且不等待空位，来源只改变重要日志满载时的等待或丢弃分支。第三方重要日志覆盖主事件循环线程和普通工作线程、过滤、入队成功、满载丢弃及腾出位置后再次接纳，确认丢弃分支返回、无后台补投及重复 stderr 错误，并验证来源路由正确。队列保持满载时，验证数据库操作的实际结果及工作线程错误仍能交付，必要故障处理不以日志接纳为前置条件，由所属协程记录重要错误且不重复投递；审查自身重要日志实际调用入口及执行上下文，覆盖主循环同步辅助函数、工作线程和报告子进程结果处理。还须覆盖多个等待者、异常上下文与调用位置，以及正常退出处理已接纳记录并关闭队列通知资源。取消与正常退出按下述状态分类补充验收。队列能力依据见 [janus 项目说明](https://github.com/aio-libs/janus)。

### 重要日志等待期间的取消与退出

camctl 自身的重要日志已经开始投递、正在等待队列空位时，取消请求不丢弃该记录。记录仍由所属协程持有，直到确认入队，或日志通道实际失效并按既有规则禁用后结束本次投递；再传播待处理的协程取消或完成原有收场，不把取消吞掉并恢复普通业务。重复取消不产生记录副本，也不提前结束这项交接责任。已入队记录归日志消费侧处理，不因调用协程随后取消而撤回。

日志等待保护只延后所属协程的最终结束，不延后必要的业务取消和设备停止。收到取消或会话收场请求时，取消事实保存、停止新增普通动作、录像停止、源读取停止及适用清理，继续按各自契约推进。流程必须在日志等待前完成必要的责任安排，或通过已有取消与监督路径保证这些操作可以在日志等待期间推进；若必要停止只能由当前等待协程执行，须调整该流程的调用顺序或责任分工。仅用取消屏蔽让整个业务流程停在日志等待中，不满足此契约。

下表的“通道可用”也包含轮换失败但仍能可靠追加的情况；单纯队列满载不属于通道失效。

| 本条记录与日志通道状态 | 取消或收场处理 |
| --- | --- |
| 尚未开始本次投递 | 继续按所属业务的取消与错误处理规则决定工作，不因保护机制额外生成记录 |
| 正在等待入队，通道可用，尚无取消请求 | 所属协程异步等待接纳 |
| 正在等待入队，通道可用，收到取消或会话收场请求 | 保留本条及其所有权，必要业务停止继续推进；确认入队后才允许所属协程最终结束 |
| 已确认入队，随后收到取消 | 不撤回、不重新投递；日志线程继续处理，所属协程按原取消或收场规则结束，不必等该条写入文件 |
| 通道实际失效并被禁用，本条尚未入队 | 通知并结束全部受影响的等待，本条按日志通道故障结束，不能宣称入队或写入成功；所属协程继续取消或收场 |
| 通道实际失效并被禁用，本条已经入队或正在处理 | 按已有日志通道故障规则结束处理，不为本条补投，不改变原业务结果 |
| 取消与入队、通道禁用发生竞争 | 以实际接纳阶段确认唯一结果，同一记录最多入队一次；不能因取消通知先到就丢掉已入队记录，也不能因结果竞争再次入队 |
| 进程被强制终止或突然退出 | 不保证内存中待投递、已入队记录和丢弃计数保留 |

通道禁用须传递到接纳侧，唤醒正在等待空位的协程并使后续投递遵守禁用规则；不能只让消费线程停止，再把生产者留在等待中。因通道故障未写出的记录不计入水位、采样或满载丢弃摘要。具体通知和结果表示由日志适配实现，保持日志故障不掩盖业务故障的契约。

正常退出按下列顺序组织：停止新增普通工作，推进必要业务收场及其日志投递；保持日志消费可用，等待现有生产者及其待投递记录完成交接，或按通道故障规则结束投递；确认生产已经结束后，处理完已接纳记录，按既有规则尝试写出一次丢弃摘要；最后停止监听线程并关闭文件处理器、队列及其通知资源。不能提前停止消费者或关闭队列来让尚未完成的重要日志交接看似结束。

日志积压可以延长正常取消收场中的协程结束和正常进程退出，不另设超时后丢弃重要日志的规则，也不承诺固定完成时间。底层系统持续不返回的处置继续遵守第一版已有故障范围。所有待投递记录保持在既有所属流程内，不为规避取消等待另建逐条后台补投任务；接纳侧保护不改变业务责任、状态数据库事实或设备实际结果。

验收覆盖等待前取消、等待中取消、重复取消、入队后取消、取消与接纳竞争、等待期间通道禁用，以及正常收场时队列仍满。使用受控消费者证明：队列暂不释放空位时记录仍被持有，必要设备停止及数据库结果交付仍可推进；释放位置后本条只接纳一次且取消继续生效；禁用通道时所有受影响等待者结束，不宣称日志保存成功、不计为满载丢弃。集成验证先完成生产与投递交接，再处理已接纳记录、退出摘要及组件关闭；重复收场不重复投递或汇总。

### 日志按水位接纳并顺序消费

第一版通过提前限制低级别日志接纳，为 `WARNING`、`ERROR` 和 `CRITICAL` 留出队列空间。每个进程使用一个有界先进先出队列，已接纳记录按实际入队顺序交给文件处理器；不因新日志级别更高而删除、替换或重排已有记录。先入队顺序不等于不同线程中日志调用开始时间的顺序。

设队列总容量为 `C`，第一水位为 `L`，第二水位为 `H`，均按记录条目计量，满足 `0 < L < H < C`。`q` 为接纳判定时已在队列中等待的记录数量，不包含日志线程已取出的记录或尚未入队的等待者。日志先经过配置级别过滤，再按下表处理；表中的丢弃均针对本条新记录。

| 队列状态 | `DEBUG`，任意来源 | `INFO`，任意来源 | `WARNING`，任意来源 | camctl 自身 `ERROR` / `CRITICAL` | 第三方 `ERROR` / `CRITICAL` |
| --- | --- | --- | --- | --- | --- |
| `0 ≤ q < L` | 接纳 | 接纳 | 接纳 | 接纳 | 接纳 |
| `L ≤ q < H` | 丢弃 | 采样选中才接纳，未选中则丢弃 | 接纳 | 接纳 | 接纳 |
| `H ≤ q < C` | 丢弃 | 丢弃 | 接纳 | 接纳 | 接纳 |
| `q = C` | 丢弃 | 丢弃 | 丢弃 | 所属协程异步等待接纳 | 丢弃 |

判定随队列积压变化：下降到第二水位以下后恢复 `INFO` 的采样接纳，下降到第一水位以下后恢复普通接纳；丢弃的记录不补投。水位及容量约束在同步与异步生产者之间共同成立，容量判定与实际接纳须协调为一致结果，不能用未受协调的 `qsize()` 检查宣称满足水位边界。等待重要日志入队时，不持有消费者或其他生产者取得位置所需的锁。并发适配的具体方式在实施时验证，复用 `janus` 的等待与唤醒机制。

`WARNING` 不采样、不等待空位。第二水位以上的空间由警告和错误共同使用，不为单个级别或来源独占；警告和错误自身持续积压仍可填满队列。默认日志级别为 `WARNING` 时，低级别记录已在入口过滤，水位抑制主要用于启用更详细日志的部署。已入队的重要记录仍需等待前面的记录被处理，本规则不提供优先写出或固定等待时限。日志通道故障、进程突然终止及文件轮换保留继续遵守各自规则。

`C`、`L`、`H` 分别取自 `session.log_queue_capacity`、`session.log_queue_low_watermark`、`session.log_queue_high_watermark`。默认值、合法类型、组合关系及部署生效规则由[运行日志配置](../architecture/logging.md#配置与默认值)定义。

`INFO` 在 `L ≤ q < H` 时采用独立随机采样，选中概率为本次进程的 `session.log_info_sample_probability`，记为 `p`。每条符合采样条件的新记录独立进行一次判定，取均匀随机值 `u ∈ [0, 1)`，当且仅当 `u < p` 时选中；未选中即丢弃。概率为 0 时全部省略，为 1 时全部选中。低于第一水位的 `INFO` 不采样，达到第二水位后直接丢弃；配置级别已过滤的记录不参与采样。采样选中不等于已接纳，仍须与水位检查及实际入队协调；并发状态变化需要重新判断水位时，同一条记录不反复抽样以争取入队。

双方来源使用同一概率与算法，不保证每固定数量的记录恰好选中固定条数，允许连续选中或连续省略。随机采样只影响普通诊断日志，不改变业务结果、历史或报告内容。复用标准库随机数能力，随机源允许在测试中替换；不按历史事件回放采样结果。采样省略计入下述丢弃汇总。

验收按表覆盖各级别、双方来源、采样选中与未选中，以及 `L - 1`、`L`、`H - 1`、`H`、`C - 1`、`C` 的边界。配置覆盖默认值、合法覆盖、非法类型和非有限概率、概率端点、水位相等或倒置、容量不足以及部分字段覆盖后组合不合法；验证进程内配置固定、后续进程采用新值、各进程队列容量独立。单元验证通过可控随机源覆盖 `u < p`、`u = p`、`u > p`、概率端点及非采样区间，不以真实随机运行恰好产生固定条数作为通过条件。组合真实同步与异步生产者和日志线程，验证并发接纳不突破容量及相应水位限制，消费者取出后后续记录恢复适用规则，同一记录不因竞争而重复抽样，已接纳记录不被新记录淘汰且按入队顺序处理。覆盖队列仅由警告和错误填满的情况，验证第三方错误和新警告丢弃、自身错误异步等待。

### 日志丢弃计数与退出汇总

每个进程在内存中按日志级别累计因接纳策略丢弃的记录数量，包含自身和第三方来源，同一条记录只计一次。只保留计数，不保存丢弃的消息内容，不为每条丢弃生成新日志；运行中不定时或按水位恢复输出摘要。计数不写入状态库、不跨进程合并、不跨启动累计，进程突然终止时不保证保留。

| 记录处理结果 | 是否计入相应级别的丢弃数量 |
| --- | --- |
| 被配置日志级别过滤，未进入接纳判定 | 否 |
| 因水位限制直接丢弃 | 是 |
| `INFO` 采样未选中 | 是 |
| 本条按策略需尝试接纳，但最终因满载被丢弃 | 是；不得再按其他接纳原因重复计数 |
| 自身重要日志仍在等待接纳，或记录已经入队 | 否 |
| 日志文件通道故障导致无法写出，或通道已禁用而跳过 | 否；该故障继续由日志通道故障规则诊断，不能混称为队列接纳限制 |
| 退出摘要被级别过滤，或摘要本身写入失败 | 否；不生成新的丢弃摘要 |

正常退出时先结束本进程日志生产并处理完已接纳记录，再由日志线程检查最终计数，最多尝试写出一条 `WARNING` 摘要，随后关闭日志组件。这里的正常退出指能够完成有序关闭的路径，也适用于业务失败后正常完成进程收场，不表示业务成功。摘要携带本进程身份及各非零级别的丢弃数量，表明这些记录因日志接纳限制被省略；`ERROR` / `CRITICAL` 的此类丢弃只来自第三方。不同进程各自汇总，同一共享文件中出现多条不同进程的摘要不属于重复。

| 退出时状态 | 摘要处理 |
| --- | --- |
| 所有丢弃计数均为零 | 不生成摘要 |
| 存在丢弃，但当前日志级别不允许 `WARNING` | 不写摘要，不提升摘要级别或转写其他通道 |
| 存在丢弃，允许 `WARNING`，文件日志通道可用 | 日志线程直接交给原文件处理器一次，遵守已有文件锁、追加和轮换规则 |
| 存在丢弃，允许 `WARNING`，文件日志通道已禁用 | 跳过摘要，不为汇总重新打开或启用通道 |
| 摘要写入或轮换过程中发生故障 | 按已有日志通道故障分类处理，以实际追加结果判断摘要是否写入；轮换失败但追加成功仍算写入，不递归记录或重试投递摘要 |
| 进程突然终止，无法执行正常关闭 | 不保证有摘要，也不由下次进程补造 |

摘要不重新进入业务日志队列，不参与水位或采样判定。同步与异步生产者更新计数须正确协调；停止生产后读取最终计数，避免漏计或重复汇总。组件关闭被重复调用时，也不能再次生成同一进程的摘要。摘要失败不改变业务或 CLI 的原结果，日志故障的 stderr 提示继续遵守原故障规则。

单元验证覆盖计数分类、同一记录只计一次、混合级别和来源、全部为零、摘要级别过滤、通道禁用及摘要失败，断言级别与数量事实，不逐字比较文案。集成验证组合真实同步与异步生产者、队列和日志线程，验证并发计数、先处理已接纳记录再写摘要、摘要由日志线程直接写出且不入队、重复关闭不重复汇总，以及多个独立进程分别汇总；真实写入失败按既有故障契约处理。验证采样省略会计数而配置级别过滤不会计数，进程重启不继承前次计数。

## 报告模块接口契约

| 部分 | 输入与职责 | 输出 |
| --- | --- | --- |
| 报告规则 | 根据业务变化、ACK、同步要求及已有报告，判断保留、生成或补投 | 处理决定与覆盖范围 |
| 维护流程 | 组织登记、生成、发布、结果保存及失败处理 | 本次结果与尚未完成的责任 |
| 内容生成器 | 已冻结依据，以及该历史边界处的实体状态 | 按固定规则产生的 JSON 字节，可分段输出 |

生成器不读取当前时间、当前配置或设备状态。同一冻结依据和历史数据须生成相同字节；实体集合的 ID 排序和普通数组保序遵守[报告格式](../architecture/report-format.md)。字段排列、紧凑输出、文件编码及可选空实体集合的省略方式按[第一版生成器的结构与排版](../architecture/report-format.md#第一版生成器的结构与排版)执行；数字格式和字符串转义按该专题的固定规则生成。精确数字适配、计算及设备边界转换仍需细化。

正常处理顺序为“事务内登记冻结依据 → 取得冻结边界处的实体状态 → 生成并同步 `staging` 文件 → 按报告替换规则发布 → 保存发布事实”。状态读取遵守[当前投影与按范围逆向恢复](#当前投影与按范围逆向恢复)。生成期间的新变化交给下一轮，不能改写已经登记的报告。报告维护独立发现业务变化，不能只依赖 `plan_seq`。

| 本次情况 | 后续责任 |
| --- | --- |
| 本地处理完成，没有遗漏的新变化 | 报告方面允许会话收尾；不必等待客户端 ACK |
| 出现尚未覆盖的新变化 | 安排下一轮处理 |
| 内容生成或文件处理失败 | 保留责任，普通设备工作继续；按既有触发规则再次处理 |
| 数据库读取、历史解释或提交失效 | 按状态库错误处理，不能作为普通报告失败继续不可靠执行 |

报告失败不因轮询或时间经过立即重开同一轮；后续业务变化、同步要求或下一次正常 `run` 按规格触发。完整范围与恢复规则见[状态报告](../architecture/status-reports.md)、[报告发布与补投](../architecture/report-publication.md)和[状态同步](../architecture/status-sync.md)。

## 调度与会话接口契约

| 部分 | 责任 |
| --- | --- |
| 调度规则 | 根据已提交状态、时间及资源占用，计算可执行工作、等待原因和下次唤醒时间 |
| 调度循环 | 异步等待事件、发现新计划、刷新状态并调用调度规则 |
| 设备操作协调器 | 按设备管理兼容性、控制通道占用及文件拷贝机会 |
| 会话管理 | 管理启动、时钟资格、接纳锁、收尾及最终结果 |

调度规则是同步函数，不读取真实时钟、不访问数据库、不启动设备。调度循环和具体执行流程使用协程；每台设备的协调器是逻辑对象，不表示每设备一个线程。

每次唤醒先检查并吸收新计划，再合并已完成操作的结果、刷新调度依据，重新判断资格与资源条件，然后安排允许的工作或继续异步等待。获得调度机会后仍须完成意图持久化及执行前检查，不能根据旧缓存直接发令。采集、拷贝和取消流程分别管理自己的状态推进。

`submit` 的 `needs_run` 与 `run` 的退出检查共用待处理责任分类，各自按[会话接管协议](../architecture/protocol-session.md)执行事务与锁操作。不能只因内存队列为空退出：未来动作、未完成的有限收场、文件处理和本地报告责任仍参与判定；仅等待主程序传输或客户端 ACK 不要求持续运行。责任无法确认时不能按全部完成处理，报告失败退出与正常成功退出分别表达。

时间资格、提前唤醒、排序与设备占用沿用[调度规格](../architecture/scheduling-execution.md)和[时钟规则](../architecture/clock-recovery.md)。时钟异常的受限会话不能取得普通执行资格或仅因队列中还有普通工作持续运行。

### 动作执行协程的创建时机

已接纳动作由数据库保存，中央调度器管理其时间、资格及等待原因，统一等待最近需要处理的时间点或新事件。调度器决定开始推进动作的实际准备或执行工作时，才创建相应执行协程；未来动作以持久化记录和所需调度信息表示。通信准备适用已有 `prepare_at` 规则，无须等到 `scheduled_at` 才开始准备；调度提前唤醒本身不授予准备或执行资格。

下表中的时间与资格均按动作所属规则判断；终态处理先于新的普通执行派发。是否存在尚未完成的协程，以实际流程结果为准。

| 动作与流程状态 | 调度与协程处理 |
| --- | --- |
| 无活动执行协程，尚未到适用的准备或执行时间 | 保留动作及调度信息，由中央调度器统一等待 |
| 无活动执行协程，已到处理时间，但准备或执行条件不满足 | 保留等待原因，按条件变化或相关截止时间重新判断；窗口观察、过期及取消继续及时处理 |
| 无活动执行协程，已到处理时间且满足相应资格，并被调度器选中 | 创建协程推进准备或执行；实际设备副作用前仍须完成规定的持久化及最终检查 |
| 已有活动执行协程 | 由该流程继续处理通信、时间等待、数据库结果及设备结果；重复唤醒不重复创建同一执行流程 |
| 动作已进入终态 | 不再创建该动作的普通执行流程；已有流程完成必要收场，独立的产物、报告及清理责任继续按各自生命周期处理 |

协程创建不是公共动作状态转换，通信准备也不因创建协程而自动变成 `running`。准备完成后尚未到计划时间时，已经开始工作的协程可以异步等待；活动流程的取消、重试及实际结束确认继续遵守既有规则。流程结束后释放不再使用的数据，等待协程取消不代替对实际数据库、线程或设备操作结果的跟踪。

窗口内有效观察由调度与持久化规则判断，不以执行协程是否已经创建为前提。设备暂不可用时，仍须保存符合条件的观察事实，按既有规则区分窗口耗尽与窗口错过，并及时处理取消。后续执行资格变化时重新决策，不能依据旧缓存发令。

该安排减少未来动作各自长期等待所需的协程，不限制已经接纳的动作数量，也不提供固定的活动协程数量上限。多个动作同时具备资格时，仍按既有设备兼容性、排序和并发规则推进；队列外的等待者仍有资源开销，数据库入队的 9 秒时限不代表等待者数量上限。

验收覆盖大量未来动作仅登记调度信息、准备时间与执行时间分别到达、提前唤醒未到准备时间、设备占用后释放、重复唤醒、窗口观察与两类过期结果、执行前取消及活动流程收场。使用可控时间及同步点验证创建时机，确认创建协程不改变公共状态、尝试预算或设备发令条件；组合多个同时到期动作测量活动协程及数据库等待者的实际数量。

## 测试与分步实施方向

### 分类与替身

遵守根目录 [AGENTS.md](../../AGENTS.md) 的测试规范：

- 单元测试验证独立语义契约，隔离真实文件系统、数据库、网络、子进程、时钟及用户全局状态。用可控时钟推进窗口、超时及重试，不实际等待数秒。
- `pytest-mock` 提供 `mocker.patch`、`Mock`、`AsyncMock` 和 `spy` 等接口；根据需要使用 `autospec`、`spec_set` 约束替身。复杂状态协作者可用手写 fake（简化模拟实现）。
- 组件集成测试组合真实 SQLite、文件系统、线程、CLI 子进程及受契约约束的设备替身，验证事务、锁、文件交接和中断恢复。并发用明确同步点控制，不依靠随机等待制造竞争。
- 跨组件集成测试组合真实客户端、camctl 与 C 接入模块，验证输入、执行、报告导入及累计确认；相机替身与真实设备验收分别记录。
- 重要的替身隔离关系须有相应真实组合验证。正常状态与历史回放结果比较、同一报告重建字节比较，都要有独立于实现路径的契约预期。

### 推进顺序

以下是已认可的阶段方向，尚不是逐任务实施计划：

1. 确定模块职责、状态归属、依赖方向和跨模块事务边界。
2. 定义接口、公共内部类型及契约测试，用正常、失败、取消和恢复场景走查。
3. 分批实现完整业务链：先贯通初始化、受理、报告和客户端导入；再接入采集、取回、交付；随后逐步覆盖取消、清理及恢复分支。
4. 每接入一个真实实现就验证协作者组合，持续进行集成验证。

断电恢复所需的事实、身份、进度和接口必须在前两步考虑完整，不能等正常流程写完后再决定保存哪些恢复依据。具体测试按行为契约先失败、再实现；阶段门禁和验收清单留给后续完整实施计划。

## 报告生成使用独立进程

**报告生成放到独立进程中执行。** 主进程中的报告协调协程异步等待生成结果，事件循环继续处理调度与设备控制。报告逻辑接口及原有失败、恢复规则保持有效。

主进程负责决定报告生成时机、登记冻结依据、调度设备、组织最终发布与发布事实保存。报告进程负责按批次读取当前投影、历史快照及必要事件，按对象选择路径恢复到冻结边界，分段编码 JSON，以及写好并同步 `staging` 文件。

报告子进程采用标准库 `multiprocessing.Process` 管理，使用 `spawn` 启动方式。新解释器启动后自行创建数据库连接等所需资源，主进程的数据库连接和会话锁不传递给子进程。主子进程通过 `multiprocessing.Pipe` 一对一通信，使用字节消息接口传递 UTF-8 JSON。

报告进程的正常生命周期如下：

| 场景 | 处理方式 |
| --- | --- |
| 本次 `run` 尚未需要生成报告 | 不启动报告子进程 |
| 首次需要生成报告 | 启动一个报告子进程 |
| 同一 `run` 后续需要生成报告 | 复用生成成功且通信正常的子进程，一次生成一份报告；失败后的进程按下文规则结束 |
| `run` 正常结束 | 报告子进程随会话退出，不跨 `run` 复用 |

报告生成期间的新变化仍按报告接口契约交给下一轮处理。上述生命周期不替代会话收尾条件，也不授权在报告责任未处理完时正常退出。启动失败、超时、进程退出及父进程异常结束按下文规则处理；主动取消、通信线程收场和强制终止后的确认仍需细化。

主子进程按以下范围传递任务与结果数据：

| 步骤 | 责任与数据 |
| --- | --- |
| 主进程提交生成任务 | 传入报告标识、已登记的冻结依据、数据库位置、本次生成使用的临时文件路径、生成任务标识、本次会话生效的实体与事件读取批次参数，以及数据库忙等待参数 |
| 报告进程执行 | 使用自己创建的只读数据库连接，以分批短读事务取得固定范围内的数据，在事务外恢复至同一 H、分段编码 JSON，写好并同步 `staging` 文件 |
| 报告进程返回成功结果 | 返回生成任务标识、文件位置、大小和摘要，表示生成与文件同步完成；最终发布仍由主进程组织 |
| 报告进程返回失败结果 | 返回生成任务标识、明确的错误分类与诊断，保留报告错误与状态库错误的区别 |
| 主进程处理生成结果 | 根据结果组织最终发布并保存发布事实，或进入对应的错误处理流程 |

报告所需的投影、历史数据和完整报告内容在报告进程内部处理，进程之间只传递启动就绪、任务、结果及正常退出指令等控制信息。报告文件摘要遵守既有 SHA-256 规则。消息字段类型、容量、校验及通信中断后的结果确认方式仍需细化。

### 管道通信与生成任务身份

| 阶段 | 通信契约 |
| --- | --- |
| 子进程启动完成 | 通知主进程已就绪，可以接收任务 |
| 主进程派发任务 | 将本次生成任务标识与报告冻结依据等输入一起发送；子进程一次处理一份报告 |
| 子进程返回结果 | 成功或失败均携带对应生成任务标识；成功结果不代表报告已经发布 |
| 正常会话收尾 | 主进程通知子进程退出，并确认其实际退出 |

报告 ID 标识内容已经冻结的报告，生成任务标识区分对该报告的不同生成调用。同一报告重新生成时使用新的任务标识，报告 ID 保持不变。旧任务结果不能完成新任务；标识的具体类型和生成方式仍需确定。

主进程由专用通信线程执行可能阻塞的管道收发，向调度协程提供异步接口。结果接收须与子进程退出监测配合，不能只等待结果消息。线程与事件循环间的通知方式、管道端点所有权、消息边界不完整时的处理、超时和取消仍需形成具体接口及状态模型。

验收覆盖启动就绪后派发、连续生成多份报告、同报告不同任务身份、成功与分类失败消息、无结果退出及正常退出确认。退出与结果的关系及超时判定按下文处理，主动取消的预期仍需细化；通信线程替身的单元测试与真实进程管道的集成测试分别验证接口和实际组合。

### 生成结果与进程退出的判定

下表适用于尚未取消、尚未超时的当前有效生成任务。有效结果必须是完整、通过消息校验且匹配当前任务的结果消息；进程退出码为零或临时文件存在均不能单独证明生成完成。

| 观察到的情况 | 判定与处理 |
| --- | --- |
| 收到有效成功结果 | 确认生成完成，进入既有发布流程；不等于发布已经完成 |
| 收到有效的报告生成失败结果 | 本次失败，保留报告责任，普通设备控制继续 |
| 收到有效的状态库或历史解释错误结果 | 按状态库错误处理，不降为普通报告失败 |
| 子进程存活、通信正常，尚无完整结果 | 在生成时限内继续等待并监测退出，达到时限后按超时规则处理 |
| 子进程已退出或连接已中断，检查已送达消息后仍无有效结果 | 生成结果无法确认，不发布残留文件 |
| 消息格式错误或任务标识不匹配 | 按通信协议错误处理，不能据此完成当前任务 |

观察到退出通知时，先检查管道中已经送达的完整结果，再判断是否缺失结果。结果的业务含义不因退出通知先被处理而丢失。只有部分消息时不解释为完整结果；检查消息、连接中断和等待上限的具体协调方式仍需细化。

子进程每批取回数据后结束该批查询与读事务，在事务外恢复及写出。发送成功结果前，必须完成报告写入、摘要计算及文件同步，关闭本次文件，确认没有本任务遗留的活动查询或读事务；此后不再修改该任务的文件。主进程取得有效成功结果后，即使子进程随后意外退出，也可按既有发布条件继续发布。仅有文件而无有效成功结果时，后续需要生成该报告仍按恢复规则从头生成。

连接中断但子进程尚未结束时，确认它实际停止后，才能清理或重新使用相关临时文件。通信失败和缺失结果保留未完成报告责任，后续生成沿用[报告处理失败后何时再尝试](../architecture/status-reports.md#报告处理失败后何时再尝试)的触发规则，不因通信失败自行开启独立重试循环。已知的状态库错误继续按其错误契约处理。

验收分别控制消息送达、主进程接收和子进程退出的先后关系，覆盖成功后退出、失败后退出、无消息正常或异常退出、消息不完整、任务身份错误，以及连接中断后进程仍写文件的情况。不得提前发布、清理或复用临时文件；未确认的生成结果不能被标记为生成完成。

### 分阶段时限与超时收场

启动、生成和停止等待分别设置可配置时限，采用单调时钟计时。配置在会话启动时读取并在本次会话内保持不变；具体默认值通过联调确定。生成采用整次任务的总时限，进度推进不延长该期限。

| 时限 | 计时范围 |
| --- | --- |
| 启动时限 | 从开始启动子进程，到主进程确认有效的就绪通知 |
| 生成时限 | 从开始派发任务，到主进程确认有效结果，包含任务发送、数据库读取、计算、文件写入和同步 |
| 停止等待时限 | 请求子进程停止后，等待其实际退出 |

启动或生成超时后，本次按超时处理并保留报告责任。主进程请求终止对应子进程；停止等待时限内仍未退出时，再强制终止。发出终止信号不证明进程已结束，确认实际退出后才能清理或重新使用相关临时文件。后续满足既有报告触发条件时再启动新子进程，不因本次超时独立增加重试。

| 主进程已经确认的任务状态 | 随后观察到的情况 | 处理规则 |
| --- | --- | --- |
| 等待就绪或结果 | 对应期限到达，尚无已确认的有效就绪或结果 | 判定本阶段超时，进入停止流程 |
| 已确认成功 | 本任务已失效的生成计时通知到达 | 保留成功结果，不改判为超时 |
| 已确认失败 | 本任务已失效的生成计时通知到达 | 保留原失败，不另开一次超时处理 |
| 已超时 | 迟到的就绪或成功结果 | 不重新激活任务，不恢复本次发布资格 |
| 已超时 | 迟到的失败结果中含状态库错误 | 继续按状态库错误处理，不因超时而忽略该证据 |
| 已超时 | 其他迟到结果 | 保留必要诊断，不完成或重开本次任务 |

报告超时本身不单独阻止普通设备控制；已知状态库失效等执行前提错误仍按各自契约处理。较大的报告可能需要提高生成时限，联调需同时验证报告规模、内存、读事务时长及设备控制延迟。

消息校验完成与超时判定的具体串行处理方式、停止信号、正常退出等待、强制终止后仍无法确认退出的处理，以及通信线程收场仍需细化。验收使用可控时钟和同步点覆盖各阶段超时、成功与超时的两种先后顺序、迟到状态库错误、停止等待到期升级及实际退出前禁止清理或复用文件。

### 父进程异常结束时终止报告子进程

报告子进程在 Linux 上设置 `PR_SET_PDEATHSIG` 为 `SIGKILL`。正常收尾继续通过退出通知和等待流程处理；父进程突然结束时，由内核向报告子进程发送强制终止信号，不依赖 Python 清理代码执行。该机制仅适用于报告子进程，不据此改变设备工具进程的终止和恢复契约。

| 场景 | 处理规则 |
| --- | --- |
| 主进程正常收尾 | 使用退出协议，确认实际退出；等待与升级机制遵守相应时限规则 |
| 主进程突然崩溃或被强制结束 | 由 Linux 父进程死亡信号机制发送 `SIGKILL` |
| 子进程初始化时确认原父进程已结束或身份不符 | 子进程自行退出，不开始报告生成 |
| 无法设置父进程死亡信号 | 判定子进程启动失败，不发送就绪通知 |

初始化须在设置死亡信号前后核对原父进程身份，覆盖父进程在设置前已经结束的竞争分支。保护建立并完成检查后，才允许通知就绪和接收生成任务。创建子进程的父线程必须在报告子进程整个生命周期内存活；Linux 实际监测该创建线程的结束，不能通过短期线程创建后立即结束该线程。接口机制与线程所有权须同时满足这一约束，详见 [Linux 父进程死亡信号说明](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html)。

报告子进程只读状态数据库并写入自己的 `staging` 工作文件，发布由主进程组织。异常结束允许留下临时文件；报告责任按已经保存的事实恢复，需要生成时从头重建。发出 `SIGKILL` 不等于已确认实际退出，文件清理与复用继续遵守实际停止的要求。主进程重启时通过下述独立报告工作锁协调旧子进程与新报告工作。

验收覆盖保护设置失败、父进程在设置前后结束、子进程空闲及生成期间父进程突然结束，以及正常退出流程。检查子进程实际结束和后续恢复行为，不把信号发送成功作为全部验收依据。

### 独立报告工作锁

同一部署的报告子进程使用同一把 Linux `flock` 排他锁，由报告子进程独占持有，协调不同会话之间的报告工作。该锁独立于主进程的会话锁和接纳锁，不表达业务受理或设备执行资格。它是运行时协调手段，不是数据库业务状态。

子进程先建立父进程死亡保护，再取得报告工作锁，随后才通知就绪并接收任务。报告工作期间持续持锁，结束全部报告操作后才能释放；锁句柄由报告子进程持有，不因主进程结束而提前释放。新主进程在相应报告工作取得锁之前，不清理或复用可能仍由旧报告进程使用的临时文件。

| 加锁结果 | 处理规则 |
| --- | --- |
| 成功取得锁 | 完成相应启动准备后进入就绪状态 |
| 锁被旧报告进程占用 | 在启动时限内等待，不接触旧进程的报告临时文件 |
| 等待超过启动时限 | 本次报告启动失败，保留报告责任并按超时规则收场；普通设备控制继续 |
| 打开锁文件或加锁发生其他错误 | 明确记录报告启动失败，不能当作锁空闲或普通占用 |

锁文件保持稳定，不通过删除或替换锁文件取得工作资格；文件存在不表示锁被占用。锁关联的全部文件描述符关闭后由内核释放锁，见 [Linux flock 说明](https://man7.org/linux/man-pages/man2/flock.2.html)。工作锁不代替同一会话内对实际子进程退出的确认，也不改变生成结果、发布资格及重试触发规则。

锁路径与部署身份的关联、等待实现、句柄关闭次序及报告文件清理接口仍需细化。验收覆盖旧进程持锁时新进程等待、释放后取得、等待超时、加锁错误、父进程退出时子进程持锁，以及未取得工作资格前禁止清理旧临时文件。报告工作锁故障与会话锁、接纳锁故障分别断言所属错误边界。

### 报告子进程的复用与失败后回收

第一版只复用生成成功且进程、通信正常的报告子进程。生成失败或通信异常后结束该子进程；后续满足既有报告触发条件时，再启动新的子进程。结束子进程本身不构成报告重试机会，也不改变报告身份、冻结内容或尚未完成的责任。

| 本次情况 | 子进程处理 |
| --- | --- |
| 生成成功，进程和通信正常 | 保留，供同一 `run` 后续使用 |
| 收到有效成功结果，随后进程退出或通信异常 | 已确认生成结果按原规则处理；该进程不再复用 |
| 子进程明确返回报告生成失败 | 结束该进程，按既定时限确认实际退出 |
| 启动或生成超时、通信异常、消息不合法或身份不匹配 | 停止使用该进程，执行终止与回收 |
| 子进程报告状态库或历史解释错误 | 按状态库错误进入会话处理，同时结束报告进程 |
| 生成成功，主进程移动文件或同步交接目录失败，子进程仍健康 | 可以保留子进程；文件状态及后续责任按发布规则处理 |
| 发布结果无法保存到状态库 | 按状态库错误处理，不能只重启报告进程后继续普通执行 |

故障后的进程在实际停止得到确认之前不接收新任务。确认停止后才允许清理或复用相应临时文件；跨会话继续遵守报告工作锁规则。生成失败后不依赖数据库连接、文件句柄及内部缓冲已恢复到可复用状态。普通报告失败与状态库错误的区别仍有效，不因统一回收子进程而合并两类会话行为。

验收覆盖成功后复用、各类生成或通信失败后回收、已确认成功后退出、主进程发布失败但保留健康子进程，以及发布记录保存失败进入状态库错误。分别验证未出现新触发时不重新生成、出现合法触发后使用新进程，以及旧进程未停止时不派发新任务。

### 报告计算与资源约束

独立进程拥有自己的解释器和 GIL（全局解释器锁），报告计算与主进程的 Python 计算可以在不同 CPU 核心上同时执行。该选择用于减少报告计算对设备调度响应时间的影响，不构成实时性保证；CPU、内存带宽、eMMC 和数据库锁的竞争仍需单独评估。

报告采用[分批读取与分段生成报告](historical-state-query.md#分批读取与分段生成报告)。camctl 与其他软件共享主机，报告处理须限制内存占用：逐批读取、恢复和顺序写出，释放不再需要的数据，避免保存整份报告的数据对象或 JSON 大字符串。编码器维护输出位置和分隔符，不读取已写出的 JSON；最终仍生成一份完整报告。批次、缓存与恢复路径不得改变字节内容。

采用[逐层分批写出与实体排序](historical-state-query.md#逐层分批写出与实体排序)：查询接口按固定实体顺序分批返回，生成器维护当前父对象和子集合的写入位置，不组装整棵计划或动作子树。父对象补齐、跨批次去重与跨计划引用继续遵守报告选择规则。查询采用[按最后一个排序值续读](historical-state-query.md#按最后一个排序值续读)，实体按 ID、事件按恢复方向和完整历史位置分页；位置仅用于本次一致读取，中断后重新生成报告。具体接口类型和索引仍需细化。

报告遵守[资源处理约束](#通过处理流程控制资源使用)：实体与事件读取分别使用正整数配置 `history.entity_batch_size` 和 `history.event_batch_size`，部署时独立调整；默认值与完整规则见[读取批次配置](historical-state-query.md#实体与事件读取批次分别配置)。主进程向报告进程传递本次会话的生效值，故障后重新创建进程仍使用相同值。读取批次参数由读取流程使用，内容生成器继续按固定规则处理恢复后的状态。缓存与队列限制条目数，编码及文件读写采用有容量上限的缓冲；减少临时副本，处理完成后释放不再需要的引用。第一版按单个字段能在目标部署环境中正常处理来设计和验收；累计实体、子集合和相关历史数量增加时，继续分批读取并逐步写出。测试与联调同时覆盖数据数量及单条数据大小，测量实际峰值与延迟；容器容量和负载验收条件仍需确定。

文件或计算失败按报告规则处理，数据库与历史解释错误按状态库规则处理，半成品不得发布。进程通信必须保留这些错误分类；进程异常退出或通信中断时，不能将缺失结果解释为生成成功。

实施前须确定报告规模预期及设备调度延迟的负载验收门槛，落实规定的短读事务、分阶段时限、父进程异常结束保护及失败后触发规则。主动取消、通信线程收场和具体接口仍需细化。负载验收应测量生成报告期间的设备调度延迟与内存峰值，不能只测报告总耗时。

## 尚需细化的事项

时钟异常时，camctl 在有限收场后检查并处理一次报告责任。复用现有报告生成与补投机制，遵守[受限报告资格](../architecture/clock-recovery.md#时钟异常期间的报告)，不启动普通动作或新的同步动作，不持续接纳后来的业务变化；报告处理完成后仍以时钟异常退出。实现须覆盖冻结前后并发提交、没有报告工作、已有适用文件、生成或文件失败以及状态库错误，不能复用正常关闭接纳循环使受限会话持续运行。
