# 检查副本清理的运行生命周期核对

现场现象符合清理预算，不构成新的生产缺陷。`processed` 保存本次运行已经取得的 `KEPT` 结果，阻止同一文件再次取得清理机会；该缓存应当保留。生产工作区保持干净，没有生产提交。

`docs/architecture/file-handoff.md:173` 规定同一中间文件每次正常 `run` 最多检查和尝试一次；184、188—195 行进一步规定，无法删除的检查也消费历史额度，检查后用途改变不重新开启本次机会。分段复用规格的保留与删除资格仍须同时遵守该运行预算。

原现场的 H179、H182、H185 已分别可靠推进 file1、file2、file3 的检查游标。来源在 H172 提交；属于发布截点等待集合的取回动作2、3在 H338、H349 才结束。因此本次检查时保留副本，之后仍留到下一次正常运行处理，符合契约。H368 的最终 `DELETE` 分类只证明当前删除资格成立，不能代替新的运行机会。原测试在同次运行中被动等待180秒删除，缺少正确的运行生命周期边界。

窄见证使用原现场 SQLite 的独立备份及三份匹配的真实媒体副本，通过生产 `WorkFileRuntime.initialize/flow/settle`、真实 `BusinessDatabase` 与 `FileTaskExecutor` 执行；未启动完整 CLI 链。主见证使用 batch32、limit128：实际文件使用期间，历史扫描对三文件形成 `KEPT`，游标到3，剩余额度125，未调用 stat/unlink；实际使用结束后，再次 flow 及首次入口复用原结果，数据库和文件不再变化。新建下一次正常运行的维护器后，三文件各 stat/unlink 一次，数据库全部为 `RELEASABLE/COMPLETED`；重复推进不增加操作。

独立副本另以合法配置 batch1、limit1 核对预算边界：每次正常运行仅删除一文件，游标依次3→1→2，耗尽后重复推进不增加删除，第三文件等待后续运行。原现场数据库摘要及三份媒体摘要保持；未登记的哨兵文件保留。所有维护任务和数据库 worker 已完整结束。
