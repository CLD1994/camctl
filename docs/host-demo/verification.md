# C 接入模块验证记录

[返回接入入口](README.md) · [构建与调用说明](../../apps/host-demo/README.md)

本记录对应 `apps/host-demo` 第一版源码、静态库和终端演示。组件不包含业务 CLI、设备驱动或文件传输实现。

## 开发环境与已执行检查

验证环境为 x86_64 Linux、Ubuntu 24.04、GCC 13.3.0、glibc 2.39。测试使用 cmocka 和可控 CLI；依赖的确定版本及摘要见[依赖清单](../../apps/host-demo/vendor/manifest.cmake)。

| 检查 | 实际范围 |
| --- | --- |
| CMake 3.28.3 常规构建 | 静态库、终端演示、组件测试 |
| CMake 3.10.2 Release 构建 | 实际使用该版本配置、编译并运行分类测试 |
| 单元测试 | 6 个 CTest 入口，包含结果校验、调度状态、日志队列、文件领取、配置与输入队列、进程读取与退出判断 |
| 集成测试 | 8 个 CTest 入口，使用真实线程、子进程、管道和文件系统；其中主程序场景与终端场景由 Python 组织 |
| AddressSanitizer 与 UndefinedBehaviorSanitizer | 对组件和测试启用内存及未定义行为检测后运行分类测试 |
| 生产交付 | 关闭测试构建、安装静态库/公开头文件/演示，使用安装后的文件链接独立 C 调用方，生成源码包与当前平台二进制包 |

可从仓库根目录重现常规测试：

```sh
cmake -S apps/host-demo -B .local/host-demo-build -DHOST_BUILD_TESTS=ON
cmake --build .local/host-demo-build -- -j2
ctest --test-dir .local/host-demo-build -L unit --output-on-failure
ctest --test-dir .local/host-demo-build -L integration --output-on-failure
```

CMake 3.10.2 使用传统目录调用方式：进入独立构建目录，执行 `cmake /absolute/path/to/apps/host-demo -DHOST_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Release`，随后执行 `cmake --build .` 和 `ctest -L unit`、`ctest -L integration`。测试构建保留断言，Release 不会移除验收调用。

## 已验证的契约

| 责任边界 | 覆盖的行为 |
| --- | --- |
| stdout 与进程退出 | 完整单行消息、分段读取、消息与退出码不一致、未知错误原因、字段缺失或类型错误、重复判定字段、额外输出、超限、退出事实未知；收到消息不提前认定子进程结束 |
| 命令与重试 | 首次计划保留与释放、后续 submit、共用重试次数、实际尝试前计数、成功不清零、等待期间预算耗尽、多个 needs_run 合并、false/错误保留待启动要求、重试耗尽后新提交触发启动 |
| 输入与初始化 | 配置与路径复制、队首保持与容量拒绝、未初始化调用、重复初始化、配置非法、分配/管道/两个线程创建阶段失败后的清理 |
| 进程与主程序 | 长 run 期间仍提交、持续输出不堵塞管道、明确启动失败与执行后退出 127、指定 PID 回收、主程序目录和信号处理保持、关闭标准流时模块日志不持续占用其描述符 |
| 文件领取 | 完整遍历后才移动、列表超限不部分移动、同名覆盖、inode 与原始字节保持、单项失败继续、目录故障停止、移动结果未知不回退 |
| 文件操作竞争 | 在首次原子移动边界安排发布新文件、撤下已列文件、移动成功但返回未知错误、目录位置变化；依据实际位置确认已移动文件和本次未领取文件 |
| 日志与业务调用 | 队列拥塞丢弃新诊断、恢复后记录丢弃数量、单条截断、轮换数量与大小、日志路径不可用，以及日志写入被明确阻塞时仍能提交和领取 |
| 模块基础设施故障 | 单调钟失效后拒绝新路径、保留诊断，文件领取仍可调用 |
| 终端示例 | 公开接口调用、中文和空格路径、同名文件领取、非法和超长命令、输入结束后模块继续运行 |

并发测试使用文件门闩或系统调用边界安排事件顺序；日志轮换的文件数量与大小在暂停主程序线程后检查，避免将正常轮换期间的路径变化误判为存储故障。测试中的受控进程和替身只安排协作结果，不承担真实业务语义。

## 仍需真实环境验收

| 未验证项目 | 所需环境与验收方式 |
| --- | --- |
| arm64 Ubuntu 18.04 | 使用实际编译器、glibc 和第三方链接参数重新构建并执行组件测试；确认 posix_spawn 的错误证据和资源限制 |
| 第三方主程序 | 接入三个调用时机，核验双方子进程回收、信号设置、描述符继承和长期资源占用 |
| 真实 camctl 与客户端全流程 | 仓库中的 camctl 尚未实现；待可运行后，按行为规格验证计划导出、递交、执行、报告领取、客户端处理及累计确认 |
| 相机与设备 | 在真实设备上验证设备能力、执行及恢复结果；可控 CLI 不提供这项证据 |
| 主机突然断电 | 在目标存储设备上切断电源，验证文件与目录同步、重启后的实际文件位置和 camctl 恢复；普通进程终止测试不代表断电落盘 |
| 第三方文件传输 | 由第三方在真实链路验证传输、失败残留和后续文件处理 |

本机测试通过不代表上述项目已验收。源码包可独立编译；当前开发机产生的二进制只适用于匹配的 x86_64 环境。
