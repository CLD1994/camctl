# C 接入模块实现设计

[返回主程序对接入口](README.md) · [行为规格](design.md)

本页整理第一版的技术选型、公开接口、提交顺序、日志和资源限制，供实施者与第三方接入人员使用。组件实现、完整调用示例与构建说明见[源码入口](../../apps/host-demo/README.md)，开发环境验证和目标环境待验收事项见[验证记录](verification.md)。业务行为、首次计划处理、自动重试和文件领取以[行为规格](design.md)为依据。

文中明确标为“建议”的内部划分、构建兼容基线和验证方法，是实现方向，实施者可以根据实际代码和工具链调整。调整不得改变已经确认的调用与失败处理规则。

## 目标环境与依赖

目标环境为 **arm64 Ubuntu 18.04**。第三方保留持续运行的 C 主程序，模块编入该主程序，camctl 作为独立程序部署。

| 用途 | 已选方案 | 使用范围 |
| --- | --- | --- |
| 基础操作 | C 标准库 | 内存、字符串等基础操作 |
| 系统操作 | POSIX（类 Unix 系统接口），包括 pthread | 线程、同步、子进程、管道、计时和文件操作 |
| JSON 解析 | yyjson | 读取 camctl 的 stdout 结果消息 |
| 单元测试 | cmocka 与手写测试替身 | 断言、测试准备与清理、模拟协作者 |
| 构建与测试执行 | CMake、CTest | 构建模块与演示，分别执行单元测试和集成测试 |

yyjson 固定版本，源码随模块交付并参与编译。公开 C 接口使用模块自身定义的类型，第三方调用时无需接触 yyjson。cmocka 只用于测试构建，不编入交付模块。

实现采用 C11，构建文件兼容 CMake 3.10.2。实际编译器、系统 C 库和第三方构建方式尚未在目标主机核验；当前构建使用确定版本的依赖源码，目标兼容性须通过实机编译和测试验收。版本号、来源与校验信息在[依赖清单](../../apps/host-demo/vendor/manifest.cmake)集中维护，交付包包含所需依赖源码及许可文件。

## 部署参数与公开接口

### 参数由谁提供

第三方在部署时准备目录及需要的配置文件，主程序通过初始化结构体向模块提供参数。

| 参数 | 归属与使用方式 |
| --- | --- |
| camctl 程序位置 | 主程序传入；模块用它启动 camctl |
| `ready`、`processing` 绝对路径 | 主程序传入；模块按这些路径领取文件 |
| `staging` 路径 | 第三方在 camctl 部署配置中确定，由 camctl 使用 |
| camctl 配置文件路径 | 主程序可选传入；提供时，模块为各次 camctl 调用附带 `--config` |
| 模块日志路径 | 主程序传入；日志线程写入该文件并管理对应归档 |
| 重试和容量参数 | 初始化结构体提供默认值，主程序可覆盖 |

没有提供 camctl 配置路径时，模块省略 `--config`。camctl 按[既有加载规则](../architecture/configuration.md#本地配置的加载与更新)读取默认位置的文件；文件不存在则使用内置默认值。

部署人员负责保证主程序传入的交接目录与 camctl 实际使用的目录一致，并准备相应访问权限。模块使用主程序提供的目录和参数，camctl 的配置内容由 camctl 自己解释。配置在本次运行期间固定，更新遵守既有部署流程。

### 三个调用入口

一个主程序进程对应一个模块实例，使用以下接口：

```c
int camctl_host_init(
    const camctl_host_config *config,
    const char *initial_plan_path
);

int camctl_host_submit(const char *plan_path);

void camctl_host_claim(void);
```

| 接口 | 调用与返回约定 |
| --- | --- |
| `camctl_host_init` | 接收部署参数；首次没有计划时传入 `NULL`。模块资源建立完成、首次启动安排给工作线程后返回 `0`；本地初始化失败返回 `-1` |
| `camctl_host_submit` | 初始化成功后调用，提供完整写入并关闭的计划文件的绝对路径。复制并接收路径后及时返回 `0`；无法接收时返回 `-1` |
| `camctl_host_claim` | 初始化成功后由主程序显式调用，同步处理本次文件移动，结束后返回；过程诊断由模块记录 |

返回 `0` 只表示本地初始化或路径接收成功。camctl 是否已启动、计划是否受理，以及业务动作的执行结果，分别按进程结果和报告协议判断。

模块保存配置和路径字符串的独立副本。调用返回后，主程序可以复用原字符串缓冲区；计划文件本身仍由调用方保留和管理。文件读取及删除时机的边界见[计划文件](design.md#计划文件)。

初始化结构体提供默认值宏：

```c
camctl_host_config config = CAMCTL_HOST_CONFIG_INIT;
```

接入示例先使用该宏，再填写程序位置、交接目录和日志路径，按需填写 camctl 配置路径及覆盖参数。结构体成员和整数类型由[公开头文件](../../apps/host-demo/include/camctl_host.h)定义，合法范围见[调用说明](../../apps/host-demo/README.md#配置范围与日志)。默认值由头文件的宏提供，示例与测试通过该定义取得默认配置。

初始化成功后，模块随主程序持续运行，直到主机断电。第三方按初始化、收到计划、准备传输三个时机顺序调用这些入口。

## 线程与进程管理

### 各线程负责什么

模块创建两个后台线程。进程工作线程管理 camctl，日志线程负责可能较慢的日志文件操作。

| 执行位置 | 负责的操作 |
| --- | --- |
| 主程序调用初始化或递交入口 | 校验调用参数、复制数据、接收启动或提交要求 |
| 进程工作线程 | 启动子进程、读取 stdout 和 stderr、取得退出结果、维护提交顺序和重试计数 |
| 主程序调用领取入口 | 遍历一次 `ready`，随后逐个原子移动到 `processing` |
| 日志线程 | 读取内存日志队列，追加和轮换模块日志 |

主程序中的模块调用和进程工作线程只将日志放入内存队列。队列操作不能等待日志文件写入；文件领取也不能长时间占用进程管理需要的锁。

### 系统接口

| 操作 | 实现选择 |
| --- | --- |
| 启动 camctl | `posix_spawn`，程序位置与参数数组分别传入；使用 `POSIX_SPAWN_SETPGROUP` 及组号 `0`，在执行程序前建立独立进程组 |
| 等待子进程输出 | `poll` 配合管道读取 |
| 接收新的计划路径 | 有容量上限的队列，接收后通知工作线程 |
| 观察子进程退出 | 针对模块保存的具体 PID 取得退出结果并保留待回收记录；随后检查原进程组内是否还有进程或线程未停止，查找、读取及错误处理要求见[本地进程收场责任](design.md#接入模块的本地进程收场责任) |
| 最终回收子进程 | 确认原组执行工作结束后，使用 `waitpid(pid, ..., WNOHANG)` 回收所持有的 camctl 退出记录 |
| 计算重试等待 | 使用单调钟；等待期间继续处理输入和子进程事件 |

实现使用非阻塞管道通知工作线程，`poll` 最多等待 50 毫秒，每轮每条输出管道最多读取 64 KiB。等待逻辑同时处理新输入、输出可读、进程退出和重试到期；某条管道持续有数据时，其他事件仍能得到处理。这些内部配额可随实机验证调整，不改变公开行为契约。

模块维护每次调用的输出、退出结果、进程组身份及收场阶段。收到 stdout 最终消息不等于进程已退出，camctl 自身退出也不单独证明其执行工具已经停止；下一次 `run` 启动前，须完成原调用的进程收场、最终回收及输出处理。

启动错误使用系统接口提供的实际证据判断。退出码 `127` 本身不能证明 camctl 未曾运行；无法确认的情况保留为未知，按[首次计划规则](design.md#首次启动时如何处理计划文件)和[重试规则](design.md#有限自动重试)处理。目标环境验证须区分程序不存在、无法执行、已执行后异常结束及启动结果未知。

第三方主程序遵守[启动与回收约定](design.md#受管工具的启动与主程序回收约定)。初始化与启动入口检查可检查的信号条件；主程序其他线程的回收行为按集成约定及联调验证，不以一次检查代替持续的责任分工。模块保持主程序既有的工作目录、环境及标准输入输出使用方式。

## 后续计划按顺序提交

模块最多同时运行一个 `run` 和一个 `submit`。后续计划按模块接收顺序执行 `submit`；一次提交明确未能启动时，先完成它适用的有限重试，再处理下一份计划。

下表只定义后续提交顺序；`run` 命令是否携带首次计划路径、如何合并待启动要求，继续遵守行为规格。子进程尚未确认结束时，先继续监控；关于启动失败后重试或继续下一份的行，均以本次尝试未创建子进程或该子进程已确认结束为前提。

| 当前提交的情况 | 后续提交怎样处理 | 对 `run` 管理的影响 |
| --- | --- | --- |
| 没有正在处理的提交，队列非空 | 取最早接收的路径，尝试启动 `submit` | 继续独立管理已有或待启动的 `run` |
| `submit` 子进程尚未结束 | 后续路径排队等待 | 持续读取 `run` 输出并处理其退出 |
| 可以确认当前 `submit` 未能启动，还有重试次数 | 保留当前路径及顺序位置，等待规定间隔后重试；后续路径继续等待 | 等待提交重试不阻止处理 `run` |
| 当前 `submit` 未能启动，共享重试次数已用完 | 记录诊断，结束该路径的提交尝试，继续下一份 | 保留已有 `run` 待启动要求 |
| 当前 `submit` 已运行并结束，结果正常或异常 | 按协议处理结果，结束该路径的提交尝试，继续下一份 | 有效 `needs_run: true` 建立或合并待启动要求；错误不清除已有要求 |
| 当前调用是否开始运行无法确认，但其子进程已确认结束 | 记录未知结果，不重送该输入，继续下一份 | 按已有证据保留和处理 `run` 待启动要求 |

`run` 是否正在运行或等待重试，不改变上表的提交顺序。特别是 `run` 等待自动重试时，工作线程仍正常处理提交队列，新的有效 `needs_run: true` 可按规格合并启动要求。

`run` 与 `submit` 的自动尝试使用[同一份重试计数](design.md#重试次数与等待间隔)。工作线程在每次实际自动尝试前检查并增加计数。某条命令等待期间，另一条命令可能耗尽剩余次数，因此等待结束后必须重新检查。

后续提交的首次尝试不计入自动重试次数。前一份提交耗尽次数后，下一份仍可进行首次尝试；但它明确启动失败时，只能使用当时剩余的自动重试次数。

首次 `run A` 确认未启动、B 通过 `submit` 保存并返回有效 `needs_run: true` 的场景，仍按行为规格合并为一次 `run A`。后续提交串行，不改变首次 `run` 与 `submit` 可以分别处理的规则。

## 资源上限与输出处理

以下是模块自身的默认参数，可通过初始化结构体调整。自动重试默认值及计数规则在行为规格中维护。

| 参数 | 默认值 | 计量范围 |
| --- | --- | --- |
| 尚未处理完的后续计划 | 64 份 | 包含排队、正在提交及因启动失败等待重试的计划路径 |
| stdout 缓冲 | 每个子进程 256 KiB | 本次子进程累计收到的 stdout 字节 |
| 日志队列 | 256 KiB | 等待日志线程处理的日志数据 |
| 单条日志 | 8 KiB | 格式化后保留的日志内容，包含截断提示 |
| 单个模块日志文件 | 10 MiB | 触发轮换的文件大小阈值 |
| 模块日志文件总数 | 3 份 | 包含当前文件及归档 |

首次计划路径单独按首次 `run` 规则保存。后续计划从排队转为正在提交或等待重试时，继续占用同一名额；本份提交尝试结束后释放名额。主程序递交时容量已满，返回 `-1`，不接收这份路径；已接收的路径继续按顺序处理。

限制计划份数不等于限制所有内存字节。实现须同时为复制的路径、队列记录和其他临时数据制定有界的分配方式；容量检查应覆盖接受数据之后实际需要保留的内容。

| 输出情况 | 模块处理 | 进程结果判断 |
| --- | --- | --- |
| stdout 在限额内 | 收集完整消息，由 yyjson 解析，再按公共协议检查字段和类型 | 结合实际退出结果判断 |
| stdout 超过限额 | 标记超限，记录诊断，继续读取并丢弃超出部分 | 本次调用按协议异常处理，不能从保留的前缀推断成功 |
| stderr 持续产生输出 | 按固定大小分块读取，将诊断交给日志队列 | stderr 文案不替代 stdout 和退出结果 |
| 日志队列满或文件日志已停用 | 按日志故障规则处理诊断，继续读取 stdout 和 stderr | 保持本次调用实际取得的结果，不能因日志故障修改它 |

JSON 语法有效与消息符合 camctl 协议是两项检查。模块需要验证消息结构、字段类型及对应命令的必填字段，包括 `submit` 成功消息中的 `needs_run`。公共规则见[stdout 与退出状态](../architecture/cli-commands.md#stdout-与退出状态)，实现不能通过字符串搜索代替解析与校验。

## 模块日志

模块日志单独保存在部署指定的路径，记录调用标识、进程编号、文件路径、操作、结果和实际错误。camctl 自己的日志继续由 camctl 管理。

日志线程独自负责模块日志的追加与轮换。每次追加前检查本条记录是否会超过文件阈值，需要时先轮换；保留规定数量的文件并淘汰最旧归档。归档使用 `.1`、`.2` 等后缀，`.1` 是最近归档。记录使用可读的字段和值，截断时包含 `[truncated]`；实际文件大小与归档数量通过集成测试验证。

新日志先按单条长度上限形成有界记录，再按下表判断能否入队。丢弃计数和文件故障状态保存在内存中。

| 文件日志状态 | 队列能否容纳本条记录 | 处理 |
| --- | --- | --- |
| 可用 | 能 | 入队后继续原调用，由日志线程写入 |
| 可用 | 不能 | 丢弃这条新日志，累计丢弃数量，不等待磁盘写入 |
| 已停用 | 任意 | 放弃本条日志，继续原调用，保留内存故障状态 |

日志线程处理队列和文件时，按下表处理故障与拥塞恢复。文件通道已经停用后，不再适用“队列恢复可用”的补记规则。

| 文件日志状态 | 观察到的事件 | 处理 |
| --- | --- | --- |
| 可用 | 此前有丢弃记录，队列恢复可用 | 安排记录丢弃数量；只有记录成功入队后，才扣除它所覆盖的计数 |
| 可用 | 首次发现打开、追加或轮换等文件操作明确失败 | 停用本次运行的文件日志，在内存保留故障信息 |
| 已停用 | 仍有排队日志 | 放弃无法写入的日志，释放相应队列空间，保留内存故障状态 |

队列拥塞、截断和文件故障允许造成诊断丢失，模块继续接收计划、管理子进程和领取文件。日志故障处理自身也须有界。主机断电后，尚在内存中的日志、丢弃计数和故障状态可能丢失；业务恢复仍由 camctl 按其持久化记录完成。

## 建议的内部组织

以下按职责给出划分建议，不固定源文件数量或内部函数名。

| 部分 | 接收什么、产生什么 | 主要协作者 |
| --- | --- | --- |
| 公开入口与参数保存 | 接收初始化参数和计划路径，返回本地结果或完成领取 | 模块状态、输入队列、日志队列 |
| 命令选择与重试判断 | 接收进程事件、提交结果和时间，决定下一步启动及计数变化 | 内部状态、时钟、进程操作接口 |
| POSIX 进程操作 | 接收程序与参数，提供进程编号、输出、退出及启动错误 | 系统接口 |
| CLI 结果检查 | 接收完整 stdout 和退出结果，产生受约束的结果分类 | yyjson、公共 CLI 协议 |
| 同步文件领取 | 接收部署目录，遍历并逐项移动，提供诊断 | 文件操作接口、日志队列 |
| 日志处理 | 接收有界诊断，处理队列、截断、轮换及通道故障 | 文件操作接口 |

建议将可独立判断的命令与重试逻辑和实际系统操作分开，以便用测试替身控制失败与时间。内部状态分别记录 camctl 是否曾开始运行，以及本次尝试创建的子进程是否已经结束，并保留无法确认的情况；这两项不能都用一个空进程编号代替。

## 构建、交付与测试

### 交付内容

交付源码、公开头文件、CMake 构建文件及完整接入示例，默认构建静态库。第三方可以链接静态库，也可以把源码纳入现有工程。工具链匹配时可附预编译 arm64 静态库；源代码交付仍是基础。

构建目标分别组织模块、独立终端演示和测试。默认生产构建只需要生产依赖，启用测试后才引入 cmocka。终端演示使用同一个公开接口，参数填写、计划递交和同步领取都应能直接作为第三方参考。

### 单元测试

采用 cmocka 和手写测试替身。替身放在进程、时钟和文件操作等稳定的协作者接口处，受真实接口约束。以生产函数的独立行为为单位，优先断言返回值和其拥有的状态；命令参数、次数和顺序本身属于契约时，检查对应交互。

重试测试通过模拟时钟推进时间，通过进程替身指定启动失败、输出及退出结果。同一用例内不启动真实子进程、不实际等待，也不访问真实文件系统。公开单实例形式不要求所有内部判断都依赖全局变量；建议让判断函数接收其所需状态，便于隔离测试。

重点补充本页新增的分类：串行提交等待、等待期间共享次数耗尽、当前提交占用容量、接收拒绝后原队列保持、stdout 超限继续读取、日志队列拥塞和文件通道停用。原有首次计划、合并启动及文件移动分类仍按行为规格验证。

### 集成测试与目标验证

组件单元测试和集成测试分别放在 `apps/host-demo/tests/unit` 与 `apps/host-demo/tests/integration`，由 CTest 分别执行。跨组件测试位于根 `tests/integration`。

| 范围 | 验证内容 |
| --- | --- |
| 模块与真实系统接口 | 线程通知、管道持续读取、启动错误、指定子进程回收、原子移动和同名覆盖 |
| 主程序与模块 | 主程序继续执行自身工作，双方各自取得子进程结果，公开参数在复制后可复用 |
| 提交顺序与重试 | 一个 `run` 与一个 `submit` 并行，提交重试期间后续排队，共享次数和首次计划合并规则 |
| 日志与进程管理 | 慢写入、队列满和文件故障时，进程输出仍被读取，计划和文件调用继续按自身结果处理 |
| 模块与真实 camctl、客户端 | 计划导出与递交、执行、报告领取、客户端处理和累计确认 |
| 目标 arm64 主机 | 编译与链接、真实系统 C 库的启动错误行为、第三方进程回收方式、存储和断电行为 |

测试所用可控 CLI 程序属于进程协作者，用来安排输出、退出与故障；与真实 camctl 的组合仍须单独验证。目标系统编译成功不代替目标集成测试，普通进程中断不代替真实断电验证。

## 实现约定与目标核验

公开配置成员及合法范围见[接入说明](../../apps/host-demo/README.md#配置范围与日志)。路径最多 4095 字节，领取时的文件名列表最多占 16 MiB，JSON 解析使用由 stdout 上限推导的有限内存池。初始化中途失败会清理已经建立的资源；成功初始化之后，模块持续运行。

终端演示的命令为 `submit <绝对路径>`、`claim`、`logs` 和 `help`。`submit` 后整段内容作为路径，不在终端命令内额外加引号；启动参数仍按 shell 规则处理引号。具体调用和构建方式见[终端示例](../../apps/host-demo/README.md#运行终端演示)。

进程创建错误、标准流重定向、主程序子进程归属、持续输出、初始化失败清理及日志故障均有开发环境验证，证据范围见[验证记录](verification.md)。部署时仍须使用实际 arm64 Ubuntu 18.04 工具链和第三方链接参数重新编译，验证其信号、描述符、子进程回收及目标存储的断电行为。发现实际平台无法满足契约时，先报告具体证据并补齐设计。
