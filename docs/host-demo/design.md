**规格状态：第一版讨论确认稿，2026-09-17，尚未实现。** 本页定义 `apps/host-demo` 的交付范围、对外行为和验收条件。公共 CLI 协议、业务状态和目录所有权分别引用其责任专题；函数名、内部文件划分和构建方式属于实现设计。

## 目标与交付范围

本组件使用 C，面向 Linux，交付可由第三方现有主程序直接调用的接入模块，以及使用同一模块的终端演示程序。第三方保留自己的主程序，将初始化、收到计划和准备传输三个时机接到模块入口。模块完整封装 camctl 的进程管理和待传文件领取，减少第三方需要理解的协议与协调逻辑。

本地演示用于验证真实 CLI 调用、进程结果和文件交接，并作为第三方接入参考。部署目标是嵌入式 Linux 主机；本地软件验证也在 Linux 环境进行。源代码、构建配置及组件测试位于 `apps/host-demo`，跨组件测试位于根 `tests/integration`。

| 责任方 | 承担的工作 |
| --- | --- |
| 第三方主程序 | 接收外界输入，保存完整计划文件；决定传输时机，处理 `processing` 文件的实际传输、传输完成后的删除及失败残留 |
| 接入模块 | 接收计划路径；内部使用工作线程管理 camctl 子进程、解释会话结果、交接后续启动并有限重试；按主程序调用同步领取文件 |
| 终端演示程序 | 将终端操作转换为模块调用，展示本地诊断，供人工演练和集成测试驱动 |
| camctl | 校验和受理计划，调度设备、保存业务状态、恢复工作、维护报告及发布完整文件 |
| 客户端 | 导出计划，校验并保存收到的报告和产物，依据业务证据确认受理及维护累计确认 |

实际传输的协议、时机及失败恢复属于第三方。模块的文件操作责任在文件进入 `processing` 后完成。业务结果以 camctl 的状态报告为依据，模块的调用返回和本地诊断只表达本地处理事实。

## 运行模型与共同不变量

主程序随主机上电启动，实际部署中持续运行直到主机断电。主机可能在任何时刻断电，没有可依赖的退出通知、清理步骤或固定供电时长；相机独立供电。运行条件遵守[运行环境与协作分工](../architecture/system-context.md)。

模块在同一主程序进程中初始化一次，工作线程持续驻留。某次 `run` 结束只改变执行会话状态，模块继续接收计划与领取调用。待启动标记、异步交接和自动重试计数保存在内存中；已经受理的业务恢复依据由 camctl 持久化。

必须保持以下不变量：

1. 同一模块对同一部署最多管理一个尚未退出的 `run`；后续 `run` 等旧进程实际退出后才启动。
2. `run` 长期运行或等待未来任务时，模块仍能推进后续计划提交、读取子进程输出和处理进程结束。
3. 主程序只调用业务入口；`run`、`submit`、`needs_run`、待启动标记和重试预算全部由模块处理。
4. 模块只回收自己创建的子进程，保持主程序已有的信号处理、工作目录、环境变量和标准输入输出的使用方式。
5. 文件领取由主程序显式触发，和当前 camctl 是否运行独立。同步领取期间，工作线程继续推进进程管理。
6. 模块调用失败或诊断通道故障通过本地结果或可用诊断表达，不能结束主程序或解释为业务任务失败。
7. 临时交接、子进程数量、输出缓冲及诊断保留必须有界；达到上限时明确表达本地无法继续接收或处理，不能静默丢弃后宣称已接收。

主机再次上电后重新初始化模块并获得新的重试预算，发起首次执行会话。camctl 核实历史与实际设备、文件状态后继续符合资格的工作。文件已经进入 `processing` 的，继续由主程序管理。

## 对外调用契约

以下是语义入口；C 函数名、结构体和错误值在实现设计中确定。

| 入口 | 输入 | 调用完成与输出 | 后续责任 |
| --- | --- | --- | --- |
| 初始化 | 部署配置，可选的首次计划路径 | 建立模块资源并接下首次启动责任后返回；本地建立失败时明确返回失败 | 工作线程执行首次启动、监控及适用重试 |
| 递交计划 | 已保存计划文件的绝对路径 | 复制路径并接下本地处理责任后及时返回；无法接收时明确返回失败 | 工作线程启动提交进程并处理会话交接 |
| 领取文件 | 初始化时确定的实际交接目录 | 同步完成本轮尽力领取后返回；调用方不消费领取成败或数量 | 主程序按自己的流程处理 `processing` |

初始化和递交计划的成功返回，只证明模块建立或接下了本地责任，不证明 CLI 已成功启动、计划已受理或动作已执行。异步故障由模块保留诊断；业务确认继续经过报告协议。主机断电时，尚未由 camctl 可靠保存的输入不能仅凭模块曾接收而保证恢复。

### 计划文件

调用方提供完整写入并关闭的文件，短期内保留，但具体删除时机由调用方决定。模块取得路径字符串的独立副本，文件的内容、存续和删除仍由调用方管理。后续读取以实际文件状态为准。

camctl 负责读取与校验输入。文件不存在、打开失败或读取中断按[输入计划文件读取失败](../architecture/cli-commands.md#输入计划文件读取失败)记录，由 CLI 继续判断会话职责。模块不能仅凭文件路径或不完整内容推断请求身份或受理结果。后续裸 `run` 依据状态库恢复，客户端依据[确认与重送规则](../architecture/plan-acceptance.md#客户端确认与重送)补送尚未确认的请求。

### 部署配置

模块需要取得 camctl 程序位置、所选 CLI 配置来源、实际 `ready` / `processing` 路径，以及本页规定的自动重试参数。CLI 使用同一运行账户和配置来源；交接路径、权限和同一文件系统条件按[部署联调样例](../architecture/deployment-example.md#一确定本地配置)核实。

具体配置载体由实现设计确定，必须从部署的权威配置取得实际值。camctl 的默认值和覆盖规则继续由[本地配置](../architecture/configuration.md#本地配置的加载与更新)定义，不能在接入模块另行维护一套可能漂移的完整默认值。配置在当前运行期间固定，更新遵守部署流程。

状态库和运行目录由部署人员通过[显式初始化](../architecture/initialization.md)准备。模块初始化表示建立本进程的接入能力，不承担状态数据库建库职责。主程序尝试校时的时机继续服从运行环境约定，camctl 自行验证时间可信性。

## 计划路由与进程交接

### 调用路由

| 输入时机 | 首次计划路径 | 当前 `run` | 内部调用 |
| --- | --- | --- | --- |
| 初始化 | 未提供 | 尚未启动 | 裸 `run` |
| 初始化 | 已提供 | 尚未启动 | `run <plan-path>` |
| 初始化之后递交计划 | 不适用 | 正在初始化、运行或收尾 | `submit <plan-path>` |
| 初始化之后递交计划 | 不适用 | 当前没有进程，包括等待重试或预算耗尽 | `submit <plan-path>` |

首次会话的启动责任成立后，后续输入按后两行处理，不因观察到暂时没有 `run` 而绕过提交协议。新输入的异步处理不能等待已有 `run` 全部完成。

### 首次输入与执行启动目标

初始化携带计划路径时，模块保存这份首次输入的交接责任。创建或执行明确失败不会消费这份责任；只有可靠确认此前未启动，才能在后续启动中继续附带原路径。确认已经启动或启动事实无法确认时，后续按下表区分。自动重试预算耗尽只停止自动尝试；当前主程序仍运行时，后续新的合法接管要求可以再次提供启动机会。

后续输入仍各自通过 `submit` 处理；它们产生的执行启动要求与首次启动责任按下表合并。表中的“可启动”还须满足旧进程已经退出和下文的启动条件。

| 执行启动时的首次输入状态 | 可启动时使用的命令 | 责任处理 |
| --- | --- | --- |
| 首次带计划调用尚未尝试，或此前尝试均可靠确认未启动，原路径交接责任仍存在 | `run <原计划路径>` | 同一次启动交接首次输入并驱动状态库中已经保存的其他工作 |
| 初始化未提供计划路径 | 裸 `run` | 驱动状态库工作 |
| 首次带计划调用已经成功启动过 | 裸 `run` | 后续执行从持久化状态恢复，首次输入不因响应丢失被重新附加 |
| 首次带计划调用是否已开始运行无法确认，相关进程已经确认结束 | 裸 `run` | 保留输入处理未知的诊断；后续重送由客户端依据受理证据决定 |

例如首次 `run A` 明确启动失败、等待重试期间，B 通过 `submit B` 保存并返回 `needs_run: true`，模块合并为一次 `run A`。A 由这次会话处理，B 从状态库接管。新接管要求触发的这次启动按正常启动计数；再次启动失败后，后续自动尝试继续使用共享预算。A 的文件是否仍可读取由 camctl 按输入文件契约判断。

主机断电后，内存中的未启动输入责任不构成持久化恢复依据；客户端继续按受理证据决定重送。

### 结果判断

每个子进程分别收集 stdout 最终结果、stderr 诊断和实际退出状态，完整采用[stdout 与退出状态](../architecture/cli-commands.md#stdout-与退出状态)的决策表。分段读到的数据须组合后判断；最终消息已经到达但进程尚未退出时，继续等待实际结束。

结构合法但未知的 `reason` 按合法会话错误保留诊断。计划被拒绝、输入读取失败或某个动作失败，都不能由模块自行推断为会话失败。收到错误或结果丢失也不能推断此前的事务已回滚。

输出读取随工作线程持续推进，避免任一子进程因管道写满而阻塞。缓冲达到上限时必须保留溢出诊断并继续处理通道；被截断的最终结果不能判为合法成功。诊断存储故障不能阻止继续排空管道和跟踪进程。

### 待启动责任

待启动标记表示已经取得合法、成功结束的 `submit` 返回的 `needs_run: true`。多个这样的要求可以合并；`false`、其他提交的错误和旧 `run` 的失败均不清除已有标记。

| 新观察到的事件 | 当前状态 | 处理 |
| --- | --- | --- |
| `submit` 正常成功，`needs_run: false` | 任意 | 不新增启动要求，保留已有要求 |
| `submit` 正常成功，`needs_run: true` | 已有 `run` 尚未退出 | 设置或保留待启动标记，继续监控旧进程 |
| `submit` 正常成功，`needs_run: true` | 当前没有 `run` | 合并要求，按“首次输入与执行启动目标”发起一次 `run` |
| 旧 `run` 实际退出 | 已有待启动标记 | 按“首次输入与执行启动目标”发起一次 `run`，其启动责任优先于同一目标的异常重启计时 |
| 后续启动成功 | 正在消费对应待启动责任 | 消费发起本次启动前已合并的标记；发起启动之后新增的要求仍须保留 |
| 后续启动明确失败 | 已有待启动标记 | 保留责任，按自动重试预算有限处理；不能无间隔反复尝试 |
| `submit` 已运行但异常结束或返回合法 `error` | 任意 | 保留诊断和已有待启动责任；该次响应不授予新的成功接管判断 |

进程是否存在由模块管理的实际子进程状态判断，业务工作和接纳资格由 camctl 按[会话接管协议](../architecture/protocol-session.md#会话接管协议)判断。模块消费合法结果，不访问业务数据库或自行实现接纳锁探测。

## 有限自动重试

### 预算与计时

每次模块初始化后，共用一份自动重试预算，默认最多 **3 次**，固定等待间隔默认 **5 秒**；次数和间隔可配置。该预算覆盖 `run` 的异常重启，以及 camctl 调用明确未成功启动后的再次启动。多个输入和进程共用预算，不按每次异常、每个文件或每个子进程重新分配。

首次启动、正常输入触发的首次 `submit`、由新的合法 `needs_run` 要求触发的启动不消耗自动重试次数。只有由失败触发的再次尝试才消耗预算：实际尝试前占用一次，创建失败、执行失败或成功均不退还。一次运行成功不重置计数。

失败已确认且旧进程已结束后，使用单调钟计量等待；等待期间继续处理输入、输出和领取调用。间隔到达还须满足预算及对应启动资格。主机断电使内存预算和计时结束，下次上电建立新范围。

### 失败分类与重试目标

| 调用事实 | 分类与目标 |
| --- | --- |
| 可靠确认 CLI 程序未成功启动，例如创建进程失败或取得明确的执行失败证据 | 在预算内重试原调用；原调用携带计划路径时沿用同一路径 |
| 已运行的 `run` 被信号终止，或最终输出与退出状态按公共协议判为异常 | 在预算内重新启动裸 `run`，从持久化状态恢复 |
| 已运行的 `run` 合法返回 `error` 且退出码为 `1` | 保存诊断；该错误自身不新增自动重试，已有待启动责任继续处理 |
| 已运行的 `run` 正常成功 | 不新增异常重试；后续启动由待启动责任决定 |
| 已运行的 `submit` 返回错误、异常结束或结果无法确认 | 保存诊断和已有待启动责任；不自动重送该次输入 |
| 无法确认 CLI 是否已经开始运行 | 不能使用“明确未启动”分支重送输入；按实际可取得的进程和结果证据处理 |

这一区分同时适用于首次带计划的 `run`：明确未启动时可以重试原路径；已经运行后异常结束时只重新启动裸 `run`。模块不把进程异常转换成“该计划尚未受理”。

对同一待启动 `run`，正常接管要求与异常恢复要求合并为一次实际启动，命令目标仍须保留上节规定的首次输入责任。已有合法接管要求触发启动时，取消同一目标的异常重启计时，不重复启动或预先扣减异常预算。明确启动失败后，后续自动尝试仍消耗共享预算。

### 启动条件

下表按从上到下的顺序判断；每次实际尝试重新检查当前条件。

| 条件 | 行为 |
| --- | --- |
| 对应旧进程尚未确认退出 | 继续跟踪实际进程，保持最多一个 `run` 的约束 |
| 存在新的合法接管启动责任，可与同一 `run` 的异常恢复合并 | 发起一次接管启动；失败后转入有限自动重试 |
| 仅由失败触发后续尝试，预算已耗尽 | 记录预算耗尽，停止自动尝试，保留实际诊断和尚未兑现的接管责任 |
| 仅由失败触发后续尝试，有预算，间隔尚未到达 | 保持等待，推进其他工作 |
| 仅由失败触发后续尝试，有预算，间隔已到达且目标可启动 | 占用一次预算并尝试启动 |
| 没有接管或重试责任 | 保持待命 |

保留的待启动标记不能在启动失败后无限触发免费尝试。预算耗尽后仍可接收新输入；后续新的合法 `needs_run: true` 可以建立新的正常启动机会。下次上电仍有首次启动入口。已运行但结果未知的输入，由客户端按原请求身份和受理证据决定重送。

## 同步领取文件

### 调用时机与范围

主程序决定准备处理待传文件时调用领取入口。模块同步完成一轮有限处理后返回，主程序随后按自己的时机处理 `processing`。该入口不返回要求主程序处理的领取结果或数量，过程诊断由模块保留。

一次调用完整枚举一次 `ready`，收集本轮待移动文件，随后逐个处理。枚举并非原子快照；枚举期间或之后新发布的文件，不保证属于本轮，后续调用可继续领取。本轮不反复扫描至目录为空。空目录是合法情况。

领取对象是 `ready` 中按目录协议发布的完整文件，包括报告、普通交付和异常诊断文件。模块使用实际文件名，不解析业务内容、推导报告覆盖范围或重命名交付文件。部署提供的目录应满足[文件交接要求](../architecture/file-handoff.md#发布原子性)。

### 移动及同名覆盖

每个文件使用同一文件系统内的原子移动，从 `ready` 移到 `processing`；目标存在同名文件时，以本次 `ready` 文件原子替换目标。源文件名和内容保持不变，移动成功后源目录不再保留该文件。不能将跨文件系统的复制后删除解释为满足该契约。

单个文件的移动成功就是领取边界，多文件不要求整体原子完成。成功项保留在 `processing`，后续失败不使其回到 `ready`。模块不以数据库记录或报告正文作为允许主程序领取的附加条件。

报告身份继续服从[报告不可变规则](../architecture/status-reports.md#报告不可变)：同一报告的 ID、内容和文件名固定，新状态报告使用新 ID 和新文件名。不同报告可以同时位于 `processing`；同名替换规则不改变报告身份或累计确认语义。

### 并发与失败分类

camctl 可以在模块枚举后替换报告或撤回交付。模块必须根据实际操作结果表达事实，不能将“枚举过”解释为“已经领取”。

| 操作及可确认的状态 | 本轮行为 |
| --- | --- |
| 目录可访问，枚举成功且没有文件 | 结束本轮 |
| 目录无法访问，枚举失败，或发生其他影响整批操作的目录故障 | 保留诊断，结束本轮；枚举未完整结束时不开始按残缺列表移动 |
| 源文件存在，目标没有同名文件，移动成功 | 文件由主程序接管，继续下一项 |
| 源文件存在，目标已有同名文件，替换移动成功 | 目标成为本次领取文件，继续下一项 |
| 交接目录仍可靠可用，明确确认枚举过的源文件已经消失 | 记录该项未领取，继续下一项；不推断消失原因或传输结果 |
| 单个文件移动明确失败，例如该文件访问失败或目标对象不兼容 | 记录文件、操作和实际原因，继续其余文件 |
| 单项结果无法可靠确认 | 保留已知事实和未知结果，继续独立且仍可可靠处理的其余文件；不把该项记成成功 |
| 处理期间发现影响整批的目录故障 | 停止本轮，保留已经完成的移动和实际诊断 |

整批故障和单项故障按实际失败范围区分，不能只凭一个错误号把目录消失归为正常的源文件撤回。失败项留待后续由主程序发起的领取机会按当时状态处理；模块不建立自动搬运循环。

领取和 camctl 的报告替换或交付撤回由实际原子操作决定先后。模块先移动成功时，文件进入主程序所有权；camctl 先撤下文件时，该源路径可能已经不存在。进入 `processing` 的文件按[目录所有权](../architecture/file-handoff.md#processing)处理。

运行期间的移动成功与突然断电后的目录持久性分别验证。文件系统接口及同步方式由实现结合目标存储环境落实，不能仅凭进程终止测试宣称断电落盘保障。重启后以实际目录状态和 camctl 自身恢复规则继续，不从文件缺失推断客户端已收到。

## 与主程序共存及诊断

进程工作线程负责模块自己的句柄、输出收集、退出判断和重试计时；同步领取路径独立推进文件操作。实现应避免在领取期间持有进程管理所需的长时间锁，避免日志存储阻塞进程输出消费。

诊断保留本地已知事实，包括进程启动失败、最终结果异常、合法会话错误、重试及预算耗尽、文件枚举和移动失败。错误至少能定位相关调用或文件、失败操作及实际原因；未知结果如实表达。领取入口无需调用方读取诊断来决定是否传输。

日志路径、保留上限和输出方式在实现设计中确定，模块和 camctl 的诊断责任分别管理；camctl 已有日志遵守[运行日志](../architecture/logging.md)。诊断机制采用有界保留，故障处理本身不形成无界重试或递归记录，也不能夺用主程序的标准输出。

同一部署的模块实例、主程序的子进程回收方式及目标文件系统能力需要在真实集成中核验。接入代码只管理自己创建的子进程；第三方主程序也须保持这些子进程的退出结果可由模块取得。具体共存方式由接入实现和联调验证。

## 终端演示与全流程验证

独立演示程序使用与第三方相同的模块。启动时提供部署参数和可选的首次计划路径，随后通过终端操作递交新计划或触发同步领取。命令名称和参数语法在实现设计中确定，含空格及非 ASCII 字符的路径须能无损交接。

演示运行期间可以观察模块诊断。领取后的文件位于实际 `processing` 目录，供人工或跨组件测试按既有客户端入口使用；文件的名称和字节遵守公共协议。

全流程按以下可观察结果验收：

| 步骤 | 执行方与可观察结果 |
| --- | --- |
| 准备 | 部署人员确定配置、显式初始化状态库，按既定流程将设备能力说明交给客户端 |
| 导出 | 客户端生成计划并导出文件，保留原请求身份 |
| 递交 | 演示程序将文件路径交给模块，模块驱动真实 camctl |
| 执行 | camctl 保存受理与执行事实，报告及适用产物发布到 `ready` |
| 领取 | 终端显式触发移动，文件进入 `processing`，主程序调用返回 |
| 客户端处理 | 从 `processing` 取得报告与适用产物，经客户端既有入口校验、合并和展示 |
| 确认 | 后续计划携带有效累计确认，再经同一模块递交；camctl 按报告协议吸收 |

相机尚未到位时使用受驱动契约约束的替身；真实设备能力、目标存储断电行为和第三方传输仍分别通过实际联调验收。

## 验收要求

### 单元测试

以有独立语义的生产函数为单元，使用受真实接口约束的进程、时钟和文件操作替身。验证本页各决策表的有效分区，重点包括：

- 首次有无计划、后续输入时有无 `run` 的路由，以及未来任务仍在等待时继续接收输入。
- 公共 stdout 与退出状态组合；分段完整结果、截断、额外输出、未知合法错误原因及 `submit` 成功结果缺少 `needs_run`。
- 多次 `true` 合并、`false` 不清除已有要求、旧进程错误退出仍保留要求、启动失败后保留责任但限制重试。
- 默认预算和配置覆盖；`run` 异常与调用明确未启动共用预算，尝试失败也占用次数，成功不重置，预算耗尽后仍接受新输入。
- 原调用明确未启动时保留路径；已运行的 `submit` 结果未知时不重送；已运行的带计划 `run` 异常后使用裸 `run`。
- 正常接管与异常计时同时存在时合并；等待期间的新输入不会被阻塞，也不会重复启动或超额占用预算。
- 首次计划尚未成功启动时，后续提交产生执行要求仍携带首次路径；预算耗尽后新接管要求也不丢失该责任；首次调用已经成功启动后的恢复使用裸 `run`。
- 文件为空、移动成功、同名覆盖、源文件消失、单项失败、整批故障及结果未知的处理；成功项不回滚，诊断不伪造成功。
- 输出与诊断达到上限时的处理，以及诊断故障不改变已有业务或领取事实。

单元测试不启动真实进程或访问真实文件系统。优先断言结果与模块拥有的状态；启动次数、目标命令、只回收所属子进程和原子移动等属于本模块的副作用契约，可据此验证交互。

### 集成测试

组件测试放在 `apps/host-demo/tests/integration`，使用真实进程、管道、线程和文件系统。可控 CLI 测试协作者用于精确安排输出、退出和失败时机；与真实 camctl 的组合放在根 `tests/integration`。

| 协作边界 | 验收内容 |
| --- | --- |
| 主程序与模块 | 模块运行时其他主程序工作可继续；其他子进程由原调用方回收；信号处理、工作目录和环境保持原约定 |
| 模块与 CLI 进程 | 双通道持续读取、实际退出后判定、长时间 `run` 与新 `submit` 并行、明确执行失败与运行后异常的区分 |
| 进程恢复 | 可控同步点覆盖 `submit` 与旧 `run` 收尾先后、异常退出、合法错误、启动失败、待启动要求及预算交叉组合 |
| 模块与文件系统 | 真实原子移动和同名替换，源名消失、目标字节完整、不同报告并存；单项失败后继续，目录故障后结束 |
| 领取与进程管理 | 领取耗时或失败期间，工作线程仍能消费输出、提交新计划和管理会话结束 |
| 模块与 camctl | 真实输入失败仍按业务报告表达；报告发布、替换、领取和取消竞争遵守实际所有权 |
| 客户端、模块与 camctl | 按上节完整链路验证请求身份、报告完整性、业务结果及累计确认，不用模块成功返回替代受理证据 |

竞争测试通过可控同步点安排先后，不能仅靠随机等待。分别覆盖枚举之后新文件发布、报告撤下之后领取、领取之后取消、部分文件已移动时处理被中断。恢复验证以已提交业务事实和实际文件位置为依据。

目标存储环境另行验证突然断电后的文件和目录状态；设备替身测试和普通进程结束测试不能替代真实设备与断电验收。

## 实现设计与交付核验

正文规定行为，以下事项由实现设计结合代码和部署落实：C 接口名称及类型、源码划分、线程与子进程 API、JSON 解析依赖、配置读取方式、资源上限数值、日志载体、终端命令语法、构建及交付形式。资源上限和依赖清单须有唯一权威来源，具体选择不得改变调用语义或引入主程序需要自行处理的 CLI 状态机。

实施前核验目标 Linux 工具链、实际配置和目录、原子替换能力，以及第三方现有的子进程回收方式；形成可直接编译并接入的示例和明确运行说明。若发现已确认行为在实际环境中无法满足，先报告具体事实并补齐设计，再实施相关部分。

本规格完成不表示真实 CLI、设备、断电或第三方链路已经验收；完成情况以相应实现和验证证据记录。
