## 目标与交付范围

本组件使用 C，面向 Linux，提供接入模块和使用该模块的终端演示程序。第三方保留现有主程序，在启动、收到计划、准备传输文件这三个时机调用模块。模块负责管理 camctl 进程和领取待传文件，使第三方可以直接复用代码。

本地演示使用同一个模块验证真实 CLI 调用、进程结果和文件交接。部署目标是嵌入式 Linux 主机，本地软件验证也在 Linux 环境进行。源代码、构建配置及组件测试位于 `apps/host-demo`；客户端、模块与 camctl 之间的集成测试位于根 `tests/integration`。

| 程序或模块 | 负责的工作 |
| --- | --- |
| 第三方主程序 | 接收外界输入，保存完整计划文件；决定何时传输，传输 `processing` 中的文件，并处理传输完成后的删除和失败后留下的文件 |
| 接入模块 | 接收计划文件路径；使用内部工作线程启动和监控 camctl 子进程，读取结果并安排后续启动和有限重试；主程序调用领取入口时，同步移动待传文件 |
| 终端演示程序 | 将终端命令转换为模块调用，展示本地诊断，供人工操作和集成测试使用 |
| camctl | 校验和受理计划，调度设备，保存计划与执行结果，恢复未完成的任务，生成报告并发布完整文件 |
| 客户端 | 导出计划，校验并保存收到的报告和产物，根据报告确认计划是否受理，并维护累计确认 |

实际传输的协议、时机及失败后的处理由第三方负责。模块完成文件领取后，文件位于 `processing`，后续由主程序处理。计划受理和执行结果以 camctl 的状态报告为依据；模块的返回值和本地诊断只说明模块自身的处理情况。

## 本文使用的对象和术语

| 名称 | 本文中的含义 |
| --- | --- |
| 主程序 | 第三方持续运行的 C 程序；本地演示程序使用相同的模块调用方式 |
| 工作线程 | 接入模块在主程序进程内创建的线程，负责管理 camctl 子进程 |
| 子进程 | 模块为执行一条 camctl 命令而创建的操作系统进程；创建了子进程，不等于已在其中成功启动 camctl 程序 |
| `run` 进程 | 已经开始执行 `camctl run` 的子进程，负责处理已受理的计划、恢复未完成的任务和生成报告 |
| `submit` 进程 | 已经开始执行 `camctl submit` 的子进程，负责处理本次计划输入，并判断是否需要再启动 `run` |
| 状态数据库 | camctl 使用的 SQLite 数据库，保存已受理的计划、动作状态、业务历史和报告记录；数据库的具体内容由 camctl 管理 |
| 待启动标记 | 模块在内存中保存的标记，表示已经收到有效的 `needs_run: true`，还需要启动一次 `run` |
| 自动重试次数 | 模块因启动失败或 `run` 异常结束而再次尝试启动的次数；首次调用及正常提交引起的启动不计入此次数 |

本文所说的“从状态数据库恢复”，是指 camctl 读取其中保存的记录，据此继续执行计划、核实设备状态和处理尚未完成的报告。接入模块通过启动 camctl 完成这些工作，不直接读写状态数据库。

## 运行方式与基本约束

主程序随主机上电启动，持续运行直到主机断电。主机可能在任何时刻断电，没有可依赖的退出通知、清理步骤或固定供电时长；相机独立供电。运行条件见[运行环境与协作分工](../architecture/system-context.md)。

模块在主程序进程中初始化一次，工作线程随后持续运行。某次 `run` 进程结束后，模块仍接收新计划和文件领取调用。模块已接收但尚未处理的计划路径、待启动标记和自动重试次数保存在内存中；已受理计划及其恢复所需的信息由 camctl 写入状态数据库。

必须保持以下约束：

1. 对于同一套部署，模块最多管理一个尚未退出的 `run` 进程。启动下一个 `run` 前，必须确认前一个已经退出。
2. `run` 长期运行或等待未来任务时，模块仍能提交新计划、读取子进程输出和处理子进程退出。
3. 主程序只调用模块提供的入口。`run`、`submit`、`needs_run`、待启动标记和自动重试全部由模块处理。
4. 模块只回收自己创建的子进程，保持主程序已有的信号处理、工作目录、环境变量和标准输入输出的使用方式。
5. 主程序显式调用领取入口时，模块才移动文件。无论 camctl 当前是否运行，这个入口都可调用；同步移动文件期间，工作线程继续管理子进程。
6. 模块调用失败或记录诊断失败时，通过返回值或仍可用的诊断通道说明情况，不能因此结束主程序，也不能将这些故障解释为业务任务失败。
7. 等待处理的输入、子进程数量、输出缓冲和诊断文件都必须有资源上限。达到上限时明确说明无法接收或处理，不能丢弃输入后仍返回已接收。

主机再次上电后，主程序重新初始化模块，自动重试次数从零开始，并启动首次 `run`。camctl 读取状态数据库，核实设备和文件的实际状态，再按调度与恢复规则继续处理。已经位于 `processing` 的文件仍由主程序管理。

## 对外调用契约

下表定义三个调用入口的行为。公开 C 接口及返回值见[实现设计](implementation.md#三个调用入口)。

| 入口 | 输入 | 何时返回、返回什么 | 返回后由谁继续处理 |
| --- | --- | --- | --- |
| 初始化 | 部署配置，可选的首次计划文件路径 | 模块资源建立完成、首次启动已安排给工作线程后返回成功；模块资源无法建立时返回失败 | 工作线程启动和监控 camctl，并按规则重试 |
| 递交计划 | 已保存计划文件的绝对路径 | 模块复制并保存路径后及时返回成功；无法接收时返回失败 | 工作线程调用 `submit`，读取结果并安排必要的 `run` |
| 领取文件 | 使用初始化时确定的交接目录 | 同步完成本轮文件移动后返回；主程序无需接收成败结果或数量 | 主程序按自己的流程处理 `processing` 中的文件 |

初始化或递交计划返回成功，只表示模块已安排启动或保存了待处理路径，不表示 camctl 已成功启动、计划已受理或动作已执行。工作线程后续遇到故障时记录诊断；计划受理与执行结果仍通过状态报告确认。如果主机断电时 camctl 尚未将输入保存到状态数据库，就不能仅凭模块曾接收路径而保证恢复这份输入。

### 计划文件

调用方提供完整写入并关闭的文件，短期内保留，具体删除时机由调用方决定。模块复制路径字符串；文件内容、保留和删除仍由调用方管理。camctl 读取时，文件可能已经不存在或无法访问。

camctl 负责读取与校验输入。文件不存在、打开失败或读取中断时，按[输入计划文件读取失败](../architecture/cli-commands.md#输入计划文件读取失败)记录错误并继续处理本次会话。模块不能仅凭文件路径或不完整内容推断请求身份或受理结果。

后续不带计划路径的 `run` 根据状态数据库中的记录恢复任务。客户端根据[确认与重送规则](../architecture/plan-acceptance.md#客户端确认与重送)补送尚未确认受理的请求。

### 部署配置

模块需要取得 camctl 程序位置、CLI 使用的配置来源、`ready` 和 `processing` 的实际路径，以及自动重试参数。模块启动的 CLI 使用同一运行账户和配置来源。部署人员按[部署联调样例](../architecture/deployment-example.md#一确定本地配置)核实目录路径、访问权限，以及交接目录是否位于支持原子移动的同一文件系统内。

第三方在部署时准备目录和需要的配置文件，主程序通过初始化参数提供 camctl 程序位置、交接目录和可选的 camctl 配置文件路径。部署人员保证主程序提供的交接目录与 camctl 实际使用的目录一致。camctl 的默认值和覆盖规则由[本地配置](../architecture/configuration.md#本地配置的加载与更新)定义，模块使用传入的路径；参数归属见[实现设计](implementation.md#参数由谁提供)。当前运行期间配置保持固定，更新按部署流程进行。

部署人员通过[显式初始化](../architecture/initialization.md)准备状态数据库和运行目录。主程序初始化接入模块时，只建立模块在本进程中需要的资源。主程序按运行环境约定尝试校时，camctl 自行验证时间可信性。

## 计划递交与进程管理

### 模块怎样选择命令

| 调用时机 | 是否提供首次计划路径 | 当前 `run` 的状态 | 模块启动的命令 |
| --- | --- | --- | --- |
| 初始化 | 未提供 | 尚未启动 | `run` |
| 初始化 | 已提供 | 尚未启动 | `run <plan-path>` |
| 初始化之后递交计划 | 不适用 | 正在初始化、执行或收尾 | `submit <plan-path>` |
| 初始化之后递交计划 | 不适用 | 当前没有 `run` 进程，包括等待重试或重试次数已用完 | `submit <plan-path>` |

模块初始化时安排首次 `run`。此后递交的计划都通过 `submit` 处理，不能因为暂时没有 `run` 进程就改变这个规则，也不能等已有的 `run` 结束后才提交新计划。

### 首次启动时如何处理计划文件

初始化时提供了计划路径，模块就保存该路径，准备交给首次 `run`。如果创建子进程失败，或者可以确认子进程没有成功启动 camctl，模块仍保留路径，后续可以再次尝试。已经启动过或无法确认是否启动过时，按下表处理，不能一律重新附带原路径。

自动重试次数用完后，模块停止自动尝试。如果之后的 `submit` 正常成功并返回 `needs_run: true`，模块仍可据此再次启动 `run`。

后续计划始终通过 `submit` 处理。如果这些提交要求启动 `run`，模块还需检查首次计划是否尚未交给 camctl。每次实际启动前，都要确认上次尝试创建的子进程已经退出，并满足下文的启动条件。

| 首次调用的情况 | 这次使用的命令 | camctl 或模块怎样处理 |
| --- | --- | --- |
| 尚未尝试首次带计划的调用，或可以确认此前每次尝试都未成功启动 camctl；模块仍保存着首次计划路径 | `run <原计划路径>` | camctl 读取和校验首次计划文件，并按调度与恢复规则继续处理状态数据库中已有的计划和未完成的报告 |
| 初始化时没有提供计划路径 | `run` | camctl 根据状态数据库中的记录，继续执行计划、核实设备状态和处理未完成的报告 |
| 首次带计划的 `run` 已经开始运行过 | `run` | camctl 从状态数据库恢复任务；即使首次调用的响应丢失，模块也不再次附带原计划路径 |
| 无法确认首次带计划的 `run` 是否已经开始运行，但模块为执行这条命令创建的子进程已经确认结束 | `run` | 模块记录无法确认输入是否已处理；客户端根据受理证据决定是否重送 |

例如，A、B 分别是两份计划文件的路径。模块启动 `run A` 失败，并且可以确认 camctl 没有开始运行。等待重试期间，`submit B` 已将 B 的处理结果保存到状态数据库，正常成功返回 `needs_run: true`。模块此时只启动一次 `run A`：camctl 读取 A，同时可以继续处理数据库中已保存的 B。

这次启动由 B 的提交结果触发，不计入自动重试次数。如果启动再次失败，后续自动尝试仍受同一个次数上限限制。A 是否仍可读取，由 camctl 按计划文件读取规则判断。

模块保存的路径只在内存中。主机断电后，客户端仍需根据报告中的受理证据决定是否重送，不能假定模块下次启动时还记得这些路径。

### 怎样判断子进程结果

模块分别从每个子进程的 stdout（标准输出）读取最终结果，从 stderr（标准错误输出）读取诊断，并取得实际退出状态，按[stdout 与退出状态](../architecture/cli-commands.md#stdout-与退出状态)的决策表判断。分多次读到的输出要组合后再检查。最终消息已经收到、但子进程尚未退出时，仍不能判定本次调用已经结束。

错误消息的结构符合协议、但模块不认识 `reason` 的值时，仍按会话错误记录。计划被拒绝、输入读取失败或某个动作失败，不一定表示 camctl 会话失败。错误消息或响应丢失也不能证明此前的数据库事务已经回滚。

工作线程持续读取子进程输出，避免子进程因管道写满而阻塞。输出缓冲达到上限时，模块记录溢出情况并继续读取管道；被截断的最终结果不能判为成功。诊断无法保存时，也必须继续读取管道并监控子进程。

### 何时启动下一个 run

`submit` 正常成功并返回 `needs_run: true` 后，模块设置待启动标记，表示还需要启动一次 `run`。多个这样的要求可以合并。另一次提交返回 `false` 或发生错误，以及当前 `run` 失败，都不会清除已有标记。

| 模块观察到的事件 | 当前状态 | 模块怎样处理 |
| --- | --- | --- |
| `submit` 正常成功，`needs_run: false` | 任意 | 不新增启动要求，保留已有要求 |
| `submit` 正常成功，`needs_run: true` | 已有 `run` 尚未退出 | 设置或保留待启动标记，继续监控该 `run` |
| `submit` 正常成功，`needs_run: true` | 当前没有 `run` | 合并启动要求，按“首次启动时如何处理计划文件”选择命令并启动 |
| 当前 `run` 已经退出 | 已有待启动标记 | 启动下一个 `run`；如果此前安排了异常重启，就合并为这一次启动 |
| 新的 `run` 成功启动 | 本次启动用于满足此前的待启动要求 | 清除本次启动之前已合并的要求；开始启动之后收到的新要求继续保留 |
| 新的 `run` 明确启动失败 | 已有待启动标记 | 保留标记，按次数和间隔限制重试 |
| `submit` 已经开始运行，但异常结束或返回符合协议的 `error` | 任意 | 记录诊断，保留已有待启动标记；不能从这次错误结果中推断还需要新增一次启动 |

模块根据自己创建的子进程判断 `run` 是否还在运行。是否有未完成的业务任务、当前 `run` 是否还会接收新任务，由 camctl 按[会话接管协议](../architecture/protocol-session.md#会话接管协议)判断。模块根据合法响应决定后续启动，不直接查询业务数据库或探测 camctl 的接纳锁。

## 有限自动重试

### 重试次数与等待间隔

每次模块初始化后，所有自动重试共用一个次数上限，默认最多 **3 次**；每次重试前固定等待 **5 秒**。次数上限和等待间隔可配置。这个上限同时限制 `run` 异常后的重启，以及 camctl 明确未成功启动后的再次尝试，不按输入文件、异常或子进程分别计算。

以下启动不计入自动重试次数：模块初始化后的首次启动、每份新输入对应的首次 `submit`，以及新收到的有效 `needs_run: true` 所要求的启动。

由失败触发的再次尝试才计入自动重试次数。模块在实际尝试前将计数增加一次，无论这次尝试成功还是失败，都不扣回。某次 camctl 调用成功，也不把已经使用的重试次数清零。

模块确认上次尝试失败，且那次尝试创建的子进程已经退出后，才开始计算等待时间；如果上次没有创建出子进程，就从确认失败时开始计算。等待使用单调钟，即不受系统时间校正影响的计时来源。等待期间，模块继续接收输入、读取子进程输出和响应文件领取调用。

等待结束后，模块还须检查剩余次数及下表的其他条件。主机断电后内存中的计数和计时不再保留；下次上电初始化时重新开始计算。

### 哪些失败可以重试

| 调用情况 | 模块怎样处理 |
| --- | --- |
| 可以确认 camctl 没有成功启动，例如创建子进程失败，或明确得知子进程无法执行 camctl 程序 | 在次数上限内重试原命令；原命令带计划路径时继续使用该路径 |
| `run` 已开始运行，后来被信号终止，或输出与退出状态按公共协议判为异常 | 在次数上限内启动不带计划路径的 `run`，让 camctl 从状态数据库恢复任务 |
| `run` 已开始运行，返回符合协议的 `error`，退出码为 `1` | 记录诊断，不因这次错误新增自动重试；已有待启动标记继续按规则处理 |
| `run` 正常成功结束 | 不新增自动重试；是否再次启动取决于已有的待启动要求 |
| `submit` 已开始运行，后来返回错误、异常结束或结果无法确认 | 记录诊断，保留已有待启动标记，不自动重送这份输入 |
| 无法确认 camctl 是否已经开始运行 | 保留这个未知状态；不能按“确认未启动”的规则重送输入，应根据能取得的进程和输出信息处理 |

这些规则也适用于首次带计划路径的 `run`：确认未启动时可以重试原命令；已经运行后异常结束时，后续重启使用不带计划路径的 `run`。模块不能因为进程异常就认定计划尚未受理。

如果模块既收到了有效的 `needs_run: true`，又安排了 `run` 异常后的重启，就将两者合并为一次启动。是否携带首次计划路径仍按前面的表判断。模块取消同一个 `run` 的重试等待，不重复启动，也不扣减自动重试次数。如果这次启动明确失败，后续自动尝试继续计入重试次数。

### 何时发起重试

下表按从上到下的顺序判断，每次尝试前都重新检查。

| 当前情况 | 模块怎样处理 |
| --- | --- |
| 上次尝试创建的子进程尚未确认退出 | 继续监控该子进程；启动新的 `run` 前，还须确认已有的 `run` 已经退出 |
| 新收到有效的 `needs_run: true`，可以合并此前安排的 `run` 重启 | 按提交结果启动一次 `run`；失败后再按自动重试规则处理 |
| 没有新的提交要求，本次只因上次失败而重试，且重试次数已用完 | 记录次数已用完，停止自动尝试；保留诊断和仍未完成的待启动要求 |
| 本次属于自动重试，还有剩余次数，但等待间隔尚未结束 | 继续等待，同时处理其他输入和进程事件 |
| 本次属于自动重试，还有剩余次数，等待间隔已结束，且可以启动 | 将重试计数增加一次，再尝试启动 |
| 没有待启动要求，也没有需要重试的调用 | 保持待命 |

启动失败后，模块不能仅因为待启动标记还在，就反复发起不计次数的尝试。自动重试次数用完后，模块仍可接收新输入；后续 `submit` 正常成功并返回新的 `needs_run: true` 时，仍可启动 `run`。下次上电也会按首次启动规则处理。

输入已经交给 camctl、但结果未知时，由客户端根据原请求身份和报告中的受理证据决定是否重送。

## 同步领取文件

### 何时调用、处理哪些文件

主程序准备处理待传文件时，调用领取入口。模块同步完成这一轮文件移动后返回，主程序随后按自己的时机处理 `processing`。主程序无需接收领取成败或数量，过程中的诊断由模块记录。

每次调用先完整遍历一次 `ready` 目录，收集文件名，再逐个移动。遍历期间目录仍可能变化，因此本次列表不是某一时刻的固定快照。遍历期间或之后新发布的文件，可能要等下一次调用才领取；本次调用不会反复扫描直到目录为空。目录为空时正常结束。

领取范围包括 `ready` 中按交接协议发布的报告、普通交付文件和异常诊断文件。模块保留实际文件名，不解析业务内容、计算报告覆盖范围或改名。部署提供的目录须满足[文件交接要求](../architecture/file-handoff.md#发布原子性)。

### 怎样移动和覆盖同名文件

模块在同一文件系统内，将每个文件从 `ready` 原子移动到 `processing`。目标位置已有同名文件时，用本次 `ready` 中的文件原子替换它。移动保持文件名和内容不变；成功后，该文件不再位于源目录。跨文件系统的复制后删除不能满足这里的原子移动要求。

每个文件移动成功后，就由主程序接管。整批文件不要求同时移动成功。已经成功移动的文件留在 `processing`，后续文件失败时也不搬回。领取不需要额外检查数据库记录或报告正文。

报告仍遵守[内容不可变的规则](../architecture/status-reports.md#报告不可变)：同一报告的 ID、内容和文件名固定，新状态报告使用新的 ID 和文件名。不同报告可以同时保存在 `processing`。同名覆盖不改变报告身份或累计确认规则。

### 并发操作和失败处理

模块遍历目录后，camctl 仍可能替换报告或撤回交付文件。模块必须根据实际移动结果记录诊断，不能因为文件曾出现在列表中，就认为已经领取。

| 实际发生的情况 | 本次调用怎样处理 |
| --- | --- |
| 目录可访问，完整遍历后没有文件 | 结束本次调用 |
| 目录无法访问、遍历失败，或出现影响整批操作的目录故障 | 记录诊断并结束；文件列表尚未收集完整时，不开始移动 |
| 目标没有同名文件，移动成功 | 文件由主程序接管，继续处理下一项 |
| 目标已有同名文件，原子替换成功 | 主程序取得本次移动的文件，继续处理下一项 |
| 可以确认两个交接目录仍可正常访问，但列表中的某个源文件已经消失 | 记录该文件未领取，继续处理下一项；不猜测文件消失的原因或是否已经传输 |
| 单个文件移动明确失败，例如无法访问该文件，或目标位置的对象不能被替换 | 记录文件、失败操作和实际原因，继续处理其余文件 |
| 无法确认某个文件的移动结果 | 记录已知情况和无法确认的结果；其余文件仍可独立处理时，继续移动 |
| 移动期间发现影响整批操作的目录故障 | 停止本次处理，保留已经完成的移动并记录诊断 |

模块要区分影响整批操作的目录故障和单个文件的故障。例如，源目录已经消失时，不能仅凭“找不到文件”的错误就认定 camctl 撤回了某个文件。

本次未移动的文件，在主程序下次调用领取入口时按实际情况处理。模块不会自动反复搬运。领取与 camctl 的报告替换、交付撤回谁先发生，由原子文件操作的实际结果决定：模块先移动成功，文件就归主程序处理；camctl 先撤下文件，模块再移动时可能找不到源文件。后续处理遵守[目录所有权](../architecture/file-handoff.md#processing)。

移动操作已经成功，与突然断电后文件是否仍保存在目标目录，是两个需要分别验证的问题。实现时应结合目标存储环境选择文件操作接口和同步方式。结束进程的测试不能证明断电后数据已经落盘。重启后按实际目录状态和 camctl 的恢复规则继续，不能从文件缺失推断客户端已收到。

## 与主程序共存及记录诊断

工作线程管理模块自己的进程句柄，读取子进程输出，判断退出结果并计算重试时间。文件领取由同步调用单独处理。移动文件期间，不能长时间占用工作线程需要的锁；记录日志也不能阻止工作线程读取子进程输出。

模块记录实际取得的故障信息，包括启动失败、最终结果异常、符合协议的会话错误，以及目录遍历或文件移动失败。模块也记录自动重试的情况和次数是否已用完。诊断至少说明涉及哪次调用或哪个文件、哪一步失败、取得了什么错误信息。无法确认的结果应明确写出。主程序无需先读取这些诊断，再决定是否传输。

模块日志采用独立日志线程和有容量上限的队列，文件路径由主程序提供。默认容量、轮换和故障处理见[实现设计](implementation.md#模块日志)。camctl 自己的日志继续遵守[运行日志规则](../architecture/logging.md)。模块诊断采用有上限的存储方式；诊断失败时，不能无限重试、递归记录错误或占用主程序的标准输出。

真实集成时，需要核实部署中使用的模块实例、主程序原有的子进程回收方式，以及文件系统能力。模块只回收自己创建的子进程，主程序也要保证模块能取得这些子进程的退出结果。实现和联调须验证双方不会互相取走对方负责的子进程结果。

## 终端演示与全流程验证

独立演示程序调用与第三方相同的模块。启动时提供部署参数和可选的首次计划路径，运行期间通过终端命令递交新计划或同步领取文件。具体命令名和参数语法在实现设计中确定，包含空格和中文等字符的路径须能完整传给模块。

演示运行期间可以查看模块诊断。领取后的文件保存在实际 `processing` 目录，人工操作或跨组件测试可以通过客户端现有入口使用这些文件，并保留协议要求的名称和原始字节。

全流程按以下步骤验收：

| 步骤 | 谁做什么、怎样观察结果 |
| --- | --- |
| 准备 | 部署人员确定配置，显式初始化状态数据库，并按既定流程把设备能力说明交给客户端 |
| 导出 | 客户端生成计划并导出文件，保留原请求身份 |
| 递交 | 演示程序把文件路径交给模块，模块启动真实 camctl 处理 |
| 执行 | camctl 保存计划受理和执行结果，将报告及需要交付的产物发布到 `ready` |
| 领取 | 用户在终端触发领取，模块将文件移到 `processing`，处理结束后返回 |
| 客户端处理 | 人工操作或测试程序从 `processing` 取得报告和产物，通过客户端现有入口校验、合并和展示 |
| 确认 | 客户端在后续计划中携带有效的累计确认，模块递交这份计划，camctl 按报告协议保存确认结果 |

相机尚未到位时，使用受驱动接口约束的测试替身。真实设备能力、目标存储断电后的行为和第三方实际传输，分别通过真实环境联调验收。

## 验收要求

### 单元测试

以有独立行为契约的生产函数为单元，使用受真实接口约束的进程、时钟和文件操作替身。根据本页决策表逐项验证，重点包括：

- 首次有无计划、后续递交时有无 `run`，是否选择了正确命令；`run` 等待未来任务时，模块是否仍能提交新计划。
- stdout 与退出状态的各种组合，包括分段输出、截断、额外输出、未知但合法的错误原因，以及 `submit` 成功响应缺少 `needs_run`。
- 多次 `needs_run: true` 是否合并；`false` 或旧进程错误退出是否保留已有要求；启动失败后是否保留标记并限制重试次数。
- 默认重试参数和配置覆盖；`run` 异常与 camctl 未能启动是否共用次数上限，失败的尝试是否计数，成功后是否保留已用次数，次数用完后是否仍能接收新输入。
- 原命令确认未启动时是否保留计划路径；已运行的 `submit` 结果未知时是否避免重送；已运行的带计划 `run` 异常后是否使用不带计划路径的 `run`。
- 新收到 `needs_run: true` 时，是否合并此前安排的异常重启；等待重试时是否仍处理输入，是否避免重复启动或超过次数上限。
- 首次 camctl 尚未成功启动时，后续提交触发的 `run` 是否仍携带首次计划路径；自动重试次数用完后，新提交触发的启动也要保留该路径。首次调用已开始运行后，恢复时使用不带计划路径的 `run`。
- 目录为空、移动成功、同名覆盖、源文件消失、单项失败、目录故障和移动结果未知时的处理；已移动的文件是否保留，诊断是否准确。
- 输出缓冲和诊断存储达到上限时的处理；诊断失败是否保持已经确认的进程和文件结果。

单元测试不启动真实进程，也不访问真实文件系统。优先断言函数结果和模块自身的状态。启动次数、命令参数、只回收所属子进程和使用原子移动属于本模块必须保证的行为，可以验证相应交互。

### 集成测试

组件的集成测试放在 `apps/host-demo/tests/integration`，使用真实进程、管道、线程和文件系统。需要精确控制输出、退出和故障时，使用可控的 CLI 测试程序；模块与真实 camctl 组合的测试放在根 `tests/integration`。

| 参与测试的程序或组件 | 验收内容 |
| --- | --- |
| 主程序与模块 | 主程序能继续执行其他工作、回收自己的其他子进程；信号处理、工作目录和环境保持原约定 |
| 模块与 CLI 子进程 | 持续读取 stdout 和 stderr；进程实际退出后才判断结果；长期运行的 `run` 与新 `submit` 并行；区分未能启动 camctl 和运行后异常 |
| 模块的进程恢复流程 | 控制 `submit` 与旧 `run` 退出的先后顺序，组合验证异常退出、合法错误、启动失败、待启动标记和剩余重试次数 |
| 模块与文件系统 | 原子移动和同名替换后，源路径不再有该文件、目标内容完整；不同报告可以并存；单项失败后继续，目录故障后结束 |
| 文件领取与工作线程 | 文件移动耗时或失败时，工作线程仍能读取输出、提交新计划和处理子进程退出 |
| 模块与 camctl | 输入文件读取失败通过业务报告表达；报告发布、替换、领取和取消并发时，按实际文件位置和操作结果处理 |
| 客户端、模块与 camctl | 按上节完整流程验证请求身份、报告完整性、业务结果和累计确认；模块返回成功不代替计划受理证据 |

测试通过可控制的暂停和恢复位置安排并发顺序，不能仅靠随机等待制造竞争。分别覆盖遍历后新文件发布、报告撤下后领取、领取后取消，以及部分文件已移动时进程中断。恢复结果依据已保存的业务记录和实际文件位置验证。

目标存储环境另行验证突然断电后的文件和目录状态。设备替身测试、普通进程结束测试不能替代真实设备和断电验收。

## 实现设计与部署核验

正文规定必须实现的行为。[实现设计](implementation.md)记录技术选型、公开 C 接口、线程与提交顺序、部署参数、资源上限、日志和构建交付方式。源码划分、内部接口及终端命令语法结合代码和部署环境落实。资源上限和依赖清单应各自有唯一的维护位置；具体实现应保持本页调用规则，让模块自行管理 CLI 状态和后续启动。
