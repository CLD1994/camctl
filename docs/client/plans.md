# 计划编辑与交接

[客户端设计入口](README.md) · [文件导入与结果查看](files-and-status.md)

本页定义一份客户端计划从草稿到导出、人工递交及后续操作的关系。计划 JSON 和主机受理规则分别由[输入契约](../architecture/plan-input.md)与[请求身份及受理](../architecture/plan-acceptance.md)定义。

## 计划入口

网页以“计划”为主要入口，在同一入口中提供“草稿”和“计划记录”两个页签。用户准备新任务时进入草稿，交接文件后进入计划记录查看受理、执行与文件接收结果。

| 页签 | 内容 | 主要操作 |
| --- | --- | --- |
| 草稿 | 尚未导出的可编辑计划，包括未填写完整或尚未通过校验的内容 | 新建、继续编辑、校验并导出 |
| 计划记录 | 客户端已保存的导出请求，以及通过有效报告取得的历史计划 | 查看交接与执行情况；有原请求时再次下载或复制为新草稿 |

例如，用户在草稿中编辑“明天录像”，首次导出时保存了原请求，随后在计划记录中查看这份只读请求并标记已递交。导入主机报告后，受理和执行信息更新到同一条记录，不因为新收到一份报告就新增一份相同计划。

### 导出后的页面变化

首次导出可靠保存原请求后，该项进入计划记录，结束原草稿的编辑阶段。网页下载尚未完成或失败，不会把它重新变成可编辑草稿；用户可以从计划记录再次下载。若原请求尚未成功保存，则仍按草稿和导出失败处理，不显示为已导出。

用户从计划记录选择“复制为新草稿”时，创建独立的编辑内容并进入草稿页签。原计划记录继续保留，新草稿之后导出使用新的请求身份。已经导出的内容不能因切换页签而恢复编辑，也不能因复制而修改原执行意图。

### 计划记录以哪些资料为依据

客户端可能先导出计划，再收到报告；也可能在恢复较旧备份后，通过同步报告第一次取得某个历史计划。两类资料按可靠的请求身份及报告中的计划关联合并，不能只凭相同计划名称判断是同一条记录。

| 有本地原请求 | 已应用报告提供对应计划 | 展示与操作 |
| --- | --- | --- |
| 有 | 无 | 展示已导出及实际存在的人工递交记录；受理、拒绝或输入错误按已有报告证据分别说明，没有执行依据时不补造计划执行状态 |
| 有 | 有 | 在同一条记录中结合本地交接信息与主机受理、执行事实，保留原请求下载和复制入口 |
| 无 | 有 | 展示报告已经提供的计划、动作及产物等信息，明确没有本地导出记录；不补造导出时间、人工递交记录或原请求文件 |
| 无 | 无 | 不建立计划记录；已有草稿或尚未关联到计划的文件诊断按各自来源展示 |

只根据报告取得的计划，仍可用于查看结果和按对象准备后续取回、取消或源产物清理。原请求下载及基于原请求的复制操作以本地确实保存了原请求为前提，不能把当前合并的执行状态直接当作原始导出文件。

报告必须已通过校验并按覆盖规则成功应用，才能成为计划展示的业务依据。无法应用的缺口报告和单纯的文件名、错误诊断片段，都不能用于拼造计划内容。导出、人工递交、主机受理和执行状态始终分别表达，具体字段依据见后文。

## 编辑当前计划

用户在一份草稿中添加所需动作，填写名称、执行时间、参数及引用。拍摄动作根据当前启用的设备能力选择参数类型；表单与 JSON 使用同一份参数和校验规则。允许一份计划包含多个动作，例如“录像 A”和引用它的“取回 A”。

按既定规则将用户选择的本地时间转换为计划中的 UTC 时间。取回和源产物清理需要明确的执行时间；所有动作仍须通过自身及公共输入校验。参数编辑的细节以[客户端计划编辑](../architecture/client-editing.md)为准。

拍摄参数预设按[设备关联规则](presets.md#预设与设备的关联)提供给当前动作。用户在动作编辑区[保存、应用或更新预设](presets.md#在动作编辑区使用预设)，应用后的参数属于当前草稿，导出时仍须符合对应设备当前已启用的参数契约。

## 自动保存草稿

编辑短暂停顿后，客户端自动保存当前内容，页面显示保存中、已保存或保存失败。每份草稿保存最新一次成功写入的编辑内容，之后重新打开时恢复它，继续编辑。具体保存边界见[草稿、预设与原请求](storage-and-recovery.md#草稿预设与原请求的保存)。

| 当前编辑内容或保存结果 | 行为 |
| --- | --- |
| 内容完整且合法 | 保存草稿；导出时仍检查准备导出的最新完整内容 |
| 必填项尚未填写、参数不合法或 JSON 尚未写完 | 保存当前编辑状态，并提示输入问题；补齐和校验通过后才能导出 |
| 保存尚未完成 | 显示保存中，不能把请求已经发出当作保存成功 |
| 保存失败 | 保留页面中的当前输入并提示失败，不显示为已保存 |

未完成的 JSON 文本、尚未形成有效数值的控件输入，也属于草稿内容。保存不能只记录上一份合法参数对象而丢失用户正在编辑的内容。自动保存的具体延迟和内部表示在后续设计中落实。

例如，用户添加了录像动作但还没填写时间，可以先离开已成功保存的草稿，之后补齐时间再导出。

## 导出与原请求

首次导出检查当前完整计划，通过后可靠保存原请求，再提供文件下载。原请求包含固定的 `request_id` 和计划正文；原请求正文与可独立更新的累计确认字段之间的边界遵守[计划正文与 ACK](../architecture/plan-acceptance.md#计划正文与-ack-独立处理)。

导出记录只读，提供以下操作：

| 操作 | 产生的结果 |
| --- | --- |
| 再次下载 | 使用原请求身份和正文；可按当前可靠保存的覆盖附带合格的 `last_report_id` |
| 复制为新草稿 | 创建独立可编辑草稿；之后导出使用新的请求身份 |

浏览器下载未完成时，已经可靠保存的原请求仍可再次下载。导出记录不能因为重新下载而悄悄成为新请求。

例如，用户已经导出“10:00 录像”，希望调整为“11:00 录像”，应复制成新草稿修改。新请求代表另一次执行意图，原 10:00 请求仍可能被递交或已经受理。对原任务的取消通过相应取消计划处理。

收到报告后，按照请求关联更新受理及执行信息。同一个请求即使执行失败，重送仍对应原实例；修正后需要重新执行的内容使用新请求。受理证据及重送规则见[客户端确认与重送](../architecture/plan-acceptance.md#客户端确认与重送)。

## 记录人工递交

导出后，用户可以手工将文件交给传输部门，再点击可选的“标记已递交”。客户端分别展示以下事实：

| 信息 | 依据 |
| --- | --- |
| 已导出 | 客户端已经生成并保存原请求 |
| 已递交给传输部门 | 用户手动记录 |
| 主机已受理 | 已成功接受的报告提供该请求的受理证据 |
| 计划与动作执行结果 | 报告中的执行状态及结果 |

人工递交标记是交接记录。用户未填写它时，报告导入仍照常更新受理与执行事实。客户端不根据下载文件推断已递交，也不根据递交标记推断主机已收到。

全局计划状态继续采用 `pending`、`running`、`completed`，与上述客户端交接信息分开。

### 标记时间与更正

人工递交标记关联本地已保存的导出请求，当前状态为“未标记递交”或“已标记递交”。用户点击“标记已递交”并成功保存后，记录本次标记的时间；误点时可以“清除递交标记”。

例如，用户上午把文件交给传输部门，下午才回来点击按钮。页面显示下午的“标记时间”，这表示用户何时作出记录，不能作为实际交付或主机收到文件的时刻。“未标记递交”也只说明客户端没有这项当前标记，不能据此断言用户没有交过文件。

| 当前标记 | 操作 | 成功保存后的结果 |
| --- | --- | --- |
| 未标记递交 | 标记已递交 | 更新为已标记，记录本次标记时间 |
| 已标记递交 | 再次请求标记已递交 | 返回已有标记及时间，重复操作不刷新时间 |
| 已标记递交 | 清除递交标记 | 更新为未标记，当前标记时间一并清除 |
| 未标记递交 | 再次请求清除递交标记 | 保持未标记，不产生虚假的标记时间 |
| 任一状态 | 再次下载原请求，或导入报告 | 保留人工标记及其时间；报告独立更新受理和执行信息 |

清除后再次标记，记录新的标记时间。标记状态与对应时间一起保存，后端确认成功后才显示操作完成；明确写入失败时保留原记录并提示，提交结果未知时根据后端实际记录核实，不能把页面已经切换显示当作保存成功。

清除只更正客户端人工记录。对主机任务的取消继续通过新计划中的 `cancel_task` 表达；人工标记操作不修改原请求正文、主机受理证据或动作执行结果。

## 从结果准备后续操作

在计划详情中，用户可以选择对象，将“取回”“取消”或“清理源产物”加入选定的一份草稿。客户端从对象记录填入准确的来源和目标引用，用户检查名称、时间及参数后统一导出。

例如，用户将录像 A 的取回动作和原视频 B 的清理动作加入同一份草稿，分别填写执行时间，再导出一份计划。目标草稿由用户选择；需要时可新建草稿，已有草稿内容保留。

取回、取消和清理仍通过主机收到并执行新计划完成。页面操作用于准备输入，不能先行改写原任务状态或把源产物标记为已清理。

需要补齐主机状态时，使用[准备状态同步](files-and-status.md#准备状态同步)入口。客户端默认根据可靠保存的报告选择补齐起点，并提供完整同步选项；用户同样选定已有或新草稿，检查并导出。

“清理源产物”按计划、动作范围或明确的 `output_ids` 操作，具体范围由[清理规则](../architecture/output-cleanup.md)定义；它与管理个人电脑上的已接收文件是不同职责。取消目标及资格由[取消规则](../architecture/task-cancellation.md)定义。

## 验收依据

- 草稿首次导出后进入只读计划记录；原请求保存失败时保留草稿状态，下载失败但原请求已保存时仍可再次下载，不产生另一份执行意图。
- 按计划记录的资料来源表，验证本地原请求与报告的先后到达、仅报告取得的历史计划，以及没有可靠计划依据的情况。报告更新不重复创建记录，同名不同请求不合并，未知交接信息不被补造。
- 从有原请求的计划记录复制到新草稿，检查原记录与新编辑内容独立；切换页签不改变请求身份、内容只读要求或主机执行状态。
- 保存未完成草稿后重新打开，仍保留当前输入；保存失败有明确提示，导出不会使用旧的合法对象替代当前输入。
- 再次下载保留原请求身份与正文；复制并导出形成新请求，原记录和执行意图保持可追溯。
- 按人工标记转换表验证标记、清除、重复操作及再次下载；标记与时间一致保存，重复标记不刷新时间，清除后重新标记取得新的标记时间。写入失败或提交未知时显示实际结果，不冒充成功。
- 递交标记只更新人工交接信息；有无标记均可依据有效报告确认受理，清除标记不取消任务、不修改原请求或已有执行结果。
- 将多个详情页操作加入指定草稿，原有内容保留，引用正确，导出执行公共和动作自身校验。
- 对新请求的导出、原请求重送及累计确认的组合，使用[协议样例](../architecture/client-protocol-examples.md)验证行为。

## 自动预览及范围操作

新建计划默认开启自动获取预览。开关状态是编辑意图，客户端维护每个适用拍摄的独立取回动作；能力重新加载成功时自动协调未导出草稿，失败时保留，完整规则见[自动获取预览文件](automatic-previews.md)。已导出正文固定，复制计划继承开关并形成独立草稿。

计划及动作详情均提供按整个来源准备取回或清理的入口；新草稿内支持显式选择当前计划，历史计划使用 `plan_instance_id`。普通取回为非预览产物并优先对应修复成品；清理则包含来源内全部正式产物。ID 操作保持精确选择，不自动扩大。来源未结束时按主机等待规则执行，不在客户端把等待解释为无文件或已清理。
