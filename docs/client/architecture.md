# 职责、数据与关键操作

本文文件接收、保存、关联、完整性核验和恢复规则同时适用于图片与视频；具体预览及多产物浏览遵守[动作摘要与媒体查看](result-browsing.md)。视频播放规则仅适用于视频。

[客户端设计入口](README.md) · [数据保存与恢复](storage-and-recovery.md) · [MVP 验收](acceptance.md)

客户端的网页和本地后端运行在用户个人电脑上。网页负责让用户编辑和查看，后端负责可靠保存并处理业务数据。例如，视频完整上传后，即使用户关闭网页，仍在运行的后端也会继续核验；下次打开网页，用户看到的是后端已经保存的结果。

本页把各使用流程中的职责和保存要求放在一起，供实现时检查它们是否衔接完整。技术组合以[客户端部署](../architecture/client-deployment.md#客户端的本地部署)为准，动作、报告和相机参数协议以各自公共专题为准。内部模块、HTTP 路由名称及数据库表结构在实施设计中确定。

## 网页、后端与共享规则

| 部分 | 职责 | 与其他部分怎样协作 |
| --- | --- | --- |
| 浏览器网页 | 展示三个入口，保留用户正在编辑的内容，提供表单和 JSON 编辑、文件选择、进度与结果展示 | 将当前输入交给后端；依据后端返回的保存、校验与执行状态更新页面 |
| 本地后端 | 管理 SQLite 与持久化文件，加载能力说明，保存草稿和原请求，处理报告合并、确认进度与视频核验 | 向网页提供实际启用规则、业务记录及处理结果；提供符合条件的文件下载和视频播放所需内容 |
| 共享规则与类型 | 保持固定协议结构、拍摄参数校验配置和错误转换一致 | 网页用于及时反馈，后端用于校验实际保存或导出的输入；报告类型与结构规则从公共 Schema 读取或生成 |

网页中的“校验通过”不能代替后端检查实际提交的内容。后端已经保存的事实也不能被网页临时状态覆盖，例如页面还显示“处理中”，但一份报告已经提交成功，重新打开后应展示成功结果。

拍摄能力由后端当前启用的说明提供。一次计划导出检查使用同一份启用说明，避免不同动作采用不同次加载的规则；加载结果及说明不可用时的功能范围遵守[能力说明加载](../architecture/client-deployment.md#启动与重新加载)。

## 各类信息以什么为准

客户端同时处理用户自己的操作和主机返回的结果。它们有不同来源，需要分别保存、关联和展示。

| 信息 | 依据与保存要求 | 使用边界 |
| --- | --- | --- |
| 正在编辑但尚未保存的内容 | 网页中的当前输入，包括不完整 JSON 和暂时非法的控件值 | 页面如实显示未保存或保存失败；不能把上一次合法内容当成本次输入 |
| 已保存草稿与预设 | 后端保存的各自最新内容，遵守[编辑内容保存规则](storage-and-recovery.md#草稿预设与原请求的保存) | 重开页面后恢复；应用预设复制参数，草稿与预设的后续修改彼此独立 |
| 已导出原请求 | 首次导出时保存的请求身份与固定正文 | 再次下载复用原请求；累计确认按独立规则处理，修改执行意图使用新草稿和新请求 |
| 人工递交信息 | 用户为导出记录保存的当前标记状态与标记时间 | 标记时间表示何时记录；可以更正标记，主机受理和执行仍以报告证据为准 |
| 主机的计划、动作、产物和交付状态 | 已通过校验并按覆盖规则成功应用的报告 | 按可靠身份关联；本地操作不能先行改写主机结果 |
| 已接受报告与完整覆盖进度 | 可靠保存的[原文件名与原始字节](storage-and-recovery.md#已接受报告的原始内容)，以及同一次事务保存的接收与原文关联、实体合并结果和确认资格 | 原文用于核对输入；接收与覆盖记录决定重复导入、后续合并、同步起点和累计确认 |
| 导入诊断与历史缺失提示 | 实际文件处理结果，以及已保存的缺口诊断 | 失败或缺口诊断不成为成功报告；缺失提示依据已知目标和实际完整覆盖判断 |
| 本地视频与核验结果 | 已登记的完整文件、当前可用性，以及同有效报告映射的大小和摘要比较结果 | 决定等待、核验、播放和下载；与主机的交付发布状态分别表达 |

记录通过已有身份关联：导出请求使用 `request_id`，报告中的实体使用各自 ID，交付文件以完整 `file_name` 匹配。名称用于帮助人阅读，不能代替身份。详细规则分别见[计划记录来源](plans.md#计划记录以哪些资料为依据)和[视频关联与核验](files-and-status.md#视频关联与核验)。

客户端数据库及文件保存的是个人电脑上的资料。嵌入式主机的执行历史、动作恢复及源产物管理由 camctl 负责，见[全局持久化基础](../architecture/README.md#持久化与配置基础)。

## 网页与后端之间的关键操作

下表定义各操作需要传递的业务信息及成功依据。具体接口命名可以在实现中确定，但两种网页入口执行同一项操作时，应使用相同的后端规则。

| 操作 | 输入 | 可观察结果与成功依据 |
| --- | --- | --- |
| 初始化及读取启动状态 | 后端已配置的数据位置；用户的显式初始化选择 | 返回未初始化、可用或具体故障；只有完整保存初始化事实后才进入正常使用 |
| 读取或重新加载设备说明 | 重新加载请求；说明文件来自固定部署路径 | 返回实际启用说明及本次加载结果；文件校验失败时按原有说明是否可用分别处理 |
| 保存、打开草稿 | 草稿身份与当前编辑内容 | 保存完成后返回已保存结果；内容不完整仍可保存，不能伪报整份计划合法 |
| 保存、应用或更新预设 | 所选设备、拍摄动作类型、参数和明确操作 | 保存或更新以合法参数可靠写入为成功；应用把具体参数放入当前草稿 |
| 校验与首次导出 | 准备导出的最新完整草稿 | 后端完成全量校验，可靠保存固定原请求后提供下载；失败保留草稿和具体问题 |
| 再次下载或复制原请求 | 已有原请求的身份与所选操作 | 下载返回原身份及正文；复制创建独立草稿，之后导出产生新请求 |
| 标记或清除人工递交标记 | 对应导出记录与用户选择的操作 | 按[标记转换规则](plans.md#标记时间与更正)保存状态和时间，可靠保存后展示结果，独立于主机状态 |
| 导入文件 | 一次选择的文件集合、各文件原名与完整字节 | 返回每份报告及视频的处理进度、保存、校验、关联或失败结果；整批处理遵守报告覆盖关系 |
| 查看计划、导入结果与文件 | 对应记录身份 | 展示后端实际保存结果；满足播放与下载条件时提供相应文件内容 |
| 从已有对象准备后续动作 | 来源对象、操作类型及用户选定的草稿 | 准确填入引用或同步参数，保留草稿原有内容；后续按正常校验、导出及手工递交流程执行 |

读取进度的接口须能让重新打开的网页取得实际结果。视频完整交给后端后，网页连接是否持续存在不决定核验是否继续；后端重启与报告导入中断则分别遵守[恢复规则](storage-and-recovery.md)。

## 保存与后续操作怎样衔接

### 编辑和导出使用当前内容

用户可能修改草稿后立刻点击导出。此时后端必须检查准备导出的最新完整输入，不能直接采用较早的自动保存内容或此前通过校验的参数对象。

草稿保存的反馈应对应它实际保存的内容。如果用户在保存期间又作了修改，较早请求返回成功，只能证明较早内容已保存，不能把新的未保存输入也显示为已保存。实现时需要让编辑内容、保存请求和反馈保持对应。

首次导出需要一起确定原请求及该草稿已经转入只读计划记录的结果。原请求一旦可靠保存，后续下载失败或结果重新查询都继续使用它；网页不能据此再生成另一份执行意图。具体状态见[导出后的页面变化](plans.md#导出后的页面变化)。

### 报告成功应用是一次完整提交

成功接收身份、与已可靠保存原文的关联、业务状态合并、完整覆盖进度及确认资格在同一事务保存。报告不能只登记为“已接收”而原文或状态尚未可靠保存，否则用户重试时会把未完成的内容当作重复并跳过。原文保存失败时，本份接收失败；已成功接受的相同报告继续复用原记录与原文。

一批报告逐份提交。后一份失败不会撤销前一份成功，前一份应用后的覆盖又是处理后一份的基础。重新导入仍按当前已保存状态判断，完整规则见[同次导入多份报告](files-and-status.md#同次导入多份报告)。

### 文件和数据库记录需要共同支持结果

视频上传、保存完整、关联报告、核验完成与开放播放是不同结果。文件只是出现在磁盘上，或数据库里只有一个文件名，都不能证明它已经完整保存并可用。

| 准备表达的结果 | 必须具备的依据 |
| --- | --- |
| 视频已完整保存 | 文件字节已保存完整，并有对应的可靠保存记录 |
| 视频已核验 | 完整文件与有效报告映射已完成大小、摘要比较，并可靠保存结果 |
| 可以在网页播放或下载 | 完整文件当前可读取，报告关联和核验均满足[开放条件](files-and-status.md#视频播放与原文件下载) |
| 正确补发已经替换错误副本 | 新文件完整保存且核验通过，替换后的文件关联与核验记录一致，完成结果可以可靠确定 |

替换所需的新文件尚未保存完整，或尚未通过核验时，保留已有副本。保存或替换被中断后，依据文件事实和数据库记录确定结果；无法确认时保留诊断，不把不明文件登记为成功。具体采用临时文件、内部保存路径及数据库事务的顺序，须在实现设计中满足[文件恢复规则](storage-and-recovery.md#后端重启后的文件处理)和[替换规则](files-and-status.md#重复导入同名视频)。

### 请求结果未知时先核实实际保存结果

网页没有收到响应，不等于后端没有保存。例如，首次导出已经保存原请求、报告已经成功应用，页面可能尚未来得及更新。恢复连接后应依据后端记录确认实际结果，再沿用对应下载或重试规则。

数据库无法可靠读取时显示数据故障。不能凭网页缓存、文件名或一次请求超时猜测操作成功，也不能据此将客户端数据重建为空。

## 校验与诊断

输入校验错误应指出对应计划字段、动作或参数，保留用户正在编辑的内容。拍摄参数错误转换由网页和后端共享；固定协议标识及报告结构来自公共契约，避免各处维护不一致的规则。

导入结果按文件展示。错误信息应包含实际处理阶段与已知原因，并保留能够识别输入的文件名及已有报告身份。文件尚未到达、内容校验失败、缺少历史、等待报告和后端无法确认结果分别表达，遵守各专题的状态分类。

界面依据实际证据展示后续操作：草稿可继续修正，已保存原请求可再次下载，报告中断可重新选择原批文件，完整视频按恢复规则继续核验。相关检查与端到端场景见[MVP 验收](acceptance.md)。
