# 自动获取预览文件

[客户端设计](README.md) · [计划编辑](plans.md) · [全局预览契约](../architecture/preview-obtaining.md)

本页定义客户端如何维护自动预览取回、保存用户意图和展示结果。相机预览图片及预览视频都是正式产物，区别于浏览器把图片缩小显示。主机能力、选择、取消及调度以全局契约为准；本页为待实现的客户端目标设计。

## 开关与派生动作

新建计划默认开启“自动获取预览文件”。开关是用户意图；每个符合条件的拍摄对应的自动取回动作是客户端维护的派生内容。用户通过开关管理，普通界面不要求编辑自动动作的名称、来源、时间或筛选参数。可以查看完整动作及生成参数，但不会因折叠而从导出内容删除。

客户端按当前设备、拍摄类型及参数类型的明确预览支持声明判断。开关开启但没有适用动作时保持开启，显示当前没有适用动作；之后新增符合条件的拍摄时自动生成。自动取回沿用拍摄时间，保留明确自动用途及来源引用，一个拍摄最多一个。手动预览取回及其他普通动作独立管理，不根据名称相似而认作自动动作。

| 开关及能力状态 | 派生内容处理 | 导出 |
| --- | --- | --- |
| 关闭 | 移除自动预览取回，保留全部手动动作 | 按完整计划校验 |
| 开启，能力有效，拍摄选择完整且明确支持预览 | 维护一个对应自动取回 | 拍摄及生成动作全部合法后可导出 |
| 开启，能力有效，参数类型明确不支持预览 | 移除该拍摄的自动取回 | 拍摄按自身规则校验 |
| 开启，设备／拍摄类型／参数类型未选完或输入非法 | 保留未完成输入，不猜测支持；对尚不能可靠判断的既有派生关联保留待核实状态 | 阻止导出未完成计划 |
| 开启，能力加载失败、无法解释或无法可靠取得 | 保留开关及现有自动动作，不解释为不支持 | 阻止依赖该能力的计划导出；恢复有效后自动协调 |

已导出请求保持固定正文；能力变化只影响尚未导出的草稿及新建内容。自动维护不改写用户拍摄参数，不为非法输入补默认值，也不改变手动取回。

## 编辑联动与身份

| 草稿事件 | 客户端处理 |
| --- | --- |
| 开启开关 | 为每个符合条件的拍摄补齐自动取回 |
| 关闭开关 | 删除本草稿自动取回，手动动作保持原样 |
| 新增或复制拍摄 | 判断支持情况，为符合条件的新拍摄创建独立自动取回 |
| 拍摄改名 | 保留自动取回的草稿身份，更新来源引用 |
| 修改拍摄时间 | 同步自动取回时间；未完成时间继续保留且阻止导出 |
| 修改设备或参数类型，仍支持预览 | 更新派生内容，保留自动取回身份 |
| 修改后明确不支持预览，或改为非拍摄类型 | 移除对应自动取回 |
| 删除拍摄 | 删除其对应自动取回 |
| 能力说明成功重载 | 对全部未导出草稿自动协调；支持关系未变时不重复生成或重建身份 |
| 能力说明加载失败 | 保留当前草稿及派生关联，显示故障；恢复有效后协调 |
| 复制计划为新草稿 | 继承开关值，创建独立草稿身份及关联，按当前有效能力协调 |

草稿动作身份不使用可修改名称或数组位置代替；导出时生成协议要求的来源引用。生成名称须满足整份计划唯一性，不改名覆盖用户动作。反复打开、刷新或重新协调同一草稿不得产生重复取回。

自动维护以可可靠解析的编辑内容为依据。JSON 尚未写完或动作身份关联无法确认时，保留用户原文，等待可判定后再协调，不能用自动生成内容覆盖未完成输入。自动动作的派生字段由客户端维护；整份 JSON 替换的关联识别与开关继承须按文末待落实边界确定，不凭动作名称猜测。

## 保存、导出与恢复

开关、拍摄的草稿身份、自动取回关联、当前正文及未完成编辑内容作为同一草稿版本保存。保存失败保留页面状态并提示；响应未知时核实完整版本，不因正文相同而忽略开关或关联变化。

导出必须使用同一份有效能力目录和同一草稿版本完成协调与完整校验，后端独立验证生成动作、唯一关联、时间及用途。若导出期间能力或草稿已变化，重新核实最新一致内容，不能把旧能力下的动作与新拍摄参数拼成请求。可靠保存原请求后，其自动取回动作、来源及请求身份固定，再下载不重新生成。

复制已导出计划时继承当时保存的开关；即使当时没有适用拍摄、正文中没有自动取回，也不能从“零个自动动作”推断开关关闭。因此客户端导出记录应同时保留用于复制的开关资料，该资料不改变固定请求正文。通过报告恢复的记录依靠显式自动用途及关联组织展示，不依赖本地草稿。

开关资料缺失的外部计划如何导入为草稿、如何继承默认值，以及整份 JSON 替换如何处理现有开关，尚需在实现前统一定义。已知关闭不能被默认开启覆盖，未知不能根据动作数量猜测。仅报告取得的记录仍遵守既有原请求可用性规则，不补造原请求或复制依据。

## 计划记录与媒体展示

自动取回默认并入对应拍摄记录；独立动作及 delivery 身份完整保留。用户可以展开技术详情或查看全部动作。手动取回保持独立动作展示。

| 自动取回或本地文件情况 | 默认展示 |
| --- | --- |
| 等待来源、修复、设备或正在取回 | 拍摄记录下显示简短阶段，不伪造实时进度 |
| 主机已经发布，本地尚未收到 | 显示等待接收，与获取成功分开 |
| 本地已可靠核验且可读取 | 展示预览图片或预览视频，折叠正常取回细节 |
| 取回失败、取消或本地文件核验失败 | 突出结果与原因，提供详情；拍摄成功不遮蔽该异常 |
| 报告尚未提供完整关联 | 保留可见的独立记录及待关联说明，不凭名称合并或隐藏异常 |

计划可以汇总已知预览获取完成数、等待数与失败数；汇总须明确基于动作结果还是本地接收，不从增量报告当前子集推算完整总数。自动取回未结束仍是计划未完成工作，隐藏细节不改变计划状态。

显示相机预览时标明其对应原文件；存在修复成品时，说明当前原片预览不代表修复结果。自动取回实际交付修复成品时，显示“修复成品已收到”，关联成品真实 `output_id`，不将其改名为预览产物。后续普通取回仍是独立请求；可提示已有合格本地副本，不能擅自删掉用户明确请求。

媒体导入、精确文件名关联、大小与摘要校验以及恢复沿用[媒体文件流程](result-browsing.md#图片与视频文件流程)。只收到预览不表示原文件已经收到。拍摄与取回的关联用于展示，不能把 delivery 从所属取回动作复制到拍摄实体内。

## 后续操作

用户可在计划、拍摄动作或具体产物上准备取回和清理。普通取回未指定 ID 时排除预览并按原片优先修复成品；按 ID 精确选择。清理按计划或动作包含原文件、预览及修复成品，按 ID 仅处理所选文件。界面使用“取回默认产物”“清理该计划／动作的全部源产物”等准确说明，不能把默认取回标为全部文件。

取消拍摄、组或整个计划由主机联动自动取回，客户端不依赖已收到的取回状态另造取消目标。单独取消自动取回不取消拍摄。已发布文件的撤回结果及已保留正式产物分别展示，不把取消当作源文件删除。

## 验收与实施边界

验证新建默认开启、明确关闭及复制继承、开启但无适用动作、每种编辑联动、反复重载不重复生成、能力故障与恢复、未完成 JSON、保存失败和响应丢失、导出期间版本变化。验证只收到报告时仍能按可靠关联组织记录，部分报告先到不误隐藏动作。

验证取回失败醒目、等待与本地未接收分开、预览已收但原文件未收、修复成品替代、原片预览说明、手动取回独立展示及查看全部动作。按计划／动作／ID 分别验证取回和清理范围，客户端准备操作不提前改写主机状态。

本轮仅更新设计。协议字段、能力缺省语义及多候选选择见[全局实施边界](../architecture/preview-obtaining.md#验收与协议落实边界)；外部计划和整份 JSON 的开关恢复规则尚待明确。客户端代码、根协议 Schema 与协议样例的同步须在这些边界落实后进行，现有实现及测试通过不代表上述新功能已实现。
