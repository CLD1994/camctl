# Hasselblad 无人值守可用性恢复实施计划

## 目标、依据与实施边界

本计划把[未知活动后的无人值守恢复规格](../../camctl/hasselblad-availability-recovery.md)接入正常拍摄、DEVICE 文件获取及重启恢复。旧拍摄失败后，后续有效工作可以在原本地调用收场、固定机身身份核对和新的 doctor 检查通过后继续使用相机；旧拍摄结果、工作文件及报告中的结束未知事实保持。

实施以当前分支的正式规格和生产代码为准；开始每个阶段前核对实际集成基线，并沿生产调用关系调整修改位置。规格中的行为和项目规则是硬性要求；下文建议的模块、新文件位置、内部接口和提交拆分可以调整，不另行固定一种类层次或仓储划分。

当前是开发阶段，直接演进当前数据库、事件和包资源。新环境通过正式 `init` 创建完整结构，不增加旧程序读写、旧事件解释或旧格式运行模式。本能力不包含全仓兼容代码清理，也不包含现场状态转换。已有现场数据库、日志、工作文件、正式产物、交付、客户端状态和待执行计划均保留；它们的部署处理由 H6 单独交接。

本计划按阶段跟踪实现。H1—H4 在该阶段的生产代码和必要隔离单元测试完成后勾选；H5 还要求实际构建并核对软件交付物；H6 只在实际部署交接和人工验收完成后勾选。阶段勾选不表示跨组件集成或真机验收已通过。

用户当前要求不新增或运行集成测试，相关集成测试正在重构。集成测试及安装版组合验证作为独立待办记录，不阻碍 H1—H5 阶段勾选；本轮没有取得的新集成结果不得记为通过。人工流程、部署和真机验证单独归入 H6，未执行时保留未完成状态。

## H1 原责任恢复与公开测试入口

- [x] 完成 H1，并在本节记录实际恢复入口、覆盖对应关系及验证证据。

**当前进度。** H1 实现与必要隔离单元验证完成，交付提交为 `12f14f10`。原恢复入口实际消费统一的恢复资格判定；`PendingCallResult.save` 让原执行者和恢复共同等待原保存，显式重送采用当前冻结申请及原键，已应用结果不被旧快照重放。Python 3.11.17 下的 11 项隔离单元测试通过，Sol 代码评审未发现必须修复的问题。占用释放与报告投影分别验证稳定边界，报告登记使用替身；真实登记、完整会话组合和真机未执行。命令、覆盖映射及证据范围见[专项验证记录](../../camctl/hasselblad-availability-implementation-verification-2026-10-28.md)。

**前置与业务结果。** 原检查必须等待旧 START 的实际本地执行与保存责任收场，因此先取得这一入口的有效证据。这里不需要新可用性操作；旧拍摄仍按原契约失败并保持未知，后续新拍摄仍可被旧限制阻挡。

**实施任务。**

1. 按 H1 原责任分区核对生产入口与隔离单元测试的对应关系，至少区分本地收场边界可靠或缺失、原调用仍在执行、保存回执未知及原结果已保存。验证记录保留测试入口、实际覆盖和剩余缺口。
2. 单元测试经生产公开入口或稳定模块边界验证原身份、原操作键、尝试计数、工作文件与零重放；不得直接构造运行时私有拥有者，也不恢复 `CaptureRuntime.owned` 兼容接口。
3. 生产恢复逻辑只在结果缺失且适用边界可靠时沿原键保存未知；已保存结果按原事实继续，原调用或保存未收场、边界缺失时等待或停止依赖工作。后续 doctor 结果、日志 PASS 或文件存在不能补写原 START 结果。
4. 可靠无效果可以释放；可能启动或输出范围未完成时保留限制；报告保持原动作错误和设备执行状态。需要通过隔离单元测试证明的分区随 H1 验证记录保存。
若生产公开入口暴露缺陷，先修复违反的原契约；涉及未定义语义时按设计缺口规则处理。旧测试装配迁移和安装版故障门的状态见“验证与状态记录”，不属于 H1 阶段完成条件。

**建议修改位置。** 隔离单元测试按责任放在 `apps/camctl/tests/unit/capture`、`apps/camctl/tests/unit/operations` 和 `apps/camctl/tests/unit/reporting`；生产入口核对 [capture/handlers.py](../../../apps/camctl/src/camctl/capture/handlers.py)、[host_photo.py](../../../apps/camctl/src/camctl/capture/host_photo.py)、[operations/recovery.py](../../../apps/camctl/src/camctl/operations/recovery.py)和[会话装配](../../../apps/camctl/src/camctl/bootstrap/capture_assembly.py)。跨组件装配的集成测试目录见单独的组合验收状态；只修改实际确认的缺口。

**完成条件。** H1 生产恢复入口实现原责任收场，H1 必要隔离单元测试通过并在验证记录中保存提交、命令、覆盖和退出码。安装版 missing START、旧测试装配和与新检查相连的零派发组合验证仍单独跟踪；它们既未在本轮执行，也不阻碍 H1 勾选。

**当前进度。** H2 实现及必要隔离单元验证完成，交付提交为 `cb02382f`。固定身份、独立检查、固定目标与全批释放事务、独立守卫、历史归属及公共错误均已有实现，Sol 核对八项生产责任未发现必须修复的问题。定向隔离单元四组分别通过 5、2、2、6 项；合并 H1 后再次核对恢复、驱动、历史及目标守卫，分别通过 11、5、2、2 项。结构用例只隔离非被测前置检查，保留原拒绝断言。真实初始化、事务与历史回放、工具进程及报告组合未执行，不作为阶段勾选门槛。覆盖映射和命令见[专项验证记录](../../camctl/hasselblad-availability-implementation-verification-2026-10-28.md)。

**前置与业务结果。** 需要能够表达“原拍摄仍 UNKNOWN，但已按新检查解除调度限制”的完整事实。在第一次持久化新事实之前，结构、历史解释、独立守卫和合法状态必须同时具备。必要隔离单元测试验证可独立判断的输入、守卫和失败分区；数据库事务与工具组合验证另行记录，不阻碍阶段勾选。

**实施任务。**

1. 从权威登记分配 `CHECK_DEVICE_AVAILABILITY`、检查证据和事件分支，更新当前结构及格式识别。按规格保存检查、固定目标关系、操作关联、预期机身、资源键和活动释放引用；流程状态与次数继续由原操作模型拥有。为同一触发动作与旧活动的唯一关系、同机查询及有界分页设置约束和索引。表名和内部字段名可以调整，事实归属和固定时点不能改变。
2. 同步 SQL、枚举适配、事件构造和校验、历史字段分类、快照范围、正向与逆向恢复及初始状态。检查与目标归触发动作历史，释放归旧动作历史；跨动作的一批事件只有完整事务共同可见。实现首次变更时就能回放，不把历史补接推迟到最终报告阶段。
3. 定义活动状态与占用的完整合法组合。行内约束明确处理 NULL，外键核对引用存在；跨表守卫核对成功尝试、检查目标、固定机身、调用收场、输出范围及当前冲突。保留原可靠未派发、无效果、时间与产物完成、可靠结束等释放路径；新增引用不能让 `ACTIVE` 或公共目录范围持有者借 doctor 放行。
4. 实现公开的检查创建、意图登记、结果消费和终结事务。创建只纳入原动作已失败、可能产生过启动效果、采用 TASK_SCOPE 且满足规格全部条件的 Hasselblad 单张旧活动，固定全体合格目标；登记意图共同增加次数并授予本次实际资格；成功结果、检查完成和所有仍需解除的目标共同提交。全部目标已被其他可靠路径解决时按事实完成；部分目标不再合格时保存真实结果而不部分释放。提交未知按原键核实，不另建责任。
5. 固定预期物理身份与独立观察。首次活动预留或检查创建在调用意图前保存 serial、产品标识和规范资源键；缺失原事实是状态错误，不能用新配置补齐。核对当前重复 serial 绑定规则，增加历史未完成责任与逻辑别名的冲突判断。当前工具路径可以变化，但替代机身不能消费旧责任。
6. 在 Hasselblad 驱动公开独立检查端口，严格执行 `list → info → doctor`。复用受管进程、输出完整性及错误事实接口；整次共享单调期限，不在驱动内部重试。保存每一步的原始双流、实际退出和前序结果，明确 PASS 才形成可用性观察；不改变活动查询能力，也不形成相机重启或采集结束证据。核对结果类型、取消传播、进程升级终止和正式装配。
7. 给 DEVICE 正式源的生产登记、文件身份和定位信息增加由可靠拍摄结果核对的原机身。`open_read` 同时核对原逻辑绑定、固定物理身份、文件名或路径、variant、大小、SHA-256 和偏移。更新当前文件格式及其消费者，不增加旧格式解释分支；HOST 的本地身份和本地处理不增加相机前提。
8. 在公共错误权威登记接入规格规定的两个错误及物理身份绑定原因，联动动作合法状态、逐项失败结构和报告字段依赖。允许合法受理但尚未 START 的准备失败，不用提前写入 running 取得失败保存资格。数字编号与完整类型从登记生成或读取，不在各层另存清单。

4. 在照片缓存交付摘要不符时，保存实际 mismatch、原 READ 收场及已有重拷申请，按原额度完成目标重置，再沿同 copy／delivery 换回原角色相机源。准确区分已分配的新轮与尚需申请的新轮，保留所有适用的累计次数；预算确已耗尽则失败。未知保存先核原键，不重比同步副本、不重选缓存，不改变普通 HOST 或视频重拷规则。
5. 照片缓存读取已完整结束、摘要不符且原相机绑定无法继续时，分别保存原读取失败和所属交付失败。若重启时仅前者已提交，先核实原结果键、时刻、错误及身份；直接设备源沿原路径，照片缓存按原产物、H、角色页和 READ_END 历史关联解析原设备来源，再接续既有绑定失败事务。普通 HOST 副本和错误关联仍拒绝，后到取消及已有终态沿原规则收场。仓储仅对原读取结果已可靠核实、将返回既有只读收场的照片申请使用历史核验，边界固定到原读取结果完整事务的首事件；活跃首次保存继续核当前资格，已提交业务键继续核原事务。恢复不新增读取、重拷或交付，不改变拷贝来源、固定摘要和累计预算。定向验证覆盖该提交间隙及来源分类，真实事务与进程中断另行记录。

**前置与边界。** 本步骤以 H5 已验交付为基础，在用户指定的独立目标环境执行真实计划；现场修复后重新构建、核对并安装后续发行物。本次范围包括真实相机拍摄、下载及用户执行的重启观察，不接续或改写旧实例，不重排旧计划。设备运行假设已由正式规格确定，不另加人工确认才能每次继续的机制。

1. 先交付两种环境处理方式及其具体影响。独立新环境保留旧环境和数据，采用正常 `init`；它不继承旧动作 ID、计划或确认水位，也不证明原现场动作已经接续。若要求继续原实例，则另行制定一次离线状态转换，覆盖备份、原历史、固定身份、文件关系、待处理责任、完整性与失败恢复；该工作不加入日常旧格式分支。
2. 新旧环境切换前，核对同机原 host、camctl、工具进程及输出读取已实际收场。一个状态库的资源守卫不能协调第二个独立环境或外部相机软件。新环境接管设备后，旧环境保持停止，防止后来再次执行同一业务。
3. 逐项交接旧待执行计划：是否已经派发或可能有未知效果、原窗口是否仍有效、引用哪些原产物和客户端关系。需要新工作时使用明确的新请求，不重用旧请求身份、延长旧窗口或直接改状态获得拍摄机会。未经单独状态转换，新环境不得声称继续旧计划。
4. 在选定的独立目标环境核对 Python、SQLite、受管进程、当前初始化、工具版本与真实机身绑定。使用真实 doctor、后续拍摄及 DEVICE 下载验证接受的运行假设，保留原活动 UNKNOWN 和文件；实际供电由部署侧执行和记录，camctl 不推断发生过重启。
5. 依据实际上电时间、工具耗时和拍摄准备时间配置既有 query 次数、间隔、期限及准备提前量，记录实际配置与预期覆盖。验证可用、持续不可用、身份改变、供电恢复晚于窗口及有限失败退出；默认值不能承诺任意断电周期。目标性能、真实媒体、ARM 环境和物理断电持久性分别记录，不外推 Linux 替身结果。

本步骤的交付为实际部署收据和验证结论，或明确的未执行清单与环境处理决定。没有选择原实例接续时，不开展现场转换；这不会阻塞新环境的软件实施。

## 状态、失败与恢复的实施核对

下表是各步骤的横向检查入口，完整判定仍以正式规格为准。实现时沿“发现 → 原资格 → 调用或不调用 → 持久结果 → 报告或交付”核对生产消费者；跨组件组合状态另见下文。

| 实际状态或失败位置 | 实施与恢复应观察的结果 | 主验证步骤 |
| --- | --- | --- |
| 原 START 未保存，原调用或保存仍未收场 | 原拥有者继续；无 doctor、新 START 或冲突 READ。可靠本地边界只结束主机责任，不生成相机结束事实。 | H1、H3、H4 |
| 旧成功结果已保存，归档或登记未完成 | 沿原文件责任继续，HOST 不依赖相机在线；不生成新拍摄。 | H1、H3 |
| 原绑定缺失或改变，固定事实缺失 | 绑定错误与状态库错误分开；不操作替代机身。创建调用前拒绝不消耗尝试，已提交意图不退还次数。 | H2—H4 |
| 创建或意图未提交、可靠回滚 | 不派发，无新责任或次数；以后重新判断实际资格。 | H2、H4 |
| 意图已提交但可靠未派发 | 保存实际未派发原因，保留次数；同目标已解决、取消、过期或让位均不制造工具错误。 | H3、H4 |
| 工具失败、不完整、超时、身份不符 | 保存每步实际事实；原进程和输出先收场，再按原检查剩余额度及资格处理。 | H2—H4 |
| 检查等待间隔，普通拍摄取得资格 | 读取保留原责任、次数和顺序，让出实际执行；不抢占在途调用，原间隔不因拍摄等待重复。 | H3、H4 |
| 全部目标已被其他路径解决 | 开放检查按真实引用结束，零新增调用；终态责任不重开。 | H2—H4 |
| PASS 可接受且全部释放前提成立 | 原结果、检查结论、全部必要释放同事务保存；旧活动 UNKNOWN、原动作和报告事实保持。 | H2—H5 |
| PASS 已取得，但仍有目标不合格或新限制出现 | 保存观察，禁止不合格的部分释放；旧批与新活动分别判断，实际后续工作再次核对资源。 | H2—H4 |
| 保存失败、回执未知或释放后通知丢失 | 原完整输入及键保留，先核实事务；已提交结果不重放，未可靠释放不派发冲突工作。 | H3—H5 |
| 取消或过期与完整返回竞争 | 分别保存触发终态、检查结果和实际调用收场；合格迟到结果可解除旧限制，不能重开工作。 | H3、H4 |
| 检查耗尽或最终未知 | 拍摄或受影响读取项有有限终结；未派发 START／READ 不增加其次数，源存在性不改写，其他工作继续。 | H3—H5 |
| DEVICE 下载已经开始后失败或取消 | 原 READ 票据、预算和交付进度继续拥有责任；下载进程、句柄和结果收场后才清理副本。 | H3—H5 |
| 终态后仍有真实调用、保存或诊断 | 恢复和关闭继续发现并完成责任；不因仅查询开放状态而遗失，也不因旧 UNKNOWN 永久保持空轮询。 | H3、H4 |

## 横切审查、提交与未决事项

每阶段提交前沿以下链路审查接缝：原绑定与 query 配置 → 固定身份和目标 → 普通候选选择 → 事务内独立守卫 → 意图及实际派发 → 原结果拥有者与收场 → 原子释放或有限失败 → 后续拍摄／文件交付 → 历史、报告、客户端和关闭。逐项核对生产者与消费者。阶段勾选说明该阶段实现和单元测试证据满足条件，不表示整条链的组合验收已经完成。

实施者按照 Git 协作规则在自己的工作区核对完整 diff、暂存范围和阶段证据，按可独立审查的阶段提交；协调者按依赖集成代码。测试覆盖对应表、失败归因和证据摘要进入版本控制中的验证记录，正式计划只维护原步骤状态与链接。集成测试重构完成后的组合验收单独排期和记录，不改写本轮禁止新增或运行的范围。

规格已经确定软件行为，本计划没有等待新的业务选择才能开始 H1—H5 的事项。实施前仍须核验目标测试依赖和当前代码基线；实施中遇到规格未覆盖的真实状态，按[设计缺口处理规则](../../../.agents/rules/design-and-planning.md#实现中发现设计缺口)说明证据并暂停依赖部分。现场选择独立新环境还是接续原实例、实际供电安排及真机验证时间属于 H6 的部署决定；它们不构成增加旧兼容实现或自动处理现场数据的依据。
