# camctl_host 交付前规格核对与修复计划

本计划针对 `apps/host-demo` 的 C 接入模块、终端示例及独立交付物。目标是在交给第三方集成之前，补齐已经确认的行为和交付缺口。正式契约由 [C 接入规格](../../host-demo/design.md)、[实现设计](../../host-demo/implementation.md)、[CLI 结果协议](../../architecture/cli-commands.md)和[文件交接](../../architecture/file-handoff.md)维护；本页记录审查证据、实施顺序及验收条件，不另立公共协议。

2026-10-08 的审查发现 5 项 P2 缺口和 3 项 P3 问题。P2 需要在正式交付前修复；P3 涉及诊断事实、安装说明和版本标识，应随同完成。三个公开入口和主要运行流程已有实现，未发现整块功能尚未提供的情况。

本计划中的行为契约与项目规则是实施要求。内部结果类型、辅助函数、预计修改文件及测试组织是实现建议；实施者可以根据实际责任边界调整，但须覆盖给定分类。实施期间如遇未定义状态、需要改变公开协议或现有故障范围，应停止相关修改并报告证据。

## 已确认问题与修复依据

### H-01：未知移动可能遗漏目录同步（P2）

**位置：** [claim.c](../../../apps/host-demo/src/claim.c) 第 55、65 行；调用链是 `camctl_host_claim → host_claim_posix → host_claim_files`。

本轮只有一个文件时，`renameat` 可以已经完成移动，但调用方取得 `EIO` 等未知结果。当前逻辑只在返回 0 时设置 `moved`，因此实际文件已进入 `processing`，两个目录却没有执行同步。这违反[接入说明](../../../apps/host-demo/README.md#部署准备与共存约定)选定的“移动后同步两个目录”规则。物理断电后的持久性仍由实机验证；软件必须执行已选定的同步操作。

根因是把“已确认移动成功”作为“目录可能已经被修改”的全部条件。修复须独立累计目录同步责任，保留未知移动本身的分类，不凭同步成功补造移动结果。H-06 需要的后端步骤信息与本问题共用，先完成任务一，再完成任务二。

**已确认行为分类：**

| 后端取得的事实 | 移动结果 | 是否新增同步责任 |
| --- | --- | --- |
| 源文件检查失败，或对象不满足普通文件前提；尚未调用原子移动 | 本模块未移动，记录检查步骤及错误。 | 否。 |
| 原子移动已尝试，取得明确失败结果 | 未移动，记录移动步骤及错误。 | 否。 |
| 原子移动明确成功 | 已移动。 | 是。 |
| 原子移动已尝试，但结果无法确认 | 保留未知移动及实际错误。 | 是。 |

整批责任是各文件责任的累积。后续单项失败、目录故障或停止继续移动均不能清除它；有责任时对两个已打开的目录分别执行同步，第一个失败也要尝试第二个。同步成功不将未知移动改为成功；任一同步失败保留其目录、步骤及错误，不回退或重送文件。

### H-02：异常 run 的自动重试使用过早的时间（P2）

**位置：** [host.c](../../../apps/host-demo/src/host.c) 第 67、87、148 行和 [scheduler.c](../../../apps/host-demo/src/scheduler.c) 第 57 行。

工作线程在 `collect` 前取得时间；收场、回收、输出和结果判定完成后，仍使用该旧时间设置重试期限。当这些操作耗时较长时，它们消耗了本应从失败确认后开始的等待。这违反[重试等待起点](../../host-demo/design.md#重试次数与等待间隔)。

独立专项检查使用退出码 0、缺少最终 stdout 的真实子进程，在最终真实扫描返回前延迟 300 毫秒。配置等待 200 毫秒，从生产结果解析确认异常到下一次启动只有约 50.1 毫秒。

修复须在最终结果已经取得后，以新的单调钟观察安排异常重试。审计 `host_schedule_finished`、`host_schedule_spawn_failed` 和所有 `due` 写入；明确启动失败入口已经重新取时，须保持其语义。

| 已确认状态 | 必须保持的行为 |
| --- | --- |
| 原调用尚未收场或输出尚未处理完 | 继续占位，不能安排冲突的新调用。 |
| run 异常，单调钟可靠，没有新的有效启动要求 | 从最终失败判定后的观察时刻起等待配置间隔；实际自动尝试前检查并增加共享计数。 |
| run 成功或返回合法 error，没有待启动要求 | 不新增自动重试。 |
| 存在新的有效 needs_run: true | 按既有规则合并启动，不将其计为自动重试，也不清零累计预算。 |
| 取得完成时刻时单调钟失效 | 保留诊断和未满足要求，停止新启动并拒绝新输入；已确认收场事实仍有效，领取仍可调用。 |

### H-03：减少日志保留数后旧归档不收敛（P2）

**位置：** [logger.c](../../../apps/host-demo/src/logger.c) 第 11—31、39—50 行。

同一路径先以 `log_file_count=3` 运行并生成当前文件、`.1` 和 `.2`，下次运行改为 1 后，即使多次写入和轮换，仍保留这三份文件。这违反[模块日志总份数](../../host-demo/implementation.md#资源上限与输出处理)与[归档淘汰规则](../../host-demo/implementation.md#模块日志)。

根因是首次打开不核对旧归档，轮换只处理当前保留数范围。修复须由日志线程在首次文件操作时收敛本模块拥有的归档，并审计重新打开及轮换入口；不得让主程序调用或工作线程等待清理。

| 观察 | 必须产生的结果 |
| --- | --- |
| 保留数为 K，存在本模块原先产生的 .N，N >= K | 删除超出保留范围的归档，保留范围内的归档顺序和内容。 |
| 目标归档明确不存在 | 正常继续。 |
| 查询或删除不能可靠完成 | 按已有文件通道故障规则停用日志，保留步骤与错误；提交、管道和领取继续。 |
| 保留数不变或增加 | 保留仍在范围内的归档。 |
| 文件不属于模块归档命名范围 | 保持原状。 |

归档命名和支持范围从现有规则取得；若需要集中常量，配置校验及清理读取同一权威定义。不得清空全部日志、放宽保留数或要求人工清理来满足数量验收。单文件大小继续按现有追加与轮换阈值处理，本任务不另行定义旧归档内容的改写规则。

### H-04：源码包过滤会排除整个源码树（P2）

**位置：** [CMakeLists.txt](../../../apps/host-demo/CMakeLists.txt) 第 117 行。

源码位于名为 `build-area` 的父目录下时，`/build[^/]*/` 匹配各源文件的绝对路径。CMake 3.28.3 和 3.10.2 均成功生成空源码包，交付方无法凭命令成功判定包有效。这违反[源码交付要求](../../host-demo/implementation.md#交付内容)。

修复须使用既有 CPack 能力，将排除范围限定为组件内部缓存、构建产物及实际构建目录，不受源码父目录名影响。审计整个排除清单，特别是 `.local` 和缓存表达式。CPack 对该变量使用正则表达式列表，配置时须处理转义，见 [CMake 3.10 的 CPack 文档](https://cmake.org/cmake/help/v3.10/module/CPack.html#variable:CPACK_SOURCE_IGNORE_FILES)。

验收覆盖普通路径、`build*` 父目录、`.local` 父目录和带空格或正则特殊字符的路径。源码包须包含构建文件、公开头文件、生产源码、依赖源码及许可，解包后可独立构建；实际构建产物和缓存仍须排除。不得以限制第三方源码放置路径代替修复。

实施时的路径复核还确认：CPack 的默认目录收集会将源路径作通配符展开，含方括号的父目录可能没有匹配文件；该步骤见 [CMake 的目录收集实现](https://github.com/Kitware/CMake/blob/v3.28.3/Source/CPack/cmCPackGenerator.cxx#L339)。源码收集因此采用 CPack 安装脚本中的 CMake `file(COPY)`，沿用同一排除清单。CPack 对构建暂存目录的归档收集也受特殊路径影响，CMake 自动生成的打包目标在含括号路径下可能产生无法执行的 shell 命令。路径验收和随包说明因此使用普通名称的独立构建目录及独立 `cpack --config` 命令；源码父目录仍覆盖空格和正则特殊字符。两项调整均保持原归档内容与交付契约。

### H-05：随包接入示例未闭合配置与交接目录（P2）

**位置：** [README.md](../../../apps/host-demo/README.md) 第 45—49、103—105 行；相关事实在 [bootstrap/config.py](../../../apps/camctl/src/camctl/bootstrap/config.py) 第 225—226 行。

C 示例使用 `/srv/camctl/ready` 和 `processing`，却令 `config_path=NULL`；终端示例也省略 `--config`。默认配置未覆盖路径时，CLI 实际发布到 `$HOME/.camctl/ready`，模块领取另一个目录。当前包内说明未明确双方实际目录必须一致，第三方按示例接入可能领取不到报告。

修复须把[目录一致性](../../architecture/file-handoff.md#配置归属)、[参数责任](../../host-demo/implementation.md#参数由谁提供)和[同账户部署](../../architecture/deployment-example.md#样例范围与准备)落实到随包运行说明。示例应选择一个完整方案：可使用一致的默认绝对路径；也可提供最小合法 TOML，使部署初始化、C 的 `config_path` 和终端的 `--config` 使用同一来源。实际源码实现不应新增解释 CLI 配置或自动初始化业务库的职责。

| 部署条件 | 说明和示例必须表达的行为 |
| --- | --- |
| 使用默认配置来源 | 双方使用运行账户展开后的相同实际目录；说明默认配置文件可能覆盖内置路径。 |
| 使用显式覆盖文件 | init、run/submit、C 和终端使用同一配置来源及实际目录。 |
| 所选覆盖文件不存在 | CLI 使用默认值；部署人员须核对生效路径，不能把文件名当作配置已生效的证明。 |
| 已有状态库或历史文件 | 保留原数据；目录变更按正式切换契约处理，不能删除状态库后重建。 |

验收按随包说明完成无设备的初始化、提交报告检查计划、发布、领取和结果观察。只检查文档含有相同字符串不能证明实际路径一致。

### H-06：领取诊断丢失失败步骤（P3）

**位置：** [claim_posix.c](../../../apps/host-demo/src/claim_posix.c) 第 81—85 行和 [claim.c](../../../apps/host-demo/src/claim.c) 第 57—59 行。

源文件 `fstatat` 在 `renameat` 前返回 `EIO` 或 `EINTR` 时，后端只返回 errno，上层将其记录为 `move_unknown`。实际上模块根本没有尝试移动，诊断却表达为移动结果未知。这违反[实际步骤与错误事实](../../host-demo/design.md#与主程序共存及记录诊断)的要求；尚未发现该分支导致文件业务结果被误判。

修复须让后端保留源文件检查与原子移动的步骤、是否尝试副作用、结果分类和实际错误，采用枚举或等价受约束类型。具体结构是实现建议，完整行为分类见 H-01。禁止仅把所有 `EIO/EINTR` 当作未知移动或同步责任；相同 errno 可以发生在移动之前。

文件后端的执行分区如下；已尝试移动时沿用现有 `EIO/EINTR` 未知分类，本任务增加前置步骤事实，不扩大错误或故障范围。

| 实际系统步骤 | 取得的结果 | 后端必须保留的分类 |
| --- | --- | --- |
| fstatat | 任意错误，包括 EIO/EINTR | 源文件检查失败，原子移动未尝试，保留实际 errno。 |
| 源对象类型检查 | 不是普通文件 | 前提不满足，原子移动未尝试。 |
| renameat | 返回 0 | 已尝试且明确移动成功。 |
| renameat | EIO/EINTR | 已尝试，移动结果未知。 |
| renameat | 已有分类中的其他明确错误 | 已尝试且移动失败，保留实际 errno。 |

后续结果超出这些已确认分类或系统接口契约时，实施者须停止相关修改并报告具体事实，不自行将它归入成功、未移动或未知。

审计目录打开、身份与权限检查、原子移动和目录同步的诊断接缝。保留“单项失败继续、目录故障停止、已移动文件不回退”的行为，不用人类文案作为结果分类来源。

### H-07：安装说明引用源码布局（P3）

**位置：** [CMakeLists.txt](../../../apps/host-demo/CMakeLists.txt) 第 112 行和 [README.md](../../../apps/host-demo/README.md) 第 32、38 行。

README 安装到 `share/doc/camctl_host/` 后，`include/camctl_host.h`、`src/demo.c` 和 `vendor/manifest.cmake` 三个链接都不存在。头文件和示例实际已安装到其他位置，依赖清单没有安装；仓库设计和验证记录也不在独立包内。

修复须按实际安装布局生成或提供可用引用。依赖信息从现有清单读取或生成，不能再维护一份独立版本列表。源码说明中的引用与安装说明中的引用分别核验；可以保留明确的仓库阅读提示，但第三方完成接入所需的规则必须随包可获得。不要求无差别复制全部架构文档。

### H-08：最低 CMake 的打包版本漂移（P3）

**位置：** [CMakeLists.txt](../../../apps/host-demo/CMakeLists.txt) 第 2、115—119 行。

项目版本为 1.0.0，CMake 3.10.2 生成的源码和二进制包却使用 0.1.1；同一源码在 3.28.3 下使用 1.0.0。当前脚本依赖不同 CMake 版本的 CPack 默认值，破坏交付标识的单一权威来源。

修复须从现有 `PROJECT_VERSION` 及各段派生 CPack 版本。两个已声明支持的 CMake 版本下，源码包、二进制包的元数据和文件名均须与项目版本一致；不得另写一组常量版本。审计同一打包配置中其他依赖默认值的项目标识。

## 执行顺序与阶段门禁

### 实施补充：默认配置路径交接（H-09，P2）

真实接入验证确认，`ConfigAdapter.load` 返回的内置路径仍含 `$HOME`；`init` 单独展开状态库路径，而 `run/submit` 的运行时直接使用未展开的快照，日常入口因此找不到刚初始化的库。这是配置适配与运行时交接的既有缺口，适用[默认配置加载规则](../../architecture/configuration.md#本地配置的加载与更新)。修复由配置适配器在向命令交付快照前统一展开已有 `$HOME/` 前缀，所有路径字段遵守同一规则；不改变配置校验、文件选择或目录切换契约。

| 配置来源与路径 | 修复必须保持的结果 |
| --- | --- |
| 默认文件或显式文件不存在 | 使用内置值，并按运行账户展开全部路径；显式文件缺失不再寻找默认文件。 |
| 部分字段覆盖 | 覆盖字段按已有路径规则处理，省略字段的内置路径仍展开。 |
| 路径以 `$HOME/` 开始 | 按适配器所持有的账户目录展开。 |
| `$HOME/` 后仍有重复分隔符 | 保留账户目录，按既有路径规则规范化；不能将剩余后缀当作独立绝对路径。 |
| 其他有效路径 | 保持原字符串；不新增环境变量替换规则。 |
| 配置读取或校验失败 | 保持原错误，不交付默认成功快照。 |

- [x] 先以文件读取替身验证 `ConfigAdapter.load` 的完整路径结果；用真实 CLI 验证默认和显式缺失配置下的 init/run，初始化与日常入口须使用同一状态库。
