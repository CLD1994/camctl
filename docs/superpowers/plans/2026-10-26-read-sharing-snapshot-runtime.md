# 剩余事实读取复用与正常运行快照维护

本计划承接[事务事实读取重构](2026-10-26-transaction-facts-refactor.md)完成后的剩余读取，以及[历史性能计划步骤 3](2026-10-25-history-performance-closure.md#3-接通正常-run-的快照维护)的生产接线。当前完整保存样本为 301 次 SELECT，其中当前集合及执行身份 116 次、固定成员及结论 46 次、文件及配对关系 58 次、产物及来源关联 29 次、历史位置及完整性 52 次。相同 SQL 与实际绑定的重复为 208 次，不能把该数字直接当作可删除工作量。

## 责任与范围

业务事件和当前投影在每次业务变化的完整事务内可靠保存。活动任务状态可按[已提交结果与当前状态的边界](../../camctl/persistence-runtime.md#已提交结果与当前状态的边界)留在有容量限制的内存缓存中；指定 H 的历史计算结果复用仍按其适用范围处理。历史快照按[变化次数阈值](../../camctl/history-snapshots.md#按对象累计变化次数触发历史快照)异步生成，不推迟业务保存，也不要求全部对象在阈值前各自常驻完整快照。

同一事件实际前序下取得的数据库输入可以供事件生成、上下文及守卫独立判断；当前提案不能作为已保存依据。固定成员批次可交付已经读取的文件、配对和关系，避免下层重复查找。同一事件之间的当前输入复用与跨事件缓存分别处理；跨事件必须覆盖业务写入、派生历史列以及集合和空关系的实际变化。

正常 run 的业务数据库操作与快照操作必须接入共同派发边界，才能兑现业务优先。已开始操作跟踪至真实结果；快照积压不延长会话、不形成业务责任。维护启动查询一次，提交与外部新对象发现唤醒，查空后等待通知；不新增周期性全候选查询。确认回滚、提交未知、入队超时停用及收尾按现有持久化和快照规格处理。

## 步骤与验收

### 1. 核实内存状态及快照责任

- [ ] 核对当前及早期规格中内存活动状态、历史计算结果缓存、派生快照和可靠业务保存的区别，给出原文位置及实际例子。
- [ ] 审查正常 run 的业务连接、同步仓储、异步操作及资源收场，明确共同派发的实际接缝，不以单独快照线程替代业务优先。

### 2. 合并实际输入的重复读取

- [ ] 用单元反例固定候选页重复取集合、成员已取配对后再次读取、结论先定位再取行及同阶段重复定位。
- [ ] 将集合、固定文件、实际配对和页关系沿批次交付；结论按集合一次取行并交给独立处置和失败判断，保持缺失、身份及固定边界错误。
- [ ] 评估并接通同一事件前序内的实际行共享，保留内核输入来源、当前写后可见、派生历史更新及空关系刷新，避免引入任意 SQL 结果缓存。
- [ ] 审查实际产物定位及反向覆盖，合并逐项重复查找；保留同组真实原片、完整覆盖、唯一 marker 与整组原子发布，有界多遍及有限入口语义保持。

### 3. 接通正常 run 的快照维护

依赖步骤 1 的真实调用边界。接口拆分随审查结果细化；不引入新的业务状态或持久化格式。

- [ ] 业务及快照共用数据库派发，实际等待中的业务优先；所有连接均由实际所属线程创建、使用和关闭，取消后保存结果仍由责任拥有者接手。
- [ ] 启动检查遗留候选；可靠提交及既有外部对象发现发出可合并且不丢失的维护唤醒，覆盖阈值 1；空候选等待通知。
- [ ] 接通只读依据、事务外准备、短写保存及批间让出；入队超时本会话停用，收尾停止新批并处理迟到结果，积压不改变会话完成条件。
- [ ] 以单元覆盖调度、通知竞争、回滚、未知、停用与退出，并将原历史性能计划的对应原验收项按实际结果更新。

### 4. 真实副本与阈值对照

- [ ] 使用 Python 3.11 运行受影响单元及完整单元，独立审查实际生产接线；本次不运行集成测试，不启动真实 camctl、调度器或设备，不修改原人工数据库与配置。
- [ ] 使用同一 H893 保存前态及原申请重放完整 finish，另测原键核实；核四事件原字节、全部业务映像及报告 43／44，记录 SQL、实际绑定重复、读取／解码量、阶段耗时与有界资源。
- [ ] 在独立副本上比较阈值 16、32、64 的候选、快照写入和永久体积、旧状态恢复与业务等待；快照创建成本与查询成本分别计量，根据证据决定是否调整默认值。
- [ ] 更新正式计划与验证记录，制作并审计人工验证发行物；原数据保留，进程停止，真实设备验证交由用户进行。
