# 剩余事实读取复用与正常运行快照维护

本计划承接[事务事实读取重构](2026-10-26-transaction-facts-refactor.md)完成后的剩余读取，以及[历史性能计划步骤 3](2026-10-25-history-performance-closure.md#3-接通正常-run-的快照维护)的生产接线。完整保存的输入基准为 301 次 SELECT，其中当前集合及执行身份 116 次、固定成员及结论 46 次、文件及配对关系 58 次、产物及来源关联 29 次、历史位置及完整性 52 次。相同 SQL 与实际绑定的重复为 208 次，不能把该数字直接当作可删除工作量。

## 责任与范围

业务事件和当前投影在每次业务变化的完整事务内可靠保存。活动任务状态可按[已提交结果与当前状态的边界](../../camctl/persistence-runtime.md#已提交结果与当前状态的边界)留在有容量限制的内存缓存中；指定 H 的历史计算结果复用仍按其适用范围处理。历史快照按[变化次数阈值](../../camctl/history-snapshots.md#按对象累计变化次数触发历史快照)异步生成，不推迟业务保存，也不要求全部对象在阈值前各自常驻完整快照。

同一事件实际前序下取得的数据库输入可以供事件生成、上下文及守卫独立判断；当前提案不能作为已保存依据。固定成员批次可交付已经读取的文件、配对和关系，避免下层重复查找。同一事件之间的当前输入复用与跨事件缓存分别处理；跨事件必须覆盖业务写入、派生历史列以及集合和空关系的实际变化。

正常 run 的业务数据库操作与快照操作必须接入共同派发边界，才能兑现业务优先。已开始操作跟踪至真实结果；快照积压不延长会话、不形成业务责任。维护启动查询一次，提交与外部新对象发现唤醒，查空后等待通知；不新增周期性全候选查询。确认回滚、提交未知、入队超时停用及收尾按现有持久化和快照规格处理。

### 3. 接通正常 run 的快照维护

依赖步骤 1 的真实调用边界。接口拆分随审查结果细化；不引入新的业务状态或持久化格式。

实际迁移边界包含会话与时钟、受理、拍摄、取消、取回、清理、电机、报告发布及它们的运行装配。协程继续拥有设备、文件和运行时状态，数据库线程只执行物化的有限查询及完整仓储操作。必要阶段同时保护数据库等待和主协程的结果应用；接纳租约仍在规定事务内取得或释放。相机每次物理调用之前的资格核实改为可等待查询，保持实际派发前核对取消和窗口的责任。

这些生产调用路径已接入共同端口。派发资格在最终数据库等待结束后核对，实际返回和可靠提交先交给所属协程，再交付取消或数据库控制异常。正常运行维护的启动、通知、业务优先及停止责任已经完成组合单元和独立审查；具体证据见[最终验证与交付](../../camctl/verification.md#共享数据库事实读取与正常运行快照维护的验证2026-10-26)。
