# 录像结果事务耗时测量

## 目标与范围

将录像结果保存的总耗时分解到实际事务阶段，定位 79 秒保存中的主要成本。沿用[数据库完整事务合同](../../camctl/persistence-runtime.md#数据库连接与完整事务)及[分段结果共同提交](../specs/2026-10-23-video-result-modes-and-segmentation-design.md#持久化共同提交与恢复)。本步骤只增加辅助计时，不改变事务、批次、调度、重试、连接所有权或设备调用。

每次事务在结束时输出一条 `db_transaction` 汇总，关联外层动作、保存方法和原 `operation_key`。记录单调钟经过时间、线程 CPU 时间、各主阶段的独占耗时、SQL API 调用与取数的次数和耗时、读取及修改行数、事件及行变更数。SQL 指标属于所在阶段内部，不能与阶段时间再次相加。历史解码和校验输出包含子调用的明细，明细之间也不相加推导总耗时。

`BEGIN IMMEDIATE` 阶段包含取得写事务的等待与执行，不能直接解释为纯锁等待；COMMIT 阶段包含实际提交及适用同步，不能从该数字单独推导磁盘耗时。线程 CPU 时间与经过时间共同用于区分计算和等待，再按实际数据继续定位。

只聚合固定类别的数字，不记录 SQL 正文、参数、媒体路径或事件正文，不缓存增长的数据集合。计量代理只在诊断上下文中用于本次事务，不改原连接、SQLite 回调、PRAGMA、游标寿命及返回、异常或保存回执。没有辅助日志目标时直接使用原连接和原调用。

## 实施与验收

- [ ] 1. 公共计时与 SQL 计量：固定主阶段、上下文关联、经过与 CPU 时间、调用和行数聚合；用受真实 SQLite 接口约束的替身验证返回、异常、惰性取数及关闭诊断。
- [ ] 2. 普通与有界事务接线：分别覆盖取得写事务、读取初始状态、规划、惰性事件生成、验证上下文、报告目标、事件校验、变化派生、SQL 写入、最终核验、提交及回滚。保留原读写顺序与事务边界。
- [ ] 3. 在最窄历史入口记录解码、结构校验及完整事件校验明细；分段保存及原保存恢复传递动作和方法上下文。
- [ ] 4. 独立只读审查并执行相关单元测试，核对没有新 SQL 或业务副作用；不运行集成测试或相机命令。
- [ ] 5. 构建并核对安装包，在人工环境没有在途调用时更新，保留配置和状态库。用户用新计划进行一次人工拍摄，取得新的事务阶段数据。

## 测量依据

原始案例为计划 5、延时动作 17。前一录像释放设备后，六次同步结果保存合计约 115.073 秒，`finish_segment_recording` 为 79.392 秒。现有总计时不能区分内部阶段。原始诊断及时间线保存在 `.local/verification/timelapse-window-20261025/plan-5-action-17.json`。
