# 拍摄首次控制与集成测试同步修复计划

本计划承接[交付核对](2026-10-08-camctl-host-delivery-audit.md)的真实回归结果。目标是使尚未实际启动的拍摄动作持续遵守设备残留、取消和启动窗口契约，并使读取并行测试通过明确同步点建立场景。正式规则见[后续动作触发的残留收场](../../architecture/camera-recovery.md#后续动作触发的残留收场)、[拍摄占用与兼容性](../../architecture/scheduling-execution.md#设备执行与操作兼容性)和[设备能力](../../architecture/camera-capabilities.md)。本页只跟踪修复，不修改公共协议或第一版故障范围。

2026-10-08，CPython 3.11.16、Linux x86_64，前台顺序执行 `apps/camctl/tests/integration/bootstrap` 得到 112 通过、1 跳过、4 失败。独立审查将四个失败分为以下两个责任边界。所列源码组织是实施建议，行为分类与不变量是实施要求。

## 问题与权威事实

**H-10（P2）：首次控制没有重新核对后来产生的残留。** `capture_flow` 对 PENDING 动作调用 `pass_residual_gate`，然后保存 RUNNING；能力处理器在另一步才通过 `_control_call` 取得启动票据。如果其他录像在两步之间停止失败并终态化，该相机的残留已经变化，早先的检查不能继续作为启动依据。三个失败的历史均显示：后续动作 RUNNING，原停止流程耗尽、原动作失败，随后直接登记后续启动尝试和启动观察，缺少执行前查询与残留收场。单独运行部分案例可以通过，说明原测试排期没有固定这一状态转换；生产不变量仍被违反。

首次控制接缝还须处理 RUNNING 且没有启动尝试的动作：残留等待不能使动作永久停在 RUNNING。`execution_started` 只证明动作进入执行，不证明设备命令发出。原过期事务与取消资格装配使用这个标记判断物理启动，会分别阻止过期、错误拒绝无停止能力的取消或留下未完成目标。窗口耗尽时，过期事务须核对实际派发事实；取消时按未派发分区保存取消并完成本地收场。已有启动尝试的动作继续原结算，不能将未确认派发解释为从未派发。

残留查询的结束也是独立责任边界。查询用途不再负责时，正式规则要求流程为 `CANCELED`，查询不能写入 `EXPIRED`；残留停止已经开始时，其确认查询随原停止责任继续，不能仅凭触发动作终态结束。依据见[一次查询结束与整项核实结束](../../camctl/database/operation-fields.md#一次查询结束与整项核实结束)。

**H-11（P3）：读取并行测试依赖未经同步的短墙钟间隔。** 原测试提前提交一秒后到期的录像，然后等待录像启动并断言首次读取已发生。时间格式化和真实装配耗时使照片、录像可以在首轮同时到期；录像已经启动不能证明读取已经失败并进入重试等待。这是测试场景构造的缺口，尚无证据证明生产并行规则错误。

## 已确认状态模型

判定维度依次为：已有启动尝试、触发动作是否有效、当前启动窗口、设备占用或残留、查询与收场结果。拍摄包括照片、录像和延时摄影，三者共同经过首次控制边界。取回等与录像兼容的操作保持原能力规则。

| 启动事实及触发条件 | 设备事实 | 必须产生的行为 |
| --- | --- | --- |
| 已有启动尝试，包括效果未知或尚未确认 | 任意 | 继续原启动核实及结算，不按首次启动再次查询、不重发已发出的控制、不重置次数。 |
| 没有启动尝试，动作终态或已取消 | 任意 | 不新增启动、查询或残留停止；已发出的必要收场由原责任继续。 |
| 没有启动尝试，尚未到启动时间 | 任意 | 等待，保持原状态和预算。 |
| 没有启动尝试，窗口已经耗尽 | 任意 | 调用已有过期事务，保存按首次窗口观察分类的终态；保留历史和活动事实，不发出新控制。 |
| 没有启动尝试，有效且在窗口内 | 无已终态录像残留 | 按现有占用、保留、排序及兼容性事务取得资格；其他正常活动占用不能被强停。 |
| 没有启动尝试，有效且在窗口内 | 已终态录像仍有占用及执行事实 | 按原责任执行或恢复有限查询和收场，可靠解除前不得登记启动尝试或调用控制端口。 |
| 同上 | 查询不可用、失败、未知或观察到其他活动 | 保存原事实，按原间隔和累计预算等待，不推测设备空闲或授权停止其他录像。 |
| 同上 | 收场未结束或次数已耗尽 | 保留残留与次数，触发动作按当前窗口或取消规则收尾。 |
| 同上 | 可靠确认空闲或目标残留已可靠结束 | 保存对应观察及收场事实，再按当前窗口、取消和占用条件取得启动机会。 |

数据从当前动作、设备活动、原启动尝试与残留责任读取；权威状态仍为不可变历史与同事务投影。PENDING 检查通过不保存永久启动许可；RUNNING 不回滚为 PENDING。不得伪造空闲、释放未确认活动、改写原终态、重建收场责任、清零预算或仅改测试排期掩盖生产接缝。查询、意图、过期或结果保存不可靠时保留错误，不能降级为可启动。

### 过期与取消的保存分类

判定以动作状态、设备活动派发记录、原启动尝试及其效果为依据。RUNNING 拍摄必须有活动登记；记录缺失或矛盾是状态库错误，不能作为零尝试放行。过期与取消保持 `execution_started` 和实际活动状态，释放只修改冲突占用。

| 当前可靠事实 | 窗口结束 | 取消 |
| --- | --- | --- |
| PENDING，尚无启动尝试 | 保存原过期原因与终态，必要时同事务完成计划 | 沿原 PRE_START 事务直接取消目标并保存成员结果 |
| RUNNING，活动可靠未派发，且没有可能生效的启动调用或待核实效果 | 保存过期原因与终态；适用时以独立 `DEVICE_OBSERVED.RELEASE` 事件在同事务释放占用 | 不要求停止能力。先保存标记并保持 RUNNING，成员等待；共同未启动取消入口完成本地收场并保存 CANCELED，随后成员保存结果 |
| 已有可靠启动成功或可能派发、效果未知、调用在途 | 继续原有限核实及结算，不能直接过期或重发 | 按已启动或可能启动及原停止能力分类；拒绝与生效后的停止失败分别保存 |
| 终态或取消已经生效 | 保持原事实，取消优先 | 保持终态，或复用原取消责任；不建立新预算 |
| 状态库事实不可解释、提交未知 | 保留错误并按原事务恢复规则核实 | 同左，不猜测成功或未启动 |

冲突占用释放仍要求原统一释放依据成立，且需要输出范围限制的活动已经解除范围限制，即适用活动的 `baseline_state = FIXED`。不能伪造活动 ENDED 或固定基线。动作过期事件只修改正式登记允许的状态和原因；活动释放使用其自身事件。RUNNING 的取消按[动作状态与执行标记](../../camctl/database/plans-actions.md#计划与动作的运行状态)分开保存生效和收场，不借 PRE_START 把执行历史清零。

可靠无效果的已有尝试须逐项核对原责任，不能只读最后一次尝试。原尝试已经取得明确无效果结论且没有待核实启动责任时，窗口结束保存过期；仍在途、效果未知或有必要核实责任时继续原链。普通调用错误不能替代无效果证据。过期共同结束尚未结束的 START 责任并清除重试等待，保留原次数、配置、尝试结果与已经结束的流程结果。

本地取消收场在现有取消终态事务中使用明确的未派发模式，重新核实全部尝试及自身活动的可靠未启动事实，再保存终态、适用释放和计划聚合。普通已派发取消模式保持其原停止、产物及收场前置条件。PENDING START 责任如果存在，须在取消生效事务共同结束为 CANCELED；本地收场核对已关闭或不存在。拍摄就绪选择入口须纳入需要本地收场的取消照片，不能只选择录像和延时。

### 取消与迟到结果的结算

取消与在途启动交错时，取消生效事务共同结束尚未终态的普通 START 为 CANCELED，并清除重试等待；保留原次数、配置和在途尝试。迟到的可靠无效果结果允许本地收场；未知或已启动结果继续原核实或停止责任。WITH_STOP 分区不能借此归一化派发状态或释放占用。原 START 已终态时保持原结果；ALREADY 和重启复用已关闭的责任。实施时先覆盖在途 APPLY、迟到无效果及已终态保持反例，再修改共同取消事务，并验证原键重送和历史恢复。

尝试结果与流程结果分别判定：原流程尚未终态时，结果事务保存本次尝试及适用的重试等待或流程结束；原流程已终态但尝试仍在途时，只保存实际尝试结果，保持原流程状态、错误、配置和次数。同键核实读取原结果事务边界，按实际保存的流程处置验证，不能要求取消后的迟到结果将原 CANCELED 改成调用者请求的其他终态。该规则在共同结果仓储落实，覆盖成功、未知、错误及无效果迟到结果。

录像和延时处理器共同按下表优先推进取消，再考虑普通发送时间或启动计时规则。停止沿本动作的活动身份、原 `stop/<id>`、次数、间隔与能力，不新建残留停止预算，也不补造 `sent_at` 或启动确认。

| 取消后的事实 | 处理器动作 |
| --- | --- |
| 目标已终态 | 保持结果 |
| 原启动尝试仍在途 | 等待实际结果，不启动或停止新的控制调用 |
| 全部启动尝试可靠无效果，且没有待核实责任 | 进入本地未启动取消收场 |
| 已可靠停止或活动已可靠结束 | 不重复停止，完成适用的文件核实与取消终态 |
| 启动可能或确认生效，原停止仍在途 | 等待原停止结果 |
| 启动可能或确认生效，停止尚有预算，间隔已到 | 按原归属和停止能力提交下一次停止 |
| 停止间隔未到 | 保持原状态及预算 |
| 原停止已终态但未确认，或预算耗尽 | 保存未确认停止结果与诊断，取消终态保持，未知活动与占用不释放 |

录像取消放弃内容；延时取消保留实际完整且归属已确认的文件。普通完成事务的取消检查保持。先建立真实授予、WITH_STOP、迟到未知或错误再进入两个处理器的失败用例；验收覆盖发送时间有无、停止成功与耗尽、在途、间隔、重建运行时及 ALREADY。

目标终态与发起取消的动作结果分别保存。`TargetSettlement` 的拍摄分支按原活动与停止责任装配结果，不执行设备副作用：目标仍执行时返回未完成；目标取消且可靠未启动、无需停止，或原必要停止已可靠成功且适用收尾已结束时返回完成；原必要停止已经失败或未确认时返回完成且失败。调用错误与可靠停止观察可以并存，效果以验证后的确认依据判定。缺失或矛盾的必要记录报状态库错误。已有成员终态保持，TERMINAL 分区不追溯改变旧目标结果。沿既有服务保存逐项 `target_cleanup_failed` 并聚合 `cancel_items_failed`；测试从目标处理器继续推进真实收场端口、逐项保存与取消汇总，不能只断言目标 CANCELED。

### 查询责任的结束分类

| 查询用途及原责任 | 处理 |
| --- | --- |
| 执行前检查，触发动作仍有效且尚未启动 | 按原查询条件、次数和间隔继续 |
| 执行前检查，触发动作终态或取消已生效 | 不再新增查询，流程保存 CANCELED；已有最终结果保持 |
| 残留停止核实，原收场未终态且已经尝试停止 | 即使触发动作取消或过期，仍沿原查询责任及累计预算核实停止 |
| 残留停止核实，原收场已结束或不再需要核实 | 原查询最终结果保持；尚未结束的查询按原责任实际结论收场，不写 EXPIRED |
| 原停止、查询或关系事实缺失、矛盾 | 保留错误，不解释为无工作或停止成功 |

多个触发动作遇到同一活动的未完成收场时，原 `STOP_RESIDUAL` 流程的 id、触发动作和目标活动固定。推进、停止、确认查询均使用原流程的触发身份与剩余预算；后续触发动作独立检查自身窗口和取消，等待原流程，不创建第二套收场。原触发动作已经终态且原流程零尝试时，只结束未派发责任；原流程已经尝试则继续原收场。
