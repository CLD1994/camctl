# 无人值守自动更新实施计划

## 目标与依据

完成从 C 主程序提交包，到内部停止、离线安装、失败恢复、自动运行及 `processing` 诊断的完整路径，并在本容器的独立部署验证。行为以[更新接入规格](../../architecture/software-update-interface.md)和[版本与更新规格](../../architecture/versioning-and-updates.md)为准。

更新允许失败；主程序只判断成功或失败，不负责恢复或重启决策。强制包提供完整配置，重建同一部署位置的环境、状态库、staging 和 ready；保留 processing，失败恢复全部旧对象。支持更新及回滚中进程强杀、主机断电及重复中断；不考虑介质损坏和备份丢失。容器中断验证与目标硬件物理断电验收分别记录。

本计划的阶段和验收条件是执行基准；下文模块、文件和拆分方式属于根据现有源码作出的实施建议。实现者可按实际责任边界调整内部组织，但不能削减行为分区、备份范围或真实生产接线。发现影响外部行为的缺口时遵守[设计缺口处理规则](../../../.agents/rules/design-and-planning.md#实现中发现设计缺口)。

## 分工、基线与隔离

基线为 `cd895697`。root 负责权威规格、计划、教程与技能 Markdown、容器实际验证和最终整合；一位实现负责人共同维护 C、Python、包构建、协议生成、部署脚本及隔离单元，不把共享事务拆成不同实现者。独立评审由 `gpt-6.1-sol` 执行。

代码在独立 worktree 和任务分支实施，交接记录实际路径及基线。依赖环境可读取原 Python 3.11 环境，源码、构建、测试缓存、临时目录、数据库及验证部署独立。root 的文档改动与实现 worktree 不重叠；阶段提交经核对后按依赖集成。

不新增或运行集成测试套件。单元遵守仓库真实边界定义，不接触真实文件系统、网络、数据库、进程或真实包资源；测试模块导入前也须隔离隐含读取。C 线程及系统调用使用已有稳定边界替身。单元运行前独立审核隔离。生产 Release 编译与静态示例编译允许。最后由 root 在全新容器部署进行用户要求的实际升级与故障恢复验证，不操作现存部署、客户端数据或相机。

## 步骤与门禁

### S0：冻结完整契约

- [ ] 更新普通入口、成功含义、并发停止、诊断、强制重建和故障范围的权威规格。
- [ ] 独立审查从包元数据到实际清空、备份、恢复、重新运行及可观察诊断的接缝。

重点确认：同一部署路径重置；旧对象损坏或缺失与读取失败区别；processing 从备份覆盖和清理中排除；旧配置被替换后恢复仍可定位；旧虚拟环境不可导入时维护程序仍可运行。稳定引导必须能够读取本次持久记录并进入冻结引擎。

### S1：接通普通自动更新与启动恢复

前提：S0 的普通生命周期及诊断契约明确。

- [ ] 公开接口只接收包路径及可选能力同步目标，返回本次完整更新成功或失败。维护配置使用已初始化实例；详细协议保留私有，生成及安装边界一致。
- [ ] 普通初始化在任何目标环境调用前自动恢复未完成事务。
- [ ] 接通停止、应用、必要恢复和内部普通资源重建，失败已恢复时自动运行原部署；重送首次计划禁止。
- [ ] 统一维护所有权，闭合外部停止优先、旧实例借用、停止观察者及候选资源收场，避免自拒绝、互等和提前释放。
- [ ] 更新失败由实际结果消费者直接发布独立 diagnostic 到 processing；维护原始事实、后续恢复及重建错误不互相覆盖。

建议复用 `host_start` 的资源创建与候选收场、`host_maintenance_run` 的进程组与双流收集、`diagnostic.c` 的原子发布边界。发布不得依赖已停止的 writer；完整准备材料保留，已发布后同步失败不重复生成。Python 引擎的原异常及工具失败内容也须送入可传输诊断，而非仅返回本地目录名。

门禁：普通生产入口形成完整业务路径；隔离单元按允许/阻止/未知资格、已提交/未改变/已恢复/仍需恢复、普通资源状态及并发停止分类。单元只证明局部契约，不替代 S5 的真实组合验证。

### S2：强制包、完整备份与可重复恢复

前提：S0 的重置范围及持久恢复契约明确；可以与 S1 的互不依赖部分交错推进。

- [ ] 构建、ZIP 与目录输入使用同一包元数据解释；强制布尔值及完整配置合法性明确，摘要覆盖全部输入。
- [ ] 发布入口保存实际部署绑定；强制新配置核对同一路径，恢复不依赖旧配置可解析、旧环境导入或旧状态库打开。合法目录切换同步绑定事实。
- [ ] 强制清空前完整保存全部约定对象及原有存在事实，核验内容、元信息并完成必要同步，随后才记录修改意图。
- [ ] 强制分支建立干净环境、发布完整配置、使用正式初始化能力建立新库与目录，并由新配置导出能力说明。
- [ ] 普通和强制分支的失败及恢复再次中断均从完整备份继续；提交不确定时读取并核验持久事实，可靠提交后不因诊断失败回滚。
- [ ] processing、日志、稳定入口、备份和设备存储保持所有权边界。符号链接、路径重叠、原对象缺失、旧库不可解析及备份操作失败按实际事实分类，不以错误解释为不存在。

建议将完整配置嵌入既有 `RELEASE.json`，减少外层 ZIP 成员变化。保留旧稳定路由可理解的基础记录形状时，不得编造原数据库身份或元信息；必要时明确维护入口发布基线，由同一组件发布能力安全建立新入口。新的恢复材料应由事务冻结记录完整定位，不依靠安装后的新包重新解释。

门禁：逐项备份、清空与恢复集合对应；所有副作用都有修改前持久定位和可重复恢复；强制路径不能落回要求旧库迁移的普通分支。

### S3：接通部署与第三方参考入口

前提：S1/S2 生产接口已确定。

- [ ] host-demo 使用正常初始化后的更新调用，并继续普通工作；移除主程序自行判断恢复和重新运行的分支。
- [ ] 完整安装入口与本地 deploy.py 都发布维护入口、记录实际绑定并传给普通启动器。
- [ ] 构建器提供普通包及强制包所需参数和校验；版本仍从各组件权威来源读取。
- [ ] 更新操作教程、组件 README、接入设计、技能及交付模板只表达当前有效流程，给出可复制的最小 C 示例和正常启动命令。

门禁：新部署能够自动取得恢复能力；文档与实际生成入口、参数及包格式一致；不留下让主程序解释内部结果或手工触发恢复的必要步骤。

### S4：独立审查与局部验证

- [ ] 独立审核测试的边界、导入隔离及状态分区，再运行受影响的隔离单元。
- [ ] 生产 Release 库和演示编译，公开示例静态编译，生成协议与源码一致，差异与文档链接检查。
- [ ] 独立审查固定源码及完整 diff，修复确证问题，复核相关共享入口与同类状态。

不因用例通过降低状态覆盖或删除现有有效反例。记录命令、源码身份、日志和退出码；原有通过范围只在新变化影响时重验。

### S5：容器内实际升级及中断恢复验证

前提：S1–S4 的生产链路和必需修复已经集成；使用正式构建和发布入口创建全新部署。

- [ ] 正常离线更新成功，C 调用只返回成功，进程自动运行新包，配置、历史和媒体按普通模式保留。
- [ ] 包校验失败时原部署未修改并恢复运行；安装或迁移阶段受控失败后完整回滚，调用返回失败，diagnostic 直接出现在 processing。
- [ ] 修改意图之后中断更新，使用普通主程序启动自动恢复并运行；恢复过程再次中断后仍可继续。
- [ ] 强制重建成功：新完整配置生效、旧额外环境文件移除、新库身份和空工作区正确、processing 原文件保留。
- [ ] 强制重建失败及中断：原配置、环境、数据库及边文件、staging、ready 完整恢复，processing 中主程序实际变化不被还原覆盖。
- [ ] 验证旧状态库不可解析或缺失、旧环境不可导入时的强制路径；对无旧可运行部署的失败，只报告原状完整恢复，不能声称修复了原业务故障。
- [ ] 汇总实际场景、源码及测试包身份、命令、日志、退出码和数据比对证据，记录未执行的目标 ARM64、真实设备和物理断电范围。

实际验证允许受控工具替身注入安装失败或设置中断门闩，但恢复、文件、锁、离线安装和主程序的真实协作须执行，不用替身结果代替整个事务。验证材料保留在独立 tmp 目录；不为验收向生产添加测试专用故障开关。
