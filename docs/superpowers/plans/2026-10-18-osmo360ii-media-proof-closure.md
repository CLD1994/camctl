# OSMO 媒体事实与保存守卫闭合计划

> **执行者要求：** 使用 `superpowers:executing-plans` 与测试先行流程，在独立媒体工作区修复；完成整组状态矩阵后再交付，不逐个追加局部例外。

**目标：** 修复媒体阶段提交 `98ae971` 中原输入已知失败分类和修复成功保存的共同缺口。此计划细化[完成契约实施计划的任务 3](2026-10-18-osmo360ii-capture-completion.md#任务-3逐流媒体事实与修复)，维护媒体工具与声明采用单原片媒体处理的任务所需的逐流事实和保存守卫，遵守[原片保留与核验结果](../../architecture/camera-recovery.md#原片保留与核验结果)。OSMO 360 II 普通录像当前的完成及交付规则由[分段产物设计规格](../specs/2026-10-20-osmo360ii-record-segmentation-design.md)维护，本页的媒体工具验证不代表该分段业务已经实现或验收。

**基线与范围：** 媒体工作区以 `98ae971` 为冻结基线；修复不得改变公共媒体字段、SQL 表结构、原片身份、原任务、取消契约或其他设备的既有规则。预计修改集中在 `capture/media_facts.py`、媒体执行、媒体保存命令、具名守卫及必要的受限读取端口；具体模块边界按真实数据流决定。

## 根因与不变量

原输入探测经过检查保存或修复准备保存进入历史，再由处理器、录像结束命令及独立成功守卫读取。当前共同分类只处理流时长和缺失视频，漏掉可靠容器时长不足；检查没有达到 `COMPLETED` 时，已有的短容器事实因而可能被控制完成依据覆盖。

修复执行层已经核验实际成品，但两种成功保存入口与独立处理守卫主要核对字节和用途，新探测成员只校验结构。后续提升正式产物依赖保存的成功状态，不能弥补此前遗漏的媒体资格。录像成功守卫缺少受限读取端口时也不能跳过原输入核实。

必须同时成立：

- 公共 `media.duration` 仅为原片实际 `format.duration`；逐流事实单独保存，不用最短流时长替换公共字段。
- 动作结束前已知原片不足目标或明确缺少必要主视频时，不允许其他控制依据把它改成成功；未知与修复输出失败不能冒充原片损坏。
- OSV 的修复成功必须在执行、保存、独立守卫和正式产物提升处消费同一媒体资格及身份关系，不能借用旧成功入口绕过。
- 保存未知和重送沿原完整申请及原 key 核实，不重新探测替换已取得事实，不重新启动录像。
- 读取限定原计划、处理身份及输入／输出文件，按页或逐行读取必要历史；不加载全库历史或扩大常驻状态。

## 原输入分类矩阵

可靠探测没有工具／结构错误时，各项事实独立判定；`no_video_stream` 是明确缺视频的事实。工具失败不授予其附带值可靠性。已可靠保存的其他失败事实仍然有效。

原容器时长|必要流事实|原输入分类
-|-|-
已知不足目标|充分或部分未知|已知失败，不能按控制完成提交成功。
达到目标或未知|任一必要主视频或实际音频明确不足目标|已知失败；视频字段未知不能掩盖短音频。
任意|明确缺少两路必要主视频，包括空流的 `no_video_stream`、只有音频、全部为封面或仅一条主视频|已知失败；未知视频用途不能补造成缺失。
达到目标或未知|必要字段未知，且没有其他可靠失败事实|保持未知；不补造损坏，也不凭此否定独立可靠控制依据。
达到目标|必要事实充分且合格|按原检查、控制和修复规则继续。
探测工具或结构失败|没有其他可靠失败事实|保留探测失败，不推断原片损坏。

上述分类分别贯穿 `REQUIRED`、直接计时的 `NOT_NEEDED + NOT_PERFORMED`、已保存准备事实后的 `RUNNING` 恢复，以及有／无控制完成依据。没有执行完整检查时不得伪造 `COMPLETED` 检查。

## 修复资格与身份矩阵

原输入、成品及保存条件|处理
-|-|-
原输入探测缺失、必要字段未知或已知不合格|不能取得 OSV 修复成功资格；保留实际原因，不发送不能依据原事实构造的修复调用。
成品探测缺失、必要字段未知、工具错误或实际容器不合格|拒绝保存成功与提升。
主视频数量不为两路，或成品含附加封面|拒绝保存成功与提升。
视频编码／画面尺寸改变，或实际音频集合改变|拒绝保存成功与提升。
可靠容器时长或任一路必要流时长不足目标|拒绝保存成功与提升；不得用另一种时长事实补足它。
探测、处理、输入副本或本次输出归属不一致，或跨计划取得依据|拒绝申请，不取其他处理的成功事实补足。
原片合格，仅成品不合格或工具失败|保存修复失败并保留 OSV；不因此否定独立采集依据。
原输入与成品全部合格，身份和原处理一致|允许保存修复成功；后续按原提升规则登记独立 MP4。
旧非 OSV 处理与历史|保持既有语义，不强制新增 OSV 专属事实。

读取端口是独立录像成功守卫的前提：缺失端口或不属于原计划时拒绝，不解释为“没有原输入问题”。媒体事实的真实性仍由真实工具调用及其原申请提供，守卫核对保存事实之间的语义和关联，不重复执行 ffprobe。

## 执行顺序与验收

1. 先审计现有数据流并登记所有消费者：正常媒体执行、`_RepairSuccessCommand`、`_RepairResultCommand` 成功分支、独立处理守卫、正式产物首次提升、录像完成命令及独立成功守卫。复用入口逐一核对两类修复成功命令、`FinishCaptureCommand._reuse` 原 key 重送、`FinishCaptureCommand._recover` 新 key 的已完成结果恢复；两个正式提升恢复入口在共同的 `_verify_recovered_outputs` 或等价边界复核保存的媒体依据，不把已经提升的文件重新套入首次提升保留状态要求。原片选择和文件完成上下文由协调者保留，不在此重新实现。
2. 增加最窄失败测试并记录 RED。原输入重点反例为“短容器＋流充分”“短容器＋流字段未知”、空视频流、短音频＋视频用途未知，覆盖三个处理阶段和控制依据分区。独立守卫另验证缺少读取端口及错误计划范围。
3. 在共同原输入分类中实现容器、流及缺失事实的独立判断；处理器、保存与守卫复用该分类。公共时长及检查阶段保持原语义。
4. 增加两类修复成功保存入口、独立处理守卫和提升入口的失败测试：缺失 source／output probe、缺流／多流／封面、编码／尺寸／音频集合变化、短容器／短流、错误输入／输出／处理／计划，以及合格成功对照。
5. 用同一受限事实入口核对原 OSV 输入副本、可靠 source probe、本次 output probe 及目标时长；执行层与持久化成功门槛一致。不得仅在正常调用者预先检查，也不得仅检查 JSON 结构。
6. 验证提交前／后 UNKNOWN、同 key 原申请重送、改变探测输入拒绝、重开数据库、`RUNNING` 恢复；确认复核不重新探测、不生成第二次修复输入申请，不把旧非 OSV 历史改成新契约。
7. 运行相关单元及最窄真实仓储／媒体集成，保留完整命令、日期、环境、日志和退出码；真实双视频与音频样本仍须通过实际修复、全流解码及原片不变校验。
8. 检查完整 diff 并独立提交修复。协调者独立复核冻结提交后合并，最终整合快照分别运行 unit、capture、bootstrap、history、persistence、host_files 及安装版联合链。此前通过结果只归属于其实际快照；通过软件门禁后才开始新 TX2 拍摄。

本计划不增加用户决策。完成状态由[OSMO 完成契约实施计划](2026-10-18-osmo360ii-capture-completion.md)统一维护，实际证据记录于[组件验证记录](../../camctl/verification.md#osmo-360-ii-完成依据与正式接入的复核2026-10-18)；本页只维护本次修复的输入分类、责任边界和执行顺序。
