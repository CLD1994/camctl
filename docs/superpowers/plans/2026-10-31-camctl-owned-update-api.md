# camctl 更新能力与 C 接口实施计划

## 目标与硬性边界

行为由[更新接入规格](../../architecture/software-update-interface.md)及[版本与恢复规格](../../architecture/versioning-and-updates.md)定义。更新实现归 camctl，随 wheel 提供；Python 专用更新包交付 wheel、离线依赖及必要元数据。`camctl_host.h` 新增更新接口，停止本模块普通工作后执行维护，返回后保持停机，由主程序重启。

保留 V9 维护基线、原虚拟环境原位更新、完整环境与数据库备份、适用能力文件恢复、残留写入者锁资格、断电及强制终止后先恢复、文件归属和诊断责任。完整三组件部署包继续满足其首次安装契约。公共 C/Python 更新表示在根 `protocol` 唯一维护。

不新增或运行集成测试，不执行真实安装、原环境更新、数据库操作、设备或物理断电。纯单元在导入前隔离真实包资源、文件、用户环境、数据库、线程和子进程；新增测试先独立静态复核隔离，再执行。组件构建资源和发行物实际组合保持未验证，不以单元或静态检查替代。

## 已确认的数据流

1. camctl 源码生成 wheel 内独立维护引擎；部署发布逻辑提供虚拟环境外的稳定入口与部署绑定。
2. host 从显式 `updater_path` 调用组件维护能力；正常启动前先检查是否存在阻止启动的更新责任。
3. 更新入口先按未完成记录运行冻结引擎恢复；只有恢复已核实才处理当前包。
4. 当前包经完整校验后冻结自己的引擎，可靠保存恢复材料和意图，更新原 Python 环境，并调用新发行物的数据库副本迁移。
5. 文件发布、最终核验和可靠完成由同一事务模型决定；失败按已确认状态恢复，结果通过公共协议交给 host，普通业务不自动恢复。

既有恢复模型的迁移由一个实现负责人统筹，不能将 C/Python 状态、稳定入口、引擎路由、交付清单及其消费者交给相互独立的实现。根代理负责规格、文档、进度和集成；独立评审只读复核。

## 实施与验收

- [ ] M1：确定组件归属、稳定引导、Python 更新包与 C 生命周期契约，完成端到端计划审查。
- [ ] M2：迁移维护引擎及其状态模型，接通 wheel 资源、独立引导发布、首次旧环境接入和恢复优先路径。
- [ ] M3：接通 Python 专用更新包的构建与校验，并同步完整部署包的初次安装与维护入口发布。
- [ ] M4：建立公共更新结果与启动资格协议，新增 C 配置、阻塞更新接口、停止协调和启动检查，接通演示入口。
- [ ] M5：迁移并补齐公开入口的隔离单元，完成静态检查、独立源码复核、按依赖集成及验证记录。

模块名、内部接口、C 结构体的具体划分及提交拆分属于实现预估。建议稳定入口只负责路由，业务事务继续复用原更新实现；引擎资源只从 app 权威源码生成。旧环境配置与元信息优先在其健康解释器的隔离探测进程读取，避免新引擎已占用 `camctl` 导入命名空间后误读新代码。

每阶段须接通真实生产调用方及相应失败路径，不能只提交辅助模型。验收覆盖健康更新、准备阶段失败、修改后失败、可靠完成记录未知、恢复再次中断、首次引导未发布、未初始化及已停止调用、并发停止或更新、配置不一致、启动时存在未完成责任、缺失或矛盾的机器结果。旧终态记录不继续约束合法变更后的新配置。
