# 基准目录读取等待与恢复修复计划

**目标：** 分段拍摄在读取启动前文件基准时，其他流程可以继续检查已有责任；尚未返回的读取不得使会话以 `state_db_error` 退出。

**依据：** [相机拍摄与恢复](../../architecture/camera-recovery.md)、[会话错误与恢复边界](../../architecture/session-errors.md)、[实施规则](../../../.agents/rules/implementation.md)。使用 Python 3.11、现有目录读取拥有者及事务仓储，不改变公共协议或数据库结构。

## 触发场景与行为契约

分段拍摄将基准目录读取交给后台任务。取消、调度和残留流程共用原基准拥有者，并会在各自推进前恢复已经形成的保存申请。目录读取尚未返回时，没有结果保存申请是合法状态；该状态不表示保存失败。

| 原拥有者状态 | 共同恢复入口的处理 |
| --- | --- |
| 原目录调用仍在执行或向实际拥有者交付结果 | 返回等待状态，不消费该拥有者仍在交付的结果，不释放占用，不启动新的目录或拍摄调用 |
| 原调用尚未取得可消费结果，且没有待提交的保存申请 | 保留原责任并等待，不虚构数据库错误或目录成功 |
| 已形成结果保存申请，但事务回执未可靠完成 | 继续使用原申请及原操作键核实；仍不可靠时按状态库错误停止，不读取下一页 |
| 目录调用可靠返回实际读取错误 | 原拍摄流程登记准备失败；不得发送 START，按既定规则结束及释放占用 |
| 目录结果、各页和最终固定均可靠保存 | 原拍摄流程重新检查取消和启动窗口，再申请 START |
| 动作取消或过期时原调用仍未收场 | 保留原调用及占用；实际调用结束、原保存可靠完成后才按终态释放规则收场 |

普通基准和分段基准共用同一等待分类。原页、操作键、页游标、读取次数、实际返回及重试预算保持原身份；状态分类不得以 `database_error is None` 推测数据库操作成功。

## 实施与验证

建议修改位置为 `capture/baseline.py`、`capture/segment_baseline.py`、`capture/handlers.py` 和 `bootstrap/lifecycle.py` 的共同入口；实施时可依实际控制流缩小修改范围。

- [ ] 在 `tests/integration/bootstrap` 增加确定性反例：目录页由事件保持等待，通过生产共同恢复入口检查，不退出、不取消读取、不发 START；原调用返回后原基准可靠固定。
- [ ] 覆盖普通与分段基准、原结果保存失败、取消后仍在读取及恢复原保存申请，先确认反例在旧实现失败。
- [ ] 在共同基准恢复边界区分等待与保存未完成，审计所有调用者，修复后运行反例。
- [ ] 顺序运行相关 `bootstrap` 与 `capture` 集成测试，以及受影响单元测试。记录原有失败，不以放宽断言使其通过。
- [ ] 独立评审实际差异和验证证据，更新 [camctl 验证记录](../../camctl/verification.md)。
- [ ] 构建并核对安装版，保留现场快照。使用禁止设备调用的正式 CLI 恢复旧计划，确认不会补拍且可以生成后续终态报告，再交付用户复测。

## 验收重点

正常等待不能成为会话故障；真实保存失败不能被等待分支吞掉。恢复不得重复读取已经取得的页、替换原保存申请或重复拍摄。现场恢复、软件回归和真实相机重新拍摄分别记录；本修复不自动重拍用户计划。
