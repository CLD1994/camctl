# Action6 与 OSMO 360 II 延时摄影领域执行计划

> **执行者要求：** 使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans` 按领域实施。执行前读取本页及对应领域计划，按复选框记录实际进度；测试、安装验证与设备验收分别留证。

**目标：** 使 Action6 与 OSMO 360 II 共用延时间隔、采集时长及严格组合规则，完成两款候选参数、命令映射、客户端和样例的同步；为 OSMO 360 II 接入正式执行，并在 ARM 上完成最短允许组合的拍摄、独立取回和报告确认。

**架构：** 驱动维护两款相机共用的时间参数权威定义并生成标准 Schema，各型号分别组合自己的曝光和输出结构，客户端消费其规则。具体相机契约接入已有控制、目录基准、延时等待、产物及恢复流程；发行物和 C host 复用已有交付链。命令编码和完成依据按型号分别作为后续任务的输入门槛。

**技术栈：** Python 3.11、JSON Schema Draft 2020-12、TypeScript、React、Ajv、ADB、SQLite、现有 C 接入模块；依赖版本使用各组件声明和锁文件。

**规格：** [参数范围及组合关系](../../hardware/camera-control-handoff.md#间隔与采集时长限制)、[候选编码](../../camctl/timelapse-command-encoding.md)、[最短实机演示](../../hardware/camera-demo-validation.md#osmo-360-ii-的最短实机演示)、[相机接入设计](../specs/2026-10-10-camctl-real-camera-demo-design.md)、[能力与参数](../../architecture/camera-capabilities.md)、[延时执行](../../architecture/camera-capture.md)、[客户端编辑](../../architecture/client-editing.md#参数选项联动)。

## 全局约束

- Action6 与 OSMO 360 II 的时间参数允许值共同由[参数限制](../../hardware/camera-control-handoff.md#间隔与采集时长限制)定义；采集时长必须严格大于间隔，各有相同的 134 种合法时间组合。两款演示使用该专题引用的最短时间组合。
- 生产参数定义是运行时权威来源，Schema、能力说明及有关文档表格从它派生。客户端、诊断脚本、样例和测试不各自维护完整允许值清单。
- `interval_s` 与 `duration_s` 继续以秒表达；数值按精确数学值校验，布尔、字符串与数值不得隐式互换。没有指定的参数不补默认值。
- 当前 Auto 与手动曝光的选择保留。时间参数的扩展不隐式切换曝光，不把普通录像的 EV 字段加入延时 Auto 分支。
- 首次受理固定原输入、生效参数、设备绑定及执行定义。同请求重送和重启恢复使用原事实；说明、驱动或配置更新不改写已经受理的要求及历史。
- `00`、参数读回、实际开始、采集结束、单文件写完和集合齐备分别表达。缺少状态查询不自动要求新增查询接口，也不自动建立时间与产物完成保证。
- 现有 [TX2 十条命令](../../hardware/camera-demo-validation.md#osmo-360-ii-的-tx2-手工复验顺序)保留为既有试验记录。新演示采用独立请求和资料目录，不覆盖原记录；结果未知不补发 START，不以新请求复拍掩盖原任务。
- Action6 延时的曝光、视频/RAW/JPEG 输出及命令编码按自身契约维护；两款相机的时间规则相同不建立相同的控制响应、结束或停止保证。普通录像、Hasselblad 及公共动作协议沿各自契约，不重建调度、取回或报告系统。
- 当前整秒域按[候选编码契约](../../camctl/timelapse-command-encoding.md)形成样例推导候选，完整保留各型号、原曝光上下文及输出模板的非时间字节。纯候选、参数设备生效和正式执行分别验收；未知字段含义、未观察位和模板适用性不由数值可表示性证明。
- 本计划中的文件拆分、内部名称、Schema 具体形状和提交拆分均为实施建议。调整时同步生产者、消费者和验证，不改变上述行为及项目规则。

### 建议的 Schema 交接形状

P 与 C 首先共同核对以下标准子集，并把最终选择同步到两边测试：根对象封闭，两款时间属性及关联条件由同一来源生成；根 `allOf` 按允许时长生成 `if` / `then`，条件显式要求判别字段存在，对间隔施加相应严格上界；`exposure` 是独立的对象 `oneOf`，`outputs` 沿各型号允许值。规则不采用私有关键字，不将时间比较写成客户端的设备特例。

P 继续通过 `candidate_capabilities(driver_id) -> tuple[ActionCapability, ...]` 交付定义，D 通过既有 `settings_for(...)` 和 `CameraContract` 消费。C 将完整原 Schema 作为校验依据，派生目录仅用于选项显示。E 从已安装的实际 `describe` 生成计划；测试注入合同与正式内置合同分别验收。

### 顺序与并行边界

1. P1 与 C1 先对齐上述子集及界面状态规则；随后 P 的参数工作、C 的通用目录工作和 D0 的设备编码资料整理可以并行。C0 的精确枚举校验是 P3 和客户端完整交付的前置。
2. D0 的对应型号有界候选规格通过审阅，且 P2 的可信原生效参数接线交付后，才能执行其 D1；纯候选所需的时间关系已有多组样例依据，其他工具和设备输入仍独立核实。OSMO 可先交付最短候选的软件生成与派发验证供 D2 取证，其完整参数域覆盖须在 D3 前完成。Action6 的编码及 D1A 独立推进，缺失时不阻塞已满足条件的 OSMO 取证或接入。
3. P2 的 OSMO 部分、D1 的 OSMO 完整映射、D2 完成后执行 D3；D4 验证正式任务的失败、取消和恢复。Action6 的正式延时仍按原 T9 门槛处理。
4. E1 可先使用测试合同验证两款最短候选样例及安装资源；涉及设备派发的场景分别等待该型号 D1。正式能力不因该项通过而启用。E2 的正式 OSMO 安装版链及联合回归依赖 D3/D4、C3 和 E1。
5. E3 的 ARM 正式演示依赖 E2。D2 的定点资料核对与 E3 的完整业务验收分别记录，不能互相替代。

## 审查重点

1. 两款的等值、反向大小及列表外输入必须被三处同源校验拒绝；1.0 秒与 1e0 秒按数学值等同于 1 秒，邻近但不相等的数字不能匹配枚举。Action6 的 5400/6000 秒旧样例不再作为新请求接受，旧冻结事实与只读复查保留。由 P1/P2、C0/C3、D1A、E1/E2 覆盖。
2. 时间组非法或有未完成输入时保留原值；曝光分支不能丢失，修改一个字段不自动替换另一字段。由 C1—C3 覆盖。
3. 编码或执行事实缺失时仍保持候选；不得由测试注入、状态标签或包内样例开放能力。由 D0—D3、E1/E2 覆盖。
4. 设置失败、启动未知、USB 断连、取消及保存结果未知，均不能造成第二次 START、替换基准或提前释放责任。由 D4、E2/E3 覆盖。
5. 文件列举错误、空集合、不合格产物和事实未知分别收场；源文件、已确认产物及报告确认各自保留。由 D3/D4、E2/E3 覆盖。

## 验证与交付约定

执行前读取 [camctl 测试指南](../../../apps/camctl/tests/AGENTS.md)、[客户端运行说明](../../../apps/client/README.md)及[跨组件测试说明](../../../tests/integration/README.md)。Python 使用部署版本 3.11；先核对解释器、SQLite 运行条件和锁定环境。客户端使用组件声明的 Node.js 版本与锁文件。

各领域的 `P` 命令从仓库根按下式定义，之后保持当前目录为仓库根：

```bash
P() {
  UV_PROJECT_ENVIRONMENT="$PWD/apps/camctl/.venv311" uv run --project apps/camctl --group test --python 3.11 pytest "$@"
}
```

单元可合并必要文件。组件集成按目录分进程、同工作区顺序执行；根组合测试单独运行。设备调用、包构建、真实文件、线程和进程不放入单元测试。每项软件任务先运行能证伪该项契约的测试，确认目标失败后实施，再运行必要回归；资料整理与实机采集按实际结果验收，不人为制造测试红灯。

每项交付包含实际 diff、验证命令、环境、日志及退出码；软件、发行物、ARM 和设备结果分别写入对应验证记录。达到完整目标范围后，不在没有新改动或疑点时重复扩大验证。提交以领域内可独立审查的交付为单位，并核对工作区中原有改动；计划编写本身不代表开始实施或执行相机命令。

本计划的软件结果见[延时参数与候选软件验证](../../camctl/verification.md#延时参数与候选软件验证2026-10-16)，客户端完整门禁见其引用的客户端验证记录。各领域计划继续分别维护任务状态；设备依据、正式接入与 ARM 验收沿原前置条件推进。
