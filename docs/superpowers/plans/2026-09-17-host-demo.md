# C 接入模块与终端演示实施计划

> 执行方式：使用 Superpowers executing-plans，由当前 Agent 顺序实施，不使用 subagent。每项先验证失败测试，再实现并验证。

**执行状态：** 组件实现和开发环境验证已完成；目标主机、真实 CLI、设备与断电验收见[验证记录](../../host-demo/verification.md)。

**目标：** 在 `apps/host-demo` 交付可独立构建的静态库、公开 C 头文件、终端调用示例及分开的单元和集成测试。

**架构：** 一个进程工作线程独立管理一个 `run` 和一个串行 `submit`，一个日志线程写有界日志；主程序同步领取文件。命令调度使用可独立测试的内存状态，系统操作在明确的协作者边界执行。

**技术：** C11、POSIX/pthread、yyjson、cmocka、CMake/CTest。

**规格：** [行为规格](../../host-demo/design.md)、[实现设计](../../host-demo/implementation.md)。

## 已确认契约与项目规则

- 公开接口为 `camctl_host_init`、`camctl_host_submit`、`camctl_host_claim`；前两个接口以 `0/-1` 表达本地接收结果，领取无返回值。
- 初始化一次，成功后持续运行；不添加退出、重建实例、业务数据库或传输接口。
- 初始化可附带首次路径，其后所有路径使用 `submit`；复制字符串，文件仍由主程序保留。
- 同时最多一个未确认退出的 `run` 和一个 `submit`。提交及其启动失败重试保持 FIFO 顺序，处理中的路径仍占容量。
- 自动重试共用计数，默认三次、每次等待五秒，使用单调钟；实际自动尝试前计数，成功不清零。
- `needs_run: true` 可合并待启动要求，并获得一次正常启动机会；明确启动失败保留要求，但不能反复免费启动。后来新的 true 可以重新触发正常启动。
- 首次计划只在确定 camctl 从未启动时保留；已启动或无法确认时，后续 `run` 不再附带路径。已运行的 `submit` 不重送。
- stdout 必须同时满足消息结构与退出状态；日志、截断输出和退出码本身不代表成功。管道持续排空，输出和日志有界。
- 领取先完整收集一次文件列表，再逐个原子移动并覆盖同名文件；单项失败继续，目录故障结束，已经移动的文件不回退。
- 运行依赖源码随组件交付，cmocka 仅进入测试构建。公共机器协议来源仍是根 `protocol` 与架构文档。
- 单元测试在同一进程内使用受接口约束的替身，不接触真实文件、进程或时钟；真实组合另用集成测试。

## 实现预估与环境限制

以下文件划分、内部函数名称、实现顺序属于建议，允许随实际数据流调整；不得改变上面的契约。

建议文件：`include/camctl_host.h`；`src/host.c`（公开入口与工作线程）、`scheduler.c/.h`（命令选择）、`result.c/.h`（输出检查）、`process.c/.h`（POSIX）、`claim.c/.h`（领取）、`logger.c/.h`（日志）、`demo.c`；`tests/unit` 和 `tests/integration`；`vendor` 保存确定版本和校验信息。

编写本计划时的开发环境是 x86_64、Ubuntu 24.04、GCC 13.3、glibc 2.39，当时仓库尚无真实 camctl。目标 arm64 Ubuntu 18.04、第三方工程回收方式、设备和断电验证须在交付说明中独立列出，不能以可控 CLI 或本机测试代替。依赖先固定用于可重复构建的版本，目标适配验收仍待实机确认。

资源落实建议：路径最多 4095 字节；领取列表最多 16 MiB，超限按未完成遍历处理；每轮每条管道读取最多 64 KiB；最长 50 ms 检查进程退出，通知使用非阻塞管道。JSON 解析使用与 stdout 上限对应的有限内存池。配置整数设合法范围并检查乘法溢出；初始化失败清理已经创建的资源，后台线程只有全部建立后才开始工作。

| stdout | 实际退出 | 分类 |
| --- | --- | --- |
| 单行 succeeded，submit 含布尔 needs_run | 正常 0 | 成功 |
| 单行 error，reason 字符串、details 对象 | 正常 1 | 会话错误，未知 reason 仍合法 |
| 任意正常消息 | 消息与退出码不一致 | 异常 |

| 任意 | 信号或无法取得退出状态 | 异常，保留无法确认的信息 |

```c
const char fixture[] = "{\"kind\":\"succeeded\",\"body\":{\"needs_run\":true}}\n";
assert_int_equal(host_result_parse(HOST_SUBMIT, fixture, sizeof(fixture) - 1,
    HOST_EXIT_NORMAL, 0).kind, HOST_RESULT_SUCCESS);
```

测试实际用 `sizeof(fixture) - 1` 取得字节数；预期分类和 needs_run 使用手工常量，不调用解析器构造预期。协议不明确的扩展字段允许保留；参与判定的字段不能有重复键歧义。

## 任务二：命令调度、共享重试和提交容量

- [x] 编写 `tests/unit/test_scheduler.c`，使用显式时间输入和受约束启动结果，先验证下表分支失败，再实现调度器。文件队列容量包含当前提交；拒绝不改变已接收队列。

| 条件（从上至下判定） | 下一步 |
| --- | --- |
| 对应子进程未确认退出 | 保持监控，不启动替代进程 |
| run 空闲且有新的正常启动机会 | 消耗该机会，合并重试；首次路径是否附带按启动证据判断 |
| 命令等待自动重试，预算耗尽 | run 保留尚未完成要求但停等；submit 结束当前路径，处理下一份 |
| 等待重试、预算未耗尽、尚未到期 | 不启动，处理其他事件 |
| 等待重试、预算未耗尽、已经到期 | 先增加共享计数，再启动原命令或裸 run |
| submit 空闲且队列非空 | 首次启动队首 submit，不扣重试次数 |
| 无工作 | 待命 |

```c
host_schedule_need_run(&state);
assert_true(host_schedule_take(&state, HOST_RUN, 0));
host_schedule_spawn_failed(&state, HOST_RUN, 0);
assert_false(host_schedule_take(&state, HOST_RUN, 4999));
assert_true(host_schedule_take(&state, HOST_RUN, 5000));
assert_int_equal(state.retries_used, 1);
```

- [x] 验证 true/false/错误的先后组合，pending 不能因 false 或旧 run 错误消失；启动失败的旧 pending 不能产生无限免费启动。
