# 多组件仓库目录整理执行计划

> 执行方式：当前 Agent 使用 superpowers:executing-plans，在当前分支直接实施。

**目标：** 客户端、Python CLI 与 C 主程序 demo 按运行边界组织，共享机器协议具有唯一来源。

**架构：** `apps/client` 保存客户端全部源码、测试和依赖配置；`apps/camctl` 与 `apps/host-demo` 提供组件入口，实际实现按各自后续任务推进。`protocol` 保存 Schema 与标准样例，`docs/architecture` 保存全局语义，组件文档各自归档。

**技术：** TypeScript、Node.js、npm；Python 与 C 为已确认的后续组件语言。

**规格：** 用户已确认的三组件目录设计；迁移后的正式契约保存于 `docs/architecture/repository-layout.md`。

## 已确认契约

| 对象 | 输入与变化 | 必须保持的结果 |
| --- | --- | --- |
| 客户端 | 从组件目录安装、构建、测试和启动 | 界面、业务协议、校验和恢复行为保持一致 |
| 数据 | 当前根目录 `data` | 不移动、不清空；日常服务通过显式绝对路径使用原目录 |
| 协议 | Schema 和标准样例迁移到 `protocol` | 内容与报告文件摘要不变，生产代码与测试读取同一来源 |
| 文档 | 移动全局和组件设计 | 本地文件链接解析到新位置，实施计划仍保留在原计划目录 |
| Docker | 组件 Dockerfile，仓库根为构建上下文 | 镜像包含客户端和协议资源，挂载数据路径仍指向根目录 data |
| demo | 可复用生成器与输入归入 demos | 原 tmp 素材和生成记录保留，新生成结果写入忽略目录 |
| 未实现组件 | 建立说明入口 | 不声称 CLI 或 C demo 已可运行，不创建假实现 |
