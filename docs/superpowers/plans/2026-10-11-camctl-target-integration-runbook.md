# camctl 目标环境联调操作步骤与通过判据清单

本清单为路线图剩余三项（第 36 条目标部署与设备联调、第 398 条目标环境资源测量、第 410 条总验收含部署）准备现场执行材料，供在目标主机（aarch64、Ubuntu 18.04.6，账户 `cld`）执行联调时逐项操作与判定。各项的行为规则、检查输入与通过条件以[部署交接与待核验项](../../camctl/verification.md#部署交接与待核验项)五维表及各自责任专题为权威，本清单只组织执行顺序、具体操作与记录方式，不定义新规则。

三项的执行方式已经确认：按[部署交接与待核验项](../../camctl/verification.md#部署交接与待核验项)五维表在目标环境另行执行，用户于 2026-10-11 确认知晓六节现场联调安排并将配合执行；软件侧待定事项已同日全部裁决闭合（见[决策清单](2026-10-11-camctl-open-decisions.md)），勾选仍以执行记录为准。

## A. 真实电机与主程序业务范围（第 36 条）

软件组合已按[电机验收要求](../../architecture/motor-control.md#验收要求)验证：不重发恢复、慢回调、并行 submit、下一次 run 与相机共存（[电机验证记录](../../camctl/verification.md#电机控制与单向通知验证2026-10-08)）。真机剩余为主程序接入与实际电机运动，规则见[电机控制](../../architecture/motor-control.md)：主程序解释位置的单位、零点与业务合法范围并执行实际控制；camctl 只保证完整通知写入通道。

**前置条件：** 第三方主程序实现并注册 `void motor(int position)` 回调（接口与编译方式见[交付资料](2026-10-08-camctl-host-notifications.md#hn6-演示与第三方交付)，从安装头文件链接静态库）；host-demo 已在目标主机安装运行。

**操作步骤：**

1. 主程序先注册回调再初始化 host（顺序为既有约定），启动后确认注册成功。
2. 客户端编辑电机计划：位置、时间窗口与最大延迟，提交后在窗口内执行 `run`。
3. 主程序侧记录收到的 `int position` 原值，按自身单位与业务范围解释并执行；对超出业务范围的位置按主程序自身规则拒绝，核对 camctl 不更正、不重发。
4. 现场复演软件矩阵中的关键分支：窗口末端与末端之后提交（末端不写通道）、发送结果不确定后的恢复（重启后零次重发）、取消（`canceled` 不发送）。
5. 客户端导入报告，核对电机动作呈现“控制通知已发送”，`input_params` 与原始提交一致。

**通过判据：** 消息写入与回调执行分别观察（动作 `succeeded` 仅证明通知写入，不证明电机到位）；主程序记录实际收到位置及业务范围判定结果；上述分支的行为与[调度与发送边界](../../architecture/motor-control.md#调度与发送边界)、[状态判断与恢复](../../architecture/motor-control.md#状态判断与恢复)一致。

## D. 目标资源测量（第 398 条）

软件侧在有限容量执行器上已完成并发受理与历史恢复（[H7 验证记录](2026-09-30-camctl-history.md#h7-验证记录2026-10-08windows-开发机)）；本项在目标环境实测合计资源与负载行为，通过条件见交接表[目标资源](../../camctl/verification.md#部署交接与待核验项)行。

**操作步骤：**

1. 在目标主机以已安装发行物（非源码目录）运行，记录环境：aarch64、Ubuntu 18.04.6、Python 3.11.17、SQLite 3.53.1、存储类型。
2. 测量主进程、报告子进程及受管工具（`adb`／`ffprobe`／`ffmpeg` 子进程）的合计常驻内存与 CPU：空闲会话、单计划拍摄、报告维护、取回传输各场景分别采样。
3. 负载场景：并发提交多个计划、报告维护与取回传输同时进行，观察受理到终态的实际延迟、队列等待时间与文件任务积压深度，记录数据规模（计划数、文件大小）。
4. 数字与负载、数据规模一并登记，不写成目标性能承诺；超限处置按实际运行证据评估（第一版不预设自适应机制）。

## E. 物理断电（第 36、410 条）

按交接表[物理断电](../../camctl/verification.md#部署交接与待核验项)行与 host-demo 表“主机突然断电”行执行。

**操作步骤：**

1. 确认状态库使用 `FULL` 同步等级与文件目录同步契约（[历史存储](../../camctl/history-storage.md#所有状态库写连接使用-full-同步)），在目标存储设备上运行拍摄与文件写入。
2. 写入进行中切断主机电源；重启后核对：状态库可打开且历史一致；未确定意图的动作零次重发（电机与拍摄各自的恢复规则）；实际文件位置与登记事实一致。
3. C 模块侧按[断电行](../../host-demo/verification.md#仍需真实环境验收)核对 `posix_spawn` 的错误证据与资源限制。

**通过判据：** 重启后各组件按各自恢复规则继续或收场，无静默丢失或补造事实；普通进程终止测试不能代替本项。

C host 已在目标主机构建安装（`HOST_BUILD_TESTS=OFF`），组件测试尚未在 ARM 执行。按 host-demo 表“arm64 Ubuntu 18.04”行：使用实际编译器（GCC 7.5.0）与 glibc 重新构建并执行 Debug、Release 组件测试，范围以[组件验证记录](../../host-demo/verification.md)及当前构建登记为准，确认 `posix_spawn` 错误证据与资源限制。
