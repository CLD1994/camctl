# 读取错误诊断的完整传递与保存

## 目标与依据

人工环境的延时摄影预览在三次读取中均失败，尝试记录只保存了 `segment_transfer_failed: read_failed`。段传输已经取得的原异常、ADB 调用信息和已处理范围，在上层转换错误时没有继续传递。因此，现有证据不能区分源文件提前结束、ADB 调用失败和其他读取异常。

用户要求立即修复，错误信息不能在传递和保存中丢失。既有[读取会话与分段契约](../../camctl/file-runtime.md)已经要求保留原异常、读取与关闭双重错误及实际范围；本计划落实这些要求，不改变读取预算、重试间隔、公共最终错误码或源结束资格。仅运行单元测试，真实设备由用户验证。

## 行为分类与责任边界

| 实际情况 | 传递与保存要求 |
| --- | --- |
| 读取抛出异常，关闭成功 | 保留原异常对象、类型、消息、完整栈和异常链；可靠结束后随原 READ 结果保存。 |
| ADB 已结束但未取得固定长度 | 保留原调用的退出码或信号、传输与输出错误、原 stderr 字节及源范围，不能只保存通用分类。 |
| 分段失败 | 保留分类、已处理范围、同步及写入范围是否可确认、原异常、源结束与源关闭错误；已处理范围不能冒充可靠进度。 |
| 读取与关闭均失败 | 两个错误共同交付；不能由 finally 中的关闭错误覆盖原读取错误，不能把关闭失败解释为可靠停止。 |
| 工具启动、读流任务或停止信号失败 | 保留实际异常与此前已知信息，不伪造退出码或已结束事实。 |
| 原结果提交未知、回滚、取消或重复等待 | 沿用原申请、原错误及完整输入，不增加设备读取或重置预算。 |
| 本地写入、同步或进度保存失败 | 保持实际失败阶段及原有处理分类，不能记作设备读取失败而消耗读取重试。 |

普通取回、自动预览及录像检查和修复的内部读取，使用同一个错误详情生成入口。公共报告继续表达最终业务失败；内部完整诊断随尝试历史保存。诊断使用 JSON 可编码结构；原始 stderr 按字节无损编码，不以替换非法 UTF-8 字符的显示文本代替原始字节。沿用受管工具已有输出上限及截断／失败事实，不新增更小的静默裁剪。

公共异常编码以标准库 traceback 为基础，保留完整异常组成员、cause、context、notes 和已知系统错误字段。循环或共享引用明确编码，不使用默认异常组排版中的宽度和深度裁剪。生产数据字节不作为 stdout 日志重复保存。
