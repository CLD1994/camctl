# camctl 会话接管边界审查与修复计划

本计划覆盖输入受理到 `submit` 接管响应，以及关闭接纳的事务边界。行为依据为[会话协议](../../architecture/protocol-session.md)，任务归属为[会话计划 S1/S4](2026-09-30-camctl-session.md)。内部接口及文件划分是实施建议，不改变公共协议。

## 行为契约

`submit` 在 `BEGIN IMMEDIATE` 内保存输入、历史、投影和独立 ACK，再查询更新后的工作事实。有工作时才探测接纳锁。探测与输入保存属于同一事务，只有事务可靠结束后才能返回 `needs_run`。重复输入没有新增事件时仍在写事务内判断接管。查询、锁操作或提交失败时不得返回成功判断；提交前错误确认回滚后，本次输入及 ACK 不得部分保存。提交结果未知保留原错误，后续重送依原请求身份判断，不重发当前操作。

| 更新后的工作分类 | 探测行为 | 可靠完成后的响应 |
| --- | --- | --- |
| 没有必要工作 | 不探测锁。 | `needs_run=false`。 |
| 有必要工作或未完成的报告责任 | 真正锁冲突。 | `needs_run=false`，由接纳者负责。 |
| 有必要工作或未完成的报告责任 | 临时取得并可靠释放锁。 | `needs_run=true`。 |
| 工作事实或锁操作失败 | 停止判断，回滚本次输入事务。 | 状态库会话错误。 |
| 提交结果未知 | 不输出接管结果，保留原操作身份。 | 状态库会话错误。 |

关闭接纳使用同一工作分类。当前会话已经尝试失败的报告责任与新工作必须分别判断。

| 最终事务内的工作分类 | 接纳资格 | 返回的关闭结果 |
| --- | --- | --- |
| 还有动作、必要收场或新报告变化 | 保持接纳。 | 继续处理工作。 |
| 无必要工作 | 事务结束前释放。 | 可以成功收尾。 |
| 仅剩本次已经尝试失败、没有新变化的报告责任 | 事务结束前释放，责任保留。 | 按 `report_error` 收尾。 |
| 查询或事务失败 | 不返回正常关闭成功；已经释放的资格不重新取得。 | 按状态库错误收尾。 |

工作数量只接受非负整数，拒绝布尔、浮点及其他类型；工作维度只接受实际布尔。未知数量保留为未知，并在分类时拒绝；未知布尔不转换为真假。

## 缺陷与修复建议

1. **事务外的提交接管。** `session.service._submit_session` 在 `AcceptanceRepository.process_input` 提交后查询工作并探测锁，仓储不消费 `ProcessInput.mode`。查询或锁失败时输入已经提交，且锁探测没有数据库写事务串行约束。违反输入与接管共同提交的不变量。建议在事务内核增加有明确职责的结果完成入口，在投影写完、提交之前计算接管结果；受理结果携带可选内部 `needs_run`，实际 `submit` 必须提供事务内接管端口，会话层只消费已完成结果。检查新受理、拒绝、输入诊断、ACK、重送无事件及回滚、提交未知全部分区。
2. **报告失败关闭保留接纳。** `_CloseCommand` 只对 `CAN_EXIT_SUCCESS` 释放接纳，对 `EXIT_REPORT_ERROR` 返回未关闭，与规范的失败机会结束规则不符。建议在没有新工作时释放两种结束分区的接纳，并保留工作分类供会话决定最终错误。检查新变化覆盖失败机会、释放后事务失败以及后续提交。
3. **工作事实接受非法类型。** `WorkFacts` 的数量检查接受浮点，部分布尔维度未检查，真值判断可能把字符串等误认成可靠事实。建议在该值类型拥有者统一验证实际类型，并覆盖每个维度，不能在消费者各自转换默认值。

以上属于原有实现缺陷。原有竞争测试没有经过真实受理入口，属于验收覆盖缺口。修复后须审计 `accept_input`、`process_input`、`run_session`、`execute_command`、`close_admission` 及全部直接输入仓储消费者，确保不存在旁路。

## 顺序与阶段门禁

- [x] T1：先写真实 `submit` 入口的失败测试，证明查询发生于写事务内、查询能看到本次投影、查询或锁失败回滚输入，并覆盖正常接管两个布尔结果。
- [x] T2：在事务内核提供投影写完后的结果完成步骤。新增事件与无事件重送都执行；完成步骤失败按实际错误回滚；提交未知不携带业务成功结果。
- [x] T3：将接管端口接入受理仓储和会话装配，删除会话层事务外的第二次查询及探测。仅验证输入内容的测试明确采用 `run` 受理模式；真实 `submit` 测试保留完整接管行为。
- [x] T4：补报告失败关闭与全部非法工作类型的失败测试，再统一修复关闭规则和值类型。
- [x] T5：组合真实 SQLite、接纳锁和入口验证两种提交/关闭先后、并发提交、ACK、诊断、无事件重送、锁及查询失败、提交未知。单元测试不访问外部资源。
- [x] T6：审计相关生产入口及测试分类，运行相关单元与集成门禁，更新原模块计划和本计划的实际证据，形成可独立审阅的提交。

禁止在事务外再做一次探测来补偿，禁止提前返回成功后保留查询错误，禁止在事务内执行设备、文件传输或报告构建，禁止增加持久化会话表，禁止以直接调用分类器代替入口竞争验证。

## 后续独立工作

默认 `run` 的业务流程尚未装配；`query_work_facts` 仍是阶段 1 查询，只查询未完成动作和 ACK 水位后的报告变化，没有消费当前已有的独立收场及本地报告完成事实。这些事实需要沿所属业务模块逐段审查并闭合，本计划完成不证明默认执行链、所有工作事实或阶段 2 门禁完成。S1/S3/S4 的生产消费者门禁据此继续保留未完成项。

## 验证记录

失败测试首先观察到工作查询处于事务外；查询或锁失败时，计划、动作及历史已经保存。首组测试为 3 项失败、2 项通过。工作类型与报告失败关闭的测试为 47 项失败、29 项通过，失败分别来自非法类型未拒绝、错误类型不符合契约及接纳未释放。

| 验证范围 | 实际结果 |
| --- | --- |
| Python 3.12：acceptance、contracts、devices、capture、outputs、bootstrap、session、persistence 单元测试 | 738 项通过，1 项已有 asyncio 标记警告。 |
| Python 3.11：相同单元测试目录 | 738 项通过，1 项相同警告。 |
| Python 3.12：真实提交边界最终矩阵 | 35 项通过；覆盖新增、重送、拒绝、诊断、有效及无效 ACK、无工作跳过锁、并发提交、两种关闭竞争、查询及探测失败、提交未知和关闭失败后保持关闭。 |
| Python 3.11：最终提交边界、关闭仓储及事务内核集成测试 | 61 项通过，其中提交边界 35 项、关闭仓储 8 项、事务内核 18 项。 |
| Python 3.12：完整组件集成测试 | 539 项通过、9 项失败、3 项已有警告。运行范围包含边界矩阵的前 27 项及关闭规则；后续增加的 8 项由最终边界矩阵独立验证。 |

完整集成测试的 9 项失败均位于 `apps/camctl/tests/integration/outputs/test_qualification.py`，与基础受理修复后的已知结果一致：

- `test_qualification_uses_business_order`
- `test_same_time_obtain_wins_over_processing`
- `test_existing_read_protection_preserves_original_copy`
- `test_cleanup_restriction_rejects_and_records`
- `test_delete_in_progress_rejects_with_dedicated_code`
- `test_cross_device_candidates_do_not_block`
- `test_grant_creates_all_records_atomically`
- `test_internal_processing_grant_skips_delivery`
- `test_unavailable_output_rejects_without_records`

这些失败留待产物资格业务审查，不计作会话接管完成的证据，也没有通过放宽验证消除。完整单元测试中的日志模块尚未纳入本计划门禁；相关日志挂起及关闭警告继续独立跟踪。软件测试不连接真实设备。

独立只读审阅核验了 8 个生产文件及其上下游，独立运行会话单元测试取得 111 项通过，并读取最终边界和回归日志。补齐关闭失败时清理前的真实锁观察，以及正文整份拒绝与 ACK、接管的组合矩阵后，本计划范围没有未解决的阻塞问题。审阅结论不扩展到上述后续独立工作。
