# 来源失败错误实施计划

目标：按[设计规格](../specs/2026-10-24-source-action-failed-design.md)让无产物的来源失败清楚解释预览和默认取回失败。

本计划使用现有 Python、TypeScript、公共错误登记和分层测试。具体内部函数可以沿最窄共享责任调整；规格中的分类、来源身份及产物保留规则必须满足。开发环境直接重建，不增加迁移流程，不执行实拍。

## 步骤与验收

- [x] **1：登记公共契约。** 在公共错误登记加入 `source_action_failed`、`output_selection` 阶段及来源身份详情，扩展来源选择的 SQL 编号约束；生成编号文档，更新预览和取回规格，运行协议及数据库结构检查。公共登记是编号和详情的唯一来源。
- [x] **2：实现生产判定。** 先添加反例并确认原实现失败；普通及分段选择按实际来源状态、完整正式目录和处理完成事实分类。默认及预览来源为 FAILED 且目录可靠为空时保存 `source_action_failed`；正式产物、显式 ID、非失败终态及选择历史边界保持原规则。分段目录存在性使用有界查询；失败受理且 `execution_spec_json` 为 `NULL` 的来源也能经过真实取回与报告路径，且不改写拍摄错误。
- [ ] **3：实现客户端说明。** 在独立工作区按相同协议识别来源失败，展示来源身份及可获得的原失败原因；保留原始详情和来源失败但有产物的展示。先验证失败用例，再实现并运行相关单元、导入及浏览器检查。
- [ ] **4：核对端到端结果。** 新建无相机的软件世界，经真实来源失败、取回选择和固定历史报告验证新码及身份一致性；客户端导入同份报告并显示来源失败。同一冻结边界重建字节不变，其他组成员及显式 ID 结果保留。
- [ ] **5：构建与重置开发环境。** 构建并核对 wheel 及客户端 ZIP；确认执行会话已结束后保留旧诊断并重建主机验证状态库，导出匹配能力说明。客户端使用新目录。记录检查、发行摘要和部署入口，不删除相机媒体。

## 评审重点

1. 来源失败但存在正式产物时仍可取回，不能仅按动作状态短路。
2. 来源查询未知不能冒充可靠空目录；分页必须完成或取得可靠的空集依据。
3. 显式请求中的每个 ID 保留自己的错误，不能被合并成来源失败。
4. 来源级错误详情与失败项中的来源身份一致，客户端不能把其他来源错误归到当前预览。
5. 新协议与新 SQL 配套使用；重置只涉及应用验证环境，相机媒体和归档证据保留。
