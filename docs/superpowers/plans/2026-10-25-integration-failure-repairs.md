# 集成测试失败修复计划

## 目标与基线

从 `implement_camctl` 的 `d9c1bac9` 同步已有实现，保留失败诊断、测试修改授权边界及通俗表达规则。在修复分支中解决[44 项失败诊断](../../camctl/integration-test-failures-2026-10-25.md)所列问题。用户已授权修复测试问题和两项经过设计复核的生产缺陷。历史测试结果保留原身份、源码和范围；新结果另存，不覆盖历史证据。

## 并行步骤与验收

各组使用独立工作树。先核对当前实现及适用规则，重现最窄反例，再修复和验证；已由主分支解决的项目核对实际通过证据，不重复修改。组内出现新失败时继续定位，不能把准备通过当作完整业务通过。修复不得删减原业务验收、扩大启动窗口或吞掉会话错误。

## 两项生产修复必须保持的状态分类

清理的权威依据为分段公共规格的检查副本生命周期及 `file-handoff.md` 的运行预算。实现方式可以调整，但不得通过周期扫描、重启或第二次实际尝试绕开生命周期。

| 文件状态 | 处理 |
| --- | --- |
| 来源结果或归属尚未可靠确认 | 继续核实并保留，不根据文件存在性删除。 |
| 本副本仍有绑定消费者，或真实读取、写入、工具未收场 | 保护实际用途，不提前删除。 |
| 来源可靠提交、本副本消费者结束、实际操作收场，本 run 尚未实际检查 | 本次及时首次清理，发现须沿消费者与来源的真实关联闭合；不受启动历史范围限制。 |
| 没有绑定消费者且原检查已结束的副本 | 来源可靠提交、实际操作收场后首次清理，不等待其他副本的消费者。 |
| 本 run 已实际检查或尝试清理，之后用途改变 | 保持每文件一次规则；复用实际结果，保留后续运行责任。 |
| 查询或删除失败 | 保存实际结果，继续其他责任，不在本 run 循环重试；数据库错误仍按会话错误处理。 |

READ 的权威依据为文件拷贝实际结束规则，以及 delivery／processing／inspection 三种唯一归属。共享集合允许由检查拥有者持有真实干净 ReadEnd；函数和队列组织属于实现选择。

| 读取状态 | 处理 |
| --- | --- |
| 原完整结果申请已经形成或提交未知 | 核实原申请，不能重开读取或重新形成不同决定。 |
| 已有终态或可靠取消 | 沿原事实收场，不建立新读取或媒体检查。 |
| 合法 inspection，实际已完整停止，绑定匹配 | 原拥有者继续本地核验和保存；普通及残留入口不得误报缺 processing。 |
| 绑定缺失，仍缺必要源摘要 | 保存真实 READ 成功与适用业务失败；不把实际成功读取改成未知。 |
| 绑定缺失，摘要已取得或明确不支持摘要 | 按既有规则继续可执行的本地工作，不新开源读取。 |
| copy、ticket、action、member、source 或 observer 关系损坏 | 保留一致性错误及诊断，不伪造 processing、不清空归属、不丢弃结束事实。 |

同类审计范围包括普通拍摄、残留恢复、检查拥有者续接、准备结果核实、用途判断及清理发现。S7、S8 的源码局部可并行；联合安装版测试在两者集成后执行，相关交付与首次清理不依赖额外 run。客户端导入和累计 ACK 按后续实际输入继续核对，不要求原 run 等待远端确认。
