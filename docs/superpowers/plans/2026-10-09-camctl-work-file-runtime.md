# 正常运行的中间文件清理接入计划

**目标：** 正常 `run` 实际处理历史清理责任，并及时处理本次业务形成的无用中间文件。状态库、目录绑定、原归属、文件实际使用及每次运行额度分别判定；维护残留不要求启动独立会话，也不重开业务终态。

**依据：** [运行预算](../../architecture/file-handoff.md#中间文件清理的运行预算)、[取回文件生命周期](../../architecture/obtaining-outputs.md#取回中间文件的保留与清理)、[录像文件生命周期](../../architecture/camera-recovery.md#内部中间文件的保留与清理)、[本地操作收场](../../camctl/file-runtime.md#本地文件操作的完成与故障边界)、[清理进度](../../camctl/database/reports-runtime.md#中间文件清理进度)。

## 生产起点与责任

2026-10-09 的生产消费者核对发现 `outputs.work_files.clean_work_files` 与 `clean_one_work_file` 只有模块定义，正常会话没有调用者。局部集成测试验证了生命周期、历史游标和单文件清理，不能证明正式 `run` 使用它们。`bootstrap.lifecycle._report_assembly` 组装正常流程，`SessionContext.on_session_open` 在会话锁内、受理及时钟事务前固定初始历史依据，可以在同一入口固定清理范围。

`clean_work_files` 每次调用自行建立范围与完整额度。因此不能在每轮调度中直接重复调用并把一次函数调用当作一次正常运行。`clean_one_work_file` 的防重复记录也必须跨业务入口及调度轮次共享。

`WorkFileFacts.operations_stopped` 当前只读取目标拷贝的未结束读取尝试。接入前还须核对媒体工具、分段、校验和移动的真实拥有者；归属终态不能成为文件已停止使用的证明。`host_files.FileTaskExecutor` 已提供默认线程池执行、同文件修改资格和等待取消后的接手，优先复用，不重新实现文件线程或进程管理。

## 行为分区与不变量

| 会话或文件事实 | 行为 |
| --- | --- |
| `submit` 或时钟异常受限运行 | 不开始普通中间文件维护；必要取消及已有实际调用继续各自收场。 |
| 正常 `run` 开始、库及三路径已核实 | 固定原历史候选范围、继续位置与本次额度；调度重入保持同一份运行状态。 |
| 历史候选尚未检查、仍有额度 | 按可靠位置分批处理。无法安全删除也计一条检查；结果及位置可靠提交后继续后项。 |
| 固定历史范围已检查一轮或额度耗尽 | 本次历史维护结束，后续调度不补充额度或扩大范围。 |
| 本次业务新形成无用途文件，且归属及相关实际操作均已结束 | 使用单文件入口首次清理，不消耗历史额度；与历史入口共享原文件身份及本次处理记录。 |
| 文件本次已检查，随后重复发现或用途改变 | 复用实际结果；不进行第二次文件查询或删除尝试。 |
| 文件仍被读取、工具处理、校验、移动或实际接手方使用 | 保持原文件及保护，等待实际使用结束；不从动作终态推出可删除。 |
| 文件已提升或已交接，或文件是报告、日志、故障标记 | 不进入此自动清理范围。 |
| 文件不存在、尚未保存完成结果 | 按本次可靠不存在观察补记完成，不补造旧删除调用结果。 |
| 本地查询或删除失败 | 保存实际失败及原责任；本次不重试，继续后项和普通设备工作。 |
| 记录、结果或位置读取失败，确认回滚或提交未知 | 保存或保留实际阶段诊断，按状态库错误结束依赖该前提的工作；不把失败当作清理已完成。 |
| 主等待取消、实际文件任务已经开始 | 拥有者继续消费实际结果并保存；实际任务结束前不能关闭其连接或释放文件修改资格。 |
| 仅剩历史额度以外或本次失败的清理残留 | 允许正常退出，`needs_run` 使用既有延后维护分类；不增加周期扫描或立即重启要求。 |

## 顺序实施与门禁

内部类、文件划分、回调名称及提交拆分是建议，正式契约是约束。

1. **WF1 固定范围与运行额度。** 先在真实拍摄、取回、发布之后通过默认正常 `run` 验证历史维护实际发生。两条历史责任、本次额度 1 时仅检查一条；同会话多轮不重置额度，下一正常会话从可靠位置继续。时钟异常及 `submit` 均保持文件和清理位置。先确认窄红，再接入会话状态和默认维护消费者。
2. **WF2 及时首次处理与实际使用。** 沿取回失败、取消、成功交接及录像检查／修复／成品提升的所有终止入口列出形成责任的文件。共用同文件拥有者和防重复状态；补历史额度已耗尽但本次新责任仍首次处理的反例。分别让读取、媒体工具及移动仍在执行时先保存归属终态，证明文件保留到实际收场。
3. **WF3 异步执行、接手与结果。** 在复用的文件执行器中处理实际文件查询和删除，数据库事务仍由原责任拥有者执行。用同步点阻止文件调用完成，证明其他设备工作可以继续；取消等待者后证明接手方消费一次实际结果、完成保存并关闭资源。文件错误不扩大为会话错误，状态库错误按可靠前提失效处理。
4. **WF4 故障与历史核验。** 覆盖结果投影失败、提交前后未知、删除完成后保存前中断，原键核实不重复删除。比较初始回放、快照正向及当前逆向恢复的文件事实和继续位置；旧业务结果、已发布副本及旧报告字节保持。
5. **最终组合。** root 前台独占按目录顺序执行 bootstrap、outputs、host_files、history、session；再运行实际 CLI 场景。每项记录日期、解释器、环境、范围和剩余项，全部门禁前不宣称正常清理闭环完成。

不得在入口直接扫描 `staging` 并删除未登记文件，不得以每轮新建 `WorkFileContext` 刷新额度，不得把所有 `REQUIRED` 记录解释为垃圾，不得通过删除测试或忽略文件调用拥有者使默认装配通过。

## 会话、实际拥有者与收场接缝

`session.service._run_session` 持有会话锁、接纳锁及主连接；`bootstrap.lifecycle.execute_command` 在它返回后才关闭报告监督方。因此文件维护的收场必须由会话在释放上述锁之前消费，不能只放在装配层的 `finally`。正常推进启动后台维护后立即继续其他设备流程；后台责任持有独立连接，并在实际查询或删除返回、结果及继续位置可靠保存后关闭该连接。

| 持久化工作事实与本次实际责任 | 会话判定及收场 |
| --- | --- |
| 持久化必需责任未知 | 保持未知，不用内存记录补造为零或成功。 |
| 仅有历史额度外、已经保存失败或本次已检查的清理残留 | 保持延后维护分类，允许退出，不增加 `submit.needs_run`。 |
| 本次已开始维护，但文件调用、结果保存或独立连接关闭尚未结束 | 在正常运行的持久化工作事实之上增加必要收场责任；推进设备工作，退出前等待实际责任。 |
| 正常退出准备关闭接纳 | 先等待本次已接纳的有限责任结束，再进入关闭接纳事务并重查持久化事实；重查发现新工作时继续同会话，新责任仍可取得首次机会，原历史范围和额度不重建。 |
| 致命错误、外部取消或转入受限运行 | 在释放任何会话或接纳锁前等待实际责任；转入受限运行前停止普通维护的新增任务。 |
| 等待收场再次收到取消 | 保留原取消，继续等待同一个拥有者；不能取消拥有者或实际文件调用，不能提前释放锁或连接。 |
| 普通文件 `OSError` | 按查询或删除阶段保存本地清理失败，继续其他清理项和设备工作。 |
| 收场可靠保存遇到状态库错误，原结果成功或 `report_error` | 最终为 `state_db_error`；已有报告错误作为次要诊断保留。 |
| 收场可靠保存遇到状态库错误，原结果为配置、时钟或其他致命错误 | 保留原主错误，并附加收场状态库错误；已有状态库错误信息同样保留。 |
| 原调用抛出异常或 `CancelledError` | 实际收场结束后保持原异常传播；收场失败保留为异常的附加诊断，不以 `finally` 中另抛异常覆盖它。 |

建议由会话接受内部本地责任端口，提供已开始但未完成的数量与异步收场方法。该端口只补充本次实际任务，不替代持久化业务事实，不创建新公开协议或持久化表。历史上界、继续位置、额度和 `processed` 在会话锁内首次可靠打开时固定；`submit` 与时钟异常开始的受限运行不启动普通维护。

实际使用核验包括四条生产链：设备读取的原 `operation_attempts`、`outputs.copy` 的准备／分段／摘要、`outputs.handoff` 的移动，以及 `bootstrap.capture_assembly` 的媒体任务。前三条目前部分直接使用 `asyncio.to_thread`；需要把它们的文件身份接入共用执行器，并在原协作者的连接关闭前消费真实结果。媒体接手方目前只等待工具结束，不能据此声称媒体业务结果已经保存；清理仅将实际使用与原业务结果分别核验。

先失败测试按依赖提交给 root 独占执行：默认入口的固定额度已确认红；随后验证后台查询挂起时设备继续、同文件媒体占用保护、新责任不受历史额度限制、取消及重复取消下锁与连接保持、四类主错误的收场优先级，以及原键核实与投影／提交前后故障。仓储文件中间文件责任段、取回执行器接线和媒体执行器注入分别与对应协作者协调后修改。

## 新责任发现与文件端口覆盖

文件登记身份与清理责任形成时刻必须分别判断。一个较早登记的 `REQUIRED` 副本，可能在本次运行才由有效取回转为取消或失败；它的首次清理不因文件编号小于历史上界而占用历史额度。已有归属终态但尚未保存保留释放的 `REQUIRED` 文件也不能永久跳过。历史候选须按保留状态、可靠归属终态与实际使用分别分类；仍活跃的 `REQUIRED` 文件继续保留。

| 责任形成依据 | 首次发现及处理 |
| --- | --- |
| 本次初始可靠视图之前已有待清理责任 | 纳入固定历史范围及有限检查，不因本次报告或其他归属元信息更新取得额外机会。 |
| 本次可靠保存取回项失败／取消或录像动作终态，原文件不再用于续传、核验、发布或登记 | 按原对象关联发现所属文件；相关操作实际结束后经共享首次入口处理。 |
| 本次可靠保存 `RetentionRelease` 或新中间文件归属 | 按事实中的稳定文件身份发现；有效用途仍保留，符合清理条件时首次处理。 |
| 本次已发现责任，但读取、摘要、移动或媒体工具尚未结束 | 保留待处理身份和实际占用；不能提前进行一次文件检查后宣称收场结束。 |
| 原拥有者记录仅更新末事件或累计次数，业务终态及文件用途未改变 | 不视为本次新清理责任，不能以 `last_event_id` 增加为理由绕过历史额度。 |

建议由业务保存后的窄通知或有界增量历史事实发现新责任。若使用历史，须核实事件中的具体业务列变化，逐批消费可靠事件，不仅比较归属对象的末事件；不增加重复全表扫描。仓储结果和清理位置仍是权威状态，内存只保留本次发现的身份、实际拥有者及已检查记录。

| 实际文件入口 | 共享身份与结果责任 |
| --- | --- |
| `outputs.copy.prepare_copy` | 目标文件观察及创建、截断、重置共用原目标文件身份；实际结果与重置保存结束前保持原连接。 |
| `outputs.copy.copy_next_segment` | 目标文件分段写入、同步及进度保存由原读取责任消费；取消不能关闭仍在使用的读取会话或数据库连接。 |
| `outputs.copy.complete_copy` | 原目标摘要核验及完整性／重拷决定保存由原责任消费；同文件校验仍在执行时不能清理。 |
| `outputs.handoff.publish_delivery` | staging 观察、移动和保存以原目标文件身份协调；实际移动结果未结束时不能删除旧 staging 路径或推断未发布。 |
| `capture.media_flow.RecordingInputCopies` 与 `MediaFlow.copies` | 将正常拍摄、残留恢复与取回的同一执行器传至上述共用拷贝端口；配置参数仍使用对应原业务契约。 |
| `bootstrap.capture_assembly.HostMediaTools` | 原输入及修复目标的全部文件身份由共享执行器保护；实际工具结束与媒体业务保存分别核实。 |
| `outputs.work_files.clean_one_work_file` 与 `clean_work_files` | 文件查询、删除和保存使用同一原身份及本次处理记录；同文件首次入口和历史入口不能分别获得机会。 |

已有文件任务协议要求句柄经登记的 `Supervisor` 交给接手方。完整异步文件操作可以增加窄调用协作者，把实际文件调用和原结果保存包含在同一拥有范围中；取消只停止新增操作，已经开始的调用及其保存继续实际收场。后台维护的整体责任与文件实际任务的监督不能相互等待同一个任务而形成循环。原实际结果已经取得而保存回滚或未知时，拥有者保留完整原请求、时刻和操作键；同一拥有者恢复只核实原键，不重新查询或删除。跨进程已失去该可靠输入时，按正式规则重新观察文件位置，不补造旧调用结果。

原 READ 的完整拥有范围包含源端实际结束及 READ 结果保存，内部准备、分段和摘要共用同一目标资格。建议完整调用协作者在同一实际执行协程中继承原执行器、关联文件集合及停止控制；内部请求是原文件集合的子集时顺序执行，不重复登记资格。派生并行任务不能继承原资格，不属于子集的请求仍按实际占用裁决。取消外层等待时停止新增段，已经开始的调用和原保存仍由原拥有者完成。该实现建议由局部同协程、并行拒绝、停止及真实 READ 取消反例验收。

## 取消汇总与首次清理的依赖

`TargetSettlement._settle_obtain` 当前只检查交付撤回，未接入 staging 中间文件的实际使用与首次清理。默认 `cancel_flow` 在维护流程之前调用它，可能先保存取消成功，再保存本次首清失败。[取回清理失败规则](../../architecture/obtaining-outputs.md#取回中间文件清理失败与后续处理)要求本次适用的清理失败参与取消汇总；文件维护可以延后，并不代表尚未完成的首次责任可以报告为全部成功。

| 取消及文件责任 | 目标收场与独立维护 |
| --- | --- |
| 取消已形成必要文件责任，但原 READ、媒体工具、摘要或移动仍未实际结束 | 目标收场保持未完成；先消费原实际结果，不关闭连接或删除原文件。 |
| 相关操作已结束，取消后的 staging 文件尚无本次首次结果 | 将原稳定文件身份交给共享首次入口；结果保存完成前，目标收场保持未完成。 |
| 本次首次查询或删除确认完成且结果可靠保存 | 采用该结果继续目标汇总，不重做文件操作。 |
| 本次首次查询或删除明确失败且结果可靠保存 | 目标结算报告失败，取消成员按既有 `target_cleanup_failed` 归类；普通文件失败本身不禁止会话完成其他职责。 |
| 首次结果保存回滚、未知或连接失效 | 停止依赖已失效前提的取消汇总，保留原实际结果和诊断，不能保存取消成功。 |
| 取消发起者或成员已经终态 | 保持原业务结果；后续有限历史清理完成不改写原取消终态。 |
| 当前取消没有新增文件收场，只有其他动作或已经结束取消的旧维护残留 | 该残留只承担独立历史维护，不增加当前取消的等待，也不重开旧取消。 |

建议在原取消责任输入和文件归属上增加内部结算协作者，由 `cancel_flow` 将本会话共享文件拥有者传给目标结算。现有拍摄、取回、ready 撤回及 processing 所有权分别保持其分类；不能把所有历史文件挂到任意取消请求，也不能用整个取回动作终态替代单个交付及实际调用的核实。改动涉及 `bootstrap.flows.cancel_flow`、`TargetSettlement._settle_obtain` 和拍摄分支，实施前与责任协作者协调。红测试须通过真实取消请求证明本次文件删除失败使原发起者失败、普通会话仍可结束，以及实际文件任务未结束时原取消成员保持处理中；旧取消终态保护独立覆盖。接入使用本会话共享的 `WorkFileRuntime`；前置复合事务及首次清理分别保存必要事实，验证范围如下。

## 验证记录与剩余门禁

### 清理结果输入身份

`CleanupResultSave.advance_cursor` 决定同一事务是否更新历史继续位置。原位置已经等于目标文件身份时，`True` 不产生位置变化；此时它和 `False` 生成相同的行事实，不能从历史反推原布尔输入。完整原请求核实不能把这种信息缺失解释为已核实。

`INTERMEDIATE_FILE_CHANGED.CLEANUP_RESULT`（事件 26、reason 4）必须保存 `evidence.cleanup_request={advance_cursor}`；该对象恰好包含布尔 `advance_cursor`，原文件身份、实际结果、错误和时刻继续由同一结果事件表达。原键核实逐项核对该输入证据和完整事件组。原位置已经等于目标时不写重复游标变化，但仍保存输入证据，`True` 与 `False` 的重送不能相互替代。显式主机清理保存 `False`。该输入不增加数据库列或对外报告字段。

#### 媒体原请求与原键的保存链

| 实际拥有者已经结束，原申请仍未可靠确认 | 先由正常、残留、受限或取消流程的只保存入口核实；收场仍有申请时，不宣称全部完成，保留原保存错误、申请与操作键。 | 致命错误退出不新开连接盲重试，不重复工具；后续恢复仍核原身份。 |
| 原主结果是成功或报告错误，收场发现原申请未可靠保存 | 状态库错误主导最终结果。 | 保留原报告错误诊断，不保存正常关闭成功。 |
| 已有 STATE、配置或时钟主错误，收场发现原申请未可靠保存 | 保持原主错误，并附次要 STATE 及原保存原因。 | 状态库前提失效后不进入受限设备流程或一次报告。 |
| 原等待者取消，收场发现原申请未可靠保存 | 传播原 `CancelledError` 并附次要 STATE 诊断。 | 原申请保持，不用异常替代实际拥有者收场。 |

`integration/bootstrap/test_media_local_settlement.py` 另提供 6 项门禁：真实 READ、probe 与 COMMIT 后未知形成共享申请，确认实际文件任务及两份监督责任已结束，再验证必要责任计数、无盲重试的收场拒绝，以及 STATE／配置／时钟／取消的主结果和原保存诊断。生产保存原 `SaveReceipt.error`，本地责任计入待核实集合，收场先排空实际拥有者，再对仍未核实的申请保留原因并传播 STATE。根 Agent 已独占验证此六项全部通过，与取消四项合计 `10 passed`，日志为 `/tmp/camctl-goal-media-settlement-current.log`。因此媒体默认入口、取消和 EXIT 的对应 22 项均有验证证据；此范围不代替完整 capture、bootstrap 回归或 WF4 的其他文件结果责任。

诊断组合仍有独立验收缺口：两份媒体申请同时尚未核实，或维护收场失败与媒体原保存失败同时存在时，收场目前呈现先遇到的错误，其余申请仍保留。两个 Supervisor 均已实际排空，此项涉及完整失败诊断，不表示实际任务或资源提前释放。后续须沿正式错误表达要求核对各份已知原因的保留方式，再补组合反例；当前不声明所有错误组合已经验证。

### 取消取回的前置持久化责任

实际代码追踪表明，`_ApplyCancelTargetCommand` 保存目标取消标记并为已发布交付建立撤回明细；`obtain_flow` 的普通推进排除已经取消的动作。`TargetSettlement._settle_obtain` 尚无未发布交付的结束消费者。不能直接调用首次清理入口，因为此时交付仍有用途，源依赖及原读取流程也可能没有结束。首次清理接入必须先闭合以下既有正式规则，不能用测试准备直接修改业务终态替代该生产过程。

| 原取回及逐项实际事实 | 持久化收场与首次清理 |
| --- | --- |
| 取回已经有原终态，本次取消没有 ready 撤回责任 | 保持原取回及取消分类；不把其历史 staging 残留挂入本次取消。 |
| 取消未生效的取回 | 不结束成员或交付，不清理有效副本。 |
| 取消已生效，来源或选择尚未确定 | 停止新增选择及授予；保留已经固定的关联，未建档项按原取消事实结束；不等待来源拍摄终态。 |
| 未建档取回项为 UNRESOLVED 或 SELECTED | 保存该项 CANCELED，不创建交付、副本、读取流程或新尝试。 |
| 未建档取回项已经 FAILED 或 CANCELED | 保持原结果，不重开本项。 |
| 已建档交付尚未发布，原 READ 尝试或本地文件任务未实际结束 | 保持原尝试、源依赖、读取机会及副本；目标结算保持未完成，由原实际拥有者继续收场。 |
| 已建档交付尚未发布，全部原尝试具有可靠实际结束结果且不再重试 | 原未发布交付保存 CANCELED，原在办 READ 流程保存 CANCELED，解除仍有效的 source_dependency 和 slot；不修改原尝试、次数、进度、摘要或已经确定的结果。随后调用共享首次入口。 |
| 已建档交付已经 FAILED 或 CANCELED，实际责任均已结束 | 保持交付原结果；尚未解除的原依赖及机会按可靠停止依据结束，取消本次才形成的必要文件责任仍按首次入口处理。 |
| 交付已发布，或实际移动结果尚未可靠保存 | 已发布按原 ready／processing 分类；实际移动未结束先由原拥有者保存结果。不能根据旧 staging 路径取消已交接文件。 |
| 每项必要收场及本次首次清理已经结束 | 原仍运行的取回保存 CANCELED；首次文件失败由取消成员汇总为 target_cleanup_failed，取回取消终态本身保持。 |
| 查询、复合收场投影或提交发生错误／未知 | 停止依赖步骤，不执行文件删除，也不保存取消成功；完整原键核实不得接受责任缺项或改变请求。 |

建议新增 `SettleCanceledObtain` 与独立仓储命令处理单个取回的有限持久化收场，以稳定 `action_id`、事实时刻和按 ID 升序固定的 `item_ids` 为输入。在同一事务中保存适用的 `READ_PERMISSION_CHANGED.CANCEL` 未建档项取消及 `RELEASE` 源依赖解除、`DELIVERY_CHANGED.CANCEL`、原操作流程结束、拷贝机会释放，以及目标 `ACTION_OUTCOME.CANCELED` 和必要父计划完成；事件各自属于正式原拥有者，事件数量与身份按实际组合一次分配。实际清理意图、文件删除及清理结果继续由独立中间文件事实表达。不得嵌套提交，不能先独立提交动作终态再假设交付及源保护已结束。

完整原键须核实原目标及时刻、原固定成员、全部实际事件、前后值和原拥有者；需要按原完整 H 恢复后续已经变化的业务列。回滚不生效，提交未知关闭原连接并由新连接核实同组。已取得的实际读取或移动结果优先由其原拥有者保存，不用取消命令伪造原结果。没有正式恢复边界的旧 RUNNING 不解释为已经停止；原 READ 的停止结果接缝由 READ 阶段单独完成。

失败测试先覆盖真实取消后首次成功、删除失败、清理结果提交未知及其他历史责任隔离；再覆盖原未结束 READ／真实文件资格保持、未建档项、准备完成未发布、已发布结果保护、成员和流程的完整原键、投影及提交前后未知。仓储责任段必须先与 READ 协作者协调，根 Agent 确认各组有效红后实施。未完成这些前置责任不能只凭 `clean_one_work_file` 的单文件通过宣布取消汇总完成。


### ready 实际撤回、共享等待明细及原结果保存

取消消费者核实原交付已经可靠发布后，只可删除仍由 camctl 拥有的 `ready/<file_name>`。`processing` 属于主程序，CLI 不删除或修改该文件。文件名、原交付、所属取回及 `file_copies.target_file_id` 必须共同核实；同一实际撤回使用原目标文件资格，不能用文件名或取回动作终态代替实际使用判定。依据见[文件交接边界](../../architecture/file-handoff.md#ready)、[取回取消](../../architecture/obtaining-outputs.md#取消取回)、[交付撤回责任](../../camctl/database/file-fields.md#普通交付)及[取消明细](../../camctl/database/workflow-fields.md#取消目标与交付项)。

| 原交付责任及实际阶段 | 必要行为与取消结果 |
| --- | --- |
| 原交付未发布，或实际发布结果尚未可靠保存 | 按前置取回及移动责任收场；不根据 staging 缺失推断 ready 可撤回。 |
| 已发布交付仍是 `NOT_REQUESTED`，本次有必要撤回明细 | 先保存 `REQUESTED`，再取得原文件资格并核实位置。保存拒绝或未知时零删除。 |
| 已发布交付为 `PENDING`，可靠观察仅在 ready | 复用 `host_files.handoff.withdraw_file`；位置观察不保存为撤回完成。实际结果及其业务保存均完成前，原连接和文件资格保持。 |
| 可靠观察仅在 processing，或已有主程序处理依据 | 保存 `NOT_RETRACTABLE`，不调用删除；保持原可靠发布及取回终态。 |
| ready 删除返回 `WITHDRAWN` | 保存原完整 `AdvanceWithdrawal(WITHDRAWN)`；交付为 `WITHDRAWN`，本次关联明细结束为 `WITHDRAWN`。 |
| 删除返回 `NOT_PRESENT`，重新观察确认 processing | 保存 `NOT_RETRACTABLE`；不对 processing 操作。 |
| 无可靠位置，或删除返回 `NOT_PRESENT` 后仍无法确认位置 | 保存 `UNKNOWN` 及位置未确认错误，交付仍为原已发布状态；相关取消明细为 `FAILED`，有限取消汇总失败，不把不存在解释为已删除。 |
| 实际删除返回 `FAILED` | 保存实际错误到撤回责任；相关明细为 `FAILED`，取消成员汇总 `target_cleanup_failed`，ready 字节保持实际结果。 |
| 实际删除返回 `UNKNOWN` | 保存未知返回及诊断；采用既有 `UNKNOWN` 明细失败分类，不能补造删除完成。 |
| 撤回责任已有 `WITHDRAWN`／`NOT_RETRACTABLE`／`FAILED`／`UNKNOWN` | 复用独立原结论；不再次删除，不重开原取回或已经终态的取消动作。 |
| 多个取消请求在同一交付结果保存前已有待处理明细 | 只有一份实际撤回；结果事务同时结束固定的全部必要等待明细，每个明细仍归其原取消动作拥有。 |
| 原结果为 FAILED／UNKNOWN，保存后已无 pending 明细 | 先汇总全部适用明细的可靠失败；提交后未知的原键核实也采用同一失败，不以 pending 为空或后续位置观察为取消成功。 |
| 实际结果已取得，投影失败或提交前后未知 | 原拥有者保留完整请求、实际时刻与操作键；下一可靠连接只核实原键，不重新观察或删除覆盖原结果。无法可靠保存时停止状态库依赖步骤，原取消不报告成功。 |
| 等待者取消或重复取消，实际删除尚未结束 | 仅停止新增操作；等待同一实际拥有者完成删除及原结果保存，随后传播原 `CancelledError`。保存失败附原 STATE 诊断，不能先关闭连接或释放文件资格。 |
| 仅有独立中间文件历史责任 | ready 撤回不使用清理历史游标、额度或 processed，也不附加不相关文件清理结果。 |

`withdrawal_error_json` 使用既有公共错误对象 `code/stage/details`，逐请求 `cancel_delivery_items.error_details_json` 保存其登记的详情；两种结构不可混用。目录同步沿现有 `withdraw_file` 的正式适用责任执行，不新增部署故障范围。

内部实现建议为 `WorkFileRuntime` 增加独立 ready 撤回消费者和完整待保存结果缓存，由 `cancel_flow` 注入 `TargetSettlement`。完整操作以共享 `FileTaskExecutor` 拥有原目标文件，从位置观察、实际删除到原结果保存；`WorkFileRuntime.file_supervisor` 收场实际拥有者。缓存按原交付身份关联并保存原目标取回和文件身份，原实际结果保存成功后才移除；同一会话重新组装取消消费者先核实该目标的已取得结果，再查询剩余等待明细，不生成新删除结果。提交后返回未知时，投影可能已经终态而普通 pending 查询为空；仍须先核原键，不能由此丢弃完整原输入。没有可靠原输入的跨进程恢复只保存新的可靠位置观察，不能声称复用已丢失调用结果。

仓储修改限定在 `_AdvanceWithdrawalCommand`：事实数量有限且由实际明细集合推导，单个 `DELIVERY_CHANGED.WITHDRAW` 事件的原完整集合包含原交付以及每个适用等待明细；事件拥有者分别保持原 delivery 和原取消 action。`cancel_delivery_items` 没有独立创建事件列；原边界的成员存在性沿本行在原取消 action 目录中的唯一不可变 CREATE 事实核实，并核对原关联与完整事务边界。创建晚于原边界的明细不属于原组；父 action 创建较早不能代替该明细的创建依据，缺失或损坏的历史也不能解释为尚不存在。原键核实恢复原完整边界后逐项比较交付、分支、错误、时刻、行前后值及完整等待集合。相同输入只读重入；改变任何输入、把 `REQUESTED` 原键当实际结果键、缺明细事实或错拥有者均拒绝，不能只比较事件类型与时刻。原键保存以后新增的其他请求不改变原组，后续请求使用可靠既有撤回结论结束自身明细，不重复删除。取消生效时，原交付仍为已发布且独立撤回为 PENDING、FAILED 或 UNKNOWN 的后到请求仍须登记本请求明细；不能只选择 NOT_REQUESTED 而遗漏必要共享责任。

顺序门禁：真实默认消费者的 ready／processing／实际删除失败 3 项已有 2 项有效失败、1 项保护通过，日志 `/tmp/camctl-goal-cancel-ready-red.log`，根 Agent 已授权实际消费者修复。随后补取消等待与文件资格、实际结果保存失败后的原键重入、所有实际返回分类及并发等待明细；仓储原键改变／完整成员组／投影及提交前后未知分别先交根 Agent 确认有效红，再实施对应块。历史恢复另在 `integration/bootstrap/test_work_file_history.py` 验证文件和继续位置的初始、快照正向与当前逆向相等，不将 ready 删除副作用放入历史回放。
