# 清理查询结果保存与续接执行计划

**目标：** 存在性查询完成收场后，沿原尝试保存完整实际结果；只有原结果可靠保存后，才允许清理成员使用该观察推进删除、成功或取消。保存中断、连接更换和本地消费中断均保持原身份、观察、时刻及累计次数。

**父任务：** [本次运行配置与原绑定计划 Task 1 的剩余责任](2026-10-09-camctl-runtime-configuration-closure.md#task-1-验证记录与剩余责任)。整体依赖及完成度仍由[实施路线图](2026-09-30-camctl-implementation-roadmap.md#阶段-6-取消清理与录像内部处理)维护。本页只安排该结果保存接缝，不建立第二份第一版进度总账。

**正式依据：** [正常返回、恢复与历史保存](../../camctl/database/operation-fields.md#正常返回恢复与历史保存)、[普通尝试结束结果的保存边界](../../camctl/database/operation-fields.md#普通尝试结束结果的保存边界)、[持久化接口契约](../../camctl/persistence-runtime.md#持久化接口契约)、[数据库连接与完整事务](../../camctl/persistence-runtime.md#数据库连接与完整事务)、[处理状态与归属](../../camctl/database/cleanup-coordination.md#处理状态与归属)、[接手时的文件事实](../../camctl/database/cleanup-coordination.md#接手时的文件事实与后续操作)、[清理取消](../../architecture/output-cleanup.md#清理取消)、[取消后删除结果与错误的保存](../../camctl/database/output-cleanup-state.md#取消后删除结果与错误的保存)和[清理项的合法字段组合](../../camctl/database/workflow-fields.md#清理项的字段组合)。

**共用规则参考：** [拍摄调用结果计划的第一阶段](2026-10-09-camctl-capture-call-results.md#第一阶段原结果原时刻与原键的公共保存责任)定义原对象、原时刻、原键及会话持有的共同不变量；其正文明确 cleanup 由所属专题负责，本任务不继承拍摄用途、活动释放或拍摄实施进度。

**实施建议：** 复用现有 `AttemptFinish`、`OperationKey`、`OperationRepository.finish_attempt`、原键复验及 `RetryWaitGate`。模块划分、类名、辅助函数和预计文件均是建议，执行者可以按实际数据流调整；下文输入、输出、不变量、状态分类及失败语义是验收约束。

## 工作边界与前置条件

输入是原存在性查询票据、实际 `DeviceCallResult`、原清理成员及其目标、本次查询配置和经过核验的既有状态库。输出是可靠保存后的观察以及已有 `CleanupStep`；保存失败向默认会话入口交付状态库错误。设备产物与主机派生成品使用同一保存边界。

本任务覆盖 `_run_query`、`_verify_before_delete`、`_verify_after_delete`、`_settle_canceling_member`、公开 `delete_source_file`、`advance_cleanup`、`session_cleanup_assembly` 和 `cleanup_flow`。查询结果后的成员结果及伴随流程收场属于本地续接范围；可靠查询在场之后的新删除仍遵守已有删除责任，不扩展为删除调用结果保存机制的重构。

实施前核对根 `AGENTS.md`、`apps/camctl/tests/AGENTS.md`、工作区及部署 Python 3.11。复用版本匹配的既有环境；任何 pytest 均由协调 Agent 前台独占、顺序执行，集成目录分开运行。测试使用受真实设备接口约束的替身，不连接相机，不承担 ARM64 性能或物理断电验收。

### 删除前查询与取消的必要前置

C1 的删除已有结束结果，但效果未知，随后 C1 可靠保存自己的失败或取消结果。C2 接手同一产物 O，先建立自己的查询责任；此时 C2 可以处于 `DELETING`，但尚未建立 DELETE 流程，也没有发出自己的删除。C2 的查询返回在场，结果尚待保存时，取消对 C2 生效。这个组合由正式接手和取消规则允许，不能仅因 C2 处于 `DELETING` 就推定 C2 已经删除。

正式契约已经定义：`DELETING` 表达处理归属，包含查询阶段；尚未形成不可撤销事实时，成员限制为 `ACTIVE`。可靠确认 C2 从未发出或可能发出删除、原查询已经完成收场、实际结果及其他必要责任可靠保存后，C2 保存 `CANCELED`、解除自己的可撤销限制且没有删除收场错误。C1 的原终态、限制及可能删除事实保持，O 是否可取回仍按全部相关事实判断。C2 不能借用 C1 的删除为自己生成 `file_delete_failed` 或 `delete_unconfirmed`。

需要协调的生产前置是：`_ProgressCleanupCommand` 为查询取得处理归属时也写入 `IRREVERSIBLE`；`decide_cleanup_cancel`、`_cancel_member`、`_CancelCleanupItemCommand.plan` 及其 `_verify_and_reuse` 按 `DELETING` 分支要求删除收场错误。这些接口尚不能完整表达上述已有契约。首次 QUERY 取得归属、首次 DELETE 形成不可撤销责任、取消实时判断及取消原键复验必须使用同一分类，不能只在一个消费者绕过。

本工作包包含 Task 0。QUERY-only 的取消分类已有正式契约，不需要重新选择业务语义；Task 3 的该取消组合以 Task 0 通过为前置。首次 DELETE 的不可撤销事实时点还须按下述接缝核清，其余原结果持有、保存门槛和本地续接可以先实施。不得以跳过该组合宣称本计划完成，不通过添加错误、放宽守卫或直接修改投影绕过。

### 首次建档与不可撤销事实的接缝（2026-10-11）

只读审查确认 `_begin_query_attempt` 和 `_delete_once` 都先提交 `OperationRepository.begin_attempt`，再单独提交 `OutputsRepository.progress_cleanup_item`。该分离违反[首次处理的共同建档规则](../../camctl/database/cleanup-coordination.md#流程关联与按需创建)：完整已提交边界不能只有首次尝试却没有处理归属，也不能只有归属却缺少对应流程、首次尝试和额度。Task 0 必须统一这两类入口，并核对原完整事件组的重送；只改限制标记不能闭合该问题。

本成员是否可能删除的权威输入是自身 `operation_runs.cleanup_item_id` 关联的全部 DELETE 尝试及其可靠派发、结束结果，不能采用整个产物的聚合事实。存在 DELETE 行不等于已经派发；最后一次可靠 `not_dispatched` 或 `NO_EFFECT` 也不能撤销早先可能派发的尝试。缺失、矛盾或无法解释的结果须停止相关推进，不默认从未删除。

首次 DELETE 意图提交后，若取消阻止实际派发，[未派发结果规则](../../camctl/database/operation-fields.md#明确返回和可靠未派发的结果记录)要求沿原尝试保存可靠 `not_dispatched`。本成员全部尝试可靠未派发且后续不会派发时，限制语义要求允许解除；但限制转换登记没有 `IRREVERSIBLE → RELEASED`。因此不能把首次 DELETE 意图无条件视为不可撤销事实，也不能为通过测试临时添加降级转换。实施该分区前须明确不可撤销事实的保存时点及崩溃恢复依据，核对文字规则、转换登记和实际派发责任能共同表达该状态。该分区没有闭合前停止相应生产修改，不影响已确定的 QUERY-only `ACTIVE → RELEASED` 分类及 Task 1 的保存反例。

| 本成员事实及可靠责任 | 分类与允许结果 |
| --- | --- |
| 已有终态 | 保留原结果、错误及最终事件；仅解决原保存或必要伴随收场。 |
| 原实际调用、结果保存或必要伴随收场未完成 | 保留处理归属，不提前终态化，不解除限制。 |
| 没有本成员可能派发的 DELETE，原 QUERY 等责任均已完成，文件在场或未知 | 无删除错误地取消；本项 `ACTIVE → RELEASED`，其他成员限制保持。 |
| 已取得可靠清理完成依据，必要责任均已完成 | 以原依据成功；成功事务保存合法不可撤销完成事实，不补造本项 DELETE。 |
| 本成员曾经或可能派发 DELETE，可靠观察仍在 | 取消并保留 `IRREVERSIBLE` 和 `file_delete_failed`。 |
| 本成员曾经或可能派发 DELETE，实际效果仍未知 | 取消并保留 `IRREVERSIBLE` 和 `delete_unconfirmed`。 |
| 只有可靠未派发的 DELETE，但此前已无条件写入 `IRREVERSIBLE` | 这是上述尚未闭合的保存时点分区；不伪装可能删除、不默认降级。 |
| 必需事实缺失、身份不符或结果不可解释 | 诊断并停止相关步骤，不解除限制，不创建替代责任。 |

## 权威输入与保存责任

1. 已提交的原 `run_id`、尝试编号、`exists/<cleanup_item_id>`、目标及所属动作决定查询身份。派发前已经可靠占用的查询额度保持；结果保存、重送或本地续接均不新增尝试，不退还次数。
2. 驱动提供 `DeviceCallResult.outcome` 时，以其中的状态、错误、效果、观察、`settlement` 和 `call_info` 作为完整实际结果。错误可以与可靠在场或缺席观察同时存在，不能用错误是否为空选择另一份观察或改写状态。兼容端口没有完整 outcome 时沿现有明确适配契约形成结果，不为保存恢复新增默认成功。
3. 调用完成适用收场、`await` 返回后先固定实际墙钟时刻、必要单调读数及唯一结果 key，并持有原对象，再执行结果验证及数据库步骤。合法结果形成的完整 `AttemptFinish` 在首次提交前固定；后续不得重取时刻、换 key、重新调用设备或以新驱动重解释旧结果。
4. 状态库的 `metadata.instance_id` 限定持有责任所属数据库。持有者保存数据和稳定身份，不保存旧连接、旧 runtime 或会再次调用设备的回调。
5. 非 `COMPLETED` 的结果保存与“查询没有可靠观察”是不同状态。前者保留原申请并停止依赖步骤，后者只有在原结果可靠保存后才进入查询预算或取消收场规则。
6. 查询保存可靠完成只解决实际调用结果责任。尚待保存的成员结果和伴随流程结果继续各自持有完整申请、首次 key 和时刻；它们可靠交接前不能因查询保存完成而遗失原观察。
7. 原结果已经保存，后来出现取消、绑定变化或终态时，原结果保持。新的执行资格影响后续设备操作，不能阻止保存或本地消费已经取得的原事实；既有业务终态不被迟到观察改写。

## 三种观察、三种保存结果与三个消费者

先核验合法结果、原身份及保存结果，再采用下表。`COMPLETED` 行要求原完整申请可靠匹配，具体可靠结果见下一节。删除前和删除后两列以普通资格仍有效为前提；取消列以本成员已经或可能发出自己的删除、必要调用已经完成收场为前提。本成员从未删除以及后来生效的取消另按后续表分类。

| 原查询观察 | 数据库结果 | 删除前 `_verify_before_delete` | 删除后 `_verify_after_delete` | 取消 `_settle_canceling_member` |
| --- | --- | --- | --- | --- |
| 在场 | `COMPLETED` | 进入既有删除资格、间隔和预算判断；观察本身不授予删除。 | 返回 `still_present`，成员保持原责任。 | 保存本成员 `CANCELED` 和 `file_delete_failed`，原错误及不可撤销限制保持。 |
| 缺席 | `COMPLETED` | 以原查询观察保存 `ABSENCE_CONFIRMED`，不删除。 | 以原查询观察保存 `ABSENCE_CONFIRMED`。 | 以原查询观察保存本成员成功，所属动作取消保持。 |
| 未知 | `COMPLETED` | 返回 `query_unknown`；后续查询沿原预算和适用间隔。 | 返回 `query_unknown`；后续查询沿原预算和适用间隔。 | 保存本成员 `CANCELED` 和 `delete_unconfirmed`，不补造文件仍在。 |
| 在场 | `ROLLED_BACK` | 持有原完整申请，交付保存错误，不删除。 | 持有原完整申请，不返回可靠在场，不推进成员结果。 | 持有原完整申请，不保存取消终态或删除错误。 |
| 缺席 | `ROLLED_BACK` | 持有原完整申请，不保存清理成功。 | 持有原完整申请，不保存清理成功。 | 持有原完整申请，不保存清理成功。 |
| 未知 | `ROLLED_BACK` | 持有原完整申请，不降为普通 `query_unknown`。 | 持有原完整申请，不降为普通 `query_unknown`。 | 持有原完整申请，不降为 `delete_unconfirmed`。 |
| 在场 | `UNKNOWN` | 停用不可靠连接，核实原 key 前不删除。 | 持有原完整申请，核实前不返回可靠在场或推进成员结果。 | 持有原完整申请，核实前不保存取消终态或删除错误。 |
| 缺席 | `UNKNOWN` | 核实原完整事务前不保存清理成功。 | 核实原完整事务前不保存清理成功。 | 核实原完整事务前不保存清理成功。 |
| 未知 | `UNKNOWN` | 核实原完整事务前不重查设备、不降为普通查询未知。 | 核实原完整事务前不重查设备、不降为普通查询未知。 | 核实原完整事务前不保存 `delete_unconfirmed`。 |

保存拒绝不撤销此前可靠提交的原查询意图、额度、处理归属或前置删除。测试从这些前置提交之后检查没有后续推进，不能误要求整个入口没有任何写入。原查询可以带调用错误；完整错误和观察同时保存，表中的观察分区仍按合法可靠事实判断。

### 可靠仓储结果与原键复验

| 仓储结果 | 原申请是否已经可靠解决 | 允许行为 |
| --- | --- | --- |
| `COMPLETED` 且 `FinishDisposition.SAVED`，首次保存或严格原键复验 | 是；完整原结果及适用流程处置已经核对。 | 进入原观察的本地消费。 |
| `COMPLETED` 且 `FinishDisposition.ALREADY_ENDED` | 尚不能据此证明本次传入观察已经保存；返回的状态不是原申请全文。 | 保留持有责任及诊断，完整核对持久化原结果；无法证明一致时停止，不能把本次观察当成已保存。 |
| `COMPLETED` 缺少合法完成值、票据对应关系矛盾，或结果类型无法解释 | 否。 | 按一致性错误停止并保留诊断，不释放原责任。 |
| 原 key 已存在且完整申请相同 | 由 `FinishAttemptCommand._reuse` 核对原票据、结果、事实时刻、`retry_wait`、事件组及原完整边界。 | 复用首次结果，零新增历史、零查询、零新增次数。 |
| 原 key 已存在，但输入、事实时刻或阶段不同 | 否；这是身份冲突。 | 整组拒绝，不换 key，不覆盖既有结果。 |
| 原 key 可靠不存在，原尝试仍允许保存该实际结果 | 原事实还未保存。 | 沿同一 `AttemptFinish` 和同一 key 保存，不重查设备。 |
| 原 key 不可读取、尝试关系无法解释或再次保存失败 | 否。 | 原责任保持，继续交付状态库错误，不执行依赖步骤。 |

优先复用已经具备严格核对能力的 `finish_attempt` 原键路径。对 `ALREADY_ENDED` 的保守诊断不修改既有结果，也不放宽该仓储分区为 `SAVED`；需要本地核对时使用原保存内容和边界，不仅比较 attempt/run 状态。

### 原结果可靠保存后的资格与取消

下表在原查询已经可靠保存后适用，优先保留已有结果。判断本成员是否可能删除时，读取本成员全部 DELETE 尝试、派发及可靠未派发依据；另一成员的删除只影响产物事实和其他限制，不证明本成员曾删除。

| 当前可靠责任与观察 | 本地续接及限制 |
| --- | --- |
| 本成员已经终态 | 保留原成员结果、错误和 `final_event_id`；保存责任原键复验仍完成，已保存终态所需伴随收场继续，零普通查询或删除。终态但仍缺必要结果属于一致性错误，不能制造正常终态路径。 |
| 普通资格有效，尚无取消 | 按三种观察矩阵继续；每次派发仍重新核对当前资格、绑定、预算与间隔。 |
| 取消已经生效，但原查询结果仍未可靠保存 | 完成原结果保存责任；不开始普通删除，不提前终态化成员或宣称取消处理完成。独立取消事实仍按其自身规则及时保存。 |
| 取消已经生效，原查询已保存，可靠确认本成员从未删除，没有其他未完成责任，目标尚未清理完成 | 保存无删除错误的 `CANCELED`，解除本项可撤销限制；其他请求的限制及可能删除事实保持。在场和未知均不改变本项从未删除的分类。 |
| 取消已经生效，原查询已保存，已有该产物清理完成的可靠依据，必要责任已完成 | 使用原完成依据保存本项成功；所属动作的取消要求保持。 |
| 取消已经生效，本成员已经或可能删除，原查询确认仍在 | 沿本成员保存 `file_delete_failed` 取消结果，零后续删除。 |
| 取消已经生效，本成员已经或可能删除，原查询仍未知 | 沿本成员保存 `delete_unconfirmed` 取消结果，不重新查询替代这次已经返回并保存的结果。 |
| 当前绑定缺失或不匹配，但原查询已有完整合法结果 | 原结果继续保存和本地消费；新的设备调用按绑定失败规则处理。不得用当前绑定失败覆盖原观察，或让另一驱动解释旧定位信息。 |

取消在原查询返回后、后续删除派发前生效时，删除资格必须重新核对；恢复不能直接续跑保存前预想的删除。查询仍在实际调用或收场时继续由原执行者持有，取消及时保存，未结束结果不能被另一推进轮次或另一成员接管查询。

## 会话持有、连接恢复与本地消费

建议会话集合按原 `(run_id, attempt_no)` 保存不可变条目。条目包括原数据库身份、成员、消费者阶段、ticket、实际结果、读数、结果 key、准备完成的 `AttemptFinish`，以及已经可靠保存后仍未完成的成员或伴随流程申请。消费者阶段建议采用有约束的枚举；从完整观察解释出的布尔值只是派生结果，不建立第二份权威缓存。

重试门槛继续采用[设备文件删除与查询的计时](../../architecture/configuration.md#设备文件删除与查询的计时)和父任务已定义的规则。原结果未可靠保存时不更新锚点；可靠保存且具备下一步资格后，未知观察建立查询重试锚点，在场观察清除查询锚点并在确认允许再次删除时建立删除锚点，缺席结束本文件处理。实际观察墙钟保持原值，但不能照搬拍摄锚点规则而把清理保存完成前的时间计为已经具备重试资格；跨运行不比较旧单调读数。

| 持有阶段 | 可执行步骤 | 释放条件 |
| --- | --- | --- |
| 实际调用已返回，尚未完成合法结果验证 | 保留原对象和身份；验证原契约。非法观察保留诊断，不能转换为空观察继续。 | 原事实可靠交接，或沿明确错误责任完成处理；不能因验证异常丢弃原返回。 |
| 完整结果申请已准备，尚未可靠保存 | 只保存或核实原申请。 | 原申请严格匹配且可靠完成后，转入本地消费；不能直接释放消费者责任。 |
| 原查询已经可靠保存，本地消费尚未完成 | 根据原观察形成成员结果；首次提交前固定完整成员申请、key 和时刻；失败后沿原申请恢复。 | 该消费者所拥有的本地结果责任已经可靠交接。 |
| 成员已经可靠终态，伴随流程收场尚未完成 | 保持主结果及原伴随收场申请，沿其原 key 保存；不重做查询或成员结果。 | 全部原本地收场责任可靠完成。 |
| 原观察已经可靠交给普通下一步，仍需后续重试 | 保留原可靠次数与等待事实，由原流程处理后续合法新操作。 | 原观察交接完成；以后有资格的新查询是新尝试，不能冒充原结果重送。 |

`CleanupRuntime` 是本轮装配，不能成为唯一会话拥有者。建议由 `session_cleanup_assembly` 的闭包持有集合和 `RetryWaitGate`，并允许显式传入会话集合以支撑另一工厂；所有 `for_item` 替换对象必须共用它们，不能共用持有旧连接的整个 runtime。

默认 `cleanup_flow` 每轮用 `context.open_connection()` 取得 fresh `OwnedConnection`，在 `finally` 中关闭本轮连接。UNKNOWN 的旧连接在所属责任内停用、可靠结束或关闭；不能在连接仍有不可靠事务时重送原 key 或用其中的新投影判定已提交。新连接先核验相同数据库实例身份，再调用原 `finish_attempt(pending.finish, pending.key, fresh_owned)`；换库必须诊断，不能把相同整数 ID 当同一责任。

恢复全部原待存结果要早于 `advance_cleanup` 的新业务安排；公开 `delete_source_file` 的所属结果恢复要早于终态、取消、绑定及新尝试早退。候选只选运行中动作时，也必须另行发现会话集合中的原责任，不能因为动作已终态就不恢复它。保存持续失败时停止依赖工作，默认入口交付状态库错误；不使用无上限循环延长数据库忙等待，不恢复本会话普通执行来掩盖先前数据库错误。

查询观察必须能从持久化原结果本地读取。当查询结果已经提交、成员结果尚未提交，而内存集合丢失时，沿原查询 ticket、目标、结果事件及完整 `result_json` 恢复实际 `file_presence.present`，不访问设备、不创建新 QUERY。必须检查观察版本、成员身份、原结果结构及其后的可能 DELETE；晚于该查询的可能删除使旧在场观察失去直接重删依据。

`EffectState.CONFIRMED` 同时适用于查询在场和缺席，不能单独代表在场。`_output_delete_facts` 及三个消费者读取共享产物事实时，都必须使用真实观察含义与后续操作顺序。已经可靠保存的缺席查询不能因为成员成功事务尚未完成而恢复成“仍在，需要删除”；未知观察也不能用空元组或已结束状态补成缺席。

内存集合跨连接及同一会话工厂共享，不声称跨进程保留未提交设备结果。原进程退出且结果从未提交时，继续遵守[旧 ADB 调用恢复记录](../../camctl/database/operation-fields.md#第一版-adb-未完成调用的恢复记录)，不补造原错误、观察或实际时刻。结果已经提交而本地消费未完成时，则必须从原持久化内容续接。

QUERY-only 取消使用上述正式契约。只有可靠未派发 DELETE 时的不可撤销事实时点与限制转换，仍按前置接缝停止相应生产修改。实施时若出现正式规格没有定义的状态、原结果无法取得完整合法解释，或现有公开事务无法建立计划前置，应停止相应步骤并列出具体证据。删除实际结果持有、旧进程确实丢失结果后的恢复、目标设备联调及第一版其他工作仍由所属专题跟踪。
