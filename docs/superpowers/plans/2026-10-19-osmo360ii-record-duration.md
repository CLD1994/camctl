# OSMO 360 II 普通录像时长排查与修复

## 目标和现有依据

用户要求普通录像至少录满目标时长，并尽量接近目标加 1 秒。例如目标 10 秒时，应排查并消除使结果达到约 15 秒的额外延迟。实际媒体时长、设备命令的生效时点及工具完整返回时点分别表达；恢复、取消和未知结果仍沿原动作与原尝试处理。

现行计时规则见[启动余量规格](../specs/2026-10-18-camera-startup-margin-design.md#正常录像与自然延时)、[相机录像](../../architecture/camera-recording.md)和[异常录像恢复](../../architecture/camera-recovery.md)。规格中的可靠响应锚点及至少录满要求是当前实现依据；若排查确认需要改变计时锚点或驱动确认语义，先在责任规格定义新依据及其适用条件，再修改消费者。

## 已取得的证据

TX2 action `1` 请求 10 秒，冻结 1000 毫秒启动余量。START 组合调用完整返回后 11.048240 秒保存 STOP 意图，STOP 调用 2.306071 秒后返回。交付文件 `processing/3.OSV` 的视频为 15.382033 秒、约 29.97 fps、461 帧。源记录和媒体探测保存在 `.local/diagnostics/20261019T021600Z-record-duration/`。

现有文件等待发生在可靠 STOP 之后。原记录没有独立保存实际首帧、实际停止时点和每项设置的耗时；START 组合调用还包含相机设置，不能把其全部耗时计作录制时间。

历史启动余量验收的 10 秒自动曝光样片为 15.982633 秒，手动曝光样片为 11.678333 秒；两者均在完整 START 返回后约 11 秒派发 STOP。该差异用于安排对照，尚不能证明原因来自曝光。历史凭据位于 `.local/acceptance/camera-startup-margin-20261017T215355Z/`。

## 执行步骤

1. 在相机实际连接的主机上核对 CLI、相机身份及当前空闲观察。保存配置、安装版本、数据库和文件基线。使用独立诊断目录及状态库，避免本次拍摄触发其他状态库中原有动作。相机接回 TX2 后使用本机 ADB；开发容器访问宿主机的方式见[对应操作说明](../../hardware/camera-demo-validation.md#开发容器访问宿主机-adb-服务)，两种通道分别记录。
2. 在实际 ADB 工具边界记录每项设置、最终 START 和 STOP 的派发、输出到达、可靠响应及退出时间，同时记录同一次调用的 UTC 和单调钟。保持正式驱动命令与响应解释规则，观察器原样转发参数、标准输出和退出结果。
3. 按当前分层安排逐轮完成 10 秒录像，保留原调用与全部源文件。只在一轮 START／STOP 结果和设备空闲能够可靠解释后安排下一轮；正式计划覆盖自动和手动曝光。核对实际媒体时长、帧数和可用设备观察，把传输、工具等待和设备采集阶段分别说明。遇到未知效果时保留现场，接续原责任处理，不自动重发拍摄。
4. 根据实际证据确定最窄修复边界：命令与工具配置、驱动事实采集、框架计时或停止调度。新的计时依据须说明为什么仍可保证至少录满；不能把调用意图当成设备已经开始的事实。没有直接依据的时间仍保持未知。
5. 涉及计时或确认契约变更时，先更新规格和完整状态表，覆盖正常、设置耗时、响应延迟、保存延迟、取消、未知、重启恢复及旧冻结定义。建议继续由设备工厂冻结规则，由纯计时模块计算，处理器与持久化守卫共同消费；模块划分以实际根因为准。
6. 在最窄责任层编写能重现根因的失败测试，再修改代码。相关 capture、devices、bootstrap、cancellation 和 history 入口按测试指南串行核验；不重复运行未受影响的组件目录。驱动调用必须保留原有限预算和可靠收场。
7. 在开发容器中构建并核对实际 wheel，在相机实际连接的主机使用独立安装包及状态库，通过正式计划执行 10 秒自动／手动录像，核验原片至少 10 秒、尽量接近 10～11 秒，以及各阶段的实际时间。保留视频、日志、数据库与报告，独立记录软件门禁和设备验收；完成差异审查后分阶段提交。

## 录像截止唤醒的实施模型

保持现有 STOP 计时契约：可靠 START 返回的原单调钟锚点，加冻结的启动余量和目标时长。只改变调度等待，不改变驱动命令、响应含义、产物处理或持久化结构。

建议由拍摄运行时发布普通录像的截止提示，由 `CaptureFlow` 按设备持有；中央等待同时考虑该提示、待执行动作和轮询上限。提示使用同一次观察中的单调钟与事件循环时钟作映射，不使用墙钟。相同动作和原截止重复登记不刷新时刻。每台设备最多保留一项；清除提示时核对动作身份，避免旧动作清掉新动作的提示。

正式会话必须装配进程内 `WorkNotifier`，并从配置读取轮询上限和提前唤醒余量；显式注入的通知器及轮询值仍优先。配置值必须通过实际 `execute_command` 装配测试验证，不能只验证配置解析。

等待通知与外部取消同时到达时，等待者必须继续抛出外部取消；正常通知返回和内部截止超时均不得吞掉它。采用 Python 3.11 的 `asyncio.timeout_at` 限定当前任务的等待，保留现有通知版本与等待者注销规则。验收分别覆盖无期限等待、有期限等待、通知与取消竞争、正常超时及正常会话的取消收场。

| 当前状态 | 截止提示 | 实际推进规则 |
| --- | --- | --- |
| START 在途、结果未知或结果尚未可靠保存 | 不新增提示。 | 保留原尝试，继续既有保存或核实流程。 |
| 本会话可靠 START 已保存，尚未到期 | 登记原截止；应用 `session.wakeup_margin_ms`，每个截止最多提前唤醒一次。 | 提前唤醒只重新检查计划和状态；原单调钟未到期时不派发正常 STOP。 |
| 原截止已到 | 提供一次立即重查机会，然后消费该提示。 | 处理器重新核对资格、取消和原预算，再推进 STOP。 |
| 同设备背景推进尚未完成 | 保留实际任务所有权；任务完成时通知中央循环。 | 完成通知仅触发重新检查，不能代替结果保存或生成成功事实。 |
| 取消、STOP 在途、停止已确认或动作终态 | 清除匹配动作的提示。 | 取消不等待原截止；停止预算及原结果保存规则保持不变。 |
| 跨会话没有原锚点 | 不从旧单调钟生成提示。 | 继续既有恢复对账；得到本会话计时依据后才能登记。 |
| 流程停止或会话退出 | 清空提示；不把提示算作待收场责任。 | 实际任务、连接和结果仍由原拥有者交付。 |

先编写失败测试，分别覆盖截止等待、提前唤醒不反复空转、相同截止不刷新、设备及动作隔离、取消、保存延迟和跨会话恢复。再接通运行时、拍摄流程、中央等待和配置。使用长轮询上限的组合测试证明 STOP 仍按自身截止推进；软件门禁通过后，以正式安装包进行真实录像并读取原片。

## 当前进度

### TX2 本机 ADB 的代码分层对照

相机接回 TX2 后，验证使用 TX2 本机 `/usr/bin/adb`，不采用开发容器的远程 ADB 服务。先确认 USB 权限、实际 serial、空闲、boot ID、已运行进程及源文件基线；修复访问权限本身不构成拍摄验收。诊断采用独立目录和状态库，保留部署中的既有任务及文件。

| 验证层 | 调用方式与计时 | 用于区分的边界 |
| --- | --- | --- |
| 独立命令对照 | 用 Python 标准库运行同源官方设置、一次 START 和一次 STOP；完整可靠 START 返回后等待目标 10 秒，不加额外余量。 | 不经过 camctl 的受管执行和调度；仍检查完整响应、退出及输出。 |
| 驱动调用对照 | 使用当前发布包的真实 OSMO 驱动、受管执行和响应解释，保持同样参数和 10 秒等待。 | 与独立命令对照比较，检查受管进程、参数、设置顺序和工具等待。此项不创建正式动作。 |
| 正式 CLI 计划 | 当前发布包按原冻结规则执行 10 秒录像；启动余量继续为 1 秒。 | 核对受理、原确认锚点、截止唤醒、实际 STOP、保存与结果核实的完整路径。与前两层分别表达等待规则。 |

各层串行执行；先完成一轮的可靠停止、文件等待、源归属和空闲核实，再安排下一轮。记录本机子进程实际启动、完整 argv、响应及退出、主机 UTC 和单调钟，设备日志保留原时钟。通过原片摘要、双路实际媒体时长与帧数判断结果。错误或效果未知时停止后续拍摄并保存原调用；不因一个样本成功就排除偶发问题，也不把本机 ADB 和远程 ADB 的差异直接当作根因。

代码审查同时覆盖 STOP 资格、唯一派发、命令构造、工具启动与输出排空、有限超时、计时锚点、取消和结果保存。对具体缺陷先写可证伪的最窄测试再修复。现有部署与当前发布包不一致时先记录差异，使用独立发布包核验，不能将旧部署结果写成当前源码结果。

### 工具启动耗时的超时边界

审查发现受管工具在取得子进程句柄后才开始超时计时，与[控制调用期限](../../architecture/configuration.md#控制调用超时)包含启动耗时的规则不一致。该缺口是否导致过当前现场异常尚未证实，须与设备对照分别记录。

修复从本次工具启动前保存原单调钟截止。等待原启动边界交出句柄，沿同一次调用取得实际退出和完整输出；不取消启动协程后丢弃迟到句柄，也不重新启动工具。期限限制正常等待，不把本地系统永久无响应纳入新的恢复保证。

| 原启动及结果状态 | 期限和收场规则 |
| --- | --- |
| 没有正常等待期限 | 保留原无期限等待及取消规则。 |
| 取得句柄时尚有预算 | 后续只等待原截止的剩余预算，不重新计算完整时长。 |
| 取得句柄时原期限已过，进程仍在运行 | 保存超时原因，沿原终止宽限与实际退出规则收场，不增加尝试。 |
| 取得句柄时原期限已过，进程已经退出 | 保留实际退出和输出，同时保存本次超时；不因正常退出清掉已超过期限的事实，也不向已退出进程发信号。 |
| 启动边界返回明确异常，未交出句柄 | 保留原启动异常及原因，不伪造进程退出或设备无效果。 |
| 取消发生在启动、等待或收场期间 | 保留原调用和句柄的拥有关系，沿原实际结果交接传播取消，不刷新截止或终止宽限。 |

先用延迟交付句柄的受约束替身证伪超时分类与剩余预算，再核对真实子进程的退出、输出和取消收场。实现与软件门禁通过后构建新 wheel，核对安装模块，再通过 TX2 正式 CLI 计划验证正常 START、STOP 计时及原片。

期限修复已完成代码评审；旧实现的新增定向用例中两项失败，修复后全部单元 5962 项及相关集成 777 项通过，见[软件核验记录](../../camctl/verification.md#工具启动期限的软件核验2026-10-19)。此前 TX2 部署的四项调度模块与当前源码不一致，控制、命令及响应模块一致；后续正式计划须使用核对过的新发布包。基线对照已在本机 ADB 完成：标准库直接调用手动曝光原片 11.678333 秒，真实驱动调用手动曝光原片 10.610600 秒，两者均不加启动余量、停止正常且原片摘要一致；单轮差异不作为调用方式的因果结论。

### TX2 正式计划与部署结果

从 `e5229ba` 构建并核对 240 份 Python 模块的 wheel，在 TX2 独立包目录使用现有运行依赖，分别执行正式手动／自动曝光计划。两轮均冻结目标 10000 毫秒和启动余量 1000 毫秒；START／STOP 尝试上限各设为 1。两轮 CLI 返回 0、动作成功、登记新增原片及配对预览，只有一次 START 和一次 STOP，结束后核实为空闲。

手动／自动原片双路分别为 11.778433 秒、353 帧和 11.211200 秒、336 帧，源端与副本摘要一致。可靠 START 返回至 STOP 意图分别为 11.043087 秒、11.032384 秒，意图后约 40 毫秒、35 毫秒实际启动 ADB，没有观察到到期 STOP 再滞留数秒。两份均录满目标，仍超出希望的 10～11 秒范围。分层四轮均正常停止，不能据此认定原未知 STOP 由远程 ADB 引起；原偶发故障与实际首帧仍未知。

已备份并更新 TX2 原虚拟环境中的正式 camctl，266 份包内文件与同一 wheel 一致，依赖检查及沿原配置的能力导出返回 0。保留原状态库及配置，没有推进原计划或以全局安装再拍摄。原片、状态库、完整时序和安装记录见[本机验收记录](../../camctl/verification.md#osmo-普通录像的-tx2-本机-adb-分层核验2026-10-19-utc)。本阶段完成代码缺陷修复、分层验证和部署；停止超时的因果及更精确的时长控制继续由[接口问题](../../hardware/camera-control-questions.md#osmo-360-ii普通录像-stop-无输出超时并继续录像)跟踪，现行启动余量规则保持有效。

### OSMO 普通录像的零余量对照

OSMO 普通录像使用 `StartReturn.SENT`，首次受理明确冻结 `startup_margin_ms=0`；正常 STOP 按原可靠命令确认加原目标时长派发。Action6 普通录像继续冻结 1000 毫秒，OSMO 原生延时继续冻结 1000 毫秒。能力说明从实际任务声明生成，不能在共用说明中写死等待 1 秒。已有动作继续使用原冻结值，不改写历史、原任务或原报告。

软件验证覆盖零余量与非零余量的定义构建、读取、持久化守卫、正常到时、截止通知、取消、未知 START、保存延迟和重启恢复。零余量仍须显式携带 SENT，不能因值为零遗漏字段或把 ACK 改写为实际开始。Action6 的 1 秒等待保留对照；OSMO 停止后文件等待、原生延时自然等待和媒体目标分别保持原契约。先用失败回归证伪原校验及任务声明，再修改最窄生产边界，通过正式安装链核对恢复到目标前后仅发送一次 STOP。

新 wheel 在 TX2 使用本机 ADB、独立包目录和状态库，分别执行 10 秒手动／自动曝光正式计划。逐轮完成可靠停止、文件与空闲核实后才安排下一轮，记录实际媒体时长、源端与副本摘要、START 及 STOP 原始时序；原片的时长由媒体读取，不由旧样本减去 1 秒推算。未知效果时保留现场，不自动重发拍摄。

实现与串行只读复核已完成，源码提交为 `9742950`。软件门禁为 5963 项单元、369 项相关集成通过，见[零余量软件验证](../../camctl/verification.md#osmo-普通录像零启动余量的软件验证2026-10-19-utc)。新 wheel 的 SHA-256 为 `27d3c1d476cc55e9162bf92b3b804fd7d60cbc1a154969dec5a8ff868ac9c10a`，240 份 Python 模块在本地与 TX2 均已核对。正式手动曝光原片为 10.110100 秒、双路各 303 帧，源端及副本摘要一致；数据库冻结余量为 0，可靠 START 返回后 10.033056 秒保存 STOP 意图，随后 41.455 毫秒实际启动 ADB，停止及后续空闲均正常。
