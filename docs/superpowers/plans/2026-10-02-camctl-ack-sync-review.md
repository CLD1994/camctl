# 累计确认与同步结束的实施审查

## 范围与依据

沿输入受理到同步结束检查 `reporting/ack.py`、受理仓储、事件守卫及真实 SQLite 事务。行为依据为[报告确认](../../architecture/status-reports.md#ack-引用的报告记录)、[同步记录](../../camctl/database/reports-runtime.md#状态同步记录)和事件登记。开始同步、完成本地发布及取消执行的真实消费者另行审查；这份计划不证明 R6 的全部消费者已经完成。

## 问题与修复责任

1. 同水位或较旧的有效 ACK 到达时，受理仓储没有检查同步；推进水位时也只写累计位置。应在所有输入分区共用的事务结束组装处保存全部合格同步的结束事件。注册、复用、拒绝和身份错误均须消费有效 ACK，不能用无事件的复用路径跳过同步。
2. 资格函数将业务水位用作同步的截止条件，遗漏开始事务边界。同步固定定义须保存 `from_wm` 和 `started_boundary_event_id`；报告必须覆盖固定起点且冻结历史包含开始事务，两个条件独立判断。
3. 同步守卫没有验证 ACK 结束的报告及事件依据。应由 ACK 所属守卫核对实际报告、责任资格和结束事件；通用结构守卫继续限制合法转换。守卫不能凭累计水位或本地报告是否存在推定资格。
4. ACK 读取使用整数强转，可能把无法可靠解释的状态当作有效事实。应使用明确类型表达报告依据，校验完整历史边界和对应业务水位，并校验累计位置与累计报告身份一致；可靠不存在与读取失败分别处理。报告冻结也须从事务实际看到的历史确定终点，不采用事务前决定中的旧终点，不截断无效起点。不得用虚构的报告水位准备真实事务测试。

## 行为契约

输入为完整解析的文档或文件诊断、已有累计确认和状态库中的报告与同步事实。输出为受理结果；副作用为同一事务中的输入历史、累计确认历史及适用同步结束历史。报告与同步管理变化不增加业务水位，不修改动作结果，不补造本地发布事实。

| ACK 事实 | 累计位置及身份 | 同步处理 |
| --- | --- | --- |
| 未提供或文档未完整解析 | 保持 | 保持 |
| 字段非法或可靠确认报告不存在 | 保持并保存诊断 | 保持 |
| 有效，报告终点高于累计位置 | 保存报告终点及其身份 | 检查全部未结束责任 |
| 有效，报告终点等于或低于累计位置 | 保持累计位置及身份 | 检查全部未结束责任 |
| 事实不可解释或读取失败 | 整次输入按状态库错误处置 | 不保存部分结果 |

对于未结束责任，报告冻结事件位置记为 H，开始事务末位记为 B，报告左端为 F，固定起点为 S。

| H >= B | F <= S | 结果 |
| --- | --- | --- |
| 否 | 否 | 保留责任 |
| 否 | 是 | 保留责任 |
| 是 | 否 | 保留责任 |
| 是 | 是 | 保存 ACKNOWLEDGED、实际 ACK 报告 ID 和本结束事件 ID |

已确认或已取消的责任保持原结束依据；重复 ACK 不再追加结束事件。`local_report_id` 可以为空，ACK 不填入该字段。输入写入、累计更新、同步更新和 submit 接管查询任一步失败都回滚整组；提交结果未知时按原操作键核实，不能按响应缺失宣称已回滚。

## 实施顺序与阶段门禁

预计文件和内部接口是实施建议，允许依据实际数据流调整。复用 P3 事务内核、既有事件登记和 SQLite，不增加依赖。

- [x] T1：建立能证伪当前资格规则及遗漏同步结束的最窄失败测试，确认失败来自目标行为；补全边界及 ACK 分类矩阵。
- [x] T2：使用精确的报告依据与同步定义，修复资格规则、状态读取及报告冻结入口；将测试报告通过真实冻结事务登记。覆盖非法类型、范围、边界中间位置、报告水位不一致、冻结前新提交及无效起点。
- [x] T3：在共用输入事务边界组装累计及同步事件，并注册正式 ACK 结束守卫。覆盖注册、复用、拒绝、身份错误、同水位、较旧 ACK、多个责任及终态保持。
- [x] T4：核验写入失败、读取失败、提交未知、submit 接管失败和历史回放。管理事件不产生业务变化，重复确认不产生额外历史。
- [x] T5：运行相关单元与集成门禁，独立审查实际差异；更新 R6 与路线图的进度及证据，提交这条已完成的修复链。
