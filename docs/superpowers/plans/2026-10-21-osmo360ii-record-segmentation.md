# OSMO 360 II 分段录像执行计划

> **执行者要求：** 逐项使用 `superpowers:executing-plans`，或在用户选择分工实施后使用 `superpowers:subagent-driven-development`。用 `- [ ]` 跟踪实际完成情况。开始实施前先阅读本计划与设计规格；本文件按任务记录实施结果与待完成工作；软件、部署和真机证据分别核对。

**目标：** 让 OSMO 360 II 的正常及异常普通录像，都能按实际分段登记、保留、选择、取回和报告，并能在进程中断后继续处理。

**架构：** 沿用现有任务定义、目录基准、结果分页、历史、取回和报告体系。增加可保存、可分页读取的分段事实与默认范围，在正常完成和异常恢复共同经过的入口作出判定；正式产物、默认范围及录像结果共同提交。

**技术栈：** Python 3.11、SQLite、既有 ADB 设备适配、TypeScript 客户端、C host（主程序接入模块）、wheel 安装包，以及仅供媒体验收使用的 ffprobe／ffmpeg。

**规格：** [录像分段产物设计规格](../specs/2026-10-20-osmo360ii-record-segmentation-design.md)。启动、停止与文件等待继续引用[拍摄完成设计](../specs/2026-10-18-osmo360ii-capture-completion-design.md)及[启动余量设计](../specs/2026-10-18-camera-startup-margin-design.md)。

## 如何使用本计划

计划中的行为、失败语义和验收条件来自规格，属于必须满足的要求。标为“建议”的新增文件、类型、接口及任务拆分，是根据当前代码作出的实施预估；执行者可以调整组织方式，但必须同步相邻任务的输入、输出和测试，不能改变业务含义。

每个任务都说明“做什么”和“为什么”。先增加能暴露当前问题的测试，实际确认失败，再修改生产代码；通过本任务的最窄验证后审查差异并作阶段提交。首次失败应来自缺少目标行为，不能以环境缺依赖、拼错路径或漏注册守卫作为有效的失败证据。

本文的 camctl 源码路径相对于 `apps/camctl/src/camctl/`；客户端小节的 `src/` 路径相对于 `apps/client/`，其他路径均以仓库根为起点。建议新增的文件和测试在本文建立时尚不存在；执行命令在相应文件建立后运行。实际完成情况由各任务勾选及阶段证据记录；单项软件通过不表示安装包或真机通过。

## 全局约束

- 分段长度、命名、完成下界和默认选段数只从规格对应的生产契约取得；相机文件归属继续使用启动前可靠保存的完整目录基准差集。
- 普通录像至少保留一份合格非零 OSV，不用目标时长推算必需文件数。每份原片与配对 LRF 各有独立身份。
- 完成判定和默认范围选择分别保存。范围外合格文件继续保留，明确 `output_ids` 可以取回它们。
- 普通默认、手动预览、自动预览及组／计划成员选择共同消费来源已保存的范围。清理继续使用自己的显式请求范围。
- 运行时使用控制、目录和文件事实，实际媒体时长保持未知。实际时长、双路主视频、音频和解码诊断在媒体验收中分别核对。
- 保存结果未知时核实原完整申请，保留原操作身份、输入及实际时刻。恢复不重新拍摄，也不重发已经可靠确认的 STOP。
- 数据读取、排序、配对、保存及报告生成都应分批处理；分批不能拆散必须共同提交的事务。
- 软件设备替身、安装包、ARM 部署、实际采集、媒体、客户端导入及 ACK（累计报告确认）分别保存证据。软件通过不代替设备或媒体通过。

## 优先审查的五类场景

审查时先检查以下容易给使用者造成错误结果的场景；后文为每一项安排了对应测试。

| 场景 | 必须保持的结果 | 主要负责的任务 |
| --- | --- | --- |
| 最后非零原片后面还有空 OSV／LRF | 空文件不把可能的短尾段提升为完整非尾段；原片身份和时长下界分别正确 | P1、P4 |
| 六段原片只默认交付前三段，之后发生重启或其中一段被清理 | 新的默认取回仍使用原范围；明确 ID 可以取范围外文件，不以第四段补位 | P3、P5 |
| 中间缺段、缺失首段、顺序未知、完成依据不足 | 明确缺口、空范围、未知范围、来源失败分别表达；已保留文件仍按资格取回 | P1、P4、P5、P6 |
| 终态事务已经提交但回执丢失，或报告生成期间文件状态继续变化 | 沿原申请核实，不重复登记；报告仅使用自身历史边界的事实 | P3、P6 |
| 多段具有相同内容，媒体未全部到达，但报告已完整应用 | 文件按交付名和身份独立关联；ACK 资格按报告覆盖判断，不等待媒体到齐 | P6、P8 |

## 实施起点与工作范围

在实施基线 `61459de` 中，OSMO 普通录像在 `devices/drivers/adb_cameras/osmo360ii_capture.py` 的 `_task()` 声明精确一份 OSV，所以两段录像会在数量检查中失败。现有分页已经可以读到多份文件，逐文件身份、独立交付和 LRF 配对也已有基础；因此应继续使用这些机制。

但只放开数量还不够。`capture/handlers.py` 的 `_advance_recording_outcome()` 异常路径会进入单原片媒体处理；`_record_media_source()` 只接受一份处理输入。分段结果必须在共同入口按自己的完成规则处理。

此外，`_catalog_drafts()`、`FinishCaptureCommand`、`CommandPlan.events`、`load_selection_facts()` 和 `_current_selection_snapshot()` 等位置仍会收集完整目录、产物、事件或选择结果。设备端分页之后，仍可能在后续步骤重新把全部数据装入内存。这是 P3 的实际前置工作，不能只给设备列举增加分页。

历史归属、公共错误及报告依赖也需要同时接入。把新成员写入数据库却漏出快照，或让取回写守卫继续按全部原片重新计算，都会使正常执行与重启恢复得到不同结果。

## 建议的职责与接口

下面给出相邻任务可以据以协作的建议接口。命名可以调整，但交接时必须交付实际采用的签名、类型定义、单位、分页顺序及失败语义。

| 建议位置 | 输入与输出 | 必须保持的边界 |
| --- | --- | --- |
| `devices/drivers/adb_cameras/osmo360ii_segments.py` | `parse_osmo_segment_key(path: str) -> SegmentKey \| None` | `SegmentKey` 包含整数目录号和 index；只解析顺序，不确认归属 |
| `capture/segment_models.py`、`capture/segments.py` | `default_segment_count(target_duration_ms: int) -> int`；`advance_segment_assessment(state: SegmentAccumulator, member: SegmentMember) -> SegmentAccumulator`；`finish_segment_assessment(state: SegmentAccumulator, completion: CompletionFacts) -> SegmentAssessment`；`iter_segment_gaps(members: Iterable[SegmentMember], *, last_nonzero_cursor: SegmentCursor \| None, last_owned_cursor: SegmentCursor \| None, start_key: SegmentKey \| None) -> Iterator[SegmentGap]` | 首遍固定可信起点并保存最后非零与最后已确认归属的独立游标；第二遍在同一冻结成员范围内逐项产生确定缺口，不将成员或全部缺口装入摘要 |
| `persistence/repositories/segments.py` | `iter_segment_members(scope: PlanReadScope, ref: SegmentSetRef, cursor: SegmentCursor \| None, limit: int) -> Page[SegmentMember, SegmentCursor]` | 引用绑定原动作、扫描及可靠末页；游标按完整排序键继续，错误不返回“读完” |
| 同一仓储及终态保存入口 | `save_segment_assessment(request: SegmentAssessmentSave, operation_key: str, owned: OwnedConnection) -> DbOutcome`；`finish_segmented_capture(request: FinishSegmentedCapture, operation_key: str, owned: OwnedConnection) -> DbOutcome` | 请求引用可靠集合及判断，返回有限回执；成员、产物和事件在事务内分批形成 |
| 取回来源读取端口 | `read_default_segment_scope(scope: PlanReadScope, action_id: int) -> DefaultSegmentScope`；`iter_default_segment_originals(scope: PlanReadScope, action_id: int, cursor: SegmentCursor \| None, limit: int) -> Page[OriginalFamilyFacts, SegmentCursor]` | 范围区分未确认、已确定为空、已确定非空；明确 ID 使用独立精确查询 |
| 报告历史读取端口 | 按历史边界分页读取缺口及默认范围关联的实际产物身份 | 使用报告的历史边界，不临时读取相机或当前目录来补结果 |

P1 的类型至少表达：实际文件身份、排序键或解析未知、原片／预览角色、完成与归属状态、零字节观察；`CompletionFacts` 表达停止、文件等待、扫描、起点、控制完成及明确错误；`SegmentAssessment` 表达结果分类、采用依据、完整非尾段计数、精确下界、多录结论、默认范围三态及稳定集合引用。`SegmentCursor` 保存完整顺序位置和唯一成员身份，`SegmentSetRef` 绑定原动作、扫描、可靠末页及已固定版本，`SegmentAssessmentSave` 和 `FinishSegmentedCapture` 引用它们及原判断，不能嵌入完整成员列表。`OriginalFamilyFacts` 是一份原片及其实际预览／修复关联所需的有限事实；`DefaultSegmentScope` 只保存范围状态、依据和稳定成员引用。保存成功的有限回执提供动作、原集合引用、范围状态、实际产物数及适用的终态，不返回全量产物或事件数组。P2 须给这些建议类型确定实际字段和往返校验。未知值不能统一改成零或空列表。

## P2：落实数据、公共错误和历史归属契约

**做什么：** 明确每项分段事实保存在哪里、归哪个动作或文件、怎样分页读取，以及失败怎样以机器可读结构报告。

**为什么：** 后续任务不能仅在内存里记住“前三段”，也不能靠一句错误文本在重启后恢复缺口。写入方、取回方和报告方需要共同的数据依据。

**预计文件：** `docs/camctl/database/schema/operations.sql` 及必要的关联 SQL，`docs/camctl/database/` 下的 `event-transitions.json`、`enum-registry.json`、`report-dependencies.json` 和对应字段／历史文档；`protocol/errors/workflow-codes.json`；`capture/segment_models.py`、建议的新仓储 `persistence/repositories/segments.py`。现有实现入口还包括 `history/events.py`、`history/validators.py`、`history/changes.py`。

**输入与交付：** 消费 P1 类型，交付实际存储字段及索引、事件归属、有限读写请求、公共错误条目和跨任务字段映射。具体表名及内部编号由权威登记确定，不在多个消费者中另抄完整清单。

- [ ] **步骤 1：增加结构和往返失败测试。** 覆盖默认范围三态、重复成员、排序键冲突、非法跨动作引用、缺口没有实际文件身份、预览指向错误原片，以及只有子表变化时的动作归属。
- [ ] **步骤 2：定义并实现增长集合的保存与查询。** 保存有序成员及可靠末页，再对该冻结集合做第二遍分页分类，逐批保存空尾观察、缺口区间、判断依据及默认范围成员关系。多份待定空 OSV 后再次出现非零原片时，必须完整记录此前每份非尾零原片；保存的缺口数量、首个缺口及成员归属与最终摘要相符后才允许终态提交。文件大小、摘要和清理状态仍由独立文件事实持有。按动作、完整排序键和成员身份设置可续读的索引。
- [ ] **步骤 3：接入任务及保存校验。** 声明、结果引用、原扫描和原活动必须一致；有限摘要携带稳定集合引用与必要计数，不携带全部成员元组。下界的精确表示须能覆盖合法计数与目标比较，不以溢出值代替事实。
- [ ] **步骤 4：登记公共错误及详情。** 分别表达缺段／非尾零原片、默认连续范围为空、默认范围未确认，以及既有无产物或结果未确认。详情能定位实际缺口区间、可靠邻接文件、默认范围及真实产物身份；无实际前邻或后邻时明确其不存在或未知，不补造引用。
- [ ] **步骤 5：让错误说明同时可供人阅读。** 在公共错误契约允许的说明成员中提供由可靠事实生成的简明说明，使现有客户端可以显示来源及缺段事实；完整结构仍独立保留。不依赖客户端重新解析设备文件名或读取内部事件编号才能解释结果。
- [ ] **步骤 6：验证权威登记及资源映射。** 对每类详情增加合法与非法样例；运行数据库、事件及协议检查。仅在报告公开字段结构确需改变时修改报告 Schema 和生成类型；单纯扩展已有开放错误详情不能误改其他报告字段。
- [ ] **步骤 7：审查并提交契约及最窄生产读写基础。** 交接实际字段、枚举、错误构造入口、分页引用及结果保存请求，后续任务据此实现，不另行解释。

公共错误中的增长详情也需要分页恢复、流式编码。较长缺口先用区间表达；需要列出已有产物身份时逐批写出，不能把全部缺口或范围身份重新拼成一个巨大动作详情对象。

## P3：补齐有界原子保存、原申请核实及历史恢复能力

**做什么：** 在同一事务内分批建立产物、关系及事件；提交结果不明时有界核实原事务；为分段成员提供同一历史边界的分页恢复。

**为什么：** “一起提交”和“全部放进内存”不是同一件事。当前事务内核和选择快照有整组驻留点，必须先解决，P4、P5 才能真正满足规格。

**预计文件：** `persistence/transaction.py`、`persistence/repositories/capture.py`、建议的新分段仓储；`persistence/repositories/history.py`、`history/snapshots.py` 及相关历史行读取。建议新增 `apps/camctl/tests/integration/persistence/test_segment_transaction_batches.py` 和 `apps/camctl/tests/integration/history/test_record_segment_history.py`。

**输入与交付：** 消费 P2 的集合引用和历史归属，交付专用或可复用的有界命令路径，以及拍摄、取回和报告均可使用的分页历史读取。新增路径可以限定到本计划所需操作，不要求全面重写所有事务命令。

- [ ] **步骤 1：写原子性和增长测试，确认当前问题。** 构造跨多个批次的实际成员，验证任意提交边界只能看到“尚未终态且无正式目录”或“全部产物、范围、终态均存在”。增加事件量时，批次不变，不能出现完整事件／产物列表被一次返回给调用者。
- [ ] **步骤 2：实现有限请求与事务内事件生成。** 先按可靠集合确定需分配的身份及事件完整范围，再逐批形成、校验和写入；历史首尾、投影及两类目录使用同一最终范围。任一批校验失败回滚整笔事务，不把前几批当成已完成业务结果。
- [ ] **步骤 3：实现跨批独立守卫。** `_action_finish_guard()`、`_output_guard()` 和 `_output_relationships()` 或其共同替代入口，重新核对实际来源、成员、配对、范围及判定依据。处理器传入“合格”布尔值不能代替数据库中的可靠事实。
- [ ] **步骤 4：覆盖回执丢失及原键重送。** 在提交前、提交后回执返回前分别中断；原键相同且输入一致时复用实际结果，原键但集合／范围引用不同则拒绝。核实不调用把原事务全部事件读入列表的路径，也不重新分配产物身份。
- [ ] **步骤 5：接入完整历史归属与快照。** 审计 `HistoryRepository._entity_row_ids()`、`_restore_owner_rows()`、`_snapshot_rows()` 及快照存储；新增分段、范围和缺口成员必须完整纳入所属动作，独立文件另行恢复。大集合不能因恢复动作自身状态而再形成完整行字典。
- [ ] **步骤 6：验证同边界结果。** 从初始历史回放、快照正向恢复、当前投影逆向恢复分别取得相同成员和范围；随后推进清理和摘要，旧边界结果不变。覆盖空有效页后仍有后续成员，查询失败不能冒充读完。
- [ ] **步骤 7：执行 persistence、history 的最窄集成测试并阶段提交。** 本步不接设备，不以新增记录触发摄录；向 P4、P5 交付有限回执与已核实的读写接口。

本步同时审计 `derive_changes` 和提交核实中的去重集合。不能只让 `CommandPlan.events` 接受迭代器，其他位置却继续把同一事务的全部事件或引用展开到内存。

## P4：把分段规则接入正常录像、异常恢复和空尾分类

**做什么：** 让实际拍摄结果经过统一分段判定，登记所有合格文件，并在同一终态事务中保存默认范围。

**为什么：** 正常完成、恢复控制完成、缺少控制计时以及有限失败，最终都应按同一份分段事实决定结果；各入口不能分别选择第一份原片或进入单原片媒体流程。

**预计文件：** `devices/drivers/adb_cameras/` 下的 `osmo360ii_capture.py`、`osmo360ii_results.py`、`bounded_result_reading.py`；`capture/result_inputs.py`、`capture/result_scans.py`、`capture/handlers.py`、`bootstrap/capture_assembly.py`、结果页和分段仓储。建议新增 `capture/segment_completion.py` 和 `apps/camctl/tests/integration/capture/test_record_segment_scope_recovery.py`。

**输入与交付：** 消费 P1 判定接口、P2 类型及 P3 保存能力，交付实际录像结果、完整保留目录、空尾诊断、默认范围及终态。结果列表的路径顺序不能代替设备分段顺序。

- [ ] **步骤 1：增加设备页和扫描测试。** 多组 OSV／LRF 分散到不同页，夹有历史文件、跨目录边界和空文件；原基准差集正确，配对使用完整主干，分页失败不固定完整集合。新增 `test_segment_scan_resume_reuses_original_baseline_and_saved_pages`。
- [ ] **步骤 2：在扫描保存后提供按排序键续读的成员。** 不在 Python 收齐目录后排序；保存每页可靠事实再继续，最后一页未知时不提前判空尾、最后一段或缺口。跨页配对在文件识别之后按已保存的同目录、同完整名称主干关联，避免每份预览都重新扫描整个 DCIM；配对未知和不唯一仍分别保留。
- [ ] **步骤 3：在 `_advance_recording_outcome()` 的共同入口分派分段处理。** 建议在建立旧媒体检查决定之前完成分派；同时审计 `_record_handler()`、`_reconcile_recording()`、`_local_recording_listing()` 及已保存结果复用。分派依据来自任务契约，不能写成某个用户设备 ID 的特例。
- [ ] **步骤 4：接入成功与明确失败。** 正常控制完成直接使用原依据；控制不足时按下界及全部前提判断。停止、文件等待、归属、顺序或集合未知时，继续原有限核实；有限结束仍不足则结果未确认，缺段则保留明确失败。
- [ ] **步骤 5：用 P3 路径统一登记及保存。** 全部合格原片和有效预览建立独立身份，空尾与缺失位置不建立 output；保存全部产物、范围及终态。一起处理来源等待状态转换，不能丢失已等待的取回责任。
- [ ] **步骤 6：覆盖终结、取消及异常入口。** 审计 `_finish_capture()`、`_settle_stop_exhausted()`、`_binding_failure_files()` 和 `_finish_canceled_capture()`。取消优先于未提交的产物登记；终态先提交则保持原终态。停止未知不由分段数量覆盖，已经确认 STOP 不重发。
- [ ] **步骤 7：接入原生延时的空尾分类。** `2 秒／300 秒` 等任务继续采用原设备目标和自然完成规则；只放宽可靠空尾的处理，不使用普通录像的下界或选段公式。
- [ ] **步骤 8：证明正常和异常路径均不读取媒体时长。** 新增 `test_segmented_recovery_never_invokes_media_processing`，在控制依据充分、下界充分、下界不足、空尾及缺口分区中核对零次主机媒体拷贝／探测调用；报告时长保持未知。
- [ ] **步骤 9：修订有效能力说明，运行最窄设备／capture／bootstrap 验证并提交。** 普通录像说明准确表达整段交付和全部原片保留；不声明尚未取得的媒体或浏览器播放保证。

## P5：让所有取回入口消费同一默认范围

**做什么：** 普通取回和预览取回先读取来源已保存的原片范围，再逐段应用既有文件选择规则；明确 ID 仍精确选择。

**为什么：** “保留六段”不等于“默认取回六段”。如果只改纯选择函数，事实读取和事务守卫仍按完整目录重算，就会在保存或恢复时扩大范围。

**预计文件：** `outputs/sources.py`、`outputs/obtain_flow.py`，以及建议新增的 `outputs/segment_selection.py`；主要保存入口为 `persistence/repositories/outputs.py`。建议新增 `apps/camctl/tests/integration/outputs/test_segment_default_scope.py`。

**输入与交付：** 消费 P4 的来源终态及范围，交付逐来源固定选择、逐文件独立交付和来源级最终失败。取回自己的选择状态与来源范围状态是两件事：来源范围未确认也可产生一次已经结束的取回选择失败。

- [ ] **步骤 1：给选择函数增加分区单测。** 六份原片全部保留，确认多录时默认只选择前三份；普通、手动预览、自动预览、计划／组成员采用同一原片范围。`test_explicit_ids_can_obtain_retained_segments_outside_default_scope` 选择第四、第五份时必须保持指定集合。
- [ ] **步骤 2：替换全量事实读取。** 审计 `load_selection_facts()`、`SelectionFacts.outputs`、`SelectionSnapshot.items` 和 `select_outputs()`；用来源范围的分页成员读取及逐原片 `select_for_original()` 或等价接口处理，不先加载全部 catalog。
- [ ] **步骤 3：同时修改事务复核。** `_FixSelectionCommand`、`_source_selection_guard()`、`_current_selection_snapshot()` 共同核对原请求、来源范围、实际文件和完整大小；选择条目用 P3 能力一起固定，半份条目不能获得读取资格。
- [ ] **步骤 4：分别处理三种范围状态。** 来源未终态时等待；终态且范围未确认时保存范围未确认失败；范围已确定为空时保存没有默认连续内容的失败。后二者不创建文件目标或 delivery，不冒充“来源没有任何产物”。
- [ ] **步骤 5：验证缺口、失败来源和逐项发布。** `A、B、缺 C、D、E` 默认只交付 A、B；来源保留缺段失败，取回可成功。某个组成员范围失败时其他成员继续准备，按既有集合发布条件发布成功文件，不提前发布仍未判定的整组。
- [ ] **步骤 6：验证新请求、重送、重启及清理。** 新取回产生独立 delivery，同请求重送复用；重启及来源后续清理不重新选段。前三段中一段被清理或读取失败时不改选第四段；明确 ID 仍按其实际可用性判断。
- [ ] **步骤 7：运行选择及 outputs 最窄验证并提交。** 清理按来源选全部正式产物、按 ID 只选指定产物；原片／预览不级联。同步回归读取保护、取消、部分失败和恢复，不能将默认范围当成删除授权。

## P6：贯通报告、客户端消费与原报告重建

**做什么：** 把源录像结果、缺口、默认范围和逐文件交付可靠传到客户端，并验证报告与媒体分开到达时的行为。

**为什么：** 使用者需要同时知道“录像缺了什么”“这次交付了什么”和“本地实际收到什么”。报告成功应用、主机发布和媒体可播放不能合并成同一个成功状态。

**预计文件：** `contracts/public_projection.py`、`reporting/generation.py`、`reporting/encoding.py`、必要的分段详情读取适配；`history/changes.py` 及报告依赖登记。客户端主要核对 `src/domain/reports.ts`、`src/shared/protocol-validation.ts`、`src/web/result-model.ts` 和既有文件／媒体流程。建议新增 `apps/camctl/tests/integration/reporting/test_record_segment_error_report.py`。

**输入与交付：** 消费 P2 错误契约及 P4、P5 的可靠事实，交付 Schema 合法、字段含义正确且可重建的报告，客户端保留全部身份、错误详情及接收核验事实。

- [ ] **步骤 1：先增加报告失败测试。** `test_gap_report_preserves_retained_outputs_and_default_prefix` 核对缺口区间、实际邻接文件、默认范围及已登记身份；缺失位置没有 output 或 delivery。范围外原片仍列为实际保留文件，来源失败不覆盖取回结果。
- [ ] **步骤 2：实现历史依赖与流式详情编码。** 按报告边界读取动作成员和独立文件事实；缺口及范围身份逐批编码，不先构造完整详情列表。业务结果变化登记正确报告对象，纯内部进度不额外扩展公开实体集合。
- [ ] **步骤 3：验证重建及增量。** `test_segment_report_rebuilds_identical_bytes_after_cleanup` 在原报告登记后清理文件、补齐摘要、追加取回，再从不同快照／恢复方向重建原报告；原字节、摘要及文件名完全相同。增量未列出的其他产物不得被客户端删除。
- [ ] **步骤 4：接入公共资源。** 同步 Python 包内公共错误登记，确认源码及安装 wheel 均从根 `protocol` 的同一资源取得。若公开 Schema 改变则重新生成 `status-report.generated.ts`；否则只验证已有开放错误详情的导入与保留。
- [ ] **步骤 5：验证使用者能看懂的错误。** 缺段、默认范围为空、范围未确认各有可定位的简明说明，客户端保留结构化详情。测试核对来源、缺口和原因被正确呈现，不逐字锁定中文文案，也不新增摄制排序或拼接流程。
- [ ] **步骤 6：增加客户端逐文件及 ACK 场景。** 同摘要异名文件分别保存；媒体先到、报告后到后继续核验；一段未到或核验失败不冒充全部收到。完整应用且覆盖可靠的报告取得 ACK 资格，媒体到达本身不推进 ACK。
- [ ] **步骤 7：回归播放、下载及展示顺序。** 未知 MIME 或浏览器解码失败时仍可下载合格原文件，已核验状态和动作结果不改写。产物／交付报告数组按整数 ID，客户端按已保存顺序分页，CAM 顺序只影响主机判定与范围。
- [ ] **步骤 8：运行 reporting／客户端／公共协议最窄验证并提交。** 单纯扩展错误详情不应扩展客户端的拍摄参数、计划输入或播放器职责。

## P7：提供独立的实际媒体验收入口

**做什么：** 新建验收专用工具，对已取回的本地分段副本读取媒体事实，输出时长、短缺量、采用容限和解码诊断。

**为什么：** camctl 运行时不查媒体时长，现有工具也没有本规格所需的部署可调短缺容限。验收需要一个可复现的入口，避免每次人工相加时误用容器、音频或双路时长。

**建议文件：** `docs/hardware/validate_osmo_segments.py`；纯比较逻辑单测 `docs/hardware/tests/unit/test_validate_osmo_segments.py`，实际媒体工具组合放 `docs/hardware/tests/integration/test_validate_osmo_segments.py`；使用说明放相邻硬件专题。该脚本只消费本地副本，不调用相机控制或生产录像流程。

**调用入口：** `python3.11 docs/hardware/validate_osmo_segments.py --manifest <本地验收清单> --shortfall-tolerance-ms 100 --output <证据文件>`。这是独立的本地媒体验收命令。部署可以提供其他非负整数毫秒值；工具记录实际生效值，省略时采用规格默认值。

- [x] **步骤 1：定义验收清单和结果。** 输入关联原任务目标、实际文件身份／本地路径、全部保留集合、默认交付范围及预期播放时长的独立依据。结果分别保存源／副本长度和摘要依据、两路主视频、容器、音频、帧覆盖、解码诊断、采用容限及未知原因。
- [x] **步骤 2：先写纯比较测试并确认失败。** 目标 10000 毫秒，实测 9900 毫秒通过时长条件，9899 毫秒不通过；零容限、调整容限、负值／布尔值／非整数及未知时长分别处理。两路主视频分别比较，不能把两路或多段容限相加。
- [x] **步骤 3：实现本地媒体读取和范围核对。** 每份非零原片分别探测两路主视频及实际音频，排除封面；原始精度保留，不能以较长音频充当视频时长。正常核完整集合，异常分别核全部保留与默认范围；默认覆盖判断不得借用范围外文件。
- [x] **步骤 4：把可靠测量与未知分开。** 只有测量依据可靠时才输出时长通过或不足。原生延时须先由任务、间隔、已核实帧率及采样端点规则独立确定预期；缺少依据时输出无法核实，不从本次实际帧数反推预期。容器和逐流时长冲突、段间重叠／缺帧未核实时如实保留边界。
- [x] **步骤 5：验证实际工具组合与诊断保留。** 用本地合成双视频流样本验证读取、缺流和工具失败；对已有原片复核双路解码及参考帧诊断。退出码为 0 不能清除已观察到的问题，也不能单独宣称各段可独立播放。
- [x] **步骤 6：运行工具的单元和集成验证并提交。** 软件样本只证明工具行为；实际媒体、目标浏览器播放及段间边界仍用独立实机证据。缺少可靠测量方法不阻止 P1—P6 的软件契约验收，也不能将该媒体项勾为通过。

**阶段证据：** 实现提交 `0a58064`、修复提交 `1a80126` 和 `b7ea0a6` 已通过独立规格及质量复核，并合入协调提交 `bbbf7f6`。工具使用独立 Python 3.11.16 环境，依赖仅登记在验收专用清单；协调工作区完成 52 项单元及 6 项受影响集成测试，均通过。任务工作区此前完成完整集成 20 项，并验证 100000 项清单、每路 3000000 个帧时间戳及大型诊断的分批处理；最终局部修复没有重复这些压力测试。已归档单份原片的只读复核保留双路时长及退出码为 0 时仍存在的解码诊断，源定位证据不足继续为未知。硬件目录已有 24 条 Action6 失败已与不含 P7 的基线逐条核对一致；本阶段不将该目录全集记为通过。ARM、真实分段范围、浏览器播放和段间连续性仍由后续验收取得。使用方法见[分段媒体验收](../../hardware/osmo360ii-segment-media-validation.md)。

## P8：完成安装版软件联合验收和发行准备

**做什么：** 从源码目录外构建并安装新 wheel，经真实客户端、C host、CLI、SQLite、交付目录和报告处理，跑通分段业务。

**为什么：** 单元测试通过仍可能遗漏安装资源、装配入口、守卫、类型或客户端消费问题。只有让发行物实际经过完整链路，才能证明交付的是同一套行为。

**预计文件：** 新增 `tests/integration/test_osmo_builtin_record_segmentation_roundtrip.py`；建议为其提供可配置的多目录、多文件 ADB 替身。`tests/integration/` 下现有 `test_osmo_builtin_timelapse_roundtrip.py`、`_osmo_builtin_adb.py` 及 `client_driver.ts` 可复用或抽取共有能力，但不能沿用只认识一组固定 OSV／LRF 的假设备而声称覆盖分段。

- [ ] **步骤 1：建立安装版场景，先证明当前发行物不满足目标。** wheel、生产内置驱动、结果解释器、参数规则及公共错误资源均来自安装目录。仅在既定 ADB 进程和业务时钟边界提供受合同约束的替身。
- [ ] **步骤 2：跑通正常多段与空尾。** 两段各有 OSV／LRF，核对四个独立产物、预览关联、原片与预览的独立取回、文件名／大小／摘要、实际客户端导入及 ACK。原生延时可靠空尾不成为 output，原自然时序保持。
- [ ] **步骤 3：跑通多录和缺段。** 六段保留而默认前三段，另用明确 ID 取回范围外文件；缺段场景默认只取缺口前连续部分，客户端取得可定位错误。包含短尾、非尾零原片、空范围与未知范围；至少串通一个来源失败但前缀取回成功的完整链路。
- [ ] **步骤 4：组合中断和文件交接。** 在扫描、终态提交、选择固定、拷贝及报告生成处用确定同步点中断，再用同一状态恢复；身份、默认范围、进度和已提交结果保持。软件中断不模拟为设备已经停机，替身须明确设备实际效果。
- [ ] **步骤 5：验证部分媒体到达及顺序。** 报告完整应用后暂不导入至少一段，核对 ACK 与媒体接收独立；随后导入晚到文件。同摘要不同交付继续独立，设备排序与产物 ID 顺序故意不同，防止偶然顺序使测试假通过。
- [ ] **步骤 6：完成一次相关范围的汇总验证。** 按下方命令及隔离要求运行；记录工作区、解释器、命令、日志、退出码和适用范围。缺工具导致跳过时保留未完成项，不能写成整组通过。
- [ ] **步骤 7：审查发行物和交付材料并提交。** wheel 中资源与根协议一致，安装版 `describe` 说明有效；补充 OSMO 正式计划生成／校验入口及媒体验收工具的部署说明。同步测试 README、数据库专题、组件验证记录和本计划状态，分别填写软件与未执行的设备事项。

## P9：按独立证据层次完成 ARM 与实机验收

**做什么：** 在软件门禁通过并进入获准的现场执行后，核对 ARM 安装、实际普通录像、分段取回、媒体和客户端结果。

**为什么：** 相同软件在开发机上使用设备替身通过，并不能证明 TX2 的安装、真实固件分段或媒体内容。现场每一步都要有自己的证据，不能复用历史样本替代新发行物结果。

**资料入口：** [目标环境与部署](../../camctl/implementation.md#目标环境与部署分工)、[C 接入说明](../../../apps/host-demo/README.md)、[实机演示操作](../../hardware/camera-demo-validation.md#arm-linux-的完整验收)及[现有固件证据](../../camctl/verification.md#osmo-360-ii-新固件真机复验2026-10-20-utc)。不在本计划保存口令、私有连接信息或原始受限材料。

- [ ] **步骤 1：准备可区分的验收部署。** 备份保留原配置、状态库及必要日志；建议使用独立验收配置、状态库和交接目录，在新位置显式初始化与目标结构一致的验证数据。原部署不执行重复初始化，原相机文件继续保留。记录本次实际使用的全部绝对路径，避免 host、init、describe 与 run 指向不同配置。
- [ ] **步骤 2：核对 ARM 发行物。** 在开发侧通过 `uv build --project apps/camctl` 生成已通过 P8 的 wheel，按部署文档准备锁定依赖并在目标机安装；C host 使用目标 ARM 构建物。保存安装文件与发行物一致性、Python／SQLite、实际驱动能力、工具、设备身份和固件证据。历史版本值不当作本次读数。
- [ ] **步骤 3：确认设备空闲和原责任。** 查询并核对当前设备与本次绑定；有未决 START／STOP 或归属未知时保留现场，先处理原责任，不新增拍摄。现场证据与程序操作记录保持对应。
- [ ] **步骤 4：普通录像自动、手动各一轮。** 使用安装版 OSMO 参数与新请求，经真实 C host 提交目标覆盖多段的任务。核对唯一 START、正常 STOP、可靠响应、实际文件等待、原目录基准及完整扫描、动作结果、各段原片和预览身份；不按预计段数判失败。
- [ ] **步骤 5：独立取回、领取及客户端确认。** 普通原片和预览分别取回，经 host `claim` 领取，再由真实客户端导入报告与各段文件。逐项记录源／副本长度与 SHA-256、实际文件名、output／delivery 关联、本地接收和累计 ACK；主机发布不能替代这些证据。
- [ ] **步骤 6：用 P7 核对实际媒体。** 保存本次部署容限、各路预期／实际时长及差值、音频、解码和参考帧诊断。空尾出现时按实际位置分类；不为了复现空尾、覆盖全部参数组合或诊断既有参考帧问题自动重拍。
- [ ] **步骤 7：在明确的专项场景中验证异常多录。** 使用届时已经确认的异常执行安排，核对分段完成依据、默认范围、重启不变及明确 ID 取回范围外文件。不能通过删除原片构造缺段；物理断电作为独立专项，不是软件验收前置。
- [ ] **步骤 8：逐层归档并完成记录。** 每轮记录原始请求、安装版本、控制日志、完整文件关系、正式报告、独立交付、客户端凭据、ACK 及媒体结果。结果未知时停止依赖该结果的新设备动作，保留原现场，不自动重试、取回、删除或重拍。

## 横切验收：检查任务之间是否真正接上

逐项任务通过后，还须沿下面的数据流检查一次；每行的事实必须能从生产者追到最终报告及恢复结果。

| 数据流 | 联合检查 | 责任任务 |
| --- | --- | --- |
| 任务声明 → 原执行定义 → 实际结果读取 → 独立保存守卫 | 同一分段声明被全部入口消费；原生延时没有误用普通下界 | P1、P2、P4 |
| 原目录基准 → 多页观察 → 排序／配对 → 固定集合 | 基准不换、错误不冒充末页、部分页不决定空尾；没有后续全量收集 | P2—P4 |
| 控制／下界 → 判定依据 → 全部保留产物 → 范围 → 来源终态及等待者 | 原子可见，取消在事务内复查，提交未知先核实；来源失败与范围资格分开 | P3、P4 |
| 来源范围 → 普通／预览选择 → 写守卫 → delivery → 新请求／恢复 | 所有入口采用同一范围，原选择不因重启或清理补位；明确 ID 可取范围外文件 | P3—P5 |
| 缺口／范围 → 历史依赖 → 报告 → 客户端 → ACK | 实际身份完整、增长详情分批、未知与空不同；ACK 与媒体接收分开 | P2、P3、P6、P8 |
| 后续清理／摘要变化 → 同边界历史恢复 → 原报告重建 | 当前变化不污染原结果，批次及恢复方向不改变字节 | P3、P6 |
| 正式文件 → 本地副本 → 实际媒体比较 → 验收结论 | 摘要、时长、解码及段间证据独立，部署容限只作用于整次播放时长比较 | P7、P9 |
