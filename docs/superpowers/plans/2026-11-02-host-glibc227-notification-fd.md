# glibc 2.27 电机通知管道继承修复

## 目标与契约

目标主机使用 glibc 2.27。C 接入模块启动 `camctl run` 时，通知写端必须在执行 CLI 后仍可用；父进程中的管道继续保留 `FD_CLOEXEC`，其他命令不能继承通知写端。公开回调、通知格式、发送结果及重启后不重放通知的规则保持[通知协议](../../../protocol/host-notifications.md)和[接入设计](../../host-demo/implementation.md#资源上限与输出处理)的契约。

现场 action 41 在 Python 初始化通知写端时取得 `EBADF`，尚未发送通知或进入回调。现有启动代码对带关闭标记的通知写端执行同号 `posix_spawn_file_actions_adddup2`，依赖较新 glibc 清除该标记的行为。修复在子进程文件动作中使用不同描述符之间的复制；不在父进程临时清除标记，不增加版本探测或回调重放。

## 实施步骤

- [ ] 在现有启动单元测试的系统接口替身中模拟旧 glibc 的文件动作和执行时关闭语义。原实现必须因通知写端不可用而失败，测试不创建真实管道、线程或子进程。
- [ ] 修改最窄的启动边界，保证传给 CLI 的描述符是复制后的写端。核对源端和目标端不与标准流、输出管道冲突；正常启动和失败退出均保留原错误及关闭责任。
- [ ] 检查所有生产 `adddup2` 调用的同号风险，覆盖启用通知的 `run`、不启用通知的 `run`、`submit` 和维护命令，以及文件动作准备和 spawn 失败。修复增加的分支才新增对应测试。
- [ ] 执行受影响单元测试和 Debug、Release 生产构建，进行独立代码评审；按实际结果维护验证记录。C 组件修订版本递增，部署说明明确需重新链接 C 主程序。

## 验证边界

不新增或运行集成测试，不访问设备，不重放现场失败请求。单元测试证明模块生成的文件动作满足旧行为下的继承契约，不能替代目标 glibc 2.27、ARM64 或实际回调触发验收。当前任务不构建完整部署包，也不替换已有部署。
