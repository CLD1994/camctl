# 历史恢复与快照维护的性能补全

本计划落实[历史计划 H4、H6、H7](2026-09-30-camctl-history.md)及[路线图阶段 7](2026-09-30-camctl-implementation-roadmap.md#阶段-7-历史快照与规模验证)的生产缺口。恢复方向由[历史查询](../../camctl/historical-state-query.md#按对象选择恢复路径)定义，维护资格、调度和退出由[快照维护](../../camctl/history-snapshots.md)定义，事务内复用由[数据库执行](../../camctl/persistence-runtime.md)定义。

## 已核实的输入与验收边界

当前完整对象恢复按对象累计变化次数选择路径，报告主要对象数组已经使用该入口。有限主行和限定业务列恢复仍固定逆向；动作分段对象的快照恢复还会逆扫 `(S,C]` 来证明 S/H 的行存在性及一次赋值事实，因此实际成本可能超过选定的 `(S,H]` 路径。

快照维护模块和仓储已经实现，但正常 `run` 尚未装配维护拥有者、提交通知及新对象发现通知。现有业务连接也尚未统一使用数据库执行器，不能仅新增一个快照线程便宣称满足业务优先。正常运行的报告轻量变化探测仍有周期读取；本计划不得把它描述成完全取消数据库轮询。

录像收尾的固定只读样本在小结果复用前执行 405 次 SQL，其中有 199 种 SQL 与参数组合；步骤 1 后为 360 次。该样本所有对象均未达到默认快照阈值，不能将其查询次数归因于缺少快照，也不能用该样本证明新快照路径的收益。

保持以下不变量：

- H、C、S 必须是可靠完整事务边界；累计变化次数按对象目录核对，不以全局事件距离代替。
- 恢复只应用原事件，不执行设备、预算或其他业务副作用；不存在、缺失、NULL、非法及未知提交分别处理。
- 坏快照、成员缺失、多余成员、借用较晚的一次赋值事实继续拒绝。不能通过信任当前值或删除证明来减少读取。
- 内存和缓存保持有限容量；原结果页仍只保留三份原页记录。提案与独立守卫之间继续清空证明范围。
- 快照积压不延长会话、不产生 `needs_run`。入队前超时仅停用本次维护，实际数据库错误和结果未知仍按原规则处理。
- 使用 Python 3.11 单元测试及同一只读样本诊断；本次不运行集成测试、不启动 camctl、不调用真机。新增跨组件协作的实际验证限制必须单列。

### 2. 闭合快照证明与有限行恢复

报告需要恢复的事实及校验范围由[报告读取与完整历史恢复的责任](../../camctl/historical-state-query.md#报告读取与完整历史恢复的责任)定义。额外工作及基准见[读取范围审查](../../camctl/report-history-read-scope-review-2026-10-25.md)。先落实报告必要读取，再测量剩余的事件读取与完整快照证明成本。通用完整恢复与报告专用读取必须分别处理；不能由公开数量字段直接推导出新增通用目录的必要性。若剩余事实定位确实需要新增派生结构，再确认其权威规则和既有状态库接续方式。

- [x] 审查报告公开依赖、完整动作恢复与其他消费者的边界，保存真实旧报告重建基准，列明范围收缩、重复读取及配置缺口；报告保障范围由历史查询责任小节定义。
- [x] 接通报告专用的保守依赖闭包和 H 发布集合筛选，复用取消目标、关联交付及当前同来源句柄，独立传递事件批次，按报告复用源连接和空校验结构；以原报告 43、44 测量候选、事件、各类 SQL 和资源，保持原登记字节。实现与证据见[本轮验证](../../camctl/verification.md#报告必要历史读取的验证与安装2026-10-25)。
- [ ] 根据 H 处实际启用的公开分支进一步收窄正式集合的增长关系，契约见[有限事实与实际公开展开](../../camctl/historical-state-query.md#有限事实与实际公开展开)。先在权威登记中表达增长断言的请求范围，恢复有限事实并投影实际节点，再按已经成立的错误头或覆盖节点恢复增长关系；错误可来自取回失败项，不能只按来源动作自己的错误决定。有限集合与请求增长关系分别核验；覆盖只读默认范围及其引用成员，完整历史与变化路由保持原范围。
- [ ] 补充快照证明成本测量：从已有真实历史在独立副本上准备并保存派生快照，不新增业务事件；覆盖 S＝H、S＜H 正向、逆向及平局，并与无快照控制的 H 映像核对。分别记录事件读取与解码、应用、快照读取和存在性／一次赋值证明的工作量及阶段耗时，快照准备不计入目标恢复时间；原只读来源不变。再用最终源码重生成报告 43、44，与相同输入及参数的前版比较。
- [ ] 根据剩余成本决定是否新增事实定位能力；确需新增时，明确创建、一次赋值及其原事件定位的权威派生规则、事务原子性和既有库升级规则。
- [ ] 快照证明只按候选行定位必要原事实；恢复事件按对象计数择短，S=H 不扫描后续普通更新。
- [ ] 有限行与有限主行共用分批事件及正反向应用，快照读取采用流式投影，不装入完整对象。
- [ ] 核对全部生产调用者及失败语义，以独立预期覆盖当前、精确快照、正向、逆向与平局，以及坏快照和一次赋值时序。

#### 报告读取优化的执行顺序

以下工作对应本步骤的报告必要读取验收，不代表完整快照定位或运行时维护接线已经完成。模块划分为实现预估，允许按实际调用关系调整。

1. 以纯单元反例固定取消目标重复读取、取回多来源重复遍历及事件批次未传递。传递已恢复的取消目标事实；按 H 处不可变来源关系有界组织交付，保留全部相关失败、唯一性、缺失关系错误和既定排序。事件批次与候选行批次分离，默认 256 及其他合法正整数均能进入实际恢复调用。
2. 增加报告专用的有限恢复范围并接通真实 `generate_report_file`。从字段依赖登记推导表、关联和前置校验闭包；动作先取得必要主行与适用有限事实，再读取正式集合和对应增长关系。普通产物、交付及其引用文件同样按必要范围恢复。通用完整对象、快照编码和精确旧版本查询保持完整。已有对象事件分页仍核对结构、计数连续性和完整事务；当前、精确快照、正向、逆向和平局按原路径契约处理。不得用报告变化目录代替恢复目录。
3. 在每份报告范围内复用有限只读连接与空校验结构。每页仍释放读事务，保留实例、格式及状态库错误语义；每个恢复对象使用独立唯一性账本，成功、失败、取消及重试均清理临时行和键。不能增加跨报告长事务、无界缓存或常驻全部对象。
4. 集成前分别审查范围推导、增长关系、快照和一次赋值时序、关联失败、配置传递、资源释放及所有同类入口。用受真实接口约束的单元替身覆盖必要行缺失、未来成员排除、晚赋值回退、无关内部投影不读取、运行中已有结果，以及跨来源和非入选交付失败。只读生成原报告 43、44，核对原登记长度和摘要；分别测量候选行、正文、源库与临时库 SQL、事件数和校验结构创建，不用新旧不同操作作提速对照。
5. 本轮运行 Python 3.11 单元全量和受影响静态检查，不运行集成、不启动 camctl、不调用设备、不修改真实状态库。更新验证及本计划原验收项；根据剩余事件与完整快照证明成本决定是否还需要事实定位设计，再报告实际收益与未覆盖边界。

### 3. 接通正常 run 的快照维护

前置条件：生产业务与快照的共同数据库派发边界闭合。预计修改启动装配、会话收场、事务完成通知和外部新对象发现；现有默认阈值及批量保持由权威配置定义。

维护模块在阶段交接时的收尾检查已有明确契约，可以先独立补齐；这项局部修复不代表生产接线已完成。

- [ ] 正常 run 启动查询一次持久化候选；提交成功及外部对象发现按达标对象唤醒，通知可合并且不丢失。
- [ ] 空候选后等待通知，不新增每 500 ms 的全候选查询；维护读、保存之间释放执行机会，业务优先于尚未开始的维护。
- [ ] 准备中、等待入队、排队中、已经开始四阶段均按实际责任退出；迟到结果和数据库错误必须交付。
- [x] 候选返回、依据返回及准备结束后重新检查收尾状态，停止时不发起下一阶段操作，并释放已取得的可再生资源。
- [ ] 只按持久化维护进度报告快照积压；积压不改变业务工作或会话结束条件。
- [ ] 以受真实接口约束的单元替身验证启动、提交、回滚、未知、发现、通知竞争、停用及退出。
