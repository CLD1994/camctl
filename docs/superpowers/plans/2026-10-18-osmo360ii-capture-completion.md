# OSMO 360 II 完成契约实施计划

> **执行者要求：** 使用 `superpowers:executing-plans` 连续执行既有 D2—D4、E2—E3 的补充步骤；媒体工具可由独立工作区协作者并行交付。每项以失败测试、实现、通过验证和阶段提交收场。

**目标：** 将普通录像和原生延时的完成、产物、取消及媒体契约接入正式内置驱动，并通过安装版与 TX2 业务链验收。

**架构：** 扩展现有冻结执行定义、结果分页和取消收场流程，不另建调度或取回系统。设备合同提供命令和文件事实，处理模块持有完成责任；媒体工具保留逐流事实，业务模块判定修复资格。

**技术栈：** Python 3.11、SQLite、现有受管 ADB 进程、ffprobe／ffmpeg、客户端及 C host。

**规格：** [完成与正式接入设计](../specs/2026-10-18-osmo360ii-capture-completion-design.md)。本计划细化已经授权的 [D2—D4](2026-10-16-osmo360ii-timelapse-driver.md#d2-明确返回结束及产物契约) 和 [E2—E3](2026-10-16-osmo360ii-timelapse-delivery.md#e2-正式内置合同的安装版联合验收)，不改变其验收边界。

## 全局约束

- 自然延时为 `DEVICE + SENT + TIME_AND_OUTPUTS`；自然余量和独立 STOP 文件等待均为 30 秒，实际采用值冻结保存。
- LRF 可选；有效非零 OSV 的成功不依赖预览存在。普通录像恰好一份原片，延时至少一份。
- 低功耗不触发 START 重试。只有声明 `finite_device_end` 的新有限延时任务使用延迟取消收场；STOP 失败事实保留。
- 修复保留双路主视频及实际音频，生成独立 MP4，保留原 OSV；保证范围为媒体内容。
- 不访问 Action6，不重复既有六次采集；新实机延时样本每次目标 300 秒。
- 下列文件和内部接口是依据当前代码的实施预估；调整须保持规格的数据流与失败语义，并记录实际采用接口。

## 审查重点

- 可选预览损坏或跨页缺失不使完整原片失效；不登记不可靠配对。
- 30 秒实际文件等待与默认 10 秒读取预算分别装配，恢复不重复采集全长。
- 原结果保存未知先复核原申请；错误活动、错误规则和未来来源页不能成为完成证据。
- STOP 失败后的自然收场只结束活动与占用，不伪造目标采集完成或成功 STOP。
- 默认 ffmpeg 选流、附加封面或 LRF 目录顺序不能导致主视频流丢失。
