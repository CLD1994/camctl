# Action6 与 OSMO 360 II 录像和延时摄影接入设计

## 目标与交付范围

camctl 在 ARM Linux 主机上通过 ADB 控制 Action6 和 OSMO 360 II，完成计划受理、录像或延时摄影、正式产物登记、独立取回、host 文件领取和状态报告。开发与软件验证先在容器完成，真实相机和目标主机的完整验证最后进行。Windows 用于连接相机、试验命令和采集设备资料，不是部署目标。

两款驱动的范围覆盖现有交接资料中的录像、原生延时摄影及可用参数选项。驱动范围不由演示预设缩减；用户通过现有能力说明选择参数并生成计划，经 camctl host 提交。客户端由另一个开发环境维护，本工作提供同源参数定义、能力说明和协议样例供其同步。独立单张拍照不属于此次接入资料覆盖的能力。

| 设备 | 录像演示 | 延时摄影演示 |
| --- | --- | --- |
| Action6 | 主机计时 10 秒后停止 | 间隔 8 秒，任务持续 30 分钟，仅视频 |
| OSMO 360 II | 主机计时 10 秒后停止 | 间隔 30 秒，任务持续 10 分钟，仅视频 |

演示任务的画面和曝光设置由对应驱动的合法参数定义选择。手动和自动曝光均属于实现范围；上述预设不额外建立参数默认值或限制。延时摄影的任务持续时间与成片视频时长不同，不能以采集间隔推算的次数代替实际设备事实。

## 规格责任与运行前提

业务规则分别由[录像](../../architecture/camera-recording.md)、[延时摄影](../../architecture/camera-capture.md)、[能力与参数](../../architecture/camera-capabilities.md)、[录像参数](../../architecture/camera-parameters.md)、[取回](../../architecture/obtaining-outputs.md)及[状态报告](../../architecture/status-reports.md)负责。本设计组织两款驱动的接入边界及验收，不另建一套动作、产物或交付协议。

两款相机的受管拍摄范围内，源文件路径不会复用；设备按键、手机应用和其他控制程序不会另行拍摄。camctl 保持需要的设备及输出范围独占，阻止冲突拍摄。普通输入合法、主机时间可信、通信正常和存储充足的第一版运行边界遵守[正常流程](../../architecture/README.md#第一版正常流程)。

文件存在、目录列举成功、命令进程退出、设备活动结束及文件写完分别表达各自事实。目录基准仅用于关联，不能替代启动确认、停止确认或产物完成依据。没有可靠依据的实际采集次数、媒体时长和设备状态保持未知。

## 驱动与公共执行流程

### 参数定义和启动登记

每款驱动提供参数类型、同源 JSON Schema、参数到设置命令的映射，以及所需执行定义和产物规则。能力导出和首次受理消费同一个权威定义，受理保存用户要求、设备身份、驱动选择及生效参数。命令映射只使用已给出的合法组合；不由样例字节推导任意间隔或持续时间的编码规则。

驱动定义与运行工厂在正常 CLI 启动路径完成一致登记，覆盖 `describe`、受理和运行入口。内部模块名称、参数类型标识及登记函数组织属于实施选择；验收要求是同一绑定和参数在能力说明、受理与实际执行中具有一致含义。

尚未形成完整结束或返回契约的设备操作不导出为已支持能力。可以先实现可独立验证的命令编码、文件适配、公共流程及契约替身；真实响应和设备事实补齐后完成对应解析和能力定义，再进行真实接入验证。候选命令被软件测试覆盖不表示该固件已经支持。

### 控制与文件适配

相机驱动复用既有 ADB 调用和受管进程能力，选择指定绑定，执行设置、启动及适用的停止操作，并解释真实响应。驱动报告调用实际结果和其能够证明的设备事实，不自行决定动作终态、业务重试或整段任务的计时。框架组织意图保存、累计预算、等待、有限核实、取消和恢复。控制调用生命周期遵守[ADB 调用返回契约](../../architecture/adb-execution.md)。

文件适配使用相机已有 Linux 工具，提供指定范围列举、存在性、必要元数据和源端摘要、按位置读取及显式删除。不向相机安装额外工具；主机媒体工具只用于已有规则要求的检查或修复。长文件读取遵守既有读取拥有者和停止责任，读取已完成文件时必要控制操作仍有执行机会。

## 目录基准与文件关联

录像和延时摄影使用相同的基准规则，详见[文件归属](../../architecture/camera-capture.md#本次任务的文件归属)和[分批历史格式](../../camctl/database/history-formats.md#拍摄基准的分批记录)。

1. 动作取得拍摄资格后，保持设备及相应输出范围独占，按驱动声明的范围分批读取目录。
2. 将稳定文件身份分批追加到历史，可靠固定非空或空基准；基准固定及启动意图保存均可靠成功后才允许派发启动命令。
3. 启动后使用原基准识别新增文件，分别保存归属、写入完成和集合确定的事实。
4. 文件与采集要求满足后，原子登记符合条件的正式产物及动作结果，解除已经能够解除的占用。

| 原基准和执行事实 | 必须保持的行为 |
| --- | --- |
| 启动前目录读取明确失败 | 动作直接失败，保留实际读取错误，不自动重试；启动尝试为 0，详见文件归属规格 |
| 基准追加或固定保存失败、提交未知，或者准备仍未完成 | 不启动；按状态库错误、原事务核实或未完成准备责任处理 |
| 基准可靠固定，尚未启动 | 启动沿用原基准，不以计划受理时目录代替 |
| 已启动或可能启动，文件关联尚未保存 | 恢复沿用原基准；不重新启动或替换基准 |
| 有新增文件，设备活动或文件完成仍未知 | 只保存能够证明的关联事实，继续适用核实 |
| 归属和集合尚未确定 | 继续阻止该输出范围内的冲突拍摄；符合资格的兼容文件操作按原规则推进 |

使用完整目录基准，不要求先补齐编号上限、编号解析和目录切换算法。大目录按需、分批读取和保存，避免一次加载全部历史文件。目录游标只说明列举是否结束，不独立证明设备已生成本次任务的全部产物。

## 完成判定与失败表达

### 普通录像

录像继续采用既有正常控制契约：可靠启动确认时记录单调钟锚点，录够目标时长后执行停止，可靠停止确认提供源文件写完依据。源文件按原基准关联；关联和其他适用处理完成后，产物与录像终态一起保存。目录准备、保存和列举不能改变原计时锚点，也不能延误到期停止的调度责任。

正常录像不为核验时长单独拷贝源视频。明确取回动作另建交付；异常检查和修复继续使用已有适用规则。缺少活动查询命令不建立虚构的恢复观察，也不把文件存在解释为设备已经停止。

### 延时摄影

驱动使用相机原生延时摄影，设备负责周期采集。处理模块不将其展开为周期性的单张拍照动作。结束控制与完成方式按[执行定义组合](../../camctl/database/execution-definitions.md#延时摄影执行定义的完成判定方式)确定：

| 经设备核实的任务行为 | 可用的执行契约 |
| --- | --- |
| 设备接受有限目标并自行结束，能够提供原任务完成依据 | 使用设备结束和 `DEVICE_EVIDENCE`，再核实产物 |
| 设备接受有限目标并自行结束，使用明确的等待及产物完成假设 | 使用设备结束和 `TIME_AND_OUTPUTS`，等待目标及声明余量后核实产物 |
| 必须由主机到时停止，停止及必要计时依据能够证明结束 | 使用主机计时和 `DEVICE_EVIDENCE`，停止后核实产物 |
| 结束方式、停止含义或文件完成依据尚未确定 | 保持候选操作，不形成可用任务契约 |

两款相机的延时结束方式仍需真机核实，不预设自行结束，也不默认对所有型号发出同一停止命令。首次受理保存合法契约后只读；执行、重送和恢复不因查询失败改用另一种完成方式。

主机计时任务失去可靠连续计时依据后的有限停止、文件保留及 `duration_unknown` 失败，遵守[主机计时任务的停止与恢复](../../architecture/camera-capture.md#主机计时任务的停止与恢复)。原生启动调用等待整项采集结束才返回时，驱动根据生效参数声明完整调用期限，首次受理保存后保持不变，遵守[完整启动调用期限](../../camctl/database/execution-definitions.md#延时摄影执行定义的完整启动调用期限)；客户端计划不增加字段。

结果核实接口和保存流程必须保留本次任务身份、必要文件事实、列举进度及实际完成依据。实现可以沿用或调整内部类型，但不能由 `result_files_listed/v1` 的条目或空列表补造集合确定事实。任务声明的每种必需产物须满足其检查规则；不默认用时长除以间隔作为必需照片数量。

### 错误与产物保存

产物检查错误按[正式错误分区](../../architecture/camera-capture.md#产物检查的错误表达)处理：可靠空集合为 `capture_failed/no_outputs`；非空集合缺必需类别、数量不符或其他必要检查明确不通过，为 `capture_failed/invalid_outputs`；事实仍未确认而预算耗尽，为 `capture_result_unconfirmed/outputs_unknown`。完整错误包含登记阶段和真实活动 ID，具体未满足规则保存在内部。原驱动错误继续保存其真实含义。

动作成功、失败和设备实际活动分别保存，符合保留条件的已完成文件仍按原规则登记。保存遇到提交未知时先解决原申请责任，不换 key、时刻或决定再做设备操作。历史与当前投影同一事务更新，报告从冻结历史重建，不利用后来的配置或观察补造旧结果。

## 软件验收与真实演示

容器的软件验收使用受上述契约约束的设备替身，组合实际参数定义、受理、执行处理器、SQLite、文件交接及报告；跨组件场景经 C host 提交计划并领取文件。客户端的现有导出及报告消费者可以作为验证对象，客户端产品代码在其独立环境同步。

两款设备分别覆盖录像和延时摄影，证明计划能够完成拍摄、登记产物、独立取回、发布完整待传文件及生成可解释的报告。检查报告和交付文件的身份、大小、摘要与业务状态；源文件保留，删除仅由另行明确的清理动作触发。报告确认与视频收到分别验证。

单元测试覆盖参数合法组合、互斥和非法输入、命令编码及响应分类，使用稳定协作者替身。集成测试覆盖真实组件协作，尤其是基准保存后才启动、旧文件隔离、新目录、跨重启原基准保持、冲突拍摄限制、完成依据未知、明确不合格、产物与终态原子保存及保存未知后的原申请恢复。长时任务使用可控时间验证等待逻辑，不将测试运行时长作为设备计时证据。

软件门禁通过后，在 ARM Linux 主机连接实际相机，按表中的预设执行真正的任务时长和取回流程。验收记录注明固件、主机环境、实际命令与响应的适用范围、产物及报告；软件替身结果不代替设备证据。必要代码调整完成后重跑对应软件门禁，再以实际设备闭环结果判定演示就绪。
