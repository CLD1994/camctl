# camctl 设计总览

camctl 用于在一台嵌入式 Linux 主机上，按照预先提交的计划控制相机等设备。用户在个人电脑的网页中编辑计划，交给负责传输的部门；主机上的 camctl 执行计划，再通过文件把结果交回客户端。

这套系统的关键限制是：主机可能随时断电，下一次开机时间无法预知；有电时也不一定能接收新计划或向外传输文件。相机独立供电，主机断电时可能仍在录像。因此，计划、执行进度和已知结果需要可靠保存，后续开机才能继续处理。详细条件见[运行环境与协作分工](camctl/system-context.md)。

本总览定义系统范围、所有专题共同遵守的规则和规格阅读入口。当前功能范围由各专题共同描述；第一版先贯通正常业务流程，影响业务结果的未明确事项在对应功能落实时确认。文档划分表示规则由哪里完整定义，不预先固定代码模块或数据库表划分。

第一次接触项目可以按本页顺序阅读，再跟随[阅读路线](camctl/reading-guide.md)。完整参数表、状态转换和失败处理都保留在对应专题中。

## 谁在使用和运行这套系统

| 角色 | 所在位置与工作 |
| --- | --- |
| 用户与客户端 | 用户在个人电脑上打开本地网页，编辑并导出计划，导入返回的状态报告，查看结果 |
| 负责传输的部门 | 接收用户递交的计划，安排送达主机；把返回的报告文件提供给用户 |
| 主程序 | 第三方维护的 C 程序，运行在嵌入式主机上；启动和管理 camctl，接收计划并中转待传文件 |
| camctl | 同一主机上的 Python 命令行程序，负责受理、调度、设备控制、状态保存、产物管理和报告生成 |
| 相机等受管设备 | 执行具体采集操作，并使用自己的存储保存原始产物；第一版接入相机录像，MCU（微控制器）预留接口 |

第一版只考虑一台主机和一个逻辑客户端。这里的客户端指维护同一份业务状态和报告确认进度的客户端应用。个人电脑上的客户端与嵌入式主机上的 camctl 是两个程序，通过既定的人工交接和传输流程交换文件。

CLI 是 Command-Line Interface（命令行接口）的简称，后文用它指 camctl 的命令入口。JSON 是计划和报告采用的结构化文本格式：人可以阅读，程序可以按字段处理。用户在网页中完成编辑后，仍须手工递交导出的 JSON；网页导出成功不表示主机已经收到或执行了计划。

## 先用一次录像理解几个对象

假设用户要在 10:00 拍一段录像，再把视频取回来。这个例子只说明业务关系，不规定真实相机的参数类型或默认录像时长。

1. 用户创建一份**执行计划**，其中有“录像 A”和“取回 A”两个**动作**。每个动作表达一件要做的事，例如录像、取回、报告或取消。
2. 客户端为这次提交生成 **`request_id`（请求标识）**。若一直没有收到受理证据，重送时继续使用这个 ID；camctl 已经受理过它时，会复用原计划及进度。
3. 正常录像完成后，相机上的原视频被登记为一份**正式产物**，获得 **`output_id`（产物标识）**。这份原视频继续保存在相机。
4. “取回 A”从相机拷贝视频，在主机准备一份独立待传文件。这次具体交付获得 **`delivery_id`（交付标识）**；正式产物与交付副本各自保留身份。
5. 用户之后用新请求再次取回同一视频时，仍引用原来的 `output_id`，但会产生新的 `delivery_id` 和独立待传文件。原视频不需要重新录制。
6. camctl 生成**状态报告**，告诉客户端哪些计划已受理、动作进行到了哪里、有哪些产物和交付。报告通过 **`report_id`（报告编号）**标识，客户端据此保存状态并反馈确认。

这些对象分开，是因为“录好了”“已准备好一份待传副本”和“客户端已经收到”发生在不同时间。确认报告已收到，也不代表报告中提到的视频已经收到。更多背景、第二次取回与取消的例子见[概念与术语](camctl/concepts.md)。

## 文件怎样交给主程序

视频和报告先在 `staging` 目录生成或拷贝。文件准备完整后，camctl 将它移入 `ready`，允许主程序领取。主程序等到可以传输时，再将文件移入 `processing`，传输完成后删除对应的传输副本。

```text
相机中的正式源文件
    │ 取回时拷贝；源文件仍保留
    ▼
staging：camctl 准备文件
    │ 完整后发布
    ▼
ready：等待主程序领取
    │ 主程序开始处理
    ▼
processing：主程序传输，完成后删除传输副本
```

主机断电时，相机可能继续录像，导致原视频明显长于计划要求。对符合修复条件的视频，camctl 会在后续恢复处理中，在主机上裁剪多录部分，另存一份修复成品，同时保留原视频。具体触发条件见[异常录像恢复与修复](camctl/camera-recovery.md#内部异常多录修复)。

这三个目录表示文件现在由谁处理。`staging/derived/` 另行保留主机加工形成、可以反复取回的正式成品，例如修复后的视频；每次取回都为它准备独立交付文件。主程序不会读取 `staging` 中的半成品，camctl 也不能撤回已经进入 `processing` 的普通交付文件。具体权限、原子移动和失败情况见[文件交接](camctl/file-handoff.md)。

## 第一版正常流程

本流程以单台主机和当前相机为对象；主机使用 ADB（Android Debug Bridge）通信，通过 `adb shell` 在相机中执行控制程序。流程假设输入合法、主机时间可信、通信正常且存储空间充足。[采集与取回计划示例](camctl/plan-acceptance.md#基本结构)使用样例驱动参数演练业务链；真实设备验收使用依据实际相机能力另行确定的正式参数类型。

| 步骤 | 谁执行什么 | 可观察结果 |
| --- | --- | --- |
| 1. 交给 CLI | 主程序调用 `run <plan-path>`；运行期间的新输入通过 `submit` 交接 | 一份计划及其全部动作原子受理，同请求重送复用原实例 |
| 2. 按时录像 | camctl 在启动窗口内调用相机；成功确认后计时，到目标时长停止 | 正常录像完成，源视频保留在相机；产物登记与录像终态同时提交 |
| 3. 取回产物 | 取回动作到时间后选择正式产物，拷贝到自己在 `staging` 中的工作文件 | 独立 delivery；文件准备完成，保存大小、摘要和最终文件名 |
| 4. 本地发布 | camctl 将准备好的文件发布到 `ready`，并生成覆盖业务结果的状态报告 | 取回成功；全部动作结束后计划 `completed` |
| 5. 中转文件 | 主程序把 `ready` 文件移到 `processing`，传输后删除本地传输副本 | 客户端收到报告和交付文件，两者可以先后到达 |
| 6. 接受并确认 | 客户端核验报告、确认累计覆盖并保存状态，通过后续输入确认报告；视频按报告中的文件名、大小与摘要另行关联和核验 | 报告确认水位推进；相机原片仍保留 |
| 7. 按需清理 | 客户端用新计划显式清理已不需要的 `output_id` | 删除对应正式源文件，数据库保留全部业务历史 |

普通文件交付名使用 `<delivery_id>.<ext>`，完整可读名称通过报告的 `display_name` 展示。报告确认不等于普通视频已收到；源视频是否删除由客户端的显式清理请求决定。

### 第一版完善与验收范围

当前先形成 MVP（最小可行版本），验证计划生成、CLI 受理与调度、产物取回、文件交接及客户端报告处理的软件流程。相机尚未到位时使用受驱动契约约束的相机替身，配合真实 CLI、SQLite、交接目录与客户端进行集成验证；已有样例参数用于协议演练，不据此宣称真实相机支持相应配置。主程序和传输环节可按已约定的职责进行测试代行，实际对接仍需第三方联调。

相机到位后，完成真实驱动命令、设备响应和实际文件的联调验收。拍摄参数优先覆盖用于验证的任务，已确定的固定设置由驱动执行；更多设备参数选项在完整交接后细调，沿用现有扩展接口。当前参数范围见[当前相机录像参数](camctl/camera-parameters.md)。

先使上述主流程完整可运行，再覆盖会改变正常使用结果的必要分支：同一请求重送、已支持动作自身参数错误、设备尝试耗尽、取消、启动窗口过期、取回断点续传及报告确认。已有规则继续作为这些分支的边界。

| 工作 | 第一版落实方式 |
| --- | --- |
| 业务与文件主流程 | 按上表交付一条贯通计划、驱动、数据库、文件和客户端报告的集成场景 |
| 数据持久化 | 保持已确认的历史与投影原子提交、身份稳定及重启恢复要求 |
| 实现细节 | 字段编码、表划分、命令封装及测试组织在对应功能实现时确定 |
| 真实相机接入 | 依据设备能力完成正式拍摄参数规格、驱动命令映射及主流程联调；驱动替身通过不代表真实设备已经验收 |
| 后续设计讨论 | 实现中出现无法由现有规则确定、且影响业务结果的情况时，再补齐该具体契约 |


## 持久化与配置基础

camctl 将计划和状态保存到 SQLite 数据库。历史记录永久保留；当前状态由历史计算，并在同一事务中与新历史一起更新。这样既能查询当前进度，也能重建之前已经保存的状态。日常运行只打开已有状态库，首次部署通过 `camctl init` 显式创建。完整的历史、恢复和配置规则见[共同原则与状态持久化](camctl/system-foundations.md)。

本地配置默认路径为 `$HOME/.camctl/config.toml`。配置文件可以不存在，此时使用内置默认值；提供的字段覆盖相应默认值。加载、生效范围及通信策略见[本地配置](camctl/configuration.md)，初始化步骤见[首次部署与初始化](camctl/initialization.md)。
