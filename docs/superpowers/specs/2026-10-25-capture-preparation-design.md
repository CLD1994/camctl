# 拍摄提前准备与实际启动

## 目标和适用范围

ADB 相机在拍摄计划时间之前完成设置和目录基准准备，到计划时间后才发送真正的 START。准备耗时不再全部挤入 `max_delay_ms`，启动窗口继续约束实际 START 的派发。相机实际采集时间与主机发令时间仍分别表达，不承诺固定触发精度。

本规格修订[通信准备](../../architecture/scheduling-execution.md#通信准备)、[驱动执行与产物边界](../../architecture/camera-capabilities.md#驱动执行与产物边界)和[启动前目录基准](2026-10-25-result-reading-performance-design.md#启动前的目录基准)。当前适用于声明独立准备能力的 Action6、OSMO 普通录像与原生延时；其他驱动继续使用其已有合同。

## 提前量和设备资格

`devices.<id>.connection.prepare_lead_s` 是设备部署参数，接受有限非负秒数，允许精确小数，拒绝布尔值。驱动提供默认值，当前 ADB 相机默认提前 10 秒。0 表示从 `scheduled_at` 开始准备。计划不能覆盖该值，配置不改变已经保存的拍摄参数和启动窗口。

准备资格的时间下界为 `scheduled_at - prepare_lead_s`，上界为原启动窗口末尾。同设备已有拍摄、保留或准备占用优先；空闲时按计划时间、计划受理顺序、原动作数组位置选择。新加入且时间更早的动作不抢占已经可靠取得的准备责任。等待设备资格不消耗设备调用的执行期限。

准备在设置前取得原活动和设备占用，在读取基准前持有原输出范围，保持到原释放条件成立。不打断已有拍摄，不允许准备动作改写其他活动的设置或基准。准备期间动作保持 `pending`、`execution_started=0`，计划不因此转入执行中；设备活动与准备尝试独立可靠保存。

## 准备、保存与启动

准备与真正启动分别拥有设备调用意图、实际结果和次数。设置准备采用当前启动配置的控制超时，每个执行会话只有一次设置组合调用，不在驱动内部重试，不消耗 START 次数。设置失败保留真实错误；基准读取继续沿用原有限规则和单次扫描上下文。

| 阶段 | 必须可靠取得的依据与动作 |
| --- | --- |
| 取得准备资格 | 在写事务内复核时间、取消、设备绑定、原占用和候选顺序；为 `pending` 动作建立唯一设备活动。 |
| 设置 | 沿原生效参数逐条执行，使用独立 `PREPARE_CAPTURE` 尝试；每条派发前核对取消、终态、原占用和窗口上界。 |
| 设置结果保存 | 原拥有者保留原返回及完整保存申请，可靠保存后才授予后续准备资格；结果未确认时不重做设置。 |
| 完整基准 | 使用原活动的独占扫描，逐页可靠保存并固定；已有固定基准复用，不因新会话重新采集。 |
| 等待计划时间 | 已完成准备的任务交回流程，不让后台任务一直等待；原活动继续持有占用。 |
| 真正启动 | 到计划时间后复用原活动，登记动作开始和适用录像处理责任，独立授予 START；实际派发前再次核对完整启动窗口及取消。 |

设置准备的成功只说明全部必需设置已经完成，通过独立的 `capture_preparation_completed` 观察表达，不表示拍摄已发送、开始或完成。设备合同允许非阻断设置失败时，该单条调用的真实失败继续保留，设置组合按必需设置的完成情况判断；不将最后一条设置的返回代替完整组合结论。完整准备资格由本会话可靠设置结果、驱动持有的同一次准备凭据及原活动固定基准共同形成；不以一项成功代替其余依据。

驱动将准备凭据绑定到原设备、实际 ADB serial、活动、操作、生效参数和准备票据。只有携带匹配凭据的实际启动调用可以省去设置。新会话清除驱动内存凭据，不能只凭数据库中的旧成功结果跳过设置。未使用独立准备的旧控制入口仍遵守其原设置和启动合同。

## 状态与失败分类

以下判断先核实原事务和数据库事实；数据库不可读、矛盾或保存未确认时沿原错误责任处理，不解释成设备没有执行。

| 状态与条件 | 处理 |
| --- | --- |
| 准备尚未完成，未取消且窗口仍有效 | 沿原身份推进；允许早于计划时间准备，禁止早于计划时间 START。 |
| 设置明确失败或目录基准明确失败，原调用已收场 | 保存实际结果；动作使用 `capture_failed`，分别采用 `device_failed` 或 `baseline_read_failed`，保留 `execution_started=0`；释放符合条件的准备占用。 |
| 准备期间取消 | 阻止后续设置、目录读取和 START；动作按取消规则结束，取消处理等待原调用、原保存和占用释放责任完成，不发送 STOP。 |
| 窗口结束且没有实际 START 或待核实启动效果 | 保存原窗口观察及适用过期原因；阻止新命令，已开始的调用独立收场后才释放占用。 |
| 已有 START 在途、效果未知或成功确认 | 进入原启动核实、采集、停止或恢复流程，不回到准备后再次发送 START。 |
| 已登记执行准备，但尚无 START 尝试，或既有 START 尝试均已可靠确认无效果；原窗口与 START 剩余额度仍允许启动 | 同会话复用匹配准备凭据；新会话可沿原活动重新准备设置，保留原 `running`、执行标记、固定基准和 START 次数，不重新创建活动。 |
| 动作已终态但准备调用或保存尚未交付 | 保留准备责任，继续必要收场，不启动新业务；终态不被迟到结果改写。 |

准备期间的合法执行失败形成 `failed + execution_started=0`，与受理失败分别验证。合法受理的驱动、参数和执行定义保留，真实设备错误保存在对应准备尝试中，报告沿原错误及来源身份解释；不将动作提前标记 `running` 来获得接口资格。

## 冷恢复和取消后的收场

冷恢复先核实原准备尝试和完整保存申请；没有真实返回的旧设置责任按现有前台命令恢复合同结束，不把旧意图当作设置成功。尚未真正启动且仍有窗口资格时，新会话建立自己的设置准备责任，复用原活动、占用和已经固定的基准；不重置 START 次数。已有 START 责任按原恢复分类优先处理。

准备原调用仍在执行或保存未交付时，基准已固定也不能单独授权释放占用。取消处理、过期、终态发现和会话结束均须能找到 `pending` 或已终态动作持有的准备责任。工作清单的最终关闭与业务占用释放分别处理，遵守[基准缓存生命周期](2026-10-25-result-reading-performance-design.md#启动前的目录基准)。

## 持久化和实现边界

沿用唯一 `device_activities` 活动保存设备与输出范围占用，新增操作种类 `PREPARE_CAPTURE` 保存设置调用。准备流程的责任键包含原活动和执行会话身份；同键保存重送继续原申请。动作开始事务复用已准备活动，历史守卫及重放核对同样的状态组合。

新增状态和操作种类使用新的数据库格式；现有事件类型与版本只在其可表达的新分支内扩展。安装交付保留当前人工验证数据库的全部历史、身份、产物及配置，先备份，再按权威结构核对升级结果；不通过初始化空库替代升级。

`camctl init --upgrade-capture-preparation` 显式将格式 V3 升级为 V4，沿用初始化的稳定会话锁和目录绑定核对；普通 `init` 保持只验证已有库。升级保留一致备份，在实际库外完成准备和内容核对，再共同发布结构与版本；身份、目录绑定、业务历史、水位和产物保持原值。既有 V4 重复执行只核验，V1/V2 先完成其已有明确升级路径，两个升级选项不合并执行。目录绑定变更也与格式升级分别进行。

## 验证

单元验证覆盖提前时间边界、0 与非法配置、多个候选和已有持有者、设置与实际 START 分离、同会话凭据绑定、准备失败且未开始、原保存未确认、取消和过期时实际调用收场、冷恢复与 START 未知优先、固定基准复用、计划状态及历史守卫。使用受真实接口约束的替身，不运行集成测试或相机命令。完整软件验证后交由用户进行真机验证，实际准备耗时由分阶段计时记录。
