# 相机录像

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义 `camera_record` 的完整生命周期，包括采集、核验、内部修复和取消。公共执行规则见[调度与设备执行](scheduling-execution.md)，正式产物的身份和清理规则见[正式产物与取回清理](outputs.md)。

## camera_record

### 基本语义

对调用方暴露一个复合动作：

```text
camera_record
```

参数：

```text
scheduled_at
duration_s
record
```

底层由：

```text
record_start
record_stop
```

组成。

### 当前相机的原片文件

已确认当前相机不会将一次连续录像按时长或文件大小自动拆成多个文件。一次连续录像形成原片时，对应一个源视频文件；本设备的原片关联、完整性核验和取回以该文件为单位。内部修复产生的成品是独立的派生产物。

### 通信方式与查询能力

当前相机运行嵌入式 Linux，具有完整文件系统，并提供具有完整命令执行权限的 `adb shell`。camctl 通过 shell 执行厂商提供的二进制程序，控制相机的录像等行为；文件列举、存在性检查、读取及删除由驱动通过 Linux 文件操作实现。已确认可以通过 shell 命令查询正在录制的文件名或路径，以及检查对应文件是否存在。

相机端只使用已有系统能力和厂商程序，不允许添加依赖或部署额外工具。`ffmpeg/ffprobe` 是主机端工具。正常录像不得仅为读取原视频时长或执行媒体核验而新增从相机到主机的视频拷贝；录像完成判定须在这一边界内设计。明确请求的取回、必要异常修复，以及正常会话中计时证据不足时的异常原片检查，按各自规则拷贝文件。

`adb shell` 和具体 shell 命令属于当前相机驱动的实现方式，不是框架要求所有相机提供的接口。框架通过驱动声明的业务能力取得录像和文件查询结果；未来驱动可以使用其他设备协议，调度、持久化和产物流程不依赖 ADB 或 Linux 命令。

查询正在录制的文件与查询指定文件是否存在分别表达各自的观察结果。文件存在本身不证明本次录像仍在进行或文件已经写完；查询错误或结果未知也不能当作文件不存在。具体命令、返回格式和结果识别在设备适配时核实，录像归属及写入完成仍按各自证据规则判断。

### 录像期间的文件操作

已确认当前相机正在录像时，可以同时读取另一份已经写完的视频，不影响正在进行的录像。当前驱动将这种文件读取声明为与录像兼容，camctl 不因相机正在录像而要求该读取等待设备空闲。

当前驱动依据 Linux 文件语义处理已完成视频；删除指定文件的目录项不要求停止另一份视频的录像，也不删除另一份视频。该判断依据现有设备前提及普通文件操作语义，具体适配通过联调验证。[Linux unlink 文档](https://man7.org/linux/man-pages/man2/unlink.2.html)

对正在录制 B 的当前相机，另一份视频 A 的操作按以下规则处理：

| 操作及资格 | 处理 |
| --- | --- |
| 读取 A，来源及写入完成已确认，所属取回、异常原片检查或内部修复具有执行资格 | 允许读取，无须等待 B 停止 |
| 删除 A，已有明确清理授权，且满足产物清理及旧取回保护条件 | 允许删除 A，无须等待 B 停止 |
| 相应操作资格不满足或无法可靠确认 | 按所属流程等待、核实或报告错误；Linux 操作能力不代替业务授权 |

操作调度遵守[设备执行与操作兼容性](scheduling-execution.md#设备执行与操作兼容性)。文件操作不能妨碍必要的录像停止操作；控制通道与文件通道的实际协作通过适配验证。未来相机由对应驱动声明兼容性，不自动继承当前相机的能力。

### 源文件命名与录像关联

启动录像时能否指定相机源文件名或保存路径，由相机驱动声明。当前相机不支持；框架保留使用该能力的扩展入口，不将其作为相机接入或断电恢复的必备条件。

| 驱动能力 | 启动与关联方式 |
| --- | --- |
| 已确认支持指定源文件名或路径 | 可以使用该能力；使用时，将选定目标与启动意图一同可靠保存，再发送启动命令 |
| 已确认不支持 | 按设备自身的命名方式启动，由驱动通过已核实的设备协议关联本次录像及其源文件 |
| 能力未知或读取能力信息失败 | 明确保留未知或错误，不据此认定支持或不支持；先确认能力再选择相应路径 |

驱动向框架提供录像与源文件的关联结果及确认依据；框架持久化这些事实，供后续收场、核验和取回使用。设备特有的命名和查询方法由驱动负责，不要求所有相机采用同一种方法。

预先指定的路径属于启动意图，不证明设备已经开始录像或实际生成了该文件。命令失败或结果未知时，仍按录像对账规则核实，不能当作能力不支持而直接改用另一种方式再次启动。当前相机通过上述 shell 查询取得文件信息；如何结合这些信息确认本次动作的录像归属，以及启动后尚未保存关联就断电时如何恢复，仍需结合实际协议确认。

### `duration_s`

`duration_s` 表示：

> 从已经确认本次录像进入 recording 状态的时刻开始，至少继续录制这么长时间。

### 录像启动确认

驱动必须定义：

> 什么证据足以确认本次录像已经处于 recording 状态。

已确认当前相机的启动录像指令返回成功时，相机已经进入录像状态。驱动可靠识别本次启动指令的成功响应，即可确认录像已开始，无须为确认启动再查询一次录像状态。收到该成功响应时读取当前会话的单调钟，作为下述计时锚点；后续持久化或源文件查询不重新设置该锚点。

该响应须可靠关联到本次启动尝试。命令已发出、响应失败、丢失或无法解释均不能代替成功确认，继续按启动结果未知及设备对账规则处理。成功响应确认录像已开始，但不自动提供源文件身份；源文件仍按“源文件命名与录像关联”确定。

未来相机由对应驱动定义可靠的启动确认依据，不自动继承当前相机的成功响应保证。

确认时记录：

```text
recording_confirmed_at_monotonic
```

正常停止目标：

```text
stop_target_monotonic =
    recording_confirmed_at_monotonic + duration_s
```

该时间点不是“第一帧真实时间”。

它只是一个保守锚点：

> 从这里开始可以确定录像已经进行。

因此正常情况下可能略微多录，但不主动少录。

如果设备协议不能提供可靠的录像启动确认，必须降低保证并如实报告，不能使用“发出 start 指令的时间”冒充实际录像起点。

### 录像启动的历史事实

按[历史事件的粒度](../2026-09-08-camctl-cli-design.md#历史事件的粒度)，启动过程分别记录以下具有独立含义的事实；下列中文名称说明事实含义，具体事件标识和字段结构仍需结合设备协议细化。

- 启动意图已登记：关联动作、相机、本次尝试和已经确定的执行参数。该事实及相关投影提交成功后，才允许发送启动命令。
- 启动已确认：取得本专题要求的确认依据后，记录确认事实，以及设备协议能够提供的录像身份和有效计时依据。
- 启动尝试结果未知：例如等待响应超时且无法确认实际结果时，记录本次尝试和未知原因，供后续设备对账使用。

启动意图提交后、结果记录提交前断电，恢复时可能只能查到启动意图。这只能证明存在一次待核实的启动尝试；实际命令是否发出、录像是否启动仍须依据设备对账判断。历史中不能凭意图补写命令已发送或启动成功，也不能把缺少结果解释为设备未执行。

### 正常轻微多录

由保守确认点造成的正常少量尾部余量，不自动视为异常录像。

不为了精确卡秒而强制对所有录像执行裁剪。

### 客户端排程责任

客户端应保证同一相机计划中的录像时长不发生预期冲突。

camctl 不负责自动重排录像计划。

如果由于实际启动/停止延迟产生运行时冲突：

> 已经开始的录像优先。

后一个录像：

- 在自己的启动窗口内等待；
- 相机释放后仍在窗口内 → 开始；
- 超窗 → `expired`。

不得为了赶后一个录像而提前截短已经开始的录像。

### 主机断电导致超时录像

允许主机断电期间相机继续录像并超过目标时长。

恢复后：

1. 对账本次录像；
2. 能证明目标时长已经满足 → 尝试停止；
3. 目标时长尚未满足 → 在能够可靠计算剩余时间时继续等待；
4. 无法正常停止 → 有限通信尝试；
5. 尝试耗尽 → 失败，不执行电源操作。

### 断电恢复后的控制完成依据

断电恢复后，能够可靠确认设备仍在进行本次同一段连续录像，且结合可信的历史计时依据与当前可信时间证明已经满足 `duration_s` 时，可以继续以控制完成作为成功依据。取得本次录像的停止成功确认，并确认对应源文件已经写完后，不为证明控制成功而单独拷贝原片；异常多录的修复及计时证据不足时的原片检查按后文处理。

恢复须保存录像归属与连续性的确认、所用可信时间及满足目标时长的判断、停止结果和源文件关联。仅文件存在、当前墙钟可信或数据库中曾有启动意图，均不能单独证明已经录够；不能将旧会话的单调钟读数与新会话读数组合计算时长。先处理取消、已有终态及已经保存的控制完成事实，其余情况再按当前录像与计时证据判断。

| 恢复时的证据 | 处理 |
| --- | --- |
| 同一段连续录像已确认，可信计时证明已满足目标时长 | 尝试停止，取得成功确认及源文件写完依据后，形成恢复控制完成事实 |
| 同一段连续录像已确认，可信计时证明尚未满足目标时长 | 按已有规则等待剩余时长，满足后再停止；等待期间仍遵守取消与异常处理规则 |
| 当前仍是同一段录像，但历史计时或当前时间不足以可靠判断 | 按对应保守收场规则处理，不直接套用可信计时成功分支 |
| 录像归属或连续性不明，或相关记录与查询结果不可可靠取得 | 先对账或按对应错误处理，不推定本次录像持续进行 |
| 录像已停止或已有可靠保存的控制完成事实 | 按已保存事实及对账结果恢复，不为了取得新的停止响应而重新执行已完成收场 |

取消与既有终态优先于上述恢复判断。已经确认的时长不足、原片损坏等失败事实不能被后续成功停止掩盖。

需要异常多录修复时，继续完成该内部流程，之后统一登记原片、适用的派生成品及动作终态。修复失败本身不撤销已经取得的恢复控制完成依据；若处理发现明确的录像失败证据，则按“录像成功标准”判定并报告。

### 时钟异常下的保守收场

如果：

- 主机墙钟不可信；
- 能确认设备仍在进行本次录像；
- 能确认是同一段连续录像；
- 无法确定历史已经录了多久；

则额外等待：

```text
min(duration_s, recovery_wait_cap_s)
```

只使用当前 run 的 单调钟。

达到该上限后：

> 尝试停止录像。

即使无法证明已经录满全部 `duration_s`，也不允许为了完整性无界继续等待。

`recovery_wait_cap_s` 是异常恢复保护参数，不是正常录像 `duration_s` 的上限。

### 安全收场与后续处理的衔接

时钟异常会话只执行允许的有限安全收场，不启动或恢复视频拷贝、媒体核验及修复。对尚未取消、未进入终态的录像，成功停止并确认源文件归属及写入完成后，若修复判断或其他适用后处理尚未完成，则保存进度，交给后续取得正常执行资格的 `run` 继续处理。

相机已经停止与动作尚未完成分别表达。此时录像动作保持 `running`，处理阶段表达“已停止，等待正常会话处理”；状态库保存停止依据、源文件关联、已有计时证据及未完成阶段，不将其表达为设备仍在录像。该阶段不增加新的公共动作状态。原片仍保存在相机，尚不登记为正式产物；等待中的取回继续遵守录像终态与正式产物的统一登记边界。

先处理取消、已有终态及记录不可可靠读取的情况，其余按会话资格和已保存进度分类：

| 会话与录像进度 | 处理 |
| --- | --- |
| 时钟异常，已确认停止、源文件归属及写完，仍有后处理未完成 | 保存等待阶段，不执行后处理、不提交录像终态或正式产物；本次有限收场完成后以时钟异常退出 |
| 时钟异常，尚未确认停止、源文件归属或写入完成 | 按原有限收场及对账规则处理，不能用等待后处理阶段代替尚未取得的停止或文件证据 |
| 后续会话仍时钟异常，已保存等待后处理阶段 | 保留进度，不重复已确认完成的停止，也不启动后处理；其他允许的有限收场完成后退出 |
| 后续会话取得正常执行资格，已保存等待后处理阶段 | 使用原停止结果、源文件与固化策略继续判断并执行适用后处理；全部完成后统一登记正式产物及录像终态 |

停止尝试耗尽仍按既有失败及残留设备事实规则结束，不能通过无限保留等待阶段重置预算。取消及已有终态按其原规则处理；等待后处理期间仍可取消尚未终态的录像，此时放弃内容，不在后续会话恢复修复。

停止确认、阶段进度及相关投影按历史事务规则保存。文件或数据库结果未知时先对账，不推断已停止、文件已写完或动作已结束。已经保存的修复输入拷贝进度、修复决定及有限预算继续保留，后续正常会话恢复原处理，不重新开始录像或重置已消耗预算。历史回放本身不执行这些外部操作。

待恢复的录像后处理仍属于未完成计划工作，但不能阻止时钟异常会话结束，也不授予普通接纳资格。下一次实际启动且取得正常执行资格的会话负责继续驱动；当前时间恢复可信不补造历史录像时长，修复仍使用既有可靠计时与证据规则。未来会话何时启动、时间何时恢复可信，不由本阶段保证。

### 停止命令的重复执行

已确认当前相机的停止录像指令可以重复执行。相机已经停止录像时，再次执行该指令仍尝试停止录像，保持停止状态，不产生额外副作用。

当前相机驱动据此声明停止操作可安全重复。停止尝试的响应丢失或结果未知时，允许在原收场流程及剩余有限重试预算内再次发送停止指令；主机重启不创建新的补偿流程或重置预算。命令可以重复执行不表示此前尝试已经成功，停止结果仍须按实际确认或查询证据保存。

重试仍受录像归属及取消目标约束：不能停止其他动作的录像，也不能把归属未知的录像当作本次目标。已确认本次录像停止后，按相应完成及取消规则继续处理，不因具备重复执行能力而增加无必要的停止操作。

本能力属于当前相机。未来相机是否支持安全重复停止由对应驱动确认，并遵守[效果登记与补偿](scheduling-execution.md#效果登记与补偿)的公共规则。

### 停止成功与文件可读

已确认当前相机的停止录像指令返回成功时，对应视频文件已经写完，可以立即读取；此后文件内容和长度保持不变。驱动将本次停止成功与已确认的录像及源文件关联，camctl 保存该确认事实后按“录像成功标准”完成正常录像，或继续必要的异常处理，不额外等待文件长度稳定。

该保证用于确认源文件已经完成写入，不表示已经读取并核验文件内的视频时长。正常录像结合启动确认和单调钟计时判定控制流程是否完成。源文件登记与动作终态继续遵守“录像动作的结束时点”。

| 停止结果与文件关联 | 文件处理 |
| --- | --- |
| 返回成功，且对应录像与源文件已可靠关联 | 确认文件写完，可完成正常录像；实际读取按取回或必要异常处理的资格执行 |
| 返回成功，但录像或源文件关联不明 | 先核实关联，不将任意已有文件视为本次产物 |
| 停止失败、响应丢失或结果未知 | 不据此认定文件写完；按停止重试及设备对账规则取得可靠依据 |
| 停止或文件确认记录的保存失败、提交结果未知 | 按持久化错误处理，恢复先确认实际记录，不猜测确认结果 |

未来相机由对应驱动定义文件写完的可靠确认依据，不自动继承当前相机的停止成功保证。仅文件存在或一次长度查询不能证明写入已经完成。

### 停止失败

停止通信尝试耗尽后：

```text
camera_record = failed
```

但是不能推断：

```text
camera is idle
```

应持久化类似：

```text
possibly_recording
```

的设备事实。

后续操作：

- 与录像兼容 → 可以继续；
- 必须要求 idle → 先按需对账。

如果后续必须 idle 的操作发现：

```text
确认仍是历史已知残留录像
```

则允许有限尝试停止。

如果：

- 无法通信；
- 无法确认录像归属；
- 停止仍失败；

则保留残留事实，当前动作按自身规则失败或过期。

不做后台周期恢复。

### 录像成功标准

正常录像的 `succeeded` 表示已按要求完成录像控制流程。未取消、未发现提前停止等录像异常时，须同时具备以下事实：

1. 已可靠取得本次录像的启动成功确认，并保存接收成功响应时的单调钟锚点。
2. 从该锚点起，按当前会话单调钟等待至少 `duration_s`，再执行停止。
3. 已取得停止成功确认，并可靠关联对应源文件及其写入完成事实。

满足上述条件且没有尚需完成的处理时，登记原片并提交动作 `succeeded`。正常录像不为读取时长或媒体核验而将原片拷贝到主机，也不要求读取视频轨道、时长或逐帧解码。

正常控制完成的事实已经可靠保存，仅在终态登记前中断时，恢复使用这些事实完成登记，不将登记中断本身视为录像异常。使用的是原会话已保存的计时结果，不能将旧单调钟锚点与新会话的时钟读数组合计算时长；完成事实缺失或未知时仍先对账。

报告区分目标时长、控制过程的计时证据及从文件取得的媒体信息。未读取文件内时长时，实际视频时长保持未知，媒体核验表达为未执行；不能以 `duration_s` 或主机等待时长代填实际视频时长，也不能将未执行核验记为核验失败或核验通过。

业务记录可可靠读取时，先处理取消与已有终态，再按下表的其余分区判断；记录保存失败或提交结果未知仍按持久化错误处理：

| 当前录像处理情况 | 结果处理 |
| --- | --- |
| 已取消或已有终态 | 按取消及终态规则处理，不由本节覆盖 |
| 正常控制流程尚未完成 | 继续执行或确认，不提前判成功 |
| 正常控制流程具备上述全部事实 | 按控制流程完成判为 `succeeded`，不要求媒体核验 |
| 已发生提前停止、断电恢复、停止失败等异常，仍有适用处理未完成 | 继续对应恢复及有限处理，不能套用正常流程的成功条件；旧会话单调钟不能用于新会话计时 |
| 异常处理结束，已有明确的录像失败证据，例如确认时长不足或原片损坏 | 按失败规则结束，不用后续停止成功覆盖已知失败事实 |
| 异常处理结束，没有明确的录像失败证据，已有可靠的恢复控制完成事实或文件核验结果确认原片包含完整目标内容 | 判为 `succeeded`，保留具体成功依据、异常及修复结果；未读取媒体时长时仍表达未知 |
| 异常处理结束，仍未取得满足成功标准的证据 | 按失败规则结束，保留已经确定的文件、异常及未知事实 |

恢复控制完成的具体依据见“断电恢复后的控制完成依据”。异常多录仍按内部修复规则处理；因必要修复已取回主机的视频可由主机工具读取视频信息。恢复已取得充分控制证据且确认无需修复时，不为核验单独拷贝原片；是否明显多录仍无法判定时，按“计时证据不足时的原片检查”拷贝检查，不凭目标时长推定文件完整。

成功结果保留实际使用的判定依据，不隐藏通信失败、延迟停止、恢复或修复过程。动作终态提交后，后续取回或检查发现的时长不足、损坏等媒体问题作为新的产物质量事实记录并报告，不改写录像动作的历史终态。

### 原片保留与核验结果

未取消的录像，只要原片存在、确认属于本次录像且已经写完，就在处理结束时登记为正式产物。原片不足目标时长、无法正常播放或核验失败，均不取消其保留及原样取回资格；报告分别表达录像动作结果、文件可取回状态及核验结果。

下表用于动作终态尚未提交时的结束判定；仅适用的核验、必要修复及有限收场需要完成，正常录像不新增媒体核验，取消优先处理：

| 录像及原片情况 | 结束时的处理 |
| --- | --- |
| 录像已被取消 | 按录像取消规则放弃内容，不登记为正式产物 |
| 未取消，原片归属和写入完成已确认，正常或恢复控制已完成，没有明确的录像失败证据 | 登记原片并按成功标准提交 `succeeded`；未执行或未取得结论的媒体核验如实表达，不能单独否定控制完成依据 |
| 未取消，原片归属和写入完成已确认，未取得控制完成依据，已执行的核验确认包含完整目标内容 | 登记原片，按录像成功标准及修复规则提交动作结果 |
| 未取消，原片归属和写入完成已确认，核验确认不足目标时长、内容损坏或无法正常播放 | 登记原片并提交动作 `failed`，保留具体核验结果及原因 |
| 未取消，原片归属和写入完成已确认，未取得控制完成依据，核验流程已按有限处理规则结束但未取得可靠结论 | 登记原片并提交动作 `failed`，报告核验未确认及原因，不能将其写成已经确认损坏 |
| 未取消，可靠确认没有形成原片 | 按相应失败或过期规则结束，不创建虚构产物 |
| 未取消，文件是否存在、归属或写入完成无法确认 | 按对账及有限收场规则处理；不能将未知文件登记为可取回产物，也不凭核验失败推断源文件不存在 |

例如目标 60 秒却只有可以正常播放的 30 秒原片，或原片已写完但无法播放：动作均为 `failed`，原片仍有稳定的 `output_id`，客户端可原样取回。报告保存目标时长、能够可靠取得的实际时长及失败原因；无法取得实际时长时明确表达未知，不以零或目标时长代替。

已有恢复控制完成依据或已确认原片包含完整目标内容，仅内部修复失败时，仍按“修复与动作成功分离”保持录像成功。核验过程中主机副本读取或校验失败，不表示相机源文件已经损坏；是否能原样取回仍按源文件及本次交付的真实状态判断。

原片按[长期保留](outputs.md#长期保留)规则保存，由客户端后续提交包含 `delete_action_outputs` 的执行计划并明确指定 `output_id` 清理。原片登记与动作终态仍在“录像动作的结束时点”规定的同一事务中提交；等待中的取回在提交后选择原片。已有终态及正式产物不因后续查询重新判定或重复登记。

### 内部异常多录修复

视频裁剪不是公开 action。

它是 `camera_record` 的内部修复机制，仅用于：

> 异常导致的明显多录。

#### 自动修复的多录门槛

以本地配置的固定额外秒数作为允许多录的余量。设该值为 `T`，本次录像的修复门槛为：

```text
修复门槛 = duration_s + T
```

对异常录像，可信计时能够证明本次同一段连续录像的录制时间严格超过该门槛时，触发内部修复。恰好等于门槛不触发。`T` 是固定秒数，不随目标录像时长按比例变化；正常停止产生的轻微余量继续按“正常轻微多录”处理。

计时使用已确认的录像归属、连续性及可靠时间证据，遵守“断电恢复后的控制完成依据”。不能将停止响应的通信耗时、无法证明仍在录像的时间或不同会话的单调钟读数差计入录制时间。该依据用于判断修复资格，不代替文件内的实际视频时长；未读取媒体信息时，报告中的实际视频时长仍为未知。

修复须在会话取得正常执行资格后进行，时钟异常时按“安全收场与后续处理的衔接”保存进度。先处理取消、已有终态及已经保存的修复决定；尚未作出决定时，按下表判断：

| 录像情况与计时证据 | 修复判定 |
| --- | --- |
| 正常完成，仅有正常轻微余量 | 按正常录像完成，不触发异常修复 |
| 异常录像，可信计时证明已严格超过 `duration_s + T` | 记录需要修复；确认本次录像停止、源文件归属及写入完成后，按执行资格开始修复 |
| 异常录像，计时证据足以确认截至停止时未超过门槛，包括恰好相等 | 不触发多录修复，继续按录像成功及原片保留规则结束 |
| 异常录像，计时或连续性证据不足以判断是否超过门槛 | 保存判定未知，完成适用的有限对账与收场；正常会话中仍无法判定时，按下一节拷贝原片检查 |
| 所需配置、历史或决定无法可靠读取，或保存失败、提交未知 | 按对应错误处理，不猜测余量、修复资格或已经完成的决定 |

仅能证明“至少录了某个时长”时，该下界超过门槛即可确认多录；下界没有超过门槛，不能反过来证明实际录制未超过。录像仍在进行时尚未超过门槛，也不能提前保存最终的不修复结论；优先完成必要停止，之后按可靠证据判定。

例如配置允许多录 10 秒，目标 60 秒：异常录像确认录制 70 秒时不触发，确认超过 70 秒时触发。10 秒仅用于说明判定，默认值尚未确定。取得充分计时证据后，不为判断是否需要修复而先取回视频读取媒体时长；满足修复资格后，再执行原有修复输入拷贝。

本次采用的余量作为动作固化策略可靠保存；修复判定及其时间证据追加到历史并同步更新投影，在启动修复拷贝前提交成功。重启沿用原余量和已保存决定，配置变化不重新解释既有动作；恢复同一修复仍遵守有限预算与断点续传规则。尚未取得停止及文件写完依据时，不能因已触发修复而读取仍在写入的源文件。

#### 计时证据不足时的原片检查

异常录像完成有限对账后，仍无法凭现有计时证据判断是否超过多录门槛时，camctl 在取得正常执行资格的会话中，将原片拷贝到主机检查，再决定是否修复。该检查属于原 `camera_record` 的必要后处理，不需要客户端另外提交取回请求；时钟异常会话仍只保存进度，按“安全收场与后续处理的衔接”等待正常会话。

拷贝前须确认源文件属于本次录像、已经停止且写完，并可靠保存检查决定、来源关联及原动作采用的门槛。录像连续时长未知不等于文件归属可以未知；来源或写入完成无法确认时，继续按原对账及有限失败规则处理，不能选择任意文件检查。

原片拷贝到 `staging` 中的工作位置，遵守相机视频的可靠读取、落盘、摘要校验及跨重启断点续传契约。完整有效的副本才交给主机工具检查；检查后需要修复时使用同一有效副本，不再次从相机拷贝。该工作文件不构成 delivery，不自动进入 `ready`，也不提前成为正式产物。

以下按可靠检查所得视频时长 `D` 分类；检查发现的其他明确媒体失败证据仍按录像成功标准处理，时长满足不单独证明全部目标内容有效：

| 检查结果 | 后续处理 |
| --- | --- |
| 可靠确认 `D < duration_s` | 不执行多录裁剪，按时长不足提交录像失败，保留原片 |
| 可靠确认 `duration_s ≤ D ≤ duration_s + T` | 不执行多录修复，保存检查结果，按录像成功标准及原片保留规则结束 |
| 可靠确认 `D > duration_s + T` | 保存需要修复的决定，使用已有副本执行内部修复，完成后统一提交结果 |
| 检查未取得可靠时长或发生工具错误 | 保留检查失败或未确认原因，按有限处理规则结束，不能猜测未超门槛或盲目裁剪 |
| 所需记录不可可靠读取、写入失败或提交未知 | 按持久化错误处理，先确认实际记录，不猜测检查或修复已完成 |

例如目标 60 秒、允许多录 10 秒：检查确认原片为 65 秒时不修复，为 5 分钟时进入修复，为 30 秒时记录录像不足。可信计时和文件检查是两种判定依据，报告保存实际采用的依据，不用媒体信息补造历史启动或停止时间。

检查输入拷贝及检查执行沿用有限超时、重试和空间不足规则。空间不足快速失败，不等待释放或跨会话自动重试；断电中断且仍有执行资格的未完成拷贝则在后续正常会话续传。拷贝或检查失败不证明相机原片损坏，也不自动删除原片。若已经具有充分的控制成功依据，仅检查失败不能单独否定该依据；没有成功依据时，按既有失败规则结束并保留原片。报告分别表达录像结果、检查错误及修复尚未取得判定，不将未执行的修复写成成功。

检查仍未完成时保留动作未完成及内部进度，适用处理全部结束后才按“录像动作的结束时点”统一登记正式产物与终态。检查决定、拷贝进度、检查结果及修复决定均按历史与投影规则保存；恢复沿用原动作、门槛、文件和预算。取消仍按录像取消规则放弃内容，已提交终态不因后续取回重新进入本次检查。

#### 修复内容与文件处理

不允许调用方通过 `obtain_action_outputs` 主动指定：

- 裁剪起点；
- 裁剪终点；
- 任意裁剪时长。

修复目标：

> 从录像内容起点开始保留至少完整 `duration_s` 内容。

原则：

```text
只能多，不能少
```

允许尾部多保留几秒。

v1 使用 `ffmpeg/ffprobe` 作为板端外部依赖，裁剪只采用**无重新编码的方式**；不为了精确边界重新编码视频。

无法安全完成无重编码修复时：

```text
repair_failed
```

保留原片，不进行转码兜底。

修复在客户端尚未请求取回时也主动执行。

内部修复及上述原片检查需要将相机视频拷贝到主机时，在 `staging` 中保存和处理输入文件，并在该目录中生成适用的目标录像；同样必须支持[跨主机重启的断点续传](outputs.md#相机视频的断点续传)。拷贝恢复继续受本动作的取消、空间和设备收场规则约束。

修复成品准备完成后保存在 `staging/derived/`，并在下文规定的结束事务中登记为正式产物。其保留与重复交付遵守[主机派生产物](outputs.md#主机派生产物)规则。

### 修复与动作成功分离

已经取得恢复控制完成依据，或原片已经核验包含完整目标内容，且没有明确的录像失败证据时，内部修复失败不影响录像成功：`camera_record = succeeded`，修复结果为失败。报告分别保存成功依据及修复失败原因。

修复输入拷贝失败、主机空间不足或修复工具执行失败，均不能单独否定已有控制完成依据。若在动作结束前确认原片时长不足或损坏，则按录像失败处理；核验未执行或未取得结论不能冒充此类失败证据。

### 录像动作的结束时点

正常录像在控制流程完成后结束；异常录像继续完成适用的核验和必要内部修复。各自需要的处理取得最终结果后，在同一数据库事务中登记应保留的全部正式产物并提交动作终态。原片与修复成品均在该事务成功提交后成为可供取回选择的正式产物，正常录像不因未执行媒体核验而延迟结束。

动作结束前照常保存源文件关联、主机文件、拷贝进度、核验和修复结果，支撑断电恢复及状态报告。这些内部处理记录不构成正式产物登记；即使原片已经完整，也不能在修复仍未结束时提前取回原片。状态报告可以表达处理进度，不将这些文件列为可取回的正式产物。

下表用于未取消、未过期的动作；启动失败、核验失败或修复失败等已按相应规则结束的阶段，不要求继续执行已无必要或无法执行的后续步骤，但须记录失败原因及未执行的依据。

| 处理进度与结果 | 动作与正式产物的处理 |
| --- | --- |
| 采集、必要收场或适用的核验、修复仍需继续执行或恢复 | 保持未完成，保存内部处理记录，不登记正式产物 |
| 正常控制流程已按成功标准完成 | 同一事务登记原片并提交 `succeeded`，保留控制证据；媒体核验未执行，实际视频时长未知 |
| 异常处理各阶段已结束，恢复控制完成或原片核验确认完整，没有明确的录像失败证据，修复不需要或已成功 | 同一事务登记原片、适用的修复成品并提交 `succeeded`，保留具体成功依据 |
| 异常处理各阶段已结束，恢复控制完成或原片核验确认完整，没有明确的录像失败证据，修复已失败 | 同一事务登记原片并提交 `succeeded`，保留成功依据及修复失败原因 |
| 异常处理各阶段已按规则结束，仍未满足成功标准 | 同一事务登记按规则应保留的正式产物或记录确认无正式产物，并提交 `failed`；保留核验结果、失败原因及残留设备事实 |
| 各阶段已结束，但处理结果或应保留文件集合无法可靠确定 | 先核实或按相应错误处理，不提交猜测的终态或产物集合 |

终态事务须确认阶段结果已经可靠保存，或将尚未保存的结果一同提交；正式产物登记、动作终态的历史与投影整体可见。等待取回的请求只有看到已提交的录像终态，才按[取回等待规则](outputs.md#等待录像动作结束)选择文件。文件读取、核验和修复在该事务之外完成。

取消与过期按各自规则结束，不能因本节要求而继续本应停止的核验或修复。修复期间动作尚未终态，取消仍按“camera_record 取消”放弃本次录像；已经提交的终态保持不变。有限收场失败后保留的未知设备状态，不要求无限等待其变为已知。

取消与结束并发时，以目标录像的持久化处理顺序判断；取消计划被受理本身不表示目标录像已经取消：

| 数据库中的先后顺序或结果 | 处理 |
| --- | --- |
| 目标录像的取消标记先保存，结束事务尚未提交 | 按取消规则放弃内容，不登记正式产物；结束处理须在事务内检查该标记 |
| 正式产物与录像终态的事务先提交，随后处理取消 | 保持录像终态和正式产物；取消录像不授权删除这些文件，文件继续按显式清理规则保留 |
| 结束事务失败且确认回滚 | 不留下部分正式产物或终态；根据已有处理结果及取消状态恢复 |
| 提交结果未知或状态无法可靠读取 | 先确认数据库事实，不据此发布产物、重复登记或将文件当作废弃内容删除 |

断电后根据已提交的内部处理记录、正式产物和动作状态恢复。终态尚未提交时，在会话具备相应执行资格后继续必要处理并完成统一提交；时钟异常时按“安全收场与后续处理的衔接”保留尚未完成的后处理，不因已看到完整原片而跳过未结束的修复。终态已经提交时不重新执行本次核验或修复，也不重复登记产物。已取消录像留下的文件继续按废弃内容处理，不因重启转成正式产物。

### 空间不足

相机自身仍有空间、状态库仍可可靠写入时：

> 板端视频处理空间不足不能阻止新的录像采集。

录像继续进行并保留设备源内容。

正常录像不为媒体核验拷贝视频，不因缺少这类拷贝空间而失败。必要异常处理或取回中需要板端空间的：

- 拉取；
- 核验；
- 修复；

遇到空间不足时快速失败。

不等待空间释放，不跨 run 自动接续。

如果异常处理确需主机核验，但因空间不足未能完成，仍无法满足成功标准：

```text
camera_record = failed
```

如果已有恢复控制完成依据，或原片已经核验完整，仅修复缺空间：

```text
camera_record = succeeded
repair_failed(storage_insufficient)
```

### camera_record 取消

在动作尚未进入终态时取消 `camera_record`：

> 放弃本次录像。

包括：

- 尚未开始；
- 正在录像；
- 已经停止但正在核验；
- 正在内部修复。

如果录像仍在进行：

- 尝试停止；
- 放弃内容；
- 协议支持时清理废弃产物。

如果录像已经停止：

- 不再次发送可能误停后续录像的通用 stop；
- 终止后续核验/修复；
- 放弃本动作产生的内容；
- 协议支持时清理废弃产物。

废弃录像不登记为正常可取回产物。

取消生效不等于物理清理一定成功。

## 配置归属

`clock.recovery_wait_cap_s` 是异常恢复等待上限，具体默认值见 U1。它不限制正常录像的 `duration_s`。

自动修复的允许多录秒数由本地配置提供，取有限、非负的秒数，作为动作固化策略保存，具体字段路径及默认值待细化。该参数只决定异常多录的修复门槛，不推迟正常停止目标，也不改变异常恢复等待上限；执行计划不提供裁剪或修复门槛覆盖参数。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

将录像意图、可恢复的设备录像身份、启动确认依据、收场进度、完整性核验结果、修复结果及残留设备事实追加到历史，并同步更新相关投影，遵守[持久化与配置基础](../2026-09-08-camctl-cli-design.md#持久化与配置基础)。历史回放不启动或停止录像，也不执行修复。回放恢复的是已记录的观察与意图；实际设备对账继续按本专题的证据规则执行。

当前会话单调钟锚点仅适用于当前会话，持久化历史不会使旧锚点在新会话中有效。跨重启恢复应依据本专题定义的可证明事实，具体记录结构待结合真实协议确定。

## 验收要求

### 单元测试

隔离设备、时钟、产物存储和视频处理协作者，验证启动确认、停止目标、冲突等待、恢复条件、成功证据、修复失败及各阶段取消。

按“录像动作的结束时点”覆盖处理进度、核验结果、修复结果及取消顺序。验证原片完整但修复未结束时只保留内部处理记录，不能取回原片；修复失败不改变已确认的录像成功依据。取消标记先保存时不登记正式产物，终态事务先提交时后续取消不删除正式产物；提交未知不能当作未登记或已取消处理。

覆盖启动意图、有效启动确认和结果未知的事实解释，验证携带对应尝试及其证据。设备状态值不变但新增恢复依据时，仍保留该观察；历史回放使用已记录参数和结果，不随当前策略变化重新作出历史决策。

当前相机启动确认覆盖本次成功响应、失败响应、响应丢失及无法解释的情况。成功响应以收到时的单调钟作为计时锚点，不再为确认启动查询录像状态；持久化及源文件查询延迟不能移动该锚点。仅发出命令不能启动正常时长计时，源文件身份不能由成功响应推定，其他驱动按自身确认契约处理。

按“源文件命名与录像关联”覆盖支持、不支持、能力未知及查询失败。支持分支验证指定目标在启动前可靠保存；不支持分支使用设备命名与驱动关联结果。指定路径不能代替录像确认，启动失败或未知不能触发另一种启动方式。

验证当前相机录制 B 时，具备执行资格且确认写完的 A 可进入读取，不因录像占用而等待空闲。A 尚未写完、来源未知或所属流程无执行资格时，不能仅凭操作兼容获得读取资格；其他相机按其驱动声明判断。文件读取期间必要的停止操作仍须获得执行机会。

验证当前相机声明安全重复停止后，结果未知的停止尝试可在原流程与剩余预算内重试；此前成功不能由重试能力推断。组合目标归属、已确认停止及预算耗尽，验证不会误停其他或归属未知的录像，不重复已完成的收场，也不因恢复重置预算。其他驱动未确认此能力时不能沿用当前相机的保证。

按“停止成功与文件可读”覆盖成功及可靠关联、关联不明、停止失败或未知，以及确认记录保存失败。成功且关联可靠时确认文件已写完，不等待长度稳定；文件写完不能单独代替正常控制流程的计时条件或提前登记正式产物。实际读取仍需所属流程资格，其他驱动按自己的文件完成证据处理。

按“原片保留与核验结果”覆盖取消、正常控制完成且未核验、核验确认完整目标内容、不足时长、确认损坏、核验无结论、确认无文件及文件归属或写入完成未知的分区。已写完且归属明确的失败原片仍登记，不因失败调用文件删除；未执行核验不等于核验失败，核验未确认不能写成损坏，未知时长不能写成零，主机副本失败不能推断源文件损坏。取消仍放弃内容，文件归属或写入完成未知时不能登记为可取回产物。

按“录像成功标准”验证正常启动确认、单调钟等待及停止成功共同决定结果；正常完成不调用视频拷贝或媒体核验协作者，不将控制等待时长填入实际视频时长。未完成、异常及记录未知不能直接判成功；终态后新增媒体质量事实只更新产物及报告，不改写录像终态。

按“断电恢复后的控制完成依据”覆盖录像归属与连续性、可信计时充分或不足、停止确认及文件写入完成的分区。仅历史启动意图或仅当前时间可信不能取得成功资格；恢复已录够且停止成功、源文件写完时，不要求媒体核验。需要修复时仍等待修复最终结果；修复失败或核验无结论不能否定已有控制依据，明确的录像失败证据仍优先处理。

按“自动修复的多录门槛”覆盖正常轻微余量、异常录像低于门槛、恰好相等、严格超过及计时未知。区分完整计时结论与仅有下界的证据，未越界的下界不能证明无需修复；停止响应延迟不自动增加已确认录制时长。验证固定秒数不随 `duration_s` 按比例变化，门槛不移动停止目标，已保存决定及余量不因新配置或重启改变。拷贝须有已保存的异常检查或修复决定，确认停止及文件写完前不读取源文件。

按“计时证据不足时的原片检查”覆盖正常会话资格、来源与写入完成、拷贝完整性及检查结果。时长分别低于目标、等于目标、位于目标与门槛之间、恰好门槛及超过门槛；错误与未知不能归入无需修复。需要修复时复用同一有效副本，不增加一次源文件拷贝。检查失败分别组合已有与缺少控制成功依据，验证录像结果、检查结果及原片保留彼此一致；取消、既有终态及有限预算继续约束处理。

按“安全收场与后续处理的衔接”覆盖会话时钟资格、停止及文件确认、未完成阶段、取消和终态。时钟异常下已成功停止且仍需后处理时，动作保持 `running` 并明确等待正常会话，不调用拷贝或媒体处理，也不登记正式产物；后续会话仍异常时不重复停止。确认缺失或记录未知不能进入已停止阶段，停止预算耗尽不能转为无限等待。正常会话恢复后使用原进度；等待期间取消后不恢复处理。

### 集成测试

组合真实 SQLite、录像调度、受接口约束的相机适配与报告生成，验证正常控制流程完成后直接原子提交录像成功及原片登记，整个流程不取回视频或执行主机媒体核验；报告保留控制依据、未知的视频时长及未执行核验。主机没有可供视频拷贝使用的空间但状态库仍可写时，正常录像仍可完成。分别在停止确认保存及终态事务提交前后中断，验证恢复依据已保存事实处理；后续取回发现媒体问题时，新增质量报告而保持既有录像终态。

组合跨进程恢复、真实 SQLite、可控时钟与相机适配，验证同一连续录像在可信计时下已经录够、恢复停止成功后，可以保存控制完成依据并登记成功；无需修复时不取回原片。分别组合修复成功、输入拷贝失败和主机空间不足，验证既有控制依据保留，必要修复完成或失败后才统一提交终态，报告分别表达录像与修复结果。覆盖归属未知、计时未知、尚未录够、停止结果未知及明确的原片质量失败，并在控制完成事实提交前后中断，验证恢复不重复已完成收场、不用跨会话单调钟差值推定时长。

组合 SQLite、恢复计时、相机适配与修复流程，验证异常录像严格超过已固化门槛后，先保存修复决定，取得停止与文件写完确认后才拷贝。使用门槛前、恰好门槛及超过门槛的独立时间数据，验证是否进入修复；判定本身不取回视频探测时长。分别在决定提交前后及修复拷贝期间中断，并修改本地配置，恢复仍沿用原动作余量和已提交决定；已有部分修复输入继续续传，报告区分计时依据与未知的媒体时长。

组合真实 SQLite、连续的异常与正常启动、录像及等待取回，验证时钟异常会话完成有限停止后保存等待阶段，以 `clock_invalid` 结束且不持有普通接纳资格，原片尚未成为正式产物。再次异常启动不重复停止或执行后处理；正常启动从原进度继续，全部适用处理结束后才将正式产物与终态一同提交，等待取回随后获得选择机会。分别在停止确认、阶段保存和终态事务提交前后中断，验证恢复依据实际提交事实，不补造录像时长、不重复登记。包含已有部分修复输入及等待期间取消的情况，进度与预算保持，取消结果阻止后续恢复修复。

使用真实 SQLite、源视频、主机检查及修复流程，构造历史计时不足但文件归属和写完已确认的异常录像。验证正常会话主动拷贝到 `staging` 检查，按可靠时长决定保留或修复，无客户端取回请求时也执行；整个内部流程不发布交付文件。检查确认明显多录后复用原副本修复，结束前没有正式产物。分别在检查决定、拷贝进度、检查结果及修复决定提交前后中断，验证续传和结果恢复不重复复制或重置预算；重启遇到时钟异常则暂停后处理。另行覆盖空间不足、摘要校验耗尽、检查工具失败及取消，验证原片与最终结果遵守各自规则。

当前相机联调验证启动指令成功返回时录像已经开始，正常停止目标以成功响应的接收时刻加 `duration_s` 确定；核实录像身份的关联协议，验证一次连续录像的原片对应一个源视频文件。组合真实文件与 `ffmpeg/ffprobe` 验证无重新编码修复和完整性，以及持久化记录与录像恢复的协作。

当前相机联调验证停止录像后再次发送停止指令仍保持停止且无额外副作用。组合持久化收场记录与设备适配，覆盖停止已执行但响应未保存以及主机中断后的恢复，验证符合目标归属条件时复用原流程和预算重试，保存实际停止证据。

当前相机联调验证停止指令成功返回后，对应视频可立即完整读取，后续长度和内容保持不变。组合 SQLite 与录像处理，在停止成功后确认记录提交前后中断，验证恢复按持久化事实及设备对账继续处理，不能将缺少成功记录解释为文件仍在写入或已经写完。

当前相机联调在录制 B 的同时读取已完成视频 A，验证 A 的内容完整且 B 的录像不受影响；在读取尚未结束时到达 B 的停止目标，验证必要停止操作不被文件读取阻塞至取回完成。取回及内部修复所需读取均覆盖该协作边界。

组合清理授权、旧取回保护与当前相机文件操作，在录制 B 时删除已完成视频 A，验证只处理 A 且 B 继续录像；存在未解除的读取依赖时仍等待，不能因 Linux 允许删除文件而绕过清理资格。

使用可正常播放但不足目标时长的视频，组合核验、SQLite、等待中的取回及报告生成，验证原片登记与录像失败整体提交，取回可以取得该原片，报告包含目标与实际时长。重启不删除或重复登记；客户端后续明确提交清理计划后才按清理规则删除，数据库历史继续保留。

另用已写完且归属明确的损坏原片及核验未取得结论的原片，验证处理结束后均可登记并原样取回，报告分别保留确认损坏与核验未知的结果。取回文件与对应源文件逐字节一致，客户端通过交付摘要核验传输内容，不以无法播放拒绝交付。覆盖结束事务提交前后中断及后续显式清理，原片保留与数据库历史遵守各自规则。

组合真实 SQLite 和受接口约束的设备替身，验证启动意图与投影提交成功前不能发送命令。分别在意图提交后命令发送前、命令发送后结果提交前、确认结果提交后中断，验证前两者恢复时均保留待核实含义，后者保留已确认的历史事实；当前设备状态仍按本专题对账。回放本身不发送启动或停止命令。

同一框架流程分别组合支持指定路径与设备自行命名的驱动适配，验证两者均能保存和恢复已确认的录像、源文件关联。当前相机的真实协议验证覆盖设备自行命名、shell 查询正在录制的文件及文件存在性，并区分查询成功、失败和未知。以不依赖 ADB 的受接口约束适配替身验证框架消费相同业务结果；未来驱动另行验证其真实设备协议。关联证据不足时保留未确认结果，不根据预期路径补造已生成文件。

组合 SQLite、录像后处理、等待中的取回与报告生成，验证修复成功时取回包含原片和修复成品，修复失败但原片完整时录像成功且报告保留修复失败。分别在内部结果保存后、结束事务部分写入后及提交后中断，验证正式产物与终态同时可见或均未提交，恢复不遗漏成品、不重复登记。修复期间的报告可包含进度，但没有可取回的原片或修复成品。

分别安排目标录像取消标记与结束事务先提交，验证前者保留取消结果且不登记正式产物，后者保留终态及正式产物。包含取消计划已受理但目标取消尚未处理的情况；取消后再次启动，废弃文件不会被登记或取回。

## 待确认与待细化

### U6. 相机真实协议能力

当前相机已确认的通信、文件查询及命名能力见本专题对应章节。仍需实际协议确认或细化：

- 录像状态查询；
- 当前录像身份、实际源文件的关联依据及关联尚未保存时的恢复方法；
- 文件列举、读取和删除的具体命令、结果解析及与主机持久化记录的对账；
- 停止响应未保存或结果未知时，如何通过设备对账确认对应历史文件已经写完；
- 录像期间厂商控制程序提供的其他操作兼容性；
- 控制通道与文件通道是否互相阻塞。

这些能力决定框架实际能够提供的保证等级。

### 后续契约完善

正常录像及具有充分证据的断电恢复按已确认的控制流程判定成功。自动修复采用“自动修复的多录门槛”中定义的固定额外秒数；正常会话中仍无法确定是否超过门槛时，按“计时证据不足时的原片检查”拷贝检查。仍需明确该配置的字段路径及默认值、恢复所用历史时间与连续性证据的具体表示、主机媒体检查的方法与可靠判定依据，以及其他媒体核验适用场景。这些规则须遵守相机端不增加依赖、不为控制成功判定单独拷贝原片的边界。文件归属及写入完成已经确认的原片按“原片保留与核验结果”登记并保留；失败原因、未执行核验及未知媒体信息的字段表达仍需细化，不能将主机工具可用当作原片已经位于主机。正式产物登记、终态提交及与取消的先后关系遵守“录像动作的结束时点”；废弃文件的具体清理能力与恢复仍需结合设备协议细化。覆盖停止失败、内容完整证据、结果未知及后续对账的有效组合，保持动作终态不可迁移。
