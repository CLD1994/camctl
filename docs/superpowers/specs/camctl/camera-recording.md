# 相机拍摄

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义相机拍摄能力与驱动参数类型的扩展边界，以及第一版当前 ADB 相机录像的完整生命周期。公共执行规则见[调度与设备执行](scheduling-execution.md)，正式产物的身份和清理规则见[正式产物与取回清理](outputs.md)。

## 拍摄能力与参数类型

### 能力、参数类型与用户预设

拍摄能力表达要做什么；驱动定义的拍摄参数类型表达目标相机接受哪一种参数结构及其约束，正文简称“参数类型”。驱动根据选定的参数类型和参数值执行对应设备操作。当前已知能力为拍摄单张照片、录像和延时摄影，分别使用动作类型 `camera_take_photo`、`camera_record`、`camera_timelapse` 表达。每台相机可以支持其中任意一种或多种，后续可以新增拍摄能力及动作类型。

第一版实现当前 ADB 相机的 `camera_record` 与本专题定义的 `timed` 参数类型。单张照片、延时摄影及其他相机参数类型属于接入扩展范围，列出能力名称不表示本版已支持执行；其受理结果遵守[整份校验与原子受理](protocol-session.md#整份校验与原子受理)。

| 层级 | 定义者与职责 |
| --- | --- |
| 拍摄能力 | 动作契约定义行为类别及是否产生正式产物；新增类别通过动作接入机制扩展 |
| 参数类型 | 目标相机驱动声明该能力下支持的参数结构、字段和约束，并定义相应的执行流程与结果判定 |
| 用户预设 | 客户端保存能力、参数类型及一组合法参数值，生成计划时展开成明确的字段和值 |

一个参数完全开放的相机可以只提供一种参数类型，允许分别调整分辨率、帧率等参数。厂商按拍摄任务提供固定组合指令的相机，可以提供多种参数类型，每种类型只开放相应的可调参数。固定的设置属于驱动契约，调用方不能通过额外参数覆盖。

是否划分多种参数类型取决于参数结构和行为契约，而非固定组合的数量。若设备提供多个“分辨率与帧率”组合，且其余参数及执行流程相同，可以在同一参数类型中提供一个组合选项；若不同任务接受不同参数或具有不同完成条件，则分别定义参数类型及对应执行契约。驱动可以扩展参数类型，不要求所有类型共享录像时长、分辨率、帧率等参数。

客户端预设仍受选定参数类型的约束。camctl 第一版接收展开后的能力、参数类型和参数值，不保存、解析或动态引用用户预设。预设之后被修改，不改变已提交计划；同一请求重送继续以首次受理内容为准。

### 部署时向客户端提供说明

第一版在部署时向客户端提供机器可读的能力及参数说明。说明由实际部署的驱动定义与主机设备配置共同生成：驱动定义拍摄能力、参数类型和规则，设备配置确定各 `device_id` 绑定哪个驱动。导出说明是这些权威输入的派生产物，客户端据此使用规则，不另外手工维护一套参数契约。

| 说明内容 | 客户端用途 |
| --- | --- |
| 配置的 `device_id` 及对应驱动 | 选择实际部署的目标设备，并确定其参数规则 |
| 每台设备支持的拍摄动作类型 | 选择录像、单张照片等已接入能力 |
| 各拍摄能力接受的 `params.type` | 选择目标驱动支持的参数类型 |
| 各参数类型的字段名称、数据类型、单位、必填性、默认值和取值限制 | 生成和校验具体参数值 |
| 固定设置、可选组合及组合限制、必要的任务含义说明 | 向用户说明实际拍摄要求，以及哪些设置可以调整 |

说明只列出所部署版本与设备配置实际支持的能力，不将扩展预留名称视为可执行能力。它描述配置和参数契约，不表示设备此刻空闲、通信正常或已经取得执行资格。客户端生成完整计划时，还须遵守公共动作字段及对应动作的业务策略要求。

部署人员负责完成“配置主机设备—生成对应说明—交给客户端导入”的交接。同步时机如下：

| 部署事件 | 同步要求 |
| --- | --- |
| 首次部署 | 客户端导入对应说明后，再据此生成该主机的执行计划 |
| 更换相机，或修改设备标识与驱动绑定 | 按更新后的设备配置重新生成说明并同步给客户端 |
| 修改驱动参数契约，包括支持的类型、字段、默认值或限制 | 同步更新后的说明，客户端后续生成的计划使用新规则 |

客户端是否依据说明自动生成界面由客户端决定。用户预设由客户端保存，生成计划时按已导入的规则校验并展开；说明更新不改写已经受理的动作输入、生效参数或历史结果。

说明文件通过部署流程交接，主程序继续负责既有的计划输入与文件中转。状态报告表达动作输入、生效参数及执行结果，客户端通过部署交接取得完整的能力和参数定义。

导出所需的驱动定义或设备配置无法读取、解释或生成完整说明时，保留错误并判定本次导出失败；不能将缺失部分解释为设备不支持并交付残缺说明。客户端未同步说明而生成了不适用的计划时，camctl 仍按当前受理契约校验，不自动换参数类型或修改参数值；动作错误范围见下一节。

### 计划字段与参数校验

| 动作字段 | 含义 |
| --- | --- |
| `device_id` | 选择目标设备及其已配置的驱动 |
| `type` | 选择拍摄能力对应的动作类型 |
| `params` | 必填对象，包含参数类型标识及该类型接受的参数值 |
| `params.type` | 必填的非空字符串，选择该驱动在该拍摄能力下声明的参数类型；即使只有一种类型也显式填写 |

动作外层的 `type` 标识拍摄能力，`params` 内的 `type` 标识参数类型。拍摄参数对象中的 `type` 是框架用于选择参数结构的保留字段；其余字段与它同层，由选定参数类型定义，例如 `params.duration_s`。正文脱离对象上下文时，使用“动作类型”和“参数类型”区分两者。

参数类型标识在所属驱动及拍摄能力内解释，不要求跨相机通用。驱动为每种参数类型提供字段说明、必填性、默认值、合法范围、可选组合及组合限制，并以同一份定义支持校验与执行。固定参数及未开放的调整项应明确说明，不能静默丢弃调用方提交的非法调整。

校验以本地已接入的动作和驱动定义为依据，不调用相机探测运行状态。遵守公共受理规则，按以下分区处理：

| 条件 | 处理 |
| --- | --- |
| `type` 未知或本版未实现 | 拒绝整份计划 |
| `type` 已支持，但 `device_id` 缺失或格式错误、指定设备不存在，或其驱动明确不支持该能力 | 仅该动作初始为 `failed`，保留设备或能力不适用的原因 |
| 设备与能力匹配，但 `params` 缺失或不是对象 | 仅该动作初始为 `failed`，保留参数对象错误 |
| `params` 为对象，但 `params.type` 缺失、格式错误或不受该驱动支持 | 仅该动作初始为 `failed`，保留参数类型错误 |
| 参数类型有效，但其余字段、取值或组合不符合该类型定义 | 仅该动作初始为 `failed`，保留具体参数错误 |
| 能力、参数类型与参数值合法，但动作其他自身字段不合法 | 仅该动作初始为 `failed`，按公共校验规则保存错误 |
| 能力、参数类型、参数值及其他公共字段均合法 | 受理为 `pending`，执行时仍需满足调度与设备条件 |
| 定义或数据库因内部故障无法可靠读取，不能完成判定 | 保留实际错误，按会话错误处理，不伪装成设备不支持或参数错误 |

整份拒绝优先级、零次执行尝试和无副作用规则由请求专题定义。初始失败不删除动作的拍摄类型；拍摄动作仍属于可产生正式产物的来源类型，不能因参数类型或参数值错误被组取回静默排除。

首次受理保存原始结构化输入，并为合法动作保存选定驱动、能力、参数类型及包含驱动默认值的生效参数。后续执行、重试和恢复沿用这些已确定的值；重建原计划使用原始输入，报告可分别表达输入与实际生效参数。驱动默认值或客户端预设的后续变化不重新解释已受理动作。历史回放不调用驱动重新计算参数。

### 驱动执行与产物边界

驱动为每种参数类型定义对应的启动方式、完成依据、取消及断电恢复方式、设备操作兼容性，以及本次正式产物的识别和写入完成依据。框架统一管理调度资格、动作状态、操作意图与观察事实的持久化、正式产物和报告。驱动通过这些公共流程执行，遵守先持久化意图再产生设备副作用的规则。

框架不要求所有拍摄操作具备独立的启动和停止命令，也不统一假设由主机计时。设备内部固定时长的复合指令可以由驱动通过对应参数类型表达；可调参数与完成判定由驱动契约定义。当前录像的时长检查和修复流程只适用于本专题明确的驱动及参数类型。

拍摄动作类型声明可以产生正式产物；具体文件种类、数量及关联方式由驱动为对应参数类型定义，不能仅凭“延时摄影”等名称推断产物一定是视频或照片序列。实际接入后，正式产物继续进入已有的取回、清理和报告流程，无须为每种参数类型新建一套交付协议。

## camera_record

本节及后续录像执行、取消、恢复和验收规则适用于当前 ADB 相机的 `timed` 参数类型。使用该类型时，主机在启动确认后计时并停止录像；其他参数类型及驱动须定义对应行为，不自动继承本节的设备前提。

### 基本语义

对调用方暴露一个复合动作：

```text
camera_record
```

底层由：

```text
record_start
record_stop
```

组成。

自身参数在首次受理时按[公共动作参数校验规则](protocol-session.md#整份校验与原子受理)检查。例如缺少 `duration_s` 时，将该 `camera_record` 登记为 `failed`，保留参数错误及零次执行尝试；不启动或停止相机，也不登记源视频。其他动作继续受理。以下采集、收场和恢复规则适用于已取得执行资格的录像动作。

### 参数

| 字段 | 要求与含义 |
| --- | --- |
| `params.type` | 必填，当前驱动本节定义的录像参数类型为 `timed` |
| `scheduled_at` | 必填，录像的计划启动时间；遵守公共时间规则 |
| `params.duration_s` | 必填，成功确认开始后应继续录制的目标时长，单位秒；具体语义见 `duration_s` 一节 |
| `policy.max_delay_ms` | 必填的非负整数，允许晚于 `scheduled_at` 启动的最大毫秒数，无缺省值 |

`timed` 类型当前对调用方开放的拍摄参数为 `duration_s`；厂商其他可调拍摄字段须在设备接入时依据实际能力补齐参数类型定义后再开放。参数类型选择及参数值错误遵守[计划字段与参数校验](#计划字段与参数校验)。

`policy` 必须是对象且提供合法的 `max_delay_ms`。缺少整个 `policy`、缺少该字段或字段值不合法时，仅将该录像动作在受理时登记为 `failed`，保留错误字段与原因、零次执行尝试；不等待计划时间，也不影响同计划其他合法动作的受理。

例如 `max_delay_ms = 5000` 表示启动窗口截至计划时间之后 5 秒，`0` 表示不允许迟到。窗口仍按公共规则判断，不承诺实际调度能够精确命中某个时刻；该字段不延长录像时长，也不改变本地通信超时和尝试上限。已受理请求重送仍复用首次输入及结果。

### 正常录像流程

合法录像到达计划时间后，按相机选择顺序取得启动机会：保存启动意图，发送启动命令，取得成功确认并保存计时依据及源文件关联。按 `duration_s` 录够后停止，成功响应确认文件已经写完，随后在同一事务中登记原片及录像成功结果。

正常流程的输出是一份保留在相机中的正式原片。录像动作本身不创建 delivery；取回由独立的 `obtain_action_outputs` 处理。异常录像的检查和修复由后文专节定义。

### 当前相机的原片文件

已确认当前相机不会将一次连续录像按时长或文件大小自动拆成多个文件。一次连续录像形成原片时，对应一个源视频文件；本设备的原片关联、完整性核验和取回以该文件为单位。内部修复产生的成品是独立的派生产物。

### 通信方式与查询能力

当前相机运行嵌入式 Linux，具有完整文件系统，并提供具有完整命令执行权限的 `adb shell`。camctl 通过 shell 执行厂商提供的二进制程序，控制相机的录像等行为；文件列举、存在性检查、读取及删除由驱动通过 Linux 文件操作实现。已确认可以通过 shell 命令查询正在录制的文件名或路径，以及检查对应文件是否存在。

相机端只使用已有系统能力和厂商程序，不允许添加依赖或部署额外工具。`ffmpeg/ffprobe` 是主机端工具。正常录像不得仅为读取原视频时长或执行媒体核验而新增从相机到主机的视频拷贝；录像完成判定须在这一边界内设计。明确请求的取回、必要异常修复，以及正常会话中计时证据不足时的异常原片检查，按各自规则拷贝文件。

`adb shell` 和具体 shell 命令属于当前相机驱动的实现方式，不是框架要求所有相机提供的接口。框架通过驱动声明的业务能力取得录像和文件查询结果；未来驱动可以使用其他设备协议，调度、持久化和产物流程不依赖 ADB 或 Linux 命令。

查询正在录制的文件与查询指定文件是否存在分别表达各自的观察结果。文件存在本身不证明本次录像仍在进行或文件已经写完；查询错误或结果未知也不能当作文件不存在。具体命令、返回格式和结果识别在设备适配时核实，录像归属及写入完成仍按各自证据规则判断。

### 第一版驱动接入契约

第一版接入当前已确认的 ADB 相机。业务层消费下表的结果；厂商二进制名称、命令参数及响应解析属于驱动实现和设备联调输入。

| 驱动职责 | 提供给业务层的结果 |
| --- | --- |
| 启动录像 | 本次启动成功确认；成功后通过设备查询关联实际录像和源文件 |
| 停止录像 | 本次停止成功确认，以及对应源文件已写完的依据 |
| 查询录像 | 是否正在录像、正在录制的文件路径，以及可关联到已知动作的依据 |
| 查询文件 | 指定源文件是否存在、完整长度及源端摘要；保留设备路径与产物的关联 |
| 读取与删除 | 对已写完文件按位置读取或删除指定文件；读取完成文件与录像兼容 |
| 调度控制与文件操作 | 文件传输期间必要的停止命令仍能得到执行机会 |

当前相机能力依据已确认的设备前提。真实设备接入前，驱动交付物须补齐上述操作的命令映射、正常响应样例，以及一条“启动—查询路径—停止—读取—删除”的联调记录。

第一版正常路径使用启动成功后的路径查询保存关联，并使用停止成功确认文件写完。尚未保存关联就断电或停止响应丢失时，沿用既有设备对账契约；具体恢复证据由驱动结合实际协议提供，不能靠猜测文件名完成关联。业务主流程的实现先使用受这些结果约束的驱动替身，实际相机验收以真实驱动满足契约为准。

### 录像期间的文件操作

已确认当前相机正在录像时，可以同时读取另一份已经写完的视频，不影响正在进行的录像。当前驱动将这种文件读取声明为与录像兼容，camctl 不因相机正在录像而要求该读取等待设备空闲。

当前驱动依据 Linux 文件语义处理已完成视频；删除指定文件的目录项不要求停止另一份视频的录像，也不删除另一份视频。该判断依据现有设备前提及普通文件操作语义，具体适配通过联调验证。[Linux unlink 文档](https://man7.org/linux/man-pages/man2/unlink.2.html)

对正在录制 B 的当前相机，另一份视频 A 的操作按以下规则处理：

| 操作及资格 | 处理 |
| --- | --- |
| 读取 A，来源及写入完成已确认，所属取回、异常原片检查或内部修复具有执行资格 | 按同一相机的拷贝并发限制读取，无须等待 B 停止 |
| 删除 A，已有明确清理授权，且满足产物清理及旧取回保护条件 | 允许删除 A，无须等待 B 停止 |
| 相应操作资格不满足或无法可靠确认 | 按所属流程等待、核实或报告错误；Linux 操作能力不代替业务授权 |

操作调度遵守[设备执行与操作兼容性](scheduling-execution.md#设备执行与操作兼容性)。文件操作不能妨碍必要的录像停止操作；控制通道与文件通道的实际协作通过适配验证。未来相机由对应驱动声明兼容性，不自动继承当前相机的能力。

当前相机允许录像与完成文件的读取同时进行；多份完成文件的读取则遵守[同一相机的拷贝并发限制](outputs.md#同一相机的拷贝并发限制)，取回与录像内部处理共用一次只拷贝一份文件的约束。

### 源文件命名与录像关联

启动录像时能否指定相机源文件名或保存路径，由相机驱动声明。当前相机不支持；框架保留使用该能力的扩展入口，不将其作为相机接入或断电恢复的必备条件。

| 驱动能力 | 启动与关联方式 |
| --- | --- |
| 已确认支持指定源文件名或路径 | 可以使用该能力；使用时，将选定目标与启动意图一同可靠保存，再发送启动命令 |
| 已确认不支持 | 按设备自身的命名方式启动，由驱动通过已核实的设备协议关联本次录像及其源文件 |
| 能力未知或读取能力信息失败 | 明确保留未知或错误，不据此认定支持或不支持；先确认能力再选择相应路径 |

驱动向框架提供录像与源文件的关联结果及确认依据；框架持久化这些事实，供后续收场、核验和取回使用。设备特有的命名和查询方法由驱动负责，不要求所有相机采用同一种方法。

预先指定的路径属于启动意图，不证明设备已经开始录像或实际生成了该文件。命令失败或结果未知时，仍按录像对账规则核实，不能当作能力不支持而直接改用另一种方式再次启动。当前相机通过上述 shell 查询取得文件信息；如何结合这些信息确认本次动作的录像归属，以及启动后尚未保存关联就断电时如何恢复，仍需结合实际协议确认。

### `duration_s`

`duration_s` 表示：

> 从已经确认本次录像进入 recording 状态的时刻开始，至少继续录制这么长时间。

### 录像启动确认

驱动必须定义：

> 什么证据足以确认本次录像已经处于 recording 状态。

已确认当前相机的启动录像指令返回成功时，相机已经进入录像状态。驱动可靠识别本次启动指令的成功响应，即可确认录像已开始，无须为确认启动再查询一次录像状态。收到该成功响应时读取当前会话的单调钟，作为下述计时锚点；后续持久化或源文件查询不重新设置该锚点。

该响应须可靠关联到本次启动尝试。命令已发出、响应失败、丢失或无法解释均不能代替成功确认，继续按启动结果未知及设备对账规则处理。成功响应确认录像已开始，但不自动提供源文件身份；源文件仍按“源文件命名与录像关联”确定。

未来相机由对应驱动定义可靠的启动确认依据，不自动继承当前相机的成功响应保证。

确认时记录：

```text
recording_confirmed_at_monotonic
```

正常停止目标：

```text
stop_target_monotonic =
    recording_confirmed_at_monotonic + duration_s
```

该时间点不是“第一帧真实时间”。

它只是一个保守锚点：

> 从这里开始可以确定录像已经进行。

因此正常情况下可能略微多录，但不主动少录。

如果设备协议不能提供可靠的录像启动确认，必须降低保证并如实报告，不能使用“发出 start 指令的时间”冒充实际录像起点。

### 录像启动的历史事实

按[历史事件的粒度](../2026-09-08-camctl-cli-design.md#历史事件的粒度)，启动过程分别记录以下具有独立含义的事实；下列中文名称说明事实含义，具体事件标识和字段结构仍需结合设备协议细化。

- 启动意图已登记：关联动作、相机、本次尝试和已经确定的执行参数。该事实及相关投影提交成功后，才允许发送启动命令。
- 启动已确认：取得本专题要求的确认依据后，记录确认事实，以及设备协议能够提供的录像身份和有效计时依据。
- 启动尝试结果未知：例如等待响应超时且无法确认实际结果时，记录本次尝试和未知原因，供后续设备对账使用。

启动意图提交后、结果记录提交前断电，恢复时可能只能查到启动意图。这只能证明存在一次待核实的启动尝试；实际命令是否发出、录像是否启动仍须依据设备对账判断。历史中不能凭意图补写命令已发送或启动成功，也不能把缺少结果解释为设备未执行。

### 正常轻微多录

由保守确认点造成的正常少量尾部余量，不自动视为异常录像。

不为了精确卡秒而强制对所有录像执行裁剪。

### 启动与停止的尝试上限

启动录像与停止录像分别计数，尝试上限由本地设备配置分别提供，**默认均为 3 次，包含第一次**。动作首次受理时保存两类实际生效的上限，后续配置变化、请求重送或重启不改变既有动作的上限与已用次数。启动消耗不占用停止次数；采用默认值时，启动第三次才成功，停止仍有自己的 3 次尝试。

以下以 `S` 表示该动作固化的启动上限、`T` 表示固化的停止上限；两者是本节说明用符号，本地配置字段见实现时细化事项。

| 操作及已有结果 | 后续尝试规则 |
| --- | --- |
| 启动尚未成功，已用次数少于 `S` | 仍须满足启动窗口、重试等待及设备条件，符合条件才可再次尝试 |
| 启动已确认成功 | 停止启动尝试，进入录像及停止流程 |
| 启动已用次数达到 `S` 且仍未成功 | 原启动流程不再追加启动尝试；按实际失败、未知及窗口事实结束或对账 |
| 停止尚未确认，已用次数少于 `T` | 在目标归属、重复执行能力等条件允许时使用剩余次数 |
| 停止已确认成功 | 不再为该流程发送无必要的停止命令 |
| 停止已用次数达到 `T` 且仍未确认成功 | 原停止流程不再追加停止尝试；按停止失败及残留设备事实规则处理，不推断相机空闲 |

正常停止、取消触发的停止及断电恢复停止，同一次录像共用原停止流程的计数。切换入口、重复取消、进程重启或恢复会话不重新分配预算；已保存的成功确认也不能因重启丢失。后续其他动作针对历史残留录像的处理使用“后续动作触发的残留收场”定义的独立流程与预算。

启动与停止次数、每次尝试结果及对应投影分别持久化，报告分别表达已用次数和上限，不以一个总尝试次数代替两类预算。尚未尝试和受理时参数校验失败均保持相应次数为零。次数分配与启动或停止意图之间的具体落盘边界仍需明确；结果未知不能按“未尝试”清零。

### 客户端排程责任

客户端应保证同一相机计划中的录像时长不发生预期冲突。

camctl 不负责自动重排录像计划。

如果由于实际启动/停止延迟产生运行时冲突：

> 已经开始的录像优先。

后一个录像：

- 在自己的启动窗口内等待；
- 相机释放后仍在窗口内 → 开始；
- 超窗 → `expired`。

不得为了赶后一个录像而提前截短已经开始的录像。

### 多个待启动录像的选择顺序

先处理已经开始的录像，以及下节定义的等待重试保留关系。没有这些占用或保留时，同一相机有多个尚未开始录像、且同时具备启动条件的动作，按 `scheduled_at` 从早到晚选择。正常到点调度、延后开机和重启恢复采用相同规则；计划受理顺序、数据库查询顺序和内存加载顺序不能颠倒不同计划时间的先后。

选择前先按公共规则处理取消、既有终态、可信时间、启动窗口及设备执行条件。下表只对相机已经允许启动新录像的情况选择候选，不授权绕过设备对账或必要收场：

| 待启动动作的情况 | 处理 |
| --- | --- |
| 没有具备启动条件的动作 | 不发出录像启动命令，按各动作的等待、过期或失败规则处理 |
| 只有一个具备启动条件的动作 | 选择该动作 |
| 多个动作同时具备启动条件，最早 `scheduled_at` 只有一个动作 | 选择该最早动作；其他动作继续按自己的启动窗口等待 |
| 多个动作同时具备启动条件，最早 `scheduled_at` 相同 | 在这些动作中选择最早受理计划内的动作；同一计划内再按原 `actions` 数组顺序选择 |

候选动作依次按 `scheduled_at`、所属计划的 `plan_seq`、动作在首次受理的 `actions` 数组中的位置升序比较。`plan_seq` 使用[新计划受理序列](scheduling-execution.md#新计划发现与内存调度缓存)，不以墙钟记录的受理时间或计划名称代替。原数组位置随计划结构持久化，其他动作失败或取消不改变仍有效动作的相对顺序。

正常执行、增量加载、重启恢复及历史重建均使用这些已保存的排序依据。同一 `request_id` 重送不重新分配计划顺序，也不采用重送正文中的数组顺序。排序依据缺失、读取失败或无法可靠解释时按持久化错误处理，不退回数据库返回顺序或随机选择。此规则仅选择尚未取得启动机会的候选，不改变已经开始或等待重试的保留关系。

例如主机 10:12 开机：A 计划 10:00 开始，最晚可在 10:20 启动；B 计划 10:10 开始，最晚可在 10:15 启动；两者均录像 5 分钟，且此时均具备启动条件。先启动 A，B 等待并在自己的窗口耗尽后过期。即使反过来执行有机会完成两项，也不据此改变选择顺序。A 开始后继续遵守“客户端排程责任”中的已开始录像优先规则。

该排序不修改输入的计划时间、启动窗口或录像时长，也不复活已过期动作。启动尝试失败或结果未知后的处理仍按对应恢复与重试契约执行，不能仅凭排序认定设备已空闲。

#### 等待重试时保留相机

按上述顺序选中的录像启动尝试明确失败、确认未开始录像，且仍允许重试时，为该动作保留下一次录像启动机会。重试等待期间，相机即使空闲，其他录像也继续等待；不能因它们当前可以发令而绕过已有保留。

| 保留动作及设备情况 | 处理 |
| --- | --- |
| 仍允许重试，但尚未到下一次尝试时间 | 保留启动机会；其他录像等待，并独立判断各自的窗口是否耗尽 |
| 仍允许重试，已到尝试时间且设备条件满足 | 由原动作再次尝试；再次明确失败且仍可重试时继续保留 |
| 原动作已确认开始录像 | 转入已开始录像优先的规则，其他录像等待其释放相机 |
| 原动作取消、最终失败或过期 | 不再为其保留重试机会；确认设备满足启动条件后重新选择其他录像 |
| 原尝试结果未知、设备状态不明，或持久化事实无法可靠确认 | 先按原动作的对账或错误规则处理，不猜测空闲或将启动机会交给其他录像 |

保留不延长启动窗口、不增加或重置尝试预算。等待期间窗口耗尽时及时按过期规则结束，不等到下一次重试时间才释放保留。其他录像可能在等待期间过期，该结果继续如实保存和报告。

保留关系依据持久化的动作、尝试及重试事实确定，与相关结果同步保存，不能仅存在于内存。重启后先恢复原关系及预算，再选择新录像；历史回放只恢复事实，不发送命令。报告表达原动作等待重试，以及其他录像因该相机的启动机会已被保留而等待的情况。

这里保留的是录像启动机会。与其兼容的已完成文件读取、清理等操作仍按设备能力和各自资格执行；这些操作不能妨碍必要的设备对账或停止。

### 主机断电导致超时录像

允许主机断电期间相机继续录像并超过目标时长。

恢复后：

1. 对账本次录像；
2. 能证明目标时长已经满足 → 尝试停止；
3. 目标时长尚未满足 → 在能够可靠计算剩余时间时继续等待；
4. 无法正常停止 → 有限通信尝试；
5. 尝试耗尽 → 失败，不执行电源操作。

### 断电恢复后的控制完成依据

断电恢复后，能够可靠确认设备仍在进行本次同一段连续录像，且结合可信的历史计时依据与当前可信时间证明已经满足 `duration_s` 时，可以继续以控制完成作为成功依据。取得本次录像的停止成功确认，并确认对应源文件已经写完后，不为证明控制成功而单独拷贝原片；异常多录的修复及计时证据不足时的原片检查按后文处理。

恢复须保存录像归属与连续性的确认、所用可信时间及满足目标时长的判断、停止结果和源文件关联。仅文件存在、当前墙钟可信或数据库中曾有启动意图，均不能单独证明已经录够；不能将旧会话的单调钟读数与新会话读数组合计算时长。先处理取消、已有终态及已经保存的控制完成事实，其余情况再按当前录像与计时证据判断。

| 恢复时的证据 | 处理 |
| --- | --- |
| 同一段连续录像已确认，可信计时证明已满足目标时长 | 尝试停止，取得成功确认及源文件写完依据后，形成恢复控制完成事实 |
| 同一段连续录像已确认，可信计时证明尚未满足目标时长 | 按已有规则等待剩余时长，满足后再停止；等待期间仍遵守取消与异常处理规则 |
| 当前仍是同一段录像，但历史计时或当前时间不足以可靠判断 | 按对应保守收场规则处理，不直接套用可信计时成功分支 |
| 录像归属或连续性不明，或相关记录与查询结果不可可靠取得 | 先对账或按对应错误处理，不推定本次录像持续进行 |
| 录像已停止或已有可靠保存的控制完成事实 | 按已保存事实及对账结果恢复，不为了取得新的停止响应而重新执行已完成收场 |

取消与既有终态优先于上述恢复判断。已经确认的时长不足、原片损坏等失败事实不能被后续成功停止掩盖。

需要异常多录修复时，继续完成该内部流程，之后统一登记原片、适用的派生成品及动作终态。修复失败本身不撤销已经取得的恢复控制完成依据；若处理发现明确的录像失败证据，则按“录像成功标准”判定并报告。

### 时钟异常下的保守收场

如果：

- 主机墙钟不可信；
- 能确认设备仍在进行本次录像；
- 能确认是同一段连续录像；
- 无法确定历史已经录了多久；

则额外等待：

```text
min(duration_s, recovery_wait_cap_s)
```

只使用当前 run 的 单调钟。

达到该上限后：

> 尝试停止录像。

即使无法证明已经录满全部 `duration_s`，也不允许为了完整性无界继续等待。

`recovery_wait_cap_s` 是异常恢复保护参数，不是正常录像 `duration_s` 的上限。

### 安全收场与后续处理的衔接

时钟异常会话只执行允许的有限安全收场，不启动或恢复视频拷贝、媒体核验及修复。对尚未取消、未进入终态的录像，成功停止并确认源文件归属及写入完成后，若修复判断或其他适用后处理尚未完成，则保存进度，交给后续取得正常执行资格的 `run` 继续处理。

相机已经停止与动作尚未完成分别表达。此时录像动作保持 `running`，处理阶段表达“已停止，等待正常会话处理”；状态库保存停止依据、源文件关联、已有计时证据及未完成阶段，不将其表达为设备仍在录像。该阶段不增加新的公共动作状态。原片仍保存在相机，尚不登记为正式产物；等待中的取回继续遵守录像终态与正式产物的统一登记边界。

先处理取消、已有终态及记录不可可靠读取的情况，其余按会话资格和已保存进度分类：

| 会话与录像进度 | 处理 |
| --- | --- |
| 时钟异常，已确认停止、源文件归属及写完，仍有后处理未完成 | 保存等待阶段，不执行后处理、不提交录像终态或正式产物；本次有限收场完成后以时钟异常退出 |
| 时钟异常，尚未确认停止、源文件归属或写入完成 | 按原有限收场及对账规则处理，不能用等待后处理阶段代替尚未取得的停止或文件证据 |
| 后续会话仍时钟异常，已保存等待后处理阶段 | 保留进度，不重复已确认完成的停止，也不启动后处理；其他允许的有限收场完成后退出 |
| 后续会话取得正常执行资格，已保存等待后处理阶段 | 使用原停止结果、源文件与固化策略继续判断并执行适用后处理；全部完成后统一登记正式产物及录像终态 |

停止尝试耗尽仍按既有失败及残留设备事实规则结束，不能通过无限保留等待阶段重置预算。取消及已有终态按其原规则处理；等待后处理期间仍可取消尚未终态的录像，此时放弃内容，不在后续会话恢复修复。

停止确认、阶段进度及相关投影按历史事务规则保存。文件或数据库结果未知时先对账，不推断已停止、文件已写完或动作已结束。已经保存的修复输入拷贝进度、修复决定及有限预算继续保留，后续正常会话恢复原处理，不重新开始录像或重置已消耗预算。历史回放本身不执行这些外部操作。

待恢复的录像后处理仍属于未完成计划工作，但不能阻止时钟异常会话结束，也不授予普通接纳资格。下一次实际启动且取得正常执行资格的会话负责继续驱动；当前时间恢复可信不补造历史录像时长，修复仍使用既有可靠计时与证据规则。未来会话何时启动、时间何时恢复可信，不由本阶段保证。

### 停止命令的重复执行

已确认当前相机的停止录像指令可以重复执行。相机已经停止录像时，再次执行该指令仍尝试停止录像，保持停止状态，不产生额外副作用。

当前相机驱动据此声明停止操作可安全重复。停止尝试的响应丢失或结果未知时，允许在原收场流程及剩余有限重试预算内再次发送停止指令；主机重启不创建新的补偿流程或重置预算。命令可以重复执行不表示此前尝试已经成功，停止结果仍须按实际确认或查询证据保存。

重试仍受录像归属及取消目标约束：不能停止其他动作的录像，也不能把归属未知的录像当作本次目标。已确认本次录像停止后，按相应完成及取消规则继续处理，不因具备重复执行能力而增加无必要的停止操作。

本能力属于当前相机。未来相机是否支持安全重复停止由对应驱动确认，并遵守[效果登记与补偿](scheduling-execution.md#效果登记与补偿)的公共规则。

### 停止成功与文件可读

已确认当前相机的停止录像指令返回成功时，对应视频文件已经写完，可以立即读取；此后文件内容和长度保持不变。驱动将本次停止成功与已确认的录像及源文件关联，camctl 保存该确认事实后按“录像成功标准”完成正常录像，或继续必要的异常处理，不额外等待文件长度稳定。

该保证用于确认源文件已经完成写入，不表示已经读取并核验文件内的视频时长。正常录像结合启动确认和单调钟计时判定控制流程是否完成。源文件登记与动作终态继续遵守“录像动作的结束时点”。

| 停止结果与文件关联 | 文件处理 |
| --- | --- |
| 返回成功，且对应录像与源文件已可靠关联 | 确认文件写完，可完成正常录像；实际读取按取回或必要异常处理的资格执行 |
| 返回成功，但录像或源文件关联不明 | 先核实关联，不将任意已有文件视为本次产物 |
| 停止失败、响应丢失或结果未知 | 不据此认定文件写完；按停止重试及设备对账规则取得可靠依据 |
| 停止或文件确认记录的保存失败、提交结果未知 | 按持久化错误处理，恢复先确认实际记录，不猜测确认结果 |

未来相机由对应驱动定义文件写完的可靠确认依据，不自动继承当前相机的停止成功保证。仅文件存在或一次长度查询不能证明写入已经完成。

### 停止失败

停止通信尝试耗尽后：

```text
camera_record = failed
```

但是不能推断：

```text
camera is idle
```

应持久化类似：

```text
possibly_recording
```

的设备事实。

### 后续动作触发的残留收场

后续动作要求相机空闲时，先按需查询设备状态。本节适用于仍有效且已取得执行资格的触发动作；与录像兼容的操作按自身条件执行，不为此主动停止残留录像。

| 对账结果 | 处理 |
| --- | --- |
| 可靠确认相机已空闲 | 保存当前观察，继续触发动作；无须发送停止命令 |
| 可靠确认仍在录制，且属于已结束动作留下的已知残留录像 | 为触发动作建立独立的有限收场流程，再按目标归属与重复执行能力尝试停止 |
| 属于其他尚未结束动作的正常录像或已有启动保留 | 按占用、保留及触发动作的窗口规则等待，不能当作历史残留强行停止 |
| 无法通信、录像归属不明、设备状态未知或记录不可可靠解释 | 按对账及相应错误规则处理，不推测相机空闲，不授权停止任意录像 |

每个收场流程关联触发动作、相机及目标历史录像，拥有单独的尝试计数和可配置上限，默认最多 **3 次，包含第一次**。上限取自触发动作固化策略中的生效配置，并随收场流程登记保存。它不重置历史录像原停止流程的次数，也不消耗触发录像自身的启动或停止次数。

同一触发动作针对同一历史录像只建立一个这样的流程。后续调度、通信重试、同一请求重送及主机重启均恢复原流程和剩余次数，不反复建立新的预算。登记、目标关联、尝试与结果遵守历史和投影的持久化规则；回放不调用设备。

停止成功后保存设备观察及本次收场结果，再按触发动作当前的时间与设备条件继续执行。次数耗尽仍未确认停止时，本次收场结束，保留已知残留或结果未知的事实，触发动作按自身规则失败或过期。旧录像动作的终态和原停止结果不因后来收场成功而改写。

例如录像 A 原停止流程耗尽后失败；录像 B 到执行时间，为取得空闲相机而触发对 A 的独立收场。B 的这次收场采用自己的固化上限，成功后 B 才能继续启动。后来 B 停止自身录像时，使用 B 自身的停止预算。

没有新的、需要相机空闲的有效动作时，不为残留录像启动后台周期收场。

#### 触发动作结束时的收场

触发动作取消或启动窗口耗尽后，不再启动该动作的录像。已经登记的残留收场按下表结束：

| 对历史残留录像的停止命令 | 处理 |
| --- | --- |
| 确认尚未发出 | 不再开始收场，保存结束原因 |
| 已经发出，仍未取得最终收场结果 | 使用原剩余次数继续确认或停止；成功或次数耗尽后结束 |
| 是否发出无法确认 | 按已保存的意图及设备对账恢复，不据此增加预算或宣称未发出 |
| 收场已经结束 | 保留原结果，不重新执行 |

继续的是已经开始、目标已固定的收场，不增加目标、次数或新的后台任务。触发动作按取消或过期规则结束；该有限收场作为独立的本地处理责任完成并报告，不改写旧录像或触发动作的终态。重启后恢复原收场及剩余次数。

### 录像成功标准

正常录像的 `succeeded` 表示已按要求完成录像控制流程。未取消、未发现提前停止等录像异常时，须同时具备以下事实：

1. 已可靠取得本次录像的启动成功确认，并保存接收成功响应时的单调钟锚点。
2. 从该锚点起，按当前会话单调钟等待至少 `duration_s`，再执行停止。
3. 已取得停止成功确认，并可靠关联对应源文件及其写入完成事实。

满足上述条件且没有尚需完成的处理时，登记原片并提交动作 `succeeded`。正常录像不为读取时长或媒体核验而将原片拷贝到主机，也不要求读取视频轨道、时长或逐帧解码。

正常控制完成的事实已经可靠保存，仅在终态登记前中断时，恢复使用这些事实完成登记，不将登记中断本身视为录像异常。使用的是原会话已保存的计时结果，不能将旧单调钟锚点与新会话的时钟读数组合计算时长；完成事实缺失或未知时仍先对账。

报告区分目标时长、控制过程的计时证据及从文件取得的媒体信息。未读取文件内时长时，实际视频时长保持未知，媒体核验表达为未执行；不能以 `duration_s` 或主机等待时长代填实际视频时长，也不能将未执行核验记为核验失败或核验通过。

异常录像还可以采用原片时长检查作为成功依据：已确认原片属于本次录像且已经写完，主机检查可靠确认视频时长达到 `duration_s`，且没有明确的录像失败证据时，即使缺少可靠的控制计时，也满足第一版的录像成功标准。成功依据记为“时长检查满足目标”，保存实际视频时长及检查依据，不补造控制计时，也不承诺整段视频均可正常解码。正常或恢复控制完成与时长检查是分别成立的成功依据，数据库保存实际取得的依据；对外报告内容遵守[报告内容](status-reports.md#报告内容)。

取得时长成功依据不代表动作立即结束；必要修复及其他适用后处理仍须取得最终结果，再统一登记正式产物和动作终态。时长不足或其他明确媒体错误优先按失败处理，时长未知不能取得该成功依据。取消、已有终态及持久化错误继续按各自规则处理。

业务记录可可靠读取时，先处理取消与已有终态，再按下表的其余分区判断；记录保存失败或提交结果未知仍按持久化错误处理：

| 当前录像处理情况 | 结果处理 |
| --- | --- |
| 已取消或已有终态 | 按取消及终态规则处理，不由本节覆盖 |
| 正常控制流程尚未完成 | 继续执行或确认，不提前判成功 |
| 正常控制流程具备上述全部事实 | 按控制流程完成判为 `succeeded`，不要求媒体核验 |
| 已发生提前停止、断电恢复、停止失败等异常，仍有适用处理未完成 | 继续对应恢复及有限处理，不能套用正常流程的成功条件；旧会话单调钟不能用于新会话计时 |
| 异常处理结束，已有明确的录像失败证据，例如确认时长不足或原片损坏 | 按失败规则结束，不用后续停止成功覆盖已知失败事实 |
| 异常处理结束，没有明确的录像失败证据，已有可靠的恢复控制完成事实或原片时长检查满足目标 | 判为 `succeeded`，保留具体成功依据、异常及修复结果；未读取媒体时长时仍表达未知，不宣称完成整段解码验证 |
| 异常处理结束，仍未取得满足成功标准的证据 | 按失败规则结束，保留已经确定的文件、异常及未知事实 |

恢复控制完成的具体依据见“断电恢复后的控制完成依据”。异常多录仍按内部修复规则处理；因必要修复已取回主机的视频可由主机工具读取视频信息。恢复已取得充分控制证据且确认无需修复时，不为核验单独拷贝原片；是否明显多录仍无法判定时，按“计时证据不足时的原片检查”拷贝检查，不凭目标时长推定文件完整。

成功结果保留实际使用的判定依据，不隐藏通信失败、延迟停止、恢复或修复过程。动作终态提交后，后续取回或检查发现的时长不足、损坏等媒体问题作为新的产物质量事实记录并报告，不改写录像动作的历史终态。

### 原片保留与核验结果

未取消的录像，只要原片存在、确认属于本次录像且已经写完，就在处理结束时登记为正式产物。原片不足目标时长、无法正常播放或核验失败，均不取消其保留及原样取回资格；报告分别表达录像动作结果、文件可取回状态及核验结果。

下表用于动作终态尚未提交时的结束判定；仅适用的核验、必要修复及有限收场需要完成，正常录像不新增媒体核验，取消优先处理：

| 录像及原片情况 | 结束时的处理 |
| --- | --- |
| 录像已被取消 | 按录像取消规则放弃内容，不登记为正式产物 |
| 未取消，原片归属和写入完成已确认，正常或恢复控制已完成，没有明确的录像失败证据 | 登记原片并按成功标准提交 `succeeded`；未执行或未取得结论的媒体核验如实表达，不能单独否定控制完成依据 |
| 未取消，原片归属和写入完成已确认，未取得控制完成依据，可靠时长检查满足目标且没有明确的录像失败证据 | 登记原片，适用处理结束后提交 `succeeded`，成功依据记为时长检查；修复结果分别报告 |
| 未取消，原片归属和写入完成已确认，核验确认不足目标时长、内容损坏或无法正常播放 | 登记原片并提交动作 `failed`，保留具体核验结果及原因 |
| 未取消，原片归属和写入完成已确认，未取得控制完成依据，核验流程已按有限处理规则结束但未取得可靠结论 | 登记原片并提交动作 `failed`，报告核验未确认及原因，不能将其写成已经确认损坏 |
| 未取消，可靠确认没有形成原片 | 按相应失败或过期规则结束，不创建虚构产物 |
| 未取消，文件是否存在、归属或写入完成无法确认 | 按对账及有限收场规则处理；不能将未知文件登记为可取回产物，也不凭核验失败推断源文件不存在 |

例如目标 60 秒却只有可以正常播放的 30 秒原片，或原片已写完但无法播放：动作均为 `failed`，原片仍有稳定的 `output_id`，客户端可原样取回。报告保存目标时长、能够可靠取得的实际时长及失败原因；无法取得实际时长时明确表达未知，不以零或目标时长代替。

已有恢复控制完成或原片时长检查满足目标的依据，仅内部修复失败时，仍按“修复与动作成功分离”保持录像成功。核验过程中主机副本读取或校验失败，不表示相机源文件已经损坏；是否能原样取回仍按源文件及本次交付的真实状态判断。

原片按[长期保留](outputs.md#长期保留)规则保存，由客户端后续提交包含 `delete_action_outputs` 的执行计划并明确指定 `output_id` 清理。原片登记与动作终态仍在“录像动作的结束时点”规定的同一事务中提交；等待中的取回在提交后选择原片。已有终态及正式产物不因后续查询重新判定或重复登记。

### 内部异常多录修复

视频裁剪不是公开 action。

它是 `camera_record` 的内部修复机制，仅用于：

> 异常导致的明显多录。

#### 自动修复的多录门槛

以本地配置 `devices.<id>.recording.repair_margin_s` 的固定额外秒数作为允许多录的余量，默认值及取值范围见[配置归属](#配置归属)。设该值为 `T`，本次录像的修复门槛为：

```text
修复门槛 = duration_s + T
```

对异常录像，可信计时能够证明本次同一段连续录像的录制时间严格超过该门槛时，触发内部修复。恰好等于门槛不触发。`T` 是固定秒数，不随目标录像时长按比例变化；正常停止产生的轻微余量继续按“正常轻微多录”处理。

计时使用已确认的录像归属、连续性及可靠时间证据，遵守“断电恢复后的控制完成依据”。不能将停止响应的通信耗时、无法证明仍在录像的时间或不同会话的单调钟读数差计入录制时间。该依据用于判断修复资格，不代替文件内的实际视频时长；未读取媒体信息时，报告中的实际视频时长仍为未知。

修复须在会话取得正常执行资格后进行，时钟异常时按“安全收场与后续处理的衔接”保存进度。先处理取消、已有终态及已经保存的修复决定；尚未作出决定时，按下表判断：

| 录像情况与计时证据 | 修复判定 |
| --- | --- |
| 正常完成，仅有正常轻微余量 | 按正常录像完成，不触发异常修复 |
| 异常录像，可信计时证明已严格超过 `duration_s + T` | 记录需要修复；确认本次录像停止、源文件归属及写入完成后，按执行资格开始修复 |
| 异常录像，计时证据足以确认截至停止时未超过门槛，包括恰好相等 | 不触发多录修复，继续按录像成功及原片保留规则结束 |
| 异常录像，计时或连续性证据不足以判断是否超过门槛 | 保存判定未知，完成适用的有限对账与收场；正常会话中仍无法判定时，按下一节拷贝原片检查 |
| 所需配置、历史或决定无法可靠读取，或保存失败、提交未知 | 按对应错误处理，不猜测余量、修复资格或已经完成的决定 |

仅能证明“至少录了某个时长”时，该下界超过门槛即可确认多录；下界没有超过门槛，不能反过来证明实际录制未超过。录像仍在进行时尚未超过门槛，也不能提前保存最终的不修复结论；优先完成必要停止，之后按可靠证据判定。

例如使用默认余量，目标 60 秒：异常录像确认录制 70 秒时不触发，确认超过 70 秒时触发。取得充分计时证据后，不为判断是否需要修复而先取回视频读取媒体时长；满足修复资格后，再执行原有修复输入拷贝。

本次采用的余量作为动作固化策略可靠保存；修复判定及其时间证据追加到历史并同步更新投影，在启动修复拷贝前提交成功。重启沿用原余量和已保存决定，配置变化不重新解释既有动作；恢复同一修复仍遵守有限预算与断点续传规则。尚未取得停止及文件写完依据时，不能因已触发修复而读取仍在写入的源文件。

#### 计时证据不足时的原片检查

异常录像完成有限对账后，仍无法凭现有计时证据判断是否超过多录门槛时，camctl 在取得正常执行资格的会话中，将原片拷贝到主机检查，再决定是否修复。该检查属于原 `camera_record` 的必要后处理，不需要客户端另外提交取回请求；时钟异常会话仍只保存进度，按“安全收场与后续处理的衔接”等待正常会话。

拷贝前须确认源文件属于本次录像、已经停止且写完，并可靠保存检查决定、来源关联及原动作采用的门槛。录像连续时长未知不等于文件归属可以未知；来源或写入完成无法确认时，继续按原对账及有限失败规则处理，不能选择任意文件检查。

原片拷贝到 `staging` 中的工作位置，遵守相机视频的可靠读取、落盘、摘要校验及跨重启断点续传契约。完整有效的副本才交给主机工具检查；检查后需要修复时使用同一有效副本，不再次从相机拷贝。该工作文件不构成 delivery，不自动进入 `ready`，也不提前成为正式产物。

以下按可靠检查所得视频时长 `D` 分类；检查发现的其他明确媒体失败证据仍按录像成功标准处理，时长满足不单独证明全部目标内容有效：

| 检查结果 | 后续处理 |
| --- | --- |
| 可靠确认 `D < duration_s` | 不执行多录裁剪，按时长不足提交录像失败，保留原片 |
| 可靠确认 `duration_s ≤ D ≤ duration_s + T` | 不执行多录修复；没有明确的录像失败证据时，以时长检查满足目标作为成功依据，适用处理结束后登记原片及 `succeeded` |
| 可靠确认 `D > duration_s + T` | 保存时长结果及需要修复的决定，使用已有副本执行内部修复；没有明确的录像失败证据时已取得时长成功依据，仍须等待修复最终结果再统一提交 |
| 检查未取得可靠时长或发生工具错误 | 保留检查失败或未确认原因，按有限处理规则结束，不能猜测未超门槛或盲目裁剪 |
| 所需记录不可可靠读取、写入失败或提交未知 | 按持久化错误处理，先确认实际记录，不猜测检查或修复已完成 |

例如目标 60 秒、允许多录 10 秒：检查确认原片为 65 秒时不修复，为 5 分钟时进入修复，为 30 秒时记录录像不足。可信计时和文件检查是两种判定依据，报告保存实际采用的依据，不用媒体信息补造历史启动或停止时间。

检查输入拷贝及检查执行沿用有限超时、重试和空间不足规则。空间不足快速失败，不等待释放或跨会话自动重试；断电中断且仍有执行资格的未完成拷贝则在后续正常会话续传。拷贝或检查失败不证明相机原片损坏，也不自动删除原片。若已经具有充分的控制成功依据，仅检查失败不能单独否定该依据；没有成功依据时，按既有失败规则结束并保留原片。报告分别表达录像结果、检查错误及修复尚未取得判定，不将未执行的修复写成成功。

检查仍未完成时保留动作未完成及内部进度，适用处理全部结束后才按“录像动作的结束时点”统一登记正式产物与终态。检查决定、拷贝进度、检查结果及修复决定均按历史与投影规则保存；恢复沿用原动作、门槛、文件和预算。取消仍按录像取消规则放弃内容，已提交终态不因后续取回重新进入本次检查。

#### 第一版原片检查的范围

上述主机原片检查以取得可靠的视频时长、判断是否达到目标和是否需要多录裁剪为范围，不要求逐帧解码整段视频。检查结果只表达实际取得的媒体信息及已发现的问题；时长足够不能证明全部画面均可正常解码，也不保证整段视频没有损坏。

检查须能将所得时长可靠关联到本次原片的视频内容。文件或音频的总时长、按文件大小估算的时长、目标 `duration_s` 和控制等待时间，均不能直接代替可靠的视频时长。具体工具读取方式及可靠性判断由设备文件适配细化。

| 时长检查的结果 | 记录与使用 |
| --- | --- |
| 取得可靠视频时长且达到目标，未发现明确媒体错误 | 保存时长、来源及检查依据；满足录像成功标准的其他条件时取得时长成功依据，再按修复门槛处理，不记录整段解码通过 |
| 已可靠发现时长不足或其他明确媒体错误 | 保存具体失败事实，按录像结果及原片保留规则处理；不能因没有逐帧检查而忽略已知错误 |
| 无法取得可靠时长、信息矛盾或检查工具失败 | 保存实际失败或未确认原因，时长判定保持未知；不能当作时长为零、已经足够或已确认源文件损坏 |
| 尚未执行或检查仍未完成 | 保存相应阶段，不提前给出检查通过或失败结论 |

时长信息、是否达到目标、是否超过修复门槛及已发现的媒体错误分别保存和报告。未执行的整段逐帧解码不能写成通过；客户端也不能从 `sha256` 一致推断媒体可正常播放。相机到主机的字节一致性检查仍按拷贝契约完成，时长检查不代替它。

#### 修复内容与文件处理

不允许调用方通过 `obtain_action_outputs` 主动指定：

- 裁剪起点；
- 裁剪终点；
- 任意裁剪时长。

修复目标：

> 从录像内容起点开始保留至少完整 `duration_s` 内容。

原则：

```text
只能多，不能少
```

允许尾部多保留几秒。

v1 使用 `ffmpeg/ffprobe` 作为板端外部依赖，裁剪只采用**无重新编码的方式**；不为了精确边界重新编码视频。

无法安全完成无重编码修复时：

```text
repair_failed
```

保留原片，不进行转码兜底。

修复在客户端尚未请求取回时也主动执行。

内部修复及上述原片检查需要将相机视频拷贝到主机时，在 `staging` 中保存和处理输入文件，并在该目录中生成适用的目标录像；同样必须支持[跨主机重启的断点续传](outputs.md#相机视频的断点续传)。拷贝恢复继续受本动作的取消、空间和设备收场规则约束。

修复成品准备完成后保存在 `staging/derived/`，并在下文规定的结束事务中登记为正式产物。其保留与重复交付遵守[主机派生产物](outputs.md#主机派生产物)规则。

### 修复与动作成功分离

已经取得恢复控制完成依据，或可靠的原片时长检查满足目标，且没有明确的录像失败证据时，内部修复失败不影响录像成功：`camera_record = succeeded`，修复结果为失败。数据库保存实际成功依据，报告分别表达录像结果及修复失败原因；采用时长检查时不承诺整段原片均可正常解码。

修复输入拷贝失败、主机空间不足或修复工具执行失败，均不能单独否定已有控制完成依据。若在动作结束前确认原片时长不足或损坏，则按录像失败处理；核验未执行或未取得结论不能冒充此类失败证据。

### 录像动作的结束时点

正常录像在控制流程完成后结束；异常录像继续完成适用的核验和必要内部修复。各自需要的处理取得最终结果后，在同一数据库事务中登记应保留的全部正式产物并提交动作终态。原片与修复成品均在该事务成功提交后成为可供取回选择的正式产物，正常录像不因未执行媒体核验而延迟结束。

动作结束前照常保存源文件关联、主机文件、拷贝进度、核验和修复结果，支撑断电恢复及状态报告。这些内部处理记录不构成正式产物登记；即使原片已经写完且时长检查满足目标，也不能在修复仍未结束时提前取回原片。状态报告可以表达处理进度，不将这些文件列为可取回的正式产物。

下表用于未取消、未过期的动作；启动失败、核验失败或修复失败等已按相应规则结束的阶段，不要求继续执行已无必要或无法执行的后续步骤，但须记录失败原因及未执行的依据。

| 处理进度与结果 | 动作与正式产物的处理 |
| --- | --- |
| 采集、必要收场或适用的核验、修复仍需继续执行或恢复 | 保持未完成，保存内部处理记录，不登记正式产物 |
| 正常控制流程已按成功标准完成 | 同一事务登记原片并提交 `succeeded`，保留控制证据；媒体核验未执行，实际视频时长未知 |
| 异常处理各阶段已结束，恢复控制完成或原片时长检查满足目标，没有明确的录像失败证据，修复不需要或已成功 | 同一事务登记原片、适用的修复成品并提交 `succeeded`，保留具体成功依据 |
| 异常处理各阶段已结束，恢复控制完成或原片时长检查满足目标，没有明确的录像失败证据，修复已失败 | 同一事务登记原片并提交 `succeeded`，保留成功依据及修复失败原因 |
| 异常处理各阶段已按规则结束，仍未满足成功标准 | 同一事务登记按规则应保留的正式产物或记录确认无正式产物，并提交 `failed`；保留核验结果、失败原因及残留设备事实 |
| 各阶段已结束，但处理结果或应保留文件集合无法可靠确定 | 先核实或按相应错误处理，不提交猜测的终态或产物集合 |

终态事务须确认阶段结果已经可靠保存，或将尚未保存的结果一同提交；正式产物登记、动作终态的历史与投影整体可见。等待取回的请求只有看到已提交的录像终态，才按[取回等待规则](outputs.md#等待录像动作结束)选择文件。文件读取、核验和修复在该事务之外完成。

取消与过期按各自规则结束，不能因本节要求而继续本应停止的核验或修复。修复期间动作尚未终态，取消仍按“camera_record 取消”放弃本次录像；已经提交的终态保持不变。有限收场失败后保留的未知设备状态，不要求无限等待其变为已知。

取消与结束并发时，以目标录像的持久化处理顺序判断；取消计划被受理本身不表示目标录像已经取消：

| 数据库中的先后顺序或结果 | 处理 |
| --- | --- |
| 目标录像的取消标记先保存，结束事务尚未提交 | 按取消规则放弃内容，不登记正式产物；结束处理须在事务内检查该标记 |
| 正式产物与录像终态的事务先提交，随后处理取消 | 保持录像终态和正式产物；取消录像不授权删除这些文件，文件继续按显式清理规则保留 |
| 结束事务失败且确认回滚 | 不留下部分正式产物或终态；根据已有处理结果及取消状态恢复 |
| 提交结果未知或状态无法可靠读取 | 先确认数据库事实，不据此发布产物、重复登记或将文件当作废弃内容删除 |

断电后根据已提交的内部处理记录、正式产物和动作状态恢复。终态尚未提交时，在会话具备相应执行资格后继续必要处理并完成统一提交；时钟异常时按“安全收场与后续处理的衔接”保留尚未完成的后处理，不因已看到完整原片而跳过未结束的修复。终态已经提交时不重新执行本次核验或修复，也不重复登记产物。已取消录像留下的文件继续按废弃内容处理，不因重启转成正式产物。

### 空间不足

相机自身仍有空间、状态库仍可可靠写入时：

> 板端视频处理空间不足不能阻止新的录像采集。

录像继续进行并保留设备源内容。

正常录像不为媒体核验拷贝视频，不因缺少这类拷贝空间而失败。必要异常处理或取回中需要板端空间的：

- 拉取；
- 核验；
- 修复；

遇到空间不足时快速失败。

不等待空间释放，不跨 run 自动接续。

如果异常处理确需主机核验，但因空间不足未能完成，仍无法满足成功标准：

```text
camera_record = failed
```

如果已有恢复控制完成依据，或原片时长检查已满足目标，仅修复缺空间：

```text
camera_record = succeeded
repair_failed(storage_insufficient)
```

### camera_record 取消

在动作尚未进入终态时取消 `camera_record`：

> 放弃本次录像。

包括：

- 尚未开始；
- 正在录像；
- 已经停止但正在核验；
- 正在内部修复。

如果录像仍在进行：

- 尝试停止；
- 放弃内容；
- 协议支持时清理废弃产物。

如果录像已经停止：

- 不再次发送可能误停后续录像的通用 stop；
- 终止后续核验/修复；
- 放弃本动作产生的内容；
- 协议支持时清理废弃产物。

废弃录像不登记为正常可取回产物。

取消生效不等于物理清理一定成功。

## 配置归属

`clock.recovery_wait_cap_s` 是异常恢复等待上限，默认 **60 秒**，允许通过本地配置设置为有限的非负秒数；设为 0 时不额外等待。异常时等待 `min(duration_s, recovery_wait_cap_s)` 后尝试停止，它不限制正常录像的 `duration_s`。

`devices.<id>.recording.repair_margin_s` 是当前 ADB 相机 `timed` 参数类型允许的异常多录余量，默认 **10 秒**，允许本地配置为有限、非负的秒数。设为 0 时，已确认异常录像严格超过目标时长即达到多录修复条件。该值在动作首次受理时作为生效策略保存，后续配置变化仅影响新受理的动作。

该参数只决定异常多录的修复门槛，不推迟正常停止目标，也不改变异常恢复等待上限；执行计划不提供裁剪或修复门槛覆盖参数。正常轻微多录及修复资格判断继续遵守“自动修复的多录门槛”。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

将录像意图、可恢复的设备录像身份、启动确认依据、收场进度、完整性核验结果、修复结果及残留设备事实追加到历史，并同步更新相关投影，遵守[持久化与配置基础](../2026-09-08-camctl-cli-design.md#持久化与配置基础)。历史回放不启动或停止录像，也不执行修复。回放恢复的是已记录的观察与意图；实际设备对账继续按本专题的证据规则执行。

当前会话单调钟锚点仅适用于当前会话，持久化历史不会使旧锚点在新会话中有效。跨重启恢复应依据本专题定义的可证明事实，具体记录结构待结合真实协议确定。

## 验收要求

### 单元测试

录像输入覆盖 `policy` 缺失、不是对象、缺少 `max_delay_ms`、值为负数或类型不符，以及合法零值和正整数。非法输入只使该录像在受理时失败且不产生尝试；合法输入按明确给出的启动窗口执行，不使用隐藏默认值。

触发动作取消或过期时，覆盖停止命令尚未发出、已经发出、发出状态未知及收场已结束。未发出则不开始，已开始则继续原剩余次数；不启动触发动作的录像，不创建新预算。

按“后续动作触发的残留收场”覆盖设备空闲、已知历史残留、其他有效动作占用及状态未知。已知残留才可触发独立收场；上限默认 3 次且可配置，原停止计数与新录像自身计数均不消耗或重置。同一触发动作重复检查不新建预算；新收场成功不改写旧录像终态，耗尽后不能后台重复启动。

当前相机联调验证停止指令成功返回后，对应视频可立即完整读取，后续长度和内容保持不变。组合 SQLite 与录像处理，在停止成功后确认记录提交前后中断，验证恢复按持久化事实及设备对账继续处理，不能将缺少成功记录解释为文件仍在写入或已经写完。

组合清理授权、旧取回保护与当前相机文件操作，在录制 B 时删除已完成视频 A，验证只处理 A 且 B 继续录像；存在未解除的读取依赖时仍等待，不能因 Linux 允许删除文件而绕过清理资格。

使用可正常播放但不足目标时长的视频，组合核验、SQLite、等待中的取回及报告生成，验证原片登记与录像失败整体提交，取回可以取得该原片，报告包含目标与实际时长。重启不删除或重复登记；客户端后续明确提交清理计划后才按清理规则删除，数据库历史继续保留。

另用已写完且归属明确的损坏原片及核验未取得结论的原片，验证处理结束后均可登记并原样取回，报告分别保留确认损坏与核验未知的结果。取回文件与对应源文件逐字节一致，客户端通过交付摘要核验传输内容，不以无法播放拒绝交付。覆盖结束事务提交前后中断及后续显式清理，原片保留与数据库历史遵守各自规则。

组合真实 SQLite 和受接口约束的设备替身，验证启动意图与投影提交成功前不能发送命令。分别在意图提交后命令发送前、命令发送后结果提交前、确认结果提交后中断，验证前两者恢复时均保留待核实含义，后者保留已确认的历史事实；当前设备状态仍按本专题对账。回放本身不发送启动或停止命令。

同一框架流程分别组合支持指定路径与设备自行命名的驱动适配，验证两者均能保存和恢复已确认的录像、源文件关联。当前相机的真实协议验证覆盖设备自行命名、shell 查询正在录制的文件及文件存在性，并区分查询成功、失败和未知。以不依赖 ADB 的受接口约束适配替身验证框架消费相同业务结果；未来驱动另行验证其真实设备协议。关联证据不足时保留未确认结果，不根据预期路径补造已生成文件。

组合 SQLite、录像后处理、等待中的取回与报告生成，验证修复成功时取回包含原片和修复成品，修复失败但原片时长满足目标且无明确失败证据时，录像成功且报告保留修复失败。分别在内部结果保存后、结束事务部分写入后及提交后中断，验证正式产物与终态同时可见或均未提交，恢复不遗漏成品、不重复登记。修复期间的报告可包含进度，但没有可取回的原片或修复成品。

分别安排目标录像取消标记与结束事务先提交，验证前者保留取消结果且不登记正式产物，后者保留终态及正式产物。包含取消计划已受理但目标取消尚未处理的情况；取消后再次启动，废弃文件不会被登记或取回。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 拍摄能力与参数类型

- 同一种拍摄能力在不同驱动下可以使用不同参数类型；固定任务参数不能被未开放字段覆盖。
- 由实际驱动定义和设备配置生成说明，验证设备绑定、可执行能力及参数规则一致；更换绑定或修改参数契约后，导出说明反映对应变化。
- 将导出说明与计划入口组合验证：合法示例通过对应驱动校验，违反字段或组合限制的拍摄动作按自身参数错误失败；说明生成故障不能产生可交付的残缺说明。
- 按“计划字段与参数校验”覆盖未实现类型、设备不适用、参数类型错误、参数错误、合法输入和定义读取故障；分别验证整份拒绝、单动作失败和会话错误。
- 驱动默认值首次受理后固定，重送、恢复和历史回放不按新的默认值重算参数；原计划重建保留原始输入。
- 参数类型或参数值校验失败的拍摄成员仍是组取回来源，终态无正式产物时按取回失败项表达。
- 第一版以当前 ADB 相机的 `timed` 参数类型贯通计划受理、录像、产物登记和取回；未来驱动接受不同参数类型的能力可用受接口约束的替身验证扩展边界，不宣称已接入对应设备。

#### camera_record

- 录像启动确认；
- `duration_s` 从确认点计时；
- 已开始录像保护；
- 后续录像冲突等待/过期；

## 实现时细化

正文定义第一版的业务规则。本节列出接口、配置和联调中需要落实的细节；先按正常流程推进，涉及正文尚未确定的业务结果时，再明确对应选择。

能力及参数说明的具体机器格式、导出入口及客户端导入方式在驱动接入与部署联调时落实；内容和同步责任遵守“部署时向客户端提供说明”。导出规则须覆盖驱动实际校验的字段和组合约束，不通过另写一套完整规则实现导出。

启动与停止的尝试上限默认各 3 次且允许分别配置，正常、取消及恢复入口共享原停止计数。仍需明确次数分配与设备意图的持久化边界、启动、停止及后续按需收场在本地设备配置中的具体字段。计划不提供通信策略覆盖，按调度专题的配置归属规则处理。后续动作触发的收场采用已确认的独立预算，触发动作结束时按本专题的收场规则处理。

正常录像按控制流程完成判定成功；异常录像按已确认的恢复控制完成或原片时长检查满足目标判定成功。自动修复采用“自动修复的多录门槛”中定义的固定额外秒数；正常会话中仍无法确定是否超过门槛时，按“计时证据不足时的原片检查”拷贝检查。仍需明确恢复所用历史时间与连续性证据的具体表示、主机媒体检查的方法与可靠判定依据，以及其他媒体核验适用场景。这些规则须遵守相机端不增加依赖、不为控制成功判定单独拷贝原片的边界。文件归属及写入完成已经确认的原片按“原片保留与核验结果”登记并保留；失败原因、未执行核验及未知媒体信息的字段表达仍需细化，不能将主机工具可用当作原片已经位于主机。正式产物登记、终态提交及与取消的先后关系遵守“录像动作的结束时点”；废弃文件的具体清理能力与恢复仍需结合设备协议细化。覆盖停止失败、内容完整证据、结果未知及后续对账的有效组合，保持动作终态不可迁移。
