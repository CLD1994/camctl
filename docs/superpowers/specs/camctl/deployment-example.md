# 首次部署与联调样例

[返回设计总览](../2026-09-08-camctl-cli-design.md) · [首次部署与初始化](initialization.md) · [客户端协议样例](client-protocol-examples.md)

本样例串联第一版实现完成后的部署和联调步骤：确定配置、初始化状态库、导出能力说明、手工交给客户端，以及通过主程序提交计划和中转报告。具体行为以链接的责任专题为准。

## 样例范围与准备

本例使用一台主机、一个逻辑客户端和已安装可调用的 `camctl`。主机运行环境及工具按[依赖与部署](../2026-09-08-camctl-cli-design.md#依赖与部署)准备。命令由实际运行 CLI 的账户执行，默认路径以该账户的用户主目录计算；主程序调用 CLI 时须使用对应的运行账户和生效配置。

客户端一侧由部署人员按[客户端的本地部署](../2026-09-08-camctl-cli-design.md#客户端的本地部署)准备 Docker Compose 应用，在用户个人电脑上启动包含后端和构建后网页资源的单个应用容器，浏览器访问对应的本地端口。客户端数据使用持久化存储，更新容器后继续保留。下面的 `camctl` 命令在嵌入式主机上执行；导出能力说明后，按第三步交给客户端使用。

| 演练范围 | 输入与条件 | 可以验证的内容 |
| --- | --- | --- |
| 默认环境部署 | 无配置文件，或仅使用下面的通用覆盖样例；设备目录为空 | 初始化、能力说明导出与客户端加载，以及无设备动作的报告流程 |
| 真实相机接入 | 已完成实际设备的驱动绑定、正式参数类型、命令映射及联调准备 | 在上述流程基础上，验证真实录像、产物取回及必要失败处理 |

真实相机配置中的设备标识、驱动标识、连接信息和参数类型来自对应的设备接入规格。协议样例中的拍摄参数用于演练，实际部署使用正式驱动定义。本例的报告检查计划只使用已经确定的公共动作。

| 文件 | 用途 |
| --- | --- |
| [config.toml](examples/deployment/config.toml) | 可选的通用配置覆盖样例，仅将日志级别设为 `INFO` |
| [report-plan.json](examples/deployment/report-plan.json) | 无设备的报告检查计划，可交给主程序用于联调 |

本例假设首次部署尚未产生业务历史，主程序的日常 CLI 调用尚未启用。已有部署的配置调整按[停止后更新规则](scheduling-execution.md#本地配置的加载与更新)进行；已有数据库继续保留。

## 一、确定本地配置

默认配置文件为 `$HOME/.camctl/config.toml`。可以完全不创建该文件；CLI 仍使用内置默认值。

需要在首次联调时增加日志信息，可将本例的 `config.toml` 放到默认位置。文件只覆盖日志级别，其余配置沿用默认值。已有设备配置时只合入所需字段，保持已有设备声明。

默认状态库和交接目录分别见[通用配置](../2026-09-08-camctl-cli-design.md#通用配置)与[文件交接配置](file-handoff.md#配置归属)。主程序的目录设置使用这些路径展开后的实际绝对路径，并具备领取、传输及删除对应文件所需的访问权限；`staging` 中的处理文件仍由 camctl 管理。

若部署选择另一份覆盖文件，本例后续所有 CLI 调用均应带上同一个 `--config <path>`。文件不存在时使用默认值的行为仍适用，因此部署人员须核对自己选择的配置来源；是否有实际设备以最终能力说明为准。

## 二、初始化本地运行环境

在主机上执行：

```bash
camctl init
```

成功时退出码为 `0`，stdout 为空。状态库和必要目录已准备，配置文件仍可不存在。默认业务路径如下：

```text
$HOME/.camctl/
    state.db
    staging/
        derived/
    ready/
    processing/
```

日志和稳定锁文件按各自规则管理，未列入这份业务路径示意。重复执行 `init` 验证已有合法数据库并保留历史、身份及累计 ACK。初始化失败时处理 stderr 中的实际错误，按[再次执行规则](initialization.md#创建失败与再次执行)核实状态后继续；不能为了继续联调删除已有业务库。

## 三、导出并手工交接能力说明

在主机上执行：

```bash
camctl describe > device-capabilities.json
```

正常退出码为 `0` 且文件为完整有效的 JSON 后，才把这次文件交给客户端。单份文件按[能力说明格式](capabilities.md)包含设备、拍摄动作、参数类型及完整 Schema；Schema 的版本声明和离线加载遵守[拍摄参数的 JSON Schema](camera-recording.md#拍摄参数的-json-schema)。默认空设备配置输出 `{"devices": []}`，可对照[空设备说明](examples/capabilities/empty-devices.json)检查；正式相机配置完成后，导出内容应与实际驱动及设备绑定一致。命令不探测设备是否在线。

用户手工将文件复制到客户端约定的能力说明文件位置，覆盖对应文件。客户端完整读取和校验后启用新目录；失败则明确报告错误，不使用部分内容。客户端文件位置由客户端部署约定给出，遵守[能力说明加载规则](camera-recording.md#客户端加载能力说明)。

这一步的可观察结果是客户端可按当前设备目录和规则生成计划。单纯复制完成不表示加载成功，手工覆盖也不保证旧文件仍可恢复。

## 四、启用主程序的日常调用

初始化和配置交接完成后，由部署流程启用主程序。主程序具体的启动命令由其部署方式决定，其 CLI 调用行为如下：

| 场景 | 主程序如何调用 | 结果处理 |
| --- | --- | --- |
| 主机上电，本次没有执行计划 | `camctl run` | 等待实际进程结束，联合最终结果与退出状态判断会话结果 |
| 主机上电，本次发现执行计划 | `camctl run <plan-path>` | 输入路径交给 CLI，等待会话结束；计划文件之后由主程序自行清理 |
| 后续收到新的计划输入 | `camctl submit <plan-path>` | 成功时读取 `needs_run`，按接管规则决定后续启动 |

`submit` 成功且 `needs_run = true` 时，主程序记录待启动要求；已有 `run` 尚未退出则等其实际结束，再启动一次裸 `run`。多个待启动要求可以合并。`needs_run = false` 时不因此追加启动。完整条件以[会话接管协议](protocol-session.md#会话接管协议)为准。

主程序按进程结果处理调用，不据此判断录像是否成功或计划是否受理。一次 `run` 正常退出且没有待启动要求时，不无条件再次启动；状态库错误也不触发主程序自动执行 `init`。

## 五、提交报告检查计划

客户端在空设备目录下也可以生成 `report_status` 动作。用户在网页中准备与本例 [report-plan.json](examples/deployment/report-plan.json) 对应的计划，导出 JSON 文本并手工递交给负责消息传输的部门。该部门将计划送达主程序所在主机，由主程序保存文件并按上表调用 CLI；具体传输方式由该部门安排。样例文件内容完整有效，不依赖具体相机参数。

样例请求 ID 为 `req-deployment-check-001`，计划名为“部署报告检查”，只有一个未填写 `scheduled_at` 的 `report_status` 动作。它按立即动作规则执行；`created_at` 是样例 UTC 时间，不用于判断主机时钟是否可信。真实生成计划时由客户端填写生成时间和请求 ID。

这一步要求主机时间满足现有可信性规则，状态库与报告目录可用。若在启用主程序前先手工检查 CLI，可执行等价的本地调用：

```bash
camctl run report-plan.json
```

该命令假设样例文件已经放在当前目录；它只替代本次 CLI 调用，主程序输入中转和报告传输仍需分别联调。手工执行时避免与主程序重复启动执行会话。

正常会话结束时，`run` 输出一条 `{"kind":"succeeded"}` 并以 `0` 退出。若主程序先通过 `submit` 接收计划，它还需依照 `needs_run` 完成必要的 `run` 启动。后续业务结果以实际状态报告为准。

## 六、中转报告并确认客户端状态

| 顺序 | 实际处理 | 可观察结果 |
| --- | --- | --- |
| 1 | camctl 在 `staging` 生成完整报告，按规则发布到 `ready` | 文件名为 `status-report-<report_id>-<sha256>.json`；实际编号和摘要由本次运行决定 |
| 2 | 主程序在实际可用的输出窗口，将 `ready` 文件移到 `processing` 并传输；传输部门向用户提供收到的报告 JSON 文件 | 全程保持文件名及原始字节；主程序判定传输完成后删除本地传输副本 |
| 3 | 用户在网页上点击导入按钮并选择报告文件；客户端计算摘要，校验后按实体 ID 合并并保存内容 | 合并覆盖动作终态的报告后，能确认样例请求已受理、计划 `completed`、报告动作 `succeeded` |
| 4 | 客户端在后续导出的计划中携带实际可累计确认的 `last_report_id`，用户再次手工递交给传输部门 | 确认输入到达后，camctl 按已登记报告推进确认水位，完成相应报告责任 |

显式报告可能先表达动作执行中的状态，动作结束后的自动报告再表达终态；联调按实际报告覆盖及合并结果判断，不要求只产生一份报告，也不预设某个固定报告编号。ACK 仅确认客户端已经完整保存的连续报告覆盖，不能简单取见过的最大编号。

客户端可以在保留样例原请求正文的重送中增加有效 `last_report_id`。相同 `request_id` 复用原计划和动作；如需再执行一次新的显式报告检查，客户端使用新的请求 ID。输入与 ACK 的组合及重送规则见[客户端确认与重送](protocol-session.md#客户端确认与重送)。

文件残留在 `processing` 时，不推断第三方会再次传输。报告补投继续遵守[状态报告规则](status-reports.md)，客户端未取得报告时也不能仅凭主程序本地删除文件而宣称已经完成核验。

## 必要失败处理

| 出现的情况 | 本次部署或联调如何继续 |
| --- | --- |
| 所选配置文件不存在 | 使用默认值继续；核对空设备目录是否符合本次演练范围 |
| 覆盖文件无法读取或内容非法 | 修正配置，保持已有状态库和业务文件 |
| `init` 发现已有无效或无法读取的数据库 | 保留原文件并处理实际错误，不覆盖为新库 |
| 日常入口找不到已投入使用的状态库 | 核对用户目录及生效路径，恢复原数据；不让主程序自动初始化 |
| `describe` 失败或客户端加载失败 | 不启用本次说明，重新提供有效的完整文件 |
| `run` 返回 `clock_invalid` | 按既有时间校正和实际后续启动安排继续；已受理输入仍以数据库为准，不因会话错误换请求 ID |
| 普通文件日志写入失败，但必要职责正常 | 按[日志故障规则](logging.md#日志通道故障)继续；文件日志可能不完整 |
| 状态库或报告职责失败 | 按[会话错误](session-errors.md)处理，保留实际持久化及文件结果，后续正常入口依据已有状态恢复 |

## 实际相机与第三方联调输入

通用部署流程使用上述文件和命令。真实相机接入前，还需依据实际设备完成正式参数规格、驱动配置及命令映射，并用对应能力说明生成真实录像计划；真实采集结果按[相机接入契约](camera-recording.md#第一版驱动接入契约)验收。

客户端约定的能力说明文件位置仍需在部署接口中落实。主程序的具体启用方式和实际输入、输出窗口由第三方联调提供；完整链路验收使用这些真实协作入口。这里的命令结果和业务状态是验收预期，不构成已经完成设备联调的证据。
