# 请求受理与会话

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义调用方、主程序与 camctl 的请求和进程契约。动作特有参数与执行结果由各动作专题定义；`last_report_id` 的有效性及覆盖含义由[状态报告与累计确认](status-reports.md)定义。

主程序由第三方维护，其集成职责是 CLI 进程管理和数据中转。进程协议应让它能够判断会话结束结果、处理后续启动，并尽量减少它需要实现的协调逻辑。计划受理及动作执行的业务结果由 camctl 向调用方客户端表达。

## CLI 命令与进程协议

### 命令面

```text
camctl run [<plan-path>] [--config <path>]
camctl submit <plan-path> [--config <path>]
camctl --version
```

#### `run`

完整执行会话。

不带 `plan-path` 时为裸 `run`：

```text
camctl run
```

用于驱动状态库中已经受理的任务、恢复遗留状态和生成必要报告。

#### `submit`

快速受理：

1. 打开并验证状态库；
2. 解析输入，分别取得 `request_id` 和 `last_report_id`，保留其余正文供首次受理使用；
3. 按 `request_id` 查询已受理关联；已知 ID 复用原计划，未受理 ID 才校验正文并完整注册或记录拒绝结果；
4. 独立吸收有效 ACK，或记录 ACK 校验错误；
5. 判断是否需要后续 `run`；
6. 提交处理结果后秒级退出。

`submit`：

- 不执行设备操作；
- 不生成数据产物；
- 不要求系统墙钟当前可信。

### 主机上电后的首次启动

每次主机上电后，主程序都发起一次 `run`。启动形式由本次是否存在数据输入，以及输入中是否发现执行计划决定：

| 有数据输入 | 输入中发现执行计划 | 主程序启动命令 |
| --- | --- | --- |
| 否 | 不适用 | `camctl run` |
| 是 | 否 | `camctl run` |
| 是 | 是 | `camctl run <plan-path>` |

主程序将发现的执行计划持久化为文件，并将其路径作为 `<plan-path>` 传入。这里的“发现执行计划”不等于 camctl 已完成计划校验和受理。

因此，即使本次没有新计划输入，状态库中的已受理任务与遗留设备状态也会获得一次由 `run` 检查和驱动的机会。实际恢复及执行仍遵守时钟和设备条件等规则。

这条规则适用于每次上电后的首次启动。一次 `run` 在同一供电窗口内正常退出后，后续启动仍按本专题的 `needs_run` 协议处理。

### 输入计划的保留责任

输入计划文件归主程序管理，删除由主程序执行。文件在提交后不会立即删除，但后续删除时点由主程序决定，camctl 不知道具体时间。文件暂时存在不构成长期保留或恢复保证；主程序不承担基于历史输入自行重送的责任。再次收到客户端输入时，仍按正常入口中转。

后续 `run` 的恢复依据是 camctl 已可靠保存的状态。已提交的计划及业务结果可由后续实际启动的会话发现；尚未可靠保存的输入不能仅靠启动裸 `run` 恢复，由客户端按“客户端确认与重送”承担补送责任。

camctl 通过 `<plan-path>` 读取本次输入，受理结果可靠保存后，执行与恢复仅依据其持久化状态，不再依赖原计划文件。输入文件的删除时间不参与计划调度或退役判定。

“不会立即删除”尚未定义读取期间的可用性保证。实施前仍需明确文件打开或读取失败的处理语义；不能据未知的删除时点假定文件始终可读。

### 带计划启动时的受理结果

`camctl run <plan-path>` 对传入计划的受理结果，与已有任务能否继续被驱动分别判断。在状态库和运行条件允许的前提下：

| 启动输入 | 本次计划受理结果 | 会话行为 |
| --- | --- | --- |
| 未传入计划路径 | 不适用 | 检查并驱动已有任务，按规则恢复遗留状态 |
| 传入计划路径 | 成功，包含同一请求的幂等复用 | 将受理结果纳入当前会话，并驱动已有任务及恢复遗留状态 |
| 传入计划路径 | 因输入解析、请求 ID 或首次受理的正文校验错误被拒绝 | 保留面向客户端的受理错误，继续驱动已有任务及恢复遗留状态 |

例如，计划 JSON 格式错误，或未受理 ID 携带的动作参数不合法，均属于最后一个分区。有效的已受理 ID 按幂等规则复用原计划。被拒绝的输入不注册为新的执行意图。

计划受理错误本身不能作为跳过已有任务恢复的理由。这不改变状态库校验、时钟资格和设备条件的要求；这些条件影响会话能执行哪些工作，仍按各自契约判断。

本次计划被拒绝属于面向调用方客户端的业务结果，由 camctl 记录并纳入状态报告。主程序通过会话结束结果管理进程，通过文件交接协议中转业务信息。受理错误的报告记录与关联信息由[状态报告与累计确认](status-reports.md)定义。

### `run` 的启动顺序

完成定位状态库和锁文件所需的配置读取后，裸 `run` 与带计划路径的 `run` 按以下顺序启动：

1. 取得会话锁。
2. 打开并验证状态库。
3. 传入计划路径时，完成输入解析和请求幂等判断，仅对未受理 ID 校验计划正文，并独立处理 ACK、提交处理结果；未传入计划路径时直接进入下一步。输入被拒绝时，保存面向客户端的拒绝结果后继续启动流程。
4. 在受理事务结束后，读取可信历史时间下界，检查当前墙钟，并在必要时延迟复检。
5. 时钟检查通过时，按会话接管协议取得接纳资格，进入正常恢复、调度、执行和报告流程。时钟检查仍失败时，按时钟规则执行有限安全收场，并以时钟异常结束。

计划受理与 `submit` 使用相同的静态时间校验规则。受理阶段不依据当前墙钟判断动作已到期或已过期，也不产生设备副作用。墙钟检查失败不撤销已经提交的计划、请求关联或有效 ACK。

初始化所需的会话锁、状态库及受理结果持久化出现会话级错误时，按对应错误处理；只有受理结果已可靠保存，才进入后续时钟判断。墙钟复检等待不占用受理或交接写事务。

以下组合适用于会话锁和状态库正常、本次受理处理已可靠结束的情况：

| 本次输入结果 | 时钟检查结果 | 数据库结果与后续行为 |
| --- | --- | --- |
| 未传入计划 | 通过 | 进入正常流程，驱动已有任务 |
| 首次受理成功或幂等复用 | 通过 | 保留受理结果，驱动当前状态库中的任务 |
| 计划因业务输入错误被拒绝 | 通过 | 保留拒绝结果，正常驱动已有任务 |
| 未传入计划 | 失败 | 有限安全收场，以时钟异常结束 |
| 首次受理成功或幂等复用 | 失败 | 保留受理结果，有限安全收场并以时钟异常结束；受理本身不授予普通动作执行资格 |
| 计划因业务输入错误被拒绝 | 失败 | 保留拒绝结果，有限安全收场，以时钟异常结束 |

在时钟校验之前读取的本机时间尚未获得可信性证明，不得据此推进未来启动校验使用的可信历史时间下界。相关时间事实的表达由[调度与设备执行](scheduling-execution.md)定义。

### stdout 与退出状态

stdout 只负责：

```text
进程控制 / 会话控制
```

主程序消费这些消息以管理进程和后续启动。业务结果通过 camctl 的客户端报告机制表达，文件交付通过目录协议完成。

`run/submit` 在结束时输出一条最终结果：以 UTF-8 编码的一行 JSON 对象，行末为换行符。stdout 仅包含该结果；运行日志和诊断信息写入 stderr，子进程输出也须与结果通道隔离。正常返回结果时只输出一次，突然终止或输出失败时可能没有完整消息。

合法消息示例：

```json
{ "kind": "succeeded" }
```

```json
{ "kind": "succeeded", "body": { "needs_run": true } }
```

```json
{ "kind": "error", "body": { "reason": "clock_invalid", "details": {} } }
```

`run/submit` 正常完成时输出 `succeeded` 并以 `0` 退出；主动报告会话错误时输出 `error` 并统一以 `1` 退出。计划拒绝或 ACK 无效等业务错误已按规则处理且会话正常完成时，仍使用 `succeeded` 和退出码 `0`。

错误结果的 `body` 包含：

| 字段 | 类型与含义 |
| --- | --- |
| `reason` | 稳定字符串，作为区分错误种类的机器标识，例如 `clock_invalid` |
| `details` | JSON 对象，提供该错误的上下文；没有附加上下文时为 `{}` |

主程序依据会话结果判断成功或失败，错误原因用于诊断及后续约定的处理策略。结构合法但主程序尚不认识的 `reason` 仍表示会话失败，应保留错误信息；不能据此推断重试资格。各错误种类及其上下文字段由后续错误分类契约统一定义。

主程序结合最终消息和实际进程终止状态判断结果。消息已经到达但进程尚未终止时，尚不能认定会话正常结束；数据分多次读到也不等于消息被截断，应在收集完整输出后判断。

| 最终 stdout 状态 | 进程终止状态 | 主程序判定 |
| --- | --- | --- |
| 一条完整且符合命令契约的 `succeeded` | 正常退出，退出码 `0` | 会话成功；`submit` 按 `needs_run` 处理后续启动 |
| 一条完整且符合命令契约的 `succeeded` | 正常退出，退出码非零 | 消息与退出状态不一致，判为会话异常 |
| 一条完整且符合命令契约的 `error` | 正常退出，退出码 `1` | 会话失败，使用消息中的错误信息 |
| 一条完整且符合命令契约的 `error` | 正常退出，退出码不为 `1` | 消息与退出状态不一致，判为会话异常 |
| 消息缺失、截断、不合法，或输出不符合单条结果约定 | 正常退出，退出码任意 | 判为会话异常，不能仅凭退出码 `0` 认定成功 |
| 任意消息状态 | 被信号等异常终止，未正常返回退出码 | 判为会话异常，不能仅凭已收到的消息认定成功 |

符合命令契约包含 `submit` 成功结果携带明确的 `body.needs_run` 布尔值。消息异常和进程异常不表示已提交业务结果被撤销；持久化结果仍按失败与恢复规则处理。异常后的输入重送与后续启动责任须另行约定。

### `run` 会话结束结果

`succeeded` 表示 camctl 按规则完成本次会话职责并正常收尾。计划受理、动作执行及产物处理的业务结果通过状态报告交给客户端。

适用于裸 `run` 和带计划路径的 `run`：

| 会话结束情况 | 本次会话中的业务失败 | 向主程序表达的结果 |
| --- | --- | --- |
| 按规则完成职责并正常收尾 | 无 | `succeeded` |
| 按规则完成职责并正常收尾 | 有，例如新计划被拒绝、动作失败或过期 | `succeeded`；具体业务结果进入状态报告 |
| 因会话级错误无法正常完成，并能够返回错误结果 | 有或无 | `error` |
| 进程被突然终止，未能返回最终结果 | 未必能完成判断 | 不能保证存在最终 stdout 消息；由主程序观察进程终止 |

会话级错误包括状态库不可用、时钟异常等影响本次会话正常完成的情况。时钟异常下即使完成了允许的有限安全收场，本次 `run` 仍返回时钟异常结果，具体执行资格见[调度与设备执行](scheduling-execution.md)。

业务失败本身不决定会话失败。会话仍须履行适用的状态记录、恢复、调度和报告职责；只有这些职责按规则完成，才满足正常收尾条件。各类基础设施错误及其恢复、退出规则须在本专题后续细化。

### `submit` 会话结束结果

`submit` 的职责是完成本次输入处理、持久化及接管判断。正常完成这些职责后返回 `succeeded`，并在 `body.needs_run` 中明确提供本次判定的布尔值。它不表示计划一定被受理，也不表示动作执行或报告文件发布已经完成。

| 会话处理情况 | 计划或 ACK 的业务错误 | 向主程序表达的结果 |
| --- | --- | --- |
| 输入处理及接管判断完成，事务提交成功，正常结束 | 无 | `succeeded`，携带 `needs_run` |
| 输入处理及接管判断完成，事务提交成功，正常结束 | 有，包括计划拒绝、ACK 无效或二者同时发生 | `succeeded`，携带 `needs_run`；业务错误已保存，后续通过状态报告表达 |
| 数据库、锁操作等会话级错误使职责无法完成，且能够返回结果 | 有或无 | `error`，不提供成功的接管判定 |
| 进程突然终止，未能返回最终结果 | 未必能完成判断 | 不能保证存在最终 stdout 消息；由主程序观察进程终止 |

`needs_run` 的值统一按会话接管协议计算。只产生业务错误报告责任时，也要判断由当前接纳者承担还是请求后续 `run`；不能因计划被拒绝而省略交接。

`submit` 不等待动作执行或报告发布。它正常结束前须可靠保存应报告的业务结果，并完成相应责任的交接判断；状态保存失败或提交结果不确定时遵守会话错误及恢复规则。

### `needs_run`

`needs_run: true` 表示：

> 本次提交需要一个后续 `run` 驱动。

它不要求发送此消息时旧 `run` 已经退出。

主程序应维护一个“后续需要启动 run”的本地事实：

```text
收到 needs_run
    │
    ├── 当前无 run → 启动裸 run
    │
    └── 当前 run 尚未退出
            ↓
         记录 pending-start
            ↓
         当前 run 退出后启动一次裸 run
```

多个 `needs_run` 可以合并为一次后续启动。

`run` 正常退出且没有 pending-start 时，主程序不应无条件再次启动 `run`。

### `run` 生命周期

`run` 是当前主机供电窗口内的持续调度执行器。

其结束情况包括：

```text
主机突然断电
    → 进程在任意状态下被直接终止

当前已经没有需要继续驱动的计划工作
    → run 可以主动进入收尾并正常退出

发生影响会话正常完成的会话级错误
    → 按对应错误的处理规则退出，并在能够返回结果时报告 error
```

只要仍然存在尚未完成、未来仍可能需要当前 `run` 驱动的计划工作，`run` 可以持续存活并等待。例如，未来 `scheduled_at` 的 `pending` action 本身就是未完成计划工作，不要求为了缩短进程生命周期而提前退出并另建定时唤醒机制。

第一版的[MCU 接口预留](mcu-actions.md#第一版范围)不建立串口连接，也不产生需要会话继续驱动的 MCU 工作。

运行中的 `run` 不是启动时计划集合的静态快照。只要尚未进入最终收尾阶段，它必须持续接纳后来通过 `submit` 成功受理的新计划，并将这些计划纳入同一进程的调度集合。

`possibly_recording` 等残留 `device_fact` 是持久化设备事实，不等同于待执行工作。如果所有计划工作已经结束，且当前没有安全且必要的主动收场责任，仅存在这类未解决残留事实时，不阻止 `run` 正常退出。

正常退出必须经过本专题“会话接管协议”的最终检查。新工作在该检查前成功提交时由接纳者负责；在接纳关闭后成功提交且仍需驱动时，由 `needs_run` 请求后续会话。

## 会话接管协议

### 责任与依据

成功提交后仍需驱动的本地工作，必须由当前接纳者承担，或通过 `needs_run: true` 请求后续会话。请求受理、接纳资格观察与正常关闭接纳使用同一 SQLite 数据库的写事务确定先后顺序；协调全部由 camctl 完成。

SQLite 同时只允许一个写事务。协议使用 `BEGIN IMMEDIATE` 在检查状态前取得写事务资格，避免先读旧快照再尝试升级事务。事务忙等待及失败必须有有限预算，具体配置待细化。[SQLite 事务文档](https://sqlite.org/lang_transaction.html)

### 两把锁及生命周期

同一状态库的所有 `run/submit` 入口使用同一对稳定锁文件。锁文件的存在只提供锁定对象；实际资格由内核锁持有情况表达。锁文件在正常运行和清理期间保持稳定，不通过删除重建来释放锁。

| 锁 | 持有者与持有期 | 责任 |
| --- | --- | --- |
| 会话锁 | `run` 在初始化前取得，覆盖初始化、接纳、收尾，直到退出清理 | 同一状态库最多一个执行会话 |
| 接纳锁 | `run` 在能够承担普通调度责任时取得，持有至关闭接纳 | 承诺检查并驱动接纳期间成功提交的工作 |

两把锁采用 Linux `flock` 排他锁。接纳锁的操作均使用非阻塞方式，只有真正的锁冲突才表示已有持有者；其他错误单独报告。所有相关句柄关闭后内核释放锁，因此句柄必须由所属 CLI 进程独立持有，不得传给 `adb`、`ffmpeg` 等子进程。[Linux `flock` 文档](https://man7.org/linux/man-pages/man2/flock.2.html)

其他交接事务可观察到的阶段如下；取得和释放接纳锁的事务内部步骤按后文顺序执行。

| `run` 阶段 | 会话锁 | 接纳锁 | 提交能否据此认定存在接纳者 |
| --- | --- | --- | --- |
| 初始化，尚未获得普通执行资格 | 持有 | 未持有 | 否 |
| 接纳并驱动工作 | 持有 | 持有 | 是 |
| 最终收尾 | 持有 | 已释放 | 否 |
| 受限收场或错误退出处理 | 持有至清理 | 不持有普通接纳资格 | 否 |
| 已结束且句柄已关闭 | 释放 | 释放 | 否 |

时钟异常期间，未填写 `scheduled_at` 的取消动作按[时钟异常期间的取消](scheduling-execution.md#时钟异常期间的取消)执行。受限会话不持有普通接纳资格，不能据其可处理取消推断它能够承担普通调度工作。

正常 `run` 在短写事务内取得接纳锁，并在成功结束该事务后进入接纳阶段。该会话承诺检查状态库中的全部待驱动工作，包括初始化期间已经提交的工作。数据库事务之外可以持续持有接纳锁；同一会话正常关闭接纳后直接完成收尾。

### 待驱动工作的判定

`needs_run` 与正常退出检查都依据持久化工作和本地处理责任。下面的各类条件可以并存，任一类存在待处理责任即需要继续驱动；不能根据内存队列暂时为空或 `plan_seq` 未变化认定全部完成。

| 状态 | 是否构成待驱动工作 |
| --- | --- |
| 尚未完成的动作，包括未来 `scheduled_at` 的 `pending` 动作 | 是 |
| 仍应继续执行或恢复的有限设备收场、产物处理或交付流程 | 是，由对应专题定义具体责任 |
| 应报告的业务变化尚未完成本地报告职责，包括受理拒绝及 ACK 校验错误 | 是 |
| 仅存在已结束动作留下的残留设备事实，且当前没有安全且必要的主动收场责任 | 否；该事实自身新增的报告责任另行判断 |
| 本地报告职责已完成，仅等待主程序发送或客户端 ACK | 否；补投按报告机会触发 |
| 工作是否完成无法可靠判断 | 不能判定为无工作，进入相应错误处理 |

报告责任的权威定义见[状态报告与累计确认](status-reports.md)。接管检查只读取持久化记录以及本次报告机会的处理结果；报告生成、文件操作和设备调用均在短写事务之外执行。重复提交、ACK 更新和受理拒绝也必须按实际产生或仍存在的责任判定，不能仅按“是否创建新 plan”判定。

有效 ACK 的报告影响由[ACK 与业务变化](status-reports.md#ack-与业务变化)定义。若本次处理仅吸收有效 ACK，且处理后没有其他待驱动责任，则 `needs_run: false`；若仍有其他责任，继续按接纳锁和工作状态判断。有效 ACK 本身不阻止 `run` 正常关闭接纳。

### `submit` 的事务顺序

1. 在事务外读取并解析计划文件，检查 `request_id`。依赖已受理请求、ACK 和其他持久化状态的判断留在事务内；事务内的已受理关联决定复用或首次受理，只有首次受理需要校验正文。
2. 开启短写事务，按“计划正文与 ACK 独立处理”追加本次状态变化的历史并同步更新投影，再依据更新后的状态判定提交后是否存在待驱动工作。受理拒绝及 ACK 校验错误也属于应保存的业务结果；具体记录身份由报告专题定义。
3. 有待驱动工作时，尝试以非阻塞方式取得接纳锁。如果成功，说明当前没有接纳者；立即释放本次探测取得的锁。如果发生锁冲突，说明有 `run` 持有接纳资格。
4. 保存本次 `needs_run` 判定并提交数据库事务。判定是本次响应数据，不要求新增持久化会话登记表。提交成功后才输出成功响应。

只有 `run` 可以在写事务结束后继续持有接纳锁。所有提交探测都受同一数据库写事务串行约束，且临时锁在事务结束前释放，所以一个 `submit` 不会把另一个 `submit` 的探测误认成接纳者。`submit` 不取得会话锁。

| 事务及工作判定 | 待驱动工作 | 接纳锁观察 | 结果 |
| --- | --- | --- | --- |
| 可靠且提交成功 | 无 | 无需探测 | `needs_run: false` |
| 可靠且提交成功 | 有 | 锁冲突，存在接纳者 | `needs_run: false` |
| 可靠且提交成功 | 有 | 临时取得并成功释放，无接纳者 | `needs_run: true` |
| 状态判断、锁操作或事务提交失败，或结果不确定 | 任意 | 任意 | 会话错误，不输出成功的接管判定 |

接纳观察表达事务内该判定时点的责任。随后发生的进程启动、错误或突然终止，按对应生命周期规则处理。

### `run` 正常关闭接纳

1. 在接纳阶段完成已有动作及本次应执行的报告工作。设备操作、报告构建和文件发布不占用交接写事务。
2. 开启短写事务，基于当前持久化状态重新检查待驱动工作。必须检查初始化或上次调度检查之后的提交，以及报告生成期间出现的业务变化。
3. 仍有待驱动工作时，结束事务，保持接纳锁并继续驱动；工作完成后再次检查。
4. 确认没有待驱动工作时，在写事务结束前释放接纳锁。此后当前会话完成资源清理和最终结果输出，继续持有会话锁至退出清理。

正常释放接纳锁是关闭接纳的边界。释放之后即使数据库事务结束或资源清理失败，该会话也保持关闭接纳并按错误路径退出；下一次会话重新建立接纳资格。

`run` 先取得会话锁，再开启交接写事务；事务内只进行非阻塞接纳锁操作，不等待会话锁、设备操作或其他长任务。接纳锁正常取得、提交探测及正常释放都必须遵守同一事务顺序。

| 竞争顺序 | 当前会话行为 | 提交结果 |
| --- | --- | --- |
| 提交事务先结束，接纳者随后检查退出条件 | 看到待驱动工作则继续；若已经处理完则可以正常收尾 | 有接纳者时返回 `false` |
| 关闭接纳的事务先结束，随后提交仍需驱动的工作 | 旧会话保持收尾 | 没有其他接纳者时返回 `true` |
| 多个 `submit` 并发 | 各写事务依次执行，探测期间互不误认 | 每次按自己的事务状态判定；多个 `true` 由主程序合并 |

### 失败与恢复边界

进程突然终止会释放其锁句柄；内核锁与数据库事务不组成跨资源的原子提交。上述顺序保证正常受理和正常收尾之间的交接，异常情况下以持久化提交结果和下一次实际启动的 `run` 进行恢复。

| 中断位置或错误 | 处理与恢复要求 |
| --- | --- |
| 提交事务尚未成功 | 不报告提交成功；事务回滚后的状态由后续请求按幂等规则重新判断 |
| 数据库提交结果不确定 | 报告会话错误；不得自行断言请求不存在，后续重试按持久化请求记录判定 |
| 提交成功，但进程在返回响应前终止 | 已提交的请求及业务结果保留，后续实际启动的 `run` 可以发现；客户端未获确认时按重送规则处理，已受理 ID 复用原计划 |
| 观察到接纳者后，该 `run` 崩溃或进入会话级错误退出 | 已提交工作保留；不承诺依赖该接纳者继续执行，等待后续实际启动的 `run` |
| `run` 关闭接纳后，在最终退出前终止 | 接纳资格保持关闭；后续提交按锁的实际状态判断 |
| 锁探测发生非冲突错误，或临时锁释放失败 | 保留诊断信息并终止成功判定；不得当作存在或不存在接纳者 |

异常退出清理可以释放接纳锁，即使数据库已无法开启事务。该路径表示会话失去履职能力，结果按会话错误处理；正常收尾仍必须经过事务内的最终工作检查。

主程序有限重启能力仍是待外部确认的建议，本协议不以该能力为前提。主机再次上电后的首次启动规则继续提供已确认的恢复入口。

## 执行计划

### 整份校验与原子受理

一份计划的全部动作通过静态校验后，才能首次受理。任一动作的类型、参数或引用格式不合法，都拒绝整份计划；校验过程中不注册已经检查通过的部分动作。

可执行动作由本版已实现能力确定；MCU 预留动作的受理规则见[计划中的 MCU 动作](mcu-actions.md#计划中的-mcu-动作)。

取回动作使用[本计划内的产物引用](outputs.md#本计划内的产物引用)时，首次受理须在完整动作集合中解析名称；目标缺失或引用不合法时拒绝整份计划。解析所得关联与计划及全部动作在同一事务保存，不能先受理计划再补建局部引用关系。

首次受理成功时，计划实例、全部动作实例、请求与实例的关联，以及新计划受理序列的推进，其历史和投影在同一数据库事务中提交。历史回放也必须整体呈现这次受理。受理过程不产生设备副作用。该规则同时适用于 `run <plan-path>` 和 `submit <plan-path>`。

| 首次受理的处理情况 | 计划与动作实例结果 | 对外表达 |
| --- | --- | --- |
| 整份静态校验通过，注册事务提交成功 | 一个完整计划及其全部动作实例 | 计划受理成功，执行由后续调度资格决定 |
| 解析或任一静态校验失败 | 不注册本次计划和动作实例，不推进新计划受理序列 | 记录整份计划被拒绝的业务结果 |
| 静态校验通过，注册事务失败且已确认回滚 | 不保留部分计划或动作实例，不推进新计划受理序列 | 会话级错误 |
| 注册事务的提交结果不确定 | 不向调用方断言已受理或未受理；后续依据数据库中的完整注册结果判断 | 会话级错误，重试遵守请求幂等规则 |

已受理请求按本专题的请求幂等规则复用，不重新创建实例。拒绝记录属于面向客户端的业务结果，可以在没有新计划实例时存在；已有计划及其动作保持原有执行意图。

整份受理约束计划进入状态库的方式。计划进入执行阶段后，各动作仍按自身条件独立执行，某个动作失败不自动阻止其他动作。

本节定义计划正文与动作实例的受理原子性。`last_report_id` 单独校验，其业务校验结果按“计划正文与 ACK 独立处理”组合，不属于使整份计划正文校验失败的条件。

### 基本结构

动作的 `scheduled_at` 必填性及省略后的执行含义见[调度与时间语义](scheduling-execution.md#scheduled_at)。

示例：

```json
{
  "request_id": "req-20260910-001",
  "created_at": "2026-09-10 15:00:00",
  "name": "夜间采集-01",
  "last_report_id": 42,
  "actions": [
    {
      "name": "主录像",
      "type": "camera_record",
      "device_id": "cam0",
      "group": "采样-1",
      "scheduled_at": "2026-09-10 16:00:00",
      "params": {
        "duration_s": 60,
        "record": {}
      },
      "policy": {
        "max_delay_ms": 5000
      }
    }
  ]
}
```

### `request_id`

`request_id` 由调用方生成。

首次成功受理：

```text
request_id
    ↓
plan_instance_id
    ↓
action_instance_ids
```

之后永久保留该关联。同一 ID 永远以首次成功受理的内容为准；后续提交直接复用原计划，忽略本次正文。复用不改变原计划内容、实例身份或执行进度，也不因本次重试新增动作、交付或设备操作；原计划尚未完成的工作仍按现有状态继续驱动。

输入处理按以下顺序分类；数据库查询及首次注册在受理写事务中完成。

| 输入与持久化状态 | 本次正文 | 计划处理结果 |
| --- | --- | --- |
| 整份 JSON 无法解析 | 无法取得 | 拒绝输入，不能据其中的片段认定请求身份 |
| JSON 可解析，但 `request_id` 缺失或不合法 | 任意 | 拒绝计划输入 |
| 有效 ID，已受理关联查询失败或结果无法确认 | 任意 | 会话错误，不能当作首次受理 |
| 有效 ID，已有成功受理关联 | 任意，包括变化、字段缺省或动作参数不合法 | 复用首次受理的计划，本次正文不参与静态校验 |
| 有效 ID，没有成功受理关联 | 整份静态校验通过 | 原子注册新计划及全部动作 |
| 有效 ID，没有成功受理关联 | 静态校验失败 | 拒绝本次计划，不建立成功受理关联 |

此前被拒绝且尚未成功受理的 ID，后续仍按未受理 ID 处理。原计划完成或退役后，同一 ID 仍关联原计划；表达新的执行意图应使用新的 ID，即使动作内容与历史完全相同。

并发提交相同 ID 时，以首个成功提交受理事务的内容为准；后续事务读取该关联并复用。尚未提交或已回滚的注册不构成首次成功受理。提交结果不确定时，遵守失败与恢复规则。

### 客户端确认与重送

客户端保留待确认请求的 `request_id` 和原计划内容，通过状态报告确认受理结果。确认依据由[状态报告与累计确认](status-reports.md#客户端对受理结果的判断)定义；未收到报告或报告中没有该请求，只表示尚未确认。

请求尚未确认时，由客户端按重试策略使用相同 `request_id` 和原计划内容重送，主程序按普通输入中转。重送不要求先证明上一次未受理：camctl 已有成功受理关联时复用原计划，没有关联时按首次受理处理。`last_report_id` 仍可按独立 ACK 规则更新。

收到已受理证据后，该请求结束受理确认等待；后续执行状态继续通过报告获取。收到能关联到本次输入的明确拒绝结果后，按已知业务错误处理，不再将该次输入视为结果未知。明确拒绝只描述对应输入，不表示该 ID 永久无法受理。

受理确认等待与动作完成等待分别处理。原计划已经受理但仍未执行完，不属于受理结果未知。客户端的重试间隔、次数预算及停止条件仍需细化。

### 重试中的 `last_report_id`

`last_report_id` 在每次输入中独立处理，包括已受理 ID 的重试。有效 ACK 可以单调推进累计确认位置；较旧 ACK 或字段缺省保持确认位置。ACK 的业务错误不改变计划复用结果。

### 计划正文与 ACK 独立处理

`run <plan-path>` 与 `submit <plan-path>` 使用相同规则。计划正文不包含 `last_report_id`；计划按请求 ID 复用或首次受理，与 ACK 的有效性判断分别进行。任何一方的业务输入错误都不阻止处理另一方。

输入能够解析并分别判断请求与 ACK 时，按下表处理。计划“可受理”包含首次完整注册及已受理 ID 的幂等复用；“拒绝”包含请求 ID 不合法及未受理 ID 的正文静态校验失败。计划处理的具体分区由 `request_id` 决策表定义。

| 计划处理判定 | ACK 状态 | 计划处理 | 累计确认与错误记录 |
| --- | --- | --- | --- |
| 可受理 | 有效 | 完整注册或幂等复用 | 按单调规则吸收 ACK |
| 可受理 | 无效 | 完整注册或幂等复用 | 保持确认位置，记录 ACK 校验错误 |
| 可受理 | 未提供 | 完整注册或幂等复用 | 保持确认位置 |
| 拒绝 | 有效 | 保存拒绝结果 | 按单调规则吸收 ACK |
| 拒绝 | 无效 | 保存拒绝结果 | 保持确认位置，同时记录 ACK 校验错误 |
| 拒绝 | 未提供 | 保存拒绝结果 | 保持确认位置 |

有效 ACK 对应的确认位置等于或早于当前确认位置时，吸收结果为保持不变，不因此产生错误。报告查询和未知 ID 的判定由[ACK 引用的报告记录](status-reports.md#ack-引用的报告记录)定义，报告覆盖含义由同一专题定义。

整份 JSON 无法解析时，不能从中受理计划或吸收 ACK，保存输入拒绝结果。已解析但无法按公共结构提取字段的输入，须依据公共字段契约判定；不能把无法判定的 ACK 静默解释为未提供。公共结构及字段的具体合法范围仍需细化。

独立处理指业务校验结果互不阻断，不改变本专题的数据库事务边界。计划处理结果、有效 ACK 更新及应保存的错误记录仍在本次受理事务中提交；状态库不可用、写入失败或提交结果不确定属于会话错误，遵守失败与恢复规则。

幂等复用不创建新计划或动作实例，也不推进 `plan_seq`；有效 ACK 和 ACK 校验错误仍按表处理。计划拒绝与 ACK 校验错误通过状态报告交给客户端，主程序无需理解这两类业务结果。`needs_run` 继续依据处理后实际存在的工作和报告责任判定。

### 名称和实例 ID

调用方提供：

- `request_id`
- plan `name`
- action `name`
- `group`

CLI 分配：

- `plan_instance_id`
- `action_instance_id`
- `output_id`
- `delivery_id`
- `report_id`

plan/action `name` 是人类可读标签。

CLI 分配的实例 ID 是机器身份，不要求调用方解析格式。

### group

`group` 是轻量集合标签。

同一计划允许：

```text
action A → group = 采样-1
action B → group = 采样-1
```

第一版中，允许归组的 action 最多属于一个 group；`obtain_action_outputs` 不允许属于任何 group，其动作公共字段中必须省略表示自身归组的 `group`。

动作自身的归组与操作参数中的目标组分别判断。取回动作可以引用某个 group 的产物，但该引用不会使取回动作成为该组成员。首次受理时，归组校验按下表处理；表中的 `group` 专指动作公共字段，不包含取回或取消参数中的目标组：

| 动作类型 | 自身归组的 `group` 字段 | 处理 |
| --- | --- | --- |
| `obtain_action_outputs` | 未提供 | 符合归组约束，取回来源引用另行校验 |
| `obtain_action_outputs` | 已提供，无论字段值 | 静态校验失败，拒绝整份计划 |
| 其他本版支持的动作 | 未提供 | 动作不属于任何组 |
| 其他本版支持的动作 | 提供合法组名 | 动作属于本计划内该组 |
| 其他本版支持的动作 | 提供不合法值 | 静态校验失败，拒绝整份计划 |

该校验同时适用于两个计划输入入口，不通过忽略归组字段或移除违规动作来受理部分计划。已受理 `request_id` 的重试仍直接复用原计划，不校验本次被忽略的正文。

group：

- 不参与调度；
- 没有独立状态机；
- 没有成功/失败语义；
- 不创建动作依赖；
- 可以作为取回范围；
- 可以作为取消范围；
- 用于报告组织。

`action name` 在同一计划内保持唯一。

`group` 不要求唯一。

按组取回先按动作类型[筛选产物来源](outputs.md#按组取回的成员筛选)，不等待非产物动作，也不将其列为无产物失败；组取消及报告组织仍使用原组成员。录像来源分别准备文件，发布条件见[组内录像分别准备与统一发布](outputs.md#组内录像分别准备与统一发布)。

取回可以直接用本计划内的动作名称或组名表达来源，首次受理时由 camctl 关联到实例；具体寻址规则见[本计划内的产物引用](outputs.md#本计划内的产物引用)。该方式不要求客户端预先取得本次新计划的实例 ID。

## 取消目标寻址

`cancel_task` 可以按：

- `request_id`（计划级）；
- `plan_instance_id`；
- `action_instance_id`；
- `(plan_instance_id, group)`

寻址。

寻址结果限定本次取消的范围：计划级目标对应该计划内的动作，动作级目标只对应指定动作，group 目标只对应指定计划内该组的动作。不会因设备共用、时钟异常或目标查询失败扩展到其他计划和动作；执行及设备收场遵守[普通动作取消](scheduling-execution.md#普通动作取消)。

取回动作不属于任何 group；取消某组不会自动取消引用该组的取回动作。取消取回须指定该取回动作，或取消包含它的整个计划；仍有效的取回按来源动作的最终状态及正式产物继续处理。

### request_id 取消

允许客户端在尚未收到状态报告、还不知道 `plan_instance_id` 时：

> 使用原计划的 `request_id` 取消整个计划。

承载该 `cancel_task` 的计划自身拥有新的 `request_id`。

不能修改原计划正文来表达取消。

### 只取消已知计划

取消动作实际执行时查询目标。

目标不存在：

```text
target_not_found
```

本次取消结束。

本次结果只针对执行时已知的目标。目标以后首次提交仍可正常受理。

同一个取消请求 ID 的重试复用原取消结果。

如果目标后来出现并且客户端仍希望取消：

> 使用新的取消请求 ID 再次提交取消。

## 新计划受理序列

首次成功受理新计划时分配单调递增的 `plan_seq`。同一 `request_id` 的幂等重试不推进该序列。状态库提供轻量读取的 `latest_plan_seq`。这两个名称为候选，见 U8。序列推进须与新计划成功受理保持一致。

该序列定义受理顺序；[调度与设备执行](scheduling-execution.md)据此发现新计划。业务变化报告使用的 `change_seq` 由[状态报告与累计确认](status-reports.md)定义。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

请求/计划投影包含：`request_id`、`plan_instance_id`、`plan_seq`、首次成功受理的结构化计划字段及动作参数、`created_at`、`name`、计划状态。首次受理历史保存足以重建该计划语义的结构化数据；后续状态变化追加历史并同步更新投影。输入 JSON 文件由主程序管理，计划恢复和 JSON 重建依据数据库中的已受理数据。数据保留遵守[全局规则](../2026-09-08-camctl-cli-design.md#持久化与配置基础)，计划退役后仍保留请求、计划、动作及其历史关联。

受理序列投影提供 `latest_plan_seq`。待驱动工作依据对应业务投影和报告处理事实判定，实际接纳资格由本专题的内核锁协议表达，不能从历史回放中取得。

## 验收要求

### 单元测试

隔离状态存储和会话协作者，验证公共输入、请求幂等判断、group 约束、取消寻址与进程响应的行为分支。

首次受理的计划校验覆盖全部动作合法，以及非法动作位于首部、中间和末尾的情况；分别验证非法类型、参数和引用格式导致整份拒绝。单元测试验证拒绝结果及完整受理内容，不以内部校验函数的调用顺序作为预期。

按 group 归组表覆盖动作类型与字段有无、合法性的组合。取回动作自身填写 `group` 时拒绝整份计划，包括空值及与目标组不同名的情况；自身未归组而在来源参数中引用组时正常校验。已受理 ID 的重试正文即使包含违规归组，也只复用原计划。组取消只选择组成员，不自动选择引用该组的取回动作。

按请求 ID 与“计划正文与 ACK 独立处理”的决策表推导用例；计划分别覆盖首次受理、幂等复用、请求 ID 错误和首次正文静态拒绝，ACK 分别覆盖有效推进、有效但不推进、无效和未提供。已受理 ID 的重试覆盖正文变化、字段缺省及非法动作参数，均复用原计划；原计划分别处于未完成、已完成及退役状态。另行覆盖整份 JSON 无法解析，验证不会受理计划或吸收 ACK。

`submit` 结束结果按会话完成情况与业务错误分别分类。正常完成时覆盖业务错误有无及 `needs_run` 的两个布尔值，验证响应携带实际接管判定；状态保存、锁操作失败及提交结果不确定时验证返回会话错误，不给出成功的接管判定。

结果序列化验证单行 JSON 和换行边界、协议字段及特殊字符转义；日志文案不作逐字断言。错误结果精确验证 `reason` 和 `details` 的结构与机器标识，覆盖空上下文及主程序未知的错误标识。最终结果判定按“stdout 与退出状态”决策表覆盖，包括 `submit` 成功消息缺少 `needs_run`，以及 `error` 配合退出码 `0`、`1` 和其他退出码的情况。

### 集成测试

组合真实 SQLite、独立 `run/submit` 进程与主程序启动逻辑，验证并发受理、收尾交接、重复提交和 pending-start（待启动标记）。涉及进程生命周期的验证归集成测试。

通过真实子进程管道验证最终 JSON、stderr 诊断与退出状态的配合，覆盖成功、已处理的业务错误、会话级错误、输出截断和异常终止。正常完成时精确断言退出码 `0`，主动报告会话错误时精确断言退出码 `1`。分段读取完整消息仍应正确判定；日志及设备工具输出不得混入 stdout，收到消息后仍须观察进程终止状态。

使用已有持久化任务与错误的新计划文件组合运行 `camctl run <plan-path>`，验证新计划被明确拒绝时，已有任务仍按正常资格规则获得驱动，原请求记录保持不变。覆盖 JSON 格式错误和未受理 ID 的正文静态校验失败。

使用真实 SQLite 验证首次受理时计划、全部动作、请求关联和受理序列的历史与投影一同提交。在部分历史追加或投影更新后中断或令事务失败，确认回滚后不存在部分注册结果；在提交后响应前中断，确认重试复用完整实例集合。两个计划输入入口均需覆盖。

两个入口分别提交含有归组取回动作的首次请求，验证整份拒绝、没有部分实例且受理序列不推进，报告能定位违规动作。再提交取回仅在来源参数中引用组的合法计划，验证固定组成员不包含该取回，重启后保持同一关联。取消来源组时取回不被自动取消；指定取回动作或其所属整份计划时，按取回取消规则处理。

分别回放受理前后及后续执行的已提交边界，验证完整计划与动作状态；重建当前投影应与正常提交得到的状态一致。组合幂等重试、ACK 和受理错误，验证历史顺序、`plan_seq` 与 `change_seq` 各自的职责。回放不能发送设备命令、执行文件操作、重新生成身份或取得会话接纳资格；历史缺失或不可可靠解释时须明确失败。

受理结果提交后由主程序删除输入文件，验证当前会话执行和后续裸 `run` 恢复仍使用持久化计划；camctl 的执行、恢复和清理流程遵守输入文件归主程序管理的责任边界。

两个计划输入入口均验证正文与 ACK 的独立业务结果及共同持久化：计划拒绝时有效 ACK 仍被吸收，无效 ACK 不阻止合法计划受理，双重错误均有报告记录；幂等复用不增加实例或推进 `plan_seq`，本次正文不改变原计划内容与执行进度。事务回滚不留下部分更新，提交结果不确定时按数据库事实恢复。

使用不同正文并发提交同一 ID，验证只有首个成功提交的完整计划被保存，后续提交复用该实例。覆盖先前输入被拒绝、注册事务回滚及提交后响应丢失，再次提交该 ID 的情况；已受理 ID 在两个入口间重试也遵守同一规则。

组合客户端待确认记录、主程序中转与真实状态库，分别在首次受理提交前和提交后中断 CLI。原输入文件随后被主程序删除，客户端未获确认时用同一 ID 和原计划内容重送，验证前者可首次受理、后者复用原实例，最终由状态报告确认。收到已受理但动作未完成的报告后，不再因等待动作完成而判定受理未知。

带计划启动后令时钟检查失败，验证受理结果已经提交、普通动作尚未执行；下一次时钟正常的 `run` 能发现同一计划及动作实例。覆盖首次受理、幂等复用、业务拒绝，以及受理提交后、时钟检查前进程中断的情况。

会话交接使用真实 SQLite、多进程和内核锁验证。以可控的同步点安排“提交在退出检查之前”“关闭接纳在提交之前”和“多个提交探测”的顺序，断言工作由当前会话处理或得到 `needs_run: true`，不依赖随机 sleep 碰撞竞态。验证初始化、接纳、收尾各阶段的锁生命周期，以及设备工具子进程不继承锁句柄。

在提交前、提交后响应前、探测接纳后、关闭接纳后终止相关进程，验证已提交状态与后续恢复。另行验证报告准备期间提交仅产生受理拒绝等业务变化时，`plan_seq` 未推进也不能漏掉报告责任。锁错误与提交结果不确定的分类可用受接口约束的替身验证；真实锁竞争和事务提交恢复归集成测试。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 请求幂等

- 同 `request_id` 重复提交不重新执行；
- 同 ID 以首次成功受理的正文为准，后续正文被忽略，原计划及执行进度保持不变；
- 同 ID 允许更新 ACK；
- 新 ID + 相同动作仍执行。

#### 整份计划受理

- 全部动作通过静态校验后才首次受理；
- 首次受理时任一动作静态校验失败，整份计划被拒绝，且不推进新计划受理序列；
- 计划、全部动作和请求关联在同一事务中提交；
- 注册事务回滚不留下部分实例，提交结果不确定时按持久化状态对账；
- 受理拒绝结果通过状态报告表达，已有计划及动作保持不变；
- 受理成功后，动作执行结果仍各自独立。

#### run / submit

- 每次上电均由主程序发起一次 `run`，覆盖无数据输入、有输入但无执行计划、有执行计划三个分区；
- 有执行计划时主程序先持久化文件，再通过 `camctl run <plan-path>` 传入；
- 带计划启动时，输入解析、请求 ID 或首次正文校验错误不阻断已有任务的恢复与执行；
- 新计划被拒绝的业务结果由 camctl 向客户端表达，主程序仅需处理会话控制结果与文件中转；
- 正常收尾的 `run` 返回 `succeeded`，覆盖无业务失败、新计划被拒绝、动作失败或过期等分区；
- `submit` 正常完成输入处理、持久化及接管判断后返回 `succeeded` 和明确的 `needs_run` 布尔值，覆盖计划拒绝、ACK 无效及二者同时发生；
- `submit` 仅产生业务错误时，错误记录持久化且报告责任得到接管判定；会话成功不依赖动作执行或报告文件发布完成；
- 会话级错误返回 `error`，即使会话中已有业务动作成功；时钟异常的有限收场完成后仍报告时钟异常；
- 进程突然终止时允许没有最终 stdout 消息，主程序通过进程终止事实发现异常；
- submit 不要求可信墙钟；
- 带计划 `run` 在取得会话锁、验证状态库后先完成受理，再检查墙钟；
- 时钟检查失败不撤销受理结果，且不会据异常墙钟把新受理动作判为过期；
- 受理阶段未校验的本机时间不能推进可信历史时间下界；
- `needs_run` 与旧 run 收尾竞态；
- 主程序 pending-start 模拟；
- `run` 可以跨整个主机供电窗口持续运行；
- 所有需要驱动的计划工作完成后 `run` 可以主动正常退出；
- 未来 `pending` action 阻止 `run` 因“当前无立即工作”而提前退出；
- 运行中的 `run` 持续吸收后续 `submit` 成功受理的新计划；
- 只剩 `possibly_recording` 等残留 `device_fact` 时允许正常退出。

#### group

- 多动作共享 group；
- 取回动作自身不能归组，首次受理违规时整份拒绝；来源参数仍可引用组；
- group 取回；
- group 取消只影响成员，不自动取消引用该组的取回动作；
- group 不影响调度。

```text
plan_seq
latest_plan_seq
last_seen_plan_seq
```

### 后续契约完善

补齐计划公共字段的必填性、合法范围、时间字面量，以及动作类型入口与各专题的引用。统一定义各会话级错误的 `reason`、对应 `details` 字段和处理规则，以及主程序对显式错误和非预期进程终止的后续启动责任。计划状态与退役条件尚需定义。

会话接管机制已由本专题定义。实施前还需结合各业务专题细化待驱动工作查询、报告本地职责的完成证据、事务等待预算、输入计划文件的读取保障和读取失败语义，以及客户端重试间隔、次数预算和停止条件；这些内容不能以测试中假定“有工作/无工作”代替实际端到端契约。

### 主程序有限重启建议

状态：待用户与主程序负责人沟通确认。该能力属于对接建议，当前规格不以其获得接受或已经实现为前提。

建议场景：主机仍有电，但 camctl 在返回最终会话结果前崩溃或被系统终止。

建议行为：主程序确认原进程已退出后，按固定间隔、有限次数重新启动裸 `camctl run`，使已持久化任务在当前供电窗口内获得恢复机会。重启次数和间隔建议可配置，具体数值及计数范围待双方确认。

| 运行条件 | 当前可以依赖的恢复入口 |
| --- | --- |
| 主机再次上电 | 主程序按“主机上电后的首次启动”规则发起 `run` |
| 主机仍有电，camctl 非预期退出，有限重启能力尚未确认 | 保留持久化恢复依据，等待下一次实际发起的 `run`；不承诺同一供电窗口内自动恢复 |
| 主机仍有电，双方确认并实现有限重启能力 | 按约定的次数和间隔尝试启动裸 `run`；预算耗尽后的处理须另行约定 |

对 camctl 已明确返回 `error` 的情况，重启资格和处理方式仍需按会话级错误分类细化。本建议不定义主程序收到 `error` 后的统一重启行为。
