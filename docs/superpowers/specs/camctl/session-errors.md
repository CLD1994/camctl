# 会话错误与恢复边界

[返回设计总览](../2026-09-08-camctl-cli-design.md) · [请求受理与会话](protocol-session.md)

本专题定义 `run` / `submit` 无法完成会话职责时的错误分类、诊断字段及恢复边界。最终 stdout 的格式、退出码、`needs_run` 和锁交接协议由[请求受理与会话](protocol-session.md#stdout-与退出状态)定义。客户端消费的计划、动作、取回失败项等业务错误继续由相应业务专题定义。

## 业务失败与会话失败

错误分类依据失败的职责及其实际结果，不仅依据底层异常类型。例如，同样是空间不足，视频拷贝失败与状态报告无法落盘承担不同的责任。

| 失败位置与结果 | 会话如何处理 | 正常结束的条件或错误分类 |
| --- | --- | --- |
| 输入计划文件无法读取、JSON 无法解析或计划被拒绝 | 保存本次输入失败，继续承担已有工作及报告责任 | 这些职责完成时仍为 `succeeded`；`submit` 还须提供可靠的 `needs_run` |
| 已支持动作自身参数错误 | 保存该动作的初始 `failed`，其他动作继续处理 | 业务错误已处理且会话职责完成时为 `succeeded` |
| 设备命令、文件取回或显式清理按自身规则最终失败 | 保存对应动作、产物或交付结果，继续其他适用工作 | 业务结果与必要报告可靠保存、正常收尾后为 `succeeded` |
| 保存上述业务结果时，状态库操作失败或事务结果未知 | 无法完成状态持久化职责 | `state_db_error`，不能用原业务错误掩盖保存失败 |
| 生成、写入、同步、发布或核对必要报告文件失败 | 无法完成本次报告的本地职责 | 已知报告处理错误为 `report_error`；底层状态库失败按 `state_db_error` |
| 所有动作已经终态，但必要报告处理仍失败 | 会话职责仍未完成 | 按实际会话错误返回，不能仅凭计划完成返回成功 |
| 取回半成品清理允许延后，且待清理事实及报告均可靠保存 | 按已确认的延后清理规则处理 | 其他职责完成时可以正常结束，不单独升级为会话错误 |

`submit` 只处理输入、持久化和责任交接；它不执行设备动作、不进行墙钟可信性检查，也不生成或发布报告文件。向后续 `run` 交接了报告责任不等于报告已经发布。

## 错误标识

下表是本版会话 `body.reason` 的权威清单。已知错误按失败的责任边界映射，不把操作系统或数据库的原始异常名称直接用作顶层 `reason`。

| `reason` | 适用入口 | 触发条件 | 后续实际启动的处理依据 |
| --- | --- | --- | --- |
| `invocation_error` | `run`、`submit` | CLI 调用本身不符合入口契约，例如 `submit` 缺少计划路径；不包括计划文件内容错误 | 修正调用；不据此假定某个请求已经受理 |
| `configuration_error` | `run`、`submit` | 当前入口必需的本地配置无法读取、解析或不合法，无法建立所需运行条件 | 修正配置，再从现有状态库开始；执行计划中的动作参数错误按业务规则处理 |
| `lock_error` | `run`、`submit` | 所需锁文件打开、加锁、解锁或句柄管理失败，无法可靠建立或释放协议要求的资格 | 核实实际内核锁及存储条件；锁文件存在或历史记录不能代替实际锁资格 |
| `state_db_error` | `run`、`submit` | 状态库打开、校验、查询、历史解释、事务提交失败，或提交结果无法确认；事务忙等待的既定有限预算耗尽也属于此类 | 状态库可可靠访问后，根据实际已提交历史核实和恢复；不自动重建空库替代现有历史 |
| `clock_invalid` | 仅 `run` | 已取得所需可信历史依据，墙钟检查及适用复检仍不满足可信性规则 | 完成本次允许的有限安全收场；后续正常 `run` 再按时间、设备及原动作状态判断执行资格 |
| `report_error` | 仅 `run` | 必要报告的构建或文件操作发生已知失败，或文件处理结果无法可靠确认 | 按已登记报告、冻结依据、实际文件及累计 ACK 恢复本地报告职责 |
| `internal_error` | `run`、`submit` | 未被上述已知失败规则覆盖的程序内部异常，使会话无法继续；进程仍能进入错误处理并输出最终结果 | 保留诊断，修正问题后依据持久化状态恢复；不据此重置动作、预算或请求身份 |

本地配置文件不存在是合法缺省情况，使用内置默认值，不属于 `configuration_error`。文件读取故障、格式或覆盖值错误仍按[配置加载规则](scheduling-execution.md#本地配置的加载与更新)处理；空设备目录不等于配置加载失败，新计划的设备适用性由动作受理校验判断。

接纳锁探测中的正常锁冲突表示已有接纳者，是 `submit` 计算 `needs_run` 的合法分支，不是 `lock_error`。`run` 尚未取得会话锁时不得开展受理或设备工作；会话锁被另一合法会话持有时的等待方式及有限预算仍由锁获取契约细化，不用文件存在检测代替。

读取可信历史时间下界失败属于 `state_db_error`，不表示已经证明时钟异常。报告文件已移入 `ready`，但保存发布记录失败时，属于 `state_db_error`，并保留已确认的文件操作事实；不能将这一情况改写成报告从未发布。

进程被直接终止、解释器尚未建立错误输出能力，或结果通道已无法使用时，不保证存在完整错误消息。主程序按 stdout 与进程终止状态的既有组合表判断异常。

## 诊断字段

错误消息仍为一行 UTF-8 JSON，`body` 包含 `reason` 与对象类型的 `details`。`details` 只包含实际已知的诊断信息；没有附加上下文时为 `{}`。主程序可以保存这些字段用于诊断，不需要依据业务身份、文件路径或内部阶段推导恢复动作。

| `details` 字段 | 表达内容 |
| --- | --- |
| `stage` | 错误发生阶段；取值为 `invocation`、`configuration`、`locking`、`state_open`、`input_handling`、`clock_check`、`recovery`、`execution`、`reporting`、`handoff` 或 `shutdown`；阶段不可靠时省略 |
| `path` | 与错误直接相关且实际已知的文件或目录路径；不以路径推断请求身份 |
| `errno` | 已取得的操作系统错误号；没有对应错误号时省略 |
| `message` | 供人类阅读的简短诊断；不作为机器分支条件，完整日志和堆栈进入 stderr |
| `request_id`、`report_id` | 能够可靠关联到本次错误的请求或报告；输入读取失败等情况下不补造未知身份 |
| `transaction_status` | 错误所涉及的那次状态事务的结果，遵守下表；不代表整段会话中所有事务的结果 |
| `publication_status` | 错误所涉及报告的本地发布事实，遵守下表；不表示客户端是否收到 |
| `secondary_errors` | 错误退出期间实际取得的其他会话错误，元素为 `reason` 与 `details`；元素中不再嵌套此字段 |
| `emergency_stops` | 本次会话错误收场中各录像的停止尝试及保存结果，按“正在录像时的应急停止”表达；主程序无须解析它来操作设备 |

事务或报告发布结果与当前错误有关且已进入相应操作流程时，须通过明确状态区分已确认结果与未知；不能因查询失败而省略一个本应表达为未知的操作结果。

| 字段与取值 | 成立条件 |
| --- | --- |
| `transaction_status: not_started` | 可靠确认相关事务尚未开始 |
| `transaction_status: not_committed` | 可靠确认相关事务未提交，例如回滚已确认完成 |
| `transaction_status: committed` | 已取得相关事务成功提交的可靠结果，之后其他职责失败 |
| `transaction_status: unknown` | 无法可靠确认该事务是否已经提交；异常返回本身不等于未提交 |
| `publication_status: not_published` | 可靠确认该报告文件没有完成向 `ready` 的移动 |
| `publication_status: moved` | 已确认向 `ready` 的移动成功，但所需后续目录同步尚未可靠完成 |
| `publication_status: published` | 已确认完成该次发布所需的文件及目录同步；数据库发布记录是否提交由其事务状态另行表达 |
| `publication_status: unknown` | 无法可靠判断该次发布操作结果，须按报告恢复规则核实 |

上述发布状态描述本次已取得的操作事实。主程序后来领取或删除文件不会抹去这些事实；当前位置与发布事实分别判断。

如果错误发生于业务动作提交后的报告发布，`transaction_status` 仅描述实际关联的那次报告事务，不能用它否定此前已提交的计划和动作。所有诊断字段都不承担客户端受理确认或报告 ACK 的职责。

## 当次退出与后续恢复

确定会话无法正常完成后，`run` 停止发起新的普通动作并退出普通接纳阶段；错误退出不使用“所有工作已经完成”的正常收尾结论。释放实际持有的接纳资格，会话锁继续覆盖退出清理。状态库不可用时不依赖新写入才能承认本次会话发生错误，也不向主程序输出一个未经可靠计算的 `needs_run`。

`submit` 的错误处理仍限于提交和交接职责，不借错误收场操作设备，也不代替 `run` 发布报告。事务结果未知时，不宣称受理失败或成功；后续输入继续依据同一请求 ID 和实际持久化状态判断。

| 当次已成立的条件 | 可以确定的处理与恢复边界 |
| --- | --- |
| 错误发生在取得执行资格前，尚未发起设备操作 | 不发起设备动作，保留诊断并结束；不能因启动失败而操作其他会话的设备 |
| 时钟检查失败，状态及目标归属可可靠读取，满足现有受限收场条件 | 按[时钟异常](scheduling-execution.md#时钟异常)完成允许的有限收场，仍返回 `clock_invalid` |
| 文件读取中出现状态保存失败或事务未知 | 停止依赖该未确认进度继续读取和推进；后续恢复以原文件与已提交进度核实，不跳过缺失数据 |
| 报告处理失败或发布记录提交未知 | 保留登记及已知文件事实，后续按[从历史重建报告](status-reports.md#从历史重建报告)与文件交接规则处理；不为尽快退出伪造发布完成 |
| 已有业务事务成功提交，之后会话职责失败 | 保留计划、动作、产物及交付的实际状态；会话错误不将它们批量改成 `failed` 或撤销原请求 |
| 正在录像时发生非时钟类致命错误，且仍能可靠确认归属并执行安全停止 | 按“正在录像时的应急停止”立即有限尝试停止，不等待原定停止时刻；停止结果与持久化结果分别表达 |

后续实际 `run` 先按已确认的启动顺序验证状态库和时钟，再恢复符合资格的工作。已进入终态的动作保持终态；未完成工作继续原身份与已消耗预算。会话失败、主机重启或客户端重送都不重置已持久化的普通动作尝试计数；会话应急预算按下节的独立范围处理。

首个使会话无法继续的已分类错误作为主 `reason`。同一操作已经知道是状态库失败时，直接分类为 `state_db_error`，不额外包装成 `report_error`；错误退出期间另外发生的会话错误保留为 `secondary_errors`。后续错误不能覆盖最初诊断，也不能使已经失去的执行或持久化条件被当作仍然可用。

最终结果通道失败时，可能没有完整 JSON。尚能控制退出状态时按失败结束，日志在可用的 stderr 中保留；stdout 已输出部分或完整结果后，不追加第二条结果试图修复消息。主程序继续联合最终输出与实际进程退出状态判断。

### 正在录像时的应急停止

本次 `run` 因非时钟类会话错误必须退出时，对能够可靠确认属于本次会话控制范围、且驱动保证可以安全重复停止的录像，立即执行有限应急停止。即使状态数据库已经不可写，也不等待原定录像结束时刻。时钟异常收场期间再发生状态库等非时钟类错误，使原收场流程无法继续时，也按本节资格处理应急停止。提前停止可能使视频短于目标时长；应急停止成功只证明本次停止已确认，不能据此宣告录像动作成功。

先判定进程及设备状态，再判断是否能够执行应急停止：

| 进程与已确认状态 | 执行条件 | 对该录像的处理 |
| --- | --- | --- |
| 进程突然终止、主机直接断电或错误处理已无法运行 | 任意 | 不保证能够停止或产生最终消息，后续实际会话按历史与设备证据恢复 |
| 进程仍能处理错误，已可靠确认该录像停止 | 任意 | 不再重复发出停止，保留已有确认及其持久化状态 |
| 进程仍能处理错误，该录像尚未确认停止 | 排他资格、归属、驱动、有限停止配置均可信，停止可安全执行 | 立即建立或继续本次会话对应录像的唯一应急停止流程 |
| 进程仍能处理错误，该录像尚未确认停止 | 上述任一执行条件不成立或未知 | 不依据猜测操作设备；保存实际诊断，无法持久化时通过仍可用的错误通道表达未处理事实 |

对于已建立的应急停止流程，每次继续前按下表判断：

| 停止确认 | 当前执行条件与额度 | 处理 |
| --- | --- | --- |
| 已取得驱动定义的成功确认 | 任意 | 结束该录像的应急停止，不继续补发剩余次数 |
| 尚未确认停止 | 执行条件仍成立，且还有额度 | 按已固化的命令超时及重试间隔有限尝试 |
| 尚未确认停止 | 额度耗尽，或执行条件已失效、未知 | 结束本次有限收场，如实保留停止未确认，不继续无限等待或补发 |

本表中的可靠归属可以来自本次进程已确认的控制结果及仍可信的内存信息；状态库写入失败不自动抹去这些事实。内存信息缺失或不可信时不能借本规则扩大停止范围。尚在途的设备控制按驱动既有协议协调，不为了收场并行发出相互冲突的指令。

应急停止采用本动作已固化的停止尝试上限作为本次会话的应急限额，默认 3 次、可通过对应本地停止配置调整。它是错误退出流程的独立有限预算，与[普通启动与停止预算](camera-recording.md#启动与停止的尝试上限)分别记录；不会重置原动作已经消耗的普通停止次数。无论原错误后又出现多少其他错误，同一会话对同一录像只建立一个应急停止流程，不重新获得额度。

每次实际发出应急停止前先在内存中占用一次额度；明确失败、超时或结果未知均不退还该次额度。状态库可写时保存对应应急事实，无法写入时也允许上述有限停止，不因保存失败反复创建新流程。这是会话错误退出期间针对已确认录像的收场规则，不授予启动录像、取回、修复或删除文件的执行资格；`submit` 不执行该流程。

内存计数只能限制当前进程中的应急尝试。数据库无法保存时，不承诺跨进程准确恢复这些新增尝试次数；后续会话不能补造丢失的计数或停止成功记录。能够读取可靠历史后，仍须核实设备实际状态；原动作的普通预算继续依据其已持久化事实，不能将普通预算重置来吸收应急尝试。

已取得的停止结果在状态库可可靠写入时追加为应急收场事实，并同步相关投影；无法保存时，保留内存诊断并通过仍可用的 stderr 和最终错误消息表达。不为等待数据库恢复而无限延长退出，也不把已经提交的动作批量改成 `failed`。后续正常会话根据已保存历史及设备证据判断原片、必要后处理和动作结果；应急停止本身不删除源文件。

`details.emergency_stops` 的每项记录包含：

| 字段 | 含义 |
| --- | --- |
| `action_instance_id`、`device_id` | 本次能够可靠关联的录像与设备 |
| `max_attempts`、`attempts_used` | 本次应急限额及实际已开始次数；未实际发令为 0 |
| `outcome` | `stopped` 为取得停止成功确认；`unconfirmed` 为执行后仍未确认停止；`not_attempted` 为尚未发令且已无法执行 |
| `record_status` | `recorded` 为该结果已可靠保存；`not_recorded` 为确认尚未保存；`unknown` 为保存结果不确定 |

无法可靠确认目标身份时，用其他诊断字段保留原因，不创建虚构的应急目标记录。已经确认目标但停止配置无法可靠取得时，表达 `not_attempted`、实际为 0 的 `attempts_used`，省略未知的 `max_attempts`，不将未知配置解释为零次预算。

该诊断不代替状态报告或数据库中的事实。主程序保留诊断即可，不根据 `outcome` 修改业务状态或代替 camctl 继续停止。任何应急收场结果都不会把原会话 `error` 改成 `succeeded`。

## 主程序处理边界

| 已收到的结果与已有职责 | 主程序行为 |
| --- | --- |
| `run` 正常成功，且没有待启动标记 | 按既定规则结束本次调用，不无条件再次启动 |
| `submit` 正常成功，`needs_run: true` | 保留或合并待启动标记，按既有顺序启动后续裸 `run` |
| 合法 `error` 与退出码 `1` | 记录会话失败及诊断；消息不包含成功的接管判断 |
| 进程异常或结果消息缺失、不合法、不一致 | 记录会话异常，不推断事务回滚或业务动作失败 |
| 收到错误或进程异常，但此前已有合法 `needs_run: true` 建立的待启动标记 | 保留这个既有启动职责，在旧 `run` 实际退出后按既定协议处理；不是由错误码新授予重试资格 |
| 无既有待启动职责，收到错误或进程异常 | 不从 `reason` 或错误中的身份推导自动重启要求；同一供电窗口内的有限重启仍为待双方确认的对接建议 |

主程序无需检查动作是否成功、设备是否仍在录像或报告是否被客户端确认。未知 `reason` 仍是会话失败，保留收到的诊断即可。后续重启不保证原输入文件还存在；客户端是否需要重送继续依据已经取得的受理证据判断。

## 消息样例

下面只展示正常退出码为 `1` 且错误消息完整输出时的情况。路径、报告 ID 和错误号是演示值，不证明实际部署状态。

状态库提交结果无法确认：

```json
{"kind":"error","body":{"reason":"state_db_error","details":{"stage":"input_handling","transaction_status":"unknown"}}}
```

主程序只记录失败；不能把它解释为计划一定没有受理。客户端尚未确认请求时继续使用原请求 ID 重送，由数据库中的实际结果决定复用或首次受理。

报告文件移动成功，但目录同步失败：

```json
{"kind":"error","body":{"reason":"report_error","details":{"stage":"reporting","report_id":27,"path":"/var/lib/camctl/ready","errno":5,"publication_status":"moved"}}}
```

文件可能已经被主程序领取，后续恢复结合报告登记和实际文件处理，不能据此撤回 `processing` 中的文件。

发布文件及目录同步已经成功，但保存发布记录的事务结果未知：

```json
{"kind":"error","body":{"reason":"state_db_error","details":{"stage":"reporting","report_id":27,"publication_status":"published","transaction_status":"unknown"}}}
```

这里保留已确认的本地发布事实，后续核实数据库记录；不要求文件一直留在 `ready` 才能保存正确结果。

录像期间的状态事务已确认未提交，随后一次应急停止成功，但该停止结果尚未保存：

```json
{"kind":"error","body":{"reason":"state_db_error","details":{"stage":"execution","transaction_status":"not_committed","emergency_stops":[{"action_instance_id":"a-001","device_id":"cam0","max_attempts":3,"attempts_used":1,"outcome":"stopped","record_status":"not_recorded"}]}}}
```

该消息同时表达会话失败、设备停止已确认及停止事实未落库。主程序不据此修改动作结果；后续 camctl 仍以实际可取得的历史和设备证据恢复，不能把应急停止成功直接解释为已录满目标时长。

## 验收要求

单元测试隔离状态库、锁、文件、设备和结果输出协作者，按“业务失败与会话失败”表验证责任分类。同一个底层 I/O 错误分别发生在视频拷贝、失败结果保存、报告文件写入时，应得到各自不同的业务或会话结果。正常接纳锁冲突不得误判为锁错误，历史时间下界读取失败不得误判为时钟异常。

诊断测试区分事务明确未提交、已提交及未知，以及报告未发布、已移动、已完成同步及结果未知。精确断言机器标识和已知事实，不逐字断言人类诊断。只对相关操作表达对应状态，不能让某次失败事务的状态否定此前已提交工作；后续错误保留最初原因并阻止依赖已失效条件继续执行。

集成测试组合真实状态库、进程管道和交接目录，验证已提交业务结果不会因后续报告失败而回滚，报告文件发布后状态保存失败仍保留可恢复的事实；正常返回错误时只有一条 JSON 且退出码为 `1`。另行覆盖输出失败、进程异常及已有待启动标记，验证主程序不猜测受理结果或自行按错误码添加业务职责。

应急停止按归属与排他资格可信、停止能力可用、数据库可写或不可写、剩余额度、停止确认结果及进程可继续运行的分区验证。状态库写入失败时，对已确认属于本会话的录像立即停止，不等待原定时刻；只控制确认归属的录像，不启动新拍摄或文件业务。停止成功、耗尽或执行条件失效均结束该有限流程，同一会话的后续错误不增加额度；普通停止预算保持原值。

集成测试在录像进行中注入状态写入失败，验证应急停止可发生于该写入失败之后，停止结果与记录结果分别表达，最终仍输出原会话错误。在应急尝试及结果保存期间终止进程，验证后续恢复不补造丢失的计数或停止事实，而是核实历史与实际设备状态；不能把没有持久化保证的内存次数断言成跨重启精确计数。
