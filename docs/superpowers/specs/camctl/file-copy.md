## 相机视频的断点续传

第一版要求相机视频拷贝到主机时支持跨主机重启的断点续传。拷贝因主机断电而中断后，后续实际启动的 `run` 在该处理仍有执行资格时，使用主机上已经可靠保留的部分继续拷贝，不因进程重启而统一从头取回整个视频。

已确认的运行前提是：相机内的源文件不会自行丢失，camctl 是这些文件的唯一访问者。拷贝对象为相机已经写完的视频文件，写完后内容和长度保持不变。camctl 按显式清理请求删除文件时，仍遵守[清理与取回并发规则](output-cleanup.md#清理与取回并发)；已经取得取回资格的请求恢复续传时继续持有原资格。

开始拷贝时确定源文件身份及其完整长度，后续续传继续读取同一份固定内容，并以该长度确定拷贝的结束位置。当前相机的文件写入完成依据见[停止成功与文件可读](camera-recording.md#停止成功与文件可读)；来源身份表示及停止结果未知时的对账方式仍需结合设备协议细化。

该要求适用于 camctl 将视频从相机拷贝到主机的流程，包括 `obtain_action_outputs` 取回、相机录像内部修复，以及[计时证据不足时的原片检查](camera-recovery.md#计时证据不足时的原片检查)所需的拷贝。后两者属于录像内部处理，不创建普通 delivery。主机向外部客户端传输文件由第三方主程序负责，其重试行为按文件交接专题处理。

续传需要保留相机源文件、主机上的未完成文件及所属处理任务之间的关联，以及能够可靠恢复的拷贝进度。已确认的进度变化按全局规则追加历史并同步更新投影。恢复同一次取回时沿用原请求和交付身份，未完成文件继续由 camctl 管理，不能发布到 `ready`。完成后的交付仍遵守本次取回的开始发布的条件。

### 同一相机的拷贝并发限制

第一版同一相机在同一时刻最多进行一份文件从相机到主机的拷贝。`obtain_action_outputs`、异常原片检查和内部修复所需的源文件拷贝共用这个限制，不能各自启动一份并行拷贝。同一产物的不同交付请求仍分别准备独立副本，依次取得拷贝机会，不合并请求或复用在途 delivery。

限制以源相机为范围；不同相机分别协调。从主机 `staging/derived/` 准备交付副本、主机上的媒体处理以及主程序对外传输，不占用相机的拷贝机会。它们继续遵守自身的执行资格与资源要求。

| 拷贝或设备操作情况 | 并发约束 |
| --- | --- |
| 同一相机已有一份文件正在拷贝 | 其他文件等待；分段保存进度期间仍属于同一份拷贝，不借段间间隙交错拷贝另一份文件 |
| 当前拷贝读取失败，仍有执行资格及重试预算，正在等待重试 | 保留该文件的拷贝机会，其他文件继续等待；到达重试时间后恢复原拷贝 |
| 一份文件的源内容已全部读取，且相应设备读取已结束 | 后续仅在主机进行的校验、修复、等待组成员或发布，不占用该相机的拷贝机会 |
| 拷贝被取消或最终失败，但实际读取尚未停止或无法确认已经停止 | 先完成对应停止与确认，不启动同一相机的另一份拷贝 |
| 拷贝被取消或最终失败，且已确认实际读取及后续重试停止 | 解除拷贝机会的保留，再选择其他具备条件的文件 |
| 相机继续录像，或需要执行必要的停止命令 | 按驱动兼容性执行控制操作，不要求它们等待整份文件拷贝完成 |

只有具备源文件读取资格、来源已写完且满足所属流程执行条件的文件，才可开始拷贝。排队不等于拷贝失败，也不消耗设备读取尝试次数；等待源录像结束的请求不占用拷贝机会。获得拷贝机会不授予新的取回资格，也不解除已有取回对源文件的清理保护。

正常调度、取消处理及重启恢复均使用同一限制，不能分别创建互不协调的拷贝通道。重启后保留每份文件原有的身份、进度与预算，按既有断点续传规则恢复；一次只恢复一份相机拷贝，不因存在多个未完成文件而全部并行启动。实际复制工作的暂停或结束，与源文件读取依赖的解除分别处理，后者仍须满足[准备完成与断电恢复](output-cleanup.md#准备完成与断电恢复)的持久化条件。

#### 等待重试时保留拷贝机会

取回、异常原片检查及修复输入拷贝使用相同规则：一份文件已经取得相机拷贝机会后，读取失败进入有限重试等待，仍为它保留下一次拷贝机会。其他文件即使已具备读取条件，也不能在等待期间开始拷贝。源文件内容固定，原半成品、可靠进度、身份、读取资格和剩余预算继续按既有规则保留。

读取重试使用固化的[通信重试间隔](configuration.md#通信重试间隔)。例如 A 已可靠保存 100 MB，读取失败且旧读取确认结束后，按默认配置等待 3 秒。此时 B 已准备好，也须等待；间隔到达且 A 仍具备重试资格时，A 从其可靠进度继续读取。A 完成源内容读取后，才允许选择 B 等候选文件。若 A 取消或最终失败，则在确认读取及重试已停止后解除保留。

拷贝机会的归属、重试等待与解除事实按历史和投影规则可靠保存。重启时先恢复已有保留关系：A 尚具备重试资格则继续等待或恢复 A，不能因重新加载候选文件而让 B 抢先。保留关系不增加重试预算；错误耗尽后仍按原有限失败规则结束，不通过反复新建拷贝重置预算。

保留范围仅为该相机的文件拷贝。录像、必要的停止命令及其他已确认兼容的控制操作继续按设备执行规则处理。该保留也不解除源文件的旧取回保护。

源内容读完并释放拷贝机会后，后续校验发现不一致而需要重拷时，按有限重拷规则重新参与候选选择；不能追溯恢复已经释放的保留关系，或打断此时正在拷贝的另一份文件。

#### 多个候选文件的选择顺序

每台相机独立选择待拷贝文件。先恢复和处理已有活动拷贝或等待重试的保留关系；只有没有此类占用或保留时，才在当前已具备拷贝条件的文件中选择一个。条件包括所属动作仍可执行、计划时间已到、源内容已写完、读取资格成立，以及所属流程允许本次读取。尚未形成文件或仍在等待来源结束的请求不阻挡其他合格候选文件。

排序使用负责发起这次拷贝的动作，而不是一律使用源录像动作：

| 拷贝用途 | 用于排序的所属动作 |
| --- | --- |
| 用户请求取回原片 | 本次 `obtain_action_outputs` |
| 异常原片检查 | 需要该检查的 `camera_record` |
| 内部修复所需的源文件拷贝 | 需要该修复的 `camera_record` |
| 校验不一致后的有限重拷 | 沿用原拷贝所属动作，不按重拷发生时间改排 |

合格候选文件按以下顺序比较，前一项相同才比较后一项：

1. 所属动作的 `scheduled_at`，从早到晚。
2. 所属计划的 `plan_seq`，首次受理较早的计划优先。
3. 所属动作在原计划 `actions` 数组中的位置，从前到后。
4. 同一动作内文件条目的首次登记顺序；登记时保存固定顺序，后续恢复沿用。

内部检查或修复不会仅因用途而取得额外优先级。相应录像的计划时间较早时，其已具备条件的输入拷贝排在较晚的取回动作之前；用户取回的计划时间较早时，顺序相反。

例如，09:00 录像的修复输入与 10:00 的取回请求在本次调度时均可拷贝，且该相机没有活动拷贝或保留关系：先处理修复输入。若修复输入尚不能读取，则可以开始该取回；取回开始后，即使较早录像的修复输入随后具备条件，也须尊重当前文件的拷贝及重试保留关系。

每次释放拷贝机会后重新从当时合格的文件中选择。一次取回包含多份文件时，不为整个取回动作预占相机；同一动作后续才确定的文件追加登记顺序，不改变已登记条目的顺序，也不扩大已固定的选择集合。

正常调度和重启恢复使用同一组持久化排序依据；数据库查询返回顺序、目录枚举顺序和内存加载顺序不能代替它们。排序依据无法可靠读取或解释时，按状态库错误处理，不猜测先后。取得机会后遵守原身份、进度及有限预算；排序本身不授予读取资格、不修改删除限制，也不提前执行尚未到时间的动作。

### 先保存文件，再记录进度

拷贝按段保存进度。数据库中的进度表示从文件开头起，已经连续写入并可靠落盘的字节数。进度为 `C` 时，主机文件的前 `C` 字节必须与源文件对应内容一致；进度的推进不能跳过字节或包含尚未可靠保存的数据。

每段按以下顺序处理：

1. 从源文件的对应位置读取数据，连续写入主机文件。
2. 清空写入缓冲并完成文件同步；文件新建或路径发生变化时，同时保证所需目录变更已经落盘。
3. 在数据库事务中追加已保存进度的历史并同步更新投影，提交成功后继续下一段。

进度按实际连续写入并同步成功的字节数计算。写入或同步失败时不推进进度；进度事务失败或提交结果不确定时停止继续拷贝，后续恢复先确认数据库实际提交的进度。文件操作及设备读取不占用数据库写事务。

### 重启后选择续传位置

以下规则适用于处理任务仍有执行资格、源文件身份及未完成文件关联可可靠确认的情况。设源文件完整长度为 `N`，数据库已保存进度为 `C`，主机未完成文件当前长度为 `L`。这些量均以字节计，合法进度满足 `0 ≤ C ≤ N`。先处理无法可靠判断或数值越界的情况，再按文件是否存在及长度关系处理。

| 恢复时的情况 | 处理 |
| --- | --- |
| 文件不存在，`C = 0` | 创建未完成文件，从源文件开头开始 |
| 文件存在，`L = C < N` | 从源文件及主机文件的偏移 `C` 处继续拷贝 |
| 文件存在，`C < L ≤ N` | 将未被进度确认的尾部截去，使文件长度回到 `C`，再从 `C` 继续 |
| 文件存在，`L = C = N` | 全部字节已经保存，进入后续完整性确认及相应处理，不再读取视频数据来续传 |
| 文件不存在但 `C > 0`，或 `L < C` | 已记录的可靠数据缺失，保留诊断并按错误处理，不能跳过缺失部分继续拷贝 |
| `C` 超出合法范围，或 `L > N` | 状态不符合拷贝约束，保留诊断并按错误处理 |
| 文件、进度或身份无法可靠读取或确认 | 停止依赖这些信息的续传判断，不能当作文件不存在或进度为零 |

例如，数据库记录前 100 MB 已保存，文件当前有 110 MB，且未超过源文件长度时，恢复先截去后 10 MB，再从 100 MB 处续传。已记录进度内的数据保留，未被记录确认的尾部允许重新读取。截断失败时不能继续写入；恢复操作再次中断后仍按上表判断。

最终文件必须与固定源文件逐字节一致。续传不能留下空洞、重复片段或多余尾部；读取提前结束但尚未达到 `N` 时不能判定拷贝完成。文件长度及进度相同只说明字节范围已经保存，读取及校验还须满足下一节的要求。

每段的大小、进度保存频率和设备按指定位置读取的能力仍需细化。

### 文件读取的无数据超时

相机文件内容读取使用本地配置 `devices.<id>.copy.read_idle_timeout_s`，默认 **10 秒**，允许配置为有限的正秒数。该值随所属动作的对应设备配置在首次受理时固化，后续拷贝、重试和恢复沿用；执行计划不覆盖该值。

超时计量的是驱动正在等待源文件新数据时，连续未取得数据的时间。使用当前进程的单调钟计时：开始等待时启动计时，每次取得非空的源文件内容字节后重新计时，连续无数据达到阈值时判定本次读取超时。首批数据也受此限制。只要持续取得数据且尚未读完已知长度，就继续当前读取，不设置整份文件必须在固定时长内完成的截止时间。

| 当前读取阶段或结果 | 超时处理 |
| --- | --- |
| 已开始等待源数据，连续无数据尚未达到阈值 | 继续等待，仍处理取消等事件 |
| 正在等待源数据，连续无数据达到阈值 | 记录读取超时，按读取失败与有限重试规则处理 |
| 取得非空源文件内容，尚未读完 | 重新计时并继续；无须等整个分段完成或写入数据库后才确认收到数据 |
| 只收到设备日志、控制响应或其他非文件内容 | 不作为新文件数据，不重置无数据计时 |
| 主机正在写入、落盘、保存进度、计算摘要或处理媒体，当前未等待源数据 | 不计入相机无数据超时；进入下一次源数据等待时重新计时 |
| 正在排队、等待重试时间或等待源录像结束 | 尚未等待源数据，不启动该计时 |
| 已读完已知源文件长度，且读取正常结束 | 结束读取计时，进入后续校验 |
| 源读取异常终止或未到已知长度便提前结束 | 直接按已确认的读取错误处理，无须再等待无数据阈值 |

驱动须能在完整分段返回前识别文件数据的到达；分段大小、内部缓冲或调用方尚未收到整个分段，不能把持续有数据的传输误判为停滞。收到数据与可靠保存进度是不同事实：数据到达可以重置计时，数据库中的进度仍只按完成落盘的连续字节数推进。

超时只使当前读取尝试失败。仍有读取重试额度时，停止并确认本次实际读取结束，按既有规则保留拷贝机会、等待后从可靠进度续传；额度耗尽时结束该文件的拷贝。超时不消耗摘要不一致的重拷额度，报告保留采用的超时阈值、读取失败原因及可靠进度。

主机断电期间不累计无数据时间。恢复后实际开始等待源数据时建立新的单调钟计时，沿用已固化的阈值及原读取尝试；重启前已保存的超时失败仍按原失败及剩余预算处理，不因新计时而撤销。设备控制、文件元数据查询和摘要计算采用各自适用的超时与错误规则。

### 按文件累计读取尝试

读取尝试上限由本地设备配置 `devices.<id>.copy.max_read_attempts` 提供，默认 **3 次**，包含第一次；允许配置为大于等于 1 的整数。执行计划不覆盖该值。每份文件使用所属动作首次受理时固化的对应设备配置，创建拷贝记录时保存所采用上限及其归属；配置变化不刷新已有动作的预算。

一次读取尝试可以连续读取多段数据，也可以跨主机断电恢复继续进行。成功读取新的一段不结束该尝试、不增加次数，也不清零之前的失败。只有驱动明确报告读取错误，才将当前尝试记录为失败，包括已确认的读取超时、异常终止或未达到源文件固定长度便提前结束；仍具备执行资格且未达到上限时，等待后开始下一次尝试，从可靠进度继续读取。

开始读取后的已用次数等于“1 + 因读取错误而实际开始的重试次数”。摘要不一致引发的整片重拷另外记录轮次，沿用当前读取尝试的计数，不消耗读取错误重试额度，也不清零之前的读取失败。设备读取记录关联所属文件、读取尝试身份与整片拷贝轮次，以区分一次读取尝试中发生的不同重拷轮次。

该规则统一用于取回、异常原片检查及修复输入拷贝。预算按所属处理中的每份文件分别保存，不由整个取回动作或整台相机共用。不同请求对同一 `output_id` 的独立交付分别计数；同一请求重送、同一文件分段及原内部处理的恢复均复用原记录。

| 文件读取情况 | 次数与处理 |
| --- | --- |
| 仅在排队，尚未开始读取 | 已用次数为 0，不因等待消耗次数 |
| 首次开始读取 | 记录第 1 次尝试后开始读取 |
| 当前尝试成功读取一段，文件尚未读完 | 继续同一次尝试，按已确认进度推进，不重置计数 |
| 全部内容读完后摘要不一致，且具备整片重拷资格 | 沿用当前读取尝试计数，由独立重拷预算控制下一轮从头读取 |
| 驱动明确报告读取错误，已用次数小于上限，处理仍可执行 | 保存当前失败及重试等待，保留拷贝机会；下一次尝试沿用可靠进度并增加已用次数 |
| 驱动明确报告读取错误，已用次数达到上限 | 该文件读取最终失败；确认实际读取和重试停止后解除拷贝机会保留 |
| 主机断电中断当前尝试，未保存该尝试的明确失败结果 | 重启后核实进度并继续原尝试，不因重新打开连接、恢复文件或再次启动进程增加次数 |
| 重启前已有明确失败及重试等待记录 | 沿用原失败及剩余预算，不能将其解释为尚未失败的原尝试继续读取 |
| 当前处理已取消或终态 | 按原有规则停止及收场，不开启新的读取尝试 |
| 历史、次数或提交结果无法可靠确认 | 按状态库错误及恢复规则处理，不默认成 0，也不猜测已耗尽 |

例：第一次在 100 MB 处读取失败，第二次续传到 500 MB 后失败，第三次续传到 900 MB 后失败。使用默认上限时，该文件最终失败；中间增加的可靠进度不会让它获得新的三次机会。若第三次只是被主机断电中断，恢复后仍可继续第三次尝试。

开始首次或下一次尝试前，将尝试身份、已用次数及所属文件关联可靠保存，再发起读取。恢复已有尝试不重复登记新尝试；同一失败结果不重复计数。失败、重试等待及拷贝机会保留遵守同一组持久化事实，取消或数据库错误不能绕过有限预算继续发令。

开始下一次尝试仍须确认前一次实际读取已经停止，不能因驱动报告超时就并行发起另一条读取；实际读取是否停止无法确认时，继续按并发限制保留诊断和拷贝机会。

主机写入、落盘、状态库及摘要计算错误按各自错误契约处理，不伪装成相机读取错误。文件字节读完后仍须通过后续校验，读取次数尚有剩余不代表副本已经有效。摘要不一致的从头重拷及其额度关系见“摘要不一致后的有限重拷”。

报告记录该文件采用的读取上限、已开始的尝试次数、各次明确失败及当前等待或结束原因。取回中某份文件耗尽次数，继续按[部分成功](obtaining-outputs.md#部分成功)处理其他项；内部拷贝失败与录像结果按相机专题的规则分别判定。半成品与源文件遵守各自保留、清理契约。

### 读取正确性与文件校验

相机驱动负责从指定位置正确读取源文件，并检测、报告传输错误；camctl 负责连续写入、落盘和恢复位置的正确性。设备接入时必须确认驱动能够履行可靠读取的契约。读取失败或结果无法确认时，不能仅凭取得了足够长度的数据就认定取回成功。

源端摘要是额外校验能力，不是所有相机的必备条件。设备具备该能力时，取回完整视频后比较源端与主机端摘要；明确不具备该能力时，以已确认的可靠读取契约和正确续写流程为依据完成取回。

当前相机已确认能计算源文件的 SHA-256，采用源端与主机端 SHA-256 比较；其通信方式见[通信方式与查询能力](camera-recording.md#通信方式与查询能力)。其他相机由对应驱动说明其读取和摘要能力；具体命令、返回格式、二进制数据读取和错误识别方式仍需在设备适配时核实。

主机端仍须计算最终文件的 SHA-256，并作为报告中的 `sha256` 提供给客户端，用于检查后续收到的文件。该摘要对应实际交付内容；它与可选的源端比较承担不同职责。

完成可靠读取、文件落盘及主机摘要计算后，按下表处理源端校验：

| 源端摘要能力 | 获取或比较结果 | 处理 |
| --- | --- | --- |
| 已确认支持 | 摘要相同 | 校验通过，继续该视频的后续处理 |
| 已确认支持 | 摘要不同 | 内容不一致，按“摘要不一致后的有限重拷”处理，不将该副本用于交付或修复 |
| 已确认支持 | 摘要获取或比较失败、结果未知 | 保留诊断并按错误处理，不能当作设备不支持而跳过校验 |
| 已确认不支持 | 无源端摘要 | 按可靠读取及正确续写的结果继续处理，主机摘要仍用于客户端校验 |
| 能力尚未确认 | 无可靠判定 | 先确认设备能力，不能直接归入“不支持”分支 |

成功取得的源端摘要关联同一份内容固定的源文件，可以在后续取回中复用。摘要及比较结果按全局历史规则保存；能力不支持、获取失败和内容不一致分别表达。

### 摘要不一致后的有限重拷

源端与主机端 SHA-256 不一致时，当前主机副本无效，不能交付或用于修复。camctl 保留相机源文件，在有限次数内从头重拷同一视频；每次重拷完成后重新校验，仍不一致且次数耗尽时报告该视频拷贝失败。

| 当前处理是否仍允许执行 | 剩余重拷次数 | 处理 |
| --- | --- | --- |
| 是 | 还有次数 | 持久化本次重拷决定，再从源文件开头重新拷贝 |
| 是 | 已耗尽 | 该视频拷贝失败，不交付或使用无效副本 |
| 否，例如处理已被取消或已终态 | 任意 | 不开始新的重拷，按原有取消或终态规则处理 |
| 执行资格或次数无法可靠判断 | 无法确认 | 保留诊断并按错误处理，不能获得新的重拷次数 |

整片重拷上限由本地设备配置 `devices.<id>.copy.max_recopies` 提供，默认 **额外 1 次**，允许配置为非负整数；首次拷贝不计入重拷次数。使用默认值时，首次完整拷贝摘要不一致后允许从头重拷一轮，这一轮仍摘要不一致则该文件最终失败。设为 0 时，首次摘要不一致即失败。

执行计划不覆盖该值。每份文件使用所属动作首次受理时固化的对应设备配置，创建拷贝记录时保存所采用上限；已消耗次数跨重启保留，配置变化不刷新已有动作的预算。重拷仍属于原处理任务，同一次取回保留原请求、产物和交付身份。

读取错误重试与摘要不一致重拷各有独立预算，按同一文件分别累计：

| 本次处理结果 | 使用的预算与后续处理 |
| --- | --- |
| 读取明确报错，尚可继续读取重试 | 当前读取尝试失败；下一次读取尝试增加读取计数，沿用本轮可靠进度；重拷计数不变 |
| 读取明确报错，读取尝试上限已达到 | 该文件最终失败；即使仍有重拷额度，也不能绕过读取失败继续拷贝 |
| 全部内容读完但摘要不一致，仍有重拷额度 | 增加重拷计数并开始新一轮从零拷贝；读取计数不变，已发生的读取失败仍保留 |
| 全部内容读完但摘要不一致，重拷额度已耗尽 | 该文件最终失败；剩余读取重试额度不能替代重拷额度 |
| 当前轮次被主机断电中断 | 恢复原轮次及读取尝试，保留两项计数，不额外消耗次数 |
| 已取消、已终态，或预算事实无法可靠确认 | 按取消、终态或状态库错误处理，不通过另一项预算重新开始 |

例如已发生两次读取错误，正在第 3 次读取尝试；读完后发现摘要不一致，只要尚有重拷额度，就可以从头重拷，读取计数仍为 3。若这轮重拷再次发生读取错误，该文件立即达到读取失败上限；若完整读完，则继续按摘要结果与剩余重拷额度判断。任何成功分段或新重拷轮次都不补满读取预算。

开始每次重拷前，在同一数据库事务中记录原副本无效、消耗一次重拷次数及新一轮从零开始的拷贝状态，并同步更新投影。提交成功后才重新准备主机文件，原无效副本的进度不再作为这一轮的续传依据。记录失败或提交结果不确定时，先确认数据库事实，不能直接重置文件或重新分配次数。

重拷过程中仍支持断点续传。若决定已提交、文件尚未重新准备时断电，恢复继续执行这次已经计数的重拷；若已经保存新一轮的部分数据，恢复从该轮已确认进度继续。恢复同一轮重拷不重复消耗次数，也不能把前一轮的无效数据接到新一轮文件中。

次数耗尽的失败仅说明这次主机拷贝未取得有效副本，不据此判断相机源文件损坏。取回请求的其他成功项继续按部分成功及开始发布的条件规则交付；内部修复的失败与录像结果按[相机录像](camera-recording.md)的证据规则分别处理。相机源文件仍遵守显式清理规则。

主机重启、同一请求的重试和校验结果的重复处理均不能重置或重复消耗已确定的次数。报告分别表达读取尝试上限与已用次数、重拷上限与已用次数，并保留失败原因及轮次关联。
