# 首次部署与初始化

[返回设计总览](../2026-09-08-camctl-cli-design.md) · [请求受理与会话](protocol-session.md)

本专题定义首次部署建立运行目录和初始状态库的方式。初始化由用户或部署人员执行，主程序的日常调用仍使用 `run` / `submit`。

从配置到客户端报告确认的完整步骤与可用输入文件见[首次部署与联调样例](deployment-example.md)。

## 部署入口

```text
camctl init [--config <path>]
```

`init` 使用[本地配置的默认值与覆盖规则](scheduling-execution.md#本地配置的加载与更新)。没有配置文件时可直接使用默认值初始化，默认状态库为 `$HOME/.camctl/state.db`；指定 `--config` 时使用对应的生效路径。初始化不生成或覆盖配置文件。

部署人员在日常 CLI 调用尚未开始或已经暂停、已有 `run` / `submit` 均已退出时执行初始化。`init` 取得目标状态库对应的稳定会话锁后检查状态和准备目录，锁保持到初始化结束；不取得接纳锁，也不承诺驱动任何任务。多个初始化进程须通过同一锁协调，不能同时创建或替换目标数据库。实际锁资格无法取得时报告失败，不无界等待。

初始化仅处理本地运行环境，不连接相机或 MCU，不检查墙钟可信性，不执行已有动作、恢复设备或发布报告。默认空设备目录不妨碍初始化。普通日志通道故障仍遵守[辅助日志故障规则](logging.md#日志通道故障)。

## 目录与状态库

初始化准备实际配置中的状态库父目录、稳定锁文件所需目录、`staging`、`staging/derived`、`ready` 和 `processing`。已有目录及其内容保留；路径已被普通文件占用、必要目录不可访问或不满足[交接目录要求](file-handoff.md#发布原子性)时，报告初始化失败，不覆盖冲突对象或删除业务文件。日志目录按辅助日志规则处理。

首次创建的状态库包含第一版所需的完整结构、可验证的 camctl 数据库标识及初始状态。初始库没有计划、动作、产物、交付或报告记录，业务变化水位和累计确认水位均为 0；后续身份和序列按各自分配规则首次产生。建立空库本身不生成业务报告。

状态库的判定以实际文件及其可验证内容为依据，文件名或扩展名不能代替数据库校验。

| 目标状态库情况 | `init` 的处理 |
| --- | --- |
| 可靠确认不存在，执行首次部署初始化 | 创建完整的初始状态库，并完成必要目录准备 |
| 已存在，能够确认是完整有效的第一版 camctl 状态库 | 验证并准备必要目录后成功结束；保留全部已有记录、身份、序列及累计 ACK |
| 已存在，但为空文件、其他数据库、格式不合法或缺少必要结构 | 报告失败，保留原文件，不清空、覆盖或自动修复 |
| 无法可靠判断是否存在，或无法读取、校验 | 报告失败，不把未知解释为不存在 |

`init` 是首次部署及已初始化环境的验证入口，不是历史数据丢失后的重建工具。已经投入使用的数据库丢失时，应先恢复原有数据并核实部署路径；普通运行入口不会把这种情况转换为新部署。

## 创建失败与再次执行

正式状态库应在完整结构及初始状态可靠保存后才对运行入口可用。首次创建的准备过程与正式数据库分开，发布时须保持“只创建尚不存在的目标”的约束；不能先向正式路径放置一个空文件，再让其他入口将其当作已初始化状态库。

创建及发布须完成必要的数据库提交、文件落盘和目录持久化后，才能返回成功。具体准备文件与发布方式由实现选择，必须保证新库可以独立打开并通过校验，不依赖遗漏的临时数据库辅助文件。

| 中断或失败后的实际状态 | 后续处理 |
| --- | --- |
| 正式数据库尚未发布，只有本次初始化的目录或可确认归属的准备文件 | 下次显式 `init` 可以重新准备；不得把准备文件当作已有业务库 |
| 完整数据库已发布，但进程在返回结果前失败或中断 | 下次 `init` 验证已有库，保留其数据，不重复初始化 |
| 正式路径出现不能可靠解释的文件或数据库 | 按已有库校验失败处理，保留诊断及文件，不猜测为空库 |

初始化失败后允许保留已创建的目录，不为恢复到空目录而删除其他内容。输出失败或未收到成功退出状态不证明数据库一定没有建立，再次执行时仍按实际状态判定。

## 命令结果

`init` 是面向部署人员的命令。成功时退出码为 `0`；可正常处理的调用、配置、目录、锁或数据库错误统一以 `1` 退出，诊断写入 stderr。stdout 保持为空，不使用 `run` / `submit` 的会话结果或 `needs_run`。进程异常终止时不保证完整诊断，部署方不能将其判为初始化成功。

成功只说明本地初始化职责完成，不表示设备在线、已有任务完成或客户端能力说明已经更新。

## 日常运行入口

`run` 和 `submit` 只打开已经初始化的状态库，不创建空库或自动调用 `init`。所选状态库不存在、无法打开或校验失败时，按[状态库错误](session-errors.md#错误标识)结束；不继续受理本次计划、执行设备动作或发布报告，也不向主程序提供未经计算的 `needs_run`。`run` 在建立锁资格前先做只读存在性检查，实际数据库打开和内容校验仍在持有会话锁时完成；文件在预检之后消失也必须报错，不能由数据库打开操作隐式创建。

`describe` 读取本地配置及驱动定义，可在初始化之前导出能力说明，其职责不需要业务状态库。

## 验收要求

单元测试使用受接口约束的配置、路径、锁和状态库替身，覆盖不存在、完整有效、已有无效和无法确认的分区；验证只有明确允许首次创建时才创建，已有库验证不清空数据，初始化不进入设备、接纳及调度流程。

集成测试使用独立测试用户目录、真实 SQLite、文件系统和 CLI 进程，验证默认配置缺省初始化、显式路径、空设备目录、目录冲突及创建失败。对已有业务库重复执行，验证历史、编号、累计 ACK 及业务文件保留；无效库和读取故障不被替换。

分别在新库准备、发布及结果返回前中断，验证再次执行遵守上述状态表；多进程争用同一初始化目标时不覆盖另一进程已经发布的库。验证 `init` 的 stdout、stderr 与退出码，以及 `run` / `submit` 面对缺失数据库时不创建文件或受理输入；完成初始化后，同一路径的日常入口可以正常使用该库。
