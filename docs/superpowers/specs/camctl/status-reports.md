# 状态报告与累计确认

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义状态快照、报告身份、累计 ACK 和报告补投。`last_report_id` 通过[请求受理与会话](protocol-session.md)的计划入口提交；报告文件的所有权与基本发布规则见[文件交接](file-handoff.md)。

## 状态报告与 ACK

### report_id

每份逻辑报告具有单调递增的：

```text
report_id
```

### 文件名与完整性校验

文件名：

```text
status-report-<report_id>-<sha256>.json
```

`sha256` 是最终报告文件全部原始字节的 SHA-256，以完整的 64 位小写十六进制字符串表示。摘要覆盖实际输出的编码、空白及换行；客户端直接对收到的文件字节计算，不能先解析 JSON 再重新序列化计算。

camctl 在 `staging` 完整生成报告并计算摘要，确定最终文件名后，按[状态报告发布前落盘](file-handoff.md#状态报告发布前落盘)完成同步和原子发布。生成、摘要计算失败或结果未知时不发布，按会话错误处理。主程序保留文件名和内容进行搬运及传输，无须解析报告或计算摘要。部署与对接须确认文件系统和传输协议能够保留完整文件名。

客户端按以下顺序检查收到的报告：

| 检查结果 | 处理 |
| --- | --- |
| 文件名不符合约定，无法取得合法报告 ID 或完整摘要 | 不接受为有效报告，不据此推进累计 ACK |
| 文件内容无法完整读取，或摘要计算失败、结果未知 | 不接受报告内容，不据此推进累计 ACK；保留失败或未完成原因 |
| 计算所得摘要与文件名中的摘要不同 | 判定文件校验失败，不使用其中的业务状态，不据此推进累计 ACK |
| 摘要相同 | 文件内容校验通过，再解析并校验报告结构及业务内容；满足累计确认条件后才能推进 ACK |

解析后的报告身份须与文件名中的 `report_id` 一致。文件校验通过不代替报告结构校验、业务覆盖检查和持久化接收，也不证明其他报告已经收到。校验失败不撤销客户端此前已经接受的事实或确认水位；camctl 继续按已有累计 ACK 和报告机会规则判断补投。

### 报告不可变

不变量：

```text
同一个 report_id
    → 内容永久不变

内容发生变化
    → 新 report_id
```

纯粹重新投递同一报告：

> 复用原 `report_id`。

同一报告的输出字节不变，因此摘要和最终文件名也保持不变。摘要由冻结依据生成的实际报告字节计算，不构成另一套业务身份。

重新投递本身不推进：

```text
change_seq
```

### 报告覆盖区间

每份报告的业务覆盖区间为 `(from_wm, to_wm]`，即不包含下界、包含上界。

| 生成依据 | 定义 |
| --- | --- |
| 历史上界 | 选定并冻结的完整已提交事务边界 |
| `from_wm` | 在该历史边界处已经持久化的客户端累计确认水位 |
| `to_wm` | 在该历史边界处最新的业务变化水位 |

三者从同一个一致的历史边界确定，满足 `from_wm ≤ to_wm`。之后发生的 ACK 推进或业务变化不修改这份报告的边界。两端相等时业务覆盖区间为空；是否需要执行报告处理继续按报告机会与本地职责规则判断。

| 业务变化的位置 | 本份报告如何处理 |
| --- | --- |
| `change_seq ≤ from_wm` | 已确认，无需因该次变化单独补报 |
| `from_wm < change_seq ≤ to_wm` | 纳入本份报告覆盖，选中对应实体 |
| `change_seq > to_wm` | 留给后续报告，本份报告不包含该次变化 |

实体在区间内发生过任一应报告变化，就纳入本份报告；同一实体在区间内的多次变化合并为该实体在冻结历史上界处的状态快照。选择实体及计算其状态均使用历史，不能用文件生成时的当前投影替代。

例如，报告覆盖 `(10, 15]`，某动作在业务水位 `12` 进入运行状态、在 `18` 完成。本份报告包含该动作在边界 `15` 处的运行状态；即使文件生成或补投时动作已经完成，内容仍保持相同。

报告边界必须包含完整事务。一次事务受理计划及其全部动作时，不能将边界放在该事务的部分业务变化之后。累计 ACK 引用已登记报告的上界，因此后续报告的下界也保持完整事务边界。

历史上界与业务水位承担不同职责。有效 ACK 和报告内部管理变化可以推进历史顺序，但不增加 `change_seq`；具体分类继续遵守“ACK 与业务变化”和“状态报告自身的管理”。

### 从历史重建报告

报告的权威依据是数据库中的不可变历史及已登记的生成依据，遵守[持久化与配置基础](../2026-09-08-camctl-cli-design.md#持久化与配置基础)。每份报告登记时冻结以下信息，后续重建始终使用同一组值：

| 生成依据 | 约束 |
| --- | --- |
| `report_id` | 报告的稳定身份 |
| 历史上界 | 已提交事务的完整边界，决定报告观察到的实体状态 |
| `from_wm`、`to_wm` | 按“报告覆盖区间”确定的业务范围 `(from_wm, to_wm]` |
| 固定生成元数据 | 内容中出现的生成时间等值在登记时确定；重建时不重新取值 |

报告登记历史及对应查询投影在同一数据库事务中提交，成功后成为可查询的已登记报告。登记必须校验这些生成依据相互一致；所引用的历史边界已经完整提交，登记自身的内部管理变化不属于这份报告的历史范围。生成依据及其所依赖的历史永久保留。

首次生成及补投均从冻结的历史边界计算实体快照，再按第一版确定的生成规则输出 JSON。后续动作状态变化、ACK 推进、配置变化和进程重启不能改变同一 `report_id` 的输出字节。字段及实体排列、数字和字符串编码等影响字节的规则必须确定。重建过程不查询当前设备状态，也不使用当前时间或当前配置补齐历史字段。

报告计算、JSON 生成和文件操作均在短写事务之外完成；报告登记成功后才能将完整 `staging` 文件发布到 `ready`。登记成功只表示生成依据已经持久化，本次报告机会是否完成仍取决于本地发布及会话收尾契约。

| 报告登记及生成依据 | 文件状态 | 处理依据 |
| --- | --- | --- |
| 尚未成功登记 | 任意临时文件 | 完成登记后才能发布；临时文件不能证明报告已登记 |
| 已登记，重建依据可可靠读取和解释 | 文件尚未生成，或此前文件已被删除 | 按报告机会及补投规则判断责任；需要发布时重建同一报告 |
| 已登记，重建依据可可靠读取和解释 | 仅有完整或未完成的 `staging` 文件 | 需要发布该报告时，按“staging 中报告的恢复”从头重新生成，完整后再发布 |
| 已登记，生成依据可信 | 文件位于 `ready` 或 `processing` | 遵守替换、领取和补投规则，避免重复排队；文件由对应所有者处理 |
| 已登记，但重建所需历史不可可靠读取或解释 | 需要生成或核验文件 | 保留诊断并按会话错误处理，不能以当前状态生成替代内容 |
| 提交结果不确定，或登记依据无法可靠读取 | 任意 | 按会话错误处理；恢复时先确认数据库事实，不凭文件存在与否推断登记结果 |

历史回放只恢复报告登记和管理状态；实际生成、发布和补投由报告机会驱动。业务变化需要新的报告时，选择新的历史边界并登记新的 `report_id`。数据库登记、文件发布和发布结果记录之间的完整断电对账仍由文件交接及报告完成证据契约细化。

### 报告内容

报告是基于 `change_seq` 的状态快照。

应报告的业务变化包括至少：

- 请求/计划注册；
- 计划受理拒绝及其原因；
- ACK 校验错误及其原因；
- action 状态变化；
- 持续设备效果与残留设备事实变化；
- output 登记及可用状态变化；
- 修复结果；
- 原片媒体信息和质量变化，包括核验未执行、已取得结果或核验未确认；判定及对录像终态的影响见[录像成功标准](camera-recording.md#录像成功标准)；
- 普通产物的 delivery 发布、撤回等变化；
- output 清理状态；
- 取消结果；
- 计划退役。

报告采用：

> 业务覆盖区间内发生变化的实体，在该报告冻结的历史上界处的状态快照。

不是逐事件日志导出。

普通交付的机器映射字段由[正式产物与取回清理](outputs.md)的“报告负责机器映射”定义；报告须包含这些字段，让客户端关联实际收到的文件。

录像检查结果遵守[第一版原片检查的范围](camera-recording.md#第一版原片检查的范围)，区分可靠视频时长、目标与修复门槛的判定、检查未完成或失败及已发现的媒体错误。时长检查通过不表示整段视频已通过逐帧解码；报告不能扩大实际检查所提供的保证。

计划受理和动作执行的业务结果由状态报告交给客户端，主程序按文件交接协议中转。会话正常结束时仍可能存在受理拒绝或动作失败，客户端以报告中的具体业务状态为依据。

### 状态报告自身的管理

状态报告的生成、发布、领取、补投、替换和清理属于内部管理变化，追加历史并同步更新管理投影，不推进 `change_seq`，也不因这些操作本身产生下一份报告。报告身份分配、观察到的文件位置和本地处理进度仍须按各自规则记录，支撑恢复及会话收尾判断。

| 发生变化的对象 | 变化的归属 | 对业务报告的影响 |
| --- | --- | --- |
| 状态报告自身的内容生成记录、文件发布或领取、补投、替换、清理记录 | 报告内部管理状态 | 不推进 `change_seq`，不新增业务报告责任 |
| 普通产物的交付状态，包括发布和撤回 | 业务状态 | 按业务变化规则推进 `change_seq` 并报告 |
| 请求、动作或其他业务实体，包括 `report_status` 动作自身的状态 | 业务状态 | 继续按对应业务规则报告 |

报告处理期间并发发生的业务变化，仍须被后续适用的报告覆盖。报告管理操作的内部状态更新不等于本地处理已经成功；失败、结果未知和未完成状态仍按文件交接、恢复及会话收尾规则处理。这里的清理针对报告文件，数据库记录遵守[全局数据保留规则](../2026-09-08-camctl-cli-design.md#持久化与配置基础)。报告文件的清理资格和恢复细节需在相应生命周期契约中细化。

### 客户端对受理结果的判断

客户端根据已经收到并保存的报告事实判断请求状态。报告是变化实体的快照，不是每次都列出全部历史请求；请求未出现可能源于报告生成较早、相关报告尚未送达或该报告不包含该实体。

| 已取得的报告证据 | 可以确认的结果 |
| --- | --- |
| 对应 `request_id` 的已受理计划实例或执行状态 | 该请求已经成功受理；即使动作尚未完成或执行失败，受理事实仍成立 |
| 能关联到某次输入的明确计划拒绝记录 | 那次输入被拒绝；该记录不能撤销已经确认的受理事实 |
| 既无请求受理证据，也无可关联的计划拒绝记录，包括未收到报告、报告未包含该请求或仅有 ACK 校验错误 | 尚未确认，不能据此断言未受理 |

新报告未包含某请求时，客户端保留此前已经确认的事实。客户端按[请求受理与会话](protocol-session.md#客户端确认与重送)保存和重送待确认请求，无需通过报告缺项证明提交失败。计划拒绝记录与具体输入的关联结构仍需在本专题细化。

### ACK

ACK（累计接收确认）通过计划中的以下字段提交：

```text
last_report_id
```

其含义是：

> 客户端已经持久化并接受足以完整覆盖截至该报告 `to_wm` 的状态。

它不是：

> 客户端见过的最大 report_id。

因此客户端收到更大的增量报告，但此前存在缺口时，不应推进累计 ACK。

一份新的合并报告如果已经完整补齐缺口，则可以直接推进到新的累计确认位置。

ACK 只单调推进。

### ACK 引用的报告记录

`last_report_id` 通过字段类型和范围校验后，camctl 在受理事务中查询同一状态库内对应的已登记报告，以该报告持久化的 `to_wm` 作为本次确认位置的依据。

| 报告记录查询结果 | 与当前累计确认位置的关系 | ACK 处理 |
| --- | --- | --- |
| 查到已登记报告，覆盖水位可可靠读取 | `to_wm` 更大 | 有效，累计确认位置推进至该 `to_wm` |
| 查到已登记报告，覆盖水位可可靠读取 | `to_wm` 相同或更小 | 有效，保持当前累计确认位置 |
| 查询成功，查不到对应报告 | 无可用覆盖水位 | 无效 ACK，保持确认位置并记录业务错误 |
| 查询失败，或报告记录无法提供可信的覆盖水位 | 无法可靠判断 | 会话错误，不能解释为报告不存在或吸收成功 |

报告文件位于 `ready`、`processing`，或已经被主程序删除，均不改变上述判定；ACK 的依据是已登记报告记录。`report_id` 用于定位报告，确认位置取自对应的 `to_wm`。即使输入 ID 小于已知报告 ID，也必须查询对应记录，不能据数值大小推定它有效。

有效 ACK 的序列影响及无效 ACK 的报告责任按“ACK 与业务变化”处理；计划受理仍遵守与 ACK 独立处理的规则。已登记报告及其覆盖水位永久保留，迟到的 ACK 仍可查询历史报告。登记时点由“从历史重建报告”定义。

### ACK 与业务变化

成功吸收有效 ACK 时，camctl 将确认位置的变化追加到历史，并在同一事务更新累计确认投影。ACK 推进本身不推进 `change_seq`，也不产生新的业务报告责任；有效的较旧或相同 ACK 保持确认位置，同样不产生新的业务报告责任。

| ACK 处理结果 | 其他新增业务变化 | 新增业务报告责任 |
| --- | --- | --- |
| 有效，确认位置推进或保持 | 无 | 无；不因 ACK 更新生成新报告 |
| 有效，确认位置推进或保持 | 有 | 按其他业务变化报告，ACK 本身不增加业务变化 |
| 无效 | 有或无 | 按既定规则记录并报告 ACK 校验错误，同时覆盖其他业务变化 |
| 未提供 | 无 | 无 |
| 未提供 | 有 | 按其他业务变化报告 |

本表适用于输入处理结果可靠保存的情况；ACK 更新的数据库写入失败或提交结果不确定仍按会话错误处理。

已有未确认内容在实际报告机会中仍按补投规则处理。判断补投范围时使用已持久化的累计确认位置；有效 ACK 不新增报告责任，也不表示其他尚未完成的报告或业务工作已经完成。与 ACK 同次提交的新计划注册、计划拒绝等变化，仍各自承担报告责任。

### submit 可以独立吸收 ACK

由于 `submit` 不要求墙钟可信，因此时钟异常期间也允许：

- 受理请求；
- 接收相同 `request_id` 的重试；
- 推进有效 ACK。

计划正文与 ACK 的组合结果统一由[请求受理与会话](protocol-session.md#计划正文与-ack-独立处理)定义。计划被拒绝时仍处理有效 ACK；ACK 无效时保留确认位置，记录面向客户端的业务错误，计划继续按请求 ID 复用或首次受理。已受理 ID 的重试关联原计划及其当前状态，ACK 独立处理。

### 报告生成点

正常 `run` 中：

1. 恢复/对账后；
2. `report_status` 执行时；
3. 会话收尾前。

`report_status` 只表示：

> 立即执行一次本地状态报告更新。

它不保证主程序会立即传输，更不保证客户端立即收到。

### 与会话收尾的协作

状态报告生成和发布属于本地处理责任。`run` 在关闭接纳之前完成本次报告机会应承担的工作，再按[请求受理与会话](protocol-session.md)的交接协议进行短写事务内的最终检查。

| 最终检查观察到的状态 | 对关闭接纳的影响 |
| --- | --- |
| 报告准备期间出现新的应报告业务变化，当前报告处理结果尚未覆盖 | 保持接纳资格，完成新增报告责任后再检查 |
| 本次报告机会的本地处理已完成，且没有新增应报告责任 | 报告方面允许关闭接纳；其他动作和收场责任仍需检查 |
| 仅剩本地发送或客户端 ACK 尚未完成 | 不要求 `run` 持续等待 |
| 本地报告职责是否完成无法确认 | 保留诊断并按错误处理，不能当作已经完成 |

这里的业务变化包含受理拒绝及 ACK 校验错误，不依赖新计划受理序列是否推进。报告构建与文件发布在短交接事务之外执行；报告内容、覆盖水位和本地完成证据必须相互一致。

为完成同一次收尾而反复进行的交接检查，不各自构成新的报告机会。本次机会已完成本地处理且没有新增业务变化时，主程序随后领取或删除文件不会使该收尾循环不断补投。下一次实际报告机会仍按报告补投规则检查未确认状态。

## 报告文件与交接目录

状态报告是 `ready` 中唯一允许被“更新替换”的特殊文件类型。

### staging 中报告的恢复

恢复时，对于 `staging` 中残留的报告文件，camctl 先确认数据库中的报告登记及生成依据可用，并检查 `ready` 和 `processing` 中是否已有同一 `report_id` 的报告。已有报告时按对应目录规则处理；目录检查失败或结果无法确认时，不能当作文件不存在。

确认只有 `staging` 中有该报告，且按报告机会、覆盖范围及补投规则仍需发布它时，第一版统一从头生成文件。原 `staging` 文件无论只写了一部分还是已经写完，都由完整重新生成的内容替代。

重新生成使用数据库中冻结的历史边界、覆盖水位和生成元数据，保持原 `report_id` 和内容。完整生成后按[状态报告发布前落盘](file-handoff.md#状态报告发布前落盘)完成文件同步、移动及后续记录。重建或文件写入失败时，保留诊断并按会话错误处理，未完成文件留在 `staging`，不进入 `ready`。

本节定义状态报告文件的恢复；普通产物的生成、拷贝及取回恢复由[正式产物与取回清理](outputs.md)定义。

### 恢复时识别已发布报告

第一版通过交接目录中的文件位置及对应的数据库报告登记识别已发布报告，不常规读取全文、解析 JSON 或重建预期内容来比对文件。该判断以发布流程正确执行、报告内容发布后保持不变且存储未损坏为前提；报告在对主程序可见前已经完整写入并落盘，具体顺序见文件交接专题。

camctl 在 `ready` 或 `processing` 发现报告文件，并可靠确认文件名中的 `report_id` 对应数据库中的已登记报告后，按所在目录处理已有报告。数据库缺少已发布记录时，追加“恢复时发现该报告已发布”的事实并同步更新投影，保留现有文件，不重复生成或投放，也不推测断电前的准确发布时间。

文件名须符合“文件名与完整性校验”的格式。文件身份无法关联，或目录、数据库读取失败及结果不确定时，不能据此认定报告已经发布或不存在，应保留诊断并按错误处理。这里的识别用于本地交接恢复；客户端收到报告后仍须计算文件摘要并按文件名校验。

### 记录报告已经发布

camctl 成功将完整报告从 `staging` 放入 `ready` 后，在数据库中记录“这份报告已经发布过”。顺序为：

```text
报告已登记
    → staging 文件完整写入并同步
    → 原子移动到 ready
    → 完成本次移动涉及的目录同步
    → 提交该报告的已发布记录
```

已发布记录关联对应的 `report_id`，追加到不可变历史，并在同一数据库事务中更新报告投影。首次发布和后续成功补投均记录各自的发布事实；报告身份及内容继续遵守原有规则。文件发布在数据库写事务之外执行。

主程序可能在 camctl 写入记录前就取走并删除文件。当前 camctl 进程可靠确认放入 `ready` 及所需同步成功后，就依据这些结果写入记录，无需等文件仍留在目录中。文件后来被领取或删除，也不改变“曾经成功发布”的历史事实。

该记录证明 camctl 发布过报告；它不能证明文件目前还在 `ready`，也不能证明客户端已经收到报告。后续补投仍依据累计 ACK 和对应的文件规则判断。

放入 `ready` 失败或结果无法确认时，不能写成发布成功。目录同步及数据库记录保存的失败按文件交接及会话错误规则处理。重启后仍能找到报告文件时，按“恢复时识别已发布报告”处理；文件已不在交接目录时，继续按 ACK 和报告补投规则判断，不能仅凭缺少已发布记录断定文件从未发布。

### ready 中至多一个待领取状态报告

如果：

```text
ready 中已有 report R1
```

且没有新的业务变化：

> 保留 R1，不重新生成。

如果出现新变化：

1. 根据一致的历史边界及该边界下的累计 ACK 水位，冻结新报告 R2 的覆盖范围和生成元数据，提交登记历史及投影；
2. 按 R2 的冻结依据从历史重建合并快照，生成 `staging` 文件；
3. 完整生成后撤下 ready 中的 R1；
4. 发布 R2；成功后按“记录报告已经发布”保存发布事实。

R1 的逻辑报告记录本身仍不可变。

### processing 报告不可修改

如果主程序已经领取：

```text
processing/status-report-42-<sha256>.json
```

CLI 不修改、不撤回它。

此时产生新状态时，可以同时出现：

```text
processing/status-report-42-<sha256>.json
ready/status-report-47-<sha256>.json
```

这是合法状态。

### 防止频繁裸 run 产生大量重复报告

只要覆盖未确认状态的报告仍然：

- 位于 `ready`；
- 或位于 `processing`；

就不因为又启动了一次裸 `run` 而排入一份完全相同的报告。

报告可能因主程序传输失败或中断而残留在 `processing`。主程序是否会再次处理该文件未知，详见[文件交接](file-handoff.md#processing)。上述避免重复排队的规则不构成后续一定送达的保证；文件持续残留时，camctl 也不据此判断客户端已经收到。

### 本地传输完成后仍未 ACK

主程序删除 processing 文件只表示：

> 主程序判定本地传输已经完成。

远端是否收到未知。

如果累计 ACK 仍未推进，且：

```text
ready
processing
```

都已经没有能够承担该未确认状态的报告，则下一次报告机会重新承担补投责任。

没有新业务变化：

> 从数据库历史及原报告的冻结依据重建内容，使用原 `report_id` 重新投递，文件字节与首次发布相同。

出现新业务变化：

> 生成新的合并报告和新 report_id。

这样避免：

```text
每次裸 run
    → 新报告
    → 主程序重复排队传输
```

同时仍保留在没有远端接收确认时的自动补救能力。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

历史记录承载业务变化、报告登记及内部管理变化，是状态计算的权威来源。报告查询投影提供 `report_id`、`from_wm`、`to_wm`、历史上界、固定生成元数据，以及文件发布状态；累计 ACK 投影提供当前确认位置。各次变化的历史及相关投影在同一事务中提交。具体表划分和字段命名仍属实现设计。

业务状态变化通过 `change_seq` 驱动报告覆盖；全部历史变更的顺序用于历史回放，两者按全局规则区分。报告内部管理状态遵守“状态报告自身的管理”规则，报告对外输出实体快照。

## 验收要求

### 单元测试

隔离历史存储和文件交接协作者，验证报告覆盖、ACK 单调推进、合并、纯重投复用身份及补投资格。历史计算验证固定边界下的实体状态；JSON 生成验证冻结元数据下的确定性，包括字段排列和特殊字符。

使用已知字节及独立确定的 SHA-256 预期验证文件名包含完整的小写摘要。按客户端检查表覆盖文件名非法、摘要缺失或长度错误、读取及计算失败、摘要不匹配和匹配的情况；另行覆盖摘要正确但 JSON 或报告结构不合法、报告身份不一致及累计覆盖存在缺口，验证文件校验通过不能直接授权 ACK。

按“报告覆盖区间”覆盖变化位于下界之前、恰好等于下界、区间内部、恰好等于上界及上界之后的情况，并覆盖两端相等的空区间。同一实体分别组合区间内变化和上界后的变化，验证选中实体及其历史状态；区间内多次变化应得到一份边界处的实体快照。

按“ACK 引用的报告记录”决策表覆盖已登记报告的确认推进与保持、未知报告及查询失败。未知 ID 分别覆盖小于和大于已知报告 ID 的情况；确认位置的预期取自对应报告覆盖水位，不以 ID 数值替代。

按“ACK 与业务变化”决策表覆盖各分区，断言有效 ACK 自身不推进 `change_seq`、不新增业务报告责任，其他业务变化和 ACK 校验错误仍按各自规则报告。

按变化对象区分状态报告内部管理、普通产物交付和动作状态，验证各自的序列及报告责任，包含 `report_status` 动作状态与其生成报告的管理状态分别处理。

验证恢复识别使用目录位置、文件身份及数据库登记，不调用全文校验或报告重建来确认完整性。覆盖报告位于 `ready`、`processing`，已发布记录存在或缺失，以及身份无法关联、目录或数据库读取失败的情况；缺少已发布记录时保存恢复观察，不虚构历史发布时间。

### 集成测试

使用真实 SQLite 与交接目录验证快照生成期间的并发业务变化、报告替换与领取、重启恢复和乱序报告消费。组合报告生成、文件交接和客户端接收校验，验证文件名中的摘要对应实际发布字节，主程序传递完整文件名与内容，客户端校验后才接受报告。

分别截断报告、改变内容但保持合法 JSON，以及改变空白或换行，保留原文件名，验证客户端均发现摘要不匹配，且不采用该报告的业务状态或推进 ACK。覆盖原样传输、文件名被截断或改写，以及摘要正确但报告结构或身份不合法的情况。补投和断电重建须保持原报告的 ID、全部字节、摘要及文件名；本地恢复识别继续遵守不常规全文校验的规则。

验证报告身份、历史边界、覆盖水位及生成元数据的登记历史与投影一同提交。分别在提交前、提交后文件生成前、`staging` 写入期间中断，恢复后按数据库登记状态处理。报告选择的历史边界不能拆开同一事务中的业务变化。

分别保留只写了一部分及已经写完的 `staging` 报告，在仍需发布、且 `ready` 和 `processing` 均没有同一报告时恢复，验证均从冻结依据完整重新生成，保持原 ID 和内容，完整后才发布。另行覆盖同一报告已在 `ready` 或 `processing`、目录检查失败，以及重新生成过程中再次中断，验证不会把已有交接文件重复排队，也不会发布半成品。

使用一次事务受理计划及全部动作，验证报告边界只能位于整次受理之前或之后，不能只覆盖部分注册结果。报告冻结后并发推进 ACK 或提交业务变化，验证已登记报告的下界、上界及实体快照保持原值，后续报告再按新的历史边界确定覆盖范围。

删除已交接的报告文件后，在符合补投条件时重建文件，逐字节断言与首次发布文件相同，并覆盖特殊字符。分别在动作状态变化、ACK 推进、配置修改及进程重启后重建同一报告，验证仍使用原历史边界和生成元数据；新业务报告采用独立 ID。历史不可可靠读取或解释时须明确失败。

验证回放报告历史能够恢复登记、覆盖水位和累计 ACK 状态，且不生成文件、不执行补投、不新增业务变化或重新分配序列。恢复后的实际报告机会按文件交接事实执行必要工作。

使用已受理请求的重试提交有效 ACK，验证确认位置持久化且 `change_seq` 不因 ACK 改变。分别组合无其他工作、已有未确认内容及新增业务变化，验证后续报告机会和会话收尾按实际剩余责任处理；有效 ACK 不触发用于确认该 ACK 的新报告。

两个计划输入入口均使用真实报告记录验证：报告文件位于 `ready`、`processing` 或已被主程序删除时，ACK 仍按持久化覆盖水位吸收；未知报告 ID 保持确认位置并记录 ACK 错误，同次合法计划仍按规则受理或复用。

使用真实状态库与交接目录验证报告生成、发布、领取、补投、替换和清理后，仅有内部管理变化时 `change_seq` 保持不变。另行组合普通产物交付或动作状态变化，验证业务变化仍被报告；报告管理失败及恢复仍保留可诊断状态，不被视为本地职责已完成。

验证成功放入 `ready` 后才提交对应 `report_id` 的发布历史与投影。让主程序在放入成功后、记录提交前领取并删除文件，验证 camctl 仍能依据已确认的发布结果保存记录，重启后该事实仍可查询。首次发布和成功补投分别记录发布事实，且不推进 `change_seq` 或累计 ACK。发布失败或结果未知时不记录成功；发布后的数据库写入失败或提交结果不确定时按会话错误处理。

分别保留 `ready` 或 `processing` 中的已登记报告，但不保留已发布记录，再启动恢复。验证 camctl 从文件位置及报告登记补记恢复观察，保持已有文件及所属目录，且不重复投放该报告。

累计 ACK 推进且报告文件被清理后，验证数据库中的报告、覆盖水位和既有错误记录仍保留；重启后收到较旧的合法 ACK 时仍能查到对应报告并保持当前确认位置。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 状态报告

- 同一逻辑报告内容不可变；
- 纯重投复用 ID；
- 新状态创建新 ID；
- ready 至多一个待领取报告；
- ready 合并替换；
- processing 与新 ready 报告并存；
- 无 ACK 时本地传输完成且文件被删除后的再次补投；
- 累计 ACK；
- 有效的较旧或相同 ACK 不产生错误、不回退确认位置；
- 无效 ACK 保持确认位置并进入业务报告，相关计划受理结果按请求专题的独立处理规则表达；
- 重叠快照幂等消费。
- 会话正常结束时，计划拒绝和动作失败仍在状态报告中如实表达。
- 待确认请求未出现在报告中或报告迟到时，客户端保持尚未确认；已有受理事实不因后续报告缺项而丢失；
- 能关联的计划拒绝只说明对应输入被拒绝，ACK 校验错误本身不能证明计划被拒绝；
- 计划实例或执行状态可以确认受理，动作尚未完成或执行失败不改变该事实；
- 报告准备期间发生受理拒绝等变化时，收尾前补齐覆盖，即使 `plan_seq` 未推进；
- 同一收尾过程的重复交接检查不会仅因文件被领取或删除而无限补投；
- 报告完成证据不足时，不允许通过会话最终检查。

## 待确认与待细化

本节不构成已确认的行为选择。涉及其结果的实现须先补齐契约。

### 后续契约完善

定义报告机器结构、初始业务水位和累计确认水位的表示，以及 `last_report_id` 的字段类型和合法范围。完整分类 ACK 不变/推进、业务无变化/有变化、已有覆盖报告位于 ready/processing/均不存在的有效组合，补齐各组合的文件处理及补投规则。

细化历史边界与业务覆盖水位的存储关联、生成元数据字段，以及第一版历史解释和 JSON 生成规则。按已确认的覆盖区间和实体选择规则，定义具体实体字段、排列顺序、数字及字符串编码。

已发布记录和恢复观察分别按“记录报告已经发布”及“恢复时识别已发布报告”保存。还需定义请求受理和会话退出检查如何结合这些记录、覆盖范围及已有文件判断本次报告处理是否完成。需要区分新增业务尚未报告、本次报告处理未完成、已经发布但远端尚未 ACK，以及文件发布结果未知等状态。

计划受理拒绝及 ACK 校验错误的报告记录需要补齐。须明确有有效 `request_id`、缺少或无法解析 `request_id` 等状态的关联方式，以及重复输入、断电恢复、报告补投和 ACK 后的状态处理。错误记录永久保留，且不能改变已受理请求的执行意图。
