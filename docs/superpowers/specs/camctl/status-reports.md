# 状态报告与累计确认

[返回设计总览](../2026-09-08-camctl-cli-design.md) · [阅读路线](reading-guide.md)

本专题定义状态快照、报告身份、累计 ACK 和报告补投。`last_report_id` 通过[请求受理与会话](protocol-session.md)的计划入口提交；报告文件的所有权与基本发布规则见[文件交接](file-handoff.md)。

第一版为一个逻辑客户端保存累计确认水位。客户端需要重新取得状态时，使用[客户端状态同步](status-sync.md)的完整或局部同步入口；两者均保留本专题的累计 ACK 和自动报告机制。

普通产物的交付记录包含实际文件名 `file_name` 和完整可读名称 `display_name`，并显式关联 delivery、output 及来源动作；字段语义与客户端匹配规则见[报告负责机器映射](outputs.md#报告负责机器映射)。

拍摄动作的报告表达目标设备、动作类型、参数类型、调用方输入参数，以及合法受理时已确定的生效参数。两类参数分别表达，便于客户端理解驱动默认值；参数错误的动作保留原始输入和具体诊断，不补造合法的生效参数。报告从冻结的数据库历史生成这些内容，不读取客户端预设，也不调用当前驱动重新套用默认值。参数来源与固化规则见[计划字段与参数校验](camera-capabilities.md#计划字段与参数校验)。

[状态报告字段契约](report-format.md)及其 [JSON Schema](schemas/status-report.schema.json) 定义报告结构、字段出现条件和语义检查；[客户端协议样例](client-protocol-examples.md)提供完整报告、配套计划和客户端合并结果。报告选择、历史边界及累计确认的业务规则由本专题定义。

**阅读提示：** 先看正常报告流程，再读报告编号、覆盖范围和合并。ACK 表示客户端已保存报告覆盖的状态；水位表示覆盖到哪次业务变化，背景与数字例子见[状态报告为什么需要确认](concepts.md#状态报告为什么需要确认)。文件补投另见[报告发布](report-publication.md)。

## 正常报告与确认流程

camctl 在报告机会到来时，冻结一个完整的数据库历史边界，生成覆盖客户端尚未确认业务变化的快照。在 `staging` 生成最终字节和摘要后，以 `status-report-<report_id>-<sha256>.json` 发布到 `ready`，并保存本地发布事实。

主程序原样中转。客户端先验证报告文件摘要及内容，再保存业务状态；普通文件按报告中的 `file_name` 关联并核验。客户端确认累计覆盖完整并持久化接收后，通过后续计划输入的 `last_report_id` 表达累计确认，camctl 保存确认水位。视频是否已经收到不影响报告自身的累计确认含义，也不授权自动删除正式源产物。

## 状态报告与 ACK

### report_id

每份逻辑报告具有单调递增的：

```text
report_id
```

### 报告编号与水位的数值范围

第一版 `report_id` 与输入 ACK 的 `last_report_id` 均使用 JSON 正整数，合法范围为 1～9007199254740991；布尔值和数字字符串不合法。`last_report_id` 省略表示没有提交新 ACK，显式提供 0 或 `null` 则属于 ACK 校验错误，不影响合法计划的受理或复用。

`change_seq` 从 0 表示尚无业务变化的位置，业务覆盖水位 `from_wm`、`to_wm` 及累计确认水位均为 0～9007199254740991 的整数。没有已吸收 ACK 时累计确认水位为 0；报告继续满足 `from_wm ≤ to_wm`。这些数值保持精确，不通过浮点舍入改变身份或覆盖区间。编号和水位达到上限时，不能回绕或复用旧值；不能再可靠分配所需序列时按状态库会话错误处理。

整数值的类型判断遵守[执行计划输入契约](plan-input.md#输入文件与基本值类型)。合法数字仅代表通过静态校验，ACK 仍须查询其对应的实际报告及覆盖水位。

### 文件名与完整性校验

文件名：

```text
status-report-<report_id>-<sha256>.json
```

`sha256` 是最终报告文件全部原始字节的 SHA-256，以完整的 64 位小写十六进制字符串表示。摘要覆盖实际输出的编码、空白及换行；客户端直接对收到的文件字节计算，不能先解析 JSON 再重新序列化计算。

camctl 在 `staging` 完整生成报告并计算摘要，确定最终文件名后，按[状态报告发布前落盘](file-handoff.md#状态报告发布前落盘)完成同步和原子发布。生成、摘要计算失败或结果未知时不发布，按会话错误处理。主程序保留文件名和内容进行搬运及传输，无须解析报告或计算摘要。部署与对接须确认文件系统和传输协议能够保留完整文件名。

客户端按以下顺序检查收到的报告：

| 检查结果 | 处理 |
| --- | --- |
| 文件名不符合约定，无法取得合法报告 ID 或完整摘要 | 不接受为有效报告，不据此推进累计 ACK |
| 文件内容无法完整读取，或摘要计算失败、结果未知 | 不接受报告内容，不据此推进累计 ACK；保留失败或未完成原因 |
| 计算所得摘要与文件名中的摘要不同 | 判定文件校验失败，不使用其中的业务状态，不据此推进累计 ACK |
| 摘要相同 | 文件内容校验通过，再解析并校验报告结构及业务内容；满足累计确认条件后才能推进 ACK |

解析后的报告身份须与文件名中的 `report_id` 一致。文件校验通过不代替报告结构校验、业务覆盖检查和持久化接收，也不证明其他报告已经收到。校验失败不撤销客户端此前已经接受的事实或确认水位；camctl 继续按已有累计 ACK 和报告机会规则判断补投。

### 报告不可变

不变量：

```text
同一个 report_id
    → 内容永久不变

内容发生变化
    → 新 report_id
```

纯粹重新投递同一报告：

> 复用原 `report_id`。

同一报告的输出字节不变，因此摘要和最终文件名也保持不变。摘要由冻结依据生成的实际报告字节计算，不构成另一套业务身份。

重新投递本身不推进：

```text
change_seq
```

后文用区间 `(from_wm, to_wm]` 表达报告覆盖：左边不包含、右边包含。例如 `(10, 15]` 包含序号大于 10 且不超过 15 的业务变化。这个区间决定选择哪些对象；每个被选对象的字段仍取自同一个报告截止位置。

### 报告覆盖区间

每份报告的业务覆盖区间为 `(from_wm, to_wm]`，即不包含下界、包含上界。

| 生成依据 | 定义 |
| --- | --- |
| 历史上界 | 选定并冻结的完整已提交事务边界 |
| `from_wm` | 按[同步报告范围](status-sync.md#报告范围)取得累计确认水位与全部有效同步起点中的最小值；无同步责任时为累计确认水位 |
| `to_wm` | 在该历史边界处最新的业务变化水位 |

三者及当前有效的同步责任从同一个一致的历史边界确定，满足 `from_wm ≤ to_wm`。之后发生的 ACK 推进、同步责任变化或业务变化不修改这份报告的边界。两端相等时业务覆盖区间为空；是否需要执行报告处理继续按报告机会与本地职责规则判断。同步起点、责任生效与结束由[状态同步](status-sync.md#camctl-何时开始同步)定义。

| 业务变化的位置 | 本份报告如何处理 |
| --- | --- |
| `change_seq ≤ from_wm` | 已确认，无需因该次变化单独补报 |
| `from_wm < change_seq ≤ to_wm` | 纳入本份报告覆盖，选中对应实体 |
| `change_seq > to_wm` | 留给后续报告，本份报告不包含该次变化 |

实体在区间内发生过任一应报告变化，就纳入本份报告；同一实体在区间内的多次变化合并为该实体在冻结历史上界处的状态快照。嵌套组织时还须携带这些实体的所属计划和动作，规则见[按计划嵌套与客户端合并](#按计划嵌套与客户端合并)。选择实体及计算其状态均使用历史，不能用文件生成时的当前投影替代。

例如，报告覆盖 `(10, 15]`，某动作在业务水位 `12` 进入运行状态、在 `18` 完成。本份报告包含该动作在边界 `15` 处的运行状态；即使文件生成或补投时动作已经完成，内容仍保持相同。

报告边界必须包含完整事务。一次事务受理计划及其全部动作时，不能将边界放在该事务的部分业务变化之后。累计 ACK 引用已登记报告的上界，因此后续报告的下界也保持完整事务边界。

历史上界与业务水位承担不同职责。有效 ACK 和报告内部管理变化可以推进历史顺序，但不增加 `change_seq`；具体分类继续遵守“ACK 与业务变化”和“状态报告自身的管理”。

### 按计划嵌套与客户端合并

报告按计划嵌套组织业务对象。每个出现的对象携带完整的自身字段；所属子集合只列出本份报告需要更新的成员，客户端按各自 ID 合并。

| 对象 | 在报告中的位置 | 合并身份 |
| --- | --- | --- |
| 计划 | 顶层 `plans` 集合 | `plan_instance_id` |
| 动作 | 所属计划的 `actions` 集合 | `action_instance_id` |
| 正式产物 | 来源动作的 `outputs` 集合 | `output_id` |
| 普通交付 | 发起取回动作的 `deliveries` 集合 | `delivery_id` |
| 计划文件诊断 | 顶层 `plan_file_diagnostics` 集合 | `diagnostic_id` |

名称用于人类阅读，不能替代这些 ID；数组顺序不承担对象身份。其余应报告的业务事实按所属对象组织。计划文件诊断使用独立顶层集合，包括能够取得请求身份的 ACK 错误；它描述某次文件处理，不作为计划或动作的当前执行状态。字段和处理边界见[计划文件诊断](#计划文件诊断)。

先按业务覆盖区间选择发生变化的实体，再补齐承载这些实体的父对象。例如，仅交付 D 发生变化时，报告包含 D、发起取回的动作和该动作所属计划；父对象同样携带完整自身字段，其他没有入选的动作、产物及交付不因此全部加入报告。补齐父对象只影响报告内容，不产生业务变化，也不推进 `change_seq`。所有入选实体及补齐父对象均取自同一冻结历史上界，不能使用当前投影补齐父对象。

对象自身字段与子集合由报告结构统一区分。例如，计划的名称、状态属于自身字段，`actions` 是子集合；动作的参数和结果属于自身字段，`outputs`、`deliveries` 是子集合。参数或结果字段即使采用 JSON 对象或数组表示，也按所属对象的完整自身字段更新；只有协议明确声明的实体子集合才按 ID 合并。

以下合并规则适用于报告已通过校验，并且其覆盖范围与接收顺序允许应用的情况：

| 收到的内容与客户端已有记录 | 合并结果 |
| --- | --- |
| 对象 ID 在客户端尚不存在 | 创建该对象，保存完整自身字段，再按 ID 合并携带的子集合 |
| 对象 ID 已存在 | 整体更新其自身字段，再按 ID 合并携带的子集合 |
| 完整自身字段中某个合法可选字段未出现 | 该对象在报告边界处没有此字段；移除客户端保留的该字段旧值，不能把旧等待原因等信息拼接到新快照中 |
| 已有子集合成员未出现在本份报告中 | 保留该成员，不因缺席而删除或改写它 |
| 子集合为空或未携带 | 本份报告没有该子集合的成员更新，保留客户端已有成员 |
| 产物已清理、交付已撤回或动作已取消 | 根据出现的对象快照更新对应状态，保留其身份与历史关联 |

必填字段缺失仍属于报告结构错误；可选字段的缺省含义不能将未知、未完成等业务状态合并为不存在，需表达的状态按相应实体字段契约显式提供。完整自身字段更新不等于替换整棵计划或动作子树，也不要求为每个对象增加容器或快照类型标记。

例如，客户端已有计划 P 的动作 A 为 `succeeded`、B 为 `running`。B 完成后，报告携带 P 的完整自身字段（状态为 `completed`）和 B 的完整自身字段（状态为 `succeeded`），未变化的 A 可以不出现。客户端更新 P 和 B，继续保留 A。仅 P 自身变化时，可以只携带 P 的自身字段，而不重复发送其全部动作。

跨计划取回仍按对象所属关系组织：P1 的录像动作 A 产生正式产物 O，P2 的取回动作 B 创建交付 D，则 O 位于 P1/A 下，D 位于 P2/B 下。D 通过 `output_id` 和 `source_action_instance_id` 引用 O 和 A，并通过所属取回动作关联本次取回。交付自身仍须包含[报告负责机器映射](outputs.md#报告负责机器映射)规定的字段；不会因为 D 出现就复制 O 到 P2，或要求未变化的 P1/A/O 同时出现。

报告没有携带某个实体不表示它已被删除。重复报告、乱序报告及覆盖缺口继续遵守报告校验与累计确认规则；嵌套合并不能让较旧快照覆盖已经应用的较新状态，也不能仅凭收到较大的 `report_id` 就越过覆盖缺口推进累计确认。

### 计划文件诊断

顶层 `plan_file_diagnostics` 报告执行计划文件读取、解析、整份受理校验及 ACK 校验中发现的问题。每次 `run <plan-path>` 或 `submit <plan-path>` 的输入处理中，有此类问题才形成一条诊断；同次输入的多个问题集中在该条记录中。裸 `run` 没有新输入文件，不为历史恢复、报告生成或补投创建新的输入诊断。动作自身错误、设备执行错误及会话错误按各自契约表达。

#### 记录字段

每条记录具有以下完整自身字段：

| 字段 | 条件与含义 |
| --- | --- |
| `diagnostic_id` | 必填，camctl 分配的稳定标识，遵守[标识字符串范围](plan-input.md#输入文件与基本值类型)；在当前主机历史中唯一，不复用 |
| `file_name` | 必填，取本次实际传入 `<plan-path>` 的文件名部分，不依赖文件是否能打开、完整读取或解析 |
| `request_id` | 可选；仅在文件完整读取、无歧义解析且该字段通过标识校验时提供；否则省略 |
| `errors` | 必填的非空数组，集中保存本次已经确定的相关错误；每项使用 `code`、`stage`、`details` |

`file_name` 保留调用方传入路径中的实际文件名称，不替换为 JSON 内的计划 `name`，也不通过解析符号链接改成另一个名称。它是文件系统名称，不套用计划可读名称的长度和字符约束。完整主机路径继续保存在本地诊断中。文件名用于展示和定位，不要求跨输入唯一；主程序改过名时，报告反映 camctl 实际收到的名称。客户端可以利用已知文件名对应关系辅助定位，但不能仅凭名称推导 `request_id`、认定计划已受理或改写计划状态。

`request_id` 提供时，仅表示本次输入携带了这个合法请求身份，不证明本次计划被接受。同一 ID 尚未成功受理时可能有多个被拒绝的输入；后来成功受理后，这些历史诊断仍然成立。文件无法完整读取或解析时，即使已读片段或文件名包含类似 ID 的文字，也不填写该字段；字段本身非法时，实际错误值可保留在相应 `details` 中。

#### 错误归属与阶段

下表根据公共输入契约的处理顺序判定；计划和 ACK 的业务结果独立，仍在同次受理事务中保存。

| 本次处理情况 | 诊断记录 | 计划及动作 |
| --- | --- | --- |
| 文件打开、读取、解码或解析失败 | 一条文件诊断，记录实际失败阶段，不带 `request_id` | 不从片段受理计划或吸收 ACK |
| 解析成功，出现整份拒绝条件 | 一条文件诊断，包含已确定的整份拒绝原因，以及独立发现的 ACK 错误；合法请求 ID 可附带 | 不注册本次计划或动作，合法 ACK 仍可吸收 |
| 计划正常受理或幂等复用，但 ACK 校验错误 | 一条文件诊断，包含 ACK 错误 | 计划受理或复用不受该错误影响 |
| 已支持动作仅有自身参数错误，且没有上述问题 | 不创建文件诊断 | 计划受理，错误保存在对应动作，动作初始 `failed` |
| 动作自身参数错误与 ACK 错误同时存在 | 文件诊断只包含 ACK 错误 | 动作自身错误仍在动作下面，不重复列入文件诊断 |
| 计划和 ACK 处理均无此类问题 | 不创建文件诊断 | 按正常受理或复用结果处理 |
| 处理结果无法可靠保存或提交结果未知 | 不宣称诊断一定已保存或一定未保存 | 按会话错误和事务恢复规则处理 |

文件诊断中的 `stage` 使用下列值，表示发现错误的阶段，不表示整个会话执行失败：

| `stage` | 含义 |
| --- | --- |
| `input_read` | 打开或读取本次文件失败 |
| `input_parse` | UTF-8 解码或完整 JSON 解析失败 |
| `admission` | 公共结构、动作名称或类型等整份受理校验失败 |
| `ack` | 当前输入的 `last_report_id` 校验失败 |

错误内容只记录实际已确定的事实。字段路径针对本次输入，数组下标从 0 开始；缺失字段不补造 `value`，无法解析的文件不补造结构化字段路径。具体错误码及 `details` 按对应校验契约解释，客户端样例中的已定义表达见[计划文件诊断样例](client-protocol-examples.md#计划文件诊断样例)。

#### 持久化、重复输入与报告合并

一条诊断的身份、文件名、合法请求 ID 及全部错误，与同次输入的计划处理结果、适用的 ACK 更新一起原子提交。诊断历史及其投影使用同一事务；提交后这条诊断的内容固定，永久保留。诊断的产生是应报告的业务变化，纳入 `change_seq`；读取、重建、重复发布这条诊断不产生新的业务变化。

同一请求重新通过命令入口提交文件，是另一次输入处理；如果再次产生文件诊断，则分配新的 `diagnostic_id`，即使文件名、请求 ID 和错误完全相同。已有成功受理关联的请求仍跳过本次正文校验，只独立处理当前 ACK；新的诊断不重新执行原计划。对已提交记录的恢复和报告重建复用原诊断 ID，不将同一持久化事实解释为新的输入尝试。

报告从覆盖区间内的诊断创建事实选择记录，每条都携带完整自身字段，使用同一冻结历史上界。`errors` 是该条记录的普通数组，不是按 ID 合并的实体子集合。客户端按 `diagnostic_id` 保存整条记录；重复收到同一诊断不增加条目，不同 ID 表示不同输入处理，可以在界面汇总相同问题的发生次数。

`plan_file_diagnostics` 缺席或为空表示本报告没有该集合的更新，不删除客户端已有诊断。累计 ACK 使用统一业务覆盖水位；确认后这些记录不因其历史存在而再次产生待报告变化，数据库历史与客户端已保存记录继续保留。诊断不反向修改计划状态：客户端以 `plans` 中的请求关联确认受理，不能让迟到的历史拒绝诊断覆盖后来取得的受理证据。

### 从历史重建报告

报告的权威依据是数据库中的不可变历史及已登记的生成依据，遵守[持久化与配置基础](system-foundations.md#持久化与配置基础)。每份报告登记时冻结以下信息，后续重建始终使用同一组值：

| 生成依据 | 约束 |
| --- | --- |
| `report_id` | 报告的稳定身份 |
| 历史上界 | 已提交事务的完整边界，决定报告观察到的实体状态 |
| `from_wm`、`to_wm` | 按“报告覆盖区间”确定的业务范围 `(from_wm, to_wm]` |
| 固定生成元数据 | 内容中出现的生成时间等值在登记时确定；重建时不重新取值 |

报告登记历史及对应查询投影在同一数据库事务中提交，成功后成为可查询的已登记报告。登记必须校验这些生成依据相互一致；所引用的历史边界已经完整提交，登记自身的内部管理变化不属于这份报告的历史范围。生成依据及其所依赖的历史永久保留。

首次生成及补投均从冻结的历史边界计算实体快照，再按第一版确定的生成规则输出 JSON。后续动作状态变化、ACK 推进、配置变化和进程重启不能改变同一 `report_id` 的输出字节。字段及实体排列、数字和字符串编码等影响字节的规则必须确定。重建过程不查询当前设备状态，也不使用当前时间或当前配置补齐历史字段。

报告计算、JSON 生成和文件操作均在短写事务之外完成；报告登记成功后才能将完整 `staging` 文件发布到 `ready`。登记成功只表示生成依据已经持久化，本次报告机会是否完成仍取决于本地发布及会话收尾契约。

| 报告登记及生成依据 | 文件状态 | 处理依据 |
| --- | --- | --- |
| 尚未成功登记 | 任意临时文件 | 完成登记后才能发布；临时文件不能证明报告已登记 |
| 已登记，重建依据可可靠读取和解释 | 文件尚未生成，或此前文件已被删除 | 按报告机会及补投规则判断责任；需要发布时重建同一报告 |
| 已登记，重建依据可可靠读取和解释 | 仅有完整或未完成的 `staging` 文件 | 需要发布该报告时，按[staging 中报告的恢复](report-publication.md#staging-中报告的恢复)从头重新生成，完整后再发布 |
| 已登记，生成依据可信 | 文件位于 `ready` 或 `processing` | 遵守替换、领取和补投规则，避免重复排队；文件由对应所有者处理 |
| 已登记，但重建所需历史不可可靠读取或解释 | 需要生成或核验文件 | 保留诊断并按会话错误处理，不能以当前状态生成替代内容 |
| 提交结果不确定，或登记依据无法可靠读取 | 任意 | 按会话错误处理；恢复时先确认数据库事实，不凭文件存在与否推断登记结果 |

历史回放只恢复报告登记和管理状态；实际生成、发布和补投由报告机会驱动。业务变化需要新的报告时，选择新的历史边界并登记新的 `report_id`。数据库登记、文件发布和发布结果记录之间的完整断电对账仍由文件交接及报告完成证据契约细化。

### 报告内容

报告根据业务变化序号 `change_seq` 选择需要更新的对象，再给出这些对象在报告截止位置的状态快照。数据库保存变化经过，报告告诉客户端这些对象在该位置是什么状态。

应报告的业务变化包括至少：

- 请求/计划注册；
- 由动作历史派生的计划执行状态变化；
- 输入计划文件读取失败及实际取得的诊断信息；
- 计划受理拒绝及其原因；
- ACK 校验错误及其原因；
- action 状态变化；
- 录像启动与停止各自的尝试记录及结果；次数与上限按[启动与停止的尝试上限](camera-recording.md#启动与停止的尝试上限)分别表达；
- 持续设备效果与残留设备事实变化；
- 已可靠保存的[会话应急停止](session-errors.md#正在录像时的应急停止)事实，单独关联录像动作、会话收场流程及其尝试与结果；没有保存的结果不能从主程序诊断补造为数据库历史；
- 后续动作触发的残留收场及其结果，关联触发动作、目标历史录像和该流程独立的尝试次数与上限；
- output 登记及可用状态变化；
- 修复结果；
- 原片媒体信息和质量变化，包括核验未执行、已取得结果或核验未确认；判定及对录像终态的影响见[录像成功标准](camera-recording.md#录像成功标准)；
- 普通产物的 delivery 发布、撤回等变化；
- output 清理状态；
- 取回半成品的待清理、实际清理失败或结果未知及清理完成事实；保留所属取回、文件关联及原因，规则见[半成品清理失败与后续处理](obtaining-outputs.md#半成品清理失败与后续处理)；
- 取消结果。

报告采用：

> 业务覆盖区间内发生变化的实体，在该报告冻结的历史上界处的状态快照。

不是逐事件日志导出。

普通交付的机器映射字段由[正式产物与取回清理](outputs.md)的[报告负责机器映射](outputs.md#报告负责机器映射)定义；报告须包含这些字段，让客户端关联实际收到的文件。

取回已经确定的逐项最终失败按[取回失败项的报告表达](obtaining-outputs.md#取回失败项的报告表达)纳入动作自身结果，包含没有正式产物或尚未创建 delivery 的失败，并按实际存在的身份建立关联。

计划执行状态遵守[计划执行状态](plan-acceptance.md#计划执行状态)，表达 `pending`、`running` 或 `completed`。动作变化导致计划阶段变化时，所属计划也属于应报告的变化实体；计划状态与动作快照均从同一冻结历史上界计算。`completed` 与具体动作的失败或取消结果可以同时出现，报告不能把计划完成解释为全部动作成功。

已支持动作在受理时因自身参数错误而登记为 `failed` 时，报告同时表达计划已受理、该动作失败、失败发生于受理校验阶段及具体字段或引用错误；不能将其表达为整份计划拒绝或设备执行失败。全部动作在受理时失败的计划为 `completed`，仍须报告其受理和动作结果；即使其中的 `report_status` 自身校验失败，会话也继续履行这些报告职责。取回的跨计划来源在执行时确认，来源选择及其处理状态保存在数据库中，支撑执行与恢复。报告通过取回动作的状态、必要的等待原因和具体错误解释进度与结果，并通过产物及交付记录表达来源关联；产物可用性继续按实际事实表达。

录像检查结果遵守[第一版原片检查的范围](camera-recovery.md#第一版原片检查的范围)，区分可靠视频时长、目标与修复门槛的判定、检查未完成或失败及已发现的媒体错误。控制流程完成或时长检查满足目标的成功判定依据及实际证据保存在数据库中，支撑恢复、历史重建与诊断。报告表达录像结果、实际检查结果及修复结果；不能用媒体时长补造控制过程时间。`succeeded` 或时长检查通过不表示整段视频已通过逐帧解码；报告不能扩大实际检查所提供的保证。

计划受理和动作执行的业务结果由状态报告交给客户端，主程序按文件交接协议中转。会话正常结束时仍可能存在受理拒绝或动作失败，客户端以报告中的具体业务状态为依据。

输入文件读取失败按[输入计划文件读取失败](cli-commands.md#输入计划文件读取失败)纳入报告，即使无法取得 `request_id`，也须表达失败阶段、实际路径及已知原因。该记录只证明一次输入读取失败，不能凭路径关联某个请求，也不否定客户端此前已取得的受理证据。客户端无法关联到待确认请求时，仍保留其原有确认状态并按既有规则重送；报告不能补造缺失的请求身份。

### 状态报告自身的管理

状态报告的生成、发布、领取、补投、替换和清理属于内部管理变化，追加历史并同步更新管理投影，不推进 `change_seq`，也不因这些操作本身产生下一份报告。报告身份分配、观察到的文件位置和本地处理进度仍须按各自规则记录，支撑恢复及会话收尾判断。

| 发生变化的对象 | 变化的归属 | 对业务报告的影响 |
| --- | --- | --- |
| 状态报告自身的内容生成记录、文件发布或领取、补投、替换、清理记录 | 报告内部管理状态 | 不推进 `change_seq`，不新增业务报告责任 |
| 普通产物的交付状态，包括发布和撤回 | 业务状态 | 按业务变化规则推进 `change_seq` 并报告 |
| 请求、动作或其他业务实体，包括 `report_status` 动作自身的状态 | 业务状态 | 继续按对应业务规则报告 |

报告处理期间并发发生的业务变化，仍须被后续适用的报告覆盖。报告管理操作的内部状态更新不等于本地处理已经成功；失败、结果未知和未完成状态仍按文件交接、恢复及会话收尾规则处理。这里的清理针对报告文件，数据库记录遵守[全局数据保留规则](system-foundations.md#持久化与配置基础)。报告文件的清理资格和恢复细节需在相应生命周期契约中细化。

### 客户端对受理结果的判断

客户端根据已经收到并保存的报告事实判断请求状态。报告是变化实体的快照，不是每次都列出全部历史请求；请求未出现可能源于报告生成较早、相关报告尚未送达或该报告不包含该实体。

| 已取得的报告证据 | 可以确认的结果 |
| --- | --- |
| 对应 `request_id` 的已受理计划实例或执行状态 | 该请求已经成功受理；即使动作尚未完成或执行失败，受理事实仍成立 |
| 能关联到某次输入的明确计划拒绝记录 | 那次输入被拒绝；该记录不能撤销已经确认的受理事实 |
| 既无请求受理证据，也无可关联的计划拒绝记录，包括未收到报告、报告未包含该请求或仅有 ACK 校验错误 | 尚未确认，不能据此断言未受理 |

新报告未包含某请求时，客户端保留此前已经确认的事实。客户端按[请求受理与会话](plan-acceptance.md#客户端确认与重送)保存和重送待确认请求，无需通过报告缺项证明提交失败。计划拒绝通过[计划文件诊断](#计划文件诊断)关联实际文件名及可可靠取得的请求 ID；诊断 ID 标识一次输入处理，不代替计划身份。

### ACK

ACK（累计接收确认）通过计划中的以下字段提交：

```text
last_report_id
```

其含义是：

> 客户端已经持久化并接受足以完整覆盖截至该报告 `to_wm` 的状态。

它不是：

> 客户端见过的最大 report_id。

因此客户端收到更大的增量报告，但此前存在缺口时，不应推进累计 ACK。

一份新的合并报告如果已经完整补齐缺口，则可以直接推进到新的累计确认位置。

ACK 只单调推进。

### ACK 引用的报告记录

`last_report_id` 通过字段类型和范围校验后，camctl 在受理事务中查询同一状态库内对应的已登记报告，以该报告持久化的 `to_wm` 作为本次确认位置的依据。

| 报告记录查询结果 | 与当前累计确认位置的关系 | ACK 处理 |
| --- | --- | --- |
| 查到已登记报告，覆盖水位可可靠读取 | `to_wm` 更大 | 有效，累计确认位置推进至该 `to_wm` |
| 查到已登记报告，覆盖水位可可靠读取 | `to_wm` 相同或更小 | 有效，保持当前累计确认位置 |
| 查询成功，查不到对应报告 | 无可用覆盖水位 | 无效 ACK，保持确认位置并记录业务错误 |
| 查询失败，或报告记录无法提供可信的覆盖水位 | 无法可靠判断 | 会话错误，不能解释为报告不存在或吸收成功 |

报告文件位于 `ready`、`processing`，或已经被主程序删除，均不改变上述判定；ACK 的依据是已登记报告记录。`report_id` 用于定位报告，确认位置取自对应的 `to_wm`。即使输入 ID 小于已知报告 ID，也必须查询对应记录，不能据数值大小推定它有效。

有效 ACK 的序列影响及无效 ACK 的报告责任按“ACK 与业务变化”处理；计划受理仍遵守与 ACK 独立处理的规则。已登记报告及其覆盖水位永久保留，迟到的 ACK 仍可查询历史报告。登记时点由“从历史重建报告”定义。

存在同步责任时，同次事务还须按[ACK 如何结束同步](status-sync.md#ack-如何结束同步)判断这份报告满足哪些责任。该判断与累计确认数值是否推进分别进行：较早的报告只要覆盖所需范围，且采用的记录已包含本次同步开始，就可以用于结束同步；数值更大的报告仍须满足这些要求。确认位置更新与责任结束一起原子提交。

### ACK 与业务变化

成功吸收有效 ACK 时，camctl 将确认位置的变化追加到历史，并在同一事务更新累计确认投影。ACK 推进本身不推进 `change_seq`，也不产生新的业务报告责任；有效的较旧或相同 ACK 保持确认位置，同样不产生新的业务报告责任。

| ACK 处理结果 | 其他新增业务变化 | 新增业务报告责任 |
| --- | --- | --- |
| 有效，确认位置推进或保持 | 无 | 无；不因 ACK 更新生成新报告 |
| 有效，确认位置推进或保持 | 有 | 按其他业务变化报告，ACK 本身不增加业务变化 |
| 无效 | 有或无 | 按既定规则记录并报告 ACK 校验错误，同时覆盖其他业务变化 |
| 未提供 | 无 | 无 |
| 未提供 | 有 | 按其他业务变化报告 |

本表适用于输入处理结果可靠保存的情况；ACK 更新的数据库写入失败或提交结果不确定仍按会话错误处理。

已有未确认内容在实际报告机会中仍按补投规则处理。判断补投范围时结合已持久化的累计确认位置和有效的同步责任；有效 ACK 及其导致的责任结束不新增业务报告责任，也不表示其他尚未完成的报告或业务工作已经完成。同步责任全部结束后，所确认报告之后的业务变化仍须按普通规则报告。与 ACK 同次提交的新计划注册、计划拒绝等变化，仍各自承担报告责任。

### submit 可以独立吸收 ACK

由于 `submit` 不要求墙钟可信，因此时钟异常期间也允许：

- 受理请求；
- 接收相同 `request_id` 的重试；
- 推进有效 ACK。

计划正文与 ACK 的组合结果统一由[请求受理与会话](plan-acceptance.md#计划正文与-ack-独立处理)定义。计划被拒绝时仍处理有效 ACK；ACK 无效时保留确认位置，记录面向客户端的业务错误，计划继续按请求 ID 复用或首次受理。已受理 ID 的重试关联原计划及其当前状态，ACK 独立处理。

### 报告生成点

正常 `run` 中：

1. 恢复/对账后；
2. `report_status` 执行时；
3. 会话收尾前。

`report_status` 只表示：

> 立即执行一次本地状态报告更新。

它不保证主程序会立即传输，更不保证客户端立即收到。

该动作的 `params` 可省略或为空对象，按当前报告责任更新；提供 `scope: "full"` 时请求完整同步，提供 `scope: "since"` 和 `after_report_id` 时请求从指定报告之后补齐。参数组合及实际覆盖范围由[同步入口](status-sync.md#请求入口)定义。`device_id` 须省略，`policy` 可省略或为空对象。非法范围、额外参数、不适用的策略及非法字段只使该动作初始失败，公共规则见[第一版动作入口](plan-input.md#第一版动作入口)。

### 与会话收尾的协作

状态报告生成和发布属于本地处理责任。`run` 在关闭接纳之前完成本次报告机会应承担的工作，再按[请求受理与会话](protocol-session.md)的交接协议进行短写事务内的最终检查。

| 最终检查观察到的状态 | 对关闭接纳的影响 |
| --- | --- |
| 报告准备期间出现新的应报告业务变化，当前报告处理结果尚未覆盖 | 保持接纳资格，完成新增报告责任后再检查 |
| 本次报告机会的本地处理已完成，且没有新增应报告责任 | 报告方面允许关闭接纳；其他动作和收场责任仍需检查 |
| 仅剩本地发送或客户端 ACK 尚未完成，包括完整或局部同步待确认 | 不要求 `run` 持续等待；持久化责任由后续实际报告机会继续承担 |
| 本地报告职责是否完成无法确认 | 保留诊断并按错误处理，不能当作已经完成 |

这里的业务变化包含受理拒绝及 ACK 校验错误，不依赖新计划受理序列是否推进。报告构建与文件发布在短交接事务之外执行；报告内容、覆盖水位和本地完成证据必须相互一致。

为完成同一次收尾而反复进行的交接检查，不各自构成新的报告机会。本次机会已完成本地处理且没有新增业务变化时，主程序随后领取或删除文件不会使该收尾循环不断补投。下一次实际报告机会仍按报告补投规则检查未确认状态。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

历史记录承载业务变化、报告登记及内部管理变化，是状态计算的权威来源。报告查询投影提供 `report_id`、`from_wm`、`to_wm`、历史上界、固定生成元数据，以及文件发布状态；累计 ACK 投影提供当前确认位置。同步责任保存发起动作、输入范围、引用报告、确定后的起点、本次开始的记录及结束结果，遵守[同步需要保存的信息](status-sync.md#数据库需要保存哪些信息)。各次变化的历史及相关投影在同一事务中提交。具体表划分和字段命名仍属实现设计。

业务状态变化通过 `change_seq` 驱动报告覆盖；全部历史变更的顺序用于历史回放，两者按全局规则区分。报告内部管理状态遵守“状态报告自身的管理”规则，报告对外输出实体快照。

## 验收要求

### 单元测试

隔离历史存储和文件交接协作者，验证报告覆盖、ACK 单调推进、合并、纯重投复用身份及补投资格。历史计算验证固定边界下的实体状态；JSON 生成验证冻结元数据下的确定性，包括字段排列和特殊字符。

使用已知字节及独立确定的 SHA-256 预期验证文件名包含完整的小写摘要。按客户端检查表覆盖文件名非法、摘要缺失或长度错误、读取及计算失败、摘要不匹配和匹配的情况；另行覆盖摘要正确但 JSON 或报告结构不合法、报告身份不一致及累计覆盖存在缺口，验证文件校验通过不能直接授权 ACK。

按“报告覆盖区间”覆盖变化位于下界之前、恰好等于下界、区间内部、恰好等于上界及上界之后的情况，并覆盖两端相等的空区间。同一实体分别组合区间内变化和上界后的变化，验证选中实体及其历史状态；区间内多次变化应得到一份边界处的实体快照。

按“按计划嵌套与客户端合并”验证仅计划、仅动作、仅产物、仅交付变化时的实体选择与父对象补齐。父对象自身字段须取自同一历史边界，补齐不推进业务水位，也不扩展为全部兄弟对象。客户端合并按新旧 ID、自身可选字段消失、子集合缺席或为空、已有成员缺席及明确清理状态覆盖表中分区；改变数组排列不改变关联，不把参数或结果中的普通数组误当作实体子集合。跨计划取回只沿各自所属关系嵌套，并保留交付的显式来源映射。

按“计划文件诊断”的错误归属表验证读取、解析、整份拒绝、ACK 失败与动作自身失败的分区。文件不可读或不可解析时仍表达传入文件名，不从名称或片段填写请求 ID；非法请求 ID 不作为外层关联。同次输入多个错误形成一条记录，动作自身错误不重复列入。客户端分别验证同 ID 重复报告、新 ID 同名同内容输入、集合缺席或为空，以及旧拒绝与后来受理证据同时存在；`errors` 随整条诊断保存，不按数组项合并。

按“ACK 引用的报告记录”决策表覆盖已登记报告的确认推进与保持、未知报告及查询失败。未知 ID 分别覆盖小于和大于已知报告 ID 的情况；确认位置的预期取自对应报告覆盖水位，不以 ID 数值替代。

按“ACK 与业务变化”决策表覆盖各分区，断言有效 ACK 自身不推进 `change_seq`、不新增业务报告责任，其他业务变化和 ACK 校验错误仍按各自规则报告。

按变化对象区分状态报告内部管理、普通产物交付和动作状态，验证各自的序列及报告责任，包含 `report_status` 动作状态与其生成报告的管理状态分别处理。

验证恢复识别使用目录位置、文件身份及数据库登记，不调用全文校验或报告重建来确认完整性。覆盖报告位于 `ready`、`processing`，已发布记录存在或缺失，以及身份无法关联、目录或数据库读取失败的情况；缺少已发布记录时保存恢复观察，不虚构历史发布时间。

### 集成测试

使用真实 SQLite 与交接目录验证快照生成期间的并发业务变化、报告替换与领取、重启恢复和客户端处理乱序报告。组合报告生成、文件交接和客户端接收校验，验证文件名中的摘要对应实际发布字节，主程序传递完整文件名与内容，客户端校验后才接受报告。

分别截断报告、改变内容但保持合法 JSON，以及改变空白或换行，保留原文件名，验证客户端均发现摘要不匹配，且不采用该报告的业务状态或推进 ACK。覆盖原样传输、文件名被截断或改写，以及摘要正确但报告结构或身份不合法的情况。补投和断电重建须保持原报告的 ID、全部字节、摘要及文件名；本地恢复识别继续遵守不常规全文校验的规则。

验证报告身份、历史边界、覆盖水位及生成元数据的登记历史与投影一同提交。分别在提交前、提交后文件生成前、`staging` 写入期间中断，恢复后按数据库登记状态处理。报告选择的历史边界不能拆开同一事务中的业务变化。

分别保留只写了一部分及已经写完的 `staging` 报告，在仍需发布、且 `ready` 和 `processing` 均没有同一报告时恢复，验证均从冻结依据完整重新生成，保持原 ID 和内容，完整后才发布。另行覆盖同一报告已在 `ready` 或 `processing`、目录检查失败，以及重新生成过程中再次中断，验证不会把已有交接文件重复排队，也不会发布半成品。

使用一次事务受理计划及全部动作，验证报告边界只能位于整次受理之前或之后，不能只覆盖部分注册结果。报告冻结后并发推进 ACK 或提交业务变化，验证已登记报告的下界、上界及实体快照保持原值，后续报告再按新的历史边界确定覆盖范围。

通过 `run <plan-path>` 与 `submit <plan-path>` 分别触发计划文件诊断，组合真实文件读取、SQLite、报告生成与客户端合并，验证诊断、计划处理结果和有效 ACK 原子保存。提交前中断不得留下部分诊断，提交后恢复及报告补投复用原身份和内容；另一次命令输入再次发生错误才产生新诊断。文件之后被主程序删除不影响诊断重建；覆盖诊断的 ACK 推进后，历史保留且不因此新增业务变化。

删除已交接的报告文件后，在符合补投条件时重建文件，逐字节断言与首次发布文件相同，并覆盖特殊字符。分别在动作状态变化、ACK 推进、配置修改及进程重启后重建同一报告，验证仍使用原历史边界和生成元数据；新业务报告采用独立 ID。历史不可可靠读取或解释时须明确失败。

验证回放报告历史能够恢复登记、覆盖水位和累计 ACK 状态，且不生成文件、不执行补投、不新增业务变化或重新分配序列。恢复后的实际报告机会按文件交接事实执行必要工作。

使用已受理请求的重试提交有效 ACK，验证确认位置持久化且 `change_seq` 不因 ACK 改变。分别组合无其他工作、已有未确认内容及新增业务变化，验证后续报告机会和会话收尾按实际剩余责任处理；有效 ACK 不触发用于确认该 ACK 的新报告。

两个计划输入入口均使用真实报告记录验证：报告文件位于 `ready`、`processing` 或已被主程序删除时，ACK 仍按持久化覆盖水位吸收；未知报告 ID 保持确认位置并记录 ACK 错误，同次合法计划仍按规则受理或复用。

使用真实状态库与交接目录验证报告生成、发布、领取、补投、替换和清理后，仅有内部管理变化时 `change_seq` 保持不变。另行组合普通产物交付或动作状态变化，验证业务变化仍被报告；报告管理失败及恢复仍保留可诊断状态，不被视为本地职责已完成。

验证成功放入 `ready` 后才提交对应 `report_id` 的发布历史与投影。让主程序在放入成功后、记录提交前领取并删除文件，验证 camctl 仍能依据已确认的发布结果保存记录，重启后该事实仍可查询。首次发布和成功补投分别记录发布事实，且不推进 `change_seq` 或累计 ACK。发布失败或结果未知时不记录成功；发布后的数据库写入失败或提交结果不确定时按会话错误处理。

分别保留 `ready` 或 `processing` 中的已登记报告，但不保留已发布记录，再启动恢复。验证 camctl 从文件位置及报告登记补记恢复观察，保持已有文件及所属目录，且不重复投放该报告。

累计 ACK 推进且报告文件被清理后，验证数据库中的报告、覆盖水位和既有错误记录仍保留；重启后收到较旧的合法 ACK 时仍能查到对应报告并保持当前确认位置。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 状态报告

- 同一逻辑报告内容不可变；
- 纯重投复用 ID；
- 新状态创建新 ID；
- ready 至多一个待领取报告；
- ready 合并替换；
- processing 与新 ready 报告并存；
- 无 ACK 时本地传输完成且文件被删除后的再次补投；
- 累计 ACK；
- 有效的较旧或相同 ACK 不产生错误、不回退确认位置；
- 无效 ACK 保持确认位置并进入业务报告，相关计划受理结果按请求专题的独立处理规则表达；
- 客户端重复处理覆盖重叠的快照时，按身份与覆盖规则合并，不重复创建对象或倒退状态。
- 会话正常结束时，计划拒绝和动作失败仍在状态报告中如实表达。
- 待确认请求未出现在报告中或报告迟到时，客户端保持尚未确认；已有受理事实不因后续报告缺项而丢失；
- 能关联的计划拒绝只说明对应输入被拒绝，ACK 校验错误本身不能证明计划被拒绝；
- 计划实例或执行状态可以确认受理，动作尚未完成或执行失败不改变该事实；
- 报告准备期间发生受理拒绝等变化时，收尾前补齐覆盖，即使 `plan_seq` 未推进；
- 同一收尾过程的重复交接检查不会仅因文件被领取或删除而无限补投；
- 报告完成证据不足时，不允许通过会话最终检查。

## 实现时细化

正文定义第一版的业务规则。本节列出接口、配置和联调中需要落实的细节；先按正常流程推进，涉及正文尚未确定的业务结果时，再明确对应选择。

各类对象的自身字段、必填及可选规则、实体子集合和语义检查按[状态报告字段契约](report-format.md)落实；报告 ID、初始水位及 ACK 值类型遵守“报告编号与水位的数值范围”。完整分类 ACK 不变/推进、业务无变化/有变化、已有覆盖报告位于 ready/processing/均不存在的有效组合，补齐各组合的文件处理及补投规则。

细化历史边界与业务覆盖水位的存储关联、生成元数据字段，以及第一版历史解释和 JSON 生成规则。按已确认的报告字段、覆盖区间和实体选择规则，落实排列顺序、数字及字符串编码，验证冻结报告可以重建为相同字节。

已发布记录和恢复观察分别按[记录报告已经发布](report-publication.md#记录报告已经发布)及[恢复时识别已发布报告](report-publication.md#恢复时识别已发布报告)保存。还需定义请求受理和会话退出检查如何结合这些记录、覆盖范围及已有文件判断本次报告处理是否完成。需要区分新增业务尚未报告、本次报告处理未完成、已经发布但远端尚未 ACK，以及文件发布结果未知等状态。

计划文件诊断按“计划文件诊断”提供字段、错误归属、持久化与合并语义。各输入校验分支仍须落实具体错误码及结构化细节，并验证读取失败、整份拒绝和 ACK 错误在两个输入入口中的一致表达；诊断不能改变已受理请求的执行意图。
