# 状态报告与累计确认

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义状态快照、报告身份、累计 ACK 和报告补投。`last_report_id` 通过[请求受理与会话](protocol-session.md)的计划入口提交；报告文件的所有权与基本发布规则见[文件交接](file-handoff.md)。

## 状态报告与 ACK

### report_id

每份逻辑报告具有单调递增的：

```text
report_id
```

文件名：

```text
status-report-<report_id>.json
```

### 报告不可变

不变量：

```text
同一个 report_id
    → 内容永久不变

内容发生变化
    → 新 report_id
```

纯粹重新投递同一报告：

> 复用原 `report_id`。

重新投递本身不推进：

```text
change_seq
```

### 报告内容

报告是基于 `change_seq` 的状态快照。

应报告的业务变化包括至少：

- 请求/计划注册；
- action 状态变化；
- 持续设备效果与残留设备事实变化；
- output 登记及可用状态变化；
- 修复结果；
- delivery 发布、撤回等变化；
- output 清理状态；
- 取消结果；
- 计划退役。

报告采用：

> 区间内发生变化的实体的当前状态快照。

不是逐事件日志导出。

普通交付的机器映射字段由[正式产物与取回清理](outputs.md)的“报告负责机器映射”定义；报告须包含这些字段，让客户端关联实际收到的文件。

### ACK

ACK（累计接收确认）通过计划中的以下字段提交：

```text
last_report_id
```

其含义是：

> 客户端已经持久化并接受足以完整覆盖截至该报告 `to_wm` 的状态。

它不是：

> 客户端见过的最大 report_id。

因此客户端收到更大的增量报告，但此前存在缺口时，不应推进累计 ACK。

一份新的合并报告如果已经完整补齐缺口，则可以直接推进到新的累计确认位置。

ACK 只单调推进。

### submit 可以独立吸收 ACK

由于 `submit` 不要求墙钟可信，因此时钟异常期间也允许：

- 受理请求；
- 接收相同 `request_id` 的重试；
- 推进有效 ACK。

### 报告生成点

正常 `run` 中：

1. 恢复/对账后；
2. `report_status` 执行时；
3. 会话收尾前。

`report_status` 只表示：

> 立即执行一次本地状态报告更新。

它不保证主程序会立即传输，更不保证客户端立即收到。

## 报告文件与 ready/processing

状态报告是 `ready` 中唯一允许被“更新替换”的特殊文件类型。

### ready 中至多一个待领取状态报告

如果：

```text
ready 中已有 report R1
```

且没有新的业务变化：

> 保留 R1，不重新生成。

如果出现新变化：

1. 根据当前累计 ACK 水位重新生成合并快照；
2. 在 `staging` 生成新报告 R2；
3. 完整生成后撤下 ready 中的 R1；
4. 发布 R2。

R1 的逻辑报告记录本身仍不可变。

### processing 报告不可修改

如果主程序已经领取：

```text
processing/status-report-42.json
```

CLI 不修改、不撤回它。

此时产生新状态时，可以同时出现：

```text
processing/status-report-42.json
ready/status-report-47.json
```

这是合法状态。

### 防止频繁裸 run 产生大量重复报告

只要覆盖未确认状态的报告仍然：

- 位于 `ready`；
- 或位于 `processing`；

就不因为又启动了一次裸 `run` 而排入一份完全相同的报告。

### 本地发送结束后仍未 ACK

主程序删除 processing 文件只表示：

> 本地发送流程已经结束。

远端是否收到未知。

如果累计 ACK 仍未推进，且：

```text
ready
processing
```

都已经没有能够承担该未确认状态的报告，则下一次报告机会重新承担补投责任。

没有新业务变化：

> 可以重新投递原不可变 report_id。

出现新业务变化：

> 生成新的合并报告和新 report_id。

这样避免：

```text
每次裸 run
    → 新报告
    → 主程序重复排队传输
```

同时仍保留在没有远端接收确认时的自动补救能力。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

业务状态变化通过 `change_seq` 驱动报告；events 是仅追加的审计日志，报告不直接导出逐事件日志。reports 记录 `report_id`、`from_wm`、`to_wm`、不可变内容身份、文件路径或重建依据，以及累计 ACK 情况。各业务实体的状态变化与对应序列之间的一致性需要由事务契约保证，具体协议待细化。

## 验收要求

### 单元测试

隔离快照存储和文件交接协作者，验证报告覆盖、ACK 单调推进、合并、纯重投复用身份及补投资格。

### 集成测试

使用真实 SQLite 与交接目录验证快照生成期间的并发业务变化、报告替换与领取、重启恢复和乱序报告消费。报告自身完整性验证依 U3 确认的传输保障执行。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 状态报告

- 同一逻辑报告内容不可变；
- 纯重投复用 ID；
- 新状态创建新 ID；
- ready 至多一个待领取报告；
- ready 合并替换；
- processing 与新 ready 报告并存；
- 无 ACK 时本地发送结束后的再次补投；
- 累计 ACK；
- 重叠快照幂等消费。

## 待确认与待细化

本节不构成已确认的行为选择。涉及其结果的实现须先补齐契约。

### U3. 状态报告自身完整性验证

普通产物可以通过状态报告中的：

```text
size
sha256
```

让客户端核验。

状态报告文件自身的完整性需要由传输保障或独立校验机制验证。

需要最终确认底层传输是否已经提供足够的完整性保证，或者是否需要为报告增加其他校验机制。

### 后续契约完善

定义 `from_wm/to_wm` 的端点和一致性快照规则、报告机器结构、未知或无效 ACK 的结果。完整分类 ACK 不变/推进、业务无变化/有变化、已有覆盖报告位于 ready/processing/均不存在的有效组合；明确报告自身操作产生业务变化的范围。
