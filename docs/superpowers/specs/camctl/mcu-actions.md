# MCU 接口预留

[返回设计总览](../2026-09-08-camctl-cli-design.md) · [阅读路线](reading-guide.md)

本专题定义第一版的 MCU 扩展边界。公共动作与设备驱动职责见[调度与设备执行](scheduling-execution.md)，未来产物接入遵守[正式产物与取回清理](outputs.md)。

**阅读提示：** MCU（微控制器）的具体功能不进入第一版。先看当前需要保留的接口边界，再读后续通过 UART（串行通信接口）接入的依据。

## 第一版范围

第一版预留 MCU 接入位置，具体 MCU 功能属于后续接入范围。

| 对象 | 第一版约束 |
| --- | --- |
| 设备接入 | 沿用设备身份与驱动选择的公共边界，为 MCU 驱动保留扩展位置 |
| 动作接入 | 允许后续通过公共动作处理边界接入 MCU 命令与查询，使用共同的调度、取消及恢复机制 |
| 结果接入 | 后续驱动能够提交动作结果、设备事实及正式产物，复用持久化、报告与交付机制 |
| 实际通信 | 本版运行不建立 MCU 串口连接，不发送或接收 MCU 指令，不产生 MCU 数据产物 |
| 部署与运行 | 本版不要求 MCU 硬件、固件或串口通信依赖；MCU 接口预留不产生等待或阻止会话退出的工作 |

接口预留表达职责和数据流边界。具体模块、方法签名、串口框架及数据库结构由实现时结合公共驱动结构确定，不为尚未确定的 MCU 业务建立专用运行系统。

### 计划中的 MCU 动作

`mcu_send_command` 与 `mcu_read_data` 是后续接入的动作名称，第一版不将其注册为可执行能力。

首次提交的计划包含这类尚未实现的动作时，按[整份校验与原子受理](plan-acceptance.md#整份校验与原子受理)拒绝整份计划，并明确报告动作类型尚未支持；不创建部分动作实例。该规则适用于 `run <plan-path>` 和 `submit <plan-path>`。已有受理请求仍遵守请求幂等规则，不因重送正文而重新校验或改变首次受理内容。

## 后续接入依据

以下是后续 MCU 接入应继承的设备前提与设计约定，不属于第一版通信实现或设备联调的验收范围：

- MCU 通过 UART（通用异步收发接口）与主机双向通信，只响应指令，不主动上报。
- MCU 固件与通信协议均由项目团队维护，可以共同定义两端行为。
- camctl 负责收发、响应关联及业务处理；第三方主程序继续只承担进程管理和数据中转。
- 指令携带通信编号，响应原样返回；编号与指令的关联须支持主机重启恢复，旧响应不能完成另一条指令。响应归属与重复执行控制分别定义。
- 命令发送拟由 `mcu_send_command` 表达，按时效动作处理；查询拟由 `mcu_read_data` 表达，按无时效动作读取实际执行时的当前值。
- 一次成功查询形成独立正式产物，后续取回使用同一份已保存结果，不能重新查询当前值来代替历史结果。实际数据形式、保存位置与清理方式在接入时确定。

## 第一版验收要求

### 单元测试

使用受公共驱动接口约束的替身验证扩展边界能够承接动作处理和结果表达。验证未实现的 MCU 动作进入静态校验拒绝分支，不调用设备执行；测试不依赖真实串口或 MCU。

### 集成测试

通过实际计划入口、校验、SQLite 与报告生成，分别对两个入口提交包含 MCU 动作的计划，验证整份拒绝、无部分动作登记，以及报告能够定位不支持的动作类型。组合合法动作与 MCU 动作，验证不会只受理合法部分；原有已受理工作按会话规则继续处理。

在未安装 MCU 通信依赖、未连接 MCU 的环境中，验证本版初始化及已有功能可以运行，预留接口不建立串口连接，也不产生额外的会话驻留责任。

## 后续接入时完善

具体 MCU 功能启动设计时，再定义命令与数据种类、消息边界、响应关联、确认语义、超时重试、副作用去重、取消与断电恢复，以及查询产物的持久化和清理契约。双方协议确定后完成固件与主机联调。
