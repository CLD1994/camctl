# 调度与设备执行

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义公共动作状态、调度资格、时间窗口、设备执行和恢复的公共规则。会话接纳与退出由[请求受理与会话](protocol-session.md)定义；录像证据、录像收场与恢复结果由[相机录像](camera-recording.md)定义。

## 动作状态模型

动作登记时的初始状态由[整份校验与原子受理](protocol-session.md#整份校验与原子受理)确定：已支持且通过校验的动作为 `pending`；已支持但自身参数校验失败的动作直接登记为 `failed`，不经过 `running`、不产生执行尝试，也不等待计划时间。该失败属于校验结果，`submit` 可以保存它而不执行设备、文件、取消或显式报告操作。

已登记为 `pending` 的动作按下图转换：

```text
pending
    │
    ├──────────────→ expired
    ├──────────────→ canceled
    │
    ▼
running
    │
    ├──────────────→ succeeded
    ├──────────────→ failed
    ├──────────────→ expired
    └──────────────→ canceled
```

终态：

```text
succeeded
failed
expired
canceled
```

终态本身不迁移。

注意：

> 动作终态与动作留下的设备事实、正式产物、待传 delivery 是不同生命周期。

例如：

```text
camera_record = failed

设备事实：
    possibly_recording = true
```

两者可以同时成立。

## 效果登记与补偿

持续设备效果使用独立效果登记。

例如录像启动成功：

```text
recording effect
    registered
```

效果收场：

```text
registered
    ↓
compensating
    ├── compensated
    └── compensation_failed
```

“只补偿一次”的准确含义为：

> 原动作对同一设备效果只创建一个持久化补偿流程。

不是：

> 设备停止指令在物理上永远只能发送一次。

多个取消路径触达同一效果时，不创建多个独立补偿流程。

后续其他动作要求相机空闲时，可以按[后续动作触发的残留收场](camera-recording.md#后续动作触发的残留收场)建立关联该新动作的独立流程。它有自己的有限预算，不是原动作补偿流程的重置；同一触发动作对同一历史录像仍只登记一次。

补偿执行被主机断电中断后，可以恢复同一补偿流程。

如果驱动明确保证某项收场操作可以安全重复，则即使无法确认上一次尝试结果，也允许在原有限重试预算内再次执行。

支持设备端命令去重时，同一逻辑操作的重试应复用同一设备命令身份。

通信重试耗尽后：

```text
compensation_failed
```

不进行电源重启。

## 调度与时间语义

### `scheduled_at`

`scheduled_at` 表示：

> 主机希望开始处理该动作的绝对 UTC 时间。

对于设备操作，主机应尽可能按时发出真正设备指令；取回、清理等动作到达该时间后，仍须满足各自的业务执行条件。

调度采用尽力按时执行的保证，不承诺固定毫秒级触发精度。主机发令时间与设备真实采集时间分别表达。

字段是否允许省略由动作类型决定，不由动作是否有时效决定：

| 动作类型 | `scheduled_at` 要求 | 省略时的处理 |
| --- | --- | --- |
| 已支持的设备动作、`obtain_action_outputs`、`delete_action_outputs` | 必填 | 首次受理时将该动作登记为 `failed` |
| `report_status`、`cancel_task` | 可省略 | 执行会话取得相应执行资格后立即处理，无须等待指定的计划时间 |

允许省略时，“立即”仍须遵守动作的执行条件及会话模式；`submit` 只受理，不执行这些动作。时钟异常时，未填写时间的 `cancel_task` 按“时钟异常期间的取消”处理。显式填写时间时，按该时间调度。首次受理的静态参数错误按请求专题的整份计划校验规则处理；已受理 ID 的重试继续复用原计划。

### 单调钟

墙钟用于确定绝对目标时间。

等待与超时使用 单调钟。

正常情况下：

```text
mono_target =
    monotonic_now
    + (scheduled_at - wall_now)
```

### 时效动作

时效动作具有：

```text
max_delay_ms
```

允许执行区间：

```text
scheduled_at
    ↓
    ├──────── max_delay_ms ────────┤
```

定义：

```text
window_end = scheduled_at + max_delay_ms
```

窗口内可以继续尝试。

窗口耗尽后：

- 尚未真正执行成功 → `expired`
- 已执行但最终失败 → `failed`

#### 过期原因

`expired` 是动作终态；为什么过期通过独立结果字段表达，不增加新的动作终态。

第一版至少区分：

```text
expiration_reason = window_missed
expiration_reason = window_exhausted
```

`window_missed` 表示：

> `run` 第一次能够在可信墙钟下对该 action 进行有效窗口判断时，执行窗口已经结束，并且数据库中没有证据证明 camctl 曾经在该执行窗口内观察过它。

`window_exhausted` 表示：

> camctl 曾经在该 action 的有效执行窗口内观察并持久化过这一事实，但直到窗口结束仍未真正执行成功。

`window_exhausted` 不要求已经发出过设备指令，因此下面的结果合法：

```text
status = expired
expiration_reason = window_exhausted
attempts = 0
```

例如 camctl 已经在窗口内知道 action 存在，但目标设备持续 busy、要求 idle 的条件始终不满足，或者调度竞争导致始终没有实际设备尝试，都可以最终得到 `window_exhausted`。

原因分类只依据持久化观察事实；证据不足时，不进一步推断客户端提交晚、主机离线或调度延迟。

#### 窗口内有效观察

只有满足：

```text
scheduled_at <= trusted_wall_now <= window_end
```

才算 action 处于有效执行窗口。

`run` 提前加载了未来 action，并不等于已经观察过它的执行窗口。

第一次在有效窗口内观察到该 action 时，必须先持久化：

```text
first_window_observed_at
```

之后才进入设备条件检查、调度竞争和可能产生设备副作用的执行流程。

只有已经成功持久化的 `first_window_observed_at` 才能作为断电恢复后的事实依据。如果 camctl 恰好在首次内存观察与该字段成功落盘之间断电，恢复后不得根据已经丢失的内存事实推断曾经观察过执行窗口。

目标设备当时是否 ready、idle 或 compatible，不影响“窗口内有效观察”的成立；这些条件影响是否能够执行，不影响 `window_missed / window_exhausted` 的分类依据。

### 无时效动作

无时效动作允许延后；具有 `scheduled_at` 时，该字段表示开始处理的时间，不形成过期截止时间。

设备通信及操作仍有有限超时和重试预算，重试耗尽后失败，不进行断电重启。等待业务条件的规则由对应专题定义，不能把计划执行时间已过去当作通信失败。

取回与清理的无时效类别、时间判定和恢复规则见[取回与清理的执行时间](outputs.md#取回与清理的执行时间)。

### 动作独立

一个动作失败不会级联取消后续动作。

### 新计划发现与内存调度缓存

`run` 使用 SQLite 作为权威持久状态，同时在内存中维护可丢弃、可重建的调度缓存。

新计划通过独立的 `camctl submit` 受理。`run` 使用 `asyncio` 等待，通过周期检查状态库保证新计划发现。

当前目标为：

> `run` 对新提交计划的目标最大感知延迟为 500ms。

这不是硬实时调度保证；系统仍受 Python 事件循环、SQLite 事务、Linux 调度和不可中断设备调用等实际条件约束。

为避免每次轮询扫描 plans/actions，调度器使用[请求受理与会话](protocol-session.md)定义的新计划受理序列。候选名称见该专题 U8：

```text
plan_seq
```

序列的分配与幂等规则由[请求受理与会话](protocol-session.md)的“新计划受理序列”定义。

状态库能够轻量读取：

```text
latest_plan_seq
```

当前 `run` 在内存中保存：

```text
last_seen_plan_seq
```

正常检查：

```text
latest_plan_seq == last_seen_plan_seq
    → 没有新计划，不扫描 plans/actions

latest_plan_seq > last_seen_plan_seq
    → 增量加载新受理计划
    → 合并进入内存调度器
    → 更新 last_seen_plan_seq
```

`plan_seq` 与 `change_seq` 语义不同：

```text
plan_seq
    = 新计划的受理顺序 / 新计划发现水位

change_seq
    = 业务状态变化顺序 / 状态报告水位
```

不得使用 `change_seq` 代替新计划发现序列，否则 `run` 自己产生的 action/output/delivery 状态变化会造成无意义的调度缓存刷新。

该轻量检查只判断是否需要增量加载计划。受理拒绝等业务变化可以不推进 `plan_seq`，但仍产生报告责任；报告机会与正常退出检查须按各自契约观察这些变化。

`run` 正常退出前，按[请求受理与会话](protocol-session.md)的“会话接管协议”，在短写事务内重新检查持久化工作并关闭接纳。单次轮询结果和内存缓存都不能替代该检查。设备操作、文件处理及报告生成在交接事务之外完成。

### 唤醒后的统一重新决策

内存调度缓存可以包含当前 `run` 已知的时间驱动工作，例如：

- 通信 `prepare_at`；
- action `scheduled_at`；
- 重试截止时间；
- 超时截止时间；
- `camera_record` 的 停止截止时间；
- 其他运行时产生的有限截止时间。

调度器允许在最近业务截止时间 之前提前一小段时间唤醒，为 SQLite 检查、增量计划加载、调度重算和运行时抖动留下余量。具体提前量尚未最终确定。

无论一次唤醒来源于：

- 周期性新计划检查；
- 某个缓存中的 工作截止时间；
- 某个提前唤醒点；
- 其他内部截止时间；

在依据旧缓存决定下一项实际设备操作之前，都先进行一次轻量的 `latest_plan_seq` 检查。

统一流程：

```text
wake
  ↓
check latest_plan_seq
  ↓
有新计划？
  ├── 否 → 保留当前缓存
  └── 是 → 增量加载并合并新计划
  ↓
重新计算当前最早 work / deadline
  ↓
处理已经 due 的工作，或重新 await
```

因此：

> 定时唤醒只代表调度器获得了一次重新决策机会，不代表唤醒前缓存中的某个 action 已经取得执行权。

提前唤醒后到真正业务截止时间 之间，不进入不可打断的“最终 sleep 模式”。调度器重新回到同一个中央等待循环，并继续同时考虑：

```text
真实业务截止时间
下一次新计划检查时间
其他运行时截止时间
```

如果这段短暂等待期间又有新计划入库，下一次最多 500ms 的计划检查仍然能够打断旧调度决策；醒来后再次检查、合并并重新排序，然后才决定真正执行哪个已到期动作。

涉及同一产物、尚未开始且均已到计划时间的取回与清理，按[延后执行时的取回与清理顺序](outputs.md#延后执行时的取回与清理顺序)处理；正常调度与重启恢复使用相同规则。

同一相机的录像启动选择按[多个待启动录像的选择顺序](camera-recording.md#多个待启动录像的选择顺序)处理。先尊重已开始录像及等待重试的保留关系；没有已有占用或保留时，再从同时具备启动条件的待启动录像中按 `scheduled_at` 从早到晚选择，同一时间按计划受理顺序、同计划原数组顺序选择。

## 通信准备

### 不要求持续在线

CLI：

- 不发送设备心跳；
- 不要求控制通信持续保持连通；
- 不在没有设备操作需求时主动维持连接。

只有需要进行设备操作时，才准备或验证通信。

### `prepare_lead_s`

时效设备动作允许提前准备通信。

```text
prepare_at =
    scheduled_at - prepare_lead_s
```

时序：

```text
prepare_at
    ↓
建立 / 验证通信
    ↓
通信准备完成
    ↓
等待 scheduled_at
    ↓
发送真正业务指令
```

若 `scheduled_at` 到达时通信尚未准备完成：

```text
继续有限尝试
    ↓
仍在 max_delay_ms 窗口内时
通信一旦可用立即执行
```

`prepare_lead_s`：

- 由驱动提供默认值；
- 允许设备本地配置覆盖；
- 执行计划不能覆盖。

它是设备/部署参数，不是业务参数。

### 通信准备的归属

通信准备属于具体设备操作的准备阶段，不作为独立业务动作。

## 设备执行与操作兼容性

每台设备由 DeviceActor（设备操作协调器）协调设备操作。

但是：

> 一个长生命周期 action 处于 `running`，不代表它持续独占整个设备。

`camera_record` 在录像期间可以保持 `running`，同时允许其他与录像兼容的设备操作执行。

驱动需要能够表达某项操作在当前设备状态下：

- 可执行；
- 要求设备 idle；
- 与录像兼容；
- 与录像不兼容；
- 是否独占控制通道；
- 长操作是否会妨碍必要的停止操作。

框架不写死：

```text
取文件一定干扰录像
```

或：

```text
维护操作一定不能并行
```

由设备能力决定。

## 普通动作取消

`cancel_task` 只取消其寻址结果对应的计划或动作。计划级取消作用于该计划内的动作，动作级取消只作用于指定动作；已有 group 寻址表示指定计划内该组的动作集合。具体寻址及不存在目标的结果见[取消目标寻址](protocol-session.md#取消目标寻址)。取消某个目标不授权取消其他计划或动作，也不授权停止目标设备上归属其他动作或归属未知的活动。

`pending`：

```text
→ canceled
```

`running`：

- 标记取消请求；
- 已经发出的不可安全中止设备调用先完成当前尝试；
- 不再继续新的普通重试；
- 进入取消收场。

已经终态：

> 一般不改变动作历史终态。

但 `obtain_action_outputs` 的可撤回 delivery 属于独立交付生命周期，仍可按[正式产物与取回清理](outputs.md)的“取消取回”处理。

## 时钟防御

### submit

`submit` 不进行启动墙钟可信性检查。

只验证时间字段：

- 格式；
- 结构；
- 静态合法性。

不依据当前本机时间判断：

- 动作是否已过期；
- 是否已经到 scheduled_at。

### run

`run` 按[请求受理与会话](protocol-session.md)的“`run` 的启动顺序”，在取得会话锁、验证状态库并完成适用的计划受理后，进行墙钟可信性检查。

时钟检查读取可信历史时间下界，再检查当前墙钟，必要时延迟复检。带计划启动的受理事务在此之前已经结束，墙钟复检等待不持有该事务。

计划受理阶段的本机时间尚未经过启动校验，不能用于推进可信历史时间下界。首次受理、幂等复用及受理拒绝的时间记录均遵守这一规则。

### 时钟正常

进入正常：

- 恢复；
- 调度；
- 执行；
- 报告。

### 时钟异常

复检仍失败时，不进入正常时间调度。

进入：

> 有限安全收场模式。

处理已经存在并且能够证明安全的遗留收场责任，以及下节允许的立即取消请求。取消产生的收场仍须证明属于被取消的目标。

不：

- 启动新的普通定时动作；
- 用错误墙钟判断 pending 动作已经过期；
- 依据错误墙钟推断录像已录多久。

受限收场结束后，本次 `run` 仍以时钟异常退出。

时钟异常不回滚启动阶段已经提交的计划受理结果。新计划的普通动作保留待驱动状态，后续实际启动的会话再按当时的时间与设备条件判断执行资格。

录像停止后的文件拷贝、媒体核验与修复不属于本模式允许的安全收场。已停止但后处理未完成的录像按[安全收场与后续处理的衔接](camera-recording.md#安全收场与后续处理的衔接)保存进度，等待后续正常会话；未完成的后处理不能使当前受限会话转入普通执行或持续等待。

### 时钟异常期间的取消

墙钟复检仍失败时，`run` 允许执行已受理、未填写 `scheduled_at` 的 `cancel_task`，包括本次启动时新受理的取消请求。该资格只允许取消指定计划或动作及完成其必要收场，不授予其他普通动作执行资格；`submit` 仍只负责受理。

先检查取消动作自身的持久化状态，再判断时间和目标。已取消或已进入其他终态的取消动作保持原结果，不重新执行；已形成的遗留收场责任按各自恢复规则处理。已经开始且仍未完成的取消，按已保存的目标和进度恢复能够证明安全的有限收场，不重新判断原计划时间或扩大目标。对于尚未开始的取消动作，按下表处理：

| `scheduled_at` | 目标查询结果 | 处理 |
| --- | --- | --- |
| 已填写 | 任意 | 保留待执行状态，不依据不可信墙钟判断已到时间或过期 |
| 未填写 | 可靠定位到指定计划或动作 | 执行该目标范围内的取消，按目标类型处理必要收场及可撤回交付 |
| 未填写 | 可靠确认目标不存在 | 按既定寻址规则记录 `target_not_found`，本次取消结束 |
| 未填写 | 查询失败、关联不明或结果未知 | 保留诊断并按对应错误处理，不能当作目标不存在，也不能扩大取消范围 |

例如取消计划 P1 时，同一相机当前正在执行 P2 的录像，不能为了完成 P1 的取消而停止 P2。只有证据确认正在进行的录像属于取消目标时，才按录像取消规则尝试停止；归属无法确认时保留未知事实。设备操作仍遵守有限重试与安全收场约束，不用取消请求绕过这些条件。

目标已经终态时保持其历史终态；目标为取回动作时，仍按所属规则处理其可撤回 delivery。源产物与其他动作的文件继续遵守各自生命周期。取消处理不依赖错误墙钟安排等待，必要超时及有限等待使用当前会话的单调钟。

受限会话仍不持有普通接纳资格。并发 `submit` 按既有接管协议判断 `needs_run`；本节不承诺受限会话持续接纳后来的工作。允许的取消及有限收场结束后，本次 `run` 仍返回时钟异常，不因尚有普通待执行动作而转入正常调度。

### 时钟异常期间的事件

保留实际墙钟读数，但明确：

```text
wall_time_trusted = false
```

这类时间不能更新未来启动校验所使用的可信墙钟下界。

业务顺序和报告覆盖使用：

- `change_seq`
- `report_id`
- 状态机身份

而不是依靠错误墙钟排序。

### v1 已知边界

运行中的墙钟跳变：

> v1 不持续监测、不主动处理。

稳定但错误的外部时间源：

> 缺少外部可信基准时无法判定。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

动作投影包含：动作实例、所属计划、类型、设备、group、`scheduled_at`、参数、固化 policy（执行策略）、状态、尝试次数、`first_window_observed_at`、`expiration_reason`、结果/错误，以及关联业务变化的 `change_seq`。

效果记录承载持续设备效果及其补偿流程；设备事实记录承载动作终态后仍需保留的未确认设备状态。`change_seq` 规则见[状态报告与累计确认](status-reports.md)。

上述投影依据不可变历史同步更新，遵守[持久化与配置基础](../2026-09-08-camctl-cli-design.md#持久化与配置基础)。状态转换、尝试结果、窗口观察、可信时间下界的推进和固化策略均保存当时的事实。回放使用已记录的值，不用当前时钟重新判定历史动作，也不执行重试或补偿；实际恢复由调度器在重新取得执行资格并完成必要对账后驱动。

## 验收要求

### 单元测试

使用受接口约束的时钟、存储和驱动替身，验证窗口分区、状态转换、唤醒后重新决策、兼容性、有限重试、取消与受限收场资格。

按已支持动作类型覆盖 `scheduled_at` 缺省与显式填写：设备动作、取回及清理缺省时仅该动作登记为 `failed`；报告与取消缺省时不等待计划时间，显式填写时遵守调度时间。各类型提供非法时间值时也仅该动作失败。区分受理校验失败与实际执行：前者可以由 `submit` 保存且不产生执行尝试，后者仍受会话和时间资格约束。

按“时钟异常期间的取消”覆盖取消自身终态、尚未开始与已经开始、时间字段有无、目标存在、不存在及查询未知的分区。验证立即取消只作用于指定计划、动作或既有 group 对应的动作集合；同设备上的其他录像及归属未知活动不能被停止。尚未开始的显式定时取消保留待执行；已开始的取消按原目标和进度恢复有限收场。已有目标终态保持不变，取回交付撤回遵守目录所有权规则。

### 集成测试

验证真实 SQLite 的受理序列发现及窗口观察持久化，组合调度器与真实驱动边界验证通信准备、超时和必要停止操作的协作；真实设备验证以已核实协议为依据。

组合计划受理、SQLite、受限会话与受接口约束的设备适配，在启动墙钟检查失败时验证新受理的立即取消能够执行，定时取消及其他普通动作保持待执行。分别安排录像属于目标计划、其他计划和归属未知的情况，验证只对确认属于目标的录像进行有限停止。取消结果跨重启保留，重复请求不扩大目标或重置预算；受限会话不取得普通接纳锁，完成后仍报告时钟异常。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 调度

- `prepare_lead_s`；
- scheduled_at；
- max_delay；
- 单调钟等待；
- `plan_poll_interval_ms = 500`；
- 未变化时只读取轻量 `latest_plan_seq`，不扫描 plans/actions；
- 新 plan 推进 `plan_seq`，同 request_id 重试不推进；
- `plan_seq` 变化后增量加载并合并内存调度器；
- 调度截止时间 提前唤醒时同样先检查新计划；
- 提前唤醒后的短暂 await 仍能被下一次计划检查打断；
- 每次 wake 后重新决策，不让旧缓存 action 自动取得执行权；
- `window_missed` 与 `window_exhausted` 明确区分；
- `window_exhausted` 允许 `attempts = 0`；
- 提前加载未来 action 不算窗口内观察；
- `first_window_observed_at` 必须先持久化，再进入后续调度/设备条件检查；
- 断电恢复只承认已经持久化的窗口内观察事实。
- `plan_seq` 未变化时，正常退出检查仍覆盖新出现的报告责任；
- 最终检查发现新提交的未来动作时，保持接纳资格并继续等待执行；
- 最终检查确认无待驱动工作后，在同一写事务结束前关闭接纳。

## 待确认与待细化

本节不构成已确认的行为选择。涉及其结果的实现须先补齐契约。

### U7. 调度提前唤醒余量

已经确认：

- 调度器可以在最近业务截止时间 之前提前唤醒；
- 提前唤醒用于为新计划检查、增量合并、调度重算和运行时抖动留出余量；
- 提前唤醒后不会进入不可打断的最终 sleep，而是回到统一等待循环。

但具体提前量、是否暴露为配置项以及最终命名尚未确定。

### 后续契约完善

补齐发令、确认执行、结果未知与窗口结束的决策表；定义尝试预算、超时、重试退避及断电后的预算恢复。明确无时效动作等待设备条件的结束规则。时钟可信性判定、可信历史下界更新时点和受限收场允许的工作集合需要完整分类。

时间记录还需明确区分启动校验尚未完成、已经校验通过和已经判为异常的状态。具体字段待细化；只有满足可信性规则的时间事实才能推进可信历史下界。
