# 文件交接

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义 camctl 与主程序通过目录交接文件的共同协议。普通产物的业务身份见[正式产物与取回清理](outputs.md)，状态报告的替换与补投策略见[状态报告与累计确认](status-reports.md)。

文件交接引起的状态变化按所属对象处理：普通产物交付属于业务状态，状态报告自身的文件管理属于内部状态，具体序列及报告责任见[状态报告自身的管理](status-reports.md#状态报告自身的管理)。

## 文件交接状态机

目录本身是文件交接状态机：

```text
staging/
ready/
processing/
```

### staging

CLI 正在：

- 生成文件；
- 拉取文件；
- 拷贝文件；
- 计算最终内容。

主程序不读取这里的文件。

文件必须完整准备后才能发布。

### ready

CLI 已完成本地发布。

等待主程序在合适的传输窗口领取。

普通产物发布到 `ready` 后：

> 本次取回的本地交付责任已经完成。

### processing

主程序在发起一次数据传输前，将 `ready` 中的全部待传输文件逐个移动到 `processing`：

```text
ready → processing
```

从此由主程序接管。

该移动是普通产物的不可撤回边界。

主程序传输 `processing` 中的文件。已知的文件处理规则如下：

| 本地传输结果 | 文件处理 |
| --- | --- |
| 主程序判定传输完成 | 删除对应的 `processing` 文件 |
| 传输失败 | 文件残留在 `processing` |
| 传输中断 | 文件残留在 `processing` |

主程序由第三方维护，失败或中断后是否再次处理残留文件、何时处理及如何重试均未知。camctl 的执行和恢复不依赖主程序一定会重试，也不能将残留文件视为正在传输或一定会再次传输。

文件进入 `processing` 后仍归主程序管理；camctl 遵守各专题的交接边界。本地传输完成及文件删除均不能证明远端客户端已经完整收到文件。

### 发布原子性

单个文件：

> 必须在 `staging` 完整生成后，再原子发布到 `ready`。

`staging`、`ready`、`processing` 应位于支持所需原子重命名/移动语义的同一文件系统范围内。

多个文件不要求整体原子发布。

状态报告文件依据 SQLite 中的不可变历史和已登记的冻结生成依据重建，登记与文件生成的先后关系见[从历史重建报告](status-reports.md#从历史重建报告)。文件交接对账结合持久化历史与实际文件证据，同时遵守目录所有权和报告补投规则；回放历史本身不执行文件移动或删除。

状态报告成功放入 `ready` 后，由 camctl 在数据库中保存[已发布记录](status-reports.md#记录报告已经发布)。主程序继续按目录协议领取和处理文件。

## 配置归属

`paths.staging`、`paths.ready`、`paths.processing` 指定三个交接目录，部署时须满足本专题的原子移动要求。

## 验收要求

### 单元测试

使用受接口约束的文件操作与状态存储替身，验证发布、领取、撤回的许可判定和错误分类。

主程序传输失败或中断、文件持续残留在 `processing` 时，验证 camctl 保持文件所有权边界，不从文件存在推断传输成功或后续必然重试。

### 集成测试

使用真实文件系统、SQLite 与主程序领取流程，验证完整文件发布、领取与撤回竞争，以及各持久化/移动步骤断电后的对账。文件系统原子性和实际断电持久性不能仅由单元测试证明。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 文件交接

- staging 不可见半成品；
- staging → ready 原子发布；
- ready → processing 不可撤回；
- 主机断电恢复。

## 待确认与待细化

本节不构成已确认的行为选择。涉及其结果的实现须先补齐契约。

### 后续契约完善

定义业务记录与文件移动之间的持久化协议；以记录状态、文件位置和所有者建立恢复表。必须覆盖发布成功但记录未更新、文件已被领取并删除、撤回与领取竞争、报告替换中断。需要结合主程序可提供的协调方式和目标存储环境确认保障，不能仅依据目录中缺少文件推断发送成功。
