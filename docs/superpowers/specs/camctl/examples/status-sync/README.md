# 从旧备份补齐录像与交付状态

[客户端状态同步](../../status-sync.md) · [其他客户端协议样例](../../client-protocol-examples.md) · [业务变化编号](history.md)

用户连续两天用相机拍摄录像 A、B，并把视频取回到个人电脑。随后，用户提交计划，清理已经保存到电脑的录像 A 的相机原片。此时客户端数据库需要恢复，用户使用了一份只保存到第一天的旧备份。

恢复后，页面记得录像 A，却不知道第二天的录像 B，也不知道 A 已经从相机清理。用户需要把这些状态补齐，才能继续判断哪些录像已拍摄、哪些文件已取回、哪些相机原片还可以清理。

本例沿着这一过程说明：缺少历史怎样被发现、怎样从一份已知报告之后补齐，以及补齐后怎样继续日常业务。

## 先看用户实际做什么

| 阶段 | 用户操作 | 主机发生的事与返回内容 |
| --- | --- | --- |
| 第一天 | 提交“录像 A、取回 A”，导入报告和视频，并保存客户端备份 | 完成录像和取回，自动报告 1；相机原片 A 继续保留 |
| 第二天 | 提交“录像 B、取回 B”，顺便确认报告 1；导入新报告和视频 | 完成录像和取回，自动报告 2；相机原片 B 继续保留 |
| 第三天 | 提交“清理原片 A”，顺便确认报告 2 | 删除相机原片 A，自动报告 3 |
| 恢复旧备份后 | 导入报告 3，发现缺少历史；提交从报告 1 之后补齐的计划 | 保持已保存的累计确认，另行生成覆盖缺失状态的同步报告 |
| 补齐后 | 导入同步报告，重新看到录像 B 和 A 的清理结果；随后提交“清理原片 B”，顺便确认同步报告 | 删除相机原片 B，恢复普通增量报告 |

本例中用户收到的视频文件仍保留在个人电脑上，恢复的是较旧的业务状态。同步报告可以恢复视频与计划、动作、交付的关联。必要时，用户重新导入自己保留的视频文件完成关联及核验；状态同步本身不要求重新录像或重新从相机取回。

## 文件入口与演练前提

这些文件属于独立的一份单主机历史，从水位 0 开始，不与其他样例混合。时间均为 UTC。正常业务计划不需要附加报告动作，会话按既定规则自动报告；用户需要恢复状态时才显式请求同步。

| 用途 | 完整执行计划 |
| --- | --- |
| 第一天录像并取回 A | [capture-a-plan.json](capture-a-plan.json) |
| 第二天录像并取回 B，同时确认报告 1 | [capture-b-plan.json](capture-b-plan.json) |
| 清理相机原片 A，同时确认报告 2 | [cleanup-a-plan.json](cleanup-a-plan.json) |
| 从旧备份对应的报告 1 之后补齐 | [recover-plan.json](recover-plan.json) |
| 补齐后清理相机原片 B，同时确认报告 5 | [cleanup-b-plan.json](cleanup-b-plan.json) |

确认附带在实际要递交的业务计划中。用户导入报告之后暂时没有任务，可以等待下次业务输入再确认。

| 4 | `(20, 47]` | [报告 4](status-report-4-508254cf5833e6fba62afb6f6d3efde26752d126849dbe6ab5d745c1f8737dfd.json) | 缺失状态已覆盖，同步动作仍在运行 |

相机参数沿用[协议样例驱动](../../client-protocol-examples.md#阅读与使用范围)的 `timed` 类型，60 秒仅为本次演练任务时长。这些 JSON 用于解释协议，真实相机应使用其正式能力说明。视频大小和视频摘要是演示数据；报告文件名中的 SHA-256 则根据所提供 JSON 的真实字节计算。

## 第一步：两天的录像分别完成

第一天的 `capture-a-plan.json` 包含“录像 A”和“取回录像 A”。执行成功后：

- 录像 A 的相机原片登记为 `o-sync-001`。
- 本次取回登记交付 `d-sync-001`，待传文件为 `d-sync-001.mp4`。
- 自动报告 1 覆盖 `(0,20]`，说明计划完成、录像成功、交付已发布。

客户端导入报告和视频，核验视频后显示已经收到。用户此时保存一份客户端备份：它具有截至水位 20 的完整业务状态，所对应的报告 ID 是 1。

第二天，用户提交“录像 B、取回 B”，在计划顶层附带 `last_report_id: 1`。主机累计确认位置成为 20。第二天的动作完成后，报告 2 覆盖 `(20,40]`，包含 B 的录像、原片 `o-sync-002` 和交付 `d-sync-002`。A 没有变化，本次报告不再重复它；客户端合并后同时拥有 A、B 的记录。

`report_id: 2` 表示这份报告的身份，其终点是 `to_wm: 40`。两个动作包含受理、启动、停止、产物登记、拷贝和发布等多次业务变化，因此水位不能按动作数量计算。

## 第二步：清理 A 后，旧备份接不上新报告

用户已核验并保存 A 的视频，提交 `cleanup-a-plan.json` 清理相机原片 `o-sync-001`。计划顺便附带 `last_report_id: 2`，因此主机累计确认位置变为 40。

清理完成后，报告 3 覆盖 `(40,45]`，包含 A 的原片已清理，以及清理动作成功。已经收到的电脑视频和此前交付记录保留。

在导入报告 3 之前，客户端恢复到第一天的旧备份。两边此时掌握的状态是：

| 位置 | 记住的状态 |
| --- | --- |
| 客户端旧备份 | 完整到 20：只知道 A 已录像、已取回，原片在相机上可用 |
| 主机累计确认 | 已到 40：此前收到过报告 2 的有效确认 |
| 主机当前业务状态 | 已到 45：还保存了清理 A 的结果 |

客户端导入报告 3 时发现：本地完整到 20，报告却从 40 之后开始，缺少 `(20,40]`。它显示历史缺失异常，保留旧备份中的页面状态，抛弃这次无法应用的报告，并引导用户请求同步。

缺口依照报告覆盖范围判断。若只套用报告 3，页面虽然能更新 A 的清理结果，却仍不知道录像 B，无法构成完整的业务状态。

## 第三步：从旧备份的报告之后补齐

用户递交 [recover-plan.json](recover-plan.json)，完整输入为：

```json
{
  "request_id": "req-sync-004",
  "created_at": "2026-09-15 10:00:00",
  "name": "恢复旧备份后的状态同步",
  "actions": [
    {
      "name": "补齐报告 1 之后的状态",
      "type": "report_status",
      "params": {
        "scope": "since",
        "after_report_id": 1
      }
    }
  ],
  "last_report_id": 1
}
```

`last_report_id: 1` 表示客户端现有的可靠确认。主机已保存的位置为 40，较旧确认不会让它回退：`max(40,20)=40`。

`after_report_id: 1` 另外表达这次同步的起点。主机查询报告 1 的终点 20，在同步动作执行时固定该起点。受理和开始同步产生业务变化 46、47，因此报告 4 的范围为：

```text
主机累计确认 A = 40
本次同步起点 S = 20
此时报告截止的业务水位 H = 47

报告下界 = min(40,20) = 20
报告 4 覆盖 (20,47]
```

报告 4 已经补齐 B 的记录和 A 的清理结果，同时说明同步动作正在执行。报告 4 完成本地发布后，同步动作才能保存成功，产生变化 48。会话收尾的报告 5 因而覆盖 `(20,48]`，并表达同步动作成功，结果引用 `result.report_id: 4`。

两份同步报告都包含本次责任登记事务。报告 1、2、3 生成得更早，不能确认本次同步责任；不能只因为旧确认数值较大，就认为本次恢复已经完成。

## 第四步：导入报告 5，恢复业务状态

假定客户端只收到报告 5。旧备份完整到 20，报告 5 覆盖 `(20,48]`，可以直接合并至 48，无需再寻找并导入报告 2、3、4。

| 业务对象 | 旧备份中的状态 | 合并报告 5 后 |
| --- | --- | --- |
| 录像 A 的原片 | 在相机上可用 | 已从相机清理，历史身份保留 |
| A 的取回及交付 | 取回成功，交付 `d-sync-001` 已发布 | 保留原有记录；本次没有变化 |
| 录像 B、原片和交付 | 尚无记录 | 录像及取回成功，原片仍可用，交付为 `d-sync-002` |
| 清理 A 的计划 | 尚无记录 | 已完成，清理成功 |
| 本次同步计划 | 尚无记录 | 已完成，同步动作成功 |

报告 5 中，A 所在计划的 `actions` 只包含原片发生变化的录像动作，未包含没有变化的取回动作。客户端按动作 ID 合并，保留已有取回和交付；不能把这次数组直接覆盖成计划的全部动作。

保存完整状态后，页面可以恢复 A、B 的历史及文件关联，结束本例的历史缺失提示。同步动作的结果引用报告 4，不要求先收到报告 4，也不表示视频交付重新执行。

## 第五步：在清理 B 的计划中确认同步

用户确认 B 的视频已在电脑上保存并核验，决定清理相机原片。`cleanup-b-plan.json` 明确选择 `o-sync-002`，并附带 `last_report_id: 5`。

输入到达主机后，累计位置推进至报告 5 的终点 48。这份报告从 20 开始，且包含本次同步登记事务，因此同时结束本次同步责任。清理 B 作为新业务继续执行；原同步动作保持原有成功结果。

清理完成产生自动报告 6，范围为 `(48,53]`，只携带 B 的原片清理变化及本次清理计划。客户端保留此前已经合并的其他状态，继续按普通增量规则更新。确认没有单独占用一份人工递交文件，也没有授权计划目标以外的文件删除。

## 必要失败处理与核对

引用了不存在的起点报告时，只有该同步动作失败，原片和既有交付保持原状态。完整输入、报告及编号见[起点报告不存在的附例](missing-report.md)。它接续报告 6 之后的状态，单独演练运行失败，不属于上述正常使用步骤。

核对本例时应确认：

- 报告文件名、原始字节摘要、报告身份及 Schema 一致；水位对应[编号附页](history.md)的完整事务边界。
- 报告 3 无法接上旧备份；报告 5 可以直接接上，同时恢复丢失的 B 和 A 的清理结果。
- A 的取回及交付没有在同步报告中出现时，客户端继续保留；报告 6 同样不会删除未出现的历史对象。
- 旧 ACK 不回退主机进度；同步起点独立保存；合格 ACK 结束同步，后续新业务按普通范围报告。
- 设备调用、视频拷贝和删除仅由对应业务计划发起，状态同步不重放这些动作。

文件和静态推演用于验证协议表达，不代表真实相机、CLI、数据库恢复或客户端已经通过集成测试。
