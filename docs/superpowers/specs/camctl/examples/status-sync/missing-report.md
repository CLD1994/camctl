# 附例：请求同步时引用了不存在的报告

[返回正常使用过程](README.md) · [同步起点解析规则](../../status-sync.md#camctl-何时开始同步)

本附例用于核对必要的失败处理。它接续正常样例：客户端已经导入报告 6，完整保存到水位 53，两段录像的相机原片均已清理，历史和个人电脑中的视频保留。

假定一次输入错误使用了尚不存在的报告 999 作为同步起点。这个引用不满足正常客户端选择可靠起点的前提；格式上却是合法正整数，应由动作执行时查询确认。

| 文件 | 用途 |
| --- | --- |
| [missing-report-plan.json](missing-report-plan.json) | 新请求 `req-sync-006`，参数为 `scope: "since"` 和 `after_report_id: 999`，同时携带有效 ACK 6 |
| [报告 7](status-report-7-b3c69f87a6b052170f47c8d243fc22c6b1aad24a180dfbd3e8d3aa96bdc68905.json) | 覆盖 `(53,56]`，表达同步动作的运行失败 |

| 业务编号 | 已保存的事实 |
| --- | --- |
| 54 | 受理计划 `p-sync-006`，动作 `a-sync-601` 为 `pending`；同次 ACK 6 使累计位置推进到 53 |
| 55 | 同步动作开始执行 |
| 56 | 查询可靠确认报告 999 不存在，动作失败，计划完成 |

55、56 在同一个执行事务保存，不登记同步责任。报告 7 采用的记录截止于这次完整提交之后，覆盖 `(53,56]`；客户端可以把它接在报告 6 之后，看到具体失败。

动作保留原输入，错误为：

```json
{
  "code": "sync_report_not_found",
  "stage": "execution",
  "details": {"after_report_id": 999}
}
```

`execution.started` 为 true，没有成功的 `result.report_id`，也没有改为完整同步。既有计划、原片清理结果及视频交付保持原事实。需要恢复时，客户端核对起点并使用新请求，或选择完整同步。

报告不存在与数据库查询失败分别处理。查询失败、报告记录中的必要生成信息损坏或结果未知须按会话错误处理，不能使用本附例的“报告不存在”结果。格式错误则属于受理时的单动作自身错误，执行时未知引用不归入该分区。

重复提交同一请求继续对应原动作和失败结果；后来出现报告 999 也不重新执行这个已终态动作。不同正常业务请求按各自资格继续处理。
