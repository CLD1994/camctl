# 正式产物与取回清理

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义正式产物和普通 delivery（一次具体交付）的业务生命周期，包括取回、撤回资格和清理。目录所有权及发布/领取规则由[文件交接](file-handoff.md)定义；状态报告通过[状态报告与累计确认](status-reports.md)对外表达这些业务事实。

## 正常取回与清理流程

一次正常取回从已受理的来源引用开始：到达 `scheduled_at` 后取得来源动作的正式产物，为选中的每份产物建立本次请求独立的 delivery，将源文件拷贝到 `staging`，完成读取校验及落盘后发布到 `ready`。报告记录实际文件名、可读名称、大小、摘要和来源，供客户端接收与校验。

成功交付后，正式源文件仍保留。客户端需要再次取回时使用新的请求；需要释放源文件空间时，通过 `delete_action_outputs` 明确指定产物 ID。相机原片与修复成品各自选择、各自清理。具体选择、时机和文件所有权遵守后续各节。

## 正式产物模型

正式产物具有稳定身份：

```text
output_id
```

产物记录至少能够表达：

- `output_id`
- `source_action_instance_id`
- 类型
- 原始文件名（如适用）
- 大小
- `sha256`
- 可用状态
- 视频时长（如适用）
- 派生关系（如适用）
- 清理状态

动作状态与产物可用性相互独立。

录像原片的保留资格见[原片保留与核验结果](camera-recording.md#原片保留与核验结果)。媒体核验结果与文件可取回状态分别表达：已登记的原片即使无法正常播放或核验未确认，仍允许原样取回；本次拷贝继续满足可靠读取、落盘和摘要校验要求，媒体内容问题不能代替或绕过交付文件的一致性校验。

不能使用：

```text
source action = failed
```

直接推导：

```text
没有任何可取回产物
```

异常多录录像修复成功后产生两份不同正式产物：

```text
原片
修复成品
```

两者拥有不同 `output_id`。

### 主机派生产物

在主机加工形成的成品保存在[派生产物目录](file-handoff.md#staging) `staging/derived/`。每份正式派生产物具有自己的 `output_id`、保存位置及来源产物关联；其内容在登记后保持不变，后续取回使用这份保留文件生成独立 delivery。

修复成品的登记时点遵守[录像动作的结束时点](camera-recording.md#录像动作的结束时点)。文件准备完成但登记尚未提交时，仍按原处理流程恢复；提交结果未知时先核实数据库事实，不能仅凭目录中的文件将其登记或删除。

| 文件职责 | 保存位置 | 生命周期依据 |
| --- | --- | --- |
| 相机等已接入设备的正式产物 | 所属设备存储 | 本专题的长期保留与显式清理规则 |
| 主机已登记的派生成品 | `staging/derived/` | 同样长期保留，清理时指定其自身 `output_id` |
| 主机加工输入、未完成文件及尚未登记的成品 | `staging`；准备完成的派生成品可已位于 `derived` | 所属加工流程的完成、取消及恢复规则 |
| 某次取回的工作文件与独立交付文件 | `staging` 中 `derived` 以外的工作位置，发布后进入 `ready/processing` | 本次取回及文件交接规则 |

取消取回只处理该次取回的文件，不删除 `derived` 中的正式成品；主程序发送并删除交付文件后，新的取回仍能使用该成品。派生成品与其来源分别遵守“不级联删除”规则。

### 长期保留

所有正式产物，包括照片、普通录像、异常录像原片及修复成品，统一保留到客户端明确提交清理请求。客户端通过 `delete_action_outputs` 指定要清理的 `output_id`，camctl 按本专题的清理资格、旧取回优先及失败恢复规则处理。MCU 第一版仅[预留接口](mcu-actions.md#第一版范围)，其产物在后续接入时遵守公共生命周期。

| 是否存在针对该产物的有效清理请求 | 其他情况 | 正式产物的处理 |
| --- | --- | --- |
| 否 | 任意取回或传输结果、保存时长及剩余空间 | 继续保留；这些情况单独或共同出现均不授权自动删除 |
| 是 | 任意取回或传输结果、保存时长及剩余空间 | 按“产物清理”处理；有效请求不等于可以立即删除，仍须满足清理与取回并发规则 |

修复成功不自动删除原片；空间不足也不通过淘汰旧正式产物解决。客户端负责安排显式清理以释放空间，当前操作按其空间不足规则报告结果。

本规则约束正式产物的保留。主程序传输后删除 delivery 文件、camctl 撤回可撤回的 delivery，仍遵守各自的交接规则，不因此删除正式产物。未成为正式产物的临时文件和取消录像产生的废弃文件，按所属处理流程管理；不能用临时文件清理绕过正式产物的保留要求。

清理只改变文件及其可用性，不删除数据库中的产物、取回、交付和清理历史。数据库记录继续永久保留。

## 取回与清理的执行时间

`obtain_action_outputs` 和 `delete_action_outputs` 均为无时效动作，可以按 `scheduled_at` 指定开始处理的时间，允许延后执行。`scheduled_at` 不表示完成期限；这两类动作不采用 `max_delay_ms` 过期窗口，终态为 `succeeded`、`failed` 或 `canceled`。

取回与清理请求的 `scheduled_at` 均必填，缺省按[公共时间字段规则](scheduling-execution.md#scheduled_at)处理。已指定合法时间的请求按下表处理，取消和已提交的终态优先于时间判断：

| 动作与时间情况 | 处理 |
| --- | --- |
| 动作已取消或进入其他终态 | 保持原结果，按所属收场规则处理，不因到达计划时间而重新执行 |
| 动作未开始，可信当前时间早于 `scheduled_at` | 等待计划时间，不提前取回或删除 |
| 已到达或超过 `scheduled_at`，动作仍未完成 | 按产物可用性、取回与清理并发规则及剩余重试预算执行；需要等待录像结束或旧取回时保留未完成状态 |
| 主机重启，动作仍未完成且已超过计划时间 | 恢复原请求和已保存的进度，不因延迟自动过期 |
| 时间无法可靠判断 | 遵守公共时钟检查与受限执行规则，不能自行判为已到时间或过期 |

单次通信超时、有限重试耗尽、空间不足和取消仍按各自规则处理。等待录像结束或已有取回完成，不等于一次设备通信失败，不能只因计划时间已过去就记录失败；设备操作也不能因“无时效”而无限重试。

计划受理时间与动作计划执行时间分别保存；受理较早不表示应在自己的 `scheduled_at` 之前执行。取回与清理竞争同一产物时，遵守下面的执行顺序。

### 延后执行时的取回与清理顺序

正常调度或重启恢复时，同次调度看到指向同一已登记、可用产物的取回与清理动作，若两者均未开始、均已到计划时间，且尚无既有取回资格或删除限制，则按 `scheduled_at` 从早到晚处理；计划时间相同时，取回优先于清理。请求受理顺序、数据库查询返回顺序及内存加载顺序不能颠倒这一顺序。

| 两个动作的计划执行时间 | 处理顺序 |
| --- | --- |
| 取回早于清理 | 先处理取回并建立旧取回保护，再按“清理与取回并发”处理清理；不能抢先登记删除限制而使这个取回失去资格 |
| 清理早于取回 | 先按清理规则处理；后续取回遵守已经形成的删除限制与实际产物可用状态，不能仅因它更早提交而插队 |
| 两者相同 | 先处理取回并建立旧取回保护，再按“清理与取回并发”处理清理；即使清理请求更早受理，也不能抢先删除 |

例如 10:00 取回视频 A、11:00 删除 A，主机直到 12:00 才上电，两者均未执行且 A 仍可用：先处理取回，再删除 A。清理等待已有取回不再需要读取 A，具体见“清理与取回并发”；独立交付副本可靠准备完成后，无须等待发布、主程序发送或客户端收到。取回最终失败或取消时，须确认该项读取及重试已停止，不要求取回必须成功才允许清理。

该排序用于尚未开始的动作。已经取得的取回资格、已经登记的删除限制及已经发生的删除仍按并发和恢复规则处理，不能因重新排序而撤销。资格授予与顺序保存的事务边界，以及取回仍在等待录像结束而尚不能确定产物时的处理，仍需细化。

## 相机视频的断点续传

第一版要求相机视频拷贝到主机时支持跨主机重启的断点续传。拷贝因主机断电而中断后，后续实际启动的 `run` 在该处理仍有执行资格时，使用主机上已经可靠保留的部分继续拷贝，不因进程重启而统一从头取回整个视频。

已确认的运行前提是：相机内的源文件不会自行丢失，camctl 是这些文件的唯一访问者。拷贝对象为相机已经写完的视频文件，写完后内容和长度保持不变。camctl 按显式清理请求删除文件时，仍遵守本专题的清理与取回规则；已经取得取回资格的请求恢复续传时继续持有原资格。

开始拷贝时确定源文件身份及其完整长度，后续续传继续读取同一份固定内容，并以该长度确定拷贝的结束位置。当前相机的文件写入完成依据见[停止成功与文件可读](camera-recording.md#停止成功与文件可读)；来源身份表示及停止结果未知时的对账方式仍需结合设备协议细化。

该要求适用于 camctl 将视频从相机拷贝到主机的流程，包括 `obtain_action_outputs` 取回、相机录像内部修复，以及[计时证据不足时的原片检查](camera-recording.md#计时证据不足时的原片检查)所需的拷贝。后两者属于录像内部处理，不创建普通 delivery。主机向外部客户端传输文件由第三方主程序负责，其重试行为按文件交接专题处理。

续传需要保留相机源文件、主机上的未完成文件及所属处理任务之间的关联，以及能够可靠恢复的拷贝进度。已确认的进度变化按全局规则追加历史并同步更新投影。恢复同一次取回时沿用原请求和交付身份，未完成文件继续由 camctl 管理，不能发布到 `ready`。完成后的交付仍遵守本次取回的发布屏障。

### 同一相机的拷贝并发限制

第一版同一相机在同一时刻最多进行一份文件从相机到主机的拷贝。`obtain_action_outputs`、异常原片检查和内部修复所需的源文件拷贝共用这个限制，不能各自启动一份并行拷贝。同一产物的不同交付请求仍分别准备独立副本，依次取得拷贝机会，不合并请求或复用在途 delivery。

限制以源相机为范围；不同相机分别协调。从主机 `staging/derived/` 准备交付副本、主机上的媒体处理以及主程序对外传输，不占用相机的拷贝机会。它们继续遵守自身的执行资格与资源要求。

| 拷贝或设备操作情况 | 并发约束 |
| --- | --- |
| 同一相机已有一份文件正在拷贝 | 其他文件等待；分段保存进度期间仍属于同一份拷贝，不借段间间隙交错拷贝另一份文件 |
| 当前拷贝读取失败，仍有执行资格及重试预算，正在等待重试 | 保留该文件的拷贝机会，其他文件继续等待；到达重试时间后恢复原拷贝 |
| 一份文件的源内容已全部读取，且相应设备读取已结束 | 后续仅在主机进行的校验、修复、等待组成员或发布，不占用该相机的拷贝机会 |
| 拷贝被取消或最终失败，但实际读取尚未停止或无法确认已经停止 | 先完成对应停止与确认，不启动同一相机的另一份拷贝 |
| 拷贝被取消或最终失败，且已确认实际读取及后续重试停止 | 解除拷贝机会的保留，再选择其他具备条件的文件 |
| 相机继续录像，或需要执行必要的停止命令 | 按驱动兼容性执行控制操作，不要求它们等待整份文件拷贝完成 |

只有具备源文件读取资格、来源已写完且满足所属流程执行条件的文件，才可开始拷贝。排队不等于拷贝失败，也不消耗设备读取尝试次数；等待源录像结束的请求不占用拷贝机会。获得拷贝机会不授予新的取回资格，也不解除已有取回对源文件的清理保护。

正常调度、取消处理及重启恢复均使用同一限制，不能分别创建互不协调的拷贝通道。重启后保留每份文件原有的身份、进度与预算，按既有断点续传规则恢复；一次只恢复一份相机拷贝，不因存在多个未完成文件而全部并行启动。实际复制工作的暂停或结束，与源文件读取依赖的解除分别处理，后者仍须满足“准备完成与断电恢复”的持久化条件。

#### 等待重试时保留拷贝机会

取回、异常原片检查及修复输入拷贝使用相同规则：一份文件已经取得相机拷贝机会后，读取失败进入有限重试等待，仍为它保留下一次拷贝机会。其他文件即使已具备读取条件，也不能在等待期间开始拷贝。源文件内容固定，原半成品、可靠进度、身份、读取资格和剩余预算继续按既有规则保留。

例如 A 已可靠保存 100 MB，读取失败后等待 30 秒重试。此时 B 已准备好，也须等待；30 秒后 A 从其可靠进度继续读取。A 完成源内容读取后，才允许选择 B 等候选文件。若 A 取消或最终失败，则在确认读取及重试已停止后解除保留。

拷贝机会的归属、重试等待与解除事实按历史和投影规则可靠保存。重启时先恢复已有保留关系：A 尚具备重试资格则继续等待或恢复 A，不能因重新加载候选文件而让 B 抢先。保留关系不增加重试预算；错误耗尽后仍按原有限失败规则结束，不通过反复新建拷贝重置预算。

保留范围仅为该相机的文件拷贝。录像、必要的停止命令及其他已确认兼容的控制操作继续按设备执行规则处理。该保留也不解除源文件的旧取回保护。

源内容读完并释放拷贝机会后，后续校验发现不一致而需要重拷时，按有限重拷规则重新参与候选选择；不能追溯恢复已经释放的保留关系，或打断此时正在拷贝的另一份文件。

#### 多个候选文件的选择顺序

每台相机独立选择待拷贝文件。先恢复和处理已有活动拷贝或等待重试的保留关系；只有没有此类占用或保留时，才在当前已具备拷贝条件的文件中选择一个。条件包括所属动作仍可执行、计划时间已到、源内容已写完、读取资格成立，以及所属流程允许本次读取。尚未形成文件或仍在等待来源结束的请求不阻挡其他合格候选文件。

排序使用负责发起这次拷贝的动作，而不是一律使用源录像动作：

| 拷贝用途 | 用于排序的所属动作 |
| --- | --- |
| 用户请求取回原片 | 本次 `obtain_action_outputs` |
| 异常原片检查 | 需要该检查的 `camera_record` |
| 内部修复所需的源文件拷贝 | 需要该修复的 `camera_record` |
| 校验不一致后的有限重拷 | 沿用原拷贝所属动作，不按重拷发生时间改排 |

合格候选文件按以下顺序比较，前一项相同才比较后一项：

1. 所属动作的 `scheduled_at`，从早到晚。
2. 所属计划的 `plan_seq`，首次受理较早的计划优先。
3. 所属动作在原计划 `actions` 数组中的位置，从前到后。
4. 同一动作内文件条目的首次登记顺序；登记时保存固定顺序，后续恢复沿用。

内部检查或修复不会仅因用途而取得额外优先级。相应录像的计划时间较早时，其已具备条件的输入拷贝排在较晚的取回动作之前；用户取回的计划时间较早时，顺序相反。

例如，09:00 录像的修复输入与 10:00 的取回请求在本次调度时均可拷贝，且该相机没有活动拷贝或保留关系：先处理修复输入。若修复输入尚不能读取，则可以开始该取回；取回开始后，即使较早录像的修复输入随后具备条件，也须尊重当前文件的拷贝及重试保留关系。

每次释放拷贝机会后重新从当时合格的文件中选择。一次取回包含多份文件时，不为整个取回动作预占相机；同一动作后续才确定的文件追加登记顺序，不改变已登记条目的顺序，也不扩大已固定的选择集合。

正常调度和重启恢复使用同一组持久化排序依据；数据库查询返回顺序、目录枚举顺序和内存加载顺序不能代替它们。排序依据无法可靠读取或解释时，按状态库错误处理，不猜测先后。取得机会后遵守原身份、进度及有限预算；排序本身不授予读取资格、不修改删除限制，也不提前执行尚未到时间的动作。

### 先保存文件，再记录进度

拷贝按段保存进度。数据库中的进度表示从文件开头起，已经连续写入并可靠落盘的字节数。进度为 `C` 时，主机文件的前 `C` 字节必须与源文件对应内容一致；进度的推进不能跳过字节或包含尚未可靠保存的数据。

每段按以下顺序处理：

1. 从源文件的对应位置读取数据，连续写入主机文件。
2. 清空写入缓冲并完成文件同步；文件新建或路径发生变化时，同时保证所需目录变更已经落盘。
3. 在数据库事务中追加已保存进度的历史并同步更新投影，提交成功后继续下一段。

进度按实际连续写入并同步成功的字节数计算。写入或同步失败时不推进进度；进度事务失败或提交结果不确定时停止继续拷贝，后续恢复先确认数据库实际提交的进度。文件操作及设备读取不占用数据库写事务。

### 重启后选择续传位置

以下规则适用于处理任务仍有执行资格、源文件身份及未完成文件关联可可靠确认的情况。设源文件完整长度为 `N`，数据库已保存进度为 `C`，主机未完成文件当前长度为 `L`。这些量均以字节计，合法进度满足 `0 ≤ C ≤ N`。先处理无法可靠判断或数值越界的情况，再按文件是否存在及长度关系处理。

| 恢复时的情况 | 处理 |
| --- | --- |
| 文件不存在，`C = 0` | 创建未完成文件，从源文件开头开始 |
| 文件存在，`L = C < N` | 从源文件及主机文件的偏移 `C` 处继续拷贝 |
| 文件存在，`C < L ≤ N` | 将未被进度确认的尾部截去，使文件长度回到 `C`，再从 `C` 继续 |
| 文件存在，`L = C = N` | 全部字节已经保存，进入后续完整性确认及相应处理，不再读取视频数据来续传 |
| 文件不存在但 `C > 0`，或 `L < C` | 已记录的可靠数据缺失，保留诊断并按错误处理，不能跳过缺失部分继续拷贝 |
| `C` 超出合法范围，或 `L > N` | 状态不符合拷贝约束，保留诊断并按错误处理 |
| 文件、进度或身份无法可靠读取或确认 | 停止依赖这些信息的续传判断，不能当作文件不存在或进度为零 |

例如，数据库记录前 100 MB 已保存，文件当前有 110 MB，且未超过源文件长度时，恢复先截去后 10 MB，再从 100 MB 处续传。已记录进度内的数据保留，未被记录确认的尾部允许重新读取。截断失败时不能继续写入；恢复操作再次中断后仍按上表判断。

最终文件必须与固定源文件逐字节一致。续传不能留下空洞、重复片段或多余尾部；读取提前结束但尚未达到 `N` 时不能判定拷贝完成。文件长度及进度相同只说明字节范围已经保存，读取及校验还须满足下一节的要求。

每段的大小、进度保存频率和设备按指定位置读取的能力仍需细化。

### 读取正确性与文件校验

相机驱动负责从指定位置正确读取源文件，并检测、报告传输错误；camctl 负责连续写入、落盘和恢复位置的正确性。设备接入时必须确认驱动能够履行可靠读取的契约。读取失败或结果无法确认时，不能仅凭取得了足够长度的数据就认定取回成功。

源端摘要是额外校验能力，不是所有相机的必备条件。设备具备该能力时，取回完整视频后比较源端与主机端摘要；明确不具备该能力时，以已确认的可靠读取契约和正确续写流程为依据完成取回。

当前相机已确认能计算源文件的 SHA-256，采用源端与主机端 SHA-256 比较；其通信方式见[通信方式与查询能力](camera-recording.md#通信方式与查询能力)。其他相机由对应驱动说明其读取和摘要能力；具体命令、返回格式、二进制数据读取和错误识别方式仍需在设备适配时核实。

主机端仍须计算最终文件的 SHA-256，并作为报告中的 `sha256` 提供给客户端，用于检查后续收到的文件。该摘要对应实际交付内容；它与可选的源端比较承担不同职责。

完成可靠读取、文件落盘及主机摘要计算后，按下表处理源端校验：

| 源端摘要能力 | 获取或比较结果 | 处理 |
| --- | --- | --- |
| 已确认支持 | 摘要相同 | 校验通过，继续该视频的后续处理 |
| 已确认支持 | 摘要不同 | 内容不一致，按“摘要不一致后的有限重拷”处理，不将该副本用于交付或修复 |
| 已确认支持 | 摘要获取或比较失败、结果未知 | 保留诊断并按错误处理，不能当作设备不支持而跳过校验 |
| 已确认不支持 | 无源端摘要 | 按可靠读取及正确续写的结果继续处理，主机摘要仍用于客户端校验 |
| 能力尚未确认 | 无可靠判定 | 先确认设备能力，不能直接归入“不支持”分支 |

成功取得的源端摘要关联同一份内容固定的源文件，可以在后续取回中复用。摘要及比较结果按全局历史规则保存；能力不支持、获取失败和内容不一致分别表达。

### 摘要不一致后的有限重拷

源端与主机端 SHA-256 不一致时，当前主机副本无效，不能交付或用于修复。camctl 保留相机源文件，在有限次数内从头重拷同一视频；每次重拷完成后重新校验，仍不一致且次数耗尽时报告该视频拷贝失败。

| 当前处理是否仍允许执行 | 剩余重拷次数 | 处理 |
| --- | --- | --- |
| 是 | 还有次数 | 持久化本次重拷决定，再从源文件开头重新拷贝 |
| 是 | 已耗尽 | 该视频拷贝失败，不交付或使用无效副本 |
| 否，例如处理已被取消或已终态 | 任意 | 不开始新的重拷，按原有取消或终态规则处理 |
| 执行资格或次数无法可靠判断 | 无法确认 | 保留诊断并按错误处理，不能获得新的重拷次数 |

首次拷贝不计入重拷次数。次数上限在该视频拷贝处理开始时确定并持久化，已经消耗的次数跨重启保留。重拷仍属于原处理任务；同一次取回保留原请求、产物和交付身份。

开始每次重拷前，在同一数据库事务中记录原副本无效、消耗一次重拷次数及新一轮从零开始的拷贝状态，并同步更新投影。提交成功后才重新准备主机文件，原无效副本的进度不再作为这一轮的续传依据。记录失败或提交结果不确定时，先确认数据库事实，不能直接重置文件或重新分配次数。

重拷过程中仍支持断点续传。若决定已提交、文件尚未重新准备时断电，恢复继续执行这次已经计数的重拷；若已经保存新一轮的部分数据，恢复从该轮已确认进度继续。恢复同一轮重拷不重复消耗次数，也不能把前一轮的无效数据接到新一轮文件中。

次数耗尽的失败仅说明这次主机拷贝未取得有效副本，不据此判断相机源文件损坏。取回请求的其他成功项继续按部分成功及发布屏障规则交付；内部修复的失败与录像结果按[相机录像](camera-recording.md)的证据规则分别处理。相机源文件仍遵守显式清理规则。

具体重拷次数上限及其与公共通信重试限制的配合仍需细化；主机重启、同一请求的重试和校验结果的重复处理均不能重置或重复消耗已确定的次数。

## obtain_action_outputs

### 作用

选择性获取指定动作或动作组的正式产物，并为本次请求生成独立 delivery。

产物的生成与修复由来源动作负责。来源动作尚未结束时，按本节的等待规则取得最终正式产物；本动作将选中的产物准备为独立待传文件，再按文件交接协议发布。

### 参数

`obtain_action_outputs` 的来源统一放在必填的 `params.source` 对象中。该对象恰好采用下表的一种字段组合，各字段值仍须满足对应名称或实例 ID 的合法性要求：

| `params.source` 的字段组合 | 查找范围与含义 |
| --- | --- |
| `action_instance_id` | 按稳定实例 ID 引用指定动作 |
| `plan_instance_id` 与 `group` | 引用指定计划实例内的组 |
| `action_name` | 仅引用本次取回所属计划中同名的动作 |
| `group` | 仅引用本次取回所属计划中该组的动作集合 |

`source` 缺失、不是对象、为空，或字段组合不属于上表时，首次受理将该动作登记为 `failed`。不能混用动作名、动作实例 ID 和组引用，不能仅提供计划实例 ID 来选择整个计划，也不能用计划名称定位另一个计划。错误范围与校验时点见“校验与失败处理”。

以下是一个取回动作，作为执行计划 `actions` 数组中的成员使用：

```json
{
  "name": "取回上午录像",
  "type": "obtain_action_outputs",
  "scheduled_at": "2026-09-11 12:00:00",
  "params": {
    "source": {
      "group": "上午采集"
    }
  }
}
```

本例获取自身所属计划中“上午采集”组的产物；`params.source.group` 表示来源组，动作公共字段 `group` 表示动作所属的组。`obtain_action_outputs` 不属于任何组，填写动作公共字段 `group` 会使该动作在受理时登记为 `failed`。

动作级引用的精确产物筛选使用 `params.output_ids`，与 `params.source` 并列；`source` 只承担来源引用。筛选的可选性和取值语义见“产物选择”，使用本计划内名称时的解析见“本计划内的产物引用”。

### 校验与失败处理

在计划公共结构合法、动作可被识别为 `obtain_action_outputs` 且满足动作名称约束的前提下，该动作自身的输入错误只使它失败。计划及全部动作仍按[整份校验与原子受理](protocol-session.md#整份校验与原子受理)一同保存；其他动作按各自规则执行。

| 校验内容 | 判定时点 | 发现错误时的处理 |
| --- | --- | --- |
| 该动作的参数结构、字段格式和组合，包括 `params`、来源引用及 `output_ids` | 首次受理 | 将该动作登记为 `failed`，保存具体错误 |
| 该动作自身的时间、策略及所属组等字段违反已定义的要求 | 首次受理 | 将该动作登记为 `failed`，不执行或加入任何组 |
| 本计划内名称引用对应的动作或组是否存在、是否有能产生产物的来源动作 | 首次受理，根据本次完整计划判断 | 将该动作登记为 `failed`，保存缺失或来源类型不适用的原因 |
| 通过实例 ID 引用的动作，或指定计划实例内的组，是否存在并适合作为来源 | 首次执行且取得相应执行资格时 | 可靠确认目标缺失或没有产物来源时，仅该动作 `failed` |
| 来源产物是否已生成、可用，以及后续读取与交付结果 | 执行期间 | 按等待、逐项失败及发布屏障规则处理 |
| 数据库查询、记录解释或持久化失败、结果未知 | 发生时 | 按会话错误及恢复规则处理，不伪装为输入错误或目标缺失 |

首次受理不查询其他计划的来源是否存在，也不提前固定其来源集合。合法的实例引用先保存调用方指定的 ID 与组名，执行时再解析；本计划内的名称引用在受理时解析并保存有效来源关联。

初始失败状态、输入及诊断保留、原子受理和请求重送统一遵守请求专题的公共规则。参数错误的取回不产生执行尝试或 delivery；报告将其表达为已受理计划中的动作失败。

### 产物选择

客户端可以先通过状态报告取得 `output_id`，再提交新的取回请求。动作级引用允许可选的 `params.output_ids`：

语义：

```text
不带 output_ids
    → 获取该动作全部正式产物

output_ids = 非空数组
    → 精确获取这些产物

output_ids = []
    → 受理时该动作 failed
```

不得因为指定产物不可用而自动扩大选择范围。

例如：

```text
只请求修复视频
```

修复视频不可用时，不能擅自改传原片。

但调用方如果省略 `output_ids`，表示明确请求“全部正式产物”，其中包括原片。

### 本计划内的产物引用

`obtain_action_outputs` 通过 `params.source.action_name`，或仅含 `group` 的 `params.source` 对象，引用自身所属计划中的产物来源，无须客户端预先知道 camctl 分配的实例 ID。引用形式及字段位置见本动作的“参数”；本节定义其中两种局部引用的解析。

动作所属的组遵守[公共 group 约束](protocol-session.md#group)：取回动作不属于任何组，但允许引用组。无论来源组位于本计划还是其他计划，该引用均不把取回动作加入目标组；首次受理时须分别校验 `params.source` 和动作公共字段。

仅首次受理需要解析本计划内引用：先校验完整动作集合及名称约束，再按本计划的动作名称和组成员关系解析。允许引用在 `actions` 数组中排在取回动作后面的录像，数组顺序不限制引用，实际执行仍由各动作的时间和业务条件决定。

| 首次受理时的局部引用情况 | 处理 |
| --- | --- |
| 动作名对应本计划中唯一且能产生产物的动作 | 解析为目标动作的实例关联；其他参数继续按各自规则校验 |
| 本计划内的目标组存在，按类型筛选后至少有一个产物来源 | 保存本计划及目标动作的实例关联；其他参数继续按各自规则校验 |
| 本计划内的目标组存在，但按类型筛选后没有产物来源，或指定动作类型不产生产物 | 将该取回动作登记为 `failed`，保存来源类型不适用的原因 |
| 本计划内没有对应动作或组 | 将该取回动作登记为 `failed`，不延后等待其他计划提供同名目标 |
| 来源引用形式缺失、混用或不合法 | 按“校验与失败处理”将该取回动作登记为 `failed` |
| 计划内动作名称违反唯一约束 | 按计划公共结构错误拒绝整份计划 |
| 实例分配或关联保存失败、提交结果未知 | 按受理事务错误及恢复规则处理，不能保留部分计划或猜测关联 |

计划、全部动作、有效来源关联及失败动作的诊断在同一受理事务中保存历史和投影。历史保留调用方原有的局部引用语义；有效引用同时保存对应的实例关联，失败引用保留错误而不虚构关联。执行和恢复使用固定关联，不按后来出现的同名计划、动作或组重新查找。同一 `request_id` 的重试直接复用原计划，不重新解析本次正文。

例如一份计划安排“10:00 主录像”和“10:10 取回主录像产物”，后者使用 `action_name = 主录像`。camctl 受理时建立两者的实例关联；取回到达自己的 `scheduled_at` 后，录像若仍未结束则按等待规则继续等待。引用本身不建立成功依赖，也不提前授予尚未生成产物的读取资格。

局部引用只增加来源寻址方式。单个录像及组取回仍遵守后续的成员筛选、等待、产物选择、逐成员准备和发布屏障。动作级局部引用的 `output_ids` 规则与实例引用相同；请求尚未生成的全部产物时省略 `output_ids`，局部引用不提前分配产物身份。

### 按动作实例 ID 查找来源

使用 `params.source.action_instance_id` 时，首次受理仅校验引用结构及 ID 格式，合法时保存调用方指定的 ID，不查询目标或创建占位来源动作；格式错误按“校验与失败处理”登记动作失败。该规则同时适用于两个计划输入入口。取回取得执行资格后，才依据可靠的数据库查询结果处理目标；本计划内 `action_name` 的解析遵守前节规则。

取回自身的取消和既有终态优先；对仍有效的取回，按下表判定：

| 来源查询与已有事实 | 处理 |
| --- | --- |
| 可靠查到指定动作，其类型可产生产物，状态及记录可解释 | 保存来源关联，按动作状态及产物选择规则继续；录像尚未结束时遵守等待规则 |
| 可靠查到指定动作，但其类型不产生产物 | 仅该取回动作 `failed`，保存来源类型不适用的原因 |
| 可靠确认指定 ID 没有动作记录，且此前没有该来源已存在的可靠事实 | 仅该取回动作进入 `failed`，原因表达“来源动作不存在”；不等待该 ID 将来出现 |
| 查询失败、结果未知或记录无法可靠解释 | 按状态库错误处理，不记为来源不存在或正常等待 |
| 已有来源存在的可靠事实，但应永久保留的动作记录无法找到 | 按持久化一致性错误处理，不能用普通目标不存在掩盖历史缺失 |

来源查询所得有效关联或失败结果在同一事务中保存历史和投影，报告保留取回动作及请求中指定的来源 ID；不虚构来源动作、产物或 delivery。其他动作继续按自身时间与执行条件运行，不因该失败被拒绝或取消。记录保存不成功或提交结果不确定时，按状态库错误与恢复规则处理，不能假定来源已固定或失败终态已经成立。

已经保存的失败结果在重启、同一请求重送及后续来源出现时保持不变；新的取回意图须使用新的请求。报告和历史回放保留当时查询与判定的事实，不重新查询当前来源来改写结果。

### 等待录像动作结束

通过 `action_instance_id` 或已解析的本计划内引用请求单个 `camera_record` 的全部正式产物时，取回可以在录像动作结束前提交。camctl 保留该取回请求，等待被引用的录像动作进入终态，再确定本次要取回的文件集合。不能将等待期间暂时没有产物判为取回失败，也不能提前用当时已有的部分产物代表本次“全部产物”。

在取回已取得执行资格后，按下表处理；取回自身的取消和既有终态优先于继续等待或选择文件：

| 取回与被引用录像的状态 | 处理 |
| --- | --- |
| 取回仍有效，录像存在且尚未结束 | 保持取回未完成，记录等待对象；不开始文件取回 |
| 取回仍有效，录像已结束且有正式产物 | 确定并持久化本次选择的产物集合，再按逐项处理及发布屏障规则执行 |
| 取回仍有效，录像已结束且确认未产生正式产物 | 按“已结束动作没有正式产物”结束取回 |
| 取回已取消或进入其他终态 | 不因录像随后结束而重新开始取回；遵守原终态及收场规则 |
| 直接指定的动作实例 ID 确认不存在 | 按“按动作实例 ID 查找来源”处理，不解释为录像尚未结束或已结束但无产物 |
| 已固定且应存在的来源记录缺失，或状态、产物查询失败或结果未知 | 按持久化错误处理，不能冒充正常等待或无产物 |

等待不停止或重新启动录像，也不阻塞录像收场、其他动作或新取消请求的处理。录像的 `failed`、`expired` 或 `canceled` 不直接复制为取回的状态；取回依据最终正式产物及自身处理结果结束。

等待对象、已确定的产物集合及后续进度遵守数据库历史与投影规则。主机重启后，后续实际启动的 `run` 恢复同一取回：录像仍未结束则继续等待，已经结束则继续选择或处理；已确定的集合不因重启重新扩大。等待中的取回属于尚未完成的计划工作，参与会话接管与退出检查，无须客户端重新提交或主程序保留计划文件。

例如计划录像 10 分钟，第 3 分钟收到已经到执行时间的取回全部产物请求，camctl 先保留请求，等录像动作结束后再选择文件。录像完成正常控制流程或适用的异常处理后，将正式产物登记与动作终态一同提交，具体见[录像动作的结束时点](camera-recording.md#录像动作的结束时点)。原片也遵守这一登记边界；单独取回原片不能提前访问仍属录像内部处理的文件。等待遵守本专题的执行时间规则；报告中的等待阶段表达仍需细化。

### 按组取回的成员筛选

按组取回只将动作类型能够产生正式产物的成员作为来源，不以成员当前是否已有产物或执行是否成功决定是否选入。产物能力由动作接入时的业务契约声明，取回读取该声明，不自行维护一套拍摄动作类型清单。第一版 `camera_record` 可以产生正式产物；`report_status`、`cancel_task`、`delete_action_outputs` 不产生供取回的正式产物。状态报告使用独立的报告交接流程。

拍摄动作的具体文件种类、数量与关联由目标驱动为相应参数类型定义，见[驱动执行与产物边界](camera-recording.md#驱动执行与产物边界)。新增参数类型继续使用公共产物选择与交付流程。已支持的拍摄动作即使因目标设备不适用、参数类型或参数值错误而初始失败，仍按其拍摄类型作为产物来源；终态没有正式产物时记为失败项，不能将“本次未能执行”解释为“该类型不产生产物”。

本规则同时适用于指定计划实例的组引用和本计划内组引用。先按来源计划中各动作所属的组定位成员，再筛选取回来源；不修改原组成员，不影响组取消范围或报告组织。`obtain_action_outputs` 不属于任何组，遵守公共 `group` 约束。

| 成员类型与当前状态 | 本次组取回的处理 |
| --- | --- |
| 类型不产生正式产物，动作状态任意 | 不作为取回来源，不等待其结束，也不记为无产物失败项 |
| 类型可产生正式产物，尚未进入终态 | 保留为来源，按所属动作的等待规则处理，不能因当前无产物而跳过 |
| 类型可产生正式产物，已进入终态 | 保留为来源，按最终正式产物处理；无产物时记录失败项，动作失败但留有产物时仍取回 |
| 成员关系、类型或能力无法可靠判断 | 保留实际错误或未知，不能按“不产生正式产物”跳过，也不能确认筛选已完成 |

本计划内组在首次受理时确定来源，指定计划实例的组在首次执行时确定来源，具体见下一节。来源集合可靠保存后，执行和重启恢复沿用固定范围。以下组取回规则中的“成员”“全部来源”和发布等待均指筛选后的来源动作，不包含已排除的非产物动作。

例如组内 A 在 10:00 录像，B 在 18:00 执行 `report_status`，12:00 发起组取回：只处理 A 的正式产物，不等待 B。若 A 已失败且没有正式产物，则记录 A 的无产物失败；B 不构成失败项。其他普通动作的调度和执行不受筛选影响。

### 组来源的确定

仅含 `params.source.group` 的本计划内引用，在首次受理时根据完整输入解析并保存结果。包含 `plan_instance_id` 与 `group` 的引用，在受理时只保存格式合法的来源描述；首次执行取得资格后，从数据库查询指定计划及组，按成员类型筛选来源。客户端可以提前检查自己掌握的计划内容，camctl 仍在各自规定的时点作出判定。

以下来源判定适用于计划公共结构及该动作自身字段、参数格式均合法的情况。跨计划引用执行前先处理取消及既有终态；已保存有效来源集合时直接恢复原集合及进度，不重新解析。

| 解析目标组及来源的结果 | 本计划内引用：首次受理 | 指定计划实例的组：首次执行 |
| --- | --- | --- |
| 组存在，至少有一个能产生产物的来源动作 | 保存来源集合，该取回初始为 `pending` | 保存来源集合，按各来源动作及产物状态继续 |
| 目标计划不存在 | 不适用，来源计划就是本次输入的计划 | 仅该取回 `failed`，不等待目标将来出现 |
| 目标组不存在，或没有组成员 | 将该取回登记为 `failed`，保存具体缺失原因 | 仅该取回 `failed`，不等待目标将来出现 |
| 组存在，但成员类型均不产生产物 | 将该取回登记为 `failed`，保存没有产物来源的原因 | 仅该取回 `failed`，保存没有产物来源的原因 |
| 记录无法可靠解释或保存，或数据库查询失败、结果未知 | 按会话错误及恢复规则处理 | 按会话错误及恢复规则处理，不解释为目标缺失 |

本计划内的来源集合或诊断与计划、全部动作在受理事务中整体保存；指定计划实例的组在运行时通过同一事务查询并保存来源集合或失败结果。来源尚未解析、有效集合已固定、解析已失败分别记录，不能都表示为空集合。集合保存前不开始产物选择、读取或交付。提交结果未知时先对账，不能重复固定来源或猜测结果。

确定来源只判断组成员及其类型，不保证产物已经生成或仍可读取。运行时继续检查每个来源的动作状态、正式产物及可用性；录像未结束时等待，已结束且无产物时记录失败，失败录像留有产物时仍按实际产物处理。

已经可靠保存的来源集合、失败结果在重启和同一请求重送后保持不变。后续文件清理不改变已选来源身份，但影响实际取回结果；已完成的逐项选择、准备进度及发布事实仍按各自规则保留。其他动作继续按自身条件执行。

### 组内录像分别准备与统一发布

通过 `(plan_instance_id, group)` 或已解析的本计划内组引用取回一组录像的全部正式产物时，每个录像动作进入终态后，就确定并持久化该成员的全部正式产物集合，按取回资格开始准备独立交付文件。其他成员尚未结束不阻止这一步；发布须等待全部成员结束并完成产物判定，以及全部所选产物取得最终准备结果。

本节适用于按“按组取回的成员筛选”得到至少一个 `camera_record` 来源的第一版组取回，原组可以同时包含非产物动作。按原计划中保存的组成员及类型固定本次取回来源，不跨计划合并同名 group。取回已到计划时间且仍有执行资格时，对每个来源成员分别应用下表；本次取回的取消和既有终态优先处理：

| 成员及本次取回的情况 | 本成员的处理 |
| --- | --- |
| 录像未进入终态，包括未来尚未开始的录像 | 保存等待对象，不选择该成员的产物，不阻止其他已结束成员准备文件 |
| 录像已进入终态，尚未完成产物判定，查询可靠完成 | 固定并保存该成员的完整选择或无产物失败项；有产物时按资格开始准备 |
| 该成员的选择或无产物失败项已经保存 | 继续原条目，不重新选择、扩大集合或重复创建 delivery |
| 本次取回已取消或进入其他终态 | 不继续等待或开始新的准备，按原终态及收场规则处理 |
| 组成员、录像状态、既有选择或产物查询失败、结果未知 | 保留实际问题，按对应错误处理，不能当作成员已结束、已完成选择或没有产物 |

成员成功、失败、过期及取消均属于录像结束。录像自身状态不直接复制为取回状态；未产生正式产物的成员按“已结束动作没有正式产物”记录失败项。已经登记但已清理或不可用的产物按实际状态处理，不能当作从未产生。全部成员完成判定后，本次完整选择为各成员已保存集合的合并结果。

等待遵守取回的无时效规则，不阻塞组内录像、其他动作及取消请求，也不改变 group 作为集合标签的性质。组成员、逐成员选择、无产物失败项及逐产物准备进度遵守数据库历史与投影规则。断电后恢复同一请求：继续等待未结束的成员，恢复未完成的准备，保留已经可靠准备完成的交付副本；不能只因组未结束就重新取回已准备的文件。等待属于尚未完成的计划工作，参与会话退出检查。

例如组内 A 上午结束、B 下午结束，中午开始组取回时即准备 A 的交付副本，同时等待 B。A 的副本可靠准备完成后，按“清理与取回并发”可释放对 A 保留文件的读取依赖。B 结束后准备 B 的文件；全部成员与产物处理满足发布屏障后，再逐文件发布。

### 已结束动作没有正式产物

通过 `action_instance_id` 取回单个动作的全部正式产物时，若该动作已经进入终态，且确认没有产生任何正式产物，则本次 `obtain_action_outputs` 以 `failed` 结束。报告关联被引用的动作，说明该动作没有可取回的产物；不创建 delivery。

本规则用于已受理取回动作的执行结果，取回自身的取消和既有终态仍遵守公共动作状态机。判定时必须区分以下情况：

| 被引用动作及产物的情况 | 处理 |
| --- | --- |
| 动作存在且已结束，确认未产生正式产物 | 取回为 `failed`，报告没有可取回的产物 |
| 动作存在且已结束，已登记正式产物 | 按产物选择及逐项处理规则执行；已清理或不可用的产物不能当作从未产生 |
| 动作尚未结束 | 不适用本条空产物判定；单个录像全部产物的取回按“等待录像动作结束”处理，其他范围见待细化契约 |
| 动作不存在，或动作状态、产物查询失败或结果未知 | 保留实际的缺失、错误或未知情况，不能解释为已结束且没有产物 |

例如录像启动失败，动作已经结束且没有正式视频，随后取回该动作全部产物时，取回结果为 `failed`。报告说明未取得文件的原因，不为此重新启动录像。

组取回筛选所得的录像来源非空时，每个来源成员结束后即应用上述产物判定：没有产生任何正式产物的录像记为本次取回的一个失败项，关联其 `action_instance_id` 并报告无产物原因，不为该项创建 `output_id` 或 delivery。其他来源成员已经登记的产物继续按逐项规则取回。录像自身失败但留有正式产物时，按这些产物的实际取回结果判断，不额外计为无产物失败。

无产物失败项与本次选择的产物集合按历史与投影规则保存，恢复时保留已确定的结果。部分成员无产物时，完成其他文件的必要发布后，取回整体为 `failed`；所有成员均确认无产物时，整体为 `failed` 且不创建 delivery。组不存在、没有成员或查询失败均不属于“组内录像全部无产物”。取消及既有终态仍优先处理。

### 部分成功

`obtain_action_outputs` 的整体状态表示本次取回是否全部完成；报告逐产物列出处理结果及失败原因，录像组的无产物失败项则按来源动作列出。整体为 `failed` 不表示所有文件都未交付。

本表适用于尚未进入终态、且全部来源已完成产物判定的取回；本次已选产物和已确认的录像组无产物失败项合计至少有一项。组内仍有成员等待结束或尚未完成产物判定时，继续等待与处理，不发布文件，也不根据当前已有条目汇总整体终态：

| 产物取回及无产物项的处理情况 | 动作整体状态与后续处理 |
| --- | --- |
| 仍有产物等待处理、正在处理或可以继续重试 | 继续处理；某项已失败也不能提前结束整个动作；遵守发布屏障 |
| 全部产物准备处理已结束，但仍有成功准备的文件等待发布或发布结果尚未确定 | 继续完成发布或恢复对账，不能仅凭准备成功宣告动作成功，也不能因其他项失败而扣留这些文件 |
| 所有已选产物均已成功发布，且没有无产物失败项 | `succeeded` |
| 至少一个产物取回最终失败或存在无产物失败项，其余各项均已成功发布或最终失败 | `failed`；保留各项实际结果和失败原因，包含录像组所有成员均无产物的情况 |

这里的成功发布以文件交接协议定义的本地交付完成为准，不等待主程序发送或客户端收到。已经发布的文件即使被主程序移走，也不因此退回未完成状态。发布失败或结果未知必须如实记录，不能当作成功发布。

例如请求 A、B、C，A、B 准备成功而 C 重试耗尽：先发布 A、B，再将动作整体置为 `failed`；报告分别说明 A、B 已发布及 C 的失败原因。不因为 C 失败扣留 A、B，也不因 A、B 成功将整个动作标为 `succeeded`。

取消及既有终态遵守公共动作状态机与本专题的取消规则，不通过本表覆盖已有终态。单个已结束动作或录像组成员未产生正式产物时，按“已结束动作没有正式产物”处理。组取回在适用时点确定非空来源集合后才进入产物处理；执行时没有文件不能解释为没有来源，也不能以零个成功项汇总为成功。其他空集合场景见待细化契约。

### 发布屏障

本次取回仍有效且未终态时，按以下条件判断能否开始发布。单个录像在结束后完成产物判定；录像组须对全部固定成员完成判定，才能确认没有尚待补入的条目。

| 来源与条目状态 | 发布处理 |
| --- | --- |
| 仍有来源等待结束或尚未完成产物判定 | 继续等待及准备，不发布已有成功文件 |
| 全部来源判定完成，仍有产物等待准备、正在处理或可继续重试 | 继续处理，不发布已有成功文件 |
| 全部来源判定完成，全部产物准备结果已确定 | 发布成功准备的文件；无产物或准备失败项保留失败结果，没有成功文件时不创建交付文件 |
| 以上条件无法可靠确认 | 按对应错误处理，不推测已满足发布条件 |

之后才进入发布阶段。

发布阶段允许逐文件发布。

因此：

```text
A → ready → 被主程序领取
B → 稍后才进入 ready
```

是合法的。

A、B 可以落入不同数据传输窗口。

不要求整组原子发布。

### 每个新请求产生独立 delivery

新的 `request_id` 发起新的取回时：

> 即使选择与历史完全相同的 `output_id`，也创建独立 delivery。

各取回请求独立持有自己的待传文件。

同一 `request_id` 的重试则复用原请求，不创建新的 delivery。

### 取回半成品的保留与清理

本节适用于某次取回在 `staging` 工作位置留下、尚未可靠准备完成的独立副本。以该取回项的持久化结果、文件归属及实际读取、写入和重试状态判断，不根据文件年龄、大小或整次取回的汇总状态推测是否可以删除。

| 文件与所属取回项的情况 | 处理 |
| --- | --- |
| 文件归属、取回项结果或读写是否停止无法可靠确认 | 保留文件，核实或按对应错误处理，不猜测为可删除半成品 |
| 取回项仍未结束，包括仍可重试或仅因断电中断 | 保留半成品及已保存进度，按原请求续传 |
| 取回项已最终失败或取消，但读取、写入或重试尚未确认停止 | 先停止并确认，不删除仍可能被使用的半成品 |
| 取回项已最终失败或取消，读取、写入和重试均已确认停止 | camctl 自动删除该项自己的半成品，无须客户端另行提交清理请求 |
| 成功副本已可靠准备完成，本次取回仍有效且尚待发布 | 保留副本并继续原发布流程；其他项失败不授权删除该副本 |

半成品删除不删除相机源文件、`staging/derived/` 中的正式产物、其他取回的副本或已进入交接目录的文件。取回取消后的完整副本处置和已发布文件撤回遵守“取消取回”与文件交接规则。

数据库永久保留取回项的结果、失败原因、拷贝进度历史和清理处理事实。先可靠保存最终失败或取消及半成品归属，再执行物理清理；删除文件不抹去诊断或释放交付名称，也不把失败改为成功。新的取回请求继续创建独立 delivery，不接管这份已经失败的半成品。

重启后区分未结束请求的续传文件与已结束项的待清理半成品。清理中断时，依据原归属和最终结果继续核实：确认文件仍存在且符合清理条件时继续清理；确认不存在时保存清理已完成的恢复事实；查询失败或结果未知不能冒充清理成功。

#### 半成品清理失败与后续处理

本节仅处理已经可靠确定归属、满足清理条件的取回半成品。原动作及取回项的终态保持不变，清理结果单独记录。

| 清理结果与会话履职情况 | 处理 |
| --- | --- |
| 已确认删除完成或恢复时确认文件不存在，结果可靠保存 | 记录清理完成；其他职责完成后允许会话正常结束 |
| 文件查询或删除失败、结果未知，但数据库、其他动作及报告职责仍可正常完成 | 本次有限尝试后保存尚未清理及具体失败或未知原因，继续其他工作；报告职责完成后允许会话正常结束 |
| 数据库不能可靠读取或保存处理状态、事务结果未知，或本地报告等必要职责无法完成 | 按相应会话错误与恢复规则处理，不能以允许延后清理代替必要职责 |

尚未清理的记录保留原取回及文件关联，后续实际启动的正常 `run` 再核实并有限尝试清理。它不恢复原取回、不重新拷贝、不创建新的业务动作；清理完成也不改变已经结束的计划状态。时钟异常的受限会话仍遵守已有工作范围。

每个正常会话对这些残留文件的清理工作均有有限尝试范围。本次尝试结束后，残留本身不阻止正常收尾，也不单独要求立即再启动 `run`；调度重扫、新输入、报告处理及最终退出检查不能重新开启本次已经结束的清理尝试。新产生的清理结果仍须履行报告职责，不能将尚未发布的诊断误判为无需处理。

清理失败、后续实际尝试所得的新结果及清理完成事实按历史与投影规则保存，并通过状态报告表达；单纯再次看到同一条待清理记录不构成新的清理尝试或新的失败事实。具体尝试次数与超时参数见待细化事项。

### 取消取回

取回尚未完成时取消：

- 停止尚未开始的处理；
- 已经准备但尚未发布的文件不再发布；
- 不删除正式源产物。

取消来源组不会自动取消本次取回；取消寻址见[取消目标寻址](protocol-session.md#取消目标寻址)。本次取回仍有效时，来源录像因组取消而结束，继续按其最终正式产物处理；没有产物的成员按既定无产物失败规则记录。

文件已经发布到 `ready` 后：

> `obtain_action_outputs` 可以进入终态。

但之后仍允许针对这次取回撤回尚位于 `ready` 的 delivery 文件。

已经：

```text
ready → processing
```

的文件进入不可撤回阶段。

即使主程序尚未真正开始发送字节，也不再由 CLI 撤回。

如果一个已终态的 obtain 动作被后续 cancel：

- 历史动作终态不改变；
- 只处理其仍可撤回的 delivery。

## 产物清理

正式产物的清理动作：

```text
delete_action_outputs
```

清理必须显式指定 `output_id`。

不允许：

```text
省略 output_ids = 删除全部
```

也不允许空列表表示全部。

### 清理含义

清理一个正式产物意味着：

- 删除该 `output_id` 对应的保留文件：设备产物删除所属设备上的文件，主机派生产物删除 `staging/derived/` 中的对应成品；
- 使该 `output_id` 后续不再可取回；
- 保留该产物曾经存在以及被清理的历史记录。

已经发布到 `ready/processing` 的合法 delivery 不因此被撤回。

### 再次清理已完成的产物

新的清理请求可以再次指定已有清理完成记录的 `output_id`。对已取得执行资格的清理项，数据库可靠确认该产物此前已经完整清理时，该项按成功处理，报告说明“此前已清理”，不再执行文件删除。产物继续保持不可取回。

| 数据库中的产物与清理记录 | 本次清理项的处理 |
| --- | --- |
| 产物存在，已确认清理完成 | 本项成功，说明此前已清理，不重复删除 |
| 产物存在，尚未开始清理、仍在清理或已明确部分失败 | 按清理资格、并发及失败恢复规则处理，不能直接按此前已清理成功结束 |
| 产物存在，删除结果尚未确定 | 按恢复规则核实，不能把删除意图或已发出删除操作当作完成记录 |
| 查询成功，但没有该 `output_id` 的产物记录 | 本项失败，报告“产物不存在”；其他目标按“批量清理结果”继续处理 |
| 数据库查询失败或无法可靠解释记录 | 按持久化错误处理，不能推断目标不存在或清理已完成 |

“清理完成”必须覆盖该产物按“清理含义”确定的完整文件集合。仅集合中的部分文件已删除、取回权限已关闭或文件路径找不到，都不能代替完整清理记录。已有删除意图但缺少完成记录时，按“删除中断后的恢复”核实并保存恢复结果，再据此判定完成。

新请求的成功结果按历史与投影规则保存，并关联本次请求和 `output_id`；它表示确认此前已清理，不新增虚构的物理删除事实。同一 `request_id` 重复提交仍复用首次受理的请求及原处理结果，不按新请求重新处理。清理自身的取消和既有终态仍遵守公共动作状态机。

### 批量清理结果

`delete_action_outputs` 对明确指定的各个 `output_id` 分别处理、保存并报告结果。格式合法的 ID 在执行时查不到产物，是该清理项的业务失败，不阻止其他目标清理。输入格式非法、缺少目标列表或列表为空时，首次受理将该清理动作登记为 `failed`，不登记删除意图或执行列表中的任何删除；其他动作一同受理。受理失败状态及历史保留遵守公共动作参数校验规则。

例如请求清理 A、B，A 存在而 B 未登记：A 按清理规则执行，B 报告“产物不存在”；A 完成后，动作整体为 `failed`，报告分别保留 A 已清理、B 不存在的结果。已完成的删除不会因另一项失败而撤销。

对于目标列表非空且清理动作尚未进入终态的情况，整体结果按下表确定：

| 各项处理状态 | 清理动作的处理 |
| --- | --- |
| 仍有目标等待旧取回、正在删除、仍可重试或需要核实删除结果 | 继续按各项规则处理；其他项已失败也不能提前将动作置为终态 |
| 全部目标均已成功，包括确认此前已清理的项 | `succeeded` |
| 全部目标均已有最终结果，至少一项失败 | `failed`；报告逐项列出实际结果与失败原因 |

查询和结果保存须可靠完成。数据库读取失败、写入失败或提交结果未知按会话错误及恢复规则处理，不能伪装成某个 ID 不存在，再假定其余清理可以安全继续。删除意图、部分删除和结果未知分别保留；动作整体失败不恢复已受删除限制的产物。

逐项结果及整体终态按历史与投影规则持久化。中断后恢复原请求中尚未结束的条目，已经保存的最终结果保持不变，不因另一项失败重新删除成功项。取消和既有终态遵守公共动作状态机及本专题的清理取消规则，不由结果汇总覆盖。

### 不级联删除

原片与修复成品具有派生关系，但删除：

```text
原片
```

不会自动删除：

```text
修复成品
```

反之亦然。

只删除客户端明确指定的正式产物。

### 清理与取回并发

已有取回优先。

多个尚未开始的取回与清理均已到计划时间时，先按“延后执行时的取回与清理顺序”确定先后，再进入清理流程。

清理开始时：

1. 持久化删除意图；
2. 禁止新的取回请求获取该产物；
3. 逐个 `output_id` 等待所有已获得资格的旧取回不再需要读取其保留文件；
4. 再进行物理删除。

清理开始以后新来的 obtain 请求不能插队。

#### 新取回遇到删除限制

取回到达自身计划时间、确定产物后，在申请该产物的读取资格时按下表判断。取消及既有终态优先；受理请求本身不提前授予资格，也不提前作出本表中的运行时失败判定。

| 本次取回的逐项事实 | 处理 |
| --- | --- |
| 该项已经最终失败或取消 | 保留原结果，不重新申请资格 |
| 已持有该产物的旧取回资格 | 按原资格继续或恢复；后来登记的删除限制不撤销该资格 |
| 尚无资格，产物存在有效删除限制 | 立即将该项记为最终失败，原因表达“产物已进入清理流程”；不拷贝，不等待删除完成或取消 |
| 尚无资格，可靠确认没有有效删除限制 | 继续按执行顺序及产物实际可用性判断，不能仅据此推断文件可读或已取得资格 |
| 资格或删除限制无法可靠确认 | 按持久化错误及恢复规则处理，不能推测可取回，也不能冒充已确认的清理限制失败 |

删除限制的判断与对应资格授予或失败结果在同一数据库事务中保存，历史和投影同步更新。与清理取消同时发生时，以事务确定的先后为准：限制解除在先则按解除后的状态判断；失败已保存则不因随后解除限制而改写结果。提交失败或结果未知须先按事务恢复规则核实。

该失败只针对本次取回中的对应产物，其他产物继续处理，整体结果仍按“部分成功”和发布屏障汇总。只有一个目标时，本次取回随该项失败而整体失败；包含其他未完成来源或产物时，不提前结束整个动作。

清理后来被取消、源文件仍存在或主机重启，都不恢复已经失败的取回项。同一 `request_id` 重送沿用原结果；客户端须用新请求表达再次取回的意图，新请求仍按执行时的资格与产物状态处理。

#### 逐产物解除读取依赖

原片与修复成品分别判断，每个取回也分别持有自己的交付副本。对同一 `output_id`，依次检查下表；清理自身仍须有执行资格，并满足删除意图、目标记录及重试规则：

| 所有已有取回对该产物的依赖情况 | 物理删除处理 |
| --- | --- |
| 依赖记录或准备结果无法可靠确认 | 先核实或按对应错误处理，不授权删除 |
| 至少一个取回仍需读取，包括尚未拷贝、拷贝中、未完成校验或仍可重试 | 等待；其他取回已经准备完成不能代替该请求完成 |
| 每个取回均已确认不再需要读取，或可靠确认没有已有取回 | 可以删除该产物的保留文件，不等待其他产物、整组发布或主程序传输 |

一个取回对该产物不再需要读取，有以下依据之一：独立交付副本已按下节可靠准备完成；交付已按协议确认发布；该项最终失败或被取消，且其读取和重试已确认停止。仅整次取回收到取消标记，不等于正在执行的读取已停止。

副本准备完成后，即使来源已被显式清理，原取回仍使用已有交付副本继续等待和发布，不能以源产物当前不可用否定这份已准备的交付。取消或清理某个取回的工作文件，不影响其他取回的副本；源产物清理也不删除这些独立副本。

#### 准备完成与断电恢复

交付副本须完成全部写入、符合所属文件读取与校验契约，并完成文件及相关目录项的落盘。随后在同一数据库事务中保存该副本的身份、位置、大小、摘要和准备完成事实，并解除这次取回对该产物的读取依赖；历史与投影同时更新。该规则同样适用于从相机取回原片和从 `staging/derived/` 拷贝成品。文件名存在、长度相同或拷贝命令返回成功均不能单独作为准备完成依据。

| 准备步骤及持久化结果 | 恢复与删除处理 |
| --- | --- |
| 文件写入、校验或落盘未完成、失败或未知 | 保留读取依赖，按原处理进度恢复或记录失败，不因准备意图允许删除 |
| 文件已可靠准备，准备完成事务尚未提交或确认回滚 | 保留读取依赖；恢复核实原副本并保存完成事实，不直接放行删除 |
| 准备完成事务提交成功 | 本取回不再阻止删除；重启后使用同一副本、原选择和交付身份继续处理 |
| 事务提交结果未知或记录不可读 | 先核实实际提交结果，不猜测准备完成、重新拷贝或授权删除 |

清理在物理删除前须依据可靠保存的逐请求依赖确认可执行；删除意图阻止新取回取得资格，准备完成与依赖解除整体提交，不能出现依赖已解除但准备事实未保存的状态。已解除依赖后，不再要求源文件存在来恢复本次交付，也不能把已准备副本当作可重新生成的临时文件删除。若副本缺失、损坏或状态未知，保留实际故障并按错误处理，不能撤销历史删除或假定源文件仍可读取。发布期间的文件位置与记录对账继续遵守文件交接协议。

### 删除中断后的恢复

物理删除前，数据库必须已可靠保存清理请求、删除意图、`output_id` 及该产物应删除的完整文件集合，包括文件所属设备或主机存储位置和识别依据。恢复以这些记录为依据，不根据临时列举出的剩余文件缩小原清理范围；合法 delivery 不属于源产物清理集合。

后续实际启动的 `run` 发现删除意图仍未取得最终结果时，核实各目标文件。必须区分“确认不存在”“确认仍存在”和“结果未知”；相机连接失败、目标设备或存储无法确认、查询失败及响应无法解释均属于未知，不能当作文件不存在。

先核实原请求的恢复资格和记录，再逐文件处理：

| 原请求与记录情况 | 恢复处理 |
| --- | --- |
| 已有可靠保存的清理完成记录 | 使用已保存结果，不重复删除 |
| 请求仍未结束，删除意图及完整目标记录可靠可读 | 按下表核实；实际删除仍须满足旧取回优先和剩余重试预算 |
| 请求或条目已失败或取消，且没有清理完成记录 | 不自动恢复物理删除，不改写原终态；保留已发生的删除及未知事实，继续清理须有新的有效请求 |
| 请求资格、删除意图或完整目标记录缺失、不可读或无法可靠判断 | 保留诊断并停止依赖这些记录的恢复，不能补造删除授权或以空集合判成功 |

对于仍有恢复资格的请求，各目标文件的处理如下：

| 文件核实结果 | 本文件的处理 |
| --- | --- |
| 确认不存在 | 保存恢复时确认不存在的事实，不重复删除该文件 |
| 确认仍存在且属于原清理目标 | 在具备删除资格及剩余重试预算时继续删除，并按实际结果保存事实 |
| 结果未知 | 保存未知原因，按有限重试规则继续核实；不能记录为删除成功 |

全部目标均已确认不存在时，补记该产物清理完成和本次清理项成功；只要仍有文件存在或结果未知，就不能宣告完整清理成功。各文件可以分别取得结果：某文件未知不抹去其他文件已确认的状态，继续删除已确认存在的文件仍须满足上述资格。重试耗尽按清理失败处理，保留未删除及未知的具体范围，不因重启重置预算。

恢复记录表达“恢复时确认目标已不存在”，不推测断电前的准确删除时间。恢复观察、清理完成和相应投影遵守数据库事务规则；保存失败或提交结果未知时按持久化错误处理，先确认实际提交情况再继续。已确认删除或无法排除删除发生的产物，继续受清理限制，不因查询失败恢复取回权限。

### 清理部分失败

已经发出可能删除文件的操作，但最终仍有应删除文件未删除或结果未知时：

- 不允许新的取回；
- 不重新开放尚存的产物文件；
- 如实报告物理清理未完成；
- 以后只能通过新的清理请求继续清理。

### 清理取消

如果清理尚处于等待旧取回的阶段：

```text
尚未发出任何可能删除文件的操作
```

则允许取消。

取消后，如果没有其他有效删除限制：

> 恢复新的取回权限。

已经因删除限制失败的取回项保持失败，按“新取回遇到删除限制”处理。

一旦已经发出删除操作，或者无法排除删除已经发生：

> 不再因为取消而恢复取回权限。

## Delivery 与文件名

每次独立取回产生：

```text
delivery_id
```

delivery 与 output 是不同身份：

```text
output_id
    = 正式业务产物

delivery_id
    = 一次具体交付
```

### 实际文件名

普通产物的交付文件名使用完整的 `delivery_id`，保留文件类型扩展名：

```text
<delivery_id>.<ext>
```

例如 `d-000042.mp4`、`d-000043.mp4`。示例中的 ID 仅说明命名结构，不规定 ID 的生成算法。不能截短 ID 来构造文件名；同一产物的不同取回请求各自使用自己的 delivery 身份及路径。

ID 的文件名表示须长度有界、可安全用作单个文件名；扩展名须采用与文件类型对应的安全表示，不能直接拼入设备路径或任意长度的输入。具体 ID 编码及扩展名边界见待细化事项。

### 历史全局唯一

唯一性范围为单台主机的持久化历史。`delivery_id` 与实际交付 `file_name` 在该范围的整个 delivery 历史中保持唯一，数据库对其建立唯一约束。名字一经分配就保持不变，从 `staging` 发布到 `ready`、由主程序移至 `processing` 时均使用同一名字。文件被传输删除、撤回或源产物被清理，都不释放名称；同一请求恢复沿用原记录。

### 完整可读名称

状态报告通过 `display_name` 保存完整的人类可读名称：

```text
<original-stem>-<plan-name>-<action-name>.<ext>
```

例如 `VID_0001-夜间采集-主录像.mp4`。修复成品可通过原始名称部分的 `repaired` 标记帮助人识别。这里使用产物来源计划及动作的名称；来自设备的原始名称只取文件名部分，不包含设备目录。

`display_name` 保留中文等可读内容，可在不同 delivery 之间重复。它作为报告中的字符串供显示，不作为主机交付路径，不受交付文件名的长度限制，也不承担机器身份或唯一性。

### 报告负责机器映射

状态报告包含：

```text
delivery_id
output_id
file_name
display_name
source_action_instance_id
size
sha256
delivery 状态
```

客户端根据报告中的**完整 `file_name` 精确匹配**收到的文件，取得 `delivery_id`、`output_id` 及来源等信息；不要求客户端解析文件名推导业务身份，也不能用 `display_name` 进行唯一匹配。

## 普通产物传输失败与重新取回

主程序完成本地发送不证明客户端收到，交接事实由[文件交接](file-handoff.md)定义。

对于照片、视频等普通产物：

> 不自动重传。

客户端如果未收到或完整性校验失败：

1. 根据已经掌握的 `output_id`；
2. 使用新的 `request_id`；
3. 再提交 `obtain_action_outputs`。

只要正式源产物仍然可用，即可重新产生新的独立 delivery。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

产物投影提供本专题定义的稳定身份、来源、可用性、派生关系和清理状态。交付投影提供 `delivery_id`、`output_id`、来源 obtain 动作、历史唯一的实际 `file_name`、完整可读的 `display_name` 及交付状态。登记、发布、撤回和清理等变化均追加历史并同步更新投影，遵守[持久化与配置基础](../2026-09-08-camctl-cli-design.md#持久化与配置基础)。

文件位置与业务记录之间的对账引用[文件交接](file-handoff.md)。历史回放不能执行取回、发布、撤回或源文件删除；历史中的删除意图与已确认删除结果保持区分。数据库保留产物历史不意味着已清理的产物文件仍然可用。

相机视频拷贝还需保存来源与未完成文件的关联，以及已经可靠保存的拷贝进度，供后续会话续传。历史回放恢复这些事实，实际读取设备文件由取得执行资格的处理流程完成。

## 验收要求

### 单元测试

按“取回半成品的保留与清理”覆盖取回未结束、最终失败、取消，与读写仍在进行、已停止及未知的组合。未结束项保留续传；失败或取消项仅在确认停止后删除自己的半成品。组合已准备成功的 A 和失败半成品 B，验证只清理 B、A 仍须发布；原片、派生成品及其他请求文件均保留。

按“半成品清理失败与后续处理”覆盖清理成功、文件查询或删除失败及结果未知，分别组合状态保存与报告职责完成或失败。局部清理问题可延后，数据库与必要报告错误仍为会话错误；本次有限尝试结束后，调度重扫和收尾检查不重启尝试，原动作及计划不恢复执行。

按“新取回遇到删除限制”覆盖旧资格、新请求、有效限制、限制已解除及状态未知。新请求在限制有效时对应项立即失败且不开始拷贝；旧资格继续受保护。组合单项和多项请求验证失败范围、其他项继续处理及整体结果。限制后来解除、重启和同一请求重送均不恢复已失败项。

隔离产物目录、设备文件和交付存储协作者，验证产物选择、部分成功、发布屏障、文件名规则、清理限制、取消及重取身份。

按本动作的“参数”和“校验与失败处理”覆盖四种来源形式，以及 `params`、`source` 缺失、非对象、空对象、字段混用和非法组合；另行覆盖 `output_ids` 空数组和动作自身的所属组字段错误。公共结构合法时只将错误取回登记为 `failed`，保留输入与诊断，不执行或创建 delivery；其他动作一同受理。已有请求重试仍忽略本次正文。

按“本计划内的产物引用”覆盖局部名称存在、缺失、来源类型不适用及混用引用，仅该取回在受理时失败；重复动作名属于公共结构错误，按整份拒绝处理。局部引用只在本计划解析，支持数组中的前向引用；其他计划的同名动作或组不能成为目标。已有请求重试不重新解析正文。

按“按动作实例 ID 查找来源”覆盖目标存在且类型适用、类型不适用、不存在、查询错误、结果未知，以及曾确认来源存在但其记录缺失。受理阶段不查询目标，取得执行资格后确认目标缺失或类型不适用时仅取回失败。取消及已有终态优先；已经保存的结果不会因重启、同一请求重送或后续来源出现而改变。

按“取回与清理的执行时间”覆盖计划时间之前、恰好到达、延后及时间未知，验证两类动作均不提前执行、不因延后进入 `expired`。区分业务等待、单次通信超时与重试耗尽；延后不能重置预算，也不能覆盖已有终态。

按“延后执行时的取回与清理顺序”覆盖取回时间较早、清理时间较早及两者相同，并分别改变受理顺序和加载顺序。验证较晚或同一计划时间的清理不能抢先限制取回，较早清理产生的限制也不会被较晚取回绕过；已有资格、删除限制和终态按原规则保留。

按“再次清理已完成的产物”覆盖完整清理记录、未完成或部分失败、删除结果未知、目标不存在及数据库错误。已确认清理完成时本项成功且不调用删除协作者；报告保留本次请求、目标及此前已清理的含义。仅文件缺失或仅一个副本删除不能进入该成功分支。

按“批量清理结果”覆盖全部成功、部分失败、全部失败及仍有未完成项，包含此前已清理、目标不存在、删除失败和结果未知。目标不存在不能阻止其他合法目标执行；数据库异常不能当作逐项目标不存在处理；取消及既有终态不被汇总覆盖。

按“删除中断后的恢复”覆盖请求资格与目标记录分类，以及文件全不存在、部分存在、全存在、包含未知的组合。只有全部目标确认不存在才能补记完成；设备不可达或查询失败不能当作不存在，终态请求不能自动继续删除，未知或缺失的完整目标记录不能当作空集合。验证重试耗尽、恢复结果保存失败及提交未知时保留实际状态。

按“长期保留”覆盖有无有效清理请求，以及取回完成、传输完成、保存时间增长和空间不足的组合，验证所有正式产物采用相同保留规则。无清理请求不能删除正式产物；有请求仍需满足旧取回优先及取消规则。

按“等待录像动作结束”覆盖取回资格、录像是否结束、产物有无及查询异常的分区。验证等待期间不提前固定部分产物或判无产物失败；录像进入不同终态后按正式产物处理；已取消的取回不能因录像结束恢复执行。

按“组内录像分别准备与统一发布”覆盖全部未结束、部分结束、全部结束及取回取消，包含未来录像尚未开始、录像失败或取消、查询错误和跨计划同名组。验证已结束成员分别固定完整选择并开始准备，未结束成员仍等待；任何成员尚未完成判定时，不能发布已有成功文件或汇总整体终态。恢复保留逐成员选择，不遗漏未来成员或重复创建交付。

按“按组取回的成员筛选”覆盖类型产物能力与动作状态的组合。非产物动作尚未开始、运行中或已结束均不影响取回等待、发布及失败汇总；录像尚无产物仍须保留为来源，终态无产物仍记失败，不能通过筛选隐藏失败录像。成员或类型查询未知须明确处理，不当作可忽略成员。组取消及报告组织仍使用原组成员。

按“组来源的确定”覆盖本计划内及指定计划实例的组引用，与来源未解析、存在有效成员、目标缺失、成员均不产生产物和查询错误的组合。本计划内引用在受理时解析，跨计划引用在首次执行时解析；可靠的缺失或无产物来源只使该取回失败。有效集合保存后恢复不重新选择；产物尚未生成或已清理不改变来源类型的判定，仍按运行时可用性处理。

按“逐产物解除读取依赖”与“准备完成与断电恢复”覆盖单个和多个已有取回的依赖组合，以及写入、校验、落盘、事务提交的成功、失败和未知。只有所有已有取回均不再需要读取才允许删除；某项最终失败或取消还须确认读取与重试停止。验证准备完成与依赖解除在同一事务中保存，删除源文件不影响已准备交付的发布资格。

按“已结束动作没有正式产物”覆盖动作终态与产物情况的分区，验证无产物时取回失败且不创建 delivery。动作未结束、引用缺失、查询失败或未知，以及曾产生但已清理的产物均不能误入该分支。保留 `output_ids = []` 的参数错误语义。

录像组另行覆盖每个成员均有产物、部分成员无产物及全部成员无产物，并组合产物取回成功、失败、重试或发布未完成。无产物项关联来源动作，不创建虚构产物或 delivery；存在无产物项时整体失败，但仍须完成其他文件的必要发布。录像失败但留有产物不自动使取回失败，数据库错误不能当作成员无产物。

按“部分成功”表覆盖全部成功、部分失败、全部失败，以及其他项仍在重试、等待发布或发布结果未知的情况。验证整体状态与逐项结果一致，某项失败不能提前结束动作或扣留成功项；取消及既有终态不能被结果汇总覆盖。

按“重启后选择续传位置”覆盖各分区，验证续传偏移、尾部截断、已完成数据范围及错误分类。覆盖实际读取长度小于请求长度、提前结束，以及写入、同步、截断、进度提交失败或结果不确定；未可靠保存的字节不能推进进度。进度提交前的文件和目录同步顺序属于断电恢复契约，须明确验证。

按“同一相机的拷贝并发限制”组合取回、异常原片检查和内部修复入口，验证同一相机最多有一份活动拷贝，分段保存进度不允许另一份文件插入。等待不消耗读取次数；取消或最终失败后，实际读取结束前不能启动另一份拷贝。分别验证不同源相机独立协调、主机派生文件拷贝不占相机机会，以及控制操作仍遵守驱动兼容性。

按“等待重试时保留拷贝机会”覆盖仍可重试、取消、预算耗尽、读取尚未停止或状态未知，以及源内容读取完成。验证等待期间其他文件不能开始、重试继续原进度和预算、符合解除条件后才选择其他文件。源内容读完后发生校验失败的重拷须重新参与选择，不追溯抢占另一份活动拷贝。

按“多个候选文件的选择顺序”覆盖所属动作时间不同、同时间跨计划、同计划不同动作以及同动作多文件。取回使用取回动作时间，检查和修复使用所属录像时间，重拷沿用原依据；未具备读取条件的较早请求不阻挡合格候选。另行验证已有活动拷贝及重试保留优先于候选排序，排序数据缺失或未知不能使用加载顺序替代。

按“读取正确性与文件校验”覆盖摘要支持、不支持和能力未知，以及摘要相同、不同、获取失败和结果未知的分区。读取失败或结果未知、主机摘要计算失败、源端校验未通过时不能交付该副本；不支持源端摘要的驱动仍须满足可靠读取契约，并提供主机端 SHA-256。

按“摘要不一致后的有限重拷”覆盖执行资格与剩余次数的组合，验证重新开始、次数耗尽及取消后的处理。摘要获取失败或结果未知不能冒充内容不一致；同一不一致结果的重复处理不能重复扣减次数。

### 集成测试

组合设备操作协调器、相机驱动替身、真实 SQLite 和工作文件，同时安排取回与内部处理拷贝，并在存在多份半成品时重启恢复。验证同一相机读取不会重叠，各文件保留原身份及可靠进度；等待组成员、主机校验或媒体处理不占用相机拷贝机会。当前驱动联调还须验证文件拷贝期间的录像与必要停止操作满足已确认的兼容性契约。

在 A 读取失败、已保存重试等待且 B 可执行时中断会话，重启后改变候选加载顺序，验证仍为 A 保留拷贝机会。分别让 A 恢复成功、取消或耗尽预算，确认 B 只在原保留解除后取得机会；必要录像停止仍能执行，各入口不建立独立的并行拷贝。

组合真实 SQLite、调度器与拷贝入口，分别安排较早录像的修复输入和较晚用户取回同时可执行、修复输入稍后才可执行、计划时间相同，以及同一取回包含多份文件。重启时改变查询与加载顺序，验证仍使用动作时间、计划受理顺序、原数组位置及固定文件登记顺序；后到候选不能抢占已取得的文件拷贝机会。

组合真实 SQLite、受管工作文件和恢复流程，分别在拷贝中断、最终失败保存后、半成品删除后但清理结果保存前中断。验证恢复分别执行原请求续传、半成品清理或记录确认不存在，不重复取回、复活失败项或丢失历史。文件查询和删除失败、结果未知时不得记录清理成功。

组合真实状态库、报告发布及进程结果，在半成品删除失败但其他职责正常时验证有限尝试、诊断进入报告、`run` 返回 `succeeded` 与退出码 `0`。后续正常 `run` 清理成功后报告完成事实，历史失败不改写；仅残留记录且报告职责已完成时不触发立即再启动。数据库保存或报告发布失败时验证会话错误，不能沿用局部清理失败的正常收尾结果。

组合真实 SQLite、调度及报告生成，验证旧取回正在拷贝、清理等待旧取回时，新取回对该产物失败并报告原因。分别在失败记录提交前后中断，并交换清理取消与资格判断事务的顺序，验证恢复服从已提交事实；失败保存后取消清理不会复活该项，新的请求可按取消后的实际状态重新申请资格。

验证真实数据库的交付名称唯一性、取回资格与删除意图的并发处理；组合真实文件交接验证源产物与独立 delivery 的生命周期，以及删除或取消后恢复。

通过两个计划输入入口提交包含录像及本计划内取回的计划，使用实际 `params.source` 对象，组合真实 SQLite、调度、产物选择与报告验证局部动作名和组引用的完整流程。交换动作数组顺序并加入其他计划的同名动作及组，目标仍固定为本计划实例；取回早于录像结束时保留等待。分别在受理事务提交前后和执行期间中断，验证计划、全部动作及引用关联整体保存或回滚，恢复不重新解析或重复创建 delivery。同一请求改变正文重送时仍沿用原关联。

另行通过两个入口使用 `params.source.action_instance_id` 和计划实例加组名引用，动作级精确选择使用 `params.output_ids`。验证受理只保存合法引用描述，首次执行才查询及固定来源；非法来源结构在受理时使该动作 `failed`。报告可追溯本次取回及判定依据；从历史重建计划 JSON 时保留原字段层级、值及错误参数。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 正式产物

- `output_id` 稳定；
- 原片和修复产物独立；
- 所有正式产物保留到客户端显式清理，取回、传输、保存时长及空间不足不触发自动删除；
- 清理不级联。

#### 产物取回

- 默认选择全部正式产物；
- 精确选择 `output_ids`；
- 提前提交的单个录像全部产物取回等待录像动作结束，跨重启保留请求；
- 按组取回按类型筛选产物来源，不等待非产物动作；失败且无产物的录像仍保留为失败项；
- 本计划内引用在受理时确定来源，跨计划引用在首次执行时确定；取回自身的参数错误、来源缺失或无产物来源仅使该动作失败；
- 按 group 取回一组录像时，成员结束后分别选择并准备，全部成员及产物处理结束后才发布；
- 单个已结束动作未产生正式产物时，取回失败并报告原因；
- 部分失败仍交付成功项；
- 全部成功时整体为 `succeeded`，部分或全部失败时整体为 `failed`，报告保留逐项结果；
- 全部条目结束后才开始发布；
- 文件逐个发布；
- 每个新请求产生独立 delivery；
- 相机视频拷贝支持跨主机重启的断点续传；
- 取消撤回 ready；
- processing 不可撤回。

#### delivery 文件名

- 实际文件名使用完整 `delivery_id` 和文件类型扩展名，路径安全且长度有界；
- 同一产物的两次独立取回使用不同实际文件名，同一请求恢复沿用原名；
- 实际文件名历史唯一，传输删除或撤回后也不复用；
- `display_name` 保留完整可读名称及中文，可重复且不参与路径构造；
- 来源名称很长时不增加实际文件名长度；
- 报告保存两个名称，客户端按 `file_name` 唯一关联，不按显示名称或文件名解析推导身份。

#### 产物清理

- 新请求再次清理有完整清理记录的产物时，该项成功且不重复删除；
- 批量清理逐项处理，目标不存在不阻止其他项；全部成功时整体成功，全部结束且至少一项失败时整体失败；
- 删除中断后按原完整目标集合恢复，全部确认不存在才补记完成，未知不冒充成功；
- 已获得资格的取回优先；
- 每个产物的所有已有取回解除读取依赖后，即可清理，无须等待整组发布；
- 新取回被阻止；
- 删除部分失败仍禁止新取回；
- 未开始删除前允许取消并恢复；
- 已开始删除后取消不恢复。
