## 正式产物模型

camctl 为已登记的正式产物分配稳定标识。后续取回或清理引用这份产物时使用：

```text
output_id
```

产物记录至少能够表达：

- `output_id`
- `source_action_instance_id`
- 类型
- 原始文件名（如适用）
- 大小
- `sha256`
- 可用状态
- 视频时长（如适用）
- 派生关系（如适用）
- 清理状态

动作是否成功与它是否留下可取回文件分别判断。例如录像时长不足可以使动作失败，但已写完且归属明确的原片仍可按规则保留。

录像原片的保留资格见[原片保留与核验结果](camera-recovery.md#原片保留与核验结果)。媒体核验结果与文件可取回状态分别表达：已登记的原片即使无法正常播放或核验未确认，仍允许原样取回；本次拷贝继续满足可靠读取、落盘和摘要校验要求，媒体内容问题不能代替或绕过交付文件的一致性校验。

不能使用：

```text
source action = failed
```

直接推导：

```text
没有任何可取回产物
```

异常多录录像修复成功后产生两份不同正式产物：

```text
原片
修复成品
```

两者拥有不同 `output_id`。

### 主机派生产物

在主机加工形成的成品保存在[派生产物目录](file-handoff.md#staging) `staging/derived/`。每份正式派生产物具有自己的 `output_id`、保存位置及来源产物关联；其内容在登记后保持不变，后续取回使用这份保留文件生成独立 delivery。

修复成品的登记时点遵守[录像动作的结束时点](camera-recording.md#录像动作的结束时点)。文件准备完成但登记尚未提交时，仍按原处理流程恢复；提交结果未知时先核实数据库事实，不能仅凭目录中的文件将其登记或删除。

| 文件职责 | 保存位置 | 生命周期依据 |
| --- | --- | --- |
| 相机等已接入设备的正式产物 | 所属设备存储 | 本专题的长期保留与显式清理规则 |
| 主机已登记的派生成品 | `staging/derived/` | 同样长期保留，清理时指定其自身 `output_id` |
| 主机加工输入、未完成文件及尚未登记的成品 | `staging`；准备完成的派生成品可已位于 `derived` | 所属加工流程的完成、取消及恢复规则 |
| 某次取回的工作文件与独立交付文件 | `staging` 中 `derived` 以外的工作位置，发布后进入 `ready/processing` | 本次取回及文件交接规则 |

取消取回只处理该次取回的文件，不删除 `derived` 中的正式成品；主程序发送并删除交付文件后，新的取回仍能使用该成品。派生成品与其来源分别遵守[不级联删除](output-cleanup.md#不级联删除)规则。

### 长期保留

所有正式产物，包括照片、普通录像、异常录像原片及修复成品，统一保留到客户端明确提交清理请求。客户端通过 `delete_action_outputs` 指定要清理的 `output_id`，camctl 按本专题的清理资格、旧取回优先及失败恢复规则处理。MCU 第一版仅[预留接口](mcu-actions.md#第一版范围)，其产物在后续接入时遵守公共生命周期。

| 是否存在针对该产物的有效清理请求 | 其他情况 | 正式产物的处理 |
| --- | --- | --- |
| 否 | 任意取回或传输结果、保存时长及剩余空间 | 继续保留；这些情况单独或共同出现均不授权自动删除 |
| 是 | 任意取回或传输结果、保存时长及剩余空间 | 按“产物清理”处理；有效请求不等于可以立即删除，仍须满足清理与取回并发规则 |

修复成功不自动删除原片；空间不足也不通过淘汰旧正式产物解决。客户端负责安排显式清理以释放空间，当前操作按其空间不足规则报告结果。

本规则约束正式产物的保留。主程序传输后删除 delivery 文件、camctl 撤回可撤回的 delivery，仍遵守各自的交接规则，不因此删除正式产物。未成为正式产物的临时文件和取消录像产生的废弃文件，按所属处理流程管理；不能用临时文件清理绕过正式产物的保留要求。

清理只改变文件及其可用性，不删除数据库中的产物、取回、交付和清理历史。数据库记录继续永久保留。

## Delivery 与文件名

每次独立取回产生：

```text
delivery_id
```

delivery 与 output 是不同身份：

```text
output_id
    = 正式业务产物

delivery_id
    = 一次具体交付
```

### 实际文件名

普通产物的交付文件名使用完整的 `delivery_id`，保留文件类型扩展名：

```text
<delivery_id>.<ext>
```

例如 `d-000042.mp4`、`d-000043.mp4`。示例中的 ID 仅说明命名结构，不规定 ID 的生成算法。不能截短 ID 来构造文件名；同一产物的不同取回请求各自使用自己的 delivery 身份及路径。

ID 遵守公共标识字符串约束，扩展名使用与文件类型对应的非空 ASCII 字母或数字表示，整个文件名不超过 255 个 ASCII 字节。不能直接拼入设备路径或任意长度的输入；分配时须同时满足 ID 与文件名长度限制。具体 ID 分配算法不属于客户端匹配协议。

### 历史全局唯一

唯一性范围为单台主机的持久化历史。`delivery_id` 与实际交付 `file_name` 在该范围的整个 delivery 历史中保持唯一，数据库对其建立唯一约束。名字一经分配就保持不变，从 `staging` 发布到 `ready`、由主程序移至 `processing` 时均使用同一名字。文件被传输删除、撤回或源产物被清理，都不释放名称；同一请求恢复沿用原记录。

### 完整可读名称

状态报告通过 `display_name` 保存完整的人类可读名称：

```text
<original-stem>-<plan-name>-<action-name>.<ext>
```

例如 `VID_0001-夜间采集-主录像.mp4`。修复成品可通过原始名称部分的 `repaired` 标记帮助人识别。这里使用产物来源计划及动作的名称；来自设备的原始名称只取文件名部分，不包含设备目录。

`display_name` 保留中文等可读内容，可在不同 delivery 之间重复。它作为报告中的字符串供显示，不作为主机交付路径，不受交付文件名的长度限制，也不承担机器身份或唯一性。

### 报告负责机器映射

状态报告包含：

```text
delivery_id
output_id
file_name
display_name
source_action_instance_id
size
sha256
delivery 状态
```

客户端根据报告中的**完整 `file_name` 精确匹配**收到的文件，取得 `delivery_id`、`output_id` 及来源等信息；不要求客户端解析文件名推导业务身份，也不能用 `display_name` 进行唯一匹配。

字段按已取得的事实提供。已成功发布的交付须提供完整文件大小及经本次读取和校验流程取得的 SHA-256。尚未完成准备或已失败的交付，可以报告已可靠确认的完整源文件大小；不能用部分拷贝进度作为 `size`，也不能为尚未取得的完整文件摘要补造值。读取进度、校验未执行或失败，以及文件处理结果分别表达；文件名已分配不表示文件已发布。具体成功与失败样例见[客户端协议样例](client-protocol-examples.md#交付与文件读取)。

## 正常取回与清理流程

一次正常取回从已受理的来源引用开始：到达 `scheduled_at` 后取得来源动作的正式产物，为选中的每份产物建立本次请求独立的 delivery，将源文件拷贝到 `staging`，完成读取校验及落盘后发布到 `ready`。报告记录实际文件名、可读名称、大小、摘要和来源，供客户端接收与校验。

成功交付后，正式源文件仍保留。客户端需要再次取回时使用新的请求；需要释放源文件空间时，通过 `delete_action_outputs` 明确指定产物 ID。相机原片与修复成品各自选择、各自清理。具体选择、时机和文件所有权遵守后续各节。

## 取回与清理的执行时间

`obtain_action_outputs` 和 `delete_action_outputs` 均为无时效动作，可以按 `scheduled_at` 指定开始处理的时间，允许延后执行。`scheduled_at` 不表示完成期限；这两类动作不采用 `max_delay_ms` 过期窗口，终态为 `succeeded`、`failed` 或 `canceled`。

取回与清理请求的 `scheduled_at` 均必填，缺省按[公共时间字段规则](scheduling-execution.md#scheduled_at)处理。已指定合法时间的请求按下表处理，取消和已提交的终态优先于时间判断：

| 动作与时间情况 | 处理 |
| --- | --- |
| 动作已取消或进入其他终态 | 保持原结果，按所属收场规则处理，不因到达计划时间而重新执行 |
| 动作未开始，可信当前时间早于 `scheduled_at` | 等待计划时间，不提前取回或删除 |
| 已到达或超过 `scheduled_at`，动作仍未完成 | 按产物可用性、取回与清理并发规则及剩余重试预算执行；需要等待录像结束或旧取回时保留未完成状态 |
| 主机重启，动作仍未完成且已超过计划时间 | 恢复原请求和已保存的进度，不因延迟自动过期 |
| 时间无法可靠判断 | 遵守公共时钟检查与受限执行规则，不能自行判为已到时间或过期 |

单次通信超时、有限重试耗尽、空间不足和取消仍按各自规则处理。等待录像结束或已有取回完成，不等于一次设备通信失败，不能只因计划时间已过去就记录失败；设备操作也不能因“无时效”而无限重试。

计划受理时间与动作计划执行时间分别保存；受理较早不表示应在自己的 `scheduled_at` 之前执行。取回与清理竞争同一产物时，遵守下面的执行顺序。

### 延后执行时的取回与清理顺序

正常调度或重启恢复时，同次调度看到指向同一已登记、可用产物的取回与清理动作，若两者均未开始、均已到计划时间，且尚无既有取回资格或删除限制，则按 `scheduled_at` 从早到晚处理；计划时间相同时，取回优先于清理。请求受理顺序、数据库查询返回顺序及内存加载顺序不能颠倒这一顺序。

| 两个动作的计划执行时间 | 处理顺序 |
| --- | --- |
| 取回早于清理 | 先处理取回并建立旧取回保护，再按[清理与取回并发](output-cleanup.md#清理与取回并发)处理清理；不能抢先登记删除限制而使这个取回失去资格 |
| 清理早于取回 | 先按清理规则处理；后续取回遵守已经形成的删除限制与实际产物可用状态，不能仅因它更早提交而插队 |
| 两者相同 | 先处理取回并建立旧取回保护，再按[清理与取回并发](output-cleanup.md#清理与取回并发)处理清理；即使清理请求更早受理，也不能抢先删除 |

例如 10:00 取回视频 A、11:00 删除 A，主机直到 12:00 才上电，两者均未执行且 A 仍可用：先处理取回，再删除 A。清理等待已有取回不再需要读取 A，具体见[清理与取回并发](output-cleanup.md#清理与取回并发)；独立交付副本可靠准备完成后，无须等待发布、主程序发送或客户端收到。取回最终失败或取消时，须确认该项读取及重试已停止，不要求取回必须成功才允许清理。

该排序用于尚未开始的动作。已经取得的取回资格、已经登记的删除限制及已经发生的删除仍按并发和恢复规则处理，不能因重新排序而撤销。资格授予与顺序保存的事务边界，以及取回仍在等待录像结束而尚不能确定产物时的处理，仍需细化。

## 普通产物传输失败与重新取回

主程序完成本地发送不证明客户端收到，交接事实由[文件交接](file-handoff.md)定义。

对于照片、视频等普通产物：

> 不自动重传。

客户端如果未收到或完整性校验失败：

1. 根据已经掌握的 `output_id`；
2. 使用新的 `request_id`；
3. 再提交 `obtain_action_outputs`。

只要正式源产物仍然可用，即可重新产生新的独立 delivery。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

产物投影提供本专题定义的稳定身份、来源、可用性、派生关系和清理状态。交付投影提供 `delivery_id`、`output_id`、来源 obtain 动作、历史唯一的实际 `file_name`、完整可读的 `display_name` 及交付状态。登记、发布、撤回和清理等变化均追加历史并同步更新投影，遵守[持久化与配置基础](system-foundations.md#持久化与配置基础)。

文件位置与业务记录之间的对账引用[文件交接](file-handoff.md)。历史回放不能执行取回、发布、撤回或源文件删除；历史中的删除意图与已确认删除结果保持区分。数据库保留产物历史不意味着已清理的产物文件仍然可用。

相机视频拷贝还需保存来源与未完成文件的关联，以及已经可靠保存的拷贝进度，供后续会话续传。历史回放恢复这些事实，实际读取设备文件由取得执行资格的处理流程完成。

## 验收要求

### 单元测试

按[取回半成品的保留与清理](obtaining-outputs.md#取回半成品的保留与清理)覆盖取回未结束、最终失败、取消，与读写仍在进行、已停止及未知的组合。未结束项保留续传；失败或取消项仅在确认停止后删除自己的半成品。组合已准备成功的 A 和失败半成品 B，验证只清理 B、A 仍须发布；原片、派生成品及其他请求文件均保留。

按[半成品清理失败与后续处理](obtaining-outputs.md#半成品清理失败与后续处理)覆盖清理成功、文件查询或删除失败及结果未知，分别组合状态保存与报告职责完成或失败。局部清理问题可延后，数据库与必要报告错误仍为会话错误；本次有限尝试结束后，调度重扫和收尾检查不重启尝试，原动作及计划不恢复执行。

按[新取回遇到删除限制](output-cleanup.md#新取回遇到删除限制)覆盖旧资格、新请求、有效限制、限制已解除及状态未知。新请求在限制有效时对应项立即失败且不开始拷贝；旧资格继续受保护。组合单项和多项请求验证失败范围、其他项继续处理及整体结果。限制后来解除、重启和同一请求重送均不恢复已失败项。

隔离产物目录、设备文件和交付存储协作者，验证产物选择、部分成功、开始发布的条件、文件名规则、清理限制、取消及重取身份。

按本动作的“参数”和[校验与失败处理](obtaining-outputs.md#校验与失败处理)覆盖四种来源形式，以及 `params`、`source` 缺失、非对象、空对象、字段混用和非法组合；另行覆盖 `output_ids` 空数组和动作自身的所属组字段错误。公共结构合法时只将错误取回登记为 `failed`，保留输入与诊断，不执行或创建 delivery；其他动作一同受理。已有请求重试仍忽略本次正文。

按[本计划内的产物引用](obtaining-outputs.md#本计划内的产物引用)覆盖局部名称存在、缺失、来源类型不适用及混用引用，仅该取回在受理时失败；重复动作名属于公共结构错误，按整份拒绝处理。局部引用只在本计划解析，支持数组中的前向引用；其他计划的同名动作或组不能成为目标。已有请求重试不重新解析正文。

按[按动作实例 ID 查找来源](obtaining-outputs.md#按动作实例-id-查找来源)覆盖目标存在且类型适用、类型不适用、不存在、查询错误、结果未知，以及曾确认来源存在但其记录缺失。受理阶段不查询目标，取得执行资格后确认目标缺失或类型不适用时仅取回失败。取消及已有终态优先；已经保存的结果不会因重启、同一请求重送或后续来源出现而改变。

按“取回与清理的执行时间”覆盖计划时间之前、恰好到达、延后及时间未知，验证两类动作均不提前执行、不因延后进入 `expired`。区分业务等待、单次通信超时与重试耗尽；延后不能重置预算，也不能覆盖已有终态。

按“延后执行时的取回与清理顺序”覆盖取回时间较早、清理时间较早及两者相同，并分别改变受理顺序和加载顺序。验证较晚或同一计划时间的清理不能抢先限制取回，较早清理产生的限制也不会被较晚取回绕过；已有资格、删除限制和终态按原规则保留。

按[再次清理已完成的产物](output-cleanup.md#再次清理已完成的产物)覆盖完整清理记录、未完成或部分失败、删除结果未知、目标不存在及数据库错误。已确认清理完成时本项成功且不调用删除协作者；报告保留本次请求、目标及此前已清理的含义。仅文件缺失或仅一个副本删除不能进入该成功分支。

按[批量清理结果](output-cleanup.md#批量清理结果)覆盖全部成功、部分失败、全部失败及仍有未完成项，包含此前已清理、目标不存在、删除失败和结果未知。目标不存在不能阻止其他合法目标执行；数据库异常不能当作逐项目标不存在处理；取消及既有终态不被汇总覆盖。

按[删除中断后的恢复](output-cleanup.md#删除中断后的恢复)覆盖请求资格与目标记录分类，以及文件全不存在、部分存在、全存在、包含未知的组合。只有全部目标确认不存在才能补记完成；设备不可达或查询失败不能当作不存在，终态请求不能自动继续删除，未知或缺失的完整目标记录不能当作空集合。验证重试耗尽、恢复结果保存失败及提交未知时保留实际状态。

按“长期保留”覆盖有无有效清理请求，以及取回完成、传输完成、保存时间增长和空间不足的组合，验证所有正式产物采用相同保留规则。无清理请求不能删除正式产物；有请求仍需满足旧取回优先及取消规则。

按[等待录像动作结束](obtaining-outputs.md#等待拍摄动作结束)覆盖取回资格、录像是否结束、产物有无及查询异常的分区。验证等待期间不提前固定部分产物或判无产物失败；录像进入不同终态后按正式产物处理；已取消的取回不能因录像结束恢复执行。

按[组内录像分别准备与统一发布](obtaining-outputs.md#组内录像分别准备与统一发布)覆盖全部未结束、部分结束、全部结束及取回取消，包含未来录像尚未开始、录像失败或取消、查询错误和跨计划同名组。验证已结束成员分别固定完整选择并开始准备，未结束成员仍等待；任何成员尚未完成判定时，不能发布已有成功文件或汇总整体终态。恢复保留逐成员选择，不遗漏未来成员或重复创建交付。

按[按组取回的成员筛选](obtaining-outputs.md#按组取回的成员筛选)覆盖类型产物能力与动作状态的组合。非产物动作尚未开始、运行中或已结束均不影响取回等待、发布及失败汇总；录像尚无产物仍须保留为来源，终态无产物仍记失败，不能通过筛选隐藏失败录像。成员或类型查询未知须明确处理，不当作可忽略成员。组取消及报告组织仍使用原组成员。

按[组来源的确定](obtaining-outputs.md#组来源的确定)覆盖本计划内及指定计划实例的组引用，与来源未解析、存在有效成员、目标缺失、成员均不产生产物和查询错误的组合。本计划内引用在受理时解析，跨计划引用在首次执行时解析；可靠的缺失或无产物来源只使该取回失败。有效集合保存后恢复不重新选择；产物尚未生成或已清理不改变来源类型的判定，仍按运行时可用性处理。

按[逐产物解除读取依赖](output-cleanup.md#逐产物解除读取依赖)与[准备完成与断电恢复](output-cleanup.md#准备完成与断电恢复)覆盖单个和多个已有取回的依赖组合，以及写入、校验、落盘、事务提交的成功、失败和未知。只有所有已有取回均不再需要读取才允许删除；某项最终失败或取消还须确认读取与重试停止。验证准备完成与依赖解除在同一事务中保存，删除源文件不影响已准备交付的发布资格。

按[已结束动作没有正式产物](obtaining-outputs.md#已结束动作没有正式产物)覆盖动作终态与产物情况的分区，验证无产物时取回失败且不创建 delivery。动作未结束、引用缺失、查询失败或未知，以及曾产生但已清理的产物均不能误入该分支。保留 `output_ids = []` 的参数错误语义。

按[取回失败项的报告表达](obtaining-outputs.md#取回失败项的报告表达)覆盖来源无产物、有产物但尚无 delivery、delivery 已创建后最终失败、仍可重试以及来源未知的分区。验证身份字段按实际记录提供，三次读取失败只形成一个文件最终失败项；失败项与交付错误同源且一致。已有失败而其他来源仍未结束时，报告可以表达失败项，但不提前结束动作或发布文件；恢复和重复报告不新增失败项，客户端随动作自身字段整体更新 `result.failures`。

录像组另行覆盖每个成员均有产物、部分成员无产物及全部成员无产物，并组合产物取回成功、失败、重试或发布未完成。无产物项关联来源动作，不创建虚构产物或 delivery；存在无产物项时整体失败，但仍须完成其他文件的必要发布。录像失败但留有产物不自动使取回失败，数据库错误不能当作成员无产物。

按[部分成功](obtaining-outputs.md#部分成功)表覆盖全部成功、部分失败、全部失败，以及其他项仍在重试、等待发布或发布结果未知的情况。验证整体状态与逐项结果一致，某项失败不能提前结束动作或扣留成功项；取消及既有终态不能被结果汇总覆盖。

按[重启后选择续传位置](file-copy.md#重启后选择续传位置)覆盖各分区，验证续传偏移、尾部截断、已完成数据范围及错误分类。覆盖实际读取长度小于请求长度、提前结束，以及写入、同步、截断、进度提交失败或结果不确定；未可靠保存的字节不能推进进度。进度提交前的文件和目录同步顺序属于断电恢复契约，须明确验证。

按[按文件累计读取尝试](file-copy.md#按文件累计读取尝试)覆盖默认上限、合法配置、分段成功、明确读取失败、次数耗尽、断电恢复、取消及历史未知。用在不同位置发生的多次读取失败验证同一文件累计计数，成功段不重置预算；用多文件和不同请求验证各自计数。报告中的已用次数与上限须来自保存的事实。

按[文件读取的无数据超时](file-copy.md#文件读取的无数据超时)覆盖首批数据等待、阈值之前与达到阈值、间歇性新数据、持续慢速读取、非文件响应、主机处理阶段、排队与重试等待、正常结束及提前结束。验证默认阈值和合法配置，非法零值、负值、非有限数值或类型错误不能作为缺省值。使用可控单调钟验证计时，不依赖测试实际等待。

按[同一相机的拷贝并发限制](file-copy.md#同一相机的拷贝并发限制)组合取回、异常原片检查和内部修复入口，验证同一相机最多有一份活动拷贝，分段保存进度不允许另一份文件插入。等待不消耗读取次数；取消或最终失败后，实际读取结束前不能启动另一份拷贝。分别验证不同源相机独立协调、主机派生文件拷贝不占相机机会，以及控制操作仍遵守驱动兼容性。

按[等待重试时保留拷贝机会](file-copy.md#等待重试时保留拷贝机会)覆盖仍可重试、取消、预算耗尽、读取尚未停止或状态未知，以及源内容读取完成。验证等待期间其他文件不能开始、重试继续原进度和预算、符合解除条件后才选择其他文件。源内容读完后发生校验失败的重拷须重新参与选择，不追溯抢占另一份活动拷贝。

按[多个候选文件的选择顺序](file-copy.md#多个候选文件的选择顺序)覆盖所属动作时间不同、同时间跨计划、同计划不同动作以及同动作多文件。取回使用取回动作时间，检查和修复使用所属录像时间，重拷沿用原依据；未具备读取条件的较早请求不阻挡合格候选。另行验证已有活动拷贝及重试保留优先于候选排序，排序数据缺失或未知不能使用加载顺序替代。

按[读取正确性与文件校验](file-copy.md#读取正确性与文件校验)覆盖摘要支持、不支持和能力未知，以及摘要相同、不同、获取失败和结果未知的分区。读取失败或结果未知、主机摘要计算失败、源端校验未通过时不能交付该副本；不支持源端摘要的驱动仍须满足可靠读取契约，并提供主机端 SHA-256。

按[摘要不一致后的有限重拷](file-copy.md#摘要不一致后的有限重拷)覆盖执行资格与剩余次数的组合，验证重新开始、次数耗尽及取消后的处理。摘要获取失败或结果未知不能冒充内容不一致；同一不一致结果的重复处理不能重复扣减次数。

验证重拷上限未配置时，首次拷贝不计数，只允许额外一轮重拷；这一轮仍摘要不一致即失败。另行覆盖合法零值和正整数、非法负值和类型错误，以及配置变化后已有动作仍沿用固化上限。新一轮重拷中断后恢复原轮次，不额外增加次数。

组合读取错误和摘要不一致，验证两项预算独立累计且不互相补充：读取报错后的续传不增加重拷次数，摘要不一致后的重拷不增加或清零读取计数。分别耗尽其中一项并保留另一项额度，验证相应失败不能借用另一项额度继续。第三次读取完成后仍可使用已有重拷额度，但后续读取再失败即结束该文件。

### 集成测试

组合相机读取适配、真实工作文件与状态库，模拟分段尚未完整返回但持续取得文件字节的慢速读取，验证持续时间超过阈值仍可完成。另行模拟停滞到达阈值、主机处理阶段暂停读取及断电恢复，验证超时只消耗读取预算、可靠进度不因收到未落盘数据而推进、恢复不累计断电时间，重启前已记录的超时不被撤销。

组合状态库、相机读取替身、主机文件与摘要校验，在读取错误后续传成功，再制造源端与主机摘要不一致。分别在新重拷轮次登记前后中断恢复，验证读取计数保持、重拷计数只增加一次、新轮次进度不会连接上一轮无效副本；两类失败及计数均可从报告追溯。

组合真实 SQLite、工作文件与受接口约束的驱动替身，在同一文件的不同进度处报告读取错误，验证第三次明确失败后按默认预算结束该文件。分别在尝试登记后、分段进度保存后及明确失败记录保存后中断并恢复；已登记而未结束的尝试继续原身份，已有失败须保留，重试仍须消耗下一次尝试。计数与失败事实不能因重启丢失或重复增加，其他文件保留各自预算。

组合设备操作协调器、相机驱动替身、真实 SQLite 和工作文件，同时安排取回与内部处理拷贝，并在存在多份半成品时重启恢复。验证同一相机读取不会重叠，各文件保留原身份及可靠进度；等待组成员、主机校验或媒体处理不占用相机拷贝机会。当前驱动联调还须验证文件拷贝期间的录像与必要停止操作满足已确认的兼容性契约。

在 A 读取失败、已保存重试等待且 B 可执行时中断会话，重启后改变候选加载顺序，验证仍为 A 保留拷贝机会。分别让 A 恢复成功、取消或耗尽预算，确认 B 只在原保留解除后取得机会；必要录像停止仍能执行，各入口不建立独立的并行拷贝。

组合真实 SQLite、调度器与拷贝入口，分别安排较早录像的修复输入和较晚用户取回同时可执行、修复输入稍后才可执行、计划时间相同，以及同一取回包含多份文件。重启时改变查询与加载顺序，验证仍使用动作时间、计划受理顺序、原数组位置及固定文件登记顺序；后到候选不能抢占已取得的文件拷贝机会。

组合真实 SQLite、受管工作文件和恢复流程，分别在拷贝中断、最终失败保存后、半成品删除后但清理结果保存前中断。验证恢复分别执行原请求续传、半成品清理或记录确认不存在，不重复取回、复活失败项或丢失历史。文件查询和删除失败、结果未知时不得记录清理成功。

组合真实状态库、报告发布及进程结果，在半成品删除失败但其他职责正常时验证有限尝试、诊断进入报告、`run` 返回 `succeeded` 与退出码 `0`。后续正常 `run` 清理成功后报告完成事实，历史失败不改写；仅残留记录且报告职责已完成时不触发立即再启动。数据库保存或报告发布失败时验证会话错误，不能沿用局部清理失败的正常收尾结果。

组合真实 SQLite、调度及报告生成，验证旧取回正在拷贝、清理等待旧取回时，新取回对该产物失败并报告原因。分别在失败记录提交前后中断，并交换清理取消与资格判断事务的顺序，验证恢复服从已提交事实；失败保存后取消清理不会复活该项，新的请求可按取消后的实际状态重新申请资格。

验证真实数据库的交付名称唯一性、取回资格与删除意图的并发处理；组合真实文件交接验证源产物与独立 delivery 的生命周期，以及删除或取消后恢复。

通过两个计划输入入口提交包含录像及本计划内取回的计划，使用实际 `params.source` 对象，组合真实 SQLite、调度、产物选择与报告验证局部动作名和组引用的完整流程。交换动作数组顺序并加入其他计划的同名动作及组，目标仍固定为本计划实例；取回早于录像结束时保留等待。分别在受理事务提交前后和执行期间中断，验证计划、全部动作及引用关联整体保存或回滚，恢复不重新解析或重复创建 delivery。同一请求改变正文重送时仍沿用原关联。

另行通过两个入口使用 `params.source.action_instance_id` 和计划实例加组名引用，动作级精确选择使用 `params.output_ids`。验证受理只保存合法引用描述，首次执行才查询及固定来源；非法来源结构在受理时使该动作 `failed`。报告可追溯本次取回及判定依据；从历史重建计划 JSON 时保留原字段层级、值及错误参数。

通过两个入口提交包含合法录像 B 和按合法但未登记的动作实例 ID 取回 A 的计划，组合真实 SQLite、调度与报告，验证完整计划正常受理；取回到执行时间后失败，录像 B 仍按自身条件执行。失败报告保留指定来源 ID，不创建虚构来源或 delivery。分别在判定与结果的事务提交前后中断，恢复使用已提交事实；同一请求不重开失败取回。另用本计划内缺失的 `action_name` 验证该取回在受理时即为 `failed`，录像 B 仍为 `pending`。

组合真实 SQLite 与调度器，分别验证取回和清理在计划时间前保留待执行状态、计划时间后启动或跨进程恢复时继续原请求；不产生因迟到而过期的结果，已保存的拷贝或删除进度与重试预算保持一致。

组合 SQLite、调度器与真实受管文件，保存 10:00 取回、11:00 清理同一产物的两个未开始动作，在可信时间为 12:00 的会话启动后验证先取回、后清理。另设取回和清理都为 10:00 的场景，分别在正常到点调度和延后启动恢复时验证取回优先。反转计划受理及查询返回顺序，结果仍相同；另行覆盖清理计划时间更早、取回失败或取消，以及发布后主程序尚未发送的情况。

组合真实文件与 SQLite，验证 delivery 被领取并删除后，正式产物仍可由新请求再次取回；显式清理完成后文件不可再取回，但产物及历次取回、交付、清理历史仍可查询和回放。

对保存在 `staging/derived/` 的修复成品，分别在取回取消、交付发布及主程序领取并删除后检查成品仍可用；新请求得到独立交付文件且内容一致。显式清理修复成品仅删除对应成品，原片仍保留；清理原片也不删除修复成品。登记前中断或提交结果未知时，验证恢复依据处理记录和数据库事实，不将目录存在当作正式登记。

对已持久化清理完成的产物提交新的清理请求，组合 SQLite 与报告生成验证本项成功及此前已清理的说明；在新请求结果提交前后中断，恢复后不重复物理删除、不虚构新的删除事实，原产物清理历史与不可取回状态保持一致。

组合计划受理、SQLite、真实受管文件与报告生成，验证含不存在目标的合法批量清理请求能够受理，存在的目标正常清理，最终整体失败且报告包含全部条目结果。在条目结果保存后、其他条目完成前中断，验证恢复继续未完成项，保留成功项与失败项的原结果。

使用真实 SQLite、主机受管文件及受接口约束的相机适配替身，分别在删除意图提交后、仅部分文件删除后、全部文件删除但完成记录提交前，以及恢复结果提交后中断。验证原目标集合保持完整，已不存在的文件不重复删除，剩余文件在有资格时继续处理，全部确认不存在后补记成功。包含相机查询失败及后续恢复可达的情况；真实设备适配另行验证目标识别和文件存在性查询能区分不存在与通信错误。

组合真实文件交接、SQLite 和报告生成，验证部分失败时成功文件仍交付，动作整体为 `failed`，报告保留逐项结果。覆盖成功文件逐个发布期间中断后恢复，以及文件已被主程序领取的情况；未完成发布的成功项不能因其他项失败而被遗留。

使用数据库中已结束且未产生正式产物的动作执行取回，验证持久化的取回终态为 `failed`，生成的报告包含被引用动作和无产物原因，且无对应 delivery；重启恢复后结果保持一致。

组合调度器、SQLite 与产物处理，验证提前提交的录像取回在录像结束后自动继续，等待不阻塞录像结束或取消。覆盖等待期间、录像终态提交后及产物集合持久化后的进程中断；恢复使用原请求和已确定集合，等待工作不会被会话退出检查遗漏。

组合 SQLite、调度器、录像处理及交接目录，安排同组上午 A 与下午 B 两次录像，中午执行组取回。验证立即准备 A，B 结束前没有本次取回的文件发布；B 结束后补入该成员完整选择，按逐项结果及开始发布的条件处理。分别在成员结束、成员选择保存、交付副本准备完成及等待 B 期间中断，恢复保持原请求、固定组成员和各成员选择；等待期间取消取回后，不因 B 结束恢复交付。

通过本计划内组引用和指定计划实例的组引用，分别取回混合了录像及非产物动作的组。安排 A 上午录像结束、B 晚间生成报告，中午取回仅处理 A，准备完成后即可发布；B 仍按原计划执行。分别令 A 成功有产物、失败有产物及失败无产物，验证文件与整体结果由 A 的实际取回结果决定。筛选与来源关联保存前后及等待期间中断，恢复保持原来源范围，非产物成员不成为等待对象或无产物失败项。

两个入口分别提交合法录像与引用错误组的取回，覆盖本计划内目标组缺失、只有非产物动作，以及跨计划目标计划缺失、组缺失或没有产物来源。验证完整计划受理并推进受理序列；本计划内错误在受理时使取回失败，跨计划错误在首次执行时使取回失败，合法录像继续执行。报告保留不同失败阶段及原因，有效 ACK 独立处理。另用包含尚未结束录像的目标组验证正常等待，终态无产物按逐项失败处理。

组合真实 SQLite 与调度，在跨计划取回受理后、首次执行前改变目标产物的可用状态，验证受理未查询或固定跨计划来源，执行按届时的来源与文件状态判断。分别在运行时来源事务提交前后、成员准备期间中断，恢复保留已固定集合及逐项进度；查询或保存失败不能当作空组或已完成解析。已确认来源仍存在但文件被合法清理时，报告实际产物不可用，不把它描述为来源动作不存在。

分别使用相机原片与 `staging/derived/` 成品，在 A 的交付副本准备完成后、B 尚未结束时执行对 A 的显式清理。验证对应保留文件可删除，A 的交付副本仍在，B 结束后可继续发布 A。另设第二个已有取回仍在拷贝 A，验证其读取依赖解除前不能删除。分别在文件落盘后、准备完成与依赖解除事务提交前后、源文件删除后中断；恢复不能提前删除、重复创建副本或要求已删除的源文件重新出现。目标存储环境须验证突然断电下的落盘保证。

组合真实 SQLite、组产物选择、文件交接与报告生成，使用 A 有视频、B 已结束且无产物的组，验证 A 成功发布后组取回为 `failed`，报告分别包含 A 的交付结果与 B 的无产物失败。分别在选择及无产物结果提交前后、A 发布期间中断，恢复保留完整选择和失败项；另行验证整组无产物时不创建 delivery，以及录像失败但有产物且全部取回成功时整体为 `succeeded`。

针对相机视频取回、异常原片检查及内部修复所需的拷贝，使用已经写完、内容和长度固定的源文件，验证中断后跨进程恢复能够复用已可靠保留的部分，保持来源关联及原完整长度；同一次取回的恢复不新建交付身份，录像内部处理不创建 delivery。真实设备适配须验证文件写入完成的确认依据、身份与长度读取及从指定位置继续读取；目标存储环境须验证断电后部分文件与进度记录的恢复。

分别在段写入中、文件同步后进度提交前、进度提交后及恢复截断后中断，使用真实文件与 SQLite 验证恢复结果。安排同一文件经历多次中断，最终逐字节比较主机文件与固定源文件，覆盖段边界和最后不足一段的数据。正常进程重启验证之外，还须验证目标存储环境的断电落盘行为。

当前相机适配验证源端 SHA-256 的取得和比较，并验证二进制文件读取保留原字节、错误被明确报告。明确不提供源端摘要的设备适配，须通过已知内容的固定文件验证可靠读取与跨重启续传，实际交付文件与报告中的主机 SHA-256 一致。

使用真实文件与 SQLite，分别在重拷决定提交前后、主机文件重新准备期间及重拷进度保存后中断，验证次数、原处理身份和新一轮进度正确恢复。覆盖重拷后校验通过及连续不一致直至耗尽；无效副本不进入交付或修复，相机源文件保留，成功项仍按开始发布的条件交付。重启不能导致无限重拷。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 正式产物

- `output_id` 稳定；
- 原片和修复产物独立；
- 所有正式产物保留到客户端显式清理，取回、传输、保存时长及空间不足不触发自动删除；
- 清理不级联。

#### 产物取回

- 默认选择全部正式产物；
- 精确选择 `output_ids`；
- 提前提交的单个录像全部产物取回等待录像动作结束，跨重启保留请求；
- 按组取回按类型筛选产物来源，不等待非产物动作；失败且无产物的录像仍保留为失败项；
- 本计划内引用在受理时确定来源，跨计划引用在首次执行时确定；取回自身的参数错误、来源缺失或无产物来源仅使该动作失败；
- 按 group 取回一组录像时，成员结束后分别选择并准备，全部成员及产物处理结束后才发布；
- 单个已结束动作未产生正式产物时，取回失败并报告原因；
- 部分失败仍交付成功项；
- 全部成功时整体为 `succeeded`，部分或全部失败时整体为 `failed`，报告保留逐项结果；
- 全部条目结束后才开始发布；
- 文件逐个发布；
- 每个新请求产生独立 delivery；
- 相机视频拷贝支持跨主机重启的断点续传；
- 取消撤回 ready；
- processing 不可撤回。

#### delivery 文件名

- 实际文件名使用完整 `delivery_id` 和文件类型扩展名，路径安全且长度有界；
- 同一产物的两次独立取回使用不同实际文件名，同一请求恢复沿用原名；
- 实际文件名历史唯一，传输删除或撤回后也不复用；
- `display_name` 保留完整可读名称及中文，可重复且不参与路径构造；
- 来源名称很长时不增加实际文件名长度；
- 报告保存两个名称，客户端按 `file_name` 唯一关联，不按显示名称或文件名解析推导身份。

#### 产物清理

- 新请求再次清理有完整清理记录的产物时，该项成功且不重复删除；
- 批量清理逐项处理，目标不存在不阻止其他项；全部成功时整体成功，全部结束且至少一项失败时整体失败；
- 删除中断后按原完整目标集合恢复，全部确认不存在才补记完成，未知不冒充成功；
- 已获得资格的取回优先；
- 每个产物的所有已有取回解除读取依赖后，即可清理，无须等待整组发布；
- 新取回被阻止；
- 删除部分失败仍禁止新取回；
- 未开始删除前允许取消并恢复；
- 已开始删除后取消不恢复。

## 实现时细化

正文定义第一版的业务规则。本节列出接口、配置和联调中需要落实的细节；先按正常流程推进，涉及正文尚未确定的业务结果时，再明确对应选择。

取回半成品按已确认的保留、清理失败及后续正常会话处理规则执行；仍需确定每次正常会话的清理尝试次数、超时参数和有限工作量的具体控制方式。

取回与清理均为无时效动作，输入字段及不适用策略的校验遵守[第一版动作入口](plan-input.md#第一版动作入口)。`max_delay_ms` 不为这两类动作启用过期窗口，显式提供时仅该动作初始失败。

单个录像在结束后选择全部产物，组取回按成员类型筛选来源，再逐来源在结束后选择并准备文件，正式产物登记与录像终态一同提交。参数、本计划内引用及跨计划来源的校验时点、错误范围和来源保存按本动作已确认规则处理；仍需细化精确 ID 选择的集合固定时点、ID 不匹配和不可用产物的逐项结果；等待阶段按[报告字段契约](report-format.md#错误与等待原因)表达。尚未开始、指向同一可用产物的动作按计划时间排序，同一时间取回优先于清理；仍需定义尚未生成的产物如何承接等待请求的取回资格、资格授予与顺序持久化边界，以及多个删除意图的组合、删除取消与重启恢复表。已授予资格的取回按逐产物读取依赖保护，准备完成与依赖解除遵守已确认的事务规则。产物可用性、清理进度及摘要尚未取得时的表达遵守[报告字段契约](report-format.md#正式产物)；文件类型到安全扩展名的映射及缺失处理由驱动接入落实。交付 ID 的字符与长度范围遵守[基本值类型](plan-input.md#输入文件与基本值类型)。

清理目标的逐项结果、整体终态及删除中断恢复按已确认规则处理；仍需核实设备与主机存储的目标识别、删除结果和不存在查询的具体确认依据、删除的断电持久性，以及查询与删除共用或分别使用的有限重试预算。

断点续传需补齐来源身份与完整长度的记录方式、停止结果未知时确认文件已经写完的设备对账依据、驱动按位置可靠读取的具体协议、分段大小与进度保存频率、摘要获取及比较的接口，以及取消和清理期间的具体处理。当前相机停止成功后的文件可读保证、命令执行及源端摘要能力已确认，具体适配协议仍需核实；必须满足已确认的跨重启续传要求后才能验收相关拷贝流程。

同一相机的拷贝遵守单文件并发限制、等待重试时的保留规则及候选文件排序。文件条目登记顺序与拷贝机会归属的具体历史字段，在持久化接口中落实。
