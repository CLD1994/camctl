# 正式产物与取回清理

[返回设计总览](../2026-09-08-camctl-cli-design.md)

本专题定义正式产物和普通 delivery（一次具体交付）的业务生命周期，包括取回、撤回资格和清理。目录所有权及发布/领取规则由[文件交接](file-handoff.md)定义；状态报告通过[状态报告与累计确认](status-reports.md)对外表达这些业务事实。

## 正式产物模型

正式产物具有稳定身份：

```text
output_id
```

产物记录至少能够表达：

- `output_id`
- `source_action_instance_id`
- 类型
- 原始文件名（如适用）
- 大小
- `sha256`
- 可用状态
- 视频时长（如适用）
- 派生关系（如适用）
- 清理状态

动作状态与产物可用性相互独立。

不能使用：

```text
source action = failed
```

直接推导：

```text
没有任何可取回产物
```

异常多录录像修复成功后产生两份不同正式产物：

```text
原片
修复成品
```

两者拥有不同 `output_id`。

异常录像原片：

> 保留到客户端明确要求清理。

修复成功不自动删除原片。

## 相机视频的断点续传

第一版要求相机视频拷贝到主机时支持跨主机重启的断点续传。拷贝因主机断电而中断后，后续实际启动的 `run` 在该处理仍有执行资格时，使用主机上已经可靠保留的部分继续拷贝，不因进程重启而统一从头取回整个视频。

已确认的运行前提是：相机内的源文件不会自行丢失，camctl 是这些文件的唯一访问者。拷贝对象为相机已经写完的视频文件，写完后内容和长度保持不变。camctl 按显式清理请求删除文件时，仍遵守本专题的清理与取回规则；已经取得取回资格的请求恢复续传时继续持有原资格。

开始拷贝时确定源文件身份及其完整长度，后续续传继续读取同一份固定内容，并以该长度确定拷贝的结束位置。源文件写入完成的确认依据及身份表示仍需结合设备协议细化。

该要求适用于 camctl 将视频从相机拷贝到主机的流程，包括 `obtain_action_outputs` 取回及相机录像内部修复所需的拷贝。主机向外部客户端传输文件由第三方主程序负责，其重试行为按文件交接专题处理。

续传需要保留相机源文件、主机上的未完成文件及所属处理任务之间的关联，以及能够可靠恢复的拷贝进度。已确认的进度变化按全局规则追加历史并同步更新投影；具体保存方式与频率仍需细化。恢复同一次取回时沿用原请求和交付身份，未完成文件继续由 camctl 管理，不能发布到 `ready`。完成后的交付仍遵守本次取回的发布屏障。

设备按指定位置读取文件的能力，以及主机部分文件与持久化进度在断电后的对账方式，属于后续必须补齐的设备和存储契约。

## obtain_action_outputs

### 作用

`obtain_action_outputs` 只负责：

> 选择已有正式产物，并为本次取回生成独立 delivery。

它不负责：

- 触发录像修复；
- 重新录像；
- 修改视频；
- 隐式生成业务产物。

### 产物选择

客户端可以先通过状态报告取得：

```text
output_id
```

再提交新的取回请求。

动作引用可以指定：

```text
action_instance_id
```

或：

```text
(plan_instance_id, group)
```

动作级引用允许可选：

```text
output_ids
```

语义：

```text
不带 output_ids
    → 获取该动作全部正式产物

output_ids = 非空数组
    → 精确获取这些产物

output_ids = []
    → 参数错误
```

不得因为指定产物不可用而自动扩大选择范围。

例如：

```text
只请求修复视频
```

修复视频不可用时，不能擅自改传原片。

但调用方如果省略 `output_ids`，表示明确请求“全部正式产物”，其中包括原片。

### 部分成功

例如请求：

```text
A
B
C
```

最终：

```text
A success
B success
C failed
```

A、B 仍然交付。

C 单独报告失败原因。

不因为 C 失败扣留 A、B。

### 发布屏障

在任何已选产物 仍在重试时，不提前发布其他成功产物。

必须先等：

> 本次请求中的全部已选产物 都取得最终处理结果。

之后才进入发布阶段。

发布阶段允许逐文件发布。

因此：

```text
A → ready → 被主程序领取
B → 稍后才进入 ready
```

是合法的。

A、B 可以落入不同数据传输窗口。

不要求整组原子发布。

### 每个新请求产生独立 delivery

新的 `request_id` 发起新的取回时：

> 即使选择与历史完全相同的 `output_id`，也创建独立 delivery。

各取回请求独立持有自己的待传文件。

同一 `request_id` 的重试则复用原请求，不创建新的 delivery。

### 取消取回

取回尚未完成时取消：

- 停止尚未开始的处理；
- 已经准备但尚未发布的文件不再发布；
- 不删除正式源产物。

文件已经发布到 `ready` 后：

> `obtain_action_outputs` 可以进入终态。

但之后仍允许针对这次取回撤回尚位于 `ready` 的 delivery 文件。

已经：

```text
ready → processing
```

的文件进入不可撤回阶段。

即使主程序尚未真正开始发送字节，也不再由 CLI 撤回。

如果一个已终态的 obtain 动作被后续 cancel：

- 历史动作终态不改变；
- 只处理其仍可撤回的 delivery。

## 产物清理

提供明确的产物清理能力，暂名：

```text
delete_action_outputs
```

清理必须显式指定 `output_id`。

不允许：

```text
省略 output_ids = 删除全部
```

也不允许空列表表示全部。

### 清理含义

清理一个正式产物意味着：

- 删除相机源文件（如存在且受 camctl 管理）；
- 删除板端受管保留副本；
- 使该 `output_id` 后续不再可取回；
- 保留该产物曾经存在以及被清理的历史记录。

已经发布到 `ready/processing` 的合法 delivery 不因此被撤回。

### 不级联删除

原片与修复成品具有派生关系，但删除：

```text
原片
```

不会自动删除：

```text
修复成品
```

反之亦然。

只删除客户端明确指定的正式产物。

### 清理与取回并发

已有取回优先。

清理开始时：

1. 持久化删除意图；
2. 禁止新的取回请求获取该产物；
3. 等待已经获得取回资格的旧请求完成必要交付；
4. 再进行物理删除。

清理开始以后新来的 obtain 请求不能插队。

### 清理部分失败

如果：

```text
板端副本已删除
相机源文件删除失败
```

则：

- 不允许新的取回；
- 不重新开放剩余副本；
- 如实报告物理清理未完成；
- 以后只能通过新的清理请求继续清理。

### 清理取消

如果清理尚处于等待旧取回的阶段：

```text
尚未发出任何可能删除文件的操作
```

则允许取消。

取消后，如果没有其他有效删除限制：

> 恢复新的取回权限。

一旦已经发出删除操作，或者无法排除删除已经发生：

> 不再因为取消而恢复取回权限。

## Delivery 与文件名

每次独立取回产生：

```text
delivery_id
```

delivery 与 output 是不同身份：

```text
output_id
    = 正式业务产物

delivery_id
    = 一次具体交付
```

### 文件名优先人类可读

默认：

```text
<original-stem>-<plan-name>-<action-name>.<ext>
```

例如：

```text
VID_0001-夜间采集-主录像.mp4
IMG_0042-设备巡检-东侧拍照.jpg
```

文件名不是机器身份。

客户端不解析文件名推导 `output_id` 或 `delivery_id`。

### 历史全局唯一

实际交付 `file_name` 在整个 delivery 历史中保持唯一。

已经：

- 使用过；
- 被传输；
- 被撤回；

的名字都不再复用。

发生冲突时：

```text
<original-stem>-<plan-name>-<action-name>-<short-delivery-id>.<ext>
```

例如：

```text
VID_0001-夜间采集-主录像-d052ab.mp4
```

数据库应对最终实际 `file_name` 建立唯一约束。

### 文件名安全

来自设备的原始文件名只使用 basename（文件名部分）和 stem（去扩展名后的文件名）。

plan/action 名称参与文件名时进行安全化：

- 禁止路径分隔符；
- 禁止 NUL；
- 处理控制字符和非法文件系统字符；
- 尽量保留中文等人类可读字符。

### 报告负责机器映射

状态报告包含：

```text
delivery_id
output_id
file_name
source_action_instance_id
size
sha256
delivery 状态
```

客户端根据报告中的**完整 `file_name` 精确匹配**收到的文件。

## 普通产物传输失败与重新取回

主程序完成本地发送不证明客户端收到，交接事实由[文件交接](file-handoff.md)定义。

对于照片、视频、MCU 数据等普通产物：

> 不自动重传。

客户端如果未收到或完整性校验失败：

1. 根据已经掌握的 `output_id`；
2. 使用新的 `request_id`；
3. 再提交 `obtain_action_outputs`。

只要正式源产物仍然可用，即可重新产生新的独立 delivery。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

产物投影提供本专题定义的稳定身份、来源、可用性、派生关系和清理状态。交付投影提供 `delivery_id`、`output_id`、来源 obtain 动作、历史唯一的实际 `file_name` 及交付状态。登记、发布、撤回和清理等变化均追加历史并同步更新投影，遵守[持久化与配置基础](../2026-09-08-camctl-cli-design.md#持久化与配置基础)。

文件位置与业务记录之间的对账引用[文件交接](file-handoff.md)。历史回放不能执行取回、发布、撤回或源文件删除；历史中的删除意图与已确认删除结果保持区分。数据库保留产物历史不意味着已清理的产物文件仍然可用。

相机视频拷贝还需保存来源与未完成文件的关联，以及已经可靠保存的拷贝进度，供后续会话续传。历史回放恢复这些事实，实际读取设备文件由取得执行资格的处理流程完成。

## 验收要求

### 单元测试

隔离产物目录、设备文件和交付存储协作者，验证产物选择、部分成功、发布屏障、文件名规则、清理限制、取消及重取身份。

### 集成测试

验证真实数据库的交付名称唯一性、取回资格与删除意图的并发处理；组合真实文件交接验证源产物与独立 delivery 的生命周期，以及删除或取消后恢复。

针对相机视频取回及内部修复所需的拷贝，使用已经写完、内容和长度固定的源文件，验证中断后跨进程恢复能够复用已可靠保留的部分，保持来源关联及原完整长度；同一次取回的恢复不新建交付身份。真实设备适配须验证文件写入完成的确认依据、身份与长度读取及从指定位置继续读取；目标存储环境须验证断电后部分文件与进度记录的恢复。具体中断位置和异常状态的验收矩阵随续传契约补齐。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 正式产物

- `output_id` 稳定；
- 原片和修复产物独立；
- 清理不级联。

#### 产物取回

- 默认选择全部正式产物；
- 精确选择 `output_ids`；
- 部分失败仍交付成功项；
- 全部条目结束后才开始发布；
- 文件逐个发布；
- 每个新请求产生独立 delivery；
- 相机视频拷贝支持跨主机重启的断点续传；
- 取消撤回 ready；
- processing 不可撤回。

#### delivery 文件名

- 人类可读名称；
- 中文保留；
- 安全化；
- 历史唯一；
- 名称冲突时追加交付 ID 的短标识；
- 撤回后名称也不复用。

#### 产物清理

- 已获得资格的取回优先；
- 新取回被阻止；
- 删除部分失败仍禁止新取回；
- 未开始删除前允许取消并恢复；
- 已开始删除后取消不恢复。

## 待确认与待细化

本节不构成已确认的行为选择。涉及其结果的实现须先补齐契约。

### U2. `obtain_action_outputs` 部分成功时的动作整体终态

已经确认：

- 成功项必须交付；
- 失败项逐项报告；
- 不扣留成功项。

但动作整体最终采用：

```text
failed
```

还是引入其他整体表达，目前尚未由需求方最终确认。

逐产物结果应当始终是权威信息。

### U5. 普通正式产物的长期保留策略

已经明确：

> 异常录像原片一直保留到客户端显式清理。

其他类型正式产物是否全部采用同样的无限期显式清理策略，尚未单独确认。

### 后续契约完善

明确动作/group/精确 ID 选择的集合固定时点，缺失引用、空集合和不可用产物的结果。定义旧取回资格的授予时点、多个删除意图的组合、删除取消与重启恢复表。补齐产物可用性状态及哈希尚未取得时的表达、文件名长度与碰撞处理。

断点续传需补齐源文件写入完成的确认依据、来源身份与完整长度的记录方式、设备按位置读取能力、进度与文件落盘顺序，以及部分文件不存在、长度与进度不一致、读取失败、取消和清理期间的处理。设备协议尚未核实；必须满足已确认的跨重启续传要求后才能验收相关拷贝流程。
