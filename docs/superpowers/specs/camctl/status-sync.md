# 客户端状态同步

[返回设计总览](../2026-09-08-camctl-cli-design.md) · [状态报告与累计确认](status-reports.md) · [执行计划输入契约](plan-input.md) · [阅读路线](reading-guide.md)

用户恢复了客户端的旧备份后，页面上的记录可能落后于主机。例如，旧备份只记得第一天的录像 A，主机却已经完成第二天的录像 B，还按后续计划清理了 A 的相机原片。客户端需要重新取得这些状态，才能正确展示已经发生的事。

camctl 提供两种补齐方式：保留可靠的历史状态时，可以从指定报告之后补齐；没有可靠基础时，可以重新取得完整状态。两种方式都通过执行计划请求，使用现有报告 JSON、文件交接和 ACK（客户端接收确认）。第一版面向单台主机和一个逻辑客户端。

本页先说明用户怎样选择和请求同步，再说明报告包含什么、怎样确认完成，最后介绍数据库需要保存的信息。包含录像、取回和清理的完整操作过程及 JSON 见[从旧备份补齐录像与交付状态](examples/status-sync/README.md)。

## 先看一次需要补齐的实际情况

客户端与主机上的 camctl 通过文件交换信息。用户把计划交给传输部门，之后再把收到的报告导入网页；camctl 不能直接查看个人电脑上的数据库，也不知道用户是否恢复过备份。

正常情况下，camctl 根据已经收到的确认，省略客户端已经保存的旧变化。例如，第一天的录像 A 没有再发生变化，第二天的报告就可以只提供录像 B 的新状态。客户端把两份报告合并起来，页面上仍能同时看到 A 和 B。

每份报告有两个需要区分的数字：`report_id` 标识是哪一份报告；`to_wm` 说明这份报告采用的业务记录到哪里为止。后者称为业务水位。一项录像会经历开始、停止、产物登记等多次变化，所以报告 1 完全可以记录到业务变化 20。下面这些编号都有对应的[逐项业务事实](examples/status-sync/history.md)。

| 发生的事情 | 客户端与主机分别知道什么 |
| --- | --- |
| 第一天完成录像和取回 A，客户端保存报告 1，并留下备份 | 报告 1 完整覆盖到变化 20；备份知道 A 已拍摄、已取回，原片还在相机中 |
| 第二天完成录像和取回 B，客户端保存报告 2 | 报告 2 从变化 20 之后补充到 40；客户端合并后知道 A 和 B |
| 用户提交清理 A 的计划，同时确认报告 2 | 主机记住客户端已经保存到 40；清理后，报告 3 只需提供 40 之后、截至 45 的变化 |
| 客户端恢复到第一天的备份，再导入报告 3 | 本地只有截至 20 的状态，却收到从 40 之后开始的报告；第二天关于 B 的记录缺了一段 |

这时，报告 3 虽然能说明 A 已清理，却不能补出缺失的 B。客户端应保留最后一次可用状态，提示历史缺失，并请求从报告 1 的终点 20 之后重新补齐。补齐报告会把 B 的记录、A 的清理结果和相关计划一起交回来。

主机不能仅凭一个较旧的确认就猜测客户端丢了状态，因为旧计划也可能只是晚到。客户端因此需要明确提出同步请求；主机据此在原有自动报告机制中增加本次需要补齐的内容。

## 客户端选择同步范围

选择起点前，客户端需要知道自己已经完整保存到哪里。这里的“完整保存”包括校验报告、合并其中的状态，并成功保存合并结果；仅有一个报告文件或记住一个较大的报告编号，还不足以作为起点。

| 客户端现有的状态 | 怎样请求 |
| --- | --- |
| 已完整保存截至某份报告终点的状态 | 可以提供这份报告的 ID，请求补齐其后的变化 |
| 没有完整状态，或不能可靠确定它对应哪份报告 | 请求完整同步 |
| 新收到的报告与已有状态之间有缺口 | 使用最后一次可靠保存的状态作为基础；这份接不上的报告不能作为同步起点或 ACK |
| 局部同步失败，原因是 `sync_report_not_found` | 保留最后有效状态和错误信息，核对起点；需要恢复时另建完整同步请求 |

“局部”按历史范围划分。例如，从第一天的报告之后补齐，就要包含第二天录像 B 和后来清理 A 等相关变化，不能只选择某个计划、动作或视频。报告编号不连续，或者某份报告没有出现某个请求，本身都不说明状态有缺口；是否缺少历史要根据报告实际覆盖的范围判断。

同步动作可以单独组成一份新计划，也可以加入下一份需要提交的新业务计划，再按正常人工流程递交给传输部门。

## 请求入口

通过 `report_status` 动作请求报告。它的 `params` 只接受下表列出的组合，输入值保持原 JSON 类型，不自动转换或补齐。

| 输入 | 含义 |
| --- | --- |
| 省略 `params`，或提供 `{}` | 按当前需要报告的内容处理；不额外发起一次同步 |
| `{"scope":"full"}` | 请求完整同步，报告从最初的业务记录开始覆盖 |
| `{"scope":"since","after_report_id":N}` | 请求从报告 N 的终点之后补齐；camctl 在数据库中查询该报告的 `to_wm` 作为起点 |
| 其他结构或字段组合 | 仅该报告动作在受理时记为 `failed`，保留原输入和错误原因，不开始同步 |

`after_report_id` 须符合[报告编号的正整数范围](status-reports.md#报告编号与水位的数值范围)。各字段必须一起满足所选组合：

- `scope: "since"` 必须提供 `after_report_id`；不能只提供报告 ID 而省略 `scope`。
- 完整同步和普通报告不接受 `after_report_id`。提供 `scope` 时，只接受表中的字符串值。
- `after_report_id` 为 `null`、布尔值、数字字符串、0 或超出范围的数字，以及额外字段、其他 `scope` 值和非对象 `params`，均属于参数错误。

本表只定义 `report_status.params`。动作公共字段及错误处理遵守[第一版动作入口](plan-input.md#第一版动作入口)与[校验顺序](plan-input.md#校验顺序与错误优先级)，整份计划的拒绝条件仍优先处理。

### 同步请求与累计确认

一份计划中可能同时出现两个报告 ID，它们表达不同的事情：

| 字段 | 客户端表达的意思 |
| --- | --- |
| 计划顶层的 `last_report_id` | 我已经完整保存到这份报告所覆盖的位置 |
| 同步动作参数中的 `after_report_id` | 请从这份报告的终点之后，再给我补齐状态 |

例如，主机此前收到报告 2 的确认，知道客户端已经保存到业务变化 40。客户端后来恢复旧备份，只保留报告 1 对应的状态，也就是业务变化 20。新输入可以同时填写 `last_report_id: 1` 和 `after_report_id: 1`：

- 旧确认不会让主机从 40 回退到 20。
- 同步动作另外要求补齐 20 之后的状态。

两个字段可以相同、不同，也可以只提供同步起点而不提供 ACK。`after_report_id` 本身不是确认，不清零或降低主机保存的确认位置。

较旧的 ACK 也可能来自延迟送达的计划或原请求重送，所以它不能自动触发同步。需要重新补齐时，必须用新请求中的同步动作表达。修改已经受理的同一 `request_id` 的正文，仍然不会增加或改变原动作。

## camctl 何时开始同步

“计划已经交给 camctl”和“同步已经开始”是两个步骤。例如，主程序先通过 `submit` 交入一份计划，这只会把输入和受理结果保存到数据库。之后 `run` 调度到其中的同步动作，才开始按这次要求补齐。

计划受理时，只检查参数格式和字段组合，不查询起点报告是否存在。`submit` 只负责受理，因此执行 `submit` 不会立即改变报告范围。同步动作实际开始以前，报告继续按此前已有的要求处理。

同步动作取得执行资格后，camctl 才查询报告记录、确定从哪里补齐，并保存本次同步要求。这里不访问相机，也不读取以前交付的报告文件。

camctl 为每份报告保存了编号、覆盖范围、采用的历史记录范围等信息。比如报告 1 的记录会说明它覆盖到变化 20。即使原文件已经传走，这些信息仍保留在数据库中，可以用于查找同步起点和重新生成报告。

| 动作实际执行时的情况 | 处理结果 |
| --- | --- |
| 普通报告更新 | 动作进入运行，处理当前应报告的内容，不另外保存一项新的同步要求 |
| 完整同步 | 将本次起点保存为 0，开始从最初的业务记录补齐 |
| 局部同步，找到报告记录，且其中的信息完整可读 | 将该报告的 `to_wm` 保存为本次起点，开始补齐 |
| 局部同步，查询成功并确认没有这份报告的记录 | 仅该动作运行失败，不开始同步，也不自动改成完整同步 |
| 查询或保存失败、已有记录缺失必要信息或相互矛盾、提交结果无法确认 | 按状态库会话错误处理；恢复时先查明实际保存了什么，不能把这些情况说成“报告不存在”或“同步已开始” |

报告文件可能还在 `staging`、`ready`、`processing`，也可能已经删除，甚至尚未发布。只要数据库里的报告记录及必要生成信息可以可靠读取，camctl 就能确定它的终点。客户端是否已经完整保存相应状态，仍由客户端负责判断。

例如，报告 1 的文件早已被主程序传走并从主机删除，数据库仍记得它的终点是 20。客户端请求 `after_report_id: 1` 时，camctl 直接使用这条记录，不需要找回原报告文件。

确认起点报告不存在时，错误为 `code: "sync_report_not_found"`、`stage: "execution"`，`details` 为 `{"after_report_id":N}`。动作保留开始和失败记录，`execution.started` 为 true，没有成功的 `result.report_id`。之后即使出现这个报告编号，也不重新执行已经失败的动作；再次同步需要新请求。

为了在重启后继续处理，camctl 会记住“这次同步从哪里开始，以及是否还需要等待确认”。本页将这项尚需完成的工作称为**同步责任**：报告动作可以先完成本地工作，但这项责任通常要等客户端确认后才结束。其保存方式见[数据库需要保存哪些信息](#数据库需要保存哪些信息)。

## 报告范围

一份报告既要补齐本次请求的状态，也要包含普通报告中仍未确认的变化。有多项同步尚未结束时，报告还需要同时满足它们。因此，实际报告可以从请求起点之前开始。

以录像样例为例：主机已收到截至变化 40 的确认，客户端却请求从变化 20 之后补齐。新报告就从 20 之后开始。反过来，如果主机只收到截至 20 的确认，而某次同步要求从 40 之后开始，新报告仍要覆盖 20 之后的内容，否则会漏掉普通报告尚需交付的状态。

### 报告怎样选择和表达状态

报告提供的是各对象在本次截止位置的状态。例如，区间内发生过“录像 B 完成”和“清理 A”，报告就给出 B 的录像、产物与交付状态，以及 A 已清理的状态。它不逐条输出所有历史事件，也不重新执行录像、取回或删除。

对于每个需要更新的对象，报告完整提供它自身的信息，例如动作的名称、状态和执行结果，并携带所属计划、动作等必要关联。其他没有变化的子成员可以不出现，客户端继续保留已有记录。例如，同步报告更新了 A 的原片清理状态，但未再次列出 A 的取回动作，客户端仍须保留原来的取回和交付。

完整同步覆盖全部已保存的业务对象，包括已经结束的动作和已经清理的产物；有历史记录不表示文件仍然存在。局部同步可以省略区间内没有变化的历史对象，由客户端已保存的基础补全。两种同步都不重新交付视频。

### 实现时的范围计算

业务变化按顺序编号，某个编号表示“业务状态已经记录到这里”；协议中称为业务水位。计算报告范围时，使用以下值：

| 符号 | 含义 |
| --- | --- |
| `A` | 主机已经保存的客户端累计确认位置 |
| `S₁…Sₙ` | 各项尚未结束的同步要求从哪里开始补齐；完整同步的起点为 0 |
| `H` | 本份报告所采用的最后一条业务变化编号，对应 `to_wm` |
| `F` | 本份报告从哪里之后开始覆盖，对应 `from_wm` |

```text
没有尚未结束的同步：F = A
还有尚未结束的同步：F = min(A, S₁, …, Sₙ)
报告覆盖：(F, H]
```

`(F,H]` 表示大于 `F`、不超过 `H` 的业务变化。各情况完整列在下表中：

| 尚未结束的同步 | 新报告从哪里之后开始 | 原因 |
| --- | --- | --- |
| 没有 | `A` | 报告普通未确认内容 |
| 至少有一次完整同步 | 0 | 需要全部状态，同时也能覆盖其他同步要求 |
| 只有局部同步，最早起点小于 `A` | 最早起点 | 既补齐该起点之后的状态，也覆盖普通未确认内容 |
| 只有局部同步，所有起点都大于或等于 `A` | `A` | 普通未确认内容仍需报告 |

例如，`A=8`，两次局部同步的起点分别为 1 和 5，报告从 1 之后开始；若随后再开始一次完整同步，报告从 0 开始。若 `A=1`、局部同步起点为 8，报告仍从 1 之后开始。

**一份报告里的所有信息必须来自同一份历史状态。** camctl 先确定使用哪些已经保存的数据库记录，再据此读取 `A`、各个同步起点、`H`，以及计划、动作等对象的状态。不能先取旧的报告范围，又把后来变化的对象状态混进来。

在上述例子中，报告 2 表达的是截至变化 40 的状态。即使后来相机原片 A 已清理，camctl 再次生成报告 2 的文件时，也要保留原内容。A 的清理结果属于之后的报告，不能补进同一个报告 ID 的旧文件。

确定使用哪些记录时，以一次完整的数据库提交结束处为准。若计划及其动作在同一次提交中保存，报告不能只看到其中一部分。报告两端对应的业务水位都须满足这一要求，且 `0 <= F <= H`。同一份报告一旦保存了范围和生成信息，后来的业务变化、ACK 或同步变化都不改写它。

## 报告动作什么时候算成功

状态恢复要经过两个不同地点：camctl 在主机上准备并交出报告，客户端在个人电脑上接收、合并并保存它。中间还要经过第三方传输，可能要等下一次传输窗口。因此，报告动作的执行结果与客户端是否已经补齐，需要分别表达。

`report_status` 完成本次应做的本地报告处理后，以 `succeeded` 结束。报告需要按[发布规则](report-publication.md)交给主程序，并保存所需记录；若交接目录中已有满足本次要求的报告，可以按后文的规则使用它。

对一次新开始的同步，所用报告需要满足两点：

1. 覆盖本次要求补齐的起点之后的状态。
2. 报告依据的数据库记录已经包含本次同步开始的那次保存。

第二点保证报告反映的状态足够新。沿用上面的录像过程，客户端今天请求补齐时，几份报告的作用不同：

| 使用哪份报告 | 能否完成这次同步的本地报告工作 |
| --- | --- |
| 第一天的报告 1 | 不能。它只知道 A，还没有第二天的 B 和后来的清理结果 |
| 第二天的报告 2 | 不能。它能补充 B，但还不知道 A 已清理，更早于今天这次同步开始 |
| 本次同步开始后采用新状态生成的报告 4 | 可以。它覆盖从 20 之后需要补齐的状态，采用的记录也已包含这次同步开始 |

今天重新生成报告 1 或 2 的文件，并不会让它们包含今天的新状态。这里检查的是报告内容来自哪些数据库记录，而不是文件显示的生成时间。

成功结果中的 `result.report_id` 指向完成这次本地工作的报告。报告先发布，动作随后才能保存成功；下一份报告才会表达这个成功结果。因此，包含动作成功结果的报告可以比 `result.report_id` 更新。

例如，报告 4 已交给主程序时，同步动作保存成功，结果指向报告 4。随后生成的报告 5 可以告诉客户端“这次报告动作已成功”。用户先收到报告 5 也没有问题：它已经覆盖所需状态，不必先找到报告 4 才能合并。

本地成功不等待客户端收到文件或发送 ACK。camctl 仍保存尚未结束的同步责任，在后续报告机会继续处理；`run` 不为等待远端确认一直运行。完成本次本地工作后，也不因主程序随后领取或删除文件而在同一收尾循环中反复补投。

## ACK 如何结束同步

主机把报告交出去后，并不知道用户是否已经在网页里导入并保存。ACK 用来补上这一步证据：客户端通过后续输入告诉 camctl，哪些状态已经可靠保存，可以停止为它们安排补报。

客户端校验、合并并可靠保存了报告之后，可以在后续计划中携带 `last_report_id`。camctl 收到这份确认时，分别处理两件事：

- 根据所确认报告的 `to_wm` 更新累计确认位置，位置只前进、不后退。
- 检查这份报告是否满足某次尚未结束的同步；满足时，保存“这次同步已经确认完成”的结果。

### 什么样的报告可以确认本次同步

对一次起点为 `S` 的同步，ACK 指向的报告 `R` 必须同时满足：

1. 数据库里确实保存了这份报告，生成信息能够可靠读取。
2. `R.from_wm <= S`，没有漏掉本次要求的起始范围。
3. 报告依据的数据库记录已经包含本次同步开始的那次保存。

完整同步的 `S=0`，所以报告必须从 0 开始。局部同步可以由起点相同或更早的报告确认，也可以由满足条件的完整报告确认。

报告不必是最新的一份，也不必只服务于某一个同步动作。一份 ACK 可以结束它满足的所有同步责任。反之，同步开始之前的旧报告不能结束本次责任，即使范围足够广、编号曾被确认过，也要继续等待能够反映本次同步开始后状态的报告。

为什么还要检查报告是否早于本次同步？在录像例子中，清理 A 的旧计划带着 `last_report_id: 2`。传输部门如果后来重送这份计划，camctl 会再次看到 ACK 2。但它仍是对第二天报告的确认，不能证明客户端从旧备份恢复后，已经完成今天这次补齐。确认报告 5 则能够提供这次补齐所需的新证据。

以下两项分别检查，不能只根据报告编号大小或文件生成时间作判断：

| 报告依据的记录已包含本次同步开始 | `R.from_wm <= S` | 本次同步如何处理 |
| --- | --- | --- |
| 否 | 否 | 继续等待：报告既早于本次同步，也缺少所需范围 |
| 否 | 是 | 继续等待：范围足够，但反映的仍是同步开始前的状态 |
| 是 | 否 | 继续等待：状态足够新，但起点过晚 |
| 是 | 是 | 结束本次同步责任，保存它与该 ACK 的关联 |

### 确认位置与同步结束怎样一起保存

对合法且记录可靠的 ACK，累计位置始终更新为 `max(A, R.to_wm)`。即使该值比当前位置更旧或相同，也要继续按上表检查同步是否可以结束；确认位置没有前进，不等于这份确认没有作用。

在正常操作中，用户补齐后决定清理相机原片 B，可以在清理计划里顺便填写 `last_report_id: 5`。主机查询报告 5 的终点 48，保存新的确认位置，并结束这次同步。用户无需仅为这次确认再单独递交一份文件。

| ACK 的检查或保存结果 | 处理 |
| --- | --- |
| 引用合法，报告记录可靠存在 | 在同一次输入处理的数据库事务中，更新累计位置并结束它满足的同步；其他同步继续保留 |
| 字段非法，或可靠查询后确认报告不存在 | 保持原累计位置和同步责任，保存 ACK 校验错误；合法计划仍可受理或复用 |
| 查询、更新或提交失败，或不能确认结果 | 按会话错误处理，不能宣称累计位置或同步结果已经保存 |

确认位置与同步结束结果必须一起保存。这两类管理变化本身不增加业务水位，也不触发一份用于确认 ACK 的报告。之后发生的业务变化仍须按普通规则报告。

客户端不能仅凭同步动作成功或文件已导入就发送确认；必须已经合并并可靠保存报告覆盖的完整状态。合并时使用报告实际的 `from_wm`、`to_wm`，允许报告比请求起点覆盖得更早；输入中的 `after_report_id` 也不能代替收到报告后的 ACK。

## 取消与失败

如果同步动作约定稍后执行，用户在执行前取消了它，就不再按这次请求补齐。若报告已经交出、动作已经成功，后来对该计划发起取消，也不会把这次成功改成取消；主机仍需要客户端的确认，才能知道补齐结果已经收到。

取消是否结束同步责任，取决于它发生时，报告动作执行到了哪一步：

| 情况 | 同步责任如何处理 |
| --- | --- |
| 参数在受理时失败，或执行时确认起点报告不存在 | 没有开始这次同步，也没有需要继续等待的责任 |
| 报告动作尚未执行就被取消 | 不开始这次同步 |
| 已保存同步要求，报告动作尚未进入终态时被取消 | 在取消处理中结束该动作对应的同步责任，并保留历史；其他同步不受影响 |
| 报告动作已经成功，后来取消其计划或该动作 | 保持原成功结果；尚未得到确认的同步责任继续等待合格 ACK |
| 会话出错、断电、报告生成或发布尚未完成 | 保留已经成功保存的同步要求；恢复时核实记录和发布结果，再继续处理 |
| 同一请求重送，或同一动作重试、恢复 | 沿用原记录，不重新开始一项同步 |

取消与成功哪个先发生，以数据库实际提交的先后为准。取消不改写已有报告文件，`processing` 中的文件继续由主程序处理；取消动作自己的完成时机遵守[取消规则](task-cancellation.md#取消动作的完成时机)。

## 已有报告怎样处理

主机上可能还留着待传报告，也可能已经把文件传走并删除，却尚未收到客户端确认。例如，报告 5 已经传出，用户还没有提交后续清理计划，camctl 仍需记住这次同步没有确认结束。下次出现报告机会时，再根据文件和数据库记录决定是否需要重发。

需要报告时，camctl 先检查已有报告是否足够：它必须覆盖当前普通未确认内容和所有尚未结束的同步，并且所采用的数据库记录已包含这些同步各自的开始记录。

| 已有文件和数据库记录的情况 | 处理 |
| --- | --- |
| `ready` 或 `processing` 中已有一份报告，满足本次全部要求 | 保留它，不再排入相同副本 |
| 交接目录没有可用报告，但以前保存的一份报告仍满足本次全部要求 | 根据该报告保存的生成信息重新生成文件，保持原 ID、字节、摘要和文件名 |
| 已有报告起点过晚、截止位置太早，或依据的记录还没有包含新同步的开始 | 根据新的完整数据库状态创建报告，分配新 ID；不能扩大原报告内容并继续使用旧 ID |
| 目录、报告记录或生成信息读取失败，或结果未知 | 按会话错误处理，不能当作文件不存在或本次工作已经完成 |

如果几份旧报告各自只覆盖一部分，camctl 不能假定客户端一定会收齐它们，从而省略本次需要的完整补齐。第一版使用一份能满足当前全部要求的报告完成本次发布；其他已进入 `processing` 的文件保持不动。

`ready` 中至多保留一份待领取状态报告，替换过程遵守[报告发布](report-publication.md#ready-中至多一个待领取状态报告)。新报告必须满足当前仍需交付的范围和各次同步要求；不能用内容较少的普通报告替换掉仍用于补齐的报告。

只要还有一次完整同步未结束，新报告就从 0 开始；只有局部同步时，按[报告范围](#报告范围)中最早需要覆盖的位置计算。部分同步结束后重新计算范围，全部结束后恢复普通增量。已有的较宽范围报告仍可继续交付，不必只为了缩小范围重新生成；确需替换时，新报告仍须覆盖全部尚需报告的内容。

重启后，camctl 读取已经保存的同步起点、开始记录、结束结果，以及报告生成和本地发布记录，再决定保留、重建或新建报告。动作已经成功、文件已经消失、累计确认位置较大，都不能单独说明同步已获确认。

报告重发仍只在既定的报告机会进行。主程序是否再次处理残留在 `processing` 的文件仍然未知，camctl 不据此承诺客户端一定收到，也不把主程序领取当作客户端确认。

## 数据库需要保存哪些信息

用户不需要填写以下信息。它们用于让 camctl 在重启后记住原来的同步要求，以及判断客户端确认的报告是否足够。

例如，这次要求从 20 之后补齐，而主机的累计确认早已是 40。如果断电重启后只读取累计确认，就会遗漏本次要求补齐的 20～40。camctl 必须另行保存起点 20，并记住这次要求何时在数据库中开始生效、是否已经结束。

每项同步责任关联发起它的 `action_instance_id`，保存以下信息及后续结束记录：

| 保存内容 | 用途 |
| --- | --- |
| 原请求的 `scope`；局部同步还保存 `after_report_id` | 记住用户请求的是完整同步还是从哪份报告之后补齐 |
| 确定后的起点 `S` | 完整同步为 0；局部同步为起点报告记录中的 `to_wm`；以后恢复仍使用同一个起点 |
| 本次同步开始的记录 `B` | 记住“动作进入运行、确定起点、保存同步要求”这次提交在完整数据库历史中的位置，用于判断某份报告是否已经采用了包含它的记录 |
| 是否尚未结束，以及结束原因和关联 | 记住是继续等待，还是已经因合格 ACK 或适用的取消结束；保留关联的确认或取消记录 |

动作开始、起点确定和同步要求必须在同一次短数据库事务中保存；局部同步对起点报告的查询也在这个事务内完成。事务使这些变化一起生效，不能只保存其中一部分。`B` 表示这次完整提交结束后的位置，既不是同步起点，也不是主机时钟时间。

数据库历史还包括 ACK 和报告管理等记录，因此完整历史顺序与业务变化编号是两套不同的序列，不能直接把 `B` 当作业务水位。比较报告与本次同步的先后时，要检查报告采用的历史记录是否包含这次完整提交。

例如，保存一次有效 ACK 会增加数据库历史记录，但不会增加业务变化编号。仅比较业务水位的数字，不能代替对完整历史先后关系的检查。`B` 是本文用于解释这项内部记录的符号，不是客户端要填写的新字段。

同一动作的重试、断电恢复和同一请求重送，都沿用原起点、原 `B` 和同一责任；不能因为后来收到 ACK 就重新计算它的起点。另一个实际开始执行的同步动作保存独立记录，即使起点相同，也各自保留开始位置。原输入、起点和开始位置不改写，结束情况通过后续历史记录表达。

同步管理记录本身不增加 `change_seq`，动作注册、开始和结果变化仍照常增加业务变化。历史记录和用于查询当前状态的数据（投影）在同一事务中保存。根据历史重建状态时，只恢复这些记录，不新建同步请求，不执行设备操作，也不重新发布文件。

## 完整同步时先收到较早的报告

客户端丢失本地状态，主机以前已经收到截至业务变化 100 的确认。客户端提交以下完整同步计划：

```json
{
  "request_id": "req-full-sync-001",
  "created_at": "2026-09-14 08:00:00",
  "name": "恢复客户端状态",
  "actions": [
    {
      "name": "请求完整状态",
      "type": "report_status",
      "params": {"scope": "full"}
    }
  ]
}
```

假定同步动作开始并保存同步要求后，业务已经记录到变化 110。主机随后陆续生成报告 41 和 42，分别覆盖到 150、160。以下只展示身份和范围字段，完整报告还包含业务状态：

```json
{"report_id":41,"from_wm":0,"to_wm":150}
```

```json
{"report_id":42,"from_wm":0,"to_wm":160}
```

两份报告采用的数据库记录都已包含这次同步开始。客户端先收到报告 41，完整合并并可靠保存后，就可以确认它。例如，重送原请求并附带 ACK：

```json
{
  "request_id": "req-full-sync-001",
  "created_at": "2026-09-14 08:00:00",
  "name": "恢复客户端状态",
  "last_report_id": 41,
  "actions": [
    {
      "name": "请求完整状态",
      "type": "report_status",
      "params": {"scope": "full"}
    }
  ]
}
```

这次输入继续对应原计划和动作，不重新开始同步。camctl 查询报告 41 的终点 150，将累计确认位置推进到 150；这份报告也满足本次完整同步要求，因此同步责任结束，不必等客户端收到报告 42。

报告 42 仍可继续交付。若它已不在本地交接目录、客户端也未收到，下一次报告机会就覆盖 `(150, 最新业务水位]`。没有更多变化时，范围是 `(150,160]`；若又有新变化，截止位置相应向后延伸。客户端已经有截至 150 的完整基础，可以继续合并这些增量。

报告 ID 与业务水位要分别理解。如果另一份已登记报告是 `report_id: 150`、`to_wm: 160`，填写 `last_report_id: 150` 确认的就是业务水位 160。

## 验收要求

### 输入、起点与请求身份

验证普通报告的参数省略和空对象、完整同步、合法局部同步，以及请求结构表之外的所有组合。对 `after_report_id` 覆盖缺省、null、布尔值、数字字符串、0、安全整数的最大合法值和越界值。动作自身错误只使本动作初始失败，整份拒绝条件优先，有效的顶层 ACK 仍独立处理。

分别通过 `run <plan-path>` 与 `submit <plan-path>` 受理，确认受理时不查起点报告是否存在，也不提前改变同步范围。执行时分别验证报告存在、可靠确认不存在、读取失败和已有生成信息无效；只有确认不存在才产生对应动作失败，数据库错误按会话错误处理。旧报告文件已经删除或尚未发布，都不影响读取可靠的报告记录。

### 报告范围与确认

按范围表验证没有同步、只有局部同步、存在完整同步、多个不同起点，以及 `A` 小于、等于、大于最早起点。确认报告覆盖普通未确认内容及所有同步要求；范围和全部对象状态取自同一份已完整提交的历史，所属计划和动作补齐、未出现子成员保留均符合报告契约。

将“报告依据的记录是否已包含本次同步开始”“起点覆盖是否足够”四种组合，与 ACK 终点小于、等于、大于当前 `A` 的三种情况组合验证。包含较早但满足要求的报告、较新但起点过晚的报告、同步开始前的旧报告、用完整报告确认局部同步，以及一份 ACK 只结束部分同步的情况。较旧或相同 ACK 仍须检查同步是否结束，其他同步和更晚变化继续保留。

### 取消、发布与重启恢复

验证同步尚未开始、已经开始但尚未确认、因合格 ACK 结束、运行中取消及成功后取消。对同一请求重送、同一动作恢复和同起点的新动作，确认前两者沿用原记录，新动作保存自己的开始记录。完成新同步的本地工作须使用包含本次开始记录的报告；之后不等待远端 ACK，也不在同次 `run` 中无限补投。

组合真实 SQLite、报告文件交接和客户端合并，分别在计划受理、同步开始保存、报告生成信息保存、文件发布、动作成功和 ACK 提交前后中断。检查一次事务中的记录完整可见、历史重建没有外部操作、同步起点保持原值、同一报告重建后字节不变，以及无法确认结果时保留诊断。目录确实存在、确认文件缺失、目录读取失败分别处理。

验证旧报告范围足够但所用记录早于本次同步、报告截止位置太早、多份旧报告各自只满足部分要求、`processing` 残留，以及部分同步结束后缩小后续范围。替换后的报告仍须满足当前全部要求，较宽旧报告可以继续交付，新范围使用新 ID；主程序领取文件不能代替客户端确认。

使用[实际业务同步样例](examples/status-sync/README.md)验证旧备份恢复、旧 ACK 不回退、局部报告合并和后续普通增量。文档与 JSON 校验仅验证规格表达，不能代替真实程序组合测试和设备联调。
