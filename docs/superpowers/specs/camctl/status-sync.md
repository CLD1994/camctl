# 客户端完整状态同步

[返回设计总览](../2026-09-08-camctl-cli-design.md) · [状态报告与累计确认](status-reports.md) · [执行计划输入契约](plan-input.md)

第一版面向单台主机与一个逻辑客户端。camctl 保存该客户端的累计 ACK 水位，并在既有报告机会中自动生成和补投报告。客户端首次取得已有主机的状态，或本地状态丢失后，通过本专题的入口请求完整同步；日常接收仍使用现有自动报告机制。

## 请求入口

`report_status` 的 `params` 可省略或为空对象，表示按当前报告责任执行一次本地报告更新；可填写 `scope: "full"` 请求完整同步。

| 输入 | 受理与执行含义 |
| --- | --- |
| `params` 省略或为 `{}` | 使用当前报告规则；若已经存在待确认的完整同步责任，本次报告也须满足它 |
| `params` 为 `{"scope":"full"}` | 执行时登记本动作的完整同步责任，并履行本次本地报告职责 |
| `params` 非对象、`scope` 非字符串或不是 `full`、含其他参数 | 该报告动作初始 `failed`，不登记完整同步责任；其他动作继续受理 |

`device_id` 须省略，`policy` 可省略或为空对象；`scheduled_at` 可省略，显式提供时遵守既有调度资格。`submit` 只受理，不执行报告动作，也不提前改变当前报告范围。当前入口不接受客户端任意指定历史区间。

完整同步不清零或降低主机保存的累计 ACK。客户端已经丢失本地状态时，不再提交未经本地完整状态支持的旧 ACK；正常通过新请求 ID 发起恢复即可。

## 完整同步责任

报告动作实际开始执行时，先在数据库事务中登记由该 `action_instance_id` 发起的完整同步责任，并保存其登记所在的完整历史边界，记作 `B`。该事务同时保存动作开始执行的业务事实，之后才生成相应报告。`B` 表示本次同步要求从何时开始生效，不是客户端请求的增量起点。

同一动作的重试、断电恢复和同一请求 ID 的重送复用原责任及 `B`。另一个实际执行的完整同步动作具有自己的责任；一份完整报告可以同时满足它覆盖的多个责任，不需要分别生成相同内容的报告。

责任的生效和确认属于报告管理历史，不单独推进 `change_seq`；动作注册、开始和结果变化仍按既有业务规则推进。所有历史及相应投影原子保存，报告重建仅消费这些事实，不重新发起同步。

### 报告范围

每次报告生成从同一冻结历史边界取得累计 ACK、当前有效责任和最新业务水位 `H`：

| 是否存在尚未结束的完整同步责任 | 报告覆盖范围 |
| --- | --- |
| 否 | `(累计 ACK 水位, H]` |
| 是 | `(0, H]` |

完整报告仍按[报告覆盖区间](status-reports.md#报告覆盖区间)选择实体，并输出它们在冻结上界处的完整自身字段。数据库中的计划、动作、正式产物、交付、计划文件诊断等已登记业务实体都包含在完整覆盖中，包括已经终态或已经清理的对象；它们的当前状态不等于对应文件仍存在。完整同步不输出全部历史事件，也不重放设备操作或重新交付视频。

请求尚未实际执行时，不改变报告范围。责任一旦登记，后续恢复、显式报告及会话收尾等实际报告机会均须考虑它；会话错误或主机断电不清除已提交的责任。

### 本地动作完成与远端确认

`report_status` 在本次要求的报告已经完成本地发布职责后，按既有规则结束为 `succeeded`，不等待客户端 ACK。此后尚未确认的完整同步由报告管理继续承担，不让 `run` 为远端接收而持续运行。

取消尚未执行的报告动作，不登记完整同步责任。取消仍未终态的报告动作时，结束该动作已登记的完整同步责任，保留历史；其他动作发起的责任不受影响。已经成功的报告动作保持终态，对该计划或动作的后续取消不撤销其待确认责任。已经产生的报告继续按目录所有权及当前报告责任管理，不通过取消修改 `processing` 中的文件。

单次报告职责完成后，主程序随后领取或删除文件，不使同一收尾循环无限补投。后续实际报告机会按下表决定是否需要完整报告：

| 完整同步责任 | 可用报告与业务变化 | 处理 |
| --- | --- | --- |
| 尚未结束 | `ready` 或 `processing` 中已有报告，能够覆盖当前所需状态及责任边界 | 不重复排队相同报告 |
| 尚未结束 | 本地无可承担该责任的报告，且原报告仍满足当前覆盖要求 | 按冻结依据重建原报告，复用 ID、字节和文件名 |
| 尚未结束 | 已有报告不能满足新业务变化或新的责任边界 | 生成新的 `(0, H]` 报告 |
| 已结束 | 还有普通未确认业务变化 | 按累计 ACK 继续普通报告与补投 |

`processing` 中报告是否被主程序再次传输仍属于既有外部保障边界；其存在不证明客户端收到。完整同步不改变该边界。

## ACK 如何结束完整同步

对于尚未结束、登记边界为 `B` 的责任，一份报告只有同时满足以下条件，才能通过其 ACK 结束这项责任：

- 报告已经登记，身份及冻结依据可以可靠查询；
- `from_wm = 0`，完整覆盖从初始状态到其上界的业务状态；
- 报告的冻结历史上界包含责任登记事务 `B`。

不要求该报告是最新生成的完整报告，不根据报告编号大小推测其覆盖范围。责任生效之前的旧完整报告不能满足本次请求；即使旧报告曾经覆盖当时全部状态，也不能据其 ACK 清除后来登记的责任。

`last_report_id` 仍用于查询报告记录，确认水位取该报告的 `to_wm`。设原累计 ACK 为 `A`，查到报告的上界为 `R.to_wm`，在同一次输入处理事务中更新为 `max(A, R.to_wm)`，并结束该报告满足的全部完整同步责任。报告确认的数值推进与责任结束分别判断：有效 ACK 数值相同或较旧时，也不能跳过责任资格检查。

| ACK 查询与覆盖结果 | 累计 ACK | 完整同步责任 |
| --- | --- | --- |
| 查到可靠报告，满足某项责任的全部条件 | 按 `to_wm` 单调推进或保持 | 结束满足条件的责任；其他责任保留 |
| 查到可靠报告，但不满足某项责任的条件 | 按 `to_wm` 单调推进或保持 | 该责任继续有效，不能仅因 ACK 变大而清除 |
| 字段非法或报告不存在 | 保持 | 保持，并按既有文件诊断规则报告 ACK 错误 |
| 查询、更新或提交失败，或结果未知 | 不宣称推进或保持已可靠完成 | 按会话错误处理，恢复后依据实际事务结果判断 |

ACK 与责任结束本身不新增业务报告责任，也不推进 `change_seq`。原报告之后的变化仍受普通累计 ACK 约束，不能随着完整同步责任结束被视为已经确认。

## 与报告替换和恢复的衔接

待确认责任存在时，`ready` 中待发布的新报告必须保持完整覆盖；普通增量报告不能替换掉仍需承担完整同步的报告。报告是否足以承担责任，要同时检查其覆盖区间和冻结历史边界，不能只看文件是否存在或编号是否更新。

责任全部结束后，`ready` 或 `processing` 中已有的较新完整报告仍可继续交付。确需更新 `ready` 报告时，新的增量报告须覆盖尚未被累计 ACK 确认的变化；已确认前缀可以不再重复。替换文件先在 `staging` 完整生成，再按既有流程发布；已登记报告内容保持不可变，`processing` 不修改。

登记责任、报告登记、文件发布、动作终态与 ACK 分别具有既有事务和文件交接边界。恢复先读取已提交历史，识别有效责任和已有报告，再决定生成、重建或保留；不把动作 `succeeded`、本地发布成功或文件消失当作完整同步已被客户端确认。

## 较早完整报告先被确认的推演

客户端丢失本地状态，主机原累计 ACK 为 100。客户端提交完整执行计划：

```json
{
  "request_id": "req-full-sync-001",
  "created_at": "2026-09-14 08:00:00",
  "name": "恢复客户端状态",
  "actions": [
    {
      "name": "请求完整状态",
      "type": "report_status",
      "params": {"scope": "full"}
    }
  ]
}
```

假定动作实际执行时登记责任的事务结束在业务水位 110，随后先后生成两份完整报告。以下仅展示各报告的身份和覆盖字段，不是完整报告文件：

```json
{"report_id":41,"from_wm":0,"to_wm":150}
```

```json
{"report_id":42,"from_wm":0,"to_wm":160}
```

两份报告的冻结历史边界均包含本次责任登记。客户端先收到并可靠保存报告 41，通过重送原请求携带 ACK：

```json
{
  "request_id": "req-full-sync-001",
  "created_at": "2026-09-14 08:00:00",
  "name": "恢复客户端状态",
  "last_report_id": 41,
  "actions": [
    {
      "name": "请求完整状态",
      "type": "report_status",
      "params": {"scope": "full"}
    }
  ]
}
```

原请求幂等复用，不重建动作或再次登记完整同步责任。报告 41 的 `to_wm` 为 150，因此累计 ACK 推进到 150，同时结束本次责任；不要求客户端等待报告 42。

报告 42 仍可继续交付。若它已经不在本地交接目录、客户端也未收到，则下一次报告机会覆盖 `(150, 最新业务水位]`。例如没有更多业务变化时，报告的覆盖为 `(150, 160]`；若有新变化，则相应扩展上界。客户端已经有截至 150 的完整基础，继续按既有规则合并后续报告。

反过来，如果查询到的是 `report_id = 150`、`to_wm = 160` 的报告，则输入 `last_report_id = 150` 确认的是水位 160。报告编号与业务水位分别解释。

## 验收要求

单元测试覆盖参数缺省、空对象、合法完整同步及非法字段；分别验证责任未生效、有效和已结束时的报告范围。报告的完整覆盖、冻结边界是否包含责任登记与 ACK 数值大于、等于、小于当前水位组合判定，验证较早但合格的完整报告可以完成同步，较新的不合格报告不能清除责任。多个责任按各自边界分别判断，不能用一个全局“最新完整报告 ID”代替。

覆盖同一请求重送、动作恢复、未执行取消、执行中取消与成功后取消，验证责任身份和有效范围。动作本地成功后责任仍可待确认，单纯等待 ACK 不使 `run` 保持运行；取消一项责任不结束其他责任。

集成测试组合真实 SQLite、报告文件交接和客户端状态合并，在责任登记、报告发布和 ACK 提交前后中断，验证事务原子性、原报告重建、客户端去重和原请求幂等。安排较新完整报告已经生成但较早完整报告先获 ACK，验证责任结束后缺口仍由普通自动报告承担；本地文件消失、较新报告仍在 `ready` 或 `processing`、以及恢复后才发现 ACK 已提交分别覆盖。
