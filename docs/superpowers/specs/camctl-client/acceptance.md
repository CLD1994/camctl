# MVP 验收

[客户端设计入口](README.md) · [职责与关键操作](architecture.md)

第一版客户端应通过本页六组验收场景，验证用户从部署、编辑和交接，到查看结果、发起后续请求及恢复数据的完整流程。验收依据是本目录已确定的行为和公共协议；各专题的决策表继续定义完整的状态分类。

文档与 JSON 检查只能证明规格产物相互一致。软件交付还需运行本页描述的实际操作和测试，才能说明流程可用；运行入口和软件验证范围见[客户端验证说明](../../../client-verification.md)。

## 准备配套资料

验收需要一个按既定目录部署的客户端、可用的测试能力说明，以及匹配执行计划身份的报告和视频资料。

| 资料 | 用途及要求 |
| --- | --- |
| 能力说明 | 包含第一版可用的录像动作及参数规则；没有真实设备时使用明确标注为演示的说明 |
| 执行计划与配套报告 | 报告中的请求、计划、动作和产物关联与相应输入一致，遵守[客户端协议样例](../camctl/client-protocol-examples.md)和公共 Schema |
| 可播放的测试视频及对应报告 | 报告给出该实际文件的完整名称、大小与 SHA-256；媒体内容与报告核验值必须匹配 |
| 局部同步报告样例 | 使用[状态同步业务演练](../camctl/examples/status-sync/README.md)及其中的历史编号，验证缺口、补齐、清理状态和累计确认 |

协议样例中的报告可以用于结构、身份及状态合并测试。验证真实视频导入时，应另行准备内容一致的测试视频与配套报告；不能把任意视频改成相同文件名后，宣称它应通过摘要核验。不同独立场景分别准备一致的初始数据，避免把彼此无关的样例身份混成同一套历史。

这些资料可以验证客户端处理规则。真实相机拍摄参数、实际厂商视频的播放兼容性及第三方传输对接，仍需按全局设计在设备和协作方可用时联调。

## 场景一：首次部署并准备录像计划

1. 在空数据目录部署并打开网页，确认提供“创建客户端数据”；点击后建立客户端数据并进入三个正常入口。
2. 在“设备说明”查看已启用的设备与参数规则。手工替换说明文件后重新加载，确认显示实际结果，并按公共规则更新可用能力。
3. 在“计划”的“草稿”中新建一份采集计划，添加录像动作和引用它的取回动作，使用测试设备已声明的参数类型。时间、名称和引用按公共协议填写。
4. 在内容尚未填写完整时等待保存，再重新打开草稿，确认恢复的是最新一次保存成功的未完成输入。修正后才允许导出。
5. 保存一份合法拍摄参数预设，应用后修改当前动作，确认预设与当前草稿独立；明确更新预设后，重开预设取得最新保存值，已经应用过它的其他草稿保留原值。

通过条件：三个入口可找到对应操作，草稿保存不丢失未完成输入，当前能力规则与预设行为符合约定，导出检查的是最新完整计划。

## 场景二：导出、交接与重送

1. 导出完成的采集草稿，取得包含固定 `request_id` 的计划 JSON。原请求可靠保存后，该项进入只读计划记录。
2. 再次下载同一记录，确认身份和正文保持，累计确认仅按有效覆盖独立处理。
3. 用户标记已递交，页面展示标记时间，并仍根据报告证据判断主机是否受理及执行。重复标记保持原时间；清除后显示未标记，再次标记记录新时间，原请求及主机结果保持各自事实。
4. 复制这份计划为新草稿并修改。再次导出形成新的请求身份，原计划仍保留自己的交接与执行事实。
5. 覆盖下载中断但原请求已经保存的情况：重新打开记录仍能取得同一请求。原请求尚未保存成功时，保留草稿与实际失败结果。

通过条件：不会因重复下载或页面未收到响应而制造新执行意图；复制产生独立的新请求；人工标记可更正，标记时间不冒充实际交付时间，清除不改变主机任务。

## 场景三：导入报告和视频，查看结果

分别验证视频先到、报告先到，以及同次混合选择的流程：

| 操作及阶段 | 预期结果 |
| --- | --- |
| 视频完整保存，报告尚未到达 | 文件保留并等待报告，用户原文件保留 |
| 报告成功应用，视频尚未到达 | 计划详情展示执行和交付事实，视频显示等待接收 |
| 文件与有效报告映射齐全 | 自动关联并比较大小、摘要，无需重新导入此前已保存的文件 |
| 核验通过且文件可读取 | 在对应计划详情提供播放与原文件下载 |
| 核验通过，但浏览器不能播放该编码 | 显示播放问题，仍可下载，保留已有核验与主机动作结果 |
| 重复导入相同报告或相同视频 | 依据原有接收和文件记录处理，不重复制造计划、交付或持久化视频副本 |

补充一份包含动作失败或取回部分成功的合法报告，确认计划已结束时仍能分别查看各动作结果、成功交付和失败原因。网页应正确表达“主机已发布文件”“本地文件已保存”“本地核验已通过”这几种不同事实。

检查每份已接受报告都保留原文件名与完整原始字节，摘要与原文件名匹配。重新导入同一报告时复用已有原文；导入新报告后，旧报告原文仍可作为输入依据，页面继续展示合并后的状态。

## 场景四：从结果准备下一份计划

在计划详情选择已有产物或动作，将再次取回、取消或源产物清理加入用户选定的草稿。检查引用由可靠对象身份填写，草稿原有内容保留；按需填写执行时间，再校验并导出。

来源状态由报告决定。仅在客户端加入动作或导出计划，不会使原动作变成已取消，也不会使产物变成已清理。新的取回按新请求产生独立交付；相机源产物清理与个人电脑保存的视频分别处理。

通过条件：新请求能够准确表达所选对象和操作意图，原计划与本地文件在收到相应证据前仍显示实际状态。后续报告到达后，按相同协议更新结果。

## 场景五：发现缺少历史并补齐

使用[录像 A/B 的完整历史](../camctl/examples/status-sync/history.md)，在独立的验收数据中执行：

1. 客户端已经完整保存到位置 20，导入报告 3 `(40,45]`。保留原状态、抛弃该报告并保存缺口诊断，页面提示需要补齐已知缺失的历史。
2. 重新导入报告 2 `(20,40]`，完整进度更新到 40，但历史缺失提示仍保留。
3. 再次导入报告 3，更新到 45，解除当前提示并保留此前诊断。
4. 从第 1 步的状态另行验证同步路径：点击“准备状态同步”，默认从可靠的报告 1 之后补齐；选择已有或新草稿后正常导出、递交。主动选择完整同步时，生成相应完整同步参数。
5. 按业务演练导入能衔接的补齐报告，验证录像 B、录像 A 的清理结果及相关状态正确合并，未出现的既有子成员仍保留。报告可靠保存后，下一份真实业务输入可以附带合格累计确认。

再验证同次选择报告 2 和报告 3 时，无论文件选择和上传完成的先后如何，都先应用能够衔接的内容；大视频的上传不阻塞报告结果展示。某份报告校验失败时，按实际剩余覆盖处理。

通过条件：缺口判断、同步参数与提示消除分别由正确依据决定。导出、人工递交、主机同步动作成功和视频接收均不能代替报告合并。

## 场景六：中断、文件不符与恢复

以下情况分别验证，不要求在同一次操作中人为叠加全部故障：

| 情况 | 预期结果及恢复方式 |
| --- | --- |
| 视频上传未完成时关闭网页 | 保留中断结果，重新选择后从头导入 |
| 完整视频正在核验时关闭网页，后端正常运行 | 核验继续，重新打开网页可查看实际结果 |
| 后端重启，完整视频尚未核验 | 根据保存记录和文件事实继续处理；可核验时从本地文件开头计算摘要 |
| 一批报告中部分已提交，后端随后中断 | 保留成功报告及覆盖，重新选择原批文件时仅继续尚未成功接受的内容 |
| 本份报告的原始内容保存失败 | 本份导入失败，不能部分保存成功接收、业务更新或确认；此前成功的报告保留 |
| 同名视频内容不同，已有报告证明新文件正确、旧文件错误 | 新文件完整保存并核验后替换，保留原失败诊断；其他组合按[重复视频规则](files-and-status.md#重复导入同名视频)处理 |
| 能力说明加载失败 | 按此前有无已启用说明分别展示；数据库正常时仍可导入报告和使用不依赖拍摄参数的功能 |
| 数据库或文件无法可靠读取 | 显示具体故障或无法确认，保留诊断及已有数据，按恢复规则处理 |
| 停止容器、复制完整数据目录并恢复 | 草稿、原请求、预设、交接记录、报告原文与进度、视频及关联随同恢复；旧备份需要的补齐按同步规则处理 |

通过条件：每种失败都保留实际已完成结果，未完成和未知不被显示为成功。完整分类见[数据保存与恢复](storage-and-recovery.md)及各操作决策表。

## 验证层次与交付判断

单元测试验证具有独立契约的局部行为，例如报告覆盖判定、同步起点选择、参数校验结果或文件开放条件，通过测试替身隔离真实数据库、文件和网络。

集成测试验证真实协作者组合，包括后端与 SQLite 的原子保存、文件保存和恢复、网页与后端交互，以及部署后的完整使用流程。使用真实文件、数据库或子进程的检查属于集成测试，遵守仓库测试分类。

实现后的交付检查应证明：

- 按文档可完成首次部署，并找到三个入口中的主要操作。
- 草稿、导出、手工交接记录、报告处理、视频核验与后续请求形成完整流程。
- 正常路径以及各专题规定的必要失败处理有对应验证，尤其是请求身份、报告覆盖和文件一致性。
- 已完成的软件验证与仍需真实相机或第三方参与的联调分别列明。

具体测试框架、测试函数划分和实施顺序在实现计划中确定，不能用文档链接检查代替这些运行证据。
