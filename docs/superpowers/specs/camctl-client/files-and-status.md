# 文件导入与结果查看

[客户端设计入口](README.md) · [计划编辑与交接](plans.md) · [数据保存与恢复](storage-and-recovery.md)

用户从传输部门取得状态报告和视频后，通过网页导入。报告告诉客户端主机已经记录的业务事实，视频是某次交付的实际文件；两者可以先后到达。

## 统一网页导入

网页提供一个导入区域，支持拖入或选择文件，可以一次混合选择多个视频和报告。浏览器将文件交给本地后端，后端集中保存并处理，逐文件显示进度和结果。

挂载到容器的目录用于持久化存储，由部署配置负责。用户通过网页完成操作，不需要了解目录位置。网页导入在客户端保存一份副本，用户原文件保留；个人电脑需要相应的存储空间。

拖入和选择文件使用同一套处理规则。文件传输到后端、保存完整、校验通过和业务状态更新分别表达；收到一个文件名或开始传输不代表导入完成。某个文件失败时提供具体诊断，其余文件仍可按各自条件处理。

文件名和字节按全局交接协议保留。报告校验原始字节，不能通过重新排版 JSON 来保存另一份同名报告；视频使用报告中的完整实际文件名关联，完整可读名称用于展示。

### 视频导入中断与后台核验

用户通过网页导入视频时，浏览器读取用户选择的文件，交给同一台个人电脑上的本地后端保存。文件完整保存后，由后端负责关联报告、检查大小和计算 SHA-256；网页展示这些操作的进度与结果。

第一版的网页视频上传在中断后从头重试。是否需要重新导入，依据后端是否已经完整保存文件判断：

| 后端保存情况 | 网页或处理情况 | 行为 |
| --- | --- | --- |
| 文件尚未完整保存 | 正在正常上传 | 显示上传进度，尚不标记为已收到或已核验 |
| 文件尚未完整保存 | 上传失败或因刷新、关闭网页等原因中断 | 显示失败或中断；用户重新选择文件后从头导入，不复用上次的部分上传进度 |
| 文件已完整保存 | 后端正常运行，有效报告映射可用，核验尚未完成 | 后端继续核验；关闭网页不取消这些工作，重新打开网页可查看实际进度或结果 |
| 文件已完整保存 | 后端正常运行，尚无有效的报告映射 | 保留文件并显示等待对应报告；后续按视频关联规则自动继续，无需重新上传 |
| 文件已完整保存 | 核验结果已经可靠保存 | 重新打开网页可查看结果，不因关闭网页要求再次导入 |
| 保存是否完整无法确认，或文件虽完整但核验尚未完成 | 后端不可用或处理结果无法确认 | 保留实际未完成或失败的状态，不宣称已经保存或核验成功；后端重新可用后依据保存记录和文件事实确定结果 |

例如，一个视频上传到一半时关闭网页，需要重新选择并从头导入。若视频已经完整保存，只是摘要还没算完，用户可以关闭网页；后端仍正常运行时继续计算，结果由后端保存供之后查看。

部分上传文件不能作为完整视频参与交付关联、核验成功或播放。重新导入也不删除用户原始文件，且不因这次中断撤销已经成功应用的报告或其他文件的处理结果。后端重启后按[文件恢复规则](storage-and-recovery.md#后端重启后的文件处理)继续处理，完整保存但尚未核验的视频无需重新上传。

## 报告导入与覆盖

报告按[文件名和摘要规则](../camctl/status-reports.md#文件名与完整性校验)、[字段及语义契约](../camctl/report-format.md#语义校验与验收)完成检查。验证身份与覆盖后，按实体 ID 合并业务状态，可靠保存后才取得相应累计确认资格。

报告中对象的自身字段整体更新，实体子集合按 ID 合并；没有出现的已有子成员保留。报告缺项不能解释为对象删除，旧报告也不能覆盖较新状态。完整规则见[按计划嵌套与客户端合并](../camctl/status-reports.md#按计划嵌套与客户端合并)。

以下表格区分客户端的报告接收结果。`C` 表示客户端已应用且连续完整覆盖的业务水位；新报告声明的范围为 `(F, T]`，即大于 `F`、不超过 `T` 的变化。按表从上到下判断，后续各行以前面条件均不成立为前提。同次导入多份报告时，先按下一节处理能够衔接的报告，最后才对仍无法衔接的报告作出缺少历史的判定。

| 条件 | 处理 |
| --- | --- |
| 文件、解析、结构或当前可以判定的业务语义校验失败 | 记录导入诊断，不应用业务内容，不推进确认 |
| 已接受同一报告身份，本次内容与它不同 | 显示报告身份冲突，保留原记录 |
| 已接受同一报告身份，本次内容相同 | 返回已有接收结果，不重复创建业务对象 |
| 新有效报告，`T <= C` | 保留接收记录，当前状态不被旧快照覆盖 |
| 新有效报告，`F <= C < T` | 按既定合并规则更新状态，原子保存结果及完整覆盖至 `T` 的事实 |
| 新有效报告，`C < F <= T` | 显示历史缺失异常，抛弃这份报告，保留最后一次可用状态与原确认位置 |

新客户端的 `C` 为 0；一份有效的 `(0, T]` 报告可以提供完整基础。报告 ID 是否连续不参与缺口判断，也不要求每份历史报告都收到。

每份报告的成功接收记录、与已可靠保存原文的关联、业务应用与确认资格须一起原子保存，失败不会留下部分计划更新或确认。成功接受的报告按[原文保存规则](storage-and-recovery.md#已接受报告的原始内容)保留原文件名和完整字节，相同报告复用已有原文。导入失败记录不冒充已成功接受的报告。后端中断时，按[报告导入恢复规则](storage-and-recovery.md#报告导入中断后重新导入)保留成功结果，并由用户重新选择原批报告继续处理。

## 同次导入多份报告

一次拖入或选择文件构成一次导入。客户端先收齐本次选择中的报告文件，再按覆盖关系处理，最后判断是否缺少历史。报告和视频分别显示进度；报告处理不等待同次选择的大视频完成上传或核验。

例如，客户端已经保存录像 A 的状态，完整进度到第 20 条业务变化。用户同时导入报告 2、报告 3 和视频 B：报告 2 包含录像 B 及取回结果，覆盖 `(20,40]`；报告 3 包含清理录像 A 的结果，覆盖 `(40,45]`。这些编号来自[完整业务样例](../camctl/examples/status-sync/history.md)。即使报告 3 先上传完成，也不能立即认定历史缺失；客户端应先应用报告 2，再应用报告 3，将完整进度更新到 45。

处理过程如下：

1. 确定这次选择中的报告文件，等待各份报告取得完整内容或明确上传、读取失败。页面显示正在接收或检查报告；不要求用户调整选择顺序。
2. 完成不依赖本地历史的文件、解析和结构等校验。失败文件记录自己的诊断，其内容不参与覆盖计算。报告身份冲突、重复及旧报告继续按前述判定表处理。
3. 从剩余报告中找出满足 `F <= C < T` 的报告，在可衔接的报告中按 `T` 从小到大处理。每份应用前，以当时已经保存的状态完成所需的历史关联和语义检查；全部通过后，原子保存状态与覆盖进度，再重新检查剩余报告。此前无法衔接的报告可能因此变得可用，已被新覆盖包含的报告则按旧报告处理。
4. 当本次已无可继续应用的报告时，对剩余满足 `C < F <= T` 的报告给出历史缺失诊断，按既定规则抛弃。这些文件不跨导入操作保留为待应用报告。

报告编号、文件名排列和上传完成顺序均不能代替覆盖判断。某份报告缺少历史时，也应继续寻找本次其他可用的报告；一份范围更宽的有效报告可能直接补齐所需状态。

| 本次情况 | 处理与页面结果 |
| --- | --- |
| 尚有报告未接收完整，且未确定失败 | 显示接收或检查进度，尚不作最终缺口判定 |
| 有报告能够衔接当前完整状态，且通过全部校验 | 应用并保存该份报告，再检查其余报告 |
| 某份报告上传、读取或校验失败，客户端状态仍可正常读取和保存 | 该文件显示具体失败；继续处理其他报告，已经保存的成功结果保留 |
| 全部报告已检查，仍有报告无法衔接 | 对这些报告提示缺少历史并抛弃，页面保留截至本次最后成功应用的状态 |
| 客户端状态数据库无法可靠读取，或保存结果无法确认 | 显示处理失败或中断，停止依赖该状态的后续应用；不能据此推断历史缺失或宣称覆盖已经推进 |

以上每份报告独立提交结果，整次导入不作为一个必须全部成功的事务。例如，报告 2 成功而报告 3 校验失败，客户端保留进度 40。反过来，报告 2 损坏且没有其他报告能补齐时，报告 3 仍然存在缺口；页面分别说明报告 2 的校验失败和报告 3 所缺的历史。

报告处理完成后，即使视频仍在上传，用户也可以查看已经更新的计划结果。视频收到、关联和核验的结果继续独立展示。

## 缺少历史时怎样使用

例如，客户端恢复了一份较旧备份，之后收到一份较晚的增量报告，中间部分状态已经缺失。客户端明确显示这个异常，计划页面仍展示最后一次可用快照，并让用户知道这些是此前保存的结果。

这次无法应用的报告被抛弃，只保留文件名、报告身份、覆盖范围和缺口等异常诊断信息。它不作为之后自动应用的待处理报告；导入操作不删除用户原始选择的文件。

页面提供“准备状态同步”入口，用户可以立即准备同步计划，或将同步动作加入下一份新业务计划。同步按[全局状态同步](../camctl/status-sync.md)执行，范围选择和加入草稿的过程见[准备状态同步](#准备状态同步)。已经固定的原请求通过其只读和幂等规则处理，新同步动作放入新请求。

导出同步计划、标记递交与收到有效同步结果分别处理。异常是否解决以足以补齐缺失状态的报告已成功应用为依据，具体条件如下。

### 历史缺失提示何时解除

收到缺口报告时，客户端已经知道还有一段状态没有取得。后来找回部分历史，可以让页面显示更多已确认结果，但只有补齐到这份缺口报告的终点，才解决了这次已知的缺失。

沿用前面的录像 A/B 样例，分别在不同次导入中处理报告：

| 用户操作 | 成功保存后的完整进度 | 页面结果 |
| --- | --- | --- |
| 从进度 20 导入报告 3，范围为 `(40,45]` | 仍为 20；报告被抛弃，留下缺口诊断 | 提示历史缺失，已知至少需要补齐到 45 |
| 找回并导入报告 2，范围为 `(20,40]` | 更新到 40，取得录像 B 及取回结果 | 继续提示；报告 3 中的录像 A 清理结果仍未应用 |
| 再次选择报告 3 并成功导入 | 更新到 45 | 解除当前历史缺失提示，保留此前导入诊断 |
| 或者，导入一份能衔接当前状态并覆盖至少到 45 的有效同步报告 | 更新到该报告终点 | 同样解除提示，无需再找到报告 3 |

补齐依据来自实际成功应用的报告。重新导入找回的报告、收到范围更宽的普通报告或同步报告，都可以补齐；不要求由某个指定同步动作完成。

精确判断使用两项已有信息：

- `C`：客户端已成功应用并可靠保存的连续完整覆盖位置，含义与报告导入判定表相同。
- `G`：已知需要补齐的位置，由保存的历史缺失诊断中最大的 `to_wm` 得到。只有通过当时可完成的检查、没有报告身份冲突，并最终按报告导入规则判为缺少历史的报告，才提供这个位置。上传、读取或校验失败的文件不能提供或提高它；没有此类诊断时，`G` 不存在。

同次选择多份报告时，仍先处理可衔接报告，最后才登记剩余缺口。诊断只保存异常信息，不保存为之后自动应用的报告，也不把其中的业务内容用于计划展示或视频关联。

按下表判断当前提示；后续各行以前面条件不成立为前提：

| 已保存信息及覆盖情况 | 页面结果 |
| --- | --- |
| 无法可靠读取完整进度或缺口诊断 | 显示实际数据故障或无法确认，不能宣称历史已补齐 |
| 没有历史缺失诊断，`G` 不存在 | 没有已发现的历史缺失；是否已有主机状态仍以实际导入结果说明 |
| 存在 `G`，且 `C < G` | 保留历史缺失提示，正常页面使用截至 `C` 的可用状态 |
| 存在 `G`，且 `C >= G` | 解除当前历史缺失提示，此前诊断保留供查看 |

多份缺口报告取最晚的终点作为目标，补齐其中较早的一段不会提前解除提示。提示根据可靠保存的进度与诊断计算，刷新网页或重启后端后仍可恢复；不依赖网页临时记住一次“已解决”操作。

导出同步计划、标记已递交或同步动作在主机上成功，本身都不推进 `C`。历史补齐也不以视频已收到或报告 ACK 已送达主机为条件。解除提示只表示已经补齐客户端知道缺失的状态，主机之后是否又有变化仍由后续报告说明。

## 准备状态同步

“准备状态同步”根据客户端已经保存的资料选择补齐范围。用户通常只需查看说明，无需查找或填写报告编号；需要时可以主动选择“重新获取完整状态”。尚未导入任何报告的新客户端也可以通过该入口准备完整同步。

例如，用户恢复了只包含录像 A 的旧备份，导入后续清理报告时发现缺少历史。客户端知道自己已经可靠保存报告 1 对应的状态，于是默认准备从报告 1 之后补齐，并说明“将从本地已保存的状态之后补齐”。用户可以把这个动作加入正在编辑的明日录像草稿，随同一次文件交接提交。

### 自动选择范围与完整同步选项

默认起点依据[全局同步范围规则](../camctl/status-sync.md#客户端选择同步范围)确定。先检查本地数据是否可可靠读取，再结合用户选择处理：

| 本地依据及用户选择 | 准备结果 | 页面说明 |
| --- | --- | --- |
| 本地数据无法可靠读取，不能判断已保存状态 | 显示数据故障，先恢复客户端数据访问 | 说明无法确定状态；不能把不可读解释为尚未保存任何状态 |
| 数据可正常使用，用户主动选择“重新获取完整状态” | 准备 `report_status`，`params` 为 `{"scope":"full"}` | 说明将获取全部历史业务状态，报告可能更大 |
| 数据可正常使用，沿用默认选择，具有可靠的完整状态及对应报告依据 | 自动选择报告起点，准备 `{"scope":"since","after_report_id":N}` | 说明将从本地已保存的状态之后补齐 |
| 数据可正常使用，沿用默认选择，但没有完整状态基础或无法确定对应的报告 | 准备 `{"scope":"full"}` | 说明缺少可用起点，因此将获取完整状态 |

自动选择时，从已成功接受的报告记录中，选择终点最靠后且本地已完整覆盖到该终点的一份报告。起点依据是报告终点及对应完整状态，不能直接取最大的报告 ID，也不能采用被抛弃的缺口报告。同一终点有多份符合条件的报告时，任一份都可以提供起点。

用户主动选择完整同步时采用该选择，不因本地仍有部分历史改为局部同步。两种方式都只恢复主机记录的业务状态，视频继续按取回及文件导入规则处理。同步不以某个计划或某个视频作为范围。

### 加入草稿并递交

1. 用户查看默认范围，或选择“重新获取完整状态”。
2. 用户选择一份已有草稿，或新建草稿。客户端将选定范围展开为具体的 `report_status` 参数并加入草稿，保留其中已有动作与编辑内容。
3. 用户检查动作名称、执行安排和整份计划，按正常导出规则校验并保存原请求，然后下载 JSON。自动选择的具体起点保存在草稿参数中，导出仍须有已完整保存到该起点的依据；不能只依赖页面先前显示过的推荐。
4. 用户将文件交给传输部门，可以标记已递交。报告返回后，通过统一导入入口校验、合并和保存，按前述条件判断历史是否已补齐。

已经导出的原请求保持只读。要追加同步动作，应使用新草稿形成新请求；再次下载原请求仍遵守原身份、正文及独立累计确认的规则。

若主机报告局部同步因 `sync_report_not_found` 失败，客户端保留当前可用状态及该动作错误，并引导用户核对起点、通过新草稿准备完整同步。不会把原失败动作改成成功或在原请求内替换同步参数。具体失败语义继续以全局同步规格为准。

该流程中的“加入草稿”“已导出”“已递交”和历史是否补齐分别展示。普通报告的准备仍遵守其原有动作含义；用于补齐状态的入口明确生成上述局部或完整同步参数。

## 视频关联与核验

客户端根据已经接受并应用的报告，用完整 `file_name` 关联交付、产物和来源动作，再比较实际文件大小与 SHA-256。

| 当前取得的资料 | 展示与处理 |
| --- | --- |
| 视频已经保存，尚无可用报告映射 | 保留视频，显示等待对应报告 |
| 已有交付报告，视频尚未收到 | 展示交付事实及等待视频的状态 |
| 文件与有效映射均可用，核验尚未结束 | 显示核验中，或实际未完成原因 |
| 大小和摘要均匹配 | 显示该交付文件已收到并核验 |
| 大小或摘要不匹配，或无法完成读取核验 | 显示实际失败或未完成原因，不显示为核验成功 |

报告与文件后续齐全时，客户端自动继续关联和核验。已经保存的有效文件不要求用户再次导入。已抛弃报告中的信息不能作为已经应用的业务映射。

报告的 `published` 表示主机完成本地发布，客户端自己的文件接收事实另行保存。报告 ACK 的资格与视频是否收到分开；日常在下一份真实业务输入中附带有效确认，见[人工交接中的累计确认](../camctl/system-context.md#何时递交累计确认)。

### 重复导入同名视频

用户再次拖入一批文件，或者在校验失败后收到补发文件时，可能重复导入同一个交付文件。客户端用完整实际文件名找到已有副本，比较文件大小和 SHA-256，决定是否复用或替换。相同名字本身不能证明内容相同；比较内容也不代替按报告核验。

例如，第一次收到的 `d-001.mp4` 与报告摘要不符。传输部门随后补发同名文件，客户端确认新文件的大小和摘要都符合报告后，自动替换错误副本，保留此前失败的诊断；用户无需先删除旧文件。如果用户再次选择的仍是同一份错误文件，则复用已有副本并保留校验失败的结果。

以下规则适用于已有同名完整副本的情况。没有完整副本时，按普通导入和中断重试规则处理。只有文件完整性、用于比较的大小和摘要，以及适用的报告映射能够可靠确定，才进入表中的相同或不同分支；读取失败、比较未完成或结果未知时，显示实际原因，保留已有副本，不作替换决定。

| 两份文件的大小和摘要 | 当前依据及核验结果 | 处理 |
| --- | --- | --- |
| 都相同 | 有或没有可用报告映射 | 复用已有文件，提示已导入，不再保留重复副本；原来的等待报告、核验中、核验失败或成功状态继续按实际依据处理 |
| 至少一项不同 | 尚无已接受并应用的报告映射 | 保留已有副本，提示同名文件内容冲突，本次不接受新文件为持久化副本 |
| 至少一项不同 | 有可用映射，新文件的大小或摘要不符 | 保留已有副本，提示新文件不符合报告；已有副本若合格，继续保留其核验成功结果，若不合格，也不因此改成成功 |
| 至少一项不同 | 有可用映射，新文件符合报告，旧副本已确认不符合 | 自动替换旧副本，保存新文件的核验结果，保留之前的失败诊断 |
| 至少一项不同 | 有可用映射，但替换所需的核验尚未完成或结果无法可靠确认 | 显示核验中或具体失败原因，保留已有副本，不能提前宣称替换成功 |

一份有效报告映射对该交付规定唯一的大小和摘要。已核验合格的副本不被内容不同的新文件覆盖；如果保存的核验记录与本次取得的文件事实互相矛盾，应保留诊断并按无法确认处理，不能任意选一份当作正确文件。

自动替换须先完整保存并核验新文件，不能在新文件仍上传或核验未通过时覆盖已有副本。替换结果可靠保存后才显示成功；中断后依据[文件恢复规则](storage-and-recovery.md#后端重启后的文件处理)确认完成情况，持久化步骤在实现设计中落实。复用或替换不会创建新的 `delivery_id`，也不改变报告中的产物来源或动作结果。

视频先到、报告后到时，客户端会核验此前保留的副本。先前因同名冲突未被接受的新文件不会作为另一候选副本等待自动选用；若报告证明保留的副本有误，用户需要重新选择正确文件导入。导入过程中不删除用户原始选择的文件。

本节按相同的 `file_name` 处理重复输入。不同文件名对应的交付仍按各自身份管理，不能因 `output_id` 或视频内容相同而把两次交付合并。

## 按计划查看结果

计划是主要入口。用户进入详情后，先看到各动作的进度和结果，再查看关联产物、各次交付与客户端接收核验情况。

例如，“上午采集”中录像 A 成功、录像 B 失败，页面同时显示 A 的结果及已收到视频，以及 B 的失败原因。没有视频的动作仍有执行结果。取回整体失败时，已经成功取得的文件仍可单独查看。

计划 `completed` 表示全部动作已经结束，具体成功、失败、取消或过期结果按动作展示。跨计划取回保留来源计划和动作关联，通过 `output_id` 关联同一正式产物及其多次独立交付。

## 视频播放与原文件下载

计划详情为已关联报告、核验通过且当前可读取的视频提供基础播放，包括播放、暂停、拖动进度和调节音量，并提供原文件下载。网页入口依据当前本地副本的保存、关联和核验记录开放。

| 当前本地文件情况 | 报告关联及核验情况 | 网页行为 |
| --- | --- | --- |
| 尚未完整保存 | 任意 | 显示上传或中断状态，等待完整保存 |
| 无法确认完整保存，或文件缺失、不可读 | 任意 | 显示实际问题，等待文件恢复可用 |
| 已完整保存且可读取 | 尚无有效报告映射 | 保存文件并显示等待报告；报告到达后自动关联和核验 |
| 已完整保存且可读取 | 有有效映射，核验尚未结束或无法完成 | 显示核验中或未完成原因，等待核验结果 |
| 已完整保存且可读取 | 大小或摘要与报告不符 | 显示核验失败，按文件导入规则处理后续补发 |
| 已完整保存且可读取 | 有有效映射，大小和摘要均匹配，结果已可靠保存 | 在对应计划详情提供播放和原文件下载 |

表中只有最后一行提供网页播放和下载。等待报告、核验中及核验失败的完整文件继续保留，后续处理仍遵守关联、核验和正确副本替换规则。

核验通过的文件如果无法在网页播放，显示无法播放的提示，保留原文件下载。网页播放结果、文件一致性核验和主机录像执行结果分别表达；播放失败不改写报告中的动作结果。

原文件下载保留原始字节。实际设备视频与浏览器的播放兼容性需在实现和设备联调时验证，当前没有选定播放器库或宣称全部真实视频都能直接播放。

第一版按[本地视频保留规则](storage-and-recovery.md#本地视频的保留)持续保存已纳入管理的副本，计划结束或相机源产物清理后仍可查看本地文件。

## 验收依据

- 混合导入视频与报告，覆盖两者不同到达顺序、逐文件失败和重复导入，检查文件保存及业务关联。
- 在视频尚未完整上传时刷新或关闭网页，验证中断后的重试从头开始，部分文件不会显示为已收到；在完整保存后关闭网页且后端正常运行，验证核验继续、结果保存且重新打开可查。报告映射尚未到达时保留完整视频，后续自动继续关联。
- 覆盖同名视频判定表：相同内容只保留一个副本且不把失败改成成功；错误副本由符合报告的补发文件替换；已有合格副本不被错误文件覆盖；缺少报告时不同内容产生冲突，报告到达后核验保留的副本。读取或核验结果未知时不替换，不同交付身份不因内容相同而合并。
- 覆盖报告判定表，检查身份冲突、重复、旧报告、可衔接增量和覆盖缺口；无法应用时状态及确认不被部分更新。
- 对同次导入调换文件选择和上传完成顺序，验证先应用可衔接报告，再对剩余报告判定缺口；覆盖连续报告、可补齐的较宽报告、重复与旧报告、部分文件失败，以及数据库处理失败。某份失败不撤销此前成功结果，也不使失败报告参与覆盖。
- 使用录像 A/B 样例的报告 2、3，验证从进度 20 更新到 45；报告 3 损坏时保留 40，报告 2 损坏且无其他可用报告时保留 20 并诊断缺口。大视频未上传完不阻塞报告结果展示。
- 缺口报告产生明确异常，页面使用最后可用状态。按提示判定表覆盖没有已知缺口、尚未补齐、已经补齐及数据无法确认；导出、人工递交、主机同步动作成功或视频到达均不能代替报告应用推进覆盖。
- 从进度 20 导入报告 3 后，再导入报告 2 到 40，验证提示仍保留；重新导入报告 3 到 45，或导入能衔接并覆盖至少到 45 的有效报告，提示解除且旧诊断保留。多份缺口报告以最晚终点为目标，失败或身份冲突文件不提高目标；刷新和重启后仍依据已保存信息展示。
- 按同步范围表验证默认局部同步、无基础时的完整同步、用户主动选择完整同步及数据不可读。自动起点有已接受报告和完整状态依据，不使用最大报告 ID 或缺口报告猜测；用户无需手填编号。
- 将同步动作加入已有或新草稿，检查具体参数、原有内容保留及正常导出校验。已有原请求不能追加动作；局部同步起点不存在时保留错误并通过新请求准备完整同步，不修改原请求或提前解除异常。
- 视频大小或摘要不符、读取失败、网页无法播放分别表达，不能相互替代；下载保持原字节。
- 按网页播放与下载表覆盖保存未完成、文件不可用、等待报告、核验未完成、核验不符及核验成功；只有完整可用、已关联且核验通过的副本开放入口。核验通过但浏览器无法播放时，保留下载和已有核验结果。
- 验证计划完成但动作部分失败、取回部分成功和跨计划取回，保证页面忠实呈现报告及实际文件证据。
