# 文件导入与结果查看

[客户端设计入口](README.md) · [计划编辑与交接](plans.md)

用户从传输部门取得状态报告和视频后，通过网页导入。报告告诉客户端主机已经记录的业务事实，视频是某次交付的实际文件；两者可以先后到达。

## 统一网页导入

网页提供一个导入区域，支持拖入或选择文件，可以一次混合选择多个视频和报告。浏览器将文件交给本地后端，后端集中保存并处理，逐文件显示进度和结果。

挂载到容器的目录用于持久化存储，由部署配置负责。用户通过网页完成操作，不需要了解目录位置。网页导入在客户端保存一份副本，用户原文件保留；个人电脑需要相应的存储空间。

拖入和选择文件使用同一套处理规则。文件传输到后端、保存完整、校验通过和业务状态更新分别表达；收到一个文件名或开始传输不代表导入完成。某个文件失败时提供具体诊断，其余文件仍可按各自条件处理。

文件名和字节按全局交接协议保留。报告校验原始字节，不能通过重新排版 JSON 来保存另一份同名报告；视频使用报告中的完整实际文件名关联，完整可读名称用于展示。

## 报告导入与覆盖

报告按[文件名和摘要规则](../camctl/status-reports.md#文件名与完整性校验)、[字段及语义契约](../camctl/report-format.md#语义校验与验收)完成检查。验证身份与覆盖后，按实体 ID 合并业务状态，可靠保存后才取得相应累计确认资格。

报告中对象的自身字段整体更新，实体子集合按 ID 合并；没有出现的已有子成员保留。报告缺项不能解释为对象删除，旧报告也不能覆盖较新状态。完整规则见[按计划嵌套与客户端合并](../camctl/status-reports.md#按计划嵌套与客户端合并)。

以下表格区分客户端的报告接收结果。`C` 表示客户端已应用且连续完整覆盖的业务水位；新报告声明的范围为 `(F, T]`，即大于 `F`、不超过 `T` 的变化。按表从上到下判断，后续各行以前面条件均不成立为前提。

| 条件 | 处理 |
| --- | --- |
| 文件、解析、结构或当前可以判定的业务语义校验失败 | 记录导入诊断，不应用业务内容，不推进确认 |
| 已接受同一报告身份，本次内容与它不同 | 显示报告身份冲突，保留原记录 |
| 已接受同一报告身份，本次内容相同 | 返回已有接收结果，不重复创建业务对象 |
| 新有效报告，`T <= C` | 保留接收记录，当前状态不被旧快照覆盖 |
| 新有效报告，`F <= C < T` | 按既定合并规则更新状态，原子保存结果及完整覆盖至 `T` 的事实 |
| 新有效报告，`C < F <= T` | 显示历史缺失异常，抛弃这份报告，保留最后一次可用状态与原确认位置 |

新客户端的 `C` 为 0；一份有效的 `(0, T]` 报告可以提供完整基础。报告 ID 是否连续不参与缺口判断，也不要求每份历史报告都收到。

同批多份报告的排序与检查交互在后续客户端设计中落实；每份报告的业务应用须保持原子性，失败不会留下部分计划更新或确认。导入失败记录不冒充已成功接受的报告。

## 缺少历史时怎样使用

例如，客户端恢复了一份较旧备份，之后收到一份较晚的增量报告，中间部分状态已经缺失。客户端明确显示这个异常，计划页面仍展示最后一次可用快照，并让用户知道这些是此前保存的结果。

这次无法应用的报告被抛弃，只保留文件名、报告身份、覆盖范围和缺口等异常诊断信息。它不作为之后自动应用的待处理报告；导入操作不删除用户原始选择的文件。

页面引导用户立即准备同步计划，或将同步动作加入下一份新业务计划。同步按[全局状态同步](../camctl/status-sync.md)执行，依照可用的完整状态基础选择相应入口。已经固定的原请求通过其只读和幂等规则处理，新同步动作放入新请求。

导出同步计划、标记递交与收到有效同步结果分别处理。异常是否解决以足以补齐缺失状态的报告已成功应用为依据。同步请求的具体客户端交互仍需在本客户端规格中完善。

## 视频关联与核验

客户端根据已经接受并应用的报告，用完整 `file_name` 关联交付、产物和来源动作，再比较实际文件大小与 SHA-256。

| 当前取得的资料 | 展示与处理 |
| --- | --- |
| 视频已经保存，尚无可用报告映射 | 保留视频，显示等待对应报告 |
| 已有交付报告，视频尚未收到 | 展示交付事实及等待视频的状态 |
| 文件与有效映射均可用，核验尚未结束 | 显示核验中，或实际未完成原因 |
| 大小和摘要均匹配 | 显示该交付文件已收到并核验 |
| 大小或摘要不匹配，或无法完成读取核验 | 显示实际失败或未完成原因，不显示为核验成功 |

报告与文件后续齐全时，客户端自动继续关联和核验。已经保存的有效文件不要求用户再次导入。已抛弃报告中的信息不能作为已经应用的业务映射。

报告的 `published` 表示主机完成本地发布，客户端自己的文件接收事实另行保存。报告 ACK 的资格与视频是否收到分开；日常在下一份真实业务输入中附带有效确认，见[人工交接中的累计确认](../camctl/system-context.md#何时递交累计确认)。

## 按计划查看结果

计划是主要入口。用户进入详情后，先看到各动作的进度和结果，再查看关联产物、各次交付与客户端接收核验情况。

例如，“上午采集”中录像 A 成功、录像 B 失败，页面同时显示 A 的结果及已收到视频，以及 B 的失败原因。没有视频的动作仍有执行结果。取回整体失败时，已经成功取得的文件仍可单独查看。

计划 `completed` 表示全部动作已经结束，具体成功、失败、取消或过期结果按动作展示。跨计划取回保留来源计划和动作关联，通过 `output_id` 关联同一正式产物及其多次独立交付。

## 视频播放与原文件下载

计划详情提供已接收视频的基础播放，包括播放、暂停、拖动进度和调节音量，并提供原文件下载。

如果文件无法在网页播放，显示无法播放的提示，保留原文件下载。网页播放结果、文件一致性核验和主机录像执行结果分别表达；播放失败不改写报告中的动作结果。

原文件下载保留原始字节。实际设备视频与浏览器的播放兼容性需在实现和设备联调时验证，当前没有选定播放器库或宣称全部真实视频都能直接播放。

## 验收依据

- 混合导入视频与报告，覆盖两者不同到达顺序、逐文件失败和重复导入，检查文件保存及业务关联。
- 覆盖报告判定表，检查身份冲突、重复、旧报告、可衔接增量和覆盖缺口；无法应用时状态及确认不被部分更新。
- 缺口报告产生明确异常，页面使用最后可用状态；同步结果成功应用前，不因导出或人工递交清除异常。
- 视频大小或摘要不符、读取失败、网页无法播放分别表达，不能相互替代；下载保持原字节。
- 验证计划完成但动作部分失败、取回部分成功和跨计划取回，保证页面忠实呈现报告及实际文件证据。
