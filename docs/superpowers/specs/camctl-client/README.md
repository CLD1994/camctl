# 客户端 MVP 设计

**状态：已确认设计的阶段性整理，2026-09-15。** 本目录保存客户端目前已确定的使用流程。完整客户端规格仍在完善；本页末尾列出后续需要落实的内容。状态同步的公共协议由[全局同步规格](../camctl/status-sync.md)定义。

## 使用背景

用户在个人电脑上打开本地网页，编辑一份执行计划并导出 JSON 文件，手工交给负责传输的部门。该部门安排文件送达嵌入式主机；主机上的 camctl 执行计划，通过状态报告说明执行结果，并按计划交付视频。

用户收到报告和视频后，在网页导入这些文件。客户端保存文件及业务状态，让用户查看计划中的动作执行到了哪里、哪些视频已经收到，以及接下来是否需要取回、取消或清理。

文件导出、人工递交、主机受理、设备执行和客户端收到视频发生在不同时间。界面依据各自证据展示这些事实，具体协议遵守[全局设计总览](../2026-09-08-camctl-cli-design.md)与[运行环境及人工交接](../camctl/system-context.md)。

## 第一版范围与阅读顺序

第一版面向一台嵌入式主机和一个逻辑客户端。每次编辑围绕当前一份计划的实际需要；一份计划可以包含多个动作，并按全局规则引用此前计划的动作或产物。

| 专题 | 已确定内容 |
| --- | --- |
| [计划编辑与交接](plans.md) | 自动保存草稿、校验并导出、只读导出记录、再次下载、复制新草稿、可选人工递交标记，以及详情页操作加入选定草稿 |
| [文件导入与结果查看](files-and-status.md) | 视频和报告统一拖入或选择导入、集中保存、按计划查看结果、视频核验和基础播放，以及缺少历史时的异常提示与同步引导 |

公共动作和字段继续由[执行计划输入契约](../camctl/plan-input.md)定义。第一版支持的录像、取回、清理、取消和报告动作各自遵守对应专题；客户端通过当前已启用的能力说明编辑拍摄参数。

## 一次完整使用过程

1. 用户新建“上午采集”草稿，加入“录像 A”和“取回 A”，按设备能力填写参数及执行时间。编辑过程中自动保存，未完成内容也可以保留。
2. 用户完成检查并导出。客户端保存原请求，提供 JSON 下载，随后将这份导出记录作为只读内容保留。
3. 用户把文件交给传输部门，可以在客户端标记“已递交”。之后依据收到的报告确认主机是否受理和执行。
4. 用户将返回的报告与视频拖入网页。客户端分别保存、核验及关联文件，按计划展示动作结果和视频接收情况。
5. 用户可以播放已接收的视频、下载原文件，或选择历史产物，将取回、取消、清理操作加入一份草稿，再检查并导出。

例如，录像成功、取回部分失败时，计划详情同时展示录像结果、成功交付的视频和失败原因。计划已经结束不代表每个动作都成功，报告已经确认也不代表视频已经收到。

## 共同技术基础

客户端采用 TypeScript 浏览器界面和 Node.js / TypeScript 本地后端，由一个 Docker Compose 应用容器提供服务。后端使用 SQLite 保存客户端数据，使用挂载到个人电脑的目录保存持久化文件。用户通过网页完成日常操作；部署人员配置保存位置。

技术组合、`data/client.db`、`data/device-capabilities.json` 及能力说明加载规则继续以[客户端部署](../camctl/client-deployment.md)为准。拍摄参数表单与 JSON 编辑以[公共编辑规则](../camctl/client-editing.md)为准，规则来源见[能力说明](../camctl/capabilities.md)。本目录补充客户端的具体使用流程，不另行维护这些公共契约的副本。

- 整体页面布局、草稿选择与人工递交记录的具体交互，以及参数预设的操作。

- 前后端职责、必要接口和共享规则的组织，以及真实视频的播放兼容性。
- 贯通草稿、导出、报告导入、视频处理及后续请求的 MVP 验收场景。
