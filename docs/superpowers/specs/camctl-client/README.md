# 客户端 MVP 设计

**状态：客户端 MVP 第一版已定稿，2026-09-16。** 本目录定义第一版客户端的用户流程、数据保存、必要失败处理及验收范围。本页末尾列出实现设计和联调时需要落实的事项。状态同步的公共协议由[全局同步规格](../camctl/status-sync.md)定义。

## 使用背景

用户在个人电脑上打开本地网页，编辑一份执行计划并导出 JSON 文件，手工交给负责传输的部门。该部门安排文件送达嵌入式主机；主机上的 camctl 执行计划，通过状态报告说明执行结果，并按计划交付视频。

用户收到报告和视频后，在网页导入这些文件。客户端保存文件及业务状态，让用户查看计划中的动作执行到了哪里、哪些视频已经收到，以及接下来是否需要取回、取消或清理。

文件导出、人工递交、主机受理、设备执行和客户端收到视频发生在不同时间。界面依据各自证据展示这些事实，具体协议遵守[全局设计总览](../2026-09-08-camctl-cli-design.md)与[运行环境及人工交接](../camctl/system-context.md)。

## 页面入口与操作衔接

完成首次初始化后，网页提供“计划”“文件导入”“设备说明”三个入口。各入口围绕用户当下要完成的事情组织，具体业务规则由对应专题定义。

| 入口 | 主要内容与操作 | 相关规则 |
| --- | --- | --- |
| 计划 | 使用“草稿／计划记录”两个页签；编辑、导出及记录递交，在详情查看执行结果和已核验视频，准备后续取回、取消、清理或同步请求 | [计划编辑与交接](plans.md)、[按计划查看结果](files-and-status.md#按计划查看结果) |
| 文件导入 | 混合拖入或选择报告与视频，查看各批文件的处理进度、结果和失败原因 | [文件导入与结果查看](files-and-status.md) |
| 设备说明 | 查看当前启用的设备能力与参数说明；手工替换说明文件后点击“重新加载能力说明”，查看实际加载结果 | [说明加载与失败处理](../camctl/client-deployment.md#启动与重新加载) |

例如，用户在“计划”中导出上午采集任务。收到文件后进入“文件导入”，查看报告是否已应用、视频是否已核验，再进入对应计划详情查看业务结果与视频。文件导入结果通过已有的可靠关联指向计划；尚无报告映射的文件继续显示等待状态。

预设的保存、应用和更新位于拍摄动作编辑区，规则见[拍摄参数预设](presets.md)。状态查看及历史缺失提示处提供[准备状态同步](files-and-status.md#准备状态同步)入口，再将动作加入用户选定的草稿。由详情发起取回、取消和清理时，也沿用选定草稿、检查、导出的流程。

“设备说明”展示后端当前实际启用的说明及加载结果。替换文件尚未重新加载、加载失败但仍有此前有效说明等情况，按公共加载规则解释，避免让用户把磁盘文件内容当作已经生效的参数规则。

首次初始化按[首次初始化与正常启动](storage-and-recovery.md#首次初始化与正常启动)进入相应页面。正常使用中的能力说明问题与客户端数据库问题分别展示，可用操作依据各自条件开放。

## 一次完整使用过程

首次部署时，用户先在网页点击“创建客户端数据”完成初始化；之后每次启动直接使用已有数据。正常使用过程如下：

1. 用户在“计划”的“草稿”页签新建“上午采集”，加入“录像 A”和“取回 A”，按设备能力填写参数及执行时间。编辑过程中自动保存，未完成内容也可以保留。
2. 用户完成检查并导出。客户端保存原请求，提供 JSON 下载，随后在“计划记录”页签保留这份只读记录。
3. 用户把文件交给传输部门，可以在客户端标记“已递交”。之后依据收到的报告确认主机是否受理和执行。
4. 用户将返回的报告与视频拖入网页。客户端分别保存、核验及关联文件，按计划展示动作结果和视频接收情况。
5. 用户可以在计划详情播放已关联且核验通过的视频、下载原文件，或选择历史产物，将取回、取消、清理操作加入一份草稿，再检查并导出。

例如，录像成功、取回部分失败时，计划详情同时展示录像结果、成功交付的视频和失败原因。计划已经结束不代表每个动作都成功，报告已经确认也不代表视频已经收到。

## 共同技术基础

客户端采用 TypeScript 浏览器界面和 Node.js / TypeScript 本地后端，由一个 Docker Compose 应用容器提供服务。后端使用 SQLite 保存客户端数据，使用挂载到个人电脑的目录保存持久化文件。用户通过网页完成日常操作；部署人员配置保存位置。

技术组合、`data/client.db`、`data/device-capabilities.json` 及能力说明加载规则继续以[客户端部署](../camctl/client-deployment.md)为准。拍摄参数表单与 JSON 编辑以[公共编辑规则](../camctl/client-editing.md)为准，规则来源见[能力说明](../camctl/capabilities.md)。本目录补充客户端的具体使用流程，不另行维护这些公共契约的副本。

## 实现设计与联调事项

各专题已经定义用户操作、成功依据和必要失败处理。以下内容应在实施计划、实现及联调中具体落实；内部技术选择需要满足这些已确定的行为。

| 事项 | 实施时需要落实的内容 | 已确定的依据 |
| --- | --- | --- |
| 页面与编辑交互 | 三个入口内的布局、草稿选择、字段控件、保存反馈及操作结果展示 | 页面入口、草稿保存与导出、人工标记转换和各项文件处理状态 |
| 数据组织 | 数据库表、已接受报告原文的保存形式、导入记录及其他业务记录的关联 | 信息来源、最新编辑内容、固定原请求、报告原文及文件保留规则 |
| 文件与数据库衔接 | 文件保存和替换的具体步骤、临时文件管理、事务提交及中断后结果核实 | 成功结果需要的完整依据、报告原子提交、正确副本替换及恢复规则 |
| 本地接口与内部结构 | 网页与后端的具体请求响应、模块划分及共享类型和校验代码 | [职责与关键操作](architecture.md)及全局公共协议 |
| 运行验证与联调 | 客户端真实运行测试、实际视频的浏览器兼容性，以及设备和第三方交接验证 | [六组 MVP 验收场景](acceptance.md)与全局联调范围 |

实际实施中若出现会改变业务结果、且现有契约无法确定的选择，应再补充该具体规则。客户端实现和真实设备验证的结果分别以相应运行证据为准。
