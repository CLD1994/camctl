# 数据保存与恢复

[客户端设计入口](README.md) · [文件导入与结果查看](files-and-status.md)

本页定义个人电脑上的客户端如何初始化、保存编辑内容与视频、在重启后继续处理导入，以及部署人员怎样备份和恢复。部署路径、容器挂载和能力说明加载继续以[客户端部署](../camctl/client-deployment.md)为准。

## 首次初始化与正常启动

首次部署时，部署人员已经准备 `data/` 及所需权限，也可以先放好能力说明。此时还没有客户端数据库，网页显示尚未初始化，并提供“创建客户端数据”按钮。用户明确点击后，后端创建 `client.db`，保存本次初始化完成的事实，再进入正常界面。

初始化建立新的客户端数据，不导入历史计划、不猜测主机状态。初始完整报告进度为 0；之后通过报告导入取得业务状态。能力说明是否已经准备好不影响创建数据库：说明缺失或有误时，仍按既有能力加载规则提示，不能自动生成空说明掩盖问题。

正常启动先检查当前挂载目录和已有数据库，按表从上到下判断；后续各行以前面条件均不成立为前提。

| 当前能够确认的情况 | 网页与后端行为 |
| --- | --- |
| 挂载位置、目录读写权限或数据库存在性无法可靠确认 | 显示具体部署或访问故障，不创建数据库，也不使用容器临时目录替代持久化目录 |
| `client.db` 存在，但无法读取、数据结构不完整或不能确认初始化已完整完成 | 显示数据故障，保留文件与诊断，不覆盖或重建为空库 |
| `client.db` 正常，且初始化已完整完成 | 直接使用已有数据，按正常启动规则加载能力说明和恢复后端处理 |
| `client.db` 确认不存在，但目录中有已保存的视频、其他客户端业务数据，或无法解释的既有数据 | 显示数据缺失或目录状态不明，指导检查部署位置或恢复备份；不提供覆盖这些数据的初始化操作 |
| `client.db` 确认不存在，目录中没有既有客户端业务数据，仅为空目录或已准备能力说明 | 显示首次初始化页面，等待用户点击“创建客户端数据” |

能力说明文件本身属于部署准备内容，不作为已有业务数据库的证明。首次页面应展示当前使用的数据目录，供部署人员核对。程序只能依据当前可见的文件和记录判断；如果误挂载了一个全新的空目录，也会显示首次初始化页面，由用户检查位置后明确选择是否建立新数据。

用户点击后，后端重新检查目录和数据库条件。若此时已有正常数据库，就使用它；存在故障或既有业务数据时，按上表返回相应结果。重复点击不能创建多套数据，也不能清空已经完成初始化的数据库。

只有建库及初始化完成记录可靠保存后，才能报告创建成功。失败或提交结果无法确认时，显示具体问题并保留诊断；再次检查时依据完整完成的事实决定是否进入正常界面，不能把半成品数据库当作正常空库。初始化步骤与中断后的清理方式由实现设计落实，并保持已有数据不被覆盖的要求。

## 草稿、预设与原请求的保存

草稿和预设用于准备接下来的任务，客户端分别保存它们最近一次成功写入的内容。已经导出的请求则记录当时确定的执行意图，保留原请求身份与固定正文。

| 对象 | 保存内容 | 再次打开或使用时的行为 |
| --- | --- | --- |
| 草稿 | 最新一次保存成功的编辑内容，包括尚未填写完整、未通过校验的输入 | 恢复这份内容继续编辑；后续成功保存更新当前草稿 |
| 预设 | 最新一次明确创建或更新成功的设备关联与合法参数 | 提供当前保存的参数；应用到草稿后形成独立副本 |
| 已导出原请求 | 首次导出时可靠保存的 `request_id` 与固定计划正文 | 再次下载复用原身份及正文；修改执行意图使用新草稿和新请求 |

例如，用户更新“白天巡检”预设后，下次打开预设会取得新参数。此前已导出的采集计划继续保存当时采用的参数，已经应用过预设的其他草稿也保持各自内容。用户需要重新调整预设时，编辑当前参数并明确保存。

草稿和预设的持久化记录只保存当前内容，不提供每次编辑的历史版本列表或跨会话版本回退。已导出请求的固定正文及报告接收证据分别按对应契约保存；它们是独立业务记录。

保存结果按实际是否可靠写入判断：

| 本次结果 | 已保存内容及页面行为 |
| --- | --- |
| 草稿保存成功，或预设通过校验并保存成功 | 当前记录更新为本次内容，页面可以显示已保存 |
| 校验不通过，或明确未完成写入 | 保留原有保存记录；页面保留当前编辑并显示问题，不用失败输入替换原记录 |
| 写入是否成功无法确认 | 保留当前编辑及未确认状态，依据后端记录核实实际结果后再展示，不能猜测新旧哪份已保存 |

表中的校验失败遵守各对象的保存条件：草稿可以保存未完成或非法输入；预设创建和更新要求当前参数合法。不能把草稿的计划校验失败当作拒绝保存当前编辑的理由。

备份保存的是制作备份时已经成功写入的内容。按[完整目录恢复流程](#从备份恢复)还原后，草稿、预设及原请求回到该备份中的记录；备份恢复与日常编辑分别处理。

## 已接受报告的原始内容

第一版持续保留每份成功接受报告的原文件名与完整 JSON 原始字节。报告原文用于核对当时实际收到的输入；网页中的当前业务状态继续由成功应用的报告按合并规则更新。

例如，用户先后导入两份报告，后一份更新了某段录像的清理状态。计划详情展示合并后的结果，两份已接受报告分别保留各自原文。排查显示问题时，可以核对每份报告原本提供了哪些内容。

原始内容须保留收到时的字节，不能先解析再重新序列化作为原文。即使 JSON 表达相同信息，重新排版、调整字段顺序或换行也可能改变字节和文件名中的 SHA-256。报告的原文件名与其原始内容一起保留。

按[报告导入判定规则](files-and-status.md#报告导入与覆盖)得到接收结果后，分别处理：

| 接收结果 | 原文保存与后续使用 |
| --- | --- |
| 新报告合法并成功接受，推进当前完整覆盖 | 保存这份报告的原文件名、完整原始字节及接收结果；业务状态按既定规则合并 |
| 新报告合法并成功接受，范围已由当前状态完整覆盖 | 同样保留原文及接收结果，当前状态不被旧快照覆盖 |
| 同一报告身份、相同内容已经成功接受 | 复用原有报告及原文，不再增加一份持久化副本 |
| 同一报告身份的内容冲突，或本次文件校验失败、最终判为历史缺失 | 按实际原因保留诊断；本次内容不纳入已接受报告原文，已有成功记录及原文保留 |
| 本次接收尚未完成，或成功提交与否无法确认 | 依据已保存记录核实实际结果；未完成文件不能冒充已接受原文，中断恢复遵守本页规则 |

原文是成功接收结果的一部分。提交成功接收记录前，原始内容必须已经能够可靠保存并与该记录关联；接收身份、原文关联、业务合并及确认资格须形成一致的提交结果。原文保存失败时，本份导入失败，不能留下已成功接受、部分更新业务状态或推进确认的结果。

原始内容可随数据库记录保存，也可由持久化文件承载，具体组织在实现设计中确定；无论采用哪种方式，成功记录都必须能够可靠取得它对应的完整原文。独立文件尚未取得成功接收资格时，仅属于本次处理中间资料，不能作为之后自动应用的报告。恢复时仍按[报告导入中断后重新导入](#报告导入中断后重新导入)处理。

原文及其接收记录纳入完整数据目录的备份。收到更晚的报告、累计确认已经送达主机或相关计划结束，都不释放已接受报告的原文。报告文件和视频文件分别按各自身份保存及使用。

## 本地视频的保留

第一版持续保留客户端已经完整保存并纳入管理的视频副本，供后续关联报告、核验、播放和下载。计划结束、报告得到累计确认、相机上的源产物被清理，都不触发客户端视频删除。重新创建或更新容器时，继续使用同一持久化目录中的文件。

等待对应报告或核验未通过的完整副本，也按既定导入规则保留。收到正确补发文件时，可按[重复导入同名视频](files-and-status.md#重复导入同名视频)替换已确认错误的副本；重复内容复用现有文件。未被接受的冲突文件、重复上传产生的多余副本和未完成上传的临时文件，按各自处理规则管理，不因此变成需要长期保留的完整视频。

相机源产物的清理仍通过执行计划完成，遵守[源产物清理规则](../camctl/output-cleanup.md)。用户原始选择的文件由用户管理，客户端保存的是导入形成的副本。

## 哪些数据需要备份

用户可以通过状态同步重新取得主机记录的计划和执行结果，但这些信息不能代替客户端自己的数据。例如，“明天录像”的草稿还没有导出，主机就没有这份草稿；用户保存的参数预设、人工递交标记和已经收到的视频，也无法通过状态报告重新取得。

客户端持久化内容集中位于部署目录的 `data/` 中，由单个应用容器使用。备份以整个目录为单位：

| 内容 | 备份的作用 |
| --- | --- |
| `client.db` 及其必要伴随文件 | 保留已经保存的草稿、原请求、预设、报告状态、累计确认进度及客户端操作记录 |
| `device-capabilities.json` | 保留备份时的能力说明文件，恢复后仍按既定加载规则检查和启用 |
| 已接受报告的原文件名、原始字节及接收记录 | 保留完整输入依据与对应接收结果；具体内容可以存于数据库或同一持久化目录内的文件 |
| 已保存的视频及相关持久化文件 | 保留实际文件及其与数据库记录配套的资料 |

目录内文件的具体组织在实现设计中落实，不另行把必要持久化内容放入随容器删除的临时存储。备份应用已经保存的内容；浏览器内尚未保存的编辑和未完整上传的视频，不因复制目录就变成完整、有效的数据。

第一版由部署人员按操作说明完成停机备份与恢复。日常用户仍通过网页编辑计划、导入文件和查看结果。

## 后端重启后的文件处理

容器停止或电脑重启后，内存中的上传、核验进度可能已经丢失。客户端启动时，以数据库中已经保存的文件与处理记录为依据，结合本地文件的实际情况，恢复能够继续的工作。数据库本身必须可正常使用；打不开数据库时不能依靠文件名猜测交付身份或处理结果。

例如，视频已经完整保存，但 SHA-256 只算了一半时电脑重启。客户端能够确认该文件完整可用后，从本地文件开头重新计算摘要，不要求用户重新上传。此前只上传了一半的文件则仍属于未完成上传，用户重新选择后从头导入。

按下表从上到下判断，后续各行以前面条件均不成立为前提。“完整保存”需要已有可靠的保存记录和对应文件，不能仅凭文件存在、名称正确或大小看起来合理来推断。

| 启动后能够确认的情况 | 处理与页面结果 |
| --- | --- |
| 数据库不可正常读取，无法取得可靠的保存和处理记录 | 显示数据问题，停止依赖这些记录的恢复，不创建虚假的接收或核验结果 |
| 已登记为完整副本的文件缺失、不可读，或保存、替换是否完成无法确认 | 显示具体问题，保留记录和诊断，不猜测成功；问题解决后再依据实际条件继续处理 |
| 已确认上传没有完成 | 显示导入中断，用户重新选择文件后从头上传；部分文件不能作为完整副本使用 |
| 完整文件可用，已有可靠保存的核验结果 | 沿用已有结果，不在每次启动时重新扫描全部视频内容 |
| 完整文件可用，核验尚未完成，已有有效的报告映射 | 自动恢复核验，从本地文件开头重新计算摘要，再按报告检查大小和摘要 |
| 完整文件可用，核验尚未完成，尚无有效报告映射 | 保留文件，显示等待对应报告；报告成功应用后自动继续关联和核验 |

沿用结果适用于已经确定的核验成功或内容不符。文件读取失败、摘要尚未算完等情况不构成已完成的内容核验，不能因此认定视频内容错误。已有成功记录但当前文件明确缺失或不可用时，也应显示文件的实际问题，不能继续把它展示为可用视频。

恢复后端处理使用原来的文件、交付关联及导入记录，不创建新的主机动作、产物或交付身份。视频的本地可用性与主机报告中的执行结果分别保存；本地文件问题不改写相机录像结果，也不撤销已经可靠应用的报告及其累计确认资格。

重新计算摘要的进度可以从头开始，已经保存的完整视频无需重新上传。文件保存与记录提交、错误副本替换等步骤之间的中断，仍须依据相应完成事实判定；具体持久化步骤和临时文件整理在后续实现设计中落实，不能用缺少记录代替完成证据。

## 报告导入中断后重新导入

报告导入期间后端意外停止时，已经成功应用的报告及完整覆盖进度保留。尚未完成的部分显示导入中断，等待用户重新选择原来那批报告；用户原文件一直保留，无需向传输部门重新索取。

例如，客户端同时导入报告 2、3，报告 2 已把完整进度推进到 40，处理报告 3 时后端停止。用户重新导入两份文件，报告 2 按已接受的重复报告处理，报告 3 继续接受正常检查并应用，最终到 45。若报告 3 在停止前实际上也已提交成功，重新导入时同样识别为重复。

成功接收记录、与已可靠保存原文的关联、报告中的实体合并、完整覆盖进度及相应确认资格必须在同一次数据库事务中保存。不能先把 `report_id` 记为已成功接受，再分别保存原文依据、业务内容和确认位置，否则重试可能把尚未完成的报告误当作重复并跳过。

恢复判断依据实际保存结果，不能把网页最后显示的“处理中”当作未提交的证据。按表从上到下判断，后续各行以前面条件均不成立为前提；前三行以数据库可正常读取为前提：

| 可确认的情况 | 处理 |
| --- | --- |
| 某份报告已完整提交，网页尚未收到结果或整次导入仍未结束 | 保留该份成功结果；再次收到相同报告时按重复规则处理，不撤销或重复应用 |
| 上传或处理未完成，且没有该份报告已成功接受的记录 | 显示导入中断，等待用户重新选择文件；启动不自动应用这些未完成报告 |
| 某份报告已有明确的校验失败或历史缺失诊断 | 保留诊断；它不是成功接收记录，用户再次导入时按当时状态重新检查 |
| 数据库不可读，无法确定提交结果 | 显示数据故障，不猜测已完成或未完成；数据库恢复可用后再依据实际记录判断 |

用户可以重新选择整批原文件，不必自己筛出中断位置。每次重新选择均按[同次导入多份报告](files-and-status.md#同次导入多份报告)检查覆盖关系，以当前已经保存的完整状态为基础，先处理可衔接的报告，再对剩余报告判定缺口。已成功应用的报告与本次新报告可以同时出现，单份失败仍不撤销其他成功结果。

尚未完成的报告不得用于视频关联或累计确认。已经判定缺口并抛弃的报告也不作为重启后自动应用的任务。视频中断恢复仍按上一节处理，不因需要重新导入报告而重新上传完整保存的视频。

仅网页断开连接而后端仍在处理时，不能直接推断后端已经中断。重新打开网页或重新导入时，客户端仍依据后端的实际处理与保存结果展示状态。

## 停机备份

1. 停止客户端应用容器，确认后端已停止对 `data/` 的写入。仅关闭网页不能达到这一目的，因为后端可能仍在核验文件或保存结果。
2. 在容器停止期间，将整个 `data/` 复制到独立的备份位置；复制期间也不手工修改源目录内容。
3. 确认整次复制成功后，将该副本作为一次完整备份保留，再按需要启动原客户端。

数据库、能力说明和视频来自同一次停机后的目录内容，不从不同备份中拼接。仅复制 `client.db` 无法保留所有视频；只复制视频也无法恢复草稿、原请求和报告确认进度。备份位置应位于被复制的 `data/` 之外。

## 从备份恢复

1. 准备客户端部署包和选定的完整备份，保持目标客户端容器停止。
2. 若目标位置已有 `data/`，先移开并保留，再将选定备份完整还原为本次使用的 `data/`。恢复到独立的完整目录，不把备份内容零散覆盖到仍含其他数据的目录里。
3. 确认目录复制完成，检查挂载位置及应用所需的读写权限，再启动客户端。
4. 确认客户端能够读取数据库和已有文件，按正常启动规则加载能力说明，并展示备份中已经保存的状态。

恢复以选定备份为准。备份之后新增的草稿、导出记录和文件不在该副本中，不能把它们描述为已经恢复。恢复操作不重新递交已有计划，也不重新生成原请求身份。

若恢复的是较旧备份，客户端保存的报告进度也会回到该备份中的位置。之后收到无法衔接的增量报告时，按[缺少历史时怎样使用](files-and-status.md#缺少历史时怎样使用)显示异常并指导状态同步；不能仅因已经还原目录就声称取得了主机最新状态。旧备份里的累计确认也不会使主机的确认位置倒退，具体规则见[全局状态同步](../camctl/status-sync.md)。

## 操作结果与失败处理

按表从上到下判断；后续各行以前面条件均不成立为前提。

| 条件 | 处理 |
| --- | --- |
| 容器仍在运行，或不能确认后端已停止写入 | 不开始目录备份或恢复，先确认应用已经停止 |
| 复制尚未完成、失败或中断 | 本次副本或恢复目标尚未完成，不能当作成功结果；恢复目标复制完整前不启动客户端 |
| 完整复制后，目标挂载位置或权限不满足要求 | 保留目录，修正部署问题后再启动，不以空目录替代 |
| 完整复制后，数据库或必要文件无法正常使用 | 明确报告数据问题，保留诊断及已有副本，不能把打不开的数据当作空数据 |
| 数据可正常读取，能力说明加载失败 | 按既有能力加载规则显示错误；已保存的业务数据保留，可用功能仍按各自条件开放 |
| 完整复制且相应数据可正常使用 | 备份或恢复完成；恢复后展示的仍是该备份实际包含的内容 |

应用的备份恢复说明须覆盖这些结果。能力说明加载失败、数据无法读取与复制未完成是不同问题，不能统一显示为恢复成功或数据为空。

## 验收依据

- 对新接受报告、已被当前覆盖包含的旧报告和相同报告重导，验证分别保存对应原始字节或复用已有原文；计算原文字节的摘要，确认仍与原文件名一致。后续报告、累计确认及计划结束不改变原文。
- 对冲突、校验失败和缺口报告，验证只保留诊断，不纳入已接受原文；原文保存失败时，接收身份、状态合并和确认不留下部分成功。完整备份恢复后，能够取得与接收记录对应的原文件名和字节。
- 连续修改并保存草稿和预设后重新打开，分别取得最新保存内容；草稿的不完整输入可以恢复，预设非法输入不覆盖原值。保存失败和结果未知分别展示，不能让网页输入冒充已保存内容。
- 更新预设或复制新草稿后，验证已有导出请求仍保留固定身份与正文、其他草稿保留自身参数；从完整备份恢复时，各记录来自该备份，不混入之后的编辑。
- 在计划结束、报告得到累计确认、相机源产物被清理以及重新创建容器后，验证客户端纳入管理的视频仍保留且可按实际核验状态使用；相同内容复用与正确补发替换仍按导入契约执行。
- 在空数据目录和仅有能力说明的目录启动，确认显示初始化页面；点击后创建数据库并进入正常界面，初始报告进度为0。未点击前不因普通启动创建业务数据库。
- 已有正常库时直接读取既有数据；覆盖库缺失但有业务文件、库损坏或未完整初始化、访问失败与挂载位置错误，确认不覆盖既有文件或自动建立替代空库。
- 重复点击初始化，或页面显示后数据库条件发生变化，确认后端重新检查并保持单一正常数据库；创建失败或结果未知时不显示成功，已有能力说明不被改写。
- 在视频上传中断、完整保存但核验未完成、等待报告及核验结果已保存时停止并重启后端，覆盖文件处理表，确认分别要求重新上传、自动核验、继续等待或沿用已有结果。
- 对完整保存且等待核验的视频，重启后自动从本地文件开头计算摘要；对已有可靠结果的视频，确认不会因启动而读取全部内容重算摘要。结果及交付身份保持一致。
- 文件缺失、不可读、保存情况未知或数据库不可用时，显示各自诊断，不补造完成记录，不修改主机执行结果，不撤销已经可靠保存的报告确认资格。
- 分别在报告应用事务提交前、提交后但网页未收到结果时中断后端，再导入原批报告，验证只应用尚未接受的内容，已保存的成功结果和覆盖不倒退；成功接收身份不能早于业务状态单独提交。
- 在同批报告部分成功、后续处理中断时，验证页面保留实际结果并提示重试，重新导入仍按整批覆盖检查；失败或缺口诊断不被当作成功身份，未完成报告不用于视频映射或确认。
- 准备已保存草稿、导出记录、人工递交标记、报告状态与确认位置、能力说明和视频，停机复制完整目录，在独立部署位置恢复，检查内容及关联保留。
- 在备份后增加一份草稿，再恢复该备份，确认展示的是备份时的内容；恢复不产生新的执行计划提交或请求身份。
- 覆盖应用未停止、复制中断、权限或挂载错误、数据不可读与能力加载失败，验证各自诊断及数据保留，不能宣称部分复制成功恢复全部内容。
- 恢复旧备份后导入较晚的增量报告，按实际覆盖判断缺口、保存原有可用状态并引导同步，不绕过累计确认要求。
