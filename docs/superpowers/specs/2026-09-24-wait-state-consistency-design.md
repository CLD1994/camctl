# 逐项等待与来源结束的事务边界

## 适用范围

本设计定义动作内部逐项等待的保存原则，以及来源拍摄动作结束时，与依赖动作的来源等待共同提交的行为契约。它供数据库规格细化、事件转换登记和后续实施计划使用。

依赖动作包括取回和范围清理。来源拍摄动作可以成功、失败、过期或取消；是否结束与是否产生可用产物分别判断。文件选择、取回资格、设备操作、复制、清理和交付仍遵守各自流程。

相关基础规则见[来源与取回](../../camctl/database/sources-obtaining.md)、[等待来源结束](../../architecture/obtaining-outputs.md#等待拍摄动作结束)、[数据库事务](../../camctl/database/transactions.md)和[历史格式](../../camctl/database/history-formats.md)。物理字段及报告展示的细化范围列在文末，不作为本设计已经固定的实现方式。

## 内部等待、报告数据与界面展示

一个动作可以包含多项分别推进的工作。每项等待均须能定位所属动作、具体工作、等待条件，以及适用的来源、文件或占用责任。同一动作的两个读取流程可以分别等待不同的重试间隔，不能以一个动作级剩余时长覆盖二者。

内部逐项保存服务于正确执行、恢复和诊断。公共报告提供哪些详情由报告契约确定，客户端展示哪些内容由用户需求确定；内部存在一条等待记录，不自动要求报告增加字段或界面显示该记录。

等待记录表达可靠判定并保存的等待事实。设备活动、文件读取保护、操作预算、取消和时间资格仍由所属业务记录决定。没有有效等待记录只表示没有已保存的等待原因，不单独授予执行资格；等待解除也不证明后续工作已经开始或成功。

## 输入、输出与不变量

来源结束操作接收来源动作身份及满足其结束条件的可靠事实。事务内核对原状态、取消事实、正式产物登记条件和来源依赖；不能以事务外缓存的旧判断覆盖新提交。

一次成功提交提供以下可观察结果：来源动作具有可靠终态；依据现有规则共同登记的正式产物及关联完整；所有现存的“等待该来源结束”记录不再生效；来源和受影响动作的历史及报告变化关联完整。

以下不变量同时成立：

- 同一完整已提交状态中，来源已经结束时，不存在仍生效的“等待该来源结束”记录。
- 来源结束只解除对应来源等待，不自动解除等待设备、其他来源、重试间隔或其他独立条件。
- 来源失败、过期或取消也属于结束。依赖动作依据正式产物及自身结果继续判定，不直接复制来源的终态。
- 依赖动作的取消和已有终态保持有效，来源随后结束不重新开启其普通工作。
- 每项等待变化具有可恢复的历史；影响动作报告内容时，该动作获得相应业务变化关联，即使动作主表的状态没有变化。
- 已登记报告使用原冻结依据，后续业务变化不改写同一报告的字节。

## 来源结束的共同提交

来源拍摄动作 A 被取回 C、D 引用时，A 的结束按以下顺序处理：

1. 在写事务中核对来源结束资格及可靠结果，执行原规则要求的终态、正式产物、来源关系和适用计划状态更新。
2. 沿来源关系及等待记录定位依赖者，解除其对 A 结束的有效等待。只修改能够由本次事实与事务内已有记录确定的直接变化。
3. 保存各项独立事实的历史、受影响对象的关联、累计计数及适用业务变化序号。一个事务可以包含多个事件，不把它们合成缺乏业务含义的任意行修改。
4. 提交事务。提交成功后唤醒相关未完成责任，并安排报告维护。

报告可以采用提交前或提交后的完整历史边界，不采用事务中间位置。不能把来源终态与等待解除拆成多个提交，再假定异步通知足够快而不会被报告读取。

共同提交不执行文件选择的完整后续流程，不等待设备调用、文件复制、媒体处理、删除或报告文件生成。取回与范围清理被唤醒后，分别重新检查自身资格，并按原规则选择、读取或清理。报告维护和设备控制继续异步推进。

## 状态分类

以下分类中的“等待”均特指等待某个来源拍摄动作结束。按表中顺序选择适用分区；状态库错误优先按错误规则处理，不进入普通业务分支。读取已经提交的状态时，若发现来源已结束却仍有有效来源等待，应视为不变量被违反，不能将其当作普通等待继续执行。

| 条件 | 等待记录的处理 | 后续行为 |
| --- | --- | --- |
| 读取或保存所需事实失败，或结果无法可靠解释 | 不推测创建、解除或完成等待 | 按状态库错误及事务核实规则处理 |
| 依赖动作已经进入终态 | 不创建或重新启用等待；动作进入终态时应已停用自身等待 | 保持原终态；发现终态仍有有效等待属于一致性错误 |
| 依赖动作取消已生效，普通来源处理责任已结束 | 在取消事实所属事务中解除该普通来源等待；来源随后结束不重新启用 | 必要收场按其独立责任继续，不恢复普通文件选择 |
| 依赖动作尚未进入来源判定阶段，且没有已建立的来源等待 | 不凭来源关联的存在创建有效等待 | 取得相应阶段资格后，按当时已提交状态判断 |
| 依赖动作仍承担来源处理责任，已进入判定阶段，来源尚未结束 | 创建或保持该来源的等待；事实未变时不重复写历史 | 等待来源变化或其他影响资格的事件 |
| 来源在依赖动作首次保存等待判断之前已经结束 | 不创建“等待来源结束”的有效记录 | 依赖动作按自身资格处理已确定的来源结果 |
| 来源从未结束变为终态，已有依赖动作等待该来源 | 与来源终态共同解除全部对应有效等待 | 提交后唤醒依赖者；执行仍受各自资格约束 |
| 其他来源结束或其他等待条件变化 | 仅更新实际受影响的等待 | 未解除的条件继续保留 |

创建等待与来源结束均在可靠的写事务中检查现状。两者交错时：等待先提交，则来源结束事务解除它；来源先提交，则后续判断不创建过时的等待。取消与来源结束按同样的提交顺序规则处理，不能用迟到的通知覆盖已经生效的取消。

## 失败与恢复

数据库事务状态与设备已经发生的行为分别解释。

| 保存阶段或结果 | 已可靠保存的范围 | 恢复要求 |
| --- | --- | --- |
| 尚未提交，或确认整个事务已经回滚 | 本次来源终态及等待解除均未成为已提交事实 | 按原流程恢复和核实设备、产物及结束依据；不把回滚解释为设备操作没有发生，不因此重复启动拍摄 |
| 提交成功，但依赖唤醒或报告通知尚未处理 | 来源终态、等待解除、历史及对象关联均已保存 | 正常恢复根据未完成任务和可靠业务状态继续工作；报告维护发现尚未覆盖的变化，不依赖丢失的内存通知 |
| 提交结果未知 | 是否整体保存尚待核实 | 沿原稳定操作身份核实，确认前停止依赖步骤；不另建身份盲目重做 |
| 数据库事实可靠，报告生成或发布失败 | 来源终态和等待解除保持有效 | 保留未完成报告责任，后续按报告维护规则处理；不阻止仍具备条件的设备工作 |

进程恢复既检查有效等待，也检查未完成动作及其具体工作。已经解除等待但尚未开始下一步的任务必须能被发现；只查询仍有效的等待记录不足以恢复调度。

## 历史与报告重建

逐项等待属于其所属动作的历史状态。创建、详情变化和启用状态变化均保存可逆前后值；对象事件关联、历史计数和适用报告业务序号与投影共同提交。重复检查没有事实变化时不创建重复历史。

动作快照包含恢复其等待说明所需的记录。报告从冻结边界处恢复动作及其等待记录，再按报告契约生成说明，不读取其他动作的最新状态补算旧名单。历史回放只恢复状态，不发出设备命令，不启动复制或清理，也不重发正常运行中的调度通知。

同一动作的多项等待按完整身份保存。报告选择、去重和排列依据由公共报告规则定义；生成批次或数据库行返回顺序不能改变报告字节。

## 验证要求

验证依据本设计的不变量独立构造反例，至少覆盖：

1. 来源成功、失败、过期和取消分别解除对应等待，依赖动作不继承来源的终态。
2. 一个来源有多个等待者；一个等待者还有其他未结束来源。前者全部解除对应等待，后者保留其他等待。
3. 创建等待在来源结束之前及之后提交，均不留下“来源已结束但仍等待其结束”的状态。
4. 取消先提交、来源结束先提交、依赖动作已终态等顺序，不重新开启已经结束的工作。
5. 来源结果和等待解除共同提交前后中断、明确回滚、提交结果未知，以及提交成功但通知未处理时中断。
6. 报告读取在共同提交前后发生，只取得对应完整状态；重建旧报告保持原字节。
7. 从初始状态回放、从快照正向恢复、从当前状态逆向恢复所得等待记录一致。
8. 动作主表状态不变但等待名单变化时，该动作仍被报告选择；重复通知没有重复事实，不重复消耗尝试次数。
9. 同一动作的两项工作具有不同等待条件或重试时长，保存与恢复时互不覆盖。

软件集成验证使用真实 SQLite 和受接口契约约束的设备替身，不连接真实相机。目标主机上的事务耗时和资源占用单独测量。共同提交按相关索引定位并分批读取记录；分批读取不拆分本应共同提交的事务。不能为了缩短事务而先提交来源终态、稍后才解除等待。若实际依赖规模使这项保证无法满足既定运行边界，应带测量证据重新讨论。

## 待细化的结构与范围

以下内容属于后续设计核对，不能直接当作执行者可以自行补全的字段规格：

- 建议使用统一等待明细表，暂称 `action_waits`。每项记录怎样关联动作内的具体工作，哪些工作在等待建立前已有操作流程、拷贝或处理项身份，仍须逐类核对。
- 等待来源和读取文件的成员身份、同一具体工作的设备阻挡者变化、重试再次发生时的记录复用，以及各类字段组合和唯一约束，须形成完整分类。
- 九类等待全部具有自身可恢复依据后，再决定移除 `waiting_mask`、`waiting_boundary_event_id`，并将阻挡者和观察时长迁入明细。字段替代须覆盖事件、快照、查询和校验规则。
- 正常设备占用沿已有活动或拷贝责任追溯所属动作。设备状态未知与活动归属不明分别按原恢复规则核对，不能仅因原字段可空而新增普通等待分支。
- 本设计固定来源结束的共同提交规则。设备机会、读取依赖、重试和报告处理等其他触发点，须逐一确定哪些变化能够直接共同保存，哪些后续处理需要独立推进。
- 内部逐项等待不直接决定公共报告增加哪些字段。报告汇总、逐项关联和界面展示分别按需求细化。
- 产物是否保留独立清理进度，以及取回失败项、共享文件和其他数据库评审问题，不由本设计一并决定。

本设计不包含生产实现、完整建表 SQL 或执行计划。结构细化完成后，再将字段组合、事件转换、责任入口和上述验收逐项落实到实施计划。
