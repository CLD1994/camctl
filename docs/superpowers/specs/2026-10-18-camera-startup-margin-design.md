# 相机启动余量与 OSMO 最小延时间隔设计

## 目标与适用范围

启动余量按型号及任务类型声明。OSMO 360 II 普通录像采用 **0 毫秒**启动余量，Action6 普通录像保留 **1000 毫秒**；OSMO 原生延时继续采用 **1000 毫秒**。普通录像保留至少录够目标时长、允许略多录的要求；设备自行计时的原生延时在核实自然结束之前等待其声明的余量。OSMO 的新延时请求从 2 秒间隔起，Action6 保留自己的间隔域。

本设计修订[普通录像启动与计时](../../architecture/camera-recording.md#录像启动确认)，并补充[OSMO 完成与正式接入设计](2026-10-18-osmo360ii-capture-completion-design.md)。启动余量、命令确认和新旧任务兼容规则由本页维护；参数、计时、恢复和媒体消费者采用同一规则。原片、状态库及已有任务身份保持不变。

OSMO 将 1 秒间隔按 2 秒执行，依据为[现场确认](../../camctl/verification.md#osmo-最小延时间隔与两款相机录像启动延迟的现场确认2026-10-18)。Action6 普通录像采用命令成功与实际开始之间延迟不超过 1 秒的运行假设；OSMO 普通录像采用可靠命令确认后按原目标时长计时的运行假设。原生延时采用独立的保守余量。上述规则均不提供独立测得的首帧时刻或跨固件保证，实际原片时长按[实机记录](../../hardware/osmo360ii-record-duration-report.md)核对。

Action6 的设备访问继续遵守[固件修复暂停安排](../plans/2026-10-10-camctl-real-camera-demo.md#当前真机验证安排)。启动余量规则不使尚未提供正式工厂的 Action6 原生延时自动进入能力目录；其正式接入仍须满足原有设备与软件门槛。

## 用户目标与内部计时

用户参数中的目标时长、设备实际收到的目标时长、主机启动余量及结果处理等待分别表达。普通录像请求 10 秒时，媒体达标及异常裁剪目标仍为 10 秒；原生延时请求采集 300 秒时，下发相机的采集时长仍为 300 秒。

启动余量属于主机执行规则，不增加 `effective_params` 中的目标值，不改写 `6c` 时间负载，不改变编码格式，也不把自然结束余量改成 31 秒。正常录像的轻微多录继续沿原规则处理，不为精确裁成目标时长而增加正常媒体拷贝。

| 计时量 | 固定含义 | 对其他量的影响 |
| --- | --- | --- |
| 目标时长 | 用户要求的录像或设备有限采集目标 | 保存原值，媒体检查和修复继续使用它。 |
| 启动余量 | 驱动按型号和任务声明的非负整数毫秒等待 | 只参与适用的正常停止或自然核实时点。 |
| 自然结束余量 | 设备目标后用于自然结果核实的原等待规则 | 保留独立字段和原值，不吸收启动余量。 |
| STOP 后文件等待 | 可靠停止确认后的单独文件处理等待 | 从原 STOP 依据执行，不叠加启动余量。 |
| 部署额外等待 | 本次等待实际采用并保存的配置值 | 未完成等待按[既有配置规则](../../camctl/database/operation-fields.md#等待未知结果和占用恢复)采用新值时重新保存预计时点；等待已完成后不重开。 |

## 命令确认与录像开始语义

普通录像新任务的成功 START 响应只提供本次命令已被设备接受的可靠依据。记录须保留原尝试身份、实际返回、响应时刻及其时钟来源；命令派发、输出未知或结果丢失不能代替这份依据。

新任务使用 `StartReturn.SENT` 表达上述语义；它仍要求相应驱动识别完整正常响应，不由本地管道写入成功推导。普通录像不得继续因动作类型固定推导 `STARTED`。驱动响应、活动能力、受理定义、开始处理、历史与恢复共同识别新语义。

命令确认时点加启动余量得到的是当前运行假设下用于保证后续录制时间的保守计时起点，不是实际首帧时刻。只得到命令确认时，保存 `sent_at`，`started_at` 保持未知；不得把确认时点或确认后 1 秒写成直接设备开始观察。可靠的独立设备开始观察仍按其原证据记录，不由软件等待生成。

设备从 START 派发起继续被本任务占用。实际开始状态未知或启动余量尚未经过，不表示设备空闲，也不允许另一项拍摄取得设备。主机已经取得可靠命令确认后，可以按下述有界规则安排正常停止，无须增加未定义的设备查询或 ADB 保活。

## 正常录像与自然延时

令 `A` 为原可靠命令确认锚点，`S` 为原启动余量，`D` 为原目标时长，`R` 为原自然结束余量，`E` 为本次等待实际采用并保存的部署额外等待。

| 任务及控制方式 | 正常处理时点 | 该时点不提供的事实 |
| --- | --- | --- |
| 主机停止的普通录像 | 正常 STOP 不早于 `A + S + D`。OSMO 新任务 `S = 0`，Action6 新任务 `S = 1 秒`。 | 不表示第一帧出现在 `A` 或 `A + S`，也不保证停止调用零延迟。 |
| 设备自行结束、可靠 SENT 的有限延时 | 自然结果核实不早于 `A + S + D + R + E`。当前 OSMO 为 `S = 1 秒`、`R = 30 秒`。 | 不表示设备实际多采了 1 秒，不提供精确帧数、参数回读或直接设备结束观察。 |

同一会话的录像计时使用本次响应接收时取得的单调钟，不将事务保存、目录读取或再次调度的时刻作为新起点。延时仍在主机异步等待，到期之前不轮询相机、读取采集中目录或保活。

例如普通录像目标 10 秒时，OSMO 新任务在可靠确认后至少经过 10 秒，Action6 新任务至少经过 11 秒，才按正常到时流程 STOP；停止响应和文件等待另行处理。OSMO 延时目标 300 秒且没有部署额外等待时，可靠 SENT 后至少经过 331 秒才进入自然文件核实；设备收到的目标仍为 300 秒。

超过核实时点只是相应文件完成运行假设的一项前提。完整目录、原基准归属、非零必要原片和最终集合仍须分别核实；启动余量不替代任何产物规则，也不使错误、空集合或读取失败自动通过。

已经取得的实际证据若明确违反启动上界或连续录制假设，不能继续使用原等待证明已经录够目标；沿相应异常停止、恢复及实际媒体核实规则处理，保留原控制结果，不补发 START 或另建拍摄掩盖它。

## 取消、未知结果与恢复

| 原任务实际情况 | 控制与计时规则 | 结果边界 |
| --- | --- | --- |
| START 尚未派发且取消生效 | 阻止 START，不等待启动余量。 | 按未派发事实结束，不补造设备活动。 |
| START 已派发，结果仍在途或未知 | 沿原尝试对账及有限收场；不由 1 秒到期补造确认，也不重发 START。 | 保留未知与必要占用。 |
| 已可靠接受 START，启动余量期间取消 | 立即进入适用 STOP 流程，不等余量或目标时长；沿原停止预算执行。 | 这段期间仍是设备占用期，不按未开始任务释放。 |
| 普通录像正常到时 | 沿原确认锚点、冻结余量与目标计算正常 STOP。 | 原停止及文件完成规则继续适用。 |
| 原生延时取得可靠 STOP 确认 | 执行原独立 STOP 文件等待；不再追加启动余量或等待原目标全长。 | 保存允许保留的实际文件，不补造完整目标采集。 |
| 有限延时第一次 STOP 失败或未知，已进入有限取消收场 | 保存原 STOP 失败，不立即重试；自然核实沿原 `A/S/D/R` 和本次实际采用的 `E` 使用同一时点公式。 | 充分核实后目标 `canceled`、取消动作 `failed`；只保存独立活动结束与释放依据，不写目标采集完成。 |
| 相机会话或主机进程重启 | 保留原任务、参数、确认、启动余量和预算；未完成等待采用新配置 `E` 时按原锚点重新保存预计时点，再按可靠日期时间与恢复资格计算剩余责任。已完成等待不重新打开。 | 不跨会话比较单调钟，不重新等待整段目标或在每次恢复时增加 1 秒。 |
| 缺少可靠确认，或时间／历史／结果依据不足 | 继续原异常恢复、时钟处理和有限预算。 | 不用重启时刻或当前默认值建立新起点；必要时保留未知占用。 |

取消和异常保护停止优先于正常到时等待。启动余量不扩大控制调用期限、不重置调用次数，也不推迟安全收场。

## 时长证据与媒体处理

从命令确认到 STOP 确认的原始经过时间，包含启动余量及可能的停止延迟，不能整体解释为已录制的内容时间。消费者须区分原始控制耗时、按声明启动上界取得的录制时间下界和实际媒体探测时长；仅有上界等待不能生成精确媒体时长。

新规则下的正常到时及可信恢复判定，须按原确认加原启动余量计算可保证的录制时间，不能把等待启动的 1 秒计入目标完成。异常多录判断不得仅因正常增加了启动余量就触发裁剪；恢复、检查与修复按原目标及其适用时长依据判定。取消发生在保守计时起点之前时，不产生负的媒体时长，也不把计算得到的零下界写成实际媒体时长；实际内容和是否录够目标按已有证据分别处理。

实际媒体检查已经取得的结果继续按其原精度判断。实际内容不足原目标时，不因采用了启动余量而标成达标；修复与失败按既有规则处理。双路 OSV 的必要流、实际音频、原片保留和修复 MP4 的发布条件不变，裁剪目标仍是 `D`。

## 冻结定义、历史与证据闭合

新任务首次受理时保存独立启动余量，内部字段名为 `startup_margin_ms`。普通录像接受精确的非负整数毫秒，`0` 明确表示不追加启动等待，并与 `SENT` 语义共同保存；有限延时采用正整数毫秒。字段不能接受布尔值、负数、小数毫秒或由读取端隐式补入。具体型号的当前值由本页适用范围定义；能力说明读取实际任务声明，不另行维护默认值。

新普通录像的确认语义与启动余量共同冻结，不能只增加余量后仍将新 ACK 解释为实际 `STARTED`。旧普通录像缺少新规则字段时保持原语义及原计时公式；已有原生延时缺少启动余量时也保持原公式。旧记录中的 `started_at` 保留原合同的确认事实，不升级为新规则下的实测首帧。缺字段不是新定义应默认使用 1000 的依据，不重写历史、原任务或原报告。新旧定义可可靠区分；非法或只有部分新规则的定义须拒绝。

| 责任边界 | 必须保持的一致性 |
| --- | --- |
| 驱动任务、受理及能力 | 驱动声明、冻结定义、参数校验及对外能力说明一致；说明目标、启动余量与实际开始的关系，不向用户新增必填的启动余量参数。 |
| 活动与开始响应 | 普通录像识别新的可靠 SENT 语义；命令确认与实际开始分别保存，旧记录仍按原事实读取。 |
| 正常计时与录像恢复 | 原确认锚点、原余量和原目标生成同一停止要求；缺乏可信时间时沿原异常路径处理。 |
| 延时预计时点与完成上下文 | 正常和有限取消均使用原 `A/S/D/R` 及实际采用的 `E` 计算预计时点；引用同一次可靠等待依据，完成后复用原等待事件及关联结果页。 |
| 结果页保存与独立守卫 | 核对原定义中的启动余量、确认来源、等待时点和实际完成上下文；不能只在外层等待加 1 秒。 |
| 有限取消结束依据 | 独立保存并校验原启动余量及完整公式，原 STOP 失败和目标未完成事实不变。 |
| 历史、重放及提交未知 | 原事件来源与冻结定义参与同样校验；重送保持原键和完整输入，不换锚点或重新调用设备。 |
| 媒体与报告 | 目标时长保持原值，控制时间与内容时长分别表达；不填造实际开始或精确媒体时长。 |

预计时点计算还须检查精确整数与持久表示的上限，不能靠舍入或溢出后的值通过。录像参数上限和延时完整时间域在增加余量后仍需核对其可表示性；若某个新请求无法可靠表达，必须在设备调用前明确拒绝。

## OSMO 最小间隔与新旧请求

间隔允许值按型号从同一个权威参数定义派生。OSMO 的新请求排除 1 秒，以 2 秒为最短允许值；其余已定义间隔和采集时长不变。Action6 保留自身允许值，时长严格大于间隔的条件继续适用。修订参数域不改变已经冻结的时间字节编码格式。

能力说明、客户端选择与精确校验、主机受理、命令前校验、默认样例、安装资源和诊断消费者读取相应型号的定义。OSMO 新输入为 1 秒时明确拒绝，不静默改成 2 秒；客户端已有草稿或预设保留原值并提示修正，不替用户保存另一个值。

已受理的 OSMO 1 秒任务按其原有效参数、原负载及原确认依据继续恢复，不重新套用当前新请求域。历史中可以同时存在“原请求为 1 秒”和“用户后来确认设备按 2 秒执行”两项事实，不覆盖原输入或补造参数回读。

## 验证与交付边界

软件验证须覆盖按型号的最小值、非法精确数值、客户端与主机结论一致、安装资源、旧 1 秒任务恢复，以及新旧执行定义的读取与拒绝。启动余量还须覆盖成功确认与未知结果、正常到时、余量期间取消、停止失败、同会话计时、重启恢复、实际时长不足、正常轻微多录和异常裁剪目标。

延时验证须同时核对预计时点、真实等待事件、完成上下文、跨页与跨运行复用、有限取消依据及历史守卫；覆盖未完成等待采用新配置 `E` 后保存新预计时点、已完成等待不因配置变化重开，以及冻结的 `S` 始终不变。错误活动、错误余量、未来事件、未实际等待及重复加余量均应被拒绝。安装版联合链须验证原用户目标和设备下发目标不变、正常录像停止至少等待 `S + D`、自然延时核实至少等待 `S + D + R + E`，以及唯一 START、独立取回和累计 ACK。

OSMO 真机补测只覆盖新最短间隔和启动余量引出的实际缺口，延时目标继续使用 300 秒；已有原片与验收记录保留。Action6 可以运行不访问设备的软件验证，实机验收继续等待固件修复。软件、安装物与实机结果分别记录，既有 331 秒之前的样本不改写成已经采用新余量。

实现进度和新增验证由[后续修订入口](../plans/2026-10-18-osmo360ii-capture-completion.md#新增现场事实的后续修订)维护。既有任务的通过记录不表示本设计已经实现或部署。
