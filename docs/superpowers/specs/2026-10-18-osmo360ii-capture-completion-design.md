# OSMO 360 II 拍摄完成与正式业务接入设计

## 目标与范围

OSMO 360 II 的普通录像和原生延时通过同一个内置驱动提供正式能力。客户端导出计划，C host 递交，camctl 完成拍摄与正式产物登记，再由独立取回动作交付文件和报告，客户端导入后提交累计 ACK。已受理任务的参数、设备绑定、目录基准和执行规则跨重启保持不变。

本设计补充[相机接入设计](2026-10-10-camctl-real-camera-demo-design.md)，沿用[延时驱动计划 D2—D4](../plans/2026-10-16-osmo360ii-timelapse-driver.md#d2-明确返回结束及产物契约)和[交付计划 E2—E3](../plans/2026-10-16-osmo360ii-timelapse-delivery.md#e2-正式内置合同的安装版联合验收)。普通录像作为独立合同任务加入这条交付路线，不因延时工厂完成而自动通过。

共同时间参数继续由既有生产定义维护，不缩小到已经实拍的代表值，也不要求逐项运行全部 134 种组合。Action6 继续遵守其[暂停安排](../plans/2026-10-10-camctl-real-camera-demo.md#当前真机验证安排)，不执行任何 Action6 设备访问。

## 设备证据与完成方式

[2026-10-17 真机记录](../../camctl/verification.md#osmo-360-ii-全量真机验证2026-10-17)包含普通录像两种曝光、延时两种曝光、30／60 秒长间隔、主动停止及十二份媒体核验。自然结束试验在目标 300 秒后约 330 秒读取到同 boot 的新待机回调及有效 OSV／LRF；这证明对应样本的观察结果，不证明 30 秒是固件文件封装上限。既有归档日志没有把文件关闭事件或完整文件集合与本次控制调用直接关联起来。

原生延时 START 在约 0.223—0.254 秒内返回，后续设备仍继续采集，因此这些样本不采用 `COMPLETED`。正式合同将正常响应解释为 `SENT`，不把它提升为独立的实际开始确认。工具帮助未给出省略 `-o` 时的默认值和单位；驱动继续省略 `-o`，实际调用由受管工具的有限外层期限约束。外层期限覆盖设置和 START 的完整调用，超时按原调用未知处理，不重发 START，也不把超时当作采集结束。

完成方式选择既有 `TIME_AND_OUTPUTS`，不新增状态查询接口。等待和产物保证采用下列明确运行假设；它们不是厂家协议保证，也不是由样本推导出的全部参数支持证明。适用设备、固件和工具以真机记录中的读数为依据；更换型号、固件或工具后重新核对适用性，不从相同 ADB serial 推导设备相同。

| 事项 | 本设计采用的运行假设及边界 |
| --- | --- |
| 正常设备与供电 | 设备、存储和供电正常；受管期间没有按键、手机或其他程序拍摄；文件路径不复用。发现相反证据时保留错误，不由等待覆盖。 |
| 原生有限延时 | 完整设置和唯一 START 被接受后，设备执行本次有限目标并自行结束；主机通信中断不重新启动设备任务。 |
| 自然结束后的文件 | 从可靠 START 返回时点等待目标时长再加 **30 秒**，并满足部署额外等待后，进入完整目录与产物核实。在这些运行前提下，该时点之后本次文件不再写入，最终集合不再增加。 |
| STOP 后的文件 | 普通录像与原生延时取得本次可靠停止确认后，分别等待 **30 秒**，再核实完整目录与产物。该等待与自然结束余量独立，提前停止不等待原目标全长。 |
| 普通录像控制 | 按其独立合同解释完整 `00` 为开始／停止确认，从 START 返回建立主机计时；停止重复安全性使用[当前相机的录像停止契约](../../architecture/camera-recording.md#停止命令的重复执行)。原生特殊响应不扩展到普通录像。 |
| 普通录像的辅助设置 | 两条 `simulate_device` 的完整正常退出只按命令执行被接受记录，允许推进原设置流程，不声明参数独立回读、实际码率或曝光实效。异常退出、stderr、截断及传输失败均阻止后续设置和 START。 |
| 保障范围 | 成功表示约定控制流程和必要产物规则满足，不保证逐次采集质量、实际曝光值、精确帧数或识别所有未留下明确故障证据的提前结束。最长时间组合仍保留尚无实拍证据的边界。 |

正式工厂按这组运行假设提供能力；重复采样、文件大小稳定和完整解码不扩大其保证范围。

## 产物与预览

受管范围为 `/mnt/media_rw/emulated/DCIM` 的完整递归目录。启动前保存可靠完整基准；归属只使用原基准差集，不使用相机时钟、文件编号上限或最新修改时间。基准失败时 START 为零，启动后恢复不重建基准。

OSV 是原始视频，LRF 是对应的低分辨率预览视频，两者保留原文件名、后缀和独立正式产物身份。配对规则为同目录、同一不含后缀的名称，OSV／LRF 后缀不区分大小写，名称其余部分按原字节区分；不跨目录猜测配对。同一原片有多个仅后缀大小写不同的预览时，配对不唯一，不能任取一份。临时文件和其他后缀不冒充已完成视频。没有可靠内容类型依据时 `media_type` 保持未知，不根据后缀猜测 MIME。

普通录像沿用[当前连续录像的单个源视频契约](../../architecture/camera-recording.md#当前相机的原片文件)，本设计不扩展分段重建；多个本次 OSV 是必要产物数量不合格，不任取第一份做异常媒体修复。延时不从时长／间隔推算文件数量，支持按任务完整集合登记实际形成的原片。LRF 是可选预览，缺少预览不影响满足规则的 OSV 原片进入成功候选。

参数类型声明支持预览。普通取回按既有规则选择原片或相应修复成品；预览通过既有预览筛选或明确产物 ID 取回，不把 LRF 当成第二份普通原片。结果读取先识别文件，再通过有界第二阶段关联跨页配对，不能要求同一页同时出现一对文件，也不能一次把完整目录驻留内存。

只有完整、归属可靠且唯一配对的 LRF 才登记为可取回预览；缺失、损坏或配对不唯一的可选预览分别保存实际事实，不使合格原片失效。预览未登记时，预览取回按实际缺少预览处理。成功判定与文件保留分别处理：

| 已可靠取得的事实 | 动作判定与保留 |
| --- | --- |
| 原片与预览完整、归属可靠、唯一配对且满足全部数量规则 | 按相应完成方式进入成功候选。 |
| 原片完整，但完整集合中明确缺少对应 LRF，或可选 LRF 不合格 | 按原片规则进入成功候选；不登记不合格预览，保留实际预览事实。 |
| 完整集合中只有孤立 LRF | 不将其登记为普通原片，不补造配对。 |
| 完成依据充分后，文件明确为零长度或必要类别／数量明确不符 | 保存明确不合格和实际文件事实；符合保留条件的其他文件继续保留。 |
| 调用失败、文件未完成、集合未定或配对尚未知 | 保留无法核实，不改报可靠空集合、明确缺件或成功。 |

采集结束、文件写完、目录末页、归属完成和集合齐备分别保存。成功判定要求相应完成规则已满足、完整目录已读完且原片归属可靠。失败或取消在适用有限处理结束后，按实际已知集合登记符合保留条件的文件并提交对应终态；未确定的集合、文件和活动事实继续保持未知。媒体哈希与解码属于实际取回及验收证据，不在正常录像登记前强制拷贝全部视频。

## 执行定义、完成上下文与恢复

同一个 `CameraContract` 组合 `osmo360ii_record`、`osmo360ii_timelapse` 两个任务工厂。不得在同一驱动身份下登记两个合同。两种任务使用各自命令与响应解释器，共享已经核实的文件工具；[OSMO 特定响应约定](../../camctl/timelapse-command-encoding.md#osmo-响应处理与可用接口)仍只在原专题维护。

自然延时固定 `DEVICE + SENT + TIME_AND_OUTPUTS`，保存目标时长与自然结束必要余量。停止后的文件等待在首次执行定义中独立保存；扩展现有 `file_completion_wait_ms` 的适用范围到声明支持停止的延时任务，不用自然结束余量替代它，也不在恢复时读取新驱动常量补旧规则。声明该等待时必须是精确的正整数毫秒；零值、缺失、非法类型与旧定义分别校验，不将零改写成默认等待。

必要产物规则同时固定原片数量和非零长度。普通录像恰好一份 OSV，延时至少一份 OSV，均不能由孤立 LRF 满足必要原片类别。扩展既有规则的可选 `min_size_bytes` 保存非零长度门槛；旧规则省略该成员时保留原语义。受理、保存、历史、恢复和实际检查消费同一份冻结规则。`preview_supported` 表示参数类型支持可选预览。

新 OSMO 延时任务另将 `cancel_completion_policy=finite_device_end` 固定到原执行定义，表示 STOP 未确认后仍可按原有限任务结束责任进行取消收场；该字段只适用于上述有限、设备自行结束的任务组合。未声明此字段的旧任务继续原取消契约，不因驱动升级获得新的等待或释放占用语义。字段和允许值由同一内部类型定义维护，Schema、受理、历史与恢复从它消费。

处理模块向结果读取器传递具有明确种类的完成上下文。上下文来自原任务、原调用及可靠历史；驱动不读取业务库猜测任务种类或运行阶段。

| 上下文种类 | 必须携带及核对的依据 | 结果取得条件 |
| --- | --- | --- |
| 普通录像 STOP 后完成 | 原活动、原 STOP 结果事件、原完整停止结果、首次固定的停止后等待规则及已存在的真实等待页引用 | 原停止确认可靠，停止后等待完成；分页复用原等待来源。 |
| 原生延时自然结束 | 原活动、固定执行定义、原可靠 SENT 与等待完成事件，实际采用的等待规则 | 原有限目标与必要等待满足，再核实文件和集合；不生成设备直接完成观察。 |
| 原生延时提前 STOP | 原活动、原 STOP 结果事件、原完整停止结果及独立固定的停止后等待规则 | 先满足停止后等待，再核实已经生成的完整文件；不虚构原目标已完成。 |

三种上下文有明确种类和完整身份；两个停止上下文均引用原实际等待来源，自然上下文不得携带伪造 STOP。旧普通录像上下文按其原格式继续读取。

停止后等待采用首个结果调用内的有限等待，计时从该调用中实际等待开始取得本次运行的单调钟，严格晚于原可靠 STOP 返回；因此保证至少等待声明的时长，不声称恰好在 STOP 后第 30 秒结束。完整结果调用期限显式分为“本次仍需实际执行的停止后等待 + 配置中的设备结果读取预算”。例如设备读取预算默认 10 秒、尚需完整等待 30 秒时，完整页调用期限为 40 秒，等待不挤占设备读取预算，也不静默修改部署配置。自然结束的目标与余量等待仍由主机处理模块执行，不消耗结果读取轮次。

已可靠保存的实际等待页跨分页和跨运行复用，不重复等待。等待尚未完成或完成回执尚未可靠保存时，先核实原申请；没有可复用完整等待依据且新调用已获原有限预算时，保守重新执行停止后等待，不跨运行累加单调钟，不重等原采集全长。调用、页保存及有限尝试次数始终保留原责任。

结果分页的端口、调用期限装配、保存和恢复消费者共同识别三种上下文；同时扩展单文件完成保存、结果页守卫、等待来源识别及历史回放，不能仅修改解释器。引用的事件必须属于原活动和原调用，等待规则必须与原冻结定义相符；实际等待页与复制页分别表达。提交未知先核实原完整申请，不能重新列目录或生成新等待事实掩盖原结果。错误活动、错误 STOP、错误规则、未来页引用及自然／停止上下文混用均拒绝。

自然延时在预计结果核实前只在主机异步等待，不轮询 ADB、保活或读取采集中目录。重启按既有可靠日期时间恢复规则计算剩余等待，不跨运行比较单调钟，也不重新等待已经可靠完成的阶段。START 已尝试但没有可靠发送时间时保留启动未知和必要占用，不创建虚构的等待锚点。

## 低功耗期间的取消与异常

ADB 低功耗断开与拍摄失败分开。控制、文件核实及取回沿各自原有限预算执行，预算不因重新调度、会话重启或 USB 重现而清零。

| 原任务阶段及实际结果 | 处理 |
| --- | --- |
| 尚未发送 START，取消已经生效 | 停止后续设置及 START，按实际派发事实收场。 |
| 原生延时已可靠发送，STOP 取得正常停止确认 | 保存原停止结果，等待独立的停止后文件余量，按原取消规则保存允许保留的完整文件。 |
| 声明新取消策略的原生延时已可靠发送，STOP 调用失败或结果未知 | 保存第一次实际 STOP 的失败／未知，并可靠结束该 STOP 责任为失败，不再使用其剩余次数立即重试；在同一转移中建立原有限任务的取消后自然收场责任。不重发 START，也不宣称已经物理停止。 |
| 上述取消任务达到原自然结束核实时点，取得充分文件、归属与集合依据 | 使用原有限结束运行假设结束取消后收场，保存真实等待与文件事实及有界的占用释放依据；目标动作最终为 `canceled`，发起的 `cancel_task` 因原停止失败最终为 `failed`。原 STOP 失败不改写为成功。 |
| 缺少可靠 SENT 时间，或自然结束后的有限核实仍失败 | 沿既有未知活动与残留占用规则收场；不补造停止、文件完成或成功，不无限延长会话。 |
| 普通录像 STOP 未确认 | 沿其原有限停止与异常录像恢复规则处理，不套用原生有限延时的自然结束假设。 |
| 取回中断或同请求重送 | 沿原源文件、固定长度、原 delivery 和已可靠进度继续；拍摄身份与 START 次数不变。新的独立取回具有新的交付身份。 |

这项取消策略扩展[原有有限停止后的收场规则](../../architecture/camera-capture.md#取消失败与文件保留)。它允许低功耗期间无法立即停止的任务继续运行至原有限目标；自然等待由原目标、固定余量及实际采用的部署额外等待限定，之后的文件核实另有原有限调用预算，不声称总收场只需目标加固定余量。普通任务、其他设备及报告继续具有执行机会。

新增的取消后自然收场依据只说明“原有限任务按原运行假设已结束，相关文件可核实及占用可释放”，不说明原目标采集完整完成。STOP 可能实际提前生效但响应丢失，因此不得写入 `capture.status=completed` 或生成目标完成凭据，也不得伪造成功 STOP 或直接设备观察。收场依据关联原 SENT、等待事件、原冻结取消策略和可靠结果页，单独保存活动结束及占用释放事实；目标终态、取消项结果和原操作结果保持各自语义。

结果充分、明确不合格和仍无法核实分别处理。空集合、缺件或调用失败本身不提供解除占用的保证；若没有按原合同取得足够的收场依据，保留未知活动和残留占用。新增责任必须纳入会话工作量、取消结算、残留处理和报告；切换及结算在事务提交未知时沿原完整申请恢复，不重开 STOP 责任，也不让已失败的 STOP 永久保持 ACTIVE。

## 普通录像媒体检查与修复

异常录像的媒体输入必须明确选择 OSV 原片，排除配对 LRF，不依赖目录顺序。源文件、主机检查副本和修复成品各保留原身份及格式信息。

OSV 双主视频不能由 ffmpeg 默认选择而丢弃一路。必要异常修复使用真实 ffmpeg／ffprobe，显式选择两路主视频及输入中存在的音频流，排除附加封面图；以无重新编码的流复制生成独立 MP4 成品。成品须具有两路与输入编码、画面尺寸一致的主视频，保留要求的音频，每路必要媒体的可确认内容时长至少达到目标。实际输出缺流、时长不足、无法取得必要结果、工具失败或容器不合格时，按 `repair_failed` 保留原 OSV，不发布不合格成品。

修复保证限于上述媒体内容，不声明成品保持原生 OSV、厂商全景编辑兼容或未知专有元数据。能力说明须说明普通取回会按既有规则优先选择已经登记的修复 MP4，原 OSV 仍可用明确产物 ID 原样取回。修复不以缺少未知元数据契约而预先整体关闭；如果以后要求成品保留厂商原生编辑能力，再独立补齐相应契约与验收。修复失败与录像结果按既有规则分离，不掩盖已知原片损坏或目标时长不足。

主机原片检查使用 ffprobe 读取实际容器及双路流信息，不转换原 OSV。软件验证使用真实双视频流样本，覆盖合格裁剪、缺少必要流、输出不足目标和工具失败，并对合格样本做全流解码；不要求每次生产修复都完整解码整片。LRF 排在前面时仍只检查唯一 OSV；异常多原片不任取第一份检查或修复。正常录像不为媒体检查增加整片拷贝。

## 软件与 ARM 验收

实施计划按依赖拆分为：执行定义与完成上下文、两个正式任务合同及结果读取、低功耗取消与恢复、安装版联合链、ARM 真机链。每项先增加能证伪上述规则的测试，再实施和运行相应门禁；已存在的机制通过实际 OSMO 合同复验，不另建调度、取回、报告或恢复系统。

必须覆盖设置失败及取消后零次后续 START、特殊响应不能跨命令使用、唯一 START 后等待期零次 ADB 调用、三种完成上下文、跨页配对、空集合／缺件／零字节／读取错误、原调用及结果保存未知、主机进程中断、低功耗取消、取回中断和同请求重送。恢复均须核对原参数、原绑定、原目录基准及同一启动身份。

安装版联合链从源码目录之外构建和安装 wheel，生产登记、合同、解释器和结果读取器均来自 wheel，只在 ADB 进程和受控时钟边界提供软件替身。两种动作都经真实客户端、C host、CLI、SQLite、独立取回、报告导入和 ACK 验证；原片与预览分别核对。

通过软件门禁后，在 TX2 使用普通账户、实际配置及原状态库完成正式业务验收，不重新初始化现有业务数据。普通录像执行一段新的正式任务；原生延时执行一次 1 秒间隔、300 秒目标的正式任务，用来验收程序链而非重复补交已有手工演示材料。再用一轮 30 秒间隔、300 秒目标任务，定点验证正式程序在低功耗期间的主机进程中断／恢复；若取消恢复仍缺设备证据，另以同样五分钟上限做一次取消定点验证。每轮只启动一次，任务状态未知时不以新请求复拍覆盖它。

ARM 证据包括安装版本与实际 `describe`、客户端生成请求、C host 实际提交、原调用与完成依据、正式产物及配对、独立交付身份、源与副本长度和 SHA-256、全流解码、客户端实际导入及累计 ACK 水位。供电、原片和合法状态库继续保留。已完成的六次拍摄及十二份媒体核验不重新运行，最长时间组合、物理断电和光学画质专项不混入本项通过结论。
