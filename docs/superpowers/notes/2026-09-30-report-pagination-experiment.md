# 报告对象分页的 SQLite 实验

本页记录开发环境的查询实验，不作为目标主机性能承诺。有效算法、候选容量和 SQL 统一见[报告对象选择](../../camctl/database/report-changes.md#报告对象选择的索引与分页)，完整结构见[SQL 目录](../../camctl/database/schema/README.md)，生产验收见[报告分页验证](../../camctl/database/consistency-verification.md#报告对象分页的具体查询验证)。

## 环境与测量范围

2026-09-30，使用开发容器中 `~/.venv/bin/python` 的标准库 `sqlite3`，SQLite 版本为 3.53.1，数据库为内存数据库。实验使用目标 `report_entity_changes` 的最小模型：整数主键、类型、对象 ID、事件 ID、非空业务序号，对象与事件唯一索引，以及正式规则中的两种候选索引。没有实施完整历史表、外键、事件处理器或报告生成器。

用 `EXPLAIN QUERY PLAN` 检查索引范围和临时排序，按每千条 VM 指令的进度回调累计近似执行工作量，同时记录整个对象集合选完的耗时。该计数不是实际索引行访问量、磁盘读取量或内存峰值；小查询不足一次回调不能解释为没有成本。耗时包含 Python 查询及收集结果的开销，返回身份的测试列表仅用于核验，不代表生产加载方式。

SQLite 的统计信息参与索引选择，见[查询规划说明](https://www.sqlite.org/queryplanner.html)。执行计划文本用于诊断，不作为跨版本逐字稳定接口，见[执行计划说明](https://www.sqlite.org/eqp.html)。进度回调统计的是虚拟机执行工作，见[进度回调说明](https://www.sqlite.org/c3ref/progress_handler.html)。

## 均匀变化样本

生成 200000 条关联，序号 `i` 从 1 到 200000：`id = event_id = change_seq = i`，类型使用实验值 1，`entity_id = (i * 7919) % 20000 + 1`。因此共有 20000 个对象，每个对象十条变化，业务序号顺序与对象顺序不同。实验类型值仅区分样本，不定义项目类型编号。

比较两种方法：一条普通 `DISTINCT entity_id` 查询同时限定类型、对象游标和业务区间，再按 ID 排序并限制页面；以及正式规格中的有界预查询与对象续读组合。每页 32 个对象，计时包含全部页面，不只测首批。

| 数据与统计 | 普通查询 | 规格查询 | 观察 |
| --- | --- | --- | --- |
| 200000 条关联，完整区间，有数据后执行 `ANALYZE` | 约 7.158 秒、6.90 亿 VM 指令 | 约 0.014 秒、251 万 VM 指令 | 普通查询选择业务序号索引并逐页临时去重；规格查询使用对象索引续读 |
| 最近 200 条变化，无统计 | 约 0.0044 秒、83 万 VM 指令 | 约 0.0001 秒、约一千 VM 指令 | 普通查询选择对象索引并过滤历史；有界查询直接定位业务区间 |
| 最近 10000 条变化，有数据后执行 `ANALYZE` | 约 0.145 秒、1747 万 VM 指令 | 约 0.009 秒、106 万 VM 指令 | 规格查询切换到按对象 ID 续读 |

无统计和删除统计后重新加载两种情况下，也分别比较了完整区间、最近两百条、最近一万条、空区间及中间十条变化。两种方法得到相同的去重有序集合；耗时差异说明只添加两个索引并不保证查询会选择适合该范围的路径。

规格中的大范围查询在无统计、空库分析后填充、填充后分析三个状态下均使用 `report_changes_by_entity`，定位条件包含类型等值及对象 ID 下界；预查询使用 `report_changes_by_sequence` 定位业务区间。大范围查询未出现全范围临时排序。

## 容量边界、并发追加与数据倾斜

另建两种实验类型、相同序号关联多个对象的样本。第一种类型只在 ID 7 和 90001 之间变化，第二种类型使用 ID 17，共五千个业务序号。分别验证容量边界、空区间、水位端点及页大小 1、2、32、127；三种统计状态共完成 96 项结果或分支断言。

在第一页返回 ID 7 后，为旧对象和新对象追加大于冻结上界的变化。后续页面仍只返回 ID 90001；新对象不进入旧范围，有界路径的旧范围结果也保持不变。这是同一连接上交错提交的结果验证，不代表已经验证生产双连接 WAL 并发、进程取消或恢复。

将均匀样本从 200000 条扩大到 1000000 条，最近两百条变化的有界选择仍约一千 VM 指令；完整同步仍正确返回两万个对象。不同统计可启用不同的索引去重优化，因此不要求指令数与关联数严格成正比。

另建一个对象具有十万条历史、随后一万个对象各有一条变化的样本。完整选择返回 10001 个对象，页大小为 1、32、128 时近似 VM 指令分别为 173 万、138 万、137 万；缩小页面没有出现每页重扫整个范围的增长。

## 实际 SQL 结构与查询的检查

[实际结构](../../camctl/database/schema/history.sql)定义了独立报告目录、事件与业务序号的成对外键及两种覆盖索引。[数据库结构检查](../../../scripts/check-database-spec.py)和[历史与报告 SQL 集成检查](../../../tests/integration/test_database_history_sql.py)使用该结构执行预查询和带游标的续读查询。2026-09-30 在 SQLite 3.53.1 上复核，735 项结构断言与 21 项 SQL 集成检查通过；这些数量包含其他数据库主题，并非全部属于分页检查。

分页相关检查验证：无统计信息和填充数据后执行 `ANALYZE` 时，两条查询使用各自的覆盖索引且不出现临时排序；同时覆盖预查询的空结果、小范围与容量加一条、按对象 ID 读完多个页面、冻结后追加及大整数 ID。这些检查核对实际结构上的查询计划与结果，没有重新测量上文的耗时，也未执行生产报告生成器。
