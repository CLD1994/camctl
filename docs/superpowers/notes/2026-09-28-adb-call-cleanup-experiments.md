# ADB 普通前台命令收场实验与后续重构参考

## 第一版采用的方案

第一版采用[设计文档中的运行假设](../../architecture/adb-execution.md#第一版普通前台命令的运行假设)：适用的普通前台命令在本地 ADB 客户端退出并完成本地资源收场后，依赖 ADB 连接关闭机制收场远端命令，假定旧命令在后续相关设备操作开始前结束。运行时不逐次查询远端进程身份；收场依据与实际业务效果分别保存。

本文记录用户在目标相机上执行并提供输出的两次实验，以及开发环境中的本地进程收场核验。相机实验为运行假设提供经验依据，不把实验观察提升为 ADB 对所有设备、版本和命令的时序保证。本地实验核对 Linux 进程管理方法，不验证远端命令的行为。后续重构参考独立列出，不属于第一版实现或验收要求。

## 实验环境与方法

| 项目 | 实际环境 |
| --- | --- |
| 主机 | Windows，使用 PowerShell 执行命令 |
| ADB 客户端 | Android Debug Bridge 1.0.41，Platform Tools 37.0.1-15733141 |
| 设备 | Linux 相机，`adb features` 返回 `shell_v2` |
| 连接 | USB；拔掉 USB 后相机可独立供电并保持开机 |
| 设备端版本 | 未能从设备返回的系统版本属性识别 adbd 的具体版本 |
| 测试命令 | `adb shell -T 'echo <实验标记>=$$; exec sleep 300'` |

命令先输出远端 PID，再通过 `exec` 在同一 PID 下执行 `sleep 300`。另一次 ADB 调用读取 `/proc/<pid>/stat`，确认测试进程存在及其状态；测试进程只等待，不修改相机文件。实验要求在启动后一分钟内完成，避免把自然结束混同为断线收场。

两个场景各有一次用户提供的实验记录。设备序列号、具体 PID 和启动标识值不作为方案的配置或判定常量。

## 实验一：USB 保持连接，终止本地客户端

PowerShell 按命令行中的实验标记定位唯一的本地 ADB 客户端，使用 `Stop-Process` 终止该进程并等待本地退出；没有终止 ADB server，也没有向设备另发终止命令。

| 观察阶段 | 用户提供的结果 |
| --- | --- |
| 本地客户端终止前 | 远端 PID 对应 `sleep`，状态为 `S` |
| 本地客户端退出后 | 四次查询均返回 `ABSENT`，查询退出码均为 `0` |
| 查询开始时间 | 距本地退出约 2、287、1065、3313 毫秒 |

本次观察支持该组合下本地客户端被终止后，远端普通前台进程随之退出。第一次查询在约 2 毫秒时开始，不代表远端在 2 毫秒内退出；只能确定第一次查询实际检查时进程已不存在。此实验没有直接观察收到的信号，也没有验证 Linux 主机发送 `SIGTERM` 的路径。

## 实验二：USB 断开后重新连接

先确认远端测试进程存在，读取相机的 `/proc/sys/kernel/random/boot_id`。保持相机供电，断开 USB 约 5 秒后重新连接；设备恢复可通信后，再读取启动标识和原进程状态。

| 观察阶段 | 用户提供的结果 |
| --- | --- |
| USB 断开前 | 远端 PID 对应 `sleep`，状态为 `S`；成功取得启动标识 |
| 本地原调用结束 | ADB 客户端返回 `255` |
| USB 重连后 | 设备状态为 `device`；启动标识与断开前相同 |
| 重连后的三次查询 | 原 PID 均为 `ABSENT`，查询退出码均为 `0` |

本次观察支持相机未重启，原远端进程在断开至重连检查期间已经退出。实验不能确定退出发生在拔线时还是重连过程中，也不能给出退出耗时上限。结合本次拔线过程，`255` 符合未取得远端退出结果的连接中断路径；不能据此认定远端测试命令自己返回了 `255`。

## 公开实现依据与结论范围

AOSP 的 shell 服务在协议连接关闭时向其管理的远端子进程发送 `SIGHUP`；正常结束路径等待子进程退出，再在连接仍有效时发送远端退出码。该行为针对服务管理的进程，不构成任意后台任务或独立拍摄服务的终止保证。见 [shell 服务实现](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/daemon/shell_service.cpp)。

AOSP 的 `test_non_interactive_sigint` 验证终止本地非交互式客户端后远端进程退出；`test_sighup` 验证远端收到挂断信号，并明确区分本地退出和远端退出的时机。测试中采用的等待时间不是产品时限。见 [ADB 官方测试](https://android.googlesource.com/platform/packages/modules/adb/+/1012d1197035a8d244e7bf6a014b0f72241bb3b2/test_device.py)。

所查客户端的 shell 协议读取以 `255` 为未取得远端退出码时的默认结果，收到远端退出消息后替换该值；仅凭数值 `255` 不能区分所有可能来源。见 [ADB 客户端实现](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/client/commandline.cpp)。

两次目标设备实验支持使用 ADB 自带机制收场普通前台命令。以下边界分别保留：

- 实验检查时进程已经退出，不证明本地退出与远端退出同步，也不证明任何后续操作都必然晚于远端退出。第一版采用的先后关系属于明确接受的运行假设。
- `sleep` 的退出不证明实际删除发生与否，也不证明独立拍摄活动停止。文件效果、拍摄活动和产物完成继续按各自契约判断。
- 样本来自 Windows 客户端、USB 和该目标相机；不是 Linux 部署主机、其他传输方式或所有命令形态的实测结果。部署联调核对实际组合，不把真实设备实验纳入软件集成测试的运行前提。
- 第一版软件验证使用受契约约束的替身，验证适用假设、事实保存、预算、取消及恢复行为；不实现针对已排除故障范围的额外机制。

## Linux 本地进程收场核验

核验在开发容器中进行，内核为 `6.6.87.2-microsoft-standard-WSL2`；没有连接相机。测试程序模拟一个已退出的 camctl，以及它在同一进程组中留下的工具进程。工具的主线程调用 `pthread_exit`，另一个线程持续等待，用于区分主线程退出与整个进程退出。

| 检查 | 实际观察 |
| --- | --- |
| 对模拟 camctl 使用 `waitid(P_PID, ..., WEXITED | WNOHANG | WNOWAIT)` | 可以重复取得退出码 `42`，进程记录仍保留；最后针对该 PID 回收时仍取得同一退出码 |
| 只查看遗留工具的主线程状态 | 状态为 `Z`，但 `/proc/<pid>/stat` 中线程数为 `2`，工作线程仍在等待 |
| 向原进程组发送 `SIGKILL` 后检查工具 | 工作线程消失，工具主线程记录为 `Z`，线程数为 `1` |
| 原组只剩等待回收的进程记录时使用 `kill(-pgid, 0)` | 调用仍然成功，不能据此判断组内是否还有执行工作 |
| 直接等待主线程已退出、工作线程仍存活的工具 | `waitid` 尚不报告整个进程退出；终止整个组后才取得被信号终止的结果 |
| 同时创建另一个独立子进程 | 它的退出码 `73` 保持可回收，针对原调用的等待没有取走该结果 |

测试监督进程仅为回收实验孤儿进程而设置了 subreaper（接管孤儿后代的进程）属性；这不是对接入模块的实现要求。实验进程均已终止并回收。

Linux 的 [进程创建接口](https://man7.org/linux/man-pages/man3/posix_spawn.3.html)支持通过 `POSIX_SPAWN_SETPGROUP` 和组号 `0`，在执行目标程序前建立以子进程 PID 为组号的独立进程组。[等待接口](https://man7.org/linux/man-pages/man2/waitpid.2.html)的 `WNOWAIT` 允许读取退出结果并保留待回收记录；该记录保留期间，原 PID 不会被重新分配。接口还要求区分 `WNOHANG` 返回时没有退出事件的情况，不能只看返回值是否为零。

根据接口和实验，建议采用“创建独立组、保留 camctl 的待回收记录、终止原组、确认组内没有执行线程、最后回收 camctl”的实现顺序。成员检查可读取 `/proc` 中的组号、状态和线程数；发送组终止信号之后，`Z` 且线程数为 `1` 的记录可以作为已停止执行的候选判据，主线程为 `Z` 但仍有其他线程时不能通过检查。不能把[信号接口](https://man7.org/linux/man-pages/man2/kill.2.html)的成功返回当作全部成员已退出，也不能把 `/proc` 的读取或解析失败当作进程不存在。[线程目录文档](https://man7.org/linux/man-pages/man5/proc_pid_task.5.html)还说明主线程退出后线程目录可能不可用，因此不能只依赖枚举该目录判断全部线程结束。

公开 Linux v4.15 源码中的[进程创建](https://github.com/torvalds/linux/blob/v4.15/kernel/fork.c)、[信号发送](https://github.com/torvalds/linux/blob/v4.15/kernel/signal.c)、[退出与等待](https://github.com/torvalds/linux/blob/v4.15/kernel/exit.c)和[进程状态输出](https://github.com/torvalds/linux/blob/v4.15/fs/proc/array.c)提供了相应实现依据：组信号与创建进程的登记相互协调，创建路径检查待处理信号；等待路径不会仅因主线程成为僵尸就交付整个进程的退出结果。这支持先发送组终止信号、再确认成员停止执行的顺序，但不替代目标部署内核的联调。

工具留在原组、接入模块能够查询和终止工具、主程序保留 camctl 退出记录等要求，遵守[启动与回收约定](../../host-demo/design.md#受管工具的启动与主程序回收约定)。共享 ADB 服务端遵守[独立生命周期](../../architecture/adb-execution.md#共享-adb-服务端的生命周期)。这里读取进程状态和线程数的方法属于实现建议；怎样分批找出原组进程，以及读取期间进程退出或读取失败时怎样处理，仍须在实施设计中细化。实际主程序与工具是否满足约定，由联调核验。正式责任以[接入模块设计](../../host-demo/design.md#接入模块的本地进程收场责任)为准。

仓库现有 `host_child_spawn` 尚未创建独立进程组，`host_child_collect` 使用 `waitpid` 直接回收 camctl，`host_child_done` 只检查 camctl 和输出管道。因此现有实现尚不满足该正式责任。实施时须一并调整启动、退出观察、成员收场、最终回收和下一次调用的放行条件，并覆盖上述实验分类及查询失败、身份丢失、`run` 与 `submit` 并行的情况。该修改涉及跨调用恢复，须先形成执行计划。

## 共享 ADB 服务端的公开实现核验

本节核对公开 AOSP 源码，没有在目标 Linux 主机执行服务端启动实验。产品行为以[共享服务端生命周期](../../architecture/adb-execution.md#共享-adb-服务端的生命周期)为准。

[客户端实现](https://android.googlesource.com/platform/packages/modules/adb/+/ec7028fb5c2cde5c18522dd08f7c34c5e668fc83/client/adb_client.cpp)在无法连接本机服务端时调用 `launch_server`。版本检查还包含协议版本不匹配时终止并重新启动服务端的路径；Linux 上部分情况先尝试切换到现有服务端对应的可执行文件。因此，部署固定工具版本与一次业务调用的收场是不同责任。

[服务端实现](https://android.googlesource.com/platform/packages/modules/adb/+/45c08c5130b7f5f8787c0c226e72eb0d3a7f7f45/client/main.cpp)在非 Windows 后台启动路径中调用 `setsid()`，随后等待设备初始化并开放客户端连接。它还将标准输入关闭，并将标准输出和标准错误重定向到日志。由该顺序可知，启动中的服务端与已经脱离原组的服务端需要分别处理；不能把共享服务端永久视作某次 camctl 调用的执行进程。这些源码依据不证明目标部署版本已经通过联调。

## 后续需要时的重构参考

实际发现普通命令在后续相关操作开始后仍继续执行，或产品要求将调用先后关系从运行假设提升为逐次取得的结束依据时，可以评估“正常返回使用远端结果，异常后确认原进程结束”的方案。设备、传输方式或命令形态变化时，先核实原假设是否适用，再决定是否需要重构。

该方案的基本流程是：正常收到可信远端退出结果时直接使用；超时、取消中止或断线后，先完成本地收场，再确认原远端执行责任结束，随后才核实文件效果或派发后续操作。它不要求每次正常调用增加进程查询，也不预设必须部署设备端常驻服务。

实施前须完整定义以下契约：

| 责任 | 需要解决的问题 |
| --- | --- |
| 原进程身份 | 识别设备启动实例及原执行实例，处理 PID 复用；不能仅以某个数字 PID 存在与否判定 |
| 身份取得与派发 | 覆盖设备已经开始执行但身份未传回、身份或意图保存失败、派发结果未知等窗口，不根据缺少记录推断未执行 |
| 异常后确认 | 区分原进程已结束、仍在执行和无法确认；查询失败不能解释为进程不存在 |
| 次数和时限 | 明确进程结束确认的独立责任及有限预算，不无说明地占用文件存在性查询预算 |
| 取消与恢复 | 保持原业务身份和累计次数，覆盖断线、进程中断、跨会话恢复及原进程已经结束但收场事实未保存 |
| 历史及验收 | 保存结束依据与效果的独立事实；用进程复用、身份丢失、迟到结果及提交未知等反例验证，不执行历史回放中的外部副作用 |

该参考不固定字段、模块或具体实现，也不作为第一版待完成任务。需要启用时，依据届时的设备能力、运行证据和产品要求另行完成设计与实施计划。
