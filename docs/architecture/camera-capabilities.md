# 拍摄能力与参数类型

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页解释如何让不同相机使用不同的拍摄参数，以及如何把参数规则交给客户端。理解“做什么”“接受哪些参数”“用户常用的一组值”后，再看能力说明的机器格式。当前真实相机的固定设置见[当前相机录像参数](camera-parameters.md)。

**阅读提示：** 例如“录像”说明要做什么，`params.type` 选择该相机允许填写的参数，用户预设保存常用参数值。先读三者区别，再读说明交接与 JSON Schema（JSON 数据规则）的校验约束。

## 拍摄能力与参数类型

### 能力、参数类型与用户预设

拍摄能力表达要做什么；驱动定义的拍摄参数类型表达目标相机接受哪一种参数结构及其约束，正文简称“参数类型”。驱动根据选定的参数类型和参数值执行对应设备操作。当前已知能力为拍摄单张照片、录像和延时摄影，分别使用动作类型 `camera_take_photo`、`camera_record`、`camera_timelapse` 表达。每台相机可以支持其中任意一种或多种，后续可以新增拍摄能力及动作类型。

第一版支持 `camera_take_photo`、`camera_record` 和 `camera_timelapse`，每台设备只导出其实际支持的能力。单张拍摄与延时摄影遵守[单张拍摄与延时摄影](camera-capture.md)，录像行为遵守[相机录像](camera-recording.md)及[异常恢复](camera-recovery.md)。实际设备的参数及命令由驱动定义；支持某个动作类别不表示所有相机都支持该类别。

| 层级 | 定义者与职责 |
| --- | --- |
| 拍摄能力 | 动作契约定义行为类别及是否产生正式产物；新增类别通过动作接入机制扩展 |
| 参数类型 | 目标相机驱动声明该能力下支持的参数结构、字段和约束，并定义相应的执行流程与结果判定 |
| 用户预设 | 客户端保存能力、参数类型及一组合法参数值，生成计划时展开成明确的字段和值 |

一个参数完全开放的相机可以只提供一种参数类型，允许分别调整分辨率、帧率等参数。厂商按拍摄任务提供固定组合指令的相机，可以提供多种参数类型，每种类型只开放相应的可调参数。固定的设置属于驱动契约，调用方不能通过额外参数覆盖。

是否划分多种参数类型取决于参数结构和行为契约，而非固定组合的数量。若设备提供多个“分辨率与帧率”组合，且其余参数及执行流程相同，可以在同一参数类型中提供一个组合选项。同一任务内的参数差异可以通过条件分支表达，当前普通录像的[曝光选择](camera-parameters.md#普通录像与曝光选择)采用这种方式；需要独立参数契约或不同完成条件的任务，分别定义参数类型及对应执行契约。驱动可以扩展参数类型，不要求所有类型共享录像时长、分辨率、帧率等参数。

客户端预设仍受选定参数类型的约束。camctl 第一版接收展开后的能力、参数类型和参数值，不保存、解析或动态引用用户预设。预设之后被修改，不改变已提交计划；同一请求重送继续以首次受理内容为准。

### 部署时向客户端提供说明

第一版在部署时向客户端提供机器可读的能力及参数说明。说明由实际部署的驱动定义与主机设备配置共同生成：驱动定义拍摄能力、参数类型和规则，设备配置确定各 `device_id` 绑定哪个驱动。导出说明是这些权威输入的派生产物，客户端据此使用规则，不另外手工维护一套参数契约。

部署人员通过 [`camctl describe`](cli-commands.md#describe) 导出一份 UTF-8 JSON 说明，内含各参数类型的 JSON Schema 及解释这些规则所需的引用定义，可使用 `--config <path>` 选择本地配置。字段按[设备、拍摄动作、参数类型](capabilities.md)组织。命令只读取本地配置及驱动定义，相机未连接时也可导出。输出与失败处理以该命令契约为准。

| 说明内容 | 客户端用途 |
| --- | --- |
| 配置的 `device_id` 及对应驱动 | 选择实际部署的目标设备，并确定其参数规则 |
| 每台设备支持的拍摄动作类型 | 选择录像、单张照片等已接入能力 |
| 各拍摄能力接受的 `params.type` | 选择目标驱动支持的参数类型 |
| 各参数类型的字段名称、数据类型、单位、必填性、默认值和取值限制 | 生成和校验具体参数值 |
| 固定设置、可选组合及组合限制、必要的任务含义说明 | 向用户说明实际拍摄要求，以及哪些设置可以调整 |

说明只列出所部署版本与设备配置实际支持的能力，不将扩展预留名称视为可执行能力。它描述配置和参数契约，不表示设备此刻空闲、通信正常或已经取得执行资格。客户端生成完整计划时，还须遵守公共动作字段及对应动作的业务策略要求。

用户或部署人员负责完成“配置主机设备—生成说明文件—手工复制覆盖客户端部署目录中的 `data/device-capabilities.json`—启动或点击重新加载”的交接，具体步骤见[客户端部署与能力说明加载](client-deployment.md)。客户端读取并校验后使用。同步时机如下：

| 部署事件 | 同步要求 |
| --- | --- |
| 首次部署 | 手工复制对应说明，客户端成功加载后，再据此生成该主机的执行计划 |
| 更换相机，或修改设备标识与驱动绑定 | 按更新后的设备配置重新生成说明并同步给客户端 |
| 修改驱动参数契约，包括支持的类型、字段、默认值或限制 | 同步更新后的说明，客户端后续生成的计划使用新规则 |

客户端按[计划编辑契约](client-editing.md)根据 Schema 生成普通参数表单，并提供 JSON 编辑处理复杂参数；两种方式使用同源校验。用户预设由客户端保存，生成计划时按当前已启用的规则校验并展开；说明更新不改写已经受理的动作输入、生效参数或历史结果。

说明文件通过部署流程交接，主程序继续负责既有的计划输入与文件中转。状态报告表达动作输入、生效参数及执行结果，客户端通过部署交接取得完整的能力和参数定义。

导出所需的驱动定义或设备配置无法读取、解释或生成完整说明时，保留错误并判定本次导出失败；不能将缺失部分解释为设备不支持并交付残缺说明。客户端未同步说明而生成了不适用的计划时，camctl 仍按当前受理契约校验，不自动换参数类型或修改参数值；动作错误范围见[计划字段与参数校验](#计划字段与参数校验)。

### 客户端加载能力说明

每份能力说明表达该主机当前部署的完整设备目录及参数规则。客户端通过[启动或网页重新加载](client-deployment.md#启动与重新加载)完整读取文件，完成[说明结构与关联](capabilities.md)和全部必要 Schema 的校验后，再一次性启用整份说明。成功加载时整体替换用于生成新计划的能力目录，不把新旧设备或参数规则逐项合并。

| 文件读取与校验结果 | 客户端处理 |
| --- | --- |
| 说明完整有效，全部必要 Schema 及引用均可解释 | 启用整份说明；后续生成计划使用其中的设备与规则 |
| 文件无法读取或 JSON 不完整、不合法 | 报告加载错误，本次文件不作为可用能力说明 |
| JSON 有效，但说明结构、设备或参数定义有错误，必要 Schema 的版本声明不符合下文契约，或必要 Schema 无法解释 | 报告加载错误，不启用其中的部分设备或规则 |

例如，旧说明包含 `cam0` 和 `cam1`，新说明只包含 `cam0`：成功加载新说明后，新计划的设备目录只有 `cam0`。历史计划、状态报告及执行结果继续保留原有设备关联；用户预设在生成新计划时按新规则校验，不自动改写为另一个设备或参数类型。

手工覆盖文件与客户端成功加载是两个不同步骤。覆盖后旧文件可能已不存在，本流程不提供恢复旧文件的保证；加载失败时，用户应重新提供有效的完整文件。是否已有启用说明及对应提示遵守[加载结果与现有数据](client-deployment.md#加载结果与现有数据)。错误或不完整的说明不能因为文件已复制到指定目录而被视为可用。

### 拍摄参数的 JSON Schema

第一版使用 JSON Schema（描述 JSON 数据校验规则的标准格式）表达拍摄参数的静态约束。驱动定义是权威来源：同一份参数定义供 camctl 受理校验使用，并由 `camctl describe` 导出给客户端；客户端使用导出的规则校验用户输入。驱动可以直接维护 Schema，也可以从自己的权威参数定义生成 Schema，但不能另外手写一套完整的导出规则或客户端校验规则。

客户端按[客户端技术选型](client-deployment.md#客户端的本地部署)在浏览器与 Node.js 后端使用 Ajv，共用校验配置及错误转换代码。浏览器校验为编辑过程提供即时反馈，后端在导出完整计划前执行相应校验。三处校验均以同源规则为依据；camctl 对首次收到的输入继续执行自己的受理校验。

校验准备提交的拍摄参数时，保持 JSON 数据原样，禁止校验器隐式转换类型、删除额外字段或根据 `default` 自动修改输入；缺省值按下文的默认值契约处理。首次部署或更新能力说明后，浏览器和客户端后端使用同一份成功启用的参数规则。

Schema 的校验对象是单个拍摄动作的完整 `params` 对象，包含 `params.type`。不同设备、拍摄能力及参数类型通过能力说明建立关联；所选类型的 Schema 须约束对应的 `type` 值，并完整表达允许的字段、必填性、数据类型、取值范围、枚举及参数组合限制。固定设置和未开放字段的边界仍由参数类型契约决定，不能因通用校验器允许额外字段而接受驱动未开放的调整项。

| 规则或事实 | 负责的位置 |
| --- | --- |
| 拍摄 `params` 的字段、值及静态组合限制 | 驱动提供的 JSON Schema；camctl 与客户端使用同源规则 |
| 参数含义、单位、固定设置及使用说明 | 同源能力说明中的元数据；必须影响合法性的约束同时具有机器可执行的表达 |
| 动作的 `device_id`、`scheduled_at`、`group`、`policy` 等公共字段，以及计划结构和引用 | 公共输入及对应动作契约；拍摄参数 Schema 不替代整份计划校验 |
| 相机是否在线、是否正在录像，以及当前是否具备执行资格 | 运行时按设备证据及调度规则判定；Schema 校验成功不证明这些事实成立 |
| 参数缺省时采用的值 | 驱动参数契约定义，首次受理计算并保存生效参数；原始输入保持原样 |

例如，假设某个参数类型开放分辨率与帧率，合法组合为 `4K / 30`、`1080p / 30` 和 `1080p / 60`，Schema 必须使这三种组合通过、使 `4K / 60` 失败；分别列出两个字段的可选值不能代替组合约束。这是规则表达示例，不表示当前 ADB 相机已开放这些参数。JSON Schema 的条件约束可用于这类判定，见[条件校验说明](https://json-schema.org/understanding-json-schema/reference/conditionals)。

第一版统一使用 JSON Schema Draft 2020-12。每个参数类型的 Schema 根对象，以及被引用的独立 Schema 资源根对象，都必须包含以下版本声明；资源内部的子规则和共享定义继承所属资源的版本，通过独立资源定义的共享规则按资源根对象处理：

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema"
}
```

上例只展示标准版本声明，实际参数 Schema 还须包含该类型的字段和约束。版本声明的含义见[JSON Schema 版本声明](https://json-schema.org/understanding-json-schema/reference/schema)，采用的标准见[Draft 2020-12](https://json-schema.org/draft/2020-12)。

客户端浏览器、客户端后端和 camctl 都须显式按该版本解释规则。必需的版本声明缺失、声明不匹配、Schema 定义无效或必要语义不受支持时，按规则处理失败，不依据校验库默认值猜测版本，也不把规则错误判成用户参数错误。通过版本检查后，仍须完成 Schema 定义、引用及具体参数的既有校验。

导出说明应包含解析其参数规则所需的引用定义；校验器所需的标准定义随应用或依赖在本地提供。`$schema` 中的 URI 用于标识标准，部署后的加载和校验不依赖临时联网下载规则。接入实际参数类型时，仍须通过共同样例验证三处对所用约束的判定一致，不能仅凭版本声明相同就视为完成对接。

JSON Schema 的 `default` 是说明信息，标准校验不会自动补齐输入，见[默认值与说明字段](https://json-schema.org/understanding-json-schema/reference/annotations)。驱动导出的默认值必须与实际生效规则一致；camctl 按既有契约保存原始输入与补齐默认值后的生效参数，不能依赖校验库的隐式修改来改变计划正文。必填字段缺失、显式 `null` 或非法值仍按该类型定义校验，不能用默认值掩盖错误。同一请求重送、重试及历史恢复沿用已保存值。

| 校验条件 | 处理 |
| --- | --- |
| 规则有效且参数符合规则 | 拍摄参数校验通过，继续公共字段和业务条件的既有处理 |
| 规则有效，但参数不符合规则 | 客户端提示对应输入错误；camctl 首次受理时仅将该动作登记为 `failed`，遵守整份拒绝优先级 |
| 必需的版本声明缺失或不匹配、Schema 无效、必要引用缺失、所需校验语义不受支持，或规则无法可靠取得 | 规则处理失败：导出或客户端加载失败；camctl 受理入口按实际配置或内部错误结束会话，不判成调用方参数错误 |

接入一种参数类型时，须确认其静态校验约束能完整导出并被两端执行；不能把未表达的约束只写成文字，再宣称客户端已经完成同等校验。未来类型需要现有规则表示尚不支持的约束时，应先明确共同支持方式，再作为可用能力导出。

### 计划字段与参数校验

动作公共字段及基本值类型遵守[执行计划输入契约](plan-input.md)。本节定义驱动参数类型的选择与校验；具体拍摄参数的范围由该类型契约提供。

| 动作字段 | 含义 |
| --- | --- |
| `device_id` | 选择目标设备及其已配置的驱动 |
| `type` | 选择拍摄能力对应的动作类型 |
| `params` | 必填对象，包含参数类型标识及该类型接受的参数值 |
| `params.type` | 必填的非空字符串，选择该驱动在该拍摄能力下声明的参数类型；即使只有一种类型也显式填写 |

动作外层的 `type` 标识拍摄能力，`params` 内的 `type` 标识参数类型。拍摄参数对象中的 `type` 是框架用于选择参数结构的保留字段；其余字段与它同层，由选定参数类型定义。正文脱离对象上下文时，使用“动作类型”和“参数类型”区分两者。

参数类型标识在所属驱动及拍摄能力内解释，不要求跨相机通用。驱动为每种参数类型提供字段说明、必填性、默认值、合法范围、可选组合及组合限制，并以同一份定义支持校验与执行；静态参数校验及导出遵守[拍摄参数的 JSON Schema](#拍摄参数的-json-schema)。固定参数及未开放的调整项应明确说明，不能静默丢弃调用方提交的非法调整。

校验以本地已接入的动作和驱动定义为依据，不调用相机探测运行状态。遵守公共受理规则，按以下分区处理：

| 条件 | 处理 |
| --- | --- |
| `type` 未知或本版未实现 | 拒绝整份计划 |
| `type` 已支持，但 `device_id` 缺失或格式错误、指定设备不存在，或其驱动明确不支持该能力 | 仅该动作初始为 `failed`，保留设备或能力不适用的原因 |
| 设备与能力匹配，但 `params` 缺失或不是对象 | 仅该动作初始为 `failed`，保留参数对象错误 |
| `params` 为对象，但 `params.type` 缺失、格式错误或不受该驱动支持 | 仅该动作初始为 `failed`，保留参数类型错误 |
| 参数类型有效，但其余字段、取值或组合不符合该类型定义 | 仅该动作初始为 `failed`，保留具体参数错误 |
| 能力、参数类型与参数值合法，但动作其他自身字段不合法 | 仅该动作初始为 `failed`，按公共校验规则保存错误 |
| 能力、参数类型、参数值及其他公共字段均合法 | 受理为 `pending`，执行时仍需满足调度与设备条件 |
| 定义或数据库因内部故障无法可靠读取，不能完成判定 | 保留实际错误，按会话错误处理，不伪装成设备不支持或参数错误 |

整份拒绝优先级、零次执行尝试和无副作用规则由请求专题定义。初始失败不删除动作的拍摄类型；拍摄动作仍属于可产生正式产物的来源类型，不能因参数类型或参数值错误被组取回静默排除。

首次受理保存原始结构化输入，并为合法动作保存选定驱动、能力、参数类型及包含驱动默认值的生效参数。后续执行、重试和恢复沿用这些已确定的值；重建原计划使用原始输入，报告可分别表达输入与实际生效参数。驱动默认值或客户端预设的后续变化不重新解释已受理动作。历史回放不调用驱动重新计算参数。

### 驱动执行与产物边界

驱动为每种参数类型定义对应的启动方式、完成依据、取消及断电恢复方式、设备操作兼容性，以及本次正式产物的识别和写入完成依据。框架统一管理调度资格、动作状态、操作意图与观察事实的持久化、正式产物和报告。驱动通过这些公共流程执行，遵守先持久化意图再产生设备副作用的规则。

框架不要求所有拍摄操作具备独立的启动和停止命令，也不统一假设由主机计时。设备内部固定时长的复合指令可以由驱动通过对应参数类型表达；可调参数与完成判定由驱动契约定义。[录像成功标准](camera-recording.md#录像成功标准)及[时长检查与修复](camera-recovery.md#内部异常多录修复)适用于已确认的录像控制方式，具体驱动接入时须明确其参数如何确定这些流程所需的执行信息。

拍摄动作类型声明可以产生正式产物；具体文件种类、数量及关联方式由驱动为对应参数类型定义，不能仅凭“延时摄影”等名称推断产物一定是视频或照片序列。实际接入后，正式产物继续进入已有的取回、清理和报告流程，无须为每种参数类型新建一套交付协议。
