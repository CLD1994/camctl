# 概念与术语

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页用具体情境介绍后续规格中的用语。例子帮助理解对象之间的关系，精确字段、状态及允许的操作由链接的专题定义。

## 为什么要区分计划、产物和交付

用户希望相机在某个时间录像，再把视频带回来。但采集和传输不是同时发生的：相机可能已经录完，主机还没有机会对外传输；传输部门可能已经提供报告，视频文件仍未送到用户手中。camctl 必须分别记住这些进度。

**执行计划**是用户交给 camctl 的一组工作要求。计划包含一个或多个**动作**，例如“录像 A”“取回 A”和“报告状态”。动作各自判断执行条件，一个动作失败不会自动阻止其他动作。全部动作进入终态时，计划完成；计划完成不表示每个动作都成功。

**受理**表示 camctl 已经可靠保存这份计划及其全部动作，之后可以据此调度或恢复。它不表示动作已经执行。已支持动作的自身参数有错误时，可以随计划一并保存为失败动作；影响整份计划结构的错误则拒绝整份计划。分类见[执行计划输入](plan-input.md#校验顺序与错误优先级)。

**正式产物**是动作产生并已经登记的文件，例如相机中的原视频。登记使它获得稳定的 `output_id`，后续取回和清理可以明确指定它。相机原片保存在相机。主机断电后，相机可能继续录像；对符合修复条件的异常多录，camctl 在恢复处理中裁剪并另存修复成品，原片仍保留。修复成品保存在 `staging/derived/`，与原片各有产物身份，具体见[异常录像恢复与修复](camera-recovery.md#内部异常多录修复)。

**交付（delivery）**是某次取回为一份正式产物建立的交付记录。它有自己的 `delivery_id` 和独立待传文件路径。主程序传完后可以删除这个副本，正式源文件仍按显式清理规则保留，因此以后还可以再次取回。

### 例子：同一视频取回两次

假设录像 A 已完成，原视频登记为 `o-001`。下面的 ID 只用于说明关系。

| 用户的操作 | camctl 保存和处理什么 | 原视频如何处理 |
| --- | --- | --- |
| 请求 R1 取回录像 A | 为 `o-001` 创建交付 `d-001`，拷贝并准备本次待传文件 | 原视频继续保留在相机 |
| 请求 R2 再次取回录像 A，使用新的 `request_id` | 仍选择 `o-001`，创建另一次交付 `d-002` 和独立待传文件 | 使用同一个原视频，无须重新录像 |
| R1 尚未获受理确认，客户端用同一个 `request_id` 重送 | 若 R1 已受理，复用 R1 的计划和进度，不再因重送创建另一份交付 | 原视频及 R2 不受影响 |
| 客户端取消 R1 中的取回动作 | 按该动作的当前进度处理 `d-001`；仍可撤回的文件按规则撤回，已由主程序领取的普通文件不可撤回 | 不影响 R2 的 `d-002`，也不删除原视频 |
| 客户端后来明确请求删除 `o-001` | 按产物清理规则处理，必要时等待已经取得资格的读取结束 | 删除符合清理条件的正式源文件，数据库历史继续保留 |

`cancel_task` 的目标是计划或动作。例子中的取消通过指定取回动作实现，参数与完成条件见[取消计划与动作](task-cancellation.md)；文件取回、撤回和删除分别见[取回](obtaining-outputs.md)、[文件交接](file-handoff.md)和[清理](output-cleanup.md)。

### 名称、请求 ID 与实例 ID

名称供人阅读，ID 用来准确关联同一个对象。例如两个计划都可以叫“夜间录像”，程序仍须区分它们；同一计划内的动作名称则必须唯一，才能使用名称引用本计划的动作。

客户端生成 `request_id`，表示一次逻辑提交。camctl 首次受理后为计划和动作分配 `plan_instance_id`、`action_instance_id`。后者标识数据库中已经受理的具体实例，而非某一类动作。产物和交付分别用 `output_id`、`delivery_id` 关联，具体范围见[名称和实例 ID](plan-acceptance.md#名称和实例-id)。

**请求级幂等**表示：同一个 `request_id` 重送，不重复创建或执行一套计划。首次受理内容始终有效，后续正文忽略，报告确认字段独立处理。新 ID 则表示新意图，详见[请求身份](plan-acceptance.md#request_id)。

**动作组（group）**给同一计划内的一组动作提供共同名称，方便一次选择这些来源的正式产物。例如多个录像动作都属于“上午采集”，取回动作可以引用这个组。组不表示动作依次执行或成功依赖；取回动作自身不能成为组成员。完整规则见[动作组](plan-acceptance.md#group)。

## 状态报告为什么需要确认

主程序将文件放入传输流程，并不能证明客户端已经完整收到。camctl 因此通过状态报告描述自己的已知事实，客户端保存报告覆盖的状态后，再把确认交回 camctl。报告和普通视频各自传输，收到报告不代表视频也已收到。

**ACK（确认消息，acknowledgment）**在这里指客户端对报告覆盖范围的累计确认。客户端在后续提交的 JSON 中填写 `last_report_id`；camctl 查询对应报告，确认客户端已经保存到哪个业务变化位置。它不是相机命令的成功响应，也不授权删除原视频。

**业务变化序号 `change_seq`**为需要向客户端报告的变化排列先后。**水位（watermark，字段中缩写为 `wm`）**表示已经覆盖或确认到这个顺序中的哪个位置，不是时间，也不是报告编号。报告的 `from_wm` 和 `to_wm` 表示它覆盖的范围，详细规则见[报告覆盖区间](status-reports.md#报告覆盖区间)。

例如，报告编号是 `150`，但覆盖到业务变化位置 `160`：客户端完整保存该报告覆盖的状态后，提交的是 `last_report_id: 150`。camctl 查询这份报告，取得其上界 `160`。报告编号用来找到报告，水位用来判断覆盖，两者不要求相等。完整推演见[较早完整报告先被确认](status-sync.md#完整同步时先收到较早的报告)。

### 快照与变化的区别

**快照**表示某个确定位置上的状态。例如动作 B 先开始、后完成，一份覆盖这两次变化的报告会给出 B 在报告截止位置的状态。数据库仍保存两次历史变化，报告不必把它们逐条导出。

**完整自身字段**表示报告给出一个对象在该位置的完整属性；**实体子集合**则只给出此次需要更新的成员。假设计划 P 包含 A、B，客户端已保存 A 成功、B 运行中。新报告可以只携带 P 和已经完成的 B。客户端更新 P 与 B，同时保留没有出现的 A；不能把整份动作列表替换为只有 B。字段缺省与子集合缺席的具体处理见[客户端合并](status-reports.md#按计划嵌套与客户端合并)。

报告文件名包含 **SHA-256 摘要**，即根据文件全部字节计算的一串校验值。客户端用收到的原始文件字节重新计算并比较，可以判断是否与文件名中的摘要一致。校验不能先改 JSON 的排版；它也不能证明视频可正常播放。校验步骤见[文件名与完整性校验](status-reports.md#文件名与完整性校验)。

## 断电恢复中常见的词

| 术语 | 含义与例子 |
| --- | --- |
| 持久化、落盘 | 将恢复所需的信息可靠写入存储，使其不只存在于当前进程的内存中；具体文件与数据库提交顺序由对应专题规定 |
| 事务、原子提交 | 一组数据库变更共同提交。例如计划及全部动作一起受理，不能只保存前半份计划就让调度使用 |
| 不变量 | 在规定范围内始终必须成立的规则，例如同一个 `report_id` 的内容永远不变 |
| 事件溯源 | 以已经发生的事实历史为依据计算状态；camctl 的业务历史只追加并永久保留 |
| 当前状态投影 | 从历史计算出的当前状态，便于查询。例如从受理、启动和完成事实计算动作现在已成功 |
| 历史回放 | 读取历史来重建状态；回放本身不再次启动录像、发布文件或删除文件 |
| 对账 | 比较已保存的操作意图和结果与现在可查询的设备或文件事实，确定中断后已知什么、还需要确认什么 |
| 副作用 | 对数据库之外的对象产生实际影响，例如启动相机、停止录像、移动或删除文件 |
| 持续设备效果、补偿 | 一次动作可能使设备持续录像；停止这种持续效果的处理称为补偿。补偿有自己的进度和有限尝试，动作失败不保证相机已经空闲 |
| 终态 | 一个动作已结束的状态，之后不改写；它留下的设备状态、正式产物和交付文件仍可能继续变化 |
| 会话 | 一次 `camctl run` 进程承担的执行与恢复过程；`submit` 将新输入交给当前或后续会话处理 |
| 墙钟与单调钟 | 墙钟表示日期时间，校时可能使其跳变；单调钟用于在一次运行中测量经过的时间，不将不同会话的读数直接相减 |

“收场”指结束当前允许继续的有限处理，例如确认并停止遗留录像、终止读取或清理可处理的工作文件；具体范围由所属动作规定。“预算”指该流程允许使用的有限尝试次数或等待时长，已消耗部分不能因重启自动恢复。

“固化”指在规定时点确定并保存后续沿用的值。拍摄动作的原始参数保留用户实际输入，`effective_params`（生效参数）则表达首次受理时按驱动规则确定的具体参数，包括适用默认值。计时“锚点”是保存的计时起点，例如收到录像启动成功响应时的单调钟读数。

这些概念的约束分别见[共同原则与状态持久化](system-foundations.md)、[会话接管](protocol-session.md)、[调度与设备执行](scheduling-execution.md)及[时间检查](clock-recovery.md)。

例如 camctl 已保存“准备启动录像”，发出命令后立即断电：这条意图不能证明相机已经开始，也不能证明命令没有执行。恢复时要查询并核实。无法确认时记录未知，不能为了让流程继续而猜测成功或失败。

## 相机与客户端的技术用语

| 用语 | 在本项目中的含义 |
| --- | --- |
| 驱动 | 把 camctl 的动作和参数转换为具体设备操作，并解释设备响应的代码；不同相机可以使用不同驱动 |
| ADB、`adb shell` | ADB 是 Android Debug Bridge；当前设备使用它建立通信，通过 `adb shell` 在相机的嵌入式 Linux 中执行厂商程序或 shell 脚本。未来设备的通信方式由对应驱动定义 |
| 拍摄能力、动作类型 | 表达要做什么，例如录像；第一版实际支持范围与预留能力见[拍摄能力](camera-capabilities.md) |
| 参数类型、`params.type` | 选择该相机接受的一套参数结构和约束；同样是录像，不同设备可以允许不同参数 |
| 用户预设 | 客户端保存的一组常用选择与参数值；生成计划时展开为具体内容 |
| JSON Schema | 描述 JSON 数据应有哪些字段、字段是什么类型及允许哪些组合的规则格式；同源规则供 camctl 和客户端校验 |
| Ajv | 客户端使用的 JSON Schema 校验库，负责执行上述规则，而非另一份相机参数定义 |
| UART | 串行通信接口；MCU 的后续通信接入依据，第一版只预留接口 |
| `ffprobe`、`ffmpeg` | 主机上用于读取媒体信息和处理视频的工具；不会因为采用它们而要求在相机端安装新依赖 |

参数示例与正式设备参数应分开理解：协议样例中的参数类型用于演练流程，当前真实相机的已确认设置及待核对部分见[当前相机录像参数](camera-parameters.md)。
