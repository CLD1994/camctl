# 计划文件诊断

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页定义一次计划文件输入如何形成诊断、怎样保存，以及客户端如何合并。报告的覆盖与累计确认见[状态报告](status-reports.md)，具体 JSON 字段见[字段契约](report-format.md#计划文件诊断)。

顶层 `plan_file_diagnostics` 报告执行计划文件读取、解析、整份受理校验及 ACK 校验中发现的问题。每次 `run <plan-path>` 或 `submit <plan-path>` 的输入处理中，有此类问题才形成一条诊断；同次输入的多个问题集中在该条记录中。裸 `run` 没有新输入文件，不为历史恢复、报告生成或补投创建新的输入诊断。动作自身错误、设备执行错误及会话错误按各自契约表达。

## 记录字段

每条记录具有以下完整自身字段：

| 字段 | 条件与含义 |
| --- | --- |
| `diagnostic_id` | 必填，camctl 分配的稳定标识，遵守[对象 ID 格式与范围](plan-input.md#对象-id)；在当前主机历史中唯一，不复用 |
| `file_name` | 必填，取本次实际传入 `<plan-path>` 的文件名部分，不依赖文件是否能打开、完整读取或解析 |
| `request_id` | 可选；仅在文件完整读取、无歧义解析且该字段通过请求整数身份校验时提供；否则省略 |
| `errors` | 必填的非空数组，集中保存本次已经确定的相关错误；每项使用 `code`、`stage`、`details` |

`file_name` 保留调用方传入路径中的实际文件名称，不替换为 JSON 内的计划 `name`，也不通过解析符号链接改成另一个名称。它是文件系统名称，不套用计划可读名称的长度和字符约束。完整主机路径继续保存在本地诊断中。文件名用于展示和定位，不要求跨输入唯一；主程序改过名时，报告反映 camctl 实际收到的名称。客户端可以利用已知文件名对应关系辅助定位，但不能仅凭名称推导 `request_id`、认定计划已受理或改写计划状态。

`request_id` 提供时，仅表示本次输入携带了这个合法请求身份，不证明本次计划被接受。同一 ID 尚未成功受理时可能有多个被拒绝的输入；后来成功受理后，这些历史诊断仍然成立。文件无法完整读取或解析时，即使已读片段或文件名包含类似 ID 的文字，也不填写该字段；字段本身非法时，实际错误值可保留在相应 `details` 中。

## 错误归属与阶段

下表根据公共输入契约的处理顺序判定；计划和 ACK 的业务结果独立，仍在同次受理事务中保存。

| 本次处理情况 | 诊断记录 | 计划及动作 |
| --- | --- | --- |
| 文件打开、读取、解码或解析失败 | 一条文件诊断，记录实际失败阶段，不带 `request_id` | 不从片段受理计划或吸收 ACK |
| 解析成功，出现整份拒绝条件 | 一条文件诊断，包含已确定的整份拒绝原因，以及独立发现的 ACK 错误；合法请求 ID 可附带 | 不注册本次计划或动作，合法 ACK 仍可吸收 |
| 计划正常受理或幂等复用，但 ACK 校验错误 | 一条文件诊断，包含 ACK 错误 | 计划受理或复用不受该错误影响 |
| 已支持动作仅有自身参数错误，且没有上述问题 | 不创建文件诊断 | 计划受理，错误保存在对应动作，动作初始 `failed` |
| 动作自身参数错误与 ACK 错误同时存在 | 文件诊断只包含 ACK 错误 | 动作自身错误仍在动作下面，不重复列入文件诊断 |
| 计划和 ACK 处理均无此类问题 | 不创建文件诊断 | 按正常受理或复用结果处理 |
| 处理结果无法可靠保存或提交结果未知 | 不宣称诊断一定已保存或一定未保存 | 按会话错误和事务恢复规则处理 |

文件诊断中的 `stage` 使用下列值，表示发现错误的阶段，不表示整个会话执行失败：

| `stage` | 含义 |
| --- | --- |
| `input_read` | 打开或读取本次文件失败 |
| `input_parse` | UTF-8 解码或完整 JSON 解析失败，包含字段名或字符串值中的未配对代理码点 |
| `admission` | 公共结构、动作名称或类型等整份受理校验失败 |
| `ack` | 当前输入的 `last_report_id` 校验失败 |

错误内容只记录实际已确定的事实。字段路径针对本次输入，数组下标从 0 开始；缺失字段不补造 `value`，无法解析的文件不补造结构化字段路径。具体错误码及 `details` 按对应校验契约解释，客户端样例中的已定义表达见[计划文件诊断样例](client-protocol-examples.md#计划文件诊断样例)。

## 持久化、重复输入与报告合并

一条诊断的身份、文件名、合法请求 ID 及全部错误，与同次输入的计划处理结果、适用的 ACK 更新一起原子提交。诊断历史及其投影使用同一事务；提交后这条诊断的内容固定，永久保留。诊断的产生是应报告的业务变化，纳入 `change_seq`；读取、重建、重复发布这条诊断不产生新的业务变化。

同一请求重新通过命令入口提交文件，是另一次输入处理；如果再次产生文件诊断，则分配新的 `diagnostic_id`，即使文件名、请求 ID 和错误完全相同。已有成功受理关联的请求仍跳过本次正文校验，只独立处理当前 ACK；新的诊断不重新执行原计划。对已提交记录的恢复和报告重建复用原诊断 ID，不将同一持久化事实解释为新的输入尝试。

报告从覆盖区间内的诊断创建事实选择记录，每条都携带完整自身字段，使用同一冻结历史上界。`errors` 是该条记录的普通数组，不是按 ID 合并的实体子集合。客户端按 `diagnostic_id` 保存整条记录；重复收到同一诊断不增加条目，不同 ID 表示不同输入处理，可以在界面汇总相同问题的发生次数。

`plan_file_diagnostics` 缺席或为空表示本报告没有该集合的更新，不删除客户端已有诊断。累计 ACK 使用统一业务覆盖水位；确认后这些记录不因其历史存在而再次产生待报告变化，数据库历史与客户端已保存记录继续保留。诊断不反向修改计划状态：客户端以 `plans` 中的请求关联确认受理，不能让迟到的历史拒绝诊断覆盖后来取得的受理证据。
