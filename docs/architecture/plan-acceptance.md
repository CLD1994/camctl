## 执行计划

公共字段、基本值类型、时间格式、额外字段及校验顺序由[执行计划输入契约](plan-input.md)定义。本专题定义这些输入如何原子受理、幂等复用并交接给运行会话。

### 整份校验与原子受理

首次受理时，`actions` 必须是至少包含一个动作的数组。计划公共结构、动作类型及名称须满足已定义的要求。校验按下表区分整份计划拒绝与单个动作失败，不能在校验尚未完成时逐个注册动作。已有成功受理关联的 `request_id` 直接复用原计划，忽略本次正文。

| 首次受理的校验结果 | 处理 |
| --- | --- |
| 计划公共结构错误，如 `actions` 缺失、非数组、为空，动作无法识别，或动作名称不合法、重复 | 拒绝整份计划，不注册实例 |
| 包含未知或本版未支持的动作类型 | 拒绝整份计划，不注册实例 |
| 已支持且名称合法的动作存在自身字段、参数格式或可在受理时诊断的引用错误 | 保留该动作，将其初始状态登记为 `failed`，保存错误；其他动作继续校验并按结果一同受理 |
| 没有导致整份拒绝的错误 | 原子受理完整计划及全部动作，包括校验失败的动作 |
| 数据库操作失败或提交结果未知 | 按会话错误和恢复规则处理，不宣告部分受理 |

整份拒绝的条件优先于单个动作失败；两者同时出现时不注册本次计划及动作实例。

可执行动作由本版已实现能力确定；MCU 预留动作的受理规则见[计划中的 MCU 动作](mcu-actions.md#计划中的-mcu-动作)。

已实现的拍摄动作还须按目标驱动校验能力、参数类型与参数值。动作类型已实现但目标设备不支持该能力，或参数类型或参数值不适用时，仅该动作失败；分区见[计划字段与参数校验](camera-capabilities.md#计划字段与参数校验)。

所有已支持动作采用相同的自身参数校验规则，包括必填字段、字段类型、取值范围和组合，以及动作自身的设备、时间、策略与所属组字段。具体合法条件由相应动作契约定义；违反条件时该动作在受理事务中直接登记为 `failed`，保存失败阶段、具体字段及原因，执行尝试次数为零，不等待计划时间，也不补造执行开始事实。

校验失败的动作不产生执行副作用：录像不启动或停止设备，取回不准备 delivery，删除不登记删除意图或删除文件，取消不标记或操作目标，报告动作不执行其显式报告请求。受理及失败事实仍由会话按正常报告职责处理。受理校验不通过调用设备来探测运行条件；执行时才可判断的目标存在性及业务条件按各动作契约处理。

已有 `request_id` 始终复用首次受理的输入、实例和结果，修正参数后重送同一 ID 也不重新执行已失败的动作；新的执行意图使用新的请求。动作自己的参数错误不改变其合法名称和类型，也不使同计划中的其他动作失去受理资格。

取回动作自身的校验范围见[校验与失败处理](obtaining-outputs.md#校验与失败处理)。本计划内名称引用在首次受理时根据完整输入解析，保存有效关联或该动作的失败诊断。通过实例 ID 指定动作或其他计划内的组时，受理只校验引用格式、保存来源描述；目标存在性、来源类型及集合在执行时确认，受理阶段不查询跨计划来源。

首次受理成功时，计划实例、全部动作实例、有效的本计划内来源关联、各动作的校验失败结果、请求与实例的关联，以及新计划受理序列的推进，其历史和投影在同一数据库事务中提交。历史回放也必须整体呈现这次受理。失败动作仍是计划成员，保存其输入的结构化字段和值及诊断，不丢弃动作或将错误参数改写成合法值。受理过程不产生设备、文件交付等执行副作用。该规则同时适用于 `run <plan-path>` 和 `submit <plan-path>`。

| 首次受理的处理情况 | 计划与动作实例结果 | 对外表达 |
| --- | --- | --- |
| 无整份拒绝条件，注册事务提交成功 | 一个完整计划及其全部动作实例，校验失败的动作为 `failed`，其余为 `pending` | 计划受理成功；动作失败进入报告，其余执行由后续调度资格决定 |
| 输入解析失败或出现整份拒绝条件 | 不注册本次计划和动作实例，不推进新计划受理序列 | 记录整份计划被拒绝的业务结果 |
| 无整份拒绝条件，注册事务失败且已确认回滚 | 不保留部分计划或动作实例，不推进新计划受理序列 | 会话级错误 |
| 注册事务的提交结果不确定 | 不向调用方断言已受理或未受理；后续依据数据库中的完整注册结果判断 | 会话级错误，重试遵守请求幂等规则 |

已受理请求按本专题的请求幂等规则复用，不重新创建实例。拒绝记录属于面向客户端的业务结果，可以在没有新计划实例时存在；已有计划及其动作保持原有执行意图。

整份受理约束计划进入状态库的方式。计划进入执行阶段后，各动作仍按自身条件独立执行，某个动作失败不自动阻止其他动作。

本节定义计划正文与动作实例的受理原子性。`last_report_id` 单独校验，其业务校验结果按“计划正文与 ACK 独立处理”组合，不属于使整份计划正文校验失败的条件。

### 计划执行状态

计划执行状态由所属动作在同一已提交历史边界处的状态及执行历史计算。首次受理提交时，计划至少包含一个动作；校验失败的动作为 `failed`，其余为 `pending`。仍有待执行动作时计划初始为 `pending`，全部动作均因校验失败而终态时计划初始为 `completed`；这两种情况均没有动作开始执行。统一按以下完整分区判定：

| 全部动作已进入终态 | 是否曾有动作开始执行 | 计划状态 | 含义 |
| --- | --- | --- | --- |
| 否 | 否 | `pending` | 尚无动作开始执行，且仍有动作未结束 |
| 否 | 是 | `running` | 已有动作开始执行，且至少一个动作尚未进入终态 |
| 是 | 否或是 | `completed` | 全部动作已经进入终态 |

动作的终态及允许转换由[动作状态模型](scheduling-execution.md#动作状态模型)定义。“开始执行”以动作首次从 `pending` 进入 `running` 的持久化事实为依据，包含不操作设备的动作；不要求设备命令已经成功，也不能仅凭计划时间已到、调度器查询过动作或动作已进入终态来推断。受理时校验失败、动作尚未执行就直接过期或被取消，均不产生开始执行的事实。

计划允许保持原状态，或发生 `pending → running`、`pending → completed`、`running → completed`。已经有动作开始执行后，即使它已经结束、其余动作都在等待未来时间，计划仍为 `running`。全部动作在执行前被取消或过期时，计划直接成为 `completed`。重试和进程重启不使计划退回 `pending`，同一请求的幂等复用不重新开始计划。

`completed` 表示执行结束，具体结果由各动作的成功、失败、过期和取消状态表达。取消请求已发出但目标动作仍在必要收场时，仍按实际动作状态计算。正式产物是否保留、delivery 是否已传输、报告是否得到 ACK，以及残留设备事实是否解决，均不改变已经成立的计划执行状态；相关后续职责由各自协议判定。

计划进入 `completed` 后保持该状态，其历史及实例关联永久保留。客户端仍可查询历史，并通过新计划取回尚可用的产物或清理指定产物；这些新动作属于新计划，不重新打开原计划。

动作变化引起的计划投影变化与该动作历史在同一事务提交；计划状态只从动作历史派生，不由另一套独立指令改变。历史回放和报告生成使用各自指定的完整历史边界计算，不能从当前正在运行的动作数量或当前进程是否存在来猜测；历史无法可靠读取或解释时按状态库错误处理。

### 基本结构

动作的 `scheduled_at` 必填性及省略后的执行含义见[调度与时间语义](scheduling-execution.md#scheduled_at)。第一版 `camera_record` 必须提供 `policy.max_delay_ms`，具体要求见[录像参数](camera-recording.md#参数)。拍摄 `params` 按目标驱动正式声明的参数类型校验。

执行计划提供业务要求；通信尝试次数、超时和重试间隔来自主机本地设备配置。动作 `policy` 的字段边界及错误处理见[计划要求与本地通信配置](configuration.md#计划要求与本地通信配置)。

客户端通过[部署交接的能力及参数说明](camera-capabilities.md#部署时向客户端提供说明)确定目标设备支持的拍摄能力、参数类型和字段约束，结合公共计划规则生成输入。camctl 首次受理仍执行既有校验，同一请求重送继续复用首次结果。

下面是一份用于协议演练的采集计划：样例驱动提供 `timed` 参数类型，并以 `duration_s` 字段指定 60 秒目标时长，再按默认范围取回该动作的产物。这里的类型名称和拍摄字段仅用于样例；实际设备计划使用部署说明中提供的正式参数类型。它不携带报告 ACK；客户端已有可累计确认的报告时，才在输入中提供 `last_report_id`。若用户在客户端选择预设，客户端先展开为能力、参数类型及具体参数再提交。

完整的计划输入、状态报告、ACK 重送及客户端合并演练见[客户端协议样例](client-protocol-examples.md)。

```json
{
  "request_id": "req-20260910-001",
  "created_at": "2026-09-10 15:00:00",
  "name": "夜间采集-01",
  "actions": [
    {
      "name": "主录像",
      "type": "camera_record",
      "device_id": "cam0",
      "scheduled_at": "2026-09-10 16:00:00",
      "params": {
        "type": "timed",
        "duration_s": 60
      },
      "policy": {
        "max_delay_ms": 5000
      }
    },
    {
      "name": "取回主录像",
      "type": "obtain_action_outputs",
      "scheduled_at": "2026-09-10 16:02:00",
      "params": {
        "source": {
          "action_name": "主录像"
        }
      }
    }
  ]
}
```

主程序将输入文件路径交给 `camctl run <plan-path>`；已有运行会话时使用 `camctl submit <plan-path>`，并按 `needs_run` 处理接管。首次受理一次保存计划、动作及本计划内的来源关联；相同请求重送复用这些记录。

这里的取回时间表示开始处理时间。若录像届时仍未结束，取回等待其正式产物；录像和取回均结束后计划进入 `completed`。计划受理及动作结果通过状态报告给客户端，主程序只消费会话结果。

### `request_id`

`request_id` 由调用方生成。

首次成功受理：

```text
request_id
    ↓
plan_instance_id
    ↓
action_instance_ids
```

之后永久保留该关联。同一 ID 永远以首次成功受理的内容为准；后续提交直接复用原计划，忽略本次正文。复用不改变原计划内容、实例身份或执行进度，也不因本次重试新增动作、交付或设备操作；原计划尚未完成的工作仍按现有状态继续驱动。

输入处理按以下顺序分类；数据库查询及首次注册在受理写事务中完成。

| 输入与持久化状态 | 本次正文 | 计划处理结果 |
| --- | --- | --- |
| 文件未能完整读取 | 未可靠取得 | 按[输入计划文件读取失败](cli-commands.md#输入计划文件读取失败)保存结果，不能据路径或片段认定请求身份 |
| 整份 JSON 无法解析 | 无法取得 | 拒绝输入，不能据其中的片段认定请求身份 |
| JSON 可解析，但 `request_id` 缺失或不合法 | 任意 | 拒绝计划输入 |
| 有效 ID，已受理关联查询失败或结果无法确认 | 任意 | 会话错误，不能当作首次受理 |
| 有效 ID，已有成功受理关联 | 任意，包括变化、字段缺省或动作参数不合法 | 复用首次受理的计划，本次正文不参与静态校验 |
| 有效 ID，没有成功受理关联 | 无整份拒绝条件，可能包含校验失败的动作 | 原子注册新计划及全部动作，保存适用的动作失败结果 |
| 有效 ID，没有成功受理关联 | 存在整份拒绝条件 | 拒绝本次计划，不建立成功受理关联 |

此前被拒绝且尚未成功受理的 ID，后续仍按未受理 ID 处理。原计划完成后，同一 ID 仍关联原计划；表达新的执行意图应使用新的 ID，即使动作内容与历史完全相同。

并发提交相同 ID 时，以首个成功提交受理事务的内容为准；后续事务读取该关联并复用。尚未提交或已回滚的注册不构成首次成功受理。提交结果不确定时，遵守失败与恢复规则。

### 客户端确认与重送

客户端保留待确认请求的 `request_id` 和原计划内容，通过状态报告确认受理结果。确认依据由[状态报告与累计确认](status-reports.md#客户端对受理结果的判断)定义；未收到报告或报告中没有该请求，只表示尚未确认。

请求尚未确认时，由客户端按重试策略使用相同 `request_id` 和原计划内容重送，主程序按普通输入中转。重送不要求先证明上一次未受理：camctl 已有成功受理关联时复用原计划，没有关联时按首次受理处理。`last_report_id` 仍可按独立 ACK 规则更新。

收到已受理证据后，该请求结束受理确认等待；后续执行状态继续通过报告获取。收到能关联到本次输入的明确拒绝结果后，按已知业务错误处理，不再将该次输入视为结果未知。明确拒绝只描述对应输入，不表示该 ID 永久无法受理。

受理确认等待与动作完成等待分别处理。原计划已经受理但仍未执行完，不属于受理结果未知。客户端的重试间隔、次数预算及停止条件仍需细化。

### 重试中的 `last_report_id`

`last_report_id` 在每次输入中独立处理，包括已受理 ID 的重试。有效 ACK 可以单调推进累计确认位置；较旧 ACK 或字段缺省保持确认位置。ACK 的业务错误不改变计划复用结果。

### 计划正文与 ACK 独立处理

`run <plan-path>` 与 `submit <plan-path>` 使用相同规则。计划正文不包含 `last_report_id`；计划按请求 ID 复用或首次受理，与 ACK 的有效性判断分别进行。任何一方的业务输入错误都不阻止处理另一方。

输入能够解析并分别判断请求与 ACK 时，按下表处理。计划“可受理”包含首次完整注册及已受理 ID 的幂等复用，首次注册也可以包含校验失败的动作；“拒绝”包含请求 ID 不合法及首次校验发现的整份拒绝条件。计划处理的具体分区由 `request_id` 决策表定义。

| 计划处理判定 | ACK 状态 | 计划处理 | 累计确认与错误记录 |
| --- | --- | --- | --- |
| 可受理 | 有效 | 完整注册或幂等复用 | 按单调规则吸收 ACK |
| 可受理 | 无效 | 完整注册或幂等复用 | 保持确认位置，记录 ACK 校验错误 |
| 可受理 | 未提供 | 完整注册或幂等复用 | 保持确认位置 |
| 拒绝 | 有效 | 保存拒绝结果 | 按单调规则吸收 ACK |
| 拒绝 | 无效 | 保存拒绝结果 | 保持确认位置，同时记录 ACK 校验错误 |
| 拒绝 | 未提供 | 保存拒绝结果 | 保持确认位置 |

有效 ACK 对应的确认位置等于或早于当前确认位置时，累计确认位置保持不变，不因此产生错误。报告查询和未知 ID 的判定由[ACK 引用的报告记录](status-reports.md#ack-引用的报告记录)定义，报告覆盖含义由同一专题定义。该报告是否满足已有同步责任须另行判断，并在同次输入处理事务中保存相应的责任结束事实，见[ACK 如何结束同步](status-sync.md#ack-如何结束同步)。

文件未能完整读取或整份 JSON 无法解析时，不能从中受理计划或吸收 ACK，保存对应输入失败结果。根对象及字段提取按[校验顺序与错误优先级](plan-input.md#校验顺序与错误优先级)处理；不能把无法判定的 ACK 静默解释为未提供。

独立处理指业务校验结果互不阻断，不改变本专题的数据库事务边界。计划处理结果、有效 ACK 更新及应保存的错误记录仍在本次受理事务中提交；状态库不可用、写入失败或提交结果不确定属于会话错误，遵守失败与恢复规则。

幂等复用不创建新计划或动作实例，也不推进 `plan_seq`；有效 ACK 和 ACK 校验错误仍按表处理。计划拒绝与 ACK 校验错误通过状态报告交给客户端，主程序无需理解这两类业务结果。`needs_run` 继续依据处理后实际存在的工作和报告责任判定。

### 名称和实例 ID

调用方提供：

- `request_id`
- plan `name`
- action `name`
- `group`

CLI 分配：

- `plan_instance_id`
- `action_instance_id`
- `output_id`
- `delivery_id`
- `report_id`

plan/action `name` 是人类可读标签。

CLI 分配的实例 ID 是机器身份，不要求调用方解析格式。

### group

`group` 是轻量集合标签。

同一计划允许：

```text
action A → group = 采样-1
action B → group = 采样-1
```

第一版中，其他支持的动作最多属于一个 group；`obtain_action_outputs` 不属于任何 group，其动作公共字段中必须省略表示动作所属组的 `group`。

动作所属的组与操作参数中的目标组分别判断。取回动作通过 `params.source.group` 引用某个 group 的产物，该引用不会使取回动作成为该组成员；字段结构见 [obtain_action_outputs 的参数](obtaining-outputs.md#参数)。首次受理时按下表校验动作所属的组；表中的 `group` 专指动作公共字段，不包含取回或取消参数中的目标组：

| 动作类型 | 表示动作所属组的 `group` 字段 | 处理 |
| --- | --- | --- |
| `obtain_action_outputs` | 未提供 | 动作不属于任何组，来源引用另行校验 |
| `obtain_action_outputs` | 已提供，无论字段值 | 该动作登记为 `failed`，保留输入与错误，不加入所填写的组 |
| 其他本版支持的动作 | 未提供 | 动作不属于任何组 |
| 其他本版支持的动作 | 提供合法组名 | 动作属于本计划内该组 |
| 其他本版支持的动作 | 提供不合法值 | 该动作登记为 `failed`，保留输入与错误，不生成组成员关系 |

该校验同时适用于两个计划输入入口。动作所属的组与其他参数分别校验：允许属于组的动作提供合法组名时，即使因其他参数错误而失败，仍属于该组；不能通过移出失败动作来改变组的取回或报告范围。取回动作不属于任何组，其他动作填写非法组名时也不生成有效组成员关系，但均保留输入供诊断。已受理 `request_id` 的重试仍直接复用原计划。

group：

- 不参与调度；
- 没有独立状态机；
- 没有成功/失败语义；
- 不创建动作依赖；
- 可以作为取回范围；
- 可以作为取消范围；
- 用于报告组织。

`action name` 在同一计划内保持唯一。

`group` 不要求唯一。

按组取回先按动作类型[筛选产物来源](obtaining-outputs.md#按组取回的成员筛选)，不等待非产物动作，也不将其列为无产物失败；组取消及报告组织仍使用原组成员。录像来源分别准备文件，发布条件见[组内录像分别准备与统一发布](obtaining-outputs.md#组内录像分别准备与统一发布)。

取回可以直接用本计划内的动作名称或组名表达来源，首次受理时由 camctl 保存有效实例关联或该动作的失败诊断；具体寻址规则见[本计划内的产物引用](obtaining-outputs.md#本计划内的产物引用)。该方式不要求客户端预先取得本次新计划的实例 ID。
