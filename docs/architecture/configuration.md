# 本地配置与通信策略

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页定义配置何时加载、默认值怎样覆盖，以及控制调用超时和通信重试策略。配置属于主机部署；执行计划只指定业务要求。首次部署可结合[部署样例](deployment-example.md)阅读。

**阅读提示：** 先读计划要求与通信配置的分工，再看加载、生效时间和默认值。用户要求与拍摄参数随动作保存；本地执行配置由每次运行加载，影响尚未完成工作的后续处理。

例如，一个录像动作已经启动失败两次，尚未结束。程序停止后，部署人员将启动上限从 3 次改为 5 次，再次运行时，这个动作至多还有 3 次新的启动机会，仍须满足启动窗口和安全重试条件。已经结束的失败动作保持终态，不因上限提高而重新执行。

配置文件采用 TOML，一种按字段和值组织配置的文本格式。部署样例给出可直接阅读的[配置覆盖文件](deployment-example.md#一确定本地配置)；无需通过计划 JSON 重复填写本地通信策略。

## 配置归属

### 计划要求与本地通信配置

执行计划描述业务要求：动作类型、拍摄参数类型与参数值、执行时间、适用的启动延迟，以及取回、清理或取消的目标。拍摄参数按目标驱动的正式类型定义提供，驱动从生效参数及任务定义取得执行所需的信息。通信尝试上限、单次命令超时和重试间隔由主机本地设备配置提供，执行计划不覆盖这些值。

| 信息 | 配置来源与处理 |
| --- | --- |
| `scheduled_at`、拍摄 `params`（含 `type`）、动作来源及目标 | 执行计划，按对应动作及目标驱动的参数类型定义校验 |
| 适用于时效动作的 `policy.max_delay_ms` | 执行计划中的业务要求，表示允许延后启动的窗口 |
| 启动、停止及残留收场的尝试上限 | 本地设备配置，各自计数；默认值和预算归属由相机专题定义 |
| `devices.<id>.copy.max_read_attempts` | 本地设备配置，按每份文件累计；默认值、恢复计数及失败语义见[按文件累计读取尝试](file-copy.md#按文件累计读取尝试) |
| `devices.<id>.copy.max_recopies` | 本地设备配置，独立限制摘要不一致后的额外整片重拷；默认值及计数见[摘要不一致后的有限重拷](file-copy.md#摘要不一致后的有限重拷) |
| `devices.<id>.copy.read_idle_timeout_s` | 本地设备配置，限制等待源文件新数据时的连续无数据时长；默认值及计时见[文件读取的无数据超时](file-copy.md#文件读取的无数据超时) |
| 启动、停止及文件读取的重试间隔 | 本地设备配置，分别设置；字段、默认值和计时见[通信重试间隔](#通信重试间隔) |
| 启动、停止及状态查询的单次调用超时 | 本地设备配置，分别设置；字段、默认值和计时见[控制调用超时](#控制调用超时) |
| 状态查询与产物核实的次数、间隔及设备查询时限 | 本地设备配置，按[查询与核实配置](#状态查询与产物核实的配置)分别限制各项责任；执行计划不覆盖 |
| `adb.terminate_grace_s` | 主机本地 ADB 客户端的终止宽限，各设备共用；默认值及计时见[本地 ADB 客户端的终止宽限](#本地-adb-客户端的终止宽限) |
| 延时摄影结果核实前的部署额外等待 | 本地设备配置，非负时长，默认 0；与首次受理固定的驱动必要余量相加，不允许抵消设备要求，见[等待余量](camera-capture.md#驱动必要余量与部署额外等待) |
| 计划在动作 `policy` 中携带通信策略字段，包括 `max_attempts`、`timeout_ms`、`backoff_base_ms` 或 `backoff_max_ms` | 该动作自身参数错误，首次受理登记为 `failed`；不执行该动作，其他动作继续受理 |

第一版动作 `policy` 只承载该动作支持的业务策略。把通信策略写入计划不会改变本地配置，也不静默忽略这些输入；计划及动作的错误范围继续遵守[整份校验与原子受理](plan-acceptance.md#整份校验与原子受理)。

设备控制命令使用各自的命令超时。源文件内容传输按无数据超时判断停滞，不能把普通命令的总时长限制直接套到整份文件拷贝上；持续有新文件数据时，仍可继续读取至已知长度。

当前已核实设备的录像控制调用遵守[厂商控制程序的调用生命周期](camera-recording.md#厂商控制程序的调用生命周期)：调用处理后返回，所启动的设备工作独立持续。该类控制命令的等待上限不按录像目标时长增加；异步等待子进程期间，调度器继续处理其他已具备资格的工作。其他任务的期限遵守其[命令返回含义](camera-capture.md#命令返回含义与等待起点)，调用超时后的结果确认和重试仍服从具体设备契约。

动作首次受理时保存调用方的结构化输入及适用的业务要求，包括 `policy.max_delay_ms`。本地执行配置在每次 CLI 启动时加载，本次运行内固定；新动作和未完成的旧动作在本次运行中的后续操作使用相应的本地值。重建原计划 JSON 使用调用方输入，不把本地通信配置添加进计划。

拍摄动作的业务策略通过校验时，将启动延迟提取到 `actions.max_delay_ms`，同时保留原始 `policy`；其他字段导致受理失败时，仍保留该合法值。业务策略缺失或非法，以及该动作不采用启动窗口时，该列为 SQL `NULL`。具体保存、空值及一致性规则见[生效拍摄参数与启动延迟](../camctl/database/plans-actions.md#生效拍摄参数与启动延迟)。

拍摄动作的驱动、参数类型及其默认值也在首次受理时确定，按[计划字段与参数校验](camera-capabilities.md#计划字段与参数校验)保存；拍摄参数与本地通信策略分别表达。

## 本地配置的加载与更新

第一版本地配置使用 TOML，默认文件为 `$HOME/.camctl/config.toml`，其中 `$HOME` 表示本次 CLI 进程的用户主目录。`init`、`run`、`submit`、`describe` 使用相同规则：未提供 `--config` 时选择默认文件，提供时只选择指定文件；显式相对路径按本次进程的工作目录解释。默认配置文件和默认数据路径均位于用户主目录内，无须为默认部署取得 root 权限。

所有本地配置项均有内置默认值，配置文件只提供覆盖值。先取得完整默认配置，再按字段应用所选文件中实际提供的值，最后校验生效配置。嵌套配置按字段覆盖，省略字段及空表保留默认值；数组配置作为完整值替换。只读取这一份配置文件，不自动搜索其他目录或叠加其他配置文件。显式指定文件不改变其他配置项的默认值，例如仅改变 `--config` 路径不会改变默认状态库位置。

| 所选文件及内容 | 配置加载结果 |
| --- | --- |
| 文件不存在，无论使用默认位置还是显式 `--config` | 使用完整内置默认值；不再寻找另一份文件 |
| 文件为空、仅有注释或合法空表 | 使用完整内置默认值 |
| 文件只提供部分合法字段 | 对应字段使用文件值，其余沿用默认值 |
| 文件无法可靠读取，且不能确认为不存在 | 按配置错误结束本次调用，不将权限或读取故障当作缺省 |
| TOML 无法解析、字段未知、结构或值不合法 | 按配置错误结束本次调用，不用默认值掩盖错误 |

例如，配置文件仅包含以下内容时，只有日志级别被覆盖，目录、调度及其他本地策略继续使用默认值：

```toml
[session]
log_level = "INFO"
```

默认值由所属配置契约集中定义，读取、校验及文档生成使用同一权威来源。设备目录 `devices` 默认为空：没有配置文件也能完成配置加载，但不会凭空绑定相机或 MCU。`describe` 可成功导出空设备目录；新计划引用未配置设备时，仅对应动作按设备不存在失败。显式声明设备时，其绑定及驱动配置仍须合法；具体设备的默认设置由后续接入契约定义。已有动作保留受理时确定的设备身份、驱动选择和拍摄参数；执行前仍须能够可靠取得所需的本地运行配置。设备目录为空不删除历史、不重置结果，也不授权改用另一台设备。

本地配置缺省不改变执行计划的必填要求。拍摄参数由驱动正式类型定义，`policy.max_delay_ms` 等业务字段仍按各自输入契约校验。

配置文件可缺省与状态库须已初始化是两个不同条件。首次部署通过 [`camctl init`](initialization.md) 建立运行环境，`run` / `submit` 不因配置加载成功而自动创建缺失的状态库。

每次 CLI 启动时加载配置，本次进程运行期间保持不变。配置加载不要求创建配置文件；`describe` 仍只读取定义，不为默认路径创建状态库或交接目录。部署流程更新配置前，须暂停新的 CLI 调用，并确认已有 `run`、`submit` 均已退出；完成配置更新后再恢复调用。配置更新是部署流程的职责，日常计划提交和文件中转不需要增加配置切换操作。

会话使用本次启动加载的目录、调度、通信及处理配置。`run` 接管由 `submit` 受理的动作时，从持久化记录取得用户要求、设备身份、驱动选择及生效拍摄参数，执行过程使用本次 `run` 的本地配置。请求重送复用原动作与业务事实，不重置执行进度。

合法拍摄动作以 `actions.driver_id` 保存首次选定驱动。发起设备操作前，须确认所需设备配置可用且绑定驱动与原记录一致；设备配置缺失或驱动绑定不一致时，按[设备绑定异常的影响范围](#设备绑定异常的影响范围)仅阻止相关设备工作，并明确报告配置问题。仅调整本地通信参数不改变原驱动与生效拍摄参数。部署负责保持设备身份以及同一驱动标识下对已有动作的兼容性；完整存储与恢复分类见[拍摄动作的驱动绑定](../camctl/database/plans-actions.md#拍摄动作的驱动绑定)。

Action6 与 OSMO 360 II 的 ADB 连接使用 `devices.<id>.adb.serial`。它必须是明确、非空、不以 `-` 开头且不含 NUL 的字符串；没有默认 serial，不按连接设备的列表顺序选择。每次实际调用根据原 `device_id`、`driver_id` 核对本次配置，并将该设备的 serial 传给 ADB。同一型号的多台设备分别配置自己的 serial；这个本地通信字段不进入客户端计划或替代原设备身份。

| 场景 | 采用的配置与处理 |
| --- | --- |
| CLI 启动且默认值与文件覆盖组成的生效配置有效 | 加载配置，供本次进程使用；运行期间不重新加载 |
| `run` / `submit` 启动时配置加载失败 | 按[会话错误](session-errors.md)结束；文件不存在的合法缺省情况按上表处理 |
| `describe` 启动时配置加载失败 | 按[导出入口](cli-commands.md#describe)的错误输出与退出规则处理 |
| `init` 启动时配置加载失败 | 按[初始化入口](initialization.md#命令结果)报告失败，不开展建库 |
| 更新配置后首次受理新 `request_id` 的计划 | 按本次部署的设备及参数规则校验，保存用户要求及生效拍摄参数 |
| 更新配置后重送已受理的 `request_id` | 复用原动作、用户要求和执行事实，不重新受理或重置次数 |
| 更新配置后执行尚未开始的已有动作，或重试、恢复未完成动作 | 保留原身份、用户要求、生效拍摄参数及执行事实，后续操作采用本次运行的本地配置 |
| 更新配置时动作或所属处理已经结束 | 保持已有终态与结果，不因增加上限或放宽门槛重新执行 |

例如，停止 CLI 后将录像启动超时从 10 秒改为 20 秒，重新启动后，新旧动作接下来实际发起的启动调用都使用 20 秒。之前因等待 10 秒而失败的调用仍保留原失败及当时的依据，不能被重新解释为成功。

### 文件目录的绑定与变更

交接文件在 `staging`、`ready` 和 `processing` 之间移动。程序恢复一次未完成交接时，需要核对这三个位置；仅修改其中一个配置值，也不能让旧文件或原责任改指另一处目录。因此，`paths.staging`、`paths.ready`、`paths.processing` 与状态库共同绑定，按一组路径核对和切换。其默认值见[交接目录配置](file-handoff.md#配置归属)。

三个配置值须为非空绝对目录路径；默认值先按用户主目录生成完整路径。配置加载将重复分隔符、`.`、`..` 及末尾分隔符按主机路径规则规范化，禁止 NUL；不通过配置文件位置或 CLI 工作目录推导基准。绑定保存规范化后的绝对路径文本。三个目录不得相同或相互包含，初始化还须核对实际目录没有指向同一位置的别名，并满足[原子移动条件](file-handoff.md#发布原子性)。部署期间不能更换目录挂载、链接目标或以其他方式改变同一路径指向的位置。

首次初始化在 `database_metadata.staging_path`、`ready_path`、`processing_path` 中保存这组路径。它们表示该状态库正在使用的文件位置，不保存调度、重试等其他配置；字段规则见[数据库元信息](../camctl/database/reports-runtime.md#数据库元信息)。`run`、`submit` 及报告子进程在使用业务状态或文件前，比较本次规范化配置与这三个已保存值；不一致时报告 `configuration_error`，诊断指出变更字段、原路径和新路径，不受理计划、不启动设备或报告工作，也不自动修改绑定。`describe` 仍不读取状态库。

日常启动只核对配置与绑定，不为此扫描全部文件或等待旧责任结束。路径一致时，目录访问和文件操作错误按实际所属业务、报告或日志流程处理；报告目录不可访问不因此变成阻止普通设备动作的额外启动条件。状态库缺失、元信息无效或无法读取仍按状态库错误处理，不据此建立新绑定。日志副本继续遵守其独立故障通道，不以成功读取数据库绑定为交付前提。

#### 哪些情况阻止切换目录

存在保留文件或仍依赖原目录的未完成责任时，拒绝切换。下面各项分别检查；只要有一项阻止，或者无法可靠完成检查，就不能切换。文件实际不存在也不自动解除数据库保存的责任，应先使用原配置按正常业务规则完成恢复或清理。

| 检查对象及状态 | 是否阻止切换，以及应先完成什么 |
| --- | --- |
| 中间文件为 `REQUIRED`，包括已登记但尚未创建的文件 | 阻止；先完成所属读取、处理、登记或交接，再按生命周期结束原目录中的责任 |
| 中间文件为 `RELEASABLE`，清理不是 `COMPLETED` | 阻止；待清理、清理中、失败和未知均须在原目录处理并保存可靠结果 |
| 中间文件为 `PROMOTED`，关联正式产物尚未 `CLEANED` | 阻止；修复成品仍保留，或存在性尚待核实。须通过显式产物清理结束保留责任，不能由初始化删除 |
| 中间文件已可靠自动清理；或已提升且正式产物已 `CLEANED` | 记录本身不阻止；仍核对没有未结束的使用或删除操作，并保留全部历史 |
| 中间文件为 `HANDED_OFF` | 原工作位置不再需要保留，但仍检查对应交付、撤回及交接目录；不能单凭此状态跳过检查 |
| 普通交付处于 `PENDING`、`PREPARING`、`PREPARED`、`PUBLISHING`；或撤回为 `PENDING`、`UNKNOWN` | 阻止；先完成交付恢复或撤回结果。动作终态不代替这些独立责任的结束 |
| 与原目录有关的读取、写入、工具处理、移动、删除或结果保存尚未结束 | 阻止；确认实际操作结束，并按所属流程保存结果，取消等待不算完成 |
| 当前报告责任仍要求完成本地生成、发布或恢复 | 阻止；按[报告责任](status-reports.md)完成必要的本地处理，不以某条旧报告的文件阶段单独判断。已由后续报告覆盖的旧管理记录不新增责任 |
| 只剩客户端 ACK 或显式同步的远端确认，必要本地报告已经完成 | 该确认责任本身不阻止；保留报告和同步记录，后续仍可按原冻结依据重建。原目录中的报告文件仍须按下一行处理 |
| 任一原目录仍有文件、故障标记、无法识别的对象，或者目录不能可靠检查 | 阻止；包括已交给主程序的文件、日志副本和报告残留。由各自责任方处理，初始化不删除、不搬迁、不推断传输成功 |
| 仅有已结束的数据库历史和空目录，没有依赖原路径的责任 | 不因记录永久保留而阻止；历史查询继续解释原相对路径及事实，不访问实际文件 |

尚未产生原目录文件或文件责任的未来设备动作，不因计划仍存在而阻止切换；后续首次建立主机文件时使用新绑定。对于关联缺失、生命周期矛盾或无法确认的责任，报告状态库或检查错误，不能采用“不阻止”的分支。

目录检查覆盖原三目录的全部内容，以有界缓冲分批读取，遇到首个阻止项即可返回诊断；只允许空的实际子目录。不能仅扫描数据库候选而遗漏日志和未知文件，也不能只查看目录为空而忽略已登记但尚未创建的文件。新目录须不存在或只有空的实际子目录，不能接管其他部署已有的文件。已发布文件由主程序完成传输及所属清理，camctl 不为切换而删除 `processing` 内容。

#### 切换入口、共同保存与失败处理

第一版通过显式 `camctl init` 核对并切换目录，不增加日常请求中的切换操作。部署人员先用原配置处理保留文件和未完成责任，再暂停新的 CLI 调用及主程序的目录领取、传输，确认原 `run`、`submit`、报告子进程和文件工具均已退出；随后修改配置，针对原状态库执行 `init`。主程序采用对应的新 `ready`、`processing` 配置后，才能恢复调用和中转。第一版不自动迁移文件。

`init` 保持原状态库的稳定会话锁，先读取旧绑定并检查业务资格，再在数据库事务外核对原目录、准备新目录和检查部署条件。检查通过后，在一次元信息更新事务中重新核对原绑定与责任，将三个路径一起保存；数据库身份、格式、历史、对象 ID、累计 ACK 及原报告依据保持。目录准备沿用初始化的落盘要求，不能把未完成的目录准备与绑定更新一起宣称成功。

| 检查或提交结果 | 后续行为 |
| --- | --- |
| 本次三路径与已保存值相同 | 按重复初始化规则验证原部署，不更换绑定；已有业务文件保留 |
| 路径不同，任一保留文件、未完成责任、旧目录错误或新目录冲突成立 | 初始化失败，指出阻止原因；原绑定和业务记录保持，不删除或迁移文件 |
| 路径不同，全部资格及目录检查可靠通过 | 一次提交新三路径，完成后才允许采用新配置正常运行 |
| 新目录已准备，但绑定保存失败或确认回滚 | 原绑定仍有效；新建空目录可以保留，重新执行时重新核对全部条件 |
| 绑定提交结果未知或进程在返回前退出 | 重新读取原状态库：三路径均为新值表示已经完成；均为旧值表示尚未完成，应重新检查；无法读取或出现不完整组合时报告错误，不选择某一套路径继续 |

路径切换不生成业务事件，不改写旧文件的相对路径、原结果或报告字节；元信息只保存当前部署位置。已经结束的旧文件不因新目录中出现同名对象而恢复使用，永久保留的文件 ID 也不重新分配。历史恢复和目录重建不修改部署绑定。

### 设备绑定异常的影响范围

本次配置已经成功加载，但旧动作或设备文件需要的设备配置缺失，或者配置中的驱动与原绑定不同，camctl 不发起依赖该异常绑定的设备操作，将因此无法执行的动作或逐项处理判为失败。其他设备和不依赖该设备的本地工作继续按各自条件执行，`run` 不因此立即结束或撤销普通接纳资格。

例如，旧录像由 `cam0` 的驱动 A 受理，本次配置将 `cam0` 绑定到驱动 B。camctl 不能把旧录像的参数或设备文件定位信息交给驱动 B；`cam1` 的合法拍摄、已经在主机上准备完成的文件交付，以及状态报告仍可继续。一个取回动作涉及多台设备时，分别判断各份文件的设备依赖，不因其中一台设备的绑定异常停止其他可处理的文件；动作最终汇总仍须反映全部明细的实际结果。

| 待执行的工作 | 绑定异常时的处理 |
| --- | --- |
| 尚未取消且仍有执行资格的拍摄动作，需要通过异常绑定启动、停止或查询设备 | 不发起相关设备操作，将动作判为 `failed`，保存配置缺失或绑定不一致的原因及实际设备事实 |
| 尚未取消的取回或清理动作，其某个处理项需要通过异常绑定读取、核实或删除设备文件 | 将受影响的处理项判为失败，其他项继续处理；全部适用处理结束后按原逐项规则汇总动作结果 |
| 其他设备的工作，且其绑定和执行条件成立 | 继续执行；不因另一台设备的绑定问题提前停止录像或发起应急停止 |
| 不需要访问异常设备的数据库处理、主机文件处理、报告生成及交付 | 继续按所属规则处理；所需输入尚未取得时仍保留原依赖条件 |
| 针对相关动作的合法取消请求 | 按取消规则保存目标取消事实；需要异常绑定的停止或查询处理以失败结束，保留未确认停止等实际事实；目标取消终态及发起取消动作的逐项结果按各自规则汇总 |
| 既有设备活动仍有停止或恢复流程，但执行它需要异常绑定 | 相关流程以失败结束，保留已知残留或未知设备事实，不通过另一种驱动尝试收场；其他设备的收场继续独立处理 |
| 同时发生状态库、锁、时钟或其他会话执行前提错误 | 按实际会话错误规则处理，不能因绑定问题可局部处理而忽略其他错误 |

判定先核对已有终态、取消和启动窗口，再对仍需执行的工作检查绑定。已有终态保持不变，取消已生效的目标仍按取消规则结束，已经满足过期条件的拍摄动作按过期规则处理。未来动作仍按原计划时间取得处理资格，不因加载历史记录就提前执行。合法受理的动作开始执行后发现绑定问题，属于执行失败；首次进入 `running` 与内部执行标记按原状态机保存，再保存失败结果。报告保留执行阶段错误及原生效参数，不能将这个失败改写为受理失败，也不能据此宣称设备命令已经发出。

失败记录说明相关设备标识、原驱动标识、配置缺失或绑定不一致，以及实际已知的本次驱动标识。动作或明细结果、相关流程结果、设备与文件事实、计划聚合及对应历史按所属事务契约共同保存；必要报告表达实际失败。未发起的调用不新增设备尝试或消耗通信重试次数；已有尝试、可靠结果和未知效果保持原事实。已有在途调用仍须跟踪实际结果，不能用业务失败代替调用已经结束的证据。

业务流程失败不证明设备已停止、文件不存在或删除未发生。无法核实的设备活动和文件结果保留未知，已产生的删除限制、读取保护及主机中间文件按各自收场契约处理。残留设备事实按既有后续有效动作触发规则处理，不使已失败动作重新进入等待或反复启动原流程。

配置在本次运行内固定，不通过轮询配置文件等待修正。部署更新遵守停止 CLI 后再修改配置的流程。修正配置后，已失败的动作和处理项保持终态，同一请求重送复用原结果；继续相应业务需要新的有效请求，新请求仍须满足原来源绑定和设备事实等执行条件。

本次失败结果、适用收场及必要报告均已可靠处理，且没有其他待处理工作时，`run` 按正常交接规则关闭接纳并返回 `succeeded`。动作业务失败不单独构成会话错误，也不单独要求再次启动 `run`；报告、数据库等职责另有错误时仍按各自规则处理。`needs_run` 继续依据实际未完成责任计算，不因存在历史失败动作而始终为真。

本节适用于成功加载配置后发现的业务绑定问题。配置文件无法读取、解析或通过配置自身校验时，仍按配置加载错误处理。软件验证须组合两台设备、跨设备取回、主机已有完整副本、报告维护和取消收场，确认异常绑定不会产生设备操作，受影响的动作或处理项失败，其他项及成功副本继续交付。覆盖零次设备调用的执行失败、已有终态、取消、过期、未来动作、未知设备效果、事务中断、报告失败，以及修正配置和同请求重送不重开失败任务。所有职责完成时验证正常退出和无新增责任时的 `needs_run: false`；状态库等会话错误的原处理范围保持有效。

### 本地配置变化与未完成工作

尝试次数、拷贝进度、操作结果和已经可靠保存的业务决定由历史及所属投影保存。本地配置调整影响后续执行资格和新操作，不清除已经发生的事实。设备身份、驱动选择和生效拍摄参数继续遵守受理契约，不能将通信配置更新解释为更换目标设备或拍摄内容。

对需要新增一次尝试的流程，以本次上限减去原累计已用次数计算剩余额度，最小为 0。降低上限后，已用次数可以大于本次上限，这是合法历史状态；不能裁剪旧记录，也不能把新上限作为已有次数的数据库范围约束。配置上调只可能为尚未结束、仍具备执行资格的流程提供后续机会。

以下情况按所属流程判断，已经存在的取消、成功确认、终态和设备安全条件优先成立：

| 持久化事实与本次处理 | 处理规则 |
| --- | --- |
| 动作或处理已经终态 | 保留原结果；配置变化不重新激活该责任。独立的设备收场或文件清理责任仍按自身生命周期处理 |
| 已有可靠成功确认，或取消要求已经生效 | 遵守成功或取消规则，不以增加额度为理由重复普通操作 |
| 上次调用结果未知，或无法确认实际操作已结束 | 先按所属业务核实和收场，不仅凭剩余额度重复副作用 |
| 需要新增尝试，已用次数小于本次上限 | 仍须满足窗口、重试间隔及其他执行条件；全部满足才登记并开始下一次尝试 |
| 需要新增尝试，已用次数大于或等于本次上限 | 不追加尝试，按所属业务的额度耗尽规则处理；已保存次数保持原值 |
| 按所属业务契约恢复已登记、未结束的尝试或拷贝轮次 | 沿用原身份、次数及可靠进度，不重复占用额度；本次运行的后续等待和调用采用本次配置 |
| 已可靠保存修复等处理决定 | 按原决定继续，保留当时依据；决定之后的读取、重试等操作采用本次配置 |
| 尚未可靠保存处理决定 | 使用本次配置和已有可靠事实作出判断；先保存决定再执行相应副作用 |

恢复原尝试或轮次的规则不授予重复发送未知命令的资格。跨运行的重试等待按本次间隔重新计量，无数据超时按本次阈值建立新计时；不累计断电时长。一次运行内不热更新配置，不改变已经进行中的调用期限。

### 执行依据与历史报告

动作保存用户要求和受理时确定的拍摄参数；本地执行配置由本次运行提供。操作意图、实际结果、预算判断或修复决定需要说明所采用的上限、超时或门槛时，将相关值作为该次事实的依据，与对应记录及历史共同保存。这些记录用于解释过去，不作为后续运行必须沿用的配置。

报告按[字段契约](report-format.md)从冻结历史中选取动作结果、错误、产物及交付事实。上限、超时及门槛保存在对应内部记录中；生成报告不能读取当前配置重算过去的结果。仅启动进程或加载新配置不批量改写动作；实际采用新值判断或推进业务时，由所属业务事务保存必要依据，公开结果发生变化时再产生相应报告责任。

旧报告重建使用原历史事实，保持原字节；动作与处理的已保存终态、失败原因和修复决定保持不变。软件验证须覆盖新旧动作、`submit` 受理后由 `run` 执行、上限提高和降低至已用次数以下、未知结果、未结束尝试恢复、取消与终态、判断提交前后中断，以及配置调整前后历史报告重建一致性。

## 拍摄结果核实的额外等待

`devices.<id>.capture.extra_wait_ms` 为延时摄影的结果等待分支增加部署余量，默认 0，合法值是非负整数毫秒，不接受布尔值。它只增加[驱动必要余量](camera-capture.md#驱动必要余量与部署额外等待)之后的等待，不改变目标采集时长或正常停止目标。未采用返回后等待方式的任务不使用该参数。

该值在本次运行内固定。尚未结束的等待在恢复时使用本次配置，保留原发送成功锚点；已保存等待完成则不重新等待。实际采用值与预计检查时间由[设备活动记录](../camctl/database/operation-fields.md#等待未知结果和占用恢复)保存，不能在旧报告重建时读取新配置替代。

## 各类配置的生效范围

以下配置用于当前进程或会话；涉及动作执行的配置影响该会话中实际继续处理的新旧动作。各项默认值与完整处理规则由链接的责任专题定义；本节说明读取和生效的范围。

### 数据库与日志

数据库等待队列使用本次进程的 `database.queue_capacity`，按完整操作条目计量，不固化到动作，也不作为跨进程共享额度。默认值、合法范围及容量计数由[数据库等待队列容量](../camctl/persistence-runtime.md#数据库等待队列容量)定义；满载等待及超时处理遵守[入队等待时限](../camctl/persistence-runtime.md#数据库队列入队等待时限)。

普通日志队列容量、两个接纳水位及 `INFO` 采样概率使用本次进程配置，不固化到动作；报告子进程使用主进程传入的生效值，队列容量按进程独立计算。字段、默认值及组合校验由[运行日志配置](logging.md#配置与默认值)统一定义。

SQLite 锁冲突使用本次会话的 `database.busy_timeout_ms`，每个状态库连接显式设置并核验；报告子进程采用主进程传入的生效值。默认值、合法范围及最终锁忙错误处理由[SQLite 内置忙等待](../camctl/history-storage.md#sqlite-内置忙等待与失败处理)定义。它与等待入队的时限分别计量，不构成数据库调用或整个事务的总时限。

SQLite 自动检查点使用本次会话的 `database.wal_autocheckpoint_pages`，每个状态库写连接显式设置并核验，重新创建连接时沿用相同值。默认值、合法范围和触发规则由[自动 PASSIVE 检查点](../camctl/history-storage.md#自动-passive-检查点与可配置阈值)定义；阈值按 WAL 页记录计量，不作为文件大小上限，不固化到动作。

### 文件处理

相机文件拷贝使用本次会话的 `copy.segment_size` 组织可靠进度的保存粒度，取回、异常原片检查及修复输入共用。默认值、合法范围、最后一段和跨会话调整规则由[进度保存的分段大小](file-copy.md#进度保存的分段大小)定义。读取与重拷的累计次数由所属处理保存；分段大小、尝试上限及通信时限使用本次运行的配置。

正式产物清理使用 `cleanup.max_delete_attempts` 和 `cleanup.max_query_attempts`，在本次运行内固定。每份目标文件独立累计已用次数，跨运行、重送及配置更新不清零；默认值、合法范围及额度耗尽时的处理由[删除与查询的独立尝试预算](output-cleanup.md#删除与查询的独立尝试预算)定义。内部中间文件的清理采用所属生命周期规则，不共用这两组预算。

取回及录像内部中间文件的历史清理使用本次正常运行的 `cleanup.work_file_batch_size` 和 `cleanup.work_file_limit_per_run`，不固化到原动作。默认值、检查计数、跨运行续查及新产生文件的首次清理由[中间文件清理的运行预算](file-handoff.md#中间文件清理的运行预算)统一定义。

### 历史查询与快照

历史快照维护使用本次会话的 `history.snapshot_change_threshold`，[维护范围](../camctl/history-snapshots.md#历史快照的对象范围)内的对象共用该阈值并各自累计变化次数。配置项的默认值、合法范围及跨会话判断由[历史快照触发规则](../camctl/history-snapshots.md#按对象累计变化次数触发历史快照)定义。

每批快照维护的对象数量由 `history.snapshot_batch_size` 限制，处理完成后及时释放临时数据。默认值、合法范围及批次处理规则由[快照维护批量限制](../camctl/history-snapshots.md#快照维护批量限制)定义。

报告生成及重建的实体、历史事件读取分别由 `history.entity_batch_size` 和 `history.event_batch_size` 控制，部署时可独立调整。两项配置在本次会话内固定，改变批次不改变报告内容；默认值、适用范围、校验与生效规则见[读取批次配置](../camctl/historical-state-query.md#实体与事件读取批次分别配置)。

## 容量配置的表示

本地配置中按字节计量的容量使用带单位的 TOML 字符串，字段名表达用途，例如 `copy.segment_size` 和 `session.log_max_size`。配置加载时统一解析为整数个字节，处理流程使用解析结果。默认值由各字段所属专题定义；本节统一定义容量的书写与校验规则。

| 单位 | 对应字节数 |
| --- | --- |
| `B` | 1 |
| `KiB`、`MiB`、`GiB` | 分别为 1024、1024²、1024³ |
| `KB`、`MB`、`GB` | 分别为 1000、1000²、1000³ |

字符串由十进制数值和上表中的单位组成，单位区分大小写。数值使用 ASCII 数字，可有小数点，小数点前后均须有数字；数值与单位之间及字符串首尾允许零个或多个 ASCII 空格。例如 `"128 MiB"`、`"128MiB"` 和 `"1.5 GiB"` 均符合书写规则。数值不带正负号，不使用指数、分隔符或单位缩写别名。

按下表顺序校验。换算须保留十进制数值的精确含义，不使用二进制浮点近似、截断或四舍五入取得字节数。通过通用校验后，再按所属字段的范围校验；当前分段大小和日志轮换大小均要求大于 0。

| 输入条件 | 处理 |
| --- | --- |
| 字段省略 | 使用所属字段的默认值 |
| 显式值不是字符串，包括整数、浮点数和布尔值 | 配置错误 |
| 字符串不符合书写规则或单位不在上表中，例如 `"128"`、`"128 M"`、`"128 mib"`、`"-1 MiB"` | 配置错误 |
| 书写合法，但换算结果不是整数个字节，例如 `"0.1 B"` | 配置错误 |
| 换算结果为整数，但不满足所属字段的范围，例如当前两项配置使用 `"0 B"` | 配置错误 |
| 换算结果为整数且满足所属字段的范围 | 接受，使用精确的字节数；例如 `"1.5 KiB"` 为 1536 字节 |

容量语法仅适用于声明为字节容量的本地配置项。按条目、次数或页数计量的配置继续使用各自的整数规则；报告中的完整文件长度和覆盖水位等机器字段继续按协议表示。验收须覆盖两类单位的倍率、空格、小数精确换算、全部错误分区，以及不同合法写法表示相同容量时取得相同生效值。

## 控制调用超时

第一版录像启动、录像停止的单次调用等待上限各自默认 **10 秒**，允许分别配置为有限的正秒数。状态查询的默认值由[查询与核实配置](#状态查询与产物核实的配置)定义，采用本节的单次调用计时规则。0、负数及非有限数值属于本地配置错误。配置在本次运行内固定，后续运行的新调用使用当次配置；实际结果及历史调用依据保持原值。执行计划不能覆盖。

| 本地配置 | 适用调用 |
| --- | --- |
| `devices.<id>.recording.start_timeout_s` | 一次录像启动控制调用 |
| `devices.<id>.recording.stop_timeout_s` | 一次录像停止控制调用 |
| `devices.<id>.query.timeout_s` | 一次设备状态查询，包含录像状态及正在录制文件路径的查询；完整配置见[查询与核实配置](#状态查询与产物核实的配置) |

从主机实际开始本次驱动调用时，使用当前会话的单调钟计时；当前 ADB 驱动从发起本次 `adb` 子进程调用开始覆盖启动和等待结果的过程。不把动作排队、设备准备、重试间隔或录像持续时间计入本次调用。开始读取输出不结束计时，日志或部分响应也不重置期限；取得完整调用结果后按驱动协议解释。该上限限制正常等待调用结果的时间，超时后的子进程清理与必要设备核实仍按各自有限处理规则执行，不承诺全部收场在同一上限内完成。

| 调用结果与已取得的证据 | 处理 |
| --- | --- |
| 在期限内完成，结果可以按驱动契约可靠解释 | 保存实际成功、明确失败或查询状态；程序正常退出不自动等于业务成功 |
| 在期限内完成，但结果无法可靠解释 | 保存响应异常与实际证据，不把无法解释的结果当作未执行或不存在 |
| 调用超时或通信异常，已有足以确认业务结果的可靠证据 | 保留该业务事实及调用异常，按实际设备状态处理；不抹去已取得的启动或停止确认，不盲目重复操作 |
| 调用超时或通信异常，没有足以确认业务结果的证据 | 保存结果未知，进入所属流程的有限核实或收场；查询失败不表示相机空闲或文件不存在 |

调用超时不证明远端程序已结束，也不撤销已经发生的设备操作。主机侧调用清理与再次发令的协调遵守驱动契约；只有已经满足安全重试条件、确认上次调用结束且还有执行资格时，才按[通信重试间隔](#通信重试间隔)安排下一次尝试。启动或停止的实际尝试按原预算计数，超时不退还已经消耗的次数。

例如启动调用等待 10 秒后超时，不意味着在第 13 秒必然重发。须先处理旧调用并核实是否已经启动；只有允许再次启动，才开始对应的重试等待。状态查询使用自己的调用上限，不因它由启动或停止流程触发，就改用触发操作的上限。

源文件内容读取遵守[文件读取的无数据超时](file-copy.md#文件读取的无数据超时)。本节的录像状态查询上限不套用到整片读取、源端整片摘要计算或主机媒体处理；这些操作按所属契约处理。

## 状态查询与产物核实的配置

录像启动结果未知时，camctl 可以在启动核实责任内有限查询；后来停止结果未知时，使用独立的停止核实次数。延时摄影的结果集合可以分批检查，一轮检查不因文件数或批次数增加尝试次数。责任划分以[查询用途](../camctl/database/operation-fields.md#活动查询的责任范围)和[产物核实轮次](../camctl/database/operation-fields.md#产物结果核实的责任与轮次)为准，配置只提供每项责任的执行参数。

| 本地配置 | 默认值 | 适用范围 |
| --- | --- | --- |
| `devices.<id>.query.max_attempts` | 3 次，包含第一次 | 每项独立状态查询责任的累计上限；五种查询用途采用同一配置值，但分别计数 |
| `devices.<id>.query.retry_interval_s` | 3 秒 | 同一责任因查询失败或条件暂未满足而安排再次查询的等待间隔 |
| `devices.<id>.query.timeout_s` | 10 秒 | 一次设备状态查询调用的正常结果等待上限 |
| `devices.<id>.residual_stop.max_attempts` | 3 次，包含第一次 | 同一残留收场流程停止历史录像的累计上限，不重置原停止流程次数，也不消耗触发动作自身的启动或停止次数（[残留收场](camera-recovery.md#后续动作触发的残留收场)） |
| `devices.<id>.residual_stop.retry_interval_s` | 3 秒 | 同一收场流程停止失败或未确认后，再次停止前的等待间隔 |
| `devices.<id>.residual_stop.timeout_s` | 10 秒 | 一次收场停止调用的正常结果等待上限 |
| `devices.<id>.result_check.max_attempts` | 3 轮，包含第一轮 | 同一拍摄结果核实责任的累计检查轮数 |
| `devices.<id>.result_check.retry_interval_s` | 3 秒 | 本轮失败或结果暂不能确认后，再次检查前的等待间隔 |
| `devices.<id>.result_check.call_timeout_s` | 10 秒 | 核实中每次设备文件列举、归属或完成信息查询调用的正常结果等待上限 |

上述数值是第一版的初始工程默认值，与既有有限通信尝试及固定间隔策略保持一致；实际设备响应和文件规模在联调时测量，并按设备调整配置。它们不承诺任务会在固定总时长内完成。

各项分别按字段覆盖。次数必须为正整数；调用时限必须为有限正秒数；间隔必须为有限非负秒数，0 表示不额外等待，秒数允许小数。布尔值不作为合法次数或秒数，非法值按本地配置错误处理。本次运行内配置固定，后续运行的新增尝试使用当次配置，并保存实际采用的上限、间隔和调用时限。原累计次数与确定结果保持不变；提高上限不重开终态责任，降低上限不使已有次数无效。

调用时限按[控制调用计时](#控制调用超时)执行，包含本次 ADB 客户端启动及等待完整查询响应；输出片段不刷新期限。设备调用超时后先完成适用收场，再按证据和剩余额度处理。状态查询成功但条件暂未满足也消耗一次次数；失败、超时及重启均不退还已登记次数。

产物核实按每次设备查询分别计时，不将调用时限套到整个文件集合。一轮读取多批时，后续批次继续原尝试，无须等待轮次重试间隔；某次设备查询失败使本轮不能完成时，保存本轮失败或未确认事实，再判断是否允许下一轮，不在轮内额外重试来绕过轮数上限。源端整片摘要计算、文件内容拷贝、主机媒体处理及本地文件操作遵守各自契约，不套用本节的元数据查询时限。

以下规则均以责任仍有执行资格、预算有余及先前相关调用已经完成适用收场为前提。等待使用本次会话的单调钟并异步进行，不阻塞其他设备工作；等待不消耗次数，也不授予执行资格。

| 当前需要的工作 | 间隔与后续处理 |
| --- | --- |
| 首次查询或首次产物核实 | 按业务要求的检查时机执行，不额外等待重试间隔；延时摄影仍须满足其首次结果检查条件 |
| 同一责任的调用失败，或者本次正常响应表明仍须再次检查 | 在原尝试已收场并具备再次检查资格时，开始对应间隔；有更晚的业务检查时间时继续遵守该时间，间隔不允许提前查询 |
| 只是等待动作占用、采集时长或其他业务条件 | 按原通知、期限及等待规则处理；配置存在不新增周期查询，也不使等待消耗次数 |
| 新的独立责任首次需要查询，例如进入停止核实或残留收场核实 | 使用该责任自己的次数，满足执行条件即可查询，不继承上一种查询用途的重试等待 |
| 重启后原责任已有重试等待要求 | 沿原次数，在本次重新具备重试资格后按本次间隔计时；不跨进程比较单调钟读数 |
| 重启对账需要新的观察，但没有尚待履行的重试等待 | 按恢复资格开始原责任内的新尝试，不额外增加首次等待，也不刷新原次数 |
| 已有可靠结果、已明确不满足要求，或资格及预算不再允许继续 | 按所属成功、失败、取消或未确认规则处理，不为用满次数继续检查，不重新解释为暂时未知 |

验收覆盖默认值、独立覆盖、非法数值、本次运行固定及配置变化后恢复；组合查询成功但仍在执行、多文件跨批次、设备查询超时、迟到结果、取消、预算耗尽及提交未知。验证原次数不重置、单次调用期限不因输出刷新、轮内分页不增加次数，以及下一轮不能绕过原调用收场。目标机响应和吞吐另行联调，不以软件测试耗时代替设备性能结论。

## 本地 ADB 客户端的终止宽限

删除调用超过正常等待期限，本地 ADB 客户端仍在运行时，camctl 向该客户端发送 `SIGTERM` 请求终止。客户端在宽限内退出就立即继续收场；宽限到期仍未退出时发送 `SIGKILL`，随后等待确认退出并完成本地资源清理。超时或取消需要终止本地 ADB 客户端时，均使用本节规则。

| 本地配置 | 默认值 | 合法值与归属 |
| --- | --- | --- |
| `adb.terminate_grace_s` | 3 秒 | 有限正秒数，允许小数；0、负数、非有限数值及非数值类型均为配置错误。属于主机本地 ADB 配置，同一主机各设备共用，执行计划不能覆盖 |

本次 CLI 启动时加载生效值，运行期间不变。宽限从向仍在运行的客户端发送本次 `SIGTERM` 时开始，使用本次进程的单调钟计量；重复取消通知、部分输出或其他工作推进均不刷新该期限。正常调用超时或读取无数据超时仍按各自规则计量，不从宽限中扣除，也不因进入宽限而重新开始正常等待。

| 本地客户端的可靠状态 | 处理 |
| --- | --- |
| 开始终止处理时已经退出 | 完成其余本地资源清理，不发送终止信号，也不等待宽限 |
| 仍在运行，尚未请求终止 | 发送 `SIGTERM`，开始宽限计时并异步等待退出 |
| 宽限尚未结束，客户端已经退出 | 立即继续收场，不等待剩余宽限 |
| 宽限尚未结束，客户端仍在运行 | 继续异步等待；其他动作、取消处理和报告工作按原规则推进 |
| 宽限结束，客户端仍在运行 | 发送 `SIGKILL`，继续等待可靠退出结果；不因信号已发出而放行依赖收场的后续操作 |
| 信号发送与客户端退出发生交错 | 核对实际退出状态；已退出则继续收场，无法可靠确认时保留诊断及原收场责任，不猜测成功 |

宽限只决定何时升级为强制终止，不是本地收场总时限，也不证明远端命令或业务工作已结束。适用的远端运行假设和实际业务效果仍遵守[ADB 调用契约](adb-execution.md)。底层持续失去响应继续按第一版部署边界处理。

实际使用宽限时，将采用的值随[尝试结束依据](../camctl/database/operation-fields.md#结束结果的统一结构)保存，不增加独立的数据库普通列。未使用宽限的正常返回不补造该处理事实；重启后未取得原结果时，不用新配置补填原调用的宽限值。既有结果和历史保留原依据。

本节仅管理 camctl 仍在运行时发起的本地 ADB 客户端终止。camctl 已经退出时，接入模块按[遗留进程收场规则](../host-demo/design.md#接入模块的本地进程收场责任)直接强制终止原受管执行进程，再确认退出；该路径不使用本节宽限。共享 ADB 服务端、其他本地工具及主机文件线程按各自契约管理。

## 通信重试间隔

第一版对录像启动、录像停止和文件读取采用固定重试间隔，各自默认 **3 秒**，允许分别配置为有限、非负的秒数；0 表示满足重试资格后不额外等待。配置在本次运行内固定，跨运行恢复等待时按本次间隔重新计时；原尝试次数和结果继续保留。执行计划不能覆盖。

| 本地配置 | 适用操作 |
| --- | --- |
| `devices.<id>.recording.start_retry_interval_s` | 同一录像的再次启动尝试 |
| `devices.<id>.recording.stop_retry_interval_s` | 同一停止流程的再次停止尝试；适用于正常停止、取消、恢复及使用该停止配置的有限收场 |
| `devices.<id>.copy.retry_interval_s` | 同一文件读取失败后允许的再次读取，包含取回、异常原片检查及修复输入拷贝 |

第一次尝试按自身执行资格开始，不预先等待重试间隔。一次尝试结束后，在判定允许重试且确认上次调用已经结束时开始计时；文件读取须确认旧读取实际停止。当前会话使用单调钟计量等待，每次失败后的间隔采用本次运行中该操作的配置值。等待不消耗新的尝试次数，也不刷新次数上限或启动窗口。

以下条件按表中顺序判断，时间到达本身不授予重试资格：

| 当前条件 | 处理 |
| --- | --- |
| 已取得成功确认 | 结束相应尝试流程，不再安排重试 |
| 本次操作因取消而失去资格、预算耗尽、适用的启动窗口耗尽或存在其他禁止重试条件 | 按所属动作规则结束或收场，不为等待间隔延长执行资格；取消录像后必要的停止仍按停止流程判断资格 |
| 上次调用尚未结束，或结果未知且尚不能依据设备契约安全重试 | 先完成调用收场、对账或错误处理；不能仅因已经等待足够时间再次发令 |
| 允许重试、上次调用已结束，但间隔未到 | 保持等待，继续处理其他调度事件 |
| 间隔已到，但设备或其他可等待的执行条件尚未满足 | 继续等待相应条件，不发送命令 |
| 间隔已到且全部执行条件满足 | 使用原流程剩余预算开始下一次尝试 |

等待期间继续遵守[录像启动机会保留](camera-recording.md#等待重试时保留相机)和[文件拷贝机会保留](file-copy.md#等待重试时保留拷贝机会)。取消、窗口到期及必要停止等事件可及时处理，不能用阻塞整个调度器的等待实现间隔。文件已经读完、摘要不一致后申请整片重拷属于独立的重拷流程，按其预算和候选选择规则处理，不当作本节的读取通信失败。

例如启动失败并确认调用结束的时刻为 09:00:00，采用默认间隔时，最早在 09:00:03 再次启动；若启动窗口在 09:00:02 结束，则及时按过期规则处理，不能等到 09:00:03 再发令。停止与文件读取使用各自间隔，不套用录像启动窗口。

## 设备文件删除与查询的计时

正式产物清理对设备文件删除和存在性查询分别设置调用时限及重试间隔。字段由本节统一定义，次数遵守[删除与查询的独立尝试预算](output-cleanup.md#删除与查询的独立尝试预算)。

| 本地配置 | 默认值 | 含义 |
| --- | --- | --- |
| `devices.<id>.cleanup.delete_timeout_s` | 10 秒 | 一次设备文件删除调用的正常结果等待上限 |
| `devices.<id>.cleanup.query_timeout_s` | 10 秒 | 一次设备文件存在性查询的正常结果等待上限 |
| `devices.<id>.cleanup.delete_retry_interval_s` | 3 秒 | 确认允许再次删除后，重发删除调用前的等待间隔 |
| `devices.<id>.cleanup.query_retry_interval_s` | 3 秒 | 文件存在性查询失败后，再次查询前的等待间隔 |

四项可分别配置。调用时限必须为有限的正秒数，间隔必须为有限的非负秒数，间隔为 0 时不额外等待；布尔值不作为合法数值。执行及恢复采用本次运行的配置，实际调用和结果保留当时依据；请求重送不重置次数，执行计划不能覆盖。

从实际开始一次驱动调用起，使用本次会话的单调钟计量调用时限；当前 ADB 驱动包含子进程启动及等待完整结果的过程。排队、执行资格等待和重试间隔不占用本次调用时限，部分响应不刷新期限。时限只约束正常等待结果的阶段，不包含随后必要的调用收场，也不是整个清理动作的完成期限。

删除调用超时且没有可靠结果时保留删除结果未知，先跟踪实际调用结束并按驱动契约核实，不能据超时直接重发删除。查询失败或超时不表示文件不存在。已有可靠业务结果时保留该结果及实际调用错误，不因错误抹去成功证据。每次实际尝试继续占用对应次数，超时不退还额度。

以下各项都以状态记录可靠、动作仍有资格、对应预算有余及上次调用已实际结束为前提。条件未满足时，按清理资格、取消、预算或持久化规则处理，等待时间届满不授予执行资格。

| 需要执行的操作及原因 | 间隔处理 |
| --- | --- |
| 首次删除目标文件 | 不预先等待重试间隔 |
| 删除结果未知后开始本次核实，或中断恢复时首次核实目标文件 | 具备查询条件后即可查询，不额外等待删除或查询重试间隔 |
| 查询失败，仍需再次查询 | 从确认失败且原调用已结束、具备重试资格时开始等待查询重试间隔 |
| 可靠确认删除未完成，且允许再次删除 | 从确认可重试且原调用已结束时开始等待删除重试间隔；必要查询完成之前不提前计完这段等待 |
| 已取得可靠的删除完成或文件不存在证据 | 结束本文件处理，不等待或派发后续重试 |

重试间隔使用单调钟和异步等待，期间其他设备动作及取消处理继续推进。查询成功确认文件仍存在后，再次删除依然使用原删除计数；随后因新一次删除结果未知而发起的首次核实，不属于前一次查询失败的重试，但继续使用原查询预算。等待阶段跨运行恢复时，在本次重新具备相应重试资格后按本次运行的间隔计时，不跨进程比较单调钟读数，也不重置尝试次数。

本节仅约束设备文件调用。主机上 `staging/derived/` 成品的查询和删除继续由文件工作线程执行，异步等待实际完成或返回错误，遵守[本地文件操作的完成与故障边界](../camctl/file-runtime.md#本地文件操作的完成与故障边界)，不套用设备调用时限或增加强制中止线程的机制。

验收覆盖配置缺省及独立覆盖、非法值、本次运行内固定及配置更新后恢复；用可控单调钟验证调用期限、部分响应不续期、首次核实不额外等待、查询失败后的等待及确认可再次删除后的等待。组合取消、预算耗尽、上次调用未结束、等待中断恢复及迟到结果，确认计时不绕过资格或刷新预算；主机本地文件调用保持既有完成规则。
