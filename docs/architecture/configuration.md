# 本地配置与通信策略

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页定义配置何时加载、默认值怎样覆盖，以及控制调用超时和通信重试策略。配置属于主机部署；执行计划只指定业务要求。首次部署可结合[部署样例](deployment-example.md)阅读。

**阅读提示：** 先读计划要求与通信配置的分工，再看加载、生效时间和默认值。配置文件可不存在；已受理动作使用当时保存的配置，后续修改不重新解释原动作。

例如，部署配置规定录像启动最多尝试 3 次。一份新计划受理时保存当时采用的上限；即使部署人员后来改为 5 次，这份已受理计划仍使用原来保存的值。文档将这种“确定并保存，后续沿用”的行为称为固化。

配置文件采用 TOML，一种按字段和值组织配置的文本格式。部署样例给出可直接阅读的[配置覆盖文件](deployment-example.md#一确定本地配置)；无需通过计划 JSON 重复填写本地通信策略。

## 配置归属

### 计划要求与本地通信配置

执行计划描述业务要求：动作类型、拍摄参数类型与参数值、执行时间、适用的启动延迟，以及取回、清理或取消的目标。拍摄参数按目标驱动的正式类型定义提供，驱动从生效参数及任务定义取得执行所需的信息。通信尝试上限、单次命令超时和重试间隔由主机本地设备配置提供，执行计划不覆盖这些值。

| 信息 | 配置来源与处理 |
| --- | --- |
| `scheduled_at`、拍摄 `params`（含 `type`）、动作来源及目标 | 执行计划，按对应动作及目标驱动的参数类型定义校验 |
| 适用于时效动作的 `policy.max_delay_ms` | 执行计划中的业务要求，表示允许延后启动的窗口 |
| 启动、停止及残留收场的尝试上限 | 本地设备配置，各自计数；默认值和预算归属由相机专题定义 |
| `devices.<id>.copy.max_read_attempts` | 本地设备配置，按每份文件累计；默认值、恢复计数及失败语义见[按文件累计读取尝试](file-copy.md#按文件累计读取尝试) |
| `devices.<id>.copy.max_recopies` | 本地设备配置，独立限制摘要不一致后的额外整片重拷；默认值及计数见[摘要不一致后的有限重拷](file-copy.md#摘要不一致后的有限重拷) |
| `devices.<id>.copy.read_idle_timeout_s` | 本地设备配置，限制等待源文件新数据时的连续无数据时长；默认值及计时见[文件读取的无数据超时](file-copy.md#文件读取的无数据超时) |
| 启动、停止及文件读取的重试间隔 | 本地设备配置，分别设置；字段、默认值和计时见[通信重试间隔](#通信重试间隔) |
| 启动、停止及状态查询的单次调用超时 | 本地设备配置，分别设置；字段、默认值和计时见[控制调用超时](#控制调用超时) |
| 计划在动作 `policy` 中携带通信策略字段，包括 `max_attempts`、`timeout_ms`、`backoff_base_ms` 或 `backoff_max_ms` | 该动作自身参数错误，首次受理登记为 `failed`；不执行该动作，其他动作继续受理 |

第一版动作 `policy` 只承载该动作支持的业务策略。把通信策略写入计划不会改变本地配置，也不静默忽略这些输入；计划及动作的错误范围继续遵守[整份校验与原子受理](plan-acceptance.md#整份校验与原子受理)。

设备控制命令使用各自的命令超时。源文件内容传输按无数据超时判断停滞，不能把普通命令的总时长限制直接套到整份文件拷贝上；持续有新文件数据时，仍可继续读取至已知长度。

当前已核实设备的控制调用遵守[厂商控制程序的调用生命周期](camera-recording.md#厂商控制程序的调用生命周期)：调用处理后返回，所启动的设备工作独立持续。控制命令的等待上限不按录像目标时长增加；异步等待子进程期间，调度器继续处理其他已具备资格的工作。调用超时后的结果确认和重试仍服从具体设备契约。

动作首次受理时，分别保存调用方的结构化输入和执行所需的生效配置。生效配置包含适用的计划业务要求与本地通信配置值，后续执行、重试和恢复沿用该快照；修改本地配置只影响后来首次受理的动作。同一请求重送不刷新配置。重建原计划 JSON 使用调用方输入，不把本地通信配置添加进计划。

拍摄动作的驱动、参数类型及其默认值也在首次受理时确定，按[计划字段与参数校验](camera-capabilities.md#计划字段与参数校验)保存；拍摄参数与本地通信策略分别表达。

## 本地配置的加载与更新

第一版本地配置使用 TOML，默认文件为 `$HOME/.camctl/config.toml`，其中 `$HOME` 表示本次 CLI 进程的用户主目录。`init`、`run`、`submit`、`describe` 使用相同规则：未提供 `--config` 时选择默认文件，提供时只选择指定文件；显式相对路径按本次进程的工作目录解释。默认配置文件和默认数据路径均位于用户主目录内，无须为默认部署取得 root 权限。

所有本地配置项均有内置默认值，配置文件只提供覆盖值。先取得完整默认配置，再按字段应用所选文件中实际提供的值，最后校验生效配置。嵌套配置按字段覆盖，省略字段及空表保留默认值；数组配置作为完整值替换。只读取这一份配置文件，不自动搜索其他目录或叠加其他配置文件。显式指定文件不改变其他配置项的默认值，例如仅改变 `--config` 路径不会改变默认状态库位置。

| 所选文件及内容 | 配置加载结果 |
| --- | --- |
| 文件不存在，无论使用默认位置还是显式 `--config` | 使用完整内置默认值；不再寻找另一份文件 |
| 文件为空、仅有注释或合法空表 | 使用完整内置默认值 |
| 文件只提供部分合法字段 | 对应字段使用文件值，其余沿用默认值 |
| 文件无法可靠读取，且不能确认为不存在 | 按配置错误结束本次调用，不将权限或读取故障当作缺省 |
| TOML 无法解析、字段未知、结构或值不合法 | 按配置错误结束本次调用，不用默认值掩盖错误 |

例如，配置文件仅包含以下内容时，只有日志级别被覆盖，目录、调度及其他本地策略继续使用默认值：

```toml
[session]
log_level = "INFO"
```

默认值由所属配置契约集中定义，读取、校验及文档生成使用同一权威来源。设备目录 `devices` 默认为空：没有配置文件也能完成配置加载，但不会凭空绑定相机或 MCU。`describe` 可成功导出空设备目录；新计划引用未配置设备时，仅对应动作按设备不存在失败。显式声明设备时，其绑定及驱动配置仍须合法；具体设备的默认设置由后续接入契约定义。已有动作的执行与恢复继续使用其已保存的配置和身份，不因当前设备目录为空而删除历史或重置结果。

本地配置缺省不改变执行计划的必填要求。拍摄参数由驱动正式类型定义，`policy.max_delay_ms` 等业务字段仍按各自输入契约校验。

配置文件可缺省与状态库须已初始化是两个不同条件。首次部署通过 [`camctl init`](initialization.md) 建立运行环境，`run` / `submit` 不因配置加载成功而自动创建缺失的状态库。

每次 CLI 启动时加载配置，本次进程运行期间保持不变。配置加载不要求创建配置文件；`describe` 仍只读取定义，不为默认路径创建状态库或交接目录。部署流程更新配置前，须暂停新的 CLI 调用，并确认已有 `run`、`submit` 均已退出；完成配置更新后再恢复调用。配置更新是部署流程的职责，日常计划提交和文件中转不需要增加配置切换操作。

会话使用本次启动加载的目录、调度等运行配置；执行动作时，使用该动作首次受理时已经保存的生效配置。`run` 接管由 `submit` 受理的动作时，同样从持久化记录取得动作配置，不能用自身启动配置重新计算或覆盖动作快照。

| 场景 | 采用的配置与处理 |
| --- | --- |
| CLI 启动且默认值与文件覆盖组成的生效配置有效 | 加载配置，供本次进程使用；运行期间不重新加载 |
| `run` / `submit` 启动时配置加载失败 | 按[会话错误](session-errors.md)结束；文件不存在的合法缺省情况按上表处理 |
| `describe` 启动时配置加载失败 | 按[导出入口](cli-commands.md#describe)的错误输出与退出规则处理 |
| `init` 启动时配置加载失败 | 按[初始化入口](initialization.md#命令结果)报告失败，不开展建库 |
| 更新配置后首次受理新 `request_id` 的计划 | 使用本次加载的配置，保存各动作适用的生效配置 |
| 更新配置后重送已受理的 `request_id` | 复用原动作及其配置，不刷新快照 |
| 更新配置后执行尚未开始的已有动作，或重试、恢复已有动作 | 沿用该动作原有快照 |

例如，停止 CLI 后将录像启动超时从 10 秒改为 20 秒，重新启动后，新受理动作使用 20 秒；更新前已受理的动作仍使用 10 秒，即使此前尚未执行。配置更新不改写历史，也不重置已有尝试次数。

## 各类配置的生效范围

以下配置分别用于当前进程、当前会话或已受理动作。各项默认值与完整处理规则由链接的责任专题定义；本节说明读取和生效的范围。

### 数据库与日志

数据库等待队列使用本次进程的 `database.queue_capacity`，按完整操作条目计量，不固化到动作，也不作为跨进程共享额度。默认值、合法范围及容量计数由[数据库等待队列容量](../camctl/persistence-runtime.md#数据库等待队列容量)定义；满载等待及超时处理遵守[入队等待时限](../camctl/persistence-runtime.md#数据库队列入队等待时限)。

普通日志队列容量、两个接纳水位及 `INFO` 采样概率使用本次进程配置，不固化到动作；报告子进程使用主进程传入的生效值，队列容量按进程独立计算。字段、默认值及组合校验由[运行日志配置](logging.md#配置与默认值)统一定义。

SQLite 锁冲突使用本次会话的 `database.busy_timeout_ms`，每个状态库连接显式设置并核验；报告子进程采用主进程传入的生效值。默认值、合法范围及最终锁忙错误处理由[SQLite 内置忙等待](../camctl/history-storage.md#sqlite-内置忙等待与失败处理)定义。它与等待入队的时限分别计量，不构成数据库调用或整个事务的总时限。

SQLite 自动检查点使用本次会话的 `database.wal_autocheckpoint_pages`，每个状态库写连接显式设置并核验，重新创建连接时沿用相同值。默认值、合法范围和触发规则由[自动 PASSIVE 检查点](../camctl/history-storage.md#自动-passive-检查点与可配置阈值)定义；阈值按 WAL 页记录计量，不作为文件大小上限，不固化到动作。

### 文件处理

相机文件拷贝使用本次会话的 `copy.segment_size` 组织可靠进度的保存粒度，取回、异常原片检查及修复输入共用。默认值、合法范围、最后一段和跨会话调整规则由[进度保存的分段大小](file-copy.md#进度保存的分段大小)定义。该处理配置不固化到动作；读取尝试、重拷次数及通信时限仍使用各自已固化的设备配置。

正式产物清理使用 `cleanup.max_delete_attempts` 和 `cleanup.max_query_attempts`，在清理动作首次受理时固化。每份目标文件独立计数，跨运行、重送及配置更新不重置；默认值、合法范围及额度耗尽时的处理由[删除与查询的独立尝试预算](output-cleanup.md#删除与查询的独立尝试预算)定义。内部中间文件的清理采用所属生命周期规则，不共用这两组预算。

取回及录像内部中间文件的历史清理使用本次正常运行的 `cleanup.work_file_batch_size` 和 `cleanup.work_file_limit_per_run`，不固化到原动作。默认值、检查计数、跨运行续查及新产生文件的首次清理由[中间文件清理的运行预算](file-handoff.md#中间文件清理的运行预算)统一定义。

### 历史查询与快照

历史快照维护使用本次会话的 `history.snapshot_change_threshold`，[维护范围](../camctl/history-snapshots.md#历史快照的对象范围)内的对象共用该阈值并各自累计变化次数。配置项的默认值、合法范围及跨会话判断由[历史快照触发规则](../camctl/history-snapshots.md#按对象累计变化次数触发历史快照)定义。

每批快照维护的对象数量由 `history.snapshot_batch_size` 限制，处理完成后及时释放临时数据。默认值、合法范围及批次处理规则由[快照维护批量限制](../camctl/history-snapshots.md#快照维护批量限制)定义。

报告生成及重建的实体、历史事件读取分别由 `history.entity_batch_size` 和 `history.event_batch_size` 控制，部署时可独立调整。两项配置在本次会话内固定，改变批次不改变报告内容；默认值、适用范围、校验与生效规则见[读取批次配置](../camctl/historical-state-query.md#实体与事件读取批次分别配置)。

## 容量配置的表示

本地配置中按字节计量的容量使用带单位的 TOML 字符串，字段名表达用途，例如 `copy.segment_size` 和 `session.log_max_size`。配置加载时统一解析为整数个字节，处理流程使用解析结果。默认值由各字段所属专题定义；本节统一定义容量的书写与校验规则。

| 单位 | 对应字节数 |
| --- | --- |
| `B` | 1 |
| `KiB`、`MiB`、`GiB` | 分别为 1024、1024²、1024³ |
| `KB`、`MB`、`GB` | 分别为 1000、1000²、1000³ |

字符串由十进制数值和上表中的单位组成，单位区分大小写。数值使用 ASCII 数字，可有小数点，小数点前后均须有数字；数值与单位之间及字符串首尾允许零个或多个 ASCII 空格。例如 `"128 MiB"`、`"128MiB"` 和 `"1.5 GiB"` 均符合书写规则。数值不带正负号，不使用指数、分隔符或单位缩写别名。

按下表顺序校验。换算须保留十进制数值的精确含义，不使用二进制浮点近似、截断或四舍五入取得字节数。通过通用校验后，再按所属字段的范围校验；当前分段大小和日志轮换大小均要求大于 0。

| 输入条件 | 处理 |
| --- | --- |
| 字段省略 | 使用所属字段的默认值 |
| 显式值不是字符串，包括整数、浮点数和布尔值 | 配置错误 |
| 字符串不符合书写规则或单位不在上表中，例如 `"128"`、`"128 M"`、`"128 mib"`、`"-1 MiB"` | 配置错误 |
| 书写合法，但换算结果不是整数个字节，例如 `"0.1 B"` | 配置错误 |
| 换算结果为整数，但不满足所属字段的范围，例如当前两项配置使用 `"0 B"` | 配置错误 |
| 换算结果为整数且满足所属字段的范围 | 接受，使用精确的字节数；例如 `"1.5 KiB"` 为 1536 字节 |

容量语法仅适用于声明为字节容量的本地配置项。按条目、次数或页数计量的配置继续使用各自的整数规则；报告中的文件长度、可靠进度等机器字段继续按协议表示。验收须覆盖两类单位的倍率、空格、小数精确换算、全部错误分区，以及不同合法写法表示相同容量时取得相同生效值。

## 控制调用超时

第一版录像启动、录像停止和录像状态查询的单次调用等待上限，各自默认 **10 秒**，允许分别配置为有限的正秒数。0、负数及非有限数值属于本地配置错误。配置随所属动作在首次受理时固化，后续执行、重试、恢复及使用该停止配置的有限收场沿用原值；执行计划不能覆盖。

| 本地配置 | 适用调用 |
| --- | --- |
| `devices.<id>.recording.start_timeout_s` | 一次录像启动控制调用 |
| `devices.<id>.recording.stop_timeout_s` | 一次录像停止控制调用 |
| `devices.<id>.recording.query_timeout_s` | 一次录像状态查询，包含正在录像与正在录制文件路径的查询 |

从主机实际开始本次驱动调用时，使用当前会话的单调钟计时；当前 ADB 驱动从发起本次 `adb` 子进程调用开始覆盖启动和等待结果的过程。不把动作排队、设备准备、重试间隔或录像持续时间计入本次调用。开始读取输出不结束计时，日志或部分响应也不重置期限；取得完整调用结果后按驱动协议解释。该上限限制正常等待调用结果的时间，超时后的子进程清理与必要设备核实仍按各自有限处理规则执行，不承诺全部收场在同一上限内完成。

| 调用结果与已取得的证据 | 处理 |
| --- | --- |
| 在期限内完成，结果可以按驱动契约可靠解释 | 保存实际成功、明确失败或查询状态；程序正常退出不自动等于业务成功 |
| 在期限内完成，但结果无法可靠解释 | 保存响应异常与实际证据，不把无法解释的结果当作未执行或不存在 |
| 调用超时或通信异常，已有足以确认业务结果的可靠证据 | 保留该业务事实及调用异常，按实际设备状态处理；不抹去已取得的启动或停止确认，不盲目重复操作 |
| 调用超时或通信异常，没有足以确认业务结果的证据 | 保存结果未知，进入所属流程的有限核实或收场；查询失败不表示相机空闲或文件不存在 |

调用超时不证明远端程序已结束，也不撤销已经发生的设备操作。主机侧调用清理与再次发令的协调遵守驱动契约；只有已经满足安全重试条件、确认上次调用结束且还有执行资格时，才按[通信重试间隔](#通信重试间隔)安排下一次尝试。启动或停止的实际尝试按原预算计数，超时不退还已经消耗的次数。

例如启动调用等待 10 秒后超时，不意味着在第 13 秒必然重发。须先处理旧调用并核实是否已经启动；只有允许再次启动，才开始对应的重试等待。状态查询使用自己的调用上限，不因它由启动或停止流程触发，就改用触发操作的上限。

源文件内容读取遵守[文件读取的无数据超时](file-copy.md#文件读取的无数据超时)。本节的录像状态查询上限不套用到整片读取、源端整片摘要计算或主机媒体处理；这些操作按所属契约处理。

## 通信重试间隔

第一版对录像启动、录像停止和文件读取采用固定重试间隔，各自默认 **3 秒**，允许分别配置为有限、非负的秒数；0 表示满足重试资格后不额外等待。配置在所属动作首次受理时固化，后续重送、执行和恢复沿用原值，执行计划不能覆盖。

| 本地配置 | 适用操作 |
| --- | --- |
| `devices.<id>.recording.start_retry_interval_s` | 同一录像的再次启动尝试 |
| `devices.<id>.recording.stop_retry_interval_s` | 同一停止流程的再次停止尝试；适用于正常停止、取消、恢复及使用该停止配置的有限收场 |
| `devices.<id>.copy.retry_interval_s` | 同一文件读取失败后允许的再次读取，包含取回、异常原片检查及修复输入拷贝 |

第一次尝试按自身执行资格开始，不预先等待重试间隔。一次尝试结束后，在判定允许重试且确认上次调用已经结束时开始计时；文件读取须确认旧读取实际停止。当前会话使用单调钟计量等待，每次失败后的间隔保持为该操作的固化值。等待不消耗新的尝试次数，也不刷新次数上限或启动窗口。

以下条件按表中顺序判断，时间到达本身不授予重试资格：

| 当前条件 | 处理 |
| --- | --- |
| 已取得成功确认 | 结束相应尝试流程，不再安排重试 |
| 本次操作因取消而失去资格、预算耗尽、适用的启动窗口耗尽或存在其他禁止重试条件 | 按所属动作规则结束或收场，不为等待间隔延长执行资格；取消录像后必要的停止仍按停止流程判断资格 |
| 上次调用尚未结束，或结果未知且尚不能依据设备契约安全重试 | 先完成调用收场、对账或错误处理；不能仅因已经等待足够时间再次发令 |
| 允许重试、上次调用已结束，但间隔未到 | 保持等待，继续处理其他调度事件 |
| 间隔已到，但设备或其他可等待的执行条件尚未满足 | 继续等待相应条件，不发送命令 |
| 间隔已到且全部执行条件满足 | 使用原流程剩余预算开始下一次尝试 |

等待期间继续遵守[录像启动机会保留](camera-recording.md#等待重试时保留相机)和[文件拷贝机会保留](file-copy.md#等待重试时保留拷贝机会)。取消、窗口到期及必要停止等事件可及时处理，不能用阻塞整个调度器的等待实现间隔。文件已经读完、摘要不一致后申请整片重拷属于独立的重拷流程，按其预算和候选选择规则处理，不当作本节的读取通信失败。

例如启动失败并确认调用结束的时刻为 09:00:00，采用默认间隔时，最早在 09:00:03 再次启动；若启动窗口在 09:00:02 结束，则及时按过期规则处理，不能等到 09:00:03 再发令。停止与文件读取使用各自间隔，不套用录像启动窗口。

## 设备文件删除与查询的计时

正式产物清理对设备文件删除和存在性查询分别设置调用时限及重试间隔。字段由本节统一定义，次数遵守[删除与查询的独立尝试预算](output-cleanup.md#删除与查询的独立尝试预算)。

| 本地配置 | 默认值 | 含义 |
| --- | --- | --- |
| `devices.<id>.cleanup.delete_timeout_s` | 10 秒 | 一次设备文件删除调用的正常结果等待上限 |
| `devices.<id>.cleanup.query_timeout_s` | 10 秒 | 一次设备文件存在性查询的正常结果等待上限 |
| `devices.<id>.cleanup.delete_retry_interval_s` | 3 秒 | 确认允许再次删除后，重发删除调用前的等待间隔 |
| `devices.<id>.cleanup.query_retry_interval_s` | 3 秒 | 文件存在性查询失败后，再次查询前的等待间隔 |

四项可分别配置。调用时限必须为有限的正秒数，间隔必须为有限的非负秒数，间隔为 0 时不额外等待；布尔值不作为合法数值。配置在清理动作首次受理时固化，后续执行、请求重送和恢复沿用原值，执行计划不能覆盖。

从实际开始一次驱动调用起，使用本次会话的单调钟计量调用时限；当前 ADB 驱动包含子进程启动及等待完整结果的过程。排队、执行资格等待和重试间隔不占用本次调用时限，部分响应不刷新期限。时限只约束正常等待结果的阶段，不包含随后必要的调用收场，也不是整个清理动作的完成期限。

删除调用超时且没有可靠结果时保留删除结果未知，先跟踪实际调用结束并按驱动契约核实，不能据超时直接重发删除。查询失败或超时不表示文件不存在。已有可靠业务结果时保留该结果及实际调用错误，不因错误抹去成功证据。每次实际尝试继续占用对应次数，超时不退还额度。

以下各项都以状态记录可靠、动作仍有资格、对应预算有余及上次调用已实际结束为前提。条件未满足时，按清理资格、取消、预算或持久化规则处理，等待时间届满不授予执行资格。

| 需要执行的操作及原因 | 间隔处理 |
| --- | --- |
| 首次删除目标文件 | 不预先等待重试间隔 |
| 删除结果未知后开始本次核实，或中断恢复时首次核实目标文件 | 具备查询条件后即可查询，不额外等待删除或查询重试间隔 |
| 查询失败，仍需再次查询 | 从确认失败且原调用已结束、具备重试资格时开始等待查询重试间隔 |
| 可靠确认删除未完成，且允许再次删除 | 从确认可重试且原调用已结束时开始等待删除重试间隔；必要查询完成之前不提前计完这段等待 |
| 已取得可靠的删除完成或文件不存在证据 | 结束本文件处理，不等待或派发后续重试 |

重试间隔使用单调钟和异步等待，期间其他设备动作及取消处理继续推进。查询成功确认文件仍存在后，再次删除依然使用原删除计数；随后因新一次删除结果未知而发起的首次核实，不属于前一次查询失败的重试，但继续使用原查询预算。等待阶段跨运行恢复时，在本次重新具备相应重试资格后按原固化间隔计时，不跨进程比较单调钟读数，也不重置尝试次数。

本节仅约束设备文件调用。主机上 `staging/derived/` 成品的查询和删除继续由文件工作线程执行，异步等待实际完成或返回错误，遵守[本地文件操作的完成与故障边界](../camctl/file-runtime.md#本地文件操作的完成与故障边界)，不套用设备调用时限或增加强制中止线程的机制。

验收覆盖配置缺省及独立覆盖、非法值、受理固化及配置更新后恢复；用可控单调钟验证调用期限、部分响应不续期、首次核实不额外等待、查询失败后的等待及确认可再次删除后的等待。组合取消、预算耗尽、上次调用未结束、等待中断恢复及迟到结果，确认计时不绕过资格或刷新预算；主机本地文件调用保持既有完成规则。
