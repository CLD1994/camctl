# 清理正式产物

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

`delete_action_outputs` 删除客户端明确指定的正式产物文件，数据库中的身份和历史仍保留。本页说明哪些文件会被删除、怎样保护已经开始的取回，以及删除失败或取消后的处理。先读[正式产物模型](outputs.md#正式产物模型)。

**阅读提示：** 先确认要清理的是哪份正式源文件，再读与正在进行的取回如何协调。删除交付副本和删除正式产物是不同操作；联合验收见[产物专题](output-verification.md#验收要求)。

## 产物清理

正式产物的清理动作：

```text
delete_action_outputs
```

清理必须明确给出来源范围或精确产物集合，不以缺少全部选择条件表示删除全部。

### 清理参数

`delete_action_outputs.params` 是必填对象。支持以下选择方式，完整机器字段组合见[输入协议](plan-input.md#取回来源筛选与预览)：

| 选择方式 | 范围与约束 |
| --- | --- |
| `output_ids` | 非空、无重复的合法产物 ID 数组；仅删除所指定产物 |
| 指定动作 | 本计划动作名或指定动作实例，选择其全部正式产物 |
| 指定计划 | 显式选择当前计划或指定 `plan_instance_id`，选择计划内产物来源动作的全部正式产物 |

来源范围包括原文件、预览及修复成品，不使用取回的默认筛选或大小替代规则。按计划以产物来源为依据，不包含该计划仅取回的其他计划产物。精确 ID 模式不自动扩大到关联产物；空 ID 列表不表示全部。缺少选择、混用互斥方式、非法值及额外参数使清理动作受理失败，不建立删除意图。

当前计划及其动作引用在首次受理时解析；跨计划实例引用与精确 ID 在执行时核实实际存在性。可靠解析的来源成员固定保存，重试和恢复不扩大范围。来源不存在或动作类型不适合作为产物来源属于失败；查询失败或结果未知不能解释为不存在。

| 来源及产物状态 | 处理 |
| --- | --- |
| 所选来源拍摄或适用修复尚未结束 | 等待，不提前删除已有产物，不取消来源 |
| 全部来源结束，产物登记完整 | 固定完整清理集合，再按逐项删除与取回保护规则处理 |
| 来源失败或取消，但最终产物已确定 | 选择实际保留的全部正式产物 |
| 有效来源已结束，可靠确认没有正式产物 | 成功，报告无产物需要清理 |
| 目标 ID、计划或动作可靠确认不存在 | 失败，保留无效引用原因；精确 ID 列表按逐项结果处理 |
| 来源、集合或登记完成情况无法可靠确认 | 按实际错误与恢复规则处理，不保存空集合成功 |

等待对象仅为产物来源拍摄及其内部产物处理，不是计划全部动作。按计划清理不能等待自身或其他取回终态。集合选择、删除意图及读取保护的先后见[取回与清理衔接](preview-obtaining.md#取回与清理的衔接)。

精确选择示例：

```json
{"output_ids":["o-001","o-002"]}
```

### 清理含义

清理一个正式产物意味着：

- 删除该 `output_id` 对应的保留文件：设备产物删除所属设备上的文件，主机派生产物删除 `staging/derived/` 中的对应成品；
- 使该 `output_id` 后续不再可取回；
- 保留该产物曾经存在以及被清理的历史记录。

已经发布到 `ready/processing` 的合法 delivery 不因此被撤回。

### 再次清理已完成的产物

新的清理请求可以再次指定已有清理完成记录的 `output_id`。对已取得执行资格的清理项，数据库可靠确认该产物此前已经完整清理时，该项按成功处理，报告说明“此前已清理”，不再执行文件删除。产物继续保持不可取回。

| 数据库中的产物与清理记录 | 本次清理项的处理 |
| --- | --- |
| 产物存在，已确认清理完成 | 本项成功，说明此前已清理，不重复删除 |
| 产物存在，尚未开始清理、仍在清理或已明确部分失败 | 按清理资格、并发及失败恢复规则处理，不能直接按此前已清理成功结束 |
| 产物存在，删除结果尚未确定 | 按恢复规则核实，不能把删除意图或已发出删除操作当作完成记录 |
| 查询成功，但没有该 `output_id` 的产物记录 | 本项失败，报告“产物不存在”；其他目标按“批量清理结果”继续处理 |
| 数据库查询失败或无法可靠解释记录 | 按持久化错误处理，不能推断目标不存在或清理已完成 |

每个产物的清理完成记录对应其保留文件。取回权限已关闭、交付副本已删除或未经核实的路径缺失，都不能代替该产物的清理完成依据。一个清理动作包含多份产物时，各项完成情况分别保存，再汇总动作结果。已有删除意图但缺少完成记录时，按“删除中断后的恢复”核实并保存恢复结果，再据此判定完成。

新请求的成功结果按历史与投影规则保存，并关联本次请求和 `output_id`；它表示确认此前已清理，不新增虚构的物理删除事实。同一 `request_id` 重复提交仍复用首次受理的请求及原处理结果，不按新请求重新处理。清理自身的取消和既有终态仍遵守公共动作状态机。

### 批量清理结果

`delete_action_outputs` 对明确指定的各个 `output_id` 分别处理、保存并报告结果。格式合法的 ID 在执行时查不到产物，是该清理项的业务失败，不阻止其他目标清理。输入格式非法、没有有效选择条件或显式 ID 列表为空时，首次受理将该清理动作登记为 `failed`，不登记删除意图或执行列表中的任何删除；其他动作一同受理。受理失败状态及历史保留遵守公共动作参数校验规则。

例如请求清理 A、B，A 存在而 B 未登记：A 按清理规则执行，B 报告“产物不存在”；A 完成后，动作整体为 `failed`，报告分别保留 A 已清理、B 不存在的结果。已完成的删除不会因另一项失败而撤销。

对于目标列表非空、清理动作尚未进入终态且取消尚未生效的情况，整体结果按下表确定。取消已经生效时，按[清理取消](#清理取消)逐项收场，不用本表覆盖取消结果。

| 各项处理状态 | 清理动作的处理 |
| --- | --- |
| 仍有目标等待旧取回、正在删除、仍可重试或需要核实删除结果 | 继续按各项规则处理；其他项已失败也不能提前将动作置为终态 |
| 全部目标均已成功，包括确认此前已清理的项 | `succeeded` |
| 全部目标均已有最终结果，至少一项失败 | `failed`；报告逐项列出实际结果与失败原因 |

查询和结果保存须可靠完成。数据库读取失败、写入失败或提交结果未知按会话错误及恢复规则处理，不能伪装成某个 ID 不存在，再假定其余清理可以安全继续。删除意图、部分删除和结果未知分别保留；动作整体失败不恢复已受删除限制的产物。

逐项结果及整体终态按历史与投影规则持久化。中断后恢复原请求中尚未结束的条目，已经保存的最终结果保持不变，不因另一项失败重新删除成功项。取消和既有终态遵守公共动作状态机及本专题的清理取消规则，不由结果汇总覆盖。

### 不级联删除

原片与修复成品具有派生关系，但删除：

```text
原片
```

不会自动删除：

```text
修复成品
```

反之亦然。

只删除精确 ID 或已固定来源范围选中的正式产物。按计划或动作选中原文件、预览和修复成品，是来源选择的结果；精确 ID 删除不级联。

### 清理与取回并发

已有取回优先。

多个取回与清理已经到达计划时间、来源及产物选择条件均满足时，先按[逐产物资格授予规则](outputs.md#延后执行时的取回与清理顺序)确定先后，再进入清理流程。此前已经等待来源结束的动作同样参与排序，不能由各协程唤醒或保存选择的先后决定谁先登记删除限制。已授予的资格与有效限制继续生效。

清理开始时：

1. 持久化删除意图；
2. 禁止新的取回请求获取该产物；
3. 逐个 `output_id` 等待所有已获得资格的旧取回不再需要读取其保留文件；
4. 再进行物理删除。

逐清理请求的限制由 `cleanup_items` 保存，包含本项限制状态及建立、解除依据，具体见[逐请求的删除限制](../camctl/database-schema.md#逐请求的删除限制)。同一产物的多个清理项分别维护限制；产物是否允许新的取回，结合全部有效限制及实际文件事实判断。限制与相关历史和投影在同一事务中保存，物理删除尝试按公共操作记录另行保存。

清理开始以后新来的 obtain 请求不能插队。

#### 新取回遇到删除限制

取回到达自身计划时间、确定产物后，在申请该产物的读取资格时按下表判断。取消及既有终态优先；受理请求本身不提前授予资格，也不提前作出本表中的运行时失败判定。

| 本次取回的逐项事实 | 处理 |
| --- | --- |
| 该项已经最终失败或取消 | 保留原结果，不重新申请资格 |
| 已持有该产物的旧取回资格 | 按原资格继续或恢复；后来登记的删除限制不撤销该资格 |
| 尚无资格，产物存在有效删除限制 | 立即将该项记为最终失败，原因表达“产物已进入清理流程”；不拷贝，不等待删除完成或取消 |
| 尚无资格，可靠确认没有有效删除限制 | 继续按执行顺序及产物实际可用性判断，不能仅据此推断文件可读或已取得资格 |
| 资格或删除限制无法可靠确认 | 按持久化错误及恢复规则处理，不能推测可取回，也不能冒充已确认的清理限制失败 |

删除限制的判断与对应资格授予或失败结果在同一数据库事务中保存，历史和投影同步更新。与清理取消同时发生时，以事务确定的先后为准：限制解除在先则按解除后的状态判断；失败已保存则不因随后解除限制而改写结果。提交失败或结果未知须先按事务恢复规则核实。

该失败只针对本次取回中的对应产物，其他产物继续处理，整体结果仍按[部分成功](obtaining-outputs.md#部分成功)和开始发布的条件汇总。只有一个目标时，本次取回随该项失败而整体失败；包含其他未完成来源或产物时，不提前结束整个动作。

清理后来被取消、源文件仍存在或主机重启，都不恢复已经失败的取回项。同一 `request_id` 重送沿用原结果；客户端须用新请求表达再次取回的意图，新请求仍按执行时的资格与产物状态处理。

#### 逐产物解除读取依赖

原片与修复成品分别判断，每个取回也分别持有自己的交付副本。对同一 `output_id`，依次检查下表；清理自身仍须有执行资格，并满足删除意图、目标记录及重试规则：

| 所有已有取回对该产物的依赖情况 | 物理删除处理 |
| --- | --- |
| 依赖记录或准备结果无法可靠确认 | 先核实或按对应错误处理，不授权删除 |
| 至少一个取回仍需读取，包括尚未拷贝、拷贝中、未完成校验或仍可重试 | 等待；其他取回已经准备完成不能代替该请求完成 |
| 每个取回均已确认不再需要读取，或可靠确认没有已有取回 | 可以删除该产物的保留文件，不等待其他产物、整组发布或主程序传输 |

一个取回对该产物不再需要读取，有以下依据之一：独立交付副本已按下节可靠准备完成；交付已按协议确认发布；该项最终失败或被取消，且其读取和重试已确认停止。仅整次取回收到取消标记，不等于正在执行的读取已停止。

副本准备完成后，即使来源已被显式清理，原取回仍使用已有交付副本继续等待和发布，不能以源产物当前不可用否定这份已准备的交付。取消或清理某个取回的中间文件，不影响其他取回的副本；源产物清理也不删除这些独立副本。

#### 准备完成与断电恢复

交付副本须完成全部写入、符合所属文件读取与校验契约，并完成文件及相关目录项的落盘。随后在同一数据库事务中保存该副本的身份、位置、大小、摘要和准备完成事实，并解除这次取回对该产物的读取依赖；历史与投影同时更新。该规则同样适用于从相机取回原片和从 `staging/derived/` 拷贝成品。文件名存在、长度相同或拷贝命令返回成功均不能单独作为准备完成依据。

| 准备步骤及持久化结果 | 恢复与删除处理 |
| --- | --- |
| 文件写入、校验或落盘未完成、失败或未知 | 保留读取依赖，按原处理进度恢复或记录失败，不因准备意图允许删除 |
| 文件已可靠准备，准备完成事务尚未提交或确认回滚 | 保留读取依赖；恢复核实原副本并保存完成事实，不直接放行删除 |
| 准备完成事务提交成功 | 本取回不再阻止删除；重启后使用同一副本、原选择和交付身份继续处理 |
| 事务提交结果未知或记录不可读 | 先核实实际提交结果，不猜测准备完成、重新拷贝或授权删除 |

清理在物理删除前须依据可靠保存的逐请求依赖确认可执行；删除意图阻止新取回取得资格，准备完成与依赖解除整体提交，不能出现依赖已解除但准备事实未保存的状态。已解除依赖后，不再要求源文件存在来恢复本次交付，也不能把已准备副本当作可重新生成的临时文件删除。若副本缺失、损坏或状态未知，保留实际故障并按错误处理，不能撤销历史删除或假定源文件仍可读取。发布期间的文件位置与记录对账继续遵守文件交接协议。

### 删除与查询的独立尝试预算

正式产物清理分别计量文件删除调用和文件存在性查询。每个清理动作中，每份目标文件独立保存两组次数及其上限；每份产物对应一份目标文件，不同清理项不共用额度。本节适用于设备原文件和主机派生成品，不用于内部中间文件或日志副本的清理。

| 本地配置 | 默认值 | 含义 |
| --- | --- | --- |
| `cleanup.max_delete_attempts` | 3 | 每份目标文件的删除尝试上限，包含首次调用 |
| `cleanup.max_query_attempts` | 3 | 每份目标文件在本次清理责任中的存在性查询上限，包含首次查询 |

两项均为大于等于 1 的整数，布尔值不是合法次数；执行计划不能覆盖。清理动作首次受理时固化所采用的上限，确定目标文件后将文件计数关联到原清理动作及其固化配置。配置更新、请求重送或跨 `run` 恢复均不补满预算。

数据库中的产物记录查询、资格检查及读取已保存的清理结果，不消耗文件存在性查询额度。向设备或主机文件系统实际查询目标文件是否存在时才使用该额度；正常执行与中断恢复共用原计数。适配器不能在框架不可见的重试循环中重复发出删除或存在性查询，绕过这两组上限。

每次删除或存在性查询派发前，在同一事务中可靠保存本次尝试身份、操作意图及相应额度占用，成功提交后才调用协作者。失败、超时及结果未知都不退还已占用额度，重启也不清零；占用与派发之间中断时保留已占用事实，恢复先核实结果，不把原意图当作一次可以无限重复派发的调用。等待资格或重试间隔不消耗额度，结果明确成功也不重置此前计数。文件查询额度不因再次删除而重新分配。

先检查动作取消、既有终态、数据库及目标记录是否可靠，以及上次调用是否实际结束。取消和已有终态按各自规则处理；数据库或记录异常按持久化错误处理；上次调用尚未结束时继续跟踪结果，不并发派发下一次调用。在仍有执行资格、记录可靠且没有未结束调用的前提下，按下表处理：

| 目标文件的可靠事实 | 对应预算 | 处理 |
| --- | --- | --- |
| 删除接口已可靠确认文件删除完成，或查询可靠确认文件不存在 | 任意剩余额度 | 保存完成事实，不额外查询或再次删除 |
| 尚未开始删除，或者确认目标仍存在、先前调用未完成删除 | 删除额度尚有剩余 | 满足取回保护等删除条件后，占用一次删除额度并调用删除 |
| 尚未开始删除，或者确认目标仍存在、先前调用未完成删除 | 删除额度已耗尽 | 本文件清理失败，保留尚未删除的事实，不再派发删除 |
| 已发出的删除结果未知，或恢复时需要核实实际文件状态 | 查询额度尚有剩余，无论删除额度是否耗尽 | 占用一次查询额度，核实该目标是否存在；查询失败继续保留未知 |
| 已发出的删除结果未知，或恢复时需要核实实际文件状态 | 查询额度已耗尽，无论删除额度是否尚有剩余 | 本文件清理失败，保留是否已删除未知的原因，不以重发删除代替查询 |

一份文件已可靠取得结果后，不因另一清理项失败而重复处理；逐产物结果及动作整体结果按批量清理规则汇总。明确失败但不能证明文件仍存在或删除未发生时，应进入结果未知的核实分区。删除尝试已用尽仍可使用剩余查询额度确认最后一次删除的结果；查询额度已用尽也不否定已经可靠取得的删除成功事实。

例如，一次删除结果未知，随后一次查询失败、第二次查询确认文件仍存在，此时已使用删除 1 次、查询 2 次。下一次删除消耗第二次删除额度，不刷新查询次数；其结果若仍未知，仅能使用剩下的第三次查询。所有恢复继续沿用这些计数。

额度耗尽导致的最终失败保留未删除及结果未知的具体文件范围；后续运行不自动恢复已经失败的清理项，继续清理需要新的有效请求。同一请求重送复用原结果。新请求遇到可靠的既有清理完成记录时直接确认成功，不为获得新预算重复删除。

验收组合删除额度有余或耗尽、查询额度有余或耗尽，以及已删除、仍存在和结果未知三类事实；覆盖每份文件独立计数、查询成功同样计数、查询不消耗删除额度、再次删除不刷新查询额度。分别在额度占用、调用及结果保存前后中断，验证跨重启不补满、未知不重发删除、已成功文件不重复操作；同时验证取消、配置更新、同一请求重送及新的有效请求。单次设备调用时限及重试间隔遵守[设备文件删除与查询的计时](configuration.md#设备文件删除与查询的计时)，不以有限次数替代调用完成规则。

### 删除中断后的恢复

物理删除前，数据库必须已可靠保存清理请求、删除意图、完整目标产物集合，以及每个 `output_id` 对应文件的所属设备或主机存储位置和识别依据。恢复以这些记录为依据，不根据临时列举出的剩余文件缩小原清理范围；合法 delivery 不属于源产物清理目标。

后续实际启动的 `run` 发现删除意图仍未取得最终结果时，核实各目标文件。必须区分“确认不存在”“确认仍存在”和“结果未知”；相机连接失败、目标设备或存储无法确认、查询失败及响应无法解释均属于未知，不能当作文件不存在。

先核实原请求的恢复资格和记录，按下表自上而下选择适用分区，再逐文件处理：

| 原请求与记录情况 | 恢复处理 |
| --- | --- |
| 已有可靠保存的清理完成记录 | 使用已保存结果，不重复删除 |
| 取消已经生效，包括清理动作尚在取消收场、未进入终态的情况 | 恢复逐项取消收场及结果保存，不再发出或重试删除；保留已发生的删除及未知事实，按[清理取消](#清理取消)判断各产物的取回限制 |
| 请求仍未结束、取消尚未生效，删除意图及完整目标记录可靠可读 | 按下表核实；实际删除仍须满足旧取回优先和剩余重试预算 |
| 请求或条目已失败或取消，且没有清理完成记录 | 不自动恢复物理删除，不改写原终态；保留已发生的删除及未知事实，继续清理须有新的有效请求 |
| 请求资格、删除意图或完整目标记录缺失、不可读或无法可靠判断 | 保留诊断并停止依赖这些记录的恢复，不能补造删除授权或以空集合判成功 |

对于仍有恢复资格的请求，各目标文件的处理如下：

| 文件核实结果 | 本文件的处理 |
| --- | --- |
| 确认不存在 | 保存恢复时确认不存在的事实，不重复删除该文件 |
| 确认仍存在且属于原清理目标 | 在具备删除资格及剩余删除额度时继续删除；删除额度耗尽则按本文件清理失败保存 |
| 结果未知 | 保存未知原因，有剩余查询额度时继续核实；额度耗尽则按本文件清理失败保存，不能记录为删除成功 |

某份产物的目标文件已确认不存在时，补记该产物清理完成和本次清理项成功；目标仍存在或结果未知时，该项不能宣告清理成功。各清理项分别取得结果，再按批量清理规则汇总动作状态：某项未知不抹去其他项已确认的状态，继续删除已确认存在的文件仍须满足上述资格。重试耗尽按清理失败处理，保留未删除及未知的具体范围，不因重启重置预算。

恢复记录表达“恢复时确认目标已不存在”，不推测断电前的准确删除时间。恢复观察、清理完成和相应投影遵守数据库事务规则；保存失败或提交结果未知时按持久化错误处理，先确认实际提交情况再继续。已确认删除或无法排除删除发生的产物，继续受清理限制，不因查询失败恢复取回权限。

### 清理部分失败

已经发出可能删除文件的操作，但最终仍有应删除文件未删除或结果未知时：

- 不允许新的取回；
- 不重新开放尚存的产物文件；
- 如实报告物理清理未完成；
- 以后只能通过新的清理请求继续清理。

### 清理取消

取消以清理动作作为目标，camctl 按每个 `output_id` 的实际进度分别处理。取消表示停止尚未发生的删除；已经完成的删除及其历史记录保持有效。某个产物已经开始删除，不阻止取消其他尚未开始删除的产物。

例如，一个清理动作选择 A、B、C：A 已删除，B 正在等待旧取回结束读取，C 尚未开始删除。取消生效后，camctl 保留 A 已删除的结果，取消 B、C 的删除；B、C 没有其他有效删除限制时，允许新的取回按实际可用性申请资格。

#### 取消生效与逐项收场

camctl 先可靠保存取消事实，再停止该清理动作新增的删除和普通重试。取消与删除派发必须协调：取消先于某次删除派发生效时，该次删除不再发出；已经发出的调用则跟踪其实际结果。等待工作线程的协程被取消，不证明文件删除已经停止。状态或取消事实无法可靠读取、保存时，按持久化错误处理，不猜测取消已生效或删除尚未发生。

清理动作已经进入终态时保持原终态和逐项结果。尚未进入终态时，按下表逐项处理；每个 `output_id` 根据自身保留文件的实际删除结果判断。

| 本清理项的实际情况 | 取消后的处理与逐项结果 |
| --- | --- |
| 已经保存成功、失败或取消的最终结果 | 保留原结果及已知文件事实，不改写为本次取消产生的结果 |
| 尚未取得最终结果，可靠确认该项没有发出任何可能删除文件的操作 | 撤回尚未执行的任务，确认它们不会再执行后，将该项记为 `canceled`；等待旧取回的条目无需继续等待读取完成 |
| 删除调用已经发出，尚未返回 | 跟踪当前调用，不再发出后续删除或普通重试；本项的最终结果等待实际调用结果，其他尚未开始删除的项可以先完成取消 |
| 当前调用已结束，取得该产物目标文件已删除的可靠证据 | 保存清理完成事实，本项为 `succeeded`；该事实不将整个清理动作改为成功 |
| 当前调用已结束，但删除失败或结果仍未知 | 结束本项后续删除，本项为 `canceled`；保留文件确认尚存或删除结果未知的实际事实，附错误或未知原因，不宣称清理成功 |

如果清理动作尚在等待来源结束，产物集合尚未固定，取消后结束等待，不再扩大或固定清理集合，也不为尚未选中的产物编造清理项。已有条目仍按上表处理。

#### 取消后的取回限制

是否允许新的取回，按每个产物分别判断。取消只解除本次请求在允许解除阶段建立的删除限制，不撤销其他请求的限制或已发生的删除事实。

| 产物及相关删除限制的实际情况 | 新取回的处理 |
| --- | --- |
| 该产物的保留文件已确认清理完成 | 保持已清理、不可取回 |
| 尚未确认完整清理，但该产物有已发出的删除调用、已发生的删除，或无法排除删除已经发生 | 保持取回限制，不因本次取消而重新开放尚存文件 |
| 本次请求尚未发出该产物的删除操作，但其他请求仍有有效删除限制 | 解除本次请求可撤销的限制，保留其他请求的限制 |
| 本次请求尚未发出该产物的删除操作，且可靠确认没有其他有效删除限制或可能发生过删除的事实 | 解除本次请求的限制，恢复新取回申请资格；文件是否可读取仍按实际可用性判断 |
| 删除阶段或相关限制无法可靠确认 | 保留未知，按对应错误规则处理，不猜测可以恢复取回 |

取消前已经因删除限制失败的取回项保持失败，按[新取回遇到删除限制](#新取回遇到删除限制)处理。解除限制只影响后续资格判断，不恢复旧取回。

#### 动作结果、报告与重启恢复

取消生效时尚未终态的清理动作，完成适用的取消收场后以 `canceled` 结束。逐项结果保留已完成的成功和失败，尚未完成的删除按前述规则取消；不能为了让所有条目与动作终态相同而改写已删除的事实。即使已经发出的最后一次删除最终成功，也不撤销已生效的动作取消。

报告按[清理结果格式](report-format.md#清理)表达动作终态和逐项结果。前述 A、B、C 场景中，清理动作为 `canceled`，A 为 `succeeded` 且 `outcome: deleted`，B、C 为 `canceled`。产物本身是否仍可取回，按其文件事实和全部有效删除限制表达，不由该清理动作的终态直接推断。

发起取消的 `cancel_task` 继续遵守[取消动作的完成时机](task-cancellation.md#取消动作的完成时机)：实际调用尚未结束或必要结果尚未可靠保存时，不能仅凭取消标记宣称取消处理完成。已完成的删除本身不表示取消处理失败；实际收场中的失败或未知仍按取消动作的汇总规则处理。

取消事实、逐项结果和适用的限制解除遵守历史与投影的事务规则。重启后恢复已经生效的取消及未完成收场，不再发出或重试被取消请求的删除。已经完成的项保持原结果；无法确认删除是否发生的产物保持限制。以后继续清理须由新的有效请求授权，同一请求重送不重新开始删除。
