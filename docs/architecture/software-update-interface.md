# camctl 更新能力与主程序接入

camctl 负责自身的离线软件更新、数据库迁移、失败回滚和中断恢复。更新实现及其构建资源属于 `apps/camctl`，由 camctl wheel 交付。部署工具负责构建交付物并调用组件的安装入口。

## 更新交付与独立入口

Python 专用更新包以 `camctl-update.zip` 交付，只包含 camctl wheel、锁定依赖、适用目标架构的离线 wheel，以及版本、来源和完整摘要信息。它不携带主程序或客户端。主程序接口直接接收该 ZIP 的绝对路径，组件负责校验和准备包内容；也可接收已经解压的包目录。组件更新器校验完整文件集合、摘要、平台与版本后才开始本次更新；不联网安装依赖。

wheel 内提供仅依赖标准库的维护引擎。部署时，camctl 的发布逻辑在原虚拟环境外建立稳定维护入口，绑定安装根目录和基础 CPython 3.11。主程序通过显式 `updater_path` 定位该入口，不从任意 `camctl_path` 猜测安装根目录或基础解释器。普通 camctl 命令和维护入口使用一致的配置来源；显式配置仍由 `--config` 传递。

新部署在安装 wheel 后准备维护入口。已有部署首次接入时，从新 wheel 的维护资源准备入口，再开始原环境更新；不能通过先替换原 wheel 来取得更新能力。资源和绑定信息先可靠保存，最后发布可执行入口。普通 wheel 安装不等于已经准备了某个部署的维护入口。

稳定入口先处理未完成更新，再解释新的更新包。每个事务在修改前可靠冻结自己的维护引擎及摘要；恢复只运行该事务的引擎。修改原虚拟环境、恢复旧软件或接收后续更新包，都不能改变仍在执行的引擎。引导路由契约稳定，普通软件更新不改写稳定入口；需要改变引导契约时单独维护其发布与恢复能力。

引擎、摘要与定位材料可靠保存后，才发布任何依赖它的路由记录，包括准备阶段记录。此前中断只留下尚未修改原环境的准备材料。已有未完成记录的引擎无法核实时保留责任并拒绝，不能以本次新包的引擎替代旧事务引擎。

稳定入口保存其部署身份和普通执行入口绑定，维护调用传入预期的 `camctl_path` 及实际配置来源。组件在普通启动和写入更新前核对两者一致；部署 A 的普通入口不能使用部署 B 的维护资格或更新结果。配置来源保持显式路径与默认来源的区别，host 不解析 TOML，也不从可执行文件路径猜安装目录。

配置加载沿用普通命令的完整语义，包括配置文件缺失时使用默认值。事务保存来源模式、有效路径、文件存在事实及存在时的摘要；原来不存在的文件保持不存在，不生成替代配置。权限或读取错误不能解释为缺失。未完成事务始终使用冻结的旧来源恢复，当前请求的来源只用于后续新任务；稳定入口不永久锁定某个历史配置文件。

原虚拟环境路径、V9 数据库维护起点、备份、文件归属、残留写入者、可靠完成点和错误诊断遵守[组件版本与软件更新](versioning-and-updates.md)。恢复过程中不能依赖原虚拟环境仍可导入。

## 主程序接口

`camctl_host.h` 提供阻塞式更新接口。接口接收显式配置、维护请求和调用方持有的结果对象，不依赖模块已经初始化。请求表达应用指定更新包或只恢复未完成事务；适用时指定客户端能力同步目标。接口只控制本模块拥有的普通业务进程，不声称其他独立 host 或 CLI 已停止。

`camctl_host_update` 返回 `0` 表示取得可信的维护结果，调用方仍须检查结果中的请求结论、部署效果和启动资格；它不等同于新版本已经提交。返回 `-1` 时保留实际本地错误、未知结果和可取得的原始输出。返回后均不自动恢复业务。

| 模块状态或输入 | 更新接口行为 |
| --- | --- |
| 基本参数非法，或工作线程、回调线程调用会等待自身的维护 | 拒绝本次调用，不进入更新；交付实际参数错误或死锁错误。 |
| 同一进程已有更新调用 | 拒绝第二个维护请求，不自动排队或重试整次更新。 |
| 尚未初始化 | 使用传入的维护配置执行，不先启动普通 camctl。 |
| 正在运行或停止中 | 核对与当前实例的维护配置一致，停止接纳新工作，沿现有停止流程等待提交、领取、进程组、输出、回调、诊断及在途调用收场，然后维护。 |
| 已经停止 | 直接维护，不重新初始化。 |
| 更新成功、原环境未修改或回滚已核实 | 返回实际结果，保持停止，由主程序重启。 |
| 收场失败、仍有恢复责任或结果未知 | 保持停止和诊断责任，不启动普通业务。 |

初始化、停止、显式重启与更新在同一进程协调。更新不能把自己计入普通在途调用后再等待该计数归零；其他线程的停止不能提前报告更新写入者已经结束。接受维护后不自动重建工作线程，也不自动重试整次软件更新。

配置了 `updater_path` 时，`camctl_host_init` 在启动任何原虚拟环境进程前，通过稳定入口检查启动资格。检查不安装、迁移或恢复业务对象；对已可见终态，须在持锁状态下同步记录及父目录确认可靠完成，不能仅凭读到 `committed` 放行。存在未完成更新、原写入者仍占用资格、同步失败或结果不能核实时，拒绝启动；主程序可以先调用维护接口完成恢复。该检查不通过执行原 `venv/bin/camctl --version` 探测。

### 同进程显式重新启动

主程序在维护返回后调用 `camctl_host_restart(void)`，在同一 C 进程建立新的普通运行周期。接口复用原实例保存的完整配置和已注册回调，重新建立线程、输出、日志及诊断资源，并重新检查维护资格和子进程回收前提。返回 `0` 只表示本地资源建立和首次普通 `run` 已安排，与初始化的成功含义一致。下表先拒绝模块线程，再检查维护、停止或候选资源责任，最后判断普通实例状态。

| 实际状态 | 重启结果 |
| --- | --- |
| 模块工作线程或回调线程调用 | 返回 `-1`、`EDEADLK`。 |
| 正在停止、仍有停止调用未退出、维护中、已有重启正在构造或候选资源尚未确认收场 | 返回 `-1`、`EBUSY`，不替换实例；候选资源由 `stop` 继续收场。 |
| 从未成功初始化普通实例且没有上述责任 | 返回 `-1`、`ENODEV`；先通过普通初始化提供配置。 |
| 普通实例正在运行且没有上述责任 | 返回 `-1`、`EALREADY`，保留当前实例。 |
| 原实例可靠停止，资格核对和新资源建立成功 | 原子发布新运行实例，返回 `0`；旧实例的观察者退出后才能释放其内存。 |
| 资格被阻止、未知，或新资源建立失败且新资源已经确认收场 | 返回实际错误，保留原停止实例、配置和回调，允许修正后重试。 |
| 新一代准备失败，其已创建资源尚不能确认收场 | 保留实际管理与诊断责任，阻止再次重启或维护写入，不能仅恢复旧指针就认定已停止。 |

重启不重送原首次计划，不恢复已经以取消返回的内存提交；camctl 从数据库恢复已保存的业务。新运行周期的有限重试预算、队列和进程管理状态按初始化重新建立。原回调仍有效，主程序无需重新注册。普通 `stop` 后直接调用 `init` 仍返回 `EALREADY`，重新启动只由显式接口触发。所有停止等待者及在途调用须退出，才能更换或释放其引用的实例；不能通过暂时清空全局实例来绕过这一责任。

候选收场先停止并确认已创建的线程结束，再释放其依赖的同步对象、描述符和内存。线程尚未确认结束时保留候选及实际管理责任；同步对象销毁或描述符关闭的错误独立交付诊断，其他必要收场继续推进。没有创建线程或已确认使用者结束的资源，按这些实际事实清理。初始化与显式重启共用资源创建及收场边界。

## 机器结果与诊断

维护的参数、stdout 及退出状态组合由根 `protocol` 的软件更新协议统一定义；C 与 Python 从同一来源读取或生成。更新结果独立于 `run`、`submit` 的业务会话结果和有限重试。

机器结果分别表达本次请求结果与实际启动资格。资格区分已允许、已阻止和未知，未检查不能当作已允许。已阻止时交付未完成恢复、资格仍被占用等实际原因；占用不代表已经需要回滚。允许启动只表示更新责任不再阻止启动，不代表普通业务初始化或设备检查已经成功。正常退出也不能覆盖非法或矛盾的机器结果。

| 可观察结果 | 调用方可认定的事实 |
| --- | --- |
| 请求未开始执行 | 仅本次维护未开始，不能据此断言不存在上次遗留责任。 |
| 新版本可靠提交 | 本次应用成功。 |
| 原部署确认未修改 | 没有开始修改本次部署。 |
| 原环境已核实恢复 | 目标更新未完成，原部署可供后续重启。 |
| 仍需恢复 | 存在未完成责任，继续保持停机。 |
| 结果缺失、非法、信号退出或相互矛盾 | 结果未知，不解释为已经回滚。 |

| 请求与实际事实 | 本次请求结果与启动资格 |
| --- | --- |
| 应用包完成并可靠提交 | 应用成功，资格已允许，模块仍停机。 |
| 当前应用失败，但原环境已核实恢复 | 应用失败且已回滚；核实完成后资格已允许，模块仍停机。 |
| 恢复旧事务后，本次新包校验失败 | 本次应用失败；独立报告旧恢复已经完成，不能把它改写成新的更新成功。资格按恢复后的确认事实交付。 |
| 只恢复，原本没有未完成记录 | 恢复请求完成且没有修改；核实无写入者及旧责任后资格已允许。 |
| 只恢复，旧环境恢复且终态可靠保存 | 恢复请求成功，资格已允许，模块仍停机。 |
| 启动检查没有未完成责任，绑定与终态确认通过 | 检查成功、未修改业务对象，资格已允许。 |
| 仍有未完成事务或写入者占用 | 请求没有完成维护，资格已阻止，并交付恢复责任或占用事实；不启动。 |
| 入口未准备、绑定不符、未执行检查或通道错误 | 请求失败或未开始，资格未知；不能据此启动。 |

路由旧引擎恢复、再运行新引擎应用时，路由方私下接收两阶段结果并汇总，公共 stdout 仍只有一份结果。C 只在机器结果、退出状态、进程与输出收场均符合协议时消费确定结论；stdout 缺失、截断、多份、非法或与退出状态矛盾时保留未知。仅 stderr 截断不撤销有效机器结果，但须交付截断事实。

未初始化或已经停止的维护调用，也须具备自身的进程组、退出记录、输出和取消保护。维护启动前复用已有 `SIGCHLD` 与 `SA_NOCLDWAIT` 前提检查，不假定原初始化资源仍存在，也不修改主程序的全局信号处置。

stdout 只输出一份机器结果，诊断交给 stderr 和更新日志。结果保留收据或诊断路径以及实际阶段；完整异常、原始工具输出与收场错误仍由 camctl 维护流程保存。C 的有界捕获保留截断事实，不能替代完整更新日志。必要收场不等待诊断通道，诊断失败不能撤销可靠完成结果。
