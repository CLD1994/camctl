# 文件交接

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本专题定义 camctl 与主程序通过目录交接文件的共同协议。普通产物的业务身份见[正式产物与取回清理](outputs.md)，状态报告的替换与补投策略见[状态报告与累计确认](status-reports.md)。

主程序搬运和传输文件时保留完整文件名与原始内容。状态报告的文件名包含内容摘要，由客户端按[文件名与完整性校验](status-reports.md#文件名与完整性校验)核验；主程序只负责中转，无须理解报告内容或执行摘要校验。

文件交接引起的状态变化按所属对象处理：普通产物交付属于业务状态，状态报告自身的文件管理属于内部状态，具体序列及报告责任见[状态报告自身的管理](status-reports.md#状态报告自身的管理)。

**阅读提示：** 先看三个目录分别由谁处理，再看完整文件怎样发布。目录移动、数据库记录与断电恢复的细则在后半部分；实际传输是否重试由第三方主程序决定。

## 文件交接状态机

文件所在的目录表示当前由谁处理，以及下一步允许做什么。这种按状态规定操作和转换的规则称为状态机：

```text
staging/
  derived/
  logs/
ready/
processing/
```

### staging

`staging` 是主机上唯一完全由 camctl 掌控的文件处理目录。相机等已接入设备使用各自存储空间保存设备正式产物；需要在主机进行的产物拷贝、加工和交付准备均在 `staging` 中完成，包括异常录像修复的输入文件、处理过程文件和目标录像。

文件还在准备时，camctl 可以进行以下工作：

- 生成文件；
- 拉取文件；
- 拷贝文件；
- 计算最终内容。

主程序不读取这里的文件。

文件必须完整准备后才能发布。

`staging` 中的文件由所属录像处理、取回或报告流程管理，按其业务条件准备和发布。`ready` 和 `processing` 继续遵守下文约定的交接权限。

`staging/derived/`（派生产物目录）保存由设备产物加工形成、可重复交付的成品，例如异常录像的修复成品。其正式产物身份及保留规则见[主机派生产物](outputs.md#主机派生产物)。修复输入、未完成的处理文件和每次取回的交付文件使用 `staging` 中该子目录以外的工作位置。

`staging/logs/` 保存从当前普通日志文件原样复制的日志副本，触发、重复抑制及失败规则见[日志副本交付](log-delivery.md#日志副本交付)。camctl 确认本次报告错误已经写入普通日志，并协调多进程追加和轮换，保证副本包含该错误。副本完整写入、同步并关闭后，camctl 才将副本原子移动到 `ready`。原日志继续留在配置路径供各进程追加和轮换。该流程不依赖状态库可用，也不登记为普通产物、delivery 或状态报告。

该目录还保存[跨 `run` 的故障标记文件](log-failure-marker.md#跨-run-的独立状态文件)：文件存在表示本次故障持续，内容记录故障轮次及日志副本处理进度，报告本地处理可靠恢复成功后删除。故障标记文件由 camctl 留在本地维护，不移入 `ready`，不随日志副本一起传输，也不由普通日志轮换清理。标记保存留下的临时文件按[所属清理规则](log-failure-marker.md#故障标记的临时文件)处理，不作为正式标记或日志副本。

如果 camctl 准备日志副本或将日志副本移入 `ready` 时遇到错误，camctl 按[日志副本的失败清理](log-delivery.md#日志副本的失败清理)处理：确认相关操作已经结束且句柄已经关闭后，删除仍留在 `staging/logs` 中、归属明确的本次日志副本，保留故障标记文件。对于已经移入 `ready` 或被主程序领取到 `processing` 的日志副本，camctl 保持原状。camctl 不自动重试或补投本次日志副本；业务状态报告的恢复与补投仍按报告规则处理。

每次 `run` 取得会话锁后，camctl 按[启动清理规则](log-delivery.md#run-启动时清理遗留日志副本)检查一次旧日志副本。camctl 只尝试删除仍在 `staging/logs` 中、归属明确且已无人继续操作的旧日志副本；本次日志副本、故障标记文件及其他用途的文件均保留。检查或删除失败时，camctl 记录错误，留待后续 `run` 再检查，不增加定时清理，也不让设备动作等待清理成功。

发布派生产物时，在工作位置准备本次取回的独立交付文件，再将该交付文件原子移动到 `ready`；保留在 `derived` 中的成品不随交付移动。目录中的文件是否已经登记为正式产物，以数据库记录为准，不能仅凭所在目录判定。

重启后残留的状态报告文件按[staging 中报告的恢复](report-publication.md#staging-中报告的恢复)处理，需要发布时从数据库保存的生成依据完整重新生成。

相机视频拷贝保留可用于[断点续传](file-copy.md#相机视频的断点续传)的部分文件，其恢复按所属拷贝流程处理。报告重新生成的规则只适用于状态报告文件。

取回项最终失败或取消后，符合条件的半成品由 camctl 自动清理；取回取消后，仍在本次 `staging` 工作位置的完整交付副本也自动清理。清理须先保存取消或失败事实，确认归属及相关读写、校验、移动和重试已经结束。未结束项的续传文件及仍有效、待发布的完整副本继续保留；失败后的有限尝试及后续正常 `run` 处理共用[中间文件清理规则](obtaining-outputs.md#取回中间文件的保留与清理)。

### ready

CLI 已完成本地发布。

等待主程序在合适的传输窗口领取。

普通产物发布到 `ready` 后：

> 本次取回的本地交付责任已经完成。

### processing

主程序在发起一次数据传输前，将 `ready` 中的全部待传输文件逐个移动到 `processing`：

```text
ready → processing
```

从此由主程序接管。

该移动是普通产物的不可撤回边界。

采用本项目的[C 接入模块](../host-demo/design.md#同步领取文件)时，主程序在准备传输的时机显式调用同步领取入口，由模块完成本次逐文件移动。调用范围、同名原子替换及失败后的继续条件由模块规格定义；领取后的传输和文件处理仍由主程序承担。

主程序传输 `processing` 中的文件。已知的文件处理规则如下：

| 本地传输结果 | 文件处理 |
| --- | --- |
| 主程序判定传输完成 | 删除对应的 `processing` 文件 |
| 传输失败 | 文件残留在 `processing` |
| 传输中断 | 文件残留在 `processing` |

主程序由第三方维护，失败或中断后是否再次处理残留文件、何时处理及如何重试均未知。camctl 的执行和恢复不依赖主程序一定会重试，也不能将残留文件视为正在传输或一定会再次传输。

文件进入 `processing` 后仍归主程序管理；camctl 遵守各专题的交接边界。本地传输完成及文件删除均不能证明远端客户端已经完整收到文件。

这里的“原子发布”使主程序在 `ready` 看到的是已经完整准备好的单个文件；主程序不会读到 camctl 仍在生成的前半份文件。移动成功与突然断电后是否仍可靠保存分别由后面的移动和落盘规则保证。

### 发布原子性

单个文件：

> 必须在 `staging` 完整生成后，再原子发布到 `ready`。

`staging`、`ready`、`processing` 应位于支持所需原子重命名/移动语义的同一文件系统范围内。

多个文件不要求整体原子发布。

状态报告文件依据 SQLite 中的不可变历史和已登记的冻结生成依据重建，登记与文件生成的先后关系见[从历史重建报告](status-reports.md#从历史重建报告)。文件交接对账结合持久化历史与实际文件证据，同时遵守目录所有权和报告补投规则；回放历史本身不执行文件移动或删除。

状态报告成功放入 `ready` 后，由 camctl 在数据库中保存[已发布记录](report-publication.md#记录报告已经发布)。主程序继续按目录协议领取和处理文件。

### 状态报告发布前落盘

camctl 按以下顺序发布状态报告：

1. 在 `staging` 写完全部内容，按报告命名规则计算摘要并确定最终文件名，清空程序的写入缓冲，并成功完成文件同步后关闭文件。
2. 将完整文件原子移动到 `ready`，从此允许主程序领取。
3. 同步 camctl 此次移动涉及的目录，随后保存数据库中的已发布记录。

文件同步必须在文件对主程序可见之前完成。Linux 可通过 `fsync` 将文件数据提交到存储；文件同步和目录同步分别承担内容与目录项的持久化，不能仅以关闭文件或移动成功代替。[Linux fsync 文档](https://man7.org/linux/man-pages/man2/fsync.2.html)

任一步骤失败或结果不确定时，停止后续正常步骤并按[会话错误分类](session-errors.md#错误标识)处理，区分报告文件操作失败与数据库记录保存失败。文件尚未移出 `staging` 时不发布；文件已经移入 `ready` 时仍按实际交接状态处理，不能把同步失败解释为文件从未发布，也不能撤回主程序已经领取的文件。

主程序可能在目录同步或数据库记录完成前领取文件。camctl 根据自身已确认的操作结果记录事实，不要求文件持续留在 `ready`。本节定义 camctl 负责的写入和移动；主程序后续移动、删除的持久化行为仍属于第三方边界。

### 普通交付的保存顺序与中断恢复

本节适用于照片、视频等普通产物的独立 delivery。成功表示 camctl 完成本地交付，不表示主程序已经发送，也不表示远端客户端已经收到。状态报告和日志副本仍按各自的恢复规则处理。

正常交付按以下顺序进行：

1. camctl 在 `staging` 完整准备本次交付副本，完成校验、文件及必要目录的同步，按[准备完成与断电恢复](output-cleanup.md#准备完成与断电恢复)保存准备完成事实。
2. 确认本次取回满足发布条件后，camctl 在数据库中保存本次 delivery 的发布意图，再开始移动文件。发布意图不等于发布成功。
3. camctl 将完整副本原子移动到 `ready`。主程序从此可以将文件领取到 `processing`，不等待数据库中的完成记录。
4. camctl 同步此次移动涉及的目录，再将本地交付完成事实及当前投影保存到同一数据库事务中。

主程序可能在第 4 步完成前领取、发送并删除文件。当前 camctl 进程根据自身已经确认的移动与同步结果保存事实，不要求文件持续留在 `ready`；进程中断后，恢复程序依据已持久保存的事实和能够确认的文件证据处理。不能提前保存交付成功来消除这个窗口，也不能把文件消失解释为发送成功。

恢复先核对已有终态、取消及撤回事实，按所属规则处理，不重新激活已经结束的取回。下表用于尚未结束、没有取消或撤回要求的交付；文件观察必须能够关联到原 delivery，并结合已保存的准备记录确认是同一份完整副本。

| 已保存事实与恢复检查结果 | camctl 的处理 |
| --- | --- |
| 已有可靠的本地交付完成事实，且没有后续撤回等状态变化 | 保留成功结果。文件后来被主程序移走或删除，不撤销已确认的本地交付事实。 |
| 尚无完成事实，但能够确认同一完整副本位于 `ready` 或 `processing` | 根据恢复观察保存本地交付事实，并遵守所在目录的所有权；不再次生成或投放副本。 |
| 尚无完成事实，完整副本仅在 `staging`，原请求仍满足发布条件 | 核对准备记录和中断阶段，继续原 delivery 的交付，不分配新身份。 |
| 尚无完成事实，能够确认三个位置均无副本，已保存事实也不足以确定交接结果 | 将该 delivery 结束为 `failed`，明确保存“中断后无法确认本地交接结果”的原因；不自动重新投放，不因后续重启重新激活该交付。 |
| 数据库或目录检查失败，或者现有证据无法可靠归入以上情形 | 按实际错误或未确认状态处理，保留诊断；不能套用“三个位置均无副本”的分支，也不能猜测成功或重新投放。 |

交接结果无法确认而结束为 `failed`，表示本次操作没有可确认的成功结果，不表示已证明视频没有发送或客户端没有收到。历史和报告必须保留这个区别，不能将其表达为已确认的传输失败。使用[错误登记](../../protocol/errors/workflow-codes.json)中的 `delivery_handoff_unconfirmed`，详情关联本次 delivery。

其他交付继续独立处理，取回动作按[部分成功](obtaining-outputs.md#部分成功)汇总。客户端需要再次取回时提交新请求；只有正式源产物仍可用时，才能准备新的独立交付。原交付副本准备完成后，源产物可能已经按显式清理请求删除，恢复不能假定源文件仍然存在。

## 中间文件清理的运行预算

取回废弃副本与录像检查、修复留下的无用中间文件共用本节预算。是否允许删除仍分别由[取回中间文件](obtaining-outputs.md#取回中间文件的保留与清理)及[录像内部中间文件](camera-recovery.md#内部中间文件的保留与清理)的生命周期确定。正式产物、状态报告、日志副本及故障标记不使用本节的历史清理额度。

同一中间文件在一次正常 `run` 中最多进行一次检查和清理尝试。一次尝试包含必要的记录核实、文件状态检查、符合条件时的删除及结果保存，不是只能调用一次文件接口。文件查询或删除失败后，保存错误与未完成责任，本次不循环重试；读取记录或保存结果发生数据库错误时，继续按会话错误规则处理。

| 本地配置 | 默认值 | 含义 |
| --- | --- | --- |
| `cleanup.work_file_batch_size` | 32 | 每批从数据库取得的历史待清理记录上限 |
| `cleanup.work_file_limit_per_run` | 128 | 一次正常运行最多检查的历史待清理记录数 |

两项均为大于等于 1 的整数，布尔值不是合法值，可分别调整；使用本次运行的生效配置，不固化到原动作。实际批量还受本次剩余额度限制，批量配置大于每次运行上限时也不能多处理。单文件每次运行最多一次是固定规则，不因批量或上限改变而增加重试。

正常 `run` 开始安排清理时，从数据库确定此前已经保存的待清理责任范围，并固定该范围的登记上界。本次历史检查只覆盖这个上界之前的记录，不在运行期间不断把新记录加入历史扫描。按稳定的登记顺序和文件身份分批读取，从上次可靠保存的位置之后继续；到达范围末尾后可回到开头，但本次最多检查这个范围一轮，或者达到本次记录数上限时结束，以先到者为准。已经完成的清理记录不再作为候选；候选选择不能靠扫描 `staging` 后把所有文件当作垃圾。

已检查但尚不能安全删除的记录也占用本次历史处理额度，包含归属或操作状态无法确认、文件仍被使用等情况。检查所得的实际结果及继续位置可靠保存后再向后推进；删除失败的记录仍保留清理责任，但不留在队首阻止后续记录取得机会。下一次正常运行继续上述顺序，最终再次检查尚未完成的旧记录。

| 文件或运行状态 | 预算与处理 |
| --- | --- |
| 文件属于本次固定的历史范围，本次尚未检查，历史额度仍有剩余 | 占用一条历史检查额度，按所属生命周期检查并在允许时删除；本次不再次处理该文件 |
| 历史记录已经检查，但本次无法安全删除，或查询、删除失败 | 保存实际原因和继续位置，保留待清理责任，继续后面的记录；本次不重新排队 |
| 本次运行中新形成清理责任，文件已无用途且符合删除条件 | 由所属业务流程及时进行首次清理，不受历史记录数上限限制；失败后保留责任，后续正常运行再处理 |
| 本次已经处理过同一文件，随后被调度重扫、业务流程或退出检查再次发现 | 复用本次实际结果，不发起第二次检查和清理尝试 |
| 历史额度耗尽，或固定范围已经检查一轮 | 结束本次历史清理，剩余责任留待后续正常运行；不增加定时扫描、独立清理会话或立即重启要求 |
| 清理记录、结果或继续位置无法可靠读取和保存，或者提交结果未知 | 按数据库错误处理，保留实际文件事实，不猜测已经清理或进度已经推进 |

新产生文件的首次清理与历史清理按稳定文件身份协调，同一文件不能分别取得两次机会。历史候选中已经被所属业务流程处理的文件不再重复处理，仍计入本次已经检查的历史记录数。检查后用途改变也不重新开启该文件在本次运行中的清理尝试；必要的业务使用和停止继续由所属流程处理。

跨会话继续位置由 `runtime_state` 的独立清理字段组保存，职责见[中间文件清理进度](../camctl/database/reports-runtime.md#中间文件清理进度)。检查结果、适用的中间文件状态、继续位置及对应历史在同一数据库事务中提交；位置变化本身不增加业务变化序号。本次固定范围上界、已检查数及防重复检查状态按会话管理，后续正常运行重新建立。

清理结果与继续位置须保持可恢复的一致性：确认实际结果并可靠保存后，才能跨过对应记录。文件已删除、结果尚未保存就中断时，后续正常运行重新核实文件不存在并补记完成，不推测旧调用的结果。继续位置指向的记录已经完成或不再是候选时，仍从其顺序位置之后继续，不要求记录仍在待清理集合内。每次运行的已处理数重新计量，原业务动作终态保持不变。

检查范围、继续位置及计数是清理调度信息，本身不作为新的业务失败反复生成报告；实际清理结果仍按所属专题保存和报告。历史清理与设备动作异步推进，设备动作不等待历史清理全部完成。已经开始的文件调用仍须跟踪实际结束，遵守[本地文件操作的完成与故障边界](../camctl/file-runtime.md#本地文件操作的完成与故障边界)；本节的数量限制不构成底层调用的完成时限。

验收覆盖配置缺省与覆盖、非法值、批量大于剩余额度，历史记录数少于、等于及超过每次运行上限。组合成功、失败、无法确认及仍被使用的文件，验证检查即计数、同次运行不重试、失败记录不阻挡后面的记录，以及跨运行到末尾后继续检查旧残留。覆盖本次新增清理责任、同一文件被两个入口发现、结果与继续位置提交前后中断；分别验证正式产物及其他文件类型不受本节自动清理影响。

## 配置归属

交接目录使用以下用户级默认值，允许本地配置逐项覆盖；`$HOME` 的含义及文件覆盖规则见[本地配置的加载与更新](configuration.md#本地配置的加载与更新)。

| 字段 | 默认值 |
| --- | --- |
| `paths.staging` | `$HOME/.camctl/staging` |
| `paths.ready` | `$HOME/.camctl/ready` |
| `paths.processing` | `$HOME/.camctl/processing` |

`derived` 与保存日志副本及故障标记的 `logs` 均位于实际 `staging` 目录之下。部署时须保证主程序使用相同的实际 `ready` / `processing` 路径及所需访问权限，并满足本专题的原子移动要求；覆盖路径不改变目录所有权和发布规则。

## 验收要求

### 单元测试

使用受接口约束的文件操作与状态存储替身，验证发布、领取、撤回的许可判定和错误分类。

验证主机上的录像修复、取回及报告文件使用 `staging` 作为生成和处理位置，发布资格依据所属流程判断，不因文件出现在 `staging` 就自动发布。

验证派生产物发布使用独立交付文件，保留文件仍位于 `staging/derived/`；清理取回中间文件时不涉及该保留文件。

主程序传输失败或中断、文件持续残留在 `processing` 时，验证 camctl 保持文件所有权边界，不从文件存在推断传输成功或后续必然重试。

验证状态报告完成写入及文件同步后才允许移入 `ready`，相关目录同步完成后才提交已发布记录。分别覆盖写入、文件同步、移动和目录同步的失败或未知结果；按失败发生的位置验证后续步骤停止及已交接文件的所有权。

普通交付按[保存顺序与中断恢复](#普通交付的保存顺序与中断恢复)覆盖各证据分区。验证移动前必须保存意图，正常完成记录必须晚于目录同步；意图本身不证明成功。三个位置均无文件且结果无法确认时，交付最终为 `failed`，错误保留未知含义，不重新投放或分配身份；目录检查错误不能被解释为文件缺失。已有终态、取消和撤回不被普通恢复分支覆盖。

### 集成测试

本节验证软件组件组合，设备交互使用受契约约束的替身，不连接真实设备。受控故障和进程中断用于验证软件恢复，实际硬件性能与物理断电另行联调；范围遵守[第一版完善与验收范围](README.md#第一版完善与验收范围)。

使用真实文件系统、SQLite 与主程序领取流程，验证完整文件发布、领取与撤回竞争，以及各持久化、移动步骤发生受控故障或进程中断后的对账。

状态报告组合真实文件系统与主程序领取流程，覆盖主程序在 camctl 记录发布结果前领取文件的情况。

组合真实 SQLite、交接目录及主程序领取流程，在普通交付的意图提交、文件移动、目录同步及完成事务前后中断。分别保留副本在 `staging`、`ready`、`processing`，以及让主程序领取后删除，验证恢复结果符合决策表。组合源产物已清理、多文件取回部分成功、恢复结果再次提交中断，验证未知原因被保留、其他文件继续交付、已保存的最终失败不被重启复活。

### 后续存储联调

在目标存储上单独核实文件写入、文件与目录同步、原子移动在突然断电后的实际持久性。软件集成测试中的进程中断验证恢复逻辑，不作为物理断电结论；这项联调不属于集成测试运行条件或通过门槛。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 文件交接

- 主程序不能看到或领取 `staging` 中的半成品；
- staging → ready 原子发布；
- ready → processing 不可撤回；
- 主机断电恢复。
