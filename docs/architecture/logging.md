# 运行日志

[返回设计总览](README.md) · [请求受理与会话](protocol-session.md) · [阅读路线](reading-guide.md)

本专题定义普通运行日志的保留、日志副本的交付及日志通道故障的处理。camctl 自身与第三方日志共用[按级别接纳的策略](../camctl/implementation.md#日志异步投递入口与有界队列)，来源只影响重要日志满载时是否允许丢弃。CLI 的 stdout 结果、stderr 诊断及退出状态由[进程结果协议](cli-commands.md#stdout-与退出状态)定义。

队列采用[按水位接纳并顺序消费](../camctl/implementation.md#日志按水位接纳并顺序消费)：积压增加时逐步限制 `DEBUG` 和 `INFO`，为警告和错误保留接纳空间；已入队记录按顺序处理，不因后来的高级别日志而淘汰。

因水位、采样或满载而省略的记录按级别计数，正常退出时按[丢弃汇总规则](../camctl/implementation.md#日志丢弃计数与退出汇总)最多写一条 `WARNING` 摘要。被配置级别正常过滤的记录不计入；摘要遵守当前日志级别，突然终止时不保证保存计数或摘要。

自身重要日志等待入队时，取消不撤销投递责任；所属协程确认入队或按通道禁用规则结束投递后再最终结束。必要业务停止独立推进，具体边界和正常退出顺序见[重要日志等待期间的取消与退出](../camctl/implementation.md#重要日志等待期间的取消与退出)。

**阅读提示：** 运行日志用于近期排查问题，永久业务历史保存在数据库。普通日志在本地轮换；报告首次失败时准备一份日志副本，交给主程序传输。两类文件分别遵守下文的保留与交付规则。

## 日志用途

普通运行日志用于排查近期运行问题。计划受理、动作结果、设备恢复证据及报告重建依据仍按[持久化规则](system-foundations.md#持久化与配置基础)写入数据库并永久保留；这些事实不能只写日志而不保存到状态库。

业务恢复与报告重建依据数据库历史，日志轮换或删除不会删除业务历史。日志文件不登记为正式产物、delivery 或状态报告。

## 配置与默认值

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `paths.log_file` | `$HOME/.camctl/camctl.log` | 正在写入的日志文件 |
| `session.log_level` | `WARNING` | 日志级别 |
| `session.log_max_size` | `"10 MiB"` | 单文件轮换阈值，按文件字节数判断 |
| `session.log_file_count` | `3` | 保留文件总数，包含正在写入的文件 |
| `session.log_queue_capacity` | `1000` | 每个进程日志队列允许等待的最大记录条数 |
| `session.log_queue_low_watermark` | `700` | 第一水位，达到后停止接纳 `DEBUG`，对 `INFO` 采样 |
| `session.log_queue_high_watermark` | `800` | 第二水位，达到后停止接纳 `INFO`，剩余位置供警告和错误使用 |
| `session.log_info_sample_probability` | `0.1` | 两个水位之间每条 `INFO` 独立被选中的概率，默认值表示 10% |

轮换阈值遵守[容量配置的表示](configuration.md#容量配置的表示)，换算后须为大于等于 1 的整数个字节。文件总数须为大于等于 1 的整数；0、负数、布尔值及其他错误类型属于本地配置错误。配置文件可省略这些字段，按[默认值与覆盖规则](configuration.md#本地配置的加载与更新)处理。配置更新后，后续进程使用新值；日志策略属于会话配置，不作为动作执行预算固化。

队列容量与两个水位均为正整数，按条数配置，不使用字节容量字符串；完整生效配置须满足 `0 < log_queue_low_watermark < log_queue_high_watermark < log_queue_capacity`。采样概率使用有限数值，合法范围为闭区间 `[0, 1]`：0 表示采样区间内全部省略 `INFO`，1 表示该区间内全部选中。布尔值、错误类型、非有限概率及不满足范围或组合关系的值均属于本地配置错误；不自动修正水位或随容量缩放。省略字段先补默认值，再校验整组配置。

第一版的实际部署保证日志级别能够接纳 `ERROR` 及以上记录。

这些参数可在部署时分别调整，每个进程启动时读取并在本次运行内固定；报告子进程使用主进程传入的生效配置，各进程独立计算队列条数。默认值是用于联调的初始工程取值，不代表已经测得固定内存占用或日志吞吐保证；实际资源占用还取决于记录大小和待投递协程。接纳与采样的完整行为由[水位规则](../camctl/implementation.md#日志按水位接纳并顺序消费)定义。

## 文件轮换

当前文件使用 `paths.log_file`。归档文件在该路径后追加数字后缀，`.1` 是最近一份，数字越大表示越旧。按默认配置，正常保留的文件为：

```text
$HOME/.camctl/
    camctl.log
    camctl.log.1
    camctl.log.2
```

设换算为字节数的轮换阈值为 `B`，保留总数为 `N`。处理一条日志前，先按表判断；只有配置合法且相关文件操作可以完成时，才适用表中的正常结果。

| 当前文件状态 | 处理 |
| --- | --- |
| 当前文件不存在 | 创建当前文件并写入本条日志，不因缺少当前文件而清空已有归档 |
| 当前文件大小小于 `B` | 向当前文件追加本条日志 |
| 当前文件大小大于等于 `B`，且 `N = 1` | 轮换时淘汰旧内容，只保留新当前文件并写入本条日志 |
| 当前文件大小大于等于 `B`，且 `N > 1` | 将当前文件转为最近归档，已有归档依次后移，删除超过 `N - 1` 份的最旧归档，再写入新当前文件 |

阈值按一条完整日志写入后的大小判断，因此跨过阈值的那条日志可以使文件略大于 `B`；下一条写入前轮换，不为凑齐阈值截断诊断内容。重启沿用已有文件的实际大小与归档顺序，不重新累计一套进程内文件额度。

将保留数量调小时，下一次写入前清理本机制管理的超限旧归档，使正常完成后的文件总数符合新值。清理范围仅为所配置日志路径对应的归档文件，不扩大到其他目录、状态库或业务文件。

## 多进程共用

相同日志路径对应一组文件和一个保留上限；并发运行的 `run`、`submit` 共用这组文件，而不是每个进程各保留 `N` 份。

追加与轮换须在所有写入进程之间协调，避免某个进程移动归档时另一个进程仍把新日志写进旧文件。一次正常完成的写入追加到当前文件，轮换后保持上述归档顺序及数量上限；不能仅以进程内互斥保护多个进程共享的日志路径。

第一版采用[普通日志执行与多进程轮换方案](../camctl/implementation.md#普通日志执行与多进程轮换)：各进程使用 `janus` 有界队列连接日志投递入口与专用 `QueueListener` 日志线程，由 `concurrent-log-handler` 的 `ConcurrentRotatingFileHandler` 通过文件锁协调共享文件的追加与轮换。协程使用可等待入口，同步来源经 `QueueHandler` 及接纳适配进入同一队列；接口语义与分级目标见[日志异步投递入口与有界队列](../camctl/implementation.md#日志异步投递入口与有界队列)。各进程独立管理自身生命周期，使用同一路径及一致的轮换配置；一个进程退出不关闭其他进程的日志通道。

## 日志通道故障

普通文件日志是辅助诊断通道。在配置已经合法的前提下，日志目录或文件无法创建、打开、追加、刷新或轮换，均不单独导致会话失败，也不触发录像应急停止。仅为写日志而使用的进程间协调失败，同样按日志通道故障处理，不扩大为会话排他或接纳资格失效。

轮换失败时，只要进程间写入协调仍然有效且当前日志文件可以追加，就继续记录日志。故障期间文件可能超过轮换大小，归档数量与顺序以实际成功的操作为准；后续日志仍按正常流程尝试追加与适用轮换，不为本条日志反复重试轮换。首次识别轮换故障时，向可用的 stderr 提示一次实际已知的路径、操作和原因，重复故障不反复提示。

无法创建、打开、追加或刷新当前日志文件，或无法可靠协调多进程写入时，停止本次进程后续的文件日志写入和轮换，首次禁用时向仍可用的 stderr 提示一次实际原因。提示直接使用 stderr；关闭失败通道或输出诊断时发生的错误，不得形成递归记录或无界重试。正常 stderr 诊断仍可继续输出。

| 条件 | 日志处理 | CLI 及业务处理 |
| --- | --- | --- |
| 日志配置字段本身不合法 | 不用默认值掩盖错误 | 按本地配置错误处理 |
| 配置合法，轮换失败，进程间写入协调仍有效且当前文件追加成功 | 继续记录日志，首次识别轮换故障时向可用的 stderr 提示一次；不把轮换失败解释为追加失败 | 继续原有职责，不改变动作结果或会话结果 |
| 配置合法，当前文件无法创建、打开、追加或刷新，或写入协调失效，包括轮换失败后又发生这些错误 | 禁用本进程文件日志，首次禁用时向可用的 stderr 提示一次 | 继续计划受理、调度、录像及报告等原有职责，不改变动作结果或会话结果 |
| 本进程文件日志已经禁用，之后又有日志产生 | 跳过文件日志，不反复打开、写入、轮换或重复提示同一禁用状态 | 继续按业务与会话契约执行 |
| stderr 诊断也无法输出，但 stdout 和其他必要职责仍可完成 | 停止对失败的诊断通道反复写入，不把日志转写到 stdout | 不仅因辅助诊断丢失而结束会话或停止录像 |
| 同时发生状态库、报告、设备操作或 stdout 结果通道等其他错误 | 在剩余可用诊断通道保留实际信息 | 各错误按原责任边界处理；日志故障不能掩盖它们或把失败改成成功 |

文件日志禁用只作用于发现故障的进程，不修改持久化业务状态或其他进程的日志开关。下一次实际启动的 CLI 可以按配置重新尝试使用现有日志文件；这不是重建业务状态或清空归档的理由。

一次运行可能只留下部分文件日志。关键业务事实仍须按数据库契约保存；不能因为日志通道不可用而省略持久化。若数据库无法写入，仍按[会话错误及应急停止](session-errors.md#正在录像时的应急停止)处理。其他职责正常完成时，`run` / `submit` 可照常输出成功结果；`submit` 的 `needs_run` 仍按实际持久化工作和接纳资格计算，日志故障不参与该判断。`describe` 以能力说明是否完整导出判断结果，`init` 以[本地初始化职责](initialization.md#命令结果)是否完成判断结果。

## 日志副本交付

报告处理第一次失败时，camctl 将当前普通日志文件原样复制一份，交给主程序传输，供维护人员排查问题。该流程不等待会话结束或多次 `run` 均失败。camctl 负责将日志副本放入本地 `ready`；主程序何时传输、远端何时收到，由后续传输流程决定。

### 准备与交接

`paths.log_file` 指向各进程持续追加并按配置轮换的普通日志文件。`staging/logs` 保存准备交付的日志副本和留在本地的故障标记文件。日志副本具有唯一文件名，内容固定；普通日志轮换只管理原日志及其归档。

camctl 先按[独立状态文件规则](#跨-run-的独立状态文件)可靠保存本次故障标记及日志副本身份。标记创建失败或保存结果未知时，按[创建失败规则](#故障标记创建失败)停止本次日志副本交付流程。报告错误仍通过普通日志和可用的 stderr 记录。

1. 所属业务协程通过正常日志入口记录本次报告失败的阶段、实际错误、可可靠关联的请求或报告身份及已有异常堆栈。日志仍使用统一的格式与级别规则。
2. 日志副本交付流程确认本次错误记录已经实际写入普通日志文件并刷新写入缓冲。普通异步日志调用返回只表示记录已入队，不能作为文件写入完成的证据；确认写入的具体接口在实现设计中确定。
3. camctl 协调共享日志文件的追加与轮换，将包含本次错误记录的当前日志文件完整、原样复制到 `staging/logs`。从该错误写入到副本内容确定之间，其他进程的轮换不能使副本漏掉该错误；复制期间的追加也不能造成副本中的日志记录不完整。该协调须复用日志处理器的跨进程锁，具体接入方式在实现时核验。
4. camctl 清空副本的写入缓冲，完成副本的文件同步并关闭副本，然后将副本原子移动到 `ready`，完成涉及目录的同步。原日志文件继续留在 `paths.log_file`，后续日志仍由各进程按正常追加与轮换规则处理。
5. 主程序按 `ready → processing → 本地传输完成后删除` 的现有流程中转日志副本，保留完整文件名和内容。camctl 不修改或撤回已被领取的日志副本。日志副本传回后，由人工递交给负责软件维护的人员查看。

副本保留复制时当前日志文件的全部字节及原有编码、格式，只复制当前文件。副本大小取决于该文件的实际大小，不能把轮换阈值当作副本大小的硬上限；刚完成轮换时，副本可能只有很少的历史上下文。锁等待、文件复制和同步在工作线程中执行，主事件循环异步等待结果；具体协作遵守[日志执行方案](../camctl/implementation.md#普通日志执行与多进程轮换)。

主机日志的接收与分析由上述人工维护流程负责；客户端网页的文件处理范围为业务状态报告、图片和视频。

日志副本不登记为业务产物、普通 delivery 或状态报告，不分配 `report_id`，不推进 `change_seq`，也不接受状态报告 ACK。复制日志、将副本移入 `ready` 及记录这些操作的错误，均不能触发下一份业务报告或再次交付日志副本；业务状态和未完成报告责任仍按原契约保存。

### 首次失败与重复失败

从首次报告处理失败，到报告本地处理已可靠恢复成功，连续未恢复期间统一视为一轮故障，只触发一次日志副本交付。该范围跨越多次报告尝试和多次 `run`；期间失败阶段、错误类别、错误信息或关联报告身份发生变化，仍属于同一轮。后续失败继续记录普通日志，不额外复制日志。首份日志副本内容固定，因此可能不包含本次后续出现的新错误。

报告本地处理已可靠恢复成功后，结束本次故障；之后再次失败才触发新一轮日志副本交付。恢复依据[报告本地处理及完成证据](status-reports.md#与会话收尾的协作)判断，单个步骤成功不代表整轮处理恢复。例如，业务状态报告已经生成，但 camctl 将报告移入 `ready` 时失败，故障仍持续。收到 ACK、主程序领取或删除文件、日志副本成功移入 `ready`、进程重启及一段时间没有新的报告尝试，都不单独构成恢复依据。

| 报告及日志副本状态 | 处理 |
| --- | --- |
| 已可靠确认此前无未恢复故障，发生报告处理失败 | 开始一轮故障，立即尝试可靠保存故障标记，成功后复制日志并将副本移入 `ready`；保留报告责任，普通设备动作继续，其他执行前提失效仍按各自错误规则处理 |
| 本次故障仍未恢复，后续报告尝试失败，包括阶段、错误类别、文案或关联报告身份变化 | 保持本次故障，只记录普通日志，不再次触发日志副本交付 |
| 本次故障仍未恢复，只有部分报告步骤成功，其余必需步骤失败、未完成或结果未知 | 保持本次故障，不以局部成功重新允许触发日志副本交付 |
| 本次故障仍未恢复，发生重启、新业务变化、ACK、文件领取或删除，或暂时没有报告尝试 | 这些事件自身不结束本次故障；后续报告处理仍依据实际结果判断恢复 |
| 报告本地处理已可靠恢复成功 | 结束本次故障持续状态，保留已有日志及文件交接事实 |
| 恢复成功后再次报告失败 | 作为新一轮故障触发日志副本交付 |
| camctl 读取原日志、写入或同步日志副本失败，或者将日志副本移入 `ready` 的操作失败 | camctl 记录实际错误，并按[日志副本的失败清理](#日志副本的失败清理)处理本次日志副本；camctl 保留故障标记文件，不自动重试本次日志副本交付，也不因此单独终止设备动作 |
| 日志副本移动或同步结果未知 | 保留实际已知的文件操作和错误事实，不宣称成功或从未移入 `ready`，不通过再次复制日志掩盖未知结果 |
| 无法可靠确认此前故障轮次、是否已经触发或是否已经恢复 | 明确保留未知及诊断，不把未知当作首次失败、已发布或已恢复；具体跨进程处理边界见下节 |

### 跨 run 的独立状态文件

第一版采用独立的小型状态文件，以正式文件是否存在表示跨 `run` 的故障状态：存在表示本次故障持续，不存在表示当前没有故障标记。首次报告失败时创建，报告本地处理可靠恢复成功后删除。首次部署不预先创建该文件。文件位于实际 `staging/logs` 下，由 camctl 留在本地维护；主程序不领取它，普通日志轮换不删除它。日志副本被传走或删除，不改变该状态文件的存在性。

第一版以故障标记文件能够正常删除为明确运行假设。业务状态报告的本地处理可靠恢复成功后，camctl 删除故障标记文件并同步所在目录；本次故障结束，之后再次发生报告故障时可以建立新标记。故障标记删除的设计与验收按这一正常流程展开。

正式状态文件的存在性及其内容是这组故障标记及日志副本管理信息的权威来源，检查和读写不依赖业务状态数据库可用。文件内容保存本次身份及日志副本处理进度；是否仍处于一轮故障由文件存在性判断。业务历史及报告责任继续由状态数据库管理，重复错误继续写入普通日志。

| 保存的信息 | 含义 |
| --- | --- |
| 故障轮次标识 | 将多次报告尝试及多次 `run` 关联到同一轮故障 |
| 本次日志副本身份及文件名 | 识别本次已尝试交付的日志副本 |
| 最后可靠确认的处理阶段 | 区分已开始复制、副本已完整保存、已移入 `ready` 并完成目录同步等事实；具体字段与状态枚举在实现设计中细化 |

存在性检查与内容读取分别判断，首次触发资格按下表处理。文件存在只表示本次已建立标记，不证明日志副本已准备完成或成功发布。

| 正式状态文件的存在性 | 内容读取结果 | 新一次报告失败的处理 |
| --- | --- | --- |
| 可靠确认不存在 | 不适用 | 创建新故障标记及日志副本身份，可靠保存成功后再复制日志；创建失败或保存结果未知时停止本次日志副本交付流程 |
| 可靠确认存在 | 内容有效 | 本次故障持续，不触发另一份日志副本；camctl 使用已保存身份和进度识别本次日志副本，失败或中断的交付流程不自动接续 |
| 可靠确认存在 | 内容无法读取或无效 | 仍能确认存在故障标记，不触发另一份日志副本；身份和进度保留为未知，不由内容读取失败推断无故障 |
| 无法可靠确认是否存在 | 不适用 | 记录实际检查错误，保留存在性未知，不当作不存在，也不据此开始新一轮；后续再检查的时机仍待明确 |

存在性检查成功取得正式文件信息时判为存在，明确返回路径不存在时判为不存在；父目录搜索权限不足等检查错误须单独保留，不能捕获所有文件操作异常后统一返回“不存在”。已经确认文件存在后，内容读取失败不改变该存在性判断。此处只要求正确区分检查结果，不增加独立轮询或复杂的故障探测机制。

下表定义文件操作能够可靠完成时的正常更新流程；恢复成功的依据遵守“首次失败与重复失败”。

| 当前可靠状态与新事件 | 更新及后续处理 |
| --- | --- |
| 正式状态文件可靠确认不存在，发生报告处理失败 | 创建状态文件，保存新故障轮次及日志副本身份，再复制日志并将本次副本移入 `ready` |
| 本次日志副本准备或发布取得可确认的结果 | 保存对应的实际处理进度，不将已触发记成已发布 |
| 本次尚未恢复，后续报告处理再次失败，包括跨 `run` 的情况 | 沿用已有轮次及日志副本身份，继续记录普通日志，不因重复失败创建日志副本 |
| 正式状态文件存在，报告本地处理已可靠恢复成功 | 删除状态文件并同步所在目录，结束本次故障标记；日志副本的既有交接事实仍按其实际状态处理 |
| 正式状态文件可靠确认不存在，报告本地处理成功 | 保持无故障标记，无须创建状态文件 |
| 上一轮状态文件已可靠删除，之后再次报告处理失败 | 创建新状态文件及新的日志副本身份，再按首次触发流程处理 |

创建或更新采用先完整写入临时文件、同步文件，再原子放置到正式路径并同步目录的方式；更新已有文件时原子替换，不先删除正式文件而暴露无故障标记的间隙。只有正式状态文件作为故障标记，临时文件的中断处理仍需细化。本次结束后的迟到进度更新不得重建已删除的状态文件。状态文件操作与日志副本发布分别跟踪实际结果；具体编码和接口在实现设计中确定，可复用标准库的 JSON 编解码及文件操作能力。

故障标记文件与日志副本分别保存。进程可能在故障标记文件已经建立、日志副本尚未写完时退出，也可能在日志副本已经移入 `ready`、但交接结果尚未记回时退出。故障标记文件仍存在时，进度记录未更新或交接目录中没有日志副本，都不能单独证明日志副本从未交给主程序，也不能据此重新触发另一份日志副本。故障标记创建失败按下节处理，日志副本按[失败清理规则](#日志副本的失败清理)处理。已有故障标记文件的更新失败，以及无法确认故障标记文件是否存在时的后续处理仍待明确。

### 故障标记创建失败

本次故障标记及日志副本身份可靠保存成功，是开始复制日志并将副本移入 `ready` 的前置条件。创建结果包含文件完整写入、文件同步、放置到正式路径及所在目录同步的实际结果；只确认正式文件存在，不等于已经完成这些持久化步骤。

| 故障标记创建结果 | 本次日志副本交付处理 |
| --- | --- |
| 所需写入、同步及正式路径放置均已确认成功 | 开始复制日志并将本次副本移入 `ready`；标记成功本身不证明日志副本已生成或发布 |
| 创建操作失败，可靠确认正式标记尚未建立 | 记录实际错误，停止本次日志复制与交接，不宣称标记已保存 |
| 已确认放置到正式路径，但后续目录同步失败或未确认 | 保留已有标记及实际操作结果，停止本次日志复制与交接，不将其解释为确定未创建 |
| 无法可靠确认创建操作的结果 | 保留未知及实际错误，停止本次日志复制与交接，不以删除可能存在的标记后重新创建来掩盖未知结果 |

错误通过仍可用的普通日志和 stderr 记录。标记创建失败不递归触发日志副本交付，也不单独停止录像或其他业务；原报告错误、状态库错误及其他执行前提错误仍按各自规则处理。保留可能已创建的标记，不因本次失败撤销故障标记来重新触发日志副本交付。

本节规定停止本次日志副本交付流程，不据此判定整个 `run` 后续的日志副本交付永久停用。已经建立故障标记的轮次遵守[失败后不自动重试的规则](#日志副本的失败清理)。故障标记未建立或创建结果未知时，后续何时再检查及如何处理故障标记的临时文件仍需明确；不能仅凭首次创建失败，自动选择重试或清空记录。

### 日志副本的失败清理

本节处理的是从普通日志文件复制出来、准备交给主程序传输的日志副本。故障标记文件继续留在 `staging/logs` 中，直到业务状态报告的本地处理可靠恢复后，camctl 才按既有规则删除故障标记文件。

camctl 每轮只尝试一次日志副本的准备与交接。如果 camctl 在复制日志、同步日志副本、将日志副本移入 `ready` 或完成后续目录同步时遇到错误，camctl 停止本次日志副本交付流程，并记录实际错误。如果进程中途退出，后续 `run` 也不自动继续写入、重新复制或再次投递本次日志副本。仍正常进行的首次日志副本交付流程可以继续完成，不因观察到本次已有故障标记而中止。

camctl 清理本次日志副本之前，必须确认相关文件操作已经结束，并且相关文件句柄已经关闭。不能因为等待工作线程的协程被取消，就认为工作线程已经停止写入或移动文件。在满足这一前提后，camctl 根据日志副本的实际位置和归属执行下表；文件内容是否完整，不改变仍在 `staging/logs` 的失败文件应被删除的规则。

| camctl 已确认的情况 | camctl 对本次日志副本的处理 |
| --- | --- |
| 相关文件操作尚未结束，或者尚未确认相关句柄已经关闭 | camctl 继续跟踪实际操作结果，此时不删除日志副本 |
| 相关操作已结束且句柄已关闭；本次日志副本仍在 `staging/logs`，可以确认归属 | camctl 删除这份日志副本，包括未写完的半成品和未成功移入 `ready` 的完整文件 |
| 相关操作已结束；日志副本已移入 `ready`，但后续目录同步或进度记录出错 | camctl 保持已交接的日志副本不变，记录实际错误，不从 `ready` 撤回或删除日志副本 |
| 主程序已经将日志副本领取到 `processing` | 主程序继续负责日志副本的传输和后续删除；camctl 不修改或删除这份日志副本 |
| 相关操作已结束；camctl 可靠确认本次日志副本已不在其准备位置，且没有可清理的本地文件 | camctl 无须删除文件，也不重新复制或再次投递；文件不在准备位置本身不能证明远端已收到日志副本 |
| camctl 无法确认日志副本的位置、归属或移动结果 | camctl 保留实际已知结果及错误，不根据猜测删除文件，也不重新复制或再次投递 |

删除日志副本不会删除故障标记文件，也不会删除普通运行日志或业务状态报告。camctl 删除未能交付的日志副本后，也不重新尝试本次交付。如果删除操作本身失败，camctl 记录清理错误和实际残留，本次不循环重试删除，也不因此单独停止业务。

本次报告故障可能因此没有日志副本传出；排障依靠仍保留的普通日志。业务状态报告的恢复与补投继续遵守报告规则。进程突然退出或删除失败后留下的日志副本，由后续 `run` 按[启动清理规则](#run-启动时清理遗留日志副本)检查；清理不允许重新复制或投递本次日志副本。

### run 启动时清理遗留日志副本

每次 `run` 启动并取得会话锁后，camctl 安排一次检查，清理以前的日志副本交付流程留在实际 `staging/logs` 中的日志副本。这些遗留文件可能来自进程突然退出，也可能来自上次未成功完成的删除操作。camctl 不在运行期间定时扫描，也不因为本次清理失败而再次安排同一轮检查。

camctl 根据日志副本的专用命名规则及所属流程识别清理对象，具体名称在实现设计中确定。能够确认文件来自以前的日志副本交付流程，并且已经没有程序继续操作这份文件时，camctl 才允许删除。检查与本次日志副本交付流程可能同时推进，因此 camctl 必须排除本次 `run` 创建或正在处理的日志副本；不能仅凭文件出现在 `staging/logs` 中就删除，也不能把取消等待等同于文件操作已经结束。

| 检查中发现的对象或情况 | camctl 的处理 |
| --- | --- |
| 以前日志副本交付流程留下的日志副本仍在 `staging/logs`，归属明确且已无人继续操作 | camctl 尝试删除这份文件；半成品和完整文件采用相同规则 |
| 旧日志副本仍有程序操作，或者 camctl 无法确认相关操作是否结束 | camctl 本次不删除这份文件，不为等待删除机会增加轮询 |
| 故障标记文件 | camctl 保留故障标记文件，由业务状态报告可靠恢复后的流程负责删除 |
| 本次 `run` 创建或正在处理的日志副本 | camctl 不将这份文件列为启动清理对象，由本次日志副本交付流程负责处理 |
| 普通日志、业务状态报告或其他文件，或者 camctl 无法确认文件用途和归属 | camctl 不删除这些文件 |
| 日志副本已经在 `ready` 或 `processing` 中 | camctl 不将这份文件列为启动清理对象，由主程序继续处理 |
| camctl 可靠确认没有符合条件的旧日志副本 | camctl 结束本次检查，不创建或重新投递日志副本 |
| camctl 无法完成目录检查或文件检查 | camctl 记录实际错误，不把未能检查的文件当作不存在，也不根据猜测删除；后续 `run` 再检查 |
| camctl 删除某份旧日志副本失败 | camctl 记录实际错误和残留，本次不重复删除这份文件；后续 `run` 再检查，其他已确认符合条件的旧文件仍可处理 |

目录检查和删除通过已有的本地文件工作线程执行。设备动作不等待启动清理完成，也不以清理成功为前提；其他执行前提仍按原有规则判断。已经开始的文件操作继续按[本地文件操作的完成规则](../camctl/implementation.md#本地文件操作的完成与故障边界)跟踪实际结果，不能为结束清理而宣称仍在执行的操作已经完成。

本次 `run` 的日志副本交付失败时，camctl 仍按前述失败清理规则处理。启动清理只负责以前留下的日志副本，不改变故障标记的存在性，不启动日志复制或副本补投，也不改变业务状态报告的恢复规则。故障标记文件的临时文件属于标记保存流程，其处理规则仍需单独细化。

### 独立性与可靠性边界

日志复制及副本交接不依赖状态库可用：不能要求先分配数据库身份、登记业务交付或成功提交报告记录才允许交付日志副本。状态库故障时，所属协程将已经掌握的错误写入普通日志，不为了补齐日志而继续查询已失效的状态库。

该流程依赖普通日志文件可用。文件日志无法写入时，遵守[日志通道故障规则](#日志通道故障)；不能把错误已入队或仅输出到 stderr 当作该错误已写入普通日志。原日志无法读取、复制失败或副本未完整保存时，camctl 不能将本次日志复制记为成功，仍按失败清理规则处理副本并保留故障标记。

日志副本与业务文件共用存储和主程序传输，不能保证报告失败时日志必然送达。报告内容生成出错，而普通日志与文件交接仍可用时，camctl 可以交付日志副本。磁盘已满、`ready` 不可写或文件系统故障时，日志副本交付可能同样失败；主程序或传输链路故障时，日志副本可能无法送达。camctl 保留仍可用的本地日志和 CLI 诊断，不将日志副本交付等同于业务报告完成或客户端已经收到状态。

### 实现前仍需明确的边界

上述按连续未恢复期间划分故障轮次、首次触发、重复抑制、恢复后重新触发、失败不递归及独立状态文件是已确认规则。正式状态文件存在表示故障持续，可靠恢复后删除，首次部署不预建；首次创建未可靠成功时停止本次日志复制与交接。第一版按故障标记文件能够正常删除的假设设计。实施前须细化内容字段、归属协调、故障标记创建失败后的再检查时机，以及存在性检查失败、内容无效或无法读取、已有故障标记更新失败、故障标记临时文件残留的处理；跨 `run` 的判断使用持久化标记与可靠证据，不以进程内标志代替，也不依赖状态库必然可用。

还需确定日志副本的具体命名规则，以及错误实际写入的完成通知、文件锁与复制操作如何接入现有日志组件。副本内容已经确定为当前普通日志文件的全部原始字节。日志级别沿用前述部署约定。

日志副本交付流程失败后，camctl 按既定条件删除仍在 `staging/logs` 的本次日志副本；后续每次 `run` 取得会话锁后检查一次遗留日志副本。两种清理都保留故障标记文件，不自动重试或补投日志副本。其他意外情况是否触发此通道仍需按具体故障确认，不把任意日志错误自动扩大为新触发条件。

## 验收要求

日志副本交付的单元测试按“首次失败与重复失败”状态表验证首次失败、连续未恢复期间的重复失败、报告恢复、恢复后再失败、日志复制或将副本移入 `ready` 时失败及结果未知。重复失败分别覆盖失败阶段、错误类别、文案及关联报告身份变化，均只触发首份日志副本。业务状态报告已经生成但尚未成功交接，属于局部成功；ACK、主程序领取或删除文件、日志副本成功移入 `ready` 和没有新报告尝试，也均不单独结束故障轮次。验证日志副本交付不产生业务变化、不触发报告重试或递归交付日志副本。

复制流程的单元测试通过受真实接口约束的日志与文件协作者，分别控制错误尚未入队、已入队但尚未写入、已写入并刷新以及写入失败，验证复制流程依据实际写入结果推进。给定固定的当前日志字节，验证副本内容逐字节一致；只有副本完整写入、同步并关闭后，camctl 才将它移入 `ready`。普通日志的格式化行为单独验证，不把人类阅读的错误文案固定为副本格式。

复制流程的集成测试组合真实日志队列、文件处理器和多个独立写入进程，覆盖错误写入前后发生轮换、复制期间其他进程追加日志，以及副本交接后原日志继续追加和轮换。验证副本包含触发交付的错误记录，各条日志完整，副本字节在交接后保持不变；原日志留在配置路径继续使用。普通日志轮换不删除副本或故障标记。

独立状态文件的单元测试按存在性及正常更新表验证：不存在时首次失败先创建标记再复制日志；已存在时即使内容无法读取或无效也不触发另一份日志副本；存在性未知不当作不存在；重复失败沿用身份并只记录实际确认的进度；可靠恢复后删除标记，之后再次失败创建新轮次；迟到更新不重建已结束轮次的标记。集成测试组合真实状态文件与文件交接，验证首次部署不预建标记、恢复后的正常删除及目录同步、原子更新不暴露无标记间隙，以及日志副本被领取并删除后，后续 `run` 仍能识别原故障持续；普通日志轮换不删除状态文件，状态库不可用而状态文件及交接目录可用时仍可交付日志副本。创建与更新阶段尚未确定的故障及中断处理，在相应语义确认后补齐验收。

存在性检查的单元测试分别控制成功、明确不存在及权限等检查错误，验证检查错误保留实际原因并阻止以“不存在”为由新建轮次；另行验证已确认存在后内容读取失败，仍按已有故障标记处理。

故障标记创建的单元测试按创建结果表覆盖成功、正式标记尚未建立时失败、已放置但目录同步失败及结果未知，验证只有可靠成功才开始日志复制与交接；失败保留实际错误和可能已创建的标记，不递归触发日志副本交付、不单独停止业务，也不改写原报告或状态库错误。集成测试组合真实文件操作与受控故障，覆盖写入、文件同步、正式路径放置和目录同步各阶段失败，检查失败路径没有日志副本交给 `ready`，已经建立的正式标记不被删除以重试。

日志副本清理的单元测试按失败清理表覆盖：文件操作仍在进行、句柄尚未关闭、半成品留在 `staging/logs`、完整文件留在 `staging/logs`、日志副本已经移入 `ready` 或 `processing`、没有本地文件可清理，以及位置或归属未知。验证 camctl 只删除操作已结束且归属明确的本次准备文件；删除操作失败时保留实际错误，本次不循环重试。所有分支都保留本次故障标记文件，不删除普通日志或业务状态报告，也不重新开始日志副本交付流程。

日志副本清理的集成测试组合真实文件工作线程和交接目录，在日志副本写入期间、移动之前以及移入 `ready` 之后分别注入故障。验证 camctl 等待实际文件操作结束后才删除准备文件；主程序已经领取日志副本时，camctl 不修改 `processing` 中的文件。后续报告重复失败及再次启动 `run` 均不重新复制或补投原日志副本，业务状态报告仍按自身规则恢复。

启动清理的单元测试按启动检查表覆盖旧文件归属、操作是否结束、文件所在目录和文件类型，验证 camctl 取得会话锁后只安排一次检查。验证 camctl 保留故障标记、本次日志副本、普通日志、业务状态报告和无法确认归属的文件；目录检查失败时记录错误，单个文件删除失败时本次不重复尝试。后续报告失败、时间经过和调度重扫均不再次触发启动清理。

启动清理的集成测试在真实 `staging/logs` 中准备上次中断及删除失败留下的日志副本，再启动 `run`，验证 camctl 删除符合条件的旧日志副本并保留故障标记。检查期间安排本次日志复制，验证本次日志副本不会被误删。通过受控文件操作等待验证设备动作不等待清理完成；通过一次删除失败和下一次 `run` 的再次检查，验证失败残留可在后续运行中清理，而不会自动重新复制或投递日志副本。

日志副本交付的集成测试组合真实文件系统、主程序领取及状态报告处理，验证首次失败即可交付、普通设备动作继续、同一故障期间多次报告失败不重复交付，以及恢复后再次失败触发新的日志副本交付。分别验证状态库不可用但日志与交接目录可用，以及磁盘或目录故障导致日志副本也无法移入 `ready`；后者保留实际本地记录和 stderr 诊断，不宣称日志副本已交接成功。跨 `run` 去重及中断恢复的具体验收须先落实“实现前仍需明确的边界”所列事项。

单元测试按配置合法性和文件状态分类，验证默认值、阈值以下、恰好达到阈值、跨过阈值、保留数量为 1 和大于 1，以及重启继续采用已有文件大小。通过受接口约束的替身验证轮换顺序、最旧归档淘汰与删除范围，日志文案不逐字断言。

集成测试使用真实文件系统验证追加、轮换、减少保留数量及重启后的文件内容与数量；使用真实并发进程验证同一路径的写入与轮换共同满足约束。在不会触发正常淘汰的场景中，每条成功写入的测试日志完整出现且不重复；发生淘汰时按最旧归档边界判断，不要求已淘汰内容仍然存在。验证普通日志删除不修改状态库、产物及报告文件。

单元测试按“日志通道故障”分类，验证配置非法与日志 I/O 故障的不同结果、轮换失败但追加成功时继续记录、轮换失败后追加也失败时禁用、协调失效、首次禁用、后续跳过、stderr 提示次数、诊断通道再次失败，以及关闭时不递归记录。替身只隔离日志写入和协调边界，不能把原业务异常模拟成日志故障后吞掉。

集成测试组合真实 CLI、SQLite、stdout/stderr 管道及受接口约束的设备适配，通过受控日志故障验证：轮换失败但仍能追加时保留后续日志，后续轮换成功时恢复正常归档；日志无法写入时录像继续按目标停止，业务历史与报告正常保存；`submit` 仍返回正确的 `needs_run`；`describe` 仍可完整导出。再组合真实状态库故障，验证原会话错误及有限应急停止仍生效；组合报告文件处理故障时，验证普通设备动作继续及报告责任保留。验证本进程禁用不影响其他进程，后续新进程可以重新尝试文件日志。
