# 运行日志

[返回设计总览](README.md) · [请求受理与会话](protocol-session.md) · [阅读路线](reading-guide.md)

本专题定义普通运行日志的保留、异常诊断文件的交付及日志通道故障的处理。CLI 的 stdout 结果、stderr 诊断及退出状态由[进程结果协议](cli-commands.md#stdout-与退出状态)定义。

**阅读提示：** 运行日志用于近期排查问题，永久业务历史保存在数据库。普通日志在本地轮换；报告首次失败时准备一份异常诊断文件，交给主程序传输。两类文件分别遵守下文的保留与交付规则。

## 日志用途

普通运行日志用于排查近期运行问题。计划受理、动作结果、设备恢复证据及报告重建依据仍按[持久化规则](system-foundations.md#持久化与配置基础)写入数据库并永久保留；这些事实不能只写日志而不保存到状态库。

业务恢复与报告重建依据数据库历史，日志轮换或删除不会删除业务历史。日志文件不登记为正式产物、delivery 或状态报告。

## 配置与默认值

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `paths.log_file` | `$HOME/.camctl/camctl.log` | 正在写入的日志文件 |
| `session.log_level` | `WARNING` | 日志级别 |
| `session.log_max_bytes` | `10485760`（10 MiB） | 单文件轮换阈值，按文件字节数判断 |
| `session.log_file_count` | `3` | 保留文件总数，包含正在写入的文件 |

轮换阈值和文件总数均为大于等于 1 的整数；0、负数、布尔值及其他错误类型属于本地配置错误。配置文件可省略这些字段，按[默认值与覆盖规则](configuration.md#本地配置的加载与更新)处理。配置更新后，后续进程使用新值；日志策略属于会话配置，不作为动作执行预算固化。

## 文件轮换

当前文件使用 `paths.log_file`。归档文件在该路径后追加数字后缀，`.1` 是最近一份，数字越大表示越旧。按默认配置，正常保留的文件为：

```text
$HOME/.camctl/
    camctl.log
    camctl.log.1
    camctl.log.2
```

设轮换阈值为 `B`，保留总数为 `N`。处理一条日志前，先按表判断；只有配置合法且相关文件操作可以完成时，才适用表中的正常结果。

| 当前文件状态 | 处理 |
| --- | --- |
| 当前文件不存在 | 创建当前文件并写入本条日志，不因缺少当前文件而清空已有归档 |
| 当前文件大小小于 `B` | 向当前文件追加本条日志 |
| 当前文件大小大于等于 `B`，且 `N = 1` | 轮换时淘汰旧内容，只保留新当前文件并写入本条日志 |
| 当前文件大小大于等于 `B`，且 `N > 1` | 将当前文件转为最近归档，已有归档依次后移，删除超过 `N - 1` 份的最旧归档，再写入新当前文件 |

阈值按一条完整日志写入后的大小判断，因此跨过阈值的那条日志可以使文件略大于 `B`；下一条写入前轮换，不为凑齐阈值截断诊断内容。重启沿用已有文件的实际大小与归档顺序，不重新累计一套进程内文件额度。

将保留数量调小时，下一次写入前清理本机制管理的超限旧归档，使正常完成后的文件总数符合新值。清理范围仅为所配置日志路径对应的归档文件，不扩大到其他目录、状态库或业务文件。

## 多进程共用

相同日志路径对应一组文件和一个保留上限；并发运行的 `run`、`submit` 共用这组文件，而不是每个进程各保留 `N` 份。

追加与轮换须在所有写入进程之间协调，避免某个进程移动归档时另一个进程仍把新日志写进旧文件。一次正常完成的写入追加到当前文件，轮换后保持上述归档顺序及数量上限；不能仅以进程内互斥保护多个进程共享的日志路径。具体协调方式由实现选择。

## 日志通道故障

普通文件日志是辅助诊断通道。在配置已经合法的前提下，日志目录或文件无法创建、打开、追加、刷新或轮换，均不单独导致会话失败，也不触发录像应急停止。仅为写日志而使用的进程间协调失败，同样按日志通道故障处理，不扩大为会话排他或接纳资格失效。

首次发现文件日志故障时，停止本次进程后续的文件日志写入和轮换，并向仍可用的 stderr 提示一次，附带实际已知的路径、操作和错误原因。提示直接使用 stderr，不再经过已失败的文件日志通道；关闭失败通道或输出诊断时发生的错误，不得形成递归记录或无界重试。正常 stderr 诊断仍可继续输出。

| 条件 | 日志处理 | CLI 及业务处理 |
| --- | --- | --- |
| 日志配置字段本身不合法 | 不用默认值掩盖错误 | 按本地配置错误处理 |
| 配置合法，普通文件日志首次发生操作或协调故障，必要职责仍可完成 | 禁用本进程文件日志，向可用的 stderr 提示一次 | 继续计划受理、调度、录像及报告等原有职责，不改变动作结果或会话结果 |
| 本进程文件日志已经禁用，之后又有日志产生 | 跳过文件日志，不反复打开、写入、轮换或重复提示同一禁用状态 | 继续按业务与会话契约执行 |
| stderr 诊断也无法输出，但 stdout 和其他必要职责仍可完成 | 停止对失败的诊断通道反复写入，不把日志转写到 stdout | 不仅因辅助诊断丢失而结束会话或停止录像 |
| 同时发生状态库、报告、设备操作或 stdout 结果通道等其他错误 | 在剩余可用诊断通道保留实际信息 | 各错误按原责任边界处理；日志故障不能掩盖它们或把失败改成成功 |

文件日志禁用只作用于发现故障的进程，不修改持久化业务状态或其他进程的日志开关。下一次实际启动的 CLI 可以按配置重新尝试使用现有日志文件；这不是重建业务状态或清空归档的理由。

一次运行可能只留下部分文件日志。关键业务事实仍须按数据库契约保存；不能因为日志通道不可用而省略持久化。若数据库无法写入，仍按[会话错误及应急停止](session-errors.md#正在录像时的应急停止)处理。其他职责正常完成时，`run` / `submit` 可照常输出成功结果；`submit` 的 `needs_run` 仍按实际持久化工作和接纳资格计算，日志故障不参与该判断。`describe` 以能力说明是否完整导出判断结果，`init` 以[本地初始化职责](initialization.md#命令结果)是否完成判断结果。

## 异常诊断文件

异常诊断文件向人工排障提供失败阶段、实际错误信息和相关日志。报告处理第一次失败时就触发准备和发布，不等待会话结束或多次 `run` 均失败。这里的发布指交给本地 `ready`，不保证主程序立即传输或远端立即收到。

### 准备与交接

异常诊断使用实际 `staging` 下的 `logs` 子目录保存相关日志和准备中的文件。普通运行日志仍按 `paths.log_file` 的配置轮换；准备诊断时选取相关内容形成独立文件，普通日志的轮换不负责清理异常诊断文件。

1. 收集本次失败阶段、已知错误、可可靠关联的请求或报告身份，以及相关日志；无法取得的内容如实表达为缺失或未知，不补造事实。
2. 在 `staging/logs` 准备一份内容固定、具有唯一文件名的诊断文件。清空写入缓冲，完成文件同步并关闭文件后，才允许发布；后续日志写入其他本地文件。
3. 将完整文件原子移动到 `ready`，完成涉及目录的同步。不得直接移动仍被任何进程写入的日志文件。
4. 主程序按 `ready → processing → 本地传输完成后删除` 的现有流程中转，保留完整文件名和内容。camctl 不修改或撤回已被领取的诊断文件。
5. 日志文件传回后，由人工递交给负责软件维护的人员，由其查看和排查问题。

主机日志的接收与分析由上述人工维护流程负责；客户端网页的文件处理范围为业务状态报告、图片和视频。

异常诊断不登记为业务产物、普通 delivery 或状态报告，不分配 `report_id`，不推进 `change_seq`，也不接受状态报告 ACK。诊断的生成、发布及故障记录不能触发下一份业务报告或再次诊断；业务状态和未完成报告责任仍按原契约保存。

### 首次失败与重复失败

以同一故障持续期间为一次诊断触发范围。已经触发首份诊断后，重复报告失败继续记录本地日志，不因后续业务变化或再次启动 `run` 自动产生同一故障的另一份诊断。报告本地处理已可靠恢复成功后，再次失败可以触发新一轮诊断。恢复以报告处理结果为依据，不以收到 ACK、主程序删除文件或进程重启为依据。

| 报告及诊断状态 | 处理 |
| --- | --- |
| 首次报告失败，尚未触发该故障的诊断 | 立即尝试准备并发布一份诊断，保留报告责任，普通设备动作继续 |
| 同一故障仍持续，已经触发诊断 | 后续失败继续记录本地日志，不重复生成或排入诊断 |
| 报告本地处理已可靠恢复成功 | 结束本轮故障持续状态，保留已有日志及文件交接事实 |
| 恢复成功后再次报告失败 | 作为新一轮故障触发诊断 |
| 诊断生成、文件同步或发布失败 | 保留实际已有的本地日志和未完成文件，通过仍可用的 stderr 输出错误；不递归生成诊断，也不因该失败单独终止设备动作 |
| 诊断移动或同步结果未知 | 保留实际已知的文件操作和错误事实，不宣称成功或从未发布，不通过再次生成另一份诊断掩盖未知结果 |
| 无法可靠确认是否属于此前故障、是否已经触发或是否已经恢复 | 明确保留未知及诊断，不把未知当作首次失败、已发布或已恢复；具体跨进程处理边界见下节 |

### 独立性与可靠性边界

准备和发布异常诊断不依赖状态库可用：不能要求先分配数据库身份、登记业务交付或成功提交报告记录才允许诊断交付。状态库故障时使用仍可信的本地错误信息，不为了补齐日志而继续查询已失效的状态库。

该通道与业务文件共用存储和主程序传输，不能保证报告失败时日志必然送达。报告内容生成出错而文件交接可用时，诊断可以发布；磁盘已满、`ready` 不可写或文件系统故障时，诊断可能同样失败；主程序或传输链路故障时，文件可能无法送达。保留仍可用的本地日志和 CLI 诊断，不能把日志交付等同于业务报告完成或客户端已经收到状态。

### 实现前仍需明确的边界

上述首次触发、重复抑制、恢复后重新触发及失败不递归是已确认规则。实施前须明确同一故障的判定字段、跨 `run` 保存触发与恢复状态的方式，以及这些记录无法读取、无法保存或发布中断时的处理；不能只使用进程内标志宣称跨重启去重，也不能把该机制建立在状态库必然可用的前提上。

还需确定诊断文件名、内容格式、相关日志截取范围、`staging/logs` 的保留与清理规则，以及首次诊断发布失败后原文件的恢复处理。诊断文件不自动继承业务状态报告的累计 ACK 和补投机制。其他意外情况是否触发此通道仍需按具体故障确认，不把任意日志错误自动扩大为新触发条件。

## 验收要求

异常诊断的单元测试按“首次失败与重复失败”状态表验证首次失败、同一故障持续、报告恢复、恢复后再失败、诊断生成或发布失败及结果未知。验证诊断不产生业务变化、不触发报告重试或递归诊断；内容断言覆盖失败阶段、实际错误及关联日志，未知身份不补造。用受真实接口约束的文件协作者验证只有完整写入、同步并关闭后才发布，普通日志轮换不删除待交付诊断。

异常诊断的集成测试组合真实文件系统、主程序领取及状态报告处理，验证首次失败即可交付、普通设备动作继续、同一故障期间多次报告失败不重复发布，以及恢复后再次失败触发新诊断。分别验证状态库不可用但日志与交接目录可用，以及磁盘或目录故障导致诊断也无法发布；后者保留实际本地记录和 stderr 诊断，不输出伪造的发布成功。跨 `run` 去重及中断恢复的具体验收须先落实“实现前仍需明确的边界”所列事项。

单元测试按配置合法性和文件状态分类，验证默认值、阈值以下、恰好达到阈值、跨过阈值、保留数量为 1 和大于 1，以及重启继续采用已有文件大小。通过受接口约束的替身验证轮换顺序、最旧归档淘汰与删除范围，日志文案不逐字断言。

集成测试使用真实文件系统验证追加、轮换、减少保留数量及重启后的文件内容与数量；使用真实并发进程验证同一路径的写入与轮换共同满足约束。在不会触发正常淘汰的场景中，每条成功写入的测试日志完整出现且不重复；发生淘汰时按最旧归档边界判断，不要求已淘汰内容仍然存在。验证普通日志删除不修改状态库、产物及报告文件。

单元测试按“日志通道故障”分类，验证配置非法与日志 I/O 故障的不同结果、首次禁用、后续跳过、stderr 提示次数、诊断通道再次失败，以及关闭时不递归记录。替身只隔离日志写入和协调边界，不能把原业务异常模拟成日志故障后吞掉。

集成测试组合真实 CLI、SQLite、stdout/stderr 管道及受接口约束的设备适配，通过受控日志故障验证：日志无法写入时录像继续按目标停止，业务历史与报告正常保存；`submit` 仍返回正确的 `needs_run`；`describe` 仍可完整导出。再组合真实状态库故障，验证原会话错误及有限应急停止仍生效；组合报告文件处理故障时，验证普通设备动作继续及报告责任保留。验证本进程禁用不影响其他进程，后续新进程可以重新尝试文件日志。
