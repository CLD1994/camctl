# 组件版本与软件更新

[返回设计总览](README.md) · [首次部署](initialization.md) · [运行日志](logging.md)

三个组件各自管理发行版本。部署包记录本次实际包含的组件版本和源码身份；更换 Python 包不要求同时更换 C 接入模块或客户端。是否能够组合运行，仍须满足命令、通知、报告及数据库的实际契约，不能仅比较版本号。

## 版本来源与发布

| 对象 | 唯一版本来源 | 消费方式 |
| --- | --- | --- |
| Python camctl | `apps/camctl/pyproject.toml` 的项目版本 | wheel 元数据、安装后的 `camctl --version` 及 Python 启动日志使用该发行版本。 |
| C 接入模块 | `apps/host-demo/src/host_version.h` 的版本定义 | CMake 读取同一来源设置项目与 CPack 版本，模块直接将该定义编入启动记录。 |
| 客户端 | `apps/client/package.json` 的包版本 | npm 锁文件保存生成的元数据，服务启动日志读取包版本。 |
| 完整部署包 | 构建时生成的 `RELEASE.json` | 记录实际组件版本组合、源码提交、工作树状态和摘要；不人工维护另一份组件版本清单。 |

版本使用三段数字。主版本表示不兼容的公开契约变化，次版本表示兼容功能，修订版本表示修复。公开契约包括 CLI 命令及机器结果、C 接口、通知和报告的行为；新增日志字段本身不要求各组件同步升级。处于 `0.x` 的组件仍记录实际变化，但不能由主版本相同推断其兼容性。

发布时，只递增发生变更的组件。已经交付的同一版本不重新发布不同内容；开发提交和发行物仍保留源码摘要，用于识别构建输入。`--reinstall-package camctl` 只用于明确重装指定交付物，不授权用旧版本号发布新代码。组件的变更记录应说明新增能力、修复及实际协议或数据格式要求。

数据库格式、公共协议格式与软件发行版本各自表达不同事实。软件升级不自动增加数据库格式号；需要数据迁移时按[显式初始化与格式升级](initialization.md)处理，使用者保留原历史和备份。换回旧软件不等于撤销数据库迁移。

## 启动版本记录

Python 的 `run`、`submit`、`init`、`describe` 在所属日志上下文建立后，各记录一次当前安装发行物版本。`--version` 只向 stdout 输出一行版本，不启动业务或输出启动记录。配置错误导致日志上下文尚未建立时，继续使用原命令错误诊断。

启动版本记录保持 INFO 级别，并作为单独的启动记录绕过普通等级过滤和 INFO 采样。队列满或文件通道失效时使用既有 stderr 后备通道；它不进入 ERROR 的等待队列，也不取得 ERROR 的断电持久保证。版本读取失败时交付实际诊断，明确版本不可用，不编造版本，也不阻挡必要业务收场。普通日志的等级、采样、容量及错误处理保持各自契约。

C 接入模块在日志建立后、其他工作线程启动前记录一次已编入的模块版本；这条记录不代表后续初始化已经成功。客户端在服务监听成功时记录一次包版本。它们均使用既有日志通道。C 主程序自身的版本仍由主程序维护；同一主程序可以依次启动多次 camctl，每次 Python 进程都记录自己的版本。

版本记录不进入 `run`、`submit` 的结果 JSON、通知管道或 `describe` 的能力 JSON。它是运维诊断信息，不产生计划、动作、报告或数据库历史变化。

## 停机离线更新 Python 包

首次安装使用部署包的 `install-host.py`；已有部署使用随包 Python 更新入口。两者职责分别由[部署 skill](../../.agents/skills/camctl-real-device-deploy/SKILL.md)和[完整部署包契约](../../.agents/skills/camctl-real-device-deploy/references/packaging.md)维护。更新入口、命令参数及文件清单由随包脚本和 README 维护，不在本页复制完整清单。

更新前，操作者停止接收新任务并等待 host、camctl 及其原有子进程结束。更新器复用原状态库的稳定会话锁和接纳锁，持有到安装及原部署检查完成；锁只能阻止同一数据库的并发 CLI，不能代替操作者停止 host。更新器不终止其他进程，不自动恢复主程序运行。

离线更新面向已有的 Linux Python 3.11 虚拟环境和 uv。构建机联网取得两种 Linux 目标架构的锁定依赖 wheel，并随包记录及校验。目标机安装使用本地 wheel，禁止访问软件源；不能把构建机的原生依赖误当作 ARM64 安装物。新建部署在缺少 Python 解释器或其他组件工具时仍须满足首次部署前提，不能把 Python 包离线更新解释为整机所有依赖均可离线安装。

更新保持原虚拟环境绝对路径，先校验交付物、原环境与配置，记录原安装身份，再安装配套依赖和本次 camctl wheel。新软件检查实际版本、依赖、原配置、原状态库及交接目录绑定。检查不创建状态库、不调整目录绑定、不探测设备，也不执行迁移或业务任务。能力说明可以按原配置导出为更新产物；只有提供明确同步目标时才覆盖客户端的能力说明文件，客户端数据库和媒体保持原样。

| 当前阶段或结果 | 更新器行为 |
| --- | --- |
| 摘要、文件集合、平台、原配置或状态库前提不成立 | 在修改 Python 环境前失败，报告具体事实。 |
| 无法取得原稳定锁 | 不开始安装；报告仍有调用或锁错误。 |
| 安装已开始 | 原环境可能已经改变；持续保存步骤、退出码和原安装信息。 |
| 安装、依赖或版本核验失败 | 返回失败，保留日志及收据；不启动 host，不声称原环境完整或已经自动回滚。 |
| 新软件不支持原数据库格式或目录绑定不符 | 原库保持原样，报告检查失败；由部署人员另行处理显式迁移或配置，不能直接恢复普通调用。 |
| 全部检查完成 | 报告指定软件已安装且仍停机；操作者沿原入口恢复 host。 |

指定同一版本重装或显式选择旧交付物，仍以该包的实际摘要及安装后版本为准，不仅根据版本大小拒绝。部署人员保留先前部署包、配套依赖和配置备份，以便在失败时人工恢复软件。收据和原安装版本不是可执行环境的自动备份；原地更新不提供环境原子切换或自动回滚保证。
