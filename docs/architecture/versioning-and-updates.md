# 组件版本与软件更新

[返回设计总览](README.md) · [首次部署](initialization.md) · [运行日志](logging.md)

三个组件各自管理发行版本。部署包记录本次实际包含的组件版本和源码身份；更换 Python 包不要求同时更换 C 接入模块或客户端。是否能够组合运行，仍须满足命令、通知、报告及数据库的实际契约，不能仅比较版本号。

调整版本、构建交付物、现场停机应用、首次接入维护入口、失败自动恢复及强制重建的操作步骤见[版本发布与现场更新操作](../camctl/software-updates.md)。本页定义行为规则，操作说明中的命令须与这些规则一致。

## 版本来源与发布

| 对象 | 唯一版本来源 | 消费方式 |
| --- | --- | --- |
| Python camctl | `apps/camctl/pyproject.toml` 的项目版本 | wheel 元数据、安装后的 `camctl --version` 及 Python 启动日志使用该发行版本。 |
| C 接入模块 | `apps/host-demo/src/host_version.h` 的版本定义 | CMake 读取同一来源设置项目与 CPack 版本，模块直接将该定义编入启动记录。 |
| 客户端 | `apps/client/package.json` 的包版本 | npm 锁文件保存生成的元数据，服务启动日志读取包版本。 |
| 完整部署包 | 构建时生成的 `RELEASE.json` | 记录实际组件版本组合、源码提交、工作树状态和摘要；不人工维护另一份组件版本清单。 |

版本使用三段数字。主版本表示不兼容的公开契约变化，次版本表示兼容功能，修订版本表示修复。公开契约包括 CLI 命令及机器结果、C 接口、通知和报告的行为；新增日志字段本身不要求各组件同步升级。处于 `0.x` 的组件仍记录实际变化，但不能由主版本相同推断其兼容性。

发布时，只递增发生变更的组件。已经交付的同一版本不重新发布不同内容；开发提交和发行物仍保留源码摘要，用于识别构建输入。`--reinstall-package camctl` 只用于明确重装指定交付物，不授权用旧版本号发布新代码。组件的变更记录应说明新增能力、修复及实际协议或数据格式要求。

数据库格式、公共协议格式与软件发行版本各自表达不同事实。自动更新以当前格式 V9 为维护基线，后续格式变化登记迁移步骤，由更新入口自动选择并验证。普通业务入口仍不迁移数据库；独立维护入口见[初始化与格式检查](initialization.md)。更新回滚同时恢复软件环境和数据库，不能只切回旧软件。

## 启动版本记录

Python 的 `run`、`submit`、`init`、`describe` 在所属日志上下文建立后，各记录一次当前安装发行物版本。`--version` 只向 stdout 输出一行版本，不启动业务或输出启动记录。配置错误导致日志上下文尚未建立时，继续使用原命令错误诊断。

启动版本记录保持 INFO 级别，并作为单独的启动记录绕过普通等级过滤和 INFO 采样。队列满或文件通道失效时使用既有 stderr 后备通道；它不进入 ERROR 的等待队列，也不取得 ERROR 的断电持久保证。版本读取失败时交付实际诊断，明确版本不可用，不编造版本，也不阻挡必要业务收场。普通日志的等级、采样、容量及错误处理保持各自契约。

C 接入模块在日志建立后、其他工作线程启动前记录一次已编入的模块版本；这条记录不代表后续初始化已经成功。客户端在服务监听成功时记录一次包版本。它们均使用既有日志通道。C 主程序自身的版本仍由主程序维护；同一主程序可以依次启动多次 camctl，每次 Python 进程都记录自己的版本。

版本记录不进入 `run`、`submit` 的结果 JSON、通知管道或 `describe` 的能力 JSON。它是运维诊断信息，不产生计划、动作、报告或数据库历史变化。

## 普通离线更新 Python 包

首次安装使用部署包的 `install-host.py`；已有部署由 camctl 自身的维护能力更新，C 主程序通过 `camctl_host.h` 的更新接口调用。更新实现和稳定恢复引导由 camctl wheel 提供，Python 专用更新包交付 wheel、离线依赖和元数据。组件归属、稳定入口、主程序生命周期及公共结果边界由[更新接入规格](software-update-interface.md)定义；部署工具调用组件能力。首次安装交付仍由[部署 skill](../../.agents/skills/camctl-real-device-deploy/SKILL.md)和[完整部署包契约](../../.agents/skills/camctl-real-device-deploy/references/packaging.md)维护。

主程序通过更新接口停止接收新任务并等待本模块的普通工作与原有子进程结束；其他独立实例仍由操作者停止。更新器先串行化同一环境的更新，再取得原状态库的稳定会话锁和接纳锁，持有到更新可靠完成或回滚结束。更新器不终止其他实例；本模块的恢复和普通运行重建由 C 接入模块内部完成。

离线更新面向已有的 Linux Python 3.11 虚拟环境和 uv。构建机联网取得两种 Linux 目标架构的锁定依赖 wheel，并随包记录及校验。目标机安装使用本地 wheel，禁止访问软件源；不能把构建机的原生依赖误当作 ARM64 安装物。新建部署在缺少 Python 解释器或其他组件工具时仍须满足首次部署前提，不能把 Python 包离线更新解释为整机所有依赖均可离线安装。

更新保持原虚拟环境绝对路径。交付物、原环境与配置校验通过后，先可靠保存完整 Python 环境和 SQLite 一致备份，再保存修改意图并安装配套依赖及 camctl wheel。备份保留旧版本、原配置身份、数据库身份和格式、目录绑定，以及恢复入口所需信息；日志和收据是更新证据，不能替代这些可恢复内容。

更新器统一核对保留对象与实际会写入、搬移、删除的路径。能力同步目标必须独立于原配置、状态库、稳定锁、媒体与交接目录、虚拟环境及更新控制材料。修改前同时核对规范路径与已有文件身份，拒绝会覆盖、搬移、删除这些对象的路径重叠或文件别名；配置、状态库、稳定锁和媒体也不能落入更新时整体恢复或清理的环境及临时目录。发布、备份和探针的临时文件同样遵守此规则。只有具备本次创建意图和归属依据的临时对象可以继续写入或清理，不能把已有对象当作临时材料。路径身份无法核实时明确失败。

新版在独立数据库副本上自动执行已登记的迁移步骤，保全历史、进度、预算、对象身份和文件绑定。副本验证通过后才发布到原数据库路径。格式号和迁移步骤由权威登记维护，不从空库重建或重放设备操作。当前 V9 库只验证结构、SQLite 完整性和实际外键关系；后续格式只有在迁移路径已登记且核验通过时才发布。原库、副本和最终发布均须核验，基线范围外、没有路径、未知或无效的数据库明确拒绝。

安装、迁移、发布和最终核验共同构成一次更新。提交前任何阶段失败，更新器自动恢复原 Python 环境和原数据库，并核实恢复结果。能力说明按原配置导出；明确指定同步目标时，将该能力文件一并纳入备份和回滚，客户端数据库和媒体保持原样。原配置不改写，目录绑定不切换，不探测设备或执行业务任务。

全部文件发布结束后统一核验，再同步并提交。环境、数据库及适用能力文件的备份和恢复核验包括内容及所承诺的权限、所有者等元信息，不能仅凭复制调用成功确认恢复。

### 中断恢复与可靠完成

更新器在副作用开始前持久保存恢复记录，并同步相应文件和目录。断电或强制终止后，下一次调用先读取未完成记录，按记录中的原环境和数据库取得锁，再恢复到更新前状态。该路径不能依赖部分更新后的包仍可导入；执行恢复的解释器及入口须在环境恢复期间保持可用。

同一环境的更新资格覆盖更新器启动的安装和迁移子进程。父进程退出不代表这些写入者已经结束；恢复或新更新必须等待它们结束后才可修改原环境，不能与上次仍在运行的写入者并行。

恢复按实际文件、备份清单和数据库身份核实进度，可以处理恢复过程中再次中断。只有软件环境、数据库和适用能力文件全部验证通过，才记录回滚完成并允许开始新的更新。日志、备份及原失败原因保留供排查，不以删除恢复记录解释为恢复成功。

只有安装、迁移和全部核验结束，且完成记录可靠保存后，更新才算成功。已有可靠完成记录时，不因迟到的诊断或输出故障撤销完成结果；没有完成记录时，不根据新版本号或数据库格式猜测更新已经成功。

完成记录写入发生异常时，在持锁状态下读取正式记录：本次仍为更新中则立即回滚；本次完成记录已发布则补足同步以确认完成；无法读取、身份不符或仍无法同步时保留结果未知的责任。修改意图及回滚完成记录也按实际发布结果处理，不仅根据内存标志判断。非法或不完整的恢复记录不能解释为未修改或回滚成功。

| 当前阶段或结果 | 更新器行为 |
| --- | --- |
| 摘要、文件集合、平台、原配置或状态库前提不成立 | 在修改环境前失败，保持原部署并报告事实。 |
| 无法取得更新锁或原数据库锁 | 不开始修改；保留锁冲突或系统错误诊断。 |
| 备份或恢复记录尚未可靠完成 | 不开始安装；中断后按尚无修改意图处理。 |
| 安装、自动迁移、发布或提交前核验失败 | 自动恢复原 Python 环境、数据库及适用能力文件；分别记录原失败和回滚结果。 |
| 上次更新中断且没有可靠完成记录 | 先自动恢复上次更新，验证后才允许本次更新。 |
| 回滚失败或结果尚不能核实 | 保留恢复责任，阻止新更新；后续入口继续恢复，不能报告恢复成功。 |
| 全部核验和完成记录可靠保存 | 确认本次安装提交，由 C 接入模块内部建立普通运行周期。 |

指定同一版本重装或显式选择旧交付物，仍以该包的摘要及其实际迁移能力为准。数据库没有受支持的降级路径时不能只安装旧软件并改写格式号。自动回滚只恢复本次未完成更新的完整备份，不用于撤销更新成功后新发生的业务事实。故障范围及普通启动恢复要求见下文[无人值守保障](#无人值守保障与验证范围)。


## 强制重建

更新包的 `RELEASE.json` 保存 `update` 元数据。`update.force` 必须为布尔值；普通包为 `false`，强制包为 `true`。强制包同时保存 `update.config_toml`，内容是完整的新配置 TOML 文本。元数据沿同一文件集合和 `SHA256SUMS` 校验，不增加另一份不受包摘要保护的配置。构建器与更新器共用组件内的元数据定义。缺省 `update` 或缺省 `force` 时采用普通模式；非布尔值拒绝。`force=true` 必须携带 TOML 字符串；`force=false` 时不得携带 `config_toml`，避免普通包意外替换配置。空配置文本是否有效由正式配置加载规则判断。

强制重建在同一部署位置替换配置、建立干净 Python 环境和新状态库，清空原 camctl 本地工作及待领取数据。新配置是整体替换，不与旧配置合并；未写出的可选项仍使用正式配置默认值。强制模式不要求旧状态库完整或存在迁移路径，也不通过迁移旧数据建立新库。

| 对象 | 强制重建成功时的结果 | 失败或未可靠提交时的恢复 |
| --- | --- | --- |
| 原虚拟环境 | 建立干净环境并从离线包安装；不遗留原环境的额外包和文件。 | 恢复原环境的全部内容、链接关系及所承诺元信息。 |
| 配置文件 | 将包内完整配置发布到实例原配置来源，不合并旧项。 | 恢复原正文及元信息；原来不存在时恢复不存在的事实。 |
| 状态库及其 WAL、SHM | 建立符合当前格式的新状态库，使用新的实例身份。 | 原文件以不依赖旧库可解析的一致停机快照完整备份，恢复其原内容及存在事实。 |
| `staging` | 重建为空的 camctl 工作区，再建立正式初始化所需内容。 | 完整恢复原目录和媒体、半成品、文件及目录元信息。 |
| `ready` | 重建为空的待领取目录。 | 完整恢复更新前未领取文件。 |
| `processing` | 保留原目录及其主程序所有权。 | 不以回滚覆盖、删除或重放其中的文件。 |
| 显式指定的能力同步文件 | 由新配置导出并发布。 | 恢复原文件或原来不存在的事实。 |

普通日志、更新日志与收据、稳定维护入口、恢复材料、host、客户端数据库及相机存储保留。重置逐项操作已登记对象，不能删除整个部署根目录。目录内部的符号链接不得导致清理或恢复越过登记边界。

### 路径定位与配置替换

配置文件、状态库及交接目录可以位于部署根目录之外，不能根据目录名推断清空对象。发布维护入口时记录由有效配置和初始化结果得到的数据库及 `staging`、`ready`、`processing` 部署绑定，供强制重建定位原对象。该部署布局发布后保持不可变，是既有绑定的冻结事实，不是另一组手工维护的路径默认值。完整清单仅保存在一个组件记录；稳定入口和初始化使用同一记录，其他定位材料只引用该记录。

已登记维护部署的初始化，在写入数据库之前拒绝改变状态库及上述目录绑定。同绑定重复初始化照常执行，未登记维护的部署继续使用原初始化规则。检查覆盖使用同一部署环境改变 `state_db` 的入口，不能只在请求的新数据库旁寻找旧登记而漏检。此次自动更新不执行部署路径重绑定；不能先提交新数据库绑定再事后刷新维护记录。

强制包的新配置必须采用同一数据库及交接目录绑定，`processing` 路径和目录身份保持。配置来源继续使用实例原显式或默认来源。该模式重置部署内容，不迁移部署路径；新配置与绑定不一致时在清空前拒绝。C 保存的 `ready_path`、`processing_path`、配置来源与新配置保持一致，内部重新运行继续使用这些路径。

强制重建的准备和恢复不依赖旧数据库可打开、旧虚拟环境可导入或旧配置正文可解析。使用环境外的维护程序、已保存的部署绑定及包内新配置定位并核验范围。旧对象不存在时保存不存在的事实；读取或备份错误不能当作不存在。

### 完整备份、重建与中断恢复

强制模式先取得部署更新资格以及原数据库的稳定会话锁和接纳锁。只在所有实际写入者结束后保存旧对象。配置、环境、数据库及其边文件、staging、ready 和适用能力文件全部完成备份、内容及元信息核验和必要同步后，才可靠保存修改意图；任何一项准备失败均不能开始清空。备份与原对象不共享可写数据。

修改意图之后，重新建立环境、发布新配置、建立新状态库、清空工作目录、导出能力和最终核验属于同一事务。新库和目录使用正式初始化能力准备，不在已经持锁的原数据库上重复竞争同一把锁，也不维护另一份建表定义。全部对象核验、同步和提交记录可靠保存后才认定强制更新成功。

恢复按冻结清单处理各个旧对象及其原有存在事实，不从新配置或部分恢复的数据库推导旧路径。原备份保留到恢复全部核实并可靠记录完成；恢复使用可重复准备及发布的对象，任意一次中断后可再次从完整备份恢复。恢复配置后再核对旧配置身份，不能要求当前已被替换的配置仍是旧正文。原数据库本来无效时，恢复只确认原数据已完整还原，不宣称已修复原有业务故障。

## 无人值守保障与验证范围

更新、强制重建和回滚支持进程强制终止及主机断电后的恢复，包括恢复过程再次中断。介质损坏和备份丢失不在故障范围内。基础解释器、稳定入口与备份可用，文件系统遵守文件及目录同步语义，且不再持续中断时，后续普通启动先自动完成未提交事务的回滚，再运行已核实的部署。主程序不用选择恢复动作或解释维护结果。

更新失败并核实恢复原部署后，C 模块自动建立普通运行周期；原部署本来具有的配置或数据错误不会被普通回滚修复，强制包可以用新配置和空库替换这些对象。无法取得仍被实际写入者持有的资格、恢复操作尚未完成或结果未知时，组件保留责任，禁止启动部分安装环境。公开调用只返回成功或失败，具体事实按[更新诊断交付](software-update-interface.md#更新诊断直接交付)进入 `processing`。

软件验证分别记录隔离单元、真实容器部署和目标硬件物理断电结果。容器内强杀可以验证中断后的路由、恢复与再次启动，不能证明目标存储在物理断电时的实际同步效果。验证结论以实际执行的场景与证据为准，不以设计说明代替已验证结果。
