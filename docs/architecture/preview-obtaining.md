# 预览文件与自动取回

[设计总览](README.md) · [产物模型](outputs.md) · [取回](obtaining-outputs.md) · [清理](output-cleanup.md)

本专题定义预览支持、文件选择、自动取回的责任、调度和取消。客户端开关与展示由[自动预览获取](../client/automatic-previews.md)定义。本文描述目标行为；文末列出协议字段及设备接入尚需落实的边界。

## 能力与产物身份

照片对应预览图片，录像对应低分辨率预览视频。设备是否支持预览，由驱动在“设备 → 拍摄动作 → 参数类型”的参数类型上明确声明；同一拍摄能力下的不同参数类型可以不同。声明从驱动权威定义导出并供主机受理使用，不依据设备名称、文件大小或扩展名猜测。

预览是具有独立 `output_id` 的正式产物，驱动提供对应原文件的明确关联及文件写入完成依据。文件类别和用途分别表达：视频既可能是原片、修复成品，也可能是预览。原片、预览与修复成品身份独立，登记后的内容保持不变。预览遵守正式产物保留、交付校验及显式清理规则。

相机预览关联原片；主机修复不额外生成修复版预览。预览与修复结果可能不同，客户端须准确展示关联。一个动作有多个原文件时，按每个原文件的关联分别判断，不因其中一个文件存在修复成品而排除其他文件。

## 自动取回的责任

客户端将开启的自动预览意图展开为明确的 `obtain_action_outputs` 动作。每个符合条件的拍摄动作最多对应一个自动预览取回动作，显式保存自动用途，并通过本计划内的 `source.action_name` 引用该拍摄。它只选择预览用途，不能混入普通或精确 ID 筛选。普通手动预览取回不具有自动用途及取消联动。

自动取回沿用来源拍摄的 `scheduled_at`，不属于动作组；到时间后等待来源文件及设备读取条件。每个取回独立准备和交付，不等待其他拍摄动作。计划本身不另建隐式交付责任；交付属于发起它的取回动作，来源仍属于拍摄动作。动作失败、等待及完成沿用公共状态模型；计划按全部动作汇总 `pending`、`running`、`completed`，不另加计划失败状态。

| 主机首次受理条件 | 结果 |
| --- | --- |
| 自动用途、来源关联及参数组合合法，来源参数类型明确支持预览 | 保存固定来源关联及受理时的能力依据，继续其他动作校验 |
| 来源合法，但参数类型明确不支持预览 | 仅对应取回动作受理失败；拍摄按自身条件处理 |
| 来源缺失、不是拍摄动作、跨计划自动关联或组合非法 | 对应取回动作受理失败，保留输入与原因 |
| 同一拍摄对应多个自动预览取回 | 按重复关联拒绝冲突的自动用途；具体受理失败归属须在协议组合校验中统一确定，不按数组顺序任意保留一个 |
| 能力定义无法可靠读取或解释 | 配置或内部错误，不冒充不支持预览 |

原始输入、有效关联及失败诊断在计划受理事务中保存；同一请求重送、执行及恢复沿用已保存事实。客户端能力重载不改写已受理任务。其他拍摄参数错误不被预览支持声明掩盖，来源失败时继续按下面的实际产物规则判断。

## 产物选择与失败

普通取回未指定 `output_ids` 时排除预览；每份原片有已登记修复成品时只选择对应修复成品，否则选择原文件。已经登记但后来被清理、不可读取的修复成品仍是所选目标，按实际错误处理，不退回原片。显式 `output_ids` 精确选择，可以主动取回原片或预览。

预览取回按以下顺序判定，取消与已有终态优先。预览必须真实登记且归属与写入完成可信；仅能力声明支持不代表本次已经生成。

| 事实分区 | 预览取回处理 |
| --- | --- |
| 来源拍摄或适用修复尚未结束，最终产物尚未确定 | 等待，不把暂时没有文件解释为失败 |
| 来源及产物已确定，可靠确认没有预览 | 取回失败；即使有修复成品也不自动传该成品 |
| 存在有效预览，不需要修复或修复已失败 | 选择预览 |
| 存在有效预览及对应修复成品，完整大小已确定，修复成品大于预览 | 选择预览 |
| 存在有效预览及对应修复成品，完整大小已确定，修复成品小于或等于预览 | 选择修复成品 |
| 所需关联、修复结果、完整大小或文件状态无法可靠确认 | 按实际错误与恢复规则处理，不猜测选择或冒充无产物 |

大小比较按完整字节数，不比较传输进度或预估值；相等时选择修复成品。选择修复成品时，delivery 引用它真实的 `output_id`，不改变其产物类别或归属。选择持久化后，重试和恢复使用原选择与交付身份。所选文件之后被清理或读取失败时按既有资格和错误规则处理，不重新选择较方便的文件。

拍摄自行失败仍可留下有效预览，取回继续按实际文件处理。用户取消拍摄则按取消联动处理；用户后来用新请求手动取回已保留文件不受原取消联动影响。取回失败不改变拍摄结果，其他拍摄继续执行。多个来源文件按既有逐项失败与发布条件汇总。

自动预览已经交付修复成品后，新的普通取回仍创建独立交付，不因历史发布而省略：主机发布不证明客户端已收到。客户端根据本地核验事实提示成品已收到。

## 读取调度

预览优先及时获取，拍摄优先于尚未开始的冲突读取。当前相机支持拍摄期间读取其他已经完成的文件；实际驱动接入须验证并行控制与读取契约。不同设备按各自兼容性判断。

| 设备兼容性及读取阶段 | 行为 |
| --- | --- |
| 拍摄与读取兼容 | 可以并行，控制操作仍须获得执行机会 |
| 不兼容，尚未开始读取，拍摄已到执行时间 | 先处理拍摄，预览等待 |
| 不兼容，一份预览文件的一次读取尝试已经开始 | 允许该次尝试结束，再让已到时间的拍摄执行；不因拍摄主动打断本次读取 |
| 本次读取失败、正在等待重试 | 拍摄先行；重试不是已开始读取的延续，不要求耗尽读取重试才让路 |
| 全部源字节已读完，仅剩主机校验和发布 | 不再占用相机读取通道，继续独立处理 |

一次读取指一份文件的一次完整读取尝试，不是一个数据块，也不是包含所有重试的整个取回。失败、无数据超时、取消及未知结果仍按既有规则收场。等待拍摄不计为读取失败，也不消耗失败重试预算；对其他文件的原拷贝机会保留继续有效。

对不支持并行的设备，允许当前一次读取造成拍摄等待，拍摄仍受原启动窗口限制。预览通常较小不构成耗时保证，不以预估文件小绕过超时、窗口或设备兼容校验。

## 取消联动

主机根据持久化的自动用途及来源关联扩大本次取消处理集合，客户端无需另发取消请求。对同一取回去重处理，重试与恢复沿用本次取消事实。

| 取消目标 | 处理范围 |
| --- | --- |
| 拍摄动作 | 该拍摄及其自动预览取回 |
| 拍摄所在组 | 组成员及其中拍摄关联的自动预览取回；取回本身仍不属于组 |
| 整个计划 | 计划内动作，包括自动预览取回 |
| 单个自动预览取回 | 仅取回，不取消来源拍摄 |

拍摄已终态仍须处理关联取回及可撤回交付，已有拍摄和取回终态不改写。取消结果逐项包含实际处理的关联取回，等待适用的有限收场完成后汇总；失败不抹去其他项已完成的处理。`ready` 中交付按既有规则撤回，`processing` 中不可撤回。已登记的正式源产物继续保留，取消不授权清理。

## 取回与清理的衔接

等待来源或修复不提前取得未知产物的读取资格。来源集合、产物选择、读取资格和删除限制是不同事实：来源结束后可靠保存选择，再按统一调度和同一事务内的资格判定协调清理。自动用途不授予绕过既有删除限制的特权。

按计划或动作清理等待来源拍摄及其产物处理结束，不等待取回、清理、报告等动作终态，也不等待整个计划完成。选择清理集合后沿用已有取回优先：已获资格者保留保护；未获资格者遇有效删除限制按取回失败处理。旧取回副本可靠准备完成后逐项解除读取依赖，不必等待整组发布或远端接收。因此清理不会等待一个因删除限制而永远不能取得资格的取回。

## 验收与协议落实边界

验收须覆盖参数类型支持差异、重复自动关联、能力过期、等待来源与修复、无预览、修复失败、大小小于／等于／大于、大小未知、选择保存中断、取消各入口、非并行读取与重试让路，以及清理在取得读取资格前后的先后顺序。按多原文件分别验证关联，不因某一份存在修复成品漏取其他文件。

本文及取回、清理专题确定行为契约；以下机器表示须在实现前统一落实到根 `protocol` 及样例，不由客户端与主机分别发明：参数类型预览支持字段及缺省语义、产物预览类别与原文件关联、预览筛选与自动用途标记、当前计划和指定计划来源组合、报告中的固定来源与选择依据、对应错误码和等待结果，以及重复自动关联时具体哪些冲突动作受理失败。当前 Schema 尚未表达这些扩展，不能据本文直接声称现有实现已经支持。

真实驱动还须明确多文件预览配对、预览完整大小与写入完成证据。若同一原片可能有多个修复成品或多个可替代预览，须先确定唯一选择规则；不能依赖目录或数据库返回顺序。这些多候选语义尚未确定，不作为已确认设备行为。
