# 取消计划与动作

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

`cancel_task` 用于取消一个已知计划或动作。本页定义目标如何指定、什么时候算取消处理结束；具体设备停止和文件处理仍按目标动作的规则执行。先读[计划与动作身份](plan-acceptance.md#名称和实例-id)。

**阅读提示：** 例如取消正在执行的录像 A：camctl 先保存取消事实，再进行本次允许的有限停止与清理处理，最后给出取消动作结果。取消生效、设备确实停止和文件清理完成分别判断，完整分类见下文。

设备任务先按[设备任务的取消资格](#设备任务的取消资格)判断是否允许取消，再保存取消事实。单张拍摄和延时摄影取消生效后，停止继续拍摄，保留已经拍完、确认归属且写入完成的文件；具体分区见[取消、失败与文件保留](camera-capture.md#取消失败与文件保留)。录像仍遵守其自身取消规则。取消动作的成功只证明所需有限处理完成，不将目标拍摄改为成功。

实现协程若正在等待自身重要日志入队，遵守[日志等待期间的取消与退出](../camctl/logging-runtime.md#重要日志等待期间的取消与退出)：保留待投递记录可延后协程最终结束，但必要的取消事实保存、设备停止和适用清理不能以日志接纳为前提。日志是否入队、协程是否结束与设备实际停止分别确认，不以日志处理结果替代本页的业务完成条件。

## 取消目标寻址

### 取消参数

`cancel_task.params` 为必填对象，只包含必填对象 `target`。`target` 恰好采用下表的一种字段组合；标识与组名遵守[基本值类型](plan-input.md#输入文件与基本值类型)。

| `params.target` 字段组合 | 目标 |
| --- | --- |
| `request_id` | 该请求首次受理的整个计划 |
| `plan_instance_id` | 指定计划实例 |
| `action_instance_id` | 指定动作实例 |
| `plan_instance_id` 与 `group` | 指定计划中该组的动作集合 |

目标对象为空、组合不在表中、含额外字段或字段值非法时，仅该取消动作在受理时登记为 `failed`。合法目标是否存在在实际执行时查询；同名计划或动作不能替代实例身份。组目标最终取消其成员动作，仍遵守本节的目标范围。

例如取消尚未获得实例 ID 的原请求，动作参数为：

```json
{"target":{"request_id":"1001"}}
```

### 支持的目标范围

上表四种方式分别按请求、计划实例、动作实例或指定计划中的组确定目标。

目标引用的字段格式及组合在首次受理时校验。自身参数不合法时，`cancel_task` 按公共规则登记为 `failed`，不标记目标取消，也不发出停止或撤回操作；格式合法的目标是否存在仍在执行时查询。

寻址结果限定本次取消的范围：计划级目标对应该计划内的动作，动作级目标对应指定动作，group 目标对应指定计划内该组的动作；其中拍摄动作另按明确关联纳入自动预览取回。不会因设备共用、时钟异常或目标查询失败扩展到其他计划和动作；执行及设备收场遵守[普通动作取消](scheduling-execution.md#普通动作取消)。

取回动作不属于任何 group；取消某组不联动普通手动取回，但联动组内拍摄对应的自动预览取回。普通手动取回的取消须指定该取回动作，或取消包含它的整个计划；仍有效的取回按来源动作的最终状态及正式产物继续处理。

### 自动预览取回的取消关联

寻址得到拍摄动作后，camctl 根据已保存关联确定自动预览候选。拍摄允许取消或已经终态时，将关联取回加入实际处理集合；拍摄因不支持取消而被拒绝时，不通过该拍摄联动取消取回。动作、组、整计划入口均适用；取回不因此加入拍摄的组。取回本身属于直接寻址范围时仍独立处理，例如取消整个计划。直接取消自动取回不反向取消拍摄，手动取回不受联动。拍摄已终态仍处理关联取回及可撤回交付，终态本身不变。

本次集合去重保存，逐项结果包含实际处理的自动取回，有限处理和失败汇总沿用本页规则。完整决策表见[取消联动](preview-obtaining.md#取消联动)。

### 目标集合不得包含取消动作自身

取消动作执行时先解析直接目标及其自动预览候选关联，去重后检查完整寻址范围是否包含本次取消动作自身。该检查必须在向任何目标保存取消事实或发出停止、撤回等操作之前完成。检查通过后，按取消资格和联动规则固定实际处理集合；拒绝取消的直接目标仍须保留失败明细，不能因不触发预览联动而从结果中消失。

| 目标解析与自身包含情况 | 处理 |
| --- | --- |
| 目标可靠存在，完整集合不包含本次取消动作 | 按正常取消流程处理 |
| 完整集合包含本次取消动作，包括直接指向自身、所属计划或包含自身的组 | 本次取消动作以 `failed` 结束，明确说明目标集合包含自身；不取消集合中的任何动作，也不执行停止或撤回 |
| 目标可靠确认不存在 | 按 `target_not_found` 处理 |
| 无法可靠确定目标集合或自身是否在其中 | 按查询、持久化及恢复错误处理，不猜测集合有效或先取消其中一部分 |

已有终态或本次取消动作自身已经被取消时，仍优先遵守自身状态规则。该限制适用于所有目标寻址方式；通过 `request_id` 取消原计划仍由另一个计划承载取消动作。目标包含自身是执行时的目标语义错误，不属于目标不存在或逐项收场失败；使用[错误登记](../../protocol/errors/workflow-codes.json)中的 `cancel_self_target`，详情关联发起动作自身。同一请求重送保留原结果。

### request_id 取消

客户端尚未收到状态报告、还不知道 `plan_instance_id` 时，可以使用原计划的 `request_id` 取消整个计划。承载该 `cancel_task` 的计划自身使用新的 `request_id`；原计划正文保持不变，不能通过修改原计划表达取消。

### 只取消已知计划

取消动作在实际执行时查询目标。目标不存在时，以 `target_not_found` 结束本次取消；该结果只针对执行时已知的目标，目标以后首次提交仍可正常受理。

同一个取消请求 ID 的重试复用原取消结果。如果目标后来出现，且客户端仍希望取消，应使用新的取消请求 ID 再次提交取消。

### 设备任务的取消资格

驱动为任务声明停止能力。设备任务尚未启动时可以取消；任务已经启动且尚未终态时，只有驱动声明支持停止才允许取消。停止能力可以由设备提供的专用接口或其他具有明确终止语义的操作实现，结束本地协程、断开通信和终止本地命令进程本身不构成设备停止能力。

延时摄影使用首次受理时保存的 [stop_supported](../camctl/database/execution-definitions.md#延时摄影执行定义的停止能力) 判断原任务的停止能力，不因恢复时的新默认值改变原契约。实际停止结果由执行记录表达，不能从能力声明推导。

在可靠读取目标及原执行记录后，按下表顺序判断。已有取消事实继续有效；数据库结果未知先对账，不撤销已经生效的取消，也不把记录读取失败解释为设备没有启动。

| 目标事实与能力 | 本次处理 |
| --- | --- |
| 目标已经终态 | 保持终态，处理仍适用的关联取回或交付责任 |
| 目标取消已经生效 | 继续原取消处理及累计预算，不重复施加取消 |
| 能够可靠确认任务尚未启动，且没有可能生效的在途启动调用 | 允许取消，阻止后续启动，不要求设备具备停止能力 |
| 任务已经启动且尚未终态，驱动不支持停止 | 本次逐项取消失败，保存不支持取消的原因；不修改目标的取消标记，不停止原任务的等待、产物核实或正常结果登记 |
| 启动调用仍在执行或发送结果未知，无法排除任务已经启动，驱动不支持停止 | 本次逐项取消失败，保留原执行事实与未知状态；原任务继续其执行或恢复流程，不能按未启动任务取消 |
| 任务已经启动或可能启动，驱动支持停止 | 允许取消，按原归属、停止和有限收场规则处理；能力声明不代替本次停止成功或设备归属证明 |

取消资格判断与启动派发必须在同一目标的执行协调边界内保持一致。取消先可靠生效时，不能再发出启动命令；启动先进入可能产生设备效果的阶段时，取消按启动中或已启动分支判断，不能沿用此前读到的未启动状态。

不支持取消是本次请求对该目标的失败，不是目标任务的执行失败。该目标继续原任务及其设备、输出范围占用，随后按正常结果结束；取消动作不等待该设备任务自然结束。停止接口存在但调用失败则属于取消已经生效后的收场失败，两种情况分别保存和报告。

计划、组及请求 ID 入口按目标逐项判断。一项不支持取消不阻止其他目标的适用处理，也不撤销其他目标已生效的取消；本次所有适用处理结束后，按失败项汇总。重复请求和重启沿用已保存的拒绝结果，不在设备后来结束时把旧的取消失败改写为成功。

### 取消动作的完成时机

`cancel_task` 在本次取消所需的有限处理结束、结果可靠保存后给出最终结果。保存目标的取消标记只表示取消已经生效到执行控制，不表示停止录像、结束读取、撤回文件或适用清理已经完成。

执行时固定本次已知目标，并保存逐动作的取消处理记录。目标未终态且允许取消时，保存取消事实并阻止其继续普通执行或重试，再按该动作的规则收场；拒绝取消的目标继续原流程。目标已终态时保持原终态，只处理仍适用的独立责任，例如撤回该取回的 `ready` 文件。设备调用沿用原超时与恢复规则，停止次数保持原预算。本地文件操作等待实际结果，遵守[完成与故障边界](../camctl/file-runtime.md#本地文件操作的完成与故障边界)；本次有限处理约束工作范围和尝试次数，底层持续失去响应时的处置属于部署范围。

本次取消动作尚未被取消且尚未进入终态时，按下表判断；目标与进度无法可靠读取或保存时，优先按会话错误处理：

| 本次目标与处理进度 | `cancel_task` 的结果 |
| --- | --- |
| 格式合法，但执行时目标不存在 | `failed`，原因为 `target_not_found`；不留下针对未来目标的取消责任 |
| 目标存在，至少一项所需停止、读取结束、撤回或适用清理仍在有限处理中 | 保持 `running`，报告逐项进度；不能仅凭取消标记提前成功 |
| 没有拒绝或失败项，所有目标的本次适用处理均已确认成功完成，或可靠确认没有适用处理 | `succeeded`，保存逐项结果；不要求已经终态的目标变为 `canceled` |
| 所有目标的本次处理均已结束，至少一项拒绝取消、明确失败或仍无法确认完成 | `failed`，保存拒绝、失败及未知原因；已生效取消保持，拒绝取消的目标继续原流程 |
| 目标、进度或结果无法可靠读取或保存 | 按会话错误处理，不能猜测取消成功或覆盖已提交结果 |

本次处理范围服从现有所有权与动作能力。已确认进入 `processing` 或已由主程序处理完的 delivery 不属于可撤回文件：报告为不可撤回，不等待主程序，也不把它写成撤回成功；其他适用处理全部完成时，本次取消仍可成功。文件位置或撤回结果未知不等于已经越过撤回边界，须按文件交接规则有限核实，结束后仍未确认则按失败表达。

因逐项取消被拒绝或有限处理未完成而整体失败时，动作错误使用 `cancel_items_failed`，阶段为 `execution`，`details` 为空对象；具体失败或未知原因由 `result.items` 给出。不因已经确定一项失败就放弃其他项仍需进行的本次有限处理。

例如取消正在录像的 A：先保存取消标记，再按原有限预算停止和处理适用的废弃内容。全部所需处理成功后，取消动作才成功；停止尝试耗尽仍未确认停止时，取消动作失败，A 按取消规则结束，报告继续保留可能仍在录像的设备事实。该失败不授权 A 再次启动录像。

等待的是本次有限取消处理，不是主程序传输、客户端收件，或设备永远恢复到正常状态。重启恢复同一取消记录及原流程的剩余预算，保留已完成项；同一请求重送不重新执行完成项。多个取消入口触达同一设备活动时，复用已有补偿流程，遵守[设备活动登记与停止处理](scheduling-execution.md#设备活动登记与停止处理)。取消动作自身被取消时，按[取消动作自身被取消](#取消动作自身被取消)处理；已有终态保持不变。

对于显式同步报告动作，未执行取消、运行中取消及成功后取消对同步责任的影响见[同步动作的取消与失败](status-sync.md#取消与失败)。取消结果与同步责任结束事实按对应事务规则保存；不因寻址到已成功的报告动作而撤销待确认责任。

对于 `delete_action_outputs`，按[清理取消](output-cleanup.md#清理取消)逐个产物停止尚未发生的删除，并跟踪已经发出的删除调用。一个产物已删除，不阻止取消其他产物的删除，也不单独使本次取消失败。取消处理完成后，目标清理动作及其逐项删除事实分别报告；仍在执行的调用、结果保存失败或无法确认的收场结果继续按本节规则处理。

报告结构见[取消结果](report-format.md#取消)。验收覆盖标记已保存但停止尚未结束、停止成功、预算耗尽、多个目标部分失败、已终态取回的撤回、文件已在 `processing`、处理中重启及状态保存失败；确认最终结果与所需处理一致，且不扩大目标范围或重置预算。

验收按取消资格表覆盖不支持停止任务的未启动、启动中、已启动和终态；覆盖支持停止但实际停止失败，确认其与拒绝取消的目标状态不同。组合动作、组、计划及请求 ID 入口验证逐项失败汇总；验证被拒绝任务继续等待及登记产物，不延长取消动作的等待范围。验证取消与启动竞争、重启和同请求重送保持判定结果，以及自动预览只通过有效联动或直接目标范围取消。设备操作使用受真实契约约束的测试替身。

## 取消动作自身被取消

取消动作负责施加取消并等待本次处理结果。一旦目标的取消已经可靠生效，必要停止和清理由目标所属流程负责，不依赖发起取消的动作继续运行或等待。取消一个 `cancel_task` 不撤销它已经产生的效果，也不使其目标恢复普通执行。

例如 C1 取消正在录像的 A：camctl 保存 A 的取消事实后，A 的停止流程已经开始，C1 等待结果。此时 C2 取消 C1，C1 停止尚未生效的工作并结束对 A 的结果等待；A 仍按原预算完成停止及适用文件处理。C1 被取消不授权中止 A 的必要收场，也不创建另一套停止流程。

### 进度与取消生效顺序

先核实已经提交的状态及尚未确认的数据库操作，再按下表处理。取消生效与最终结果以可靠保存的事实区分，不能只按协程是否仍在等待判断。

| C1 的已知进度与自身取消情况 | 处理 |
| --- | --- |
| C1 已可靠保存终态 | 保留原终态，不重新取消或重开其处理 |
| C1 自身取消已生效，尚未让任何目标的取消生效 | 不再向目标施加取消；完成自身必要收场后，C1 以 `canceled` 结束 |
| C1 自身取消已生效，部分目标取消已生效，其他目标尚未处理 | 已生效目标继续必要收场；不再向剩余目标新增取消，C1 完成自身收场后以 `canceled` 结束 |
| C1 自身取消已生效，其目标取消已生效且仍在停止、撤回或清理 | 目标所属流程继续处理，C1 不再等待这些目标完成；完成自身收场后以 `canceled` 结束 |
| 目标处理已完成，C1 尚未保存最终结果，而 C1 自身取消先被可靠保存 | 保留目标实际结果，C1 以 `canceled` 结束，不由目标成功覆盖自身取消 |
| 目标取消事务、C1 最终结果或自身取消的保存结果尚未确认 | 先按事务恢复规则核实实际结果，再归入对应分支；不将取消数据库等待解释为事务未提交 |

C1 的自身收场包括跟踪已经提交的数据库操作结果，以及按既有规则处理它自身尚未完成的重要日志投递等责任。停止等待目标结果，不等于立即丢弃自身尚未确认的操作。事务与历史须能区分哪些目标已经取消、哪些目标尚未受影响；具体字段和接口由实施设计落实。

### 后一个取消动作的等待范围

C2 按自身寻址结果及明确的自动预览关联确定目标，不沿 C1 曾经取消过的对象递归扩大范围。

| C2 的目标范围 | C2 等待的工作 |
| --- | --- |
| 包含 C1，但不包含 A | 等待 C1 自身的取消处理结束，不通过 C1 间接等待 A；A 的必要收场独立继续 |
| 同时包含 C1 和 A | 分别按 C1 和 A 的规则等待本次适用处理；A 复用已有收场流程及剩余预算，不重复创建 |
| 目标或处理结果无法可靠确认 | 按取消与会话错误规则处理，不猜测 C2 成功，也不擅自扩大范围 |

因此 C1 为 `canceled`、C2 为 `succeeded`、A 的停止仍在进行可以同时成立：C2 只取消 C1 时，其成功不证明 A 已停止。C1、C2 的结果及 A 的实际进度分别报告，已有取消事实与已完成处理不能因等待结束而被删除或伪装为未执行。

### 恢复与验收

目标的取消事实及必要收场进度必须独立于发起取消动作的等待状态持久保存。重启后继续原有未完成收场，保留已有结果与剩余预算；即使 C1 已经 `canceled`，也不能漏掉 A 的停止、恢复 A 的普通执行或重置重试次数。这个责任边界同样适用于取回读写停止、交付撤回及清理动作取消，不只适用于设备上的持续录像。必要收场仍参与原有会话完成判断，不因 C1 或 C2 结束而被遗漏。

单元测试按目标集合检查表、进度表和等待范围表分别推导。覆盖直接指向自身、所属计划、包含自身的组及 `request_id` 入口；验证完整集合包含自身时，其他目标也不产生取消副作用。覆盖未生效、部分生效、全部生效、已终态，以及取消与提交结果未知的组合。取消时保留必要数据库结果确认，不能通过取消等待来隐藏已提交事务。

集成测试组合真实 SQLite、调度及受契约约束的设备和文件协作者，验证 C1 取消 A、C2 取消 C1 后 A 的必要处理仍继续；分别令 C2 的范围包含和不包含 A，验证等待范围与报告结果。用受控同步点在目标取消提交、C1 自身取消提交、目标处理完成及 C1 最终结果提交前后中断，验证恢复不丢失责任、不重复创建流程、不重置预算。多个取消入口触达同一目标时复用原进度；一并覆盖录像停止、读取结束、交付撤回和清理取消，以及时钟异常期间本来允许的取消与有限收场范围。
