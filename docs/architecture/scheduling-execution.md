## 动作状态模型

动作登记时的初始状态由[整份校验与原子受理](plan-acceptance.md#整份校验与原子受理)确定：已支持且通过校验的动作为 `pending`；已支持但自身参数校验失败的动作直接登记为 `failed`，不经过 `running`、不产生执行尝试，也不等待计划时间。该失败属于校验结果，`submit` 可以保存它而不执行设备、文件、取消或显式报告操作。

已登记为 `pending` 的动作按下图转换：

```text
pending
    │
    ├──────────────→ expired
    ├──────────────→ canceled
    │
    ▼
running
    │
    ├──────────────→ succeeded
    ├──────────────→ failed
    ├──────────────→ expired
    └──────────────→ canceled
```

终态：

```text
succeeded
failed
expired
canceled
```

终态本身不迁移。

注意：

> 动作终态与动作留下的设备事实、正式产物、待传 delivery 是不同生命周期。

例如：

```text
camera_record = failed

设备事实：
    possibly_recording = true
```

两者可以同时成立。

## 调度与时间语义

### `scheduled_at`

字段采用[执行计划输入契约中的 UTC 时间字面量](plan-input.md#时间字面量)。格式校验与本节的到期、过期判断分别进行。

`scheduled_at` 表示：

> 主机希望开始处理该动作的绝对 UTC 时间。

对于设备操作，主机应尽可能按时发出真正设备指令；取回、清理等动作到达该时间后，仍须满足各自的业务执行条件。

调度采用尽力按时执行的保证，不承诺固定毫秒级触发精度。主机发令时间与设备真实采集时间分别表达。

字段是否允许省略由动作类型决定，不由动作是否有时效决定：

| 动作类型 | `scheduled_at` 要求 | 省略时的处理 |
| --- | --- | --- |
| 已支持的设备动作、`obtain_action_outputs`、`delete_action_outputs` | 必填 | 首次受理时将该动作登记为 `failed` |
| `report_status`、`cancel_task` | 可省略 | 执行会话取得相应执行资格后立即处理，无须等待指定的计划时间 |

允许省略时，“立即”仍须遵守动作的执行条件及会话模式；`submit` 只受理，不执行这些动作。时钟异常时，未填写时间的 `cancel_task` 按[时钟异常期间的取消](clock-recovery.md#时钟异常期间的取消)处理。显式填写时间时，按该时间调度。首次受理的静态参数错误按请求专题的整份计划校验规则处理；已受理 ID 的重试继续复用原计划。

### 单调钟

墙钟用于确定绝对目标时间。

等待与超时使用 单调钟。

正常情况下：

```text
mono_target =
    monotonic_now
    + (scheduled_at - wall_now)
```

### 时效动作

时效动作通过 `policy.max_delay_ms` 指定允许延后启动的范围。第一版三种拍摄动作均必须显式提供该字段，无缺省值；输入要求与错误处理见[录像参数](camera-recording.md#参数)。

允许执行区间：

```text
scheduled_at
    ↓
    ├──────── max_delay_ms ────────┤
```

定义：

```text
window_end = scheduled_at + max_delay_ms
```

窗口内可以继续尝试。

窗口耗尽后：

- 尚未真正执行成功 → `expired`
- 已执行但最终失败 → `failed`

#### 过期原因

`expired` 是动作终态；为什么过期通过独立结果字段表达，不增加新的动作终态。

第一版至少区分：

```text
expiration_reason = window_missed
expiration_reason = window_exhausted
```

`window_missed` 表示：

> `run` 第一次能够在可信墙钟下对该 action 进行有效窗口判断时，执行窗口已经结束，并且数据库中没有证据证明 camctl 曾经在该执行窗口内观察过它。

`window_exhausted` 表示：

> camctl 曾经在该 action 的有效执行窗口内观察并持久化过这一事实，但直到窗口结束仍未真正执行成功。

`window_exhausted` 不要求已经发出过设备指令，因此下面的结果合法：

```text
status = expired
expiration_reason = window_exhausted
attempts = 0
```

例如 camctl 已经在窗口内知道 action 存在，但目标设备持续 busy、要求 idle 的条件始终不满足，或者调度竞争导致始终没有实际设备尝试，都可以最终得到 `window_exhausted`。

原因分类只依据持久化观察事实；证据不足时，不进一步推断客户端提交晚、主机离线或调度延迟。

#### 窗口内有效观察

只有满足：

```text
scheduled_at <= trusted_wall_now <= window_end
```

才算 action 处于有效执行窗口。

`run` 提前加载了未来 action，并不等于已经观察过它的执行窗口。

第一次在有效窗口内观察到该 action 时，必须先持久化：

```text
first_window_observed_at
```

之后才进入设备条件检查、调度竞争和可能产生设备副作用的执行流程。

只有已经成功持久化的 `first_window_observed_at` 才能作为断电恢复后的事实依据。如果 camctl 恰好在首次内存观察与该字段成功落盘之间断电，恢复后不得根据已经丢失的内存事实推断曾经观察过执行窗口。

目标设备当时是否 ready、idle 或 compatible，不影响“窗口内有效观察”的成立；这些条件影响是否能够执行，不影响 `window_missed / window_exhausted` 的分类依据。

### 无时效动作

无时效动作允许延后；具有 `scheduled_at` 时，该字段表示开始处理的时间，不形成过期截止时间。

设备通信及操作仍有有限超时和重试预算，重试耗尽后失败，不进行断电重启。等待业务条件的规则由对应专题定义，不能把计划执行时间已过去当作通信失败。

取回与清理的无时效类别、时间判定和恢复规则见[取回与清理的执行时间](outputs.md#取回与清理的执行时间)。

### 动作独立

一个动作失败不会级联取消后续动作。

### 新计划发现与内存调度缓存

`run` 使用 SQLite 作为权威持久状态，同时在内存中维护可丢弃、可重建的调度缓存。

新计划通过独立的 `camctl submit` 受理。`run` 使用 `asyncio` 等待，通过周期检查状态库保证新计划发现。

当前目标为：

> `run` 对新提交计划的目标最大感知延迟为 500ms。

这不是硬实时调度保证；系统仍受 Python 事件循环、SQLite 事务、Linux 调度和不可中断设备调用等实际条件约束。

为避免每次轮询扫描 plans/actions，调度器使用[请求受理与会话](protocol-session.md)定义的新计划受理序列。序列名称为：

```text
plan_seq
```

序列的分配与幂等规则由[请求受理与会话](protocol-session.md)的[新计划受理序列](protocol-session.md#新计划受理序列)定义。

状态库能够轻量读取：

```text
latest_plan_seq
```

当前 `run` 在内存中保存：

```text
last_seen_plan_seq
```

正常检查：

```text
latest_plan_seq == last_seen_plan_seq
    → 没有新计划，不扫描 plans/actions

latest_plan_seq > last_seen_plan_seq
    → 增量加载新受理计划
    → 合并进入内存调度器
    → 更新 last_seen_plan_seq
```

`plan_seq` 与 `change_seq` 语义不同：

```text
plan_seq
    = 新计划的受理顺序 / 新计划发现水位

change_seq
    = 业务状态变化顺序 / 状态报告水位
```

不得使用 `change_seq` 代替新计划发现序列，否则 `run` 自己产生的 action/output/delivery 状态变化会造成无意义的调度缓存刷新。

该轻量检查只判断是否需要增量加载计划。受理拒绝等业务变化可以不推进 `plan_seq`，但仍产生报告责任；异步报告维护与退出检查须按各自契约观察这些变化，不能只等待新计划轮询或设备动作结束。

`run` 正常退出前，按[请求受理与会话](protocol-session.md)的[会话接管协议](protocol-session.md#会话接管协议)，在短写事务内重新检查持久化工作并关闭接纳。单次轮询结果和内存缓存都不能替代该检查。设备操作、文件处理及报告生成在交接事务之外完成。

### 唤醒后的统一重新决策

内存调度缓存可以包含当前 `run` 已知的时间驱动工作，例如：

- 通信 `prepare_at`；
- action `scheduled_at`；
- 重试截止时间；
- 超时截止时间；
- `camera_record` 的 停止截止时间；
- 其他运行时产生的有限截止时间。

调度器通过本地配置 `session.wakeup_margin_ms` 在最近业务截止时间之前提前唤醒，默认 **50ms**，取非负整数；设为 0 时关闭提前唤醒。该余量用于新计划检查、合并和调度重算，不允许业务动作提前执行。每个未变化的截止时间最多安排一次提前唤醒；完成检查后等待实际截止时间或新的事件，不能在余量区间反复空转。

无论一次唤醒来源于：

- 周期性新计划检查；
- 某个缓存中的 工作截止时间；
- 某个提前唤醒点；
- 其他内部截止时间；

在依据旧缓存决定下一项实际设备操作之前，都先进行一次轻量的 `latest_plan_seq` 检查。

统一流程：

```text
wake
  ↓
check latest_plan_seq
  ↓
有新计划？
  ├── 否 → 保留当前缓存
  └── 是 → 增量加载并合并新计划
  ↓
重新计算当前最早 work / deadline
  ↓
处理已经 due 的工作，或重新 await
```

因此：

> 定时唤醒只代表调度器获得了一次重新决策机会，不代表唤醒前缓存中的某个 action 已经取得执行权。

提前唤醒后到真正业务截止时间 之间，不进入不可打断的“最终 sleep 模式”。调度器重新回到同一个中央等待循环，并继续同时考虑：

```text
真实业务截止时间
下一次新计划检查时间
其他运行时截止时间
```

如果这段短暂等待期间又有新计划入库，下一次最多 500ms 的计划检查仍然能够打断旧调度决策；醒来后再次检查、合并并重新排序，然后才决定真正执行哪个已到期动作。

涉及同一产物、尚未开始且均已到计划时间的取回与清理，按[延后执行时的取回与清理顺序](outputs.md#延后执行时的取回与清理顺序)处理；正常调度与重启恢复使用相同规则。

同一相机的录像启动选择按[多个待启动录像的选择顺序](camera-recording.md#多个待启动录像的选择顺序)处理。先尊重已开始录像及等待重试的保留关系；没有已有占用或保留时，再从同时具备启动条件的待启动录像中按 `scheduled_at` 从早到晚选择，同一时间按计划受理顺序、同计划原数组顺序选择。

同一相机的文件读取按[多个候选文件的选择顺序](file-copy.md#多个候选文件的选择顺序)处理。先尊重活动拷贝及重试保留，再按所属动作的计划时间、计划受理顺序、原动作数组位置及文件登记顺序选择当前合格候选。取回使用取回动作的时间，内部检查和修复使用所属录像动作的时间；控制操作仍遵守设备兼容性与必要停止要求。

## 通信准备

### 不要求持续在线

CLI：

- 不发送设备心跳；
- 不要求控制通信持续保持连通；
- 不在没有设备操作需求时主动维持连接。

只有需要进行设备操作时，才准备或验证通信。

### `prepare_lead_s`

时效设备动作允许提前准备通信。

```text
prepare_at =
    scheduled_at - prepare_lead_s
```

时序：

```text
prepare_at
    ↓
建立 / 验证通信
    ↓
通信准备完成
    ↓
等待 scheduled_at
    ↓
发送真正业务指令
```

若 `scheduled_at` 到达时通信尚未准备完成：

```text
继续有限尝试
    ↓
仍在 max_delay_ms 窗口内时
通信一旦可用立即执行
```

`prepare_lead_s`：

- 由驱动提供默认值；
- 允许设备本地配置覆盖；
- 执行计划不能覆盖。

它是设备/部署参数，不是业务参数。

### 通信准备的归属

通信准备属于具体设备操作的准备阶段，不作为独立业务动作。

## 设备执行与操作兼容性

框架按目标设备的驱动、拍摄动作类型及参数类型选择参数校验和执行契约，具体见[拍摄能力与参数类型](camera-capabilities.md#拍摄能力与参数类型)。驱动为选定参数类型提供设备操作、完成判定、取消与恢复依据，框架负责公共调度及持久化生命周期；不将所有相机统一成需要主机计时的启动和停止接口。

每台设备由 DeviceActor（设备操作协调器）协调设备操作。

但是：

> 一个长生命周期 action 处于 `running`，不代表它持续独占整个设备。

`camera_record` 在录像期间可以保持 `running`，同时允许其他与录像兼容的设备操作执行。

第一版从同一相机到主机的文件拷贝共用[单文件并发限制](file-copy.md#同一相机的拷贝并发限制)，覆盖取回、异常原片检查及修复输入拷贝。设备操作协调器统一协调这些入口；该限制不将整个设备锁定到文件处理结束，必要停止命令及其他兼容操作仍须获得执行机会。

选择文件前先尊重该相机已有的活动拷贝及[等待重试时保留的拷贝机会](file-copy.md#等待重试时保留拷贝机会)。重试等待期间其他文件不能开始；正常调度和重启恢复都沿用已保存的归属与剩余预算。

驱动需要能够表达某项操作在当前设备状态下：

- 可执行；
- 要求设备 idle；
- 与录像兼容；
- 与录像不兼容；
- 是否独占控制通道；
- 长操作是否会妨碍必要的停止操作。

框架不写死：

```text
取文件一定干扰录像
```

或：

```text
维护操作一定不能并行
```

由设备能力决定。

## 效果登记与补偿

动作对设备造成的持续影响，需要独立保存。例如启动录像后，相机可能在主机断电期间继续录制；动作记录之外还要保存这项持续设备效果及其停止处理进度。

例如录像启动成功：

```text
recording effect
    registered
```

效果收场：

```text
registered
    ↓
compensating
    ├── compensated
    └── compensation_failed
```

“只补偿一次”的准确含义为：

> 原动作对同一设备效果只创建一个持久化补偿流程。

不是：

> 设备停止指令在物理上永远只能发送一次。

多个取消路径触达同一效果时，不创建多个独立补偿流程。

后续其他动作要求相机空闲时，可以按[后续动作触发的残留收场](camera-recovery.md#后续动作触发的残留收场)建立关联该新动作的独立流程。它有自己的有限预算，不是原动作补偿流程的重置；同一触发动作对同一历史录像仍只登记一次。

补偿执行被主机断电中断后，可以恢复同一补偿流程。

如果驱动明确保证某项收场操作可以安全重复，则即使无法确认上一次尝试结果，也允许在原有限重试预算内再次执行。

支持设备端命令去重时，同一逻辑操作的重试应复用同一设备命令身份。

通信重试耗尽后：

```text
compensation_failed
```

不进行电源重启。

单张拍摄与延时摄影的自动结束、恢复与文件保留遵守[对应动作契约](camera-capture.md)。设备操作协调器对三种拍摄动作统一检查同一设备的占用与兼容性，不因动作类别不同允许冲突的拍摄同时启动。

## 普通动作取消

`cancel_task` 取消其寻址结果对应的计划或动作，并按[自动预览取消关联](preview-obtaining.md#取消联动)加入对应自动取回。计划级取消作用于该计划内的动作，动作级取消作用于指定动作及契约明确关联的自动预览取回；已有 group 寻址表示指定计划内该组的动作集合。具体寻址及不存在目标的结果见[取消目标寻址](task-cancellation.md#取消目标寻址)。取消某个目标不授权取消其他计划或动作，也不授权停止目标设备上归属其他动作或归属未知的活动。

`pending`：

```text
→ canceled
```

`running`：

- 标记取消请求；
- 已经发出的不可安全中止设备调用先完成当前尝试；
- 不再继续新的普通重试；
- 进入取消收场。

已经终态：

> 一般不改变动作历史终态。

但 `obtain_action_outputs` 的可撤回 delivery 属于独立交付生命周期，仍可按[正式产物与取回清理](outputs.md)的[取消取回](obtaining-outputs.md#取消取回)处理。

发起取消的 `cancel_task` 等待本次适用的有限处理结束后再给出最终结果，具体汇总和恢复规则见[取消动作的完成时机](task-cancellation.md#取消动作的完成时机)。目标已保存取消标记、目标动作已经终态与本次取消处理完成分别判断。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

动作投影包含：动作实例、所属计划、类型、设备、group、`scheduled_at`、参数、固化执行策略（适用的计划要求及本地通信配置）、状态、尝试次数、`first_window_observed_at`、`expiration_reason`、结果/错误，以及关联业务变化的 `change_seq`。

效果记录承载持续设备效果及其补偿流程；设备事实记录承载动作终态后仍需保留的未确认设备状态。`change_seq` 规则见[状态报告与累计确认](status-reports.md)。

上述投影依据不可变历史同步更新，遵守[持久化与配置基础](system-foundations.md#持久化与配置基础)。状态转换、尝试结果、窗口观察、可信时间下界的推进和固化策略均保存当时的事实。回放使用已记录的值，不用当前时钟重新判定历史动作，也不执行重试或补偿；实际恢复由调度器在重新取得执行资格并完成必要对账后驱动。

## 验收要求

### 单元测试

按[计划要求与本地通信配置](configuration.md#计划要求与本地通信配置)验证合法业务策略使用计划值，通信策略使用本地值。动作 `policy` 携带通信策略字段时仅该动作校验失败，不能覆盖本地值或静默忽略；已受理请求重送仍复用首次结果。

按[控制调用超时](configuration.md#控制调用超时)的结果与证据表验证默认 10 秒、三类调用分别配置及非法配置；排队和重试等待不消耗调用时间，持续日志不推迟超时，长录像不延长启动调用上限。超时保留已经确认的业务事实；无确认时不得推断未启动、已停止或文件不存在。超时不退还尝试预算，旧调用未收场或未满足安全重试条件时，不得仅凭 3 秒间隔到达而重发。

按[通信重试间隔](configuration.md#通信重试间隔)的条件表验证默认 3 秒、三类操作分别覆盖配置、0 间隔及非法配置；首次尝试无额外等待，后续尝试从规定起点计时。等待期间取消或启动窗口耗尽应及时处理，未知结果不能仅凭间隔到达而重发；等待不占用新尝试次数、不阻塞兼容工作，重启沿用固化间隔及原预算。

提前唤醒覆盖默认 50ms、配置为 0 及其他合法余量；提前检查后动作仍等待计划时间，截止时间不变时不反复立即唤醒，新计划检查仍可打断等待。

使用受接口约束的时钟、存储和驱动替身，验证窗口分区、状态转换、唤醒后重新决策、兼容性、有限重试、取消与受限收场资格。

按已支持动作类型覆盖 `scheduled_at` 缺省与显式填写：设备动作、取回及清理缺省时仅该动作登记为 `failed`；报告与取消缺省时不等待计划时间，显式填写时遵守调度时间。各类型提供非法时间值时也仅该动作失败。区分受理校验失败与实际执行：前者可以由 `submit` 保存且不产生执行尝试，后者仍受会话和时间资格约束。

按[时钟异常期间的取消](clock-recovery.md#时钟异常期间的取消)覆盖取消自身终态、尚未开始与已经开始、时间字段有无、目标存在、不存在及查询未知的分区。验证立即取消作用于指定计划、动作或既有 group 对应的动作集合及明确关联的自动预览取回；同设备上的其他录像及归属未知活动不能被停止。尚未开始的显式定时取消保留待执行；已开始的取消按原目标和进度恢复有限收场。已有目标终态保持不变，取回交付撤回遵守目录所有权规则。

### 集成测试

使用真实 SQLite 保存动作的输入与生效配置，受理后修改本地通信配置并重启，验证原动作继续使用原快照、新受理动作使用新配置。重建原计划不混入本地配置；带非法通信覆盖字段的动作与其他合法动作一同受理，前者失败且不产生设备操作。

组合真实配置文件、SQLite 与 CLI 入口，按[本地配置的加载与更新](configuration.md#本地配置的加载与更新)覆盖默认路径、显式路径、文件不存在、空文件、部分嵌套覆盖、配置错误、停止后更新及重新启动。使用独立测试用户目录验证默认路径不随工作目录改变，显式选择文件不改变未覆盖的数据路径；读取故障不冒充不存在。验证空设备目录合法，`describe` 不创建业务文件，新请求引用未配置设备时只使对应动作失败。验证配置在本次进程内保持不变；分别以 `run` 和 `submit` 受理计划，再由 `run` 执行，已有动作、同 ID 重送和新请求采用表中规定的配置，恢复不刷新快照或尝试次数。

验证真实 SQLite 的受理序列发现及窗口观察持久化，组合调度器与真实驱动边界验证通信准备、超时和必要停止操作的协作；真实设备验证以已核实协议为依据。

组合计划受理、SQLite、受限会话与受接口约束的设备适配，在启动墙钟检查失败时验证新受理的立即取消能够执行，定时取消及其他普通动作保持待执行。分别安排录像属于目标计划、其他计划和归属未知的情况，验证只对确认属于目标的录像进行有限停止。取消结果跨重启保留，重复请求不扩大目标或重置预算；受限会话不取得普通接纳锁，完成后仍报告时钟异常。

### 行为覆盖清单

以下按行为组织，执行时按上述单元测试与集成测试边界归类。

#### 调度

- `prepare_lead_s`；
- scheduled_at；
- max_delay；
- 单调钟等待；
- `plan_poll_interval_ms = 500`；
- 未变化时只读取轻量 `latest_plan_seq`，不扫描 plans/actions；
- 新 plan 推进 `plan_seq`，同 request_id 重试不推进；
- `plan_seq` 变化后增量加载并合并内存调度器；
- 调度截止时间 提前唤醒时同样先检查新计划；
- 提前唤醒后的短暂 await 仍能被下一次计划检查打断；
- 每次 wake 后重新决策，不让旧缓存 action 自动取得执行权；
- `window_missed` 与 `window_exhausted` 明确区分；
- `window_exhausted` 允许 `attempts = 0`；
- 提前加载未来 action 不算窗口内观察；
- `first_window_observed_at` 必须先持久化，再进入后续调度/设备条件检查；
- 断电恢复只承认已经持久化的窗口内观察事实。
- `plan_seq` 未变化时，正常退出检查仍覆盖新出现的报告责任；
- 最终检查发现新提交的未来动作时，保持接纳资格并继续等待执行；
- 最终检查确认无待处理工作后，在同一写事务结束前关闭接纳。

## 实现时细化

正文定义第一版的业务规则。本节列出接口、配置和联调中需要落实的细节；先按正常流程推进，涉及正文尚未确定的业务结果时，再明确对应选择。

补齐发令、确认执行、结果未知与窗口结束的决策表；落实尝试预算及断电后的预算恢复。启动、停止和录像状态查询的调用上限遵守[控制调用超时](configuration.md#控制调用超时)；实际驱动仍须落实超时后的子进程清理与设备核实。重试间隔遵守[通信重试间隔](configuration.md#通信重试间隔)，仍需在恢复模型中明确等待进度的持久化与时间证据。明确无时效动作等待设备条件的结束规则。时钟可信性判定、可信历史下界更新时点和受限收场允许的工作集合需要完整分类。

时间记录还需明确区分启动校验尚未完成、已经校验通过和已经判为异常的状态。具体字段待细化；只有满足可信性规则的时间事实才能推进可信历史下界。
