## obtain_action_outputs

### 作用

选择性获取指定动作、动作组或计划的正式产物，并为本次请求生成独立 delivery。

产物的生成与修复由来源动作负责。来源动作尚未结束时，按本节的等待规则取得最终正式产物；本动作将选中的产物准备为独立待传文件，再按文件交接协议发布。

### 参数

`obtain_action_outputs` 的来源统一放在必填的 `params.source` 对象中。该对象恰好采用下表的一种字段组合，各字段值仍须满足对应名称或实例 ID 的合法性要求：

| `params.source` 的字段组合 | 查找范围与含义 |
| --- | --- |
| `action_instance_id` | 按稳定实例 ID 引用指定动作 |
| `plan_instance_id` 与 `group` | 引用指定计划实例内的组 |
| `action_name` | 仅引用本次取回所属计划中同名的动作 |
| `group` | 仅引用本次取回所属计划中该组的动作集合 |
| `current_plan: true` | 引用本次取回所属计划中的产物来源动作 |
| `plan_instance_id` | 引用指定计划实例中的产物来源动作 |

`source` 缺失、不是对象、为空，或字段组合不属于上表时，首次受理将该动作登记为 `failed`。不能混用动作名、动作实例 ID 和组引用，整个计划允许按下述计划来源规则显式选择；不能用计划名称定位另一个计划。错误范围与校验时点见“校验与失败处理”。

以下是一个取回动作，作为执行计划 `actions` 数组中的成员使用：

```json
{
  "name": "取回上午录像",
  "type": "obtain_action_outputs",
  "scheduled_at": "2026-09-11 12:00:00",
  "params": {
    "source": {
      "group": "上午采集"
    }
  }
}
```

本例获取自身所属计划中“上午采集”组的产物；`params.source.group` 表示来源组，动作公共字段 `group` 表示动作所属的组。`obtain_action_outputs` 不属于任何组，填写动作公共字段 `group` 会使该动作在受理时登记为 `failed`。

动作级引用的精确产物筛选使用 `params.output_ids`，与 `params.source` 并列；`source` 只承担来源引用。筛选的可选性和取值语义见“产物选择”，使用本计划内名称时的解析见“本计划内的产物引用”。

精确取回的 `params` 包含 `source` 和 `output_ids`；预览筛选与自动用途的字段为 `filter` 和 `purpose`，合法组合见[输入扩展](plan-input.md#取回来源筛选与预览)，行为仍遵守[预览专题](preview-obtaining.md)。`source` 只允许所选组合的字段。额外字段仅使该动作在受理时失败。提供 `output_ids` 时，它必须是非空且不含重复值的对象 ID 字符串数组；本次列表中的同一个 ID 不生成多份交付。标识与可读名称遵守[基本值类型](plan-input.md#输入文件与基本值类型)，跨计划 ID 的格式合法不表示引用存在。

通过全部受理校验后，默认取回、预览取回或精确 ID 取回的选择方式使用只读动作执行定义中的 [selection_mode](../camctl/database/execution-definitions.md#取回执行定义的选择方式) 保存，省略参数所采用的默认含义也在此时确定。原输入仍保留字段存在性与请求值；实际来源、选中文件和逐项结果按规定时点另行保存。自动预览与手动预览共享预览选择方式，自动用途及取消联动由关联记录表达。具体职责见[各类动作的执行定义分工](../camctl/database/execution-definitions.md#各类动作的执行定义分工)。

### 校验与失败处理

在计划公共结构合法、动作可被识别为 `obtain_action_outputs` 且满足动作名称约束的前提下，该动作自身的输入错误只使它失败。计划及全部动作仍按[整份校验与原子受理](plan-acceptance.md#整份校验与原子受理)一同保存；其他动作按各自规则执行。

| 校验内容 | 判定时点 | 发现错误时的处理 |
| --- | --- | --- |
| 该动作的参数结构、字段格式和组合，包括 `params`、来源引用及 `output_ids` | 首次受理 | 将该动作登记为 `failed`，保存具体错误 |
| 该动作自身的时间、策略及所属组等字段违反已定义的要求 | 首次受理 | 将该动作登记为 `failed`，不执行或加入任何组 |
| 本计划内名称引用对应的动作或组是否存在、是否有能产生产物的来源动作 | 首次受理，根据本次完整计划判断 | 将该动作登记为 `failed`，保存缺失或来源类型不适用的原因 |
| 同一拍摄是否被多个自动预览取回引用 | 首次受理，根据本次完整计划判断 | 按[重复自动预览关联](preview-obtaining.md#重复自动预览关联)将全部冲突的自动取回登记为 `failed`；拍摄、手动取回及其他动作独立处理 |
| 通过实例 ID 引用的动作，或指定计划实例内的组，是否存在并适合作为来源 | 首次执行且取得相应执行资格时 | 可靠确认目标缺失或没有产物来源时，仅该动作 `failed` |
| 格式合法的显式 `output_ids` 是否存在、属于指定来源，以及能否取得读取资格 | 执行期间，按来源确认及产物选择规则判断 | 按[精确 ID 取回的逐项判定](#精确-id-取回的逐项判定)保存每项结果；普通目标错误不阻止其他合法项继续 |
| 来源产物是否已生成、可用，以及后续读取与交付结果 | 执行期间 | 按等待、逐项失败及开始发布的条件规则处理 |
| 数据库查询、记录解释或持久化失败、结果未知 | 发生时 | 按会话错误及恢复规则处理，不伪装为输入错误或目标缺失 |

首次受理不查询其他计划的来源是否存在，也不提前固定其来源集合。合法的实例引用先保存调用方指定的 ID 与组名，执行时再解析；本计划内的名称引用在受理时解析并保存有效来源关联。

初始失败状态、输入及诊断保留、原子受理和请求重送统一遵守请求专题的公共规则。参数错误的取回不产生执行尝试或 delivery；报告将其表达为已受理计划中的动作失败。

### 产物选择

客户端可以先通过状态报告取得 `output_id`，再提交新的取回请求。动作级引用允许可选的 `params.output_ids`，其语义如下：

```text
不带 output_ids
    → 获取该动作的非预览产物；每份原片有已登记修复成品时只取对应修复成品

output_ids = 非空数组
    → 精确获取这些产物

output_ids = []
    → 受理时该动作 failed
```

不得因为指定产物不可用而自动扩大选择范围。

例如只请求修复视频时，修复视频不可用不能擅自改传原片。

省略 `output_ids` 使用默认选择规则：排除预览，并以已登记修复成品替代对应原片。所选修复成品不可用时失败，不自动退回原片；其他原文件独立判断。显式 ID 允许选择原片、预览或修复成品。

### 精确 ID 取回的逐项判定

本节适用于输入格式已经通过校验、指定来源动作已经可靠确认，且按执行资格与来源规则进入产物选择的取回。`params.output_ids` 中的每个 ID 是独立的取回目标；某个 ID 不存在、归属不匹配或对应产物已不可取回，只使该项失败。其他合法目标继续准备与交接，整次取回按[部分成功](#部分成功)汇总。

例如，请求从录像动作 A 取回甲、乙、丙：甲属于 A 且可读取，乙属于 A 但已清理，丙不存在或属于录像动作 B。camctl 取回甲，分别保存乙、丙的失败原因。甲的副本按交接规则移入 `ready` 后，整次取回为 `failed`，报告同时保留甲的成功交付和乙、丙的失败。

取消、既有终态及已经保存的逐项最终结果优先处理。对尚未完成判定的 ID，按下表自上而下选择适用分区；来源动作自身不存在或无效时，仍按来源确认规则处理整个取回，不能虚构已确认来源来创建逐项结果。

| 执行时可靠取得的事实 | 本项处理 |
| --- | --- |
| 状态库查询失败、记录无法解释、事务结果未知，或者此前已可靠确认存在的产物记录缺失 | 按状态库错误及恢复规则处理，不记为普通的 ID 不存在或归属不匹配 |
| 查询可靠完成，指定 ID 没有正式产物记录，且没有此前已经确认该产物存在的可靠事实 | 本项最终失败，保留请求中的 ID，不等待这个 ID 将来出现 |
| 正式产物存在，但其来源动作不是本次指定来源 | 本项最终失败，说明归属不匹配；不读取该文件，不改变本次来源 |
| 产物属于指定来源，但已清理、可靠确认文件缺失，或按现有规则无法取得读取资格 | 本项最终失败，记录实际不可用或删除限制原因；不替换为其他产物 |
| 产物属于指定来源，文件状态检查或读取暂未完成，包括等待设备、有限重试或文件查询结果未知 | 按原设备与文件错误规则继续等待、核实或结束本项；不能把暂时未完成当作 ID 不存在，也不将设备查询错误改为状态库错误 |
| 产物属于指定来源，符合读取资格及实际可用性要求 | 按原文件读取、校验及交接规则处理；读取期间的等待、有限重试和失败仍遵守各自契约 |

不存在或归属不匹配的 ID 不创建 delivery，也不建立虚假的产物与来源关联。错误报告保留调用方填写的 ID，具体表达见[取回失败项的报告表达](#取回失败项的报告表达)。同一产物因不可用或读取失败形成的最终失败只记录一次，不因不同处理阶段重复追加失败项。

显式 ID 列表随原请求保存；执行时确认的归属、逐项失败及已有交付进度按历史与投影规则持久化。已经保存的失败不因重启、同一请求重送、产物后来出现或删除限制解除而重新执行。新的取回意图使用新请求；仍未完成的合法项继续按原身份和进度恢复。结果保存失败或提交结果未知时，先按状态库规则核实，不能当作普通逐项失败后继续副作用。

### 本计划内的产物引用

`obtain_action_outputs` 通过 `params.source.action_name`，或仅含 `group` 的 `params.source` 对象，引用自身所属计划中的产物来源，无须客户端预先知道 camctl 分配的实例 ID。引用形式及字段位置见本动作的“参数”；本节定义其中两种局部引用的解析。

动作所属的组遵守[公共 group 约束](plan-acceptance.md#group)：取回动作不属于任何组，但允许引用组。无论来源组位于本计划还是其他计划，该引用均不把取回动作加入目标组；首次受理时须分别校验 `params.source` 和动作公共字段。

仅首次受理需要解析本计划内引用：先校验完整动作集合及名称约束，再按本计划的动作名称和组成员关系解析。允许引用在 `actions` 数组中排在取回动作后面的录像，数组顺序不限制引用，实际执行仍由各动作的时间和业务条件决定。

| 首次受理时的局部引用情况 | 处理 |
| --- | --- |
| 动作名对应本计划中唯一且能产生产物的动作 | 解析为目标动作的实例关联；其他参数继续按各自规则校验 |
| 本计划内的目标组存在，按类型筛选后至少有一个产物来源 | 保存本计划及目标动作的实例关联；其他参数继续按各自规则校验 |
| 本计划内的目标组存在，但按类型筛选后没有产物来源，或指定动作类型不产生产物 | 将该取回动作登记为 `failed`，保存来源类型不适用的原因 |
| 本计划内没有对应动作或组 | 将该取回动作登记为 `failed`，不延后等待其他计划提供同名目标 |
| 来源引用形式缺失、混用或不合法 | 按“校验与失败处理”将该取回动作登记为 `failed` |
| 计划内动作名称违反唯一约束 | 按计划公共结构错误拒绝整份计划 |
| 实例分配或关联保存失败、提交结果未知 | 按受理事务错误及恢复规则处理，不能保留部分计划或猜测关联 |

计划、全部动作、有效来源关联及失败动作的诊断在同一受理事务中保存历史和投影。历史保留调用方原有的局部引用语义；有效引用同时保存对应的实例关联，失败引用保留错误而不虚构关联。执行和恢复使用固定关联，不按后来出现的同名计划、动作或组重新查找。同一 `request_id` 的重试直接复用原计划，不重新解析本次正文。

例如一份计划安排“10:00 主录像”和“10:10 取回主录像产物”，后者使用 `action_name = 主录像`。camctl 受理时建立两者的实例关联；取回到达自己的 `scheduled_at` 后，录像若仍未结束则按等待规则继续等待。引用本身不建立成功依赖，也不提前授予尚未生成产物的读取资格。

局部引用只增加来源寻址方式。单个录像及组取回仍遵守后续的成员筛选、等待、产物选择、逐成员准备和开始发布的条件。动作级局部引用的 `output_ids` 规则与实例引用相同；请求尚未生成的默认范围产物时省略 `output_ids`，局部引用不提前分配产物身份。

### 按动作实例 ID 查找来源

使用 `params.source.action_instance_id` 时，首次受理仅校验引用结构及 ID 格式，合法时保存调用方指定的 ID，不查询目标或创建占位来源动作；格式错误按“校验与失败处理”登记动作失败。该规则同时适用于两个计划输入入口。取回取得执行资格后，才依据可靠的数据库查询结果处理目标；本计划内 `action_name` 的解析遵守前节规则。

取回自身的取消和既有终态优先；对仍有效的取回，按下表判定：

| 来源查询与已有事实 | 处理 |
| --- | --- |
| 可靠查到指定动作，其类型可产生产物，状态及记录可解释 | 保存来源关联，按动作状态及产物选择规则继续；录像尚未结束时遵守等待规则 |
| 可靠查到指定动作，但其类型不产生产物 | 仅该取回动作 `failed`，保存来源类型不适用的原因 |
| 可靠确认指定 ID 没有动作记录，且此前没有该来源已存在的可靠事实 | 仅该取回动作进入 `failed`，原因表达“来源动作不存在”；不等待该 ID 将来出现 |
| 查询失败、结果未知或记录无法可靠解释 | 按状态库错误处理，不记为来源不存在或正常等待 |
| 已有来源存在的可靠事实，但应永久保留的动作记录无法找到 | 按持久化一致性错误处理，不能用普通目标不存在掩盖历史缺失 |

来源查询所得有效关联或失败结果在同一事务中保存历史和投影，报告保留取回动作及请求中指定的来源 ID；不虚构来源动作、产物或 delivery。其他动作继续按自身时间与执行条件运行，不因该失败被拒绝或取消。记录保存不成功或提交结果不确定时，按状态库错误与恢复规则处理，不能假定来源已固定或失败终态已经成立。

已经保存的失败结果在重启、同一请求重送及后续来源出现时保持不变；新的取回意图须使用新的请求。报告和历史回放保留当时查询与判定的事实，不重新查询当前来源来改写结果。

### 按计划取回与预览筛选

取回来源支持显式选择当前计划或指定 `plan_instance_id` 的整个计划；既有动作和组引用继续有效。当前计划来源与其拍摄成员在首次受理时解析，其他计划在首次取得执行资格时可靠解析并固定。计划名称不能替代实例 ID。完整来源字段组合遵守[协议落实边界](preview-obtaining.md#验收与协议落实边界)。

按计划只选来源计划中能产生正式产物的动作，不把该计划取回的其他计划产物纳入。固定成员后，各来源拍摄及其适用修复结束即可分别按默认产物规则准备文件；全部来源判定和全部条目准备结果确定后，才发布成功文件。该等待不包含取回自身、清理、报告等非产物来源动作，不等待整个计划 `completed`。无来源或逐来源无产物沿用现有取回失败规则。

预览筛选、自动用途和大小替代遵守[预览取回契约](preview-obtaining.md)。每个自动取回只关联单个本计划拍摄，各自准备和发布。普通计划级取回的集合等待规则不延伸到其他独立自动取回。

### 等待拍摄动作结束

通过 `action_instance_id` 或已解析的本计划内引用请求单个拍摄动作的默认范围产物时，取回可以在拍摄动作结束前提交。camctl 保留该取回请求，等待被引用的拍摄动作进入终态，再确定本次要取回的文件集合。不能将等待期间暂时没有产物判为取回失败，也不能提前用当时已有的部分产物代表本次完整选择。

在取回已取得执行资格后，按下表处理；取回自身的取消和既有终态优先于继续等待或选择文件：

| 取回与被引用拍摄的状态 | 处理 |
| --- | --- |
| 取回仍有效，拍摄存在且尚未结束 | 保留固定来源关系和未完成选择，按[来源处理规则](../camctl/database/waiting.md#来源等待的记录与转换)等待来源变化；不开始文件取回 |
| 取回仍有效，拍摄已结束且有正式产物 | 确定并持久化本次选择的产物集合，再按逐项处理及开始发布的条件规则执行 |
| 取回仍有效，拍摄已结束且确认未产生正式产物 | 按“已结束动作没有正式产物”结束取回 |
| 取回已取消或进入其他终态 | 不因拍摄随后结束而重新开始取回；遵守原终态及收场规则 |
| 直接指定的动作实例 ID 确认不存在 | 按“按动作实例 ID 查找来源”处理，不解释为拍摄尚未结束或已结束但无产物 |
| 已固定且应存在的来源记录缺失，或状态、产物查询失败或结果未知 | 按持久化错误处理，不能冒充正常等待或无产物 |

等待不停止或重新启动拍摄，也不阻塞拍摄收场、其他动作或新取消请求的处理。拍摄的 `failed`、`expired` 或 `canceled` 不直接复制为取回的状态；取回依据最终正式产物及自身处理结果结束。

等待对象、已确定的产物集合及后续进度遵守数据库历史与投影规则。主机重启后，后续实际启动的 `run` 恢复同一取回：拍摄仍未结束则继续等待，已经结束则继续选择或处理；已确定的集合不因重启重新扩大。等待中的取回属于尚未完成的计划工作，参与会话接管与退出检查，无须客户端重新提交或主程序保留计划文件。

例如计划录像 10 分钟，第 3 分钟收到已经到执行时间的取回全部产物请求，camctl 先保留请求，等拍摄动作结束后再选择文件。拍摄完成正常控制流程或适用的异常处理后，将正式产物登记与动作终态一同提交，具体见[拍摄动作的结束时点](camera-recording.md#录像动作的结束时点)。原片也遵守这一登记边界；单独取回原片不能提前访问仍属拍摄内部处理的文件。等待遵守[取回与清理的执行时间](outputs.md#取回与清理的执行时间)；等待期间按[动作状态](report-format.md#计划与动作)表达执行阶段，实际交付和失败按各自结果报告。

### 按组取回的成员筛选

按组取回只将动作类型能够产生正式产物的成员作为来源，不以成员当前是否已有产物或执行是否成功决定是否选入。产物能力由动作接入时的业务契约声明，取回读取该声明，不自行维护一套拍摄动作类型清单。第一版三种拍摄动作均可以产生正式产物，包括取消后按[文件保留规则](camera-capture.md#取消失败与文件保留)登记的文件；`report_status`、`cancel_task`、`delete_action_outputs` 不产生供取回的正式产物。状态报告使用独立的报告交接流程。

拍摄动作的具体文件种类、数量与关联由目标驱动为相应参数类型定义，见[驱动执行与产物边界](camera-capabilities.md#驱动执行与产物边界)。新增参数类型继续使用公共产物选择与交付流程。已支持的拍摄动作即使因目标设备不适用、参数类型或参数值错误而初始失败，仍按其拍摄类型作为产物来源；终态没有正式产物时记为失败项，不能将“本次未能执行”解释为“该类型不产生产物”。

本规则同时适用于指定计划实例的组引用和本计划内组引用。先按来源计划中各动作所属的组定位成员，再筛选取回来源；不修改原组成员，不影响组取消范围或报告组织。`obtain_action_outputs` 不属于任何组，遵守公共 `group` 约束。

| 成员类型与当前状态 | 本次组取回的处理 |
| --- | --- |
| 类型不产生正式产物，动作状态任意 | 不作为取回来源，不等待其结束，也不记为无产物失败项 |
| 类型可产生正式产物，尚未进入终态 | 保留为来源，按所属动作的等待规则处理，不能因当前无产物而跳过 |
| 类型可产生正式产物，已进入终态 | 保留为来源，按最终正式产物处理；无产物时记录失败项，动作失败但留有产物时仍取回 |
| 成员关系、类型或能力无法可靠判断 | 保留实际错误或未知，不能按“不产生正式产物”跳过，也不能确认筛选已完成 |

本计划内组在首次受理时确定来源，指定计划实例的组在首次执行时确定来源，具体见下一节。来源集合可靠保存后，执行和重启恢复沿用固定范围。以下组取回规则中的“成员”“全部来源”和发布等待均指筛选后的来源动作，不包含已排除的非产物动作。

例如组内 A 在 10:00 录像，B 在 18:00 执行 `report_status`，12:00 发起组取回：只处理 A 的正式产物，不等待 B。若 A 已失败且没有正式产物，则记录 A 的无产物失败；B 不构成失败项。其他普通动作的调度和执行不受筛选影响。

### 组来源的确定

仅含 `params.source.group` 的本计划内引用，在首次受理时根据完整输入解析并保存结果。包含 `plan_instance_id` 与 `group` 的引用，在受理时只保存格式合法的来源描述；首次执行取得资格后，从数据库查询指定计划及组，按成员类型筛选来源。客户端可以提前检查自己掌握的计划内容，camctl 仍在各自规定的时点作出判定。

以下来源判定适用于计划公共结构及该动作自身字段、参数格式均合法的情况。跨计划引用执行前先处理取消及既有终态；已保存有效来源集合时直接恢复原集合及进度，不重新解析。

| 解析目标组及来源的结果 | 本计划内引用：首次受理 | 指定计划实例的组：首次执行 |
| --- | --- | --- |
| 组存在，至少有一个能产生产物的来源动作 | 保存来源集合，该取回初始为 `pending` | 保存来源集合，按各来源动作及产物状态继续 |
| 目标计划不存在 | 不适用，来源计划就是本次输入的计划 | 仅该取回 `failed`，不等待目标将来出现 |
| 目标组不存在，或没有组成员 | 将该取回登记为 `failed`，保存具体缺失原因 | 仅该取回 `failed`，不等待目标将来出现 |
| 组存在，但成员类型均不产生产物 | 将该取回登记为 `failed`，保存没有产物来源的原因 | 仅该取回 `failed`，保存没有产物来源的原因 |
| 记录无法可靠解释或保存，或数据库查询失败、结果未知 | 按会话错误及恢复规则处理 | 按会话错误及恢复规则处理，不解释为目标缺失 |

本计划内的来源集合或诊断与计划、全部动作在受理事务中整体保存；指定计划实例的组在运行时通过同一事务查询并保存来源集合或失败结果。来源尚未解析、有效集合已固定、解析已失败分别记录，不能都表示为空集合。集合保存前不开始产物选择、读取或交付。提交结果未知时先对账，不能重复固定来源或猜测结果。

确定来源只判断组成员及其类型，不保证产物已经生成或仍可读取。运行时继续检查每个来源的动作状态、正式产物及可用性；录像未结束时等待，已结束且无产物时记录失败，失败录像留有产物时仍按实际产物处理。

已经可靠保存的来源集合、失败结果在重启和同一请求重送后保持不变。后续文件清理不改变已选来源身份，但影响实际取回结果；已完成的逐项选择、准备进度及发布事实仍按各自规则保留。其他动作继续按自身条件执行。

### 组内拍摄分别准备与统一发布

通过 `(plan_instance_id, group)` 或已解析的本计划内组引用取回一组拍摄的默认范围产物时，每个拍摄动作进入终态后，就确定并持久化该成员按筛选规则选中的完整产物集合，按取回资格开始准备独立交付文件。其他成员尚未结束不阻止这一步；发布须等待全部成员结束并完成产物判定，以及全部所选产物取得最终准备结果。

本节适用于按“按组取回的成员筛选”得到至少一个拍摄动作来源的第一版组取回，原组可以同时包含非产物动作。按原计划中保存的组成员及类型固定本次取回来源，不跨计划合并同名 group。取回已到计划时间且仍有执行资格时，对每个来源成员分别应用下表；本次取回的取消和既有终态优先处理：

| 成员及本次取回的情况 | 本成员的处理 |
| --- | --- |
| 拍摄未进入终态，包括未来尚未开始的拍摄 | 保存等待对象，不选择该成员的产物，不阻止其他已结束成员准备文件 |
| 拍摄已进入终态，尚未完成产物判定，查询可靠完成 | 固定并保存该成员的完整选择或无产物失败项；有产物时按资格开始准备 |
| 该成员的选择或无产物失败项已经保存 | 继续原条目，不重新选择、扩大集合或重复创建 delivery |
| 本次取回已取消或进入其他终态 | 不继续等待或开始新的准备，按原终态及收场规则处理 |
| 组成员、拍摄状态、既有选择或产物查询失败、结果未知 | 保留实际问题，按对应错误处理，不能当作成员已结束、已完成选择或没有产物 |

成员成功、失败、过期及取消均属于拍摄结束。拍摄自身状态不直接复制为取回状态；未产生正式产物的成员按“已结束动作没有正式产物”记录失败项。已经登记但已清理或不可用的产物按实际状态处理，不能当作从未产生。全部成员完成判定后，本次完整选择为各成员已保存集合的合并结果。

等待遵守取回的无时效规则，不阻塞组内拍摄、其他动作及取消请求，也不改变 group 作为集合标签的性质。组成员、逐成员选择、无产物失败项及逐产物准备进度遵守数据库历史与投影规则。断电后恢复同一请求：继续等待未结束的成员，恢复未完成的准备，保留已经可靠准备完成的交付副本；不能只因组未结束就重新取回已准备的文件。等待属于尚未完成的计划工作，参与会话退出检查。

例如组内 A 上午结束、B 下午结束，中午开始组取回时即准备 A 的交付副本，同时等待 B。A 的副本可靠准备完成后，按[清理与取回并发](output-cleanup.md#清理与取回并发)可释放对 A 保留文件的读取依赖。B 结束后准备 B 的文件；全部成员与产物处理满足开始发布的条件后，再逐文件发布。

### 已结束动作没有正式产物

通过 `action_instance_id` 取回单个动作的默认范围产物时，若该动作已经进入终态，且确认没有产生任何正式产物，则本次 `obtain_action_outputs` 以 `failed` 结束。报告关联被引用的动作，说明该动作没有可取回的产物；不创建 delivery。

本规则用于已受理取回动作的执行结果，取回自身的取消和既有终态仍遵守公共动作状态机。判定时必须区分以下情况：

| 被引用动作及产物的情况 | 处理 |
| --- | --- |
| 动作存在且已结束，确认未产生正式产物 | 取回为 `failed`，报告没有可取回的产物 |
| 动作存在且已结束，已登记正式产物 | 按产物选择及逐项处理规则执行；已清理或不可用的产物不能当作从未产生 |
| 动作尚未结束 | 不适用本条空产物判定；单个拍摄动作默认范围产物的取回按[等待拍摄动作结束](#等待拍摄动作结束)处理，其他范围见待细化契约 |
| 动作不存在，或动作状态、产物查询失败或结果未知 | 保留实际的缺失、错误或未知情况，不能解释为已结束且没有产物 |

例如录像启动失败，动作已经结束且没有正式视频，随后取回该动作全部产物时，取回结果为 `failed`。报告说明未取得文件的原因，不为此重新启动录像。

组取回筛选所得的录像来源非空时，每个来源成员结束后即应用上述产物判定：没有产生任何正式产物的录像记为本次取回的一个失败项，关联其 `action_instance_id` 并报告无产物原因，不为该项创建 `output_id` 或 delivery。其他来源成员已经登记的产物继续按逐项规则取回。录像自身失败但留有正式产物时，按这些产物的实际取回结果判断，不额外计为无产物失败。

无产物失败项与本次选择的产物集合按历史与投影规则保存，恢复时保留已确定的结果。部分成员无产物时，完成其他文件的必要发布后，取回整体为 `failed`；所有成员均确认无产物时，整体为 `failed` 且不创建 delivery。组不存在、没有成员或查询失败均不属于“组内录像全部无产物”。取消及既有终态仍优先处理。

### 部分成功

`obtain_action_outputs` 的整体状态表示本次取回是否全部完成；报告逐产物列出处理结果及失败原因，录像组的无产物失败项按来源动作列出，显式 ID 不存在或归属不匹配则按请求中的 ID 列出失败原因。整体为 `failed` 不表示所有文件都未交付。

本表适用于尚未进入终态、全部来源已完成产物判定，且适用的显式 ID 均已完成判定的取回；本次已选产物、录像组无产物失败项及显式 ID 判定失败项合计至少有一项。仍有来源或显式 ID 尚未完成判定时，继续等待与处理，不发布文件，也不根据当前已有条目汇总整体终态：

| 本次取回条目的处理情况 | 动作整体状态与后续处理 |
| --- | --- |
| 仍有产物等待处理、正在处理或可以继续重试 | 继续处理；某项已失败也不能提前结束整个动作；遵守开始发布的条件 |
| 全部产物准备处理已结束，但仍有成功准备的文件等待发布或发布结果尚未确定 | 继续完成发布或恢复对账，不能仅凭准备成功宣告动作成功，也不能因其他项失败而扣留这些文件 |
| 所有已选产物均已成功发布，且没有任何逐项失败 | `succeeded` |
| 至少存在一个逐项最终失败，其余各项均已成功发布或最终失败 | `failed`；保留各项实际结果和失败原因，包含录像组所有成员均无产物、全部显式 ID 均无效或不可取回的情况 |

这里的成功发布以文件交接协议定义的本地交付完成为准，不等待主程序发送或客户端收到。已经发布的文件即使被主程序移走，也不因此退回未完成状态。发布失败或结果未知必须如实记录，不能当作成功发布。

中断恢复遵守[普通交付的保存顺序与中断恢复](file-handoff.md#普通交付的保存顺序与中断恢复)。没有可靠完成记录、三个交接位置均无副本且无法确定交接结果时，该 delivery 最终为 `failed`，原因明确为本地交接结果无法确认。该项进入逐项最终失败，不长期停留在等待发布状态，也不自动重新投放；其他项继续完成必要交付，再汇总动作结果。这不证明主程序未发送或客户端未收到。

例如请求 A、B、C，A、B 准备成功而 C 重试耗尽：先发布 A、B，再将动作整体置为 `failed`；报告分别说明 A、B 已发布及 C 的失败原因。不因为 C 失败扣留 A、B，也不因 A、B 成功将整个动作标为 `succeeded`。

取消及既有终态遵守公共动作状态机与本专题的取消规则，不通过本表覆盖已有终态。单个已结束动作或录像组成员未产生正式产物时，按“已结束动作没有正式产物”处理。组取回在适用时点确定非空来源集合后才进入产物处理；执行时没有文件不能解释为没有来源，也不能以零个成功项汇总为成功。其他空集合场景见[产物专题的实现细化事项](outputs.md#实现时细化)。

### 取回失败项的报告表达

已开始执行的取回动作通过 `result.failures` 列出本次取回已经确定的逐项最终失败；尚无此类失败时为空数组。该列表是动作自身结果的一部分，从冻结历史边界计算并随动作完整自身字段更新，不作为需要按 ID 合并的实体子集合。已确认失败的条目在其他来源仍等待或处理时也可报告，但不因此提前判定整次取回结束或越过开始发布的条件。

每项包含具体 `error`，以及已经可靠确定的来源身份。来源动作字段采用 `source_action_instance_id`，含义与产物、交付中的同名字段一致；只有正式产物存在且归属与该来源一致时，才通过 `output_id` 关联它。`delivery_id` 仅在已经存在对应交付记录时提供。

| 来源及处理情况 | 失败项中的身份 | 处理与报告 |
| --- | --- | --- |
| 默认范围取回的来源动作或组成员已确认且进入终态，可靠确认没有正式产物 | `source_action_instance_id` | 记录无产物失败；错误码为 `no_outputs`，阶段为 `output_selection`，不创建产物或交付身份 |
| 指定来源动作已确认，显式 ID 可靠确认不存在 | 仅关联指定的 `source_action_instance_id` | 通过 `error` 的结构化细节保留请求中的 ID 及不存在原因；不填写指向虚构产物的 `output_id`，不创建 delivery |
| 指定来源动作已确认，显式 ID 指向其他来源的产物 | 仅关联指定的 `source_action_instance_id` | 通过 `error` 的结构化细节保留请求中的 ID 及归属不匹配原因；不将其他来源的产物关联到本次指定来源，不创建 delivery |
| 来源及正式产物已确认，该产物处理最终失败，尚未创建 delivery | `source_action_instance_id`、`output_id` | 记录该产物的具体失败原因，不为报告错误而创建 delivery |
| 本次 delivery 已创建，文件处理最终失败 | `source_action_instance_id`、`output_id`、`delivery_id` | 关联该交付及其最终错误，交付和读取尝试继续提供各自的详细结果 |
| 本次 delivery 已创建，中断恢复后因本地交接结果无法确认而最终失败 | `source_action_instance_id`、`output_id`、`delivery_id` | 与 delivery 使用同一最终错误事实，明确保留交接结果未知的原因，不表述为已确认的发送失败或客户端未收到 |
| 来源尚未结束、条目仍待处理或仍可重试 | 不因等待或本次尝试失败新增最终失败项 | 报告实际进度；已有其他条目的最终失败仍保留 |
| 来源整体尚未确认、来源查询失败或结果未知 | 不据此构造无产物失败项 | 按来源确认、动作级错误或会话错误规则处理；请求中写有某个 ID 不证明对应实体存在 |

组合约束为：存在 delivery 关联必然同时具有已确认的产物和来源动作关联，存在产物关联必然具有已确认的来源动作关联。不存在、未完成及查询未知不能相互替代。来源动作失败但已登记正式产物时，按产物实际处理结果判断，不增加无产物失败项。

显式 ID 判定失败按请求中的各个 ID 分别保留原因；即使它们关联同一个来源动作，也不能合并成一条无产物错误。使用[错误登记](../../protocol/errors/workflow-codes.json)中的 `output_not_found` 与 `output_source_mismatch`，请求中的 ID 写入 `error.details.requested_output_id`，与已确认实体关联区分。失败项识别必须包含该请求 ID，不能仅按来源、产物和交付关联去重而丢失多个无效 ID。默认范围取回的 `no_outputs` 不代替这些结果。

失败事实保存在所属动作或文件条目的历史中，`result.failures` 由这些事实生成；同一最终失败只列一次，不把同一文件的多次通信失败各算成一个取回失败项。失败项与对应 delivery 的最终错误从同一历史事实表达，不能各自维护相互冲突的结论。重送原请求、恢复或重复接收报告不增加失败项，也不重新创建身份。

整次取回因逐项失败而结束时，动作错误为 `obtain_items_failed`，阶段为 `execution`，`details` 为空对象，具体失败项由 `result.failures` 提供。成功交付继续保留在动作的 `deliveries` 子集合中；存在失败项不否定其他文件已发布。取回自身在受理阶段的参数错误仍按动作级错误表达，不假装已经执行了产物选择。

完整示例见[组内一个录像没有产物](client-protocol-examples.md#样例四组内一个录像没有产物)。

例如一组要取回录像 A、B：A 已录完时可以先拷贝 A，同时等待 B；但不能因此先把 A 发布给主程序。要等所有来源的产物已确定、每项准备已得到结果，再发布准备成功的文件。开始发布后仍可逐文件移动，因此文件可能分属不同传输窗口。下面给出完整判定条件。

### 开始发布的条件

本次取回仍有效且未终态时，按以下条件判断能否开始发布。单个录像在结束后完成产物判定；录像组须对全部固定成员完成判定，才能确认没有尚待补入的条目。

| 来源与条目状态 | 发布处理 |
| --- | --- |
| 仍有来源等待结束或尚未完成产物判定 | 继续等待及准备，不发布已有成功文件 |
| 全部来源判定完成，但显式 ID 仍有待判定条目 | 继续逐项判定，不发布已有成功文件 |
| 全部来源判定完成，仍有产物等待准备、正在处理或可继续重试 | 继续处理，不发布已有成功文件 |
| 全部来源判定完成，全部显式 ID 的判定及所选产物准备结果已确定 | 发布成功准备的文件；无产物、显式 ID 判定失败或准备失败项保留失败结果，没有成功文件时不创建交付文件 |
| 以上条件无法可靠确认 | 按对应错误处理，不推测已满足发布条件 |

满足上述条件后进入发布阶段，允许逐文件发布。例如：

```text
A → ready → 被主程序领取
B → 稍后才进入 ready
```

A、B 可以落入不同数据传输窗口，不要求整组原子发布。

### 每个新请求产生独立 delivery

新的 `request_id` 发起新的取回时：

> 即使选择与历史完全相同的 `output_id`，也创建独立 delivery。

各取回请求独立持有自己的待传文件。

同一 `request_id` 的重试则复用原请求，不创建新的 delivery。

### 取回中间文件的保留与清理

本节适用于某次取回在 `staging` 工作位置留下的独立副本，包括尚未可靠准备完成的半成品，以及取消后不再交付的完整副本。以该取回项的持久化结果、文件归属和实际文件操作状态判断，不根据文件年龄、大小或整次取回的汇总状态推测是否可以删除。

| 文件与所属取回项的情况 | 处理 |
| --- | --- |
| 文件位置、归属、取回项结果或相关操作是否停止无法可靠确认 | 保留文件，核实或按对应错误处理，不猜测文件可以删除 |
| 副本尚未准备完成，取回项仍未结束，包括仍可重试或仅因断电中断 | 保留半成品及已保存进度，按原请求续传 |
| 半成品所属项已最终失败或取消，或完整副本所属取回已取消，但相关操作尚未确认停止 | 先停止并确认，不删除仍可能被使用或移动的副本 |
| 副本尚未准备完成，取回项已最终失败或取消，读取、写入和重试均已确认停止 | camctl 自动删除该项自己的半成品，无须客户端另行提交清理请求 |
| 成功副本已可靠准备完成，本次取回仍有效且尚待发布 | 保留副本并继续原发布流程；其他项失败不授权删除该副本 |
| 副本已完整准备，取回取消已可靠保存，副本仍在本次 `staging` 工作位置，相关操作已确认结束 | camctl 自动删除这次取回的完整副本，并保存清理结果，无须客户端另行提交清理请求 |
| 副本已进入 `ready`，本次取回被取消或收到撤回要求 | 按文件撤回规则处理，不套用 `staging` 中间文件删除规则 |
| 副本已进入 `processing` | 保持主程序所有权，camctl 不删除或撤回 |

中间文件清理不删除相机源文件、`staging/derived/` 中的正式产物或其他取回的副本。交接中的文件按实际位置及所有权处理，已发布文件撤回遵守“取消取回”与文件交接规则。取消与移动发生竞争时，先确认实际操作结果，不能凭旧的 `staging` 路径推测文件仍由本次取回掌控。

数据库永久保留取回项的结果、失败原因、拷贝进度历史和清理处理事实。先可靠保存适用的最终失败或取消及副本归属，再执行物理清理；删除文件不抹去诊断或释放交付名称，也不把失败或取消改为成功。新的取回请求继续创建独立 delivery，不接管已经失败或取消请求的中间文件。

重启后区分未结束请求的续传文件、有效取回待发布的完整副本与已经符合清理条件的中间文件。清理中断时，依据原归属和已保存的取消或失败事实继续核实：确认文件仍存在且符合清理条件时继续清理；确认对应中间文件已不存在且无待核实的移动或交接时，保存清理完成的恢复事实；查询失败或结果未知不能冒充清理成功。

完整副本被取消后不承担保留最后一份数据的责任。正式源产物可能此前已被合法清理，这不阻止删除已取消取回的独立副本，也不保证以后仍能重新取回。

#### 取回中间文件清理失败与后续处理

本节处理已经可靠确定归属、满足清理条件的取回中间文件；半成品与取消后的完整副本共用同一清理机制。原动作及取回项的终态保持不变，清理结果单独记录。

| 清理结果与会话履职情况 | 处理 |
| --- | --- |
| 已确认删除完成或恢复时确认文件不存在，结果可靠保存 | 记录清理完成；其他职责完成后允许会话正常结束 |
| 文件查询或删除失败、结果未知，但数据库、其他动作及报告职责仍可正常完成 | 本次有限尝试后保存尚未清理及具体失败或未知原因，继续其他工作；报告职责完成后允许会话正常结束 |
| 数据库不能可靠读取或保存处理状态、事务结果未知，或本地报告等必要职责无法完成 | 按相应会话错误与恢复规则处理，不能以允许延后清理代替必要职责 |

尚未清理的记录保留原取回及文件关联，后续实际启动的正常 `run` 再核实并有限尝试清理。它不恢复原取回、不重新拷贝、不创建新的业务动作；清理完成也不改变已经结束的计划状态。时钟异常的受限会话仍遵守已有工作范围。

每个正常会话对这些残留文件的清理工作均有有限尝试范围。本次尝试结束后，残留本身不阻止正常收尾，也不单独要求立即再启动 `run`；调度重扫、新输入、报告处理及最终退出检查不能重新开启本次已经结束的清理尝试。清理实际影响业务动作结果时，履行对应结果的报告职责；普通中间文件的自动清理不单独形成公开结果。

不增加定时清理或独立重试会话。取回已取消、中间文件清理失败和 `run` 正常结束可以同时成立；发起取消的 `cancel_task` 仍按[取消动作的完成时机](task-cancellation.md#取消动作的完成时机)汇总，本次适用清理失败不能报告为全部处理成功。后续清理完成更新独立清理事实，不改写取回或取消动作已有终态。

清理失败、后续实际尝试所得的新结果及清理完成事实按历史与投影规则保存；单纯再次看到同一条待清理记录不构成新的清理尝试或新的失败事实。每份文件每次正常运行最多检查和清理一次，批量、历史处理上限及跨运行续查遵守[中间文件清理的运行预算](file-handoff.md#中间文件清理的运行预算)；本地文件调用遵守[完成与故障边界](../camctl/file-runtime.md#本地文件操作的完成与故障边界)。

### 取消取回

取回尚未完成时取消：

- 停止尚未开始的处理；
- 已经准备但尚未发布的文件不再发布；
- 相关操作结束后，按[中间文件清理规则](#取回中间文件的保留与清理)自动删除本次仍在 `staging` 中的半成品或完整副本，失败按有限清理与后续正常会话规则处理；
- 不删除正式源产物。

#### 拷贝期间的取消与文件操作收场

本节定义普通取回副本的拷贝取消。先可靠保存取消事实，阻止后续普通执行和重试，再按实际操作阶段收场。采用[按段提交的流式传输任务](../camctl/file-runtime.md#按段提交的流式传输任务)：主协程按段提交，线程内部连续按小块处理，段大小同时确定可靠进度的保存间隔。每个目标文件同一时刻只推进一个会改变它的操作；线程在小块之间检查停止请求，前一小块完成且仍允许继续时才推进下一块。不同文件的并发遵守相机拷贝限制，本地任务按[默认线程池规则](../camctl/file-runtime.md#本地文件执行使用默认线程池)执行。

取消生效后，分别检查源读取、本地文件操作和数据库进度操作；某一部分已停止不能替代其他部分的结束确认。先确认实际执行阶段，再按下表处理：

| 实际阶段 | 处理 |
| --- | --- |
| 下一段传输或其他普通文件任务尚未提交 | 不再提交，进入收场 |
| 分段传输或其他普通文件任务已经排队，确认尚未开始 | 尝试撤回；只有确认不会执行后才释放该任务占用 |
| 撤回与开始执行发生竞争，结果尚未确认 | 保留操作跟踪和资源占用，确认阶段后进入对应分支 |
| 分段任务已开始，处于小块之间或尚未开始段尾同步 | 线程检查停止请求，停止新增普通读写和同步，返回实际停止结果，无须完成整段 |
| 小块写入、截断或文件同步已经开始 | 跟踪实际完成或失败结果，随后不再继续下一块；调用协程取消等待不表示操作结束 |
| 文件同步已经完成，进度保存操作尚未提交 | 转入收场，不为待清理副本额外发起进度保存 |
| 进度保存操作已经入队或开始 | 按[数据库操作取消规则](../camctl/persistence-runtime.md#入队后的排队与取消)处理；已开始的事务确认实际结果，已成功提交的历史保留，取消仍然有效 |
| 源读取、本地读写和重试均已确认停止 | 按[半成品清理规则](#取回中间文件的保留与清理)核验已保存的取消结果和文件归属，再执行清理 |
| 本地文件操作仍未返回 | 继续等待实际结果，保留相应占用和文件；不因等待较久判定操作已停止或取消处理失败 |
| 已有调用结果或恢复证据仍不足以确认是否停止 | 保留相应占用和文件，按所属收场规则处理失败或未知，不能宣称清理完成 |

取回取消后，无须继续读取到段边界，也不为尚未保存进度的尾部专门发起同步。已经开始的同步及进度事务仍须跟踪实际结果；文件操作失败不推进可靠进度，状态库错误或提交结果未知继续按会话错误处理。清理、必要状态保存及结果核实属于收场操作，仍按自身资格执行。

操作结束确认前，不并发关闭其使用的文件句柄、删除或截断同一文件，也不将文件交给另一轮写入。同一相机的后续读取资格继续按[拷贝并发限制](file-copy.md#同一相机的拷贝并发限制)判定；本地文件是否可清理与相机是否可开始另一份读取分别确认。取消处理结果遵守[取消动作的完成时机](task-cancellation.md#取消动作的完成时机)，保存取消标记或发出停止请求均不单独表示取消处理成功。

例如，可靠进度为 256 MiB，当前段又写入 20 MiB 时取消：停止新增普通读写，跟踪已经开始的小块及源读取的结束，满足清理条件后删除该取回半成品。若进度事务已经开始，先确认它的实际结果，保留已提交历史。录像内部检查、修复及正式源产物的保留继续遵守各自契约，不套用取回半成品的删除资格。

验收覆盖表中各阶段、撤回与执行开始的竞争、取消后操作迟到完成或失败、同步完成但尚未提交进度，以及进度提交成功、失败和结果未知。确认取消后无新增普通读写或重试，实际停止前不关闭或清理相关文件；模拟处理中断后，依据已保存取消事实和实际文件状态恢复清理，取消结果不因重启改为继续取回。小块大小和段大小变化均不改变上述规则。

本地文件操作按[完成与故障边界](../camctl/file-runtime.md#本地文件操作的完成与故障边界)等待实际结果。小块处理用于在操作之间响应取消，底层持续不返回的故障由部署侧处置；后续启动按已保存取消事实及文件证据恢复。

#### 与来源取消及文件交接的关系

取消来源组不联动普通手动取回；具有自动预览用途的取回按[取消联动](preview-obtaining.md#取消联动)一并处理；取消寻址见[取消目标寻址](task-cancellation.md#取消目标寻址)。本次取回仍有效时，来源录像因组取消而结束，继续按其最终正式产物处理；没有产物的成员按既定无产物失败规则记录。

文件已经发布到 `ready` 后：

> `obtain_action_outputs` 可以进入终态。

但之后仍允许针对这次取回撤回尚位于 `ready` 的 delivery 文件。

已经：

```text
ready → processing
```

的文件进入不可撤回阶段。

即使主程序尚未真正开始发送字节，也不再由 CLI 撤回。

如果一个已终态的 obtain 动作被后续 cancel：

- 历史动作终态不改变；
- 只处理其仍可撤回的 delivery。
