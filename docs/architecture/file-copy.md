## 相机视频的断点续传

第一版要求相机视频拷贝到主机时支持跨主机重启的断点续传。拷贝因主机断电而中断后，后续实际启动的 `run` 在该处理仍有执行资格时，使用主机上已经可靠保留的部分继续拷贝，不因进程重启而统一从头取回整个视频。

已确认的运行前提是：相机内的源文件不会自行丢失，camctl 是这些文件的唯一访问者。拷贝对象为相机已经写完的视频文件，写完后内容和长度保持不变。camctl 按显式清理请求删除文件时，仍遵守[清理与取回并发规则](output-cleanup.md#清理与取回并发)；已经取得取回资格的请求恢复续传时继续持有原资格。

开始拷贝时确定源文件身份及其完整长度，后续续传继续读取同一份固定内容，并以该长度确定拷贝的结束位置。当前相机的文件写入完成依据见[停止成功与文件可读](camera-recording.md#停止成功与文件可读)；来源身份表示及停止结果未知时的对账方式仍需结合设备协议细化。

该要求适用于 camctl 将视频从相机拷贝到主机的流程，包括 `obtain_action_outputs` 取回、相机录像内部修复，以及[计时证据不足时的原片检查](camera-recovery.md#计时证据不足时的原片检查)所需的拷贝。后两者属于录像内部处理，不创建普通 delivery。主机向外部客户端传输文件由第三方主程序负责，其重试行为按文件交接专题处理。

续传需要保留相机源文件、主机上的未完成文件及所属处理任务之间的关联，以及能够可靠恢复的拷贝进度。已确认的进度变化按全局规则追加历史并同步更新投影。恢复同一次取回时沿用原请求和交付身份，未完成文件继续由 camctl 管理，不能发布到 `ready`。完成后的交付仍遵守本次取回的开始发布的条件。

### 同一相机的拷贝并发限制

第一版同一相机在同一时刻最多进行一份文件从相机到主机的拷贝。`obtain_action_outputs`、异常原片检查和内部修复所需的源文件拷贝共用这个限制，不能各自启动一份并行拷贝。同一产物的不同交付请求仍分别准备独立副本，依次取得拷贝机会，不合并请求或复用在途 delivery。

限制以源相机为范围；不同相机分别协调。从主机 `staging/derived/` 准备交付副本、主机上的媒体处理以及主程序对外传输，不占用相机的拷贝机会。它们继续遵守自身的执行资格与资源要求。

| 拷贝或设备操作情况 | 并发约束 |
| --- | --- |
| 同一相机已有一份文件正在拷贝 | 其他文件等待；分段保存进度期间仍属于同一份拷贝，不借段间间隙交错拷贝另一份文件 |
| 当前拷贝读取失败，仍有执行资格及重试预算，正在等待重试 | 保留该文件的拷贝机会，其他文件继续等待；到达重试时间后恢复原拷贝 |
| 一份文件的源内容已全部读取，且相应设备读取已结束 | 后续仅在主机进行的校验、修复、等待组成员或发布，不占用该相机的拷贝机会 |
| 拷贝被取消或最终失败，但实际读取尚未停止或无法确认已经停止 | 先完成对应停止与确认，不启动同一相机的另一份拷贝 |
| 拷贝被取消或最终失败，且已确认实际读取及后续重试停止 | 解除拷贝机会的保留，再选择其他具备条件的文件 |
| 相机继续录像，或需要执行必要的停止命令 | 按驱动兼容性执行控制操作，不要求它们等待整份文件拷贝完成 |

只有具备源文件读取资格、来源已写完且满足所属流程执行条件的文件，才可开始拷贝。排队不等于拷贝失败，也不消耗设备读取尝试次数；等待源录像结束的请求不占用拷贝机会。获得拷贝机会不授予新的取回资格，也不解除已有取回对源文件的清理保护。

正常调度、取消处理及重启恢复均使用同一限制，不能分别创建互不协调的拷贝通道。重启后保留每份文件原有的身份、进度与预算，按既有断点续传规则恢复；一次只恢复一份相机拷贝，不因存在多个未完成文件而全部并行启动。实际复制工作的暂停或结束，与源文件读取依赖的解除分别处理，后者仍须满足[准备完成与断电恢复](output-cleanup.md#准备完成与断电恢复)的持久化条件。

#### 等待重试时保留拷贝机会

取回、异常原片检查及修复输入拷贝使用相同规则：一份文件已经取得相机拷贝机会后，读取失败进入有限重试等待，仍为它保留下一次拷贝机会。其他文件即使已具备读取条件，也不能在等待期间开始拷贝。源文件内容固定，原半成品、可靠进度、身份、读取资格和剩余预算继续按既有规则保留。

读取重试使用本次运行的[通信重试间隔](configuration.md#通信重试间隔)。例如 A 已可靠保存 100 MB，读取失败且旧读取确认结束后，按默认配置等待 3 秒。此时 B 已准备好，也须等待；间隔到达且 A 仍具备重试资格时，A 从其可靠进度继续读取。A 完成源内容读取后，才允许选择 B 等候选文件。若 A 取消或最终失败，则在确认读取及重试已停止后解除保留。

拷贝机会的归属、重试等待与解除事实按历史和投影规则可靠保存。重启时先恢复已有保留关系：A 尚具备重试资格则继续等待或恢复 A，不能因重新加载候选文件而让 B 抢先。保留关系不增加重试预算；错误耗尽后仍按原有限失败规则结束，不通过反复新建拷贝重置预算。

保留范围仅为该相机的文件拷贝。录像、必要的停止命令及其他已确认兼容的控制操作继续按设备执行规则处理。该保留也不解除源文件的旧取回保护。

源内容读完并释放拷贝机会后，后续校验发现不一致而需要重拷时，按有限重拷规则重新参与候选选择；不能追溯恢复已经释放的保留关系，或打断此时正在拷贝的另一份文件。

#### 多个候选文件的选择顺序

每台相机独立选择待拷贝文件。先恢复和处理已有活动拷贝或等待重试的保留关系；只有没有此类占用或保留时，才在当前已具备拷贝条件的文件中选择一个。条件包括所属动作仍可执行、计划时间已到、源内容已写完、读取资格成立，以及所属流程允许本次读取。尚未形成文件或仍在等待来源结束的请求不阻挡其他合格候选文件。

排序使用负责发起这次拷贝的动作，而不是一律使用源录像动作：

| 拷贝用途 | 用于排序的所属动作 |
| --- | --- |
| 用户请求取回原片 | 本次 `obtain_action_outputs` |
| 异常原片检查 | 需要该检查的 `camera_record` |
| 内部修复所需的源文件拷贝 | 需要该修复的 `camera_record` |
| 校验不一致后的有限重拷 | 沿用原拷贝所属动作，不按重拷发生时间改排 |

合格候选文件按以下顺序比较，前一项相同才比较后一项：

1. 所属动作的 `scheduled_at`，从早到晚。
2. 所属计划的 `plans.id`，首次受理较早的计划优先。
3. 所属动作在原计划 `actions` 数组中的位置，从前到后。
4. 同一动作内文件条目的首次登记顺序；登记时保存固定顺序，后续恢复沿用。

内部检查或修复不会仅因用途而取得额外优先级。相应录像的计划时间较早时，其已具备条件的输入拷贝排在较晚的取回动作之前；用户取回的计划时间较早时，顺序相反。

例如，09:00 录像的修复输入与 10:00 的取回请求在本次调度时均可拷贝，且该相机没有活动拷贝或保留关系：先处理修复输入。若修复输入尚不能读取，则可以开始该取回；取回开始后，即使较早录像的修复输入随后具备条件，也须尊重当前文件的拷贝及重试保留关系。

每次释放拷贝机会后重新从当时合格的文件中选择。一次取回包含多份文件时，不为整个取回动作预占相机；同一动作后续才确定的文件追加登记顺序，不改变已登记条目的顺序，也不扩大已固定的选择集合。

正常调度和重启恢复使用同一组持久化排序依据；数据库查询返回顺序、目录枚举顺序和内存加载顺序不能代替它们。排序依据无法可靠读取或解释时，按状态库错误处理，不猜测先后。取得机会后遵守原身份、进度及有限预算；排序本身不授予读取资格、不修改删除限制，也不提前执行尚未到时间的动作。

### 读取工作的发现与唤醒

数据库保存每份拷贝的机会归属及未完成责任，状态分类和事务边界见[相机读取机会](../camctl/database/waiting.md#相机读取机会与未完成责任)。本节适用于普通取回、自动预览、录像原片检查、修复输入、读取重试及整片重拷。

| 变化或入口 | 负责流程与后续处理 |
| --- | --- |
| 会话启动 | 从交付、录像内部处理及独立收场责任恢复工作；先恢复已有机会归属，再选择候选 |
| 独立 `submit` 受理新取回、拍摄或取消计划 | 按[新计划发现](scheduling-execution.md#新计划发现与内存调度缓存)合并计划，再由当前 `run` 按资格执行；受理取消计划不等于目标取消已生效 |
| 计划时间、重试时间或适用截止时间到达 | 调度器或所属流程安排单调钟唤醒，到时重新判断；新增的更早截止时间参与当前等待 |
| 来源结束或产物处理完成 | 保存结果后唤醒依赖方，按逐来源结果推进选择、资格判断及建档；包括修复成品和多来源取回 |
| 普通交付或录像内部拷贝完成建档 | 建档成功后把工作纳入调度范围，检查源相机当前机会及其他条件 |
| 原持有者释放读取机会 | 保存释放事实后，重新检查同相机的合格候选 |
| 读取失败但可以重试 | 保留原机会，安排重试时间；到时仍被其他条件阻挡时，继续按对应设备变化推进 |
| 摘要不一致后登记重拷，随后完成目标文件重置 | 分别保存轮次和重置结果；读取准备条件齐备后重新参与候选选择 |
| 拍摄、控制操作或设备核实改变兼容性 | 设备流程处理可靠结果后，重新检查同设备的相关工作；覆盖预览让路、拍摄结束、取消、过期及控制通道释放 |
| 取消生效、最终失败或实际调用收场结束 | 所属流程推进自身及独立收场责任；满足条件并保存机会释放后，再选择其他候选 |
| 后续会话加载新配置并通过启动时间检查 | 依据本次配置和原持久化责任恢复，沿用原身份、已用次数及终态 |

运行期间由这些业务变化和截止时间驱动重新调度；启动检查覆盖上次提交后通知前退出的责任。线程返回由负责流程处理，设备自主结束按驱动声明的有限查询、完成等待或恢复规则取得依据。通知的保存、合并及取消后结果接手遵守[调度通知交接](../camctl/implementation.md#调度通知与待处理工作的交接)。

调度按受影响设备或工作范围分批查询未完成责任，缓存只保留所需详情。尚未加载的候选仍参与既定排序；授予前必须取得足以确定优先候选的完整依据。分批加载尚未完成时继续安排后续处理，缓存淘汰不结束调度责任。初始化期间的新提交遵守会话接纳规则；正常退出前仍按[会话接管](protocol-session.md#会话接管协议)检查持久化责任。

### 先保存文件，再记录进度

拷贝按段保存进度。数据库中的进度表示从文件开头起，已经连续写入并可靠落盘的字节数。进度为 `C` 时，主机文件的前 `C` 字节必须与源文件对应内容一致；进度的推进不能跳过字节或包含尚未可靠保存的数据。

每段按以下顺序处理：

1. 从源文件的对应位置读取数据，连续写入主机文件。
2. 清空写入缓冲并完成文件同步；文件新建或路径发生变化时，同时保证所需目录变更已经落盘。
3. 在数据库事务中追加已保存进度的历史并同步更新投影，提交成功后继续下一段。

进度按实际连续写入并同步成功的字节数计算。写入或同步失败时不推进进度；进度事务失败或提交结果不确定时停止继续拷贝，后续恢复先确认数据库实际提交的进度。文件操作及设备读取不占用数据库写事务。

### 进度保存的分段大小

从相机读取文件时，按主机本地配置确定每段最多新增多少字节后可靠保存进度。取回、异常原片检查及修复输入拷贝共用该规则。本节集中定义默认值和合法范围：

| 配置项 | 默认值 | 合法值与含义 |
| --- | --- | --- |
| `copy.segment_size` | `"128 MiB"` | 带单位的容量，换算后为正整数个字节；一次分段进度保存前，最多新增的连续文件字节数 |

配置按[本地配置加载规则](configuration.md#本地配置的加载与更新)取得。省略时使用默认值；显式值遵守[容量配置的表示](configuration.md#容量配置的表示)，换算结果须大于 0。段大小属于本次会话的处理配置，启动时读取、会话内固定，后续会话按当次配置组织剩余数据；动作身份、已保存进度及累计读取与重拷次数继续沿用。

以下规则以源文件身份、固定长度、可靠进度及执行资格均已确认，并已按恢复规则处理主机未完成文件为前提。设本段开始前的可靠进度为 `C`，源文件长度为 `N`，生效段大小为 `S`，三者均以整数个字节计量。本段目标结束位置为 `E = C + min(S, N - C)`。

| 剩余数据量 | 处理 |
| --- | --- |
| `N - C = 0` | 已无文件内容需要读取，不新增空进度段，进入所属流程的完整性确认 |
| `0 < N - C < S` | 按实际剩余字节处理最后一段，到 `N` 后同步文件并提交进度，不等待凑满一段 |
| `N - C = S` | 处理一整段，到 `N` 后同步文件并提交进度，随后进入完整性确认 |
| `N - C > S` | 处理到 `C + S`，同步文件并提交进度；确认提交成功后，从新的可靠位置组织下一段 |

每段按较小数据块连续读取并写入 `[C, E)`，不为等待整段完成而将整段内容攒在内存。采用[按段提交的流式传输任务](../camctl/file-runtime.md#按段提交的流式传输任务)：主协程提交本段范围，工作线程负责段内源数据读取、小块写入及必要同步；主协程取得成功结果后组织数据库进度保存。读取块与读写缓冲容量独立于段大小；实际写入不越过本段目标位置。前一段进度提交成功后才推进下一段。分段保存期间继续保留本文件的相机拷贝机会。

普通取回取消时，按[拷贝取消与文件操作收场](obtaining-outputs.md#拷贝期间的取消与文件操作收场)在小块操作之间停止推进，跟踪已经开始的读写和事务，不要求完成当前整段；半成品的清理资格由取回流程判断。

尚未达到本段目标时读取提前结束，不视为合法的最后短段，按既有读取失败规则处理；写入、同步或进度保存失败仍遵守各自契约，不把未确认的尾部加入可靠进度。取得数据时持续更新无数据超时的观察，不能等整段完成才确认收到数据；文件同步和进度保存不计入相机无数据等待。

后续会话调整段大小时，从数据库已经确认的字节位置 `C` 继续计算下一段，不把 `C` 向上或向下对齐到新段大小的倍数。配置调整不改写既有进度历史，也不重新读取已确认的数据；未确认尾部继续按恢复表处理。

该默认值用于减少文件同步与永久进度历史的数量，同时允许中断后重读当前未确认的一段。正常逐段处理时，每 GiB 文件对应 8 次分段进度提交，不包含创建、摘要及最终结果等其他事务。段大小不是内存缓冲容量，也不保证固定的进度更新时间或完成时延；目标主机联调须测量实际拷贝吞吐、文件同步和进度提交耗时，再按部署负载调整。

验收覆盖配置缺省、合法覆盖和非法值，剩余字节数为 0、小于、等于和大于一段，读取块跨越段边界以及中途提前结束。改变读取块大小后，文件字节、可靠进度及段边界保持正确；在文件同步和数据库提交前后分别中断，按实际已保存进度恢复。另覆盖后续会话改用更大或更小的段，原进度不是新段大小倍数时仍从原位置继续；读取与重拷已用次数不因分段或配置变化而清零。

### 重启后选择续传位置

以下规则适用于处理任务仍有执行资格、源文件身份及未完成文件关联可可靠确认的情况。设源文件完整长度为 `N`，数据库已保存进度为 `C`，主机未完成文件当前长度为 `L`。这些量均以字节计，合法进度满足 `0 ≤ C ≤ N`。先处理无法可靠判断或数值越界的情况，再按文件是否存在及长度关系处理。

| 恢复时的情况 | 处理 |
| --- | --- |
| 文件不存在，`C = 0` | 创建未完成文件，从源文件开头开始 |
| 文件存在，`L = C < N` | 从源文件及主机文件的偏移 `C` 处继续拷贝 |
| 文件存在，`C < L ≤ N` | 将未被进度确认的尾部截去，使文件长度回到 `C`，再从 `C` 继续 |
| 文件存在，`L = C = N` | 全部字节已经保存，进入后续完整性确认及相应处理，不再读取视频数据来续传 |
| 文件不存在但 `C > 0`，或 `L < C` | 已记录的可靠数据缺失，保留诊断并按错误处理，不能跳过缺失部分继续拷贝 |
| `C` 超出合法范围，或 `L > N` | 状态不符合拷贝约束，保留诊断并按错误处理 |
| 文件、进度或身份无法可靠读取或确认 | 停止依赖这些信息的续传判断，不能当作文件不存在或进度为零 |

例如，数据库记录前 100 MB 已保存，文件当前有 110 MB，且未超过源文件长度时，恢复先截去后 10 MB，再从 100 MB 处续传。已记录进度内的数据保留，未被记录确认的尾部允许重新读取。截断失败时不能继续写入；恢复操作再次中断后仍按上表判断。

最终文件必须与固定源文件逐字节一致。续传不能留下空洞、重复片段或多余尾部；读取提前结束但尚未达到 `N` 时不能判定拷贝完成。文件长度及进度相同只说明字节范围已经保存，读取及校验还须满足[读取正确性与文件校验](#读取正确性与文件校验)的要求。

进度保存遵守[分段大小规则](#进度保存的分段大小)，设备按指定位置读取的具体能力及接口仍需细化。

### 文件读取的无数据超时

相机文件内容读取使用本地配置 `devices.<id>.copy.read_idle_timeout_s`，默认 **10 秒**，允许配置为有限的正秒数。该值采用本次运行中对应设备的配置，拷贝、重试和恢复在本次运行内使用同一值；执行计划不覆盖该值。

超时计量的是驱动正在等待源文件新数据时，连续未取得数据的时间。使用当前进程的单调钟计时：开始等待时启动计时，每次取得非空的源文件内容字节后重新计时，连续无数据达到阈值时判定本次读取超时。首批数据也受此限制。只要持续取得数据且尚未读完已知长度，就继续当前读取，不设置整份文件必须在固定时长内完成的截止时间。

| 当前读取阶段或结果 | 超时处理 |
| --- | --- |
| 已开始等待源数据，连续无数据尚未达到阈值 | 继续等待，仍处理取消等事件 |
| 正在等待源数据，连续无数据达到阈值 | 记录读取超时，按读取失败与有限重试规则处理 |
| 取得非空源文件内容，尚未读完 | 重新计时并继续；无须等整个分段完成或写入数据库后才确认收到数据 |
| 只收到设备日志、控制响应或其他非文件内容 | 不作为新文件数据，不重置无数据计时 |
| 主机正在写入、落盘、保存进度、计算摘要或处理媒体，当前未等待源数据 | 不计入相机无数据超时；进入下一次源数据等待时重新计时 |
| 正在排队、等待重试时间或等待源录像结束 | 尚未等待源数据，不启动该计时 |
| 已读完已知源文件长度，且读取正常结束 | 结束读取计时，进入后续校验 |
| 源读取异常终止或未到已知长度便提前结束 | 直接按已确认的读取错误处理，无须再等待无数据阈值 |

驱动须能在完整分段返回前识别文件数据的到达；分段大小、内部缓冲或调用方尚未收到整个分段，不能把持续有数据的传输误判为停滞。收到数据与可靠保存进度是不同事实：数据到达可以重置计时，数据库中的进度仍只按完成落盘的连续字节数推进。

超时只使当前读取尝试失败。仍有读取重试额度时，停止并确认本次实际读取结束，按既有规则保留拷贝机会、等待后从可靠进度续传；额度耗尽时结束该文件的拷贝。超时不消耗摘要不一致的重拷额度。内部历史保存采用的超时阈值、读取失败原因及可靠进度。普通取回通过交付状态和逐项最终失败报告结果；录像检查或修复中的内部读取通过所属动作、检查或修复的适用公开结果表达。仅内部尝试或进度变化、公开字段未变时，不产生报告变化。

主机断电期间不累计无数据时间。恢复后实际开始等待源数据时建立新的单调钟计时，采用本次运行的阈值并沿用原读取尝试；重启前已保存的超时失败仍保留，新增尝试资格按本次上限与累计次数判断，不因新计时而撤销。设备控制、文件元数据查询和摘要计算采用各自适用的超时与错误规则。

### 按文件累计读取尝试

读取尝试上限由本地设备配置 `devices.<id>.copy.max_read_attempts` 提供，默认 **3 次**，包含第一次；允许配置为大于等于 1 的整数。执行计划不覆盖该值。每份文件按本次运行中对应设备的上限判断新增尝试资格，保存实际采用的依据及处理归属；累计次数跨运行保留，上限变化按[本地配置变化与未完成工作](configuration.md#本地配置变化与未完成工作)处理。

一次读取尝试可以连续读取多段数据，也可以跨主机断电恢复继续进行。成功读取新的一段不结束该尝试、不增加次数，也不清零之前的失败。只有驱动明确报告读取错误，才将当前尝试记录为失败，包括已确认的读取超时、异常终止或未达到源文件固定长度便提前结束；仍具备执行资格且未达到上限时，等待后开始下一次尝试，从可靠进度继续读取。

开始读取后的已用次数等于“1 + 因读取错误而实际开始的重试次数”。摘要不一致引发的整片重拷另外记录轮次，沿用当前读取尝试的计数，不消耗读取错误重试额度，也不清零之前的读取失败。设备读取记录关联所属文件、读取尝试身份与整片拷贝轮次，以区分一次读取尝试中发生的不同重拷轮次。

该规则统一用于取回、异常原片检查及修复输入拷贝。预算按所属处理中的每份文件分别保存，不由整个取回动作或整台相机共用。不同请求对同一 `output_id` 的独立交付分别计数；同一请求重送、同一文件分段及原内部处理的恢复均复用原记录。

| 文件读取情况 | 次数与处理 |
| --- | --- |
| 仅在排队，尚未开始读取 | 已用次数为 0，不因等待消耗次数 |
| 首次开始读取 | 记录第 1 次尝试后开始读取 |
| 当前尝试成功读取一段，文件尚未读完 | 继续同一次尝试，按已确认进度推进，不重置计数 |
| 全部内容读完后摘要不一致，且具备整片重拷资格 | 沿用当前读取尝试计数，由独立重拷预算控制下一轮从头读取 |
| 驱动明确报告读取错误，已用次数小于上限，处理仍可执行 | 保存当前失败及重试等待，保留拷贝机会；下一次尝试沿用可靠进度并增加已用次数 |
| 驱动明确报告读取错误，已用次数大于或等于本次上限 | 该文件读取最终失败；确认实际读取和重试停止后解除拷贝机会保留 |
| 主机断电中断当前尝试，未保存该尝试的明确失败结果 | 重启后核实进度并继续原尝试，不因重新打开连接、恢复文件或再次启动进程增加次数 |
| 重启前已有明确失败及重试等待记录 | 保留原失败，按本次上限与累计次数判断能否新增尝试；不能将其解释为尚未失败的原尝试继续读取 |
| 当前处理已取消或终态 | 按原有规则停止及收场，不开启新的读取尝试 |
| 历史、次数或提交结果无法可靠确认 | 按状态库错误及恢复规则处理，不默认成 0，也不猜测已耗尽 |

例：第一次在 100 MB 处读取失败，第二次续传到 500 MB 后失败，第三次续传到 900 MB 后失败。使用默认上限时，该文件最终失败；中间增加的可靠进度不会让它获得新的三次机会。若第三次只是被主机断电中断，恢复后仍可继续第三次尝试。

开始首次或下一次尝试前，将尝试身份、已用次数及所属文件关联可靠保存，再发起读取。恢复已有尝试不重复登记新尝试；同一失败结果不重复计数。失败、重试等待及拷贝机会保留遵守同一组持久化事实，取消或数据库错误不能绕过有限预算继续发令。

开始下一次尝试仍须确认前一次实际读取已经停止，不能因驱动报告超时就并行发起另一条读取；实际读取是否停止无法确认时，继续按并发限制保留诊断和拷贝机会。

#### 实际读取结束与所属结果

读取尝试记录实际源读取的结果，读取流程记录是否取得可用副本及所属收场。拥有者确认实际结束后先持有原 `ReadEnd`；其中 `clean ReadEnd` 指拥有者观察到 `stopped=true` 且读取没有错误，内容是否完整另按可靠进度判断。随后通过本地完整性校验确定原文件责任是否结束或继续重拷。该技术校验不表示读取尝试已经成功；需要继续重拷时，原尝试仍为 RUNNING。原 `AttemptFinish` 一旦确定，就与完整操作键共同保留，可靠保存前不执行依赖它的发布、媒体检查、修复或源依赖、工作文件保护释放。相机读取机会与这些保护分别判断：源内容已全部读取且设备读取实际结束后，只有主机校验或媒体处理的阶段按[同一相机的拷贝并发限制](#同一相机的拷贝并发限制)释放相机机会，后续读取按[多个候选文件的选择顺序](#多个候选文件的选择顺序)参与调度；该释放不结束原读取尝试，也不解除源依赖或工作文件保护。已经确定的完整结束申请优先保存，不能被后续取消或旧主机恢复假设覆盖。

读取结束事务的 `occurred_at` 在完整 `AttemptFinish` 首次确定时取得，包括当时适用的流程处置，遵守[历史事件时间字段](../camctl/database/history-formats.md#历史事务与事件字段)。较早取得的原实际 `ReadEnd` 与该结束申请分别持有；不能用实际源结束的较早时刻记录之后才生效的业务取消。结束申请保存回滚或提交未知时，重送保持原完整申请、时刻和操作键。

绑定异常时采用上述实际结束事实，要求当前拥有者确实持有可靠原 `ReadEnd`。可靠进度等于源长度以及新进程重新打开状态库，都不能替代实际结束依据；没有持有原结束事实的跨进程恢复仍采用既定主机边界、原意图与绑定恢复规则。后续协作者不可用不改变本次运行固定的读取配置。

下面的决策表按行从上到下判断，采用第一个满足全部条件的分区。先保存已经确定的完整结束申请；尚未确定结束申请时，先保持读取流程已有终态，再处理可靠业务取消，最后判断绑定、内容校验及读取预算。这一顺序遵守[设备绑定异常的影响范围](configuration.md#设备绑定异常的影响范围)。只有发起该拷贝的动作取消已经可靠生效，才属于业务取消；等待协程取消、会话退出及停止请求已发送均不能单独证明业务取消或源实际停止。

| 原结果与源实际状态 | 内容或所属条件 | 原尝试与读取流程 | 保护与后续处理 |
| --- | --- | --- | --- |
| 已确定并持有完整 AttemptFinish 结束申请，保存尚未可靠完成 | 任意后续取消或恢复输入 | 按原结果、原 ticket 和原完整操作键核实并保存，不重新计算结果。 | 保存前保留保护，不执行依赖处理；保存后沿原所属事实收场。 |
| 原读取流程已有最终结果，迟到的源实际结果结束原尝试 | 原流程 SUCCEEDED、FAILED、CANCELED 或其他终态 | 保存原尝试的真实结果，保持原流程状态、错误及配置；后到取消不改判原终态。 | 只处理仍适用的独立取消或保护责任，不重开原流程。 |
| 源完整返回且实际结束无错误 | 业务取消已可靠生效，原读取流程仍为 PENDING 或 ACTIVE，且该副本处理主动取消 | 原尝试 SUCCEEDED，使用 observed/read_returned 且没有读取错误；原流程 CANCELED。 | 保存真实结果后按取消责任收场；不执行所属发布、检查或修复，不把完整实际结果改为 read_stopped。 |
| 拥有者已经主动停止源，并确认实际停止 | 业务取消已可靠生效，文件尚未读完整，没有明确的设备读取错误，且没有优先保存的完整实际结果 | 原尝试 UNKNOWN，使用 observed/read_returned，错误为 read_stopped、阶段为 read；原读取流程 CANCELED。 | 保持原次数和可靠进度，不登记 FAILED 或读取错误重试；取消收场可靠保存后才解除适用保护。 |
| 原 RUNNING 的可靠进度已经等于源长度，持有原实际 clean ReadEnd | 尚需本地完整性校验且原设备绑定匹配，原所属责任仍可执行 | 沿原结束事实完成校验并保存原结果，不重新打开源，不重复读取字节。 | 原结束事实与待保存结果保持，保存可靠前不执行依赖处理。 |
| 原 RUNNING 的可靠进度已经等于源长度，持有原实际 clean ReadEnd | 原设备绑定缺失或驱动不匹配，源端支持摘要但所需源摘要尚未可靠取得 | 原尝试 SUCCEEDED，使用 observed/read_returned 且没有读取错误；未终态的读取流程按原绑定事实保存 FAILED/device_binding_unavailable。 | 保持原源摘要为空与原未校验事实，不发布、不检查或修复。原完整 Finish 与 key 先可靠保存，随后按所属绑定错误事务结束普通交付或内部检查／修复并释放适用保护；不调用新读取或摘要，不使用假设恢复覆盖实际结果。 |
| 原 RUNNING 的可靠进度已经等于源长度，持有原实际 clean ReadEnd | 原设备绑定缺失或驱动不匹配，所需源摘要已经可靠取得，或原设备明确不支持摘要 | 继续本地技术校验，按实际校验结果保存原尝试和流程；绑定异常本身不使纯本地工作失败。 | 不调用异常设备；副本有效后继续本地发布、检查或修复。内部还有独立未完成设备责任时，按该责任的绑定规则处理，保持已成功 READ 的事实。 |
| 原 RUNNING 的可靠进度已经等于源长度，没有原可靠 ReadEnd | 原续传资格成立，旧实际拥有者已经可靠结束 | 沿原 ticket 在 source_size 位置打开本次会话并确认本次实际结束；不新增尝试，不重新读取已保存字节。 | 本次实际结束事实先持有，再执行本地完整性校验；不能用摘要代替驱动返回。 |
| 原 RUNNING 的可靠进度已经等于源长度，没有原可靠 ReadEnd | 原续传资格不成立或旧实际拥有者尚未可靠结束 | 保留原未结束责任，不执行校验来补造读取成功。 | 保存对应恢复诊断，保留原源保护；相机机会按实际读取是否可靠结束及后续是否仍需读取的独立规则判断。 |
| 没有可靠实际停止依据 | 任意读取进度、停止请求或业务取消 | 保留原未结束尝试和流程，不新增尝试，不把请求停止记作结束。 | 实际拥有者继续确认原读取，保留 slot 与源保护。 |
| 源实际结束且明确报告读取错误 | 未取得可靠成功结果 | 原尝试 FAILED，记录原读取错误；可靠业务取消已生效时，未终态流程按取消规则结束为 CANCELED，否则按读取错误预算决定重试或失败。 | 仍有普通读取执行资格时，重试沿可靠进度；读取耗尽后结束所属业务并解除适用保护。业务取消已生效时不发普通重试，沿独立取消责任收场。 |
| 源完整返回且实际结束无错误 | 摘要通过或明确不支持摘要 | 原尝试 SUCCEEDED；可用副本准备完成后读取流程 SUCCEEDED。 | 沿已保存副本推进所属发布、检查或修复。 |
| 源完整返回且实际结束无错误 | 摘要不一致，仍可新增重拷 | 原尝试保持 RUNNING；重拷决定增加独立次数与轮次，读取次数不变。 | 原 ticket 继续承担该文件的读取责任，当前无效副本不得被使用。 |
| 源完整返回且实际结束无错误 | 摘要不一致且本次新增重拷预算耗尽 | 原尝试 SUCCEEDED；读取流程 FAILED，所属错误为 checksum_mismatch。 | 不新增读取错误重试或重拷；可靠保存所属失败后解除适用源依赖与机会。 |
| 拥有者已经主动停止源，并确认实际停止 | 没有可靠业务取消，文件尚未读完整 | 保留原未结束尝试与流程，不把等待取消或会话退出记作业务取消或读取错误。 | 按原资格保留责任与进度，后续继续原尝试；不提前解除源保护。 |

未定义或无法可靠解释的结束事实停止依赖处理并保留诊断，不补造退出码、完整文件、成功摘要或读取失败。

主机写入、落盘、状态库及摘要计算错误按各自错误契约处理，不伪装成相机读取错误。文件字节读完后仍须通过后续校验，读取次数尚有剩余不代表副本已经有效。摘要不一致的从头重拷及其额度关系见“摘要不一致后的有限重拷”。

内部记录保存该文件采用的读取上限、已开始的尝试次数、各次明确失败及当前等待或结束原因；报告表达交付结果及最终错误。取回中某份文件耗尽次数，继续按[部分成功](obtaining-outputs.md#部分成功)处理其他项；内部拷贝失败与录像结果按相机专题的规则分别判定。半成品与源文件遵守各自保留、清理契约。

### 读取正确性与文件校验

相机驱动负责从指定位置正确读取源文件，并检测、报告传输错误；camctl 负责连续写入、落盘和恢复位置的正确性。设备接入时必须确认驱动能够履行可靠读取的契约。读取失败或结果无法确认时，不能仅凭取得了足够长度的数据就认定取回成功。

源端摘要是额外校验能力，不是所有相机的必备条件。设备具备该能力时，取回完整视频后比较源端与主机端摘要；明确不具备该能力时，以已确认的可靠读取契约和正确续写流程为依据完成取回。

当前相机已确认能计算源文件的 SHA-256，采用源端与主机端 SHA-256 比较；其通信方式见[通信方式与查询能力](camera-recording.md#通信方式与查询能力)。其他相机由对应驱动说明其读取和摘要能力；具体命令、返回格式、二进制数据读取和错误识别方式仍需在设备适配时核实。

主机端仍须计算最终文件的 SHA-256，并作为报告中的 `sha256` 提供给客户端，用于检查后续收到的文件。该摘要对应实际交付内容；它与可选的源端比较承担不同职责。

完成可靠读取、文件落盘及主机摘要计算后，按下表处理源端校验：

| 源端摘要能力 | 获取或比较结果 | 处理 |
| --- | --- | --- |
| 已确认支持 | 摘要相同 | 校验通过，继续该视频的后续处理 |
| 已确认支持 | 摘要不同 | 内容不一致，按“摘要不一致后的有限重拷”处理，不将该副本用于交付或修复 |
| 已确认支持 | 摘要获取或比较失败、结果未知 | 保留诊断并按错误处理，不能当作设备不支持而跳过校验 |
| 已确认不支持 | 无源端摘要 | 按可靠读取及正确续写的结果继续处理，主机摘要仍用于客户端校验 |
| 能力尚未确认 | 无可靠判定 | 先确认设备能力，不能直接归入“不支持”分支 |

成功取得的源端摘要关联同一份内容固定的源文件，可以在后续取回中复用。摘要及比较结果按全局历史规则保存；能力不支持、获取失败和内容不一致分别表达。

### 摘要不一致后的有限重拷

源端与主机端 SHA-256 不一致时，当前主机副本无效，不能交付或用于修复。camctl 保留相机源文件，在有限次数内从头重拷同一视频；每次重拷完成后重新校验，仍不一致且次数耗尽时报告该视频拷贝失败。

| 当前处理是否仍允许执行 | 剩余重拷次数 | 处理 |
| --- | --- | --- |
| 是 | 还有次数 | 持久化本次重拷决定，再从源文件开头重新拷贝 |
| 是 | 已耗尽 | 该视频拷贝失败，不交付或使用无效副本 |
| 否，例如处理已被取消或已终态 | 任意 | 不开始新的重拷，按原有取消或终态规则处理 |
| 执行资格或次数无法可靠判断 | 无法确认 | 保留诊断并按错误处理，不能获得新的重拷次数 |

整片重拷上限由本地设备配置 `devices.<id>.copy.max_recopies` 提供，默认 **额外 1 次**，允许配置为非负整数；首次拷贝不计入重拷次数。使用默认值时，首次完整拷贝摘要不一致后允许从头重拷一轮，这一轮仍摘要不一致则该文件最终失败。设为 0 时，首次摘要不一致即失败。

执行计划不覆盖该值。每份文件采用本次运行中对应设备的重拷上限，保存实际采用的判断依据；已消耗次数跨重启保留，仅在新增轮次时比较本次上限。已登记且未结束的轮次按原进度恢复，已终态的处理不因提高上限重新开始。重拷仍属于原处理任务，同一次取回保留原请求、产物和交付身份。

读取错误重试与摘要不一致重拷各有独立预算，按同一文件分别累计：

| 本次处理结果 | 使用的预算与后续处理 |
| --- | --- |
| 读取明确报错，尚可继续读取重试 | 当前读取尝试失败；下一次读取尝试增加读取计数，沿用本次可靠进度；重拷计数不变 |
| 读取明确报错，读取尝试上限已达到 | 该文件最终失败；即使仍有重拷额度，也不能绕过读取失败继续拷贝 |
| 全部内容读完但摘要不一致，仍有重拷额度 | 增加重拷计数并开始新一轮从零拷贝；读取计数不变，已发生的读取失败仍保留 |
| 全部内容读完但摘要不一致，重拷额度已耗尽 | 该文件最终失败；剩余读取重试额度不能替代重拷额度 |
| 当前轮次被主机断电中断 | 恢复原轮次及读取尝试，保留两项计数，不额外消耗次数 |
| 已取消、已终态，或预算事实无法可靠确认 | 按取消、终态或状态库错误处理，不通过另一项预算重新开始 |

例如已发生两次读取错误，正在第 3 次读取尝试；读完后发现摘要不一致，只要尚有重拷额度，就可以从头重拷，读取计数仍为 3。若这轮重拷再次发生读取错误，该文件立即达到读取失败上限；若完整读完，则继续按摘要结果与剩余重拷额度判断。任何成功分段或新重拷轮次都不补满读取预算。

开始每次重拷前，在同一数据库事务中记录原副本无效、消耗一次重拷次数及新一轮从零开始的拷贝状态，并同步更新投影。提交成功后才重新准备主机文件，原无效副本的进度不再作为这一轮的续传依据。记录失败或提交结果不确定时，先确认数据库事实，不能直接重置文件或重新分配次数。

重拷过程中仍支持断点续传。若决定已提交、文件尚未重新准备时断电，恢复继续执行这次已经计数的重拷；若已经保存新一轮的部分数据，恢复从该轮已确认进度继续。恢复同一轮重拷不重复消耗次数，也不能把前一轮的无效数据接到新一轮文件中。

次数耗尽的失败仅说明这次主机拷贝未取得有效副本，不据此判断相机源文件损坏。取回请求的其他成功项继续按部分成功及开始发布的条件规则交付；内部修复的失败与录像结果按[相机录像](camera-recording.md)的证据规则分别处理。相机源文件仍遵守显式清理规则。

普通取回的交付最终失败使用[业务错误登记](../../protocol/errors/workflow-codes.json)中的 `checksum_mismatch`，阶段为 `source_read`。详情保存判定时实际采用的 `max_recopies` 和原累计 `recopies_used`。该错误要求已有可靠的摘要不一致事实，并且本次上限小于或等于原已用次数；尚有重拷资格时不提前保存终局失败。读取错误次数与原已登记轮次保持，不能使用 `read_attempts_exhausted` 表达摘要不一致。录像内部输入仍通过所属检查或修复的适用结果表达失败，不创建普通交付。

读取尝试保存设备实际读取的结果，副本校验与所属处理保存本地业务结果。主机已取得完整内容且设备读取正常结束，随后摘要不一致，并不构成驱动报告的读取错误。原尝试在仍可重拷时继续承担同一读取责任。下表适用于未取消且原读取流程未终态的正常处置；已有完整待保存结果、业务取消和原流程终态先按“实际读取结束与所属结果”的决策表处理。该责任结束时按下表保存，不能因副本无效补造设备读取失败。

| 实际读取及本地校验结果 | 原读取尝试 | 原读取流程及所属处理 |
| --- | --- | --- |
| 完整读取正常结束，摘要校验通过 | 保存 `SUCCEEDED`，保留实际 `read_returned` 结束依据 | 读取流程按成功结束，继续副本准备及适用处理 |
| 完整读取正常结束，摘要不一致，仍可新增重拷 | 保持原 `RUNNING` 身份及已用读取次数 | 保存独立重拷决定，继续原责任，不提前结束所属处理 |
| 完整读取正常结束，摘要不一致，不能新增重拷 | 保存 `SUCCEEDED`，错误为空，保留实际 `read_returned` 结束依据 | 读取流程以 `FAILED` 结束并保存 `checksum_mismatch`；交付或内部处理分别按其失败规则收场 |
| 设备明确报告读取错误 | 保存 `FAILED` 及真实读取错误 | 按读取预算选择等待重试或读取耗尽的终局；不消耗重拷次数 |
| 完整内容或设备读取实际结束不能可靠确认 | 不保存上述成功结果 | 保留原责任及保护，按对应调用、停止或恢复规则处理；摘要或文件长度不能代替实际结束依据 |

主机重启、同一请求的重试和校验结果的重复处理均不能重置或重复消耗已确定的次数。内部历史分别保存读取尝试上限与已用次数、重拷上限与已用次数，并保留失败原因及轮次关联；这些过程变化只有影响公开业务结果时才产生报告责任。

## 自动预览读取与拍摄协调

自动预览读取遵守[读取调度](preview-obtaining.md#读取调度)：兼容时并行；不兼容时让已开始的一份文件本次读取尝试结束，再优先执行到时拍摄。尚未开始的下一文件或读取重试等待拍摄，不因保留拷贝机会而阻塞控制。现有超时、有限重试、取消和恢复规则继续适用。

## 文件完成、产物登记与 SHA-256

文件完成表示已有可靠依据确认写入结束、内容固定及完整长度。SHA-256 是对文件内容计算得到的校验值；完成依据不自动提供该值。没有可复用结果时，计算 SHA-256 需要处理完整文件内容。当前相机的停止成功保证用于确认文件完成，源端校验能力用于取得源文件 SHA-256，两者分别按驱动契约使用。

| 产物登记时的事实 | 保存与处理 |
| --- | --- |
| 已满足适用登记条件，已有该固定文件可靠的 SHA-256 | 保留已有文件校验值；本次新取得且尚未保存时，与产物登记一并保存到文件记录 |
| 已满足适用登记条件，尚未取得 SHA-256 | 文件记录表达尚未取得，产物按既定时点登记；不额外要求所有产物在登记前计算 SHA-256 |
| 文件完成、身份或其他必要登记条件尚未满足 | 继续所属核实或处理流程，不能仅因已有 SHA-256 就登记产物 |
| 适用的内部处理尚未完成其必需校验 | 按该处理的校验及结束条件推进，不以产物登记允许缺少 SHA-256 绕过已有要求 |

取回继续履行源端与主机端的既定校验契约。当前相机支持源端 SHA-256，取回准备完成前须取得可靠源端值并与主机副本的最终 SHA-256 比较；获取失败或结果未知按对应错误处理，不能归为设备不支持而跳过。驱动明确不支持源端摘要时，才适用已有的可靠读取降级规则，主机副本仍须计算 SHA-256 供客户端校验。已经可靠取得、对应同一固定内容的源端值可以复用，不因新取回重复创建文件身份或强制重新计算。

SHA-256 后来取得时，保存文件的新事实及历史；旧边界继续表达当时尚未取得。登记产物不要求人为延后已经能够可靠保存的校验值，也不额外建立为所有产物预先计算摘要的后台责任。
