# 日志副本交付

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页定义报告首次失败时如何准备并交出日志副本，以及失败副本和启动遗留文件怎样清理。普通日志的保留与通道故障见[运行日志](logging.md)，跨 `run` 的重复抑制见[报告故障标记](log-failure-marker.md)。

报告处理第一次失败时，camctl 将当前普通日志文件原样复制一份，交给主程序传输，供维护人员排查问题。该流程不等待会话结束或多次 `run` 均失败。camctl 负责将日志副本放入本地 `ready`；主程序何时传输、远端何时收到，由后续传输流程决定。

## 准备与交接

`paths.log_file` 指向各进程持续追加并按配置轮换的普通日志文件。`staging/logs` 保存准备交付的日志副本和留在本地的故障标记文件。日志副本具有唯一文件名，内容固定；普通日志轮换只管理原日志及其归档。

camctl 先按[独立状态文件规则](log-failure-marker.md#跨-run-的独立状态文件)可靠保存本次故障标记及日志副本身份。标记创建失败或保存结果未知时，按[创建失败规则](log-failure-marker.md#故障标记创建失败)停止本次日志副本交付流程。报告错误仍通过普通日志和可用的 stderr 记录。

1. 所属业务协程通过正常日志入口记录本次报告失败的阶段、实际错误、能够可靠关联的请求或报告身份及已有异常堆栈。日志仍使用统一的格式与级别规则。
2. 日志副本交付流程确认本次错误记录已经实际写入普通日志文件并刷新写入缓冲。普通异步日志调用返回只表示记录已入队，不能作为文件写入完成的证据；确认写入的具体接口在实现设计中确定。
3. camctl 协调共享日志文件的追加与轮换，将包含本次错误记录的当前日志文件完整、原样复制到 `staging/logs`。从该错误写入到副本内容确定之间，其他进程的轮换不能使副本漏掉该错误；复制期间的追加也不能造成副本中的日志记录不完整。该协调须复用日志处理器的跨进程锁，具体接入方式在实现时核验。
4. camctl 清空副本的写入缓冲，完成副本的文件同步并关闭副本，然后将副本原子移动到 `ready`，完成涉及目录的同步。原日志文件继续留在 `paths.log_file`，后续日志仍由各进程按正常追加与轮换规则处理。
5. 主程序按 `ready → processing → 本地传输完成后删除` 的现有流程中转日志副本，保留完整文件名和内容。camctl 不修改或撤回已被领取的日志副本。日志副本传回后，由人工递交给负责软件维护的人员查看。

副本保留复制时当前日志文件的全部字节及原有编码、格式，只复制当前文件。副本大小取决于该文件的实际大小，不能把轮换阈值当作副本大小的硬上限；刚完成轮换时，副本可能只有很少的历史上下文。锁等待、文件复制和同步在工作线程中执行，主事件循环异步等待结果；具体协作遵守[日志执行方案](../camctl/logging-runtime.md#普通日志执行与多进程轮换)。

主机日志的接收与分析由上述人工维护流程负责；客户端网页的文件处理范围为业务状态报告、图片和视频。

日志副本不登记为业务产物、普通 delivery 或状态报告，不分配 `report_id`，不推进 `change_seq`，也不接受状态报告 ACK。复制日志、将副本移入 `ready` 及记录这些操作的错误，均不能触发下一份业务报告或再次交付日志副本；业务状态和未完成报告责任仍按原契约保存。

## 首次失败与重复失败

从首次报告处理失败，到报告本地处理已可靠恢复成功，连续未恢复期间统一视为一轮故障，只触发一次日志副本交付。该范围跨越多次报告尝试和多次 `run`；期间失败阶段、错误类别、错误信息或关联报告身份发生变化，仍属于同一轮。后续失败继续记录普通日志，不额外复制日志。首份日志副本内容固定，因此可能不包含本次后续出现的新错误。

报告本地处理已可靠恢复成功后，结束本次故障；之后再次失败才触发新一轮日志副本交付。恢复依据[报告本地处理及完成证据](report-maintenance.md#与会话收尾的协作)判断，单个步骤成功不代表整轮处理恢复。例如，业务状态报告已经生成，但 camctl 将报告移入 `ready` 时失败，故障仍持续。收到 ACK、主程序领取或删除文件、日志副本成功移入 `ready`、进程重启及一段时间没有新的报告尝试，都不单独构成恢复依据。

| 报告及日志副本状态 | 处理 |
| --- | --- |
| 已可靠确认此前无未恢复故障，发生报告处理失败 | 开始一轮故障，立即尝试可靠保存故障标记，成功后复制日志并将副本移入 `ready`；保留报告责任，普通设备动作继续，其他执行前提失效仍按各自错误规则处理 |
| 本次故障仍未恢复，后续报告尝试失败，包括阶段、错误类别、文案或关联报告身份变化 | 保持本次故障，只记录普通日志，不再次触发日志副本交付 |
| 本次故障仍未恢复，只有部分报告步骤成功，其余必需步骤失败、未完成或结果未知 | 保持本次故障，不以局部成功重新允许触发日志副本交付 |
| 本次故障仍未恢复，发生重启、新业务变化、ACK、文件领取或删除，或暂时没有报告尝试 | 这些事件自身不结束本次故障；后续报告处理仍依据实际结果判断恢复 |
| 报告本地处理已可靠恢复成功 | 结束本次故障持续状态，保留已有日志及文件交接事实 |
| 恢复成功后再次报告失败 | 作为新一轮故障触发日志副本交付 |
| camctl 读取原日志、写入或同步日志副本失败，或者将日志副本移入 `ready` 的操作失败 | camctl 记录实际错误，并按[日志副本的失败清理](#日志副本的失败清理)处理本次日志副本；camctl 保留故障标记文件，不自动重试本次日志副本交付，也不因此单独终止设备动作 |
| 日志副本移动或同步结果未知 | 保留实际已知的文件操作和错误事实，不宣称成功或从未移入 `ready`，不通过再次复制日志掩盖未知结果 |
| 无法可靠确认此前故障轮次、是否已经触发或是否已经恢复 | 明确保留未知及诊断，不把未知当作首次失败、已发布或已恢复；跨 `run` 的判断见[报告故障标记](log-failure-marker.md) |

## 日志副本的失败清理

本节处理的是从普通日志文件复制出来、准备交给主程序传输的日志副本。故障标记文件继续留在 `staging/logs` 中，直到业务状态报告的本地处理可靠恢复后，camctl 才按既有规则删除故障标记文件。

camctl 每轮只尝试一次日志副本的准备与交接。如果 camctl 在复制日志、同步日志副本、将日志副本移入 `ready` 或完成后续目录同步时遇到错误，camctl 停止本次日志副本交付流程，并记录实际错误。如果进程中途退出，后续 `run` 也不自动继续写入、重新复制或再次投递本次日志副本。仍正常进行的首次日志副本交付流程可以继续完成，不因观察到本次已有故障标记而中止。

camctl 清理本次日志副本之前，必须确认相关文件操作已经结束，并且相关文件句柄已经关闭。不能因为等待工作线程的协程被取消，就认为工作线程已经停止写入或移动文件。在满足这一前提后，camctl 根据日志副本的实际位置和归属执行下表；文件内容是否完整，不改变仍在 `staging/logs` 的失败文件应被删除的规则。

| camctl 已确认的情况 | camctl 对本次日志副本的处理 |
| --- | --- |
| 相关文件操作尚未结束，或者尚未确认相关句柄已经关闭 | camctl 继续跟踪实际操作结果，此时不删除日志副本 |
| 相关操作已结束且句柄已关闭；本次日志副本仍在 `staging/logs`，可以确认归属 | camctl 删除这份日志副本，包括未写完的半成品和未成功移入 `ready` 的完整文件 |
| 相关操作已结束；日志副本已移入 `ready`，但后续目录同步或进度记录出错 | camctl 保持已交接的日志副本不变，记录实际错误，不从 `ready` 撤回或删除日志副本 |
| 主程序已经将日志副本领取到 `processing` | 主程序继续负责日志副本的传输和后续删除；camctl 不修改或删除这份日志副本 |
| 相关操作已结束；camctl 可靠确认本次日志副本已不在其准备位置，且没有可清理的本地文件 | camctl 无须删除文件，也不重新复制或再次投递；文件不在准备位置本身不能证明远端已收到日志副本 |
| camctl 无法确认日志副本的位置、归属或移动结果 | camctl 保留实际已知结果及错误，不根据猜测删除文件，也不重新复制或再次投递 |

删除日志副本不会删除故障标记文件，也不会删除普通运行日志或业务状态报告。camctl 删除未能交付的日志副本后，也不重新尝试本次交付。如果删除操作本身失败，camctl 记录清理错误和实际残留，本次不循环重试删除，也不因此单独停止业务。

本次报告故障可能因此没有日志副本传出；排障依靠仍保留的普通日志。业务状态报告的恢复与补投继续遵守报告规则。进程突然退出或删除失败后留下的日志副本，由后续 `run` 按[启动清理规则](#run-启动时清理遗留日志副本)检查；清理不允许重新复制或投递本次日志副本。

## run 启动时清理遗留日志副本

每次 `run` 启动并取得会话锁后，camctl 安排一次检查，清理以前的日志副本交付流程留在实际 `staging/logs` 中的日志副本。这些遗留文件可能来自进程突然退出，也可能来自上次未成功完成的删除操作。camctl 不在运行期间定时扫描，也不因为本次清理失败而再次安排同一轮检查。

camctl 根据日志副本的专用命名规则及所属流程识别清理对象，具体名称在实现设计中确定。能够确认文件来自以前的日志副本交付流程，并且已经没有程序继续操作这份文件时，camctl 才允许删除。检查与本次日志副本交付流程可能同时推进，因此 camctl 必须排除本次 `run` 创建或正在处理的日志副本；不能仅凭文件出现在 `staging/logs` 中就删除，也不能把取消等待等同于文件操作已经结束。

| 检查中发现的对象或情况 | camctl 的处理 |
| --- | --- |
| 以前日志副本交付流程留下的日志副本仍在 `staging/logs`，归属明确且已无人继续操作 | camctl 尝试删除这份文件；半成品和完整文件采用相同规则 |
| 旧日志副本仍有程序操作，或者 camctl 无法确认相关操作是否结束 | camctl 本次不删除这份文件，不为等待删除机会增加轮询 |
| 故障标记文件 | camctl 保留故障标记文件，由业务状态报告可靠恢复后的流程负责删除 |
| 本次 `run` 创建或正在处理的日志副本 | camctl 不将这份文件列为启动清理对象，由本次日志副本交付流程负责处理 |
| 普通日志、业务状态报告或其他文件，或者 camctl 无法确认文件用途和归属 | camctl 不删除这些文件 |
| 日志副本已经在 `ready` 或 `processing` 中 | camctl 不将这份文件列为启动清理对象，由主程序继续处理 |
| camctl 可靠确认没有符合条件的旧日志副本 | camctl 结束本次检查，不创建或重新投递日志副本 |
| camctl 无法完成目录检查或文件检查 | camctl 记录实际错误，不把未能检查的文件当作不存在，也不根据猜测删除；后续 `run` 再检查 |
| camctl 删除某份旧日志副本失败 | camctl 记录实际错误和残留，本次不重复删除这份文件；后续 `run` 再检查，其他已确认符合条件的旧文件仍可处理 |

目录检查和删除通过已有的本地文件工作线程执行。设备动作不等待启动清理完成，也不以清理成功为前提；其他执行前提仍按原有规则判断。已经开始的文件操作继续按[本地文件操作的完成规则](../camctl/file-runtime.md#本地文件操作的完成与故障边界)跟踪实际结果，不能为结束清理而宣称仍在执行的操作已经完成。

本次 `run` 的日志副本交付失败时，camctl 仍按前述失败清理规则处理。启动清理只负责以前留下的日志副本，不改变故障标记的存在性，不启动日志复制或副本补投，也不改变业务状态报告的恢复规则。故障标记文件的临时文件属于标记保存流程，同次目录检查按[标记临时文件清理](log-failure-marker.md#故障标记的临时文件)单独判断，不与日志副本混为一类。

## 独立性与可靠性边界

日志复制及副本交接不依赖状态库可用：不能要求先分配数据库身份、登记业务交付或成功提交报告记录才允许交付日志副本。状态库故障时，所属协程将已经掌握的错误写入普通日志，不为了补齐日志而继续查询已失效的状态库。

该流程依赖普通日志文件可用。文件日志无法写入时，遵守[日志通道故障规则](logging.md#日志通道故障)；不能把错误已入队或仅输出到 stderr 当作该错误已写入普通日志。原日志无法读取、复制失败或副本未完整保存时，camctl 不能将本次日志复制记为成功，仍按失败清理规则处理副本并保留故障标记。

日志副本与业务文件共用存储和主程序传输，不能保证报告失败时日志必然送达。报告内容生成出错，而普通日志与文件交接仍可用时，camctl 可以交付日志副本。磁盘已满、`ready` 不可写或文件系统故障时，日志副本交付可能同样失败；主程序或传输链路故障时，日志副本可能无法送达。camctl 保留仍可用的本地日志和 CLI 诊断，不将日志副本交付等同于业务报告完成或客户端已经收到状态。

## 实现前仍需明确的边界

正式故障标记的存在性、首次触发及重复抑制遵守[故障标记决策表](log-failure-marker.md#跨-run-的独立状态文件)。检查或创建错误后的再检查时机由[故障标记异常后的再检查](log-failure-marker.md#故障标记异常后的再检查)定义，跨 `run` 的判断使用正式标记与可靠证据，不依赖状态库可用。内容字段及归属协调接口仍须落实；临时文件与进度更新分别遵守[标记临时文件清理](log-failure-marker.md#故障标记的临时文件)及[进度更新失败](log-failure-marker.md#故障标记的进度更新失败)规则。故障标记删除继续采用第一版正常运行假设。

还需确定日志副本的具体命名规则，以及错误实际写入的完成通知、文件锁与复制操作如何接入现有日志组件。副本内容已经确定为当前普通日志文件的全部原始字节。日志级别遵守[日志配置与部署约定](logging.md#配置与默认值)。

日志副本交付流程失败后，camctl 按既定条件删除仍在 `staging/logs` 的本次日志副本；后续每次 `run` 取得会话锁后检查一次遗留日志副本。两种清理都保留故障标记文件，不自动重试或补投日志副本。其他意外情况是否触发此通道仍需按具体故障确认，不把任意日志错误自动扩大为新触发条件。

## 验收要求

### 触发与复制

日志副本交付的单元测试按“首次失败与重复失败”状态表验证首次失败、连续未恢复期间的重复失败、报告恢复、恢复后再失败、日志复制或将副本移入 `ready` 时失败及结果未知。重复失败分别覆盖失败阶段、错误类别、文案及关联报告身份变化，均只触发首份日志副本。业务状态报告已经生成但尚未成功交接，属于局部成功；ACK、主程序领取或删除文件、日志副本成功移入 `ready` 和没有新报告尝试，也均不单独结束故障轮次。验证日志副本交付不产生业务变化、不触发报告重试或递归交付日志副本。

复制流程的单元测试通过受真实接口约束的日志与文件协作者，分别控制错误尚未入队、已入队但尚未写入、已写入并刷新以及写入失败，验证复制流程依据实际写入结果推进。给定固定的当前日志字节，验证副本内容逐字节一致；只有副本完整写入、同步并关闭后，camctl 才将它移入 `ready`。普通日志的格式化行为单独验证，不把人类阅读的错误文案固定为副本格式。

复制流程的集成测试组合真实日志队列、文件处理器和多个独立写入进程，覆盖错误写入前后发生轮换、复制期间其他进程追加日志，以及副本交接后原日志继续追加和轮换。验证副本包含触发交付的错误记录，各条日志完整，副本字节在交接后保持不变；原日志留在配置路径继续使用。普通日志轮换不删除副本或故障标记。

### 失败清理与启动检查

日志副本清理的单元测试按失败清理表覆盖：文件操作仍在进行、句柄尚未关闭、半成品留在 `staging/logs`、完整文件留在 `staging/logs`、日志副本已经移入 `ready` 或 `processing`、没有本地文件可清理，以及位置或归属未知。验证 camctl 只删除操作已结束且归属明确的本次准备文件；删除操作失败时保留实际错误，本次不循环重试。所有分支都保留本次故障标记文件，不删除普通日志或业务状态报告，也不重新开始日志副本交付流程。

日志副本清理的集成测试组合真实文件工作线程和交接目录，在日志副本写入期间、移动之前以及移入 `ready` 之后分别注入故障。验证 camctl 等待实际文件操作结束后才删除准备文件；主程序已经领取日志副本时，camctl 不修改 `processing` 中的文件。后续报告重复失败及再次启动 `run` 均不重新复制或补投原日志副本，业务状态报告仍按自身规则恢复。

启动清理的单元测试按启动检查表覆盖旧文件归属、操作是否结束、文件所在目录和文件类型，验证 camctl 取得会话锁后只安排一次检查。验证 camctl 保留故障标记、本次日志副本、普通日志、业务状态报告和无法确认归属的文件；目录检查失败时记录错误，单个文件删除失败时本次不重复尝试。后续报告失败、时间经过和调度重扫均不再次触发启动清理。

启动清理的集成测试在真实 `staging/logs` 中准备上次中断及删除失败留下的日志副本，再启动 `run`，验证 camctl 删除符合条件的旧日志副本并保留故障标记。检查期间安排本次日志复制，验证本次日志副本不会被误删。通过受控文件操作等待验证设备动作不等待清理完成；通过一次删除失败和下一次 `run` 的再次检查，验证失败残留可在后续运行中清理，而不会自动重新复制或投递日志副本。

### 与报告流程的协作

日志副本交付的集成测试组合真实文件系统、主程序领取及状态报告处理，验证首次失败即可交付、普通设备动作继续、同一故障期间多次报告失败不重复交付，以及恢复后再次失败触发新的日志副本交付。分别验证状态库不可用但日志与交接目录可用，以及磁盘或目录故障导致日志副本也无法移入 `ready`；后者保留实际本地记录和 stderr 诊断，不宣称日志副本已交接成功。跨 `run` 去重及中断恢复按[故障标记决策表](log-failure-marker.md#跨-run-的独立状态文件)验证，具体接口和命名在实现设计中落实。
