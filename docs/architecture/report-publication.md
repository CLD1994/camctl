# 状态报告的发布与补投

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页说明已登记报告如何生成文件、交给主程序，以及未获客户端确认时如何重新投递。先读[报告内容与累计确认](status-reports.md)和[文件交接目录](file-handoff.md)；报告编号与内容的含义不由文件所在目录决定。

**阅读提示：** 发布表示完整文件已经交给本地目录协议处理；客户端确认是另一件事。先看目录中的已有报告怎样处理，再看没有新业务变化却尚未收到 ACK 时何时补投；联合验收见[报告专题](status-reports.md#验收要求)。

## 报告文件与交接目录

状态报告是 `ready` 中唯一允许被“更新替换”的特殊文件类型。

### staging 中报告的恢复

恢复时，对于 `staging` 中残留的报告文件，camctl 先确认数据库中的报告登记及生成依据可用，并检查 `ready` 和 `processing` 中是否已有同一 `report_id` 的报告。已有报告时按对应目录规则处理；目录检查失败或结果无法确认时，不能当作文件不存在。

确认只有 `staging` 中有该报告，且按报告机会、覆盖范围及补投规则仍需发布它时，第一版统一从头生成文件。原 `staging` 文件无论只写了一部分还是已经写完，都由完整重新生成的内容替代。

重新生成使用数据库中冻结的历史边界、覆盖水位和生成元数据，保持原 `report_id` 和内容。完整生成后按[状态报告发布前落盘](file-handoff.md#状态报告发布前落盘)完成文件同步、移动及后续记录。重建或文件写入失败时，保留诊断和未完成文件，不将半成品放入 `ready`。报告构建和文件处理失败按[报告失败后的处理](status-reports.md#报告处理失败后何时再尝试)等待后续触发，普通设备动作继续；读取或解释数据库历史失败仍按状态库错误处理。

本节定义状态报告文件的恢复；普通产物的生成、拷贝及取回恢复由[正式产物与取回清理](outputs.md)定义。

### 恢复时识别已发布报告

第一版通过交接目录中的文件位置及对应的数据库报告登记识别已发布报告，不常规读取全文、解析 JSON 或重建预期内容来比对文件。该判断以发布流程正确执行、报告内容发布后保持不变且存储未损坏为前提；报告在对主程序可见前已经完整写入并落盘，具体顺序见文件交接专题。

camctl 在 `ready` 或 `processing` 发现报告文件，并可靠确认文件名中的 `report_id` 对应数据库中的已登记报告后，按所在目录处理已有报告。数据库缺少已发布记录时，追加“恢复时发现该报告已发布”的事实并同步更新投影，保留现有文件，不重复生成或投放，也不推测断电前的准确发布时间。

文件名须符合[文件名与完整性校验](status-reports.md#文件名与完整性校验)的格式。文件身份无法关联，或目录、数据库读取失败及结果不确定时，不能据此认定报告已经发布或不存在，应保留诊断并按错误处理。这里的识别用于本地交接恢复；客户端收到报告后仍须计算文件摘要并按文件名校验。

### 记录报告已经发布

camctl 成功将完整报告从 `staging` 放入 `ready` 后，在数据库中记录“这份报告已经发布过”。顺序为：

```text
报告已登记
    → staging 文件完整写入并同步
    → 原子移动到 ready
    → 完成本次移动涉及的目录同步
    → 提交该报告的已发布记录
```

已发布记录关联对应的 `report_id`，追加到不可变历史，并在同一数据库事务中更新报告投影。首次发布和后续成功补投均记录各自的发布事实；报告身份及内容继续遵守原有规则。文件发布在数据库写事务之外执行。

主程序可能在 camctl 写入记录前就取走并删除文件。当前 camctl 进程可靠确认放入 `ready` 及所需同步成功后，就依据这些结果写入记录，无需等文件仍留在目录中。文件后来被领取或删除，也不改变“曾经成功发布”的历史事实。

该记录证明 camctl 发布过报告；它不能证明文件目前还在 `ready`，也不能证明客户端已经收到报告或同步已经结束。后续补投仍依据累计 ACK、有效同步责任和对应的文件规则判断。

放入 `ready` 失败或结果无法确认时，不能写成发布成功。目录同步及数据库记录保存的失败按文件交接及会话错误规则处理。重启后仍能找到报告文件时，按“恢复时识别已发布报告”处理；文件已不在交接目录时，继续按 ACK 和报告补投规则判断，不能仅凭缺少已发布记录断定文件从未发布。

### ready 中至多一个待领取状态报告

如果：

```text
ready 中已有 report R1
```

且它能够满足当前业务覆盖与同步责任，没有需要扩大范围的新变化：

> 保留 R1，不重新生成。

如果出现需要更新报告的新变化，或 R1 不能满足当前同步责任：

1. 根据一致的历史边界、该边界下的累计 ACK 水位和有效同步责任，冻结新报告 R2 的覆盖范围和生成元数据，提交登记历史及投影；
2. 按 R2 的冻结依据从历史重建合并快照，生成 `staging` 文件；
3. 完整生成后撤下 ready 中的 R1；
4. 发布 R2；成功后按“记录报告已经发布”保存发布事实。

R1 的逻辑报告记录本身仍不可变。

完整同步待确认时，新报告从 0 开始；只有局部同步时，覆盖普通累计确认水位和全部有效同步起点要求的范围。所有同步责任结束后，已有较宽覆盖报告可以继续交付；确需替换时，允许省略已经确认的前缀，但新报告必须覆盖仍未确认的变化。不能仅因新报告 ID 更大就认定它足以替换 R1；具体处理见[已有报告怎样处理](status-sync.md#已有报告怎样处理)。

### processing 报告不可修改

如果主程序已经领取：

```text
processing/status-report-42-<sha256>.json
```

CLI 不修改、不撤回它。

此时产生新状态时，可以同时出现：

```text
processing/status-report-42-<sha256>.json
ready/status-report-47-<sha256>.json
```

这是合法状态。

### 防止频繁裸 run 产生大量重复报告

只要能够承担当前报告责任、覆盖未确认状态及适用同步范围的报告仍然：

- 位于 `ready`；
- 或位于 `processing`；

就不因为又启动了一次裸 `run` 而排入一份完全相同的报告。

报告可能因主程序传输失败或中断而残留在 `processing`。主程序是否会再次处理该文件未知，详见[文件交接](file-handoff.md#processing)。上述避免重复排队的规则不构成后续一定送达的保证；文件持续残留时，camctl 也不据此判断客户端已经收到。

### 本地传输完成后仍未 ACK

补投是指：camctl 尚未收到足以结束相关报告责任的客户端确认，而本地已经没有能继续交付这些内容的报告文件，因此重新准备报告并发布到 `ready`。

主程序删除 `processing` 中的报告文件，只表示主程序判定本地传输已经完成。客户端是否收到、校验并保存了报告，仍须由有效 ACK 确认。例如，报告 A 已被主程序传走并删除，但客户端的确认尚未送回主机；即使此后没有任何设备状态变化，camctl 仍保留 A 所覆盖内容的报告责任。

没有新业务变化或新的同步要求时，同一次 `run` 不因报告被领取或删除而再次投递；下一次正常 `run` 在恢复／对账时检查是否需要补投。判断如下：

| 持久化责任与文件检查结果 | 处理 |
| --- | --- |
| 已无未确认业务变化，也无待确认的同步责任 | 无须补投 |
| 仍有上述责任，`ready` 或 `processing` 中已有满足当前覆盖和同步要求的报告 | 保留已有报告，不重复投递 |
| 仍有上述责任，可靠确认两个目录中均无满足要求的报告 | 重新准备并发布满足当前责任的报告 |
| 无法可靠读取责任记录、关联报告身份或检查交接目录 | 保留诊断并按错误处理，不能解释为责任已结束或文件不存在 |

因此，在上述报告 A 的例子中，若下一次 `run` 启动时仍无有效确认、两个目录也均无适用报告，就需要补投。若 A 仍留在 `processing`，则保留它；若相关责任已由有效 ACK 结束，则不补投。

新的业务变化仍按报告维护规则处理，不必等待下一次 `run`。同步待确认时继续覆盖相应固定起点；所有责任已获合格 ACK 或按规则结束后，按普通增量报告处理。

没有新业务变化且原报告仍满足当前责任：

> 从数据库历史及原报告的冻结依据重建内容，使用原 `report_id` 重新投递，文件字节与首次发布相同。

出现新业务变化或原报告不满足新的同步责任：

> 生成新的合并报告和新 report_id。

这样避免：

```text
每次裸 run
    → 新报告
    → 主程序重复排队传输
```

同时仍保留在没有远端接收确认时的自动补救能力。
