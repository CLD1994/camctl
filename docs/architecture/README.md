# camctl 设计总览

**规格范围：第一版设计基线。基线日期：2026-09-15。** 本总览与业务专题定义系统行为，[camctl 实现设计](../camctl/README.md)定义内部协作，根目录 `protocol` 中的 Schema 和样例定义公共机器表示。实施进度、依赖实验和真实设备联调的结果分别记录，不改变正文中的有效规则。

camctl 用于在一台嵌入式 Linux 主机上，按照预先提交的计划控制相机等设备。用户在个人电脑的网页中编辑计划，交给负责传输的部门；主机上的 camctl 执行计划，再通过文件把结果交回客户端。

这套系统的关键限制是：主机可能随时断电，下一次开机时间无法预知；有电时也不一定能接收新计划或向外传输文件。相机独立供电，主机断电时可能仍在录像。因此，计划、执行进度和已知结果需要可靠保存，后续开机才能继续处理。详细条件见[运行环境与协作分工](system-context.md)。

本总览定义系统范围、所有专题共同遵守的规则和规格阅读入口。功能范围由各专题共同描述；第一版先贯通正常业务流程，影响业务结果的未明确事项在对应功能落实时确认。文档划分表示规则由哪里完整定义，不预先固定代码模块或数据库表划分。

第一次接触项目可以按本页顺序阅读，再跟随[阅读路线](reading-guide.md)。完整参数表、状态转换和失败处理都保留在对应专题中。

## 谁在使用和运行这套系统

| 角色 | 所在位置与工作 |
| --- | --- |
| 用户与客户端 | 用户在个人电脑上打开本地网页，编辑并导出计划，导入返回的状态报告，查看结果 |
| 负责传输的部门 | 接收用户递交的计划，安排送达主机；把返回的报告文件提供给用户 |
| 主程序 | 第三方维护的 C 程序，运行在嵌入式主机上；启动和管理 camctl，接收计划、中转待传文件，并通过注册回调执行电机控制 |
| camctl | 同一主机上的 Python 命令行程序，负责受理、调度、设备控制、状态保存、产物管理和报告生成 |
| 相机等受管设备 | 执行具体采集操作，并使用自己的存储保存原始产物；第一版支持设备声明的单张拍摄、录像和延时摄影，MCU（微控制器）预留接口 |

第一版只考虑一台主机和一个逻辑客户端。客户端保留可靠的历史状态基础时，可按指定报告请求[局部同步](status-sync.md)；需要重新取得全部状态时使用完整同步。这里的客户端指维护同一份业务状态和报告确认进度的客户端应用。个人电脑上的客户端与嵌入式主机上的 camctl 是两个程序，通过既定的人工交接和传输流程交换文件。

CLI 是 Command-Line Interface（命令行接口）的简称，后文用它指 camctl 的命令入口。JSON 是计划和报告采用的结构化文本格式：人可以阅读，程序可以按字段处理。用户在网页中完成编辑后，仍须手工递交导出的 JSON；网页导出成功不表示主机已经收到或执行了计划。

## 先用一次录像理解几个对象

假设用户要在 10:00 拍一段录像，再把视频取回来。这个例子只说明业务关系，不规定真实相机的参数类型或默认录像时长。

1. 用户创建一份**执行计划**，其中有“录像 A”和“取回 A”两个**动作**。每个动作表达一件要做的事，例如录像、取回、报告或取消。
2. 客户端为这次提交生成 **`request_id`（请求标识）**。若一直没有收到受理证据，重送时继续使用这个 ID；camctl 已经受理过它时，会复用原计划及进度。
3. 正常录像完成后，相机上的原视频被登记为一份**正式产物**，获得 **`output_id`（产物标识）**。这份原视频继续保存在相机。
4. “取回 A”从相机拷贝视频，在主机准备一份独立待传文件。这次具体交付获得 **`delivery_id`（交付标识）**；正式产物与交付副本各自保留身份。
5. 用户之后用新请求再次取回同一视频时，仍引用原来的 `output_id`，但会产生新的 `delivery_id` 和独立待传文件。原视频不需要重新录制。
6. camctl 生成**状态报告**，告诉客户端哪些计划已受理、动作进行到了哪里、有哪些产物和交付。报告通过 **`report_id`（报告编号）**标识，客户端据此保存状态并反馈确认。

这些对象分开，是因为“录好了”“已准备好一份待传副本”和“客户端已经收到”发生在不同时间。确认报告已收到，也不代表报告中提到的视频已经收到。更多背景、第二次取回与取消的例子见[概念与术语](concepts.md)。

## 文件怎样交给主程序

视频和报告先在 `staging` 目录生成或拷贝。文件准备完整后，camctl 将它移入 `ready`，允许主程序领取。主程序等到可以传输时，再将文件移入 `processing`，传输完成后删除对应的传输副本。

```text
相机中的正式源文件
    │ 取回时拷贝；源文件仍保留
    ▼
staging：camctl 准备文件
    │ 完整后发布
    ▼
ready：等待主程序领取
    │ 主程序开始处理
    ▼
processing：主程序传输，完成后删除传输副本
```

主机断电时，相机可能继续录像，导致原视频明显长于计划要求。对符合修复条件的视频，camctl 会在后续恢复处理中，在主机上裁剪多录部分，另存一份修复成品，同时保留原视频。具体触发条件见[异常录像恢复与修复](camera-recovery.md#内部异常多录修复)。

这三个目录表示文件现在由谁处理。`staging/derived/` 另行保留主机加工形成、可以反复取回的正式成品，例如修复后的视频；每次取回都为它准备独立交付文件。主程序不会读取 `staging` 中的半成品，camctl 也不能撤回已经进入 `processing` 的普通交付文件。具体权限、原子移动和失败情况见[文件交接](file-handoff.md)。

本项目提供[C 接入模块与终端演示](../host-demo/design.md)，供第三方现有主程序直接调用，并用于本地全流程验证。模块负责管理 camctl 进程、递交计划文件路径和有限自动重试，在主程序指定时机同步领取 `ready` 文件；实际传输继续由主程序负责。

## 电机控制与主程序通知

`motor_control` 在用户指定的有效时间窗口内发送位置控制通知。CLI 通过独立管道发送 NDJSON，host 解析后调用主程序注册的 `void callback(int position)`。主程序定义位置的单位和业务合法范围并执行电机控制；每种消息类型有独立的注册接口。

动作成功表示通知已完整写入通道。发送结果不确定时不重发，既不把写入成功当作电机到位，也不把无结果当作未发送。完整业务规则见[电机控制动作](motor-control.md)，机器格式与通道行为见[主程序通知协议](../../protocol/host-notifications.md)，接口见[host 回调注册](../host-demo/implementation.md#按消息类型注册回调)。实施范围和未完成接入见[实施路线图](../superpowers/plans/2026-09-30-camctl-implementation-roadmap.md#电机控制与主程序通知接入)。

## 拍摄能力与多产物

参数类型可声明支持预览图片或预览视频。客户端将自动预览意图展开为独立取回动作，主机按明确关联执行选择、交付和取消；普通取回排除预览并优先对应修复成品。完整契约见[预览文件与自动取回](preview-obtaining.md)。取回及清理均支持按计划、动作或明确产物选择，清理来源范围内的全部正式产物。

相机能力随具体设备提供，第一版支持 `camera_take_photo`、`camera_record`、`camera_timelapse`。单张拍摄执行一次拍摄；延时摄影执行设备契约定义的有限采集任务，按该契约分配设备与主机的计时、停止责任。拍摄产生哪些图片、视频以及数量由驱动及实际报告决定。单张拍摄和延时摄影取消时保留已经拍完、确认归属且写入完成的文件。完整状态转换、失败恢复及报告契约见[单张拍摄与延时摄影](camera-capture.md)。

图片与视频使用同一正式产物、独立交付及显式清理流程；同一动作可有很多产物。同一产物多次交付不改变其身份。

## 第一版正常流程

本流程以单台主机和当前相机为对象；主机使用 ADB（Android Debug Bridge）通信，通过 `adb shell` 在相机中执行控制程序。流程假设输入合法、主机时间可信、通信正常且存储空间充足。[采集与取回计划示例](plan-acceptance.md#基本结构)使用样例驱动参数演练业务链；真实设备验收使用依据实际相机能力另行确定的正式参数类型。

| 步骤 | 谁执行什么 | 可观察结果 |
| --- | --- | --- |
| 1. 交给 CLI | 主程序调用 `run <plan-path>`；运行期间的新输入通过 `submit` 交接 | 一份计划及其全部动作原子受理，同请求重送复用原实例 |
| 2. 按时录像 | camctl 在启动窗口内调用相机；成功确认后计时，到目标时长停止 | 正常录像完成，源视频保留在相机；产物登记与录像终态同时提交 |
| 3. 取回产物 | 取回动作到时间后选择正式产物，拷贝到自己在 `staging` 中的中间文件 | 独立 delivery；文件准备完成，保存大小、摘要和最终文件名 |
| 4. 本地发布 | camctl 将准备好的文件发布到 `ready`，并生成覆盖业务结果的状态报告 | 取回成功；全部动作结束后计划 `completed` |
| 5. 中转文件 | 主程序把 `ready` 文件移到 `processing`，传输后删除本地传输副本 | 客户端收到报告和交付文件，两者可以先后到达 |
| 6. 接受并确认 | 客户端核验报告、确认累计覆盖并保存状态，通过后续输入确认报告；视频按报告中的文件名、大小与摘要另行关联和核验 | 报告确认水位推进；相机原片仍保留 |
| 7. 按需清理 | 客户端用新计划显式清理已不需要的 `output_id` | 删除对应正式源文件，数据库保留全部业务历史 |

普通文件交付名使用 `<delivery_id>.<ext>`，完整可读名称通过报告的 `display_name` 展示。报告确认不等于普通视频已收到；源视频是否删除由客户端的显式清理请求决定。

正常 `run` 在业务变化保存后主动维护状态报告，与设备控制异步执行，允许多次变化合并到后续同一份报告；恢复时接续未完成责任，收尾时检查遗漏。`report_status` 用于明确请求完整或局部状态同步。报告生成或文件发布失败时，执行条件仍可靠的普通设备动作继续运行；后续业务变化或下一次正常 `run` 再处理报告。具体规则见[报告维护](report-maintenance.md#报告生成点)。

首次报告失败时，camctl 确认错误已写入普通日志后，将当前日志文件原样复制到 `staging/logs`，再将完整副本移入 `ready`，由主程序按文件交接流程传输。原日志继续用于追加和轮换。同一故障持续期间只尝试交付一次日志副本，直到报告恢复成功后再次失败才触发新一轮；日志副本不能替代业务状态或累计确认。详见[日志副本交付](log-delivery.md#日志副本交付)。

### 第一版完善与验收范围

第一版采用 MVP（最小可行版本），验证计划生成、CLI 受理与调度、产物取回、文件交接及客户端报告处理的软件流程。集成测试使用受驱动契约约束的相机替身，配合真实 CLI、SQLite、交接目录与客户端，不连接真实相机等具体设备。已有样例参数用于协议演练，不据此宣称真实相机支持相应配置。主程序和传输环节可按已约定的职责进行测试代行，实际对接仍需第三方联调。

集成测试验证组件协作、并发推进、错误处理与进程中断后的恢复；调度和超时分支使用可控时间及受控响应验证。目标主机上的实际调度延迟、设备响应、传输吞吐及物理断电持久性单独作为设备联调和测量事项，不属于第一版软件集成测试的通过门槛。开发环境的资源和性能测量只能说明相应环境中的结果，不能代替目标硬件结论；无需先确定真实设备数量或现场负载，才能编写和运行软件集成测试。

真实驱动命令、设备响应、实际文件及目标硬件性能的联调单独安排，范围和判定条件在具备设备及现场需求时确定；这些事项不作为软件集成测试的运行前提。拍摄参数优先覆盖用于联调的任务，已确定的固定设置由驱动执行；更多设备参数选项在完整交接后细调，沿用现有扩展接口。当前参数范围见[当前相机录像参数](camera-parameters.md)。

先使上述主流程完整可运行，再覆盖会改变正常使用结果的必要分支：同一请求重送、已支持动作自身参数错误、设备尝试耗尽、取消、启动窗口过期、取回断点续传及报告确认。已有规则继续作为这些分支的边界。

| 工作 | 第一版落实方式 |
| --- | --- |
| 业务与文件主流程 | 按上表交付一条贯通计划、驱动、数据库、文件和客户端报告的集成场景 |
| 数据持久化 | 保持历史与投影原子提交、身份稳定及重启恢复要求 |

## 持久化与配置基础

camctl 将计划和状态保存到 SQLite 数据库。历史记录永久保留；当前状态由历史计算，并在同一事务中与新历史一起更新。这样既能查询当前进度，也能重建之前已经保存的状态。日常运行只打开已有状态库，首次部署通过 `camctl init` 显式创建。完整的历史、恢复和配置规则见[共同原则与状态持久化](system-foundations.md)。

本地配置默认路径为 `$HOME/.camctl/config.toml`。配置文件可以不存在，此时使用内置默认值；提供的字段覆盖相应默认值。加载、生效范围及通信策略见[本地配置](configuration.md)，初始化步骤见[首次部署与初始化](initialization.md)。
