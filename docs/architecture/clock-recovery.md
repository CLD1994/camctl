# 主机时间检查与受限恢复

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

主程序会先尝试校时，camctl 仍须判断当前时间能否用于调度。本页定义时间不可信时允许做哪些有限处理，以及为什么应保存其余工作等待后续会话。正常时间与启动窗口见[调度与设备执行](scheduling-execution.md)。

**阅读提示：** 先区分日期时间的墙钟与测量经过时长的单调钟，见[恢复术语](concepts.md#断电恢复中常见的词)。随后分别阅读 `submit`、正常 `run` 和时间异常时的处理，联合验收见[调度专题](scheduling-execution.md#验收要求)。

## 时钟防御

### submit

`submit` 不进行启动墙钟可信性检查。

只验证时间字段：

- 格式；
- 结构；
- 静态合法性。

不依据当前本机时间判断：

- 动作是否已过期；
- 是否已经到 scheduled_at。

### run

`run` 按[启动顺序](cli-commands.md#run-的启动顺序)，在取得会话锁、验证状态库并完成适用的计划受理后，进行墙钟可信性检查。

时钟检查读取可信历史时间下界，再检查当前墙钟，必要时延迟复检。带计划启动的受理事务在此之前已经结束，墙钟复检等待不持有该事务。

可信历史时间下界保存在 `runtime_state` 的时间字段中，与累计确认字段共用一条[全局运行状态记录](../camctl/database/reports-runtime.md#全局运行状态)，两组字段分别按自身资格更新。合法的尚无可信历史依据与状态记录缺失、无法读取分别处理；读取失败属于状态库错误，不能解释为首次运行或已确认墙钟异常。

计划受理阶段的本机时间尚未经过启动校验，不能用于推进可信历史时间下界。首次受理、幂等复用及受理拒绝的时间记录均遵守这一规则。

### 可信历史时间下界的更新

可信历史时间下界只在 `run` 启动墙钟检查通过后建立或推进，每次 `run` 至多更新一次。检查使用此前已提交的下界，更新使用实际通过检查的那次主机墙钟读数；需要延迟复检时，采用复检通过的读数。检查和等待均在写事务之外完成。

在状态记录完整且可可靠读取的前提下，设已有下界为 L、通过检查的墙钟读数为 T，按下表处理：

| 启动检查及已有下界 | 处理 |
| --- | --- |
| 检查尚未完成 | 保持已有状态，不取得下界更新资格 |
| 检查及适用复检仍失败 | 保持已有状态，按时钟异常规则执行有限收场 |
| 检查通过，尚无可信历史下界 | 将 T 保存为首次下界，并记录依据 |
| 检查通过，已有下界且 T > L | 将下界推进到 T，并记录依据 |
| 检查通过，已有下界且 T <= L | 保持 L，不产生下界变更 |

需要建立或推进下界时，在进入普通恢复和调度前，以短事务共同保存下界变化的权威历史及 `runtime_state` 投影。保存失败或提交结果未知时，按状态库错误及提交核实规则处理，不进入依赖本次启动完成的普通执行。没有下界变更时，不为此新增历史事件或写事务。

下界变化属于内部管理事实，不增加 `change_seq`，也不单独产生状态报告责任。正常运行及退出阶段的事件仍按实际时间和可信性保存；下界保持本次启动后的值，后续 `run` 再按启动检查结果更新。`submit` 不取得下界更新资格。历史恢复只重建已经保存的下界变化，不从其他事件中的更晚时间重新计算下界。

对于采用[预计检查时间恢复等待的延时摄影任务](camera-capture.md#无状态查询任务的重启等待恢复)，部署环境保证重启前后的日期时间足够可靠。该运行前提与启动墙钟检查分别适用；检查通过本身不证明跨重启的时间差准确。日期时间只用于恢复检查安排，本次运行内的剩余等待仍使用单调钟，也不将日期时间差报告为设备实际采集时长。

### 时钟正常

进入正常：

- 恢复；
- 调度；
- 执行；
- 报告。

### 时钟异常

复检仍失败时，不进入正常时间调度。

进入：

> 有限安全收场模式。

处理已经存在并且能够证明安全的遗留收场责任，以及下节允许的立即取消请求。取消产生的收场仍须证明属于被取消的目标。

不：

- 启动新的普通定时动作；
- 用错误墙钟判断 pending 动作已经过期；
- 依据错误墙钟推断录像已录多久。

有限收场完成后，按下文处理一次报告责任，再以时钟异常退出。期间再发生状态库等会话错误时，按[会话错误与恢复边界](session-errors.md)停止依赖已失效条件的工作，并保留实际错误和设备事实。

时钟异常不回滚启动阶段已经提交的计划受理结果。新计划的普通动作保留等待处理的状态，后续实际启动的会话再按当时的时间与设备条件判断执行资格。

录像停止后的文件拷贝、媒体核验与修复不属于本模式允许的安全收场。已停止但后处理未完成的录像按[安全收场与后续处理的衔接](camera-recovery.md#安全收场与后续处理的衔接)保存进度，等待后续正常会话；未完成的后处理不能使当前受限会话转入普通执行或持续等待。

### 时钟异常期间的取消

墙钟复检仍失败时，`run` 允许执行已受理、未填写 `scheduled_at` 的 `cancel_task`，包括本次启动时新受理的取消请求。该资格只允许取消指定计划或动作、按已保存关联联动自动预览取回及完成其必要收场，不授予其他普通动作执行资格；`submit` 仍只负责受理。

先检查取消动作自身的持久化状态，再判断时间和目标。已取消或已进入其他终态的取消动作保持原结果，不重新执行；已形成的遗留收场责任按各自恢复规则处理。已经开始且仍未完成的取消，按已保存的目标和进度恢复能够证明安全的有限收场，不重新判断原计划时间或扩大目标。对于尚未开始的取消动作，按下表处理：

| `scheduled_at` | 目标查询结果 | 处理 |
| --- | --- | --- |
| 已填写 | 任意 | 保留待执行状态，不依据不可信墙钟判断已到时间或过期 |
| 未填写 | 可靠定位到指定计划或动作 | 执行该目标范围内的取消，按目标类型处理必要收场及可撤回交付 |
| 未填写 | 可靠确认目标不存在 | 按既定寻址规则记录 `target_not_found`，本次取消结束 |
| 未填写 | 查询失败、关联不明或结果未知 | 保留诊断并按对应错误处理，不能当作目标不存在，也不能扩大取消范围 |

例如取消计划 P1 时，同一相机当前正在执行 P2 的录像，不能为了完成 P1 的取消而停止 P2。只有证据确认正在进行的录像属于取消目标时，才按录像取消规则尝试停止；归属无法确认时保留未知事实。设备操作仍遵守有限重试与安全收场约束，不用取消请求绕过这些条件。

目标已经终态时保持其历史终态；目标为取回动作时，仍按所属规则处理其可撤回 delivery。源产物与其他动作的文件继续遵守各自生命周期。取消处理不依赖错误墙钟安排等待，必要超时及有限等待使用当前会话的单调钟。

受限会话仍不持有普通接纳资格。并发 `submit` 按既有接管协议判断 `needs_run`；本节不承诺受限会话持续接纳后来的工作。允许的取消及有限收场结束后，处理一次报告责任，本次 `run` 仍返回时钟异常，不因尚有普通待执行动作而转入正常调度。

### 时钟异常期间的报告

有限收场完成后，受限 `run` 检查一次已持久化的报告责任，并按已有覆盖范围、目录状态和补投规则完成本次处理。有需要时生成或补投报告，没有需要时直接结束；一次报告机会不等于必须新建报告。报告固定完整历史边界 H，依靠历史位置和业务水位恢复事实，不用当前不可信墙钟决定覆盖范围。

按下表顺序判断。报告处理仍须满足状态库、锁和实际文件操作的既有条件；本节不授予普通执行或接纳资格。

| 条件 | 处理 |
| --- | --- |
| 状态库或其他必要前提已经失效，无法可靠读取和保存所需事实 | 停止依赖该前提的报告工作，按已有会话错误规则退出 |
| 必要前提可靠，无本次需要处理的报告责任 | 结束受限会话，不生成文件 |
| 有报告责任，已有报告文件足以满足本次处理要求 | 按已有目录及覆盖规则保留文件、完成必要对账，不重复生成 |
| 有报告责任，需要生成或补投，且处理成功 | 完成本地发布及发布事实保存，然后结束受限会话 |
| 报告生成或文件处理失败，尚无状态库等前提失效 | 保留诊断、未完成责任和实际文件事实，本次不循环重试，结束受限会话 |

本次使用其冻结的责任范围。处理期间新提交的业务变化保留给后续有资格的报告机会，不因此追加第二轮；不等待主程序传输或客户端 ACK，也不启动新的 `report_status` 动作。此前已保存的同步责任仍参与本次覆盖范围判断。

本次沿用已确认的报告启动、生成和停止时限。报告成功不消除 `clock_invalid`；后续报告或状态库错误按[错误先后规则](session-errors.md#无法继续执行时的退出)保留，实际执行条件失效时立即遵守对应停止规则。受限会话不持有接纳锁，并发提交继续独立判定 `needs_run`。

验收覆盖无报告责任、已有适用文件、生成新报告、补投、报告失败及状态库错误；在有限收场和报告生成期间分别提交新变化，验证冻结边界内事实得到本次处理，边界之后的责任保留且不使受限会话持续运行。验证立即取消结果能够进入报告，普通动作与新的同步动作仍不获得执行资格。

### 时钟异常期间的事件

保留实际墙钟读数，但明确：

```text
wall_time_trusted = false
```

这类时间不能更新未来启动校验所使用的可信墙钟下界。

时间可信性描述记录中的墙钟依据，不决定事件所表达的事实是否成立。只有实际确认的设备结果、文件结果或事务结果才能记录为成功；时间标记不能把结果未知变成成功。典型记录包括：

| 来源 | 可以形成的事实 | 时间的用途与限制 |
| --- | --- | --- |
| 计划输入处理 | 首次受理、输入拒绝或动作参数错误、有效 ACK 导致的确认变化 | 受理与确认依靠输入及已提交记录；未经校验的本机时间不能用于判断动作过期 |
| 允许的立即取消 | 取消目标、状态变化、必要收场进度及结果 | 按身份及已保存关联处理；不能以异常墙钟启动定时取消 |
| 有限设备收场 | 停止尝试、已确认停止、停止未确认等实际结果 | 能证明停止的证据不自动证明录像已经满足目标时长 |
| 有限收场后的报告处理 | 报告登记、已确认发布或恢复时发现已发布等事实 | 以历史位置、业务水位和报告身份确定内容及确认关系；记录时间不证明客户端已经收到 |

输入处理还需要区分“本进程尚未校验时间”与“已经检查并判为异常”：`submit` 不进行启动墙钟检查，带计划的 `run` 在检查之前已经处理输入。这两种阶段的本机时间均不能推进可信历史时间下界，但不能据此把 `submit` 标记为已经发生 `clock_invalid`。具体内部时间状态字段仍需细化，不用一个布尔值抹去这一区别。

上述时间记录与可信性供 camctl 内部调度、恢复及诊断使用。客户端通过报告中的原始 `scheduled_at`、动作状态、等待原因、过期原因和执行结果理解时间意图的处理情况；时间异常导致尚未结束的动作等待时，按既有 `clock_untrusted` 等待原因表达。报告字段的职责见[计划与动作](report-format.md#计划与动作)。

当前会话内命令超时、有限重试间隔等经过时长使用单调钟；跨断电的录像时长不能通过相减不可信墙钟或不同会话的单调钟读数得到。后续校时成功不改写旧事件的时间可信性，也不补造旧事件的准确发生时刻。

事件先后及报告冻结使用历史位置，业务覆盖使用 `change_seq`；`report_id` 定位报告，再查询其已保存的覆盖水位用于 ACK 处理。对象身份和状态转换关系保持不变，不依靠错误墙钟排序，也不以报告 ID 的数值大小代替覆盖水位。

### v1 已知边界

运行中的墙钟跳变：

> v1 不持续监测、不主动处理。

稳定但错误的外部时间源：

> 缺少外部可信基准时无法判定。
