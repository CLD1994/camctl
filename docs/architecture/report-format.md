# 状态报告字段契约

[返回设计总览](README.md) · [报告与累计确认](status-reports.md) · [客户端协议样例](client-protocol-examples.md) · [阅读路线](reading-guide.md)

状态报告面向非技术用户，帮助用户判断计划是否按其要求执行。本专题说明第一版报告中每个字段表示什么、什么时候需要出现，以及多个字段之间必须满足什么关系。[status-report.schema.json](../../protocol/schemas/status-report.schema.json) 使用 JSON Schema Draft 2020-12，作为字段名、类型、必填项、可选项和枚举值的机器可读权威定义；本专题解释这些字段对应的业务事实。实现中的公共报告类型、校验器与状态选择应从该定义读取或生成，不另行维护一套完整字段和状态清单。

报告覆盖与合并由[状态报告与累计确认](status-reports.md)定义，各动作的执行、失败和恢复仍由对应责任专题定义。Schema 校验通过不等于覆盖连续、业务事实成立或允许确认报告；客户端还须执行本专题的语义检查。相机专属输入参数来自首次受理时保存的事实，不能用客户端目前加载的相机 Schema 重新校验历史报告。

## 文件与基本值

报告使用 UTF-8，包含一个完整 JSON 对象。解析规则与[输入文件与基本值类型](plan-input.md#输入文件与基本值类型)一致：对象成员名唯一，不接受非 JSON 数值常量，不隐式转换类型，省略与 `null` 不等价。客户端先按[文件名与完整性校验](status-reports.md#文件名与完整性校验)校验收到的原始字节，再解析内容；重新排版后的 JSON 不再是同一份交接文件。

标识、可读名称与 UTC 时间沿用输入契约；数据库对象 ID（包括报告编号）使用[规范十进制字符串](plan-input.md#对象-id)，水位、字节数和次数使用 Schema 规定的非负或正整数范围。秒数使用有限非负数，超时须大于零；未知时长不能以零表示。Schema 的时间正则只检查表示形式，实际日期和首尾 Unicode 空白还须按输入契约检查。

除了原始输入值、驱动参数及明确开放的错误细节，报告对象不接受未声明字段，状态值也必须属于该版本的 Schema。未知错误码按[错误](#错误)处理，不与未知状态值混为一谈。

报告生成从冻结历史取值，实体排列、对象字段顺序、字符串转义、精确数值和排版遵守[确定字节编码](report-encoding.md)。对既有报告重建必须保持原字节、文件名和摘要；客户端按业务身份解析，不依赖字段排列。

## 自身字段与实体子集合

报告根的必填字段为 `report_id`、`from_wm`、`to_wm`，必须满足 `from_wm <= to_wm`。`plans` 与 `plan_file_diagnostics` 可以省略；报告内容选择仍须满足所属覆盖区间，不能以 Schema 允许省略为由漏报变化。

仅以下数组采用按身份合并的规则：

| 所在对象与子集合 | 身份字段 | 所属关系 |
| --- | --- | --- |
| 报告 `plans` | `plan_instance_id` | 本主机已受理计划 |
| 计划 `actions` | `action_instance_id` | 该计划首次受理的动作 |
| 拍摄动作 `outputs` | `output_id` | 该动作登记的正式产物 |
| 取回动作 `deliveries` | `delivery_id` | 该次取回创建的交付 |
| 报告 `plan_file_diagnostics` | `diagnostic_id` | 一次输入处理的诊断 |

其余字段都是所属对象的自身字段，包括整个 `result`、`device_execution`、参数对象和逐项结果数组。它们随自身快照整体替换，不按内部 ID 增量拼接。例如新版 `result.failures: []` 表达当前没有失败项，不能保留旧数组中的项目。

| 新快照的内容 | 客户端处理 |
| --- | --- |
| 出现某个实体 | 用该历史边界的完整自身字段更新它，缺席的可选自身字段不沿用旧值 |
| 出现实体子集合 | 逐个合并所列实体，不删除本次未列出的其他实体 |
| 实体子集合省略或为空 | 不据此删除原有子实体 |
| 跨计划引用的来源没有出现在本份报告中 | 保留引用；来源可能已在以前的报告中，也可能后到，不能虚构或删除来源 |

同一实体在一份报告中只能出现一次。身份、所属计划或动作、原始请求关联及已分配文件名不能因合并改变。乱序、重叠报告与累计覆盖仍按[按计划嵌套与客户端合并](status-reports.md#按计划嵌套与客户端合并)处理，不能让旧报告覆盖新状态。

## 计划与动作

计划的必填自身字段为 `plan_instance_id`、`request_id`、`created_at`、`name`、`status`。`plan_instance_id` 同时表达受理顺序，比较时使用精确整数值。前四项关联首次受理事实，`status` 按该计划的全部动作计算：全部终态时为 `completed`；否则曾有动作开始执行时为 `running`，完全没有开始执行时为 `pending`。当前报告的 `actions` 可能只是子集，不能只用它重新计算计划状态。

动作的必填自身字段为 `action_instance_id`、`name`、`type`、`status`。状态迁移以[动作状态模型](scheduling-execution.md#动作状态模型)为准；状态编号与报告文本按[运行状态定义](../camctl/database/plans-actions.md#计划与动作的运行状态)转换。camctl 内部保存的执行经历用于受理、执行和恢复判断，报告通过动作状态、错误阶段及实际结果表达用户需要知道的事实。

目标取消已经生效而必要处理尚未结束时，动作仍为 `running`。动作终态后，设备是否仍在执行原动作要求的工作由 `device_execution` 表达；计划和动作的终态不会因此重新打开。

客户端关注动作是否按照原请求执行、已经取得什么结果以及未完成的原因。`created_at` 表达客户端创建计划的时间，`scheduled_at` 表达请求的执行时间。计划状态使用主机保存的完整计划事实，客户端不能从增量报告列出的动作子集重算计划状态。

### 原始输入与生效参数

`device_id`、`scheduled_at`、`group`、`policy` 表达首次提交的对应公共字段；合法时间从保存的整数值按固定秒级格式还原，其他输入保留原值；`input_params` 表达首次提交的 `params`。原输入省略的字段仍省略，原输入明确提供的 `null`、错误类型或非法值在初始失败报告中保留，不能改造成合法默认值。

合法的设备、时间和组字段分别从 `actions.device_id`、`actions.scheduled_at` 和 `actions.group_name` 取得；非法值从 `actions.input_fields_json` 中的原字段取得。普通列为空时仍须区分输入省略与输入非法，不能一律省略报告字段。保存与重建的完整分类见[计划与动作的输入存储](../camctl/database/plans-actions.md#计划与动作的输入存储)。

动作公共结构中的额外输入字段放在 `extra_input_fields` 对象中，键和值原样保留。例如原动作多写了 `schedule_at`，该字段出现在 `extra_input_fields.schedule_at`，错误位置仍指向原计划的 `actions[i].schedule_at`。这样既保存诊断依据，也不让任意输入键变成报告公共字段。

合法拍摄动作（`camera_take_photo`、`camera_record`、`camera_timelapse`）另有必填 `effective_params`，包含已固化的 `type` 及具体生效参数。它来自原受理事实，不从 `input_params` 或当前配置临时推算。其他动作不提供该字段。非法 `group` 原值只用于诊断；有效组成员关系仍按[动作公共字段](plan-input.md#动作公共字段)判断，取回动作不因此成为组成员。

`effective_params` 从报告历史边界对应的 `actions.effective_params_json` 解码为 JSON 对象，不输出数据库中的 JSON 文本字符串。首次受理失败的动作省略该字段；合法受理后过期、取消或执行失败的拍摄动作仍提供首次保存的完整值。`policy` 始终取自 `actions.input_fields_json` 中的原始输入，不能用供调度读取的 `actions.max_delay_ms` 补造或替换。两个存储字段的有效组合遵守[生效拍摄参数与启动延迟](../camctl/database/plans-actions.md#生效拍摄参数与启动延迟)。

| 动作事实 | 必须表达 | 不能表达 |
| --- | --- | --- |
| 首次受理因自身参数错误而失败 | `failed`、阶段为 `admission` 的 `error`，以及已提供的原始输入 | 生效参数、执行结果、正式产物或交付 |
| 合法受理，尚未进入执行 | `pending`，适用的生效参数 | 执行结果、产物或交付 |
| 已开始执行，尚未终态 | `running`，已经成立的逐项业务结果 | 尚未成立的成功或失败结论 |
| 执行成功或运行后失败 | 成功状态及实际结果，或失败状态及最终错误 | 把运行失败写成受理校验失败 |
| 过期或取消 | 保留实际状态、适用原因和已经成立的结果；过期附 `expiration_reason` | 把取消解释为已撤销全部副作用 |

三种拍摄动作（`camera_take_photo`、`camera_record`、`camera_timelapse`）及 `motor_control` 均采用有效时间窗口。`expiration_reason` 为 `window_missed` 或 `window_exhausted` 的成立条件遵守[公共过期规则](scheduling-execution.md#过期原因)；电机动作的未知发送结果按其[恢复分类](motor-control.md#状态判断与恢复)报告失败，不能仅凭窗口结束写成过期。取回、清理、取消和报告动作不采用该窗口。动作结束后的设备执行情况、交付及用户要求的产物删除结果继续按各自事实更新，原动作终态保持。

`motor_control` 的输入、状态及错误按[电机报告契约](motor-control.md#持久化与报告)表达。`succeeded` 表示控制通知已发送；客户端不能将它显示为电机已到位。该动作不提供 `effective_params`、`result`、产物、交付或 `device_execution`，发送事实不能被转换为对设备状态的观察。

合法动作的公共输入字段须满足[第一版动作入口](plan-input.md#第一版动作入口)，例如取回与清理必须有 `scheduled_at`，非相机动作不接受 `device_id`。报告不会替原始输入修错；初始失败分支对这些字段保留任意 JSON 值，其他分支遵守已通过的输入契约。

### 错误

每个 `error` 包含 `code`、`stage`、`details`。前两者为非空字符串，后者为对象；没有额外细节时使用 `{}`。字段位置和值由所属错误契约提供，缺失值不能伪造为 `null`。多个参数错误可以通过一个汇总错误的 `details.errors` 保留逐项错误；原输入位置不因报告子集合排列而变化。

错误码与阶段由产生该错误的公共边界或驱动登记，遵守[错误表达](client-protocol-examples.md#错误表达)及各责任专题。报告 Schema 不再抄录完整错误码清单。客户端对识别的码提供具体中文说明，对未识别的码保留并展示码、阶段及细节；状态合并与 ACK 资格不能依赖客户端是否认识某个错误码。

动作最终错误由 camctl 根据业务结束条件确定，其整数存储码通过固定定义映射为公共 `code`，该定义同时给出唯一的 `stage`。报告仍完整输出 `code`、`stage` 和 `details`；数据库表示遵守[整数枚举规则](../camctl/database/common.md#状态与类型的整数枚举)。驱动原始错误由对应操作尝试或业务处理结果表达，保留原始码、发生步骤及详情；动作最终错误按自身契约引用相关事实。一次驱动调用失败不自动成为动作最终错误，后续成功也不抹去此前尝试的错误，具体分工遵守[动作最终错误与驱动错误](../camctl/database/operations-devices.md#动作最终错误与驱动错误)。逐项处理、操作尝试、文件诊断和会话错误分别保留所属契约要求的阶段，不从动作最终阶段反推这些记录的实际发生步骤。

动作最终错误的 `details` 来自 `actions.error_details_json` 中的 JSON 对象。没有最终错误时，错误码与详情列同时为 SQL `NULL`，报告省略动作的 `error`；有最终错误且没有额外详情时，详情列保存 `{}`，报告输出对象 `details: {}`。不能将详情文本直接输出为 JSON 字符串。合法组合与保存规则见[动作最终错误字段](../camctl/database/plans-actions.md#动作最终错误字段)。

错误详情按所属错误契约提供，具体原因使用当前已有的可靠事实。用户界面显示涉及的动作或文件及简明原因；未知错误码保留可诊断信息。

### 预览与范围选择的报告契约

`automation` 仅用于自动预览取回，必填 `purpose: auto_preview`；可靠确认来源后提供 `source_action_instance_id`，未确认时省略。合法受理的自动预览动作提供该展示关系，受理失败也可以保留已经可靠取得的关系。客户端据此归并预览，不能仅凭关联存在就宣称动作已受理成功。

取回和清理保留原请求中的来源及选择要求。实际选择的结果通过产物、交付和可定位目标的逐项失败表达。取回或清理尚未结束时，没有明细或结果数组暂时为空，不表示最终没有产物或目标；可靠空结果须结合动作已成功结束的事实解释。

产物和交付继续保留来源、派生及预览关系。客户端只校验已经公开且已经取得的关联，不从本次增量报告未出现的对象猜测完整来源集合。

### 业务报告与内部事实

报告保留动作结果、产物、交付和用户要求的取消、删除结果。调度条件、执行配置、设备调用尝试、复制过程及自动维护责任在内部记录中保存。内部维护实际使业务动作无法完成时，由受影响动作的错误说明实际影响；内部责任存在本身不改变已确定的业务结果。

历史生成只组合固定边界处的可靠事实。报告内容的变化判断与字段生成共用[字段依赖登记](../camctl/database/report-changes.md#文件到报告字段的依赖)；登记的生产实现及跨组件验收见[跨模块契约检查](../camctl/verification.md#跨模块契约检查)。

## 动作结束后，设备是否仍在执行

用户要求录像到指定时长结束，或要求取消拍摄后，camctl 可能已经结束对该动作的处理，却仍未确认相机已经停止。例如，录像停止失败后，动作结果是失败，相机却可能继续录制。报告须同时表达动作结果和设备执行情况，让用户知道要求的停止效果尚未得到确认。

`device_execution` 表示“设备执行情况”，描述动作要求设备执行的工作是否仍在进行，或是否尚未确认结束。字段使用设备无关的名称和状态，适用于具有相应设备执行契约、且已经进入终态的动作。它只描述该动作启动或可能启动的那次工作；同一设备后来执行其他动作时，不能把新工作的状态写入原动作。

第一版由单张拍摄、录像和延时摄影的既定契约提供该字段的事实。后续接入其他设备类型时，由对应动作及驱动声明适用条件、结束依据和事实来源。报告沿用公共字段表达结果，设备特有的操作名称用于用户说明。

该字段包含必填的 `status`，两个取值直接说明设备执行情况：

| `status` | 保存的事实 | 面向用户的说明示例 |
| --- | --- | --- |
| `still_running` | 最近一次可靠观察确认，设备仍在执行该动作要求的工作。 | “最后确认时，相机仍在录制。” |
| `end_unconfirmed` | 该动作可能已使设备开始工作，但没有足够依据确认这次工作已经结束。 | “尚未确认录像已经停止。” |

说明示例用于录像，其他动作按设备和操作的具体名称表达。动作自己的 `status` 继续表达成功、失败、取消或过期等业务结果。存在对应设备执行记录当前可靠保存的 `last_error_json` 时，`device_execution.error` 提供最近一次观察设备执行情况时的错误；动作自身的 `error` 继续说明动作为什么失败，两处错误分别来自各自事实。

报告以冻结的历史边界 H 为依据，即只使用截至该边界已经可靠保存的事实。上述状态不表示生成报告或用户阅读报告时重新查询过设备。客户端应让用户知道这是最近报告中的情况；`end_unconfirmed` 不能显示成“设备已停止”。

生成字段前，须检查所需记录及其组合。记录矛盾、必需历史缺失或无法读取时，报告生成失败并按状态库错误处理。可靠且一致的记录按下表分类：

| H 时的已保存事实 | `device_execution` 的结果 |
| --- | --- |
| 动作不适用该设备执行契约，或尚未进入终态 | 省略；动作自身状态表达普通执行阶段。 |
| 适用动作已经终态，但从未建立对应的设备执行记录，或可靠确认整次工作没有派发、没有启动效果 | 省略。 |
| 适用动作已经终态，已可靠确认设备结束了这次工作 | 省略；文件归属等内部限制尚未解除，不改变已经确认的设备执行结束事实。 |
| 适用动作已经终态，未取得直接的结束观察，但已有符合驱动契约的可靠完成依据，且没有相矛盾的设备观察 | 省略；使用已有完成依据，不补造设备停止观察。第一版适用拍摄契约时，依据可以是规定的时间与全部产物。 |
| 适用动作已经终态，设备执行记录为 `ACTIVE`，仍有可靠依据表明这次工作在进行 | 提供 `status: still_running`。 |
| 适用动作已经终态，启动可能已经生效，设备执行情况未知，且没有上述可靠完成依据 | 提供 `status: end_unconfirmed`。 |

对已终态且适用该字段的动作，字段省略表示没有需要提示的“设备仍在执行或结束尚未确认”的情况。由于设备可能从未开始这次工作，也可能按驱动契约完成，客户端不能仅凭字段省略就宣称执行过停止命令。

后来 camctl 可靠确认设备结束了原动作要求的工作时，原动作取得新的应报告变化。新报告通过完整替换动作自身字段，清除客户端先前保存的 `device_execution` 及对应提示；原动作的失败、取消或过期结果保持。所需设备执行记录始终归属于原动作，后续由其他动作发起停止时也按原归属恢复历史和生成报告。

## 动作结果

`result` 是所属动作的完整结果对象。取回、清理与取消进入执行后提供对应结果，尚未产生条目时数组可以为空；执行前取消时省略结果。Schema 能从 `running`、`succeeded` 或执行失败判定已进入执行时要求结果；`canceled` 是否已经进入执行由生成端根据可靠历史判断，客户端不依据缺席结果补造执行经历。报告动作仅在成功时提供 `result.report_id`。录像仅在已有适用结论或取消内容处理结果时提供非空 `result`。

### 录像、检查与修复

`camera_record.result` 按已取得的事实提供 `check`、`repair` 和 `discard_cleanup`。尚未取得其中任何结果时省略整个对象。

| 字段 | 出现条件与含义 |
| --- | --- |
| `check` | 检查已经取得 `completed`、`failed` 或 `unconfirmed` 的最终结论；保留媒体问题和实际错误。尚未检查或仍在检查时省略。 |
| `repair` | 已确定无需修复，或修复已经成功、失败、取消，分别使用 `not_needed`、`succeeded`、`failed`、`canceled`。未决定或仍在执行时省略；失败必须有错误。 |
| `discard_cleanup` | 取消要求涉及的拍摄内容处理结果，使用 `not_needed`、`pending`、`running`、`completed`、`failed` 或 `unknown`；失败和未知必须保留错误。它不提供内部文件的数量或路径清单。 |
修复失败与录像最终结果分别按业务契约判断。取消内容的处理范围遵守[录像取消](camera-recording.md#camera_record-取消)，其进展变化不改写原录像的取消结果。

### 媒体检查与摘要

产物 `media` 和录像 `result.check` 共用媒体结果结构；录像检查字段仅允许上一节规定的最终结论：`check_status`、`duration` 必填，`issues` 与 `error` 按实际事实提供。`duration` 为 `unknown`，或为 `available` 并带 `seconds`。已读到可靠时长但后续检查失败时，可以同时保留时长与错误。

| 检查事实 | 表达 |
| --- | --- |
| 没有执行媒体检查 | `not_performed`，时长 `unknown`，不提供媒体问题或检查错误 |
| 检查正在进行 | `running`，保留目前已取得的时长或未知状态 |
| 适用检查已执行完成 | `completed`；保留时长及实际发现的 `issues`，没有问题时可省略或为空数组 |
| 检查流程明确失败 | `failed`，提供 `error`；不能因此推断视频已损坏 |
| 处理结束但无法取得可靠检查结论 | `unconfirmed`，提供说明未知原因的 `error` |

`completed` 只表示适用检查已经结束。是否查出时长不足或媒体错误由实际值及 `issues` 表达，不表示整段视频通过逐帧解码。后来发现的媒体问题可以更新产物事实，但不改写原录像终态。

源产物 `checksum` 为 `not_obtained`，或为 `available` 并带 64 位小写十六进制 `sha256`。没有源端摘要不等于源文件损坏。交付文件自己的摘要通过交付的 `sha256` 表达，不能把不完整中间文件的摘要填作最终交付摘要。

### 取回

`result.failures` 包含已确定的逐项最终失败；关联层级和无产物表达遵守[取回失败项的报告表达](obtaining-outputs.md#取回失败项的报告表达)。每项包含 `source_action_instance_id` 和错误；只有确认正式产物存在且属于该来源时才有 `output_id`，只有创建过交付时才有 `delivery_id`。拥有 delivery 关联必然同时拥有产物关联。

显式 ID 不存在或归属不匹配时，失败项关联本次已确认的指定来源，通过 `error.details.requested_output_id` 保留请求中的产物 ID；不填写不成立的 `output_id`、`delivery_id` 关联。同一来源下的多个无效 ID 分别报告，不合并为 `no_outputs`，去重不能忽略请求 ID。错误码和详情以[公共登记](../../protocol/errors/workflow-codes.json)为准。

同一失败只列一次，不按尝试次数重复。全部来源和条目处理结束前，空数组不表示取回成功；部分交付成功、其他项失败时，保留全部实际结果。该版本的 Schema 不在单份报告中强制要求所有引用实体出现，否则跨计划或增量报告会被错误拒绝。

### 清理

精确 ID 清理的 `result.items` 按输入中的 `output_ids` 顺序保存每项完整结果；来源范围清理按已持久化的产物选择顺序报告。等待来源时不能把暂时空的条目解释为完成；可靠确认空集合后，以 `succeeded` 及 `result.items: []` 表达成功空结果。每项必填 `output_id`、`status`；正在处理时分别表达等待或运行，失败时给出 `error`，取消时保留已知处理事实。成功项必须有 `outcome`：

| 成功依据 | `outcome` |
| --- | --- |
| 本次已确认删除完整目标集合 | `deleted` |
| 执行时已有可靠的产物清理完成记录 | `already_cleaned` |
| 恢复核实确认完整目标集合均不存在并补记完成 | `absence_confirmed` |

未知 ID 对应失败项，不创建产物对象。部分删除或结果未知的错误详情须列出已知未删除及未知的文件范围；不能以一句整体失败抹去具体范围。动作整体结果遵守[逐产物结果与整体终态](output-cleanup.md#批量清理结果)，旧成功项不能因另一项重试而重新删除。

清理动作取消时，按[逐产物取消规则](output-cleanup.md#清理取消)分别保存结果。动作的 `canceled` 可以与条目的 `succeeded`、`failed`、`canceled` 同时出现：已完成项保留原结果，已发出的删除须取得实际结果，尚未执行的删除被取消。取消项若有部分删除、删除错误或结果未知，仍通过 `error` 保留实际原因及文件范围；取消不表示文件一定还在。产物的 `availability` 和 `cleanup.status` 继续依据各自事实计算。

### 取消

`result.items` 包含本次实际寻址得到的每个动作，使用 `action_instance_id` 关联。只保存取消标记时，本次取消尚未成功；完成时机和汇总规则见[取消动作的完成时机](task-cancellation.md#取消动作的完成时机)。逐项 `status` 表示本次取消处理进度，不是复制目标动作的状态。

成功项 `outcome: canceled` 表示目标原本未终态，本次取消及有限处理已经完成；`already_terminal` 表示目标原有终态保持，本次适用的有限处理已经完成。目标取回原来已成功但仍有 `ready` 文件时，必须先处理撤回才能给出成功项。

设备任务因缺少停止能力而拒绝取消时，本次逐项结果为 `failed`，`cancellation_effect` 为 `not_applied`，错误说明任务已启动或可能启动且不支持取消，不提供成功项的 `outcome`。目标动作继续报告其实际执行状态，不随取消项一起变成 `failed` 或 `canceled`。批量请求按逐项规则汇总为 `cancel_items_failed`，其他目标已完成的取消保持有效；拒绝项不等待目标任务自然结束。

取回目标另提供 `withdrawals`，逐 delivery 表达撤回待处理、已撤回、已越过撤回边界或撤回失败。`not_retractable` 表示已确认超出 CLI 撤回权限，不等于客户端已经收到文件，也不表示撤回成功；其本身不要求继续等待主程序。位置或结果未知不能写成 `not_retractable`，本次有限核实结束后仍未知则作为失败并保留原因。

没有目标时取消动作以 `target_not_found` 失败，`items` 为空，不补造目标。多个目标中的失败不撤销其他目标已经完成的取消。取消动作自己被取消或已进入终态时仍服从公共状态机，不由结果汇总覆盖原终态。

目标集合包含取消动作自身时，按[自身目标检查](task-cancellation.md#目标集合不得包含取消动作自身)在任何目标取消生效前失败。动作错误须明确表达该原因，不冒充目标不存在或逐项收场失败；已解析目标不表示已经施加取消，不能报告虚构的取消成功。具体错误使用[公共登记](../../protocol/errors/workflow-codes.json)中的 `cancel_self_target`。

取消动作自身被取消时，按[进度与等待范围](task-cancellation.md#取消动作自身被取消)分别表达其自身 `canceled` 与目标已经生效的取消及实际处理事实，不能将其目标全部写为未执行，也不能宣称目标必要收场已停止。后一个取消动作仅选中前一个取消动作时，其成功不证明前一个动作的目标已经停止；目标所属流程继续报告自己的实际状态和结果。目标后续完成不改写前一个取消动作的终态。

### 取消停止等待的机器表达

取消动作自身被取消时，尚未完成的 `result.items` 可用 `status: "canceled"` 表示本次处理或等待已停止，同时必填 `cancellation_effect`：`not_applied` 表示尚未施加目标取消，`applied` 表示目标取消已生效且其必要收场独立继续，`not_required` 表示目标已有终态等无需再施加动作取消的情形。它不表示目标设备已经停止，也不撤销已启动的文件撤回等独立责任。已完成的成功或失败项保持原结果；不能为了匹配动作自身 `canceled` 改写全部条目。

后一个取消动作只取消前一个动作时，其成功项仅关联前一个动作。未直接选中的录像不递归加入其 `items`。取消自身目标的错误与交接结果未知等错误使用[统一登记](../../protocol/errors/workflow-codes.json)；业务处理结果中的 `error` 接受未识别的驱动原始错误。

### 显式报告

`report_status` 成功时的 `result.report_id` 指向完成本次本地发布责任的报告。它可以早于包含该结果的报告：报告 R 发布后动作才能保存成功，随后报告 S 再携带该成功结果。不能强制要求 `result.report_id` 等于当前根 `report_id`。

完整同步和局部同步的参数与起点解析由[同步入口](status-sync.md#请求入口)定义。`input_params` 保留实际输入；参数自身错误按受理失败表达，执行时无法找到起点报告按[起点解析错误](status-sync.md#camctl-何时开始同步)表达，不能补造成功的 `result.report_id`。

等待客户端累计确认的同步责任由[客户端状态同步](status-sync.md)维护；不把远端尚未 ACK 表达成报告动作执行失败，也不将报告内部管理状态作为新增业务字段不断触发下一份报告。

### 单张拍摄与延时摄影结果

`camera_take_photo`、`camera_timelapse` 使用动作状态、适用错误、正式产物及动作结束后的 `device_execution` 表达结果，省略 `result`。原始输入和生效参数各自保留，既有设备说明变化不重解释历史结果。完成依据及产物登记遵守[拍摄结果报告](camera-capture.md#拍摄结果报告)。

## 正式产物

每项必填 `output_id`、`source_action_instance_id`、`kind`、`availability`、`cleanup`、`checksum`、`media`。归属关系必须与所在拍摄动作一致。已知时提供原始文件名 `original_name`、内容类型 `media_type` 和完整大小 `size`；无法可靠取得时省略，而非填写空名称或零长度。

第一版 `original` 是设备生成的原始产物，包括图片和视频，`media_type` 按实际已知的 MIME 内容类型填写；未知时省略。文件类别不能由动作名称或 `kind` 推断。`original` 不要求必须是视频；`repaired` 仍仅用于录像修复。`repaired` 是正式修复成品；后者必须有 `derived_from_output_id` 指向其来源原片。两者各有独立身份，清理不级联。正常修复成品尚未正式登记时，不分配一个可供客户端取回的虚构 output。

产物 `kind: "preview"` 表达预览，并且仅该类别必填 `preview_of_output_id`，关联同一来源动作的原文件；它不填写 `derived_from_output_id`。修复成品继续使用 `kind: "repaired"` 和 `derived_from_output_id`，原文件仍为 `original`。`kind` 表达产物角色，图片或视频类型由 `media_type` 表达。自动预览交付修复成品不改变成品角色，delivery 仍只属于取回动作。

`availability` 表达该正式产物的保留和取回资格，不表达视频是否正常播放或相机此刻是否在线：

| 事实 | 表达 |
| --- | --- |
| 保留文件有效且没有删除限制 | `available`；实际读取仍须满足设备及请求资格 |
| 已存在有效删除限制，包括部分删除或不能排除删除发生 | `restricted`；不允许新取回 |
| 完整目标集合已确认清理完成 | `cleaned` |
| 没有上述清理结论，可靠确认保留文件缺失 | `missing`，附错误 |
| 没有可优先采用的清理限制或完成事实，保留文件状态无法可靠判断 | `unknown`，附错误 |

按表自上而下解释时，`available` 必须同时具备正面证据；限制和清理完成不能被文件仍存在、暂时离线或媒体错误覆盖。查询设备失败不自动推翻已保存的有效文件事实。

`cleanup.status` 表达产物在冻结边界 H 时的清理汇总，取自 `outputs.cleanup_status`；`cleanup.error` 取自同一边界的 `cleanup_error_json`。状态优先级、错误选择及共同提交规则统一见[产物清理汇总](../camctl/database/output-cleanup-state.md)。

`completed` 表示可靠清理完成，`running` 包括当前请求的删除、核实、重试及必要收场，`pending` 包括等待读取者和待删除。`incomplete` 表示没有正在推进的请求但仍留下限制或可能删除事实；`canceled`、`not_requested` 按该汇总规则区分。`pending` 和 `running` 不显示上次清理错误；各次请求的自身结果和历史错误继续保留。

报告重建直接恢复产物汇总，不读取当前清理项重新计算过去。失败的未知产物 ID 不构成有效删除意图；取消最近一次请求不抹去其他请求留下的限制。

## 交付

每个 delivery 必须有自己的 `delivery_id`、`output_id`、`source_action_instance_id`、`file_name`、`display_name`、`status`。它属于发起取回的动作，来源可以属于其他计划；不得将交付复制到来源动作下。

`file_name` 精确采用完整 `<delivery_id>.<ext>`，使用安全 ASCII 扩展名，并满足单文件名长度边界；`display_name` 保留完整可读名称。名称分配与历史唯一性遵守[Delivery 与文件名](outputs.md#delivery-与文件名)。客户端按完整实际文件名查询记录，不解析可读名称，也不按 ID 前缀匹配。

| 交付状态 | 已确认事实 |
| --- | --- |
| `pending` | 身份已登记，尚未开始准备 |
| `preparing` | 正在读取、校验或保存准备完成事实；恢复仍处于本阶段 |
| `prepared` | 独立副本及准备事实已可靠保存，可能仍在等待组内其他来源 |
| `publishing` | 已进入发布处理，尚未可靠保存发布完成事实 |
| `published` | 已可靠保存本地发布事实；主程序随后移动或删除文件不改变这项历史事实 |
| `failed` | 本次交付最终失败，必须提供错误 |
| `canceled` | 尚未可靠发布的本次交付被取消 |
| `withdrawn` | 已发布交付的可撤回文件已确认撤回；原取回动作终态保持 |

正常路径为 `pending → preparing → prepared → publishing → published`。未发布阶段按取消或最终失败结束；已发布后只有可靠撤回才能转为 `withdrawn`。发布结果尚在核实时保持 `publishing`，不能猜测为未发布再发一份，也不能猜测成功。中断恢复按[普通交付恢复规则](file-handoff.md#普通交付的保存顺序与中断恢复)确认三个位置均无副本、没有可靠完成事实且结果无法确认时，交付结束为 `failed`，错误明确保留本地交接结果未知的原因，不自动重投。已终结交付不因新的取回请求复活。

`prepared`、`publishing`、`published`、`withdrawn` 必须有完整 `size` 与最终 `sha256`。此前已知完整源长度时可以提供 `size`，已可靠取得完整目标摘要时才可提供 `sha256`；失败或取消不抹去此前已确认的大小和摘要。部分文件的已复制长度不能代填完整文件长度。

准备完成的副本须已满足[文件一致性与校验](file-copy.md#读取正确性与文件校验)，并取得完整大小和最终目标摘要。源摘要已知时，交付摘要须符合源文件校验规则。客户端依据文件名、大小及摘要核验实际收到的文件；主机发布不代表客户端已经收到。

## 计划文件诊断

每项必填 `diagnostic_id`、`file_name`、非空 `errors` 数组。文件名表达本次交给 CLI 的输入计划文件；即使读取或解析失败也保留。只有完整无歧义解析后取得合法请求 ID，才能附 `request_id`；不能从坏 JSON 片段猜测身份。

`errors[].stage` 按输入读取、解析、整份受理校验或 ACK 校验分类。诊断整体不可变，每次新的失败输入处理有独立身份；同一输入的多个问题属于同一诊断。已支持动作的自身参数错误保存在动作中，不把它们重复包装成整份计划拒绝。完整语义见[计划文件诊断](report-diagnostics.md#计划文件诊断)。

## 语义校验与验收

客户端导入依次检查：原文件名与字节摘要、无歧义 JSON 解析、Schema、当前文件可判定的语义、与本地已有状态的身份及覆盖关系。全部通过并可靠保存后才推进本地可确认范围；失败保留导入诊断，不提交部分计划更新或 ACK。

Schema 无法独立证明的检查分为以下边界：

| 边界 | 必须检查 | 不能据此拒绝的正常情况 |
| --- | --- | --- |
| 单份文件 | 文件名 ID 与根一致，水位顺序合法，真实日期有效，无重复实体 ID | 报告只有诊断或只承载部分计划 |
| 单个实体 | 状态与已知结果一致；设备执行提示、媒体结论和交付完整性依据满足本专题 | 初始失败保留非法原输入；失败或取消保留已经发生的副作用 |
| 已在同份报告或本地记录中出现的关联 | output 属于声明的来源动作；delivery 的产物与来源动作一致；派生关系及文件名一致 | 来源暂未出现在客户端已有数据中，此时保留待关联引用 |
| 已保存历史 | 身份及所属关系不可变，终态不可变，文件名不复用，旧报告不覆盖新事实 | 终态后的产物清理、媒体问题、残留设备收场和交付撤回继续更新 |
| 覆盖与 ACK | 按完整区间判断已保存的累计覆盖和合格报告 | `result.report_id` 早于当前报告；当前计划下仅有变化的动作子集；局部同步报告可以包含比指定起点更早的变化 |

实体结果校验使用完整自身快照；依赖未出现子集合或缺失历史的判断不能假装已取得完整证据。CLI 从完整冻结历史生成报告时必须满足所有成立条件；客户端只在证据可用时检查对应关系，等待来源资料不等于报告损坏。

预览、范围选择和取消停止等待的事实均遵守历史、投影及冻结报告规则；恢复和历史回放不得依赖当前能力重新推导旧选择。增量报告暂缺关联实体时保留引用并等待关联，不凭名称或媒体扩展名推测。Schema 仅验证局部结构，内部集合完整性及选择正确性由主机业务逻辑保证，客户端在已取得证据的范围内检查同源关系、交付与失败汇总。共享实例见[协议样例](../../protocol/examples/workflows/README.md)。

验证至少包括：既有成功及部分失败样例；取消仍在有限处理、取消完成及停止耗尽；删除逐项成功、失败和恢复确认；显式报告引用较早报告；未执行媒体检查；无源摘要的允许降级；初始失败保留 `null`、错误类型和额外输入键。反例覆盖错误状态值、缺少必填字段、伪造生效参数、缺少最终交付摘要、无产物却捏造关联、重复 ID、设备执行状态非法或用于未结束动作、错误水位及哈希不匹配。

Schema 与协议样例的文件检查属于规格校验。实际实现时仍须组合真实 SQLite、报告生成和客户端导入进行集成验证，证明冻结历史、字节重建、事务合并和累计确认可以共同工作；相机替身通过不等于真实设备已经完成联调。
