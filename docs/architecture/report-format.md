# 状态报告字段契约

[返回设计总览](README.md) · [报告与累计确认](status-reports.md) · [客户端协议样例](client-protocol-examples.md) · [阅读路线](reading-guide.md)

本专题说明第一版报告中每个字段表示什么、什么时候需要出现，以及多个字段之间必须满足什么关系。[status-report.schema.json](../../protocol/schemas/status-report.schema.json) 使用 JSON Schema Draft 2020-12，作为字段名、类型、必填项、可选项和枚举值的机器可读权威定义；本专题解释这些字段对应的业务事实。实现中的公共报告类型、校验器与状态选择应从该定义读取或生成，不另行维护一套完整字段和状态清单。

报告覆盖与合并由[状态报告与累计确认](status-reports.md)定义，各动作的执行、失败和恢复仍由对应责任专题定义。Schema 校验通过不等于覆盖连续、业务事实成立或允许确认报告；客户端还须执行本专题的语义检查。相机专属输入参数来自首次受理时保存的事实，不能用客户端目前加载的相机 Schema 重新校验历史报告。

## 文件与基本值

报告使用 UTF-8，包含一个完整 JSON 对象。解析规则与[输入文件与基本值类型](plan-input.md#输入文件与基本值类型)一致：对象成员名唯一，不接受非 JSON 数值常量，不隐式转换类型，省略与 `null` 不等价。客户端先按[文件名与完整性校验](status-reports.md#文件名与完整性校验)校验收到的原始字节，再解析内容；重新排版后的 JSON 不再是同一份交接文件。

标识、可读名称与 UTC 时间沿用输入契约；数据库对象 ID（包括报告编号）使用[规范十进制字符串](plan-input.md#对象-id)，水位、字节数和次数使用 Schema 规定的非负或正整数范围。秒数使用有限非负数，超时须大于零；未知时长不能以零表示。Schema 的时间正则只检查表示形式，实际日期和首尾 Unicode 空白还须按输入契约检查。

除了原始输入值、驱动参数及明确开放的错误细节，报告对象不接受未声明字段，状态值也必须属于该版本的 Schema。未知错误码按[错误与等待原因](#错误与等待原因)处理，不与未知状态值混为一谈。

报告生成从冻结历史取值，实体排列、对象字段顺序、字符串转义、精确数值和排版遵守[确定字节编码](report-encoding.md)。对既有报告重建必须保持原字节、文件名和摘要；客户端按业务身份解析，不依赖字段排列。

## 自身字段与实体子集合

报告根的必填字段为 `report_id`、`from_wm`、`to_wm`，必须满足 `from_wm <= to_wm`。`plans` 与 `plan_file_diagnostics` 可以省略；报告内容选择仍须满足所属覆盖区间，不能以 Schema 允许省略为由漏报变化。

仅以下数组采用按身份合并的规则：

| 所在对象与子集合 | 身份字段 | 所属关系 |
| --- | --- | --- |
| 报告 `plans` | `plan_instance_id` | 本主机已受理计划 |
| 计划 `actions` | `action_instance_id` | 该计划首次受理的动作 |
| 拍摄动作 `outputs` | `output_id` | 该动作登记的正式产物 |
| 取回动作 `deliveries` | `delivery_id` | 该次取回创建的交付 |
| 报告 `plan_file_diagnostics` | `diagnostic_id` | 一次输入处理的诊断 |

其余字段都是所属对象的自身字段，包括整个 `result`、`waiting`、参数对象、尝试数组和逐项结果数组。它们随自身快照整体替换，不按内部 ID 增量拼接。例如新版 `result.failures: []` 表达当前没有失败项，不能保留旧数组中的项目。

| 新快照的内容 | 客户端处理 |
| --- | --- |
| 出现某个实体 | 用该历史边界的完整自身字段更新它，缺席的可选自身字段不沿用旧值 |
| 出现实体子集合 | 逐个合并所列实体，不删除本次未列出的其他实体 |
| 实体子集合省略或为空 | 不据此删除原有子实体 |
| 跨计划引用的来源没有出现在本份报告中 | 保留引用；来源可能已在以前的报告中，也可能后到，不能虚构或删除来源 |

同一实体在一份报告中只能出现一次。身份、所属计划或动作、原始请求关联及已分配文件名不能因合并改变。乱序、重叠报告与累计覆盖仍按[按计划嵌套与客户端合并](status-reports.md#按计划嵌套与客户端合并)处理，不能让旧报告覆盖新状态。

## 计划与动作

计划的必填自身字段为 `plan_instance_id`、`request_id`、`created_at`、`name`、`status`。`plan_instance_id` 同时表达受理顺序，比较时使用精确整数值。前四项关联首次受理事实，`status` 按该计划的全部动作计算：全部终态时为 `completed`；否则曾有动作开始执行时为 `running`，完全没有开始执行时为 `pending`。当前报告的 `actions` 可能只是子集，不能只用它重新计算计划状态。

动作的必填自身字段为 `action_instance_id`、`name`、`type`、`status`、`execution`。`execution.started` 表示是否曾可靠保存进入 `running` 的事实，不表示厂商已成功开始录像。状态迁移以[动作状态模型](scheduling-execution.md#动作状态模型)为准。

状态的数据库整数编号与报告文本值按[运行状态定义](../camctl/database/plans-actions.md#计划与动作的运行状态)转换，`execution.started` 来自冻结历史边界处的 `actions.execution_started`。目标取消已生效但仍在必要收场时，动作状态为 `running`；内部 `cancel_requested` 由执行控制使用，报告继续通过既有动作状态、取消明细及设备或文件进度表达相应事实。

客户端关注动作是否按照原请求的 `scheduled_at` 及适用调度规则执行，以及当前进度和最终结果。报告通过原始时间意图、动作状态、等待原因、过期原因、错误及结果表达这些信息。实际执行资格和时间窗口由 camctl 判定；主机事件时间及其可信性由 camctl 内部用于调度、恢复和诊断。`created_at` 继续表达客户端创建计划的时间，`scheduled_at` 继续表达请求的执行时间。

### 原始输入与生效参数

`device_id`、`scheduled_at`、`group`、`policy` 表达首次提交的对应公共字段；合法时间从保存的整数值按固定秒级格式还原，其他输入保留原值；`input_params` 表达首次提交的 `params`。原输入省略的字段仍省略，原输入明确提供的 `null`、错误类型或非法值在初始失败报告中保留，不能改造成合法默认值。

合法的设备、时间和组字段分别从 `actions.device_id`、`actions.scheduled_at` 和 `actions.group_name` 取得；非法值从 `actions.input_fields_json` 中的原字段取得。普通列为空时仍须区分输入省略与输入非法，不能一律省略报告字段。保存与重建的完整分类见[计划与动作的输入存储](../camctl/database/plans-actions.md#计划与动作的输入存储)。

动作公共结构中的额外输入字段放在 `extra_input_fields` 对象中，键和值原样保留。例如原动作多写了 `schedule_at`，该字段出现在 `extra_input_fields.schedule_at`，错误位置仍指向原计划的 `actions[i].schedule_at`。这样既保存诊断依据，也不让任意输入键变成报告公共字段。

合法拍摄动作（`camera_take_photo`、`camera_record`、`camera_timelapse`）另有必填 `effective_params`，包含已固化的 `type` 及具体生效参数。它来自原受理事实，不从 `input_params` 或当前配置临时推算。其他动作不提供该字段。非法 `group` 原值只用于诊断；有效组成员关系仍按[动作公共字段](plan-input.md#动作公共字段)判断，取回动作不因此成为组成员。

`effective_params` 从报告历史边界对应的 `actions.effective_params_json` 解码为 JSON 对象，不输出数据库中的 JSON 文本字符串。首次受理失败的动作省略该字段；合法受理后过期、取消或执行失败的拍摄动作仍提供首次保存的完整值。`policy` 始终取自 `actions.input_fields_json` 中的原始输入，不能用供调度读取的 `actions.max_delay_ms` 补造或替换。两个存储字段的有效组合遵守[生效拍摄参数与启动延迟](../camctl/database/plans-actions.md#生效拍摄参数与启动延迟)。

| 动作事实 | 必须表达 | 不能表达 |
| --- | --- | --- |
| 首次受理因自身参数错误而失败 | `failed`、`execution.started: false`、阶段为 `admission` 的 `error`，以及已提供的原始输入 | 生效参数、执行结果、正式产物、delivery 或执行尝试 |
| 合法受理，尚未进入执行 | `pending`、`execution.started: false`，适用的生效参数及等待原因 | 执行结果、产物或交付 |
| 已开始执行，尚未终态 | `running`、`execution.started: true`，已取得的处理进度 | 尚未成立的成功或失败结论 |
| 执行成功或运行后失败 | `execution.started: true`，成功结果或最终错误 | 把运行失败写成受理校验失败 |
| 过期或取消 | 保留是否曾开始执行的实际值；过期附 `expiration_reason` | 重置尝试记录或把未执行写成执行成功 |

三种拍摄动作（`camera_take_photo`、`camera_record`、`camera_timelapse`）均采用启动窗口。`expiration_reason` 为 `window_missed` 或 `window_exhausted` 的成立条件遵守[公共过期规则](scheduling-execution.md#过期原因)。取回、清理、取消和报告动作不采用该窗口。终态动作不再提供自身 `waiting`；尚未结束的设备活动和文件清理责任通过各自结果表达，不能据此重开历史动作。

合法动作的公共输入字段须满足[第一版动作入口](plan-input.md#第一版动作入口)，例如取回与清理必须有 `scheduled_at`，非相机动作不接受 `device_id`。报告不会替原始输入修错；初始失败分支对这些字段保留任意 JSON 值，其他分支遵守已通过的输入契约。

### 错误与等待原因

每个 `error` 包含 `code`、`stage`、`details`。前两者为非空字符串，后者为对象；没有额外细节时使用 `{}`。字段位置和值由所属错误契约提供，缺失值不能伪造为 `null`。多个参数错误可以通过一个汇总错误的 `details.errors` 保留逐项错误；原输入位置不因报告子集合排列而变化。

错误码与阶段由产生该错误的公共边界或驱动登记，遵守[错误表达](client-protocol-examples.md#错误表达)及各责任专题。报告 Schema 不再抄录完整错误码清单。客户端对识别的码提供具体中文说明，对未识别的码保留并展示码、阶段及细节；状态合并与 ACK 资格不能依赖客户端是否认识某个错误码。

动作最终错误由 camctl 根据业务结束条件确定，其整数存储码通过固定定义映射为公共 `code`，该定义同时给出唯一的 `stage`。报告仍完整输出 `code`、`stage` 和 `details`；数据库表示遵守[整数枚举规则](../camctl/database/common.md#状态与类型的整数枚举)。驱动原始错误由对应操作尝试或业务处理结果表达，保留原始码、发生步骤及详情；动作最终错误按自身契约引用相关事实。一次驱动调用失败不自动成为动作最终错误，后续成功也不抹去此前尝试的错误，具体分工遵守[动作最终错误与驱动错误](../camctl/database/operations-devices.md#动作最终错误与驱动错误)。逐项处理、操作尝试、文件诊断和会话错误分别保留所属契约要求的阶段，不从动作最终阶段反推这些记录的实际发生步骤。

动作最终错误的 `details` 来自 `actions.error_details_json` 中的 JSON 对象。没有最终错误时，错误码与详情列同时为 SQL `NULL`，报告省略动作的 `error`；有最终错误且没有额外详情时，详情列保存 `{}`，报告输出对象 `details: {}`。不能将详情文本直接输出为 JSON 字符串。合法组合与保存规则见[动作最终错误字段](../camctl/database/plans-actions.md#动作最终错误字段)。

`waiting` 是当前仍成立的等待原因数组；没有等待原因时省略，不能用空原因表示未知错误。多个独立条件可同时出现，终态不保留旧等待。具体含义如下，`details` 中只放已知的对象关联或等待事实：

| 原因 | 含义及适用细节 |
| --- | --- |
| `scheduled_time` | 尚未到计划时间；时间由本动作的 `scheduled_at` 给出 |
| `device_busy` | 设备被不兼容活动占用；已知时给出 `action_instance_id` |
| `device_reserved` | 另一录像仍保留启动重试机会；给出其 `action_instance_id` |
| `retry_delay` | 尚未到再次尝试的时刻；可提供 `remaining_s`，不据此改写已消耗次数 |
| `source_actions` | 等待产物来源动作结束；给出 `action_instance_ids` |
| `copy_slot` | 等待相机的读取机会；已知时给出占用动作 `action_instance_id` |
| `readers` | 清理等待既有取回结束读取；给出 `output_ids` |
| `clock_untrusted` | 当前会话时间不可信，普通执行或后处理等待后续具备资格的会话 |
| `report_publication` | 显式报告动作所需的本地报告处理尚未完成 |

已知关联必须提供；暂时无法可靠取得的关联不补造。等待详情不作为新的调度输入，不直接使用客户端时间推进主机动作。

### 预览与范围选择的报告契约

下列字段及其 Schema 定义预览与范围选择的报告结构。`automation`、`obtaining`、`cleaning` 均是动作自身字段，随动作完整自身字段替换；不作为客户端按 ID 合并的子实体集合。输入原值继续放在 `input_params`，不能用这些执行事实覆盖原请求。

| 字段 | 含义与出现条件 |
| --- | --- |
| `action.automation` | 自动用途已可靠解析时保留 `purpose: "auto_preview"`、`source_action_instance_id` 和受理能力依据 `capability`；合法自动取回受理后即提供，尚未执行也保留 |
| `automation.capability` | `device_id`、`action_type`、`parameter_type`、`preview_supported` 表达受理时依据，不从当前能力重新计算；受理失败也可保留可靠依据，字段存在不表示校验通过 |
| `action.obtaining` | 取回实际开始后必填，含 `source`、`filter` 和 `selections`；`filter` 是生效的 `default`、`preview` 或 `explicit` |
| `obtaining.source` | `status: "unresolved"` 表示尚未可靠固定来源；`fixed` 时提供来源 `plan_instance_id` 及完整固定的 `action_instance_ids` |
| `obtaining.selections[]` | 每个固定来源一个记录，含 `source_action_instance_id` 与 `status`；`pending` 不提供结果数组，`fixed` 提供 `items`，空数组表示该来源已完成选择而没有选中产物 |
| `action.cleaning` | 清理实际开始后必填，含 `selection`；范围清理还必须提供与取回同结构的 `source`，精确 ID 清理省略 `source` |
| `cleaning.selection` | `pending` 表示尚未固定完整集合；`fixed` 时提供 `output_ids`，范围清理可为空，精确 ID 模式保存原非空列表及顺序 |

`unresolved` 不代表不存在、无产物或查询成功。来源确认失败保留实际错误，不能改写成 `fixed` 空集合。固定来源仅包含按契约需要处理的产物来源动作；来源未固定时 `selections` 必须为空，固定后每个来源恰有一个选择记录，不能重复或混入范围外来源。逐来源选择未完成时保持 `pending`；取回的失败项另由 `result.failures` 表达，空选择本身不决定动作成功或失败。范围清理等待全部来源结束前不能提前写成 `fixed` 空集合。

选择条目的 `output_id` 始终指向实际选中的产物，`reason` 的含义如下：

| `reason` | 选择事实及关联 |
| --- | --- |
| `original` | 普通默认选择原文件 |
| `repaired` | 普通默认选择修复成品，必填 `original_output_id` |
| `explicit` | 精确 ID 选择；来源不匹配或不存在的 ID 只进失败详情，不伪造选择条目 |
| `preview` | 选择真实预览，必填 `original_output_id`、`preview_output_id`；后者与 `output_id` 相同 |
| `repaired_not_larger` | 预览取回选择不大于预览的修复成品，必填 `original_output_id`、`preview_output_id`、`preview_size` 和 `repaired_size` |

存在修复成品且完成大小比较时，无论选预览还是成品，都提供比较时保存的 `preview_size` 与 `repaired_size`；两个字段一起出现。`repaired_not_larger` 要求成品大小小于或等于预览，因成品更大而选择 `preview` 时要求严格大于。没有适用修复成品时不补造大小。选择记录与 delivery、失败项、源产物的身份和完整大小必须一致；选择持久化后不因重试或当前文件变动重新计算。

### 本地执行配置在报告中的含义

报告中的尝试上限、读取超时和修复门槛用于表达执行及判断时采用的依据，来源见[执行依据与历史报告](configuration.md#执行依据与历史报告)。客户端按报告历史先后合并这些值，不将它们作为贯穿所有运行的身份字段。旧报告晚到时不覆盖较新的执行依据，也不能仅因同一流程在两份报告中的上限不同而拒绝报告。

| 报告中的事实 | 接收与合并规则 |
| --- | --- |
| 尚未结束的流程在后续运行中采用不同上限或超时 | 可以接收较新报告中的值；保留原尝试身份、累计次数及已经确定的结果 |
| 降低上限后，累计次数大于新上限 | 组合合法，保留累计次数；客户端不据此推断曾经违规执行 |
| 较旧报告包含不同的历史上限 | 按旧历史事实校验，不覆盖较新状态；不能按较新配置重新解释旧尝试 |
| 动作或处理已有终态，后续仅修改本地配置 | 保持其原结果及最终执行依据，不重新激活或改写；独立未完成责任按自身状态判断 |
| 已结束会话的应急停止记录 | 上限、次数及结果作为该会话事实保持不变；该记录不使用跨会话可变上限规则 |

尝试编号连续、已有记录不能消失、确定结果不能回退、同一流程不能并发执行多个尝试等约束继续成立。单份报告中的末次上限不足以验证每个历史尝试当时的执行资格；camctl 在尝试创建的业务事务中按当时上限检查，并保存相关依据。

## 动作结果

`result` 是所属动作的完整结果对象。取回、清理与取消进入执行后即提供对应结果，尚未产生条目时可以为空数组。报告动作成功时提供履行本次本地发布责任的 `report_id`。录像仅在对应处理事实已经登记时提供结果；有启动流程记录时必须包含 `recording`。

### 录像、检查与修复

`result.recording.start`、`stop` 分别包含 `max_attempts` 与该流程的 `attempts`。`max_attempts` 表示报告历史边界内最后可靠保存的对应上限依据；流程建立、尝试资格判断及后续执行按[执行依据与历史报告](configuration.md#执行依据与历史报告)保存必要值。空数组表示尚未开始尝试；尝试一旦登记，恢复、取消或重送均不删除或重新编号。`attempt_no` 从 1 连续递增。降低配置上限后，已有尝试数可以大于报告中的新上限，不能据此拒绝合法历史。

尝试 `running` 表示已开始、尚无最终结果；`succeeded` 表示已确认成功；`failed` 必须有错误；`unknown` 表示无法确认结果。未知不能写成失败后随意重试，是否允许再次发令仍由设备协议和恢复规则决定。一个流程至多有一个尚在执行的尝试；查询后来确认结果可以补充事实，不能变成一次新的命令发送。

| 字段 | 出现条件与含义 |
| --- | --- |
| `recording.control_elapsed_s` | 已可靠取得的控制计时；未知时省略，不能填媒体时长或目标时长 |
| `recording.effect` | 已登记设备活动的停止处理；按[设备活动登记与停止处理](scheduling-execution.md#设备活动登记与停止处理)表达收场进度和错误 |
| `recording.residual` | 已记录的遗留录像事实；`possibly_recording` 表达仍可能录像，后续确认停止可更新为 `stopped`，不改写原动作终态 |
| `recording.emergency_stops` | 已成功补记的[会话应急停止](session-errors.md#正在录像时的应急停止)事实；包含流程、会话、已用次数与结果，不能报告尚未落盘的内存结果 |
| `recording.followup_stops` | [后续动作触发的残留收场](camera-recovery.md#后续动作触发的残留收场)；每项包含原流程 ID、触发动作、独立预算、尝试和结果 |
| `result.source_copy` | 主机检查或修复实际使用的原片输入副本的读取进度；使用下文的公共拷贝字段，不创建取回 delivery |
| `result.check` | 正式产物登记前已经开始或取得的原片检查；登记后相应媒体事实还由正式产物表达 |
| `result.repair` | 修复决定与处理结果；未决定为 `undetermined`，已确认不需要为 `not_needed`，其余按实际待处理、执行及终结事实表达 |
| `result.discard_cleanup` | 取消录像后的废弃内容清理结果；适用文件与权限按[录像取消](camera-recording.md#camera_record-取消)判断 |

应急停止 `outcome` 分别表达确认停止、未确认停止或未尝试；应急限额在其所属会话内固定，`attempts_used` 不超过已知上限。上限无法可靠取得时省略 `max_attempts`，不能用生成报告时的配置补填历史应急记录。后续收场取消或过期表示触发动作结束且尚未发出停止命令；已发出命令的流程继续有限收场，沿用累计次数并使用执行会话的上限，再表达停止或失败。

后续会话取得新的设备证据时，应保留先前会话已经记录的应急停止事实，包括原有结果和尝试次数。例如，先前记录为未确认停止，后续会话确认设备已经停止，应另记后续事实并更新当前设备状态，不能改写旧应急记录为停止成功。客户端合并报告时遵守相同的历史不变量。

`recording.emergency_stops` 只输出已结束会话最后可靠保存的应急记录，不输出该会话仍在继续尝试的中间记录。会话结束不表示停止已经确认；记录可以保留 `unconfirmed`，也不能补造没有保存的尝试次数。某条记录一旦进入报告，其流程、会话、已用次数、已知上限和结果保持不变；后续事实使用相应的新记录及当前状态表达。

`repair` 未结束时，录像动作尚不能按正常成功结束。修复 `failed` 必须有错误，但不直接决定录像失败，遵守[修复与动作成功分离](camera-recovery.md#修复与动作成功分离)。在尚未登记正式产物的阶段，检查和修复记录不能伪装成 `outputs`。

### 媒体检查与摘要

`media` 和 `result.check` 使用同一结构：`check_status`、`duration` 必填，`issues` 与 `error` 按实际事实提供。`duration` 为 `unknown`，或为 `available` 并带 `seconds`。已读到可靠时长但后续检查失败时，可以同时保留时长与错误。

| 检查事实 | 表达 |
| --- | --- |
| 没有执行媒体检查 | `not_performed`，时长 `unknown`，不提供媒体问题或检查错误 |
| 检查正在进行 | `running`，保留目前已取得的时长或未知状态 |
| 适用检查已执行完成 | `completed`；保留时长及实际发现的 `issues`，没有问题时可省略或为空数组 |
| 检查流程明确失败 | `failed`，提供 `error`；不能因此推断视频已损坏 |
| 处理结束但无法取得可靠检查结论 | `unconfirmed`，提供说明未知原因的 `error` |

`completed` 只表示适用检查已经结束。是否查出时长不足或媒体错误由实际值及 `issues` 表达，不表示整段视频通过逐帧解码。后来发现的媒体问题可以更新产物事实，但不改写原录像终态。

源产物 `checksum` 为 `not_obtained`，或为 `available` 并带 64 位小写十六进制 `sha256`。没有源端摘要不等于源文件损坏。交付文件自己的摘要通过交付的 `sha256` 表达，不能把不完整中间文件的摘要填作最终交付摘要。

### 取回

`result.failures` 包含已确定的逐项最终失败；关联层级和无产物表达遵守[取回失败项的报告表达](obtaining-outputs.md#取回失败项的报告表达)。每项包含 `source_action_instance_id` 和错误；只有确认正式产物存在且属于该来源时才有 `output_id`，只有创建过交付时才有 `delivery_id`。拥有 delivery 关联必然同时拥有产物关联。

显式 ID 不存在或归属不匹配时，失败项关联本次已确认的指定来源，通过 `error.details.requested_output_id` 保留请求中的产物 ID；不填写不成立的 `output_id`、`delivery_id` 关联。同一来源下的多个无效 ID 分别报告，不合并为 `no_outputs`，去重不能忽略请求 ID。错误码和详情以[公共登记](../../protocol/errors/workflow-codes.json)为准。

同一失败只列一次，不按尝试次数重复。全部来源和条目处理结束前，空数组不表示取回成功；部分交付成功、其他项失败时，保留全部实际结果。该版本的 Schema 不在单份报告中强制要求所有引用实体出现，否则跨计划或增量报告会被错误拒绝。

### 清理

精确 ID 清理的 `result.items` 按输入中的 `output_ids` 顺序保存每项完整结果；来源范围清理按已持久化的产物选择顺序报告。等待来源时不能把暂时空的条目解释为完成；可靠确认空集合后报告成功及无产物原因。每项必填 `output_id`、`status`；正在处理时分别表达等待或运行，失败时给出 `error`，取消时保留已知处理事实。成功项必须有 `outcome`：

| 成功依据 | `outcome` |
| --- | --- |
| 本次已确认删除完整目标集合 | `deleted` |
| 执行时已有可靠的产物清理完成记录 | `already_cleaned` |
| 恢复核实确认完整目标集合均不存在并补记完成 | `absence_confirmed` |

未知 ID 对应失败项，不创建产物对象。部分删除或结果未知的错误详情须列出已知未删除及未知的文件范围；不能以一句整体失败抹去具体范围。动作整体结果遵守[逐产物结果与整体终态](output-cleanup.md#批量清理结果)，旧成功项不能因另一项重试而重新删除。

清理动作取消时，按[逐产物取消规则](output-cleanup.md#清理取消)分别保存结果。动作的 `canceled` 可以与条目的 `succeeded`、`failed`、`canceled` 同时出现：已完成项保留原结果，已发出的删除须取得实际结果，尚未执行的删除被取消。取消项若有部分删除、删除错误或结果未知，仍通过 `error` 保留实际原因及文件范围；取消不表示文件一定还在。产物的 `availability` 和 `cleanup.status` 继续依据各自事实计算。

### 取消

`result.items` 包含本次实际寻址得到的每个动作，使用 `action_instance_id` 关联。只保存取消标记时，本次取消尚未成功；完成时机和汇总规则见[取消动作的完成时机](task-cancellation.md#取消动作的完成时机)。逐项 `status` 表示本次取消处理进度，不是复制目标动作的状态。

成功项 `outcome: canceled` 表示目标原本未终态，本次取消及有限处理已经完成；`already_terminal` 表示目标原有终态保持，本次适用的有限处理已经完成。目标取回原来已成功但仍有 `ready` 文件时，必须先处理撤回才能给出成功项。

设备任务因缺少停止能力而拒绝取消时，本次逐项结果为 `failed`，`cancellation_effect` 为 `not_applied`，错误说明任务已启动或可能启动且不支持取消，不提供成功项的 `outcome`。目标动作继续报告其实际执行状态，不随取消项一起变成 `failed` 或 `canceled`。批量请求按逐项规则汇总为 `cancel_items_failed`，其他目标已完成的取消保持有效；拒绝项不等待目标任务自然结束。

取回目标另提供 `withdrawals`，逐 delivery 表达撤回待处理、已撤回、已越过撤回边界或撤回失败。`not_retractable` 表示已确认超出 CLI 撤回权限，不等于客户端已经收到文件，也不表示撤回成功；其本身不要求继续等待主程序。位置或结果未知不能写成 `not_retractable`，本次有限核实结束后仍未知则作为失败并保留原因。

没有目标时取消动作以 `target_not_found` 失败，`items` 为空，不补造目标。多个目标中的失败不撤销其他目标已经完成的取消。取消动作自己被取消或已进入终态时仍服从公共状态机，不由结果汇总覆盖原终态。

目标集合包含取消动作自身时，按[自身目标检查](task-cancellation.md#目标集合不得包含取消动作自身)在任何目标取消生效前失败。动作错误须明确表达该原因，不冒充目标不存在或逐项收场失败；已解析目标不表示已经施加取消，不能报告虚构的取消成功。具体错误使用[公共登记](../../protocol/errors/workflow-codes.json)中的 `cancel_self_target`。

取消动作自身被取消时，按[进度与等待范围](task-cancellation.md#取消动作自身被取消)分别表达其自身 `canceled` 与目标已经生效的取消及实际处理事实，不能将其目标全部写为未执行，也不能宣称目标必要收场已停止。后一个取消动作仅选中前一个取消动作时，其成功不证明前一个动作的目标已经停止；目标所属流程继续报告自己的实际状态和结果。目标后续完成不改写前一个取消动作的终态。

### 取消停止等待的机器表达

取消动作自身被取消时，尚未完成的 `result.items` 可用 `status: "canceled"` 表示本次处理或等待已停止，同时必填 `cancellation_effect`：`not_applied` 表示尚未施加目标取消，`applied` 表示目标取消已生效且其必要收场独立继续，`not_required` 表示目标已有终态等无需再施加动作取消的情形。它不表示目标设备已经停止，也不撤销已启动的文件撤回等独立责任。已完成的成功或失败项保持原结果；不能为了匹配动作自身 `canceled` 改写全部条目。

后一个取消动作只取消前一个动作时，其成功项仅关联前一个动作。未直接选中的录像不递归加入其 `items`。取消自身目标的错误与交接结果未知等错误，使用[统一登记](../../protocol/errors/workflow-codes.json)；操作尝试或业务处理结果中的 `error` 仍接受未识别的驱动原始错误。中间文件继续用 `copy.work_file_cleanup`，不因完整或半成品增加另一套状态。

### 显式报告

`report_status` 成功时的 `result.report_id` 指向完成本次本地发布责任的报告。它可以早于包含该结果的报告：报告 R 发布后动作才能保存成功，随后报告 S 再携带该成功结果。不能强制要求 `result.report_id` 等于当前根 `report_id`。

完整同步和局部同步的参数与起点解析由[同步入口](status-sync.md#请求入口)定义。`input_params` 保留实际输入；参数自身错误按受理失败表达，执行时无法找到起点报告按[起点解析错误](status-sync.md#camctl-何时开始同步)表达，不能补造成功的 `result.report_id`。

等待客户端累计确认的同步责任由[客户端状态同步](status-sync.md)维护；不把远端尚未 ACK 表达成报告动作执行失败，也不将报告内部管理状态作为新增业务字段不断触发下一份报告。

### 单张拍摄与延时摄影结果

`camera_take_photo`、`camera_timelapse` 的 `result` 使用 `capture_result`，详见[拍摄结果报告](camera-capture.md#拍摄结果报告)。原始输入和生效参数各自保留，既有设备说明变化不重解释历史结果。

## 正式产物

每项必填 `output_id`、`source_action_instance_id`、`kind`、`availability`、`cleanup`、`checksum`、`media`。归属关系必须与所在拍摄动作一致。已知时提供原始文件名 `original_name`、内容类型 `media_type` 和完整大小 `size`；无法可靠取得时省略，而非填写空名称或零长度。

第一版 `original` 是设备生成的原始产物，包括图片和视频，`media_type` 按实际已知的 MIME 内容类型填写；未知时省略。文件类别不能由动作名称或 `kind` 推断。`original` 不要求必须是视频；`repaired` 仍仅用于录像修复。`repaired` 是正式修复成品；后者必须有 `derived_from_output_id` 指向其来源原片。两者各有独立身份，清理不级联。正常修复成品尚未正式登记时，不分配一个可供客户端取回的虚构 output。

产物 `kind: "preview"` 表达预览，并且仅该类别必填 `preview_of_output_id`，关联同一来源动作的原文件；它不填写 `derived_from_output_id`。修复成品继续使用 `kind: "repaired"` 和 `derived_from_output_id`，原文件仍为 `original`。`kind` 表达产物角色，图片或视频类型由 `media_type` 表达。自动预览交付修复成品不改变成品角色，delivery 仍只属于取回动作。

`availability` 表达该正式产物的保留和取回资格，不表达视频是否正常播放或相机此刻是否在线：

| 事实 | 表达 |
| --- | --- |
| 保留文件有效且没有删除限制 | `available`；实际读取仍须满足设备及请求资格 |
| 已存在有效删除限制，包括部分删除或不能排除删除发生 | `restricted`；不允许新取回 |
| 完整目标集合已确认清理完成 | `cleaned` |
| 没有上述清理结论，可靠确认保留文件缺失 | `missing`，附错误 |
| 没有可优先采用的清理限制或完成事实，保留文件状态无法可靠判断 | `unknown`，附错误 |

按表自上而下解释时，`available` 必须同时具备正面证据；限制和清理完成不能被文件仍存在、暂时离线或媒体错误覆盖。查询设备失败不自动推翻已保存的有效文件事实。

`cleanup.status` 表达该产物的清理进度，按下列优先级从历史计算；各次请求的结果仍分别保存在清理动作中：

1. 已可靠保存整个目标集合清理完成：`completed`，与 `availability: cleaned` 同时成立。
2. 有未结束的有效删除意图：已开始删除或核实删除结果为 `running`；全部仍在等待旧读取为 `pending`。这两者均保持取回限制。
3. 没有进行中的清理，但仍有未解除的删除限制或可能发生过删除：`incomplete`，保持取回限制并提供错误原因。
4. 有过删除意图，均已在允许解除限制的阶段取消，且没有其他限制：`canceled`。文件的实际存在性再决定 `availability`，不凭取消推断文件一定存在。
5. 尚未登记任何有效删除意图：`not_requested`。

失败的未知产物 ID 不构成有效删除意图。删除失败、取消和恢复判断遵守[清理与取回并发](output-cleanup.md#清理与取回并发)；不能仅因为最近一次请求被取消就抹去更早的不可恢复删除限制。

## 交付与拷贝

每个 delivery 必须有自己的 `delivery_id`、`output_id`、`source_action_instance_id`、`file_name`、`display_name`、`status`、`copy`。它属于发起取回的动作，来源可以属于其他计划；不得将交付复制到来源动作下。

`file_name` 精确采用完整 `<delivery_id>.<ext>`，使用安全 ASCII 扩展名，并满足单文件名长度边界；`display_name` 保留完整可读名称。名称分配与历史唯一性遵守[Delivery 与文件名](outputs.md#delivery-与文件名)。客户端按完整实际文件名查询记录，不解析可读名称，也不按 ID 前缀匹配。

| 交付状态 | 已确认事实 |
| --- | --- |
| `pending` | 身份已登记，尚未开始准备 |
| `preparing` | 正在读取、校验或保存准备完成事实；恢复仍处于本阶段 |
| `prepared` | 独立副本及准备事实已可靠保存，可能仍在等待组内其他来源 |
| `publishing` | 已进入发布处理，尚未可靠保存发布完成事实 |
| `published` | 已可靠保存本地发布事实；主程序随后移动或删除文件不改变这项历史事实 |
| `failed` | 本次交付最终失败，必须提供错误 |
| `canceled` | 尚未可靠发布的本次交付被取消，适用中间文件清理单独表达 |
| `withdrawn` | 已发布交付的可撤回文件已确认撤回；原取回动作终态保持 |

正常路径为 `pending → preparing → prepared → publishing → published`。未发布阶段按取消或最终失败结束；已发布后只有可靠撤回才能转为 `withdrawn`。发布结果尚在核实时保持 `publishing`，不能猜测为未发布再发一份，也不能猜测成功。中断恢复按[普通交付恢复规则](file-handoff.md#普通交付的保存顺序与中断恢复)确认三个位置均无副本、没有可靠完成事实且结果无法确认时，交付结束为 `failed`，错误明确保留本地交接结果未知的原因，不自动重投。已终结交付不因新的取回请求复活。

`prepared`、`publishing`、`published`、`withdrawn` 必须有完整 `size` 与最终 `sha256`。此前已知完整源长度时可以提供 `size`，已可靠取得完整目标摘要时才可提供 `sha256`；失败或取消不抹去此前已确认的大小和摘要。不能用 `committed_bytes` 代填尚未知的完整长度。

### 公共拷贝字段

交付 `copy` 与录像的内部 `source_copy` 使用相同结构。必填项由 Schema 给出，含义及组合如下：

| 字段 | 含义与不变量 |
| --- | --- |
| `max_read_attempts`、`read_idle_timeout_s`、`max_recopies` | 本文件在报告历史边界内最后可靠保存的相关执行依据；尚未结束的处理后续采用新配置时可以变化，历史报告仍使用原记录 |
| `recopies_used`、`round` | 已启动额外重拷数与当前轮次；后者等于前者加 1，降低上限不裁剪已有次数 |
| `committed_bytes` | 当前轮次已可靠落盘并保存的字节数；重拷开始时按新轮次归零，续传不归零 |
| `source_size` | 已可靠确认的完整源长度，已知时提供；进度不能超过它 |
| `read_attempts` | 整个文件跨轮次累计的读取尝试，编号连续；成功分段、续传、重拷、重启均不清零，降低上限后已有次数可以超过新上限 |
| `verification` | 当前完整副本的校验进度或结论；摘要获取失败与摘要不一致分别表达 |
| `work_file_cleanup` | 此次中间文件的清理进度或结果，与正式源产物的清理独立 |

`verification` 的 `not_performed`、`running` 分别表示未进行与进行中；`matched`、`mismatched` 表示实际比较结果；`source_checksum_unavailable` 只用于驱动明确不提供源摘要、且已按既定可靠读取契约完成主机文件校验的降级路径。摘要命令失败或结果未知不能冒充该能力分支，使用 `failed` 并提供错误。

准备完成的副本须已满足[文件一致性与校验](file-copy.md#读取正确性与文件校验)：当前校验为 `matched` 或上述允许的降级结果，`committed_bytes` 等于完整文件长度，存在最终目标摘要。媒体错误不等于拷贝字节不一致；源摘要已知时必须与完整交付摘要一致。

`work_file_cleanup` 的 `not_needed` 表示当前没有中间文件清理责任；待处理、执行中、完成、明确失败和结果未知分别保存。失败或未知必须有错误。取回的失败、取消与文件清理遵守[取回中间文件的保留与清理](obtaining-outputs.md#取回中间文件的保留与清理)，不能因为动作终态就省略未完成清理事实，也不能误删其他请求的文件。

取消后的完整交付副本与半成品共用 `work_file_cleanup`，不另建一套完整副本清理结果。副本清理失败不恢复取回，清理后来完成也不把取回的 `canceled` 改为成功。发起取消的动作按其本次适用处理结果报告，不能将清理失败与会话允许正常结束混为一谈。

## 计划文件诊断

每项必填 `diagnostic_id`、`file_name`、非空 `errors` 数组。文件名表达本次交给 CLI 的输入计划文件；即使读取或解析失败也保留。只有完整无歧义解析后取得合法请求 ID，才能附 `request_id`；不能从坏 JSON 片段猜测身份。

`errors[].stage` 按输入读取、解析、整份受理校验或 ACK 校验分类。诊断整体不可变，每次新的失败输入处理有独立身份；同一输入的多个问题属于同一诊断。已支持动作的自身参数错误保存在动作中，不把它们重复包装成整份计划拒绝。完整语义见[计划文件诊断](report-diagnostics.md#计划文件诊断)。

## 语义校验与验收

客户端导入依次检查：原文件名与字节摘要、无歧义 JSON 解析、Schema、当前文件可判定的语义、与本地已有状态的身份及覆盖关系。全部通过并可靠保存后才推进本地可确认范围；失败保留导入诊断，不提交部分计划更新或 ACK。

Schema 无法独立证明的检查分为以下边界：

| 边界 | 必须检查 | 不能据此拒绝的正常情况 |
| --- | --- | --- |
| 单份文件 | 文件名 ID 与根一致，水位顺序合法，真实日期有效，无重复实体 ID | 报告只有诊断或只承载部分计划 |
| 单个实体 | 状态与已知结果一致；尝试次数、轮次、进度和校验结果满足本专题 | 初始失败保留非法原输入；失败或取消保留已经发生的副作用 |
| 已在同份报告或本地记录中出现的关联 | output 属于声明的来源动作；delivery 的产物与来源动作一致；派生关系及文件名一致 | 来源暂未出现在客户端已有数据中，此时保留待关联引用 |
| 已保存历史 | 身份及所属关系不可变，终态不可变，文件名不复用，旧报告不覆盖新事实 | 终态后的产物清理、媒体问题、残留设备收场和交付撤回继续更新 |
| 覆盖与 ACK | 按完整区间判断已保存的累计覆盖和合格报告 | `result.report_id` 早于当前报告；当前计划下仅有变化的动作子集；局部同步报告可以包含比指定起点更早的变化 |

实体结果校验使用完整自身快照；依赖未出现子集合或缺失历史的判断不能假装已取得完整证据。CLI 从完整冻结历史生成报告时必须满足所有成立条件；客户端只在证据可用时检查对应关系，等待来源资料不等于报告损坏。

预览、范围选择和取消停止等待的事实均遵守历史、投影及冻结报告规则；恢复和历史回放不得依赖当前能力重新推导旧选择。增量报告暂缺关联实体时保留引用并等待关联，不凭名称或媒体扩展名推测。Schema 仅验证局部结构，集合完整性、大小比较、同源关系及失败汇总由语义校验完成。共享实例见[协议样例](../../protocol/examples/workflows/README.md)。

验证至少包括：既有成功及部分失败样例；取消仍在有限处理、取消完成及停止耗尽；删除逐项成功、失败和恢复确认；显式报告引用较早报告；未执行媒体检查；无源摘要的允许降级；初始失败保留 `null`、错误类型和额外输入键。反例覆盖错误状态值、缺少必填字段、伪造生效参数、缺少最终交付摘要、无产物却捏造关联、重复 ID、进度越界、错误水位及哈希不匹配。

Schema 与协议样例的文件检查属于规格校验。实际实现时仍须组合真实 SQLite、报告生成和客户端导入进行集成验证，证明冻结历史、字节重建、事务合并和累计确认可以共同工作；相机替身通过不等于真实设备已经完成联调。
