# 单张拍摄与延时摄影

[设计总览](README.md) · [设备能力](camera-capabilities.md) · [报告结构](report-format.md)

## 输入与设备能力

第一版支持 `camera_take_photo` 和 `camera_timelapse`。两者使用拍摄公共字段：`device_id`、`scheduled_at`、`params.type` 和 `policy.max_delay_ms` 必填，可属于动作组。设备、动作、参数类型共同确定参数规则，所有参数按驱动 Schema 校验，受理时固化生效参数。设备不支持某能力时不能将请求改成其他动作。

单张拍摄执行一次拍摄，不要求一次拍摄只产生一个文件，例如设备可以提供多个图片格式。延时摄影执行设备参数契约定义的有限采集任务；采集间隔、持续时间、适用的次数要求和输出组合均受该契约约束，固定类型可以固定相应设置。持续时间指采集过程，不是输出视频的播放时长。任务的结束方式由驱动契约明确，遵守下文的计时与停止分工。

驱动定义可调范围、固定设置及组合限制，`camctl describe` 根据本地驱动定义和设备配置导出能力说明，不连接相机探测能力。客户端据此展示、校验并生成计划；camctl 首次受理使用同源规则再次校验。能力只开放具有明确执行契约的任务，不能将尚未核实的设置组合或结束方式声明为已支持，也不能静默修改用户要求以适配设备。具体机制见[能力导出](camera-capabilities.md#拍摄能力与参数类型)。

驱动声明有限任务的执行方式、支持的查询和停止能力、完成判定、文件归属和写入完成规则，以及设备操作兼容性。完成判定可以依赖实际状态证据，也可以采用下文明确的运行假设、等待规则与产物核实契约。框架只对受支持且适用的操作管理有限预算，不要求设备具有拍摄状态查询接口。部署说明列出实际可执行的参数类型及其保证范围；真实命令映射由设备接入验证，协议样例不能证明设备已经接入。

首次受理保存完整生效参数，并从生效参数及驱动任务定义取得动作处理模块确实需要的固定执行依据，作为只读动作执行定义保存；后续执行和恢复沿用首次确定的要求。单张拍摄由动作类型表达执行一次拍摄，其执行定义为空对象，不另设目标文件数量。具体存储分工见[各类动作的执行定义分工](../camctl/database/execution-definitions.md#各类动作的执行定义分工)。

## 延时摄影处理模块与驱动的职责

例如，设备支持每隔指定时间采集一次、持续指定时长并保存特定格式的文件。驱动负责定义这组参数的合法性、执行设备操作和解释设备证据；延时摄影处理模块负责推进业务任务、组织持久化、管理尝试与取消，并根据证据决定动作结果。处理模块通过既有调度、设备协调、持久化和产物模块完成公共工作。

| 阶段 | 处理模块的责任 | 驱动的责任 |
| --- | --- | --- |
| 首次受理 | 配合受理流程保存生效参数、必要执行定义、动作与历史 | 提供参数规则、默认值和任务定义，不访问设备 |
| 准备执行 | 取得执行资格，核对取消及设备占用，组织操作意图保存 | 按保存的参数配置设备，返回实际结果及已知效果 |
| 启动采集 | 先保存启动尝试，再调用驱动并保存响应事实；按声明区分命令发送成功与设备启动确认 | 执行启动操作，解释返回含义，提供实际取得的任务关联和证据 |
| 观察进度 | 按声明的方式异步等待，保存必要进度，响应取消与会话异常 | 提供受支持的设备状态或产物观察，不支持状态查询时使用声明的结果取得方式 |
| 停止采集 | 按任务契约、停止能力和取消规则组织适用操作，管理有限尝试及后续处理 | 执行受支持的停止操作，按返回契约区分命令发送、确认停止、明确失败和结果未知 |
| 整理结果 | 结合采集及文件事实确定动作结果，组织产物和终态原子保存 | 识别本次文件，提供归属、写入完成及实际可取得的媒体信息 |
| 重启恢复 | 读取原任务和尝试，组织核实，继续未完成责任 | 根据原关联核实设备任务和文件，返回可靠事实，不自行重新启动任务 |

驱动封装设备协议和命令细节，不直接写业务数据库、分配动作最终错误码、修改动作状态或生成报告。需要保存意图、累计尝试或支持重启恢复的操作阶段对处理模块可见；业务重试和恢复决策由处理模块管理。调用返回能够证明哪些事实由驱动契约决定；结束协程等待本身不证明设备已停止。

### 采集间隔与结束控制

设备提供原生延时摄影任务时，驱动将受支持的间隔、持续时间和输出设置交给设备，设备负责周期采集；处理模块不为每次采集创建独立动作，也不据此周期性发送单张拍摄命令。采集次数与产物文件数分别表达；持续时间除以间隔只能形成估算，不能作为设备实际采集次数或任务完成证据。

计时与停止责任按对应参数类型的明确执行契约分配：

| 设备任务契约 | 计时与停止责任 |
| --- | --- |
| 设备接受有限目标并自行结束 | 驱动配置任务；处理模块观察并核实完成，取消和异常收场仍由处理模块组织 |
| 设备契约要求主机到时发出停止命令 | 处理模块负责业务计时和停止决定，驱动执行停止操作并解释结果；驱动内部不隐藏整段任务的等待和停止决策 |
| 设置、结束方式或完成依据尚不明确 | 不形成可用任务契约，不导出为已支持能力 |

主机控制结束的方式只在实际接入需要且其行为得到验证时实现。相应契约必须明确计时依据、停止方式、完成判定及中断恢复，不能只提供停止命令而省略这些含义。设备自动结束与主机控制结束分别遵守各自的证据要求，不仅凭主机等待时长判断采集成功。

首次受理将正常结束责任保存为只读执行定义中的 [end_control](../camctl/database/execution-definitions.md#延时摄影执行定义的结束控制)。结束责任与命令返回时机、提前停止能力分别表达；设备自行结束不表示命令一定提前返回，也不表示任务不支持取消。

### 命令返回含义与等待起点

驱动按设备及任务类型声明命令返回的含义。命令发送完成、设备确认启动和采集任务执行完成是不同事实；框架根据声明及实际结果选择下一阶段，不仅凭调用返回或退出码统一解释。延时摄影在首次受理的只读执行定义中使用 [start_return_meaning](../camctl/database/execution-definitions.md#延时摄影执行定义的启动返回含义) 保存成功响应的含义，实际调用结果另行记录。已有取消和终态继续优先适用各自规则。

| 驱动声明及本次结果 | 处理模块的处理 |
| --- | --- |
| 成功返回只表示命令发送成功，任务在设备上继续执行 | 保存发送成功；采用返回后等待的任务，从驱动取得该成功结果的时点计时 |
| 成功响应确认设备启动，并提供任务契约规定的计时依据 | 保存实际启动事实，按声明的依据安排等待或控制 |
| 调用持续到任务执行结束，成功返回按契约证明采集已完成 | 保存任务完成事实，进入尚需进行的产物核实，不再等待一遍完整目标时长 |
| 调用返回错误、超时或中断，且没有足以确认相应结果的证据 | 保存实际错误及已知效果，进入对应异常或恢复路径，不创建成功等待锚点或完成事实 |

对于成功返回只表示发送成功、并采用返回后等待的任务，驱动取得成功结果时立即记录本次运行的单调钟时点，并随结果交给处理模块。普通结果保存、日志或其他调度等待不改变该锚点；这些步骤结束后只等待尚未经过的部分。处理模块按目标采集时长和声明的结束余量安排结果核实。锚点表示发送成功时点，不表示设备内部精确开拍时点；发送与实际开拍之间的延迟及最终文件处理由任务等待契约覆盖。

设备原生调用在任务执行完成后才返回时，处理模块异步等待该调用，事件循环继续处理其他工作。驱动等待的是设备原生操作结果，不自行增加隐藏的业务计时、停止或重试流程。调用期限必须符合该任务的返回语义，不直接套用只覆盖短控制命令的等待上限；取消等待、终止本地通信进程和设备停止仍分别判断。

采集完成响应不自动证明文件已经写完。驱动分别声明返回是否包含文件完成保证；框架对尚未确认的归属、集合及写入完成继续核实，已经可靠取得的事实不重复等待。失败响应若同时携带可靠的完成证据，保留两者并按既有事实优先规则处理。

### 驱动必要余量与部署额外等待

采用发送成功后等待的任务，将设备契约要求的必要余量与部署配置的额外等待分别管理。例如，驱动规定目标时长结束后还需等待 5 秒，部署另外增加 3 秒，则在发送成功的计时锚点之后等待目标时长加 8 秒，再开始结果核实。示例数值不构成任何设备的默认保证。

| 信息 | 来源与生效规则 | 保存位置 |
| --- | --- | --- |
| 驱动必要余量 | 驱动按参数类型及生效参数给出具体的非负时长，首次受理确定后保持不变；适用该等待方式但无需余量时明确为 0 | 保存到只读执行定义的 [result_wait_margin_ms](../camctl/database/execution-definitions.md#延时摄影执行定义的结果等待余量)；不适用该等待方式时省略字段 |
| 部署额外等待 | 本地设备配置 [capture.extra_wait_ms](configuration.md#拍摄结果核实的额外等待) 提供非负整数毫秒，默认 0；本次 `run` 内固定，不能用负值抵消驱动要求 | 实际采用的值随对应执行事实保存，不复制为首次受理的固定配置 |

本次运行的首次结果核实时点按下式安排，各项须换算到一致单位：

```text
结果核实时点 = 发送成功的单调钟锚点
             + 目标采集时长
             + 驱动必要余量
             + 部署额外等待
```

驱动必要余量可以覆盖任务启动准备及最终文件处理，其值由明确的任务契约决定。部署只能额外增加等待；缩短设备契约要求须修改驱动定义，不能通过本地配置抵消。客户端计划不提供部署额外等待字段，也不能覆盖驱动固定要求。余量只安排结果核实，不改变下发给设备的目标采集时长，不推迟主机控制结束方式的正常停止目标，也不是动作成功的独立依据。

后续运行调整本地配置时，已经可靠保存的等待完成事实、处理决定和动作终态保持原值。尚未完成的等待先根据原任务的恢复契约确定可用时间依据，再采用本次配置继续处理；不能将配置变化解释为重新开始整个任务，也不能跨运行比较单调钟读数。历史报告与回放使用当时保存的依据，不读取新的配置修改旧事实。

任务执行完成后才返回的调用不套用上述整段等待公式。返回已经保证文件写完时，继续核实尚需取得的归属及集合事实；仍需等待文件处理时，按驱动另行声明的规则执行，不再等待完整采集时长。

### 设备自行结束时的等待与完成核实

本节适用于目标采集持续时间已经确定、命令发送或启动确认后设备继续执行并自行结束的延时摄影任务。例如，设备接受每隔 25 秒采集一次、持续 100 分钟的任务。camctl 根据[命令返回含义与等待起点](#命令返回含义与等待起点)保存对应事实，再按声明的计时依据、目标时长及适用等待规则，在本次运行中使用单调钟安排首次结果核实。调用成功返回已经证明采集完成的任务直接进入尚需进行的产物核实，不进入本节的整段采集等待。

预计结束前，处理模块异步等待，不按采集间隔周期查询设备，也不提前读取仍在形成的文件。主事件循环继续处理其他动作、报告及取消。这种安排不承诺采集期间持续更新进度或即时发现设备故障；缺少相应证据时，某些采集异常可能无法识别，保证范围由任务契约说明。

首次结果核实按驱动声明分支。支持并采用拍摄状态查询的任务先核实状态，再核实产物；采用时间与产物判定的任务在满足等待规则后直接核实产物，不创建拍摄状态查询流程或占用其预算。不支持状态查询是能力事实，不是查询失败，也不触发状态查询重试。

状态查询沿[活动核实责任](../camctl/database/operation-fields.md#活动查询的责任范围)累计，重启对账与预计结束后的状态检查共用原次数，不重开启动核实。文件核实另按[产物结果核实的轮次](../camctl/database/operation-fields.md#产物结果核实的责任与轮次)计数，多文件及分页不拆成多个尝试。

采用状态查询的任务按下表处理。已有终态和已经生效的取消优先；需要状态库的步骤仍以可靠读写为前提，设备观察必须能够关联原任务。

| 阶段或已取得的事实 | 处理 |
| --- | --- |
| 启动已确认，尚未到预计结束时间，没有取消或其他中断 | 继续异步等待，不将等待时长作为采集完成证据 |
| 到达预计结束时间，任务仍有普通执行资格 | 查询原设备任务，开始有限的完成核实 |
| 查询确认原任务已经完成 | 转入本次文件的归属和写入完成核实 |
| 查询成功，确认原任务仍在执行 | 保存实际观察，在剩余核实预算内按查询间隔再次查询；第一次尚未完成不直接判为失败，也不记为通信错误 |
| 查询确认原任务明确失败或提前终止 | 按失败、有限收场及文件保留规则处理，不因已经经过目标时长而判成功 |
| 查询调用失败、超时，或无法确认原任务状态 | 保存调用结果和未知事实，按有限核实规则处理，不解释为已完成或不存在 |
| 有限核实结束后仍不能确认任务完成 | 按所属失败与有限收场规则结束处理，保留实际设备状态或未知事实，不无限查询，也不宣称设备已停止 |
| 等待或核实期间取消生效 | 及时结束普通等待或停止新增普通查询，进入取消和适用停止流程；已经开始的调用继续跟踪实际结果，不等满原任务时长 |
| 主机重启，原任务尚未结束 | 取得恢复资格后先核实原任务，不重新等待完整目标时长；沿用原身份和累计尝试 |

重启后按驱动声明的恢复方式核实原任务，不统一要求拍摄状态查询。采用状态查询的任务确认设备已经完成时，直接继续文件核实；设备仍在执行且能够提供可靠剩余时间或进度时，按任务契约安排后续检查。没有状态查询接口的任务使用其声明的时间、文件及其他可取得依据恢复；原运行的等待是否已经完成与设备是否实际完成分别判断，不重新启动采集或凭文件存在宣称成功。不同运行的单调钟读数不得直接相减，断电期间的墙钟差不作为可靠采集时长。

完成查询与文件核实分别判断。设备完成采集后，文件归属或写入完成仍未确认时，动作保持 `running`；全部适用处理结束后，再将正式产物和动作结果在同一事务中保存。该步骤取得任务结果与必要文件事实，不因采集完成而自动创建取回或交付责任；文件内容取回继续由取回动作负责。

查询间隔、单次调用时限和适用的核实预算属于执行控制，目标采集时长属于首次确定的拍摄要求，二者分别管理。单次调用超时不限制整项采集持续时间；设备仍在执行也不等同于通信失败。设备自行结束时，`target_duration_ms` 用于按声明方式安排结果核实；由主机计时结束时，该字段用于安排停止操作。结果按任务声明的完成规则判断，字段存储见[延时摄影执行定义的目标时长](../camctl/database/execution-definitions.md#延时摄影执行定义的目标时长)。

### 无状态查询任务的重启等待恢复

对于发送成功后由设备独立执行、按有限时长自行结束的任务，部署环境须保证主机重启前后的日期时间足够可靠，可以用于恢复预计检查时间。设备继续执行原任务的行为由驱动契约声明。启动墙钟检查仍须通过，但检查通过本身不证明跨重启的日期时间差准确，也不证明设备持续采集；这两项运行前提分别适用。

驱动取得发送成功结果时，除本次运行的单调钟锚点外，还取得对应的 UTC 日期时间。处理模块随发送成功事实保存该时间，并保存此次安排使用的部署额外等待和预计检查时间。预计检查时间按发送成功日期时间加目标采集时长、驱动必要余量和部署额外等待计算。数据库保存和日志处理不推迟原发送时点；这些运行事实不写入首次受理后只读的执行定义。

重启后，处理模块沿用原任务身份、文件归属基准、执行事实和累计尝试次数。尚未完成的等待以原发送成功日期时间为起点，按[配置变化规则](#驱动必要余量与部署额外等待)采用本次运行的部署额外等待；配置未变时，预计检查时间不变。配置变化时保存新的等待安排及依据，不覆盖历史安排，也不以重启时间作为新的发送时点。已经可靠保存的等待完成事实保持有效，不因新配置重新等待。

以下分类以尚未终态、没有生效取消或明确设备失败证据为前提；相关事实优先适用各自规则。处理模块依次判断：

| 恢复时的条件 | 处理 |
| --- | --- |
| 状态库无法可靠读写或提交结果未知 | 按状态库错误及提交核实规则处理，不依据不完整记录继续普通执行 |
| 启动墙钟检查未通过 | 按时钟异常规则处理，不用该时间判断普通等待已经结束 |
| 已保存等待完成事实，或已取得原任务可靠的完成凭据 | 继续尚未完成的文件核实，不重新等待完整采集时长；完成凭据只覆盖驱动明确保证的事实 |
| 发送结果尚未确认，或尚未取得恢复所需的发送日期时间 | 按原操作的结果未知及恢复规则处理，不以重启时间补造发送成功，不无依据地重发拍摄命令 |
| 恢复依据齐备，预计检查时间晚于恢复时的可信日期时间 | 计算剩余时间，将其转换为本次运行的单调钟等待；本次等待不随之后的墙钟读数反复重算 |
| 恢复依据齐备，预计检查时间已经到达或过去 | 开始产物核实，不补等完整目标时长，也不直接登记动作成功 |

例如，10:00 发送成功，目标采集时长为 20 分钟，全部适用余量合计 1 分钟，则预计在 10:21 检查。主机 10:08 中断、10:10 恢复且配置未变时，再等待 11 分钟；10:25 才恢复时直接检查产物。这些时间只安排检查，不填充报告中的实际采集时长或次数。不同运行的单调钟读数不相减；已有明确失败证据也不能被到期时间覆盖。

重启本身不解除原任务对设备及输出范围的占用。处理模块恢复相应执行限制，在满足原任务的结束及文件归属规则前，继续阻止冲突操作；其他设备和兼容操作仍可执行。动作失败与设备实际停止分别记录，失败终态本身不证明设备已停止。驱动提供可关联原任务的持久化完成凭据时，优先使用其可靠事实，不要求所有设备实现此能力。

发送意图已经保存，但既没有可靠发送时间，驱动也不能提供可关联原任务的恢复依据时，camctl 将动作按结果无法确认结束为失败，保留未知设备活动及占用。camctl 不重发可能重复执行的启动命令，也不以重启时间安排一个虚构的完整等待。新的冲突动作在没有适用的安全收场路径时按设备活动未解决失败，其他设备继续；原失败活动不单独延长会话。以后实际取得可靠结束证据时解除占用，原动作终态保持不变。具体字段和状态分类见[设备活动恢复](../camctl/database/operation-fields.md#等待未知结果和占用恢复)。

### 按时间与产物判定完成

延时摄影的只读执行定义使用 [completion_mode](../camctl/database/execution-definitions.md#延时摄影执行定义的完成判定方式) 保存完成判定方式。要求设备完成依据的任务，不能因查询失败或预算耗尽临时改用时间推断；完成依据也可以来自原调用响应或设备完成记录，不统一要求状态查询接口。

第一版允许延时摄影驱动声明基于设备运行假设、等待规则和产物核实的成功判定方式。该方式适用于没有拍摄状态查询接口、但能够按有限任务契约取得产物的设备。驱动须明确声明下表各项，框架不因查询能力缺失而自动采用这些假设。

| 契约内容 | 必须明确的含义 |
| --- | --- |
| 有限执行行为 | 命令发送成功后，设备按本次参数执行有限采集任务并自行结束 |
| 结果等待规则 | 从约定时点等待目标时长及必要的结束余量后，可以检查完整结果；等待使用本次运行的单调钟 |
| 文件归属规则 | 能够识别本次任务产物，区分历史文件，所需关联依据可以保存和恢复 |
| 产物完成规则 | 规定任务要求的产物及文件写完、结果集合确定的判定依据 |

有限执行行为和时间安排可以作为第一版明确接受的运行假设，不要求每次通过设备状态接口证明。处理模块按契约保存命令发送结果、等待完成事实及产物核实结果；满足条件后，与正式产物一起保存动作成功。成功表示约定控制流程及产物要求已经满足，不额外承诺驱动无法核验的逐次采集质量或完整次数。

按以下顺序判断，已有终态、取消和状态库错误优先适用各自规则：

| 已取得的事实 | 结果 |
| --- | --- |
| 已取得明确的设备失败或提前中断证据 | 按失败及文件保留规则处理，等待完成或存在部分文件不能覆盖该证据 |
| 已取得能够关联原任务的可靠完成依据 | 使用该依据，不重复等待已经证明完成的阶段；继续核实尚未被依据覆盖的文件归属、写入完成及集合要求 |
| 命令发送未确认，或声明的等待条件尚未满足 | 不进入成功判定，按发送结果或原等待阶段继续处理 |
| 发送和等待条件均满足，本次产物符合声明的全部要求 | 登记符合条件的正式产物和成功终态，无须补充拍摄状态查询 |
| 发送和等待条件均满足，但未取得要求的产物，或归属、写入完成、集合完整性尚未确认 | 继续适用的有限核实；结束后仍不满足时，保存失败及具体未确认事实，按既有规则保留已确认文件 |

采集次数要求由驱动契约明确。目标时长除以采集间隔不自动形成必需文件数，也不代替实测采集次数；一次采集与文件数量的对应关系须由设备契约解释。设备提前结束却留下满足较宽松产物要求的文件时，框架可能无法识别采集不足；该限制属于此判定方式的保证范围。实际次数或实际采集时长没有可靠证据时保持未知。

### 本次任务的文件归属

驱动声明本次文件的识别方式，框架保存关联结果和所需依据，不统一规定目录识别算法。设备支持指定任务目录或文件前缀时，可以在启动意图中保存指定位置；设备能返回任务与文件关联时，使用相应结果；依赖拍摄前后比较时，使用启动前可靠保存的目录或编号基准。各方式均以设备明确支持的行为为前提。

拍摄前后比较按以下顺序执行：取得拍摄资格及所需输出范围独占后，读取实际基准；可靠保存基准，再发送拍摄命令；按任务契约等待或取得完成结果后，读取目录并根据基准识别新增文件。基准在执行时取得，不在计划受理时提前读取。需要该基准的任务在基准保存失败时不能启动，重启沿用原基准，不重新取基准掩盖已经产生的文件。

启动前基准准备按下表处理。目录读取和状态库保存分别承担自己的责任；只有可靠固定的基准可以进入启动资格检查。

| 基准准备结果 | 处理 |
| --- | --- |
| 完整目录读取成功，包括实际空目录，基准固定可靠成功 | 使用原基准继续检查启动资格；仍须满足取消、窗口及占用条件 |
| 目录读取明确失败，包括中间批次读取失败 | 本次拍摄动作直接失败，保留实际读取错误，不自动重试基准读取；启动尝试次数保持为 0 |
| 基准追加或固定的状态库保存失败，或提交情况未知 | 按状态库错误和原事务核实规则处理，不解释为目录读取失败、空目录或基准已经固定；不启动 |
| 准备被会话退出或执行中断打断，尚未取得完整读取结果 | 保留尚未完成的准备责任；只有可靠未派发且基准仍在收集时，恢复才可按分批历史规则重新读取 |

目录读取失败后的占用释放依据是可靠未派发及已解除的准备责任，不记录相机已经停止的虚构观察。用户取消与已有终态继续按各自规则优先处理。录像和延时摄影使用同一基准准备失败规则。

基准读取明确失败时，动作保存 `capture_failed`，其 `details` 为原 `activity_id` 和 `reason=baseline_read_failed`，阶段为 `execution`。完整读取错误保存在原活动的 `last_error_json`。实际目录调用已经完成收场后，原错误、动作失败及适用的占用释放在同一事务保存；活动仍为 `UNKNOWN`，启动次数为 0。保存回执未知时继续核实原完整申请，不重新读取目录或更换错误。

用户取消或已有动作终态优先时，保留该终态。目录调用随后返回的实际错误仍保存到原活动，实际准备收场与适用的占用释放共同保存。基准准备结束后窗口过期时，过期决定也须持有原完整申请、key 和时刻，直到取得可靠回执；终态动作不会因此跳过原保存责任。

| 归属方式及条件 | 处理与约束 |
| --- | --- |
| 设备支持任务专用目录、名称或明确的任务文件关联 | 使用该能力及其关联依据，不额外强制目录前后比较 |
| 依赖前后比较，输出范围没有其他文件生产者，且文件身份规则明确 | 从读取基准到本次归属和集合确定期间，保持相应输出范围独占；已完成文件的兼容读取仍按既有规则进行 |
| 只比较文件路径 | 驱动契约须保证相关过程中不覆盖旧文件或复用同一路径 |
| 设备提供可靠递增编号及目录切换规则 | 可以保存能够完整区分新旧文件的较小编号基准，不仅凭文件名末尾数字推断顺序 |
| 缺少紧凑基准所需保证，但能够保存完整目录基准 | 分批读取和保存必要清单，不要求将全部历史文件登记为设备文件记录 |
| 无法区分本次文件与历史文件，或其他任务可能混入而没有区分依据 | 保留归属未确认，不能将所有新增或时间较新的文件直接登记为本次产物 |

前后比较的输出范围独占覆盖其他会在该范围内生成文件的任务；设备按键或外部程序是否可能生成文件，由驱动及部署运行假设明确。文件修改时间只有在设备时钟和时间字段语义满足相应契约时才可作为依据，不作为框架默认算法。

识别方式属于任务契约，实际目录基准属于执行记录，不写入首次受理后只读的执行定义。实际识别出的文件由 `device_files` 保存身份、归属和必要事实。归属确认不自动证明文件写完或集合完整；后两项按任务声明的产物完成规则判断，普通取回仍等待正式产物登记。

验证基准保存失败后不启动、基准与启动之间中断、启动后未保存文件关联时恢复、其他任务被输出范围独占阻止，以及兼容读取继续进行。覆盖旧文件、新目录、编号边界及关联未知；使用紧凑基准的测试替身须符合真实编号契约。验证原基准跨重启保持、归属未确认时不登记产物，以及归属确认不代替文件完成判定。

### 文件完成依据与产物检查

延时摄影设备可以只生成视频，也可以先持续生成照片，再把照片合成为视频。后一种情况下，最后一张照片已经生成，仍不代表最终视频已经写完。处理模块分别判断文件归属、单个文件是否写完，以及本次任务要求的产物集合是否齐备；其中任何一项都不能由另一项自动推导。

驱动为所接入的任务声明文件和集合完成依据。成功响应明确保证全部产物写完时，使用该保证；采用时间与产物判定时，使用驱动明确声明的运行假设和等待规则。后一种方式的等待须覆盖约定的启动延迟、采集过程及结束处理，包括任务需要的视频合成。处理模块保存实际采用的依据；按等待假设判定完成，不记录为设备直接报告了文件写完。仅发现文件、发现视频或短时间内文件大小不变，不构成框架通用的完成依据。

产物检查执行本次参数类型声明的必要文件规则。驱动说明哪些文件属于照片、最终视频或其他产物，以及各类产物的必需性、数量和适用检查条件。只要求视频的任务不检查照片是否存在；要求照片和视频的任务须同时满足两类要求。设备生成分段视频或多种格式时，按相应声明检查，不统一要求一个视频，也不按目标时长除以采集间隔推算必需照片数。

以下判定以动作尚未终态、没有生效取消、没有明确设备失败证据且状态库可用为前提；这些前提不成立时，先适用各自规则。处理模块按表中顺序判断，表中的有限核实均沿用所属任务的预算：

| 条件 | 处理 |
| --- | --- |
| 声明的完成响应尚未取得，或声明的等待条件尚未满足 | 继续相应等待或有限核实，不因已有文件而宣布成功 |
| 完成依据已具备，但读取目录或必要文件信息发生错误 | 保存读取错误及尚未取得的信息，按适用预算处理；不解释为目录为空或产物缺失 |
| 已取得必要文件信息，但归属、单个文件写完或集合完成依据仍不充分 | 保持相应事实未确认，继续有限核实；预算耗尽后按失败及文件保留规则结束 |
| 归属及完成依据充分，但产物缺少必需类别、数量不符合声明或其他必要文件检查不通过 | 保存具体未满足的规则；有限核实结束后仍不满足时，动作失败并保留符合条件的文件 |
| 归属及完成依据充分，全部必要文件规则通过 | 与正式产物登记一起保存动作成功 |

例如，某参数类型要求一组 JPEG 照片和一个最终视频。在约定的完成条件满足后，如果两类文件均已写完且满足声明的检查规则，处理模块登记产物并结束动作。如果只能找到照片，处理模块记录缺少最终视频；有限核实后仍缺少视频时，动作失败，但符合保留条件的照片仍可登记。如果只能找到视频而缺少必需照片，也按相同原则处理。如果成功读取目录后没有找到本次任务的任何文件，则记录缺少产物；如果目录读取失败，则记录读取错误，不能声称没有生成文件。

第一版不默认逐张解码照片、逐帧检查视频、验证实际采集间隔或证明没有漏拍。任务声明要求的检查仍须执行，声明以外的全面媒体质量验证不属于动作成功条件。因此，未被必要检查发现的内容损坏或采集不足可能与动作成功同时存在；成功只承诺约定控制流程及产物要求已经满足。实际采集次数和时长继续只报告可靠取得的值。`camera_record` 的原片检查与修复遵守[录像核实](camera-verification.md)的独立契约。

### 产物检查的错误表达

处理模块先保存实际核实事实，再按下表构造结果检查错误。已有设备失败、提前中断、取消和终态仍优先遵守各自规则；下表只分类产物核实，不改写原驱动调用错误。

| 产物核实取得的事实 | 有限核实结束后的错误 |
| --- | --- |
| 归属及写入完成、集合确定的依据充分，本次任务文件集合为空，未取得任务要求的产物 | `capture_failed`，`details.reason` 为 `no_outputs` |
| 归属及完成依据充分，集合非空，但缺少必需产物类别或数量不符合任务要求 | `capture_failed`，`details.reason` 为 `invalid_outputs` |
| 归属及完成依据充分，集合非空，任务声明的其他必要文件检查明确不通过 | `capture_failed`，`details.reason` 为 `invalid_outputs` |
| 文件信息读取失败，或归属、写入完成、集合确定的依据仍不充分 | `capture_result_unconfirmed`，`details.reason` 为 `outputs_unknown`；不能据此断言产物不存在或不合格 |

上述错误的 `stage` 从[公共错误登记](../../protocol/errors/workflow-codes.json)读取，`details.activity_id` 指向实际采集活动，不使用动作 ID 代替。具体未满足规则、实际读取错误和未知事实保存在内部；对外详情遵守已登记结构，不添加未登记字段。符合文件保留规则的文件继续保留；正式产物登记和动作终态仍整体保存。

### 设备事实与动作结果

驱动解释设备响应是否证明原任务启动、仍在采集、完成或停止；处理模块结合已经保存的取消、执行阶段及文件事实，决定动作状态。设备空闲只有在驱动契约能够证明其含义时，才可作为原任务完成的证据。以下分类以相关记录可靠可读写为前提，已有终态保持不变：

| 动作及设备事实 | 处理模块的处理 |
| --- | --- |
| 动作未取消，采集仍在进行 | 保存可靠进度，按原契约继续管理 |
| 动作未取消，采集已完成，文件核实尚未结束 | 保持 `running`，继续核实文件归属及写入完成 |
| 动作未取消，目标完成且全部适用处理结束 | 同一事务登记正式产物及成功终态 |
| 取消已生效，后来收到采集完成证据 | 保留实际完成事实，继续取消所需处理，不用迟到结果覆盖取消 |
| 所采用的任务契约要求的发送、启动、停止、完成或文件依据无法取得 | 按适用的有限预算核实；不支持的状态查询不属于缺失证据，不创建对应重试 |

恢复先读取已有任务身份、尝试和设备活动，再通过驱动核实实际状态。已完成任务继续核实文件；仍在执行的任务按原结束契约管理；未知状态按有限核实规则处理。恢复不重新计算驱动默认值、不从零开始采集，也不把断电期间的墙钟时间作为可靠采集时长。

## 正常执行与恢复

启动窗口与调度、效果登记和重试遵守[公共执行规则](scheduling-execution.md)。先保存操作意图，再访问设备；同一动作的重试和重启沿用原身份、生效拍摄参数与累计尝试次数，不重新执行一次已确认的拍摄。后续操作采用本次运行的本地配置，遵守[配置变化与未完成工作](configuration.md#本地配置变化与未完成工作)。驱动只有在能够保证安全重复或设备端去重时才可重发结果未知的拍摄命令。

| 已知情况 | 行为 |
| --- | --- |
| 尚未到时间或设备不具备执行资格，仍在窗口内 | `pending`，报告实际等待条件 |
| 启动窗口错过或启动重试耗尽窗口 | 按公共规则 `expired`，区分未尝试与已有尝试 |
| 已开始拍摄，完成条件尚未满足 | `running`，保存可靠进度 |
| 已确认采集目标完成，文件归属及写入完成核实仍在进行 | 仍为 `running`，不提前声明成功 |
| 目标完成且所有适用有限处理结束，产物集合已确定 | 登记文件及 `succeeded`，在同一历史事务提交 |
| 明确失败，有限收场结束 | 登记符合保留条件的文件并提交 `failed`，附错误 |
| 重启后设备仍在执行原任务，身份与进度可靠 | 按原任务结束契约继续管理，不从零开始计数或计时 |
| 重启后已完成，可可靠关联原任务及文件 | 对账并完成原动作，不再次拍摄 |
| 启动效果、完成条件、归属或写入状态无法确认 | 按原预算有限核实；预算耗尽仍未知时报告失败与未确认事实，不猜测成功或不存在 |
| 数据库无法可靠读写或提交结果未知 | 停止依赖该状态的执行，按会话错误和提交对账恢复 |

成功须满足对应驱动声明的全部完成条件，不能仅凭发现某个文件作出判断。张数进度不等于正式产物数量，一个采集可以生成多份文件，也可以生成合成视频。按时间与产物判定完成时保留实际采用的控制及产物依据，不补造设备状态观察、实际次数或实际采集时长。

## 取消、失败与文件保留

先按[设备任务的取消资格](task-cancellation.md#设备任务的取消资格)判断本次取消能否生效。任务未启动时允许取消；任务已经启动且尚未终态、驱动没有停止能力时拒绝取消，原任务继续等待、核实产物并登记正常结果。启动调用仍在执行或结果未知时，不能按未启动处理。已经生效的取消优先于普通执行和重试。停止只针对能够归属本动作的设备活动，复用已有补偿流程及剩余预算。取消不能越权停止其他动作或归属未知的设备活动。

| 动作状态 | 文件事实 | 结果 |
| --- | --- | --- |
| 确认尚未启动且没有可能生效的启动调用，收到取消 | 无本次文件 | `canceled`，不启动，不创建虚构产物 |
| 已启动或可能启动、尚未终态，驱动没有停止能力 | 任意 | 本次取消项失败，目标取消标记不变，原任务继续执行；不因拒绝取消解除设备及输出范围占用 |
| 已启动或可能启动，驱动支持停止，取消生效 | 任意 | 停止新增普通执行，按声明能力组织适用的有限停止和文件核实；取消事实本身不证明物理采集已停止 |
| 取消或失败的有限处理结束 | 已拍完、确认属于本动作、写入完成 | 登记为正式产物，长期保留并允许按可用性取回；动作仍为 `canceled` 或 `failed` |
| 取消或失败的有限处理结束 | 文件未完成、归属不明或完成情况未知 | 不登记为可用正式产物，保存实际诊断；未知不能解释为不存在，也不授权删除可能属于其他任务的文件 |
| 已终态 | 任意 | 保留既有结果和正式产物，不因后来取消或设备查询改写原结论 |

产物登记与动作终态原子提交；运行阶段报告动作状态，不对外发布部分正式产物集合。每个符合条件的原始文件独立分配 `output_id`，`kind: original`，实际已知时填写 `media_type`。图片没有视频时长，使用媒体时长未知状态，不伪造零秒或已通过视频检查。清理只能通过显式产物清理请求，不能以取消为由删除已保留正式产物。

有限停止结束仍无法确认设备已停止时，保留停止失败及残留活动事实，目标动作仍按取消规则结束；发起取消的动作按所需处理是否成功分别判定。后续会话的新观察保存为独立事实，不能覆盖旧的未确认结果。历史回放不执行设备操作。

录像的取消内容处理继续由[录像取消](camera-recording.md#camera_record-取消)定义。

## 拍摄结果报告

两种动作通过动作 `status`、适用的 `error` 和正式产物表达业务结果，省略 `result`。动作尚在执行时，缺少产物不表示最终没有产物；取消或失败后保留符合登记条件的实际产物。

动作已经结束而设备仍在执行、或尚未确认执行结束时，提供公共字段 `device_execution`，含义和分类遵守[设备执行情况](report-format.md#动作结束后设备是否仍在执行)。后续可靠确认原任务结束时清除提示，原动作终态保持。没有执行停止命令时，不能补造停止成功。

成功必须满足对应任务的完成契约，不固定表示取得设备状态查询响应。采用时间与产物判定时，生成端使用已保存的发送、等待及产物依据判断结果，不补造设备观察。

正式产物仅随已执行的 `succeeded`、`failed`、`canceled` 动作报告；全部产物选择等待来源终态。组取回包含三种拍摄动作，不以是否成功筛选来源。交付仍只嵌套在取回动作下，来源通过 ID 关联，图片和视频遵守相同大小及 SHA-256 核验规则。

## 验收

覆盖仅拍照、仅录像、仅延时和多能力设备；按张数、按持续时间、固定参数及非法参数组合；未启动取消、运行中取消并保留部分图片、停止未知、失败但保留文件、断电后任务仍执行或已结束、启动结果未知禁止不安全重拍、数据库提交未知、同请求重送不重复产物。分别验证执行状态、产物可取回、交付发布和客户端接收，不能相互推导。

按实际启用的参数类型验证能力导出、客户端校验和主机受理使用同源规则；固定值及组合限制不因手工输入而绕过。按职责表验证意图未保存时不发送操作、驱动不自行重试业务任务、发送确认不代替任务完成、取消后迟到的完成结果不覆盖取消，以及设备完成但文件尚未核实时仍为 `running`。计时和恢复验证服从所接入任务的结束契约，不要求第一版为未启用方式额外实现执行分支。软件集成测试使用受接口契约约束的设备替身，真实命令及设备证据另行联调。

按返回语义分别验证发送确认、启动确认和任务完成响应。人为延迟数据库保存或日志处理，确认发送成功锚点保持原时点、后续只等待剩余时间；失败或结果未知不产生成功锚点。对任务完成后返回的原生调用，验证不额外等待完整目标时长、调用期间事件循环可处理其他工作、期限遵守任务契约，以及采集完成但文件尚未写完时继续核实。取消和调用完成竞争时保留实际证据，并维持取消优先。

验证驱动必要余量与部署额外等待分别为零或正值的组合，确认两者相加、不互相覆盖，负值不能抵消等待要求。改变任务参数以验证驱动形成相应必要余量；改变部署配置以验证本次运行内固定、原执行定义不变、已保存等待完成事实不被重开，尚未完成工作仍须先取得恢复计时依据。核对余量不会改变设备目标时长、正常停止时点或直接产生成功结果；完成后返回的调用不进入整段等待。

对采用状态查询的定时任务，用可控时钟验证预计结束前不进行周期完成查询、到时只发起核实而不直接成功、查询发现仍在执行与查询失败分别记录。验证等待期间其他工作继续、取消可以提前进入适用收场、文件尚未写完时仍保持 `running`，以及预算结束后不无限查询。重启组合设备已完成、仍在执行且有可靠剩余时间、仍在执行但时间依据未知，确认不重等完整时长、不重新启动任务、不重置累计尝试。

对采用时间与产物判定的任务，按判定表覆盖发送未确认、等待未完成、产物齐备、无要求产物、归属未知、写入未完成，以及已有明确失败证据。验证不调用未声明的拍摄状态接口、不创建其预算、不将发送成功改写为设备启动观察；成功报告不补造实际次数或采集时长。验证完整任务定义、生效参数、发送、等待和产物依据可恢复；中断后的路径只使用驱动实际支持的能力，不能隐式切换成状态查询。

验证仅生成视频和生成照片加视频两种产物规则，覆盖类别齐备、缺少某类、全部缺失、声明数量不符、归属未知、文件仍在写入和目录读取错误。分别验证明确完成响应与等待假设两种依据；模拟照片生成完但最终视频仍在合成，确认不会提前登记成功。必要文件规则全部通过时，不额外要求声明以外的解码或逐帧检查；失败时仅保留满足归属及完成条件的文件，报告不补造实际采集次数。

重启等待恢复验证预计检查时间之前、恰好到达和之后三种情况，以及已保存等待完成、发送结果未知、时间检查失败和状态库错误。验证日志或数据库延迟不改变发送时点，重复重启不重新等待完整周期，配置变化只调整尚未完成的等待安排，历史依据和已完成事实保持不变。验证恢复后的计时使用本次单调钟、时间到达只触发产物检查、实际采集时长保持未知，以及恢复占用后冲突操作受限而兼容操作继续。设备提供可靠完成凭据时验证按其保证范围继续处理，不等待已被证明完成的阶段。

## 预览文件

参数类型声明支持预览时，按[预览产物契约](preview-obtaining.md#能力与产物身份)登记预览及对应原文件关联，不能将预览混同为另一份原始照片或原始视频。用户取消拍摄时，自动预览按[取消联动](preview-obtaining.md#取消联动)处理；拍摄拒绝取消不单独触发联动，已登记正式产物仍按既有规则保留。
