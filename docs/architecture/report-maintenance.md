# 状态报告的维护与会话收尾

[返回设计总览](README.md) · [阅读路线](reading-guide.md)

本页定义 camctl 何时处理报告、失败后何时再次处理，以及报告工作怎样与设备动作和会话退出协作。报告内容与累计确认见[状态报告](status-reports.md)，文件操作见[发布与补投](report-publication.md)，进程与内部接口见[报告执行设计](../camctl/report-runtime.md)。

## 报告生成点

正常 `run` 使用统一的报告维护机制。报告机会表示该机制需要检查并处理当前责任，不表示每次都生成一个文件。触发与处理规则如下：

| 触发条件 | 报告维护行为 |
| --- | --- |
| 应报告的业务变化已经提交，包括其他进程保存的受理结果和输入诊断 | 主动安排维护；已有处理期间提交的变化可由下一份报告合并覆盖，不等待动作或会话结束 |
| 正常 `run` 恢复／对账 | 接续尚未完成的本地处理，检查未确认内容是否需要补投 |
| 合法 `report_status` 开始执行并保存同步要求 | 按新增的完整或局部同步范围维护报告；成功条件见同步专题 |
| 会话准备收尾 | 检查是否遗漏已提交的业务变化或尚在进行的本地报告工作，按[会话收尾规则](#与会话收尾的协作)完成交接 |
| 仅有有效 ACK、报告内部管理或诊断日志变化 | 不因此生成新的业务报告 |
| 同一次 `run` 中报告被领取或删除，没有新业务变化或新的同步要求 | 不再次补投；下一次正常 `run` 按[补投规则](report-publication.md#本地传输完成后仍未-ack)检查 |

报告维护与设备控制按[报告生成期间的新变化如何合并](status-reports.md#报告生成期间的新变化如何合并)异步执行，不能让文件生成阻塞设备控制，也不能让设备操作阻塞报告维护。报告检查必须观察应报告的业务变化，不能仅依赖只在新计划受理时推进的 `plan_seq`。`submit` 只持久化输入并交接责任，不自行生成或发布报告。

`report_status` 只表达明确的状态同步请求。`params` 必须提供 `scope: "full"`，或提供 `scope: "since"` 和 `after_report_id`；参数组合及实际覆盖范围由[同步入口](status-sync.md#请求入口)定义。`device_id` 须省略，`policy` 可省略或为空对象。非法参数只使该动作初始失败，公共规则见[第一版动作入口](plan-input.md#第一版动作入口)。本地报告处理不保证主程序立即传输或客户端立即收到。

时钟异常的受限 `run` 在有限收场完成后检查并处理一次报告责任，包括按既有条件生成或补投；本次结束后退出，不持续观察新变化，也不启动新的 `report_status` 动作。资格、失败及并发边界见[时钟异常期间的报告](clock-recovery.md#时钟异常期间的报告)。`submit` 仍不自行生成或发布报告。

## 报告处理失败后何时再尝试

报告内容生成或文件写入、同步、发布、目录核对失败时，停止本次失败的报告处理，保留未完成责任及实际已知结果。只要状态库、锁及其他执行条件仍可靠，普通设备动作继续执行，不因报告失败触发录像应急停止。状态库访问或提交失败仍按 `state_db_error` 处理，不纳入本节继续执行的范围。

| 本次失败之后发生的情况 | 处理 |
| --- | --- |
| 出现新的已提交业务变化或新的同步要求 | 重新安排报告处理，覆盖此前尚未确认的内容及本次新增内容 |
| 处理期间已有尚未覆盖的新变化 | 将这些变化交给下一轮处理，不因上一轮失败遗漏它们 |
| 没有新变化，仅调度重扫、收尾检查或时间经过 | 不重开同一轮尝试，不设置独立的定时报告重试 |
| 下一次正常 `run` 启动 | 核实持久化责任及实际文件后，继续未完成处理 |
| 状态库或其他执行前提失效 | 按各自会话错误规则处理，不以报告可延后为由继续不可靠的设备操作 |

每轮处理记录其实际检查和尝试的边界，使失败后新提交的变化与已经尝试过的责任可区分。报告冻结依据保持不变；是否复用原报告或创建新报告仍按覆盖与发布规则判断。日志副本交付按[连续未恢复期间](log-delivery.md#首次失败与重复失败)划分故障轮次：首次失败触发一次，直到报告本地处理可靠恢复成功前，后续尝试失败不再次触发，包括失败阶段或错误类别变化以及跨 `run` 的情况。日志副本成功移入 `ready` 不代表业务状态报告已完成。

上表中按新变化继续安排处理适用于正常执行会话。时钟异常受限会话只有有限收场后的一次报告机会，可在该机会接续此前未完成责任；本次失败或期间出现新变化均不增加本会话的报告轮次，责任留给后续有资格的报告机会。

## 报告生成的继续与停止

报告生成由报告维护流程负责，不归某个等待它完成的同步动作独占。同步动作尚未进入终态时被取消，只结束该动作对应的同步责任；已经开始的报告继续按原冻结范围生成。即使已无其他同步等待者，也不因此停止或缩小这次生成。报告完成不能使已取消动作重新成功，其他普通报告责任及同步责任继续有效。

新报告尚未冻结时，按届时仍有效的责任确定范围。已经冻结的报告继续遵守身份和内容不变的规则；生成期间发生的取消等新业务变化按后续适用报告覆盖，不改写原冻结内容。

下表适用于尚在启动或生成中的报告任务，按顺序判断；停止条件优先于同步取消和正常收尾：

| 执行条件与会话事件 | 处理 |
| --- | --- |
| 状态库、必要的锁或其他报告执行前提失效 | 停止依赖该前提的报告工作，按相应会话错误收场；不等待生成成功后才承认前提失效 |
| 必要前提仍成立，但启动或生成超时、通信故障或生成失败 | 按对应故障规则停止并回收报告子进程，保留尚未完成的报告责任 |
| 没有上述停止条件，某个尚未终态的同步动作被取消 | 按取消规则结束该同步责任，已经开始的报告继续生成，不因等待者减少而撤销任务 |
| 没有上述停止条件，正常会话准备收尾 | 继续本次必要的生成及本地文件交接，再按收尾规则判断能否退出；不等待主程序传输或客户端 ACK |
| 没有上述停止条件，时钟异常受限会话正在处理允许的那一次报告机会 | 在既定时限内完成本次处理，之后按受限会话规则退出，不追加报告轮次 |
| 没有上述停止条件，也没有改变报告责任的事件 | 继续原任务，在既定时限内等待实际结果 |

停止一次报告生成不等于取消业务报告责任。后续有合法报告机会时，依据已保存的报告身份、冻结依据及实际文件事实恢复。状态库失效时，不要求再成功写入一条停止记录才能结束任务；已知错误和未保存的事实按会话诊断规则保留。

主进程通过异步等待跟踪报告子进程的实际退出，设备必要收场独立推进。请求停止、升级终止、迟到结果及报告临时文件清理遵守[报告任务停止与结果先后关系](../camctl/report-runtime.md#报告任务停止与结果先后关系)。取消某个等待协程不能作为子进程已经停止的依据；已经进入 `ready` 或 `processing` 的报告文件继续按交接规则处理。

### 继续与停止的验收

验收分别覆盖仍有其他同步等待者和已无等待者时的同步取消，验证已开始的生成继续、取消动作结果不被报告完成改写。覆盖正常收尾、受限会话一次报告机会、必要前提失效、超时及通信故障；组合生成结果先到和停止决定先到两种顺序，确认报告范围不变、责任不丢失、未完成文件不交付，以及报告停止不阻塞必要设备收场。

## 与会话收尾的协作

状态报告生成和发布属于本地处理责任。正常 `run` 收尾时检查已提交变化是否经过本次应做的处理，再按[请求受理与会话](protocol-session.md)的交接协议进行短写事务内的最终检查。报告失败不要求持续等待或立即重复尝试，但也不能把未完成责任解释为成功。时钟异常受限会话不持有普通接纳资格，按其一次报告机会结束，不执行下表的正常关闭接纳循环。

| 最终检查观察到的状态 | 对关闭接纳的影响 |
| --- | --- |
| 报告准备期间出现新的应报告业务变化，当前报告处理结果尚未覆盖 | 保持接纳资格，处理新增报告责任后再检查；本次失败按下述失败分支处理 |
| 本次报告机会的本地处理已完成，且没有新增应报告责任 | 报告方面允许关闭接纳；其他动作和收场责任仍需检查 |
| 仅剩本地发送或客户端 ACK 尚未完成，包括完整或局部同步待确认 | 不要求 `run` 持续等待；持久化责任由后续实际报告机会继续承担 |
| 本次报告处理已失败，此后没有尚未处理的新变化，其他可执行职责已经完成 | 保留报告及同步责任，按错误退出交接释放接纳资格；最终返回 `report_error`，不通过正常成功检查 |
| 本地报告职责是否完成无法确认 | 保留诊断并按错误处理，不能当作已经完成 |

这里的业务变化包含受理拒绝及 ACK 校验错误，不依赖新计划受理序列是否推进。报告构建与文件发布在短交接事务之外执行；报告内容、覆盖水位和本地完成证据必须相互一致。

为完成同一次收尾而反复进行的交接检查，不各自构成新的报告机会。本地处理成功后，主程序领取或删除文件不会使该收尾循环不断补投；本地处理失败后，重复检查也不重开同一轮尝试。会话内后续处理已经可靠完成全部本地报告责任、其他职责也完成时，可以正常成功结束，历史失败诊断仍保留。
