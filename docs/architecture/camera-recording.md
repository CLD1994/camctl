## camera_record

本节及后续录像执行、取消、恢复和验收规则描述已确认的录像控制流程：主机在启动确认后计时并停止录像。驱动从已确定的生效参数及拍摄任务定义取得本次目标时长，供计时、恢复和修复使用。具体相机的参数类型名称及输入字段属于设备接入规格；其他控制方式按其驱动契约定义完成条件。

### 基本语义

客户端用一个动作描述完整录像任务：

```text
camera_record
```

camctl 通过以下底层操作完成录像的启动和停止：

```text
record_start
record_stop
```

组成。

自身参数在首次受理时按[公共动作参数校验规则](plan-acceptance.md#整份校验与原子受理)检查。例如缺少所选参数类型要求的字段时，将该 `camera_record` 登记为 `failed`，保留参数错误及零次执行尝试；不启动或停止相机，也不登记源视频。其他动作继续受理。以下采集、收场和恢复规则适用于已取得执行资格的录像动作。

### 参数

| 字段 | 要求与含义 |
| --- | --- |
| `params.type` | 必填，选择目标驱动正式声明的录像参数类型 |
| `scheduled_at` | 必填，录像的计划启动时间；遵守公共时间规则 |
| `params` 中除 `type` 之外的字段 | 由所选参数类型的正式定义确定，并通过对应 JSON Schema 校验 |
| `policy.max_delay_ms` | 必填的非负整数，允许晚于 `scheduled_at` 启动的最大毫秒数，无缺省值 |

设备专属参数须先完成实际相机的正式类型定义，再通过驱动和能力说明提供给客户端。参数类型选择及参数值错误遵守[计划字段与参数校验](camera-capabilities.md#计划字段与参数校验)。

`policy` 必须是对象且提供合法的 `max_delay_ms`。缺少整个 `policy`、缺少该字段或字段值不合法时，仅将该录像动作在受理时登记为 `failed`，保留错误字段与原因、零次执行尝试；不等待计划时间，也不影响同计划其他合法动作的受理。

例如 `max_delay_ms = 5000` 表示启动窗口截至计划时间之后 5 秒，`0` 表示不允许迟到。窗口仍按公共规则判断，不承诺实际调度能够精确命中某个时刻；该字段不延长录像时长，也不改变本地通信超时和尝试上限。已受理请求重送仍复用首次输入及结果。

### 正常录像流程

合法录像到达计划时间后，按相机选择顺序取得启动机会：保存启动意图，发送启动命令，取得成功确认并保存计时依据及源文件关联。按 `duration_s` 录够后停止，成功响应确认文件已经写完，随后在同一事务中登记原片及录像成功结果。

正常流程的输出是一份保留在相机中的正式原片。录像动作本身不创建 delivery；取回由独立的 `obtain_action_outputs` 处理。异常录像的检查和修复由[异常录像恢复与修复](camera-recovery.md)定义。

### 当前相机的原片文件

已确认当前相机不会将一次连续录像按时长或文件大小自动拆成多个文件。一次连续录像形成原片时，对应一个源视频文件；本设备的原片关联、完整性核验和取回以该文件为单位。内部修复产生的成品是独立的派生产物。

### 通信方式与查询能力

当前相机运行嵌入式 Linux，具有完整文件系统，并提供具有完整命令执行权限的 `adb shell`。camctl 通过 shell 执行厂商提供的二进制程序，控制相机的录像等行为；文件列举、存在性检查、读取及删除由驱动通过 Linux 文件操作实现。已确认可以通过 shell 命令查询正在录制的文件名或路径，以及检查对应文件是否存在。

相机端只使用已有系统能力和厂商程序，不允许添加依赖或部署额外工具。`ffmpeg/ffprobe` 是主机端工具。正常录像不得仅为读取原视频时长或执行媒体核验而新增从相机到主机的视频拷贝；录像完成判定须在这一边界内设计。明确请求的取回、必要异常修复，以及正常会话中计时证据不足时的异常原片检查，按各自规则拷贝文件。

`adb shell` 和具体 shell 命令属于当前相机驱动的实现方式，不是框架要求所有相机提供的接口。框架通过驱动声明的业务能力取得录像和文件查询结果；未来驱动可以使用其他设备协议，调度、持久化和产物流程不依赖 ADB 或 Linux 命令。

查询正在录制的文件与查询指定文件是否存在分别表达各自的观察结果。文件存在本身不证明本次录像仍在进行或文件已经写完；查询错误或结果未知也不能当作文件不存在。具体命令、返回格式和结果识别在设备适配时核实，录像归属及写入完成仍按各自证据规则判断。

### 厂商控制程序的调用生命周期

已核实当前所有设备厂商提供的控制程序均在调用处理后返回，不随所启动的设备工作持续阻塞。例如启动一次 10 分钟录像，启动程序不会为了等待这段录像完成而持续运行 10 分钟。第一版相机驱动以这一前提管理控制命令调用；具体返回耗时仍由实际命令与设备条件决定。

camctl 异步管理主机上的 `adb` 子进程，取得本次调用的输出和退出结果。程序返回后，录像按已确认的设备状态与单调钟目标继续管理，到达停止条件再发出独立停止调用。驱动依据厂商协议解释返回结果；进程退出本身不自动代表业务成功，启动确认及停止后文件写完的依据仍遵守各自契约。

启动、停止与录像状态查询分别采用固化的[控制调用超时](configuration.md#控制调用超时)。控制调用超过其等待上限仍未返回，属于调用异常，不能用录像目标时长解释这次持续等待，也不能据此认定指令没有生效。结束主机侧调用的等待或终止本次 `adb` 子进程，不证明相机上的原程序已结束或录像已停止；后续使用已取得的响应和设备查询证据处理结果未知，并遵守安全重试与有限收场规则。该前提适用于当前已经核实的设备，未来驱动须根据实际设备定义调用生命周期。

### 第一版驱动接入契约

第一版接入当前已确认的 ADB 相机。业务层消费下表的结果；厂商二进制名称、命令参数及响应解析属于驱动实现和设备联调输入。

| 驱动职责 | 提供给业务层的结果 |
| --- | --- |
| 启动录像 | 本次启动成功确认；成功后通过设备查询关联实际录像和源文件 |
| 停止录像 | 本次停止成功确认，以及对应源文件已写完的依据 |
| 查询录像 | 是否正在录像、正在录制的文件路径，以及可关联到已知动作的依据 |
| 查询文件 | 指定源文件是否存在、完整长度及源端摘要；保留设备路径与产物的关联 |
| 读取与删除 | 对已写完文件按位置读取或删除指定文件；读取完成文件与录像兼容 |
| 调度控制与文件操作 | 文件传输期间必要的停止命令仍能得到执行机会 |

当前相机能力依据已确认的设备前提。真实设备接入前，驱动交付物须补齐上述操作的命令映射、正常响应样例，以及一条“启动—查询路径—停止—读取—删除”的联调记录。联调应确认启动调用返回后录像继续进行，停止通过独立调用完成；启动调用的等待上限与录像目标时长分别配置和解释。

第一版正常路径使用启动成功后的路径查询保存关联，并使用停止成功确认文件写完。尚未保存关联就断电或停止响应丢失时，沿用既有设备对账契约；具体恢复证据由驱动结合实际协议提供，不能靠猜测文件名完成关联。业务主流程的实现先使用受这些结果约束的驱动替身，实际相机验收以真实驱动满足契约为准。

### 录像期间的文件操作

已确认当前相机正在录像时，可以同时读取另一份已经写完的视频，不影响正在进行的录像。当前驱动将这种文件读取声明为与录像兼容，camctl 不因相机正在录像而要求该读取等待设备空闲。

当前驱动依据 Linux 文件语义处理已完成视频；删除指定文件的目录项不要求停止另一份视频的录像，也不删除另一份视频。该判断依据现有设备前提及普通文件操作语义，具体适配通过联调验证。[Linux unlink 文档](https://man7.org/linux/man-pages/man2/unlink.2.html)

对正在录制 B 的当前相机，另一份视频 A 的操作按以下规则处理：

| 操作及资格 | 处理 |
| --- | --- |
| 读取 A，来源及写入完成已确认，所属取回、异常原片检查或内部修复具有执行资格 | 按同一相机的拷贝并发限制读取，无须等待 B 停止 |
| 删除 A，已有明确清理授权，且满足产物清理及旧取回保护条件 | 允许删除 A，无须等待 B 停止 |
| 相应操作资格不满足或无法可靠确认 | 按所属流程等待、核实或报告错误；Linux 操作能力不代替业务授权 |

操作调度遵守[设备执行与操作兼容性](scheduling-execution.md#设备执行与操作兼容性)。文件操作不能妨碍必要的录像停止操作；控制通道与文件通道的实际协作通过适配验证。未来相机由对应驱动声明兼容性，不自动继承当前相机的能力。

当前相机允许录像与完成文件的读取同时进行；多份完成文件的读取则遵守[同一相机的拷贝并发限制](file-copy.md#同一相机的拷贝并发限制)，取回与录像内部处理共用一次只拷贝一份文件的约束。

### 源文件命名与录像关联

启动录像时能否指定相机源文件名或保存路径，由相机驱动声明。当前相机不支持；框架保留使用该能力的扩展入口，不将其作为相机接入或断电恢复的必备条件。

| 驱动能力 | 启动与关联方式 |
| --- | --- |
| 已确认支持指定源文件名或路径 | 可以使用该能力；使用时，将选定目标与启动意图一同可靠保存，再发送启动命令 |
| 已确认不支持 | 按设备自身的命名方式启动，由驱动通过已核实的设备协议关联本次录像及其源文件 |
| 能力未知或读取能力信息失败 | 明确保留未知或错误，不据此认定支持或不支持；先确认能力再选择相应路径 |

驱动向框架提供录像与源文件的关联结果及确认依据；框架持久化这些事实，供后续收场、核验和取回使用。设备特有的命名和查询方法由驱动负责，不要求所有相机采用同一种方法。

预先指定的路径属于启动意图，不证明设备已经开始录像或实际生成了该文件。命令失败或结果未知时，仍按录像对账规则核实，不能当作能力不支持而直接改用另一种方式再次启动。当前相机通过上述 shell 查询取得文件信息；如何结合这些信息确认本次动作的录像归属，以及启动后尚未保存关联就断电时如何恢复，仍需结合实际协议确认。

### `duration_s`

本专题使用 `duration_s` 表示录像执行所需的目标时长，单位为秒，其含义是：

> 从已经确认本次录像进入 recording 状态的时刻开始，至少继续录制这么长时间。

该值由驱动依据首次受理时确定的生效参数及任务定义取得，并作为执行和恢复所需的信息可靠保存。调用方可以通过设备开放的字段指定时长，也可以选择已包含固定时长的拍摄任务，具体方式由正式参数类型定义。这里的 `duration_s` 是行为规则及公式使用的名称，不规定计划中存在同名字段，也不规定客户端时长参数的数值类型或输入粒度。

### 录像启动确认

驱动必须定义：

> 什么证据足以确认本次录像已经处于 recording 状态。

已确认当前相机的启动录像指令返回成功时，相机已经进入录像状态。驱动可靠识别本次启动指令的成功响应，即可确认录像已开始，无须为确认启动再查询一次录像状态。收到该成功响应时读取当前会话的单调钟，作为下述计时锚点；后续持久化或源文件查询不重新设置该锚点。

该响应须可靠关联到本次启动尝试。命令已发出、响应失败、丢失或无法解释均不能代替成功确认，继续按启动结果未知及设备对账规则处理。成功响应确认录像已开始，但不自动提供源文件身份；源文件仍按“源文件命名与录像关联”确定。

未来相机由对应驱动定义可靠的启动确认依据，不自动继承当前相机的成功响应保证。

确认时记录：

```text
recording_confirmed_at_monotonic
```

正常停止目标：

```text
stop_target_monotonic =
    recording_confirmed_at_monotonic + duration_s
```

该时间点不是“第一帧真实时间”。

它只是一个保守锚点：

> 从这里开始可以确定录像已经进行。

因此正常情况下可能略微多录，但不主动少录。

如果设备协议不能提供可靠的录像启动确认，必须降低保证并如实报告，不能使用“发出 start 指令的时间”冒充实际录像起点。

### 录像启动的历史事实

按[历史事件的粒度](system-foundations.md#历史事件的粒度)，启动过程分别记录以下具有独立含义的事实；下列中文名称说明事实含义，具体事件标识和字段结构仍需结合设备协议细化。

- 启动意图已登记：关联动作、相机、本次尝试和已经确定的执行参数。该事实及相关投影提交成功后，才允许发送启动命令。
- 启动已确认：取得本专题要求的确认依据后，记录确认事实，以及设备协议能够提供的录像身份和有效计时依据。
- 启动尝试结果未知：例如等待响应超时且无法确认实际结果时，记录本次尝试和未知原因，供后续设备对账使用。

启动意图提交后、结果记录提交前断电，恢复时可能只能查到启动意图。这只能证明存在一次待核实的启动尝试；实际命令是否发出、录像是否启动仍须依据设备对账判断。历史中不能凭意图补写命令已发送或启动成功，也不能把缺少结果解释为设备未执行。

### 正常轻微多录

由保守确认点造成的正常少量尾部余量，不自动视为异常录像。

不为了精确卡秒而强制对所有录像执行裁剪。

### 启动与停止的尝试上限

启动录像与停止录像分别计数，尝试上限由本地设备配置分别提供，**默认均为 3 次，包含第一次**。动作首次受理时保存两类实际生效的上限，后续配置变化、请求重送或重启不改变既有动作的上限与已用次数。启动消耗不占用停止次数；采用默认值时，启动第三次才成功，停止仍有自己的 3 次尝试。

以下以 `S` 表示该动作固化的启动上限、`T` 表示固化的停止上限；两者是本节说明用符号，本地配置字段见实现时细化事项。

| 操作及已有结果 | 后续尝试规则 |
| --- | --- |
| 启动尚未成功，已用次数少于 `S` | 仍须满足启动窗口、重试等待及设备条件，符合条件才可再次尝试 |
| 启动已确认成功 | 停止启动尝试，进入录像及停止流程 |
| 启动已用次数达到 `S` 且仍未成功 | 原启动流程不再追加启动尝试；按实际失败、未知及窗口事实结束或对账 |
| 停止尚未确认，已用次数少于 `T` | 在目标归属、重复执行能力等条件允许时使用剩余次数 |
| 停止已确认成功 | 不再为该流程发送无必要的停止命令 |
| 停止已用次数达到 `T` 且仍未确认成功 | 原停止流程不再追加停止尝试；按停止失败及残留设备事实规则处理，不推断相机空闲 |

正常停止、取消触发的停止及断电恢复停止，同一次录像共用原停止流程的计数。切换入口、重复取消、进程重启或恢复会话不重新分配预算；已保存的成功确认也不能因重启丢失。后续其他动作针对历史残留录像的处理使用[后续动作触发的残留收场](camera-recovery.md#后续动作触发的残留收场)定义的独立流程与预算。

会话发生非时钟类致命错误时，已经确认归属的录像按[正在录像时的应急停止](session-errors.md#正在录像时的应急停止)立即有限停止。应急预算及数据库不可写时的记录边界由该专题定义，与本节正常、取消及恢复共用的普通停止预算分别表达。

启动与停止次数、每次尝试结果及对应投影分别持久化，报告分别表达已用次数和上限，不以一个总尝试次数代替两类预算。尚未尝试和受理时参数校验失败均保持相应次数为零。次数分配与启动或停止意图之间的具体落盘边界仍需明确；结果未知不能按“未尝试”清零。

### 客户端排程责任

客户端应保证同一相机计划中的录像时长不发生预期冲突。

camctl 不负责自动重排录像计划。

如果由于实际启动/停止延迟产生运行时冲突：

> 已经开始的录像优先。

后一个录像：

- 在自己的启动窗口内等待；
- 相机释放后仍在窗口内 → 开始；
- 超窗 → `expired`。

不得为了赶后一个录像而提前截短已经开始的录像。

### 多个待启动录像的选择顺序

先处理已经开始的录像，以及下节定义的等待重试保留关系。没有这些占用或保留时，同一相机有多个尚未开始录像、且同时具备启动条件的动作，按 `scheduled_at` 从早到晚选择。正常到点调度、延后开机和重启恢复采用相同规则；计划受理顺序、数据库查询顺序和内存加载顺序不能颠倒不同计划时间的先后。

选择前先按公共规则处理取消、既有终态、可信时间、启动窗口及设备执行条件。下表只对相机已经允许启动新录像的情况选择候选，不授权绕过设备对账或必要收场：

| 待启动动作的情况 | 处理 |
| --- | --- |
| 没有具备启动条件的动作 | 不发出录像启动命令，按各动作的等待、过期或失败规则处理 |
| 只有一个具备启动条件的动作 | 选择该动作 |
| 多个动作同时具备启动条件，最早 `scheduled_at` 只有一个动作 | 选择该最早动作；其他动作继续按自己的启动窗口等待 |
| 多个动作同时具备启动条件，最早 `scheduled_at` 相同 | 在这些动作中选择最早受理计划内的动作；同一计划内再按原 `actions` 数组顺序选择 |

候选动作依次按 `scheduled_at`、所属计划的 `plan_seq`、动作在首次受理的 `actions` 数组中的位置升序比较。`plan_seq` 使用[新计划受理序列](scheduling-execution.md#新计划发现与内存调度缓存)，不以墙钟记录的受理时间或计划名称代替。原数组位置随计划结构持久化，其他动作失败或取消不改变仍有效动作的相对顺序。

正常执行、增量加载、重启恢复及历史重建均使用这些已保存的排序依据。同一 `request_id` 重送不重新分配计划顺序，也不采用重送正文中的数组顺序。排序依据缺失、读取失败或无法可靠解释时按持久化错误处理，不退回数据库返回顺序或随机选择。此规则仅选择尚未取得启动机会的候选，不改变已经开始或等待重试的保留关系。

例如主机 10:12 开机：A 计划 10:00 开始，最晚可在 10:20 启动；B 计划 10:10 开始，最晚可在 10:15 启动；两者均录像 5 分钟，且此时均具备启动条件。先启动 A，B 等待并在自己的窗口耗尽后过期。即使反过来执行有机会完成两项，也不据此改变选择顺序。A 开始后继续遵守“客户端排程责任”中的已开始录像优先规则。

该排序不修改输入的计划时间、启动窗口或录像时长，也不复活已过期动作。启动尝试失败或结果未知后的处理仍按对应恢复与重试契约执行，不能仅凭排序认定设备已空闲。

#### 等待重试时保留相机

启动和停止使用各自固化的[通信重试间隔](configuration.md#通信重试间隔)，计时起点和再次发令资格遵守该节规则。

按上述顺序选中的录像启动尝试明确失败、确认未开始录像，且仍允许重试时，为该动作保留下一次录像启动机会。重试等待期间，相机即使空闲，其他录像也继续等待；不能因它们当前可以发令而绕过已有保留。

| 保留动作及设备情况 | 处理 |
| --- | --- |
| 仍允许重试，但尚未到下一次尝试时间 | 保留启动机会；其他录像等待，并独立判断各自的窗口是否耗尽 |
| 仍允许重试，已到尝试时间且设备条件满足 | 由原动作再次尝试；再次明确失败且仍可重试时继续保留 |
| 原动作已确认开始录像 | 转入已开始录像优先的规则，其他录像等待其释放相机 |
| 原动作取消、最终失败或过期 | 不再为其保留重试机会；确认设备满足启动条件后重新选择其他录像 |
| 原尝试结果未知、设备状态不明，或持久化事实无法可靠确认 | 先按原动作的对账或错误规则处理，不猜测空闲或将启动机会交给其他录像 |

保留不延长启动窗口、不增加或重置尝试预算。等待期间窗口耗尽时及时按过期规则结束，不等到下一次重试时间才释放保留。其他录像可能在等待期间过期，该结果继续如实保存和报告。

保留关系依据持久化的动作、尝试及重试事实确定，与相关结果同步保存，不能仅存在于内存。重启后先恢复原关系及预算，再选择新录像；历史回放只恢复事实，不发送命令。报告表达原动作等待重试，以及其他录像因该相机的启动机会已被保留而等待的情况。

这里保留的是录像启动机会。与其兼容的已完成文件读取、清理等操作仍按设备能力和各自资格执行；这些操作不能妨碍必要的设备对账或停止。

### 停止命令的重复执行

已确认当前相机的停止录像指令可以重复执行。相机已经停止录像时，再次执行该指令仍尝试停止录像，保持停止状态，不产生额外副作用。

当前相机驱动据此声明停止操作可安全重复。停止尝试的响应丢失或结果未知时，允许在原收场流程及剩余有限重试预算内再次发送停止指令；主机重启不创建新的补偿流程或重置预算。命令可以重复执行不表示此前尝试已经成功，停止结果仍须按实际确认或查询证据保存。

重试仍受录像归属及取消目标约束：不能停止其他动作的录像，也不能把归属未知的录像当作本次目标。已确认本次录像停止后，按相应完成及取消规则继续处理，不因具备重复执行能力而增加无必要的停止操作。

本能力属于当前相机。未来相机是否支持安全重复停止由对应驱动确认，并遵守[效果登记与补偿](scheduling-execution.md#效果登记与补偿)的公共规则。

### 停止成功与文件可读

已确认当前相机的停止录像指令返回成功时，对应视频文件已经写完，可以立即读取；此后文件内容和长度保持不变。驱动将本次停止成功与已确认的录像及源文件关联，camctl 保存该确认事实后按“录像成功标准”完成正常录像，或继续必要的异常处理，不额外等待文件长度稳定。

该保证用于确认源文件已经完成写入，不表示已经读取并核验文件内的视频时长。正常录像结合启动确认和单调钟计时判定控制流程是否完成。源文件登记与动作终态继续遵守“录像动作的结束时点”。

| 停止结果与文件关联 | 文件处理 |
| --- | --- |
| 返回成功，且对应录像与源文件已可靠关联 | 确认文件写完，可完成正常录像；实际读取按取回或必要异常处理的资格执行 |
| 返回成功，但录像或源文件关联不明 | 先核实关联，不将任意已有文件视为本次产物 |
| 停止失败、响应丢失或结果未知 | 不据此认定文件写完；按停止重试及设备对账规则取得可靠依据 |
| 停止或文件确认记录的保存失败、提交结果未知 | 按持久化错误处理，恢复先确认实际记录，不猜测确认结果 |

未来相机由对应驱动定义文件写完的可靠确认依据，不自动继承当前相机的停止成功保证。仅文件存在或一次长度查询不能证明写入已经完成。

### 录像成功标准

正常录像的 `succeeded` 表示已按要求完成录像控制流程。未取消、未发现提前停止等录像异常时，须同时具备以下事实：

1. 已可靠取得本次录像的启动成功确认，并保存接收成功响应时的单调钟锚点。
2. 从该锚点起，按当前会话单调钟等待至少 `duration_s`，再执行停止。
3. 已取得停止成功确认，并可靠关联对应源文件及其写入完成事实。

满足上述条件且没有尚需完成的处理时，登记原片并提交动作 `succeeded`。正常录像不为读取时长或媒体核验而将原片拷贝到主机，也不要求读取视频轨道、时长或逐帧解码。

正常控制完成的事实已经可靠保存，仅在终态登记前中断时，恢复使用这些事实完成登记，不将登记中断本身视为录像异常。使用的是原会话已保存的计时结果，不能将旧单调钟锚点与新会话的时钟读数组合计算时长；完成事实缺失或未知时仍先对账。

报告区分目标时长、控制过程的计时证据及从文件取得的媒体信息。未读取文件内时长时，实际视频时长保持未知，媒体核验表达为未执行；不能以 `duration_s` 或主机等待时长代填实际视频时长，也不能将未执行核验记为核验失败或核验通过。

异常录像还可以采用原片时长检查作为成功依据：已确认原片属于本次录像且已经写完，主机检查可靠确认视频时长达到 `duration_s`，且没有明确的录像失败证据时，即使缺少可靠的控制计时，也满足第一版的录像成功标准。成功依据记为“时长检查满足目标”，保存实际视频时长及检查依据，不补造控制计时，也不承诺整段视频均可正常解码。正常或恢复控制完成与时长检查是分别成立的成功依据，数据库保存实际取得的依据；对外报告内容遵守[报告内容](status-reports.md#报告内容)。

取得时长成功依据不代表动作立即结束；必要修复及其他适用后处理仍须取得最终结果，再统一登记正式产物和动作终态。时长不足或其他明确媒体错误优先按失败处理，时长未知不能取得该成功依据。取消、已有终态及持久化错误继续按各自规则处理。

业务记录可可靠读取时，先处理取消与已有终态，再按下表的其余分区判断；记录保存失败或提交结果未知仍按持久化错误处理：

| 当前录像处理情况 | 结果处理 |
| --- | --- |
| 已取消或已有终态 | 按取消及终态规则处理，不由本节覆盖 |
| 正常控制流程尚未完成 | 继续执行或确认，不提前判成功 |
| 正常控制流程具备上述全部事实 | 按控制流程完成判为 `succeeded`，不要求媒体核验 |
| 已发生提前停止、断电恢复、停止失败等异常，仍有适用处理未完成 | 继续对应恢复及有限处理，不能套用正常流程的成功条件；旧会话单调钟不能用于新会话计时 |
| 异常处理结束，已有明确的录像失败证据，例如确认时长不足或原片损坏 | 按失败规则结束，不用后续停止成功覆盖已知失败事实 |
| 异常处理结束，没有明确的录像失败证据，已有可靠的恢复控制完成事实或原片时长检查满足目标 | 判为 `succeeded`，保留具体成功依据、异常及修复结果；未读取媒体时长时仍表达未知，不宣称完成整段解码验证 |
| 异常处理结束，仍未取得满足成功标准的证据 | 按失败规则结束，保留已经确定的文件、异常及未知事实 |

恢复控制完成的具体依据见[断电恢复后的控制完成依据](camera-recovery.md#断电恢复后的控制完成依据)。异常多录仍按内部修复规则处理；因必要修复已取回主机的视频可由主机工具读取视频信息。恢复已取得充分控制证据且确认无需修复时，不为核验单独拷贝原片；是否明显多录仍无法判定时，按[计时证据不足时的原片检查](camera-recovery.md#计时证据不足时的原片检查)拷贝检查，不凭目标时长推定文件完整。

成功结果保留实际使用的判定依据，不隐藏通信失败、延迟停止、恢复或修复过程。动作终态提交后，后续取回或检查发现的时长不足、损坏等媒体问题作为新的产物质量事实记录并报告，不改写录像动作的历史终态。

### 录像动作的结束时点

正常录像在控制流程完成后结束；异常录像继续完成适用的核验和必要内部修复。各自需要的处理取得最终结果后，在同一数据库事务中登记应保留的全部正式产物并提交动作终态。原片与修复成品均在该事务成功提交后成为可供取回选择的正式产物，正常录像不因未执行媒体核验而延迟结束。

动作结束前照常保存源文件关联、主机文件、拷贝进度、核验和修复结果，支撑断电恢复及状态报告。这些内部处理记录不构成正式产物登记；即使原片已经写完且时长检查满足目标，也不能在修复仍未结束时提前取回原片。状态报告可以表达处理进度，不将这些文件列为可取回的正式产物。

下表用于未取消、未过期的动作；启动失败、核验失败或修复失败等已按相应规则结束的阶段，不要求继续执行已无必要或无法执行的后续步骤，但须记录失败原因及未执行的依据。

| 处理进度与结果 | 动作与正式产物的处理 |
| --- | --- |
| 采集、必要收场或适用的核验、修复仍需继续执行或恢复 | 保持未完成，保存内部处理记录，不登记正式产物 |
| 正常控制流程已按成功标准完成 | 同一事务登记原片并提交 `succeeded`，保留控制证据；媒体核验未执行，实际视频时长未知 |
| 异常处理各阶段已结束，恢复控制完成或原片时长检查满足目标，没有明确的录像失败证据，修复不需要或已成功 | 同一事务登记原片、适用的修复成品并提交 `succeeded`，保留具体成功依据 |
| 异常处理各阶段已结束，恢复控制完成或原片时长检查满足目标，没有明确的录像失败证据，修复已失败 | 同一事务登记原片并提交 `succeeded`，保留成功依据及修复失败原因 |
| 异常处理各阶段已按规则结束，仍未满足成功标准 | 同一事务登记按规则应保留的正式产物或记录确认无正式产物，并提交 `failed`；保留核验结果、失败原因及残留设备事实 |
| 各阶段已结束，但处理结果或应保留文件集合无法可靠确定 | 先核实或按相应错误处理，不提交猜测的终态或产物集合 |

终态事务须确认阶段结果已经可靠保存，或将尚未保存的结果一同提交；正式产物登记、动作终态的历史与投影整体可见。等待取回的请求只有看到已提交的录像终态，才按[取回等待规则](obtaining-outputs.md#等待录像动作结束)选择文件。文件读取、核验和修复在该事务之外完成。

取消与过期按各自规则结束，不能因本节要求而继续本应停止的核验或修复。修复期间动作尚未终态，取消仍按“camera_record 取消”放弃本次录像；已经提交的终态保持不变。有限收场失败后保留的未知设备状态，不要求无限等待其变为已知。

取消与结束并发时，以目标录像的持久化处理顺序判断；取消计划被受理本身不表示目标录像已经取消：

| 数据库中的先后顺序或结果 | 处理 |
| --- | --- |
| 目标录像的取消标记先保存，结束事务尚未提交 | 按取消规则放弃内容，不登记正式产物；结束处理须在事务内检查该标记 |
| 正式产物与录像终态的事务先提交，随后处理取消 | 保持录像终态和正式产物；取消录像不授权删除这些文件，文件继续按显式清理规则保留 |
| 结束事务失败且确认回滚 | 不留下部分正式产物或终态；根据已有处理结果及取消状态恢复 |
| 提交结果未知或状态无法可靠读取 | 先确认数据库事实，不据此发布产物、重复登记或将文件当作废弃内容删除 |

断电后根据已提交的内部处理记录、正式产物和动作状态恢复。终态尚未提交时，在会话具备相应执行资格后继续必要处理并完成统一提交；时钟异常时按[安全收场与后续处理的衔接](camera-recovery.md#安全收场与后续处理的衔接)保留尚未完成的后处理，不因已看到完整原片而跳过未结束的修复。终态已经提交时不重新执行本次核验或修复，也不重复登记产物。已取消录像留下的文件继续按废弃内容处理，不因重启转成正式产物。

### camera_record 取消

在动作尚未进入终态时取消 `camera_record`：

> 放弃本次录像。

包括：

- 尚未开始；
- 正在录像；
- 已经停止但正在核验；
- 正在内部修复。

如果录像仍在进行：

- 尝试停止；
- 放弃内容；
- 协议支持时清理废弃产物。

如果录像已经停止：

- 不再次发送可能误停后续录像的通用 stop；
- 终止后续核验/修复；
- 放弃本动作产生的内容；
- 协议支持时清理废弃产物。

废弃录像不登记为正常可取回产物。

取消生效不等于物理清理一定成功。

## 配置归属

`clock.recovery_wait_cap_s` 是异常恢复等待上限，默认 **60 秒**，允许通过本地配置设置为有限的非负秒数；设为 0 时不额外等待。异常时等待 `min(duration_s, recovery_wait_cap_s)` 后尝试停止，它不限制正常录像的 `duration_s`。

`devices.<id>.recording.repair_margin_s` 是本专题录像流程允许的异常多录余量，默认 **10 秒**，允许本地配置为有限、非负的秒数。设为 0 时，已确认异常录像严格超过目标时长即达到多录修复条件。该值在动作首次受理时作为生效策略保存，后续配置变化仅影响新受理的动作。

该参数只决定异常多录的修复门槛，不推迟正常停止目标，也不改变异常恢复等待上限；执行计划不提供裁剪或修复门槛覆盖参数。正常轻微多录及修复资格判断继续遵守[自动修复的多录门槛](camera-recovery.md#自动修复的多录门槛)。

## 持久化记录

以下是支撑本专题行为的逻辑记录建议；表划分和内部接口不构成已确认的实现约束。

将录像意图、可恢复的设备录像身份、启动确认依据、收场进度、完整性核验结果、修复结果及残留设备事实追加到历史，并同步更新相关投影，遵守[持久化与配置基础](system-foundations.md#持久化与配置基础)。历史回放不启动或停止录像，也不执行修复。回放恢复的是已记录的观察与意图；实际设备对账继续按本专题的证据规则执行。

当前会话单调钟锚点仅适用于当前会话，持久化历史不会使旧锚点在新会话中有效。跨重启恢复应依据本专题定义的可证明事实，具体记录结构待结合真实协议确定。

## 验收要求

### 单元测试

录像输入覆盖 `policy` 缺失、不是对象、缺少 `max_delay_ms`、值为负数或类型不符，以及合法零值和正整数。非法输入只使该录像在受理时失败且不产生尝试；合法输入按明确给出的启动窗口执行，不使用隐藏默认值。

触发动作取消或过期时，覆盖停止命令尚未发出、已经发出、发出状态未知及收场已结束。未发出则不开始，已开始则继续原剩余次数；不启动触发动作的录像，不创建新预算。

按[后续动作触发的残留收场](camera-recovery.md#后续动作触发的残留收场)覆盖设备空闲、已知历史残留、其他有效动作占用及状态未知。已知残留才可触发独立收场；上限默认 3 次且可配置，原停止计数与新录像自身计数均不消耗或重置。同一触发动作重复检查不新建预算；新收场成功不改写旧录像终态，耗尽后不能后台重复启动。

按“启动与停止的尝试上限”覆盖默认上限、两类上限分别配置，以及已用次数为零、尚有剩余和达到上限，与明确成功、明确失败和结果未知的组合。启动消耗不占用停止预算；原流程不能超过各自固化上限，成功后不继续尝试。正常停止、取消停止和恢复停止共享原计数，切换入口不重置；报告分别表达两类实际生效的上限与次数。

同一计划时间下，覆盖不同计划按 `plan_seq`、同一计划按原数组位置排序，以及二者组合。反转受理时间字段、名称及加载顺序，仍按已保存的排序依据选择；无效或终态动作不参与候选，不改变其他动作的相对顺序。缺失排序依据不得静默降级为查询顺序。

按“等待重试时保留相机”覆盖退避未到、退避已到、再次失败、启动成功、取消、预算耗尽、窗口耗尽及结果未知。保留期间不启动其他录像，其他动作仍独立判断过期；保留解除后才能重新选择。窗口在退避结束前耗尽时不延长占用，兼容文件操作不因启动保留被一并禁止。

按“多个待启动录像的选择顺序”覆盖零个、一个和多个具备启动条件的动作。不同计划时间时选择较早动作，即使较晚动作的窗口更早结束；反转受理、查询及加载顺序，结果保持不变。未来动作、已过期或取消动作不参与候选，设备状态未知不能通过排序获得启动许可，已开始录像不被截短。

隔离设备、时钟、产物存储和视频处理协作者，验证启动确认、停止目标、冲突等待、恢复条件、成功证据、修复失败及各阶段取消。

按“录像动作的结束时点”覆盖处理进度、核验结果、修复结果及取消顺序。验证原片已写完且时长满足目标但修复未结束时，只保留内部处理记录，不能取回原片；修复失败不改变已确认的录像成功依据。取消标记先保存时不登记正式产物，终态事务先提交时后续取消不删除正式产物；提交未知不能当作未登记或已取消处理。

覆盖启动意图、有效启动确认和结果未知的事实解释，验证携带对应尝试及其证据。设备状态值不变但新增恢复依据时，仍保留该观察；历史回放使用已记录参数和结果，不随当前策略变化重新作出历史决策。

当前相机启动确认覆盖本次成功响应、失败响应、响应丢失及无法解释的情况。成功响应以收到时的单调钟作为计时锚点，不再为确认启动查询录像状态；持久化及源文件查询延迟不能移动该锚点。仅发出命令不能启动正常时长计时，源文件身份不能由成功响应推定，其他驱动按自身确认契约处理。

按“源文件命名与录像关联”覆盖支持、不支持、能力未知及查询失败。支持分支验证指定目标在启动前可靠保存；不支持分支使用设备命名与驱动关联结果。指定路径不能代替录像确认，启动失败或未知不能触发另一种启动方式。

验证当前相机录制 B 时，具备执行资格且确认写完的 A 可进入读取，不因录像占用而等待空闲。A 尚未写完、来源未知或所属流程无执行资格时，不能仅凭操作兼容获得读取资格；其他相机按其驱动声明判断。文件读取期间必要的停止操作仍须获得执行机会。

验证当前相机声明安全重复停止后，结果未知的停止尝试可在原流程与剩余预算内重试；此前成功不能由重试能力推断。组合目标归属、已确认停止及预算耗尽，验证不会误停其他或归属未知的录像，不重复已完成的收场，也不因恢复重置预算。其他驱动未确认此能力时不能沿用当前相机的保证。

按“停止成功与文件可读”覆盖成功及可靠关联、关联不明、停止失败或未知，以及确认记录保存失败。成功且关联可靠时确认文件已写完，不等待长度稳定；文件写完不能单独代替正常控制流程的计时条件或提前登记正式产物。实际读取仍需所属流程资格，其他驱动按自己的文件完成证据处理。

按[原片保留与核验结果](camera-recovery.md#原片保留与核验结果)覆盖取消、正常控制完成且未核验、时长检查满足目标、不足时长、确认损坏、核验无结论、确认无文件及文件归属或写入完成未知的分区。已写完且归属明确的失败原片仍登记，不因失败调用文件删除；未执行核验不等于核验失败，核验未确认不能写成损坏，未知时长不能写成零，主机副本失败不能推断源文件损坏。取消仍放弃内容，文件归属或写入完成未知时不能登记为可取回产物。

按“录像成功标准”验证正常启动确认、单调钟等待及停止成功共同决定结果；正常完成不调用视频拷贝或媒体核验协作者，不将控制等待时长填入实际视频时长。未完成、异常及记录未知不能直接判成功；终态后新增媒体质量事实只更新产物及报告，不改写录像终态。

另行覆盖异常录像缺少控制计时、但原片归属和写完已确认时的时长成功依据：可靠时长恰好达到或超过目标且没有明确失败证据时，可以成功；不足时长、时长未知及已知媒体错误不能由该分支判成功。分别组合无需修复、修复成功、失败及尚未结束，验证控制完成与时长检查两类成功依据保持独立，终态仍等待必要处理结束；数据库保留实际判定依据，报告表达对应的录像、检查及修复结果。

按[断电恢复后的控制完成依据](camera-recovery.md#断电恢复后的控制完成依据)覆盖录像归属与连续性、可信计时充分或不足、停止确认及文件写入完成的分区。仅历史启动意图或仅当前时间可信不能取得成功资格；恢复已录够且停止成功、源文件写完时，不要求媒体核验。需要修复时仍等待修复最终结果；修复失败或核验无结论不能否定已有控制依据，明确的录像失败证据仍优先处理。

按[自动修复的多录门槛](camera-recovery.md#自动修复的多录门槛)覆盖正常轻微余量、异常录像低于门槛、恰好相等、严格超过及计时未知。区分完整计时结论与仅有下界的证据，未越界的下界不能证明无需修复；停止响应延迟不自动增加已确认录制时长。验证固定秒数不随 `duration_s` 按比例变化，门槛不移动停止目标，已保存决定及余量不因新配置或重启改变。拷贝须有已保存的异常检查或修复决定，确认停止及文件写完前不读取源文件。

验证多录余量未配置时采用默认值，显式配置合法零值或正值时使用对应值；负值、非有限数值或类型错误不能冒充缺省值。配置变化仅影响新受理动作，已受理动作继续使用原余量。

按[计时证据不足时的原片检查](camera-recovery.md#计时证据不足时的原片检查)覆盖正常会话资格、来源与写入完成、拷贝完整性及检查结果。时长分别低于目标、等于目标、位于目标与门槛之间、恰好门槛及超过门槛；错误与未知不能归入无需修复。需要修复时复用同一有效副本，不增加一次源文件拷贝。检查失败分别组合已有与缺少控制成功依据，验证录像结果、检查结果及原片保留彼此一致；取消、既有终态及有限预算继续约束处理。

按[第一版原片检查的范围](camera-recovery.md#第一版原片检查的范围)覆盖可靠时长、已发现媒体错误、信息无法确认、工具失败及未完成。检查不启动整段逐帧解码，结果只反映取得的视频信息；音频或文件总时长不能自动代替视频时长，缺失或矛盾信息不能使用零或目标时长填充。报告不得将时长检查通过或拷贝摘要一致写成整段视频可正常解码。

按[安全收场与后续处理的衔接](camera-recovery.md#安全收场与后续处理的衔接)覆盖会话时钟资格、停止及文件确认、未完成阶段、取消和终态。时钟异常下已成功停止且仍需后处理时，动作保持 `running` 并明确等待正常会话，不调用拷贝或媒体处理，也不登记正式产物；后续会话仍异常时不重复停止。确认缺失或记录未知不能进入已停止阶段，停止预算耗尽不能转为无限等待。正常会话恢复后使用原进度；等待期间取消后不恢复处理。

组合真实 SQLite、录像调度、受接口约束的相机适配与报告生成，验证正常控制流程完成后直接原子提交录像成功及原片登记，整个流程不取回视频或执行主机媒体核验；报告保留控制依据、未知的视频时长及未执行核验。主机没有可供视频拷贝使用的空间但状态库仍可写时，正常录像仍可完成。分别在停止确认保存及终态事务提交前后中断，验证恢复依据已保存事实处理；后续取回发现媒体问题时，新增质量报告而保持既有录像终态。

组合 SQLite、恢复计时、相机适配与修复流程，验证异常录像严格超过已固化门槛后，先保存修复决定，取得停止与文件写完确认后才拷贝。使用门槛前、恰好门槛及超过门槛的独立时间数据，验证是否进入修复；判定本身不取回视频探测时长。分别在决定提交前后及修复拷贝期间中断，并修改本地配置，恢复仍沿用原动作余量和已提交决定；已有部分修复输入继续续传，报告区分计时依据与未知的媒体时长。

组合真实 SQLite、连续的异常与正常启动、录像及等待取回，验证时钟异常会话完成有限停止后保存等待阶段，以 `clock_invalid` 结束且不持有普通接纳资格，原片尚未成为正式产物。再次异常启动不重复停止或执行后处理；正常启动从原进度继续，全部适用处理结束后才将正式产物与终态一同提交，等待取回随后获得选择机会。分别在停止确认、阶段保存和终态事务提交前后中断，验证恢复依据实际提交事实，不补造录像时长、不重复登记。包含已有部分修复输入及等待期间取消的情况，进度与预算保持，取消结果阻止后续恢复修复。

使用真实 SQLite、源视频、主机检查及修复流程，构造历史计时不足但文件归属和写完已确认的异常录像。验证正常会话主动拷贝到 `staging` 检查，按可靠时长决定保留或修复，无客户端取回请求时也执行；整个内部流程不发布交付文件。检查确认明显多录后复用原副本修复，结束前没有正式产物。分别在检查决定、拷贝进度、检查结果及修复决定提交前后中断，验证续传和结果恢复不重复复制或重置预算；重启遇到时钟异常则暂停后处理。另行覆盖空间不足、摘要校验耗尽、检查工具失败及取消，验证原片与最终结果遵守各自规则。

组合主机媒体工具、真实视频文件、SQLite 与报告，验证检查取得的视频时长及判定与独立确定的样本事实一致，且报告不宣称完成整段解码。包含音视频时长不同、无法取得可靠时长及能够明确发现媒体问题的样本，验证不误用非视频时长、不隐藏已知错误；具体样本与工具命令在适配时确定。

使用缺少可靠控制计时的异常录像，组合真实时长检查、SQLite、修复与报告，验证原片时长达到目标后可取得成功依据，无需整段逐帧解码。分别覆盖无需修复、修复成功和修复失败，适用处理结束后才原子提交正式产物及 `succeeded`，数据库保留时长成功依据，报告表达录像结果、实际时长和修复结果。在检查依据保存及终态事务提交前后中断，恢复不补造控制计时、不重复登记；后来发现媒体问题只追加产物事实，不改写已提交的动作终态。

当前相机联调验证启动指令成功返回时录像已经开始，正常停止目标以成功响应的接收时刻加 `duration_s` 确定；核实录像身份的关联协议，验证一次连续录像的原片对应一个源视频文件。组合真实文件与 `ffmpeg/ffprobe` 验证无重新编码修复和完整性，以及持久化记录与录像恢复的协作。

当前相机联调验证停止录像后再次发送停止指令仍保持停止且无额外副作用。组合持久化收场记录与设备适配，覆盖停止已执行但响应未保存以及主机中断后的恢复，验证符合目标归属条件时复用原流程和预算重试，保存实际停止证据。

当前相机联调验证停止指令成功返回后，对应视频可立即完整读取，后续长度和内容保持不变。组合 SQLite 与录像处理，在停止成功后确认记录提交前后中断，验证恢复按持久化事实及设备对账继续处理，不能将缺少成功记录解释为文件仍在写入或已经写完。

当前相机联调在录制 B 的同时读取已完成视频 A，验证 A 的内容完整且 B 的录像不受影响；在读取尚未结束时到达 B 的停止目标，验证必要停止操作不被文件读取阻塞至取回完成。取回及内部修复所需读取均覆盖该协作边界。

组合清理授权、旧取回保护与当前相机文件操作，在录制 B 时删除已完成视频 A，验证只处理 A 且 B 继续录像；存在未解除的读取依赖时仍等待，不能因 Linux 允许删除文件而绕过清理资格。

使用可正常播放但不足目标时长的视频，组合核验、SQLite、等待中的取回及报告生成，验证原片登记与录像失败整体提交，取回可以取得该原片，报告包含目标与实际时长。重启不删除或重复登记；客户端后续明确提交清理计划后才按清理规则删除，数据库历史继续保留。

另用已写完且归属明确的损坏原片及核验未取得结论的原片，验证处理结束后均可登记并原样取回，报告分别保留确认损坏与核验未知的结果。取回文件与对应源文件逐字节一致，客户端通过交付摘要核验传输内容，不以无法播放拒绝交付。覆盖结束事务提交前后中断及后续显式清理，原片保留与数据库历史遵守各自规则。

组合真实 SQLite 和受接口约束的设备替身，验证启动意图与投影提交成功前不能发送命令。分别在意图提交后命令发送前、命令发送后结果提交前、确认结果提交后中断，验证前两者恢复时均保留待核实含义，后者保留已确认的历史事实；当前设备状态仍按本专题对账。回放本身不发送启动或停止命令。

同一框架流程分别组合支持指定路径与设备自行命名的驱动适配，验证两者均能保存和恢复已确认的录像、源文件关联。当前相机的真实协议验证覆盖设备自行命名、shell 查询正在录制的文件及文件存在性，并区分查询成功、失败和未知。以不依赖 ADB 的受接口约束适配替身验证框架消费相同业务结果；未来驱动另行验证其真实设备协议。关联证据不足时保留未确认结果，不根据预期路径补造已生成文件。

组合 SQLite、录像后处理、等待中的取回与报告生成，验证修复成功时取回包含原片和修复成品，修复失败但原片时长满足目标且无明确失败证据时，录像成功且报告保留修复失败。分别在内部结果保存后、结束事务部分写入后及提交后中断，验证正式产物与终态同时可见或均未提交，恢复不遗漏成品、不重复登记。修复期间的报告可包含进度，但没有可取回的原片或修复成品。

分别安排目标录像取消标记与结束事务先提交，验证前者保留取消结果且不登记正式产物，后者保留终态及正式产物。包含取消计划已受理但目标取消尚未处理的情况；取消后再次启动，废弃文件不会被登记或取回。

#### 拍摄能力与参数类型

- 同一种拍摄能力在不同驱动下可以使用不同参数类型；固定任务参数不能被未开放字段覆盖。
- 由实际驱动定义和设备配置生成说明，验证设备绑定、可执行能力及参数规则一致；更换绑定或修改参数契约后，导出说明反映对应变化。
- 组合实际导出文件与客户端读取、校验流程，验证单份 JSON 包含全部必要 Schema 及引用定义，手工复制后可以离线加载。按[客户端加载能力说明](camera-capabilities.md#客户端加载能力说明)覆盖成功整体替换、设备移除、文件读取失败、JSON 截断和 Schema 错误；失败不启用部分规则，成功不保留新目录中已移除的设备，历史记录和用户预设按既有规则保留。
- 将导出说明与计划入口组合验证：合法示例通过对应驱动校验，违反字段或组合限制的拍摄动作按自身参数错误失败；说明生成故障不能产生可交付的残缺说明。
- 按[拍摄参数的 JSON Schema](camera-capabilities.md#拍摄参数的-json-schema)验证根部版本声明、内部子规则的版本继承、完整引用及三处校验一致性；覆盖必需声明缺失、版本不匹配和所需语义不可用的规则错误。使用实际驱动定义与明确选择所约定标准的真实校验器组合做集成测试，覆盖合法组合、非法组合、缺失必填字段、额外字段和错误值类型；在无法联网的环境中验证标准定义和引用规则均可在本地取得。规则无效或必要语义无法执行时按规则处理失败，不伪装成参数不合法或校验通过。
- 使用同一组真实 Schema 和输入样例，验证浏览器 Ajv、客户端后端 Ajv 与 camctl 参数校验的合法性判定一致，且各处校验均不修改原始输入；客户端两处使用相同的错误转换规则，camctl 的诊断继续遵守其输入错误契约。
- 验证导出的默认值与驱动实际补齐结果一致，校验和默认值处理不修改保存的原始输入；已受理动作恢复时使用原生效参数。客户端校验通过后，设备不可用等运行条件仍按执行规则处理。
- 按[计划字段与参数校验](camera-capabilities.md#计划字段与参数校验)覆盖未实现类型、设备不适用、参数类型错误、参数错误、合法输入和定义读取故障；分别验证整份拒绝、单动作失败和会话错误。
- 驱动默认值首次受理后固定，重送、恢复和历史回放不按新的默认值重算参数；原计划重建保留原始输入。
- 参数类型或参数值校验失败的拍摄成员仍是组取回来源，终态无正式产物时按取回失败项表达。
- 第一版真实相机验收使用依据设备能力完成的正式参数类型，贯通计划受理、录像、产物登记和取回；协议演练可使用样例驱动及其参数定义，未来驱动的扩展边界可用受接口约束的替身验证。

## 实现时细化

正文定义第一版的业务规则。本节列出接口、配置和联调中需要落实的细节；先按正常流程推进，涉及正文尚未确定的业务结果时，再明确对应选择。

实际相机接入前，完成[当前相机录像参数](camera-parameters.md)中的设备接入定义：确定正式参数类型标识、允许字段、默认值、范围和组合约束，以及这些参数如何确定设备操作与执行所需的目标时长等信息。规格以实际相机能力为依据，驱动据此提供同源校验定义及能力说明。

已收到的设备交接材料见[相机控制交接资料整理](../hardware/camera-control-handoff.md)，附完整原文转录和图片，可用于核对命令、任务要求及尚需确认的设备信息。

能力及参数说明通过 `camctl describe` 导出一份内含 JSON Schema 的 JSON 文件，由用户手工复制覆盖到客户端，按[客户端加载能力说明](camera-capabilities.md#客户端加载能力说明)校验并启用。具体字段结构见[能力说明格式](capabilities.md)，文件位置与加载入口见[客户端部署与能力说明加载](client-deployment.md)。标准版本、内容、同步责任和同源校验遵守[部署时向客户端提供说明](camera-capabilities.md#部署时向客户端提供说明)及[拍摄参数的 JSON Schema](camera-capabilities.md#拍摄参数的-json-schema)。

启动与停止的尝试上限默认各 3 次且允许分别配置，正常、取消及恢复入口共享原停止计数。仍需明确次数分配与设备意图的持久化边界、启动、停止及后续按需收场在本地设备配置中的具体字段。计划不提供通信策略覆盖，按调度专题的配置归属规则处理。后续动作触发的收场采用已确认的独立预算，触发动作结束时按本专题的收场规则处理。

正常录像按控制流程完成判定成功；异常录像按已确认的恢复控制完成或原片时长检查满足目标判定成功。自动修复采用[自动修复的多录门槛](camera-recovery.md#自动修复的多录门槛)中定义的固定额外秒数；正常会话中仍无法确定是否超过门槛时，按[计时证据不足时的原片检查](camera-recovery.md#计时证据不足时的原片检查)拷贝检查。仍需明确恢复所用历史时间与连续性证据的具体表示、主机媒体检查的方法与可靠判定依据，以及其他媒体核验适用场景。这些规则须遵守相机端不增加依赖、不为控制成功判定单独拷贝原片的边界。文件归属及写入完成已经确认的原片按[原片保留与核验结果](camera-recovery.md#原片保留与核验结果)登记并保留；失败原因、未执行核验及未知媒体信息的字段表达仍需细化，不能将主机工具可用当作原片已经位于主机。正式产物登记、终态提交及与取消的先后关系遵守“录像动作的结束时点”；废弃文件的具体清理能力与恢复仍需结合设备协议细化。覆盖停止失败、内容完整证据、结果未知及后续对账的有效组合，保持动作终态不可迁移。
