# 测试规则

本文件适用于程序行为设计与修改，以及测试的编写、修改、运行、评审和验证结论汇报，完整定义测试分类、隔离、替身、断言与覆盖要求。组件运行命令与局部限制由对应目录的指南补充。

## 测试设计与验证

- 如果遇到测试失败或静态检查失败，先定位根因，再修复。不要用删除测试、放宽配置、吞掉错误的方式让门禁变绿。

- 项目测试的顶层分类是单元测试和集成测试。单元测试验证局部调用逻辑与行为契约，集成测试验证真实协作者组合后的运行逻辑；其他执行属性不得模糊二者的归属。

- 第一版集成测试验证软件组件之间的协作，不连接真实相机等具体设备，也不承担依赖目标硬件的性能验收。设备交互通过受真实接口契约约束的测试替身提供；实际设备联调、目标主机性能测量及物理断电验证单独安排，不作为软件集成测试的运行前提或通过门槛。

- 单元测试以具有独立语义契约的生产函数或对象为边界，优先从生产调用者使用的稳定入口验证行为；一个用例围绕该契约的一个行为分区组织输入和预期。被测入口应有明确的输入、输出、异常或状态变化，不能仅因某个私有函数容易调用或隔离就将其选为被测单元。没有独立契约的私有辅助函数、简单转发和内部拆分通过所属公开入口覆盖；生产接口的公开范围由实际调用和业务契约决定，不为测试另加包装或公开实现细节。

- 采用偏模拟派的测试策略。测试替身（test double）是主动隔离协作者、控制输入与故障、缩小失败范围的常规设计工具，不以“迫不得已”为使用前提。根据目的选择 `stub`、`fake`、`mock` 或 `spy`。

- 单元测试应优先断言被测函数的返回值、异常和它所拥有的状态变化。只有调用是否发生、调用次数、参数或顺序本身属于协议、安全或副作用契约时，才对 `mock` 或 `spy` 的交互进行断言；不要把内部函数调用图复制成测试预期。

- 测试替身应隔离稳定的协作者边界，而不是机械替换被测函数调用的每个内部函数。相同边界复用受真实接口约束的替身与装配，避免各测试文件重复维护模块替换、内部调用顺序和生产状态定义。仅改变内部组织而不改变行为契约时，测试原则上不应大范围修改；小幅生产调整反复引发大量替身或交互断言维护时，先检查被测边界，不能继续叠加适配来维持这种耦合。

- 测试替身必须受真实接口约束，并覆盖合法返回、错误和边界状态，避免替身行为与真实实现漂移。凡是被替身隔离的重要协作关系，都必须有相应集成测试验证真实双方可以共同工作。

- 单元测试应快速、确定且在同一进程内运行；除解释器导入被测源码，以及加载随代码版本固定的只读类型定义（如枚举、事件登记和错误码）外，不访问真实文件系统、网络、数据库或用户级全局状态，不启动子进程，也不执行包构建、安装或解析。涉及这些真实边界、完整分发物、工具缓存或多进程并发的测试属于集成测试；集成测试可以耗时较长，但必须与单元测试分开执行并保留明确的失败诊断。

- I/O 隔离或集成测试的执行限制不改变测试边界要求。行为必须由真实协作者组合才能证明、当前又未获准执行时，明确记录待验证范围；不能拆出私有实现片段并逐层替换内部函数，把这些结果当作原行为已经验证。

- 判断多个测试目录能否合并到同一进程、多个测试进程能否并行时，分别检查进程内可变状态和进程外共享资源（如文件路径、端口及工具环境）。只在实际共享边界尚未隔离时要求串行；使用不同工作区或独立资源副本后，仍须按剩余共享边界判断，不能据此宣称整体并发安全。验证结论应说明实际执行的会话、命令、范围、结果和退出码；临时调试输出遵守[临时调试材料](writing.md#临时调试材料)的留存规则，前台运行本身不提供隔离。

- 测试应从行为契约和状态分类独立推导，而不是复制实现逻辑。根据风险覆盖合法、非法、边界和状态转换；测试预期不得依赖被测代码中的同一计算路径。开发时优先用能够证伪契约的最窄行为分区完成红—绿—重构循环；“最窄”不表示直接测试最深层私有函数，也不表示每条评审案例都另建一组测试。只有跨边界行为无法在单元层证明时才从集成测试开始。

- 新增测试应对应新增行为、现有覆盖缺口或已证实的回归风险。同一行为及失败分区已有等价覆盖时，优先复用或补充原用例。测试准备与维护复杂度应与风险相称；测试结构整理按当前任务的授权范围和优先级推进，不因发现耦合就默认开展全面重构或推迟生产业务接通。

- 测试评审同时检查行为覆盖、边界稳定性、替身复杂度和重复覆盖，不能只检查隔离及通过结果。验证数量用于说明实际验证范围；实现进度按[计划执行与进度控制](implementation.md#计划执行与进度控制)核对生产调用与可观察结果，不以用例数量或通过率代替业务完成度。

- 错误诊断测试须观察公共消费者实际交付的错误事实、次数及输出，不能只断言某个日志辅助函数被调用。真实队列、文件、工作线程和进程组合属于集成测试；验证满载与取消时，同时证明必要停止、原结果和资源收场可以推进。

- 测试必须区分机器使用的数据和人类阅读的文案。错误码、字段名、退出码等机器协议应精确断言；可翻译或仅供阅读的文案，默认验证输入事实是否正确呈现，以及输出的结构、顺序、数量和特殊字符处理是否正确，不应逐字比较，也不应在多个测试层重复验证同一文案。只有需求明确要求某段文案逐字不变时，才在最接近用户输出的一层测试中精确断言一次。

- 验证模块之间的依赖限制时，不要只搜索源码中有没有某段文字，因为注释、换行、别名等都可能造成误判；应直接检查实际的导入关系、代码结构或运行行为。

## 集成测试的接口边界

- 集成测试通过被测模块的公开接口验证功能，以文档明确约定的函数、对象、命令、协议或文件契约为边界，不限定接口形式。先说明输入从哪里提交、由哪些真实模块处理，以及通过返回结果、报告、文件或持久化事实核对什么行为。跨组件测试优先使用真实分发物和这些正式入口。

- 集成测试选择最小而有意义的真实模块协作范围。公开接口不等于更高层入口；测试某个模块时，不能仅因完整会话或 CLI 能触发目标，就默认经过多层业务流程准备状态。过长的准备链会扩大依赖、增加耗时，并使一处实现变化引发大量无关失败。测试辅助代码可以集中必要准备，但不能掩盖这些耦合。

- 所需调用方式没有公开时，先评估模块职责与接口设计是否合理，而不是向更高层不断绕行。记录要验证的行为、现有接口为何无法独立表达、建议怎样调整以及影响哪些测试，等待后续接口改进；其他具有明确接口的工作继续推进。接口缺口本身不等于生产功能缺陷，不能仅靠补写文档将内部实现声明为公开接口，也不能为完成测试迁移擅自修改生产代码。

- 公开入口以行为规格、接口文档和正式调用方的约定为依据，不能因为某个 Python 类或函数可以被导入，就将它视为公开接口。功能集成测试不得直接拼装内部运行对象、调用私有推进函数，或操纵内部待保存集合来代替正式入口。内部协作和状态分支由相应局部测试承担；真实协作验证仍从所属模块的公开入口执行。

- 内部实现改变、对外行为保持不变时，功能集成测试原则上保持不变。测试所需的环境创建和正式入口调用集中在少量测试支持代码中，不在大量用例里重复构造运行时、数据库执行器和后台流程。不得为了保留旧测试而给生产代码增加测试专用入口、暴露内部状态或恢复已经取消的内部参数。

- 测试准备和故障注入也须核对边界。业务场景默认经公开入口建立合法状态；验证存储模块自身契约时，可以按其明确的存储格式准备与检查数据。需要中断、未知提交或工具故障时，在有契约的文件系统、存储执行或外部工具边界注入，并保留正式业务入口到可观察结果的验证。不能靠直接修改内部状态替代整个恢复过程。

- 功能断言针对对外行为，不绑定 SQL 的空格或列书写顺序、私有缓存名称、内部对象构造方式和函数调用图。专门验证分页、容量或事务边界的用例应明确声明该目标，并检查实际边界；有明确上限的分页读取不能仅因调用 `fetchall()` 就被判为无界全量读取。

- 模块公开契约变化时，同步核对正式生产者、消费者和共享测试支持，并运行受影响的完整集成范围。单元测试或选定业务链通过不能替代这项核对。测试在准备、构造对象或等待条件建立之前失败时，明确记录目标操作尚未执行；先找共享首因，再统计受影响的参数实例，不能将大量装配错误解释为同等数量的业务功能缺陷。

- 对既有集成测试进行大规模重构、迁移或删除前，先列明原行为目标、公开入口、保留的失败与恢复分区以及覆盖承接，与用户讨论后推进；不得通过统一放宽断言或修改生产接口消除维护成本。

## 控制集成测试成本

- 优化测试耗时默认只调整测试侧内容，例如测试用例、测试夹具、测试配置和测试运行器。用户要求继续优化时，按已经授权的范围推进；测试通过或预期提速不能替代生产修改的授权。

- 常规测试重构按业务预期修改后，直接在已就绪的环境中运行受影响范围。首次使用环境时确认解释器及源码位置；只有环境配置变化、导入或依赖异常等具体疑点时，再补环境诊断。不把重复环境检查作为每批重构的前置流程。

- 验证范围由实际改动、受影响的调用方与协作者，以及尚未覆盖的风险决定。优先运行能够验证这些行为的完整相关范围；已有完整回归中未受本次改动影响的结果可以复用。相关范围通过后，仅因新的改动、失败或具体疑点追加验证，不将全量回归作为每次修改、评审、提交或计划收尾的默认门槛。此前全量有一项失败，修复后也不自动重跑所有未受影响的测试；补验与原全量结果分别记录，不能拼成一次全量成功。

- 长时间验证启动前，先向用户说明它还要排除什么风险、已有结果为什么不足、预计墙钟时间、资源占用及对后续工作的延迟，并比较较窄范围能否提供同等证据。只有存在较窄验证无法覆盖的实质风险，或用户明确要求、已确认的验收要求需要时，才安排全量回归。模块被多处调用、计划有未完成复选框，或希望得到一个全绿结果，都不足以单独证明追加全量的必要性。确有必要的全量安排在明确的集成点，不随每批小改动重复执行。

- 验证运行中如发现范围重复、成本明显变化或原疑点已由其他证据消除，按剩余验证的价值重新判断继续、缩减或停止；已经投入的时间不能作为继续的理由。用户已经明确要求的验收范围需要调整时，先说明影响并取得对应决定。停止的运行如实记录已完成、失败及未执行范围，不认定为完整通过。

- 验证与记录按实际问题安排。记录受测提交或实际差异、准确命令、范围、结果及耗时；全量文件指纹、全部数据库前后对照和重复基线不是默认门槛。需要定位输入变化、证明同负载性能差异或核对发布来源时，再增加对应的专项证据。

- 重构保留行为契约，先判断旧测试准备和断言的有效性。启动窗口、超时与重试预算、取消顺序、恢复身份及提交语义等有效条件应保持；旧辅助函数随手指定的绝对时间、内部集合形状等偶然细节不自动成为需求。调整这类准备时说明依据，并继续通过公开结果验证原有功能和失败恢复目标。

- 计时发现生产路径存在瓶颈，且当前授权未涵盖相应生产实现或正式运行配置的修改时，先向用户单独说明测量证据、拟改内容、影响范围和验证方案，取得明确同意后再实施。生产性能优化单独推进，测试侧不依赖该决定的优化继续在原范围内执行。

- 写测试前说明需要真实组合的协作者及可观察结果。局部输入分类、精确数值和纯状态判断优先在单元层覆盖；集成层保留真实输入、资源登记、持久化和消费之间的协作见证。只有找到等价输入、预期和失败分区的承接用例，才能删除重复测试。模块导入的资源读取须按用途核对：只为初始化固定类型定义的读取可以保留在单元测试，但不得声称完全没有文件访问；依赖部署目录、用户配置、业务文件或运行期资源的组合属于集成测试。资源定位、缺失、发布和内容一致性的真实验证也属于集成测试。

- 将构造真实世界、执行被测操作及核对结果分别计时。辅助函数在测试体内建库或拍摄，其成本仍属于准备；pytest 的 call 时间不能直接解释为目标操作成本。先测实际调用次数和数据量，再决定如何减少测试中的重复准备与执行；生产路径的优化按上述范围要求单独处理。调用栈中多次出现同一页，不足以单独证明可以取消完整性验证。

- 相同只读来源可以服务多个具有独立业务身份的消费者。成功提交会改变后续语义时，为每个消费者保留独立状态，或从同一只读基线创建完整独立副本。拒绝矩阵在同库循环前，必须确认操作完整回滚或只读；每个输入后检查事务结束及相关状态不变，并在失败信息中标明具体输入。取消、worker 实际结束、文件生命周期及未知提交恢复各自保留真实边界。

- 复用跨进程的完整来源时，同时核对数据库内容、持久日志模式、路径绑定、远端与工作文件、客户端数据、时钟和可变内存状态。SQLite 数据行摘要相同不能代替持久模式与已提交 WAL 的核对。使用相同物理路径恢复副本前，先关闭父测试进程的连接，核验已登记的世界进程及执行组已收场，并完成本次消费者的结果核对。资源核验以测试实际拥有的对象为边界。

- 同一真实客户端可以依次承担计划、上传和报告确认，世界之间保持独立存储及进程。专门验证重开的步骤仍须关闭并重建实际协作者。会话的操作身份、失败回执、超时和关闭均须有界，并记录启动、操作和收场耗时；按协议明确控制连接与进程的关闭顺序，避免双方互等。测试私有接缝只保留当前调用需要的适配逻辑，命令分派及其参数约束由一个权威入口维护。

- 独立守卫根据内核提供的实际数据库事实独立比较提案与业务规则，不沿用提议者的通过结论。规划、生成和守卫可以共用内核拥有的固定事实读取；独立判断不要求独立执行相同 SQL。事实首次形成或实际改变时验证其来源，普通消费按所属责任检查已保存事实及直接关系，不把整个旧来源链审计作为默认前置。保留有限和有界入口的伪造结论、实际当前依据改变、未来提案冒充前序、不同边界混用及错误传播反例；共享事实不能掩盖这些变化。

- 用例规模由被测边界决定。分页或写批测试至少真实跨过对应边界；缓存溢出、磁盘容量和增长曲线测试保持声明的规模及测量窗口。可以减少重复构造，但不能以降低规模、缩小生产容量或替换实际提交来维持原验收名称。完整验收和日常选择分别说明，未执行的覆盖不计作优化后的通过。

- 用可控时间和明确同步点推进业务状态。测试确实需要验证驱动等待所使用的真实单调钟时，保留该时间见证；其他调用不能随意继承长等待。等待成功条件时，同时检查本请求或本次执行中已经使成功不可能的不相容终态、明确执行错误，并立即保存诊断。正常子进程退出本身不一定表示失败，也不能只因仍有 host 进程就忽略 CLI 子进程错误；合法成功预算不因提前失败优化而缩短。

- 成功或恢复场景的启动窗口不应同时承担客户端导出、进程初始化和初始报告准备的耗时。需要隔离这些准备时，只在测试装配边界显式控制业务 UTC 与单调钟，取得真实 START 或既定在途门闩后再从同一对读数推进；保留原窗口、真实写入和后续等待。父进程、主程序及故障门的超时继续使用真实单调钟，未来等待、过期和真实驱动等待专项另行保留。中断点由原行为契约决定，不能因增加观察能力就推进到另一个在途操作阶段。

- 按真实共享资源决定串行边界，按隔离后的任务安排并发。进程内注册表与进程外资源分别检查；具体入口和隔离方法由组件运行指南维护。依赖在确认可安全只读共享后复用；源码副本只携带本次运行所需内容，避免重复复制历史运行输出。长任务记录当前测试身份、已完成结果和退出码，不以缓冲日志最后一行推测当前执行位置。

- 测试执行者负责本次创建的源码副本、安装环境、构建目录和私有缓存的收场，运行结束后及时释放不再需要的目录。未解决问题的临时调试材料按[写作规则](writing.md#临时调试材料)原地处理，其余生成物不随历史运行永久累积。

- 对照结果同时说明源码身份、环境、范围、节点与合同变化、计时口径和失败归因。整轮墙钟、各进程耗时之和与单项阶段耗时分别记录；带诊断包装的耗时、单次采样及不同同期负载不能直接外推为稳定提速比例或目标硬件结论。

- 优化和重构既有集成测试时，持续更新[问题复盘与编写示例](../../docs/camctl/integration-test-lessons-2026-10-27.md)。发现新的可复用问题时，记录实际过程、原因依据、修正情况和避免方法，同时记录重构自身的失误；同类问题引用既有条目，不为每批结果重复更新复盘。当前计划、进度、接口问题和验证结论只在[工作记录](../../docs/camctl/integration-test-refactor-2026-10-26.md)维护，不另建平行摘要或规则清单。临时日志、收据及现场文件按[写作规则](writing.md#临时调试材料)留存与清理。

- 验证整个程序的内存预算时，遵守[内存预算测试](../../docs/camctl/memory-budget-testing.md)，由测试侧统一配置并对被测进程及其全部后代计量。测试准备与断言留在组外，核对内存与交换空间的实际合计限额、合计峰值、内存不足事件及完整业务结果；严格无交换能力另行验收。sudo 仅用于本次专属资源组委派及其收场，测试和业务保持调用用户身份；控制器或权限不足须明确报环境错误。单个解释器的分配追踪、定时采样、单次取行上限和小规模峰值差，均不能单独替代整个程序预算验收。
