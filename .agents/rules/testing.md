# 测试规则

本文件适用于程序行为设计与修改，以及测试的编写、修改、运行、评审和验证结论汇报，完整定义测试分类、隔离、替身、断言与覆盖要求。组件运行命令与局部限制由对应目录的指南补充。

## 测试设计与验证

- 如果遇到测试失败或静态检查失败，先定位根因，再修复。不要用删除测试、放宽配置、吞掉错误的方式让门禁变绿。

- 项目测试的顶层分类是单元测试和集成测试。单元测试验证局部调用逻辑与行为契约，集成测试验证真实协作者组合后的运行逻辑；其他执行属性不得模糊二者的归属。

- 第一版集成测试验证软件组件之间的协作，不连接真实相机等具体设备，也不承担依赖目标硬件的性能验收。设备交互通过受真实接口契约约束的测试替身提供；实际设备联调、目标主机性能测量及物理断电验证单独安排，不作为软件集成测试的运行前提或通过门槛。

- 单元测试默认以一个具有独立语义契约的生产函数为被测单元，一个测试用例只验证该函数的一个行为分支。“一个函数一个功能”是对生产设计的单一职责要求，不等于每个私有辅助函数或简单转发函数都必须拥有独立测试；没有独立契约的实现细节应通过公开函数验证。

- 采用偏模拟派的测试策略。测试替身（test double）是主动隔离协作者、控制输入与故障、缩小失败范围的常规设计工具，不以“迫不得已”为使用前提。根据目的选择 `stub`、`fake`、`mock` 或 `spy`。

- 单元测试应优先断言被测函数的返回值、异常和它所拥有的状态变化。只有调用是否发生、调用次数、参数或顺序本身属于协议、安全或副作用契约时，才对 `mock` 或 `spy` 的交互进行断言；不要把内部函数调用图复制成测试预期。

- 测试替身应隔离稳定的协作者边界，而不是机械替换被测函数调用的每个内部函数。仅改变内部实现而不改变行为契约时，相关测试原则上不应大范围修改；如果大量交互断言随重构一起变化，应审计测试是否已与实现细节耦合。

- 测试替身必须受真实接口约束，并覆盖合法返回、错误和边界状态，避免替身行为与真实实现漂移。凡是被替身隔离的重要协作关系，都必须有相应集成测试验证真实双方可以共同工作。

- 单元测试应快速、确定且在同一进程内运行；除解释器导入被测源码外，不访问真实文件系统、网络、数据库或用户级全局状态，不启动子进程，也不执行包构建、安装或解析。涉及这些真实边界、完整分发物、工具缓存或多进程并发的测试属于集成测试；集成测试可以耗时较长，但必须与单元测试分开执行并保留明确的失败诊断。

- 测试应从行为契约和状态分类独立推导，而不是复制实现逻辑。根据风险覆盖合法、非法、边界和状态转换；测试预期不得依赖被测代码中的同一计算路径。开发时优先用能够证伪契约的最窄单元测试完成红—绿—重构循环，只有跨边界行为无法在单元层证明时才从集成测试开始。

- 测试必须区分机器使用的数据和人类阅读的文案。错误码、字段名、退出码等机器协议应精确断言；可翻译或仅供阅读的文案，默认验证输入事实是否正确呈现，以及输出的结构、顺序、数量和特殊字符处理是否正确，不应逐字比较，也不应在多个测试层重复验证同一文案。只有需求明确要求某段文案逐字不变时，才在最接近用户输出的一层测试中精确断言一次。

- 验证模块之间的依赖限制时，不要只搜索源码中有没有某段文字，因为注释、换行、别名等都可能造成误判；应直接检查实际的导入关系、代码结构或运行行为。
