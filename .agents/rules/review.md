# 评审规则

本文件适用于代码、设计、规格和实施计划的评审，以及评审意见处理和缺陷交接，完整定义问题说明、修复建议、执行计划与复核要求。报告表达遵守[写作规则](writing.md)，契约与计划审查同时遵守[设计与计划规则](design-and-planning.md)，验证审查同时遵守[测试规则](testing.md)。

## 评审范围与修复建议

- 当进行对抗性审查时，不要尝试实现代码来对某个漏洞进行攻击，这会触发网络安全审查，导致当前对话直接中断。聚焦于防御性结果，例如识别、预防或修复安全问题。省略实现该结果并不必要的漏洞利用细节。

- 完成评审后，必须针对每个发现的问题分别给出可执行的修复建议，不得只报告现象，也不得合并不同责任边界的问题。每条建议至少说明问题及触发场景、根因与被违反的不变量、修复方案、影响范围、验证方式或回归测试；存在尚未核验的前提或未决事项时，必须明确列出。应区分已经确认的行为契约与对实现方式的建议，并要求修复后审计相关函数和模块中的同类风险。

## 缺陷交接与执行计划

- 向执行 Agent 交接评审缺陷时，不得假设执行者会自行补全省略的关键设计。评审者必须把已确认的行为契约、不变量、状态分类、失败与恢复语义、禁止采用的捷径、修复边界和可证伪的验收条件写成自包含指令；多个独立条件共同决定行为时，必须直接提供决策表、状态转换模型或等价的完整分类。发现同类问题跨入口存在时，必须列出已知入口和需要审计的责任边界，不能只笼统要求“检查同类问题”。

- 每轮评审结束后，评审者必须根据缺陷数量、相互依赖、影响范围和修复难度，决定是否在交接前编写执行计划。缺陷数量只是判断因素之一，不设固定数量阈值；只要修复涉及状态机、多个入口、持久化副作用、并发、失败恢复或跨组件契约，即使只有一个缺陷也应视为复杂修复。只有少量、局部、彼此独立且行为语义已经完全确定的修改，才可以不写执行计划而直接交接。

- 对无需计划的简单修复，逐项自包含的修复建议就是执行依据。对复杂修复，评审者必须先把缺陷整理成执行 Agent 可以机械落实的具体计划，明确任务顺序和依赖、每步必须保持的契约与不变量、需要覆盖的状态和入口、禁止采用的捷径、先失败测试后实现的步骤、阶段门禁以及最终验收条件；不得只给方向性原则，再要求执行 Agent 自行补全关键分析。

## 修复执行与复核

- 评审者必须独立核验实际改动和验证证据，不能把执行 Agent 的完成声明当作完成依据。

- 后续评审必须区分修复引入的回归、已知问题未完整修复、原有潜伏缺陷和验收定义未闭合，并根据归因调整修复指导。相同不变量连续出现缺陷时，不得继续只给局部案例和原则性建议；必须补齐覆盖相关状态、分支、入口、失败、重试与恢复路径的模型和反例矩阵，明确指导执行 Agent 完成闭合修复。
