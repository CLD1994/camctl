# Agent 调度规则

本文件适用于协调多个 Agent 的工作，规定调度者如何划分共享责任、传递约束和跟踪交付。工作区隔离、测试分类和计划进度分别以[实施规则](implementation.md)和[测试规则](testing.md)为准。

## 任务划分与整合

- 派发实现前，先核对任务是否修改同一组业务事实及其生产者、消费者，例如同一读取票据的调度、持久化、取消和恢复。不同文件或不同 worktree 不等于责任独立。对需要共同演进的事实指定一位实现与整合负责人，让其他 Agent 以只读审查或明确互不重叠的任务协助；责任边界改变时及时调整分工。
- 各任务交接明确基线、负责的事实和接口、依赖的未完成任务以及实际使用者。需要对方继续修改时，先核对其运行状态：向已完成或空闲的 Agent 交付新任务，不能把普通消息当作重新启动任务。整合负责人按依赖核对跨分支契约后再向后续任务提供基线。
- 评审发现问题时，调度者先核对触发条件和现有事务的反证，再指定单一修复负责人。已经证明不成立的发现应及时撤回；已有独立审查结论和通过的测试只在新改动影响其范围时重新验证。
- 指定模型和思考强度时，在子代理任务名中同时标明二者，使调度记录可读；模型选择遵守[对应身份的约定](agents/codex.md)。

## 验证约束与状态

- 用户限制验证范围时，调度者在每次派发和后续任务中说明禁止的具体行为及项目对测试边界的判定。若禁止读取真实包资源，测试须在导入受测代码前阻止该访问并隔离协作者；不能仅凭测试目录或文件名判断。协调者收到命令与执行结果后核对实际范围；发生越界时立即停止、告知用户并在验证记录中保留事实，不将结果计为符合要求的验证。
- 用户调整阶段完成条件时，及时将新条件写回正式计划，区分代码和单元测试、组合验证、人工验收各自的状态。满足用户指定的阶段条件就更新对应 checkbox（复选框）；未执行的验证单独保留为待办，不能阻挡用户已明确允许完成的阶段，也不能被表述为通过。
- 共享代码可能影响其他设备或业务路径时，在调度和交付前列出实际调用入口、驱动限定条件和必要的局部回归范围。未运行的组合或设备验证保持未证实，不由单个设备分支或隔离单元测试推断。
