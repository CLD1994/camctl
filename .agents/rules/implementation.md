# 实施规则

本文件适用于功能实现、缺陷修复、代码重构与开发脚本修改，定义选型、数据流追踪、实现语义、异常处理及资源使用要求。实现前读取相关行为规格，并按[行为契约与状态分类](design-and-planning.md#行为契约与状态分类)将需求重述为可验证的契约；程序行为的验证同时遵守[测试规则](testing.md)。

## 实现与缺陷修复

- 技术选型先核实标准库和成熟第三方开源库的现有能力，优先复用能满足行为契约的实现。允许并主动评估第三方依赖，以适配程度、维护状况、部署兼容性和总体维护成本决定；自行实现通用机制前，须说明现有方案的具体缺口，将自有实现限定在必要的业务规则和适配范围。

- 修复缺陷时，不把评审或错误报告中的具体案例当作完整规格。应先识别被违反的不变量，再审计所有共享该不变量的状态、分支和入口，修复这一类问题，而不是只修复已展示的实例。

- 在修改代码前追踪相关数据流和控制流，包括生产者、消费者、正常路径、失败路径和恢复路径。优先在所有相关调用共同经过的最窄责任边界统一保证规则。

- 实现应直接表达协议或业务语义。不要用只适用于常见输入的启发式判断代替精确规则；不要为了修复当前问题进行无关重构、增加推测性抽象或引入不必要依赖。

- 对数量有限、会影响程序分支的字符串标识，应优先使用枚举（集中列出所有合法值的类型）或其他有约束的类型，避免到处手写；如果输入允许来自未来版本或外部系统，仍必须明确保留未知值的处理方式。

- 每个异常捕获、默认值、跳过、降级和清理分支都必须具有明确语义。无法证明安全的状态应停止并保留可诊断信息，不得静默解释为成功、不存在或无关。

- 不需要重复验证执行计划中明确已经验证过的信息，但是执行计划不保证绝对的正确性。在执行过程中发现冲突项需要明确列出。如果冲突项需要用户决策，则立刻停止执行并汇报。

- 存在尚未核验的前提或未决事项时必须明确列出。测试全绿不能替代对需求完整性的检查。

- 发现计划与代码事实不一致、可能的设计缺陷、规格未定义的状态、需要改变既定协议或无法满足验收条件时，按[实现中发现设计缺口](design-and-planning.md#实现中发现设计缺口)主动与用户讨论并补充规格，不得自行选择语义或用局部补丁绕过。

## Git 协作与工作区隔离

- 开始并行开发前，先检查并提交当前已授权的变更，取得干净基线。需要并行修改仓库的任务分别使用独立的 git worktree 和任务分支，并明确各自的基线提交、任务范围及工作区绝对路径。
- 执行 Agent 开始任务或切换工作区时，先用 `pwd`、`git rev-parse --show-toplevel`、`git branch --show-current` 和 `git status --short` 核对实际目录、分支及已有改动。后续命令显式指定所属 worktree 的工作目录，文件读写路径也以该 worktree 为准；相对路径基于已经核对的工作目录解释。
- worktree 只隔离仓库文件。依赖环境、测试数据、数据库及生成目录的隔离仍按对应组件指南和[测试规则](testing.md)核对；共享文件的实现和集成顺序由任务依赖决定。
- 按可独立审查的阶段提交变更。每次提交前检查完整 diff、暂存范围及相关验证结果，只纳入本阶段已授权的文件；提交后核对提交内容和工作区状态，并向协调者交付提交标识及验证范围。
- 协调者按依赖顺序集成已审查的阶段提交，并执行对应组合验证，再向后续任务交接新基线。分支和 worktree 的清理以改动已经集成、工作区没有待保留内容为前提。

## 修复边界与资源使用

- 用正确的逻辑覆盖错误，而不是打补丁。

- 资源使用通过数据结构和处理流程控制：按需加载、分批处理，限制缓存、队列及读写缓冲容量，减少重复读取、解析、编码和临时副本，及时释放已处理数据。实际资源消耗由测试与联调测量，并结合正确性和必要性能改进实现。

依据评审建议或执行计划修复时，同时读取[评审规则](review.md#修复执行与复核)，保持交接中确定的契约、不变量及失败与恢复语义。
