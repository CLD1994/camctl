# 写作规则

本文件适用于项目文档、规格、计划、详细技术解释与评审报告。中文表述遵循根工作规则中的[语言与表达](../../AGENTS.md#语言与表达)。

## 从经验提炼原则

- 先确定谁会使用这条规则，再按这个人实际要做的事选词。例如，“设计测试用例”指编写者决定要验证什么，“选择测试用例”也可能指执行者从已有用例中挑选要运行的项。界定职责时用“负责”，确实需要规定执行顺序时才用“先做……再做……”。
- 读者已经明确时，直接写要做的事。例如，给测试用例编写者的指引可以写“先查看已有的测试辅助代码”。如果还要描述程序的行为，就写明由谁执行，例如“提交无效订单后，检查支付接口返回的错误码”。这里由读者提交和检查，由支付接口返回错误码。
- 从案例中找出能用于其他场景的判断依据。可以换一个例子检验草稿，再考虑原例的前提不成立时，原则是否遗漏了读者仍须处理的情况。正文写出适用条件和判断依据，例子用来解释这些条件为什么重要。
- 一句话说不顺时，先把实际过程讲出来，再归纳原则。例如，接口 A 依次调用 B、C 和 D。即使调用顺序始终相同，A 处理 B 的结果时也可能用错状态，导致传给 C 的数据出错。顺着数据的去向推演，就能看出参数和状态如何影响 A 的输出与副作用。原则写清要验证哪些行为，具体工具留到介绍做法时再写。
- 写完后，站在没有参与讨论的读者立场上重读一遍。“有意义”“合理”等词把哪项判断留给了读者？如果这项判断会改变读者的做法，就写明读者可以依据什么来判断。如果删去一句话既不影响读者理解，也不影响读者行动，就删去它。

> 我心里有一个具体例子，却误以为读者看见一句概括，就能还原我省略的判断。

打磨测试规则时，作者用“有意义的边界情况”概括了一个分页接口的例子。接口约定每页最多可以请求 100 条记录，所以作者选了 100 和 101，分别验证接口能否接受刚好达到上限的请求、拒绝刚刚越界的请求。读者只看到“有意义”，无从得知作者为什么选这两个数。提炼成原则时，具体数值可以省去，选择它们的理由应该保留。

## 文档组织与职责

- 项目文档面向首次接触项目的维护者，以项目自身的行为、结构、约束和实施状态组织内容。概念首次出现时提供必要定义或对应文档引用，使读者仅凭文档即可理解和使用。

- 每项文档规则在其责任专题完整定义，其他文档通过引用使用；实施进度由对应计划跟踪，验证记录注明日期、环境与范围。

- 正式文档所需的行为契约、接口说明、实施步骤与进度必须保存在版本控制内，不得引用 `.superpowers/sdd` 等可随时删除的临时目录中的文档。临时调查形成的通用经验和正式决策应整理回对应责任文档；正式文档应能独立理解和使用，临时调试材料按下述规则处理。

文档用途与权威归属见[仓库文档分工](../../docs/architecture/repository-layout.md#文档分工)。编写规格或计划时同时遵守[设计与计划规则](design-and-planning.md)；评审报告同时遵守[评审规则](review.md)。

## 临时调试材料

- 开发、测试和问题排查产生的原始日志、数据库现场副本、临时运行输出等属于临时调试材料。这些文件及针对它们的内容摘要、清单、校验信息和路径引用均不进入 Git。正式验证结论、通用经验和需要维护的回归测试分别由对应文档与测试承载。
- 问题未解决时，临时材料保持用户原先放置的位置，其存在性由用户保证；Agent 不自行迁移、归档或补建丢失的现场。问题解决后，删除对应临时材料。
- 业务日志和业务数据库的保存遵守相应业务规格；正式测试使用的固定样本随测试维护。它们的保存要求不由临时调试材料的生命周期决定。
