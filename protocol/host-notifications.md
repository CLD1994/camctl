# CLI 向主程序发送通知的协议

[公共协议入口](README.md) · [电机动作语义](../docs/architecture/motor-control.md) · [host 回调接口](../docs/host-demo/implementation.md#按消息类型注册回调)

camctl CLI 在独立的单向管道中向 camctl host 发送 NDJSON（每行一个 JSON 对象）。host 解析消息并调用对应类型的主程序回调。主程序不处理 JSON，也不向 CLI 返回接收确认、回调结果或设备结果。本协议定义通知的机器表示、消息边界和通道行为；动作的发送时机、持久化及恢复由动作专题定义。

## 消息结构

每条消息为 UTF-8 编码的完整 JSON 对象，以一个 LF 换行字节结束。换行是消息边界；一次读取可以包含半条、一条或多条消息。对象内的换行字符须通过 JSON 转义表达，不能把一条消息排版为多行。对象成员名唯一，字符串使用合法 Unicode 标量值，不接受注释、非 JSON 数值常量或隐式类型转换。

| 字段 | 类型与用途 |
| --- | --- |
| `type` | 必填字符串，选择消息类型及其参数结构；电机控制使用 `motor_control` |
| `action_instance_id` | 必填，使用[公共对象 ID](../docs/architecture/plan-input.md#对象-id)表示，供内部关联和诊断，不传给电机回调 |
| `params` | 必填对象，按消息类型解析为对应回调参数 |

消息顶层只允许表中的字段。每个消息类型分别维护参数契约和 C 回调注册接口。新增参数或消息类型时同步更新发送方、host 解析及公开接口；未定义字段不能被当作已经执行的参数静默接受。

电机通知示例，文件中的这一行必须有结束换行：

```json
{"type":"motor_control","action_instance_id":"12","params":{"position":100}}
```

## 电机参数

`motor_control.params` 恰好包含必填字段 `position`。它是 JSON 整数，表示主程序定义的位置；C 回调参数类型为 `int`。目标 arm64 Ubuntu 18.04 的 `int` 为 32 位有符号整数，协议表示范围为 -2147483648～2147483647。这个范围只保证传输值可以精确交给 C 接口，不定义电机的业务合法范围。

客户端与 camctl 按该表示范围校验。计划输入和 host 收到的通知中，数学值恰为整数的小数或指数表示沿用[公共数值规则](../docs/architecture/plan-input.md#输入文件与基本值类型)；CLI 发出通知时将合法值编码为规范十进制整数字面量。例如 `1.0` 与 `1e2` 分别表示整数 1 与 100，均可接收；`1.00000000000000000001` 仍是非整数，不能因舍入而接收。host 精确读取该数学整数，检查 `INT_MIN`～`INT_MAX` 后转换，不能截断、溢出、按浮点近似或把布尔值、字符串转换为位置。

位置的单位、零点、方向解释及业务合法范围完全由主程序定义。字段省略、`null`、非整数、表示溢出或额外参数都是消息参数错误；合法的负数和零不得仅因符号被通信层拒绝。

## 通道与生命周期

host 在启动 `run` 前创建通知管道，将写入端交给该 CLI 进程，并明确告知其用途。描述符交接只作用于该子进程，不能修改主程序的标准流或全局环境，也不能把写入端继续传给 CLI 的设备工具及报告子进程。`run` 的接入参数为 `--host-notification-fd FD`。`FD` 是 3～2147483647 的 ASCII 十进制非负整数字符串，最多 10 位；0、1、2 属于标准流，不能用作通知通道。该参数只由 `run` 接受，省略表示未接入。描述符传递与此参数必须共同完成，只传数字不意味着进程拥有该描述符。

CLI 成功解析 `run` 后接管传入写端，在启动工具或报告子进程前禁止该描述符被继续继承。写端必须指向可写管道；CLI 将其设为非阻塞，一个 `run` 只持有一个串行发送器。CLI 在本次 `run` 结束时关闭写端；启动会话失败也要关闭已接管的写端。短写产生消息前缀后，CLI 立即关闭并停用该写端。host 持有对应读端，并在本次通道处理结束时关闭；双方分别关闭各自的端点，不关闭主程序标准流。

| 描述符或写入条件 | 分类及行为 |
| --- | --- |
| 非 `run` 使用接入参数；缺少 FD；FD 不是上述整数或指向标准流 | CLI 参数语法错误，遵守 CLI 的语法错误退出规则，不进入动作执行 |
| `run` 省略接入参数 | 通道未接入；普通动作继续，窗口内的电机动作按通道不可用失败 |
| FD 语法合法，但描述符未打开、不可写、不是管道，或无法完成写端设置 | 通道不可用；不把本次会话整体解释为 CLI 参数错误，电机动作保留可诊断的原因 |
| 完整消息不超过实际 `PIPE_BUF`，一次非阻塞写入成功写满 | 本地通知发送成功，只证明完整消息写入 |
| 消息超过实际 `PIPE_BUF`；管道已满；读端已关闭；写入返回错误 | 本次明确发送失败，不等待、不重试，不补造完整写入 |
| 一次写入返回的字节数少于完整消息长度 | 本次明确发送失败，保存实际字节数并关闭、停用通道；后续动作不能继续使用消息前缀所在通道 |

动作错误名称、阶段、编号及详情结构只从[公共错误登记](errors/workflow-codes.json)取得；通道不可用、明确发送失败和恢复时发送结果不确定分别登记。仅在实际发生系统调用错误时记录 `errno`；写入尚未开始时不补造已写字节，恢复未知时不推测字节数。

stdout 继续只承载命令规定的最终结果，stderr 继续承载诊断。通知不混入这两个通道，也不经过 `ready`、`processing` 文件交接。`submit` 不发送电机通知，不继承通知写入端。

未注册电机回调时，host 不为该功能启用通知通道。直接运行 CLI 而没有接入通道时，普通动作按各自规则执行；电机动作按其执行契约记录通道不可用。不能将通知打印到 stdout 作为替代。

每次 `run` 使用独立的通道和行接收状态。CLI 的完整消息写入必须串行化，不能让不同动作的字节交错。发送器不得因主程序尚未处理而无限等待；通道容量不足、已经关闭或写入出错时，本次发送明确失败。完整消息写入只证明本地写入成功，不证明 host 或主程序已经处理。

如果一次写入只留下消息前缀，发送方停止使用该通道，不能再追加其他消息形成一条新的合法行。host 在通道结束时拒绝不带结束换行的尾部片段，不能补换行后触发回调。已收到的完整合法消息独立处理，后续通道故障不撤销此前回调。

CLI 结束后，host 继续按有界流程处理该通道已到达的数据。完整消息的回调责任归 host；CLI 的退出码不取消这些责任，host 也不以等待主程序回调返回作为回收 CLI 进程的条件。下一次 `run` 不复用旧通道的半行数据。

原通知通道尚未读完时，host 保留该次调用的通道和有界读取状态；进程可以按既有规则回收，但本次 `run` 的调用位置须等到通道处理结束才释放。回调队列满时不能通过不断启动新的 `run` 累积旧管道。所有会话共用同一有界回调队列，旧会话已接收的完整消息仍按原入队顺序处理。

## 接收校验与分发

host 对每条完整行先验证 JSON 和公共消息结构，再按 `type` 解析参数。已注册回调的合法消息进入有界队列，由专用回调线程按接收顺序执行；C 参数转换完成后才调用主程序。队列中的数据由 host 持有，不能引用已经释放或复用的 JSON 缓冲。

| 收到的数据或本地状态 | host 的处理 |
| --- | --- |
| 尚未收到一条消息的结束换行，且未超限 | 保存有界前缀，等待后续字节，不调用回调 |
| 完整行合法、类型受支持、参数合法且回调已注册 | 入队并按类型调用回调，每条消息仅分发一次 |
| 一次读取包含多条完整行 | 按行顺序分别判断；未处理的字节保持在有界缓冲中 |
| 完整行存在重复字段、JSON 错误、结构错误、未知类型或非法参数 | 不调用回调，记录具体原因；下一条完整行独立判断 |
| 类型合法但没有对应回调 | 不调用其他类型的回调代替，记录未注册的诊断 |
| 单行超过容量上限 | 拒绝整行，按固定缓冲读取并丢弃至下一换行；不解析保留前缀，不影响之后的独立完整行 |
| 回调队列已满 | 保留已经接纳的消息，暂停该通知通道的读取，容量恢复后继续；不阻塞 stdout、stderr 或进程管理 |
| 通道关闭，剩余数据没有结束换行 | 拒绝尾部片段并记录诊断，不调用回调 |
| 回调已经返回 | 释放对应队列记录；返回不产生发往 CLI 的响应 |

解析错误与回调缺失发生在单向通道的接收侧，host 只能记录本地诊断，不能据此修改 camctl 已保存的动作结果或重新执行动作。host 不读取状态库、不按动作实例 ID 自动重放消息；CLI 按动作持久化规则保证不重发。

单行字节数、待分发消息数量和总缓冲字节数均须有固定上限，不能按会话持续时间累计全部通知。回调线程不得持有进程管理锁调用主程序。主程序负责回调自身及所访问状态的线程安全；长期阻塞的回调会延后后续回调，不能据通知窗口推断回调及时性。

host 随主程序运行，尚未调用或正在调用的回调责任只保存在内存中。主程序断电后不恢复队列；CLI 不根据这次丢失重发已经留下发送意图的动作。

## 共同机器定义与样例

[通知 Schema](schemas/host-notification.schema.json)的 `motor_params` 是计划输入、通知及有效动作报告共同引用的唯一参数定义。NDJSON 行边界、重复字段与 Unicode 标量值属于解析规则，Schema 不替代这些检查。

[共同夹具](examples/host-notifications/cases.json)保存原始 JSON 字符串与预期分类；[夹具说明](examples/host-notifications/README.md)区分接收合法性、计划分层受理和规范发送字节。Python 与 C 使用同一份通知输入，不重新维护整数边界或舍入反例。

## 验收边界

解析单元测试覆盖完整行、分段与多行、重复字段、非法类型、未知消息类型、整数边界、超限后恢复及截断尾部。回调注册与分发分别验证参数值、零次或一次调用和接收顺序。

真实管道和线程的组合验证覆盖队列满后恢复、回调执行期间继续提交计划及回收 CLI、写端关闭、CLI 退出后的已接收消息、独立会话之间的缓冲隔离。将这些结果与[电机动作恢复验收](../docs/architecture/motor-control.md#验收要求)组合，不能以假定回调成功代替真实双方协作。
