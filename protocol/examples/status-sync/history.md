# 录像与状态补齐样例的业务变化编号

[返回操作过程](README.md)

本页逐项列出同一主机的示例业务历史。每个数字对应一条已保存的业务事实，水位 0 表示尚无变化。它们用于解释样例报告的边界，不是生产运行测量值，也不规定实现必须采用相同的事件拆分。

计划受理事件包含该计划全部动作的初始状态和本计划内来源关联。计划执行阶段从动作历史计算，不另记编号。有效 ACK、报告登记和文件发布、同步责任的内部管理均不增加业务编号；动作开始和结果仍属于业务变化。

设备调用、拷贝和删除在数据库写事务之外执行。除表中说明的共同事务外，各条业务事件独立提交。报告采用的记录必须截止于一次完整提交之后，不能只包含同次保存中的一部分，例如只看到相机产物登记、却看不到录像终态，或只看到未知起点动作开始、却看不到它的失败结果。

## 第一天和第二天：各自录像并取回

两天均在 09:00 开始录像，可靠控制计时达到 60 秒后正常停止，09:02 开始取回。首次启动、停止、读取及摘要比较均成功；本例在一次进度提交中保存全部 8388608 字节。视频的实际媒体时长未检查。

| 对象 | 第一天 A | 第二天 B |
| --- | --- | --- |
| 请求 / 计划 | `req-sync-001` / `p-sync-001` | `req-sync-002` / `p-sync-002` |
| 录像动作 | `a-sync-101` | `a-sync-201` |
| 取回动作 | `a-sync-102` | `a-sync-202` |
| 相机原片 | `o-sync-001` | `o-sync-002` |
| 本次交付 | `d-sync-001` | `d-sync-002` |

| 保存的业务事实 | A 的编号 | B 的编号 |
| --- | --- | --- |
| 受理计划，保存请求、两个动作的初始状态及取回来源关联 | 1 | 21 |
| 录像动作开始执行 | 2 | 22 |
| 登记第 1 次启动尝试，随后调用设备 | 3 | 23 |
| 确认启动成功，保存计时起点及录像关联 | 4 | 24 |
| 可靠控制计时达到 60 秒，登记第 1 次停止尝试 | 5 | 25 |
| 确认停止成功，持续录像效果已停止，文件已写完 | 6 | 26 |
| 登记正式原片的身份、来源、大小及可用状态 | 7 | 27 |
| 录像动作成功，保存不需要修复的结果 | 8 | 28 |
| 取回动作开始执行 | 9 | 29 |
| 固定原片选择并取得读取资格 | 10 | 30 |
| 登记独立交付、实际文件名和工作文件关联 | 11 | 31 |
| 登记第 1 次读取尝试，取得相机拷贝机会 | 12 | 32 |
| 文件字节可靠落盘，保存完整进度 8388608 字节 | 13 | 33 |
| 确认源文件读取成功结束，释放相机拷贝机会 | 14 | 34 |
| 取得并保存原片的源端摘要 | 15 | 35 |
| 保存主机摘要与源端摘要一致的结果 | 16 | 36 |
| 交付准备完成，在同一事务解除对原片的读取依赖 | 17 | 37 |
| 保存交付发布意图 | 18 | 38 |
| 确认待传视频完成本地发布 | 19 | 39 |
| 取回动作成功；计划全部动作终态，计划完成 | 20 | 40 |

7、8 在同一个录像终态事务提交，27、28 也如此。报告边界不能取 7 或 27。第 15、35 条更新正式原片摘要，报告中的来源原片和交付因此表达同一个摘要。

报告 1 采用截至变化 20 的状态，没有既有确认，范围为 `(0,20]`。第二天计划携带报告 1 的 ACK，在事件 21 的受理事务中吸收，累计位置成为 20；报告 2 采用截至变化 40 的状态，范围为 `(20,40]`。

## 清理 A，随后从旧备份补齐

| 编号 | 保存的业务事实 |
| --- | --- |
| 41 | 受理清理 A 的计划 `p-sync-003`，动作 `a-sync-301` 为 `pending`；同次 ACK 2 使累计位置成为 40 |
| 42 | 清理动作开始执行 |
| 43 | 保存 `o-sync-001` 的删除意图及清理状态；已有取回完成，不再依赖相机原片 |
| 44 | 确认相机原片已删除，更新产物可用性、清理状态及本次逐项结果 |
| 45 | 清理动作成功，清理计划完成 |
| 46 | 受理同步计划 `p-sync-004`，动作 `a-sync-401` 为 `pending`；同次旧 ACK 1 保持累计位置 40 |
| 47 | 同步动作开始执行；同一事务查询报告 1，固定起点 20，登记同步责任 |
| 48 | 报告 4 完成本地发布，同步动作成功，结果引用报告 4；同步计划完成 |

报告 3 采用截至变化 45 的状态，普通下界为 40，因此覆盖 `(40,45]`。原片 A 变化，报告须携带该原片、来源录像动作和所属计划；A 的原取回与交付没有变化。

客户端恢复旧备份及导入报告发生在个人电脑上，不会增加主机业务编号。第 47 条保存了同步动作开始及本次同步要求。`B` 记下这次完整提交在全部数据库历史中的位置；因为数据库还记录 ACK 和报告管理等不增加业务编号的事情，不能把 `B` 直接当成业务编号 47。

报告 4 采用的记录已包含这次完整提交，最新业务水位为 47，有效同步起点为 20，因此覆盖 `(20,47]`。发布后保存动作成功，报告 5 采用截至变化 48 的状态，仍等待同步确认，覆盖 `(20,48]`。

## 补齐后清理 B，恢复普通增量

| 编号 | 保存的业务事实 |
| --- | --- |
| 49 | 受理清理 B 的计划 `p-sync-005`，动作 `a-sync-501` 为 `pending`；同次 ACK 5 将累计位置推进至 48，并结束本次同步责任 |
| 50 | 清理动作开始执行 |
| 51 | 保存 `o-sync-002` 的删除意图及清理状态 |
| 52 | 确认相机原片已删除，更新产物可用性、清理状态及本次逐项结果 |
| 53 | 清理动作成功，清理计划完成 |

报告 6 采用截至变化 53 的状态。没有有效同步责任，下界取累计确认位置 48，所以范围是 `(48,53]`。报告选择 B 的原片及所属父对象、清理 B 的计划；其他已有对象不因本次缺席而删除。

[未知起点附例](missing-report.md)接续本历史，使用 54～56。它与上述正常操作分开阅读，报告 7 的边界由附例中的完整事务说明。
