# 协议样例的业务变化编号

[返回客户端协议样例](../../../docs/architecture/client-protocol-examples.md)

本页列出协议样例所采用的业务历史，用于核对报告中的 `from_wm`、`to_wm`。先读主文的操作经过，需要知道某个数字从哪里来时，再查这里。

## 编号怎样计算

这些是为协议演练明确设定的历史，不是实际相机或生产程序的运行记录。每个数字对应下表中的一条应报告业务事件，依次从 1 编号；水位 0 表示尚无业务变化。正式实现的事件结构和拆分由[历史事件的粒度](../../../docs/architecture/system-foundations.md#历史事件的粒度)约束，不要求相同的两个动作总是得到相同水位。

本组样例采用以下事件边界：

- “计划受理”是一条事件，保存请求关联、计划及全部动作的初始状态，以及本计划内名称引用解析出的来源关联；某个动作受理时即失败，也保存在这次受理事实中。组取回在这里固定来源成员，执行时再选择各成员已经产生的正式产物。
- 动作开始、发起一次设备尝试、取得尝试结果分别保存。尝试失败且仍可重试时，该次失败记录也保存已确定的等待时间和保留关系；等待时间经过本身不另加编号。
- 计划的 `pending`、`running`、`completed` 从动作历史计算；动作变化引起的计划状态更新，不在这组历史中另记一条事件。报告因此携带计划快照，也不增加编号。
- 每次成功拷贝的小文件在本例中只提交一次完整字节进度；失败拷贝只提交一次 1 MiB 进度。实际分段更多时，会有更多进度事件。
- 登记、生成、发布状态报告，以及吸收有效 ACK 都不增加业务水位。`report_status` 动作自己的开始和完成属于业务变化，照常编号。

除特别标明的共同事务外，表中每条事件分别提交。共同事务内的事件不能被报告边界拆开；设备调用、文件读写和删除发生在数据库写事务之外，表中的“开始”先保存意图，“确认”保存已取得的结果。

## 正常录像的共同过程

下表的每一列是一段独立录像的具体编号。例如，样例一的录像依次使用 2、3、4、5、6、7、8；样例三的第二段录像使用 9 至 15。它们都首次启动、首次停止成功，可靠控制计时为 60 秒，媒体时长尚未检查。

| 保存的业务事实 | 样例一 `a-001` | 样例三 `a-201` | 样例三 `a-202` | 样例四 `a-302` |
| --- | --- | --- | --- | --- |
| 动作开始执行，进入 `running` | 2 | 2 | 9 | 10 |
| 登记第 1 次启动尝试，随后调用设备 | 3 | 3 | 10 | 11 |
| 确认启动成功，保存计时起点及本次录像关联 | 4 | 4 | 11 | 12 |
| 可靠控制计时达到 60 秒，登记第 1 次停止尝试 | 5 | 5 | 12 | 13 |
| 确认停止成功，持续录像效果已停止，文件已写完 | 6 | 6 | 13 | 14 |
| 登记原片的身份、来源、文件大小和可用状态 | 7 | 7 | 14 | 15 |
| 录像以 `succeeded` 结束，保存不需要修复的结果 | 8 | 8 | 15 | 16 |

每列最后两条事件在同一个终态事务中提交。例如，样例一的 7、8 必须整体可见。产物初始没有摘要，后续取回取得摘要时再追加对应变化。

## 样例一：从 0 到 20

| 业务变化编号 | 保存的事实 |
| --- | --- |
| 1 | 受理 `req-001`，保存 `p-001`、两个动作的初始状态及 `a-002` 到 `a-001` 的来源关联 |
| 2 至 8 | `a-001` 按上表完成正常录像，登记 `o-001` |
| 9 | `a-002` 开始执行 |
| 10 | 固定本次取回选择：来源 `a-001` 的原片 `o-001`，取得读取资格 |
| 11 | 登记独立交付 `d-001`、实际文件名及工作文件关联 |
| 12 | 登记第 1 次读取尝试，取得相机拷贝机会 |
| 13 | 文件字节可靠落盘，保存完整进度 8388608 字节 |
| 14 | 确认源文件读取成功结束，释放相机拷贝机会 |
| 15 | 取得并保存原片 `o-001` 的源端摘要 |
| 16 | 保存主机摘要与源端摘要一致的结果 |
| 17 | `d-001` 准备完成；在同一事务中解除对原片的读取依赖 |
| 18 | 保存 `d-001` 的发布意图 |
| 19 | 确认 `d-001.mp4` 已完成本地发布 |
| 20 | `a-002` 成功结束；据全部动作终态计算 `p-001` 为 `completed` |

报告 1 在事件 20 提交后冻结。此前确认水位为 0，所以区间是 `(0, 20]`。生成及发布这份报告不产生事件 21；样例五的新计划才继续这份业务历史。

## 样例二：从 0 到 1，再到 8

逐项编号直接列在主文的[样例二](../../../docs/architecture/client-protocol-examples.md#样例二单个动作参数错误其他动作继续执行)中：受理事件为 1，合法录像随后使用 2 至 8；7、8 在同一终态事务中提交。两份报告分别冻结在 1、8。

客户端确认报告 1 的输入在第二份报告冻结前被吸收，因此第二份报告下界为 1。没有这个 ACK，第二份报告仍须从 0 覆盖；录像产生的上界 8 不受 ACK 影响。

## 样例四：从 0 到 29

本例将本地相机**启动重试间隔配置为 1 秒**，每次拒绝及调用结束确认耗时不超过 0.1 秒，首次尝试于 09:00:00 开始。因此三次拒绝可以在计划规定的 5 秒启动窗口内完成。该配置只用于本场景；采用默认 3 秒间隔时，5 秒窗口会在第三次启动前耗尽。

| 业务变化编号 | 保存的事实 |
| --- | --- |
| 1 | 受理 `req-004`，保存 `p-004`、三个动作的初始状态及取回来源成员 `a-301`、`a-302` |
| 2 | 第一段录像 `a-301` 开始执行 |
| 3 | 登记第 1 次启动尝试 |
| 4 | 确认第 1 次启动被拒绝、未开始录像，调用已结束，安排重试 |
| 5 | 等待 1 秒后登记第 2 次启动尝试 |
| 6 | 确认第 2 次启动被拒绝、未开始录像，调用已结束，安排重试 |
| 7 | 再等待 1 秒后登记第 3 次启动尝试 |
| 8 | 确认第 3 次启动被拒绝、未开始录像，调用已结束 |
| 9 | `a-301` 因启动次数耗尽失败，无正式产物、无待停止的录像效果 |
| 10 至 16 | 第二段录像 `a-302` 按共同过程完成，登记 `o-302` |
| 17 | 取回动作 `a-303` 开始执行 |
| 18 | 确认 `a-301` 终态无产物，保存 `no_outputs` 失败项 |
| 19 | 固定 `a-302` 的完整产物选择 `o-302`，取得读取资格 |
| 20 | 登记 `d-302`、实际文件名及工作文件关联 |
| 21 | 登记第 1 次读取尝试，取得相机拷贝机会 |
| 22 | 保存完整进度 8388608 字节 |

## 样例五：接续样例一，从 20 到 40

样例一的报告 1 已完整保存，两个新计划携带的 ACK 被吸收后，确认水位为 20。本例报告 2 在报告 3 冻结前没有被确认，因此两份报告都从 20 开始覆盖。

| 业务变化编号 | 保存的事实 |
| --- | --- |
| 21 | 受理录像请求 `req-005`，保存 `p-005` 和 `a-501` |
| 22 | 受理维护请求 `req-006`，保存 `p-006` 和 `a-601`、`a-602`、`a-603` |
| 23 | 录像 `a-501` 开始执行 |
| 24 | 登记第 1 次启动尝试 |
| 25 | 确认录像启动成功 |
| 26 | 取消动作 `a-601` 开始执行 |
| 27 | 固定取消目标并保存 `a-501` 的取消标记及待处理项 |
| 28 | 为该录像登记第 1 次停止尝试，持续效果进入 `compensating` |
| 29 | 同步动作 `a-603` 开始执行，同次事务按报告 1 确定起点 20 并保存同步要求；停止调用仍在等待结果 |
| 30 | 报告 2 已发布，`a-603` 成功结束，结果引用报告 2 |
| 31 | 确认停止成功，录像持续效果为 `compensated` |
| 32 | 保存清理本次取消录像废弃内容的意图 |
| 33 | 确认废弃内容清理完成 |
| 34 | `a-501` 以 `canceled` 结束，无正式产物；`p-005` 为 `completed` |
| 35 | 保存取消动作针对 `a-501` 的逐项成功结果 |

| 37 | 清理动作 `a-602` 到达计划时间，开始执行 |
| 38 | 保存显式清理 `o-001` 的意图及该产物的清理状态 |
| 39 | 确认 `o-001` 已删除，更新其可用性、清理状态及清理逐项结果 |
| 40 | 清理动作 `a-602` 成功结束；`p-006` 为 `completed` |

报告 2 冻结在 29，覆盖 `(20, 29]`。其发布事实不增加业务水位；随后报告动作自身的成功产生事件 30。报告 3 冻结在 40，覆盖 `(20, 40]`，因此它可以包含事件 30 中的动作成功结果。

事件 38、39 改变样例一的原片，报告 3 因而再次携带它及其来源动作、计划。旧取回 `a-002` 和交付 `d-001` 没有变化，客户端继续保留旧记录。
